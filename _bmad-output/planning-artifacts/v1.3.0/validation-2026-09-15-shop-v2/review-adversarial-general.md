### C-1 · FR/NFR 编号与 v1.3.0 母版 PRD 撞号，追溯链会断
- **位置**：§4 开头「编号起点：全仓现有最大 FR-110……本版取 FR-111 / NFR-18 / A-22 起」；§5 NFR 编号说明
- **问题**：「全仓最大 FR-110」不成立。同版本 v1.3.0 的 App 母版 PRD（`1-3-0prd.md`，批次 A/B1/C 与 admin 主题都引用它）已经占了 **FR-111（里程碑庆祝）、FR-112（场所 UGC）、FR-113（内容详情）、FR-114（评论）、FR-115（灯箱）、FR-116（发布图片排序）、FR-117（Tailsonality）、FR-120（护照解锁）**。admin PRD 里「AB-17A 是 App 端 FR-112 的硬配套」「AB-18A 随 FR-120 交付」，batch-a PRD 的范围写的就是「FR-113/114/115/116/65/111」。本 PRD 的 FR-111 到 FR-120 在同一个版本目录里跟它们一对一重名。等 epics 的 FR 覆盖表、sprint-status、云端批跑 agent 按「V1.3.0 FR-115」取需求时，拿到的可能是灯箱，也可能是「待发货自助取消」。本 PRD 在 §5 已经批评过 NFR 两套编号空间撞号，自己又在 FR 上犯了一次。
- **建议**：先在 `dev_1.3.0` 和所有 `feat/1.3.0-*` 分支上 grep 出真实最大 FR / NFR / A 号，再重新编号；或者改用带主题前缀的独立编号域（如 `SV2-FR-01`），与 README「一主题一套」的约定保持一致。全文 FR 交叉引用（含 §8、§9、R-x）要一起替换。

### C-2 · ACT-1 的定性查询测不出最可能的故障，两分支判定树不成立
- **位置**：§4.1 ACT-1 SQL；§3「购买闭环」注；§7 R-1；§8.1 ACT-1
- **问题**：
  1. **没按用途过滤**。`payment_intents` 是五种用途共用的表（`VET_CONSULT / PAWCOIN_TOPUP / AI_UNLOCK / ID_HD / SHOP_ORDER`），`LIMIT 50` 取到的多半是问诊、充值的失败记录，跟电商无关。
  2. **没指定环境**。stag 上有支付模拟器，会人为造出失败（FR-111 验收里自己也写了「支付模拟器三分支」）。产品说的「好几个支付失败」是 stag 还是 prod，没有写。
  3. **漏掉了最危险的形态：卡在 `PENDING`**。回调没到、验签失败（GemPay 收款回调的验签公式曾缺文档）、channel 配错，这几种情况意图都会一直停在 PENDING，查询条件 `status IN ('FAILED','EXPIRED')` 根本看不到。
  4. **`EXPIRED` 分不清「用户没付」和「付了但回调没到」**。PRD 的推理是「EXPIRED 居多 ⇒ 体验问题」，偏偏最严重的「钱扣了、单没成」也会落进这一支，结论会被读反。
  5. `PaymentIntent` 注释写着付款窗 `expires_at`「仅 PAWCOIN_TOPUP 建单时填」，电商支付窗落在 `shop_orders.expires_at`（V20260818_0037），超时后是订单被取消。电商意图会不会被置为 `EXPIRED`，需要先核实；如果不会，这条查询对电商会系统性地查不到过期记录。
- **建议**：把 ACT-1 重写成一张定性表：`purpose='SHOP_ORDER'` + 明确环境（prod 为准，stag 另出一份）+ 纳入「PENDING 且超过 60 分钟」+ 与 `shop_orders` 的 CANCELLED/超时记录做关联 + **拿网关商户后台流水对账**（抓「网关已收款、我方未入账」）。判定树加第三支「回调 / 对账故障」，这一支的优先级最高。

### C-3 · 整份 PRD 押在 ACT-1 上，门控却只挂在 §4.1 一组
- **位置**：§3 注「本组在查清之前不进入排期」；§4.1「本组整体挂起」；§7 R-1「本 PRD 全体让路」；§8.1 ACT-1「整份 PRD 的优先级压在这一条上」，负责人「待指派」
- **问题**：三处口径互相矛盾。§4.1 只挂起「购买闭环」四条，R-1 说全体让路，§8.1 又只把它列为「阻断下游」表里普通的一行。按字面理解，§4.2 售后（退款、溢价，钱路径）、§4.3 批量改价/改库存都可以先开工。可如果支付本身是坏的，那些已付款订单的售后流程根本没有流量可验证，批量工具也不是瓶颈。ACT-1 用 psql 半小时就能查完，到现在还没指派负责人。
- **建议**：把 ACT-1 升为**整份 PRD 进入架构 delta 的硬前置**，指派具体负责人和日期（不写「建议 3 个工作日」）；在 frontmatter / §0 加一行「ACT-1 未闭合前本 PRD 不得进入 bmad-create-architecture」。结论出来后，把 PRD 分支（修体验 / 修支付 / 修回调）的优先级重排结果回写正文。

### C-4 · D-23「发货前取消没有任何库存回补路径」与代码事实相反，照做会双倍回补
- **位置**：§8.1【D-23 查证结果】全节；§4.2 FR-115 ①；D-23 行标「✅ 已闭合」
- **问题**：`AdminReturnService.executeRefund`（提交 `cbc1c2ea`，2026-09-04「发货前取消回补库存」，已在 `dev_1.3.0` 等分支）**已经做了回补**：首次执行、类型为 `CANCEL_BEFORE_SHIPMENT` 时，逐行调用 `movements.receiveReturn(...)`；拒收明确不回补（「货在承运商手里，何时入库是运营决定」）。PRD 说「`restock` 只经 `doInbound` 被三个手工动作触发」，漏掉的正是这条自动路径（`receiveReturn` → `doInbound` → `restock`）。于是：
  - FR-115 的实现要求第 1 条「必须补一次 restock」照字面实现，**会在现有回补之外再回补一次 ⇒ 账面库存虚高 ⇒ 超卖**。
  - 真正的缺陷其实是 PRD 第 2 条自己点到的：`receiveReturn` 调 `lastPurchaseCostPrice`，**对没有采购入库记录的 SKU 直接抛异常**。抛在 `@Transactional executeRefund` 里，整笔退款会回滚，**用户的取消退款卡死**。这是资金可用性问题，不只是库存问题。
  - D-23 被标成「已闭合、无需拍板」，下游不会再复查。
- **建议**：D-23 改回「未闭合」，按代码事实重写：①现状已有自动回补（引用 `AdminReturnService:210-221`）；②缺陷是成本价取不到时抛异常，阻断退款；③修法是改造现有调用（新增 `CANCEL_RESTOCK` 流水类型，或在取不到成本价时降级 + 告警），**明确禁止再加第二次 restock**；④加一条 L1 用例「无采购记录 SKU 的发货前取消能退款成功，且库存只 +qty 一次」。

## High

### H-1 · D-22 推荐「关激励溢价」等于让整个激励溢价功能下线，没有论证也没有留痕
- **位置**：§4.2 FR-116 `[ASSUMPTION 推荐…关闭激励溢价②]`；FR-118 验收；§8.1 D-22
- **问题**：`RefundExecutionService.incentiveApplies` 的门是 `type.isUndelivered() && thisCash>0`，而 `isUndelivered()` 只对 **CANCEL_BEFORE_SHIPMENT 与 REFUSED_ON_DELIVERY** 为真（D-16，2026-09-02）。按 D-16 的设计，激励溢价**只**服务这两支，用来引导「未交付退款的现金段转成 PawCoin」（浮存，AB-6C）。PRD 推荐对这两支关掉，结果就是 `premium_rate / premium_fixed` 这对配置从此没有任何生效路径，这是在推翻 C-1 / D-16 的设计，PRD 却把它写成「反套利门」。另外：
  - 「套利」没有量化。PawCoin 不可提现、不可转让（DEP-7 / FR-50D），激励是闭环币。真实风险是「没有现金垫底的赠币」（S-15、AB-6C），需要拿当前配置值算一笔最坏情况，而不是笼统写「拿双份」。
  - 「拒收拿双份」有误导性：补偿溢价的基数是 `split.thisCoin()`（币段），激励溢价的基数是 `thisCash`（现金段），两者不在同一个基数上叠加。
  - FR-118 验收写「PawCoin 到账额 = 应退额 + 补偿溢价」，默认了用户选的是 `TO_PAWCOIN`；选 `TO_BANK` 时的验收值没有写。
- **建议**：D-22 改成三选一，并明确每个选项的连带后果：(a) 关激励（写明「激励溢价功能整体下线」，补 decision-log 推翻 D-16）；(b) 保留，改加频次/金额上限；(c) 保留，自助入口只允许 `TO_BANK`。用当前 prod 配置值给出每单最坏溢价额。FR-118 的验收按 TO_PAWCOIN / TO_BANK 两种去向分别写。

### H-2 · FR-117 漏了 `DELIVERED` 态，而且与 FR-115/118 重复定义同一个入口
- **位置**：§2 UJ-4 ①；§3；§4.2 FR-117
- **问题**：后端 `requireReturnable` 允许 `DELIVERED` 或 `COMPLETED` 态在签收后 7 日内退货，App 却只在 `completed` 时渲染 `_returnBar`（`shop_order_detail_page_v2.dart:682`）。`DELIVERED` 态底栏只有「确认收货」，用户**必须先确认收货才能申请退货**。7 日窗口从签收算起，这是真实的卡点，FR-117 却只列了 `PENDING_SHIPMENT / SHIPPED`。另外，「待发货态可退款」就是 FR-115，「已发货态可拒收」就是 FR-118，FR-117 等于把它俩重复写了一遍。dev agent 可能做出三个入口，也可能把取消/拒收塞进普通退货表单（普通退货表单要求至少 2 张凭证图，且类型不对）。
- **建议**：FR-117 改为「`DELIVERED` 态提供普通退货入口（窗口内）」，并写明底栏的主次按钮（确认收货 vs 申请退货）。FR-115/118 各自负责自己的入口，删掉 FR-117 里与之重叠的部分。UJ-3「无新需求」的结论相应修正。

### H-3 · 「自助取消」名不副实：后面是人工审批 + 人工执行，且没有任何通知
- **位置**：§2 UJ-2；§4.2 FR-115；§4.4 FR-130
- **问题**：`CANCEL_BEFORE_SHIPMENT` 提交后订单立即变 `REFUNDING`（`ReturnRequestService.submit`），接着要等运营 `approve`、再手动 `executeRefund`。运营「靠人工打开页面盯」（UJ-5 ⑤），FR-130 只通知新订单，**不通知退货/取消申请**。结果是用户点了取消，订单被锁在 REFUNDING（既发不了货，也退不了款），可能几天没人处理。这比现在「不能取消」更糟。另外 `submit` 支持行级勾选，但 `skipsShipback` 类型会把**整单**推进 REFUNDING；部分取消之后剩余行怎么履约，没有定义。
- **建议**：FR-115 补三件事：①取消是否自动批准 + 自动执行（未发货、无实物往返，人工审批的价值很低），或给出人工处理 SLA；②FR-130 的触发范围扩到退货/取消/拒收申请；③限定发货前取消只能整单，或者定义部分取消后的订单状态。

### H-4 · FR-120「唯一路径」的论证不成立，而且严重低估了闭环缺口：用户看不到寄件地址和截止时间
- **位置**：§2 UJ-4 ④；§3 FR-120 注；§4.2 FR-119 / FR-120
- **问题**：
  1. 后台 `/admin/shop/returns/{token}/shipback` 仍然在，运营完全可以通过 FR-152 的 WhatsApp 深链拿到单号后代填。「兜底随之消失」「唯一路径」的说法不对（FR-120 仍然值得做，但理由要改）。
  2. S-7 规定：平台承担回程运费的情形（质量问题），用户要**上传运单凭证 + 实际运费金额**，报销才能执行。「轻量 bottom sheet 只登记单号」不够，得有金额输入、图片上传和截止时间 `shipbackDeadline`。
  3. **退货进度页出局以后，用户在哪里看到退货收件地址、寄回截止时间、审核结果？** FR-119 只在后台批准时拦截，没有任何一条 FR 负责把地址展示给用户。闭环照样是断的。
  4. 端点实际路径是 `/me/shop-returns/{token}/shipback`（`api_paths.dart:310`），PRD 写的是 `/shop-returns/...`。项目里出过「漏 `/me` 前缀导致列表恒 404」的事故。
- **建议**：FR-120 重写为「订单详情内的退货状态卡」：审核结果 + 收件地址 + 截止时间 + 登记单号（含运费金额与凭证，按回程运费归属决定是否必填）。端点写全路径。§3 那条「两条都成立、须拍板」的注释删掉，改为定稿口径。

### H-5 · FR-119 会误伤取消和拒收：不需要寄回的类型也被拦截

- **问题**：「退货收件地址未配置时阻断批准」没有限定类型。`CANCEL_BEFORE_SHIPMENT` 和 `REFUSED_ON_DELIVERY` 都是 `skipsShipback=true`，不需要地址。dev 照字面实现后，只要地址没配，FR-115 和 FR-118 的申请**全都批不了**，而现在三项地址恰好全空。
