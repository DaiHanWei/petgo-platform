# PRD Quality Review — PetGo 电商板块 V2（v1.3.0 · shop-v2）

> 评审对象：`_bmad-output/planning-artifacts/v1.3.0/PRD-v1.3.0-shop-v2.md`（status: draft，无 addendum）
> 评审基准：`.claude/skills/bmad-prd/assets/prd-validation-checklist.md`
> 评审日期：2026-09-15 · 利害等级：上生产级 · 下游：架构 delta → epics/stories → dev agent

## Overall verdict

这份 PRD 的**底子扎实，远超一般草稿**：愿景有真正能砍需求的判据（§1.1「理由是『能多卖货』就不做」），旅程是用代码行号取证的 brownfield 旅程，售后反套利（FR-116）与发货前取消库存黑洞（D-23 查证结果）两处的分析深度足以直接喂给架构。但它**还不能交给架构与拆 story**：① §8.1 仍有 6 条未闭合的「阻断下游」项且全部无负责人/无期限，其中 ACT-1 一条就可能让「整份优先级重排」；② 2026-09-15 的 WhatsApp 工作台范围收敛**没有扫干净**——§3 OPS-10、§3 FR-120 注、NFR-19、§6「客服可达」整行、R-2、§9 权限码行仍在引用已移出的 FR-132 / FR-132L / ACT-2，其中 §6 的客服指标在本版范围内**根本无法度量**；③ §4.3 从 7 条膨胀到 20 条后，§3 能力表、FR→UJ 追溯、优先级分层都没有跟上，40 条 FR 没有任何发布切片，下游 epic 排序无据可依。

## 1. Decision-readiness — adequate

决策的**陈述方式**是本 PRD 最强的地方之一：§1.2 的范围收敛写明「代价（已知并接受）：用户在 WhatsApp 上说的话仍进不了后台」，§1.3 的三条裁定每条带「连带后果」，§3「以下六项初稿既无 FR 也未排除（属静默丢弃）」主动补裁定——这是真实的取舍陈述，不是「平衡各方」式的中性化。§8 按「阻断下游 / 可延后 / 须向外通报」三档分层，结构也对。

问题在**决策的闭合度**。§8.1 标题自称「不定，则架构 / UX / 拆 story 无法开始」，而表内仍有 ACT-1、D-20、D-21、D-22、D-24、D-25 共 **6 条开放**，负责人一栏是「⬜ 待指派」或笼统的「产品」，期限一栏除 ACT-1 的「建议 3 个工作日」外全是 ⬜。更关键的是 ACT-1 不是普通阻断项：§4.1 与 R-1 都写明若查出 `FAILED` 带网关错误码，「整份优先级重排」「本 PRD 全体让路」——也就是说**本 PRD 的优先级本身是条件性的**，而条件至今未查。在 ACT-1 出结果之前启动架构，等于在可能被推翻的排序上做设计。

另有若干开放问题未进 §8 的着陆点，违反 §8 自己立的规则（「凡 PRD 中出现 ⬜ 或 `[ASSUMPTION]` 的，必在此有一行」），见下。

### Findings

- **critical** §8.1 阻断项 6 条开放且无人认领（§8.1）— ACT-1「⬜ 待指派」、D-20/21/22/25「产品 · ⬜」、D-24「运营 · ⬜ 开工前」。对一份要进架构的 PRD，这是直接的放行阻塞；且 ACT-1 的结果可能重排全部优先级（§4.1「整份优先级重排（R-1）」）。*Fix:* 先把 ACT-1 指派到具体人并执行（一条 SQL，§4.1 已给出），在 PRD 中回写结论与据此确定的优先级；D-20/21/22/25 各落具体负责人与日期；在 §8.1 顶部加一行「放行条件：ACT-1 已回写 + D-20/22 已闭合」。
- **high** D-24 被错放进「阻断下游」（§8.1 D-24）— 「深链用哪个号」是一个运营配置值（环境变量级），不阻断架构/UX/拆 story；放在 8.1 会虚增阻断数、稀释真正的阻断项。反过来 D-25（品类存量迁移）只卡 FR-141/142，D-21 只卡 FR-122，也并非全局阻断。*Fix:* D-24 移到 §8.2；8.1 内再区分「全局阻断」（ACT-1、D-22）与「局部阻断」（D-20/21/25，仅卡对应 FR 的 story，不卡架构总体）。
- **high** FR-115 的第二个前置未进 §8（§4.2 FR-115 ②）— 「批准期间被发货无守卫——`requireReturnable` 只在提交时校验，批准时订单已是 `SHIPPED` 会怎样需确认」是一个明确的开放问题，但 D-23 只闭合了 ①（库存回补），② 在 §8 无任何条目。*Fix:* 新增 D-34「发货前取消的批准时状态守卫」挂 FR-115，归「阻断」档（它决定状态机设计）。同时明确 FR-115 的自助取消是**自动批准**还是**需运营审批**——FR-115 ② 暗示有审批环节，但全文未说。
- **medium** FR-149 / FR-151 以 FR 身份出现、却「本版补不补待拍板」（§4.7、§8.2 D-27/D-28）— 一条 FR 是否在范围内都未定，下游无法判断要不要为它开 story；D-28 还依赖「本地税务顾问确认」这种外部、不受控的前置，却被归为「不卡开工」。*Fix:* 在 FR 行显式标 `[范围未定·D-27]`；给 D-28 设「若 X 日前顾问未回复，则默认口径为 ___」的兜底，避免无限挂起。
- **medium** UJ-1 ⑥「本版最想知道却没有数据的一格」无行动项（§2 UJ-1 ⑥）— 旅程自认这格「三种反应导出的优先级完全不同」，但 §4/§8 没有任何埋点或观测 FR 去获取它（项目已接 PostHog/AppsFlyer）。*Fix:* 要么加一条观测类 FR（支付失败/过期后 N 分钟内用户去向：重试/工单/深链/离开），要么在 §8 显式记为「本版不解答」。

## 2. Substance over theater — adequate

没有人设剧场（2 个主角、都驱动了决策）、没有创新剧场、愿景不可替换（「按能否跑通验收的，不是按好不好用验收的」是这个产品特有的判断）。代码证据密度高，`RefundExecutionService:222-258` 两条溢价、`InventoryService:46-82` 四原语的分析都是实打实的。

两处偏「furniture」：一是 **NFR 节几乎是空的**——4 条里 2 条划掉，剩下 NFR-19（含过期内容）与 NFR-20，整个版本没有任何性能/容量边界（批量导入行数上限、导出规模、C 端分页页长、Lark 通知时延），而 FR-122/127/129/144 恰恰是量级敏感的；二是**评审留痕文字大量留在正文**（「初稿把两者并成一句…已纠」「六份评审独立指认」「初稿整条蒸发，此为补回」等十余处），对 PM 是有用的变更史，对下游 dev agent 是噪声，且会把「已纠正前的错误说法」一并喂进上下文。

### Findings

- **high** NFR 节实质缺位（§5）— 仅 NFR-19、NFR-20 在役；无批量导入单文件行数/大小上限、无导出行数上限与超时策略、无 C 端商品列表分页页长、无 Lark 通知时延/节流上限、无对账明细下钻的数据量边界。*Fix:* 为 FR-122/127/129/130/144 各补一条带数值的 NFR（如「单次导入 ≤ 500 行、≤ 5MB，超限整体拒绝并提示」「新订单付款后 ≤ 5 分钟内送达 Lark，同一窗口内汇总」），数值可标 `[ASSUMPTION]` 待确认。
- **medium** 修订史混入需求正文（全文，尤见 §4.2 FR-116、§4.3 FR-142/145/146/147/148、§5 引言、§6 引言、§8 引言）— 「初稿…已纠」类表述约 15 处。*Fix:* 正文只保留当前结论；把「初稿错在哪」集中移到文末「修订记录」或 `.memlog.md`。
- **low** 🔴 标记通胀（全文 81 处）— 当几乎每行都是 🔴，它不再能区分「上线阻塞」与「值得注意」，与 rubric 所说「every NFR is important」同类问题。*Fix:* 🔴 只留给阻断项/资损/安全三类，其余降为 ⚠️ 或删除。

## 3. Strategic coherence — adequate

有明确论点：**本版是还债版，不追业务目标**，四条主线 A/B/C/D 从愿景直接推出，§1.3/§1.4 用这条论点砍掉了营销组、评价页、退货进度页、批量发货、猫砂——砍需求的逻辑一致，是论点在真正做功。

但论点与后补内容有三处裂缝。① **FR-146（药品注册号）与 FR-149~151（税务）不属于 A/B/C/D 任何一条主线**，也不挂任何旅程；它们是合规义务，放进本版无可厚非，但 PRD 应承认它们是论点之外的「强制项」，而不是混在「运营提效」与独立小节里。② **主线 D「用户为一笔订单找人时，有一条真的能走通的路」在本版范围内只有一半走得通**：工单路径下后台「四个动作里没有『回复用户』」（UJ-4 ③），FR-131 让客服知道是哪一单，但客服**仍无法在 App 内回复**——工单路径依旧是死胡同，真正走得通的只有 FR-152 深链。PRD 在 UJ-4 ③ 写了「工单仍是一次性表单」，却没有把「主线 D 的承诺因此只由深链兑现」讲清楚。③ **成功指标不验证论点**：§6 五条均无目标值、无度量方法、无 FR 映射，其中「客服可达」在本版范围内无法度量（见 §5 维度与机械项）。

### Findings

- **high** 主线 D 的工单路径在本版仍走不通（§1.2 主线 D、§2 UJ-4 ③、§4.4 FR-131）— 用户提工单 → 客服看到关联订单（FR-131）→ 客服无法回复用户。「一条真的能走通的路」只剩深链，而深链「后台看不到、无记录、无 SLA」。*Fix:* 二选一并写进 PRD：(a) 显式声明「本版主线 D 由 FR-152 兑现，工单路径仅改善客服侧定位，不闭环」；(b) 加一条最小 FR「后台工单『回复用户』动作 + App 通知」，让工单路径真正闭环。
- **high** §6 成功指标无目标、无方法、无 FR 映射，且自相矛盾（§6）— 引言写「这三条必须带阈值，不得以『待基线』搪塞」，表内**没有一个数值**；「运营效率」要求「现状各数一遍点击数写进本表」，也没写。支付可达/履约时效在订单量近零时无统计意义，R-5 已承认，但未给替代验收（R-5 提到「以可观测性就位替代」却没落成具体条目）。*Fix:* 运营动作数、缺陷存量两条当场填基线与目标降幅；支付/履约两条改为「埋点与报表就位」的可验收条目并各挂 FR-111/FR-130；每条指标加「验证 FR-x」。
- **medium** 合规类 FR 游离于论点之外（§4.3 FR-146、§4.7 FR-149~151）— 未挂主线、未挂旅程。*Fix:* 单列「合规强制项（不受 §1.1 砍需求判据约束）」小节，说明为何必须本版做（或为何可延后）。
- **medium** 40 条 FR 无优先级分层或发布切片（§4 全节）— 除 §4.1 挂起与若干「前置」关系外，没有 P0/P1/P2 或「第一批止血 / 第二批」划分；FR-145 自称「源清单判『高』、列第一批止血」，暗示源清单有分批，但 PRD 未继承。*Fix:* 在 §4 开头加一张「批次 × FR」表（至少分「止血 / 运营提效 / 可延后」三档），供 epic 排序直接取用。

## 4. Done-ness clarity — thin

头部几条 FR 的验收写得非常好：FR-111 把 FAILED/EXPIRED 分开处置并给出模拟器三分支验收；FR-118 给出可算的到账额等式；FR-122 的「解析失败的行不丢弃」「金额列拒收而非四舍五入」；FR-152 三条验收。这些可以直接变 AC。

但**中后段大面积失去可测性**。§4.6 与 §4.7 的表格干脆没有「验收要点」列；§4.3 的后补条目（FR-141/142/145/146）多数只有「为什么要做」，没有「做完是什么样」。以下按严重度列出下游拆 story 会直接卡住的条目。

### Findings

- **critical** FR-145 购物车部分结算无任何验收（§4.3 FR-145）— 只给了两种实现方向（「行加 selected 位，或下单接受 skuToken 列表」），未定义：未选中行下单后是否留在购物车；免运门槛/`shippingDiscount` 按选中行还是整车计；PawCoin 混合支付的可抵扣额按选中行重算；库存锁定只锁选中行；全部未选时的提交行为。这是资金链路改动，边界不写清就是资损点。*Fix:* 补 5 条以上可测后果，并与 FR-149（折扣分摊）交叉引用。
- **critical** FR-142 品类可配置无验收、且带未决数据迁移（§4.3 FR-142、§8.1 D-25）— 未定义：管理页 CRUD 范围、Species 是否一并可配、停用品类下存量商品如何处理、App 端品类筛选/复购引擎/推荐区是否依赖枚举、老版本 App 遇到新品类的降级（§9 第 5 条只点到「降级口径」未给口径）。*Fix:* 闭合 D-25 后补验收：迁移后三个存量值 ID 不变、老 App 遇未知品类显示为 ___、停用品类不出现在 C 端。
- **high** C 端商品列表改分页是破坏性契约变更，未提兼容（§4.3 FR-127 第三点）— `ShopProductController.list()` 现返回全量 `List`，改分页后线上老版本 App 会直接崩或只见首页。本仓已多次因「契约变更须前后端同批部署」出事。*Fix:* 在 FR-127 写明兼容策略（新端点/新参数、旧响应保留至最低支持版本），并给页长。
- **high** FR-146 药品注册号/有效期无字段定义与行为定义（§4.3 FR-146）— 未说：注册号是否必填（仅 Obat & Vitamin？）、格式校验、有效期到期后商品/库存是否自动下架或禁售、App 是否展示注册号、导入模板列。*Fix:* 补字段表 + 到期行为 + C 端展示 + 导入列，否则 FR-121/122/123 定稿后返工（FR-146 自己已预警此耦合）。
- **high** FR-117 与 FR-115 在 `PENDING_SHIPMENT` 态重叠且无验收（§4.2 FR-117）— FR-117 要求退款入口覆盖 `PENDING_SHIPMENT`，FR-115 已是该态的自助取消；两者是同一个按钮还是两个？`PENDING_SHIPMENT` 下「退款入口」能发起哪些 `ReturnType`？`SHIPPED` 下退款入口与 FR-118 拒收又是什么关系？*Fix:* 给一张「订单状态 × 可见入口 × 对应 ReturnType」矩阵作为 FR-115/117/118 共同验收。
- **high** §4.6 / §4.7 无验收列（§4.6 FR-133~138、§4.7 FR-149~151）— FR-136 一条塞了三件不相关的修正（售罄数口径、「售后成本口径标注」、PawCoin 可用/冻结），其中「标注」写成什么没说；FR-150 未说明系统**现在是否计算/输出 PPN**，无法判断是改算式还是新建。*Fix:* FR-136 拆三条；FR-149~151 各补现状 + 可测后果（如 FR-150：「对 DPP=X 的订单，计算 PPN=0.12×11/12×X，单测覆盖奢侈品档」）。
- **medium** FR-135 目标载体含糊（§4.6 FR-135）— 写「C 端硬编码中文收口 67 处 → 走既有 `messages.properties`」，但 C 端（Flutter）文案走 `app_*.arb`（FR-133 自己就引了 arb），`messages.properties` 是后端 i18n。67 处究竟在 App 还是在后端下发给 C 端的串，决定了改哪个代码库。*Fix:* 注明 67 处的文件分布（App / 后端各几处）与各自的目标资源文件。
- **medium** FR-124 解法未定（§4.3 FR-124）— 「满 9 张时提供**先传后删**或直接替换」是两种交互，未选。*Fix:* 选定一种写进验收，或登记为 D-xx。
- **medium** FR-126 / FR-129 / FR-123 验收过薄（§4.3）— FR-126 未说每 SKU 几张图、SKU 无图时回落主图与否；FR-129「下钻到单级明细并导出」未给明细字段、导出格式、是否含 PII（若含则需 NFR-11(v1.4.0) 权限位）；FR-123 仅一句话。*Fix:* 各补 2–3 条可测后果。
- **medium** FR-139/140/141 批量写的审计口径未纳入 NFR-20（§4.3、§5 NFR-20）— NFR-20 只点名「导入、批量改价」，FR-140 自称「须与 FR-128 同款二次确认 + 逐条审计」，FR-139（批量上下架）、FR-141（批量调品类）未提审计。*Fix:* NFR-20 改为「所有批量写操作（FR-122/128/139/140/141）」。
- **low** FR-152 验收①与需求描述张力（§4.4 FR-152）— 需求说「订单详情与工单页」提供按钮，验收说「无订单态不渲染」；非订单类工单页是否显示按钮不明。*Fix:* 明确工单页的显示条件（仅关联电商订单的工单？）。

## 5. Scope honesty — adequate（但收敛执行不干净）

**范围表态本身是诚实的**：§1.3/§1.4 的排除表、§3「本版不含（已裁，勿在 §4 出现 FR）」、§3 六项静默丢弃补裁定、§1.4 的 `netWeightG` 前置提醒，都是「显式不做」而非留给读者推断。`[ASSUMPTION]` 标注也用在了真正的推断上。

但 **2026-09-15 的 WhatsApp 范围收敛只改了主干，没有扫尾**，已移出的 FR-132 在多处在役正文里继续做功，其中两处（§6 客服可达、§3 FR-120 注）会直接误导下游。另有一处 §1.4 残留了收敛前的「待裁」表述。开放项密度方面：6 条阻断 + 8 条可延后 + 约 12 处 `[ASSUMPTION]`，对「上生产级 + 进架构」的利害等级偏高，且 §8 声称的「唯一着陆点」并未全部覆盖（见机械项）。

### Findings
