## 二、Findings

### High

#### H-1 · 「售后靠工单、WhatsApp 和运营人工处理」在系统里没有可走的路，现有唯一路径还违反 SD-2
- **位置**：§1.4 退货行；UJ-2 ①；UJ-4 ⚠️ 段；SHOP-FR-05；SHOP-R-4；ACT-C
- **问题**：PRD 让用户去找客服，由运营人工处理，但没有写运营在系统里具体能做什么。代码现状：
  1. **待发货订单**：运营唯一可用的是「异常处置 · 整单取消」（`AdminShopOrderExceptionService.cancelWholeOrder`，只要求 `PENDING_SHIPMENT`）。这条路会**发放平台责任补偿溢价**（`payCompensationPremium`），用户主动要求取消时拿它来处理，**直接违反 SD-2「发货前取消不给任何额外补偿」**。它回补库存走的也是 `receiveReturn`，对没有采购入库记录的 SKU 会抛异常，和 §8 已知问题 2 是同一个坑。
  2. **已发货或已送达订单**：后台只能处理用户已经提交的退货单（`AdminReturnController` 的 approve / reject / shipback / inspect / refund），**没有代用户发起退货的入口**（原 OPS-10 当时就裁掉了，理由是「有 WhatsApp 工作台兜底」，现在这个前提已不存在）。所以运营在系统里无法为这类订单退款。
  3. **老版本 App 仍能提交退货**：SHOP-FR-05 只隐藏新版 App 的入口，后端接口「保留且可用」。已发布的 1.2.x 在 COMPLETED 态仍有退货入口和退款方式页。PRD 没说这些退货单按电商一期规则处理，还是拒掉。
  4. 退款执行要求**用户已选现金段退回方式**（`RefundExecutionService.java:110`，未选直接 409）。退款方式页只能在 App 提交退货后跳转进入。ACT-C 所说「逐一线下处理」的在途退货单，如果用户没选过去向，后台是执行不下去的。
- **建议**：在 SHOP-FR-05 或 §1.4 补一段「本版售后的实际处置口径」，由产品从下面三种里选一种写死：(a) 全部线下处理（银行转账，PawCoin 由人工调账），系统内不留记录；(b) 允许运营对用户主动取消的订单使用异常处置取消，但必须先关掉这条路上的补偿溢价，这就不是纯前端改动了；(c) 维持现状，接受「待发货只能等发货后拒收或线下沟通」。同时写明老版本 App 提交的退货单怎么处理，并在 ACT-C 里加一条「核查在途退货单是否已选退回方式」。

#### H-2 · SHOP-FR-19 品类可配置遗漏了多个既有约束（首轮 H-13 / F-16 只收口了「多级」这一项）
- **位置**：SHOP-FR-19；§9 纪律「未知枚举值降级」
- **问题**：修订稿只处理了多级品类、物种和老版本兼容，以下几点都没提：
  1. **三语名称从哪来**：项目的 i18n 模型是「App 不渲染后端显示串，按 code 本地化」。运营新增或改名的品类，名字只能由后端下发三语文案，这是对 i18n 模型的例外，需要留痕，后台表单也要有三语输入。
  2. **CHECK 约束**：`ck_shop_products_category`（`V20260817_1154`）必须 DROP。按 CLAUDE.md 纪律，这件事要写进架构。
  3. **首页 4 个固定入口 + 吸顶分类槽**：电商一期 FR-93 ③ 规定「4 个固定品类」，C-19 把分类放进了吸顶槽。品类数量超过 4 个以后怎么排版，没有写。
  4. **停用品类的连锁影响**：「停用后该品类商品不在 App 展示」，那么购物车里已有的这类商品、复购提醒卡、档案推荐、已购订单详情里的商品链接怎么处理，都没有写。
- **建议**：SHOP-FR-19 验收补 4 条：三语名称由后台录入并下发（在决策日志加 SD 或 ASSUMPTION）、CHECK 约束的处置（交给架构）、分类入口超过 4 个时的承载规则（可加 OD）、停用品类对购物车 / 复购 / 推荐 / 历史订单的处理口径。

#### H-3 · SHOP-FR-17 批量改库存的安全语义没有收口（首轮 H-10 未处理）
- **位置**：SHOP-FR-17、SHOP-NFR-02、OD-7
- **问题**：
  - 「设为绝对值」没说写的是 `actual` 还是可售量；库存模型里有 `locked`（下单锁定），直接覆盖可能把可售量写成负数，或者抹掉在途锁定。现有盘点走的是 `inventory.stocktakeTo` 的 CAS 并写流水，PRD 没要求复用。
  - 批量写的**事务语义**（100 行里第 57 行失败时怎么办）、**预览到提交之间数据被别人改了**怎么处理、**批量操作是否需要独立权限位**，这三点对批量改价、改库存、调品类、上下架都没有定义。
  - 这条的风险在 SHOP-R-3 里已被列为资损和超卖。
- **建议**：SHOP-NFR-02 补上「批量写统一规格」：库存批量复用 stocktake 语义并逐行写流水；事务语义二选一写死；提交时校验版本，预览之后有变化就整批拒绝；权限位沿用单条操作还是新增，写明白。

#### H-4 · SHOP-FR-21 把「有效期」挂在 SKU 上，语义不对，而且会卡住导入模板定稿（首轮 H-12 未处理）
- **位置**：SHOP-FR-21、OD-8
- **问题**：有效期是**批次**属性。同一个 SKU 每次进货效期都不同，放在 SKU 上要么永远过期，要么永远不准，真要准就得牵动采购入库流水（`receivePurchase`）的批次模型。SHOP-FR-21 自己要求「与 SHOP-FR-07/08 同批定稿」，但字段放在哪一层（SKU 还是批次）没有对应的开放项。OD-8 只管处方药。
- **建议**：新增 OD-12「药品注册号与有效期的字段层级」，定在「导入模板定稿前」。推荐本版只做注册号（SKU 级），有效期留到批次模型再做，或者明确只填「当前在售批次的最早效期」这一展示口径。

### Medium

#### M-1 · SHOP-FR-01/02 的验收环境不成立：支付模拟器只在 stag，服务端埋点没有环境区分
- **位置**：SHOP-FR-01 验收；SHOP-FR-02 验收「在埋点开启的环境跑三支」
- **问题**：
  - 支付模拟器（`admin/paysim/AdminPaySimulatorService`）**只在 `origin/stag` 分支上**，main 和 dev 都没有；按项目约定，它是 stag 专属工具，合并时必须排除。所以三支验收只能在 stag 上跑。
  - App 端靠 `-stag` 版本后缀区分测试数据，但**服务端 `PostHogAnalyticsClient.capture` 不带任何环境属性**，事件属性里只有 `distinct_id`。stag 后端如果配了 `POSTHOG_SERVER_KEY`，服务端电商支付事件会混进生产漏斗。要求「前后端同一个 PostHog 项目」时，这个问题更明显。
- **建议**：SHOP-FR-02 加一条「服务端事件带环境属性（或 stag 使用独立 key），与 App 端 `-stag` 口径一致」；验收环境写明为 stag。另外说明 GemPay 的 `failure` 状态（`GemPayGateway.java:186`）在 QRIS 场景下真实出现的频率未知，被拒这一支在生产上可能只能靠模拟器验证。

#### M-2 · SHOP-FR-01 改的是共享组件，没写回归范围；「用户主动取消」没有定义
- **位置**：SHOP-FR-01
- **问题**：`QrPaymentSheet` 是问诊、AI 解锁、HD、充值、电商五条链路共用的组件（首轮 M-1 未处理）。另外，「用户主动取消 → 不弹错误」指的是关闭面板，还是调用订单取消接口（`ShopOrderPaymentService.cancel`，会把 intent 置为 FAILED + USER_CANCEL），没有说清；SHOP-FR-02 又另有一个「离开面板（未完成）」事件，两者容易混。代码层面，被拒后重试可以新建 intent（`createIntent` 在旧 intent 为 FAILED 时会新建），这一点成立。
- **建议**：验收补「其余四种支付用途各跑一遍成功 / 失败 / 超时，表现不变」；把「用户主动取消」定义为调用取消订单接口，关闭面板另算。

#### M-3 · SHOP-FR-30 订单号改造的范围和数据形态没说清
- **位置**：SHOP-FR-29、SHOP-FR-30、OD-9
- **问题**：`OrderDisplayNo` 是**计算式，不落库**（类注释「不落库、不需迁移、老数据同样有号」），CONSVET / CONSAI / TOPUP / TOKO 四种前缀共用同一套「日期 + 自增 id」算法，后台问诊订单和 AI 订单页也在用。所以：
  1. 不可推算的新号码要么落库（新列 + 存量回填迁移），要么改成由 token 派生；
  2. 本版只修 TOKO，但其余三种前缀违反的是同一条护栏，PRD 引用了护栏却没说明范围只到电商；
  3. 后台对账（AB-13D）依赖 TOKO 前缀区分实物和虚拟收入，新格式必须保留可区分的前缀。
- **建议**：SHOP-FR-30 验收补「保留 TOKO 前缀；新号码落库并回填存量」；在「范围说明」里写明其余三种前缀的同类问题留到下一版（或记入已知问题）。

#### M-4 · §8 静默丢了 3 条下一版必需的结论（SD-2 的连带后果）
- **位置**：§8「必须遵守的规则」「已知问题」
- **问题**：
  1. 决策日志 SD-2 的 `[ASSUMPTION]`「选 PawCoin 退款的激励也不发」没进 §8。按电商一期 D-16，激励溢价**只**对 CANCEL_BEFORE_SHIPMENT 和 REFUSED_ON_DELIVERY 这两种未交付类型生效（`RefundExecutionService.incentiveApplies`）。所以这条假设实际上等于**激励溢价功能整体下线**，而且会与退款方式页（电商一期 FR-105）上「转 PawCoin + 激励」的文案冲突。
  2. **S-4 质量问题补偿溢价「90 日 ≤2 次」全仓未实现**（原 FR-116 与首轮 F-07 / M-13 都点过），修订稿完全没提。退货后端保留、老版本 App 仍能提交质量问题退货，这个套利面现在仍然在线。
  3. 「两条溢价必须是两个独立配置项，不得合并」这条约束（原 FR-116 / D-22，出处是代码注释和 AB-13A / AB-6C）丢失。下一版修「拒收发补偿」时最容易踩的就是这里。
- **建议**：§8「必须遵守的规则」补第 2 条（两条溢价不得合并）；「已知问题」补 S-4 未实现、激励溢价在 SD-2 下的去留（以及退款方式页文案）。

#### M-5 · SHOP-FR-33 PPN 算式在系统里没有落点（首轮 M-7 / F-12 未处理）
- **位置**：§3.6 SHOP-FR-33
- **问题**：系统里没有任何 PPN 计算，也没有开票模块。SHOP-FR-32 和 SHOP-FR-34 都挂了开放项，唯独 SHOP-FR-33 写成了确定需求，dev agent 可能照着去造一个税额模块。电商一期架构 delta 明确「税额行不要默认不做，也不要临场加，等拍板」（OQ-40 / DEP-8）。
- **建议**：§3.6 整组改为「约束 / 依赖项」，不作为 FR 拆 story；SHOP-FR-33 写成「将来引入 PPN 计算时须按此算式」，并关联电商一期 OQ-40 / DEP-8。

#### M-6 · 评价提交接口的去留还是没定（首轮 F-11 / M-6 未处理）
- **位置**：§1.4 评价页；SHOP-FR-27
- **问题**：SHOP-FR-27 只要求日志打码。可 `POST /api/v1/me/shop-reviews` 仍然能写入评价，而评价后台管理已经出局（§1.3），商品详情页的评价列表（电商一期 7-3）也还在。于是会出现没人管的孤儿数据，内容审核也无人处理。
- **建议**：三选一写死：关闭提交端点（推荐）/ 保留接口但隐藏详情页评价区 / 维持现状并接受孤儿数据。

#### M-7 · 订单导出与账号信息搜索的 PII 细节缺失（首轮 F-15、L-5 未处理）
- **位置**：SHOP-FR-09、SHOP-FR-13、SHOP-FR-14、OD-1、OD-10
- **问题**：① 导出含用户可控字段（昵称、收件人），没有要求防 CSV / Excel 公式注入；② 注销用户的订单在详情里显示什么（admin 主题 D-48 的口径是「已注销用户」）、邮箱搜索是否命中 `users.deleted_email`（CROSS-STORY F20），都没写；③ 没有关联电商一期 OQ-41（按电话或邮箱检索属于安全攸关 PII 面）。
- **建议**：SHOP-NFR-01 补「导出单元格做公式转义」；SHOP-FR-14 补「注销用户显示『已注销用户』、不读 deleted_email」；OD-1 / OD-10 注明关联 OQ-41。

#### M-8 · §9 权限码纪律已过时：admin 合入后计数是 74，而且新增了角色-权限表
- **位置**：§9 第 1 行「当前为 72」
- **问题**：本分支 `AdminPermissionsTest.java:126` 是 `hasSize(72)`，这个数属实；但 `origin/feat/1.3.0-ops-ui-refactor` 上已经是 `hasSize(74)`，还新增了 `admin_roles` / `admin_role_permissions` 两张表和 4 个预置角色（运营专员 / 发货专员 / 客服 / 财务，D-13）。按 SD-7，shop-v2 是在 admin 之后叠加实现的，所以新权限码要改的是 **5 处**：多出预置角色的默认授予和种子迁移。
- **建议**：改成「以 admin 合入后的计数为准；第 5 处 = 预置角色默认授予 + 种子迁移」，并给新权限位（订单导出、邮箱搜索、对账导出、批量写）逐个写默认授予给哪个角色。

#### M-9 · 仍然没有优先级和分批，剃刀也没用在 banner 轮播上（首轮 H-7 / H-8 未处理）
- **位置**：§3 全局；§1.5；SHOP-FR-22

#### M-10 · SD-9 外链抓图的来源白名单没有归属，EXIF 处理没有继承
