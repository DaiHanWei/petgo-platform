### 0.2 运营的四条日常工作流（现状动线）

1. **早巡（每天开工）**：概览看数 → 人工复核清队列 → 评论管理巡查 → 被举报用户处置 → 客服工单。**痛点：五个页面分属三个导航组，无统一「待办」视图**，每天靠记忆逐页点
2. **内容供给（每周节奏）**：运营发布身份选马甲 → 种子内容发布/批量工作台 → 定时发布排期 → 顶置管理换坑位 → 内容标签打标（选品参考看内容统计 AB-3G）。**痛点：动线里的「定时发布」「内容统计」恰好是两个无导航入口的页面**
3. **数据复盘（每日/每周）**：现状只有概览四个数字 + 内容统计双口径 → **本版本 AB-15A 数据看板补上趋势复盘的主阵地**
4. **售后与钱（按需）**：退款管理 / 支付记录 / 兽医月结 / Toko 退货审核与对账。金额相关操作全部有审计链兜底

### 0.3 结构性问题清单（本版本不动，供后续 UI/UX 重整拍板）

1. **【建议】审核处置动线分散**：人工复核、评论管理、被举报用户、异常工单、客服工单五处队列分属三组——早巡靠逐页点，漏看无提示。方向：统一「待办中心」或导航组按「审核」聚合，并给各队列加未处理计数角标
2. **【建议】「运营」组已成杂物抽屉**：定价配置、算法参数、订单查询、月结、支付流水、身份池六种性质混在一组。方向：拆「订单与资金」「配置」两组
3. **【建议】兽医 + 问诊异常两组共 6 项，在兽医线延期后是低频区**，却占两个一级组位。方向：合并为一组「兽医与问诊」折叠置后
4. **内容统计 / 定时发布无导航入口**（0.1 表尾）——不论 IA 是否重排，这两项至少该补菜单项，成本极低
5. **权限勾选面板与导航不同构**：权限按「查看/编辑」两大组罗列 code，运营语言是「管哪个页面」——给 STAFF 配权限时对照成本高。方向：权限面板按导航组重排
6. 电商组 12 项独大（1.2.0 一次并入）——Toko 上线后按使用频率再看要不要分层，本版本不动

## 1. AB-15A：运营后台首页数据看板（替换现首页）

**现状：** 后台首页为「运营概览」（V1.1.0 Story 9.10 / AB-1.1-01）——用户/订单/内容/兽医四模块的实时聚合数字表格 + 种子发布链接入口。数字为「当前时点累计」，无时间维度、无趋势、无图表。

**页面位置：** 后台首页 `/admin`（左侧导航「概览」，登录后默认落地页）——在原页面原位替换，不新增菜单项。

**本条改版：** 首页整体替换为**内容运营数据看板**——以日为粒度的时间序列指标 + 图表呈现。**指标口径以本节 ①-a 口径表为准，共 18 项**（自 `内容运营所需数据-20260831.sql` 提炼，SQL 已归档同目录仅作溯源；后续不再作为取数工具，运营直接在看板看数——D-26）。

### ① 指标清单与看板分组

| 分组 | 指标（共 18 项） | 图表形式 |

#### ①-a 18 项指标口径表（权威定义，D-26）

通用规则：日 = **WIB 自然日**，截止点为该日 24:00；「真实用户」= `users.role='USER'` 且登录标识 `google_sub` 不以 `admin:` / `virtual:` / `seed-tailtopia-` 开头，**登录标识为空（Apple 登录）视为普通用户计入**（D-6）；「可见帖子」= `status='PUBLISHED'` 且未删除；「有效评论」= **已公开（审核通过）且未删除**的评论（D-38）；点赞取消即删行无需过滤；得分公式 = 点赞×1 + 评论×5。

**帖子类指标双口径（D-29，#3 #4 #8~#14 共 9 项）：** 每项同时产出两条序列——「真实用户」口径 = 帖子作者为真实用户，且点赞/评论的发起者也为真实用户（运营暖评等虚拟互动不计）；「含种子」口径 = 不做作者与互动者排除，即参考 SQL 原口径。卡内 tab 切换，默认「真实用户」，口径差异提示常驻卡底。

- 时间范围选择（2026-09-01 拍板简化）：**近 7 天 / 近 30 天 两档，用户自行切换**（默认 7 天）；不做 14 天档与自定义起止；切换用 htmx 局部替换图表区，**不整页刷新**
- **付费卡的两口径**：卡内 tab 切换「现金到账 / 含 PawCoin 消费」，默认现金到账；口径差异提示常驻卡底（非 hover 才可见）
- 图表交互：hover/点按显示 日期 + 数值 tooltip；其余交互（图例开关等）用图表库默认能力即可，不做定制要求
- **缺数据日的呈现**：预聚合缺行的日期在图上显示为**断点/缺口**，不得画成 0（画 0 会被误读为"当天没有数据量"）；图表卡加载中显示骨架、加载失败显示卡内重试按钮
- 每项指标须带口径提示（hover/图标展开），文案直接取自 SQL 头部注释的口径说明，**不另写一套**——两处口径描述走散是本条最大的长期风险

### ② 口径与刷新规则（与 SQL 严格一致）

- 所有指标的日截止点为**该自然日 24:00**（即只展示到「查询当天 00:00」为止的完整自然日；当天数据不完整、不展示）——与 SQL 日报口径一致，图上最后一根柱永远是昨天
- 排除口径见 ①-a 通用规则；`role=ADMIN` 仅指 Story 3.1 遗留的旧账密运营号（现后台账号在独立的 `admin_accounts` 表，不在 `users`），排除它是清历史残留
- **同一数字两处必须相等**：看板任一指标在任一天的数值，必须与直接执行该 SQL 得到的数值完全一致（SQL 注释已保证按天口径可复现）。验收即用这条对比
- **历史回填（D-15）**：看板上线时 **18 项指标全部一次性回填到 2026-07-17**，回填脚本与日跑批共用同一套口径实现；不再区分付费与非付费
- **性能实现自由、口径不自由**：SQL 中全量平均分等指标为 LATERAL 全表打分、直接每次实时跑不可行，允许做**日粒度预聚合**（每日跑批物化昨日一行，历史行不再变——SQL 口径本身保证了同一天的数字不随后续互动上涨，天然适合物化）。预聚合表结构与跑批时机技术方案定

### ③ 边界

- **次日留存不承载**——库里没有登录/打开 App 日志表（登录事件只进 PostHog 不落库），SQL 明确排除了该指标，看板同样不做；看板页可放一行说明 +「去 PostHog 查看留存」的提示文案（不做外链跳转集成）
- 原首页的四模块实时聚合数字**降级为看板页底部的一行紧凑摘要**（保留「当前时点总量」的速览价值），种子发布链接入口保留
- 不做导出（互动积分与导出已随 1.1.6 后期并入「内容管理」列表，管理层汇报走内容管理列表的导出——D-12；原独立「内容统计」页已撤）；不做指标自定义/拖拽布局

## 2. AB-16A：后台账号管理增强（扩展模块 1「安全 → 后台账号」）

**现状（2026-09-01 二次代码核验，再次订正）：** 「安全 → 后台账号」已具备——创建账号、**修改模块权限**、**修改岗位角色**（`changeRole`：账号在「岗位角色」体系内切换，含模板角色与 SUPER_ADMIN；已带两道护栏——超管上限 5、不降级最后一个在职超管；审计 `ACCOUNT_ROLE_CHANGED`）、**停用**（已带「不停用最后一个在职超管」护栏）、**重新激活**。此前 Roadmap 记的「只有创建与停用」与本文档初稿写的「改账号类型待新增」**均不准确——改权限/改角色/停用恢复全部已上线，本条不重复建设**。既有规则补记：**超管上限 5（ACTIVE 口径）**、账号无 delete 方法（永不硬删）。

**「重置密码」撤销（2026-08-26 拍板）：** 后台账号走 Lark OAuth 登录，STAFF 无密码；仅 bootstrap 预置的超管有一条 env 注入的紧急账密（BCrypt，运维层管理）。「重置密码」在当前架构下不成立，从本条范围移除。

**页面位置与流程：** 「安全 → 后台账号」既有页面 `/admin/accounts`——新动作全部做成**账号列表行内操作**，与既有「改角色 / 改权限 / 停用 / 重新激活」按钮并列；点击后行内展开或弹层完成，提交走既有 PRG 模式回到本页并显示结果横幅。不新增页面。

**本条实际补齐：两个新动作 + 两条缺失护栏**：

### ① 修改显示名

- 操作权限：`SUPER_ADMIN` 或持 `admin.create_account`（与创建/改权限同门槛）
- 规则与创建时一致（非空、≤100 字符）；改名不影响权限；顶栏显示名**在该账号下次登录后更新**，保存成功横幅注明「对方重新登录后生效」（D-2）
- 审计：`AuditActions` 新增 `ACCOUNT_RENAMED`（命名沿用 ACCOUNT_* 惯例，下同），summary 记录旧值 → 新值

### ② 换绑 Lark 邮箱（高危）

**场景：** 人员邮箱变更、账号移交。没有这个动作时的现状是「停用旧账号 + 新建账号」，权限配置须手工重配且历史审计上下文断裂。

- 操作权限：**仅 `SUPER_ADMIN`**
- 新邮箱须通过与创建时相同的格式校验，且不得与任何**启用中**账号的邮箱重复；**已停用账号的邮箱视为已释放**，可被换绑/新建复用（D-21）
- **换绑即时生效**：旧邮箱的 Lark OAuth 立即无法命中白名单；该账号的**既有登录会话在下一次请求即失效并跳登录页**（硬要求，D-1：账号表增加变更版本号，登录时快照进会话，每请求比对；换绑 / 停用 / 改角色均使版本号变化。换绑语义上是身份移交，不能让旧持有人的活跃会话继续存活）
- 页面须二次确认（输入新邮箱后弹确认框复述「旧邮箱 → 新邮箱，旧邮箱立即失去访问权限」）
- 审计：新增 `ACCOUNT_EMAIL_REBOUND`，summary 记录旧邮箱 → 新邮箱；**同时触发超管安全告警**（`AdminAlertService.alertSuperAdmins`，与既有高危事件同管道）
- **bootstrap 预置超管不可被换绑**（其身份由 env 配置锚定，改由运维层处理）

### ③ 补齐两条缺失的 self 护栏（2026-09-01 代码核验：既有实现确实没有）

- **不能停用自己**、**不能修改自己的岗位角色**——防误操作自锁（超管把自己降级/停用后无人能恢复的场景，现有「最后超管」护栏只防得住只剩一人的情况，防不住多超管时的自伤）
- 改角色对他人生效方式：改角色触发 D-1 的版本号变化 → 对方下次请求被踢重登，重登后新角色权限生效；成功横幅注明「对方重新登录后生效」（D-2）
- 实现位置：`deactivate` / `changeRole` 各加一条 `actorAccountId == accountId` 拒绝判断，拒绝时明示原因（沿用 `admin.err.*` 错误码模式）
- 「最后一个在职超管不可停用/降级」护栏**已存在**（A3，含幂等），本条不重复建设

### ④ 不变的原则

- **账号只可停用、永不删除**（保审计完整）——本条三个新动作均不触碰该原则
- 所有操作经统一审计入口 `AdminAuditService.record`（同事务、哈希链），不得绕过
- 页面沿用既有后台账号页（`admin-accounts.html`）扩展，不新开页面

## 6. AB-20A：虚拟账号评论（暖贴）（2026-09-03 新增）

**动机：** 早期社区帖子评论稀薄，作者发帖无人回应会流失。现状运营只能在 App 端一个帖子一个帖子点开看谁没评论，再手工切虚拟账号回复——不可规模化。本条把「找到冷帖 → 用虚拟账号评论」收进后台一条动线。

**页面位置与流程：** 「内容 → 评论管理」页升级为两页签；另在「待办中心」新增「暖贴回复跟进」队列页（见 ③）：

- **页签一「评论巡查」**＝现状评论列表与下架/恢复，功能不变。
- **页签二「帖子评论分布」（本条新增）**＝帖子维度视图，运营在这里找冷帖并直接评论。

### ① 帖子评论分布（页签二）

- **筛选：** 评论数区间（快捷档 `= 0` / `≤ 3` / 自定义 `≤ N`）+ 发布时间段 + 物种 + **「排除虚拟账号内容」开关（默认开，文案 2026-09-03 定稿）**——只排除虚拟账号池发布的帖子（真实身份池的帖照常参与），保证运营的暖评火力集中在真实账号的帖子上
- **列表列：** 帖子摘要 ｜ 作者 ｜ 发布时间 ｜ 评论数（0 红标 / 低量黄标）｜ **其中虚拟评论数** ｜ 操作「去评论」
- **数据展示（页面常驻摘要条，用于运营数据分析）：** 筛选范围内帖子数 · **篇均评论数（双口径并列：含虚拟 / 剔除虚拟）** · 0 评论帖数与占比 · 虚拟评论占比。口径＝当前筛选结果集、可见评论（已下架评论不计）；剔除虚拟口径＝评论作者 ∉ 虚拟账号池——保证暖评动作不污染真实互动数据（2026-09-03 确认）
- **排序：** 默认评论数升序（最冷的排最前）
- **列表范围：** 帖子状态为普通筛选项（全部/可见/已下架，默认全部）——**给哪些帖暖评由运营自行筛选判断，页面不做预设**（2026-09-03 拍板，撤回此前「只列可见帖」的预设）

### ② 「去评论」抽屉

- **结构：** 帖子预览（图+摘要+作者+物种+当前评论数）→ 已有评论列表（含虚拟评论标识，后台可见、App 端不标）→ 常驻评论区
- **评论区：** 评论身份下拉（取**虚拟账号池**中**启用中**账号——不含真实身份池，与 §④「判定=作者∈虚拟账号池」及 UI 稿 2-10 一致；默认只列与帖子物种匹配的，可切「全部」；每项带**「今日已评 N 条」**帮运营换手、防单账号过度使用被识破）+ 评论文本框（**上限 200 字**，与 App 端 `CommentCreateRequest` 一致）+ 发布按钮（身份未选或内容为空禁用——F7 规则 11）
- **层级限制（D-35）：** 本版暖评**只对帖子发一级评论**，不能回复他人评论。原因：评论为两级结构，二级回复不记录「回复目标」，虚拟账号发的二级评论被回复时无法识别、跟进队列收不到。后端本版预留 `comments.reply_to_comment_id` 字段与回复接口可选参数，App 分支合入后再开放二级暖评与「通知发给被回复者」。
- **发布语义（D-4）：** 走 App 评论**完整同链路，含审核**——L1 硬黑名单命中同步拒绝并行内报错；否则先落「审核中」（仅评论人可见），机审通过后转公开并通知作者，机审拿不准进 A1 内容送审页签由运营处置。作者收到普通评论推送/通知、评论计数与**推荐算法互动权重照常生效（会真实推高帖子曝光，2026-09-03 产品确认接受）**；App 端该评论与真实用户评论**无任何视觉区别**。本期只做评论，虚拟点赞不做（2026-09-03 拍板，后续版本再议）
- **连发体验：** 提交成功后显示 **「已提交，审核通过后显示」** toast（不是「发布成功」），抽屉不关闭、文本框清空，可为同帖继续评或点「下一帖」；已有评论列表内该条以「审核中」标识出现；列表「评论数」列不即时 +1，待审核通过后随刷新更新（D-4）
- **防呆：** 同一虚拟账号对同一帖 10 分钟内再次评论时，行内提示「该账号刚评过这帖，确认再发？」（不弹层，二次点击即发）；**同帖虚拟评论已 ≥3 条时评论区上方黄条提示**（不拦截——官托观感自查）。本版本**不加每日硬上限与告警**，维持软提示（D-20）

### ③ 暖贴回复跟进（待办中心新页，闭环「已读不回」）

真实用户回复了虚拟评论后，虚拟账号侧无人盯会变成「作者跟不会回话的账号说话」，暖贴反噬。故：

- **页面位置：** 「待办中心」新增第 8 页「暖贴回复跟进」，导航角标计数
- **入队规则：** 任一虚拟评论收到新回复（含二级回复）即生成一条待跟进项；同一虚拟评论的多条新回复合并为一项
- **出队规则（D-19）：** 触发入队的真实用户回复被下架或被作者自删 → 该跟进项自动出队（若合并项内仍有其他有效回复则保留）
- **工作台（模板 A 双栏）：** 左=待跟进队列（虚拟账号/帖子/回复摘要/时间）；右=帖子卡 + 评论线程（新回复高亮）+ 常驻回复区——**回复身份锁定为被回复的那个虚拟账号，不可切换**（防串人设）
- **处理动作：** 发布回复（复用 App 评论回复链路，回复者照常收通知）或 标记已读（不回复）；处理后出队并自动选中下一条
- **页签：** 待跟进 / 已跟进（近 30 天）

### ④ 工程与安全

- **新端点：** 帖子评论分布聚合查询（分页）+ `POST /admin/comments/virtual`（postId + virtualAccountId + text，幂等 token；回复时带 parentCommentId）+ 暖贴回复跟进队列查询/标记已读
- **权限：** 新权限码 `comment.virtual_post`（默认超管；可单独授予运营）；虚拟账号池本身仍归 `virtual_account.manage`
- **审计：** 每条虚拟评论落审计（动作码 `COMMENT_VIRTUAL_POST`，记录 postId/虚拟账号/文本摘要）
- **数据边界：** 「排除虚拟账号内容」的判定=作者 ∈ 虚拟账号池（仅此，2026-09-03 拍板）；虚拟评论标识只在后台展示，不落 App 端任何接口字段

### ⑤ 与既有机制的关系（并存，不替换）

评论管理页签一、内容管理、虚拟账号池的既有功能全部不动；本条只新增页签二与评论端点。虚拟账号的创建/启停/物种标记仍在「运营发布身份」页维护。

## 7. AB-21A：角色配置功能（2026-09-04 新增）

**动机：** 核实代码发现后台"改角色"只是给账号从几个写死的角色里选一个赋值——角色本身（角色叫什么、包含哪些权限码）是硬编码在 Java 枚举 `AdminRole` 里的（如 `OPS_MANAGER(List.of(CONTENT_VIEW_REPORTS, ..., VET_QUALIFY, ...))`），新增角色或调整某角色的权限范围只能改代码重新发版，运营在后台完全无法自主配置。三个关键决策点已与 Hex 讨论确认：

1. **只做可视化管理，不重新设计权限模型**——沿用代码里现有的全部权限码（`AdminPermissions.java` 共 **72 个**，如 `content.takedown`、`user.grant_pawcoin`），新角色 = 从这些权限码里勾选组合，不新增/拆分权限颗粒度
2. **完全不碰超管护栏**——`SUPER_ADMIN` 继续硬编码、隐式全权、上限 5 人不变；本功能只管理 SUPER_ADMIN 之外的角色
3. **现状固定角色迁移为系统预置角色**——**2026-09-04 核实代码后修正名单**：`AdminRole` 枚举实际有 6 个非超管角色，分别是 OPS_MANAGER（运营主管）/ OPERATIONS（运营专员）/ FULFILLMENT（发货专员）/ SUPPORT（客服）/ FINANCE（财务）/ CUSTOM（自定义，见下方架构发现）——此前草稿把角色名单记错并编造了一个不存在的"兽医管理员"，已改正。经与产品确认：**运营主管（OPS_MANAGER）不迁移，代码里原样保留不动**；迁移为系统预置角色的是 **运营专员／发货专员／客服／财务** 四个

### 技术路线（2026-09-04 发现，2026-09-09 拍板 D-9：**方案 A**）

`AdminRole` 枚举自身的类注释写明：运营专员/发货专员/客服/财务这类"岗位角色"的权限是运行时从 Java 代码实时解析的，从不写入 `admin_account_permissions` 表；表里落库的权限只有 `CUSTOM` 角色才有（即现状"编辑权限"功能背后的账号级逐条勾选机制）。把岗位角色权限变成运营可编辑，需要把解析路径从"读 Java 枚举"改成"读数据库"。

**拍板：方案 A** —— 新建角色-权限表，运营专员/发货专员/客服/财务四个预置角色的权限从枚举一次性迁移进新表（随上线跑一次脚本），运行时改为查表解析；自定义角色同表；**现有 `CUSTOM` 账号级勾选机制保留并存**（后台账号页的权限勾选面板照做、按新导航组重排——AB-19A 动线优化③ 不受影响）；`SUPER_ADMIN` 与 `OPS_MANAGER` 继续硬编码不动。方案 B（泛化 CUSTOM、废弃账号级表）不采用：需动登录权限解析主路径，风险与工期都更大。

**生效方式（D-2）：** 角色权限变更对该角色下账号**重新登录后生效**（登录时解析一次，会话内不重算）；保存成功横幅注明「对该角色下账号，重新登录后生效」。

**页面位置与流程：** 「安全 → 后台账号」下新增子页「角色配置」，导航与"后台账号"并列。

### ① 角色列表

- **列：** 角色名称 ｜ 类型（系统预置 / 自定义）｜ 权限数 ｜ 使用中账号数 ｜ 操作
- 系统预置角色 = **运营专员 / 发货专员 / 客服 / 财务** 四个（D-13；运营主管与超管不在本功能范围）**可编辑权限，但不可删除**（假设，见待确认）；自定义角色可编辑可删除（删除前必须先把使用中账号转移到别的角色，data-confirm 复述受影响账号数）

### ② 新建/编辑角色

- 角色名称（自定义角色必填且可改；预置角色名称不可改，避免和历史审计记录里的角色名对不上）
- **权限勾选：** 页面维度矩阵，每个后台页面固定“查看”+“编辑”两档；个别页面存在超出这两档的独立操作权限（如用户页的停用/删除/赠送 PawCoin 是三个独立权限，不是一个通用“编辑”），单列“其他操作权限”栏位如实列出，不强行归并成假的两档模型。数据来源=代码里唯一的权限码定义类 `AdminPermissions.java`（72 个常量），覆盖全部约 35 个页面维度（含此前遗漏的待办中心工单/客服/退款/Toko退货/异常订单、商城财务、用户手机号等）。**代码现状两处不规整，随本功能梳理时一并发现，非本功能引入**：评论管理没有独立的查看权限码（沿用 content.view）；退款管理与 Toko 退货共用同一套 refund.* 权限码，无法只放开一边——建议工程评审时确认是否需要拆分，本 PRD 不擅自定，如实记录待讨论。
- 保存=高危确认（复述新增/移除的权限项，影响该角色下所有账号，**对方重新登录后生效**——D-2）

### ③ 与既有机制的关系

- 「后台账号」页的"改角色"下拉改为从本功能的角色列表读取（含预置+自定义），行为不变（仍是给单个账号赋值一个角色）
- 现状 5 个超管上限、自我保护护栏（AB-16A）、审计记录不受影响；后台账号页的账号级「编辑权限」（CUSTOM）面板保留（D-9）

### ④ 待确认（假设先行，需产品拍板）

- **系统预置角色是否允许删除**——本节先假设"不可删除，只可编辑权限"，因为删除后该角色下的历史审计记录会失去可读的角色名上下文；如需允许删除，需要补充"删除时角色名转存进审计快照"的工程方案
