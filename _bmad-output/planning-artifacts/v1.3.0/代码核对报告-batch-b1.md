## 2. 必须先改或先定的 5 件事（2026-09-11 **已全部拍板**，结论见 `决策日志-batch-b1.md`）

### 2.1 ✅ 已定 · UI 稿 C6 把一个「已经否掉两次」的东西画回来了

UI 稿 C6 描述宠物访客视图时写了「Linimasa / Kalender 视图切换」。

实际情况：访客视图**没有**日历，只有时间线。这是 2026-08-18 拍板不做、2026-08-28 对稿时**再次确认不做**的，代码里专门留了一段警告注释，原话是「别再当成缺口补上去」。后端的访客日历接口倒是建好了、也有测试，是有意留着的。

→ **动作：** 改 UI 稿 C6 那句描述（删掉切换行），否则研发照稿做就是把已经否掉的功能做回来。若产品想借这次把日历打开，那是一个独立决定，要单独记一笔。

### 2.2 ✅ 已定 · 分享链接不能用场所名字拼

UI 稿 A9 的地址栏画的是 `tailtopia.id/place/kopi-kayu-manis`——用可读的场所名字做链接。

问题：现有三类分享页一律是「短前缀 + 一串猜不出来的随机码」，架构里有一条硬规定「对外暴露的标识一律不可枚举」。用名字拼链接，等于任何人都能按名字批量试出全站场所页（也会给爬虫留口子）。

→ **动作：** 改成随机码形式（`/place/{随机码}` 或沿用现有单字母前缀风格）。UI 稿地址栏那行示意图一并改掉，避免研发照抄。

### 2.3 ✅ 已定 · 加「有人提到了你」这类通知，会碰到一处出过四次事故的地方

通知类型在数据库里有一张「允许值清单」，加新类型必须把清单**整张重列**（目前 30 个值 + 新的 1 个）。这地方历史上翻车过四次，每次都是照着一份过期清单抄、漏掉几个值，结果那几类通知一写就报错、服务起不来。

→ **动作：** 写进 story 的硬约束：加类型时以代码里的类型枚举为唯一准，重列全集，并且再查一遍并行分支（电商线、admin 线）有没有同期加值。这不是可选的注意事项，是这条 story 最容易翻车的一步。

### 2.4 ✅ 已定 · 定位权限是上线流程项，PRD / UI 都没提

按距离排序要拿设备定位。现在两端**都没有申请过定位权限**（安卓权限清单、iOS 说明文案里都没有）。新增定位意味着：

- 两端各加一条权限声明 + 一句给用户看的用途说明；
- **App Store 隐私标签 与 Google Play「数据安全」表单要同步更新**——Play 侧新增「位置」数据类型属于需要重新过审的改动，排期上要留出时间。

→ **结论（B1-D8）：** 查过现行隐私政策——「自动收集的信息 · 位置」一节**已经覆盖** GPS 精确位置与「用户自己添加到内容里的位置信息」，场所标记正落在后者，**隐私政策与服务条款都不用改**。要做的只有商店信息（Play 数据安全表单 + App Store 隐私标签）、两端权限声明与授权弹窗用途文案。在 epics 里单列一条「定位权限与商店合规」，别挂在某条功能 story 尾巴上。

### 2.5 ✅ 已定 · 距离排序怎么算，要在架构 delta 里定死

数据库**没装任何地理扩展**（一个扩展都没装）。PRD 假设 A-2 已经写了「不引入三方 LBS」，但没说服务端怎么排。

→ **结论（B1-D9）：** 数据库**只存经纬度 + 文字地址**；排序用「普通 SQL 算直线距离 + 先用经纬度范围粗筛 + 经纬度建索引」，不装地理扩展、不接三方 LBS 服务（违反现有护栏）。

### 2.6 ✅ 已定 · 地图换成 Google，且只用在「选点」那一屏

**推翻 PRD 里「flutter_map + OpenStreetMap 免费底图」的写法。** 标记场所时 App 内嵌 Google 地图拖大头针选点；**场所详情页不嵌地图**，只有文字地址 + 一键复制 + 「在 Google 地图打开」按钮（跳出去可直接导航）。

前置条件属于账号配置、不是写代码，但会卡排期：要开通 Google Maps Platform 并绑卡，申请 iOS / Android 两套密钥，后台冷启动录入是 Web 端**还要第三套**；密钥一律 env 注入不入库，每把加平台限制与配额上限。细节见 B1-D9。

## 3. 需要补齐 / 提醒的规格细节

| # | 事项 | 说明与建议 |

| 3.1 | **宠物访客视图走哪条路** | PRD 写的是「后端补一条按宠物 id 的站内访客访问」。另一条更省事的路是：主页直接把对方宠物的**分享链接码**发下来，复用现成接口、零新接口——但代价是每个访客都拿到了对方宠物的**永久公开分享链接**，可以转发到站外。✅ **已定：走新接口**（B1-D1）。 |
| 3.2 | **访客视图顶部「由 XX 分享 · 仅可查看」横幅** | UI 稿自己也标了待确认。站内点宠物卡进来时「谁分享的」这个语境不成立，建议站内入口**隐藏该横幅**。同时注意：这一屏没有底部导航，返回按钮是唯一出口，站内进入时返回应回到上一页（主页），不能落到首页 |
| 3.3 | **Diary Tab 推荐只覆盖「未建档」一态** | 代码里 Diary 页对登录用户其实有两种没档案的状态：「养宠但没建档」和「声明未养宠 / 计划养宠」。PRD 只做了前者。✅ **已定：两态都做**（B1-D2）。 |
| 3.4 | **UI 稿表单里的选项没画全** | A5 表单类型只画了 5 个（PRD 是 7 类）、宠物友好标签只画了 4 个（PRD 是 6 个）。属于示意图省略，**实现按 PRD 全集**，UI 稿不用改 |
| 3.5 | **场所评论的 👍 / 👎 容易被误读** | PRD 定的是「提交评论时可选的二元态度」，详情页两个计数是**评论态度的累计**。UI 稿 A4 把两个圆钮放在输入条右侧与发送键并列，视觉上很像「给场所点赞 / 点踩」（与评论无关的独立动作）。✅ **已定：维持 PRD 口径**，UI 稿 A4 两个钮收进评论输入的展开态，计数口径写进 story 验收（B1-D3）。 |
| 3.6 | **H5 页只露「推荐」数** | A9 写的是「👍 12 suka」，没有不推荐数；App 内详情页是两个计数都露。如果是有意为之（分享页偏营销），写一笔即可，别让研发以为是漏画 |
| 3.7 | **「被拉黑者看拉黑者主页」的空态必须与真·没内容长得一模一样** | 这是有意不明示拉黑（PRD 已声明是对 1.1.4「完全无感」的例外）。实现上两种情况**必须复用同一个组件、同一句文案**，否则用户一对比就能推断出自己被拉黑，设计意图就废了。写进 story 验收条件 |
| 3.8 | **埋点属性别带场所名 / 地址 / 坐标** | 埋点层有一道兜底黑名单，名字、地址、经纬度这类键会被整条丢掉（传了也没数据）。场所埋点按 PRD 只传 id / 类型 / 数量是安全的 |
| 3.9 | **UI 稿写「现有 24 类通知」** | 实际是 30 类。不影响视觉复用，仅更正事实 |
| 3.10 | **「发帖总数」其实已经有了** | UI 稿 C1 写「加入时间 / 发帖总数 / 获赞总数代码现状无，需后端补充」。发帖总数迷你卡现在就在用，可直接复用；真正要新补的是**加入时间、获赞总数、宠物列表、公开内容列表** |
