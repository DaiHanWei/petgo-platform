# TailTopia V1.3.0 批次 B1 架构决策文档 —— Delta

> **形态说明**：本文件是 brownfield **增量 delta**，只写批次 B1 的**新增 / 取代 / 补齐**；未提及处一律**继承基线**。
> 冲突序：**本 delta > v1.1.6 delta > v1.1.4 delta > v1.1.2 delta > v1.1 delta > V1.0 基线 > 原型**。
> 正确性以 `PRD-v1.3.0-batch-b1-places-social.md` 为准，**产品口径以 `决策日志-batch-b1.md` 为准**（PRD 有两处已被推翻，见该文件）；
> App 视觉以 `ui-v1.3.0-batch-b1-places-social.html` 为准（该稿 2026-09-11 已按代码核对结论修订 4 处，稿内首屏有修订说明表）。
>
> **底线继承（不重述、全部延续）**：Spring Boot 4 / Java 21 / PostgreSQL + Redis + Flyway；模块化单体 + 分层；
> 异步只用 `@Async` + DB 状态机；**禁 MQ / 禁调度中间件 / 禁通用缓存层 / 禁新中间件**；
> DB snake_case ↔ Java/Dart camelCase ↔ JSON camelCase；RFC 9457 ProblemDetail；
> **对外标识一律不可枚举 token**；env 注入凭证不入库；日志禁 PII / 健康 / 令牌 / 签名 URL；`ddl-auto=validate`，schema 归 Flyway。
>
> **服务端运维 envelope 零增量**：不引入任何新中间件、不新增外部服务依赖、不改部署形态（德国单机）。
> Redis 为**既有**组件，本批次对它的使用沿用既有计数器形态，**不构成"引入缓存层"**——见 AD-9 的边界说明。
>
> **App 端依赖增量：一处。** 地图 SDK（见 AD-3）。项目现无任何地图或定位库，属真新增依赖。
> **后台（Web）依赖增量：一处。** 冷启动录入的选点地图，与 App 同厂商、另一套密钥。
>
> **跨批次关系**：

> - 批次 B1 → 批次 B2：⑧场所打卡、FR-117 Tailsonality、FR-120 护照盖章均**不在本批次**。
>   本批次的场所详情页不含打卡按钮，宠物卡上的 Tailsonality 小标位天然空状态、**不做占位设计**。
> - 批次 B1 → 后台 AB-17A（场所内容管理）：**同版本硬配套**，归 admin 主题。
>   ✅ 2026-09-14 已确认后台侧在做，不再是阻塞项。

## §1 Design Paradigm

形态不变：**模块化单体 + 分层**。本批次新增一个模块 `place`（场所本体 / 场所评论 / 场所分享页），
其余能力落在既有模块内部：公开主页与 @ 提及归 `auth`/`content`/`social` 既有边界，宠物推荐归 `profile`。

**新增跨模块依赖边（三条，全部单向、无环）：**

1. `place` → `shared/media`（照片走既有上传链路与公开桶）
2. `place` → `social`（场所评论要按拉黑关系过滤，见 AD-7）
3. `content` → `social`（@ 候选集要排除拉黑双方；这条边 v1.1.4 起已存在，本批次只是多一个调用点）

**不新增的边**：`place` **不依赖** `profile`；场所与宠物之间在本批次没有任何关联字段
（⑧打卡才会引入 `content_posts` 的场所关联，那是批次 B2 的事，本批次**不预留列**）。

## §3 Invariants & Rules

### AD-1 — 场所只存经纬度 + 文字地址，对外走不可枚举 token

1. `places` 表存：名称、类型、标签集、**纬度 / 经度（两个独立数值列）**、文字地址、描述、照片列表、标记人、状态。
2. **不存**任何地图厂商的对象 id / POI id / plus code。理由：换厂商时数据一行不用动。
3. **对外标识用不可枚举 token**（与名片 / 内容分享同款）。自增 id 只在站内 API 与后台使用，
   **绝不出现在分享链接里** —— 用场所名或自增 id 拼链接，等于让任何人按名字或按序号爬全站场所。
4. 照片走既有 `MediaUploadUseCase` 与**公开桶**（CDN 分发、长期有效），因此 AD-5 的 OG 预览图才成立。
5. 文字地址是**必填的位置备注**，平台**不做地理编码、不校验它与坐标是否一致**（PRD ① 明定）。
   → 因此它是**纯展示 + 一键复制**的字符串，不得被任何逻辑当作可解析的结构化地址。

### AD-2 — 距离排序：纯 SQL + 范围粗筛，不装扩展

1. 库内**零地理扩展**（已核实：全部迁移里没有一条 `CREATE EXTENSION`）。本批次**不引入**。
2. 排序算法：先用**经纬度矩形范围粗筛**（把候选缩到合理半径内），再在结果集上算直线距离排序。
3. 纬度、经度**各建索引**；粗筛必须能吃到索引，否则全表扫。
4. 🛡 **禁止**：装 PostGIS / cube / earthdistance；接任何三方 LBS 服务（违反假设 A-2 与"禁新中间件"）。
5. 无定位权限时**按最新排序**（PRD ②），此时不得走距离分支——两条路径要在查询层分开，
   不要用"距离为 null 排最后"这种写法把两种语义混在一条 SQL 里。

### AD-3 — 地图 SDK 只做显示与打点

**本条推翻 PRD §2.1 ① 的「flutter_map + OpenStreetMap」写法，以本条为准（B1-D9）。**

1. **允许**：显示地图、缩放拖动、把我们自己库里的经纬度渲染成标记、读取设备当前位置（走系统定位，与厂商无关）。
2. 🔴 **禁止**：地点搜索 / 自动补全、地址与坐标互转、路线规划。**这三类才是按次计费的**，
   而 PRD 本就写明"平台不做地理编码"，天然避开。谁要加，先回来改这条。
3. 地图出现的位置**只有两处**：标记场所时的选点弹层、场所详情页的定位小地图。
   列表页**不得**嵌地图（那是 PRD ⑥ 明确排除的"地图浏览视图"）。
4. 密钥三套（iOS / Android / 后台 Web），**一律 env 注入、绝不入库**，示例文件只放占位；
   每把加平台限制 + 每日调用配额上限。
5. 「在地图中打开」按钮是**普通跳转链接**（交给系统地图 App），不算 API 调用，不计费。

### AD-4 — 宠物站内访客视图：新建 petId 入口，复用既有投影层

1. **新建**一条按 petId 的站内访客接口，**仅登录用户可用**。
2. **复用 v1.1.6 AD-1 建立的那层只读投影**（结构上就取不到健康记录与问诊存档），**不另起一套**。
   两个入口（分享 token / 站内 petId）**必须落到同一个投影**，否则迟早分叉，而分叉的表现是私密数据从新入口漏出去。
3. 🛡 **不下发对方宠物的分享 token**（B1-D1 否掉的方案）：那等于把一条**永久公开、可转发到站外**的链接
   发给每一个站内访客。站内可见 ≠ 可对外分发。
4. 该通道**一次两用**：FR-118 主页的宠物卡与 FR-121 推荐集合的宠物卡走同一条，不各建一套。
5. 站内入口进入时，**隐藏「由 XX 分享」来源横幅**（站内点击不存在"谁分享的"这个语境），
   返回应回到上一页而不是落首页。⚠️ 访客视图**没有日历**（2026-08-18 / 08-28 两次拍板不做），
   UI 稿 C6 原稿画错、已于 2026-09-11 修订，**不要照旧稿补回去**。

### AD-5 — 场所分享 H5：复用直出，OG 预览图是有意例外

1. 复用既有服务端直出模式（Thymeleaf），路径形如 `/place/{不可枚举 token}`，与 `/p/` `/c/` `/m/` 同一套风格。
2. 下架后返回统一「场所不存在」空态 + 404 + noindex（复用名片失效页的既有做法），**链接长期有效**。
3. 🔴 **放 Open Graph 预览图（含 og:image），这是对既有边界的有意例外**：
   名片页与里程碑页刻意**不放**预览图，理由是不把**宠物照片**交给第三方抓取与缓存。
   场所照片是**场所本身的公开内容**，不含个人与宠物隐私，且 WhatsApp 预览卡正是这条分享链路的核心价值（约朋友同去）。
   **写这一条是为了防止下一个人把它当成漏做而"修正"掉。**
4. 分享页**不接入 FR-96 分享奖励**（2026-08-31 拍板：奖励渠道只有年龄卡 / Tailsonality 卡 / 护照卡三个）。
5. 已装 App 的访客要能被唤起进 App —— 唤起链沿用名片页那套（pagehide 判成功 + 超时回落商店），
   并**同步在安卓清单声明对应的深链 host**，否则安卓侧系统不认、唤起必失败。

### AD-6 — 主页 / 推荐 / @候选 的取数一律批量

继承 v1.1.6 AD-7 / AD-11 同一条规则族，本批次新增四个调用点：

1. 公开主页的**发帖总数 / 获赞总数 / 宠物列表 / PUBLIC 内容列表**——一次批量聚合，禁逐条查。
2. ⚠️ **发帖总数已经有了**（迷你主页卡在用），直接复用；真正要新补的是**加入时间**与**获赞总数**。
3. 推荐集合的宠物卡（头像 / 名字 / 物种年龄 / 最近一张公开照片 / 陪伴天数）——一次批量。
4. 🛡 **禁止为这些聚合新增冗余计数列**（AD-9 的 Redis 计数器是**经明确拍板的例外**，不构成先例）。

### AD-7 — 拉黑过滤四处共用同一出口

1. 四处都要按拉黑关系过滤：**场所评论、公开主页、@ 候选集、宠物推荐**。
2. 🔴 **必须复用既有的那个拉黑关系读取口**（`social` 模块已有），**禁止各写各的查询**。
   理由：写漏的那一次是**静默**的——没有报错、没有告警，只有被拉黑的人看见了他不该看见的东西。
3. 口径：**任一方向存在拉黑关系即排除**（我拉黑的、拉黑我的都算），@ 候选与宠物推荐**双向互不出现**。
4. 🔴 **主页维度是对 v1.1.4 FR-94「被拉黑方完全无感」的有意例外**（PRD §2.2 已声明，1.1.4 文档不回改）：
   被拉黑者访问拉黑者主页 → 显示模糊空态「暂无内容（对方的隐私设置）」。
   **该空态必须与"对方真的没有公开内容"复用同一个组件、同一句文案**，否则两种情况一对比就能推断出被拉黑，设计意图作废。
   Feed 与评论**不屏蔽**（被拉黑者仍正常看到对方内容）。
5. 判定一律在**服务端**做。客户端过滤只是"看不见"，抓包照样拿得到。

### AD-8 — 场所评论独立建表

**2026-09-14 拍板。**

1. **新建 `place_comments` 表**，不改既有 `comments`。
2. 理由（两条）：
   - 既有 `comments.post_id` 是 **NOT NULL** 且语义绑死在内容帖上。要共表就得把它改成可空再加场所列 —— 那是**多态外键**，
     而 v1.1.6 AD-10 已经为同类问题定过先例：**两套独立表，不共用、不用多态外键**。
   - 两者的形态本就不同：场所评论**只有一级、不能盖楼**（PRD ③：攻略提示性质，无对话需求），
     而内容评论有楼中楼。共表等于把"不能回复"变成一条只靠代码自觉维持的约定。
3. **审核链路复用不共表**：场所评论文本走与内容评论**同一套三方审核**（先发后审），
   但审核状态列各存各的。举报复用既有五类选项抽屉。
4. 场所评论附带**二元态度**（推荐 👍 / 不推荐 👎，可为空）——落在本表的一个列上，
   **不是独立投票**：不写评论就不能表态（B1-D3）。

### AD-9 — 推荐/不推荐计数：Redis 计数器 + DB 回算自愈

**2026-09-14 拍板：场所列表页要出统计数，计数走 Redis。**

1. **列表页展示**推荐 / 不推荐两个计数（不只详情页），因此这两个数进入**列表查询的热路径**。
2. 载体：**Redis 计数器 + DB 回算自愈**，形态**逐字沿用既有未读角标那一套**
   （`notify:unread:{userId}`：读不到 / 对不上就从库里重算再写回）。
3. 🔴 **这不是"引入通用缓存层"，不要据此认为缓存层解禁**：
   - Redis 是**既有**组件（本就在跑），不是新中间件；
   - 用法是**单个整数计数器 + 可从库完整重算**的派生数据，不是"给查询结果加一层缓存"；
   - **真值永远在 `place_comments` 表里**，Redis 丢了只是慢一次，不丢数据。
   任何"给场所列表整页结果做缓存"的做法都**不在本条授权范围内**，仍受基线"禁通用缓存层"约束。
4. 本版**不做列表降权、不做警示标**（PRD ③：先积累数据）。所以这两个数**只展示、不参与排序**。
5. 计数变更的触发点只有两个：评论创建（带态度）、评论被删/被下架。两处都要同步计数。

### AD-10 — @ 候选集独立建表；正文存 userId

**2026-09-14 拍板：候选集新建一张表。**

1. **新建关系表**维护"最近互动过的人"，**不每次打开输入框现扫**评论与点赞记录。
   理由：现扫要跨多张表回溯，输入框是**打字时的即时交互**，慢一点就毁掉体验。
2. 候选口径（PRD §2.3）：评论过我 / 我评论过 / 赞过我的 / 与我互相回复对话过的用户，**取最近 30 人**；
   **任一方向拉黑关系的双方互不出现**（走 AD-7 的同一个出口）。
3. 输入昵称**只在这 30 人内过滤**。🔴 **没有全局用户搜索**（搜索留在 1.6.0 未前移）——
   界面上那个输入框**不是搜索框**，@ 不到没打过交道的陌生人。
4. 🔴 **正文与评论里存下来的 @ 一律存 userId，不存昵称**：
   存昵称的话，对方改名后所有历史 @ 全部失效、点不动，而且无法判断拉黑关系。
   渲染时按 id 查当前昵称。
5. 通知：新增一个通知类型。⚠️ **加类型必须整张重列 CHECK 约束全集**（见 §4），这是本批次最容易翻车的一步。
6. 单条内容 / 评论 @ 上限 **5 人**；存量文本**不回溯解析**；删内容 / 删评论后**已发出的通知不撤回**
   （点进去显示「内容已删除」统一空态）。

## §4 Consistency Conventions

### 4.1 Flyway

- 本批次新增迁移**一律时间戳版本号** `V<yyyyMMdd_HHmm>__<snake_case>.sql`（CLAUDE.md 决策 E7），基线 `V20260902_1620`。
