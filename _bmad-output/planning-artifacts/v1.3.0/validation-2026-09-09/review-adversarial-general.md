## 一、代码证实与 PRD 论断不符（🔴）

1. **AB-16A「换绑后既有会话立即失效」无法按现状实现，假设 B-2 的退路也不成立。** 无 spring-session / SessionRegistry，会话是容器内存 HttpSession；`AdminSessionGuardFilter` 每请求只重查 `status==ACTIVE`，不比对邮箱/版本。换绑后旧持有人会话会活到 8h 超时。B-2 说「最低要求下次请求按新状态生效」——权限在 `AdminUserDetailsService.loadUserByUsername` 登录时一次 `resolvePermissions` 固化进 Authentication，下次请求不会重算。需明确要求：guard filter 增加账号版本号（或邮箱快照）比对，不匹配即 invalidate。
2. **同一根因打穿 AB-21A「角色改权限立即生效，影响该角色下所有账号」与 G0 顶栏「改名/改角色后下次请求即更新」。** 两处写成硬要求，但没有对应的「每请求重算权限」实现要求；不加就是重登才生效，运营会以为改了没用。
3. **AB-18A「0 元限免落 0 元购买记录」撞总账约束。** 两张资金表 `CHECK (amount > 0)` / `CHECK (amount_idr > 0)`，0 元不可能进账本流水。须写明「购买/解锁记录」与「账本流水」分离、0 元只落解锁记录不落账；对账页与看板付费口径如何排除 0 元单。
4. **AB-18A 假设 B-4「配置机制支持按 key 扩展」不成立。** 现状 `AdminConfigService` 每个价格一列（`id_hd_download_price` 为固定列 + `ConfigType.PRICING` diff 审计），不是 key-value。每加一款护照样式 = 加列 + Flyway 迁移 + 发版，PRD「工程随发版在配置组内加行」要改写为「每款样式一次迁移」，或本版顺手改成 key-value 表（这是架构决策，应进 delta）。
5. **AB-20A「虚拟评论走 App 同链路」与审核链路、即时反馈两处冲突。** `CommentService` 现状三段：L1 硬黑名单命中 → 同步 422 不落库；否则先落 `UNDER_REVIEW`（只评论人自己可见）→ 阿里云异步评分 → 通过才转 `VISIBLE` 并通知楼主；评分 DEGRADED → 入 A1 人工复核队列。同链路 ⇒ 运营发的暖评①要过机审②不是立即公开③可能进 A1 让运营自己审自己；PRD 写的「发布成功 toast、列表评论数即时 +1、作者收到通知」与 UNDER_REVIEW 秒回语义不符。绕过审核 ⇒「同链路」不成立。必须二选一写明。另评论上限现状 200 字（`CommentCreateRequest @Size(max=200)`），PRD 直接写 200。
6. **AB-17A 假设 B-3「举报对象类型可扩展」不成立。** `ContentReport` 只有 `postId`，`AccountReport` 只有 `targetUserId`，没有通用 targetType。场所举报 = 新表 + A1 新页签/新 TicketType + 处置动作接线，估算须按「新建」计，不是「复用」。
7. **AB-15A 排除口径有隐性 bug。** Apple 登录用户 `google_sub` 为 NULL（`User.java` 注释明写），SQL 里 `google_sub NOT LIKE 'admin:%'` 对 NULL 返回 NULL ⇒ 整批 Apple 用户被排除出用户类指标。SQL 到位后必须核 NULL 处理；PRD 口径应写「google_sub 为空视为普通用户」。另 `role=ADMIN` 只是 Story 3.1 遗留的旧账密运营号（现后台账号在 `admin_accounts` 独立表），排除它是对的但应注明是历史残留。
8. ~~「四语言包零缺失」不属实~~ **【已撤回】** 初判依据是行数差（en 2141 / id 2088），精确 diff key 集合后 en 与 id 完全一致，差异全是注释与空行。PRD 该论断成立。

## 三、缺口与风险（🟡）

19. **AB-15A 历史回填只做付费 4 项，其余 14 项「自然积累」。** 上线当天 7/30 天图几乎全空；验收「任一天数值与 SQL 直跑相等」对上线前日期天然不成立（无物化行=断点，SQL 直跑却有值）。须拍板：上线时一次性回填全部 18 项到 2026-07-17，或验收只覆盖上线后日期。
20. **「总安装用户数」名不副实。** 库里只有注册用户，无安装/登录日志（§1 ③ 自己承认）。管理层会当下载量读。改名「累计注册用户」或加口径提示。
21. **AB-15A 对全部后台账号可见**，含付费人数/次数（收入敏感），发货专员、客服都能看；与既有 `shop.finance_view` / `order.view` 分权理念相悖。至少付费卡按权限渲染。
22. **AB-19A 删除独立详情页会打断深链。** content-detail / user-detail / consult-order detail / vet-edit / vet-qualification 被「直接删除」后，审计日志目标链接、A4「去取证」深链、Lark bug 表里贴的后台直链全部 404。PRD 只对 reports 说「端点保留」。需要统一迁移规则：旧详情路由 302 到列表页 + `?open=<id>` 自动开抽屉。
23. **AB-19A 验收基线过期。** 写的是 `dev/dev_1.1.6`，该分支 09-07 已合入 main；且 v1.4.0 电商线仍并行开发，商城组 17 页会继续变。37/63 页整包重构与并行线的合并策略 PRD 未提——这是刚讨论过拆 ops 服务时的同一类风险，只是规模小一档。底账应改为 `dev_1.3.0`，并写明商城组页面以 v1.4.0 合入后为准。
24. **四份被引用的输入不在仓库。** `后台功能全量清单-20260901.md`（AB-19A 验收底账）、`内容运营所需数据.sql`（AB-15A 口径权威）、`1-3-0prd.md`（AB-17A 护照章合并语义靠 FR-120 定义）、`.decision-log.md`。PRD 自己点名「SQL 与看板两处走散是最大长期风险」，却没把 SQL 纳入版本控制。
25. **AB-20A 暖贴回复跟进的入队/出队边界未定。** 依赖「评论回复创建」事件 + 判父评论作者 ∈ 虚拟池（现有通知事件曾踩 AFTER_COMMIT 事务吞写坑）；回复被下架/作者自删是否出队、同一虚拟评论被反复回复的合并窗口、队列积压上限均未写。
26. **AB-20A 防识破只有提示没有硬规则。** 「今日已评 N」「≥3 黄条不拦截」都是软提示；无每账号每日上限、同一作者被同一虚拟号高频评论限制、虚拟号互评禁止。产品接受权重被推高，但应至少把「虚拟评论占比」列为看板监控指标并设告警线。
27. **AB-16A 换绑「不得与任何既有账号（含已停用）邮箱重复」+「永不删除」** ⇒ 邮箱一旦用过永久占用，离职再入职只能重新激活旧号。若这是期望行为请写明；否则要允许已停用账号释放邮箱。
28. **WIB 日切与跑批时机。** AB-15A 按 WIB 切日，预聚合跑批须在 WIB 00:00（UTC 17:00）之后；B23 审计页是 UTC 例外。PRD 要求「与 SQL 一致」但 SQL 时区口径未见，两处极易走散。
