## 总体判断

**两份文档在「资金与售后」这条主链上对得相当齐**（FR-100A ↔ AB-6D/AB-6A、FR-105 ↔ AB-12C、FR-95 ↔ AB-10C 的措辞几乎逐字互锁，C-9「两条溢价必须分开」的意图在 AB-6A 扩展节被完整承接），**但在「履约与状态机」这条链上是断的**——后台能执行的运营动作有相当一部分在用户端三张状态机上找不到落点（部分取消、采购入库、报损、盘点调整），而状态机上多条关键转移在后台没有操作入口（`已发货`→`已送达` 的手动标记、`待用户寄回` 超时关闭）；`已发货` 因此成为事实上的悬空态，与用户端「终态三个、无悬空态」的自我声明直接矛盾。

**最致命的一类是引用错位而非缺失：** 用户端 §2/§3.1/§3.2 有 **4 处 FR 编号整体偏移一位**（把「档案推荐」写成 FR-108、把「粮量见底预估」写成 FR-110），而后台在同样的位置引用的是**正确的** FR-107 / FR-109。两边各自读起来都通顺，合起来读却指向不同条目——这类错误 rubric 与对抗评审都不易发现，只有做交叉表才会暴露。

**配置项闭环方面**，缺口是**双向的**：后台 AB-6D 定义了两个用户端从未定义过行为的开关（PawCoin 电商支付总开关、是否允许抵扣运费），而用户端写死了四个时限值（60 分钟待支付超时、7 日自动确认、7 日退货窗口、7 日寄回超时）和一组年龄阈值，后台**零配置、零提及**。

### 1. 引用双向可解析

#### **[critical] C1 — 用户端 4 处 FR 编号整体偏移一位，与后台的正确引用互指不同条目**
（用户端 §2 L42 / §3.1 L60 / §3.2 L98 / §3.2 L102 ↔ 后台 §1 AB-10A L41,L43 / AB-10B L51 / §4 AB-13B L180）

用户端 §3.9 的权威定义是：**FR-107 = 档案推荐** · **FR-108 = 健康记录触发复购** · **FR-109 = 粮量见底预估** · **FR-110 = 问诊与商品的边界（约束性需求）**。但用户端在下列 4 处按**偏移一位**的编号自指：

| 用户端位置 | 原文 | 应为 | 后台在同一事上写的 |
|---|---|---|---|
| §2 术语表「复购触发卡」 | 「由结构化健康记录周期或粮量见底预估驱动（**FR-109/FR-110**）」 | FR-108/FR-109 | — |
| §3.1 FR-93 区域② | 「「Pilihan buat {宠物名}」，**按档案推荐（FR-108）**，4–6 个商品」 | FR-107 | AB-10A L43：「三字段决定 **FR-107** 档案推荐的过滤结果」 |
| §3.2 FR-94「适用物种」 | 「犬 / 猫 / 通用。**用于 FR-108 档案推荐过滤**」 | FR-107 | 同上 |
| §3.2 FR-94「每日建议喂量」 | 「**FR-110 粮量见底预估**的计算依据，不是展示文案」 | FR-109 | AB-10A L41：「该字段是用户端 **FR-109** 粮量见底预估的唯一计算依据」；AB-10B L51：「净含量是 **FR-109** 的计算输入」 |

后果不是排版瑕疵：实现者从后台 AB-10A 顺着 FR-107 找到用户端，读到的是 FR-107 正文（正确）；但从用户端 FR-94 顺着 FR-110 找过去，读到的是**「兽医不得推荐具体 SKU」的约束性需求**——一条与喂量字段毫无关系的条目。FR-110 因此被两侧赋予两种完全不同的语义。同理 FR-108（健康记录触发复购）被用户端两处当成「档案推荐」。§9 OQ-29「复购触发卡（FR-108/109）」与后台 AB-13B「FR-107/108/109」用的都是**正确**编号，说明错的是这 4 处而非定义本身。

*Fix:* 用户端 4 处分别改为 FR-108/FR-109、FR-107、FR-107、FR-109。改完后重跑一次 `grep -o 'FR-1[01][0-9]'` 交叉核对。

#### **[high] H10 — AB-11B 引用了 AB-11C 中不存在的「配送方式配置」；FR-99 的两档配送方式在后台只有一个服务范围集合**
（用户端 §3.4 FR-99 L198-206 ↔ 后台 §2 AB-11B L94 / AB-11C L100-103）

用户端 FR-99 定义两档配送方式，且**适用范围不同**：「当日达（Sameday）· GoSend/Grab Express · 适用范围：**服务范围内的同城 Kecamatan**」与「标准快递（Reguler）· JNE/SiCepat/Anteraja · 适用范围：**服务范围全部**」。

后台 AB-11B L94 写：「承运商为下拉枚举（…），**与 AB-11C 的配送方式配置联动**」——但 AB-11C 全节只有四条后果：服务范围（Kecamatan 粒度、可批量导入）、运费二维表、免运费门槛、变更不追溯。**没有任何「配送方式配置」**，也**只有一个服务范围集合**，无法表达「这个 Kecamatan 可当日达、那个只能标准快递」。

同时 AB-11C 是 FR-99 的唯一落点，却是全后台文档中**唯一被用户端点名两次（L196、L205）却零 FR 反向引用**的条目。

*Fix:* AB-11C 补「配送方式主数据（含承运商归属 + 可达范围）」配置项，服务范围改为按配送方式分别维护；或在 FR-99 明确「当日达可达范围 = 服务范围全集」从而取消差异。二选一必须落一个。

用户端 FR-102：`已送达` 的进入条件是「**承运商标记送达 或 后台标记**」。但后台 AB-11B L95 明确：

> 「**首版不接承运商 API**（对应用户端 FR-103 分期理由），因此「已送达」状态需后台手动标记或依赖用户确认收货。后台需在待办中列出「已发货超过 N 日未确认收货」的订单供运营跟进」

即：**两个进入条件里的第一个（承运商标记）首版不存在**，只剩「后台标记」。而后台**并没有把「标记已送达」定义成一个操作**——AB-11B 全节只定义了「发货操作 = 选择承运商 + 录入物流单号 + 确认发货」和批量发货，AB-11A 的列表/详情字段里也没有该动作。上面那句话是在**解释困难**，不是在**定义入口**。

连锁后果：
1. 运营不手动标记 → 订单停在 `已发货` → `已送达` 永不到达 → **「送达后 7 日自动确认」永不触发** → 订单只能靠用户主动确认收货才能到 `已完成`；不确认的订单**永久停在 `已发货`**。
2. 用户端 §4.1 声明「**终态为 `已完成` / `已取消` / `已退款` 三个，无悬空态**」——该声明在首版不成立。
3. FR-102 中 `已发货` 状态下用户唯一可执行操作是「查看物流」，**没有确认收货入口**（确认收货挂在 `已送达`）。所以用户即便收到货，只要运营没标记，也无从确认。
4. AB-11B 的「已发货超过 N 日未确认收货」待办，逻辑上应该是「已**送达**超过 N 日」——它跳过了 `已送达` 状态直接从 `已发货` 计时，等于默认了这条转移不会发生。

*Fix:* ① AB-11B 明确新增「标记已送达」操作（单条 + 批量），并纳入 AB-11A 订单详情；② FR-102 在 `已发货` 状态补「确认收货」为用户可执行操作（用户收到货即可自行推进），使运营漏标记不再是死锁；③ 明确无人标记时的兜底（如「发货后 N 日自动视为送达并起算 7 日」）。

#### **[high] H1 — AB-11D 的「部分取消」与「已支付订单取消」在订单状态机上无对应转移**
（后台 §2 AB-11D L108 ↔ 用户端 §3.6 FR-102 L342-356 / §4.1 状态机图 L489-505）

AB-11D：「缺货无法履约时，运营可发起**整单取消或部分取消**，均走退款流程（模块 12）」。

*Fix:* AB-12A 明确「运费归属由退货类型自动推导并只读展示，CS 仅在**例外**情形下可覆写且必须填理由」（并在 FR-104 补例外条款），或删去「必须分开判定」的要求。

### 6. 开放项与依赖对齐

于是运营在 AB-10A 把某商品标成「可退可换」后，用户端会据此展示「可换」承诺，而**平台没有任何执行换货的能力**。这是一个直接可被用户援引的对外承诺缺口。

（注意这也解释了 §3.7 与后台模块 12 标题里的「换」字从何而来——章节名先有，流程一直没补。）

*Fix:* 二选一并两侧同步：① 首版删除「可退可换」枚举值，标识改为二值（`开封不退` / `不可退换` / `可退`），§3.7 与后台模块 12 标题改为「退货与退款」，并在用户端 §7「非本版本范围」显式列入「换货」；② 或补齐换货全链路（订单状态、退款状态机分支、AB-12B 质检后补发、AB-11B 补发发货、AB-10C 换货出入库）——工作量不小，建议走 ①。

#### **[high] H9 — AB-13B 的核心指标「触发卡转化率 vs 普通商品曝光转化率」在 §5 埋点侧不可得**
（后台 §4 AB-13B L188 ↔ 用户端 §5 埋点表 L549-560 / §10 A-16 L632）

AB-13B 明确点名：

> 「**触发卡转化率 vs 普通商品曝光转化率**｜二者对比是判定 **A-16** 成立与否的直接依据」

而用户端 §5 的 13 个事件里，能承载「来源」的只有三个：`product_impression`（有 `zone`）· `product_detail_viewed`（有 `entry_source`）· `add_to_cart`（有 `entry_source`）。**转化终点 `order_submitted` 的属性只有 `order_id` / `amount` / `shipping_method`，`payment_succeeded` 只有 `order_id` / `amount` / `channel`——两者都不带 `entry_source` 或 `trigger_type`。**

所以埋点能算的只到「触发卡 → 加购」，算不到「触发卡 → 下单/支付」。AB-13B 若按加购口径算，与「普通商品曝光转化率」比较时口径也必须同为加购——但表里写的是「转化率」，未限定。

这直接关系到 A-16（致命度**高**：「若触发卡点击率不显著高于普通商品曝光，则本版本的核心论证不成立」）能否被验证。考虑到 decision-log L-6 与 §5 已经为「基线缺失导致指标不可得」立了一次前车之鉴，这里再踩一次同类坑代价很高。

*Fix:* §5 给 `order_submitted` 与 `payment_succeeded` 补 `entry_source` / `trigger_type` 属性（或补一个订单级的 `attribution_source`）；AB-13B 明确该指标的转化终点定义（加购 vs 下单 vs 支付成功）。

#### **[medium] M4 — 后台 OQ-30/31/32 在用户端 §9 无登记、在 decision-log 无 D 编号跟踪；用户端 §9 从 OQ-26 直接跳到 OQ-33**
