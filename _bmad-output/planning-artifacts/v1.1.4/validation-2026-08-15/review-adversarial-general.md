# 对抗式评审 — TailTopia V1.1.4 社区管控 PRD

**方法**：结合 `petgo-platform` 仓库真实代码逐条核对 PRD 对"既有实现"的断言，并寻找产品逻辑漏洞与口径矛盾。
**核实基准**：`hex/v1.1.4` 工作树（2026-08-15），跨 `main` / `stag` / `hex/v1.1.6` / `feat/content-moderation` / `v1.1-dev` 交叉验证。
**说明**：UI 稿只读到泳道 B 中段（B6），泳道 C/D 未覆盖。

---

## 一、PRD 断言与代码不符

### 1. [critical] 「评论举报已上线」是假的

PRD 四处把它当既成事实：§1 版本目标、§4 AB-3D 的工单类型标签、§6 第 1 条与第 3 条、§4.1 给 PM 的备注。

实测：五个分支上均无 `comment_report` 数据表、无 CommentReport 实体、无提交接口、App 端无入口。举报能力目前**只有帖子级一种**。

**后果**：AB-3D「统一视图」要统一的四类工单里有一类根本不存在；§4.1 那条"评论举报的后台界面要展示所属帖子和父评论"是在给不存在的功能提要求。

*Fix:* 确认评论举报的真实状态。若确实未做，AB-3D 的工单类型定义与 §6 第 1/3 条须重写；若产品认为它属于本版本范围，则本版本实为 3 条 FR 而非 2 条，工量需重估。

### 2. [critical] 迷你主页卡不是"5 个元素的纯展示卡"

PRD §3.1 与 UI 稿 A1 均逐字断言卡片只有头像/昵称/发布数/「主页筹备中」/关闭，并称"其余 5 个元素逐项保持不变"。

实测：2026-08-07 加入了第 6 项——**个性签名**（用户自填 ≤60 字）。且「主页筹备中」**不是常驻文案，是没设签名时的兜底**：有签名就显示签名、不显示那句话。

**后果**：25 屏 UI 稿全部画的是兜底态，签名态一屏未出；更要紧的是签名为用户自填文本，骚扰账号可把攻击性内容写在签名里，而那段文字就展示在举报卡上——PRD 未涉及。

*Fix:* UI 稿补签名态（含长签名下「⋯」菜单与文字的排版关系）；产品明确签名是否需要随账号举报一并进入工单上下文。

### 3. [high] OQ-A5「评论查询没有 viewer 上下文」判断相反

PRD 写"现有评论查询接口没有 viewer 上下文，这是一处实打实的接口改造，不要按'加个 where 条件'估工时"。

实测：评论的**每一个**查询方法都已带查看者身份（一级评论、二级回复、批量回复、评论计数，四个全带），因为内容审核那版已做过"作者始终看得到自己被挂起的评论"这层过滤。R1 基本就是加一个条件。

*Fix:* 删除该警告，避免工时被估高；OQ-A5 保留，但焦点改为 R2 的多一层归属判定与索引。

### 4. [high] 真正缺 viewer 上下文的地方 PRD 漏了

迷你主页接口是**游客可读、完全不要求登录**的。而 FR-94 生效范围第 4 条要求"主页访问拦截必须服务端校验"——这意味着该接口须从匿名可读改造成认识调用者，是实打实的接口变更。PRD 把警告贴在了不需要的地方，没贴在需要的地方。

*Fix:* 在 OQ-A5 中补入该接口的改造，并明确改造后游客访问的行为是否变化。

### 5. [medium] FR-51 回告文案与线上不一致

PRD §6 第 2 条以描述既有机制的口吻写"通知文案统一为「你的举报已处理，感谢你帮助维护社区环境」"。线上实际发的是「举报已处理 / 感谢你的举报，我们已完成审核。」

*Fix:* 明确这是未言明的文案变更还是笔误；若要改，作为一条独立需求列出。

## 二、产品逻辑漏洞

### 6. [critical] 只在评论区骚扰、从不发帖的账号，既举报不了也拉黑不了

迷你主页卡在全 App 只有两个触发点：首页 Feed 卡片作者、内容详情页作者。**评论区的头像点了不弹卡。**

而 PRD 把迷你卡定为账号举报的唯一入口、拉黑的主入口（另一入口在黑名单页，但要进那儿得先拉黑过）。

**后果**：FR-94 整套影子评论、R1/R2、通知抑制全是为**评论区骚扰**设计的，却**没有办法从评论区现场发起**。这是本版本最大的闭环缺口。

*Fix:* 评论区头像接入迷你卡（并复核已注销/已拉黑分支），或在评论行内增设「⋯」→ 举报/拉黑。

### 7. [high] 举报账号没有任何自动处置，而举报帖子有

既有实现：以"违法违规"为由举报一条帖子，**一次就会自动把帖子翻回挂起态**；或去重后满 10 人举报同样自动挂起。

账号举报的五个原因里有「发布违规内容」，语义最接近，但 PRD 对自动预处置只字未提，§5 只否掉了"自动封号"。

**后果**：又出现一遍方案甲要消灭的塌陷——举报一条帖子会触发平台自动动作，举报整个账号什么都不会发生——只是这次落在平台处置层。

*Fix:* 产品明确账号举报是否需要自动预处置（例如 N 人举报同一账号自动挂起其全部内容待审），或明确写"账号举报一律人工、无自动动作"并说明为何与帖子级不同。

### 8. [high] AB-3D 的优先级公式与既有优先级机制是两套，没说怎么合

既有内容举报已有一套 P0/P1/P2 阈值判定（含自动预处置）。新公式是"举报人数 + 高频举报人数"。两套并存时：内容举报工单按哪套排？改用新公式则自动预处置的阈值语义分叉；两套并存则"统一视图"无法统一排序。

*Fix:* 明确统一后的排序口径，以及内容举报的 P0 自动预处置是否保留、与新公式如何共存。

### 9. [high] 举报成功后内容什么时候消失，没定义

既有内容举报有明确的成功回调——**乐观移除 Feed 卡片 / 从详情页退回列表**。账号举报的 UI 稿 B5 只说"点关闭后两层一并收起，回到点开迷你卡之前的页面"——那个页面就是 Feed，上面还挂着那个人的帖子。而 PRD 说"立即隐藏"。

**后果**：用户会看到"我举报了，但他的内容还在"——第三次落回同一个塌陷。

*Fix:* 明确账号举报成功后当前列表的处理（建议比照内容举报做乐观移除该作者全部可见卡片）。

### 10. [medium] 误举报没有任何退路

举报只要三次点击，后果是该账号全部内容对我永久消失、不可解除、不进黑名单页，且他在我帖子下的所有评论对所有人隐藏。PRD 类比帖子级隐藏证明"不可解除"合理，但 §7 自己也承认"影响面差别很大"（一条帖子 vs 一个人的全部内容），却未据此给任何补救路径。

*Fix:* 至少给一条兜底（如客服工单可人工解除），或在举报二次确认里明示"该操作不可撤销"。

### 11. [medium] OQ-A6「不会空页」的结论缺依据

Feed 是游标分页。过滤是"先取 N 条再过滤"还是"过滤后凑够 N 条"，结果完全不同：前者会出现某页几乎全空、用户以为到底了。结论在拍板前需要看实现方式。

*Fix:* 把该问题移交技术方案阶段一并回答，不要在产品侧先下结论。

## 三、交互与文案缺口

### 12. [medium] 举报失败的 Toast 与抽屉层级未定义

PRD 要求失败时抽屉保持打开、不清空，同时弹 Toast。两者都在屏幕底部，抽屉是贴底模态层。Toast 浮在抽屉上还是被压住，PRD 与 UI 稿均未定义。

*Fix:* 明确失败提示的呈现方式（建议改为抽屉内联错误行，避免层级问题）。

### 13. [medium] 「警告」这档处置是空的

封号给足了中印双语文案、异议渠道、走哪条客服工单。警告只有"系统通知用户违规行为"一句：无文案、无通知类型、无用户可见后果、无升级规则。

*Fix:* 补齐警告的完整定义。

### 14. [medium] 封号通知的印尼语没有落点

后端通知正文是**硬编码中文**。PRD 给了封号通知的印尼语原文，但没说这句话存在后端还是由 App 端本地化。1.1.6 已踩过同一个坑（其决策日志 D-4 专门为此立项）。

*Fix:* 明确通知文案的本地化落点，与 1.1.6 的处理保持一致。

## 四、命名与工程陷阱

### 15. [high] "封号"与"注销"在代码里几乎同名，而 PRD 对两者要求相反

运营停用（封号）在账号状态里叫 `DEACTIVATED`；用户主动注销在迷你卡里叫 `isDeactivated`。

PRD 要求：封号用户**照常展示、可以拉黑、不做特殊标记**；注销用户**匿名化、不弹卡、不可点击**。两条要求相反，承载它们的两个字段名只差一个前缀。而 PRD 全文用的是"注销/封号"这组中文词、从不提字段名——看串一个字就会做反。

*Fix:* 在 PRD 里为这两种状态各加一个明确的英文对照，并在术语表登记。

### 16. [medium] Flyway 序号会撞

`stag` 分支上迁移已排到 V100，当前分支只到 V99。本版本要建拉黑关系表与账号举报表，新迁移须从 V101 起。

*Fix:* 开工前统一迁移号基线，写进本版本的架构 delta。

### 17. [low] ReportService 的既有注释已腐化

其文档注释写"举报人侧仅收到提交反馈，审核结果不回告（V1 无举报进度查询）"，但 FR-51 的回告闭环后来已上线。研发读该注释会误判现状。

*Fix:* 非本 PRD 职责，但可在架构 delta 中列为顺手修正项。
