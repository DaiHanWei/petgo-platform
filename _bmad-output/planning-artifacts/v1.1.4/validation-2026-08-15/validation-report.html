Poor

这是一份决策密度非常高、范围诚实度罕见的 PRD——每一处取舍都写了"为什么这么定""已知代价是什么"，§7 完整保留了备选方案与否决理由，Non-goal 覆盖到了研发最容易按常识做错的地方（双向 Block）。它的问题不在思考质量，而在三处结构性缺陷：作为定案权威的 §7.4 与正文正面矛盾且带着上一版的残留；整份文档没有任何成功度量，而 FR-58 押的正是一个可证伪的赌注（"举报即隐藏会降低工单量"）；以及没有一条端到端用户旅程——这直接导致"从评论区现场发起举报/拉黑"这条主路径无人走查、至今是断的。

对抗式评审进一步改变了判断：这份 PRD 采用了一种"已核代码"的叙述姿态（「⚠️ 核代码后的订正」「本次核 app_id.arb 发现」「核实 ContentNotifyListener 后确认」），把断言抬升为已验证事实，从而关掉了下游的复核动作——而实测至少四条不符，其中「评论举报已上线」和「迷你主页卡是 5 个元素的纯展示卡」两条会直接让 AB-3D 的工单类型定义和 25 屏 UI 稿失准。

关于评级：Poor 由 5 条 critical 触发，不是对文档整体水准的判断。7 个维度里 3 个 strong、1 个 adequate；critical 集中在"未核实的既有实现断言"和"两条 FR 交叉的未定义状态"这两簇上，都是可定点修复的，不需要重写。

1 · Decision-readiness

strong

本文档最强的部分。决策以决策的形式出现，不是藏在"考量"里：§7.1 直接给出定案表，§7.3 列出方案乙/丙及其否决理由，§3.1 与 §3.2 里成组出现的「⚠️ 已知取舍 / 已知后果」把放弃了什么讲得比选择了什么还清楚。OQ 表里的三条未决项是真的未决。

但定案区本身带着上一版的残留，而它恰恰是冲突时的裁决依据。§7.4 标题写"三件事"、底下列了五条；第 2 条要求成功态文案同时说明"已上报"与"已隐藏"，而 §3.1 明确定稿为不提隐藏。研发照 §7.4 实现就会做出与 §3.1 和 UI 稿都不一样的东西。

§7.4 第 2 条与 §3.1 正面矛盾

§7.4 / §3.1
§7.4 写「举报成功态文案必须同时说明"已上报"与"已隐藏"两件事——只说一半用户就会误判」，并注明"见 §3.1"；§3.1 的定稿文案是「已收到你的举报，我们会尽快处理」，并附「⚠️ 已知取舍：文案不提"内容将被隐藏"（2026-08-14 复核后维持不加）」。两处互指、结论相反，且矛盾出现在被标记为"✅ 已定案"的裁决区。
Fix: 删除 §7.4 第 2 条或改写为"成功态文案只说已上报，不提隐藏——已知取舍见 §3.1 与 A-A27"，并同步修 OQ-A11 结案文字。

3 · Strategic coherence

thin

thesis 清楚且有说服力：三个"让内容从我眼前消失"的机制必须语义单调递增，两条 FR 都从它推出来。FR-58 与 FR-94 的分工讲得干净，共用一层过滤的判断也对。

问题是整份 PRD 没有任何成功度量。而 thesis 里包着一个明确、可证伪、且方向不确定的赌注：§3.1 两次声称"降低工单量正是 FR-58 与 AB-3D 的立项理由"。但相反的结果同样合理——举报现在附带"立刻眼前清净"的即时收益，可能让举报量上升。这个赌注赢没赢，上线后无法回答。

high

无 Success Metrics 区块，立项理由无法验证

全文
PRD 押注"账号举报 + 举报即隐藏 → 工单量下降"，但没有工单量基线、目标值、观测窗口，也没有反向指标（举报量上升 / 误举报率 / 举报后解除需求）。
Fix: 补一节 Success Metrics：上线前基线 + 上线后 4 周目标、反向指标（单账号被举报人数分布、举报到封号的转化率）、以及"结论何时回看、谁回看"。

4 · Done-ness clarity

adequate

App 端两条 FR 的完成条件大多可验证：状态表、场景表、Toast 文案、失败态行为、幂等要求，工程可以直接照着写测试。§3.2 的 ①②③ 场景表尤其好用。

但有三处 engineer 读完不知道"完成"长什么样的地方，其中两处是两条 FR 交叉产生的、正文任何一节都没覆盖：既被拉黑又被举报时解除拉黑会撒谎；先举报后拉黑会因幂等要求而"拉黑不成功"。第三处是 AB-3D——本版本唯一的后台交付物、FR-58 的硬前置——只有一页篇幅、没有一条可验收的完成条件。

critical

两条 FR 交叉的状态组合未定义：既被拉黑又被举报

§3.1 / §3.2 黑名单管理
用户先拉黑 B、后又举报 B（PRD 允许，举报后仍可进迷你卡）→ 存在两层隐藏 → 从黑名单页解除拉黑后举报隐藏仍在 → 内容仍看不见，而定稿 Toast 是「已解除拉黑，刷新后可重新看到 TA 的内容」，这句话此时是假的。
反向：用户先举报 B、再从迷你卡拉黑 B → §3.2 要求"重复拉黑不新增记录"、§7.3 要求两类来源共用同一张关系表 → B 不会出现在黑名单页，而定稿 Toast 是「拉黑成功，请在黑名单里查看」，用户找不到人。两条路径都会被当 bug 反馈。
Fix: 补一小节「两种来源并存时的行为」：明确 source 是否可升级（REPORT → BLOCK）、解除拉黑时若仍存在举报隐藏该给什么提示、黑名单页是否收录"既举报又拉黑"的条目。
high

AB-3D 无可验收的完成条件

§4.1
它是 FR-58 的硬前置、必须同版本交付，却没有列表分页/筛选/搜索定义、批量处置的上限与部分失败行为未定、封号是否二次确认未定。运营拿到手无法验收，工程无法估工。
Fix: 按 App 端 FR 的详细度补齐 AB-3D 的界面要求与边界，或明确写"沿用既有后台列表惯例"并点名是哪个既有页面。
high

「警告」处置动作的用户侧后果完全未定义

§3.1 处置动作 / §4.1
封号给足了中印双语文案与异议渠道；警告只有"系统通知用户违规行为"一句：没有文案、没说走哪类通知、没说用户看到什么、多次警告是否升级也没说。
Fix: 补警告的通知文案（中文语义 + 印尼语）、是否可重复下发、是否计入"历史违规记录"。
medium

"立即生效 / 即时生效"未定义可观测时刻

§3.1 举报即隐藏 / §3.2 生效范围
反复出现但没说清是"当前列表立刻刷新"还是"下次拉取生效"。解除拉黑一侧反而定义得很好（措辞刻意用"刷新后"），生效一侧缺同等处理。
Fix: 比照解除侧补一句"生效以下一次拉取为准"，或明确要求当前列表即时移除。
medium

优先级实时计算与列表分页的关系未定

§4.1
"分数实时计算、不落库快照"+"按分数倒序"意味着排序键不在库里，与分页天然冲突，PRD 未给量级假设。
Fix: 给出工单量级预估与"是否接受全量排序"的产品判断，或把该问题移入 OQ 交技术方案阶段。

6 · Downstream usability

thin

这份 PRD 是链条顶端（要喂架构 → epics → story），所以这一维权重高，而它是短板。

没有任何端到端用户旅程。§3.2 的 ①②③ 场景表覆盖了"评论对谁可见"这一个切片，但全文没有一条"某个具体的人从遇到骚扰到解决"的完整走查。代价已经显现：对抗式评审发现的"评论区点头像不弹迷你卡 → 只在评论区骚扰的账号既举报不了也拉黑不了"，是一次五分钟的旅程走查就会撞上的问题。缺 UJ 不是形式问题，是它真的漏掉了主路径。

术语表覆盖不到最吃紧的那个区分。「主动拉黑 vs 举报产生的隐藏」是主页访问规则的唯一依据，却没有词条；正文用来指代同一簇概念的说法至少有五种。

adequate

对抗式评审（代码实证）

review-adversarial-general.md

结合 petgo-platform 仓库真实代码逐条核对 PRD 对"既有实现"的断言，并寻找产品逻辑漏洞。核实基准 hex/v1.1.4 工作树（2026-08-15），跨 main / stag / hex/v1.1.6 / feat/content-moderation / v1.1-dev 交叉验证。UI 稿只读到泳道 B 中段（B6），泳道 C/D 未覆盖。共 17 条，此处列 critical 与 high。

critical

「评论举报已上线」是假的

§1 / §4 / §6
PRD 四处把它当既成事实。实测：五个分支上均无 comment_report 数据表、无实体、无接口、App 端无入口。举报能力目前只有帖子级一种。后果：AB-3D「统一视图」要统一的四类工单里有一类根本不存在。
Fix: 确认评论举报的真实状态。若确未做，AB-3D 的工单类型定义与 §6 第 1/3 条须重写；若产品认为它属本版本范围，则本版本实为 3 条 FR，工量需重估。
critical

迷你主页卡不是"5 个元素的纯展示卡"

§3.1 / UI 稿 A1
实测存在第 6 项——个性签名（用户自填 ≤60 字），且「主页筹备中」不是常驻文案，是没设签名时的兜底。25 屏 UI 稿全画的是兜底态，签名态一屏未出。更要紧的是签名为用户自填文本，骚扰账号可把攻击性内容写在签名里，而那段文字就展示在举报卡上。
Fix: UI 稿补签名态（含长签名与「⋯」菜单的排版关系）；产品明确签名是否随账号举报一并进入工单上下文。
critical

只在评论区骚扰、从不发帖的账号，既举报不了也拉黑不了

§3.1 举报入口 / §3.2 入口
迷你主页卡在全 App 只有两个触发点：Feed 卡片作者、详情页作者。评论区的头像点了不弹卡。而 PRD 把迷你卡定为账号举报唯一入口、拉黑主入口。后果：FR-94 整套影子评论、R1/R2、通知抑制全是为评论区骚扰设计的，却没有办法从评论区现场发起。
Fix: 评论区头像接入迷你卡（并复核已注销/已拉黑分支），或在评论行内增设「⋯」→ 举报/拉黑。

举报账号没有任何自动处置，而举报帖子有

§3.1 / §5
既有实现：以"违法违规"为由举报一条帖子，一次就会自动把帖子翻回挂起态；或去重后满 10 人举报同样自动挂起。账号举报的五个原因里有「发布违规内容」，语义最接近，但 PRD 对自动预处置只字未提。后果：又出现一遍方案甲要消灭的塌陷，只是这次落在平台处置层。
