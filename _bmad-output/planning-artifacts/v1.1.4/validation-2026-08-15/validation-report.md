## Overall verdict

这是一份**决策密度非常高、范围诚实度罕见**的 PRD——每一处取舍都写了"为什么这么定""已知代价是什么"，§7 完整保留了备选方案与否决理由，Non-goal 覆盖到了研发最容易按常识做错的地方（双向 Block）。它的问题不在思考质量，而在三处结构性缺陷：作为定案权威的 §7.4 与正文正面矛盾且带着上一版的残留；整份文档没有任何成功度量，而 FR-58 押的正是一个可证伪的赌注（"举报即隐藏会降低工单量"）；以及没有一条端到端用户旅程——这直接导致"从评论区现场发起举报/拉黑"这条主路径无人走查、至今是断的。

对抗式评审进一步改变了判断：这份 PRD 采用了一种**"已核代码"的叙述姿态**（「⚠️ 核代码后的订正」「本次核 app_id.arb 发现」「核实 ContentNotifyListener 后确认」），把断言抬升为已验证事实，从而关掉了下游的复核动作——而实测至少四条不符，其中「评论举报已上线」和「迷你主页卡是 5 个元素的纯展示卡」两条会直接让 AB-3D 的工单类型定义和 25 屏 UI 稿失准。

**关于评级：** Poor 由 5 条 critical 触发，不是对文档整体水准的判断。7 个维度里 3 个 strong、2 个 adequate；critical 集中在"未核实的既有实现断言"和"两条 FR 交叉的未定义状态"这两簇上，都是可定点修复的，不需要重写。

## Findings by severity

### Critical (5)

**[Decision-readiness]** — §7.4 第 2 条与 §3.1 正面矛盾（§7.4 / §3.1）
§7.4 写「举报成功态文案**必须同时说明"已上报"与"已隐藏"两件事**——只说一半用户就会误判」，并注明"见 §3.1"；§3.1 的定稿文案是「已收到你的举报，我们会尽快处理」，并附「⚠️ 已知取舍：文案不提"内容将被隐藏"」。两处互指、结论相反，且矛盾出现在被标记为"✅ 已定案"的裁决区。
Fix: 删除 §7.4 第 2 条或改写为"成功态文案只说已上报，不提隐藏"，并同步修 OQ-A11 结案文字。

**[Done-ness clarity]** — 两条 FR 交叉的状态组合未定义：既被拉黑又被举报（§3.1 / §3.2 黑名单管理）
先拉黑后举报 → 解除拉黑后举报隐藏仍在 → 内容仍看不见，而定稿 Toast「已解除拉黑，刷新后可重新看到 TA 的内容」此时是假话。先举报后拉黑 → 撞上"重复拉黑不新增记录"的幂等要求 → 人不进黑名单页，而 Toast 却说"请在黑名单里查看"。两条路径都会被当 bug 反馈。
Fix: 补一小节「两种来源并存时的行为」：source 是否可升级（REPORT → BLOCK）、解除拉黑时若仍存在举报隐藏该给什么提示、黑名单页是否收录"既举报又拉黑"的条目。

**[对抗式评审]** — 「评论举报已上线」是假的（§1 / §4 / §6）
PRD 四处把它当既成事实。实测：五个分支上均无 `comment_report` 数据表、无实体、无接口、App 端无入口。举报能力目前只有帖子级一种。后果：AB-3D「统一视图」要统一的四类工单里有一类根本不存在。
Fix: 确认评论举报的真实状态。若确未做，AB-3D 的工单类型定义与 §6 第 1/3 条须重写；若产品认为它属本版本范围，则本版本实为 3 条 FR，工量需重估。

**[对抗式评审]** — 迷你主页卡不是"5 个元素的纯展示卡"（§3.1 / UI 稿 A1）
实测存在第 6 项——**个性签名**（用户自填 ≤60 字），且「主页筹备中」不是常驻文案，是没设签名时的兜底。25 屏 UI 稿全画的是兜底态。签名为用户自填文本，骚扰账号可把攻击性内容写在签名里，而那段文字就展示在举报卡上。
Fix: UI 稿补签名态；产品明确签名是否随账号举报一并进入工单上下文。

**[对抗式评审]** — 只在评论区骚扰、从不发帖的账号，既举报不了也拉黑不了（§3.1 举报入口 / §3.2 入口）
迷你主页卡在全 App 只有两个触发点：Feed 卡片作者、详情页作者。**评论区的头像点了不弹卡。**而 PRD 把迷你卡定为账号举报唯一入口、拉黑主入口。FR-94 整套影子评论、R1/R2、通知抑制全是为评论区骚扰设计的，却没有办法从评论区现场发起。
Fix: 评论区头像接入迷你卡，或在评论行内增设「⋯」→ 举报/拉黑。

### High (14)

**[Decision-readiness]** — OQ-A11 结案文字保留了已被推翻的口径（§8 OQ-A11）
结案写"举报隐藏纳入黑名单页可解除"，而 §3.1 / §3.2 / §7.4 第 3 条 / A-A25 一致规定"不可解除、不进黑名单页"。
Fix: 改为正确口径，并标注该项在 08-14 当日经历过一次翻转（决策日志 C-64 → C-68）。

**[Strategic coherence]** — 无 Success Metrics 区块，立项理由无法验证（全文）
PRD 押注"账号举报 + 举报即隐藏 → 工单量下降"，但没有基线、目标值、观测窗口，也没有反向指标。
Fix: 补一节 Success Metrics，含反向指标与"结论何时回看、谁回看"。

**[Done-ness clarity]** — AB-3D 无可验收的完成条件（§4.1）
它是 FR-58 的硬前置、必须同版本交付，却没有列表分页/筛选/搜索定义、批量处置的上限与部分失败行为未定、封号是否二次确认未定。
Fix: 按 App 端 FR 的详细度补齐，或明确写"沿用既有后台列表惯例"并点名是哪个既有页面。

**[Done-ness clarity]** — 「警告」处置动作的用户侧后果完全未定义（§3.1 / §4.1）
封号给足了中印双语文案与异议渠道；警告只有"系统通知用户违规行为"一句。
Fix: 补警告的通知文案、是否可重复下发、是否计入"历史违规记录"。

**[Downstream usability]** — 无用户旅程，且缺失已造成主路径漏洞（全文 §3）
没有任何一条端到端 UJ。直接后果就是上面那条 critical。
Fix: 补 2 条 UJ（评论区被骚扰 / Feed 刷到不想看的账号），并据此复核入口覆盖。

**[Downstream usability]** — 关键区分无术语表词条，正文出现 5 种以上同义说法（§2 / 全文）
「主动拉黑 vs 举报产生的隐藏」是主页访问规则的唯一依据，却没有词条；正文混用拉黑/隐藏/屏蔽/账号级隐藏/按查看者隐藏。
Fix: 上位概念命名为「隐藏关系」，两个下位为「主动拉黑」「举报隐藏」，全文统一。

**[Downstream usability]** — 约 30 处跨文档引用在仓库内不可解析（§0 / §1 / §6 / §8）
`../V1.x.x/…` 路径只在产品源目录成立，归档后全为死链。
Fix: 文档头部加路径说明，并把影响实现的几处改写成自包含描述。

**[Shape fit]** — "已核代码"的叙述姿态未被事实完全支撑（§3.1 / §3.2 各处）
文档以已验证口吻陈述既有实现，下游会据此停止复核；实测至少四条不符。
Fix: 每条代码断言标注核实日期与基准分支（决策日志写的是 `stag`，与当前开发分支不同），或统一降格为"实现前请复核"。

**[对抗式评审]** — OQ-A5「评论查询没有 viewer 上下文」判断相反（§8 OQ-A5）
实测评论的每一个查询方法都已带查看者身份。R1 基本就是加一个条件。该警告会把工时估高。
Fix: 删除该警告；OQ-A5 焦点改为 R2 的多一层归属判定与索引。

**[对抗式评审]** — 真正缺 viewer 上下文的地方 PRD 漏了（§3.2 生效范围 4）
迷你主页接口是游客可读、完全不要求登录的，而 FR-94 要求主页访问拦截必须服务端校验。
Fix: 在 OQ-A5 中补入该接口的改造，并明确改造后游客访问的行为是否变化。

**[对抗式评审]** — 举报账号没有任何自动处置，而举报帖子有（§3.1 / §5）
既有实现：以"违法违规"为由举报一条帖子，一次就会自动把帖子翻回挂起态；或满 10 人举报同样自动挂起。账号举报对自动预处置只字未提——方案甲要消灭的塌陷又出现一遍，只是落在平台处置层。
Fix: 明确账号举报是否需要自动预处置，或明确写"一律人工"并说明为何与帖子级不同。

**[对抗式评审]** — AB-3D 的优先级公式与既有优先级机制是两套（§4.1）
既有内容举报已有 P0/P1/P2 阈值判定（含自动预处置）。改用新公式则阈值语义分叉；两套并存则"统一视图"无法统一排序。
Fix: 明确统一后的排序口径与 P0 自动预处置的去留。

**[对抗式评审]** — 举报成功后内容什么时候消失，没定义（§3.1 / UI 稿 B5）
既有内容举报有明确成功回调（乐观移除卡片 / 退回列表）；账号举报只说"两层收起、回到原页面"，那个页面就是 Feed。而 PRD 说"立即隐藏"。第三次落回同一个塌陷。
Fix: 比照内容举报做乐观移除该作者全部可见卡片。

**[对抗式评审]** — "封号"与"注销"在代码里几乎同名，而 PRD 对两者要求相反（§3.2 边界与约束）
封号叫 `DEACTIVATED`，注销在迷你卡里叫 `isDeactivated`。PRD 要求：封号照常展示、可拉黑；注销匿名化、不弹卡。两条要求相反，字段名只差一个前缀。
Fix: 为这两种状态各加明确的英文对照，并在术语表登记。
