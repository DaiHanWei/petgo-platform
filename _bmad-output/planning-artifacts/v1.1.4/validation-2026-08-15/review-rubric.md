# PRD Quality Review — TailTopia V1.1.4 用户端 + 后台（社区管控）

## Overall verdict

这是一份**决策密度非常高、范围诚实度罕见的 PRD**——每一处取舍都写了"为什么这么定""已知代价是什么"，§7 完整保留了备选方案与否决理由，Non-goal 覆盖到了研发最容易按常识做错的地方（双向 Block）。它的问题不在思考质量，而在**三处结构性缺陷**：作为定案权威的 §7.4 与正文正面矛盾且带着上一版的残留；整份文档没有任何成功度量，而 FR-58 押的正是一个可证伪的赌注（"举报即隐藏会降低工单量"）；以及没有一条端到端用户旅程——这直接导致"从评论区现场发起举报/拉黑"这条主路径无人走查、至今是断的。

同时，这份 PRD 用了一种"已核代码"的叙述口吻（「⚠️ 核代码后的订正」「本次核 app_id.arb 发现」），把若干未经核实的断言抬到了事实的地位。下游会因此停止复核。这是本次校验里最需要立刻处理的一类问题，因为它的伤害发生在**别人身上**、且发现得越晚越贵。

---

## 1. Decision-readiness — strong

这一维是本文档最强的部分。决策以决策的形式出现，不是藏在"考量"里：§7.1 直接给出定案表，§7.3 列出方案乙/丙及其否决理由（"要改一条已上线的行为，风险与收益不成比例"），§3.1 与 §3.2 里成组出现的「⚠️ 已知取舍 / 已知后果」段落把放弃了什么讲得比选择了什么还清楚。OQ 表里的三条未决项是真的未决，不是自问自答。

但**定案区本身带着上一版的残留**，而它恰恰是冲突时的裁决依据。§7.4 的标题写"三件事"、底下列了五条；第 2 条要求成功态文案同时说明"已上报"与"已隐藏"，而 §3.1 明确定稿为「已收到你的举报，我们会尽快处理」并专门写了一段解释为什么不提隐藏。OQ-A11 的结案文字同样停在旧口径上。研发照 §7.4 实现就会做出与 §3.1 和 UI 稿都不一样的东西。

### Findings

- **[critical]** §7.4 第 2 条与 §3.1 正面矛盾（§7.4 / §3.1 举报成功态） — §7.4 写「举报成功态文案**必须同时说明"已上报"与"已隐藏"两件事**——只说一半用户就会误判」，并注明"见 §3.1"；§3.1 的定稿文案是「已收到你的举报，我们会尽快处理」，并附「⚠️ 已知取舍：文案不提"内容将被隐藏"（2026-08-14 复核后维持不加）」。两处互指、结论相反，且矛盾出现在被标记为"✅ 已定案"的裁决区。*Fix:* 删除 §7.4 第 2 条或改写为「成功态文案只说已上报，不提隐藏——已知取舍见 §3.1 与 A-A27」，并同步修 OQ-A11 结案文字里"成功态文案改为同时说明上报与隐藏"这半句。
- **[high]** OQ-A11 结案文字保留了已被推翻的口径（§8 OQ-A11） — 结案写"连带三项：……举报隐藏**纳入黑名单页可解除**（但不撤销举报）"，而 §3.1、§3.2、§7.4 第 3 条、A-A25 一致规定"举报产生的隐藏**不可解除、不进黑名单页**"。OQ 表是给"这事定了没有"的人看的，停在旧结论上等于把已关闭的问题重新打开。*Fix:* 把 OQ-A11 的第三项改为"举报隐藏不可解除、不进黑名单页"，并标注该项在 08-14 当日经历过一次翻转（决策日志 C-64 → C-68）。
- **[medium]** §7.4 标题与内容数量不符（§7.4） — 标题「随方案甲一并定下的三件事」，下列 5 条。数量对不上是一个信号：这一节被追加过但没重读。*Fix:* 改标题为"随方案甲一并定下的几件事"或据实写五。
- **[medium]** 两处"已知后果"的处置方式是无触发条件的延后（§3.1 A-A27 / §3.2 入口 1） — 「若上线后出现相关反馈，再评估是否补」出现两次。没有定义"多少反馈算触发"、谁看、什么时候看。实际效果等于不处理。*Fix:* 给一个可执行的复核条件（例如"上线后首月客服工单中出现 ≥N 起'为什么刷不到某人内容'即回看"），或干脆写明"本版本不复核"。

## 2. Substance over theater — strong

没有 persona 摆设、没有 vision 空话、没有"系统必须可扩展"式的 NFR 填充。§3.2 生效范围第 3 条那张 R1/R2 对照表和紧随其后的 ①②③ 场景表是真正在干活的内容——它把"两条规则会不会打架"这个必然被误读的点提前解掉了。§3.1 关于"为什么语义要单调递增"的那段推理，是整份文档的骨架，且经得起推敲。

唯一接近furniture 的是 §0 那张「约束 / 落实情况」全 ✅ 的表：它记录的是文档自身的迁移状态，对实现没有输入。

### Findings

- **[low]** §0 的自评表对实现无输入（§0） — 四行全 ✅ 的"约束/落实情况"表服务的是版本管理，不是需求。*Fix:* 移入 README 或版本沿革区，正文从 §1 起。

## 3. Strategic coherence — thin

thesis 是清楚且有说服力的：**三个"让内容从我眼前消失"的机制必须语义单调递增**，两条 FR 都从它推出来。FR-58 与 FR-94 的分工（"交给平台处置" vs "我自己先眼前清净"）讲得干净，共用一层过滤的判断也对。

问题是**整份 PRD 没有任何成功度量**。而 thesis 里包着一个明确、可证伪、且方向不确定的赌注：§3.1 两次声称"降低工单量正是 FR-58 与 AB-3D 的立项理由"，方案甲被选中的核心论据也是"不这么做会推高工单量"。但相反的结果同样合理——举报现在附带"立刻眼前清净"的即时收益，可能让举报量**上升**。这个赌注赢没赢，本版本上线后无法回答：没有基线、没有目标、没有反向指标、没有复核时点。§3.2 的埋点要求里唯一带判断标准的一条（黑名单页举报入口"若长期为 0，说明该入口可以撤掉"）也没定义"长期"和"0"。

### Findings

- **[high]** 无 Success Metrics 区块，立项理由无法验证（全文） — PRD 押注"账号举报 + 举报即隐藏 → 工单量下降"，但没有工单量基线、目标值、观测窗口，也没有反向指标（举报量上升 / 误举报率 / 举报后解除需求）。上线后无从判断这版是成功还是失败。*Fix:* 补一节 Success Metrics：工单总量与账号举报占比的上线前基线 + 上线后 4 周目标、反向指标（单账号被举报人数分布、举报到封号的转化率）、以及"结论何时回看、谁回看"。
- **[medium]** 埋点要求写了口径但没写判断标准（§3.2 埋点要求） — "若长期为 0，说明该入口可以撤掉；若量不小，说明原来的设计确实堵死了一条重要路径"是本文档里最接近指标的一句，但"长期"与"量不小"都没有数。*Fix:* 定成具体门槛与复核日期（例如"上线后 8 周，黑名单页举报点击 < 全部账号举报的 2% 即评估下线该入口"）。
- **[medium]** 优先级公式的阈值缺依据（§4.1） — 高频阈值取 ≥5 次的唯一依据写的是"依据产品给的第二个例子"，即从一个示例反推出来的。5 这个数字没有数据支撑，也没写日后如何调。*Fix:* 标注为 `[ASSUMPTION: 高频阈值 5 次，无数据依据，上线后按实际分布回调]` 并纳入假设索引。

## 4. Done-ness clarity — adequate

App 端两条 FR 的完成条件大多是可验证的：状态表、场景表、Toast 文案、失败态行为、幂等要求，工程可以直接照着写测试。§3.2 的 ①②③ 场景表尤其好用——三行就把 R1/R2 的联合结果钉死了。

但有三处**engineer 读完不知道"完成"长什么样**的地方，其中两处是两条 FR 交叉产生的、正文任何一节都没覆盖：

**其一，同一个人既被拉黑又被举报时，解除拉黑会撒谎。** 用户先拉黑 B、后又举报 B（PRD 允许：举报入口在举报后仍可进入）。此时存在两层隐藏。用户从黑名单页解除拉黑 → 举报产生的隐藏依旧在 → B 的内容仍然看不见。而定稿 Toast 是「已解除拉黑，刷新后可重新看到 TA 的内容」。这句话此时是假的。PRD 全文未涉及这个组合。

**其二，先举报后拉黑会拉黑不成功。** §3.2 要求"拉黑接口必须幂等：重复拉黑同一用户不报错、**不新增记录**"，而 §7.3 又要求举报隐藏与主动拉黑"共用同一张关系表 + `source` 字段"。用户举报 B（已产生一条 REPORT 记录）后再从迷你卡拉黑 B → 按幂等要求不新增记录 → B 不会出现在黑名单页。但定稿 Toast 是「拉黑成功，请在黑名单里查看」，用户去黑名单里找不到人。PRD 没有定义 source 在这种情况下是否升级、条目是否补进黑名单。

**其三，AB-3D 作为本版本唯一的后台交付物、且是 FR-58 的硬前置，只有一页篇幅、没有一条可验收的完成条件。**「批量处置：运营可选多条同类型工单批量执行相同处置动作」——批量上限多少？部分成功怎么呈现？批量封号要不要二次确认？列表分页、筛选、搜索一概未提。而"分数实时计算、不落库快照 + 按分数倒序"意味着每次列表查询都要对全量工单算分排序，PRD 没给量级假设，也没说这与分页如何共存。

### Findings

- **[critical]** 两条 FR 交叉的状态组合未定义：既被拉黑又被举报（§3.1 / §3.2 黑名单管理） — 解除拉黑后举报隐藏仍在，而定稿 Toast「已解除拉黑，刷新后可重新看到 TA 的内容」变成假话；反向操作（先举报后拉黑）撞上幂等要求，人不会进黑名单页，而 Toast 却说"请在黑名单里查看"。两条路径都会被用户当 bug。*Fix:* 补一小节「两种来源并存时的行为」：明确 source 是否可升级（REPORT → BLOCK）、解除拉黑时若仍存在举报隐藏该给什么提示、以及黑名单页是否收录"既举报又拉黑"的条目。
- **[high]** AB-3D 无可验收的完成条件（§4.1） — 它是 FR-58 的硬前置、必须同版本交付，却没有列表分页/筛选/搜索定义、批量处置的上限与部分失败行为未定、封号是否二次确认未定。运营拿到手无法验收，工程无法估工。*Fix:* 按 App 端 FR 的详细度补齐 AB-3D 的界面要求与边界，或明确写"沿用既有后台列表惯例"并点名是哪个既有页面。
- **[high]** 「警告」处置动作的用户侧后果完全未定义（§3.1 处置动作 / §4.1） — 封号给足了中印双语文案与异议渠道；警告只有"系统通知用户违规行为"一句：没有文案、没说走哪类通知、没说用户看到什么、多次警告是否升级也没说。运营点下"警告"后用户端发生什么，是空的。*Fix:* 补警告的通知文案（中文语义 + 印尼语）、是否可重复下发、是否在后台留痕计入"历史违规记录"。
- **[medium]** "立即生效 / 即时生效"未定义可观测时刻（§3.1 举报即隐藏 / §3.2 生效范围） — 反复出现但没说清是"当前列表立刻刷新"还是"下次拉取生效"。解除拉黑一侧反而定义得很好（措辞刻意用"刷新后"），生效一侧缺同等处理。*Fix:* 比照解除侧补一句"生效以下一次拉取为准"或明确要求当前列表即时移除。
- **[medium]** 优先级实时计算与列表分页的关系未定（§4.1） — "分数实时计算、不落库快照"+"按分数倒序"意味着排序键不在库里，与分页天然冲突，PRD 未给量级假设。*Fix:* 给出工单量级预估与"是否接受全量排序"的产品判断，或把该问题移入 OQ 交给技术方案阶段。

## 5. Scope honesty — strong

这一维几乎无可指摘。§5 有真正在干活的 Non-Goals（结构化申诉工作流、自动封号、双向隔断、Feed 排序改造、被拉黑数的风控联动），每条 FR 自带 Non-goal 列表，"明确不影响的（被拉黑方视角）"整段是为了防止研发按常见 Block 语义做成双向而专门写的——这是对下游失败模式的准确预判。已作废的条目（AB-3E、OQ-A7、A-A3）用删除线保留并写明作废原因，不是悄悄删掉。

假设索引存在，但**内联标记与索引的往返是双向断的**：正文只有两处 `[ASSUMPTION: …]` 内联标记（200 字上限、历史通知不回溯清理），而这两条**都不在**索引里；索引里的 A-A1~A-A5、A-A21~A-A28 共 13 条，**没有一条在正文有对应的内联标记**。索引因此不能用来定位，正文也不能用来反查。

### Findings

- **[medium]** 假设索引往返双向断裂（§9 / §3.1 / §3.2） — 正文两处内联 `[ASSUMPTION]` 均未入索引；索引 13 条均无正文内联标记。下游按索引找不到上下文，按正文找不到假设归属。*Fix:* 把两条内联假设编号入索引（A-A29 / A-A30），并在索引每条后补正文定位（"见 §3.2 生效范围第 6 条"这类），不必强求全文补内联标记。
- **[low]** 开放项密度对一份"已定稿、可开工"的 PRD 略高但可接受（§8） — 3 条真开放（OQ-A4 法务 / OQ-A5 工程 / OQ-A6 产品）。其中 OQ-A5 属技术方案阶段、不阻塞；OQ-A4 是外部依赖、须在封号功能上线前闭环。*Fix:* 在 OQ-A4 上标"上线阻塞"，与 OQ-A6 的"上线前"区分开。

## 6. Downstream usability — thin

这份 PRD 是链条顶端（要喂架构 → epics → story），所以这一维权重高，而它是短板。

**没有任何端到端用户旅程。** §3.2 的 ①②③ 场景表覆盖了"评论对谁可见"这一个切片，但全文没有一条"某个具体的人从遇到骚扰到解决"的完整走查。代价已经显现：对抗式评审发现的"评论区点头像不弹迷你卡 → 只在评论区骚扰的账号既举报不了也拉黑不了"，是一次五分钟的旅程走查就会撞上的问题——FR-94 的影子评论、R1/R2、通知抑制全部是为评论区骚扰设计的，而**发起入口在评论区不存在**。缺 UJ 不是形式问题，是它真的漏掉了主路径。

**术语表覆盖不到本 FR 最吃紧的那个区分。** §2 定义了 6 个词，但整份 PRD 反复依赖的「主动拉黑 vs 举报产生的隐藏」这组区分**没有词条**——而"主页访问是唯一需要区分两种来源的地方"这条规则完全建立在它上面。正文用来指代同一簇概念的说法至少有五种：拉黑 / 隐藏 / 屏蔽 / 举报产生的隐藏 / 账号级隐藏 / 按查看者隐藏。下游做 story 拆分时会各自选词。

**跨文档引用在仓库里全是死链。** 正文约 30 处 `../V1.0.0/`、`../V1.1.0/`、`../V1.1.6/`、`../V1.1.8/`、`../V1.2.0/` 形式的相对路径，只在产品的源目录成立。归档进仓库后，架构与 story 侧按这些路径一个都打不开。

### Findings

- **[high]** 无用户旅程，且缺失已造成主路径漏洞（全文 §3） — 没有任何一条端到端 UJ。直接后果：为评论区骚扰设计的整套能力，其唯一发起入口（迷你主页卡）在评论区不可达。*Fix:* 补 2 条 UJ——「Rina 在自己帖子的评论区被 Budi 持续骚扰」与「Dimas 刷 Feed 时刷到不想看的账号」——各写清楚从触发到收尾每一步点了什么，并据此复核入口覆盖。
- **[high]** 关键区分无术语表词条，正文出现 5 种以上同义说法（§2 / 全文） — 「主动拉黑 vs 举报产生的隐藏」是主页访问规则的唯一依据，却不在术语表；正文混用拉黑/隐藏/屏蔽/账号级隐藏/按查看者隐藏。*Fix:* 术语表新增两条词条并全文统一用词；建议把上位概念命名为「隐藏关系」，两个下位为「主动拉黑」「举报隐藏」。
- **[high]** 约 30 处跨文档引用在仓库内不可解析（§0 / §1 / §6 / §8 各处） — `../V1.x.x/…` 路径只在产品源目录成立，归档后全为死链。下游架构/story 无法验证任何一条"已迁入/已删除/见某文档"的说法。*Fix:* 在文档头部加一句"本文档的 `../` 路径指向产品源目录，仓库内不可解析"，并把真正影响实现的那几处（V1.0.0 FR-25 / FR-26、V1.1.0 FR-51、NFR-8）改写成自包含的一句话描述。
- **[medium]** 多个小节无法独立取用（§3.2 生效范围 3、4） — R2 的判定"（主动拉黑或举报，两种来源都算，见 §3.1）"、第 4 条的"理由见 §3.1"都指向一段 60 余行的正文。story 拆分时按节抽取会丢掉判定依据。*Fix:* 在 §3.2 内把依赖的结论复述一句，而不是只给指向。

## 7. Shape fit — adequate

形态基本是对的：brownfield 增量、面向消费级社交产品、链条顶端。用 FR 增量而非重写整份 PRD 是正确选择；App 端与后台合一在本版本（后台只有 1 条）也说得过去。

两处不贴合：

**其一，文档采用了"已核代码"的叙述姿态，而部分断言并未核实。** 「⚠️ 核代码后的订正」「本次核 `app_id.arb` 发现」「核实 `ContentNotifyListener` 后确认」这类措辞把断言抬升为已验证事实。对抗式评审已确认其中至少四条与代码不符（评论举报未上线、迷你卡有第 6 个元素、OQ-A5 关于 viewer 上下文的判断相反、FR-51 回告文案与线上不同）。brownfield PRD 的既有代码引用必须准确——不准确比不写更糟，因为它**关掉了下游的复核动作**。

**其二，版本管理内容占比过大。** §0 + 版本沿革 + §6（14 条跨文档影响）+ §7 留痕合计约占全文四成。对一个只有 2 条 FR 的版本，下游读者的多数阅读时间花在迁移考古上。这些内容有留痕价值，但不该与需求正文平级。

**篇幅分配与交付风险倒挂。** AB-3D 是本版本唯一的后台交付、且被明确标为"不交付则 App 上线即空转"，占全文约 3%；而已经拆走的 FR-95/FR-96 的迁移说明占的篇幅比它还多。

### Findings

- **[high]** "已核代码"的叙述姿态未被事实完全支撑（§3.1 / §3.2 各处代码断言） — 文档以已验证口吻陈述既有实现，下游会据此停止复核；实测至少四条不符。*Fix:* 给每条代码断言标注核实日期与核实基准分支（决策日志写的是 `stag`，与当前开发分支不同），并对本次校验推翻的四条做订正；或统一降格为"据了解……，实现前请复核"。

- **[medium]** AB-3D 的篇幅与其交付风险倒挂（§4） — 唯一的硬前置后台能力占全文约 3%，少于已迁走功能的迁移说明。*Fix:* 与"AB-3D 无可验收完成条件"一并补齐；若确认后台按既有惯例实现，则把该判断明确写进 §4 而不是留白。
