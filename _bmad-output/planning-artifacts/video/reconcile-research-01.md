## 一、缺口清单（按重要性排序）

### G-1 下架或删除后，视频文件仍可被直链访问（定性风险被功能结构丢掉）
- 输入原文：§1 `[删除] 只软删；OSS 对象永不删除（F21）`；§3 `MediaDeletionService 只打日志`；§5 "存储只增"。
- 缺口：PRD FR-17 / UJ-4 只保证"下架后各端不可见"（接口层）。但视频与封面是 `public-read` 的 OSS/CDN 直链，F21 又永不删对象，CDN 还有缓存。被举报的违规视频下架后，知道链接的人仍能打开和转发。PRD 只把 F21 当作"存储成本"问题（§8.3、§10 Q3），没当作"违规内容下架后仍可访问"的合规风险。
- 建议落点：PRD §9 风险表加一行；§10 待定问题 3 补充"下架视频是否需要物理删除或 CDN 缓存刷新"；addendum D 加一条 CDN 缓存刷新或对象撤权的实现备注。

### G-2 视频封面在瀑布流的比例约束与裁剪规则未定义
- 输入原文：§1 链路图 "宽高比超出 [0.75,1.78] → 露出区域页 → cropOffset"；§2 "展示"行（FeedImage / 主页网格 400 等）；`imageSizes`、`imageCropOffsets`。
- 缺口：图文帖有"比例范围 + 手动选露出区域"的现成机制。PRD FR-7 要求视频保持原比例不裁切、FR-8 封面与视频同比例，但 FR-14 没规定封面在双列瀑布流、主页网格里如何适配（极宽的横屏、极窄的竖屏视频）。addendum C 只存了 `video_width/height`，没说列表用它还是复用 `imageSizes/cropOffsets`，也没说封面是否需要露出区域。
- 建议落点：PRD FR-14 加可测条件（超出比例范围的封面如何显示）；addendum C/E 写明列表尺寸来源。

### G-3 封面没有缩略图，列表加载的是 720 原图
- 输入原文：§2 "展示"行：`AppImage.ossResized` 对所有 `*.aliyuncs.com` 拼 `image/resize`（流 800、网格 400）；§5 "`x-oss-process` 误用"。
- 缺口：addendum E 说"视频封面地址走 CDN 域名，原本就不会被拼参数"。结果是封面在流里、400 的主页网格里都按 720 短边原图加载，流量与加载速度比图文帖差，且这点没在 PRD 或 addendum 作为取舍写明。
- 建议落点：addendum E 补一句取舍说明（接受 / 或 CDN 侧开图片处理 / 或另传小图）；PRD 不必改。

### G-4 视频帖与发帖附加字段、非底栏入口的关系未说明
- 输入原文：§1 `[入口] 底栏+ / 打卡后发帖 / 首页空态 / 被拒重发 / 运营位 / 晒图 / 深链 /publish`；请求体含 `petId / mentions / placeCheckinToken / eventDate`；`422 → /publish/rejected` 重发。
- 缺口：PRD 只讲"发帖页多一个视频选项"。未说明：
  1. 视频帖是否允许带 `petId`、`placeCheckinToken`（场所打卡）、`eventDate`；
  2. 文本被拦截（422）后走"被拒重发"，已上传好的视频和封面是否保留（FR-9 只讲上传失败重试）；
  3. 深链 `/publish`、打卡后发帖等入口，等级 10 账号是否也能看到视频选项。
- 建议落点：PRD FR-10 可测条件补第 1、2 点；FR-5 补第 3 点（或写明"仅发帖页，其他入口不暴露"）。

### G-5 放弃或取消上传会留下大体积孤儿文件
- 输入原文：§1 "选完即传"；§5 "存储只增（F21 永不删除 + 视频体积大）"。
- 缺口：FR-9 "上传中关闭发帖页，放弃本次上传"、FR-7 取消、重试，都会在 OSS 留下未被任何帖子引用的视频（最大 50MB）。F21 又禁止删。PRD §8.3 / §10 Q3 只谈"已发布视频"的存储增长，没提孤儿文件。
- 建议落点：PRD §10 待定问题 3 扩一句；addendum D 备注"孤儿对象靠 OSS 生命周期规则按前缀清理"。

### G-6 视频 CDN 域名与归属校验的衔接
- 输入原文：§3 "归属校验：`MediaObjectKeys.requireAllOwned` 已有，发帖未用"；"对外 URL：`cdnBaseUrl/key`"。
- 缺口：addendum D 要复用 `AliyunOssClient.objectKeyOfPublicUrl` 做归属校验，同时又要新增独立的 `video-cdn-base-url`。现有的 URL→objectKey 解析只认现有基址，视频 CDN 域名不被识别，会让 FR-12 的"本人上传"校验对视频地址误拒或失效。两条在 addendum 里互相独立，没有互相引用。
- 建议落点：addendum D 补一条：URL 解析需同时识别图片基址与视频 CDN 基址；并要求 FR-12 的测试覆盖"CDN 域名下他人 key"。

### G-7 上传凭证有效期与大文件上传
- 输入原文：§3 "上传签名 600s"；§4 后端 1 "视频可单独加长上传有效期"；§4 前端 4 "大文件考虑分片"。
- 缺口：PRD / addendum 都没提。50MB 文件在弱网下 600 秒可能不够，会表现为"上传到快完才失败"。FR-9 只讲重试，不讲签名过期。
- 建议落点：addendum D 加"视频凭证有效期延长；过期按 FR-9 重试时重新申请凭证"。分片：不处理（50MB 单次 PUT 够用，写进 addendum 作为取舍即可）。

### G-8 老客户端过滤对分页的影响
- 输入原文：§5 旧版兼容 "用 `X-App-Version` 对旧客户端过滤视频帖"。
- 缺口：addendum D 只写"过滤掉 media_type = VIDEO"。若在取数后再过滤，旧客户端会出现短页或空页（官方集中发视频时尤甚）；推荐流还有顶置位和"已消费"逻辑（记忆里已有顶置让位 bug）。FR-18 的可测条件没覆盖分页。
- 建议落点：PRD FR-18 加可测条件"旧版客户端翻页不出现空页或条数异常"；addendum D 注明过滤要进查询条件，不要取数后再过滤。

### G-9 发帖校验里的 HEAD 校验与外部调用
- 输入原文：§5 "事务时长：视频不能进现有的同步审核链路"；§3 发帖在事务内同步审核。
- 缺口：addendum D 要在发帖时 HEAD 真实对象来校验大小（≤50MB），这是事务内的一次外部调用。PRD / addendum 没说放在事务外、超时和失败时如何报错。
- 建议落点：addendum D 一句话：HEAD 校验放在事务之前，设短超时，失败返回可重试错误。

### G-10 视频文件元数据（位置等）的去除手段
- 输入原文：§1 "ImageProcessor：去 EXIF"（图片链路明确去除）。
- 缺口：PRD §8.1 隐私要求"视频文件不带拍摄地点等元数据"，但 addendum A 没有任何实现或验证手段，且 A 又写了"已合规视频不重新编码、只做 remux"，remux 路径会原样带上 moov 里的位置信息。两者有潜在矛盾。
- 建议落点：addendum A 补"remux 路径也要剥离 udta/位置元数据"，并作为真机验证项。

### G-11 展示位置清单不完整（时间线、日历、灯箱）
- 输入原文：§1 展示行 "详情 `_ImageCarousel`(1080) · 灯箱(1080) · 主页网格 · 时间线/日历/分享页"；§4 前端 6 "卡片/网格/时间线/日历/分享页用封面并加播放角标"。
- 缺口：FR-14 用"凡是显示帖子缩略图的位置"概括，列举里没有时间线、日历。视频帖类型限定为日常 / 科普（V-12），这些位置是否会出现视频帖没有结论。
- 建议落点：PRD FR-14 补一句"时间线、日历若会出现视频帖，同样显示封面与角标；否则说明不出现"。落地时核对一次。

### G-12 读取侧 API 响应字段未列
- 输入原文：§4 后端 5 "`FeedItemResponse` / `ContentDetailResponse` / `SharedPostResponse` / `GrowthMomentView` 加字段"。
- 缺口：addendum C 只列了数据库列，没列对前端的接口字段（mediaType、videoUrl、封面、时长、宽高）。这是前后端联调的契约，当前只能由架构 delta 补。
- 建议落点：addendum C 加"接口下发字段"小节（或留待架构 delta，在 addendum 注明）。`GrowthMomentView`：视频帖不会是成长日记（V-12），写明"不加"即可。

### G-13 封面不审与调研的"封面走现有图片审核"不一致（需确认是有意）
- 输入原文：§4 后端 4 "封面走现有图片审核"。
- 缺口：PRD FR-10 写"视频和封面本身不走机器审核"，依据是 V-6。但 V-6 的原文只提"视频免审的风险前提"，没明确封面。封面走现有图片审核的成本很低，且是现成能力。
- 建议落点：决策日志补一条确认（封面是否一并免审）；若保留免审，PRD §8.2 的"免审前提"同样覆盖封面即可。

### G-14 上传状态机泛化、请求体兼容构造器（实现提示级）
- 输入原文：§2 "状态机 `ImageUploadItem`…"；§3 "另有 5 个兼容构造器"；§4 前端 5。
- 缺口：addendum E 没提 `ImageUploadItem` 要泛化为媒体项、发帖 DTO 的兼容构造器要同步改。都是实现提示，拆 story 时才会踩。
- 建议落点：addendum E 加两行提示；PRD 不处理。
