# 决策日志 · V1.4.2 exp-reverse（问诊挂起退款扣回成长值）

> 权威顺序：本文件 > PRD（`电商/1-4-2退款扣回成长值修复prd.md`）> 架构增量。以下 E-1 ~ E-10 是 2026-11-06 对照 `dev_1.4.2`（`ad0d8f33a`）补的实现口径，PRD 未写明，均按推荐先定，可推翻。

| 编号 | 决定 | 原因 |
|---|---|---|
| **E-1 默认授权** | PRD 的「客服主管」落到 `OPS_MANAGER`（运营主管），超管隐式全权；`SUPPORT` 不预授 | 系统没有客服主管角色。常规问诊退款的「主管审批」`refund.approve` 就是 `OPS_MANAGER` 持有。**2026-11-06 操作者确认** |
| **E-2 识别挂起退款** | `consult_orders` 新增 `suspension_refund_at`，只在 `ConsultSuspensionService` 现金分支写入 | `REFUNDING` 还可能来自常规退款（`markRefundingFromCompleted`），只看状态会把常规退款中的订单误列为可扣回 |
| **E-3 存量不处理的落法** | 新列不回填。存量为 NULL，天然没有按钮、不进筛选 | 比写死上线日期或部署时配截止时间简单，各环境自动准确 |
| **E-4 无入账的订单** | 没有入账流水（活动未开、1.4.0 前付款、已注销流水被删）→ 成长值节显示「—」，无按钮，不进筛选 | PRD 只写「未扣回」，没有可扣的东西时按钮无意义 |
| **E-5 已扣回判定** | 本单已扣回 > 0 即视为已扣回，不再看「入账 − 已扣回」 | `reverse` 会按用户累计值截断，极端情况实扣小于入账；PRD 要求扣回后按钮不再显示 |
| **E-6 同步直调，不走事件** | 后台直接调成长值服务，不发 `RefundSucceededEvent`；来源键沿用 `consult-refund-{orderId}`，原因 `REFUND` | 事件监听异步且吞异常，无法返回实扣额、前后等级，也无法与审计同事务；订单也并未真正退款成功 |
| **E-7 列表筛选** | 本页现状没有任何筛选。新增一个下拉（全部 / 待扣回成长值），`?filter=exp-reverse`；摘要条随筛选变化；导出仍是全表；改写「本页暂无筛选」提示，三语自拟待设计确认 | PRD 写「复用列表筛选」，但页面没有可复用的筛选 |
| **E-8 错误码** | 本功能的业务错误一律 422（`AppException.validation(...).code(...)`），不用 409 | 后台 htmx 只放行 422 / 403 / 404，409 在浏览器里没有任何提示。不全局放行 409，影响面过大 |
| **E-9 累计为 0** | 用户累计成长值为 0（运营调整所致）时视为无可扣：无按钮、不进筛选；本次扣回额取 `min(入账, 累计)` | 否则提示「已扣回」但订单永远待扣回。此情况极少，不留痕 |
| **E-10 已停用用户** | 停用用户照常可扣回；已注销用户流水已删，走 E-4 | PRD 未限制，`reverse` 不校验参与资格，退款口径不因账号状态改变 |
