## 1. AB-24：优惠券管理

**背景：** App 端 FR-130 引入优惠券（满减、免运），券的一切参数由运营在后台配置，App 端不写死任何一张券。现有后台无任何优惠券能力。

### 已确认项（2026-09-30 拍板）

**可配置的维度：**

| 维度 | 取值 |
|---|---|
| 券类型 | 满减 / 免运（本次只有这两种） |
| 面额与门槛 | 满减：减免金额 + 门槛金额；免运：可设门槛金额 + **最高减免金额**（2026-11-03 新增：免运券减免额取「本单最低快递运费」与此上限中较小者，见 App 端 FR-172；**必填**，2026-11-05） |
| 发放期 | 能领取、能兑换、新人券能发放的起止时间，**必填**（2026-11-05 新增）。列表状态「未开始 / 进行中 / 已结束」按发放期判断 |
| 使用有效期 | 固定起止日期，或领取后 N 天内有效。选固定日期时，结束日不得早于发放期结束日 |
| 数量 | 发放总量、每人限领张数。兑换码的口径：通用码的发放总量即全部用户合计可兑换的张数；批量一次性码每个码只能兑换一张，生成数量即发放总量（2026-11-05） |
| 适用范围 | 全场 / 指定品类 / 指定商品 |
| 发放方式 | 新人自动发放 / 用户领取 / 兑换码。新人的定义与发放时机由 App 端 FR-130 固定，后台不可配：注册 1 个月内且从未在电商下过已支付订单的已注册用户，首次进入 Toko 时发放；有进行中的新人券时，游客进入 Toko 弹窗引导注册（2026-11-05 同步） |

- 没有系统默认券——三种发放方式都要运营建券后才存在
- **新人券同一时间只能有一张在发放期内**，保存时校验，冲突则不能保存；游客弹窗展示的就是这一张（2026-11-05）
- 规则口径以 App 端 FR-130 为准：每单最多 1 张满减券 + 1 张免运券；满额免运与免运券并存，同时满足时系统取减得多的一个（2026-11-04）；免运券设了适用范围时须本单全部商品在范围内才可用（2026-11-04）；满减券门槛按券前商品金额判断，满额免运与免运券门槛按商品实付金额（商品金额 − 满减券）判断

### 页面位置与流程（2026-10-06 拍板）

- **位置**：🛍 商城组新增侧栏项「优惠券」，独立列表页
- **列表**：券名称、类型、面额 / 门槛、发放方式、有效期、已发 / 总量、已使用数、状态（未开始 / 进行中 / 已结束 / 已停用）；可按状态、类型、发放方式筛选
- **新建 / 编辑**：列表页右上「新建优惠券」→ 右侧抽屉表单 → 提交后回到列表并定位到新行。**已开始发放的券只能改总量（只增不减）与停用**，面额、门槛、适用范围不可改，避免用户手里同一张券前后规则不一致
- **兑换码**：发放方式选兑换码时，由运营填写一个通用码或批量生成一次性码（批量码可导出）
- **停用**：行内操作，二次确认；停用后不能再领取或兑换，**用户已领取未使用的券是否继续可用**须在确认弹层中让运营二选一。选「作废」时，已领未用的券变为「**已失效**」：App 端不再显示（「我的券」与结算页都不出现），不通知用户；**已被待付款订单占用的那张照样可用于该订单**，该订单取消时这张券也变为已失效、不再退回（2026-11-05）
- **数据**：券详情抽屉显示领取数、占用中数（被待付款订单占用）、使用数、带来的订单金额

### 防误配提醒（2026-10-06 拍板）

面额 ≥ 门槛的满减券（等于白送商品）、总量不限且每人不限领的券，保存时给出醒目提示并要求二次确认。

### 按用户查券（2026-11-04 拍板）

用户投诉券没退回、券用不了时，客服须能按用户查到他持有的券。

- **位置**：后台现有的用户详情页新增「优惠券」标签页（线上用户详情页的结构由研发评估后确定具体放法）
- **内容**：该用户的每一张券——券名、类型（满减 / 免运）、面额与门槛、获得方式（新人 / 领取 / 兑换码 / banner）、领取时间、有效期、当前状态（可用 / 被待付款订单占用 / 已使用 / 已过期 / 已失效）；占用或已使用的显示对应订单号并可点进订单
- **状态变化记录**：每张券的占用、退回、使用时间，便于查「券为什么没退回」
- **只读**：客服不能修改券的状态
- **兑换码锁定**：用户因输错兑换码被锁定时（App 端 FR-130），标签页显示「兑换已锁定，X 分钟后解除」；客服不能手动解锁
- **不在本版**：客服给指定用户手动补发券（如投诉补偿）留到下一版，需配套权限与审批

### UI 说明

**需要出稿。** 新页面、新表单，现有后台无同类先例。后台文案按中 / EN / ID 三语准备。

## 5. AB-28：异常订单取消退款与退款打款

**背景：** App 端 FR-134 ③ 拍板：异常订单取消必须退还现金部分。现状「异常订单」页的整单取消只退 PawCoin 部分、现金部分只写审计不退款；部分取消完全不退款。

**位置：** 🛍 商城 → 「异常订单」页，现有「整单取消」「部分取消」两个处置动作（另有「联系后继续发货」，不涉及退款）。2026-11-03 按线上 1.4.1 复核：整单取消只把 PawCoin 部分退回钱包，现金部分只写进审计、不生成退款单；部分取消只回补库存、不退任何款；成长值扣回只在 PawCoin 部分实际退回时触发。

### 已确认项（2026-09-30 拍板）

- 整单取消：PawCoin 与现金部分全额退回
- 部分取消：退回被取消行对应的金额
- 现金部分的去向沿用现有退货流程：退为 PawCoin 或财务线下打款（2026-10-02 拍板）
- 平台原因的退款（缺货、运单失败、揽收失败、快递原因物流异常）选退为 PawCoin 时额外补偿；用户原因被退回的取消不给（2026-11-04，见 App 端 FR-134）。补偿用哪套配置见下「整单取消：取消原因」
- **与现状的关系：完全取代现行「整单取消不退现金、部分取消不退款」的处置结果**，两个处置入口本身保留

### 整单取消：取消原因（2026-11-05 拍板）

**现状（2026-11-05 核 1.4.1）：** 整单取消一律自动回补库存、一律发「平台责任补偿」溢价，不区分原因。物流异常复用这个动作时，用户原因取消会多发补偿、多退券，退回商品经入库入口回补后会再被回补一次，丢件的商品也会被加回库存。

整单取消须先选**原因类别**，由类别决定退款金额、补偿与退券：

| 原因类别 | 适用 | 退款金额 | 转 PawCoin 补偿 | 券 |
|---|---|---|---|---|
| 平台原因 | 缺货、运单失败、揽收失败、快递原因的物流异常 | 全额（应付金额） | 给 | 退回 |
| 用户原因 | 用户原因被退回（地址错、联系不上、拒收） | 应付金额 − 用户实际支付的运费 − 保价费 | 不给 | 不退 |
| 丢件破损 | 运营已标丢件或破损（AB-38） | 买了保价：应付金额 − 用户实际支付的运费 − 保价费（即商品实付）；没买：客服填写与用户协商的金额，不超过前者 | 给 | 退回 |

- 「用户实际支付的运费」= 运费 − 满额免运或免运券减免（App 端 FR-172）
- 订单此前有部分取消已退过款的，以上各类退款金额都**减去已退金额**；PawCoin 与现金按「部分取消：退款拆分」同样的比例拆（2026-11-05）
- **库存**：只有货还在仓库（未被快递揽收）的订单取消时自动回补库存；已被揽收的不自动回补——退回仓库的商品经现有「退货与拒收的货」入库入口回补，丢件的不回补
- **补偿配置**：用 PawCoin 配置里的「**平台责任补偿**」比例与上限（`compensation_premium_rate` 及其上限，线上异常订单现用的这一套），不用退货的转币激励（`premium_rate` / `premium_fixed`）。**只对现金部分中用户选「退为 PawCoin」的金额发放**；原本用 PawCoin 支付的部分原路退回，不另给补偿（取代现状对 PawCoin 部分一律发补偿）
- **门店返佣**：整单取消（含已发货后取消）按各行原口径全额扣回门店返佣；部分取消按被取消行扣回（App 端 §2.3）
- 用户原因的取消须在退回商品确认入库后才能提交（AB-38）

### 部分取消：退款拆分（2026-11-05 拍板）

### 流程（2026-10-06 拍板）

**场景：** 订单 60 分钟未付款被自动取消后，用户的付款才到账。现状这笔到账通知被直接丢弃，后台查不到。

- **处理顺序**：
  1. **客服先联系用户**，询问是否同意由平台帮他重新下单，并核对条件是否满足（见下方核对清单）
  2. **用户同意且条件满足 → 重新下单**：订单详情点「重新下单」，系统按原订单为用户生成一张新订单，与原订单互相关联；已到账的钱用于支付 QRIS 部分，原订单用过的券与 PawCoin **正常扣除**，新订单进入待发货、正常履约
  3. **用户不同意、条件不满足或没有库存 → 退款**：点「退还到账款」，App 订单详情出现「选择退款方式」，用户选退为 PawCoin 或线下打款；**不给转 PawCoin 补偿**
- **核对清单**：点「重新下单」前，后台向客服列出须核对的事项，逐项满足才可提交：
  - 用户已同意重新下单
  - 原订单用过的券仍在用户账户中、没有被用掉；**券已被用掉则不能重新下单**，走退款。券**已过期仍可用于这张新订单**（原订单下单时券有效，按 FR-130「按下单时刻判断」的口径）
  - 用户 PawCoin 余额足以支付原订单的 PawCoin 部分（超时取消时这部分已退回用户）
  - **至少一行商品有库存**（只有部分缺货时见下「重新下单细节」；全部缺货走退款）
  - 收货地址仍有效
- 不提供「恢复原订单」

### 取消后到账：重新下单细节（2026-11-04 拍板）

- 新订单沿用原订单的商品、数量、收货地址、快递、保价与金额明细，**金额按原订单锁定**，不随现价、现在的运费报价变化；差额由平台承担

- **揽收失败**：Biteship 回传揽收失败（快递没来取件等）时订单标「揽收失败」，进入「异常订单」页（AB-28「处置范围」），无论是否已被标为已发货。运营处理与「运单失败」相同（重新提交运单 / 手工填运单 / 联系用户后取消）；**三种处理执行前系统都先取消 Biteship 上的旧运单**，避免重复取件与重复计费。用户侧不提示异常
- **自动送达与自动完成**：「发货起 14 天自动标记送达」与「送达后 7 天自动完成」都**跳过带异常标记的订单**（揽收失败、退回、物流停滞、丢件破损），标记清除后再按原规则计时。「确认收货」在任何异常下 App 端都照常可点（可能只是物流没更新、用户其实已收到货）；用户确认收货后订单照常完成，异常标记自动清除，并提醒运营核对——已标「待索赔」的由运营自行撤回索赔（App 端 FR-172）
- **手工填写的运单**（运单失败后的第三种处理）：不接 Biteship 回传。App 订单详情只显示快递名称与运单号、「去承运商官网查询」，不显示物流状态；送达靠运营手工「标记送达」（14 天自动送达照常兜底）；承运成本由运营手工录入，进对账页
- **Biteship 余额（2026-11-05 拍板，2026-11-06 改为预估）**：Biteship 不提供余额查询接口，后台显示的是**预估余额**。运营在「服务范围与运费」页手填 Biteship 后台看到的实际余额（记录录入人与时间）；系统从录入时起，按每张运单的实际运费（含保价费）往下扣，已取消的运单不扣；页面显示「上次录入的余额 − 此后运单扣除 = 预估余额」，并注明是预估值。充值后或发现与实际对不上时，运营重新录入，预估从新数重新扣。运营在同页设置预警阈值，预估余额低于阈值时提醒运营充值（见文档头「后台提醒的通道」）。余额不足会导致下运单失败
- **报警通道**：「重新提交运单次数快速上升」的报警发到技术群，阈值由研发定

### 物流异常处理（2026-11-04 拍板，承接 App 端 FR-172「物流异常」）

- **退回**：Biteship 回传退回时订单自动标「退回」。运营判定原因：
  - 快递原因：平台承担运费，免费重新发货；订单同时标「**待索赔**」，提醒运营向快递 / Biteship 处理责任认定与索赔
  - 用户原因（地址错、联系不上、拒收）：**原订单取消**，不退已花掉的运费；商品退回仓库，运营确认入库后退还商品款。用户仍想要的重新下单，按新订单发货
- **物流停滞**：物流状态 **3 天**没有更新时自动标「物流停滞」，提醒运营去 Biteship 追件
- **丢件、破损**：运营确认后手工标记。用户买了保价按商品价值赔付；没买由客服与用户协商。订单同时标「待索赔」
- 订单被标为退回、丢件或破损后，App 端订单详情显示「配送异常，请联系平台客服」

### 物流异常处理细节（2026-11-04 拍板）

- 订单履约列表新增筛选：退回 / 物流停滞 / 丢件破损 / 待索赔

- 「重新发货」只用于快递原因：在原订单上再走一次「Biteship 下单」，运费记为平台成本。退回到仓的商品**不走入库**，直接重新发出；退回途中丢失或破损的，改按「丢件破损」处理（2026-11-05）

## 8. AB-39：商品评价管理

**背景：** App 端 FR-133 改为在商品详情页**展示评价内容**（现只显示均分与条数）。
