# PRD：TailTopia 宠物 App V1.1.2 改版——底部 Tab 顺序调整 + 成长档案 Diary 改版 + 内容发布模型

## 0. 文档说明

本 PRD 为迭代版本文档，采用轻量结构——不重复 V1.0.0 已写明的产品愿景、用户旅程和术语表，仅记录本次改版范围内的新增/变更内容。如需查阅产品整体定位，参见 `TailTopia/V1.0.0/V1-0-0PRD.md`。

**编号延续规则：** 本文档 FR 编号包含 FR-78~FR-84（含 FR-78A）与 FR-86，编号非连续，沿用全局既有 FR 分配，不重新编号。（FR-85 为推送权限多触发点唤醒，归 V1.1.4。）

**版本定位：** 本次改版调整底部 Tab Bar 的信息架构与首屏心智——从"信息流优先"转向"工具+私密陪伴优先"，配套解决由此产生的游客体验问题，并同步调整内容发布与分发模型（Diary 与 Moment 的关系显式化、发布时可一键转私密）、把里程碑/身份证/健康记录整合进成长档案两个视图。**本版本不含任何运营后台配套需求**，App 端与服务端即可独立交付。

**版本拆分说明（2026-07-28）：** 本文档原为一份合并稿，同时包含「Diary 信息架构主线」与「从 V1.2.0 迁入的 6+2 项内容运营/增长能力」。2026-07-28 产品决定按**是否依赖运营后台**拆为两个版本先后上线：Diary 主线（零后台依赖、PRD 与 UI 均已就绪）留在本版本 V1.1.2；内容运营/增长能力整体移至 V1.1.4，为运营后台需求与设计留出一个版本的准备期。详见 §6。

## 1. 版本目标

1. **调整 Tab 顺序，强化工具属性与私密陪伴感**：把成长档案（Diary）提到第一位、问诊提到第二位，弱化首页 Feed 作为"入口即社交流"的产品心智。
2. **不破坏 V1.0.0 已确立的游客增长策略**：V1.0.0 明确采用"未登录可浏览、无强制拦截、软性登录推荐"的策略（FR-0A/FR-0B）。Diary 成为默认落地 Tab 后，若直接对游客展示登录墙，等于把这套策略废掉——本次改版必须为 Diary 设计一个不依赖登录墙的游客引导态。
3. **内容发布模型调整**：Diary（原成长日历）与公开 Moment 的关系显式化——发布 Diary 时新增「同步到 Moment」开关，**默认开启**，用户可手动关闭改为纯私密记录；Moment/Tips 不可回灌 Diary。覆盖 V1.0.0 FR-12/FR-17，详见 §2.4。
4. **日历视图联动结构化健康记录**（2026-07-27 新增）：V1.1.0 健康记录（疫苗/驱虫等）在成长档案日历中以小图标展示（与健康记录列表页同款图标）；格子改为按大类优先级只显一个标记，并修复纯文字日记错显医院图标的现网缺陷，详见 §2.5。
5. **健康类里程碑自动达成路径补全**（2026-07-28 新增）：疫苗/驱虫/绝育可由健康记录录入自动完成，第一次看兽医可由兽医咨询结束自动完成；**健康类里程碑取消打卡路径，改为唯一自动达成**（2026-07-31 产品拍板，见 FR-86 订正说明）。详见 §2.3 FR-86。

## 2. 功能与需求

### 2.1 底部 Tab Bar 顺序调整

**功能描述：** 现有 5 位置 Tab Bar（Home / Passport / [+] / Konsultasi / Profile，见 V1.0.0 FR-19）调整顺序与命名，[+] 发布按钮位置与形态不变，仍居中凸起。

#### FR-78：Tab Bar 顺序与命名变更（覆盖 V1.0.0 FR-19）

**变更前：** 首页(Home) / 成长档案(Passport) / [+] / 问诊(Konsultasi) / 我的(Profile)

**变更后：** 成长档案(Diary) / 问诊(**Health**) / [+] / 探索(Discovery，原首页 Feed 改名) / 我的(Profile)

> `[订正 2026-07-31]` 第 2 位 Tab 名由 **Konsultasi 改为 Health**（产品拍板）。**显示文案用英文 Health 还是印尼语 Kesehatan 待定，见 OQ-19**——App 其余 Tab 显示文案为印尼语（如 Discovery 显示为 Jelajah）。

**后果：**

- **Tab 视觉顺序变更**，5 个位置的排列如上；[+] 发布按钮继续居于正中间（第 3 位），视觉形态、协议尺寸不变
- Discovery（原 Feed）的内容与浏览逻辑不变，仅 Tab 位置从第 1 位移至第 4 位、名称从「首页」改为「探索」
- Konsultasi、[+]、Profile 三者均非落地页，V1.0.0 既有的「未登录点击非落地 Tab 触发登录引导」机制在这三者上保持不变，不需要额外设计

##### 落地 Tab 按用户状态区分（2026-07-28 确认，覆盖"所有人默认落 Diary"的早期表述）

**"冷启动"定义：** App 未在后台运行时被打开（首次安装后打开、被用户手动划掉后重开、或被系统回收后重开），会先播启动屏动画再进主界面。区别于**热启动**（App 仍在后台，切回时停留在离开时的页面）——热启动行为不变，本条只约束冷启动落在哪个 Tab。

| 用户 | 冷启动落地 Tab |
| --- | --- |
| 游客（未登录） | **Diary**（游客引导态，见 FR-80） |
| 状态 A · 已建档 | **Diary** |
| 状态 A · 未建档 | **Diary**（建档引导态，见 FR-81） |
| **状态 B（计划养宠）/ C（喜欢宠物但未养）** | **Discovery** |
| 兽医账号 | 兽医工作台（不变） |

**B/C 用户走 Discovery 的原因：** 成长档案对 B/C 用户展示的是"有宠专属"的非适用页（V1.0.0 既有设计）。若让 Diary 成为全体用户的落地页，B/C 用户冷启动第一屏就是一张功能拒绝页——比游客体验更差（游客至少有 FR-80 的预览种草页）。B/C 用户已明确回答过自己没有宠物，把他们落在内容流更合理。

**后果：**

- **B/C 用户的 Diary Tab 位置不变（仍在第 1 位）、仍可点击进入**，进入后展示 V1.0.0 既有的「有宠专属 + 修改宠物状态入口」页面，该页面本身不做改动。只是不再作为他们的落地页。
- **B/C → A 状态切换后落地页跟着变**：用户在 Diary 页或「我的」页把宠物状态改为 A 时，按 V1.0.0 既有逻辑进入 FR-0G 建档引导；此后（含后续每次冷启动）落地 Tab 变为 Diary。反向（A → B/C）同理变为 Discovery。
- **落地 Tab 是一个按当前用户状态实时计算的结果，不做持久化记忆**——不存"上次落在哪"，每次冷启动按当时状态判定。

##### 登录门控变更：Diary 必须对游客开放

**这是一项明确的门控解除，不是"保持不变"：** V1.0.0 中成长档案属受控页面，未登录访问会被拦截并重定向。**本版本起 Diary 及其游客引导态（FR-80）对未登录用户开放**，否则 FR-80 设计的游客页不可达。

- 解除门控的范围**仅限 Diary 主页本身**。成长档案下属的建档、编辑档案、当天详情、里程碑列表等页面**仍然受控**，游客访问仍按 V1.0.0 规则拦截。`[工程注意：现有实现的受控清单按路径前缀匹配，解除 Diary 主页时会连带解除其全部子页面，需改为精确匹配或显式子页白名单，见 A-4]`
- Discovery 对游客开放，维持 V1.0.0 现状不变。
- Konsultasi / [+] / 我的 三者对游客维持受控不变。

##### 落地页变更的连带调整

- **[+] 发布按钮触发登录后的回跳**：由现状的回到首页改为**回到 Diary**。
- **游客点开他人分享的宠物名片深链（V1.0.0 FR-14）**：现状游客会被拦截并重定向到首页；本版本起**落在 Diary 的游客引导态（FR-80）**，与冷启动落地页一致，不再回退到 Discovery。
- **切回 Diary 时自动刷新**：从其它 Tab 切回 Diary 时刷新时间线与日历数据。FR-82 引入的里程碑、健康记录、身份证镜像条目会在用户不在该页时发生变化（例如他人互动触发的系统自动型里程碑），不刷新会导致用户切回后看不到新内容。现状仅 Discovery 有等价的切回刷新机制。

##### 关于 Tab 索引的实现口径（`[工程注意]`）

早期表述中的"Diary 成为 `state.index === 0`"**不作为需求**，本 FR 只约束**视觉顺序**与上方的落地页矩阵。现有实现中 Tab 的索引由枚举顺序、路由分支顺序、路径映射数组三处共同决定，且视觉顺序本就与索引不一致。是否连带重排底层索引由工程按改动成本决定——**若重排，需同步核对所有以索引寻址的调用点**（登录后回跳的目标、推送深链、埋点上报的 Tab 标识）；若不重排、仅调整视觉顺序，则落地页改为按上表指定目标路径跳转即可。两种做法对用户表现一致。

#### FR-78A：Tab 图标激活态萌化（新增，2026-07-27，扩展 icon-system.md）

**功能描述：** 激活态 Tab 图标在保留原图标主体 glyph 的前提下叠加"宠物特征"萌化元素，强化可爱/陪伴调性；未选中态维持简约描边不变。**图标主体形状在选中/未选中之间保持一致**（用户靠形状辨识 Tab，不改变辨识锚点）。

**后果：**

- **仅激活态萌化，形状不变**：每个 Tab 的核心 glyph（Diary=书 / 问诊=听诊器 / [+] / 探索=罗盘 / 我的=人像）不变；激活时在其上叠加一处宠物特征装饰（如猫耳、小爪印、尾巴等，具体每 Tab 的萌化元素在页面设计阶段定），配一次轻量入场动效（弹跳/微动，`[ASSUMPTION: 时长 ≤150ms，遵循 icon-system.md 既有 reduced-motion 兜底]`）
- **与现有 pop-art 激活态的关系**：`[ASSUMPTION: 萌化装饰替换 V1.0.0 icon-system.md 定义的「紫实心+红(3,3)错位投影」pop-art 激活态——两者叠加视觉过噪；激活态改为「紫实心 glyph + 宠物特征装饰」。此为设计侧假设，替换 vs 叠加需在页面设计阶段最终确认，并回改 icon-system.md]`
- **未选中态不变**：维持 ink@55% 描边简约态
- **不影响** Tab 顺序、路由、登录门控等 FR-78 既有逻辑；本条纯视觉/动效层
- 具体每 Tab 的萌化元素与动效为页面设计阶段交付物；对应回改 `V1.0.0/icon-system.md` 的激活态规范

#### FR-79：软性登录触发点拆分（新增，独立于 FR-78）

**功能描述：** Diary 成为默认落地 Tab 后，原本挂在首页 Feed 上的软性登录推荐机制（V1.0.0 FR-0B）不能简单挪用到 Diary 上，因为 Diary 游客态不是可无限滚动的信息流，而是一个静态预览页。两套触发机制**拆分为独立的两套，互不依赖**：

- **Discovery：** 保留 V1.0.0 FR-0B「浏览至第 3 页触发软性登录推荐」逻辑，不做任何调整
- **Diary 游客态：** 触发方式为页面内常驻 CTA（见 FR-80），非滚动触发、非弹层打断

**⚠️ 对注册转化的副作用（需在上线后观察）：** 改版前游客一进 App 就在 Feed 里，FR-0B 的"滚到第 3 页"很容易自然触发；改版后游客落在 Diary，**必须主动切到 Discovery 并滚够 3 页**才会触发 FR-0B。也就是说 FR-0B 的曝光量会明显下降，游客侧的注册转化改由 FR-80 的常驻 CTA 承担主要责任。

- 这是本次 IA 调整的**预期结果**（把游客的第一印象从"社交流"换成"专属成长本"），不是缺陷，但**必须配套埋点验证**：需对比改版前后的「游客→注册」总转化率，并分别统计 FR-80 CTA 与 FR-0B 浮层各自的贡献。
- 若上线后总转化率下降，优先调整 FR-80 CTA 的文案/位置，而非退回旧 Tab 顺序。
- 状态 B/C 用户落 Discovery（见 FR-78），但他们是**已登录**用户，FR-0B 只作用于游客，对他们不触发。

### 2.2 成长档案（Diary）游客引导态

#### FR-80：未登录用户的 Diary 引导态（新增）

**功能描述：** 由于 Diary 现为默认落地 Tab，未登录游客首次打开 App 会直接看到该 Tab。为避免以登录墙作为 App 门面（与 FR-0A 游客浏览策略冲突），设计一个"预览+种草"式引导态，核心目标是让用户看完的反应是"我也想给我家宠物记一篇"，而不是"这个 App 有哪些功能"。

**页面结构（从上至下）：**

1. **Hero 时间线预览**——展示一只示例宠物（demo：金毛 Milo）的成长时间线，非真实数据，明确是示例。内容为完整的故事弧线，而非功能罗列（详见下方"示例时间线内容"）
2. **情感化标题 + 一句话说明**——强调"专属成长本/私密陪伴记录"的定位
3. **主 CTA**——直接进入建档流程，复用 V1.0.0 既有登录 → 宠物状态选择 → 档案创建引导（FR-0G）流程；按钮文案需有动作感，避免出现"登录"字样
4. ~~**次要入口**——页面底部小字「已有账号？登录」~~ **已删除（2026-07-30）**：该入口与主 CTA 最终都进同一个登录页，两个入口做同一件事，对老用户没有提供任何"更快的路径"，只是多了一个视觉噪点和一次选择成本。本页只保留一个主 CTA。

**示例时间线内容（9 条，混排"普通内容"与"特殊内容"，制造真实生活感而非成就展示墙）：**

| 顺序 | 内容 | 对应真实功能/里程碑编号 | 视觉样式类别 |
| --- | --- | --- | --- |
| 1 | 建档完成 + 第一张照片上传 | D-S1 / D-S2（系统自动，V1.0.0 FR-42） | 类别③ 系统自动型里程碑 banner |
| 2 | 普通快乐时刻——阳台晒太阳 | 无（普通内容，无里程碑） | 类别① 普通照片卡 |
| 3 | 第一次玩水 | D-S13（用户打卡，FR-42） | 类别② 打卡关联型里程碑 |
| 4 | 普通快乐时刻——深夜加餐 | 无（普通内容，无里程碑） | 类别① 普通照片卡 |
| 5 | 完成第一次疫苗接种 | D-M3（用户打卡，FR-42） | 类别④ 健康/问诊胶囊条目 |
| 6 | 普通快乐时刻——日常遛弯 | 无（普通内容，无里程碑） | 类别① 普通照片卡 |
| 7 | 第一次保存兽医问诊结论 | D-S4（系统自动，FR-16 + FR-42） | 类别④ 健康/问诊胶囊条目 |
| 8 | 领取专属宠物身份证 | 非里程碑，V1.1.0 FR-49 系列 | 类别⑤ 证件卡样式 |
| 9 | 陪伴满 100 天 | D-L2（L 级，系统推送触发，FR-42） | 类别③ 系统自动型里程碑 banner（大号，含分享卡） |

**视觉样式五分类（用样式差异传递内容类型，不依赖文案说明）：**

1. **普通快乐时刻**——标准照片卡（图 + 简短配文 + 日期），无任何徽章/标记
2. **打卡关联型里程碑**（需绑定内容才能解锁的，如"第一次玩水"）——外观仍是普通照片卡，右上角挂一个小金色徽章角标（🏆 + 里程碑名），保持"这是一条内容"的观感，只是被额外标记
3. **系统自动型里程碑**（无需绑定内容，时间/次数到了自动触发的，如建档、陪伴满 N 天）——横向通栏庆祝 banner，无需照片，图标 + 大字标题，视觉上是"事件"而非"内容"
4. **健康/问诊类记录**（疫苗、驱虫、问诊结论存档）——胶囊/标签式条目，图标 + 一行字，明显小于照片卡，像"系统自动记的一笔"
5. **身份证解锁**——独立证件卡样式（圆角 + 证件质感 + 照片/名字/编号排版），与其余四类样式均不同，专门用于展示该功能本身

**关于第 5 条和第 7 条为什么归类别④（2026-07-28 补充说明）：** 这两条（疫苗接种、问诊结论）在 V1.0.0 的里程碑定义里一个是用户打卡型、一个是系统自动型，按"触发方式"分类本应落到类别②和③。**本示例表以"是否有对应的结构化健康记录/问诊存档条目"为准**——凡是能在健康记录列表里找到对应条目的，一律用类别④健康胶囊条。FR-82 的真实时间线分类规则已按此口径改写（见 §2.3），两处一致，示例表无需调整。

**本示例表即真实时间线的样式契约：** FR-80 的核心目的是让游客相信"我也能有这样一本册子"。因此**游客看到的示例样式，必须与他注册建档后看到的真实时间线完全一致**。示例表的 9 条与 FR-82 的分类规则是同一套规则的两种表述，任何一侧调整都必须同步另一侧。

#### FR-82：时间线视图整合里程碑与身份证事件（扩展 V1.0.0 FR-37 视图一，与 FR-42 / FR-45 / FR-45B / FR-49 并存不替代）

主时间线条目类型从 FR-37 原有的「快乐时刻 + 健康事件」两类，扩展为与 FR-80 一致的五类。

##### 分类判定顺序（2026-07-28 改写，覆盖早期"按里程碑触发方式分类"的口径）

**早期版本的问题：** 早期规则按里程碑的**触发方式**分类（用户打卡→类②、系统自动→类③），但 FR-80 的示例表实际按**是否属于健康类**分类，两把尺子在「疫苗接种」「问诊结论」两条上给出不同答案。本次统一为下面这一套判定顺序，FR-80 示例表的 9 条全部成立、无需调整。

按顺序判定，命中即停：

1. **该条目对应一条结构化健康记录或问诊存档** → **类④ 健康/问诊胶囊条**
2. 否则是宠物身份证首次生成 → **类⑤ 证件卡**
3. 否则是里程碑完成，且该里程碑由用户打卡绑定了一条 Diary 内容 → **类② 照片卡 + 金色徽章角标**
4. 否则是里程碑完成（系统自动、无绑定内容） → **类③ 横向通栏 banner**
5. 否则是普通 Diary 内容 → **类① 普通照片卡**

**关键点：判定依据是"这一天有没有对应的健康记录条目"，不是里程碑声明的触发方式字段。** 这样做的原因是健康类里程碑同时存在打卡和自动两条完成路径（见下方「健康类里程碑的完成路径」），若按触发方式字段判定，同一个疫苗里程碑会因为用户走了哪条路径而显示成不同样式。改为按"有无健康记录条目"判定后，展示结果与完成路径无关，恒定一致。

##### 五类条目定义

1. **普通快乐时刻**——沿用 FR-37 既有逻辑，不变
2. **打卡关联型里程碑**——当一条 Diary 内容被用户在里程碑列表页通过「已打卡」或「去发布」关联为某个里程碑的完成凭证（FR-42 既有机制）时，该条内容在时间线里的展示形态从普通照片卡变为「照片卡 + 右上角金色徽章角标」；**不生成额外的时间线条目，只是同一条内容的展示样式变化**。**不适用于健康类里程碑**——它们走类④（判定顺序第 1 条优先）
3. **系统自动型里程碑**——触发方式为「系统自动」或「系统推送 + 用户当天发布」、且**没有对应健康记录条目**的里程碑（如陪伴满 30/100/365 天、成长日历记录满 10/30 条、建档完成、新手毕业等），完成时在对应完成日期新增一条独立的横向通栏 banner 条目，无需绑定任何内容
4. **健康/问诊类记录**——FR-45B 健康记录列表中的全部条目（结构化录入的疫苗/驱虫/月经/绝育/自定义 + FR-16 问诊记录存档）均按各自的事件日期在主时间线镜像展示一份胶囊/标签式条目。**由这些记录触发完成的里程碑不再单独生成时间线条目**，避免同一件事在同一天出现两次；**胶囊条本身不加任何里程碑标记**（2026-07-29 决定，本版本不做），保持"系统自动记的一笔"的纯粹外观；里程碑达成只在里程碑列表页与完成时的庆祝动效中体现。<br>`[现状说明，非本 FR 新增：类④在现有实现里已有两种呈现——问诊/AI 健康事件条目带 AI 风险等级标记（HIJAU 等），结构化健康记录条目为纯一行胶囊。这是 V1.0.0/V1.1.0 已上线的样式，本 FR 沿用不改，无需新设计]`
5. **身份证解锁**——宠物身份证首次生成/分配成功当天（FR-49A 新建档案的实时分配，或 FR-49 老档案「立即申请」触发的分配），在时间线新增一条证件卡样式的条目，仅出现一次，不可重复触发

**排序规则：**

- 整体仍按 FR-37 既有的「事件日期倒序」排列
- 同一事件日期内多条不同类型条目的先后顺序，沿用 FR-37 日历详情页已有的「按发布/完成时间正序排列」口径；系统自动型里程碑和身份证解锁条目没有「发布时间」概念，取其系统记录的完成/生成时间戳参与同日排序

**交互规则：**

- 点击「打卡关联型里程碑」条目 → 行为与普通快乐时刻一致，进入内容详情页（FR-28）；角标本身可再次点击跳转里程碑列表页对应条目
- 点击「系统自动型里程碑」banner → 跳转里程碑列表页对应条目
- 点击「健康/问诊类记录」胶囊 → 跳转健康记录列表页（FR-45B）对应条目；不在时间线内提供编辑入口
- 点击「身份证解锁」条目 → 跳转该宠物的身份证页（FR-49）

**明确不变更范围：**

- 日历视图（FR-37 视图二）由 §2.5 FR-84 单独调整（结构化健康记录联动），本条 FR-82 不涉及
- FR-42 里程碑列表页、FR-45/45B 健康记录列表页、FR-49 身份证页的既有功能、编辑权限、数据生命周期规则均不变，本条新增的仅是这些数据在主时间线里的只读镜像展示（里程碑完成路径的变更另见下方 FR-86）

##### 多数据源合并分页口径（`[工程注意]`，2026-07-28 补充）

时间线目前是「Diary 内容 + 问诊健康事件」两个数据源按时间游标合并分页。本 FR 把它扩展到五类、实际数据源增至四个（Diary 内容 / 结构化健康记录 / 问诊存档 / 里程碑完成 / 身份证生成）。多源游标分页容易出现**翻页时条目丢失或重复**，需明确口径：

- **统一游标锚点**：以「事件日期 + 同日排序键」作为唯一游标，所有数据源用同一个锚点各自取数后再归并，不使用各源自己的主键游标
- **同日条目不可跨页拆分**：一页的边界必须落在日期分界上；若某一天的条目数超过单页容量，该日整体作为一页返回（允许该页超出默认页大小），避免同一天的条目被拆到两页后因排序键相同而重复或丢失
- **归并后再截断**：先按游标从各源各取一批，归并排序后统一截断到页大小，用截断处的锚点作为下一页游标——不可各源先截断再归并
- 上述为口径要求，具体实现方式由工程决定

#### FR-86：健康类里程碑的自动达成路径补全（新增 2026-07-28，扩展 V1.0.0 FR-42）

> **本 FR 无 UI 交付物。** 它改的是里程碑何时被判定为完成（后端触发逻辑），不改任何页面——里程碑列表页、庆祝弹层均复用现状。因此 `ui-standalone-features-integrated-v1.html` 中不含对应屏。

**背景：** V1.1.0 Story 7.2 已为里程碑新增了**第四条触发路径**——用户在健康记录页录入结构化记录时，自动完成对应里程碑（现已实现：疫苗 → M3、驱虫 → M4，幂等，与原有打卡路径并存）。但该映射当时是工程侧填的合理默认（交付记录原话："映射为规格未细化合理默认"），PRD 从未规定过覆盖范围，导致目前**只覆盖了疫苗和驱虫，绝育和第一次看兽医仍是纯打卡**。本 FR 把这套映射补全并写进规格。

**后果：**

- **健康类里程碑一律改为由健康记录/问诊自动完成**，映射关系如下（猫 C 系列、狗 D 系列、通用 G 系列同规则）：

| 里程碑 | 触发来源 | 现状 |
| --- | --- | --- |
| M3 完成第一次疫苗接种 | 健康记录录入「疫苗」 | 已实现 |
| M4 完成第一次驱虫 | 健康记录录入「驱虫」 | 已实现 |
| **M9 完成绝育手术** | 健康记录录入「绝育」 | **本版本新增**（2026-07-29 产品确认） |
| **M5 第一次看兽医** | **首次兽医咨询会话正常结束时**（与是否存档无关） | **本版本新增**（2026-07-29 产品确认） |

**M5 与 S4 是两个不同的触发事件，不可合并实现（2026-07-29 确认）：** FR-16 的问诊存档是**用户可跳过的选择**——问诊结束后系统询问一次"是否存入健康档案"，用户可以跳过（仅记录跳过决策、不建健康记录条目），事后也可以再补存。因此：

- **M5 在兽医咨询会话结束时即触发**，用户跳过存档不影响 M5 达成——"看过兽医"这件事已经发生了
- **S4 只在用户真正选择存档时触发**；用户一直不存档，S4 就一直不达成；日后补存时补触发
- **触发范围限定为真人兽医咨询，不含 AI 问诊**（2026-07-29 产品确认）——里程碑名为「第一次看兽医」，AI 问诊不构成"看兽医"；AI 问诊无论进行多少次都不解锁 M5
- 两者常见但不必然同时发生（用户当场点保存时才同时解锁）

- **月经 / 自定义两类健康记录不映射任何里程碑**，维持现状（无对应里程碑节点）

  - **适用范围仅这四条**；非健康类里程碑（如「第一次玩水」D-S13）的打卡机制**完全不变**
  - **后端须显式拒绝**健康类 code 的打卡请求（仅前端隐藏按钮不合格——接口仍可被直接调用）
  - 打卡内容选择器的候选里程碑集合须排除这四条
  - **已接受的后果**：不录结构化健康记录、也不看真人兽医的用户，这四条永远无法解锁。产品判断：疫苗打没打是客观事实，不应靠发一条日记自称完成
- **里程碑列表页需改动（2026-07-31 订正，覆盖原「零改动」表述）**：健康类四条**隐藏「去打卡 / 去发布」按钮**；徽章弹层改为说明达成方式（「录入健康记录后自动点亮」），不提供打卡入口。其余里程碑的列表页表现不变

- **庆祝弹层只弹一次**，不连弹多次
- **复用现有单条庆祝组件原样展示"最高级别"的那一条，不新增任何视觉设计**（2026-07-30 核实：现有 `showMilestoneCelebration()` 只接受单个里程碑，且弹层底部本就有一条"已解锁收藏"圆点带含 +N 溢出——同批解锁的其余里程碑会自然出现在这条收藏带里，无需为"一次解锁多个"单独设计界面）
- 同批解锁的其余里程碑，正常写入里程碑列表页并标记为已完成，只是不各自弹一次庆祝
- 文案取最高级别里程碑的既有文案，不新写"一次解锁多个"的特殊文案（见 A-6）

**S4 / M5 是这条规则最常命中的场景，但并非必然合并**：用户问诊结束当场点保存 → 两者同时解锁 → 合并庆祝一次（按 M 级）；用户跳过存档 → 只解锁 M5 → 正常单条庆祝；日后补存 → 此时才解锁 S4 → 再单条庆祝一次。

**在时间线上的呈现（与 FR-82 判定顺序自洽，无需额外规则）：**

| 用户行为 | 健康记录列表有无该条目 | M5 在时间线的呈现 |
| --- | --- | --- |
| 问诊后当场存档 | 有（问诊存档条目） | 由该条目的**类④胶囊条**承载，M5 不单独生成条目 |
| 问诊后跳过存档 | 无 | M5 落到判定顺序第 4 条，显示为**类③通栏 banner** |
| 跳过后日后补存 | 补存后有 | 胶囊条出现，M5 自动改由胶囊承载，**banner 不再单出**，不产生重复条目 |

**`[工程注意]` 上表第 3 行成立的前提是：时间线的条目分类必须在查询时实时计算，不得把分类结果落库固化。** 否则用户补存问诊后，早先落库的 banner 不会消失，同一件事会在时间线上出现两条。

### 2.4 内容发布模型调整：Diary / Moment 同步开关（覆盖 V1.0.0 FR-12 / FR-17）

**功能描述：** V1.0.0 的三类内容（成长日历 / 日常分享 / 专业科普）中，成长日历内容**同时**进入 Feed 和成长档案时间线（FR-12/FR-17），用户无法选择只留给自己。本版本起，成长日历（更名为 **Diary**）在发布页新增「同步到 Moment」开关——**默认开启（分发行为与 V1.0.0 一致）**，用户可手动关闭，把这一条变成只有自己可见的私人记录。日常分享（**Moment**）与专业科普（**Tips**）维持公开进 Feed 不变。

`[2026-07-30 变更记录：本节 2026-07-23 初稿为「Diary 默认私密、开关默认关闭」，配合 Tab 改版的"工具+私密陪伴"定位。2026-07-30 产品决定反转默认值——理由是默认私密会显著削减 Discovery 的内容供给（Diary 是产量最高的一类内容），且会让老用户的发布结果与此前不同。反转后本 FR 从"改变默认分发"降级为"新增一个可选开关"，用户侧无感知变更，风险大幅下降。]`

**术语对齐：**

| 新前端类型 | 对应 V1.0.0 类型 | 分发 |
| --- | --- | --- |
| **Diary** | 成长日历（快乐时刻） | 必进成长档案时间线；**默认同步进 Feed**，可手动关闭改为纯私密 |
| **Moment** | 日常分享 | 公开进 Feed |
| **Tips** | 专业知识科普 | 公开进 Feed |

「Moment」同时作为"公开进 Feed 的内容"的统称（= Moment + Tips 两类公开内容）；发布 Diary 时的同步开关文案为"同步到 Moment"，指将该条 Diary 额外作为一条公开 Moment 展示在 Feed。

#### FR-83：Diary/Moment 发布与分发模型（覆盖 V1.0.0 FR-12 发布、FR-17 Feed 内容模型）

**后果：**

- **发布页保留类型选择器（Diary / Moment / Tips），默认选中 Diary**（覆盖 V1.0.0 发布页默认，强化"记录优先"心智）；发布页整体交互、图片区、正文框等沿用现状——**本版本图片上传/展示维持 V1.0.0 现状不变**，图片比例规范化与裁剪流程（FR-71）已随内容运营能力整体移至 V1.1.4，届时再改发布页图片区，本版本不预留、不提前适配（见 `V1.1.4/改版1-1-4prd.md` §2.3）
- **「同步到 Moment」开关仅在选中 Diary 时出现**：Moment/Tips 本就公开进 Feed，无需开关。**开关默认开启（2026-07-30 产品决定，反转 2026-07-23 初稿的"默认关闭/默认私密"）**——即 Diary 发布后默认同时进成长档案时间线与公开 Feed，与 V1.0.0 现状一致；想只留私人记录的用户需**手动关掉**开关
  - **这一反转改变了本 FR 的性质**：不再是"把成长日历改成私密"，而是"在维持现状（公开）的基础上，给用户一个一键转私密的开关"。默认行为与 V1.0.0 相同，因此**没有任何用户会感到内容分发方式突然变了**，也不需要教育成本
  - **保住了 Discovery 的内容供给**：Diary 是三类内容里产量最高的一类，若默认私密，公开 Feed 的内容量会显著下降。默认开启把这个风险移除了
  - **代价**：Diary 的"私密陪伴"定位从**默认行为**降级为**可选能力**。FR-80 游客引导态里"专属成长本 / 私密陪伴记录"这类文案需相应调整措辞，不宜再把"私密"当作核心卖点主打（具体印尼语文案见 OQ-1，本条为文案方向约束）
- **同步状态在发布时一次性确定，发布后不可更改（2026-07-28 确认）**：「同步到 Moment」**只在发布页出现、只在发布那一刻生效**。内容发布后，该条 Diary 的公开/私密状态即固定，**不提供任何事后开关**——内容详情页、「我的发布」列表、内容编辑流程中均**不出现**同步开关，也不提供"转为私密""取消同步"之类的入口。
  - **用户想让内容不再被他人看到，唯一途径是删除该条内容**（删除按下方"包含关系"规则联动，Diary 与 Moment 两处同时消失）
  - **设计取舍：** 不做事后可切换，是为了避免"已公开内容被撤回"带来的一系列衍生问题——他人已产生的点赞/评论如何处置、已被顶置/打标的内容中途转私密、外部已分享出去的卡片链接失效等。以"发布前想清楚 + 后悔就删除"这一条简单规则收口，成本最低、语义最清晰。
  - **对下游的确定性影响：** 因不存在"运行中状态翻转"，所有消费公开内容的能力（V1.1.4 FR-68 内容顶置、FR-75 内容装饰标签、后台 AB-3G 互动积分统计等）**只需在选取/统计时点判断一次同步状态即可**，不需要处理状态中途变化的回退逻辑；内容被删除时按各自既有的"内容下架"规则处理。
- **关闭同步的 Diary 是纯私人记录**：未开启同步的 Diary 内容**只在该宠物的成长档案（Diary）时间线里展示**（§2.3 FR-82，作为快乐时刻条目 ①/②），**不进 Discovery 信息流**、不进话题聚合页、不进任何平台公开位（含 V1.1.4 FR-68 顶置坑位）；作者本人可在「我的发布」看到自己的全部 Diary（含未同步）
- **Diary → Moment 同步（包含关系，非副本）**：发布时开启同步的，该条 Diary 同时以一条公开 Moment 形式出现在 Feed；**两处是同一条内容，删除任一处则两处同步消失**（沿用 V1.0.0 FR-12 成长日历"包含关系"的既定语义与 FR-36 删除联动规则）
- **Moment / Tips 不能回灌 Diary**：直接以 Moment 或 Tips 发布的内容无法进入成长档案时间线——Diary 条目需绑定宠物与成长语境（宠物归属必填，见 V1.2.0 FR-64），而 Moment/Tips 不强制关联特定宠物，二者不可逆向同步
- **打卡关联型里程碑（§2.3 FR-82 类②）不受影响**：里程碑绑定的是 Diary（成长日历）内容，Diary 私密化不改变"绑定内容打卡解锁里程碑"的既有机制
- **宠物名片 H5（V1.0.0 FR-14）继续展示 Diary 内容**：H5 是用户**主动分享**后他人才可见的对外页面，属用户自主授权的对外展示，与该条 Diary 是否关闭了同步无关（同步开关约束的是平台 Feed 自动分发，不约束用户主动分享）。`[待确认：作者手动关闭同步的私密 Diary，是否仍应出现在他主动分享出去的名片 H5 里。本文档取"仍展示"，理由是 H5 是作者自己按下分享键的结果；但"我特意设成私密的内容出现在对外页面"也可能违背用户预期，见 OQ-18]`**本版本 H5 页面沿用现有 UI，不做改动**；H5 UI 改版为独立设计任务，已随视觉稿归入 V1.1.4（见 `V1.1.4/改版1-1-4prd.md` OQ-9 与 `V1.1.4/ui-h5-namecard-redesign.html`）
- **存量内容迁移：维持公开、仅新内容生效**（2026-07-24 确认）：V1.0.0/V1.1.0 期间已发布、当前公开在 Feed 的成长日历内容**保持公开现状不变，不批量转为私密**；新模型仅对本版本上线后新发布的 Diary 内容生效，避免存量内容突然从 Feed 消失惊扰老用户

- **emoji 无法着色**，无法随主题/深色模式变化，也无法与其余图标做统一的尺寸与视觉重量校准
- 🩸 属 Unicode 12（2019）新增字符，**印尼市场存量老安卓设备上存在渲染为豆腐块 ☐ 的风险**

实心矢量水滴 + 红色着色在视觉呈现上即为 🩸，但可着色、跨设备一致。

**`[ASSUMPTION: 红色取值需与疫苗、问诊已用的 coral(#F0425A) 拉开距离]`** —— 健康记录列表页是 6 个分类图标同屏平铺的网格，若月经也用 coral，该屏会同时出现三个同色红（疫苗/问诊/月经），扫视时难以区分。建议为月经单独取一个偏深的经血红，具体色值待 UX 定（见 OQ-11 后续项 A-3）。日历格子每天只显一个图标，不受此影响。

**覆盖范围：** 本变更同时作用于 V1.1.0 已上线的健康记录列表页（FR-45B）与本版本新增的日历格子。V1.1.0 文档不回改，以本 FR 为准。

**其它：**

- **图标一致性**：日历中的健康记录图标与健康记录列表页同源，不新设一套
- **数据模型**：`CalendarDayCell` 需新增结构化健康记录维度（是否有、类型、条数），供格子优先级判定与图标选择；`[需后端 petProfileCalendar 接口补充对应字段]`。`[工程注意：日历格子数据里"当天是否有 Diary 内容"这一维度已经存在且当前未被使用——现有渲染只判断"有没有首图"。本 FR 的优先级 1（diary 带图）与新增的优先级 1b（diary 无图）可直接复用这两个已有维度，只有结构化健康记录这一维需要后端新增]`
- **与 FR-82 时间线的关系**：FR-82 只改时间线视图并新增里程碑/身份证镜像；本 FR-84 只改日历视图、只新增结构化健康记录，**日历不引入里程碑/身份证标记**（那部分仍留 OQ-3 待后续评估）

## 3. 数据埋点需求

**为什么本版本必须单独写一节埋点：** 本次改版调整的是 App 的信息架构与首屏心智，这类改动**没有"功能有没有做完"这种二值判断**，只能靠数据回答"改对了没有"。而现有埋点存在一处**会直接让本次改版无法度量的硬缺口**，必须先补。

### 3.1 前置缺口：Tab 切换目前完全没有埋点（P0，阻塞本版本的效果评估）

- 该缺口是既有问题（已记录在 `3.数据埋点/数据v100-v110.md` §0.1），并非本版本引入，但**本版本的效果评估完全依赖它**

**要求：本版本必须一并修复 Tab 切换埋点**，为 5 个 Tab 各上报页面浏览事件，属本版本的 P0 工程项，不可后置。
