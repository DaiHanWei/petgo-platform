# TailTopia V1.1.6 - Epic Breakdown（Delta）

## Overview

本文件是 V1.1.6 **增量** epic/story 分解，承接 PRD（10 条 FR + §3 埋点）、架构 delta（**17 条 AD，权威**）、两份 UI 视觉稿（App 28 屏 / H5 4 屏）与决策台账（D-1~D-7）。

**V1.0 / V1.1 / V1.1.2 已上线冻结；未提及处一律继承。** 冲突序见 frontmatter。

> ### ⚠️ 版本编号说明（2026-08-11 交叉重编号）
>
> 本版本**原名 1.1.4，现顺延为 1.1.6**。「1.1.4」这个号已被**另一批需求**取走——社区管控 + 身份证分享（FR-58 举报 / **FR-94 用户拉黑** / FR-96 身份证分享奖励 + 后台 AB-3D/3E/3M），该版本**与本版本并行开发、先于本版本发版**。首页推荐算法 FR-95 于 2026-08-12 又拆出单独成版 **1.1.8，排在本版本之后**。

**本轮范围仅 App 侧 + 服务端。** 运营后台 10 模块单独走一轮；其中 4 条（顶置管理 / 装饰标签管理 / 手机号查看 / 用户标签管理）**不上线则对应 App 功能是空壳**，排期须并行核对。

## Requirements Inventory

### Functional Requirements

沿用全局 FR 编号，不重新分配（编号非连续，跳号属其它版本）。

- **FR-68**：顶置坑位与内容顶置（**本版本仅 Feed 坑位**，话题页坑位不在范围内）。Feed 顶部 1 个坑位，由运营在后台配置指定时间段展示的内容；可顶置对象二选一互斥：(a) 已发布的**公开**内容（顶置是额外展示，原时间线位置不受影响）、(b) 推广卡片（图片+标题+跳转，不对应真实帖子）。含定时上下线、WIB 时区口径、排期不可重叠、顶置期间内容被下架自动结束。顶置角标固定卡片右上角。
- **FR-70**：手机号采集入口。二合一：**一次性软引导**（复用「首次问诊后 / 建档后取最早」时机，**全局仅弹一次**，不跟随 FR-85 多触发点模型）+ **「我的」页常驻可编辑入口**。选填、仅印尼格式基础校验、**不做 OTP 验证、不用于登录**；已填写态按脱敏展示；**允许留空保存写 null**（撤回权）；保存成功/失败各一条 Toast。
  > ⚠️ **`[订正 2026-08-11 · OA-5]`** 其声明复用的那套「双时机」在线上**已不再触发**（被第二代「首启即申请」置位的共用标记键跳过）。**FR-70 须自行实现时机判定**，不得指望复用旧门控。开工前需产品确认时机口径。
- **FR-71**：图片上传裁剪与展示规范化。沿用单列 Feed；原始宽高比落在 **0.75~1.34 闭区间**内免裁剪，超出者弹裁剪框、提供 **1:1 / 4:5 两档预设**（**不提供横图预设**，超宽图只能裁成这两档，属已知接受结果）；同批次内"需裁剪的图"之间锁定同一目标比例，容差区间内的图不受锁定影响。**Feed 多图改为可左右滑动轮播**（覆盖 V1.0.0 FR-17「只展示第一张」），圆点叠在图片区内底边居中；容器高度按首图锁定、滑动时高度不变。存量内容一律 clamp 到该区间。裁剪页退出按钮在**左上角 ✕**。
- **FR-73**：内容详情页分享卡片。三类内容（Diary / Moment / Tips）均支持，**含作者关闭同步的私密 Diary**（用户主动分享属授权行为）。卡片含首图/正文摘要/作者/品牌水印；**无图用纯文字模板**；双尺寸 9:16 与 1:1；页脚含**下载二维码**（内容=该条内容分享链接、留白≥4 码元、导出分辨率下边长≥140px、纯文字模板须白色底板）。分享链接按访问者身份分流；**严格只看被分享的那一条**，不得由此进入宠物主页——与主页分享**必须是不同链接类型 + 不同落地页**。卡片生成基建**本版本首次搭建**，须按供后续复用标准设计。
- **FR-74**：用户标签。运营在后台创建（图标 + 说明文案）并分配；**四处展示位**（Feed 卡昵称旁 / 内容详情页作者区 / 评论区昵称旁 / 迷你主页预览卡），不做差异化；点击弹 tooltip；**同时最多展示 3 个**，超出按分配时间倒序取最近 3 个；空间不足时**昵称完整显示优先、标签倒序丢弃、不截断昵称、不做「+N」折叠**；支持定时生效/失效与永久分配。用户不可自主申请/购买/摘除。
- **FR-75**：内容装饰标签。运营创建（图标/样式 + 说明文案）并打标；**可打标范围仅公开内容**（Moment / Tips / 已同步的 Diary）；**三处展示位**（Feed 卡左下角 / 内容详情页 / 宠物日记页内）；点击弹 tooltip；支持定时生效/失效。详情页位置按有无配图切换：**有图叠首图角落 / 无图置正文下方单独一行**（2026-08-10 订正）。⚠️ **装饰标签生效中会给推荐排序 ×1.3 加权**——打标是流量动作，非仅荣誉徽章。

### NonFunctional Requirements

**本版本零新增 NFR**，全部继承基线。以下三条是本版本实际压在其上的既有 NFR，story 中不得违反：

- **NFR-5（继承）**：游客首屏零网络依赖。→ 约束 FR-92 访客视图与既有 Diary 游客态的关系（AD-4 不得把访客态混入零网络的示例页分支）。
- **NFR-8（继承）**：作者已注销时的渲染口径（本地化「已注销用户」+ 默认头像、头像不可点）。→ 约束 FR-74 用户标签在四处展示位遇注销作者时的表现、以及 FR-92 访客视图遇作者注销时走失效页。
- **NFR-12（继承）**：绝不在 App 首次启动时请求推送权限（授权率极低）。
  > 🔴 **`[订正 2026-08-11]` 本条 NFR 已被产品于 2026-08-07 主动推翻并上线。** 真机实测发现它对存量用户是死路：两个时机都是一次性的，老用户换机/重装后既不重走建档、也未必再问诊 ⇒ App 永不申请；而 **iOS 上「从未申请过」的 App 不出现在系统设置的通知列表里**，用户连手动开都做不到 ⇒ 永久收不到推送。现状为**首启即申请**（换取"进入设置列表"这个资格），且必须排在 iOS ATT 弹窗落定之后。**story 中不得以 NFR-12 为由要求移除首启申请**——FR-85 的"跳设置"恰恰依赖它。

**另继承底线约束（架构 delta 已列，story 中一律适用）**：`ddl-auto=validate` schema 归 Flyway；禁 MQ / 禁调度中间件 / 禁通用缓存层；对外标识不可枚举 token；凭证 env 注入不入库；错误统一 RFC 9457；**日志禁记 PII / 健康数据 / 令牌 / 签名 URL**（本版本新增手机号即 PII）。

### Additional Requirements

来自架构 delta 的 17 条 AD。以下为对 story 拆分有直接约束力的技术要求：

- **访客只读投影层**（AD-1）：新建独立取数层，**结构上不持有健康记录与问诊仓库**（沿用 V1.1.2「分类器不持有 Repository」手法）；H5 与 App 两出口**共用同一层**；**禁止**在既有 `/me` 作用域查询上加访问者参数复用；访客投影**只含已发布未删除内容**；**统计条复用作者态唯一统计实现，不得重算**。
- **访客视图 token 与路由**（AD-2）：复用现有名片 token、不新发、无撤销能力；**对未登录开放**；必须是**带 token 的独立路由**，不得复用作者态档案路由（否则未登录会落 V1.1.2 的游客示例页）；失效口径**不存在/已删/已注销返回同一响应**（防枚举）。
- **私密内容不越出 token 边界**（AD-3）：公开内容可点开进既有详情页；私密 Diary 不可点 + 提示（须出 id/en 两版 ARB）；**禁止**在内容详情页为访客场景新增二次校验层。
- **访客态接入单一判定入口**（AD-4）：作为 V1.1.2 AD-15 的新增状态分支，复用作者态结构做减法，不另画页面；Diary 页**无陪伴天数字段**，不得引入。
- **图片尺寸列**（AD-5）：与图片列并排、**同序等长**的 JSONB，缺失位 null 占位；既有五处读取点不动、存量零回填；客户端上报 + 服务端兜底测量；**写入责任在发布服务单一入口**，App 发布与后台种子发布两个调用方都必须经过它。
- **图片渲染三段顺序**（AD-6）：按实际比例 → clamp 0.75~1.34 闭区间 → 高度护栏；**服务端只下发原始宽高，clamp 与护栏一律客户端施加**（禁双重裁切）；多图按首图锁定后再套护栏；**存量占位兜底为必做项**。
- **Feed 取数扩张一律批量**（AD-7）：整组图片 / 是否已赞 / 评论数三项沿用既有批量聚合模式；**禁逐条查、禁新增冗余计数列**。
- **顶置只首屏让位**（AD-8）：仅从第一页排除，**排除后须补足页大小**；顶置走独立取数、失败不连带 Feed 失败；坑位维度必须是配置项；顶置配置归 content 模块内部。
- **时间窗判定唯一实现**（AD-9）：三处定时一律查询时判定、不落状态列、不建扫描器；副作用走事件订阅；**判定必须只有一份实现，四处共用**（三处取数 + 后台列表展示）。
- **两套独立标签表**（AD-10）：不共用配置表、不用多态外键（PostgreSQL 无法对多态外键建约束）。
- **标签 7 处展示位一律批量取数**（AD-11）：评论列表尤其禁止逐条。

- **FR-85 四键物理隔离**（AD-14）：走本地非敏感偏好存储、按设备；**存量旧标记不迁移、不删除、新模型不读它**（该键由第二代在首启即置位，故此条不仅成立且是必须）；兽医端无标记位；**护栏改为更强形式——所有触发点都不得唤起原生弹窗**，埋点中出现任何"原生弹窗"形态即为违背规格，可线上告警。见 OA-5。

- **性别与手机号字段**（AD-17）：性别补成真字段（现为前端占位，选了不入库）、存量为空须容错；手机号选填/允许清空写 null/禁入日志/脱敏在展示层。
- **Flyway**：从 **V100** 起单调分配（基线 V99）；story 内占位写 `V<n>__`，实际号按执行顺序顺延，**勿照搬示例号**。

## Epic 1: 宠物主页对外分享页改版（H5）

分享给朋友的网页不再是与品牌不符的绿色、状态页不再是看不懂的英文、服务器出错时不再是浏览器白屏；页面上有里程碑徽章墙作为拉新钩子，底部只有一个明确指向下载的按钮。

As a 宠物主，

So that 我分享出去的宠物主页上能显示它是男孩还是女孩。

**Acceptance Criteria:**

**Given** 档案编辑页当前的性别选择器是纯前端占位（代码注释明写「不随 PATCH 提交、不持久化」）
**When** 用户选择性别并保存，退出后重新进入编辑页
**Then** 之前选择的性别仍然显示 `[L1]`
**And** 该字段随档案更新接口一并提交、落库 `[L1]`

**Given** 数据库尚无该字段
**When** 执行本 story 的迁移 `V<n>__`
**Then** 宠物档案表新增可空的性别列，取值 `MALE` / `FEMALE`，`NULL` 表示未填 `[L1]`
**And** 🛡 **存量宠物一律为 `NULL`，不做任何回填** `[L1]`

**Given** 存量宠物没有性别

**Given** 该宠物已经生成过身份证（身份证上另有一个性别字段）

## Epic 2: App 内访客只读视图

装了 App 的人点开别人分享的宠物链接，看到的是**被分享的那只宠物**，且看不到健康记录与问诊记录；私密日记点不开、有解释；访客不能二次转发。

> ⚠️ **本 Epic 是本版本唯一带隐私事故风险的一块，须不晚于 Epic 3 开工。**

### Story 2.1: 访客只读投影层（时间线 + 统计）

As a 收到分享链接的人，
I want 看到这只宠物的成长记录，
So that 我能了解它、并对这个 App 产生兴趣。

**Acceptance Criteria:**

**Given** 现有全部档案取数都只服务「当前登录用户自己」
**When** 新建访客视图的取数层
**Then** 该层是**唯一**的访客数据出口：H5 直接调用它，App 端只在其上套一层薄接口 `[L1]`
**And** 🛡 **禁止**在现有「我的」作用域查询上增加访问者参数来复用——访客与作者是两条物理独立的取数路径 `[L0]`

**Given** 健康记录与问诊记录绝对不能给访客看
**When** 实现该层
**Then** 🛡 **该层在结构上不持有健康记录仓库与问诊仓库的任何引用**（沿用「分类器不持有 Repository」的同一手法，使泄露不可能而非依赖自觉）`[L0]`
**And** 🛡 时间线的访客投影**不含健康记录类与问诊存档类条目**（五类中的类④整类剔除）`[L1]`
**And** 🛡 统计条**保留三列**（Diary / 问诊**次数** / 里程碑）——次数是计数、可下发；记录本身不可 `[L1]`

**Given** 作者自己能看到被下架 / 审核中的内容
**When** 访客请求时间线
**Then** 🛡 **只返回已发布且未删除的内容**——不得照搬作者态，否则被下架内容会经访客视图继续对外可见 `[L1]`

**Given** 已登录用户可能点开一个自己**拉黑过**的人的宠物主页链接（2026-08-16 产品决定，闭合 OA-6）
**When** 该用户访问访客视图
**Then** **照常看得到，不套拉黑过滤**——不做拦截页、不做空态、不返回失效页 `[L1]`
**And** 🛡 响应体**不得下发任何拉黑相关信号**（如"你拉黑过 TA"字段或提示）——那等于暴露自己的拉黑名单在此处是否生效，也给了对方探测的余地 `[L0]`
**And** ⚠️ **与 V1.1.4「拉黑后进不去对方主页」方向相反，这是刻意的**：V1.1.4 管的是**社区个人主页**（从帖子 / 评论 / 迷你卡进去的人际入口），本条管的是**宠物主页分享链接**（拿 token 从站外进来的内容页）。**发现两处口径不一致时不要"顺手对齐"** `[L0]`
**And** 实现上**什么都不用做**——访客路径物理独立、不复用 Feed 查询，天然不继承那层过滤；本组 AC 是**防止有人主动加**上去 `[L0]`

**Given** 同一只宠物在作者页与访客页都显示统计数字
**When** 渲染访客统计条
**Then** 🛡 **复用作者态的唯一统计实现，不得自行重算**——否则两处数字会不一致 `[L1]`
**And** Diary 计数含私密条目（与访客可见的时间线一致）`[L1]`

**Given** 失效口径须防枚举
**When** token 不存在 / 档案已删除 / 作者账号已注销
**Then** 🛡 **返回同一失效响应**，不得用不同状态码或错误文案区分 `[L1]`

### Story 2.2: 日历视图与某天详情的访客版

As a 收到分享链接的人，

### Story 2.3: 访客态页面渲染（作者态减法）

As a 收到分享链接的人，

## Epic 3: Feed 卡片改造与图片规范化

用户竖拍的宠物照片进首页不再被拦腰砍掉、多图帖能在首页左右滑动看完、首页可以直接点赞和看评论数；发布时只有真正的长图 / 超宽图才需要过裁剪框。

### Story 3.1: Feed 取数扩张 + 图片尺寸列（后端）

As a 前端，
I want 首页接口把滑图、点赞态、评论数一次给全，
So that 我不必为了三个字段各发一轮请求或逐条去查。

**Acceptance Criteria:**

**Given** 首页每条内容目前只下发**一张首图**
**When** 扩张取数
**Then** 下发**整组图片**（多图轮播必需）、**当前用户是否已赞**、**评论数**三项 `[L1]`
**And** 🛡 三项**一律沿用既有批量聚合模式**（一页内容编号凑一批、一次聚合成映射）——**禁逐条查询、禁新增冗余计数列** `[L0]`
**And** 点赞数已在下发，本 story 不重复实现 `[L0]`

**Given** 图片加载时的高度跳动需要提前知道比例
**When** 新增图片尺寸列
**Then** 该列与现有图片列**并排**、**同序等长**，某张缺失时以 `null` 占位保持下标对齐 `[L1]`
**And** 🛡 **等长同序是硬约束**——错位即图文不符 `[L1]`
**And** 🛡 **现有图片列结构不动**：首页首图 / 内容详情 / 时间线 / 宠物名片 / 后台五处读取点**一处都不改**，存量为空、零回填、零迁移 `[L1]`

**Given** 有两个写入端（App 发布 / 后台种子发布）
**When** 写入尺寸
**Then** 🛡 **责任在发布服务的单一入口**，两个调用方**都必须经过它**——否则两条链路会产出格式或缺省行为不同的数据 `[L1]`
**And** App 发布由客户端上报（判容差区间时尺寸已在手）；缺失或明显不合理时由服务端兜底测量；后台种子发布一律走服务端兜底 `[L1]`

**Given** 高度护栏依赖屏幕尺寸、只能在客户端算
**When** 下发图片信息
**Then** 🛡 **服务端只下发原始宽高**，**不得**下发已收敛的比例或已算好的高度（否则客户端再算一遍 = 双重裁切）`[L0]`

### Story 3.2: 通栏容器 + 操作行（点赞与评论）

As a 用户，
I want 在首页就能点赞、并看到有多少条评论，
So that 我不必为了点个赞专门点进详情页。

**Acceptance Criteria:**

**Given** 现状是白底圆角带描边、左右各 16px 屏边距的卡片
**When** 改为通栏式
**Then** 去掉描边 / 圆角 / 屏边距，图片**全宽出血**贴屏幕左右边缘；条目之间改为 **1px 分隔线 + 上下 12px 间距** `[L2]`
**And** 元素顺序为 **作者行 → 图片 → 操作行 → 正文 → 时间**；作者行为 32px 圆头像 + 昵称（13.5px/700）+ 内容类型徽章 + 右侧「···」；正文两行截断 `[L2]`
**And** **保留内容类型徽章**（三类内容需在首页可辨识）；**正文不加作者名前缀** `[L2]`

**Given** 点赞组件已实现未登录门控、乐观更新、后端真值校正、失败回滚
**When** 接进首页操作行
**Then** 🛡 **直接复用该组件，不新写点赞逻辑** `[L0]`
**And** 未点赞为描边心形；已点赞为实心 + 品牌红 `#F0425A`，**数字同步变色** `[L2]`
**And** 未登录点赞触发既有登录引导、不发请求；点赞成功仍触发既有推送；用户对自己内容点赞不通知 `[L1]`

**Given** 评论要跳详情页并定位到评论区
**When** 点击评论按钮
**Then** 跳详情页并滚动定位到评论区（详情页的 `KOMENTAR (n)` 标题行是现成锚点）`[L2]`
**And** 🛡 路由须带一个统一的"定位评论区"参数，**首页侧与详情页侧必须用同一参数名** `[L0]`
**And** **不做首页内联评论** `[L0]`

**Given** 操作行改变了卡片的点击分区
**When** 用户点击卡片各处
**Then** 点赞**就地切换、不跳转**；评论跳详情页定位评论区；**其余区域**（作者行 / 图片 / 正文 / 时间）仍整块点击进详情页顶部 `[L2]`

**Given** 需要判断"开放首页点赞是净增长还是零和"
**When** 上报点赞事件
**Then** 🛡 既有点赞事件新增来源属性（首页 / 详情页），**两侧都必须传**——只改一侧则该对比彻底失效 `[L1]`

**Given** 颜色常量存在命名陷阱
**When** 实现配色
**Then** ⚠️ **`AppColors.mint` 的实际值是品牌紫 `#845EC9`，不是绿色**（早期命名遗留，`mint500/600/700` 全是紫色阶）——**不得按名字猜颜色** `[L0]`

### Story 3.3: 图片渲染三段口径 + 加载期占位

As a 用户，
I want 我竖拍的宠物照片不再被砍掉一半，
So that 我发出去的构图还是我想要的那个构图。

**Acceptance Criteria:**

**Given** 现状首页封面是固定 4:3 裁切、卡片等高（3:4 竖拍被裁 44%）
**When** 改为按比例渲染
**Then** 🛡 **三段顺序不可调换**：① 取图片实际比例 → ② 收敛到 `0.75~1.34` **闭区间**（超出者按最近边界值居中裁切）→ ③ 施加高度护栏 `[L0]`
**And** 🛡 **闭区间含 0.75 与 1.34 两端**——3:4 竖拍恰为 0.75 且最常见，不得留给浮点比较自行决定 `[L0]`
**And** 🛡 **clamp 与护栏一律在客户端施加**（护栏依赖可视区高度）；服务端不参与 `[L0]`

**Given** 通栏出血后竖图会接近占满一屏
**When** 施加高度护栏
**Then** 图片区高度上限 = 可视区高度 − 条目其余部分高度 − 露出余量，**保证下一条内容的顶部总能露出来** `[L2]`
**And** 🛡 **露出余量的最终值须实机复核后定死**，至少覆盖一台小屏机（起点值 56pt 仅为算术推导）`[L2]`
**And** 已知代价：小屏机上 3:4 竖图会被裁约两成——**这削弱了「容差区间内不裁剪」的承诺**，实为"在装得下的屏幕上不裁"；基线仍是改善（现状对 3:4 恒裁 44%）

**Given** 存量内容**永远没有**尺寸数据
**When** 首屏滚动
**Then** 🛡 **必须有占位策略**把加载期的高度变化压到最小——本项为**必做**，不是可选优化 `[L2]`
**And** 存量与新内容走**同一条渲染路径**，不做灰度、不做新老分流 `[L1]`

### Story 3.4: 多图轮播 + 图片区叠加层

As a 用户，
I want 在首页就能左右滑动看完一个帖子的多张图，
So that 我不必为了看第二张图点进详情页。

**Acceptance Criteria:**

**Given** 首页每条内容此前只显示一张图
**When** 帖子含多图
**Then** 图片区可**左右滑动翻图**，圆点叠在**图片区内底边居中**，圆点总数 = 图片数、当前图高亮 `[L2]`
**And** 圆点**同时承担"有几张图"与"当前第几张"两个信息**，不再需要独立的数字角标 `[L2]`
**And** **单图帖不显示圆点、也不响应横向滑动** `[L2]`
**And** 右缘一道极窄暗渐变作为"可横滑"的暗示 `[L2]`

**Given** 手势会互相抢
**When** 用户在图片区操作
**Then** **横向滑动 = 翻图**（不跳转）；**纵向滑动 = 继续滚动列表**（不被轮播吃掉）；**点击 = 进详情页** `[L2]`

**Given** 首页是长列表，滑图时改变高度会推动下方所有内容
**When** 左右滑动
**Then** 🛡 容器高度按**首图**（上传顺序第一张）走完三段口径后锁定，非首图居中裁剪填满，**滑动时高度不变** `[L2]`

**Given** 本版本有三样东西都要叠在图片区上
**When** 实现图片区
**Then** 🛡 **必须交付一个叠加层结构**——现状图片区是裸的固定比例图区、无叠加能力；**三个角位写死**：圆点=底边居中、顶置角标=右上、装饰标签=左下 `[L0]`
**And** 🛡 该结构是 **Epic 4 与 Epic 5 的地基**，它们只往里挂自己那个角位、**不得各自再改图片区结构** `[L0]`

**Given** 每帖可能多张图
**When** 加载图片
**Then** 只预加载当前图与下一张，其余滑到时再加载——避免首屏请求量随多图帖数量线性膨胀 `[L2]`

### Story 3.5: 发布页图片上传裁剪

As a 用户，
I want 只有真正的长图才让我裁，
So that 我随手拍的照片能一路发出去、不被反复打断。

**Acceptance Criteria:**

**Given** 项目现在只有选图能力、**没有任何裁剪库**
**When** 实现裁剪交互
**Then** 引入第三方裁剪库或自研选区交互（属实现选择）——**这是本版本 App 端唯一的新依赖** `[L0]`

**Given** 容差区间为 `0.75~1.34` 闭区间
**When** 用户选择图片
**Then** 比例落在区间内的**直接使用、不弹裁剪框、不做任何裁切** `[L2]`
**And** 超出区间的弹出裁剪框，提供 **1:1 / 4:5 两档预设** `[L2]`
**And** 🛡 **不提供横图预设**——超宽图（如 16:9、全景）只能裁成这两档，属**已知且接受**的结果，不是缺陷 `[L0]`

**Given** 同一批次可能多张图
**When** 第一张触发裁剪的图选定了目标比例
**Then** 该选择锁定为本批次**其余同样需要裁剪的图**的目标比例 `[L2]`
**And** 🛡 **批次内落在容差区间内的图不受锁定影响**，始终保持原比例、不被跟着改成 1:1 或 4:5 `[L2]`
**And** 若批次内全部落在区间内，**全程不出现裁剪框**，也不涉及比例锁定 `[L2]`

**Given** 右上角按平台惯例是前进 / 确认位
**When** 渲染裁剪页
**Then** 退出按钮为**左上角 ✕**，前进动作（应用裁剪 / 继续）由**底部主按钮**承担 `[L2]`

**Given** 需要验证容差区间取值是否正确
**When** 弹出裁剪框
**Then** 上报事件并带上**图片原始比例数值**与批次大小 `[L1]`
**And** 该分布是**判断 0.75~1.34 取值是否合适的唯一依据**——理想结果是这个事件本身量很小 `[L1]`

## Epic 4: 内容顶置坑位

运营能把活动、功能上新或官方话题顶到首页顶部，按排期自动上下线；被顶置的内容在首屏不会与列表里的自己重复出现。

> ⚠️ **可用性依赖后台 AB-10A**：不上线则运营无处配置、App 端为空壳。代码上本 Epic 仍独立完整。

### Story 4.1: 顶置配置数据模型 + 时间窗判定

As a 工程，
I want 有一套坑位配置模型与一份到点自动生效失效的判定，
So that 后台配置界面接上来之后，运营配的排期能自动上下线、不必守着时间手动操作。

> ⚠️ **本条本轮没有可观测的用户价值**——后台配置界面（AB-10A）不在本轮范围，运营还无处配置。它交付的是**机制**：数据模型 + 时间窗判定 + 下架事件联动。如实标注，不假装它是一条面向运营的可用功能。

**Acceptance Criteria:**

**Given** 本版本只有首页一个坑位，但后续版本要接话题页坑位
**When** 设计数据模型
**Then** 🛡 **坑位维度必须是配置项，不得把首页写死**——新增坑位时只需增加坑位记录、不需重构界面与数据结构 `[L1]`
**And** 🛡 这是**下游版本的前置**：话题页坑位直接复用本机制，写死即导致下游重构 `[L0]`

**Given** 三处功能（顶置 / 用户标签 / 装饰标签）都要"到点自动生效失效"
**When** 实现生效判定
**Then** 🛡 **一律查询时按时间窗判定**（生效中 = 当前时刻落在 `[开始, 结束)` 内），**不落状态列、不建定时扫描器** `[L1]`
**And** 🛡 **该判定必须只有一份实现，由四处共用**：顶置取数、用户标签取数、装饰标签取数、**以及后台列表展示的「待生效 / 生效中 / 已结束」** `[L0]`
**And** 若各写一遍，左闭右开的边界会在某处被写成全闭，出现「App 上已失效、后台还显示生效中」`[L1]`

**Given** 运营配置的时间按印尼西部时间理解
**When** 保存配置
**Then** 入库转为 UTC 绝对时刻，上下线按该绝对时刻执行，**不按客户端本地时区二次换算** `[L1]`
**And** 已接受的影响：一条配置对三个时区的用户是三个当地时刻，**本版本不做分区上线** `[L0]`

**Given** 同一坑位不能同时有两条生效配置
**When** 提交重叠时间窗
**Then** 校验拦截并提示调整 `[L1]`

**Given** 顶置的内容可能在生效期间被下架
**When** 内容被作者删除 / 审核判违规下架 / 作者账号被封禁
**Then** 🛡 **订阅下架事件即时结束该顶置配置**（视为提前到达结束时间），坑位回退为普通内容填充，不需要运营手动摘除 `[L1]`
**And** 🛡 该副作用**走事件订阅，不靠定时扫描器** `[L0]`

### Story 4.2: 首页坑位渲染 + 只首屏让位

As a 用户，
I want 首页顶部那条运营内容看起来跟普通内容一样自然，
So that 我不觉得被硬塞了广告。

**Acceptance Criteria:**

**Given** 顶置条目与普通条目完全同构
**When** 渲染坑位
**Then** 除了多一个顶置角标，其余部分（作者行 / 图片 / 操作行 / 正文 / 时间）与普通条目完全一致 `[L2]`
**And** 顶置角标固定在**图片区内右上角**，挂在 Story 3.4 交付的叠加层上 `[L2]`
**And** 多图的顶置帖**同样适用轮播规则**（可左右滑、有圆点、高度按首图锁定）`[L2]`

**Given** 同一条内容可能既在坑位又在算法序列里
**When** 取首页第一页
**Then** 🛡 被顶置的内容**仅从第一页排除**，后续页仍可正常出现 `[L1]`
**And** 🛡 **排除后须补足页大小**（继续向后取一条），不得让第一页少一条——页大小抖动会影响"还有更多"的判断 `[L1]`
**And** 推广卡片无内容编号，不涉及排除 `[L1]`

**Given** 坑位不该拖累首页
**When** 顶置取数失败
**Then** 🛡 **不得连带整个首页失败**，降级为坑位不展示 `[L1]`
**And** 坑位走**独立取数**，首页的游标分页逻辑不因顶置改变形态 `[L0]`

**Given** 当前无生效配置
**When** 渲染首页
**Then** 坑位不展示、该位置由普通内容按正常排序填充，不留空白占位 `[L2]`

**Given** 下游版本要用这批数据做决策
**When** 上报坑位埋点
**Then** 上报**曝光**（带坑位配置标识、顶置类型、内容编号）与**点击**（带跳转目标类型）`[L1]`
**And** 🛡 **重复曝光事件必须如期交付**——它是**下游版本判断"要不要为顶置做去重"的唯一数据来源**，须带该内容在算法序列里的位次 `[L1]`

### Story 4.3: 推广卡片（不对应真实帖子）

As a 运营，
I want 不依赖任何真实帖子就能在首页顶部放一张引导卡，

**Acceptance Criteria:**

**Given** 推广卡片不对应任何真实帖子
**When** 运营配置
**Then** 字段为：图片（必填）、标题（必填）、跳转目标（二选一：外部链接 / App 内部深链）`[L1]`
**And** 深链**复用既有深链设施**，不新建深链体系 `[L1]`

**Given** 本版本按"平台自有活动引导"定位使用
**When** 渲染推广卡片
**Then** 🛡 **不加"广告 / 推广"角标**，与顶置的已发布内容视觉一致 `[L2]`
**And** ⚠️ 若未来该坑位开始承接第三方付费投放，须重新评估应用商店的广告披露政策——**不是本版本的阻塞项**，但记为商业化前的前置检查

**Given** 推广卡片在坑位里渲染的就是一张普通内容卡片
**When** 图片比例超出容差区间
**Then** 同样被收敛到 `0.75~1.34` 并居中裁切 `[L2]`
**And** 运营做素材时即应按该区间出图（否则 16:9 banner 进首页会被左右各裁约 25%）

### Story 4.4: 顶置坑位套用拉黑过滤（延后执行）

As a 拉黑了某个账号的用户，
I want 首页顶部不要再给我看这个账号的内容，
So that 拉黑不会在最显眼的位置失效。

> 🔴 **本 story 延后执行**：依赖并行版本的「用户拉黑」上线。**开工前置检查**：确认拉黑表与「按查看者隐藏」过滤层已上线。**不阻塞本 Epic 其余三条 story。**

**Acceptance Criteria:**

**Given** 顶置位是首屏第一条、比列表里任何位置都刺眼
**When** 顶置内容的作者已被当前查看者拉黑
**Then** 对**该查看者**视为坑位为空，按「坑位为空」规则回退为普通内容填充 `[L1]`
**And** 🛡 **不为该用户单独挑替补顶置内容**，其他用户的顶置展示**不受影响** `[L1]`

**Given** 拉黑过滤是通用规则、不是本功能新增机制
**When** 实现过滤
**Then** 🛡 **直接复用已建的「按查看者隐藏」过滤层**，**不新写过滤逻辑** `[L0]`
**And** ⚠️ 该层是**两条并列、刻意不合并**的子查询（V1.1.4 AD-9）：举报维度藏**一条帖**、账号维度藏**一个人**（查 `user_hide_relations`）——语义不同，**不要误当成一条**；本 story 套**账号维度**那条 `[L1]`

**And** 🛡 判定须留在 **SQL WHERE 内**、命中 `idx_user_hide_relations_holder_target`（holder 前导）；**不得挪到 Java 侧 filter**——会破坏分页与游标契约 `[L0]`
**And** 沿用该层既有的"是否登录"门控口径：**游客不过滤** `[L1]`

**Given** V1.1.4 的拉黑代码已完成但尚未合入 `main`（2026-08-16 复核）
**When** 执行本 story
**Then** 先确认拉黑过滤已随 V1.1.4 上线 `[L1]`
**And** 若最终 V1.1.4 发版晚于本版本，回头重估：本版本自建过滤 / 暂不做并记为已知缺陷（**产品决策，不由工程自行选择**）

## Epic 5: 运营标签体系（用户标签 + 内容装饰标签）

被运营认定的优质用户在四处露出身份标签、优质内容在三处露出荣誉标签，点一下能看到这个标签是什么意思。

> ⚠️ **可用性依赖后台 AB-12A 与 AB-10C。**

## Epic 6: 里程碑通知补齐

由别人互动触发的里程碑达成（「第一次被评论」「第一次收到点赞」）不再悄悄发生——本人不在现场也能在通知中心看到，且铃铛的红点会提醒他。

> **全版本最小的一条，零依赖，可立刻开工。**

### Story 6.1: S/M 级里程碑写入通知中心

As a 宠物主，
I want 别人给我点赞评论触发的里程碑达成也能告诉我，
So that 我不用自己回头翻列表才发现已经达成了。

**Acceptance Criteria:**

**Given** 现在只有一种里程碑通知类型（L 级在用，含系统推送）
**When** S/M 级里程碑完成
**Then** 新增一种通知类型：**写通知中心记录、不发系统推送** `[L1]`
**And** L 级维持现状不变（推送 + 通知中心两者都有）`[L1]`
**And** 文案复用现有的里程碑庆祝文案 `[L1]`

**Given** 铃铛角标的数字由 Redis 计数器维护、**不是查库算出来的**
**When** 写入 S/M 通知记录
**Then** 🛡 **必须同步让该未读计数器递增**——否则通知进了中心、角标不动，本 FR 的核心诉求（让本人不在场时也能被告知）**直接落空** `[L1]`
**And** 计数为 0 时隐藏角标、大于 99 显示 `99+`（沿用现状）`[L2]`

**Given** 用户点击该通知
**When** 跳转
**Then** 落**成长档案 → 里程碑列表页**，与 L 级一致、不做差异化 `[L2]`

**Given** 同一个操作可能一次解锁多个里程碑
**When** 写通知
**Then** 🛡 **写 N 条，每个达成的里程碑各一条** `[L1]`
**And** 🛡 **每条必须写明该里程碑的具体名称**（取庆祝文案中对应目录码的具体文案）——**不得使用「你完成了一个里程碑」这类看不出是哪一条的泛化文案** `[L1]`
**And** 庆祝弹层仍按既定只弹一次，两者不冲突（庆祝是即时反馈需防连弹；通知中心是留痕台账、漏记即查不到）`[L2]`

**Given** 老用户可能已完成十余条 S/M 里程碑
**When** 本版本上线
**Then** 🛡 **存量已完成的不回填**，仅对上线后新完成者生效——否则升级后通知中心一次性涌入大量历史记录、未读数字异常，观感等同故障 `[L1]`

**Given** 需要判断 S/M 通知是留痕还是召回
**When** 点击通知列表条目
**Then** 上报事件并带上通知类型（可与 L 级、点赞 / 评论类横向对比点击率）`[L1]`

## Epic 7: 手机号采集

> 🔴 **上线前阻塞 OA-2**：须确认用户协议已覆盖「手机号用于运营召回与后续触达」，否则**先补条款再上线**。

### Story 7.1: 手机号字段与保存 / 清空

As a 用户，
I want 能填手机号、也能随时清掉，

**When** 执行本 story 的迁移

**Given** 手机号是选填、且不做验证
**When** 保存
**Then** 仅做印尼手机号的**基础格式校验**；**不做验证码验证、不用于登录** `[L1]`
**And** 保存成功展示「保存成功」提示；格式校验不通过展示「保存失败，请检查手机号格式」`[L2]`

**And** 清空同样展示成功提示；**不触发任何二次确认** `[L2]`
**And** 清空后该用户在后台的筛选中回到「未填写」分组、可再次被纳入催填范围 `[L1]`

## Epic 8: 推送权限重构

关掉通知的用户在四个不同时刻各有一次机会被引导去系统设置开启；兽医每次上线时若通知关着都会被提醒，不至于收不到派单。

> **订正后本 Epic 实际做的事**：在四个时刻把关着通知的人**引去系统设置页**（不存在唤起原生弹窗这一分支）。

### Story 8.2: 用户侧三触发点 + 通知中心引导条

As a 关掉了通知的用户，

**Given** 原生弹窗机会在首启即被消耗
**When** 任一触发点触发

**Given** 旧门控与首启申请共用同一个标记键、已成死代码
**When** 实现触发点 1 / 2 的时机
**Then** 🔴 **须新建"是否刚完成首次问诊 / 建档"的时机追踪**，**不得复用旧门控** `[L0]`
**And** ⚠️ 这是本 story 工量的主要来源，且容易出错——触发点「打开通知中心」的时机是现成可判的 `[L0]`

**When** 用户换设备或重装
**Then** 计数重置、在新设备上重新获得这三次机会（判断依据"系统通知开关"本身就是设备级状态）`[L2]`

**Given** 平台不剥夺兽医的接单资格
**When** 兽医选择忽略提示
**Then** 🛡 **不做硬拦截**——仍可切为在线，可靠 App 前台停留自行盯单 `[L2]`

**Given** 该触发点允许同一用户重复上报
**When** 配置告警
**Then** 🛡 兽医端触发点**允许重复出现多条**（不受"各一次"限制），其余触发点每设备每用户最多一条 `[L1]`

**Given** 兽医端此前全流程零埋点
**When** 本 story 上线
**Then** 这将是**兽医端首次产生埋点数据**；其余兽医流程仍是黑盒（已知缺口，本版本不解决）`[L0]`

## Epic 9: 单条内容分享卡

用户能把某一条内容变成一张图分享到 WhatsApp / Instagram Stories，看到图的人扫码就能回到**那条内容**；访客只能看被分享的这一条，进不去这只宠物的其它记录。

### Story 9.1: 卡片生成基建（双尺寸 + 水印 + 文字排版）

As a 后续版本的开发者，
I want 这套出图能力是通用的，
So that 我做别的分享卡时不用从头再写一遍。

**Acceptance Criteria:**

**Given** 宠物身份证已有完整的客户端出图链路
**When** 搭建卡片生成基建
**Then** 🛡 **客户端生成**，复用身份证既有做法；**服务端那套社交预览出图能力不挪用**（尺寸、用途、水印策略都不同）`[L0]`
**And** 可直接照抄的三处：**按目标画布宽度反算截图倍率**、**白底合成防黑角**、**水印挂在截图区域的兄弟节点上**（故预览与用户手动截屏带水印、高清导出不带）`[L0]`

**Given** 本基建是后续版本的前置
**When** 设计接口
**Then** 🛡 **文字排版 / 水印 / 双尺寸输出须作为通用能力设计**，**不得写死成只服务本 FR 的一次性实现** `[L0]`
**And** 支持 **9:16（Stories）与 1:1（Feed）双尺寸**，不新增其他尺寸 `[L2]`

**Given** 生成耗时会影响体验、且后续功能会复用它
**When** 卡片生成成功
**Then** 上报事件并带上**生成耗时**——性能问题现在暴露比复用后暴露便宜得多 `[L1]`

### Story 9.2: 有图 / 纯文字两套模板 + 下载二维码

As a 用户，
I want 不管我发的是照片还是纯文字都能生成好看的卡片，
So that 我不会因为没配图就分享不出去。

**Acceptance Criteria:**

**Given** 内容可能有图也可能没图
**When** 生成卡片
**Then** 有图用图片模板（含首图 / 正文摘要 / 作者昵称与头像 / 品牌水印）；**无图用纯文字模板**（不放图片区、文字排版占满主体，仍保留作者信息与水印）`[L2]`

**Given** 卡片导出到 Stories 后观看者**无法点击**
**When** 渲染页脚
**Then** 页脚左侧品牌 logo + 引导文案、右侧下载二维码 `[L2]`
**And** 🛡 **码内容 = 该条内容的分享链接**，**不是通用下载页**——否则扫码进来的人看不到他实际看到的那条内容，漏斗断在这里 `[L1]`
**And** 🛡 **必须留安静区**：码四周留白**不小于 4 个码元宽度** `[L2]`
**And** 🛡 **按导出分辨率算边长**（不可按预览尺寸的像素直接输出），否则隔着屏幕拍照扫不动 `[L2]`
**And** 🛡 **纯文字模板必须有白色底板**——其背景是紫色渐变，码直接压上会降低识别率 `[L2]`

**Given** logo 已经承载品牌名
**When** 写页脚引导文案
**Then** **文案不重复品牌名**（写「扫码下载」而非「下载 TailTopia」）`[L2]`

**Given** 二维码占了页脚近一半版面
**When** 上报链接被打开事件
**Then** 须带**打开方式**（点链接 / 扫码）——这是**该元素的唯一验收依据**，若扫码占比长期极低则该元素可在后续版本撤掉 `[L1]`

### Story 9.3: 分享入口与链接落地分流

As a 用户，
I want 在内容详情页一键把这条内容分享出去，
So that 我能把喜欢的内容发给朋友。

**Acceptance Criteria:**

**Given** 详情页顶栏现有的「···」是举报 / 删除入口（合规入口，不能变难找）
**When** 加入分享入口
**Then** 🛡 **分享放进详情页的底部互动区**（现状那一行是 点赞 + 评论，加第三个），**顶栏保持现状不动** `[L2]`
**And** ⚠️ **视觉稿 SH1 画的是顶栏分享、把「···」画没了，需重画或加订正标注**——否则工程照稿实现会把举报入口做掉 `[L0]`

**Given** 三类内容都支持
**When** 用户点分享
**Then** Diary / Moment / Tips 均可，**含作者关闭同步的私密 Diary**（用户主动分享属授权行为）`[L2]`
**And** 通过系统分享菜单调起（沿用既有调起方式），菜单里含「生成图片卡」入口 `[L2]`

**Given** 分享链接会被各种人打开
**When** 访问者打开链接
**Then** 未安装 / 未登录 → 静态图片 + 下载引导；已登录**作者本人** → 自己的内容详情页、保留管理入口；已登录**非作者** → 该内容详情页只读态（不展示编辑 / 删除）`[L2]`

**Given** 分享一条内容 ≠ 授权浏览整只宠物
**When** 访客通过该链接进入
**Then** 🛡 **严格只能访问被分享的那一条**，**不得由此进入该宠物的 Diary 时间线或任何其它内容**（无论公开还是私密）`[L1]`
**And** 🛡 **与宠物主页分享必须是不同的链接类型 + 不同的落地页**，**不可复用同一深链目标**——若落到宠物档案页，会把该宠物名下所有私密日记暴露给任何拿到链接的人 `[L0]`

**Given** 需要评估这个拉新入口成不成立
**When** 用户点分享 / 卡片生成 / 分享完成 / 链接被打开
**Then** 各上报一个事件；点分享时带内容类型、**是否为私密 Diary**、有无配图 `[L1]`
**And** 私密 Diary 占比若长期接近 0，说明"支持私密 Diary 分享"这个分支实际无人使用 `[L1]`

## Epic 10: 埋点收尾（App 侧）

产品能回答"这一版这些改动到底起没起作用"。

### Story 10.1: App 侧剩余埋点 + 回写全局文档

As a 产品，
I want 这一版的观测口径齐全且不与既有文档分叉，
So that 我看数时不会被两套口径搞混。

**Acceptance Criteria:**

**Given** 三条决策性埋点已随各自 Epic 交付
**When** 本 story 开工
**Then** 只补剩余的机械项（顶置曝光点击、手机号、图片裁剪、标签 tooltip、通知类等），**不重复实现已交付的** `[L0]`

**Given** 命名须成体系
**When** 命名新事件
**Then** 沿用 `模块_对象_动作`（**动作在词尾**），使用本版本既定的模块前缀 `[L0]`
**And** ⚠️ **事件名以工程实现为准，但加粗的属性字段不可省略**——缺一项对应结论就做不出来，且**事后补埋点补不回已流失的数据** `[L0]`

**Given** 有两条"实现违背规格"型的护栏可配告警
**When** 配置告警
**Then** 🛡 **护栏一（订正后）**：任何触发点上报「原生弹窗」形态即违规 `[L1]`
**And** 🛡 **护栏二**：除兽医端外，同一设备同一用户出现多条权限提示曝光即标记位实现有误 `[L1]`

**Given** 服务端埋点靠一个密钥开关
**When** 部署到生产
**Then** 🛡 **服务端埋点密钥必须配置**——留空即**整个服务端上报关闭**，Epic 1 的 H5 埋点会一条数据都没有 `[L1]`

**Given** 两处口径分叉会长期误导
**When** 本版本埋点定稿
**Then** 回写并入仓库的埋点文档（新增一节）`[L0]`
**And** ⚠️ 回写**一律以仓库版为准**（工作区曾长期存在过期副本）`[L0]`

**Given** 有五项已知缺口本版本不解决
**When** 交付
**Then** 明确**不承诺**：未装用户的「安装 → 打开 → 注册」归因（缺深链归因基建）· 兽医端除本次触发点外的全流程 · 环境隔离（预发与生产共用同一 project token，须在打包时用构建参数覆盖）· **后台侧运营操作全无埋点**（配了什么、给谁打了标、何时催填过，均无法回溯）`[L0]`
