## 1. AB-18A：一次性解锁定价

### 1.1 代码现状基线（2026-09-29 核验，工程按此基线开发）

**⚠️ 本条目的三行配置已随 V1.3.0 上线至 `main`，不是待开发状态。** 线上现有：

- 运营配置页内的配置卡「**KTP 模块高清图解锁定价**」三行（KTP 卡高清下载 / 护照·护照内页 / 护照·登机牌），端点 `POST /admin/config/ktp-pricing`
- `pricing_config` 三列：`id_hd_download_price` / `passport_page_unlock_price` / `passport_boarding_unlock_price`，三条 CHECK 均为 `>= 1`
- App 端契约 `GET /me/id-cards/pricing` 已返回三个价（`price` / `passportPageUnlockPrice` / `passportBoardingUnlockPrice`）——**客户端尚无消费方，当前为死字段**

因此本条目的工作性质是「**在已上线的三行上扩充**」，不是从零建设。

**⚠️ 生产现值未知，上线前必须核实。** 护照两列的初始值取自迁移执行当时的 KTP 价，之后从未被消费方使用过，也不会随 KTP 改价联动（四行各自独立）。上线前跑：

```sql
SELECT id_hd_download_price, passport_page_unlock_price, passport_boarding_unlock_price
FROM pricing_config WHERE id = 1;
```

### 1.2 本版本的四个解锁项与定价

| 行 | 对应 App 端 FR | 目标售价 | 计价语义 |
|---|---|---|---|
| KTP 卡高清下载 | 既有 | **Rp1,000** | 每张卡，一次性永久 |
| 护照 · 护照内页（快照） | FR-120 | **Rp2,000** | **每次快照解锁**——买的是「当前这一版」，之后盖了新章想要含新章的版本需再买一次 |
| 护照 · 登机牌（每张） | FR-120 | **Rp1,000** | **每张**（宠物 × 场所各一张），一次性永久 |
| Tailsonality · 结果解锁 | FR-117 | **Rp5,000** | 每次测试结果，一次性永久 |

> **⚠️ 改价约束：护照内页（快照）的价格必须 ≥ 登机牌（单张）的价格。** 快照含当前全部章，单张登机牌只含一个地点；快照定得比单张便宜，用户一次买快照就拿到所有章的无水印图，登机牌这个 SKU 会彻底卖不动。**后台不做强校验，靠运营知道**——这条写进运营说明。

> **⚠️ 行标签与说明文案必须体现计价语义。** 「护照 · 登机牌」要写成「**护照 · 登机牌（每张）**」并附一句说明；「护照 · 护照内页」要能读出「每次快照」。否则运营会按「一次买断整本」的旧理解定价，那是完全不同的收入模型与心理价位。

### 1.3 页面位置与流程

既有**运营配置页**内的配置卡扩充，**不新增页面、不新增菜单项**：

- **组名改为「一次性解锁定价」**（原「KTP 模块高清图解锁定价」，纳入 Tailsonality 后名不副实，运营按组名找不到它）。组说明加一句「本组管理全部一次性付费解锁项的售价」。**只动展示文案与三语 message 值，不动配置 key、不动权限、不动数据**
- 卡内由三行扩为**四行**：KTP 卡高清下载 + 护照内页 + 护照登机牌 + Tailsonality 结果解锁
- 每行样式名只读 + 价格输入；沿用现状每卡自带保存钮（未修改禁用 → 修改激活并标「已修改」→ 高危确认弹层复述新旧值 → 提交）
- **金额输入带 `Rp` 前缀、数字右对齐并使用等宽数字**（2026-10-02 UI 阶段定）。既有实现是裸数字输入框，四行并列时 1,000 与 10,000 要逐位数才分得清；右对齐 + 等宽数字让位数差异一眼可见，这正是改价最容易出错的地方
- **校验错误提示紧贴出错的那一行**，不放在卡片底部；错误须可被读屏播报，不能只靠红色描边
- 确认提交后保存按钮进 loading 并禁用，防重复提交（后台写操作走审计链，重复提交会多写一条审计记录）

### 1.4 规则

- **四行各自独立配置、互不联动**——改任一行不影响其他行
- **价格校验：整数（IDR），下限 100**。低于 100 一律为非法值（含 0），行内报错、保存禁用、不弹确认层
- **⚠️ 本版本把下限由 1 收紧为 100，四列的 DB CHECK 须随迁移一并改为 `>= 100`。** Rp1～Rp99 这个区间没有任何实际售价会落进去，却能让运营手滑漏个零就把 Rp2,000 配成 Rp200；下限抬到 100 是最便宜的防手滑。上限维持既有值不变
- 加 CHECK 前须确认既有三行现值均 ≥100（见 §1.1 的核实 SQL）；新增的 Tailsonality 列初始值 5000，天然满足
- 改价即时生效，只影响**新发起**的解锁购买；已解锁用户不受任何影响
- **登机牌行的价格是单张价**，改价只影响此后新发起的单张解锁；用户已解锁的场所卡不受影响，也不会因改价需要补差价
- **护照内页行的价格是单次快照价**，已购快照永久有效、不因改价失效
- 成交价以**购买记录中的历史值**为准，改价不得回溯影响已产生的订单与对账
- 新增解锁项上架时由工程随发版在配置卡内加行（解锁项本身为发版内容，后台只管价格）
- 所有改价操作经统一审计入口落审计日志
- 权限：沿用既有定价配置项的 permission_code（`config.view` / `config.edit`），不新增

### 1.5 新增支付用途（`PaymentPurpose`）

**本版本三个新解锁点各自新增一个 purpose 值**，不复用 `ID_HD`（快照的代号为 `PASSPORT_SNAP`——已随 Story 3.1 落进代码、DB CHECK 与 `keepsake_purchases.sku`，2026-10-02 定不改名）：

| 解锁项 | purpose 值 |
|---|---|
| 护照 · 护照内页（快照） | `PASSPORT_SNAP` |
| 护照 · 登机牌 | `BOARDING_PASS` |
| Tailsonality · 结果解锁 | `TAILSONALITY` |

**为什么不复用 `ID_HD`：** 复用则四个 SKU 在后台支付记录里混成一堆，没有任何字段能区分——金额是运营可改的，改完历史单子再也拆不出来。且登机牌是「宠物 × 场所」粒度，单量会把 `ID_HD` 这个用途灌满，KTP 的数据被淹掉。**这个决定具有单向性**：现在定是几行代码，上线后想拆则历史单的 purpose 已全是 `ID_HD`，回填不出来。

规则：

- 枚举**只在末尾追加**（既有并行契约纪律），同步 `payment_intents` 的 CHECK 约束
- 后台**支付记录页**（`/admin/payments`）的「用途」筛选项同步扩充，含三语文案；导出 xlsx 的用途列随之覆盖
- **⚠️ 摘要条新增「付费用户数」**（2026-10-02 定）。现状摘要三格只有**笔数**口径（本期支付笔数 / 成功金额 / 未成交笔数），看不出这些笔数来自多少人——10 笔可能是 10 个人各买一次，也可能是 1 个人买了 10 次，对判断新 SKU 卖得好不好是完全不同的结论。新增一格「付费用户数」，与其余三格同样**随当前筛选条件实时变化**（筛了「护照快照」就是买过快照的去重人数）。
  - 口径：当前筛选条件下 `status = 'PAID'` 的**去重 `user_id` 数**。未成交的单不计；同一用户在区间内多次付费只算 1 人
  - **⚠️ 口径提示必须常驻展示**：本页数据源是 `payment_intents`，**用 PawCoin 余额购买的解锁不建支付单、不在本表内**。因此这个数是「**现金付费用户数**」，不是该 SKU 的全部付费人数。不写明的话运营会拿它当总付费人数用，低估新 SKU 的真实转化
  - 与首页看板「付费人数·现金到账」同源同口径（都是 `payment_intents` PAID 去重用户），差别只在时间维度：看板按自然日、本页按筛选区间
- 用途筛选项中，**本版本新增的三项与既有五项之间以分隔线分组**，便于运营辨认哪些是新解锁点
- 页面底部常驻一句指路：**要查某个用户到底买过什么（含 PawCoin 付的），到「用户 → 已购解锁」页签**。不指路的话运营会把「本表查不到」当成「这人没买过」
- **状态筛选维持单选不变**（2026-10-02 定）。同一排控件会出现「用途可多选、状态单选」的不一致，这是明确接受的取舍，不是遗漏——状态只有四个值且运营几乎总是看「已支付」或不限，多选收益不足以抵消改动成本
- **⚠️ 用途筛选由单选改为多选**（2026-09-30 定）。现状是单值下拉（一次只能看一个用途或全部），四个解锁 SKU 并存后，运营的常见诉求是「把三个新解锁点合起来看一眼这周卖了多少」，单选做不到、只能查三次再手工相加。改动范围：筛选控件改多选；`purpose` 由单值参数改为多值并以 `IN (...)` 查询；**分页链接、整表刷新、导出 xlsx 三处都要带上完整的多值参数**（这三处现在都在透传单个 `purpose`，漏改任何一处都会在翻页或导出时静默丢掉筛选条件）；未选 = 不限，等价于现状的「全部用途」
- 新 purpose 仅用于 QRIS 通路；PawCoin 通路不建 payment_intent，其可见性由 §3 承载

### 1.6 首页看板付费口径同步（AB-15A 变更）

**必须与本条目同版本实现，否则看板会显示自相矛盾的数据。**

现状：看板两个付费口径的实现方式不同——

- 「现金到账」（#15/#16）查 `payment_intents.status='PAID'`，**不筛 purpose**，新 SKU 会自动被计入
- 「含 PawCoin 消费」（#17/#18）是一个 `spend_events` CTE，**逐张业务表白名单式列举**（问诊 / AI 解锁 / KTP 的 PawCoin 行 / `purpose='ID_HD'` 的支付单 / 充值），三个新 SKU 一个都捞不到

不改则出现 **「付费人数·含 PawCoin」< 「付费人数·现金到账」**——而口径②本应恒 ≥ 口径①（它多算了「先充值、今天用余额买」的人）。看板上两条线长期交叉，且本版本核心指标「结果解锁转化率」中用余额付费的那部分等于不存在。

**本版本改动：** `spend_events` CTE 为三个新 SKU 加一段：三类解锁共用的购买记录表 `keepsake_purchases` 中已到账（`PAID` / `DUPLICATE_PAID` / `ORPHAN_PAID`）的行，按 `paid_at` 计。该表同时记 QRIS 与 PawCoin 两个渠道，**不再**从 `payment_intents` 按三个新 purpose 再取一遍——否则 QRIS 成交会被数两次（「付费次数」按事件计数时就错了）。（2026-10-02 按已上线代码订正；效果等同原写法的「两段」去重后的结果。）

- **口径文档同步（硬要求）：** AB-15A 规定指标口径以 `../3.数据埋点/数据查询/内容运营所需数据.sql` 为权威定义，两处走散即失效。本次改口径**必须同步改那份 SQL**，验收沿用「看板数字与直跑 SQL 完全一致」这条
- **本版本不做**按 SKU 拆分的看板视图（§4）

> **📌 通用规则（本版本新立，后续版本沿用）：新增任何付费点时，必须同步登记进看板付费口径与那份取数 SQL。** 「含 PawCoin」口径是白名单式的，每加一个付费场景都必须有人回来改它，否则该笔收入静默消失。

### 1.7 上线前价格订正（运营手改，非迁移）

**四行的目标价由运营在后台手改，不写进迁移**，但两条例外与两条纪律：

- **例外①：Tailsonality 是新增列且 NOT NULL，初始值必须在迁移里给**——**显式写死 5000**，不得照抄 KTP 价
- **例外②：** 其余三行的存量值不被迁移触碰
- **纪律①：改价动作排在发版动作之前。** 那三行当前没有消费方，提前多久改都无害；而上线时点由商店审核与用户更新决定，无法精确对齐「当天」。正确顺序是 **后台改价 → 确认改完 → 再提交发版**
- **纪律②：** 没有任何校验会拦住错误值——`Rp100 ≥ Rp100` 照样满足「快照 ≥ 单张」，配置页不会有任何提示。**必须先跑 §1.1 那条 SQL 确认现值**，再逐行改

上线前检查项见 §5。

## 2. AB-18B：场所专属章素材管理（FR-120）

### 2.1 页面位置与流程

落在既有**场所管理**（`/admin/places`）的**场所详情抽屉**内，新增一个「专属章」区，与照片墙、评论区并列。**不新增页面、不新增菜单项、不做独立素材库**——章是场所的属性，一个场所一枚，没有复用场景。

**章的上传 / 替换 / 移除各自是一个独立动作**，点击后立刻生效并局部刷新抽屉体，与既有的照片删除、下架恢复同构；**不并入编辑表单**（既有编辑表单是抽屉内折叠展开的纯文本 htmx 表单，不是 multipart，并入会让它背上文件上传，上传失败时整张表单要回填重画）。

**上传失败的报错显示在后台统一的行内错误位**，不在章区块内另设错误槽（2026-10-02 定，待确认汇总 1.5「保持现状」；UI 稿 C4 的章内报错版式不采用）。报错文案须写明具体哪一项不合格及实测值（如「须为 512×512，当前 600×400」）。

### 2.2 运营能做什么

- 为该场所上传一枚专属章素材；已上传时显示当前章的预览 + 「替换」「移除」，以及**最近一次上传的时间与上传人**（如「09-30 15:12 由 Hex 上传」；`places` 表新增 `stamp_uploaded_at` / `stamp_uploaded_by` 两列，上传 / 替换时写入、移除时清空。2026-10-02 前上传的存量章无此两项，不显示该行）
- **「移除」须二次确认**——移除会让该场所**已经盖出去的章**一并回落默认章，影响面不止于新打卡，沿用后台既有 `data-confirm` 模式
- 移除后该场所回落到**按类型的默认章**

### 2.3 默认章素材

- **7 款默认章（咖啡店 / 餐厅 / 公园 / 商场 / 酒店民宿 / 宠物服务 / 其他）由客户端内置**，随 App 发版，**后台不管理、不可配置**
- 未上传专属章即走内置兜底，客户端无需请求任何素材——纵览页一屏要画几十枚章，本地资源比网络请求稳
- **📌 规则：以后新增场所类型，必须同时补一张默认章并随 App 发版。** 场所类型是一个有 CHECK 约束的固定值域（现为 7 值），类型与默认章一一对应；只加类型不补章，该类型下的场所会掉进没有兜底的状态

### 2.4 规则

- **未上传即走兜底，不是错误态。** 绝大多数场所会一直用默认章；抽屉不得把「没传专属章」标成警告或阻断保存
- **换章对已盖出的章生效。** 章是场所的属性而非打卡快照——同一场所的用户看到的是同一枚章，换了就都换。这条写进运营说明，避免运营以为只影响新打卡
- 场所合并时：保留方的专属章生效，被合并方的素材随场所一并归档
- 场所下架时：章素材**保留**（已盖的章要继续显示）
- 权限：沿用既有 `place.manage`，不新增
- 审计：新增 `PLACE_STAMP_UPLOADED` / `PLACE_STAMP_REMOVED`（`AuditActions` 内 `PLACE_*` 系列命名同构），经统一审计入口落库

### 2.5 素材规格

## 3. AB-23：已购解锁查询（用户详情抽屉新增页签）

**背景：** 后台现在**没有任何地方能回答「这个用户买过什么」**。用户详情只有基本信息 / 宠物档案 / 发布内容 / 历史问诊 / 处置五个页签，钱相关的信息只有一个 PawCoin 余额数字；支付记录页查的是 `payment_intents`，而 **PawCoin 付的那条路根本不建 payment_intent**——用 PawCoin 买 KTP 高清图的用户在整个后台不留任何可查痕迹。

KTP 单 SKU 时这个缺口尚可忍受。本版本后变成四个 SKU，其中**护照快照是全 App 唯一会重复收费的 SKU**，「我买过怎么又要付钱」是必然到来的客诉，而客服现在一条信息都查不到。

**页面位置与流程：** 「用户运营 → 用户」列表点行拉出的既有**用户详情抽屉**（480px，整页详情已退役），在现有五个页签之后**新增第六个页签「已购解锁」**，只读列表。沿用该抽屉既有的「五页签一次性渲染、切页签不再请求」模式——本页签的数据随同一次详情聚合查出，切过去不发新请求。**不新增页面、不新增菜单项。**

> **⚠️ 本条目须把用户详情抽屉由 480px 加宽至 600px。** 2026-10-02 UI 阶段实测：六个页签在 **三种语言下全部溢出** 480px 抽屉（中文约 489px / English 约 472px / Bahasa Indonesia 约 500px，而内容区可用仅约 440px），页签条为 nowrap，溢出即折行——源码注释已写明「换行会把抽屉顶出两行」。
>
> 处置为**加宽抽屉**，不采用缩短文案（中文也超，等于为第六项牺牲既有五项的可读性，且三语要同时缩）与横向滚动（第六项默认在视野外，而让客服看见这个入口正是本条目的全部价值）。取 600 而非刚好够的 560：600 的可用宽约 560px，印尼语留约 60px 余量；560 只剩约 20px，等于把同样的问题推迟到下次加文案时再爆。
>
> **由此后台会出现两种抽屉宽度：用户详情 600px、其余（场所等）维持 480px。** 这是有意的——用户详情承载六个页签、信息量本就更大。**不要**借本条目统一加宽全部抽屉，那是独立的后台组件改动。

**内容（读业务表，不读支付表）：**

| 解锁项 | 每行展示 |
|---|---|
| KTP 卡高清 | 哪几张卡已解锁 · 解锁时间 |
| 护照 · 快照 | 买过哪几个快照版本 · 各自解锁时间 · 该版本当时的章数 |
| 护照 · 登机牌 | 已解锁的场所 · 各自解锁时间 |
| Tailsonality | 哪几次结果已解锁 · 角色代号 · 解锁时间 |

**规则：**

- **数据源是各业务表的解锁状态，不是支付记录。** 既有取数口径已确立这一原则（KTP 的权威口径是卡上的解锁位，不是购买记录表的行数——购买记录表是「支付尝试 / 收据」，QRIS 下单即插行）。读业务表同时解决了 PawCoin 购买不可见的老问题：无论用户用什么渠道付的，解锁状态都在业务表里
- **只读，不提供任何写操作**——撤销解锁、人工补发、退款均不在本版本（§4）
- 权限：沿用用户详情页既有 permission_code，不新增。本块无 PII
- **各组口径（2026-10-02 定）：**
  - **KTP 卡高清的解锁时间 = 真实付款时间**：KTP 卡只记「已解锁」位、不记时间；购买记录表的时间是下单时刻（QRIS 下单即插行）。故 QRIS 取对应支付单到账时刻（PAID 的 `updated_at`，与看板 #15 同口径），PawCoin 取购买记录时刻（当场扣币）。找不到付款记录的老卡显示「—」
  - **护照快照的版本号**：同一宠物**已付款**的快照按付款先后编号 v1、v2、v3…，未付款的快照不占号，编号连续
  - **登机牌**：场所合并后作废（superseded）的那张若已付款，**照样列出并标「已合并」**——客服据此看出用户为同一地方付过两次
  - **Tailsonality 的角色代号** = 类型码 + 能量档（如 `ENTJ-H`）

## 4. 本版本明确不做

逐条写明，避免工程与运营按旧稿或直觉预期：

| 不做的事 | 说明 |
|---|---|
| **0 = 限时免费解锁** | 线上三条 DB CHECK 已是 `>= 1`（本版本进一步收紧为 `>= 100`，见 §1.4）、服务层校验与表单同口径，购买链路也没有零价短路（价格直接进 PawCoin 扣减 / QRIS 建单，0 元建单会被渠道拒）。要做则需改四条 CHECK、放开校验、并为**四个 SKU × 两条支付通路共八个分支**补零价短路——属独立工程项。本版本配置页继续把 0 挡为非法值 |
| **虚拟商品退款通道** | 既有退款三段流绑死在兽医问诊订单上（`refund_requests.order_id` 指向问诊订单且唯一），电商退货是另一套；虚拟解锁（含既有的 KTP、AI 解锁）从来没有退款通道。**本版本维持现状，客诉走人工。** 退款诉求的根源在文案——App 端 FR-120 已要求「购买前后都写明买的是这一版」，那道防线是主要止损点 |
| **人工补发 / 撤销解锁** | 与退款是同一件事的正反面，都是能凭空发币或收回用户已购内容的高危动作，要做须连同权限、防滥用、审计一起单独设计 |
| **独立的解锁记录页** | 跨用户按 SKU / 时间筛的运营财务视角，由支付记录页的用途筛选 + 导出 xlsx 覆盖（§1.5），不另开页 |
| **按 SKU 拆分的看板视图** | 等积累两三个月真实数据后再评估是否上看板 |
