# TailTopia V1.4.0 · 精选自营电商 - Epic Breakdown（Delta）

## Overview

本文件是 V1.4.0 **增量** epic/story 分解，承接两份 PRD（用户端 FR-93~FR-110 / 后台模块 10–13 + 模块 6 扩展）、架构 delta（AD-1~AD-13，**权威**）、UX 交接（15 屏原型 + UX-DR1~12）与决策台账。

**V1.0 / V1.1 / V1.1.2 已上线冻结；未提及处一律继承。**
冲突序：**架构 delta > 本文件 > PRD > CROSS-STORY-DECISIONS > V1.0/V1.1/V1.1.2 基线**。

核心主题 = **最小可售闭环**（系统内首次出现实物商品，收货地址/物流/实物退货/库存四类能力从零建立）+ **复购引擎**（本版本两条机制：FR-107 档案推荐 + FR-109 粮量见底预估）。

> ⚠️ **三处全局前提，拆 story 时逐条生效：**
> 1. **FR-108 不在本版本**（`decision-log` C-11 → 挪 Roadmap 1.2.0）。不拆 story、不建表、`health_records` 零 schema 改动
> 2. **本版本三人并行**，触碰共享物的 story 须先完成 `PARALLEL-DEV-CONTRACT.md` 签字与认领
> 3. **复购引擎冗余已归零**：FR-109 的唯一输入 DEP-6（每日建议喂量数据，Rendy）不可控，其「缺输入不触发」是**一等路径**而非异常路径

## Requirements Inventory

### Functional Requirements

沿用全局 FR 编号，不重新分配。本版本区间 **FR-93 ~ FR-110**（现有最大 FR-92）。

**① 信息架构与入口**
- **FR-93**：Toko Tab 与首页结构。四区域固定：① 补货提醒区（最多 2 张触发卡，无触发则整区不渲染）② 为我的宠物精选（FR-107，4–6 个）③ 分类入口（Makanan / Obat & Vitamin / Camilan / Perawatan 四固定品类）④ 全部精选。**不提供全站搜索框**。含用户状态 × 区域展示矩阵（游客 / 已登录·未建档 / 已登录·已建档 / 状态 B·C 四行）。**按单宠物实现，标注「1.3.0 多宠物后启用」（L-11）**
- **FR-93A**：Toko 与既有 Tab 的关系。Toko 是**非落地 Tab**，不参与 V1.1.2 FR-78 的落地判定；**游客点击 Toko 不触发登录引导**（与既有非落地 Tab 机制有意不同——登录引导推迟到加购）；Tab 切换手动上报埋点

**② 商品与库存**
- **FR-94**：商品模型与展示。12 个字段（名称/品牌/品类/主图+图集/规格列表/适用物种/适用体型/适用年龄段/商品详情/**每日建议喂量**/保质期说明/**退货规则标识**）。每日建议喂量为 Makanan 必填且**必须结构化** `{体重下限, 体重上限, 克/日}` 数组
- **FR-94A**：规格（SKU）与价格。SKU 是价格与库存的实际承载者；**未选规格时加购按钮禁用**，不默认选中第一个；单规格商品不展示选择器；价格格式 `Rp 185.000`（点号千分位，无小数）
- **FR-95**：库存与售罄。`可售库存 = 实际库存 − 锁定库存`；四段流转（提交订单锁定 / 支付成功扣减 / 超时取消释放 / 退货质检通过入库）；**服务端原子扣减**；售罄不下架；低库存阈值提示；**购物车与结算两次独立校验**，第二次失败标出具体 SKU 并允许移除后继续

**③ 购物车与结算**
- **FR-96**：购物车。**单店模型无店铺分组**；行内调数量/删除；**失效商品单独分区**置底不参与合计 + 「清空失效商品」；角标显示件数非种类数；**游客无购物车**，加购触发 FR-0B 软登录，登录后自动完成本次加购并停留原页
- **FR-97**：结算页。自上而下：收货地址 → 商品清单 → 配送方式 → 支付方式 → 金额明细 → 提交。金额明细四行（商品小计 / 运费 / 免运费抵扣 / 应付合计）；**不含优惠券促销码会员价，不预留会员价字段**；无地址/超范围时提交按钮禁用；**提交订单 = 创建订单 + 锁定库存 + 进入待支付，尚未扣款**

**④ 收货地址与运费**
- **FR-98**：收货地址体系。印尼四级行政区划采集到第三级；9 个字段（收件人/手机号 +62 8–13 位/Provinsi/Kota·Kabupaten/Kecamatan/详细地址 ≤120/Kode Pos 5 位/地址标签/设为默认）；**地址簿上限 20 条**；首个自动设默认；删除默认后最近使用的一条升为默认；**履约手机号与账号手机号不互通、不自动填充、不同步**
- **FR-99**：服务范围与运费。按 **Kecamatan 粒度**配置，首发限 Jabodetabek；**地址保存不校验范围、结算时校验并阻断**；配送两档（当日达 Sameday / 标准快递 Reguler 2–4 日）；**按「配送方式 × 区域」固定运费表，不接承运商实时计费 API**；不做超重超体积附加费

**⑤ 支付（含 PawCoin 规则）**
- **FR-100**：电商订单支付。复用 FR-43 通用支付组件但**需扩展支付模型**（→ AD-1）；**真钱渠道仅 QRIS**（不支持 GoPay/OVO 直连、不支持银行转账/VA）；**待支付超时 60 分钟**（明显长于兽医咨询窗口，因实物购买决策节奏不同）；超时前 10 分钟推送提醒
- **FR-100A**：PawCoin 购买实物商品的使用规则，**七条**：
  - 规则 1 · **防套现（最承重，安全攸关）** —— PawCoin 支付的部分退款**只能退回 PawCoin，不提供退真钱选项**；退款方式页对该段**不展示入口**而非展示后拒绝；**不因退货原因而变**，平台责任亦然
  - 规则 2 · 混合支付与按比例退款 —— 余额优先全额抵扣、差额 QRIS 补足；比例按**订单实付**计算并在**订单创建时固化**，不随后续部分退款重算；**结算页须同时展示两段金额**
  - 规则 3 · 运费可用 PawCoin 支付 —— 计入总额一并抵扣与拆分；后台对账须能把「PawCoin 抵扣的运费」单独拆出
  - 规则 4 · 单笔上限（建议 Rp 1.000.000，后台可配）—— 用途是**故障/欺诈爆炸半径 + 监管姿态，不是控浮存**
  - 规则 5 · 浮存门槛联动
  - 规则 6 · 不参与场景（不可转让）
  - 规则 7 · **平台责任 Coin 溢价补偿** —— 质量问题退货时对 PawCoin 段额外补偿，**须与 AB-6A 既有激励溢价取两个独立配置值**
- **FR-101**：电商订单卡片（FR-54 第 5 类）。复用既有订单页主体结构不新建入口；筛选 chips 新增「Belanja」；与虚拟商品订单**同列表时间倒序混排不分栏**
- **FR-102**：订单状态机。8 态（待支付/待发货/已发货/已送达/已完成/已取消/退款中/已退款），**三终态无悬空**；已送达 7 日自动确认；自动确认后仍保留自签收起算 7 日退货窗口；**订单号必须是不可枚举 token（安全攸关，CLAUDE.md 护栏）**，对账连续序号走内部序列不外露
- **FR-103**：物流追踪。**轻量实现**：后台录入承运商 + 单号 → App 展示单号/承运商名/复制按钮/跳转官网链接；**不接承运商 API、不在 App 内渲染轨迹**；发货推送复用 FR-38 深链接

**⑥ 退货与退款**
- **FR-104**：退货规则。四种可退情形 × 退货运费归属（发货前取消 / 拒收未签收 / 质量问题 7 日内 / 非质量问题 7 日内未拆封）；**「开封不退」须在商品详情页、结算页、退货申请页三处明示**；「不可退」不提供退货入口；凭证图 ≤6 张质量问题必填；审核复用 AB-5E + AB-5B；驳回复用 FR-52A 回告
- **FR-104A**（2026-08-15 新增，C-12）：退货粒度与去程运费。**支持行级部分退货**；**同一订单同时仅允许一个进行中的退货申请**（入口置灰 + 后台双向校验）；**整单退 → 去程运费全退，部分退 → 不退**，须在退货申请页明示（堵免运门槛凑单-退货套利）；**部分退货不改订单主状态**，仅全部行退款完成才转 `已退款`
- **FR-105**：退款到账方式。先按 FR-100A 规则 2 拆两段再分别处理；PawCoin 段无选项（+ 质量问题时补偿溢价）；QRIS 段用户可选退真钱或转 PawCoin（复用 FR-43D，BCA 免手续费 / OVO·GoPay 自付 Rp2.500）；**两种溢价触发条件与目的不同，配置项必须分开**

**⑦ 评价**
- **FR-106**：商品评价。订单 `已完成` 后可评，每订单每 SKU 各一次；1–5 星必填 + 文字 ≤500 选填 + 图 ≤6 选填；**复用既有内容审核机制**（三方同步过滤，命中即拦截不发布，不走先发后审）；详情页按时间倒序；**无评价时空状态，不伪造或预填**；首版不做追评、不做商家回复

**⑧ 复购引擎（版本核心，本版本两条机制）**
- **FR-107**：档案推荐。**规则式非算法**：适用物种硬过滤 → 适用年龄段匹配 → 适用体型匹配档案体重 → 运营权重排序取前 4–6；展示位 Toko 首页区域② + Diary 档案页推荐区；**卡片文案带推荐理由（可解释）**；档案不完整时降级为按物种推荐 + 尾部「补全档案，推荐更准」引导卡
- ~~**FR-108**~~：健康记录触发复购 —— 🚫 **本版本不做，挪 Roadmap 1.2.0**（C-11）
- **FR-109**：粮量见底预估。`日喂量 ← 按体重匹配区间表；可用天数 = 净含量 ÷ 日喂量；耗尽日 = 上次购买日 + 可用天数`；**耗尽日前 7 天**展示补货卡 + 推送一次；文案给估算依据不写成断言；再次购买后从新订单日重算、旧提醒立即消失；**缺任一输入不触发、不做兜底猜测**
- **FR-110**：问诊与商品的边界（**约束性需求，安全攸关**）。**兽医在问诊会话中不得推荐具体 SKU**，不提供「兽医推荐商品」组件、**不给兽医端任何商品链接插入能力**；问诊结论页仅允许「按结论中的结构化健康记录类型跳转对应品类」这一种系统生成的关联；**此约束优先于任何转化率优化**

**⑨ 管理后台（沿用 AB 编号）**
- **AB-10A~10D**（模块 10 · 商品与库存，新建）：商品列表与创建/编辑 · SKU 价格与规格管理 · 库存管理与采购入库 · 上下架与精选排序（含 SKU 上限 30 超限告警）
- **AB-11A~11D**（模块 11 · 订单履约，新建）：电商订单列表与详情 · 发货与物流单号录入 · 服务范围与运费配置 · 订单异常处理
- **AB-12A~12D**（模块 12 · 退货与售后，新建 + 复用）：退货申请审核队列（**含行级退货行与「是否整单退」字段**）· 质检与入库 · 退款执行（**含两条独立溢价 + `coin_ratio` 拆分 + 订单状态联动口径**）· 开封判定判例库
- **AB-13A~13D**（模块 13 · 电商经营数据，新建）：销售与毛利看板 · **复购引擎效果看板**（口径已收敛为两条机制 + 新增「FR-109 触发覆盖率」）· 库存周转与滞销预警 · 对账
- **AB-6D**（模块 6 扩展，新建）：PawCoin 电商消费规则配置
- **AB-6A（扩展）**：新增第二条溢价 —— 平台责任补偿溢价（**必须是独立配置项**）
- **AB-6C（口径变更）**：浮存监控需区分来源（**电商消费加快核销 → 预期浮存下降**，非上升）

### NonFunctional Requirements

两份 PRD 无独立 NFR 章节，以下由 `CLAUDE.md` 强制护栏、架构 delta 与 PRD 正文内嵌约束提炼：

- **NFR-1 · 中间件零增量**：异步只用 `@Async` + DB 状态机、`@Scheduled` 定时；**禁 MQ / 禁调度中间件 / 禁分布式锁 / 禁通用缓存层**；不改变部署形态（德国单机）
- **NFR-2 · schema 归 Flyway**：`spring.jpa.hibernate.ddl-auto=validate`，禁 `update`/`create`；已提交迁移冻结，修正一律新起 `ALTER`
- **NFR-3 · 对外标识不可枚举**（安全攸关）：订单号、商品/SKU 对外标识一律 `SecureRandom` + Base62 token；**不用自增 id 直接外露，不用日期+序列号**
- **NFR-4 · 凭证 env 注入绝不入库**：`.env.example` 只放占位
- **NFR-5 · 日志禁 PII**：SLF4J + logback JSON；**严禁记录 PII / 健康数据 / 令牌 / 签名 URL**；本版本新增禁记项——**收货地址、收件人姓名、履约电话**（物流单号非 PII 可记）
- **NFR-6 · 错误统一 RFC 9457 ProblemDetail**（type/title/status/detail/instance/traceId），**绝不外泄堆栈**
- **NFR-7 · 命名映射链**：DB `snake_case` ↔ Java/Dart `camelCase` ↔ JSON `camelCase`；表复数 snake_case；外键 `<单数>_id`；时间戳 `created_at`/`updated_at` 为 `timestamptz` 且**一律 UTC**；枚举落库 `varchar` + UPPER_SNAKE；API `/api/v1`，资源小写复数连字符，当前用户统一 `/api/v1/me`
- **NFR-8 · 库存并发正确性**：纯 DB 条件原子写（`UPDATE ... WHERE ... AND available >= ?` 判影响行数），**可售库存不得为负，超卖目标为 0**；失败方返回明确「已售罄」而非静默失败
- **NFR-9 · 资金计算精度**（AD-2）：金额一律 `BIGINT` 最小币种单位；**按比例拆分用整数累计法，禁用浮点**；须保证多次部分退款后全额退款**精确归零**
- **NFR-10 · 幂等**：PawCoin 扣减/退回复用 `PawCoinWalletService` 既有幂等键机制（Redis 前置 + 跨 TTL 的 DB 兜底），**不另造幂等机制**
- **NFR-11 · 权限隔离**：模块 10–13 需独立角色权限，不默认授予既有运营角色；**进货价与毛利数据（AB-10B 进货价 / AB-13A 毛利 / AB-13D 对账）需单独权限位**，默认仅财务与管理层可见
- **NFR-12 · 验证层级**：每条 AC 标 **L0**（静态：`flutter analyze`/`flutter test`/`mvn -B compile|package`）/ **L1**（集成：Docker postgres+redis）/ **L2**（端到端：真机/模拟器/真实凭证）

### Additional Requirements

来自 `architecture-v1.4.0-delta.md`（AD 条目为权威）与并行契约：

- **无 starter template** —— brownfield 增量，两套工程已存在（`petgo_app/` Flutter · `petgo-backend/` Spring Boot 4 / Java 21）
- **AD-1 · 混合支付扩展既有 `PaymentIntent`**：`PayChannel` 末尾追加 `MIXED`；加 `coin_amount`/`cash_amount`/`coin_ratio` 三列（nullable，JPA 侧 `updatable=false`）；加 `ck_payment_intents_mixed_shape` 保证 `coin_amount + cash_amount = amount`；**既有 4 个 purpose 三列恒 NULL、行为逐字节不变**
- **AD-2 · `coin_ratio` 只作展示与审计冗余，资金计算一律不读它**；用 `coin_amount`/`amount` 整数**累计法**（按累计量取整非单次取整）
- **AD-3 · `MIXED` 只放宽 `ck_payment_intents_channel` 一处**；`consult_orders` / `ai_consult_orders` / `id_card_hd_purchases` 三处 CHECK **刻意不放宽**作纵深防御，迁移文件头须写明该非对称是刻意的

### Story 1.2: 库存模型与可售库存口径

As a 后端系统,
I want 具备库存的持久化模型、可售库存计算口径与原子变更原语,
So that 售罄判定有唯一权威来源，且后续下单锁定不会超卖。

**Acceptance Criteria:**

**Given** 迁移 `V102__init_sku_inventory.sql` 已应用
**When** 检视 `sku_inventory` 表
**Then** 含 `actual`（实际库存）与 `locked`（锁定库存）两列，均为 `BIGINT NOT NULL DEFAULT 0`
**And** 存在 CHECK 约束保证 `actual >= 0 AND locked >= 0 AND locked <= actual`
**And** **可售库存 = `actual − locked`**，为查询期计算，**不落库**（避免三值不一致）
`[L0]` `mvn -B package` 通过

**Given** 并发请求同时对同一 SKU 扣减
**When** 调用库存锁定原语
**Then** 实现为**单条 DB 条件原子写** `UPDATE sku_inventory SET locked = locked + ? WHERE sku_id = ? AND (actual - locked) >= ?`，**依影响行数判定成败**
**And** 影响 0 行时返回明确的「已售罄」领域错误，**不静默失败、不重试排队**（FR-95 / NFR-8）
**And** 🔴 **不得引入分布式锁、不得用 Redis 扣减、不得引入任何中间件**（CLAUDE.md 护栏 · AD-6 · 范式照 V1.0 决策 F11 兽医抢单）
**And** 不变式「**可售库存不得为负，超卖目标为 0**」有对应断言（NFR-8）
`[L0]` 单测覆盖影响行数分支 · `[L1]` 并发集成测试：N 个线程抢 M 件库存，成功数恰为 M、无负库存

**Given** 商品查询接口返回 SKU
**When** 可售库存为 0 / 低于运营配置阈值 / 正常
**Then** 分别下发 `OUT_OF_STOCK` / `LOW_STOCK`（含剩余数）/ `IN_STOCK` 三态
**And** 售罄商品**不自动下架**，仍可被列表与详情查询到（FR-95）

### Story 5.2: 🔴 按比例退款的整数累计法（安全攸关）

As a 后端系统,
I want 两段退款的拆分算法在多次部分退款后仍精确,
So that 全额退完时 PawCoin 段既不多退也不少退。

**Acceptance Criteria:**

**Given** IDR 无小数、金额一律 `BIGINT` 最小币种单位
**When** 计算某次退款的两段拆分
**Then** 🔴 **按累计量取整，不按单次取整**（AD-2）：
```
cumulativeTotal = refundedTotalBefore + thisRefund
cumulativeCoin  = cumulativeTotal * intent.coinAmount / intent.amount   ← 整数除法向下取整
thisCoin        = cumulativeCoin - refundedCoinBefore
thisCash        = thisRefund - thisCoin                                 ← 减法得出，不独立计算
```
**And** 🔴 **`coin_ratio` 列只用于后台展示与对账审计，任何资金计算路径都不得读它** —— 以注释 + 单测钉死
**And** 🔴 **中间量用 `long`，禁用 `double` / `float`**；`cumulativeTotal * coinAmount` 的量级在客单 285k、上限 1M 下远在 `long` 范围内
**And** `refundedTotal` / `refundedCoin` 为订单侧累计字段，随每次退款执行**在同一事务内递增**
`[L0]` 单测

**Given** 这是资金正确性的核心
**When** 编写单测
**Then** 🔴 **必须覆盖以下三条**（AD-2 明列）：
**And** ① 全额一次退 → Coin 段恰好等于 `coinAmount`
**And** ② **拆成 3 次不等额部分退至全额 → 累计 Coin 段恰好等于 `coinAmount`（零漂移）**
**And** ③ `coinAmount = 1`、`amount = 300000` 的极端比例下不出现负数或超退
**And** 恒等式 `thisCoin + thisCash == thisRefund` 在所有用例中成立
`[L0]` 上述单测全绿

> **为什么少退是客诉、多退是缺口：** 少退几盾用户会投诉；**多退则是 FR-100A 规则 1（防套现）的缺口** —— 真钱段被多退意味着用户拿回的真钱超过了投入的真钱。
