# 自建埋点（analytics-pipeline）· 大方向决策记录

> 主题不挂版本；分支 `feat/analytics-pipeline`（基于 main）。2026-11-11 与 Dai 讨论定下。
> 依据：[技术调研 · 第 2 步技术概况](research/technical-analytics-pipeline-research-2026-11-11.md)（存储方案对比、本机资源、体量估算）。
> 状态：大方向已定；团队需求已收齐（[department-data-summary.zh.md](department-data-summary.zh.md)），已完成需求 × 数据来源对照（见下文），进入 PRD。

## 背景

PostHog 停用。App 埋点（约 191 种事件，现经 PostHog SDK 上报）改发到自家后端，在自己的库里做分层与统计。

## 定位

- **日活一万以内的过渡方案**，以省钱、少运维为目标。现在登录日活 1,000+；体量涨到约 10 倍（日活上万）时，**考虑切回付费三方平台**。
- 因此：不为大规模设计（不做独立实例、ClickHouse 升级路线、OSS 归档）。
- **从第一天就为「以后搬走」设计**：
  - App 端所有埋点只经统一入口 `Analytics` 门面上报，以后切平台只换门面背后的发送端，业务埋点调用不动。
  - 事件格式对齐业界通用结构（事件名、客户端唯一 id、发生 / 发送 / 收到三种时间、用户、属性；参照 PostHog / Segment），便于将来把历史数据导给三方。
  - 指标口径写成文档，不只藏在 SQL 里。

## 决定

| # | 主题 | 决定 | 来源 |
|---|---|---|---|
| D1 | 接收 | 做在**现有 Spring Boot 后端**里（独立模块），不另起服务、不加中间件 | Dai |
| D2 | 批量 | **两端都批量**：App 本地攒批（如 20 条 / 30 秒，切后台与网络恢复时补发）；后端收到先入内存队列、立即回成功，按条数或时间（如 500 条 / 数秒）批量写库 | Dai（要求批量）；参数为建议值 |
| D3 | 丢数据容忍 | 后端重启 / 崩溃时内存队列里未落库的数秒数据**可以丢**；正常发版先停接收、排空队列再退出 | 建议，Dai 同意按建议执行（2026-11-11） |
| D4 | 存储位置 | 现有 `petgo-postgres` 实例内**单独建埋点库**（如 `petgo_analytics`），与业务库隔离，独立账号与连接数；不与业务表建外键，需要的业务字段复制进来 | 讨论定 |
| D5 | 原始层 | 收到什么存什么；**按天分区，库内保留 35 天**（一个月重算窗口 + 缓冲），过期整分区删除，不归档 | Dai（一个月）；35 天为建议 |
| D6 | 明细层 | 清洗、补全后的事件，是一个月后**唯一的逐条记录**；**保留 3 个月**，更早的只留汇总（原定 12 个月，按估算上限约 90G 会吃掉大部分剩余磁盘，2026-11-11 改） | Dai |
| D7 | 汇总层 | 只做团队真正要看的指标（按天 / 人 / 功能 / 漏斗），体积小、长期保留 | 讨论定 |
| D8 | 消费 | 优先用已上生产的 **AI 查数**直接查；固定看板等指标收齐再定 | 讨论定 |
| D9 | 日活口径 | **以 GA4 为准**。自建埋点并行算含游客日活，**每日与 GA4 核对差值**，观察一段时间对得上再考虑切换（阈值与观察期写 PRD 时定） | Dai |

## 需求 × 数据来源对照（2026-11-11）

依据：[department-data-summary.zh.md](department-data-summary.zh.md)（编号沿用原文：S = 共用，电商 / 内容 / 市场 / 产品 # = 各部门表内序号）。

| 类别 | 指标 | 处理 |
|---|---|---|
| **A. 只靠业务库** | S6 收入；电商 #1 #2 #3 #10；内容 #2–#8；产品 #4 | **不进埋点管道**。AI 查数现已能查，补口径文档 / 视图即可，可先行交付 |
| **B. 只靠埋点** | S1 日活；S2 安装；S3 注册；市场 D1 / D3 / D7；电商 #4 #8；产品 #1 #5；S5 曝光 / 点击 | 自建管道的核心范围 |
| **C. 埋点 + 业务库关联** | S4；内容 #1；电商 #5 #6（最后一步支付成功）#7 #9（售罄商品要详情浏览数）；产品 #2 #3；S5 的「点击后 7 天内已支付 Toko 订单」 | 汇总层需拼接两边；埋点库与业务库分库（D4），关联方式在架构定 |

结论：**PRD 范围 = B + C + 下列缺口**；A 类另做口径文档。

### 现状缺口（代码核对）

| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| G1 | `Application Opened` / `Application Installed` | PostHog SDK 自动上报（`analytics.dart` `captureApplicationLifecycleEvents`），非自埋 | S1 / S2 / 留存全依赖；自建需自实现。安装只能靠首启标记判定，卸载重装会被算新安装，口径与 PostHog 有偏差 |
| G2 | 页面浏览 `$screen` | 路由挂 `PosthogObserver` + `Analytics.screen()` 调 PostHog | 电商 #4（`toko_page`）依赖；需换自有路由观察者 |
| G3 | 推送「接收人数」 | 端上仅有打开事件（`ops_notification_opened`、`toko_coupon_expiry_push_opened`） | 发送 / 接收数只能取后端发送记录（服务端事件） |
| G4 | 其余运营位曝光 / 点击 | 已有：运营弹窗 `ops_popup_shown` / `ops_popup_tapped`、`toko_banner_shown` / `toko_banner_tapped`、新人券弹窗（2026-11-11 PRD 对账更正） | S5 要求「全部」，其余运营位逐一核对补齐 |
| G5 | 购物车「移除」 | 无移除事件 | 电商 #7 停留时长；先查购物车表是否有删除时间，有则归 C 类不补埋点 |
| G6 | 生产 / 测试区分 | 事件不带 staging、模拟器、TestFlight、侧载标记 | 通用规则「只算生产数据」；端上需随事件带环境标记，后端补内部账号排除 |

## 不做（本阶段）

- 不用 Firebase / GA4 + BigQuery 存原始事件（Dai：暂时不用）。
- 不引入 TimescaleDB / ClickHouse / 列存扩展 / pg_partman / pg_cron（分区由后端定时任务建删）。
- 不做原始数据 OSS 归档。

## 待定（写 PRD / 架构时解决）

- 日活核对的可接受差值与观察期。
- 后端服务端事件（支付成功等）是否一并改发自建库。
- 接收端细节：鉴权、防刷、限流、去重、时钟偏差（技术调研第 3 步，暂停中）。
- 单条事件实测大小（用样本 `pg_column_size` 校准体量估算）。
