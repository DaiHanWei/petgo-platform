# 自建埋点（analytics-pipeline）· 大方向决策记录

> 主题不挂版本；分支 `feat/analytics-pipeline`（基于 main）。2026-11-11 与 Dai 讨论定下。
> 依据：[技术调研 · 第 2 步技术概况](research/technical-analytics-pipeline-research-2026-11-11.md)（存储方案对比、本机资源、体量估算）。
> 状态：大方向已定；**目标指标仍在收集**，收齐后据此写 PRD → 架构 → epics / stories。

## 背景

PostHog 停用。App 埋点（约 191 种事件，现经 PostHog SDK 上报）改发到自家后端，在自己的库里做分层与统计。

## 定位

- **日活一万以内的过渡方案**，以省钱、少运维为目标。现在登录日活 1,000+；体量涨到约 10 倍（日活上万）时，**考虑切回付费三方平台**。
- 因此：不为大规模设计（不做独立实例、ClickHouse 升级路线、OSS 归档）。
- **从第一天就为「以后搬走」设计**：
  - App 端所有埋点只经统一入口 `Analytics` 门面上报，以后切平台只换门面背后的发送端，业务埋点调用不动。
  - 事件格式对齐业界通用结构（事件名、客户端唯一 id、发生 / 发送 / 收到三种时间、用户、属性；参照 PostHog / Segment），便于将来把历史数据导给三方。
  - 指标口径写成文档，不只藏在 SQL 里。

## 决定

| # | 主题 | 决定 | 来源 |
|---|---|---|---|
| D1 | 接收 | 做在**现有 Spring Boot 后端**里（独立模块），不另起服务、不加中间件 | Dai |
| D2 | 批量 | **两端都批量**：App 本地攒批（如 20 条 / 30 秒，切后台与网络恢复时补发）；后端收到先入内存队列、立即回成功，按条数或时间（如 500 条 / 数秒）批量写库 | Dai（要求批量）；参数为建议值 |
| D3 | 丢数据容忍 | 后端重启 / 崩溃时内存队列里未落库的数秒数据**可以丢**；正常发版先停接收、排空队列再退出 | 建议（待 Dai 确认） |
| D4 | 存储位置 | 现有 `petgo-postgres` 实例内**单独建埋点库**（如 `petgo_analytics`），与业务库隔离，独立账号与连接数；不与业务表建外键，需要的业务字段复制进来 | 讨论定 |
| D5 | 原始层 | 收到什么存什么；**按天分区，库内保留 35 天**（一个月重算窗口 + 缓冲），过期整分区删除，不归档 | Dai（一个月）；35 天为建议 |
| D6 | 明细层 | 清洗、补全后的事件，是一个月后**唯一的长期记录**，字段尽量保留全；**保留 12 个月** | 12 个月为建议（待 Dai 确认） |
| D7 | 汇总层 | 只做团队真正要看的指标（按天 / 人 / 功能 / 漏斗），体积小、长期保留 | 讨论定 |
| D8 | 消费 | 优先用已上生产的 **AI 查数**直接查；固定看板等指标收齐再定 | 讨论定 |
| D9 | 日活口径 | **以 GA4 为准**。自建埋点并行算含游客日活，**每日与 GA4 核对差值**，观察一段时间对得上再考虑切换（阈值与观察期写 PRD 时定） | Dai |

## 不做（本阶段）

- 不用 Firebase / GA4 + BigQuery 存原始事件（Dai：暂时不用）。
- 不引入 TimescaleDB / ClickHouse / 列存扩展 / pg_partman / pg_cron（分区由后端定时任务建删）。
- 不做原始数据 OSS 归档。

## 待定（写 PRD / 架构时解决）

- 团队要看的指标清单（Dai 收集中）→ 决定汇总层内容与是否要看板。
- D3、D6 两条建议值待 Dai 确认。
- 日活核对的可接受差值与观察期。
- 后端服务端事件（支付成功等）是否一并改发自建库。
- 接收端细节：鉴权、防刷、限流、去重、时钟偏差（技术调研第 3 步，暂停中）。
- 单条事件实测大小（用样本 `pg_column_size` 校准体量估算）。
