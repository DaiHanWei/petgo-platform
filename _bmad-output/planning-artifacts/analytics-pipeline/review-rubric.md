# PRD 质量评审 — 自建埋点（analytics-pipeline）

> 评审基准：`.claude/skills/bmad-prd/assets/prd-validation-checklist.md`。按内部工具级、快速路径 PRD 校准（技术细节留架构），不要求上线级完备度。评审日期 2026-11-11，只读，未改 prd.md。

## 总体判断

这份 PRD 主线清楚、分量合适：「日活一万以内的过渡方案 + 从第一天就能搬走」这个判断贯穿了 FR、非目标和反向指标；23 条 FR 几乎都有可验证结果；假设已建索引，非目标写得很实。风险集中在三处：**注销用户的埋点数据怎么处理完全没写**（这是项目的强制护栏）；**过渡期数据断档没有说透**（愿景写「PostHog 停用后」，§4.1 又写旧版本「继续发 PostHog」）；**「含游客日活」按什么去重没有定义**，而 SM-2 和 FR-22 都靠它。三处都是补一两段就能解决的，补完即可进架构。

## 决策可用性（Decision-readiness）— adequate

D1–D9 在 decisions.md 里写成了明确决策，PRD 正确引用而不复述（§4.2 引 D1/D2，§4.3 引 D4–D6，§4.6 引 D9）。「直接切换、不双写」（§4.1 描述）是本 PRD 最大的取舍，而且写成了决策，不是写成「考虑」。§8 开放问题四条都是真正未决的问题，不是反问句。

不足在于取舍只写了选了什么，没写**放弃了什么**。不双写意味着 V1.5.0 上线后的若干周里，B、C 类指标只覆盖已升级用户；UJ-1 的边界情况（「仅统计 ≥ 某版本的用户」）点到了，但留存队列、漏斗在爬坡期是否可比，以及这期间团队看什么，都没有交代。另外 MVP 把 FR-1 到 FR-23 全部纳入（§6.1），又和 V1.5.0 发版绑定，却没有切分线，也没写上线顺序。

### Findings
- **[high] 过渡期数据断档没说透**（§1 愿景 vs §4.1 描述、§6.2）— §1 写「PostHog 停用后，App 的行为数据要有一个自己的归宿」，§4.1 又写「旧版本继续发 PostHog 直到用户升级」，§6.2 写旧版本数据「不进自建库」。读者无法判断：PostHog 项目在过渡期是否仍开着、旧版数据谁还在看；如果已经停用，从 V1.5.0 发版到覆盖率达标这段时间，旧版用户的行为数据实际上谁也收不到。另外，覆盖率达到 90% 预计需要多久也没有估计，SM-2 的观察期因此没有起点。*Fix：* 在 §4.1 或 §6.2 补一段「过渡期」：PostHog 停用的确切时间点、旧版数据是否还有人消费、预计的覆盖率爬坡周期，以及爬坡期内团队报表的使用约定（例如只看新版用户、结果附覆盖率）。
- **[medium] MVP 没有切分线，上线顺序没写**（§6.1）— 「FR-1 到 FR-23 全部」与 V1.5.0 发版硬绑定。如果发版日期紧，哪些可以晚于发版交付（FR-22 对账、FR-18 部分指标、FR-21 口径文档都是纯后端，可以后补），哪些必须随包（FR-1~FR-6、FR-15、FR-16），没有区分。同样没写「后端接收（FR-7~FR-12）必须先于 V1.5.0 上线到生产」这一硬前置条件。*Fix：* §6.1 拆成「随 V1.5.0 包必须就绪」和「发版后可补」两组，并写明后端先上线这一前置条件。
- **[low] FR-8 的伪造处理二选一未决**（§4.2 FR-8）— 「与事件里声明的用户不一致时以凭证为准，或丢弃该事件」。两种做法对统计结果影响不同（改写会把事件归给凭证里的用户，丢弃会少计数）。*Fix：* 定一个，或者明确写「由架构定」并放进 §8。

## 内容是否落到实处（Substance over theater）— strong

没有凑数内容。§2.1 的四类使用者各自对应具体 FR（Albar → UJ-2 / 市场留存；Dai → FR-22；AI 查数 → FR-21/FR-23），§2.2「不服务的对象」把终端用户和广告归因明确排除，起了实际作用。愿景里「省钱、少运维、零新中间件」「体量约 10 倍时切回付费三方」这些表述是本项目特有的，换不到别的 PRD 里去。NFR 没有空话：保留期（35 天 / 12 个月）、批量参数、请求上限都给了数字。没有需要提的问题。

## 战略一致性（Strategic coherence）— strong

主线明确：在省钱、零新中间件的前提下，把 PostHog 的行为数据接回来，按团队口径交给 AI 查数，并保证以后能搬走。FR 分组（采集 → 接收 → 分层 → 补埋点 → 汇总口径 → 对账 → 查数）沿数据流展开，不是功能清单。SM-1（指标可答率）和 SM-2（日活对账）直接检验这个判断，而不是统计活跃度；SM-C1 / SM-C2 两条反向指标写得到位，分别约束「多埋事件」和「追求实时」两种常见的跑偏。

### Findings
- **[low] 「以后能搬走」没有对应的 FR**（§1 第二段）— 愿景把可迁移性当作设计原则（门面、业界通用事件结构、口径文档），但只有术语表里对齐 Segment 的三种时间字段算是落了地，没有任何一条可验证结果检查「事件格式对齐通用结构」。*Fix：* 在 FR-7 或 FR-13 补一条可验证结果，例如「事件字段可以无损映射到 Segment Track 规范（映射表放进口径文档）」；或者在 §5 明确写「可迁移性只靠约定，不作验收」。

## 完成标准是否清楚（Done-ness clarity）— adequate

大部分 FR 的完成标准达到了可写测试的程度：FR-2（20 条 / 30 秒、切后台补发、杀进程后补发、队列上限）、FR-7（部分合法事件照收、返回被拒条数）、FR-10（队列满返回 503、正常停机时排空队列）、FR-16（区分原因、下单离开购物车不算移除）、FR-19（与业务库 PAID 订单数一致）都写得很好。问题集中在几处形容词式的上限，以及对账这条线的呈现方式。

### Findings
- **[high] 「含游客日活」的去重键没有定义**（§3 术语、§4.6 FR-22、§7 SM-2）— 术语表定义了匿名 id、用户、身份关联，却没有定义日活本身：按匿名 id 去重，按「经身份关联合并后的人」去重，还是按设备去重？同一设备上登录前和登录后的事件算一个还是两个，换账号时又怎么算？GA4 的 activeUsers 有它自己的口径，自建侧口径不定，「日差值 ≤ 10%」就无从验证，SM-2 也就无法判定。FR-22 还混用了「用户」和「设备」（「当日新版 App **设备**占比」）。*Fix：* 在 §3 加「含游客日活」词条，写明去重单位，并说明与 GA4 activeUsers 口径的已知差异。
- **[medium] UJ-3 与 FR-22 对「收到」的说法矛盾，「标红」没有呈现位置**（§2.3 UJ-3 vs §4.6 FR-22、§6.2）— UJ-3 写「Dai 收到每日对账结果」「连续多日差值超阈值 → 标红」；FR-22 写「存进埋点库……**不推送飞书日报**」，阈值也是按单日判断。不推送的话，Dai 怎么「收到」？标红标在哪里？是单日超阈值标红，还是连续多日才标红？*Fix：* 把 UJ-3 改成「Dai 通过 AI 查数查看对账表」，并统一标红规则（单日还是连续 N 日）；标红落成表里的一个字段即可。
- **[medium] FR-13「数分钟内」没有上限**（§4.3 FR-13）— 「事件入库后数分钟内进入明细层」，「数分钟」没法验收；同时它和 SM-C2「不追求分钟级」的关系也需要说明（明细层准实时、汇总层 T+1，两者并不冲突，但应该写明）。*Fix：* 给一个上限（如 ≤ 15 分钟），或者干脆放宽成「当天数据在下一次清洗任务后可查」，并给出任务周期。
- **[medium] 「不受影响」「无显著变化」是形容词，不是上限**（§4.2 FR-8 第三条、§7 SM-4）— 「业务接口的响应时间与可用性不受影响」「业务接口 P95 响应时间无显著变化」都没法验收。*Fix：* 给一个数字，例如「接入前后业务接口 P95 差值 ≤ 10% / ≤ 50ms」，并写明对比方法（发版前后各取 7 天）。
- **[medium] 汇总任务和清洗任务失败时没有告警**（§4.3 FR-12、§4.5 FR-18）— FR-12 给分区任务配了日志级告警，但 FR-18 的 T+1 汇总只写了「可重跑、幂等」，没写失败了谁会知道。既然对账和汇总都不推送飞书（§6.2），汇总一旦静默失败，第一个发现的就是周一早上拿到空数据的电商同事（UJ-1）。*Fix：* FR-18 补一条「失败时有告警（至少日志级，沿用 FR-12 的方式）」，并说明 AI 查数返回结果时能看出数据截止到哪天（水位线可查）。

## 范围是否诚实（Scope honesty）— adequate

§5 非目标做了实事：A 类指标、看板、广告归因、服务端事件、新中间件、历史迁移、会话回放，每一条都可能被默认纳入，PRD 都明确排除了。`[ASSUMPTION]` 共 12 处，都汇总在 §9；结合 §8 的四个开放问题，对内部工具来说待定项的密度合适，不构成阻塞。

但有一块重要的缺失没有被点名：隐私与注销。

### Findings
- **[high] 注销用户的埋点数据处置完全缺失**（§4.3 FR-13、FR-14；全文）— 项目强制护栏要求「注销级联删除 / 匿名化按 D1/D2 落实」，属于安全攸关节点。本 PRD 新建了三类与用户身份挂钩的长期数据：明细层（12 个月，带用户标识）、身份关联表（**长期保留**）、汇总层（按人统计）。用户注销后这些数据删除、匿名化还是保留，全文一个字没提，§5 非目标里也没有排除。同样没写的还有：原始层「收到什么存什么」是否包含 IP（FR-8 按 IP 限流，说明后端能拿到 IP）。*Fix：* 加一条 FR（例如「FR-24 注销处置」）：注销后身份关联表删除或匿名化该用户的记录、明细层的用户标识置空或改写成不可逆值、汇总层只保留聚合结果；并写明原始层是否存 IP、存多久。如果有意推迟，至少在 §8 列为开放问题，并标注为上线前必须解决。

## 下游是否好用（Downstream usability）— adequate

本 PRD 处在规划链顶端（下游要做架构、epics、stories），对下游可用性要求较高。总体做得不错：§3 术语表覆盖了核心名词；FR-1~FR-23、UJ-1~UJ-3、SM-1~SM-4、SM-C1~SM-C2 编号连续、不重复；每条 SM 都标了「验证 FR-x」，可以反向追溯；FR 的描述段写了「实现 UJ-n」。依赖外部文档的地方（团队编号 S1–S6、电商 #n）在 §0 统一声明了来源。

### Findings
- **[low] UJ-2 漏掉了 D3 留存**（§2.3 UJ-2）— decisions.md 的 B 类清单写的是「市场 D1 / D3 / D7」，UJ-2 只写了 D1、D7。汇总层如果照着 UJ-2 去做，会漏掉 D3。*Fix：* UJ-2 改成「D1 / D3 / D7」，或者注明「以 decisions.md 清单为准」。

## 形态是否合适（Shape fit）— strong

这是内部工具 + 数据管道，以能力规格（capability spec）的形态来写是对的。UJ 只有三条，每条都有具名主角（电商同事、市场同事、Dai）和边界情况，没有过度套用面向终端用户的写法。SM 偏运营类（可答率、对账、完整性、资源占用），也符合内部工具的定位。这是存量系统上的改造，引用的现状也准确：已核对代码，`ops_popup_shown` / `ops_popup_tapped` / `ops_notification_opened` / `toko_banner_shown` 都真实存在，与 FR-15、FR-20 的描述一致。没有需要提的问题。

## 机械性问题（Mechanical notes）

- **decisions.md 与 FR-15 互相矛盾（以 PRD 为准）**：decisions.md 的 G4 写「只有 `toko_banner_shown`、`toko_newbie_coupon_popup_shown` 有曝光」，PRD 的 FR-15 写运营弹窗 `ops_popup_shown` / `ops_popup_tapped`「现有已覆盖」。代码核实 PRD 是对的（`petgo_app/lib/features/ops/presentation/ops_popup_coordinator.dart:263,275`），decisions.md 的 G4 已经过时，建议回头修正，以免架构阶段读到旧说法。
- **G3 没有显式落到 FR 上**：§0 范围写「加上缺口 G1–G6」。G1/G2/G4/G5/G6 在 FR 标题里都标注了，唯独 G3（推送接收人数）实际由 FR-20 承接却没有标注。建议 FR-20 标题加上「（G3）」。
- **「D」编号撞车**：decisions.md 的决策编号 D1–D9 与市场留存指标 D1 / D3 / D7 同名（例如 §0 的「D1–D9」和 UJ-2 的「D1、D7 留存」）。建议正文提到留存时写成「次日 / 3 日 / 7 日留存」或「市场 #1–#3」，避免下游误读。
- **术语漂移**：「用户标识」（FR-5、FR-8）在术语表中没有词条（只有「用户」）；FR-22 用「设备占比」，而 UJ-3 / SM-2 讲的是用户口径。可以和上面「含游客日活」那条 high 一起修。
- **假设索引对得上**：正文 12 处 `[ASSUMPTION]` 都能在 §9 找到对应条目（FR-5 的两处合并成了一条），§9 中也没有正文里找不到的条目。FR-2 / FR-5 / FR-8 / FR-14 / SM-3 正文里是只有标签、没有内容的 `[ASSUMPTION]`，要靠 §9 才能知道假设了什么，可以接受。
- **交叉引用**：§0 →「另做口径文档（见 §5）」能对上；FR-18 → decisions.md 的「需求 × 数据来源对照」能对上；FR-19 → D4 能对上。没有发现失效的引用。
- **必备章节**：对内部工具级 PRD 来说，愿景、使用者、场景、术语、FR、非目标、MVP、成功指标、开放问题、假设索引都齐了。没有 `[NOTE FOR PM]` 标注，对快速路径来说可以接受，但上面那条 high（注销处置）本应以这种标注的形式出现。
