# PRD：自建埋点（analytics-pipeline）

## 0. 文档说明

本 PRD 写给 Dai（产品 / 技术负责人）和下游的架构、epics / stories 编写者，建立在三份已有材料之上，不重复其内容：

- [decisions.md](decisions.md)：大方向决策 D1–D9、需求 × 数据来源对照、现状缺口 G1–G6
- [department-data-summary.zh.md](department-data-summary.zh.md)：各部门数据需求（Albar 整理，2026-11-11）。下文沿用其编号：S1–S6、电商 #n、内容 #n、市场 #n、产品 #n
- [research/technical-analytics-pipeline-research-2026-11-11.md](research/technical-analytics-pipeline-research-2026-11-11.md)：技术概况与体量估算

**范围**：需求对照中的 **B 类（只靠埋点）和 C 类（埋点关联业务库）** 指标，以及缺口 G1–G6。**A 类（只靠业务库）不在本 PRD**，另做口径文档（见 §5）。

**约定**：
- 术语以 §3 为准。
- 文中 `Dn` 一律指 decisions.md 的决策；项目级护栏写全称（见根目录 `architecture.md`）。
- 推断未确认之处标 `[ASSUMPTION]`，与开放问题一起汇总在 §9。
- 数值阈值只在一处定义，其他地方引用编号。
- PRD 阶段的决定及其演变记在 `.decision-log.md`。

## 1. 愿景

PostHog 停用后，App 的行为数据需要一个自己的归宿。本项目把 App 埋点改发到自家后端，存进自己的 Postgres 埋点库，按「原始 → 明细 → 汇总」分层，团队通过已上生产的 AI 查数直接问数，不再依赖第三方看板。

定位是**日活一万以内的过渡方案**：省钱、少运维、零新中间件。体量涨到约 10 倍时考虑切回付费第三方，所以从第一天起就按「以后能搬走」来设计：App 只经 `Analytics` 门面上报，事件格式对齐业界通用结构，指标口径写成文档。

成功的样子：四个部门在 [department-data-summary.zh.md](department-data-summary.zh.md) 里列出的 B、C 类数据，每天早上都能从 AI 查数拿到，且与口径文档一致；自建日活与 GA4 日活对上账之后，日活也切到自建口径。

**过渡期**：V1.5.0 起新版 App 只发自建、不双写，旧版本的数据不进自建库；新版覆盖率爬升期间，日活等全量口径以 GA4 为准（FR-24）。

## 2. 目标用户

### 2.1 要完成的事（JTBD）

- **各部门（电商、内容运营、市场、产品）**：每周、每月按固定口径拿到自己的指标，不必找开发写 SQL。
- **Albar（产品）**：看安装 → 注册 → 建档的转化和新用户留存，评估 OKR。
- **Dai（负责人）**：确认自建数据可信（与 GA4 日活对账），且不拖累业务库和服务器。
- **AI 查数**：有结构清晰、口径有文档的汇总表和明细表可查。

### 2.2 不服务的对象

- App 终端用户：无感知，不新增任何用户可见的功能。
- 广告归因：AppsFlyer、Meta、TikTok 的归因上报**不受影响**，继续走各自的 SDK。

### 2.3 关键场景

- **UJ-1. 电商周一早上看上周的 Toko 漏斗。** 电商同事在飞书问 AI 查数「上周 Toko 漏斗和加购转化率」。AI 查数读汇总表，返回七步漏斗（浏览 Toko 页 → 商品展示 → 详情 → 加购 / 立即购买 → 提交订单 → 点击支付 → 支付成功）每一步的去重人数和逐步转化率（电商 #6），以及加购后 7 天内支付的比例（电商 #5），数字与口径文档一致。**边界情况**：某一步的事件在旧版本 App 里不存在 → 结果注明「仅统计运行 V1.5.0 及以上版本的人」。
- **UJ-2. 市场看上周的 D1 / D7 留存。** 市场同事问「上周每日安装组的 D1、D7 留存」。系统按首次 `Application Installed`（不含升级）分组，统计第 X+1 / X+7 天是否有 `Application Opened`（市场 #1–#3）；未登录期间的事件通过匿名 id 关联到注册后的用户。
- **UJ-3. Dai 查日活对账。** Dai 在 AI 查数里问「最近两周的日活对账」，拿到每天的自建日活（含游客）、GA4 日活（含游客）、差值百分比和新版覆盖率，超阈值的日子标为异常。连续出现异常时进入排查。

## 3. 术语

- **事件**：App 或后端在某一时刻上报的一条行为记录，含事件名、事件 id、三种时间、身份（匿名 id、用户标识）、属性、环境上下文。
- **事件 id**：客户端为每条事件生成的唯一 id，用于去重。
- **发生时间 / 发送时间 / 收到时间**：事件在设备上发生的时间、批次从设备发出的时间、后端收到的时间（对应 Segment 的 `timestamp` / `sentAt` / `receivedAt`）。
- **匿名 id**：设备首次启动时生成并持久保存的随机 id，未登录和已登录时都携带。
- **用户**：已登录的账号。登录状态下的事件携带用户标识。
- **游客**：未登录状态下使用 App 的人。
- **身份关联**：一条「匿名 id ↔ 用户」记录，在某台设备上首次登录（或切换账号）时产生。
- **人**：按人去重统计时的计数单位。已登录、或能经身份关联归到某个用户的，按用户计；始终未登录的，按匿名 id 计。
- **批次**：App 一次上报的一组事件。
- **原始层**：后端收到什么就存什么，按天分区；保留期见 FR-12。
- **明细层**：清洗、补全后的逐条事件；保留期见 FR-13。
- **汇总层**：按天 / 人 / 功能 / 漏斗预先算好的指标结果，长期保留，是明细层保留期以前数据的唯一来源。
- **生产数据**：符合 [department-data-summary.zh.md](department-data-summary.zh.md) §0 通用规则的数据，即排除 staging 包、模拟器、TestFlight、侧载安装、内部员工、管理员、虚拟账号和测试账号。
- **新版覆盖率**：某天发生 `Application Opened` 的设备中，运行 V1.5.0 及以上版本的比例，从 GA4 按 App 版本取得。
- **口径文档**：每个指标的定义、数据来源、排除规则、已知偏差和计算 SQL 位置，供人和 AI 查数共同使用。
- **日活**：当天有 `Application Opened` 的去重人数，默认含游客。分「自建日活（含游客）」「GA4 日活（含游客）」两个来源；另有只计已登录用户的「登录用户日活」（`user_active_days`），仅作参照。
- **对账**：每天比对自建日活（含游客）与 GA4 日活（含游客）。

### 4.1 App 端采集

**描述**：`Analytics` 门面背后的发送端从 PostHog SDK 换成自建上报器。业务代码里现有的约 191 种事件调用、`ButtonId` 白名单，以及 PII / 自由文本剥离规则，一律不动。新版 App 随 V1.5.0 发版，**直接切换，不双写**。

#### FR-1：门面换发送端

App 的全部埋点都经 `Analytics` 门面发往自建后端，不再初始化 PostHog SDK。

**可验证结果：**
- 新版 App 不再向 PostHog 发出任何网络请求。
- 业务代码里的事件调用点无需改动（门面接口签名不变）。
- 现有的 PII 键黑名单、自由文本键黑名单和字符串长度上限在新发送端继续生效，命中的属性不上报。
- 金额类属性（价格、订单金额）允许上报，因为数据进的是自有库；PII 和健康数据仍一律剥离。
- 上报失败不抛异常，不阻断主流程（沿用现有约束）。

#### FR-2：本地攒批与补发

App 先把事件存进本地队列，再按条数或时间批量上报；切到后台、网络恢复时补发。

**可验证结果：**
- 默认每 20 条或每 30 秒发一批，以先到者为准。`[ASSUMPTION A1]`
- App 切到后台时，立即尝试发送队列中的事件。
- 断网期间事件留在本地，网络恢复后补发；App 被杀后重启，仍能补发未发送的事件。
- 本地队列有上限（如 1,000 条或 7 天），超出时丢弃最旧的事件。`[ASSUMPTION A2]`
- 后端返回成功之前，事件不从本地删除；重复发送由后端按事件 id 去重（FR-9）。
- 每条事件在**发生的那一刻**就记下当时的身份（匿名 id、用户标识）。之后即使切换账号或登出再补发，事件仍归属原来的身份，不会记到新账号头上。

#### FR-3：生命周期事件自实现（G1）

App 自己上报 `Application Installed`、`Application Updated`、`Application Opened`，事件名和含义与 PostHog 一致，团队口径无需改动。

**可验证结果：**
- **新装**：设备上既没有自建安装标记、也没有旧版 App 留下的任何本地数据时，首次启动上报 `Application Installed`，并写入安装标记。
- **升级**：从旧版升级到 V1.5.0 的设备（有旧版本地数据、没有自建安装标记），首次启动上报 `Application Updated`，**不报 `Application Installed`**；此后版本号每次变化也报 `Application Updated`。
- 每次冷启动，以及每次从后台回到前台，都上报 `Application Opened`（已核实与 PostHog 原生 SDK 行为一致），并带「是否从后台恢复」属性。
- 口径文档注明：卸载重装会算作一次新装。这与 PostHog 的行为相同，但与应用商店的安装数不同。

#### FR-4：页面浏览事件（G2）

App 用自有的路由观察者上报页面浏览，取代 `PosthogObserver`；页面名沿用现有命名（如 `toko_page`）。

**可验证结果：**
- 现有的 `Analytics.screen()` 调用和路由切换都会产生页面浏览事件，页面名与 PostHog 时期相同。
- 底部 Tab 切换（走 `goBranch`，不走路由 push）和冷启动落地页同样产生页面浏览事件（沿用现有的补报逻辑）。

#### FR-5：身份携带

每条事件都带匿名 id，已登录时再带上用户标识；登录或切换账号时上报一次身份关联。

**可验证结果：**
- 匿名 id 在设备首次启动时生成，卸载前不变，登出也不重置。`[ASSUMPTION A3]`
- 用户标识采用不可枚举的形式（对齐「对外标识不可枚举」护栏），由后端映射回内部用户。`[ASSUMPTION A4]`
- 同一台设备先后登录 A、B 两个账号，会产生两条身份关联；登出之后的事件只带匿名 id。
- 切换账号之前，先尝试把队列中属于上一个账号的事件发出去（配合 FR-2 的身份绑定）。

#### FR-6：环境标记（G6）

每条事件都携带足以判定「是否生产数据」的环境上下文。

**可验证结果：**
- 事件带 App 版本、构建号、平台（Android / iOS）和系统版本。
- 事件带渠道标记，能区分生产包与 staging 包、真机与模拟器、应用商店安装与 TestFlight / 侧载安装。`[ASSUMPTION A5]`
- staging 包的事件发往 staging 后端，不进生产埋点库。

### 4.2 后端接收

**描述**：在现有 Spring Boot 后端内新增一个独立的埋点接收模块（D1），不另起服务，也不加中间件。请求到达后先校验、放入内存队列并立即返回成功，再按条数或时间批量写入原始层（D2）。

#### FR-7：批量接收接口

后端提供一个接口，接收 App 上报的批次。

**可验证结果：**
- 单批事件数、单条大小、单个请求大小都有上限，超限返回 400 并说明原因。`[ASSUMPTION A6]`
- 格式错误的单条事件会被拒收，同批其他合法事件照常收下，响应中说明被拒的条数。
- App 在已登录和未登录状态下都能上报（未登录时的事件是日活和安装留存的必需数据）。

#### FR-8：防刷与限流

接收接口能抵御伪造和刷量，且不拖累业务接口。

**可验证结果：**
- 按单个设备 / IP 限制上报频率，超限返回 429 并带 `Retry-After`。IP 只在内存中用于限流，**不落库**。
- 后端把事件中声明的用户标识，与请求携带的登录凭证和身份关联记录对照，不能借此冒充他人；校验不通过的事件丢弃并计数。`[ASSUMPTION A7]`
- 被刷或高负载时满足 §4.7「不拖累业务」，实现手段可以是独立线程池或资源配额。

#### FR-9：去重与时间校正

后端按事件 id 去重，并校正设备时钟偏差。

**可验证结果：**
- 同一事件 id 重复上报，只保留一条（在原始层还是明细层去重，由架构定）。
- 后端用「收到时间 − 发送时间」校正设备时钟偏差，明细层同时保留原始发生时间和校正后的发生时间。
- 校正后的发生时间晚于收到时间，或早于收到时间超过本地队列时限（A2）的事件，标为可疑，不进汇总。

#### FR-10：内存队列与批量写库

后端先把事件放进内存队列，再批量写库。

**可验证结果：**
- 事件进入内存队列后立即返回成功，再按条数或时间（如 500 条 / 数秒）批量写入原始层。
- 内存队列有上限；队列满时返回 503，由 App 稍后重试，不会无限占用内存。
- 正常停机（发版）时，先停止接收，把队列写完再退出；崩溃或被强杀时丢失的数秒数据可以接受（D3）。

### 4.3 存储与分层

**描述**：在现有 `petgo-postgres` 实例内单独建一个埋点库（D4），与业务库隔离，使用独立账号和连接配额。数据分三层存储，分区由后端定时任务预建和清理。

#### FR-11：独立埋点库

埋点数据存在独立的库里，与业务库隔离。

**可验证结果：**
- 埋点数据不写进业务库 `petgo`；生产和 staging 各有自己的埋点库。
- 埋点相关的连接（接收写入、汇总任务、AI 查数）总数有上限，在实例 `max_connections=100` 内单独划出配额，满载时不挤占业务库的连接。`[ASSUMPTION A8]`
- 埋点库不与业务表建外键；需要的业务字段复制进来。

#### FR-12：原始层

原始层按天分区，保留 35 天。

**可验证结果：**
- 未来几天的分区提前建好，不会因为缺分区导致写入失败。
- 超过保留期的分区整块删除（D5），不做归档。
- 分区建删任务失败时记录错误日志并告警（沿用项目「告警走日志」的做法），不影响接收。

#### FR-13：明细层

明细层保留 3 个月，由原始层清洗、补全而来，包括去重、时间校正、身份补全和生产数据标记。

**可验证结果：**
- 事件收到后 10 分钟内进入明细层，AI 查数能查到当天的数据。
- 每条明细事件都带「是否生产数据」标记，依据 FR-6 的环境上下文和后端维护的内部账号名单。
- 超过保留期的明细数据按分区删除（D6）；更早的数据**只保留汇总层**。
- 明细层可以从原始层重算其保留期内（FR-12）的数据，用于修正口径后回算。
- 设备、系统版本等重复的上下文按设备只存一份，事件里只放引用，以控制单行体积。`[ASSUMPTION A9]`

#### FR-14：身份关联表

保存全部身份关联，用于把匿名事件归到用户。

**可验证结果：**
- 保存全部「匿名 id ↔ 用户」关联及其首次关联时间。
- 按「人」计数的指标中，登录前的匿名事件通过关联表归到对应用户，**不回写**历史事件。
- 一个匿名 id 关联了多个用户（换过账号）时，按事件发生时间判定当时属于谁。

#### FR-15：注销匿名化

用户注销时，对其埋点数据做匿名化，与业务侧的注销级联同步执行（项目架构护栏「注销级联删除 / 匿名化」）。

**可验证结果：**
- 注销后，该用户的身份关联记录被删除，明细层和原始层中该用户的用户标识被清空。
- 已算好的汇总结果不变（汇总层不含可识别个人的字段）。
- 匿名化在注销流程完成后 24 小时内生效；执行失败可重试，并记录日志。`[ASSUMPTION A10]`

#### FR-16：存储水位

每天监测埋点库的占用，超过上限时告警。

**可验证结果：**
- 每天记录生产与 staging 埋点库的占用和月增长。
- 埋点库总占用超过上限（如 40 GB）时告警。`[ASSUMPTION A11]`
- 月事件量或占用持续接近研究估算值的 10 倍时，告警中提示「评估切回第三方」，即 §1 定位中的切换触发线。

### 4.4 埋点补齐

**描述**：补上团队指标需要、但当前还没有的事件。

#### FR-17：运营位曝光与点击（G4）

S5 要求的每个弹窗和 banner 都有曝光事件和点击事件，并带运营位 id。

**可验证结果：**
- 现已覆盖：运营弹窗（`ops_popup_shown` / `ops_popup_tapped`）、Toko banner（`toko_banner_shown` / `toko_banner_tapped`）和新人券弹窗。
- 逐一核对其余运营位，缺曝光或点击的补齐；曝光沿用 Toko banner 的定义：「实际露出超过 50% 计一次」。`[ASSUMPTION A12]`
- 曝光和点击都带运营位 id，能与后台配置关联，以判断该运营位是否推广 Toko。

#### FR-18：推送打开统一事件

任何推送被点开时，都上报同一个打开事件，带推送类型；运营通知另带推送 id。

**可验证结果：**
- 运营通知、券过期提醒、点赞、评论、订单、等级等全部推送类型，被点开时都上报这个统一事件，并带推送类型。
- 运营通知的打开事件带推送 id，可按单条推送算打开率；系统推送按类型统计打开数。
- 现有的 `ops_notification_opened`、`toko_coupon_expiry_push_opened` 可以保留，但统计以统一事件为准。

#### FR-19：购物车事件补全（G5）

`shop_cart_items` 表的记录是物理删除的，没有删除时间，因此要补全购物车事件来支撑电商 #7。

**可验证结果：**
- 加购事件带商品 id、数量和单价。
- 新增「移出购物车」事件：手动删除或清空失效商品时，按商品各报一次，带商品 id、数量和原因。
- 新增「修改数量」事件，带商品 id 及修改前后的数量。
- 商品下单成功后离开购物车，不算「移出购物车」，以订单数据为准。

#### FR-20：漏斗与引导事件核对

核对团队指标引用的事件名都真实存在，且口径一致。

**可验证结果：**
- 电商 #6 漏斗、产品 #1（`pet_profile_create_submitted`）、产品 #5（`onboarding_completed`）用到的每个事件名都在代码中存在，口径与团队文档一致；不一致的，以代码为准修正口径文档，并告知团队。

### 4.5 指标汇总与口径

**描述**：把 B、C 类指标按 T+1 算进汇总层，并为每个指标写好口径。

#### FR-21：T+1 汇总

每天计算前一天的汇总。

**可验证结果：**
- 每天 WIB 凌晨计算前一个 WIB 自然日的汇总，覆盖 B、C 类的全部指标（清单见 [decisions.md](decisions.md)「需求 × 数据来源对照」），并遵守 §4.5.1 的口径要点。
- 汇总任务失败后可以重跑，重跑结果相同（幂等）；按已完成汇总的最后日期（进度点）续算，不重不漏；失败时记录错误日志并告警。
- 只统计生产数据（FR-13 标记），按「人」去重。
- 汇总层长期保留，结果中不含可识别个人的字段。

#### 4.5.1 口径要点（团队定义，汇总必须遵守）

| 口径 | 规则 | 涉及指标 |
|---|---|---|
| 时区与日 | WIB 自然日 | 全部 |
| 周 | 周一至周日；周合计 = 每日值之和，周均值 = 周合计 ÷ 天数；另含最高日、最低日，以及工作日与周末的均值 | S1 |
| 日去重不跨天相加 | 不能把每日去重人数相加当作周去重人数 | 全部按人计的指标 |
| 月比率 | 取每日比率的平均值 | S4、产品 #3 |
| 新装 | 首次 `Application Installed`，不含升级；分 Android / iOS | S2、S3、市场 #1–#3、产品 #1 |
| D1 / D3 / D7 留存 | 第 X 天安装组中，第 X+N 天再次打开的比例；只统计已满 N 天的组；按周汇总时按各组人数加权 | 市场 #1–#3 |
| 新用户 W1 留存 | `onboarding_completed` 之后第 7–13 天内任意一天打开过 | 产品 #5 |
| Toko 漏斗 | 7 天内按顺序经过各步的去重人数；转化率 = 本步 ÷ 上一步；最后一步「支付成功」取业务库 `PAID` | 电商 #6 |
| 加购转化 | 加购后 7 天内完成支付的去重人数 ÷ 加购的去重人数 | 电商 #5 |
| 购物车停留 | 从加购到购买或移出购物车；仍在车里的，算到统计周期结束；价值 = 单价 × 数量 | 电商 #7 |
| 运营位带单 | 点击后 7 天内的已支付 Toko 订单数 | S5 |
| 新用户 / 回访 | 新用户 = 当天注册；回访 = 当天日活 − 当天新用户 | 内容 #1 |

#### FR-22：C 类指标关联业务数据

S4、内容 #1、电商 #5、#6（最后一步）、#7、#9，产品 #2、#3，以及 S5 的「7 天内订单」，都需要把埋点与业务库的订单、商品、支付状态拼起来。

**可验证结果：**
- 由后端汇总任务分别读业务库和埋点库，拼好后写进埋点库；不用跨库扩展（见 §5），不建外键。
- 这些指标的汇总结果，与直接查业务库得到的已支付订单数一致（只计 `PAID`）。

#### FR-23：推送触达口径

S5 推送部分的发送、接收、打开数各有来源。

**可验证结果：**
- 运营通知的发送数和接收数取后端发送记录（`ops_notification_campaigns` 等）；接收数 = 下发成功数，口径文档注明这是近似值。
- 系统推送（券过期、点赞 / 评论等互动、订单、等级等）的发送数取各自的发送记录；没有发送记录的类型只统计打开数，并在口径文档中注明。`[ASSUMPTION A13]`
- 打开数取 FR-18 的统一打开事件。

#### FR-24：日活来源

规定 D9「日活以 GA4 为准」在库内如何落地。

**可验证结果：**
- 后端每天把 GA4 日活（含游客）和新版覆盖率写进埋点库（复用现有日报的 GA4 接入）。
- **对账观察期内**，S1 日活，以及以日活为分母或减数的指标（S4、内容 #1、产品 #3），一律使用 GA4 日活（含游客）；自建日活（含游客）只用于对账。
- 对账通过后（FR-25），由 Dai 决定是否切换；切换后，上述指标改用自建日活（含游客），口径文档记下切换日期。

#### FR-25：每日对账

每天比对自建日活与 GA4 日活。本条是对账阈值的唯一定义。

**可验证结果：**
- 每天产出：自建日活（含游客）、GA4 日活（含游客）、差值百分比、新版覆盖率，并附上登录用户日活作参照。差值百分比 =（自建 − GA4）÷ GA4。
- 新版覆盖率 ≥ 90% 之后开始观察期，为期 4 周；差值百分比的绝对值 ≤ 10% 为正常，超过即标为异常。
- 对账结果存进埋点库，供 AI 查数查询；**不推送飞书日报**。

#### FR-26：口径文档

为 B、C 类每个指标写口径，供人和 AI 查数共用。

**可验证结果：**
- 每个指标都有口径条目：团队编号、定义、数据来源（表 / 事件）、排除规则、已知偏差、计算 SQL 位置。
- AI 查数能读到口径文档，回答时按文档的口径计算。
- 口径变更有记录（日期、原因）。

### 4.6 AI 查数接入

#### FR-27：只读访问埋点库

AI 查数用独立的只读账号访问埋点库。

**可验证结果：**
- 为 AI 查数新开埋点库只读账号（与业务库的只读账号分开），可读明细层、汇总层、身份关联表、对账结果和口径文档，不能写。
- 原始层是否开放，由架构按查询压力决定。
- 跨库问题（如「某商品的浏览量和销量」）由 FR-22 预先拼好的汇总表回答，AI 查数自身不做跨库查询。

### 4.7 跨功能非功能要求

- **不拖累业务**（性能阈值的唯一定义）：埋点接收、写库、汇总任务上线后，业务接口 P95 响应时间增幅不超过 10%；汇总任务在 WIB 凌晨低峰运行。
- **零新组件**：技术禁令以 §5 为准；异步只用 `@Async` + DB 状态机（项目护栏）。
- **隐私**：不存 PII、健康数据和 IP；用户标识不可枚举；注销后匿名化（FR-15）；日志不记录事件里的用户标识。
- **可搬走**：事件字段语义对齐 Segment（事件名、事件 id、三种时间、匿名 id、用户标识、属性、环境上下文），可以整体导出给第三方。

## 5. 非目标

- **A 类指标不进埋点管道**：S6 收入，电商 #1、#2、#3、#10，内容 #2–#8，产品 #4 只靠业务库，另写口径文档给 AI 查数，可以先于本项目交付。
- 不做可视化看板，消费方式是 AI 查数（D8）；对账结果不推飞书。
- 不替代广告归因（AppsFlyer、Meta、TikTok）。
- ~~不迁移服务端事件~~（架构阶段 2026-11-12 推翻）：现有经 `AnalyticsClient` 发往 PostHog 的服务端事件改走自建管道，直接替换实现、不双写（PostHog 已停用），上线后用业务库核对；口径上支付成功等仍以业务库为准。见 architecture.md「过渡与收尾」。
- **技术禁令（唯一清单）**：不引入 Firebase / BigQuery、TimescaleDB、ClickHouse、pg_partman、pg_cron、dblink / postgres_fdw，也不引入任何新中间件或数据库扩展。
- 不归档原始数据，不迁移 PostHog 历史数据，不改旧版本 App。
- 不做会话回放、热图、实时大屏。

## 6. MVP 范围与上线顺序

MVP 包含 FR-1 至 FR-27，按 §4.0 总览表的批次分两批上线：

- **① 随 V1.5.0 必须就绪**：后端接收与存储，须**先于 V1.5.0 App 上生产**；App 端采集和埋点补齐随包发布。
- **② 发版后可补**：存储水位、汇总、口径、对账、AI 查数接入。这时数据已经在明细层，晚算不会丢。

范围外内容见 §5。

## 7. 成功指标

**主要**
- **SM-1 指标可答率**：团队清单中 B、C 类指标 100% 能由 AI 查数按口径文档回答。验证 FR-21、FR-22、FR-26、FR-27。
- **SM-2 日活对账**：FR-25 定义的观察期内，每一天都为「正常」。验证 FR-3、FR-5、FR-13、FR-25。

**次要**
- **SM-3 数据完整性**：同一时段、运行 V1.5.0 及以上版本的人范围内，明细层「点击支付」事件的人数 ≥ 业务库支付成功人数的 95%，用于抽检端上丢事件的比例。`[ASSUMPTION A14]` 验证 FR-2、FR-10。
- **SM-4 资源占用**：埋点库总占用低于 FR-16 的上限，且 §4.7「不拖累业务」在生产环境成立。验证 FR-8、FR-11、FR-16。

**反向指标（不追求）**
- **SM-C1 事件数量**：不追求多埋事件、多存字段；新增事件必须对应团队清单里的指标。制衡 SM-1。
- **SM-C2 实时性**：不追求分钟级汇总。T+1 足够，换来的是更低的库压力和复杂度。制衡 SM-1。

## 8. 风险

- **新版覆盖率爬升慢**：观察期何时开始取决于升级速度，可能拖到发版后数周。缓解：观察期内日活以 GA4 为准（FR-24），不阻塞团队用数。
- **升级判定有误差**：清除过旧版本地数据的升级用户，会被算作新装。缓解：在口径文档中列为已知偏差；上线首周把新装数与应用商店数据对比。
- **单条事件体积超出估算**：占用可能超出磁盘预算。缓解：上线前实测，并由 FR-16 水位告警兜底。
- **新指标最多只能回算 3 个月**：明细层只留 3 个月，以后新增的指标最多回算 3 个月的历史。缓解：汇总层在上线时就覆盖团队清单的全部 B、C 类指标；同比和长周期留存只能基于已有的汇总。
