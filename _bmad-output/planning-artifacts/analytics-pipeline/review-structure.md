# prd.md 结构编辑评审

> 评审对象：`prd.md`（2026-11-11 草稿）
> 方法：bmad-editorial-review-structure（只提建议，不改原文）
> 约束：FR-1~FR-27、UJ-1~UJ-3、SM-1~SM-4 / SM-C1~C2 编号**一律保留**，下面的合并、挪位都按原编号操作；已拍板的决策内容一条不删。

## 文档概况

- **用途**：自建埋点的需求规格。读者照着它写架构 delta 和 story，并据此确认范围、上线顺序、待定项。
- **读者**：Dai（拍板）+ 下游架构 / story 编写者（含 LLM agent，会按编号精确引用）
- **读者类型**：人（为下游 agent 额外看重「不歧义、单一来源」）
- **结构模型**：Strategic/Context（金字塔）为主，§4 功能部分按 Reference 模型（每条 FR 格式一致、可随机查阅）
- **当前篇幅**：约 6,400 汉字 + 560 个英文词，11 个一级章节、约 45 个小节
- **总体判断**：骨架健康，FR 粒度和「可验证结果」写法适合下游拆 story。问题集中在四处：①同一事实写了多遍（数值阈值、技术禁令、范围排除），以后改一处就会漏另一处；②§4.8 口径表和 §6 上线分批放得太靠后，离用到它们的地方太远；③§9 开放问题和 §10 假设索引是两张重叠的清单；④决策编号「D1/D2」有两套含义。

## 建议（按优先级排序）

### 1. 【高 · QUESTION/改名】FR-15 里的「护栏 D1 / D2」和 decisions.md 的 D1 / D2 撞名

- **位置**：§4.3 FR-15 描述句「与业务侧注销级联（护栏 D1 / D2 注销规则）同步执行」
- **改法**：改成不会混淆的写法，例如「（项目架构护栏的注销级联 / 匿名化规则，见根 `architecture.md`）」；或者在 §0 加一句：「本文 Dn 均指 decisions.md 的决策；项目级护栏另写全称」。
- **理由**：本文其余地方的 D1~D9 都指 decisions.md（D1 = 后端内接收模块，D2 = 攒批），只有 FR-15 的 D1/D2 指项目护栏的注销规则。下游 agent 按编号引用时很可能把 FR-15 关联到「独立接收模块 / 攒批」，而注销恰好是安全攸关点。
- **篇幅影响**：+10 字

### 2. 【高 · MOVE】§4.8 口径要点表挪进 §4.5，紧跟 FR-21

- **位置**：§4.8（现在排在 FR-27 和 §4.7 非功能要求之后）
- **改法**：把整张表移到 §4.5，放在 FR-21 后面，作为 §4.5 的子节「口径要点」（可编号 §4.5.1）；表格内容不动。FR-21 里的「见 §4.8」相应改掉。
- **理由**：这张表是 FR-21 / FR-22 汇总任务的输入规则，也是 FR-26 口径文档的种子。现在它被 AI 查数（§4.6）和非功能要求（§4.7）隔开，写汇总 story 的人要来回翻；放在 §4 末尾还容易被当成附录。
- **篇幅影响**：0

### 3. 【高 · MERGE】§9 开放问题与 §10 假设索引合成一张「待定项」表

- **位置**：§9、§10
- **改法**：合成一节「§9 待定项与假设」，用表格列出：`#` | 位置（FR/SM） | 内容 | 由谁定（架构 / 上线前实测 / Dai / 运营）| 是否阻塞 V1.5.0（对应 §6.1）。§10 的 12 条与 §9 的 5 条去重后约 14 行。正文里的 `[ASSUMPTION]` 标记保留。
- **理由**：两节有 3 组内容重复（FR-6 侧载识别、FR-17/FR-23 清单、FR-16 占用上限），而且各自缺一半信息：§10 不写谁来定，§9 不写对应哪条假设。下游最需要的是「哪些要在架构阶段关掉、哪些阻塞发版」，现在两节都答不了。顺带补一条现在漏掉的依赖：FR-9「早于收到时间超过 7 天算可疑」依赖 FR-2「本地队列上限 7 天」这条假设，两处应一起改。
- **篇幅影响**：约 −150 字，但增加了「由谁定 / 是否阻塞」两列

### 4. 【高 · MOVE+CONDENSE】在 §4 开头加 FR 总览表，并把 §6 上线分批并进表里

- **位置**：§4 开头（新增）；§6.1 / §6.2
- **改法**：在 §4 标题下加一张总览表：FR 编号 | 名称 | 所在小节 | 对应缺口 G / UJ | 上线批次（随 V1.5.0 必须就绪 / 发版后可补）。§6 精简为两句：「随 V1.5.0 必须就绪：总览表中批次 = 必须就绪的项，且后端先于 App 上生产；其余发版后可补，理由是数据已进明细层、晚算不丢。」§6 的小节标题和这句理由保留（这是已拍板的分批决策）。
- **理由**：金字塔结构要求范围和交付顺序前置。现在 story 编写者要读完 27 条 FR 再翻到 §6，才知道哪些属于 MVP；而且 §6.1 用「FR-7 到 FR-15」这种区间写法，FR 一旦挪位或增删就容易失效。总览表把 FR ↔ 批次 ↔ G ↔ UJ 一次对齐，sprint-status 排序也可以直接用。
- **篇幅影响**：+约 250 字（表格），−约 100 字（§6）

### 5. 【中 · MERGE】「业务接口 P95 增幅 ≤ 10%」只保留一处定义

- **改法**：§4.7 作为唯一定义（NFR-性能）。FR-8 第 3 条改成「满足 §4.7 不拖累业务（实现手段：独立线程池或资源配额）」；SM-4 改成「§4.7 的 P95 约束在生产成立」。
- **理由**：同一阈值写了三遍。它本来就是跨功能约束而不只是防刷，放在 FR-8 里还会让人以为只有被刷时才要满足。
- **篇幅影响**：约 −40 字

### 6. 【中 · MERGE】技术禁令只留一份清单

- **位置**：§4.3 描述「不装扩展」、FR-22「不装跨库扩展（dblink / postgres_fdw）」、§4.7「零新组件」、§5 第 5 条（具体技术名单）

- **理由**：同一条禁令散在四处，措辞也不统一（扩展 / 中间件 / 组件），下游自查时不知道以哪份为准。
