# TailTopia V1.1.4 - Epic Breakdown（Delta）

## Overview

本文件是 V1.1.4 **增量** epic/story 分解，承接 PRD（定稿 + 2026-08-15 校验订正）、**架构 delta（AD-1 ~ AD-20，权威）**、UI 视觉稿（28 屏 / 4 泳道）与跨 story 决策台账。

**V1.0 / V1.1 / V1.1.2 已上线冻结；未提及处一律继承。**
冲突序：**架构 delta > 本文件 > PRD > 决策日志 > CROSS-STORY-DECISIONS > V1.0/V1.1/V1.1.2 基线**。

> ⚠️ **决策日志只作留痕，其中 5 条已被推翻**（C-32 / C-33 / C-36 / C-64 / C-78），另 **C-50 的存储建议已被 PRD 正文取代**（它说「一对(举报人,账号)只存一行 + 次数累加」，但 PRD 重复举报要求第 3 条要求留存每次的类型与说明，一行存不下 → 架构 AD-2 取 PRD）。

核心主题 = **让「我不想看见某个人」这件事在全 App 各处都算数**。举报与拉黑在产品上是两种意图，落到实现上产生的是**同一种隐藏关系**，被四处读取（首页过滤 / 评论 R1·R2 / 互动通知抑制 / 主页访问校验）。

**⚠️ 硬前置：AB-3D 运营后台必须与 FR-58 同版本交付**，否则用户能提交举报、运营无处处理，功能上线即空转。

> **现行口径**：D1 设置页的计数由**列表长度派生**。代价是进设置页会为显示计数发一次小请求 —— 列表极小、设置页非热路径，可接受。

  - **账号维度五类理由（单选，禁复用内容维度枚举）**：垃圾信息/恶意营销 · 仿冒他人 · 持续骚扰 · 发布违规内容 · 其他。**选「其他」必填补充说明（≤200 字）**，其余四类不给说明框。
  - **二次确认须明示「提交后无法撤销」**（C-92）——只说不可撤销、**不说会隐藏**。
  - **举报即隐藏（方案甲）**：举报成功后该账号全部内容与评论立即对举报人隐藏；隐藏范围 = FR-94 生效范围全部六条，**唯一例外是「主页访问」仍可进入**（C-67，闭环需要它）。
  - **「立即」必须兑现在当前这一屏**（C-93）：点关闭收起流程时**移除该作者在当前列表的全部可见卡片**；从详情页进入的**先退回上一级列表**再移除；**移除静默、不给任何提示**。
  - **举报隐藏永久不可解除、不进黑名单页**（C-68）。
  - **影子评论（R2）同样因举报触发**（C-66）——被举报者在举报人内容下的评论对所有人隐藏。
  - **重复举报四条要求（缺一不可）**：① 按人去重（同一举报人对同一账号在工单列表只占一条）② 保留次数（供优先级公式判高频）③ **保留每一次的举报类型与「其他」补充说明**，后台按时间倒序展示全部 ④ 单人贡献封顶由公式保证，**不另设 24 小时冷却**。⚠️ **不得照抄内容举报「重复举报幂等吞掉」的实现**。
  - **「已举报」状态服务端持久化**（重启 App 不丢），显示在迷你卡与黑名单页；按钮仍可点、允许重复举报；二次确认副标题换成重复举报说明，**类型不预填上次选择**。
  - **处置动作两档：警告 / 封号**（限流曝光随 FR-95 移至 1.1.8）。
    - **警告**（C-94）= 一条系统通知；**不告知**举报人/具体内容/第几次；**可重复下发、不合并不去重**；**每次写入该账号历史违规记录**；**不自动升级**；不需要异议渠道。
    - **封号** = 账号禁用无法登录；通知告知如有异议可联系客服（走 FR-52 通用客服工单，**不建独立申诉工作流**）。
  - **零自动预处置**（C-88）：账号举报一律人工，**不设任何达阈值自动挂起该账号内容的通道**；既有帖子级两条自动通道保持不变。
  - 运营处理后按 FR-51 通知举报人（不透露处置结果）；举报行为对被举报人不可见；**用户不可举报自己**。

- **FR-94**：用户拉黑（单向屏蔽 + 影子评论，本版本新增）。
  - **入口三处**：迷你卡「⋯」菜单 · 举报流程自动产生（无需用户额外操作）· 评论区头像（同 FR-58）。
  - **生效范围六条（仅作用于发起方，即时生效）**：① Feed 候选池硬过滤 ② 运营干预位（通用规则，本版本平台无此类位、不触发）③ 评论区 R1 + R2 ④ **主页访问（唯一按来源区分的一条，只有主动拉黑禁止）** ⑤ 搜索/话题聚合等列表 ⑥ **来自被拉黑方的互动通知一律不发**。
  - **R1 按查看者隐藏**：评论作者被当前查看者隐藏 → 该评论对其不展示，**直接不展示、不占位、不显示占位符**；**照常计入评论数**。
  - **R2 影子评论**：评论作者被**该内容的作者**隐藏 → 该评论**仅评论作者本人可见**，对内容作者与第三方一律不展示；**其整条回复串一并隐藏**；**不计入对外评论数与互动量**。评论作者自己看到的是「发布成功、评论就在那里」的正常状态。
  - **通知抑制三类**：赞我的内容 / 评论我的内容 / 回复我的评论。**是「不发」不是「发了再隐藏」**（未读角标不 +1）；**解除拉黑不补发**；拉黑前的历史通知**不回溯清理**。
  - **迷你卡三处既有行为调整**：① 已主动拉黑 → 不弹卡 + Toast（**独立分支**）② **拉取失败由静默不弹改为 Toast**（⚠️ 变更既有行为，须改原 catch）③ 已注销仍不弹卡（不变）。
  - **两种隐藏来源并存的行为**（C-89 / C-90 / C-91）：先拉黑后举报 → 两条并存、举报不覆盖拉黑；**先举报后拉黑 → 照常建立拉黑关系、照常进黑名单页**（幂等只在同源之间生效）；**解除拉黑只拿掉主动拉黑那一层，被举报过的人内容依旧不可见**，提示用第二句文案；解除后**主页恢复可进入**（与内容可见性相反，属预期）。
  - **黑名单管理**：「我的」→ 设置 → 黑名单；**只收录含主动拉黑的条目**；头像+昵称+拉黑时间，按拉黑时间倒序；逐条解除（二次确认）；**每项提供行内「⋯」举报入口**（不用滑动手势，C-79）；已注销条目匿名态、去点击态、**保留不自动移除**；被封号者**照常展示、不做特殊标记、仍可被拉黑**；数量不设上限。
  - **明确不做（防止按常见 Block 语义实现成双向隔断）**：不限制被拉黑方查看发起方内容/主页/分享页；**不限制点赞**（照常写入照常计数、不做逐人扣减）；被拉黑方仍可「评论成功」；其自己发的帖对第三方可见性不变；曝光/浏览/点赞统计**不因拉黑扣减**；**历史数据不回溯清理**；不可拉黑自己；**不豁免运营虚拟账号**；**不作用于兽医问诊**；未登录游客与对外分享 H5 不做拉黑过滤；**不做被拉黑方的感知/提示/申诉通道**；**后台不展示「被拉黑数」、不作风控依据**。
  - **埋点**：拉黑/解除须区分**产生来源**（主动 / 举报自动）与**操作入口**（迷你主页 / 黑名单页 / 举报流程 / 评论区）；**黑名单页举报点击单独打点**（来源 `blocklist`）；**不对影子评论单独埋点**。

- **AB-3D**（运营后台）：审核工单统一视图（2026-08-11 从 V1.2.0 后台 PRD §1 整节迁入，编号保留；**完全替代 AB-3A**，不是两者并存）。
  - **工单类型三类**：内容举报 / 用户举报 / 账号标识字段（FR-56 异步审核产生）。**不保留「评论举报」空分类**——该能力至今未上线（C-86）。
  - **每个工单展示**：举报类型 + 原因 · 被举报对象原文/缩略图（含上下文）· **被举报账号的历史违规记录（含每一次警告）** · **被举报账号的个性签名原文**（C-95，为空显示「未设置」）· **举报人数与举报次数两个指标并列**（如「12 人 / 27 次」，只看其一都会误判）。
  - **优先级自动排序**：`分 = 举报人数 + 高频举报人数`，高频 = 单人对该对象累计举报 **≥ 5 次**（含 5），**单人贡献封顶 2 分**；**实时计算不落库快照**；按分倒序、同分按**最早一次举报时间升序**；界面**必须拆开展示**人数/次数/高频人数/总分。
  - **新公式统一接管三类工单排序**（C-96）；既有 P0 判定**保留不变、仅作用于内容举报**、只管「自动把帖子挂起」这一个动作、**不再参与排序**。

  - **处置动作两档（与 FR-58 一致）**：警告 / 封号，可组合使用。**不为限流曝光预留 UI。**

### NonFunctional Requirements

本版本不新增 NFR 编号，以下为**继承 + 本版本必须落实的约束**：

- **NFR-8（继承）**：用户注销后对外匿名化、不泄露曾否存在。落点：迷你卡对已注销**不弹卡**；黑名单条目展示为匿名态 + **去点击态** + **保留不自动移除**。
- **NFR-安全规则层（继承 architecture Enforcement）**：隐藏过滤属安全规则层，**只升不降、不可绕过**。凡新增「展示他人内容」的位置**默认套用**，不做逐场景例外。
- **NFR-服务端权威**：主页访问拦截**必须服务端校验** —— 纯前端拦截可被**推送深链 / 通知中心历史记录 / 外部分享链接**绕过。
- **NFR-零新中间件（继承）**：不引入 MQ / 通用缓存层 / 新中间件；本版本**无缓存、无异步、无定时任务**，部署形态不变（德国单机）。
- **NFR-不可枚举标识（继承，本版本有一处已知偏离）**：对外标识原则上用不可枚举 token；但既有 `/api/v1/users/{userId}/mini-profile` 已上线并暴露数字 id，**本版本新端点沿用既有口径保持一致**，改造属独立议题（架构 Deferred D-5）。
- **NFR-日志**：禁记 PII / 健康数据 / 令牌 / 签名 URL。**举报的「其他」补充说明属用户自由文本，禁止进日志。**
- **NFR-错误契约（继承）**：统一 RFC 9457 ProblemDetail，绝不外泄堆栈。
- **NFR-命名映射链（继承）**：DB snake_case ↔ Java/Dart camelCase ↔ JSON camelCase；枚举落库 varchar + UPPER_SNAKE；时间戳 timestamptz 一律 UTC。

### UX Design Requirements

来自 `ui-v1.1.4.html`（**28 屏 / 4 泳道**，2026-08-14 定稿 + 2026-08-15 校验跟改）。**视觉规格全部照搬既有实现，未自创数值。**

- **UX-DR1**（A1/A2）：迷你卡右上角新增「⋯」，点开菜单**锚在卡片右上角向上弹**（试过向下弹会溢出屏底并盖住头像，C-76），**不是第三层抽屉**；卡片内容**不省略、不压暗**；两项并列不分主次，各带副标题（举报「Langgar aturan komunitas」/ 拉黑「Berhenti melihat mereka」）。
- **UX-DR2**（A1 / **A1b**）：卡片是 **6 个元素**不是 5 个——头像(r=32) → 昵称 → 发布数 → **个性签名 或 「主页筹备中」（二选一）** → 关闭。设了签名显示签名原文、**不显示占位语**。A1b 画的是 **60 字满格**的极端情况，须验证换行后**不与「⋯」重叠、不把菜单顶出可视区**。
- **UX-DR3**（A3）：已举报态菜单——举报项显示「Sudah dilaporkan / Ketuk untuk melaporkan lagi」（紫色，**明示可再点**，避免被当成禁用态）；**拉黑项此时仍可点、不置灰**。
- **UX-DR4**（A4 / A5）：卡不弹的两种情况必须**可区分**——已主动拉黑 → Toast「Kamu sudah memblokir pengguna ini」；网络失败 → Toast「Gagal terhubung, coba lagi」。**只被举报过的照常弹卡。**
- **UX-DR5**（**A6**）：评论区（详情页内一级评论与二级回复）头像/昵称可点弹卡，与 Feed/详情页作者完全一致；**不在评论行内另设「⋯」或滑动手势**；实现须一并复核**已注销分支**。

- **UX-DR12**（B7）：重复举报 —— 副标题替换为紫底说明块（重复举报文案）；**类型重新选、不预填上次选择**（每次类型要独立留存）。

### Story 1.1: 拉黑一个人，他的帖子立刻从我首页消失（服务端）

As a 被某个账号打扰的用户,
I want 系统记住「我不想看见这个人」，并让他的内容从我的首页消失、他的主页我也进不去,
So that 我的屏蔽是真的生效的，而不是只在界面上做做样子、换个入口就能绕过。

> **本 story 交付服务端能力**（表 / 模块 / 只读端口 / 接口 / 首页过滤 / 主页拦截）。**界面在 Story 1.2**，两条一起才构成用户可用的完整体验。
> **本 story 的验收走接口层**（Story 1.2 交付后再做端到端 L2 回归）。

**Acceptance Criteria:**

**AC1（L1）· 隐藏关系落库**
**Given** 数据库已执行本版本首个迁移（**Flyway 从 V101 起**，序号按实际执行顺序单调分配）
**When** 建立一条隐藏关系
**Then** `user_hide_relations` 表存在且含 `holder_id` / `target_id` / `source`(BLOCK|REPORT，varchar + UPPER_SNAKE) / `created_at` / `updated_at`(timestamptz, UTC)
**And** 唯一索引是**三元 `(holder_id, target_id, source)`**，不是二元
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md` 的「表归属总表」，创建者标注为本 story

**AC2（L0）· 模块边界与只读端口**
**Given** 新建的社区关系模块
**When** 其他模块需要判断隐藏关系
**Then** 该模块**只对外暴露一个只读端口**，且该端口提供**两种**查询：「存在任意隐藏」与「**存在主动拉黑**」
**And** `content` / `notify` / `auth` 三侧**只依赖端口接口，不得引用其仓储**
**And** 静态检查通过：仓储类未被模块外任何 import

> ⚠️ **少提供「存在主动拉黑」这一种查询，研发就会拿「存在任意隐藏」去拦主页，直接打死 FR-58 的闭环**（见 AC6 与风险点 R1）。

**AC3（L1）· 拉黑与解除的接口行为**
**Given** 当前登录用户 A 与目标用户 B
**When** A 调用 `POST /api/v1/me/blocked-users` 拉黑 B
**Then** 建立一条 `source=BLOCK` 的隐藏关系并返回成功
**And** **重复拉黑幂等**：不报错、不新增记录、**不刷新拉黑时间**（避免反复点击把自己顶到列表最前）
**And** `DELETE /api/v1/me/blocked-users/{userId}` 只删除 `BLOCK` 行；重复解除**静默成功**
**And** **服务端不依赖前端防连点**（前端另做，但服务端自身幂等）
**And** **A 不可拉黑自己**：目标为本人时返回校验错误

**AC4（L1）· 幂等只在同源之间生效**
**Given** A 与 B 之间**已存在 `source=REPORT` 的隐藏关系**
**When** A 发起主动拉黑
**Then** **照常新增一条 `source=BLOCK` 记录**（不被幂等吞掉），两条并存
**And** A 出现在黑名单页中

> ⚠️ 写成二元唯一键或「已存在隐藏就跳过」，会让用户点了拉黑、Toast 说「请在黑名单里查看」、去了却找不到人（C-91）。

**AC5（L1）· 首页过滤**
**Given** A 已拉黑 B，且 B 有多条已发布内容
**When** A 请求首页 Feed
**Then** B 的内容**不出现在任何一页**
**And** 该过滤**写在 `findFeed` 的 SQL WHERE 内**，不是取回后在 Java 侧 filter
**And** 既有的「排除本人已举报的帖」子查询**原样保留、未被改写或合并**（AD-9）
**And** 每页仍返回满额条数（过滤后凑够 N），**不出现近乎空白的页**
**And** 游客（未登录）请求 Feed 时行为完全不变

**AC6（L1）· 主页访问服务端拦截**
**Given** A 已**主动拉黑** B
**When** A 请求 B 的迷你主页接口
**Then** 返回 RFC 9457 ProblemDetail，`type` 为可识别的 `blocked-user`
**And** 响应中**不含 B 的昵称、头像、签名、发布数等任何展示字段**
**And** 该端点**保持 `permitAll`**，游客请求行为完全不变（照常返回卡片数据）
**And** 登录用户的身份经 `@AuthenticationPrincipal` 解析（照抄 `ContentFeedController` 的可选 viewer 模式）

**AC7（L1）· ⚠️ 拦截只认主动拉黑（高风险点 R1）**
**Given** A **只举报过** B（存在 `source=REPORT`，不存在 `BLOCK`）
**When** A 请求 B 的迷你主页接口
**Then** **照常返回卡片数据、不拦截**

> ⚠️ 把条件写成「存在隐藏关系即拦」会一并把举报隐藏拦掉——「已举报」状态无处显示、重复举报无入口，**FR-58 闭环当场作废**。

> **⚠️ AC8a / AC8b / AC8c 原为一条 AC8（含 10 个 `And`），2026-08-15 IR 修补拆为三条（IR-1）——内容一字未改，只改切分。**
> 拆的理由：这 10 条彼此无关，分散在点赞、通知、统计、问诊、游客视图五条完全不同的代码路径上，「AC8 通过」这句话不表达任何信息。而 AD-20 的存在理由恰恰是**防止研发按常见 Block 语义做成双向隔断**——这是本版本产品语义最反直觉的一处，最需要逐条签字。**三条须各自独立验收、分别签字，不得合并勾选。**

**AC8a（L1）· 被拉黑方一侧的「仍然可以」（AD-20，防止做成双向隔断）**
**Given** A 已拉黑 B
**When** 检查 B 一侧的行为
**Then** B **仍可正常查看** A 的内容、主页、对外分享 H5 页
**And** B **仍可对 A 的内容点赞**，点赞**照常写入、照常计入点赞数、不做逐人扣减**
**And** B **收不到任何通知、看不到任何标记**
**And** B 自己发的帖对第三方可见性**完全不变**

**AC8b（L1）· 统计与历史数据一概不动**
**Given** A 已拉黑 B
**When** 检查数据侧
**Then** A 的曝光/浏览/点赞统计**不因拉黑扣减**
**And** 拉黑**不回溯清理**已产生的数据（此前的赞与互动记录保留不动）
**And** **后台不展示「被拉黑数」**，该数字不作为任何风控或运营处置依据

**AC8c（L1）· 适用范围的四条边界**
**Given** 拉黑能力已上线
**When** 检查其作用范围
**Then** **运营虚拟账号（种子内容作者）同样可被拉黑，不做豁免**
**And** 拉黑关系**不参与兽医问诊的匹配/展示逻辑**
**And** 未登录游客与对外分享 H5 访客页**不做拉黑过滤**
**And** 拉黑数量**不设上限、不设频次限制**

**AC9（L0）· 通用规则：凡展示他人内容的位置一律套用，不做逐场景例外**
**Given** 隐藏过滤属**安全规则层**（只升不降、不可绕过）
**When** 本 story 建立该过滤能力
**Then** 在只读端口与相关代码处**显式声明这条通用规则**：**凡是向用户展示他人内容的位置，一律套用同一层隐藏过滤**
**And** 若某个运营干预位（顶置位、推荐位等）命中被隐藏作者，则对该用户**视为该位为空**，按该功能自身已定义的「位为空」回退逻辑处理——本版本**不为其单独选替补内容、也不定义该功能本身**

**And** 该规则同步登记到 `CROSS-STORY-DECISIONS.md`，供后续版本新增内容列表时对照

**And** 实现**复用既有的「取回后 exists 检查再抛 404」模式**，**不改为 SQL 子查询**——详情路径与列表路径的这处不对称是既有的刻意设计（注释已写明防枚举理由），不要顺手「统一」掉

> **⚠️ 为什么补这一条（CS 阶段扫代码才发现，文档层面看不出来）：**
> ① **架构 AD-9 的 Binds 写了两处**——「`findFeed` 的 WHERE 构成；**内容详情对举报人的 404 判定**」，但 AD-9 的 Rule 三条**只讲 findFeed**，内容详情一个字没落实，是架构自身的一处不闭合。
> ② **代码实证：两条路径彼此独立，Feed 改了详情页不会跟着生效。** `ContentDetailService.getDetail` 对「本人已举报的帖」用的是**取回后 Java 侧 `reportService.hasReported(...)` 再抛 404**，而 Feed 用的是 JPQL 子查询。
> ③ **不补会复活 PRD §7 花一整节要消灭的塌陷**：举报**一条帖** → 那条帖详情页 404 打不开（既有行为）；拉黑**整个人**（更重的动作）→ 他的**每一条**帖详情页照样能开。方案甲的整个论证建立在「动作越重效果越强，绝不出现更重的动作反而没反应」之上，详情页这一处正好破了它。
> ④ **授权来源是 AC9 已声明的通用规则**（「凡是向用户展示他人内容的位置，一律套用同一层隐藏过滤，不做逐场景例外」）——内容详情页显然属于此列。**本条不是扩大范围，是把已声明的规则落到一个具体位置。**
> ⑤ **实现成本**：在既有 `hasReported` 判断紧邻加一个判断，复用同一句 `GONE_DETAIL` 文案。

### Story 1.2: 在他的卡片上点两下就能把他拉黑（界面）

As a 被某个账号打扰的用户,
I want 点开他的迷你主页卡、从右上角「⋯」里选拉黑并确认,
So that 我不需要知道任何技术细节，两三下点击就能让他从我眼前消失。

> **本 story 交付界面**，服务端能力由 Story 1.1 提供。**A 泳道 4 屏（A1 / A1b / A4 / A5）+ C 泳道 4 屏（C1–C4）。**

**Acceptance Criteria:**

**AC1（L2）· 迷你卡「⋯」菜单（UX-DR1，A2）**
**Given** 用户点开某人的迷你主页卡
**When** 点击右上角「⋯」
**Then** 菜单**锚在卡片右上角向上弹**（不是第三层抽屉、**不向下弹**——向下会溢出屏幕底部并盖住头像）
**And** 卡片内容**不省略、不压暗**
**And** 菜单含「举报 / 拉黑」两项**并列、不分主次**，各带副标题（举报「TA 违反了社区规定，请平台尽快处理 TA」/ 拉黑「我不想再看见 TA」）
**And** 视觉规格逐项取自既有 `report_sheet.dart`（UX-DR22），**无自创数值**
**And** ⚠️ **目标为当前登录用户本人时，「⋯」入口整体不渲染**（不是渲染后禁用、也不是点了报错）——举报与拉黑对自己都不成立（Story 1.1 AC3 服务端已拦，但用户不该先看到入口再吃一个校验错误）

> 本 story 只接通「拉黑」项；**「举报」项的动作由 Story 2.2 接入**（纯加一项，非返工）。在此之前该项不渲染，避免出现点了没反应的死菜单项。
> **⚠️ 「本人不渲染」这一态 UI 稿 28 屏未画**（2026-08-15 IR 修补补入，IR-5）——A1/A1b 画的都是看他人的卡。实现时按本条处理，无需另等出图。

**AC2（L2）· 拉黑二次确认全流程（UX-DR13/14，C1–C4）**
**Given** 用户在菜单点「拉黑」
**When** 弹出二次确认
**Then** 主按钮用**危险色 `#F0425A`**（既有 `AppColors.popRed`），**头像重复出现**（确认拉黑谁比确认动作本身更重要）
**And** 文案只说「拉黑后你将不再看到 TA 的内容和评论」——**刻意不提影子评论、不提「对方不会收到通知」**
**And** 提交中：**选项与取消一并禁用**，抽屉不关闭
**And** 成功：**两层一并收起** + Toast「拉黑成功，请在黑名单里查看」，且**该用户的卡片已从当前 Feed 列表消失**
**And** 失败：**抽屉保持打开** + Toast「拉黑失败，请重试」，可直接再点

> 成功收起、失败保持打开，两者**行为相反是刻意的**——失败不该让用户重新走一遍入口。

**AC3（L2）· ⚠️ 迷你卡三处既有行为（高风险点 R4，UX-DR4，A4 / A5）**
**Given** 既有 `showMiniProfile` 的失败路径是 `catch (_) { return; }` **静默不弹**（注释理由「非关键路径」）
**When** 本 story 改造该组件
**Then** 网络失败 → **弹 Toast「网络失败，请重试」**，且**改的是原来那个 catch 分支**，不是只加新分支
**And** 已**主动拉黑** → **不弹卡 + Toast「你已拉黑该用户」**，走**独立分支**、不复用上面那条静默路径
**And** 已注销 → **仍不弹卡**（NFR-8，既有行为不变）
**And** 三种情况的表现**互相可区分**，不会被用户当成同一回事

**AC4（L2）· 迷你卡是 6 个元素不是 5 个（UX-DR2，A1 / A1b）**
**Given** 目标用户设了个性签名
**When** 卡片渲染
**Then** 第 4 行显示**签名原文**，「主页筹备中」**不出现**（二选一，不并存）
**And** 未设签名时才回落「主页筹备中」占位文案
**And** **60 字满格签名**换行后**不与右上角「⋯」重叠、也不把菜单顶出可视区**

> ⚠️ 签名是**用户自填的自由文本**——骚扰账号完全可以把攻击性内容写在这里，而那段文字恰恰展示在你要举报他的那张卡上。**举报场景下不隐藏签名**（隐藏会让点开「⋯」时内容跳动），签名进工单上下文的要求见 Story 3.1。

**AC5（L2）· 拦截态的前端表现**

**When** 用户从任何入口点击该用户

**And** **不展示该用户的任何信息**

**AC6（L0）· 护栏**
**Given** 本 story 的实现
**Then** 未新增任何第三方依赖
**And** 底部弹层最外层**显式撑满宽度**（沿用既有 `confirm_sheet.dart` 的写法，别指望 sheet 自己会满宽）
**And** `flutter analyze` / `flutter test` 全绿

### Story 1.3: 评论区里再也看不到他，他也没法在我地盘上冲别人喊话

As a 拉黑了某人的用户,
I want 他的评论从我看到的所有评论区消失，而且他在我内容下的评论对所有人都不显示,
So that 我不用再看见他，也不会出现「全平台都看得见、唯独我看不见因而删不掉」的攻击性评论。

**Acceptance Criteria:**

**AC1（L1）· R1 按查看者隐藏**
**Given** 查看者 A 已隐藏 B（**主动拉黑或举报，两种来源都算**）
**When** A 请求任何内容下的评论列表
**Then** B 的评论**对 A 不展示**
**And** 隐藏方式是**直接不展示该条**，不占位、不显示「该内容已隐藏」占位符
**And** 对其他人的可见性**无影响**
**And** 该条件写在四个评论查询方法（一级评论 / 二级回复 / 批量回复 / 计数）的 SQL 内，与既有 `:viewerId` 条件并列

**AC2（L1）· ⚠️ R2 影子评论判的是内容作者（高风险点 R2）**
**Given** 内容作者 A 已隐藏 B，第三方 C 与谁都无隐藏关系
**When** B 在 A 的内容下发表评论
**Then** **A 看不到、C 也看不到**，**只有 B 自己看得到**
**And** R2 的判据是 `holder = 该内容的作者`，**不是 `holder = 当前查看者`**
**And** 内容作者 id **由 service 作为参数传入查询**，不在 SQL 里 join 内容表
**And** R1 与 R2 两条件**独立并列**，任一命中即隐藏

> ⚠️ 做成按查看者过滤 → 第三方仍然看得到，**等于没做**。验收必须三个视角各看一遍。

**AC3（L1）· 影子评论对评论者本人无感知**
**Given** B 的评论已被 R2 影子
**When** B 自己查看该内容的评论区
**Then** 他看到**自己那条评论正常展示**，与发布成功的状态完全一致
**And** **无任何失败提示、无视觉差异、无标记**
**And** B **能看到他人对他那条的回复**

**AC4（L1）· 回复串随父一并隐藏**
**Given** B 的一条评论被 R2 影子，C 回复了 B 那条
**When** A 或第三方查看评论区
**Then** **B 那条与 C 的回复一并不展示**，不论回复者是谁
**And** R1 同理：被 R1 隐藏的评论，其回复串对该查看者一并隐藏
**And** 不出现「回复了某条看不见的评论」的孤儿回复

**AC5（L1）· 评论数口径**
**Given** 某内容下有 5 条评论，其中 1 条被 R2 影子
**When** 第三方查看该内容
**Then** 对外展示的评论数为 **4**，与实际渲染出的条数一致
**And** 被 R2 影子的评论**及其回复串不计入对外评论数与互动量统计**
**And** **被 R1 隐藏的评论照常计入评论数**（R1 只是「我不看」，该评论对平台真实存在且公开可见）
**And** 评论作者本人视角下数字比他人多 1（影子机制固有特性，可接受）

**AC6（L1）· 被拉黑方仍可「评论成功」**
**Given** B 被 A 拉黑
**When** B 在 A 的内容下提交评论
**Then** 接口**返回成功**，界面表现与正常评论完全一致
**And** 评论**正常落库**，只是读取时被 R2 过滤

**AC7（L0）· 下游口径同步**
**Given** 本 story 确立的评论数口径
**When** 后续任何依赖评论数或互动量的功能被开发
**Then** 该口径已在代码注释与 `CROSS-STORY-DECISIONS.md` 中留痕，避免影子评论被当作真实互动信号

**AC8（L0）· 不做的**
**Given** 本 story 范围
**Then** **不做** Instagram Restrict 的「查看 / 批准」二次操作——内容作者不需要能看到、也不需要能放行被影子的评论

### Story 1.4: 他来点赞评论，我这边一点动静都没有

As a 拉黑了某人的用户,
I want 他的点赞、评论、回复不再给我发任何通知,
So that 我不会被他打扰，也不会收到点进去什么都没有的通知。

**Acceptance Criteria:**

**AC1（L1）· 三类互动通知抑制**
**Given** A 已隐藏 B（两种来源都算）
**When** B 点赞 A 的内容 / 评论 A 的内容 / 回复 A 的评论
**Then** A **收不到对应通知**
**And** 抑制点在通知模块的互动监听器内（`onContentLiked` 与 `onContentCommented` 两处，后者内部两次发送**都要判**）

**AC2（L1）· 是「不发」而不是「发了再隐藏」**
**Given** 通知被抑制
**When** A 打开通知中心
**Then** **通知记录不存在**（未写库）
**And** **未读角标不 +1**

**AC3（L1）· ⚠️ 抑制判据有两条，缺一会漏第三方（高风险点 R3）**
**Given** A 已拉黑 B；B 在 **A 的帖子下**回复了 **C 的一级评论**；C 未拉黑任何人
**When** 该回复因 R2 对所有人隐藏
**Then** **C 同样收不到「有人回复了你的评论」通知**
**And** 判据实现为两条，任一命中即不发：① 接收者隐藏了 actor；② **该内容的作者隐藏了 actor**

> ⚠️ **PRD §3.2 生效范围第 6 条列的三种场景，收通知的人全是拉黑发起方本人**，第三方这一支是空白。只做判据 ① 会让 C 收到点进去空白的通知，一对比就能推断出屏蔽机制存在。

**AC4（L1）· 系统通知不受影响**
**Given** 封号通知、审核结果通知、内容被移除通知等系统通知
**When** 这些通知被触发
**Then** **一律不接入隐藏判断，照常发送**
**And** 抑制逻辑**只存在于互动通知监听器内**，未写进通用的发送方法

**AC5（L1）· 解除与历史**
**Given** A 解除了对 B 的拉黑
**When** 检查抑制期间的通知
**Then** **不补发**，抑制期间的通知永久丢弃
**And** 拉黑**之前**已产生的历史通知**不回溯清理**（继承「拉黑不回溯清理已产生数据」原则）

**AC6（L1）· 对被拉黑方无影响**
**Given** B 的点赞与评论操作
**When** 通知被抑制
**Then** B 的操作**照常成功**，B 无从知晓对方是否收到通知

### Story 1.5: 我能看到自己拉黑了谁，随时放人出来

As a 拉黑过若干账号的用户,
I want 在设置里找到黑名单、看到拉黑了谁和什么时候拉的，并能逐个解除,
So that 我不会忘记自己屏蔽过谁，也能在改变主意时把人放出来。

**Acceptance Criteria:**

**AC1（L2）· 设置页入口（UX-DR15，D1）**
**Given** 用户进入「我的」→ 设置
**When** 查看 **PRIVASI & KEAMANAN** 分组（既有 `settingsSectionPrivacy`）
**Then** 新增「黑名单」行，**右侧显示当前拉黑数量**
**And** 该行与同组其他行**同样式**（UI 稿上的紫底仅为示意）
**And** 该计数由 `GET /api/v1/me/blocked-users` 的**返回列表长度派生**（**IR-7R 修订：不新增 `total` 字段**，理由见修订记录）；该列表只含 `source=BLOCK` 的条目，与 AC2 的列表口径一致
**And** 计数为 0 时**显示「0」而非隐藏该行的数值**，与同组其他行保持一致的视觉密度

**AC2（L1）· 列表内容与排序（UX-DR16，D2）**
**Given** 用户打开黑名单页
**When** 列表加载完成
**Then** **只收录含主动拉黑（`source=BLOCK`）的条目**，举报产生的隐藏**不出现在本页**
**And** 每项展示 头像 + 昵称 + 拉黑时间，按**拉黑时间倒序**
**And** ⚠️ **排序取 `BLOCK` 行的 `created_at`，不取 `updated_at`**（IR-4）
**And** ⚠️ **对同一目标追加 `REPORT` 行（即事后又举报了这个人）不得改变该条目在列表中的位置**——两条隐藏关系是独立的行，举报不触碰 `BLOCK` 行的任何字段
**And** 被举报过的条目在昵称后带「已举报」小标签
**And** 顶部有说明句「他们不会知道你拉黑了他们」
**And** 拉黑数量不设上限，列表分页或全量加载按既有列表页惯例

> ⚠️ **为什么排序字段要钉死（2026-08-15 IR 修补，IR-4）**：三元唯一键 `(holder, target, source)` 保证举报写的是 `REPORT` 行、碰不到 `BLOCK` 行——**但那只保证行不被覆盖，不保证列表顺序不被搅乱**。若实现取 `updated_at`、或举报流程顺手 touch 了同一 `(holder, target)` 下的记录，用户就会看到「**我今天什么都没做，这个三个月前拉黑的人怎么跑到最前面了**」，而且他永远猜不到是因为自己刚举报了对方。对应的写入侧约束见 Story 2.1 AC5。

**AC3（L2）· 主动作与次要动作分开（UX-DR16）**
**Given** 列表每一行
**Then** 「解除拉黑」是**常驻按钮**（主动作一眼可见）
**And** 行布局**为右侧「⋯」预留位置**，但**在本 story 交付时该按钮不渲染** —— 它随 Story 2.4 的举报动作一并出现
**And** 两个热区**分开、互不误触**
**And** **不使用任何滑动手势**（右滑撞系统返回、左滑会压在「解除拉黑」上误触）

> ⚠️ **不渲染是刻意的**：本 story 独立交付时「⋯」尚无任何动作可执行，渲染出来就是一个点开是空菜单的死按钮。布局预留即可，避免 Story 2.4 落地时再调整行内间距。

**AC4（L2）· 三种非正常态（UX-DR17，D3/D4/D5）**
**Given** 黑名单页加载
**When** 无数据 / 加载中 / 加载失败
**Then** 空态**给出下一步指引**（去哪儿拉黑），不是白屏
**And** 加载中用**骨架屏**（结构已知，减少布局跳动）
**And** 失败态**必须给恢复路径**（「重试」按钮），不是只报错

**Given** 用户点「解除拉黑」
**When** 弹出二次确认
**Then** 主按钮用**品牌紫，不用危险红**（解除是恢复性动作）
**And** 对**未被举报过**的对象，正文为「解除后你将重新看到 TA 的内容」
**And** 对**也被举报过**的对象，正文改为「你举报过 TA，解除拉黑后内容仍不会展示」

**AC6（L2）· 解除成功的两句文案（UX-DR19，D7 / D7b）**
**Given** 解除成功
**When** 对象**只被主动拉黑过**
**Then** Toast 为「已解除拉黑，刷新后可重新看到 TA 的内容」（**措辞用「刷新后」不用「立即」**，为后续带序列缓存的推荐算法留余地）

## Epic 2: 我能把一个账号交给平台，并且立刻眼前清净

用户可以举报一个账号、选类型说理由，**提交后那个人的全部内容立即从眼前消失**——而且是在当前这一屏就兑现，不是等下次刷新。用户在动手前就被明确告知**这不可撤销**。

> **本 Epic 复用 Epic 1 建好的隐藏关系机制**：举报只是往同一张表里写一条 `source=REPORT`，六处过滤自动生效，**唯一例外是主页访问仍可进入**（Epic 1 Story 1.1 AC7 已保证）。

### Story 2.1: 举报一个账号，他的东西立刻从我眼前消失

As a 遇到骚扰、仿冒或恶意账号的用户,
I want 举报这个账号并说明原因,
So that 平台能整体处置他，同时我不用再逐条举报他的每一篇内容。

**Acceptance Criteria:**

**AC1（L1）· 工单与明细两张表**
**Given** 数据库已执行本 story 的迁移（**接 Story 1.1 之后的号，实际序号按执行顺序顺延**）
**When** 检查表结构
**Then** `account_reports`（工单）的 `target_user_id` **唯一**，含 `status` / `first_reported_at` / `handled_by` / `handled_at` / 时间戳
**And** `account_report_entries`（明细）含 `report_id`(FK) / `reporter_id` / `reason` / `detail` / `created_at`，索引 `(report_id, reporter_id)` 供优先级公式聚合
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md` 的「表归属总表」

**AC2（L1）· 工单粒度 = 被举报账号**
**Given** 同一个被举报账号 B 被 12 个不同用户举报，其中甲报了 7 次
**When** 查询工单
**Then** **只存在一条工单**（`target_user_id = B`）
**And** 明细表有 **18 行**（12 人中 11 人各 1 次 + 甲 7 次）
**And** 「同一举报人对同一账号只占一条工单」这条要求由本粒度**天然满足**

**AC3（L1）· 每一次举报的类型与说明都要留**
**Given** 甲第一次选「持续骚扰」，第二次选「仿冒他人」并填了补充说明
**When** 查询该工单的明细
**Then** **两次的类型都在**，第二次的说明**追加保存、不覆盖**
**And** 后台可按时间倒序取出全部明细

> ⚠️ **不得照抄既有内容举报的做法**——那边重复举报直接 `return` 幂等吞掉，什么都不写。照抄会让次数、类型变化、补充说明**全部丢失**，PRD 重复举报要求的第 2、3 条直接落空。
> ⚠️ 决策日志 **C-50** 曾建议「一对(举报人,账号)只存一行 + 次数累加」，**该建议已被 PRD 正文取代**（一行存不下每次的类型与说明）。

**AC4（L1）· 五类账号维度理由**
**Given** 举报提交接口
**When** 传入理由
**Then** 只接受**账号维度五类**：垃圾信息/恶意营销 · 仿冒他人 · 持续骚扰 · 发布违规内容 · 其他
**And** 落库为 `varchar` + `UPPER_SNAKE`，**是新枚举、未复用内容维度的 `ReportReason`**
**And** 选「其他」时 `detail` **必填**，上限 **200 字**，不填则返回校验错误
**And** 其余四类**不接受也不要求** `detail`

**AC5（L1）· 举报即隐藏，同一事务**
**Given** 用户 A 举报 B
**When** 提交成功
**Then** 写入工单/明细 **与** 写入一条 `source=REPORT` 的隐藏关系**在同一事务内完成**
**And** 任一失败则整体回滚，不出现「有工单没隐藏」或「有隐藏没工单」
**And** ⚠️ **若该 `(holder, target)` 已存在 `source=BLOCK` 行（先拉黑、后举报），写入 `REPORT` 行不得修改 `BLOCK` 行的任何字段**（含 `updated_at` 等时间戳）——**两条隐藏关系是彼此独立的行**（IR-4）

> ⚠️ **这条与 Story 1.5 AC2 的排序约束是一对**：读侧钉死「排序取 `BLOCK.created_at`」，写侧钉死「举报不碰 `BLOCK` 行」，两边都做才保证**先拉黑后举报不会把条目顶到黑名单最前面**。只做一边，另一边的实现细节一变就会重新穿帮。

**AC6（L1）· 举报隐藏的生效范围（复用 Epic 1 机制的回归验证）**
**Given** A 举报了 B
**When** 检查各处
**Then** B 的内容**不出现在 A 的首页**
**And** B 的评论**对 A 不展示**（R1）
**And** B 在 **A 的内容下**的评论**对所有人不展示**（R2，影子评论**同样因举报触发**）
**And** 来自 B 的互动通知**不再发给 A**
**And** **但 A 仍可进入 B 的迷你主页**（唯一例外，闭环需要它）

**AC7（L1）· 举报隐藏不可解除、不进黑名单页**
**Given** 存在 `source=REPORT` 的隐藏关系
**When** 尝试解除或查询黑名单
**Then** **不存在任何解除该关系的接口或入口**
**And** 该关系**不出现在黑名单页**（黑名单页只收录含 `source=BLOCK` 的条目）

**AC8（L1）· 「已举报」状态服务端持久化**
**Given** A 举报过 B
**When** A 重启 App 后再查询 B 的迷你主页
**Then** 返回中带「已举报」标记，该标记**由 `source=REPORT` 行是否存在派生**，不是前端会话态
**And** 黑名单页中若该用户也在（含 BLOCK 层），同样带该标记

**AC9（L1）· 工单被处理后再收到举报**
**Given** 某工单已被运营处理（`status` 非待处理）
**When** 又有用户举报该账号
**Then** **同一条工单翻回待处理**，**不新建工单**
**And** 新的明细行照常追加
**And** 历史处置留痕**不因翻回而丢失**（留痕在 Epic 3 的处置记录表）

**AC10（L1）· 边界**
**Given** 举报提交接口
**Then** **用户不可举报自己**（目标为本人时返回校验错误）
**And** 举报行为**对被举报人完全不可见**（不发通知、不产生任何可感知变化）
**And** **不设任何自动预处置**——无论多少人举报、什么理由，都不会自动挂起该账号的内容
**And** 既有帖子级举报的两条自动通道（违法违规单次触发 / 人数达阈值）**保持不变、未被改动**
**And** ⚠️ **不设任何频率限制或冷却窗口**（IR-3）——同一举报人对同一账号**可无限次举报**，每次照常落一行明细；**不做 24 小时冷却之类的额外限流**

> ⚠️ **这是一条主动决定，不是遗漏（2026-08-15 IR 修补补入 AC，IR-3）**。PRD §3.1 与 A-A23 的理由：单个举报人对优先级分的贡献**已由公式从结构上封顶 2 分**（1 基础 + 1 高频），刷不高任何账号的优先级；加冷却只会多一处逻辑、并多一处**需要向用户解释的静默失败**。
> **为什么必须写进 AC**：本 story 的 AC3 要求「每次举报都留一行明细、绝不幂等吞掉」，研发看到「同一人可无限次写库」时，**防刷直觉几乎必然驱使他自行加一道冷却**——而那与产品判断正好相反。这条不进 AC，评审时没有任何东西能拦住它。
> ⚠️ **与下方 AC11 的短窗去重不矛盾**：AC11 防的是**误触**（双击穿透），本条禁的是**限制用户意图**。两者边界见 AC11。

**AC11（L1）· ⚠️ 服务端防重复提交（2026-08-15 IR 修补新增，IR-2）**
**Given** 用户在举报抽屉点击提交
**When** 因双击穿透、或提交中的网络重试，同一举报人对同一账号在**极短窗口内**（建议 5 秒，具体值实现时定并在 Dev Notes 记录）发生重复提交
**Then** 该重复提交**视为同一次举报，不新增 `account_report_entries` 明细行**，接口返回成功（幂等）
**And** **服务端不依赖前端防连点**——Story 2.2 AC5 的「提交中禁用」照做，但服务端自身必须成立
**And** 该去重**不改变** AC3 的要求：超出窗口后的再次举报**照常追加一行**，每次的举报类型与「其他」补充说明**照常独立留存**

> ⚠️ **为什么需要这条**：拉黑侧 Story 1.1 AC3 已明写「服务端不依赖前端防连点」，**举报侧原先没有对应条款**，而 AC3 又要求「每次都落一行」——防重复因此完全落在前端。
> **后果不是数据错误，是污染两个直接给运营看的数字**：① AB-3D 工单展示的「12 人 / 27 次」——次数虚高，而 PRD 特意要求这两个数并列展示并称「只看其中一个都会误判」；② **≥5 次高频阈值判定**（Story 3.1 AC4）——一个举报 3 次的人被双击刷到 5 次就会被计入高频加成，多贡献 1 分。
> ⚠️ **与 AC10「不设频率限制」的边界必须讲清，否则会被当成互相矛盾**：**AC11 防的是误触**（用户只想举报一次，手抖点了两下），**AC10 禁的是限制用户意图**（用户确实想再举报一次，平台不得拦）。窗口取秒级、不取小时级，正是为了把两者分开。

**AC12（L0）· 日志与护栏**
**Given** 举报的「其他」补充说明是**用户自由文本**
**When** 记录日志
**Then** **该文本不得进入任何日志**（继承日志禁 PII 红线）
**And** 未引入任何 MQ / 缓存 / 新中间件；举报写入为同步小写
**And** `mvn -B package` 全绿

As a 准备举报某个账号的用户,
I want 看到专为账号设计的举报理由、必要时能补充说明、并在提交前知道这不可撤销,
So that 我选得准、说得清，也不会因为三次点击就造成自己后悔的结果。

**When** 渲染提交按钮上方
**Then** **B1 未选 / B2 其他展开 / B3 已选 / B4 提交中 / B6 失败 / B7 重复举报——六个态全部**显示一行小字「提交后无法撤销」
**And** 该文案**只说不可撤销、不说会隐藏**（不破坏「成功态不提隐藏」那条取舍）

> ⚠️ UI 稿的待改清单原文只列了 B1/B2/B3，**但 B4 提交中与 B6 失败态同样是表单态**，实际稿件已六个态全加。按六个走。

**AC5（L2）· 提交中（UX-DR9，B4）**
**Given** 用户点击提交
**When** 请求进行中
**Then** **选项与取消按钮一并禁用**（防重复提交），抽屉**不关闭**，提交按钮内显示转圈

**AC6（L2）· 成功态（UX-DR10，B5）**
**Given** 提交成功
**When** 抽屉切换
**Then** **在抽屉内原地切换为成功态**（✅ + 「已收到你的举报」+「我们会尽快处理」+「关闭」），**不用 Toast、不自动收起**
**And** 点「关闭」→ **两层一并收起**（迷你卡 + 确认抽屉），回到点开迷你卡之前的页面
**And** 中途取消（点「取消」未提交）**只收起第二层**，回到迷你卡本身
**And** 成功态**刻意不提「内容将被隐藏」**

**AC7（L2）· 失败态（UX-DR11，B6）**
**Given** 提交失败
**When** 处理错误

### Story 2.4: 已经拉黑的人，我照样能举报他

As a 先拉黑了骚扰者、冷静下来想举报他的用户,
I want 在黑名单页那一行直接举报他,

**AC3（L1）· 从这里发起的举报后果一致**
**Given** 用户从黑名单页举报了某人

**And** 该行**仍留在黑名单页**（它含 `BLOCK` 层），解除拉黑后才移除

**AC4（L0）· 埋点来源预留**
**Given** 从黑名单页发起的举报
**When** 调用举报接口与前端埋点
**Then** **操作入口标记为 `blocklist`**（实际打点上报在 Epic 4 收口，本 story 只保证来源参数被正确传递）

> 这个数字直接验证「拉黑后仍需举报入口」这个设计判断：**长期为 0 说明该入口可以撤掉**；量不小则说明原来的设计确实堵死了一条重要路径。

## Epic 3: 运营能在一个队列里把这些举报真正处理掉

运营在**一个统一队列**里看到三类工单、按轻重缓急自动排序、能按类型/状态筛选和按被举报账号检索、能单条或批量执行警告与封号；用户收到规范的处理回告。

> **⚠️ 交付硬约束**：本 Epic **必须与 Epic 2 同版本上线**。App 端单独上线 = 用户能提交举报、运营无处处理，**功能上线即空转**。
> **⚠️ 上线阻塞（非本 Epic 可解）**：封号通知的印尼语措辞待**法务**确认（OQ-A4）。**代码可先完成、文案位留出；封号功能不得在其闭环前上线**，其余功能不受阻。

### Story 3.1: 三类工单终于在一个队列里，还知道先看哪条

As a 运营人员,
I want 在一个列表里看到全部待处理工单、自动按轻重缓急排好序、并能筛选和检索,
So that 我不用在三个入口之间来回切，也不用对着一堆互不可比的标记猜先处理哪个。

**Acceptance Criteria:**

**AC1（L1）· 处置记录表**
**Given** 数据库已执行本 story 的迁移（**接 Story 2.1 之后的号，实际序号按执行顺序顺延**）
**When** 检查表结构
**Then** `account_disposals` 含 被处置账号 / 处置类型(`WARNING`|`SUSPEND`，varchar + UPPER_SNAKE) / 处置人 / 关联工单(可空) / `created_at`
**And** 索引 `(target_user_id, created_at DESC)` 供「历史处置次数」与时间倒序展示
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md`

> 本 story 建表是因为工单列表要读它（历史处置次数）。**此时表为空、次数显示 0，属逻辑完整状态**，写入由 Story 3.2 接入。

**AC2（L1）· 三类工单读时联合**
**Given** **三个业务类别落在四张表上**：内容举报 `content_reports`（既有）· **账号标识字段审核 `name_moderation_records` + `avatar_reviews`（两张既有表）** · 账号举报 `account_reports`（本版本新增）
**When** 运营打开统一工单页
**Then** 一条**跨四表的联合查询**产出统一列表，**在数据库内排序分页**
**And** **未新增任何统一索引表、未双写、存量数据零回填**
**And** 各类工单的状态**仍由各自源表权威持有**
**And** **未为后台引入任何缓存**
**And** ⚠️ **账号标识字段那两张表只取 `status = 'MANUAL_PENDING'` 的行**（自动过 / 陈旧作废本就不该进运营队列），两表都有对应的部分索引
**And** ⚠️ **两表的状态机与时间字段不同构，须按架构 AD-7「第三类的三处不同构」做映射**：终态映射（name 有 `RESOLVED_PASS`/`RESOLVED_VIOLATION` 两个、avatar 只有 `RESOLVED` 靠 `verdict` 区分）· 时间锚点各自 `AS` 成同名列（name 用 `submitted_at`、avatar 用 `created_at`）
**And** ⚠️ `name_moderation_records.submitted_value` 与 `avatar_reviews.avatar_url` **可展示、但严禁进日志**（两处迁移注释均标明）

> **📌 2026-08-15 CS 阶段订正（据代码实证，按产品意图定）**：本 AC 原写第三类是 `manual_review_queue`，该认定不成立 —— 那张表的 `content_type` CHECK 只允许 `CONTENT_POST` / `COMMENT`，且 `V51` 迁移注释明写「**不复用帖子 manual_review_queue**」。**按 PRD §4.1 的产品意图**，第三类 = 账号标识字段审核 = `name_moderation_records` + `avatar_reviews` 两张表。**`manual_review_queue` 不进本视图。**

**AC3（L2）· 工单类型三类，不留空分类**
**Given** 类型筛选器
**When** 渲染
**Then** 只有**三类**：内容举报 / 用户举报 / 账号标识字段
**And** **不保留「评论举报」分类**——该能力至今未上线，留一个永远没数据的筛选项只会让运营以为漏了什么

**AC4（L1）· 优先级公式**
**Given** 某被举报对象的举报明细
**When** 计算优先级分
**Then** `分 = 举报人数 + 高频举报人数`；举报人数 = 举报过该对象的**不同账号数**（去重）；高频举报人数 = 其中**对该对象累计举报 ≥ 5 次**（含 5）的账号数
**And** **单个举报人对分数的贡献上限为 2 分**（1 基础 + 1 高频）
**And** 校验用例：甲报3次+乙报7次 → **3 分**；甲报5次+乙报6次 → **4 分**；10人各报1次 → **10 分**；1人报100次 → **2 分**
**And** 分数**实时计算、不落库快照**
**And** 列表按分**倒序**，同分按**最早一次举报时间升序**（先报的先处理）

**AC5（L2）· 分数必须拆开展示**
**Given** 列表每一行
**When** 渲染优先级
**Then** **同时展示 举报人数 / 举报次数 / 高频人数 / 算出的总分**，不能只给一个总分
**And** 「举报人数」与「举报次数」**并列展示**（如「12 人 / 27 次」）

> 只看次数会把「1 个人报了 27 次」当成众怒；只看人数会丢掉「同一人反复纠缠」这个信号。只给总分等于让运营对着黑盒排队。

**AC6（L1）· ⚠️ 第三类工单没有举报人，必须显式定义分数**
**Given** 账号标识字段审核工单（由 FR-56 异步审核产生，**没有任何举报人**）
**When** 参与统一排序
**Then** 其分数按该类工单的 `priority` 字段映射：**`HIGH → 10` / `NORMAL → 2`**
**And** 该映射的锚点取自公式自身的两个例子（10 人各报 1 次 = 10 分；1 人报 100 次 = 2 分），即 **`HIGH`（≥0.8 高置信违规）视为等同于十人举报的众怒、`NORMAL` 等同于一个纠缠的举报者**
**And** ⚠️ **`NORMAL` 不得映射成 0** —— 它是这两张表的 `DEFAULT` 值、绝大多数记录都是它，映射成 0 会让这类工单几乎全部永远沉底，正是本 AC 要防的事

> ⚠️ 不显式定义的话，公式对这类工单**恒为 0 分，会永远沉底没人看**。PRD 说「本公式统一接管全部三类工单」时未注意到第三类不是举报产生的。
> **📌 2026-08-15 CS 阶段订正**：本 AC 原写「按既有 `ReviewPriority` 映射 P0→10 / P1→2 / P2→0」，**该映射无处可用** —— `ReviewPriority{P0,P1,P2}` 只用在 `manual_review_queue`（帖子/评论）上，而第三类实为 `name_moderation_records` + `avatar_reviews`，其 `priority` 枚举是 **`NORMAL / HIGH` 两值**（`ck_nmr_priority` / `ck_avr_priority`）。
> **该映射为架构默认，待产品确认相对权重（OQ-CA1，提法已随本次订正重定），不阻塞开发**——确认后改**两个**常量即可。

**AC7（L1）· 既有 P0 判定退出排序、保留自动挂起**
**Given** 既有内容举报的 P0/P1/P2 判定
**When** 本 story 上线后
**Then** P0 判定**保留不变**（违法违规原因单次触发 / 举报人数达阈值），**仅作用于内容举报**
**And** 它只负责「**自动把帖子挂起**」这一个动作，**不再参与列表排序**
**And** 列表里**不再出现两套互不可比的优先级标记**
**And** **账号举报没有任何自动预处置**（Story 2.1 AC10 已保证），只受新公式排序影响

**AC8（L2）· 工单展示字段**
**Given** 任一工单
**When** 展开查看
**Then** 展示 举报类型 + 举报原因
**And** 被举报对象原文/缩略图（含上下文：所属帖子、父评论等）
**And** **被举报账号的历史违规记录**（同账号历史处置次数，**含每一次警告**）
**And** **被举报账号的个性签名原文**，为空时显示「未设置」；签名取**当前值**（经既有账号查询服务读，不快照、不落工单表）
**And** 账号举报工单可展开看到**每一次举报的类型与「其他」补充说明，按时间倒序**

> **为什么签名必须在工单里**：举报「仿冒他人」「持续骚扰」时，**签名往往就是证据本身**（冒充某人的自我介绍、指名道姓的攻击）。运营不该还要再跳一步去别处看。

**AC9（L2）· 筛选与检索**
**Given** 统一工单页
**When** 运营需要专注处理某一类
**Then** 支持**按工单类型筛选**（三类）
**And** 支持**按状态筛选**（待处理 / 已处理 / 已驳回）
**And** 支持**按被举报账号检索**——处理一条账号举报时能立刻查到「这个人之前是不是被报过、被处置过几次」

> ⚠️ **筛选不是锦上添花，是统一视图成立的前提**。三类混进一个队列、没有筛选，等于没法专注处理某一类。必须与列表同 story 交付。

**AC10（L1）· 完全替代旧举报队列**
**Given** 既有 AB-3A 举报队列视图
**When** 本 story 上线
**Then** AB-3A **不再作为独立视图存在**，其举报处理能力**并入本统一视图**
**And** **不是两者并存**

**AC11（L0）· 护栏**

**Then** 未引入 MQ / 缓存 / 索引表 / 新中间件
**And** 后台为运营内部页面、QPS 极低，联合查询直接落 DB 即可

### Story 3.2: 运营能给出警告或封号，用户也真的收得到

As a 运营人员,
I want 对一条工单执行警告或封号，并留下可追溯的处置记录,
So that 违规的人受到实际处置，而我下次再遇到这个人时一眼能看到他已经被警告过几次。

**Acceptance Criteria:**

**AC1（L1）· 两档处置动作**
**Given** 一条待处理工单
**When** 运营执行处置
**Then** 可选**警告**或**封号**，两者**可组合使用**
**And** **不提供「限流曝光」选项，也不为它预留 UI**（该动作依赖推荐算法打分链路，随 FR-95 移至 1.1.8）

**AC2（L1）· 处置必先落记录，且同一事务**
**Given** 运营点击警告或封号
**When** 执行
**Then** **先写入 `account_disposals` 一行**（被处置账号 / 类型 / 处置人 / 关联工单 / 时间），**再触发用户侧后果**
**And** 写记录与触发后果**在同一事务内**

> ⚠️ 不同事务会出现「**用户登不上了，但工单页显示从没处置过**」——既有停用链路自带审计留痕，处置记录必须与它同生共死。

**AC3（L1）· 警告的完整定义**
**Given** 运营对某账号执行警告
**When** 处理完成
**Then** 用户收到**一条系统通知**，中文语义为「你的账号因违反 TailTopia 社区规范收到一次警告，请遵守社区规范」
**And** 通知**不告知**是谁举报的、因哪条内容、也不告知这是第几次警告
**And** 警告**不影响用户使用**——能登录、能发内容、内容可见性不变
**And** 警告**不需要异议渠道**（不引导联系客服，与封号不同）

**AC4（L1）· 警告可重复、不合并、不自动升级**
**Given** 同一账号被多次警告
**When** 每次执行
**Then** **每次都发一条独立通知，不做合并、不做去重**
**And** **每次都写入一行处置记录**，工单页的「历史处置次数」相应递增
**And** 警告累计到**任何次数都不会自动触发封号、也不会自动置顶工单**
**And** 是否升级**完全由运营看到历史记录后人工判断**

**AC5（L1）· 封号的后果与告知**
**Given** 运营对某账号执行封号
**When** 处理完成
**Then** 该账号状态置为运营停用，**即时无法登录**，refresh token 一并撤销
**And** 用户收到系统通知，中文参照「你的账号因违反 TailTopia 社区规范已被停用。如有异议，请联系客服团队。」
**And** 异议走 **FR-52 通用客服工单**，由客服按个案人工判断
**And** **不建立独立的申诉审核工作流或 UI**——客服只是唯一的异议反馈渠道

**AC6（L2）· ⚠️ 封号不等于注销（高风险点 R5 的服务端侧）**
**Given** 被封号的账号
**When** 检查其在各处的表现
**Then** 其**存量内容不因封号而全部删除**
**And** 该账号在**其他用户的黑名单里照常展示、不做特殊标记、仍可被拉黑**
**And** 封号**不触发**任何注销才有的匿名化处理

> ⚠️ 代码里「运营停用」与迷你卡投影的「已注销」命名几乎一样，而本版本对两者要求**正好相反**。**以中文定义为准，不要凭字段名推断语义。**

**AC7（L1）· 工单状态流转**
**Given** 工单被处置或驳回
**When** 状态更新
**Then** 工单状态相应流转（已处理 / 已驳回），记录处理人与处理时间
**And** 若该账号**之后又被举报**，同一条工单**翻回待处理**（Story 2.1 AC9），而**历史处置记录不受影响、照常累计**

**AC8（L1）· 零自动处置的回归确认**
**Given** 任意数量的用户举报同一账号
**When** 举报累积
**Then** **系统不会自动执行警告或封号**，也**不会自动挂起该账号的内容**
**And** 所有处置**均需运营确认**

**AC9（L0/L2）· 🚩 文案与上线阻塞**
**Given** 警告通知与封号通知的印尼语措辞
**When** 实现
**Then** 代码可先完成、文案位留出
**And** **封号通知的印尼语必须经法务确认后方可上线**（OQ-A4），尤须确认「引导联系客服反馈异议」这句是否会被解读为**承诺正式申诉结果**
**And** 警告通知的印尼语与封号通知**同批送审**
**And** 其余功能**不受此阻塞**

### Story 3.3: 一批同类的工单能一次处理完，但不会一不小心封掉几百个人

As a 面对一长串同类工单的运营人员,
I want 勾选多条一次性执行同一个处置,
So that 我不用逐条点一百次；同时我不会因为手滑全选就把一整个队列的人都封了。

**Acceptance Criteria:**

**AC1（L2）· 单次上限 50 条**
**Given** 运营勾选工单
**When** 勾选数量达到 50
**Then** **不允许再勾选更多**，或提交时被拒绝并提示上限

> 不设上限的话，全选一个长队列再点封号，可以一次封掉几百个账号。

**AC2（L2）· 跨类型不可批量**
**Given** 运营勾选了第一条工单
**When** 界面更新
**Then** **其余类型的工单一律置灰不可选**

> 不同类型工单的处置对象含义不同——内容举报的处置对象是**内容**，账号举报的处置对象是**人**。

**AC3（L2）· 批量封号必须二次确认并逐条列出**
**Given** 运营对多条工单批量执行**封号**
**When** 点击执行
**Then** 弹出二次确认，**弹窗内逐条列出将被封的账号**（昵称 + 被举报次数）
**And** 确认后才执行
**And** **批量警告不需要二次确认**（警告不影响用户使用，可逆性完全不同）

**AC4（L1）· 逐条独立事务**
**Given** 批量处置 N 条
**When** 执行
**Then** **每条一个独立事务**
**And** 每条同样先写处置记录再触发后果（Story 3.2 AC2）

**AC5（L1）· 部分失败逐条回报，不整批回滚**
**Given** 批量 20 条，其中 18 条成功、2 条失败
**When** 执行结束
**Then** 界面**明确列出失败的那 2 条及其原因**
**And** 成功的 18 条**保持成功、不回滚**
**And** 运营可**对失败项重试**
**And** **不得静默吞掉任何失败项**

**AC6（L0）· 审计**
**Given** 批量处置
**When** 每条执行
**Then** 处置记录与既有审计链路**逐条留痕**，与单条处置口径一致

As a 举报过内容或账号的用户,

## Epic 4: 这一版的效果可度量

上线后能回答三个问题：举报量是**降了还是升了**（这是本版本立项赌注的方向，两种结果都说得通）、主动拉黑的**真实使用量**是多少（不被举报自动产生的量灌大）、黑名单页那个举报入口**到底有没有人用**（长期为 0 就该撤掉）。

> **为什么放在最后一条 story 统一做**：沿用 V1.1.2 的既定做法——埋点在功能逻辑全部理清后集中实现，避免边做边改、口径散在各处。

### Story 4.1: V1.1.4 埋点收尾

As a 产品负责人,
I want 拉黑与举报的行为被分来源、分入口地记录下来,
So that 上线后我能判断这一版的赌注押对了没有，而不是只能凭感觉说「好像有用」。

**Acceptance Criteria:**

**AC1（L1）· 拉黑 / 解除拉黑事件必须分来源**
**Given** 一条隐藏关系被建立或解除
**When** 上报埋点
**Then** 事件属性含**产生来源**：`BLOCK`（用户主动拉黑）/ `REPORT`（举报自动产生）

> ⚠️ 不分来源的话，**隐藏关系总量会被举报量灌大**，完全看不出主动拉黑的真实使用情况——而这两件事的产品含义截然不同。

**AC2（L1）· 拉黑事件必须分入口**
**Given** 用户发起拉黑
**When** 上报埋点
**Then** 事件属性含**操作入口**：`mini_profile`（迷你主页卡）/ `blocklist`（黑名单页）/ `report_flow`（举报流程自动产生）/ `comment`（评论区头像）
**And** 四个入口的埋点在各自 story 实现时**已预留参数**（`mini_profile` → Story 1.2 · `blocklist` → Story 1.5 / 2.4 · `comment` → Story 1.6 · `report_flow` → Story 2.1），本 story 负责**统一收口与校验**

**AC3（L1）· 黑名单页举报点击单独打点**
**Given** 用户在黑名单页点击行内「⋯」→ 举报
**When** 上报埋点
**Then** 该点击**单独成事件**，来源标记为 `blocklist`

> 这个数字直接验证「拉黑后仍需举报入口」这个设计判断是否成立：**若长期为 0，说明该入口可以撤掉**；若量不小，说明原来的设计确实堵死了一条重要路径。

**AC4（L0）· 明确不埋的**
**Given** 影子评论（R2）机制
**When** 设计埋点
**Then** **不对影子评论做任何单独埋点**

> 被拉黑方无感知是设计前提，任何针对他的行为埋点都不改变产品行为，本版本不做。

**AC5（L0）· 度量所需数据的来源核对**
**Given** PRD §4.3 定义的成功度量
**When** 核对数据来源
**Then** 确认全部指标**可由本 story 的埋点 + 后台工单数据得出，无需再新增埋点**：
- 工单总量 / 工单构成 → 后台工单数据（Epic 3 的统一视图）
- 人均举报次数 → 举报人数与举报次数的比值（Epic 3 AC5 已展示）
- 主动拉黑真实使用量 → 本 story AC1 的来源区分
- 黑名单页举报入口使用量 → 本 story AC3

**AC6（L1）· 四条反向指标可被观测**
**Given** PRD §4.3 定义的四条反向指标
**When** 上线后监控
**Then** 以下四条**均有数据可查**：
1. 账号举报量周环比翻倍且持续两周 → 后台工单数据
2. 单账号被举报**人数**分布出现异常尖峰 → 后台工单数据（Epic 3 AC5 的人数指标）
3. 客服工单出现「为什么刷不到某人内容」类咨询 ≥5 起/月 → 既有客服工单（FR-52），**需人工归类，非埋点**
4. 黑名单页举报入口点击长期为 0 → 本 story AC3

**AC7（L0）· 🚩 上线前必须先量基线（非代码交付项）**
**Given** PRD §4.3 要求上线后第 4 周对照基线
**When** 本版本上线前
**Then** **必须先量一次基线**：上线前连续 4 周的周均待处理工单数 / 工单构成 / 人均举报次数
**And** 责任人：**产品**

> ⚠️ **上线后才想起来就没有基线可对了，§4.3 整节度量也就白写了。** 这条不是代码任务，但漏了就让整个度量安排失效，故在此显式登记。

**AC8（L0）· 回看安排登记**
**Given** 度量的回看安排
**Then** 时点为**上线后第 4 周，只回看一次**；责任人为**产品**
**And** 产出一条明确结论——**达成 / 未达成 / 数据不足**，并记入决策日志
**And** **无论结果如何都要写，不留悬空**
