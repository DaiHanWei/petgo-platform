### AB-3G：内容互动积分与双口径统计（新增，扩展 AB-3B 全量内容管理列表）

**背景：** AB-10C 装饰标签目前没有任何排序工具辅助运营挑选"本周最佳/最佳萌宠"候选；管理层也需要一个量化指标观察内容质量与平台活跃度趋势。

**积分计算规则：** 单帖积分 = 点赞数 × 1 + 评论数 × 5

**后果：**

- 全量内容管理列表（AB-3B）新增「互动积分」列，支持按积分排序（默认降序）
- **双口径切换（互斥，运营选择其一）：**
  - **口径A·内容质量**：按帖子**发布时间**筛选时间段，展示该区间内发布的帖子，积分按其**至今累计**的点赞/评论总数计算——用于评估"这段时间发的内容质量如何"，辅助装饰标签选品与管理层内容质量汇报
  - **口径B·平台活跃度**：不筛选发布时间（全部已发布帖子均参与统计），积分只计算**该时间段内新增**的点赞/评论次数——用于观察"这段时间平台用户互动活跃情况"，能反映老帖子被重新带火等口径A看不到的情况
- 时间段支持自定义起止日期
- 支持导出，供管理层经营汇报使用

`[ASSUMPTION: 口径B 需要按点赞/评论各自的产生时间戳统计，而非当前累计计数字段，工程需确认底层数据是否已具备该时间戳字段以支持按区间聚合查询；若无，需新增记录]`（见 A-2）

**统计范围与 Diary 可选私密的关系（2026-07-28 新增，2026-08-05 按 FR-83 反转订正，关联 V1.1.2 FR-83）：** V1.1.2 起，作者可在发布 Diary 时关闭「同步到 Moment」把该条变为纯私人记录；该开关 **2026-07-30 已反转为默认开启**（Diary 默认公开进 Feed，私密属作者主动选择的少数分支，原"默认私密"表述已作废）。**未同步为公开 Moment 的 Diary 内容不纳入本条统计口径**——它们只在作者自己的成长档案时间线里展示、不在公开 Feed 中流通，其点赞/评论量既不代表内容质量也不代表平台公开活跃度，且不可能成为装饰标签候选（装饰标签的意义在于公开曝光）。发布时已开启「同步到 Moment」的 Diary 按公开 Moment 正常计入。

**口径稳定性（2026-07-28 确认，无需按时点取数）：** FR-83 已明确同步状态**在发布时一次性确定、发布后不可更改**，因此一条内容的"公开/私密"属性在其整个生命周期内恒定，**不存在统计时点与互动发生时点状态不一致的问题**。工程实现上只需在查询层按内容的同步状态字段静态过滤即可，不需要维护状态变更历史、也不需要区分"按统计时点"还是"按互动发生时点"取数。内容被删除的，按既有的已删除内容处理规则退出统计。见 OQ-16。

### AB-3H：种子内容物种归属标记（新增，扩展 AB-1.1-02A / AB-1.1-02 / AB-1.1-03）

**背景：** 首页推荐算法 V2 设计（`../2.数据算法/首页推荐算法.md`）要给养猫用户多展示猫内容、偶尔展示狗和其他宠物。内容侧没有物种字段，算法只能 join 作者的宠物档案（`pet_profiles.pet_type`）来推导内容物种。但 **AB-1.1-02A 虚拟账号创建时只填昵称 + 头像，不建宠物档案**，因此**全部种子内容的物种推导结果都是空**；而 Tips/科普类内容主要由运营用虚拟号发布，导致算法的「教育类」槽位几乎完全无法做物种个性化。

本条以两处最低成本的改动补上这个缺口——**不逐条打标、不引入 AI 识别**：账号级默认值一次配置覆盖该号全部内容，行级覆写复用运营本来就在逐行填写的导入 Excel。

**取值枚举（统一四值，与 `pet_profiles.pet_type` 对齐并补一个通用值）：** `CAT` 猫 / `DOG` 狗 / `OTHER` 其他宠物 / `GENERAL` 通用（不限物种，如通用养宠知识）。

**后果（三处触点，均为新增字段，不改动任何既有配置项）：**

**（1）AB-1.1-02A 虚拟账号管理——新增「账号物种定位」**

- 创建/编辑页新增「账号物种定位」下拉（必填，四值单选），语义 = 该账号定位为猫号 / 狗号 / 其他宠物号 / 通用号
- 列表字段与导出字段均新增「账号物种定位」列（原字段：账号 ID / 昵称 / 头像 / 创建时间 / 创建人 / 启用状态 / 累计发布内容数）
- 支持按账号物种定位筛选列表
- **存量虚拟账号统一置为 `GENERAL`（通用）**，不阻塞使用；运营可逐个改为具体物种，**无需任何数据回填作业**——内容物种是读时 join 推导（不是发布时快照），改完账号定位，该号名下**全部历史内容**的物种归属立即生效。这正是本条改动杠杆最高的地方
- **可随时修改**，修改即时影响该号全部历史内容的物种归属（OQ-20 已确认接受）。改完后若个别历史内容被误标，在内容管理列表逐条或批量设置行级覆写修正即可，见下方（4）

**（2）AB-1.1-02 批量上传——导入 Excel 新增「关联物种」列**

- 在既有「发布账号」列之外，**再增加一个「关联物种」列**供运营逐行填写（模板的完整列定义见 AB-3K Step 2 方式二）
- **选填**。留空 = 继承该行「发布账号」对应虚拟账号的账号物种定位（见 A-4）；**发布账号为运营真实账号时无此字段，留空即由算法按作者宠物档案推导**（算法文档 §1.2 优先级 2/3，见 AB-3J（4））
- **本列不设批次级默认值**（与「发布账号」不同）——原因见 AB-3K Step 2 的说明：账号物种定位已经承担了账号级默认，再加一层批次默认会与之冲突
- 填写值必须是四个枚举之一，用于覆盖账号默认值——解决"猫号偶尔发一篇狗内容"的错标问题
- F3A 发布账号校验之外，新增「关联物种」值域校验

| 新增异常场景 | 处理方式 |
|---|---|
| 「关联物种」填写值不在四个枚举内（错别字、自定义值等） | 校验预览标记失败，注明具体行号及合法取值，不允许入库该行 |
| 「关联物种」留空 | **正常放行**，入库时继承发布账号的账号物种定位（非必填字段，不报错） |

**（3）AB-1.1-03 单条发布——新增「关联物种」选择器**

- 在既有「发布账号」选择器之后新增「关联物种」下拉，**默认自动跟随所选发布账号的账号物种定位**，运营可当场覆盖
- 切换发布账号时，「关联物种」自动跟随更新为新账号的默认值（运营已手动改过的情况下不覆盖其选择）
- 单条发布是 `GROWTH_MOMENT` 类种子内容的唯一入口（批量上传不支持该类型，见 V1.1.0 AB-1.1-02「内容类型范围」），因此本触点不可省略

**（4）AB-3B 全量内容管理列表——新增「关联物种」列（种子内容可改，真实用户内容只读）**

- 新增「关联物种」列，展示算法最终推导出的物种值 + **推导来源**（行级覆写 / 账号定位 / 作者宠物档案 / 无——对应算法文档 §1.2 的优先级链）
- 支持按物种与按推导来源筛选
- **真实用户内容只读**：其物种由作者宠物档案决定，运营不应手工干预
- **种子内容可在此处设置 / 清除行级物种覆写，支持批量操作（2026-08-11 新增，随 OQ-20 定稿）**
  - 写入的就是（2）（3）所写的同一个行级覆写字段，算法优先级 0，高于账号物种定位
  - **这是存量种子内容唯一的物种修正入口**——（2）（3）都是发布时才存在的入口，已发布的内容回不去。没有本入口，运营就只有"改账号定位"这一个全量粗粒度开关，无法修正个别错标
  - 典型用法：把某个号的账号定位由 `GENERAL` 改为 `CAT` 后，用「推导来源 = 账号定位」+「物种 = 猫」筛出被批量套上去的内容，把其中实际是狗内容的少数几条逐条或批量改为 `DOG`
- 用途：让运营能自查"还有多少内容没有物种归属"，直接验证配置效果；否则运营配完账号定位无从确认结果

**明确不变更：** 真实用户内容的物种推导不受本条影响（仍走作者宠物档案，见算法文档 §1.2 优先级 2-4）；虚拟账号的登录能力、审核规则、Feed 混排规则（V1.1.0 AB-1.1-02A「不改变 Feed 展示规则」）均不变；本条不新增任何内容标签的用户可见展示——物种归属是纯算法输入，**App 端不展示物种标签**。

`[NOTE FOR PM/工程]` 落地需两个字段：① 虚拟账号侧的「账号物种定位」；② `content_posts` 上一个**可空**的行级物种覆写列（仅种子内容按需写入，真实用户内容恒为空，走 join 推导）。这是 **AB-3H 本条**对内容表的唯一 schema 新增，稀疏列、无需回填存量。见 A-5。（本文档另有 AB-3K / AB-3L 的草稿与排期存储，那是一张独立的新表、不动内容表主结构，见 A-11。）

### AB-3I：运营发布身份池（新增，扩展 AB-1.1-02A 虚拟账号管理）

**背景：** V1.1.0 AB-1.1-02A 把虚拟账号定位为"专用于种子内容发布"的第四类账号，不具备登录能力。运营实际使用中出现两类虚拟账号覆盖不到的需求：

1. 公司有若干**人格化 IP 账号**——用真人身份在 App 内注册、有宠物档案、有成长日历、已积累粉丝，**本质是公司资产、由运营团队维护、人走号留**。这类账号的内容无法用虚拟号替代：虚拟号没有宠物档案（发不了成长日历）、没有粉丝积累、主页是空的
2. 运营需要在**人不在手机边上**、或需要**批量 / 定时**铺内容时，从后台以这些账号的身份发布——而当前后台的发布账号选择只接受虚拟账号

因此把「虚拟账号池」扩展为**运营发布身份池**，容纳两类身份。

**身份池的两类账号：**

| 类型 | 说明 | 可登录 | 有宠物档案 | 来源 |
|---|---|---|---|---|
| 虚拟账号 | AB-1.1-02A 既有能力，无登录、纯作者身份 | 否 | 否 | 后台创建 |
| **运营真实账号** | 公司人格化 IP 号，真人身份注册 | 是（员工在 App 内正常使用） | 是 | 后台从既有真实用户中授权纳入 |

**后果：**

**（1）「虚拟账号管理」页升格为「运营发布身份」管理**

- 入口沿用 AB-1.1-02A 的「用户管理」→ 原「虚拟账号管理」，页面分为两区：【虚拟账号】【运营真实账号】
- **虚拟账号侧的既有能力全部不变**（创建、列表、启用/禁用、导出，以及 AB-3H 的「账号物种定位」）
- 顺带修正：虚拟账号的「头像」输入由 URL 文本框改为上传控件（与 AB-3J（2）同源，一并改）

**（2）运营真实账号的纳入与移除**

- **纳入**：在纳入界面按**用户 ID / 昵称**搜索既有真实用户（复用 V1.1.0 AB-1.1-15 的用户搜索能力），选中后填写**授权说明**（必填，记录该号的内部授权依据，如"公司 IP 号 · 已完成内部授权确认"）并确认纳入
- **不做 App 端验证**：不要求员工在 App 内扫码或输验证码确认（见 A-6）
- **移除**：可随时移出身份池。移出后该账号**不可再被选为新内容的发布者**；其历史已发布内容的作者归属不变、内容本身不受影响（与 AB-1.1-02A 的禁用规则同一处理）
- **移出 ≠ 封号**：移出身份池只收回"后台可代其发布"这一项能力，该账号在 App 内的一切行为完全不受影响
- **移出前须提示该账号名下的待发布排期数（2026-08-10 新增）**：移出确认弹窗须显示「该账号当前有 **N 条**待发布排期，移出后这些内容到点将发布失败」，并提供跳转链接直达按该账号过滤的排期列表
  - **不阻止移出**（运营可能正是要停掉该号），只要求知情
  - **排期本身不自动取消、不自动转草稿**，保持 AB-3L 既有的"到点标记失败并注明原因"——自动改状态是替运营做决定，且失败记录带原因比静默转草稿更可追溯
  - 不做这条的后果是：那 N 条会在未来若干天里**陆续、分散地失败**，运营要等到失败才发现，而届时内容的时间窗（如配合某活动）多半已经错过。移出是个瞬间的、有明确操作人的动作，是成本最低的提示时机
  - ⚠️ **虚拟账号的「禁用」操作同样适用本提示**：AB-1.1-02A 的禁用与本条的移出是同一处理模式，虚拟账号一样能排定时。V1.1.0 原文没有此要求（当时尚无定时发布能力），属 AB-3L 引入定时后的连带影响
- **列表字段**：用户 ID / 昵称 / 头像 / 授权说明 / 纳入时间 / 纳入操作人 / 状态（在池 / 已移出）/ 经后台发布内容数 / **物种推导结果 + 来源**
- **「经后台发布内容数」不等于虚拟账号的「累计发布内容数」**：只统计经后台代发的内容，该账号在 App 内自主发布的内容不计入
- **「物种推导结果 + 来源」是一列自查用的只读信息**（2026-08-10 补）：展示该账号当前能推导出的物种值及来源（单物种宠物档案 / 多物种→`GENERAL` / 无档案→推导为空）。运营真实账号**没有「账号物种定位」字段**（那是虚拟账号补偿"无宠物档案"的专属字段，见 AB-3J（4）与 §7.5 第 6 条），因此**未建档或养多物种的号推不出具体物种**，只能在发布时逐行填「关联物种」。本列的用途就是让运营提前知道哪些号属于这种情况，否则无从察觉
- 支持导出，字段与列表一致

**（3）权限：独立权限码**

- 新增独立权限码（建议 `seed.publish_as_real`），控制两件事：① 运营真实账号的纳入 / 移除；② 以运营真实账号身份发布内容（含 AB-3J 单条、AB-3K 批量、AB-3L 定时三处）
- **本版本仅分配给超级管理员**，不下放给普通后台账号（见 OQ-24）。权限码独立存在的意义是后续如需下放，只改权限配置、不改代码
- 与既有 `virtual_account.manage` **完全解耦**——能管虚拟账号 ≠ 能以真人身份发言
- V1.1.0 AB-1.1-29 的后台账号权限勾选清单需同步新增该项

**（4）选错身份的防呆（界面要求，三处发布入口统一遵守）**

以运营真实账号误发的后果**不可撤回**——内容会出现在该真人的个人主页并推送给其粉丝，事后删除也已经推送过了。因此 AB-3J / AB-3K / AB-3L 的所有「发布账号」选择器统一遵守：

- **分组展示，不平铺**：【虚拟账号】/【运营真实账号】两组
- 运营真实账号项带**显著视觉标记 + 后果说明**，建议文案：「⚠️ 真实账号 · 内容会出现在该账号个人主页并推送给其粉丝」
- **默认不预选任何账号**，强制显式选择
- **仅当选中运营真实账号时**弹二次确认（虚拟账号不弹，避免拖慢常用路径）

**（5）审计**

- 纳入 / 移除身份池记审计：操作人、时间、目标账号、授权说明
- **以运营真实账号发布的每条内容，记录实际操作的后台账号**——这是与虚拟账号最大的差别：虚拟账号是平台身份，运营真实账号是某个真人的账号，出事要能追到具体是谁操作的

**（6）后台代发与账号持有人自主操作的边界（2026-08-10 新增）**

运营真实账号有**两个写入方**——后台（运营代发）与 App（账号持有人本人）。这是"引入真实账号"这一决策的固有代价，不是能设计掉的问题；本条只把边界写明，使运营有预期。虚拟账号不存在此问题（只有后台一个写入方）。

- **后台不阻止持有人在 App 内删除后台代发的内容**——那是他自己的账号，系统去锁定反而越权。但**后台的批次记录须能反映该条"已被删除"**，不可继续显示为在线状态
- **持有人在 App 内自主发布的内容不进后台的批次 / 排期记录**，也**不计入「经后台发布内容数」**（见上方（2）列表字段说明）。即后台看不到、也不管他自己发的内容，两条链路各自独立
- **定时发布到点时不再做去重校验**：去重只在 AB-3K Step 3 校验一次。因此"运营排了明天的定时、持有人今天自己在 App 发了近似内容"时，明天那条**照常发布**。刻意不加到点前的二次校验——那会让"到点必发"的预期变得不确定，而重复内容的代价远小于"排好的内容莫名没发"（见 A-16）

**明确不做：**

- **不支持员工私人账号**。身份池只接纳公司资产性质的 IP 号；存量混用的私人号须先走内部授权确认转为公司号，再纳入（见 A-7）
- **不做 App 端绑定验证**（见 A-6）
- **运营真实账号的点赞 / 评论能力不在本条范围**——AB-3F 运营账号互动能力仍限虚拟账号池，其"不支持冒用真实用户账号"的限制在该条自身范围内继续有效，本条只放开"发布"（见 §7.5 第 5 条）

`[NOTE FOR PM/工程]` 运营真实账号**无需新增账号类型**——账号类型保持"真实用户"不变，只需一张"授权发布身份"关联表（用户 ID + 授权说明 + 纳入人 + 纳入时间 + 状态）。现有内容发布服务本就接受任意用户 ID 作为作者，唯一需要放开的是批量发布服务里"作者必须是虚拟账号"的硬断言，改为"在身份池内即可"。

### AB-3J：单条发布整改（新增，落地 AB-1.1-03 未交付项）

**背景：** V1.1.0 AB-1.1-03 定义了两条要求——「图片 URL 文本框改为上传控件」与「新增发布账号选择器」——**两条均未交付**（原因见 §7.5「实现偏差记录」）。连带后果是本文档 AB-3H (3) 要求的"在既有「发布账号」选择器之后新增「关联物种」下拉"没有落脚处，该触点无法实现。

**后果：**

**（1）新增「发布账号」选择器**（落地 AB-1.1-03 第 2 条）

- 数据来源为 AB-3I 运营发布身份池（虚拟账号 + 运营真实账号），支持模糊搜索
- 按 AB-3I（4）的防呆要求实现：分组、真实账号标记与后果说明、默认不预选、真实账号二次确认
- **本条覆盖当前"作者写死为登录后台账号所关联的官方作者身份"的行为**

**（2）图片输入由 URL 改为上传控件**（落地 AB-1.1-03 第 1 条）

- 「图片 URL」多行文本框改为图片上传控件：**多图上传、拖拽排序（首图即封面）、单张删除、支持粘贴上传**
- 限制对齐 App 端：每条 **≤9 张**、**单张 ≤10MB**、格式 **JPG / PNG / WEBP**（后台不支持 HEIC，见 A-12）
- **保留一个折叠的「粘贴图片 URL」入口**作为兜底——运营手上确实存在已有 CDN 链接的素材，完全砍掉会制造新的绕路；但默认路径是上传
- 同一改动一并覆盖虚拟账号头像的上传（见 AB-3I（1））

**（2b）图片宽高比检测与警告（2026-08-10 新增，关联 App 端 FR-71）**

App 端上传超出容差区间的图片时会弹裁剪框、由用户自选构图（`1-1-6prd.md` FR-71）；**后台没有这一步**，超比例图会静默进库，然后在 Feed 渲染时被 clamp 到 0.75~1.34 并做 cover 裁切（FR-71「存量内容的渲染规则」）——**运营完全不知道自己的图会被裁掉多少，构图可能被毁**。因此：

- **上传时检测图片原始宽高比**，落在 **0.75~1.34 闭区间**内的不提示；超出区间的**给出带具体数字的警告**，但**不阻止上传**
- 警告文案须说明**裁切方向与百分比**，不可笼统写"会被裁切"。示例：「该图比例 16:9（1.78），超出 Feed 展示区间 0.75~1.34，展示时将**左右各裁切约 25%**，建议先裁好再上传」
- 同时提示 **首图决定整帖容器高度**（FR-71：轮播容器高度按首图最终比例锁定，非首图居中裁剪填满）——首图超比例时该帖所有图都按 clamp 后的比例展示
- **后台不做裁剪框**（见 A-13）：运营在桌面端工作、手上有外部裁图工具，内置裁剪器是为手机端用户存在的；当前的问题不是运营不能裁，而是**不知道会被裁**
- 本条同样适用于 AB-3K Step 1 的素材上传

**（3）「绑定宠物」由手填 ID 改为按发布账号动态加载的下拉**

- 当前要求运营手填宠物的数字 ID，而服务端校验的是"该宠物是否属于所选作者"——选了 A 的账号却填了 B 的宠物 ID 会直接报错，且运营无从判断原因
- 改为：选定发布账号后，宠物选择器只列出**该账号名下的宠物档案**；切换发布账号时列表随之刷新
- **顺带修好一个当前实际发不出来的能力**：`GROWTH_MOMENT`（成长日历）按 V1.1.0 AB-1.1-02「不纳入批量上传、继续通过单条发布完成」，但虚拟账号没有宠物档案 → 选虚拟号必然校验失败。引入运营真实账号（有宠物档案）后，这条路才真正通

**（4）与 AB-3H 的衔接**

- 「关联物种」下拉按 AB-3H (3) 置于「发布账号」选择器之后，行为沿用该条
- **补齐 AB-3H 未覆盖的情形**：发布账号是**运营真实账号**时不存在「账号物种定位」字段（那是虚拟账号的属性），此时「关联物种」默认值为**留空**，由算法按作者宠物档案推导（算法文档 §1.2 优先级 2-4）。详见 §7.5 第 6 条

### AB-3K：批量发布工作台（新增，重定义 AB-1.1-02 批量上传）

**背景与现状：** 当前后台的批量发布是**两条并列的路径**——① 多行纯文本，格式为 `文本 ||| 图URL1, 图URL2`；② Excel 导入（表格前两列 = 正文 / 图片 URL）。两条路径**共用同一个后端**，Excel 路径只是把表格前两列拼回同一个竖线字符串，功能完全重叠；且各自带一个一模一样的账号下拉，所以下拉在同一页面出现两次。更关键的是**没有校验预览、没有确认入库**——提交即上线，50 行错 3 行就是 3 条线上真帖，只能逐条去找、逐条下架。

**对 AB-1.1-02 的重定义：** 原方案的 zip 图片包 + 产品编码文件夹名 + 骨架 Excel 生成 + zip 文件清单指纹**整套废止**，理由与替代方案见 §7.5 第 3 条。

**后果：一个页面、页头一处批次级设置、三步流程**

**（0）批次级设置（页头，各选一次）**

- 默认发布账号（来源 AB-3I，按其（4）防呆要求）
- 默认内容类型（**下拉不含 `GROWTH_MOMENT`**，批量不支持该类型，见 A-10）
- 默认计划发布时间（选填，见 AB-3L）
- **重复的下拉由此消除**——批次级设置全页只有这一处

**「关联物种」刻意不设批次级默认（2026-08-10 决策，见 A-14）：** 「关联物种」只有**行级填写**一档，留空即按 AB-3H 既有规则继承账号物种定位。原因是账号物种定位**本身就在扮演账号级默认值的角色，而且扮演得更好**——配一次永久生效、跟着账号走，不必每批重设；再加一层批次默认会与它冲突（批次默认设「猫」、行留空、而该行发布账号是狗号时，取谁没有正确答案）。

- **因此两个字段的默认值来源不同，但心智一致**：都是「一个默认值 + 行级填例外 + 留空继承默认」；只是**发布账号的默认值来自批次设置**（它没有任何上级来源，不设批次默认就得逐行填），**关联物种的默认值来自账号属性**
- ⚠️ **运营操作提示（须在界面明示）：先把虚拟账号的「账号物种定位」配好，再批量发**。AB-3H 规定存量虚拟账号统一置为 `GENERAL`，若在未配置定位时就开始批量发布，该批内容的物种会全部落到 `GENERAL`，只能逐行填「关联物种」补救。工程与运营都不会自行想到这个先后关系，须由界面提示

**（1）Step 1 · 素材上传（选填）**

- 多选或拖拽上传本批图片，服务端落公开桶后回显**缩略图墙 + 文件名清单**
- 限制同 AB-3J（2）：单张 ≤10MB、JPG / PNG / WEBP；**宽高比检测与警告同 AB-3J（2b）**，缩略图墙上对超出 0.75~1.34 区间的图打标记，避免整批发完才发现构图被裁
- **单批素材总量上限：≤200 张 / 总计 ≤500MB**（2026-08-10 定，替代原 AB-1.1-02 已废止的「zip ≤300MB」）
  - 推算依据：每条内容最多 9 张图，单批实际发 20~30 条已属偏多（校验预览需逐行过目），30×9=270 张，取 200 张覆盖绝大多数场景并留余量；500MB 比原 zip 上限宽松（散装不压缩），但不至于让单次操作失控
  - **超限须在选择文件时即拦截，并实时显示已选数量 / 总大小**，不可等全部传完才报错——否则运营已经等了几分钟，且部分成功部分失败的中间状态难以处置
- **支持分多次拖入，素材追加不替换**：缩略图墙**累积**展示（运营常见做法是先拖猫的文件夹、再拖狗的）；**上限按累计值计算**，否则分三次拖即可绕过限制
- **同批文件名重复在上传阶段即拦截**，要求改名或自动加序号后缀——不拖到校验阶段才报错（那时运营已经把整份表格填完了）；分次追加时与**已在墙上的素材**一并查重（见 A-9）
- 本批素材同时供下方两种录入方式引用
- **素材须挂在批次记录下，不产生游离对象（2026-08-10 新增）**：Step 1 的图片是**先落对象存储再回显缩略图**的——运营刚拖进去，图就已经在存储里、而此时还没有任何内容行引用它。因此上传的素材须与批次记录绑定（批次 ID + 素材清单），归属可追溯
  - **草稿保留 7 天，按行清理**：超过 7 天未提交的**草稿状态的行**予以清理，走定时扫描器（后台已有多个同模式扫描器可照抄）。⚠️ **清理对象是行、不是批次**（状态是行级的，批次不持有独立状态，见 AB-3L）——**已排期 / 已发布的行一律不受影响**；素材只在**不被任何非草稿行引用**时才一并删除；一个批次内所有行都被清理干净后，该批次记录本身才消失。若按批次清理，会把同批次里已排期的行一起删掉，属事故（保留期取值见 A-17）
  - 不做这条的后果是**静默的存储泄漏**：运营拖错文件夹关掉页面、填一半放弃、整批校验没过——这些图会永久留在存储里，不报错、不影响功能，无人会发现，只是账单慢慢涨（按上方上限，单个废弃批次最多留下 500MB）

**（2）Step 2 · 内容录入（两种方式，共用 Step 1 的素材）**

*方式一 · 在线录入*

- 一行一条内容，逐行填：正文 / 图片（从素材墙点选，或行内直接上传，可拖拽排序）/ 发布账号 / 内容类型 / 关联物种 / 计划发布时间
- **支持粘贴多行文本自动分行**——粘入 20 行文本自动生成 20 个待编辑行，再逐行补图片与例外字段。这保留了原竖线路径的录入速度，但没有分隔符格式风险
  - **分行规则：按单行分隔，一行一条**（空行跳过，不生成空内容行）
  - ⚠️ **界面须明示该限制**：「粘贴按**一行一条**拆分。含段落换行的长正文请用 Excel 导入，或直接在此逐行编辑。」**这句提示不可省略**——运营若粘入一篇带段落的长科普，会被拆成一堆残句和空行，且不会有任何报错提示（每一段都是合法的正文），只能手动合并回去，比原竖线格式更糟
  - **粘贴入口的定位是"一批短文案快速录入"**（如 20 条 Moment 日常，每条一两句）。长正文（多为 `KNOWLEDGE` 科普）本就该逐条精编或走 Excel；刻意不用一个入口覆盖这两种差异很大的场景（见 A-15）
- 形态为**行卡片列表**而非电子表格网格（见 A-8）

*方式二 · Excel 导入*

- 模板列：**正文 / 图片文件名 / 发布账号 / 内容类型 / 关联物种 / 计划发布时间**（当前模板只有「正文」「图片URL」两列）
- 图片列填 **Step 1 已上传素材的文件名**（多张用英文逗号分隔，**顺序即展示顺序**），不再填 URL、不再需要 zip 与产品编码
- **模板须带下拉数据校验**：内容类型、关联物种、发布账号三列在 Excel 内做成下拉可选，运营直接选而不是手打——比事后校验拦截体验好一个量级
  - **「内容类型」下拉的取值只含 `MOMENT` / `KNOWLEDGE`，不含 `GROWTH_MOMENT`**（与 Step 0 的批次级下拉一致）。若模板里能选到该值，运营选了就是整行必然失败，属可以从源头避免的错误
- 列头带填写说明；保留模板下载入口

*两种方式的字段语义完全一致，逐字段定义如下（在线录入与 Excel 导入适用同一套规则）*

| 字段 | 有批次默认？ | 留空时取什么 |
|---|---|---|
| **发布账号** | 有 | 继承批次默认 |
| **内容类型** | 有 | 继承批次默认 |
| **计划发布时间** | 有 | 继承批次默认（批次默认也为空 = 立即发布） |
| **关联物种** | **无**（刻意，见 Step 0） | ① 该行发布账号是**虚拟账号** → 继承其「账号物种定位」（AB-3H）<br>② 该行发布账号是**运营真实账号** → **留空入库**，由算法按作者宠物档案推导（算法文档 §1.2 优先级 2/3；真实账号无「账号物种定位」字段，见 AB-3J（4）） |

**「发布账号」的三层继承示例：**

| 行 | 正文 | 「发布账号」列 | 实际发布身份 |
|---|---|---|---|
| 1 | 猫咪夏天防中暑 | *(留空)* | 继承批次默认 |
| 2 | 猫粮怎么选 | *(留空)* | 继承批次默认 |
| 3 | 狗狗遛弯注意事项 | 狗号B | 狗号B（行级覆盖） |

- **四个字段的运营心智一致**——都是「填了就用你填的，留空就继承默认」，不必记"这列必填那列选填"；差别只在**默认值来自哪里**：前三个来自批次设置，「关联物种」来自账号属性（原因见 Step 0）
- ⚠️ 「发布账号」这条覆盖了 V1.1.0 AB-1.1-02「发布账号列留空 = 校验失败、视为必填缺失」的规则，改为留空继承（见 §7.5 第 2 条）

**（3）Step 3 · 校验预览与确认发布**

- 逐行展示：行号 / 正文摘要 / 图片缩略图 / 发布账号 / 内容类型 / 关联物种 / 计划发布时间 / 校验结果
- **只发通过的行**：校验失败的行**不阻塞整批**，通过的行可直接确认发布；失败行**以草稿状态保留在该批次内，可修改后再次提交**（状态是行级的，批次不持有独立状态，见 AB-3L）
- 确认发布后，按批次级 / 行级的计划发布时间决定立即发布还是转入排期（AB-3L）

**异常场景处理：**

| 场景 | 处理方式 |
|---|---|
| 图片文件名在本批素材中找不到 | 该行标记失败，注明缺失的文件名；其余行不受影响 |
| 图片格式 / 大小不符 | Step 1 上传阶段即拦截，不进入录入 |
| 同批图片文件名重复 | Step 1 上传阶段即拦截，要求改名或自动加序号后缀（分次追加时与已在墙上的素材一并查重） |
| 单批素材超出 200 张 / 500MB | Step 1 **选择文件时即拦截**并提示已选数量与总大小，不进入上传 |
| 「发布账号」填写值不在身份池内，或已禁用 / 已移出池 | 该行标记失败，注明具体行号及原因 |
| 「发布账号」留空 | **正常放行**，继承批次默认（**覆盖** V1.1.0 原「留空报错」规则） |
| 「内容类型」/「关联物种」值不在枚举内 | 该行标记失败，注明合法取值 |
| 「内容类型」填了 `GROWTH_MOMENT` | 该行标记失败，注明批量不支持该类型、请走 AB-3J 单条发布（模板下拉已不含该值，仅拦截手工改写模板的情形） |
| 与已发布内容重复（内容去重命中） | **标记为提示，不静默跳过**：注明重复的已发布内容 ID，由运营决定是否仍要发布（见下方去重口径修正） |
| 正文与图片皆空 | 该行标记失败（沿用 App 端的最低内容门槛） |

**内容类型范围：** 放开为 `MOMENT` + `KNOWLEDGE`——这本就是 V1.1.0 AB-1.1-02 的原有要求，当前实现硬编码为单一类型，属**实现偏差而非需求变更**（见 §7.5 第 4 条）。`GROWTH_MOMENT` **仍不纳入批量**，继续走 AB-3J 单条发布（见 A-10）。

**内容去重口径修正：** 当前去重指纹只算内容本身（类型 + 正文 + 图片）、**不含作者**，且命中即**静默跳过**、界面只显示一个跳过条数。两个实际后果：① 同一文案想用两个不同账号各发一遍（内容运营常规操作，引入运营真实账号后会更频繁）第二次会被吞掉；② 已发布内容被删除后指纹记录不清理，**同样的文案永久无法重发**。本条修正为：

- 去重维度**加入作者**——同一文案不同账号各自独立
- 命中不再静默跳过，改为在 Step 3 标记提示，由运营决定
- **内容被删除时清理对应的指纹记录**

**批次审计：** 每个批次记录操作人、时间、以及批次内容清单（含各行最终生成的内容 ID）。

`[NOTE FOR PM/工程]` 「确认发布」需要"存下来但还没发"的草稿态，这是当前完全不具备的能力（内容状态只有已发布 / 审核中 / 作者注销）。该草稿态与 AB-3L 的排期态是**同一数据模型的不同状态**，须一次设计到位，见 A-11 与 AB-3L。批次内容清单同时是后续「整批撤回」的数据基础（本版本不做，见 §7.2 与 OQ-22）。

### AB-3L：种子内容定时发布（新增）

**背景：** 三个驱动因素——① 运营需要在人不在手机边上时预排内容；② 批量一次灌入几十条，Feed 上时间戳全挤在同一分钟，观感明显不真实，**按节奏铺开本身就是内容运营需求**；③ 与 AB-3K 的校验草稿态共用数据模型，同期设计的成本远低于事后补建。

**后果：**

- **AB-3J 单条发布、AB-3K 批量发布均支持设置计划发布时间**；批量支持批次级统一设置 + 行级覆盖
- 到达计划时间自动发布，走**与即时发布完全相同的链路**（含内容自动审核，**无豁免**，延续 V1.0.0「种子内容不设审核豁免」的既定原则）
- **时区**：计划时间一律按 **WIB（GMT+7 / `Asia/Jakarta`）** 解释，**界面须在时间输入控件旁明示「WIB」字样**；入库转 UTC 存储，按绝对时刻执行。与本文档 AB-10A / AB-10C / AB-12A 的时区口径一致（**四处一致**）
- 计划时间**不可早于当前时刻**
- **排期管理**：新增排期列表，展示待发布的排期项（内容摘要 / 发布账号 / 计划时间 / 状态），支持**修改计划时间**与**取消排期**（取消即回退为草稿，不发布）
- **发布失败的处置**：到点发布失败时（内容审核硬拦截、发布账号已移出身份池或已禁用、绑定宠物已删除等），该项标记为失败并注明原因，**不自动重试**，保留在排期列表供运营处理
- **到点不再做去重校验**：去重只在 AB-3K Step 3 校验一次，排期期间若出现近似内容，到点仍照常发布。理由与取舍见 AB-3I（6）与 A-16
- **状态机与 AB-3K 的草稿态共用同一模型**：草稿（录入中）→ 校验通过（待确认）→ 已排期（待发布）→ 已发布 / 发布失败
- **状态是行级的，批次只是分组容器、不持有独立状态（2026-08-10 明确）**：一个批次内各行的状态可以完全不同，**不存在"批次状态"这个概念**，因此也不需要为"部分成功"设计任何混合态。批次列表按其各行状态**聚合展示**即可，例如「本批 50 条：47 已发布 / 5 排期中 / 3 待修正」。若按批次级状态实现，会被迫为"47 发了、5 在排、3 没过"这种常态定义一堆组合态，且行级操作（改某一条的计划时间、修某一条的校验错误）无法落地
- 定时发布对两类发布身份**一视同仁**，虚拟账号与运营真实账号均支持

`[NOTE FOR PM/工程]` 到点发布用定时扫描器实现即可，后台已有多个同模式的定时扫描器可直接照抄；本条的主要工程量在排期存储与状态机，而该存储与 AB-3K 的草稿态是同一张表，不应各建一套（见 A-11）。

**后果：**

**打标操作界面须向运营提示排序副作用（2026-08-05 新增）：** 首页推荐算法 V2 把「装饰标签生效中」作为荣誉加成 **×1.3** 权重（见 `../2.数据算法/首页推荐算法.md` §4），因此打标同时是一个流量动作。**打标/取消打标的操作界面需明示这一点**，建议文案如：

> 「取消打标 / 到期时，曝光将取消标签带来的曝光权重」

- 取消打标 / 标签到期同样要让运营预期到曝光会回落，避免误判为线上故障
- 本提示为界面文案要求，不改变任何功能行为；权重数值以算法文档为准，算法侧调整后本处文案需同步

### 7.4 AB-3H 的来源与依赖（2026-07-29 新增）

- **AB-3H 扩展的是 V1.1.0 已上线能力**（AB-1.1-02A / AB-1.1-02 / AB-1.1-03），不依赖 V1.1.2、不依赖 V1.1.6 App 端任何 FR，是本文档中唯一无 App 端对应 FR 且无跨版本前置的一条

### 7.5 AB-3I~AB-3L 的来源与跨版本订正（2026-08-10 新增）

**来源：** 运营试用管理后台的种子内容发布功能后提出三条问题：

1. **发布账号缺失 / 不完整**——单独发布页面完全没有「发布账号」选择；批量发布页面只能选虚拟账号，且下拉在同一页面重复出现两次（普通批量区一次、Excel 导入区一次），没有"真实账号（员工马甲）"这个选项

对应本文档 AB-3I（问题 1 的真实账号部分）/ AB-3J（问题 1 的单条部分 + 问题 2）/ AB-3K（问题 1 的重复下拉 + 问题 2 + 问题 3）/ AB-3L（问题 1 讨论中识别出的定时发布诉求）。

**不来自 V1.2.0 后台文档的拆分**（与 AB-3H 同），因此不列入 §7.1 的拆分明细表。
