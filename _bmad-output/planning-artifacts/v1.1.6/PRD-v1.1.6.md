## 1. 版本目标

1. **内容运营能力补齐**：内容顶置、用户标签、内容装饰标签、里程碑完成通知补齐——让运营具备干预内容分发、标记优质内容与优质用户、以及完整触达用户的手段。
2. **增长与召回基建**：手机号采集（为后续 WhatsApp 触达 / OTP 登录积累数据）、推送权限多触发点唤醒（提升关闭通知用户的召回机会）、单条内容分享卡片（对外拉新入口）。
3. **首页图片展示规范化**：解决 Feed 图片版面参差不齐的问题，采用 IG 模式（单列 + 容差区间外裁剪），不做瀑布流改造。
4. **宠物主页对外分享收口（FR-92）**：H5 现状视觉不佳，随本版本重新设计；同时补齐 V1.0.0 FR-14 从未定义过的「访客只读预览可见范围」——健康记录与问诊记录不对访客开放、访客不可二次转发。**不做分享前的授权范围告知**（2026-08-06，见 §2.9 §③）；**H5 双 CTA 合并为单个下载 CTA**（2026-08-07，覆盖 FR-14，见 §2.9 §④）。见 §2.9 与 OQ-9。

## 2. 功能与需求

### 2.1 内容顶置功能

**背景：** 解决官方账号推送活动与广告页面曝光度不足的问题。首页 Feed 顶部设顶置坑位，由运营通过后台配置。用户自行顶置自己发布内容到个人主页的能力本版本不做——目前没有可供其他用户互相访问查看的用户主页功能，顶到自己主页意义不大。**话题页顶部坑位不在本版本范围内**——它依赖平台的内容话题功能，该功能尚未上线，故本版本仅实现 Feed 坑位。后续版本规划见 `Roadmap.md`。

#### FR-68：顶置坑位与内容顶置（本版本仅 Feed 坑位）

首页 Feed 顶部设 1 个顶置坑位，由运营在后台配置该坑位在指定时间段展示的内容。

**后果：**

- **坑位数量**：Feed 顶部 1 个坑位（话题页坑位不在本版本范围内，见上方背景说明）
- **可顶置对象二选一（互斥，同一坑位同一时段只能是其中一种）：**
  - **(a) 顶置已发布内容**：将某个账号（含专门设立的「广告账号」）已发布的一篇**公开**内容顶到坑位展示；该内容**同时仍保留在其原有的时间线位置**（顶置是额外展示，不是从原位置挪走）。**可顶置范围仅限公开内容**（Moment / Tips / 发布时已开启「同步到 Moment」的 Diary）——未同步的 Diary 只在作者自己的成长档案时间线展示，不进任何平台公开位，运营在后台也选不到；又因 V1.1.2 FR-83 已确定**同步状态发布后不可更改**，不存在已顶置内容中途转私密的场景，无需回退逻辑（详见 `v1-1-6后台prd.md` AB-10A）
  - **(b) 推广卡片（不对应任何真实帖子）**：运营直接配置一张卡片，字段包括图片（必填）、标题（必填）、跳转目标（二选一：外部链接 URL / App 内部深链接，如跳转到某个话题页或某篇帖子——`[ASSUMPTION: 复用 V1.0.0 已有深链接基础设施（FR-22 系列 7 种推送类型深链接），扩展支持顶置卡片的深链接跳转，非新建深链接体系]`）
- **顶置角标的位置（2026-08-05 定案，闭合原 ASSUMPTION）**：**顶置角标固定在 Feed 卡片右上角**，与 FR-75 内容装饰标签（固定左下角）构成"右上 + 左下"的共存布局，两者互不遮挡。顶置内容其余部分与普通内容条目**完全同构**（作者行 / 图片 / 操作行 / 正文 / 时间，见 FR-93 §①），仅多一个顶置角标；常规互动入口（举报等）位置不变。(a)(b) 两类对象共用同一个角标，视觉不作区分
  - **作废方案：** UI 稿 01 屏曾按"顶置标记挂在头像右下角的小圆点徽章"绘制（`.pin-avatar-badge`），与 C5 屏及 FR-75 的"右上角"写法冲突，现统一为**右上角**、01 屏方案作废、该屏需重画。选择右上角的实质理由：① FR-75 已定义"右上 vs 左下"的共存布局，改为头像角标会破坏这条已定规则；② 头像/昵称区已经要承载 FR-74 用户标签（最多 3 个），再挂顶置圆点会挤到昵称；③ 顶置是"平台干预分发"的标识，需要基本的醒目度，15px 的头像角标识别度不足
- **坑位内的卡片是否支持多图轮播（2026-08-05 补充，关联 FR-71）**：FR-71 已把 Feed 卡片的多图改为可左右滑动（覆盖 V1.0.0 FR-17）。**顶置坑位展示的是一张普通内容卡片，因此同样适用轮播规则**——顶置的多图帖在坑位内可左右滑动、展示圆点指示器，容器高度按首图锁定。推广卡片(b)只有一张图，不涉及轮播
- **定时展示**：每次顶置配置需设置开始时间 + 结束时间；到开始时间自动上线展示，到结束时间自动下线（恢复坑位为空/展示下一个已排期的顶置内容）
- **时区口径（2026-08-05 确认，本版本所有定时能力统一适用）**：**运营后台配置的开始/结束时间一律按印尼西部时间 WIB（GMT+7 / `Asia/Jakarta`）解释**，后台界面需明示该时区（如输入框旁标注「WIB」），避免运营误按本机时区理解
  - **存储与判断**：入库统一转为 UTC 绝对时刻存储；上下线判断按该绝对时刻执行，**不按客户端本地时区二次换算**——同一条顶置配置对全部用户在同一物理时刻上下线
  - **对 WITA / WIT 用户的影响（已接受）**：印尼横跨 WIB / WITA(GMT+8) / WIT(GMT+9) 三个时区，因此一条配置为 WIB 08:00 上线的顶置内容，对 WITA 用户是当地 09:00、对 WIT 用户是当地 10:00。**本版本不做按用户本地时区分区上线**——运营心智以雅加达时间为准，分区上线会让同一条配置产生三套生效时刻，排期冲突校验与效果归因都会显著复杂化，收益不足
  - **适用范围**：本口径同样适用于 FR-74 用户标签、FR-75 内容装饰标签的定时生效/失效（两者均声明"与 FR-68 顶置坑位的定时逻辑一致"），不再各自重复定义
- **排期冲突处理**：`[ASSUMPTION: 同一坑位的两次顶置配置时间窗口不可重叠，后台提交时校验并拦截重叠排期，运营需调整时间窗口后才能保存]`
- **坑位为空时**：`[ASSUMPTION: 当前无生效顶置配置时，坑位不展示/该位置由普通内容按正常排序填充，不留空白占位]`
- **顶置内容的作者被当前查看者拉黑时（2026-08-14 补入）**：对**该查看者**视为坑位为空，按上一条「坑位为空」规则回退为普通内容填充；**不为该用户单独挑替补顶置内容**，其他用户的顶置展示不受影响。这是 V1.1.4 FR-94「凡向该用户展示他人内容的位置一律套用拉黑过滤」这条通用规则在本坑位的落地，**不是本 FR 新增机制**；实现上直接复用 V1.1.4 已建的「按查看者隐藏」过滤层，不新写逻辑（⚠️ 该层是**两条并列、刻意不合并**的子查询——举报维度藏一条帖、账号维度藏一个人，本条套后者；2026-08-16 复核，V1.1.4 该层已实现完毕）
- **顶置期间内容被下架**：顶置的内容（对象 a）在生效期间被下架（作者删除、举报审核判定违规下架、或作者账号被封禁），系统自动立即结束该条顶置配置（视为提前到达结束时间），坑位按上一条「坑位为空」规则回退为普通内容填充，不需要运营手动介入摘除

推广卡片(b)不加"广告/推广"角标，与顶置的已发布内容(a)视觉样式一致，采用与普通内容条目相同的外观（见 FR-93 §①）+ 顶置角标。已核实印尼现行法律（《消费者保护法》第9-10/17条、Permendag 31/2023 电子广告条款）仅规范广告内容真实性，不要求标注"这是广告"；EPI 广告道德准则虽提及内容应可与新闻/讽刺内容区分，但为行业自律准则、非强制法规，且缺乏针对数字平台的执行机制——不构成合规阻塞项。

**推广卡片的两类用途须区分（2026-08-05 补充）：** 推广卡片(b)**并不等于"广告"**，实际有两类用途，合规性质不同：

| 用途 | 举例 | 合规性质 |
| --- | --- | --- |
| **(b1) 平台自有活动引导**（本版本主要用途） | 平台自办活动、功能上新引导、官方话题征集，跳转 App 内部深链接 | **不是广告**，属应用自身内容的运营位，不涉及任何广告披露要求，也不受应用商店广告政策约束 |
| **(b2) 第三方付费投放** | 商家 / 品牌方付费购买该坑位 | 属广告。上述印尼法律核查结论仍成立（不强制标注），但**尚未评估 Google Play / App Store 的广告政策**——两家商店对"广告须与应用内容可区分、不得模拟应用 UI"均有独立要求，且这是实际的**提审拒绝风险**，比 EPI 自律准则更具约束力 |

- **本版本按 (b1) 自有活动引导定位与使用**，因此不加广告标识、与普通内容同视觉是成立的
- **⚠️ 若未来该坑位开始承接 (b2) 第三方付费投放**（`Roadmap.md`「站内广告 Banner」条目已提示本坑位可能覆盖该需求），需重新评估：① 应用商店广告政策对披露与视觉区分的要求；② 是否需要加广告标识。**这不是本版本的阻塞项**，但作为该坑位商业化前的前置检查项记录在案

配套的运营后台顶置管理见 `v1-1-6后台prd.md` AB-10A。

### 2.2 手机号采集入口

**背景：** 商务/运营需要用户联系方式用于流失召回；后续 WhatsApp 触达、WhatsApp OTP 登录（Roadmap 已提及"根据上线后注册转化率数据决定上线时机"）也依赖手机号数据积累。本版本只做采集入口，不做验证、不扩展登录方式。

#### FR-70：手机号采集入口

**后果：**

- **采集入口二合一（同时提供）：**
  - **一次性软引导**：触发时机复用 V1.0.0 已有的推送权限申请逻辑——**首次问诊后 或 档案创建后，取最早者触发，全局仅弹一次**；可跳过，跳过后不再主动弹出该一次性引导。
    - **与 FR-85 的关系（2026-07-28 已确认）**：本版本 FR-85（§2.8）把**推送权限申请本身**改为"多触发点、每点各一次"，但**手机号软引导不跟随该变更**——手机号采集仍严格维持"取最早者、全局仅一次"，避免反复索要个人信息造成反感。此处的"复用推送权限申请逻辑"仅指**借用 V1.0.0 FR-22D 原有的时机定义（首次问诊后 / 建档后取最早）**，不含 FR-85 的多触发点模型。工程实现上两者为**相互独立的两套触发计数**，不可共用同一个"是否已触发"标记位。

    - **已填写态按脱敏展示（2026-08-05 补写，对齐 UI 稿 05b 屏）**：「我的」页 AKUN 分组的「Nomor Telepon」右值，未填写时为「Belum diisi」，**已填写时展示脱敏号码**（如 `+62 812-••••-7890`，保留国家码/前缀与末四位，中间遮蔽）；点击进入编辑抽屉后展示完整号码供修改。此前 UI 稿已按脱敏绘制，PRD 未写明该规则，本次补齐

- **选填**，不做 OTP 验证，仅做基础格式校验（印尼手机号格式）；不保证号码真实由该用户本人持有
- **用途**：仅供运营后台查看，用于流失召回等触达场景；**不用于登录**（登录方式仍仅 Google/Apple，WhatsApp OTP 登录留待后续版本按 Roadmap 既定节奏评估）
- **用途告知与同意口径（2026-08-05 产品确认）**：手机号的收集用途与处理方式**已在用户协议 / 隐私条款中覆盖**，因此**填写入口处不再额外展示同意勾选或用途说明文案**——填写即视为在既有条款范围内提供。软引导与「我的」页入口均保持轻量，不加合规文案层
  - 该决定的前提是条款中确实已覆盖"手机号用于运营召回与后续触达"这一用途；**若条款文本未覆盖该具体用途，需先补条款再上线本 FR**，否则采集用途超出已获同意范围
  - **支持清空手机号（2026-08-05 产品确认）**：「我的」页的手机号编辑入口**允许留空保存**，保存时**将该字段写入 null**，视为用户撤回已提供的手机号。清空后该用户在后台 AB-11A 的筛选中回到"未填写"分组，可再次被纳入催填推送范围
    - 理由：印尼《个人数据保护法》（UU 27/2022）赋予数据主体删除权。原 FR-70 只定义了"填写/修改"，用户无法自行撤回已提供的号码，一旦有人提出删除只能走人工处理
    - **这与"用途告知"是两件事**：告知是入口问题，已由用户协议承接；清空是出口问题，需要一条自助路径。实现即"输入框允许留空 + 保存时写 null"
    - 清空同样展示「保存成功」Toast；清空不触发任何二次确认（与本 FR「不做手机号变更后的通知/二次确认流程」一致）
- Non-goal：本版本不做手机号验证、不做基于手机号的登录方式、不做手机号变更后的通知/二次确认流程；**不在填写入口做独立的同意采集**（见上条，用途告知由用户协议承接）

### 2.3 首页图片展示规范化

**背景（2026-08-07 按代码实读订正，原描述与实现相反）：** 首页 Feed（已随 V1.0.0 上线，支持日常/成长时刻/知识三类内容）是**单列全宽卡片**（`feed_view.dart` 注释原文：「单列全宽卡片，非 2 列瀑布」，16px 屏边距 + 12px 卡间距）。

> `[订正记录 2026-08-07]` 本节原文写的是「图片展示尚无统一的比例/裁剪规范——用户传什么比例就原样显示，版面参差不齐」。**这与真实实现相反。** `shared/widgets/masonry_card.dart` 里 Feed 封面是 `AspectRatio(aspectRatio: 4/3)` + `BoxFit.cover`，代码注释写明「仅裁掉超出 4:3 的部分，统一比例裁切、**卡片高度齐整**」——Feed 早已归一到 4:3，版面是齐的。原描述据此推导出的多条结论（"本 FR 把无上下界的波动收窄、实际是改善"等）随之作废，见下方各条订正。

**真实痛点（重新界定）：** 问题不是版面参差不齐，而是**固定 4:3 的 cover 裁切对竖构图损失过大，且用户无从控制裁掉哪一段**。按 4:3 cover 计算：3:4 竖拍裁掉 **44%**、4:5 裁掉 40%、1:1 裁掉 25%、9:16 长图裁掉 58%。而宠物照片以竖构图为主（手机竖拍），等于大量内容进 Feed 就被拦腰砍掉。

`FeedItem` 数据模型目前不存储图片宽高比例元数据。

**方案对比与决策：** 产品对比了两种行业主流做法后，选择 **方案A（Instagram 模式）**：

| 维度 | 方案A：IG模式（已选中） | 方案B：小红书模式（未选中） |
| --- | --- | --- |
| 首页布局 | 单列 | 双列瀑布流 |
| 图片展示 | 归一到有界区间内：区间外裁剪到固定比例，区间内原样展示 | 保留原始比例展示，不强制裁剪 |
| 数据模型变更 | 无 | 需要——`FeedItem` 须新增宽高元数据字段 + migration |
| 存量内容影响 | **有影响**（2026-08-07 订正）：本方案改的是 Feed 的**渲染规则**，存量内容不需要回填数据，但它们在 Feed 里的**显示比例与卡片高度会一并改变**，须定义存量内容的渲染口径（见 FR-71「存量内容的渲染规则」） | 需专门决策：批量回填宽高数据，还是历史内容维持旧展示方式 |
| 图片处理管线 | 单一输出（裁剪后规范尺寸） | 双输出（原图 + 个人主页居中裁剪方图） |
| 列表性能风险 | 低（单列定宽，高度波动有界；不需要瀑布流的不定高布局计算） | 中（不定高瀑布流，需专项性能验证） |
| 相对工作量 | 低 | 中到高 |

> `[表述订正 2026-08-05]` 「列表性能风险」一栏原写「低（**固定高度**，现成虚拟化）」，与本方案实际规则不符——容差区间内的图片保留原始比例，卡片高度并非固定值（见下方 FR-71「Feed 卡片高度」）。原表述会让技术方案误以为可以按定高列表实现。方案A 的性能优势来自"单列 + 高度波动有界"，不是"高度固定"，已按此订正。**选型结论不变**：方案A 仍是三项成本（数据模型迁移、存量回填决策、瀑布流性能验证）全免的那一个。

选择方案A的原因：对现有架构改动最小，不触碰 `FeedItem` 数据模型、不涉及存量内容处理，风险可控，能以低成本解决当前"图片版面无规则"的问题。方案B 视觉冲击力更强、用户上传自由度更高，但成本大头（数据模型迁移 + 存量回填决策 + 瀑布流性能验证）在 MVP 验证阶段投入产出比存疑，保留为后续版本的体验升级选项（完整方案存档于 `Roadmap.md`「待排期功能池」）。

#### FR-71：图片上传裁剪与展示规范化

沿用现有单列 Feed 布局。图片上传时，原始宽高比落在容差区间内的图片原样使用、不裁剪；超出容差区间的图片才需要裁剪，裁剪目标为用户选定的固定比例（1:1 或 4:5）。

**后果：**

- **不改变现有单列布局结构**，不涉及瀑布流/双列改造
- **容差区间（免裁剪）**：图片原始宽:高比例数值落在 **0.75~1.34 闭区间内（含两端）**，直接原样使用，不弹裁剪框、不做任何裁切处理。该区间覆盖手机拍照的两种默认出片比例与常见方图：**3:4 竖拍 = 0.75（下界，含）**、4:5 = 0.8、1:1 = 1.0、**4:3 横拍 ≈ 1.333（上界内）**
  - `[取值变更 2026-08-05]` 上界原为 **1.2**，产品确认提高到 **1.34**。原因：手机相机默认出片为 4:3，横拍即 1.333，落在 1.2 之外——照原值实现，**用户每拍一张横图发布都要过一次裁剪框，且只能裁成 1:1 或 4:5**（横图被迫变方图/竖图，损失 25%~40% 画面）。提到 1.34 后，最常见的竖拍与横拍都免裁剪，裁剪框只在真正的长图/超宽图上出现。代价是卡片高度波动区间变大（0.75 与 1.34 的高度差约 79%，原为 60%），**该代价已随"卡片高度不统一是已接受结果"一并接受**（见下方「Feed 卡片高度」）
  - `[端点口径]` **闭区间，含 0.75 与 1.34 两端**。原文档未定义端点归属，而 3:4 竖拍恰好等于 0.75、是最常见的一种照片，含与不含直接决定它走不走裁剪流程，不可留给工程按浮点比较自行决定
- **超出容差区间时才裁剪**：图片原始比例超出 0.75~1.34 区间，上传流程弹出裁剪框，**提供 2 档预设比例供用户选择——1:1、4:5**，类似 IG 的选区裁剪交互
  - **不提供横图预设档位（2026-08-05 产品确认，刻意决定）**：本 FR 引用的调研（`../V1.2.0/图片展示方案-IG模式vs小红书模式-20260714.md`）中，IG 的免裁剪范围为 1.91:1~4:5、含横图预设；本方案**刻意不跟随**——上界放宽到 1.34 后，落进裁剪框的图已很少，再加第三档会让裁剪页交互变重。**因此超宽横图（如 16:9 = 1.78、全景图）只能裁成 1:1 或 4:5，这是已知且接受的结果，不是缺陷**
- **裁剪页面左上角设退出按钮（✕）**：点击退出裁剪界面，返回重新选择图片/取消本次上传；前进动作（应用裁剪、继续）由底部主按钮承担
  - `[订正 2026-08-07]` 原文写的是「**右上角**新增返回按钮」，2026-08-07 UI 评审中发现该位置与平台惯例冲突——右上角按 iOS/Material 惯例是**前进/确认**的位置，退出/关闭应在左上角。照原文实现会画出「一个左箭头放在右上角」这种方向与位置互相矛盾的控件（设计稿一度确实这么画了）。现改为**左上角 ✕**，并明确前进动作归底部主按钮
- **同一批次（多图）的裁剪目标锁定规则**：**锁定范围仅限于"同一批次里需要裁剪的图片之间"，不涉及容差区间内本来就不需要裁剪的图**。具体逻辑——本次上传中，第一张触发裁剪（即第一张超出容差区间）的图片，用户在裁剪框里选择 1:1 或 4:5 后，这个选择锁定为本次上传后续**其他同样超出容差区间、需要裁剪的图**的目标比例，不支持同一批次里"需要裁剪的图"一部分裁成 1:1、一部分裁成 4:5；**批次内原本就落在容差区间内的图，不受这个锁定影响，始终保持原始比例原样展示，不会被跟着改成 1:1 或 4:5**；若批次内所有图片都落在容差区间内，则本次上传全程不出现裁剪框，也不涉及"锁定目标比例"这件事——比例锁定只在真正需要裁剪时才发生，不是每次上传都强制走一遍比例选择
- **同一帖内多图比例不同时的展示规则（2026-08-05 新增，产品确认）**：上一条规则允许**同一个帖子里的图片最终比例不同**（如图 1 落在容差区间内保持 0.8、图 2 超出区间被裁成 1:1）。Feed 与详情页两层的处置不同，分别定义：

  **① Feed 卡片层——改为可左右滑动的图片轮播（2026-08-05 产品确认，⚠️ 覆盖 V1.0.0 FR-17 卡片结构）**

  > **覆盖声明：** V1.0.0 FR-17「Feed 卡片结构」表规定卡片只展示**第一张图片**（「若内容含图则展示第一张，无图则纯文字卡片」）。**本 FR 起该规则变更为：Feed 卡片内的多图支持左右滑动查看。V1.0.0 文档不回改，以本 FR 为准。**
  >
  > `[与 FR-93 的分工，2026-08-10]` FR-17 被两条 FR 分别覆盖，各管一半、互不重叠：**本 FR（FR-71）只覆盖「图片展示什么」**——多图可滑、图片比例与容差区间；**FR-93 覆盖「条目由哪些元素组成、按什么顺序排、装在什么容器里」**——通栏容器、元素顺序、操作行。两者若表述冲突，图片相关以 FR-71 为准，容器与元素顺序以 FR-93 为准。

  - **多图帖在 Feed 卡片内即可左右滑动翻图**，交互参照 Instagram：图片区横向滑动切换，**图片区内部底边居中叠加一排小圆点**（2026-08-10 订正，原写「图片下方」——FR-93 已把点赞/评论操作行放在图片正下方，圆点若也放那里会与操作行争位；改为叠在图片内底边，与操作行上下分离），圆点总数 = 图片总数，当前图对应的圆点高亮——**同时承担"有几张图"与"当前看到第几张"两个信息**，不再需要独立的数字角标
  - **单图帖不展示圆点**，也不响应横向滑动
  - **手势分工（必须明确，否则会互相抢）：**
    - 图片区**横向滑动** = 翻图，不触发页面跳转
    - 图片区**纵向滑动** = 继续滚动 Feed 列表，不被图片轮播吃掉
    - 图片区**点击（tap）** = 进入内容详情页
    - `[与 FR-93 的边界，2026-08-10 补]` V1.0.0 FR-17 原文是「点击卡片**任意区域**跳转详情页」。FR-93 在图片下方新增了点赞/评论操作行后，该规则**不再适用于操作行**：**点赞按钮就地切换、不跳转**；评论按钮跳详情页但需**定位到评论区**，与点击图片/正文进入详情页顶部不同。除操作行外，卡片其余区域（作者行、图片、正文、时间）仍为整块点击进详情页
  - **容器高度口径与详情页一致**（见下方 ②）：按首图最终比例锁定，非首图居中裁剪填满，**左右滑动时卡片高度不变**——Feed 是长列表，卡片在滑图时改变高度会把下方所有卡片整体推动，比详情页更不可接受
  - `[工程注意]` Feed 卡片从"每帖 1 张图"变成"每帖可能多张图"，图片加载策略需相应调整（如仅预加载当前图与下一张，其余滑到时再加载），避免首屏请求量随多图帖数量线性膨胀。这是本次变更对 FR-71 工程量的主要增量
  - **圆点与角标的共存（2026-08-10 明确）**：圆点叠在图片内**底边居中**；顶置角标（FR-68）在图片内**右上角**；内容装饰标签（FR-75）在图片内**左下角**。三者分处三个角/边，互不重叠。`[ASSUMPTION: 装饰标签与圆点同处底边、水平错开（左下 vs 居中），窄屏下若标签文案过长仍可能逼近圆点，需 UX 确认最小间距]`

  **② 内容详情页层——左右滑动轮播（沿用 V1.0.0 FR-28），本 FR 补齐容器高度口径**

  - 详情页多图已定为左右滑动 + 「当前页/总页数」角标（V1.0.0 FR-28），本 FR 只补它没定义的部分：**比例不一致时轮播容器高度取谁**
  - **轮播容器高度按「首图」的最终展示比例锁定**（首图定义与顶置/封面一致，见本 FR 末条：取用户上传顺序的第一张）
  - **非首图在展示层居中裁剪填满容器**（cover），不留白边、不缩放留黑边
  - **左右滑动时容器高度不变**，页面不随当前图变高变矮——滑动中容器高度跳动会带动下方正文/互动栏/评论区整体位移，明确排除该做法
  - **点开大图（全屏查看）时展示完整原图**，不套用上述裁剪，用户可看到非首图被容器切掉的部分
  - **本条只约束展示层，不影响存储**：容差区间内的图片仍按原始尺寸存储、不额外生成裁剪版本（与上一条不冲突），居中裁剪是渲染时的容器裁切
  - `[待确认]` 详情页已有「2/5」数字角标（FR-28），Feed 改用圆点指示器后，两处指示形态不一致。是否把详情页也统一改为圆点、或 Feed 也保留数字，交 UX 定案；**本 FR 不强制统一**，两者各自成立
- 需要裁剪的图片，服务端按锁定的目标比例裁剪并存储规范尺寸图片，复用现有 OSS 上传管线；容差区间内原样使用的图片按原始尺寸存储，不额外生成裁剪版本
- **⚠️ 覆盖声明（2026-08-07）：本 FR 改变 Feed 封面的既有渲染规则。** 现状 `masonry_card.dart` 是 `AspectRatio(4/3)` + `BoxFit.cover`（固定 4:3、卡片等高）；本 FR 起改为**按图片实际比例渲染、高度在 0.75~1.34 之间可变**。产品已知悉该变更会使卡片高度**从齐整变为不齐整**，仍选择本方案——理由是固定 4:3 对竖构图损失过大（3:4 竖拍被裁 44%），保住构图优先于保住版面齐整。代码不回改注释，以本 FR 为准
- **存量内容的渲染规则（2026-08-07 新增，必须定义）**：存量内容发布时**没有经过上传裁剪**，其原始比例是任意的（长截图、全景图都可能存在），不受 0.75~1.34 约束。若直接按原始比例渲染，一张 9:16 长图会撑出极端高度的卡片。
  - **规则：所有内容（含存量）在 Feed 渲染时一律把展示比例 clamp 到 0.75~1.34 闭区间**——落在区间内的按原始比例显示；超出区间的按最近的边界值（0.75 或 1.34）做 cover 裁切
  - 这样存量与新内容走同一条渲染路径，无需回填、无需迁移，且卡片高度**有硬上下界**
  - **对存量内容的可见影响：** 它们在 Feed 里的显示比例会从统一的 4:3 变成各自的原始比例（或边界值）。属预期内的一次性观感变化，不做灰度、不做新老分流
- **不涉及 `FeedItem` 数据模型变更，不做存量数据回填**——上传裁剪只影响新发布内容；存量内容不重新裁剪、不回填宽高，仅渲染规则统一变更（见上条）
- **Feed 卡片高度不统一，是本方案已接受的代价（2026-08-05 确认，2026-08-07 按真实现状改写）**：容差区间内的图片保留原始比例展示，因此 Feed 里相邻卡片的高度会不一致（同一宽度下，0.75 的图与 1.34 的图高度相差约 79%）。区间有界，不会出现长图占满整屏。仍是单列布局、非瀑布流
  - `[订正 2026-08-07]` 本条原写「**产品明确接受这一点**——代价就是高度不齐」，语气上像是在既有的不齐之上继续接受不齐。**实际是从"完全齐整"退到"不齐整"**：现状卡片恒为 4:3、高度完全一致。这是一次**明确的倒退**，产品在知悉该事实后仍选择本方案（保构图 > 保版面齐整），此处如实记录，不再用"波动可控"淡化
  - **不需要给 `FeedItem` 新增宽高元数据字段**，渲染时按图片实际尺寸做比例展示即可
  - `[工程注意，2026-08-07 改写]` 由于不存宽高，客户端在图片下载完成前无法预知卡片高度，卡片会在图片加载完成时撑开到最终高度。**这是本 FR 新引入的问题**——现状 `AspectRatio(4/3)` 在图片加载前就已确定高度，不存在撑开与布局跳动；改为按实际比例渲染后，首屏滚动会出现 CLS。原文此处写的是"这不是本 FR 引入的新问题、现状本就如此"，与真实实现相反，已订正。
    - **工程必须给出占位策略**（例如统一按 1:1 预留、加载完成后调整），把加载期的高度变化幅度压到最小。这一条现在是**必做项**，不是可选优化
    - 若占位策略仍不足以消除跳动，则需补 `FeedItem` 宽高字段（推翻本方案"零数据模型变更"这一选型理由）。**本版本先不投入，但须在上线后实测滚动体验并复盘**
- **顶置坑位（FR-68）/封面图使用哪张**：统一取用户上传顺序中的第一张图（即"首图"），按该图最终展示效果（裁剪后或原样）展示，不额外判断"哪张更适合做封面"

**与 V1.1.2 发布页的衔接：** V1.1.2 FR-83 已改造发布页（类型选择器默认 Diary + 「同步到 Moment」开关），但该版本**未触碰图片区**，图片上传维持 V1.0.0 现状。本 FR 是发布页图片区的第二次改动，需在 FR-83 已上线的发布页基础上叠加，不冲突。

`[NOTE FOR PM: 瀑布流（小红书模式）作为后续版本的体验升级选项保留，重新评估时需先决策存量内容宽高元数据回填方案，见 Roadmap 待排期功能池存档]`

### 2.4 用户标签

**背景：** 用户运营需要给特定用户打上运营认定的身份/荣誉标签（如「官方账号」「最佳新人」），供其他用户识别，同时提升被打标用户的荣誉感。全部由运营在后台手动配置和分配，用户不能自主申请或购买。**V1.0.0/V1.1.0 均无任何头像/昵称旁的身份标签机制，本 FR 是首次引入，不涉及替代或与既有机制并存的问题。**

#### FR-74：用户标签

**后果：**

- **标签内容**：运营在后台创建标签，每个标签自定义上传一张小图标 + 一句说明文案（见 `v1-1-6后台prd.md` AB-12A）
- **展示位置（均展示在头像/昵称旁）**：迷你主页预览卡、内容详情页作者区、评论区昵称旁、首页 Feed 卡片用户昵称旁——四处位置同步展示，不做差异化
- **点击标签图标**：弹出轻量提示层（tooltip），展示标签名称 + 运营配置的说明文案（如「最佳新人」配「社区运营认定的优秀新人」），点击外部区域关闭；四处展示位置的点击行为一致
- **单用户同时最多展示 3 个标签（2026-08-05 定数，原写「2-3 个」）**：运营可为同一用户分配的标签数量不设上限，但同时展示的标签数超过 **3** 个时，**按分配时间倒序取最近分配的 3 个展示**，其余分配记录保留但不展示。四处展示位统一按 3，不做差异化
  - `[定数说明 2026-08-05]` 原文与后台 PRD 均写「2-3 个」，OQ-7 当时只定了排序规则、未定数字，工程无法实现"2-3"。现明确为 **3**
- **空间不足时的降级规则（2026-08-05 新增）**：四处展示位中评论区与 Feed 卡片的横向空间最紧，可能放不下昵称 + 3 个标签。**优先级为「昵称完整显示优先，标签按分配时间倒序丢弃」**——即空间不足时先减少展示的标签数（丢最早分配的），**不截断昵称**。昵称是身份识别主体，标签是装饰，不可为了挂满标签把用户名挤掉；被丢弃的标签不做「+N」折叠提示（点击标签才有 tooltip，折叠标记会额外占用本就不够的横向空间）
- **生效时间**：标签分配支持设置开始/结束时间，到点自动生效/失效（与 FR-68 顶置坑位的定时逻辑一致），也支持不设结束时间的永久分配
- Non-goal：用户不能自主申请、购买或摘除自己的标签，全部由运营在后台手动操作

- **打标是一个流量动作，不只是发奖动作。** 运营给一条内容挂上「本周最佳」，同时也把它在推荐序列里的分数提高了 30%
- **标签到期失效会同时掉权重**——设置了结束时间的标签，到点后该内容的推荐加成一并消失，不只是徽章消失
- **与 AB-3G 互动积分选品形成正反馈环**：运营按互动积分挑出高分内容 → 打标 → 获得 1.3× 加权 → 曝光上升 → 互动积分进一步上升。这个环本身是有意的（把好内容推得更广），但**运营需要知道自己在推动它**，否则会误判"这条内容本来就这么火"
- **本条为口径说明，不改变 FR-75 的任何功能行为**；算法侧口径以算法文档为准，两处需保持一致

运营挑选装饰标签候选内容时可参考后台新增的内容互动积分排序工具（见 `v1-1-6后台prd.md` AB-3G）。

### 2.7 单条内容分享卡片（2026-07-24 从 V1.2.0 迁入）

**功能描述：** 内容详情页新增分享入口，一键生成图片卡片分享至外部平台（WhatsApp / Instagram Stories）。此前只有宠物身份证（V1.1.0 FR-49）能生成分享卡片，本 FR 把同一套分享卡机制扩展到普通帖子本身。原属 V1.2.0（`Roadmap.md` 更早规划在 1.4.0），2026-07-24 决定与 Diary/Moment 发布模型（FR-83）一并前移；2026-07-28 版本拆分后，FR-83 留在 V1.1.2、本 FR 落到 V1.1.6，两者相隔一个版本上线，不影响各自功能完整性。**FR 编号保留不变（FR-73）。**

#### FR-73：内容详情页分享卡片

**后果：**

- **适用范围**：三类内容（Diary / Moment / Tips）均支持，不做例外。三类内容的术语与分发规则由 V1.1.2 FR-83 确立，本 FR 沿用
- **与 Diary 可见范围的关系（2026-08-05 按 FR-83 反转后的口径订正）**：V1.1.2 FR-83 已于 **2026-07-30 把「同步到 Moment」开关反转为默认开启**——Diary 默认公开进 Feed，只有作者手动关掉开关的那部分才是纯私人记录（原 2026-07-23 初稿的"Diary 默认私密"已作废）。本 FR 适用于三类内容全部，**包括作者关闭了同步的私密 Diary**：分享卡是**用户主动**发起的对外分享，与宠物名片 H5（FR-14）同理——同步开关约束的是平台 Feed 的自动分发，不约束作者本人把自己的内容分享出去
- **卡片内容**：含帖子首图（若有）/ 正文摘要（前若干字，超出省略）/ 作者昵称与头像 / App 品牌水印
- **无配图内容（纯文字帖子）**：使用纯文字卡片模板——不放图片区域，改为文字排版占满卡片主体，仍保留作者信息与品牌水印，保证所有内容都能生成分享卡片
- **分享方式**：一键分享至 WhatsApp / Instagram Stories，通过系统分享菜单调起（沿用 V1.0.0 FR-14 宠物名片、V1.1.0 FR-49 宠物身份证既有的系统分享菜单调起方式）
- **品牌水印**：卡片角落展示品牌 logo 水印，与宠物身份证（V1.1.0 FR-49）既有水印策略一致
- **下载二维码（2026-08-10 产品新增）**：卡片页脚右侧放一枚下载二维码，左侧为品牌 logo + 引导文案 `Scan buat unduh 🐾`。视觉稿见 `ui-standalone-features-integrated-v1.html` SH2 / SH3 屏。**加这枚码的原因是分享卡最终是一张导出到 Instagram Stories 的静态图——观看者无法点击，二维码是该场景下唯一的转化通路。** 四条实现要求：
  - **二维码内容 = 该条内容的分享链接**（与卡片 CTA 的深链同一个 URL），**不是通用下载页**——否则扫码进来的人看不到他实际看到的那条内容，漏斗断在这里
  - **必须留安静区（quiet zone）**：码四周留白不足会直接扫不出。视觉稿用白色底板 + 3px 内边距承担这个留白，工程实现须保证导出图里的实际留白不小于 4 个码元宽度
  - **导出尺寸下的可扫性**：卡片预览宽 210px、导出为 9:16 是 1080×1920，二维码在导出图里的边长须**按导出分辨率等比放大后仍 ≥ 140px**，否则隔着屏幕拍照扫不动。不可按预览尺寸的像素直接输出
  - **必须有白色底板**：纯文字卡片模板（SH3）的背景是紫色渐变，码直接压在渐变上会降低识别率
- **文案不重复品牌名**：页脚引导文案写 `Scan buat unduh`，不写 `Unduh TailTopia`——logo 已经承载品牌名，两处都写属冗余
- **非 App 用户**：点击分享出去的卡片/链接，看到静态图片 + 下载引导，无需登录（与 V1.0.0 FR-14 宠物名片 H5 面向非 App 用户的处理一致）
- **点击分享链接后按访问者身份分流（2026-08-05 新增，原缺口：只定义了非 App 用户）：**

  | 访问者 | 看到什么 |
  | --- | --- |
  | 未安装 App / 未登录 | 静态图片 + 下载引导（上一条既有规则，不变） |
  | 已登录，**且为作者本人** | 进入自己的内容详情页 / Diary 页面，保留全部编辑与管理入口（沿用现状） |
  | 已登录，**非作者**（2026-08-05 新增） | 进入**该条内容的详情页只读态**——与作者看到的详情页同一套视觉样式，但不展示编辑/删除等仅作者可见的管理入口 |

  - **⚠️ 严格限定为"只看这一条"（2026-08-05 产品确认）：** 本 FR 的分享卡是**单条内容分享**，因此访客通过该链接**只能访问被分享的那一条内容本身**，**不得由此进入该宠物的 Diary 时间线、不得看到该宠物的任何其它内容**（无论公开还是私密）。
    - 依据：分享一条内容 = 授权他人看**这一条**，不等于授权他人浏览这只宠物的全部记录。若实现时把单条分享链接落到"宠物成长档案页"，会把该宠物名下所有未同步的私密 Diary 一并暴露给任何拿到链接的人，属**严重隐私事故**，且与 V1.1.2 FR-83「未同步的 Diary 只在作者自己的成长档案时间线里展示」直接冲突。
    - **被分享的那一条即使是未同步的私密 Diary，访客也可见**——这是作者主动分享的授权结果，与 V1.0.0 FR-14 宠物名片「用户主动分享后他人可见」同一原则（见 V1.1.2 FR-83 对 H5 的确认）。
  - **与「宠物主页分享」是两条不同的链路，不可混为一谈（2026-08-05 澄清）：** 平台另有一条**宠物主页/宠物名片分享**链路（V1.0.0 FR-14 宠物名片 + FR-15 分享 FAB），那条链路分享的是**整只宠物**，访客据此可看到该宠物**完整的 Diary**。两者的授权范围完全不同：
    - **本 FR（单条内容分享卡）→ 访客只看这一条**
    - **宠物主页分享（FR-14）→ 访客可看该宠物完整 Diary**，其页面内逐区块的可见/不可见范围见 **§2.9 FR-92 §②**（健康记录与问诊记录不对访客开放、访客不可二次转发、分享前须告知）
    - 工程实现上两种链接必须是**不同的链接类型与不同的落地页**，不可复用同一个 deep link 目标
- `[ASSUMPTION: 卡片尺寸采用 9:16（Stories）与 1:1（Feed）双尺寸规格，不新增其他尺寸]`
- **卡片生成基建由本版本首次搭建（2026-07-28 确认）**：文字排版、水印、双尺寸输出这套能力此前从未实现过（`Roadmap.md`「待排期功能池」记录了原计划在 1.1.0 借月度回顾提前搭建通用框架、后随该功能移出而顺延）。**本版本是首次实现方，工程须按"供后续分享卡片功能复用"的标准设计该基建**，不可写成只服务本 FR 的一次性实现。后续复用方及其排期见 `Roadmap.md`。

### 2.8 推送权限申请触发模型调整（2026-07-27 新增，覆盖 V1.0.0 FR-22D）

**功能描述：** 现状 FR-22D 的系统推送权限申请是"两个时机取最早、全程仅弹一次、拒绝后不再主动弹"。结果是：大量关掉通知的用户此后再也不会被提醒开启，通知触达率持续走低。本 FR 改为**多触发点、每个触发点各触发一次**的模型，并新增"打开通知中心"触发点。

#### FR-85：多触发点推送权限唤醒（覆盖 FR-22D「全局仅一次/拒绝后不再弹」）

> ### 🔴 `[订正 2026-08-12 · X-20]` 本节「原生弹窗 vs 跳设置」的分流与「弹窗机会归属」整段作废
>
> **本订正依据 2026-08-11 的代码实读，非新增需求。** 亦记入 `.decision-log.md` §三（PRD 与代码的矛盾）与仓库架构 delta 的开放问题 **OA-5**。
>
> **事实：推送权限在本项目已有三代设计，本节是照第一代写的，而第二代已于 2026-08-07 上线。**
>
> | 代 | 时间 | 申请方式 |
> |---|---|---|
> | 一 | V1.0.0 FR-22D | 双时机取最早、全程仅一次、拒绝后不再弹 |
> | 二 | **2026-08-07 已上线** | **首启即申请** + 设置页开关兜底（`PushPermissionBootstrap`，已接在 `main.dart`，且必须排在 iOS ATT 弹窗落定之后——两个系统弹窗同帧会互相遮挡，2026-08-09 iPad 拒信即此因） |
> | 三 | 本节 FR-85（2026-08-10 定稿） | 多触发点、每点各一次 |
>
> **第二代出现的原因（代码注释原文）**：第一代对**存量用户是死路**——两个时机都是一次性的，老用户换机 / 重装后既不重走建档、也未必再问诊，App 于是永不申请权限；而 **iOS 上「从未申请过」的 App 不会出现在系统设置的通知列表里**，用户连手动开启都做不到 ⇒ 永久收不到任何推送。故首启即申请，换取的不是授权率，而是**「出现在系统设置列表里」这个资格**。
>
> ⚠️ **这同时推翻了 V1.0.0 的 NFR-12**（「绝不在 App 首次启动时请求推送权限」）。该 NFR 已由产品于 2026-08-07 主动推翻并上线，**工程不得以 NFR-12 为由要求移除首启申请**。
>
> **因此本节以下四处作废 / 订正：**
>
> 1. ❌ **「用户从未响应过 → 唤起原生系统弹窗」这一分支作废**——原生弹窗机会在首启即被消耗，该分支**永远走不到**。照字面实现即产出死代码。
> 2. ❌ **触发点 4「永不唤起原生弹窗、把机会留给触发点 1/2/5」这条护栏的立论基础不存在**（无机会可留）。护栏改为更强的形式：**所有触发点一律只走 App 内引导 + 跳系统设置**，不存在唤起原生弹窗这一分支。埋点中出现任何触发点上报「原生弹窗」形态即为违背规格，可线上告警。
> 3. ⚠️ **触发点 1 / 2 必须自行实现时机判定**——旧的单一标记键由第二代在首启即置位，且第二代与第一代门控**共用该键**，故第一代双时机在线上**已不再触发**（事实上的死代码）。不得靠复用旧门控实现触发点 1 / 2。
> 4. ⚠️ **第三代依赖第二代，不是取代关系**——本节「跳系统设置」这条路能走通，**恰恰因为首启已申请过一次**（App 因此在设置列表里）。**不得为「减少首启打扰」而移除第二代。**
>
> **本节仍然成立的部分（主体）**：多触发点 + 每点各一次的框架、前置闸门（已开启则跳过）、触发点 4 与触发点 5 两个新增点、兽医端不限次数且不硬拦、按设备存储、与 FR-70 两套独立计数。**FR-85 的实际效果是：在四个时刻把关着通知的人引去系统设置页。**
>
> **连带影响 FR-70（§2.2）**：其软引导声明「复用推送权限申请逻辑——首次问诊后 或 建档后取最早」，而那套时机在线上已不再触发。**FR-70 须自行实现时机判定**，不得指望复用旧门控。

**核心规则变更：**

- **取消"全局仅一次 / 拒绝后永不再主动弹"**。改为：**每个触发点相互独立、每个触发点自身最多触发一次**（同一触发点不反复打扰，但不同触发点各有一次机会）。
- **触发前置**：到达某触发点时，若系统通知**已开启** → 跳过（无需提醒，天然去重）；**仍关闭** → 唤醒提示。
- **提示行为按系统权限状态分**（受 iOS/Android 硬约束，App 无法绕过）：
  - 用户**从未响应过**原生权限弹窗 → 唤起**原生系统弹窗**
  - 用户**已响应过**（尤其已拒绝，原生弹窗已被系统消费、无法再唤起）→ 展示 App 内引导 → **跳转系统设置页**手动开启
  - **⚠️ 例外：触发点 4（打开通知中心）不适用上面第一条**——它**永不唤起原生弹窗**，一律走 App 内引导 + 跳系统设置，原因见下方「通知中心触发点的 UI」（2026-08-05 产品确认）

**触发点清单（每点各触发一次）：**

| # | 触发点 | 说明 | 可否唤起原生弹窗 | 来源 |
| --- | --- | --- | --- | --- |
| 1 | 完成第一次问诊后 | 问诊结果页关闭后 | ✅ 可以 | FR-22D 原有 |
| 2 | 完成宠物档案创建后 | 建档庆祝页后、进首页前（原"仅从未问诊用户"条件在新模型下不再需要——由"通知已开启则跳过"统一去重） | ✅ 可以 | FR-22D 原有 |
| 4 | **打开通知中心时（本 FR 新增）** | 用户打开站内通知中心、且系统通知关闭时 | **❌ 不可以**——仅 App 内引导条 + 跳系统设置（2026-08-05 确认） | **本 FR 新增** |
| 5 | **兽医切换为「在线」状态时（2026-08-05 新增，兽医端）** | 兽医在工作台「我的」Tab 把状态切为「在线」（V1.0.0 FR-32）、且系统通知关闭时 | ✅ 可以 | **2026-08-05 新增** |

> **原生弹窗机会只有一次（iOS 硬约束），归属触发点 1/2/5 中最先到达的那一个。** 触发点 4 被排除在外是刻意设计，不是遗漏——详见下方「通知中心触发点的 UI」。
>
> `[编号说明 2026-08-05]` 本清单编号跳过 3。原触发点 3「兽医问诊开始排队等待时」来自一个**尚未上线**的问诊流程改造，按「PRD 不指向之后版本」的既定要求整行移除——该场景届时由那一版自行声明"接入 FR-85 已建立的多触发点框架、新增一个触发点"，本 FR 不替它预留。**编号不重新分配**，4 / 5 保持原号（沿用 V1.1.2 §3.2 删除 T-5 时的同一处置原则）。本 FR 的框架本身即为可扩展设计，新增触发点无需改动模型。

**触发点 5（兽医端）的专门说明（2026-08-05 新增）：**

原触发点 1~4 全部面向宠物主，**兽医端完全没有覆盖**，这是一处遗漏。兽医侧的推送权限性质与用户侧不同：

- **对兽医，通知不是提升体验的加分项，而是履约前提。** V1.0.0 FR-22E 规定新问诊请求**只推送给在线状态的兽医**，点击通知才跳转工作台「待接单」Tab；兽医若关闭系统通知，等于**收不到任何派单广播**——他自己损失全部接单机会，平台侧则表现为"明明有在线兽医却无人接单"，直接损害 FR-43D「免费入队、接单后限时支付」链路的转化，且运营从后台数据（AB-7A 兽医供给核查）**看不出根因**。
- **触发时机选在"切换为在线"这一刻**，因为这正是兽医主动声明"我现在要接单"的时点：动机最强、且提示挂在他自己发起的操作上，不构成打断。
- **本触发点不受"每个触发点各一次"限制（2026-08-05 产品确认）：** **每次切换为「在线」且系统通知处于关闭状态时都提示**，不限首次。理由——兽医每次上线都是一次真实的履约承诺，通知关着这次上线就是无效供给；且该提示由兽医自己的操作触发、可当次关闭，不存在被动打扰。**这是四个用户侧触发点之外的唯一例外，工程需为兽医侧单独实现该分支**（不复用"各一次"的标记位逻辑）。
- **不做硬拦截**：不因系统通知关闭而禁止兽医切换为「在线」。兽医仍可选择靠 App 前台停留自行盯单，平台不剥夺其接单资格，只做提示。

- 「我的」页手动入口（引导去系统设置）保留，非自动触发，随时可用。
- **覆盖声明**：本 FR 覆盖 V1.0.0 FR-22D 的"取最早/仅一次/拒绝后不再弹"规则，V1.0.0 文档不回改、以本 FR 为准。
- **与 FR-70 手机号软引导的关系（2026-07-28 已确认）**：FR-70 的一次性软引导借用 FR-22D 原有的"首次问诊后 / 建档后取最早"时机定义，但**不跟随**本 FR 改为多触发点，仍维持**取最早者、全局仅弹一次**。两者是**相互独立的两套触发计数**，工程不可共用同一个"是否已触发"标记位；同一时机同时命中两者时的弹出顺序按"先推送权限、后手机号"串行处理，不叠加同屏。

**通知中心触发点的 UI：**

- 打开通知中心时，若系统通知关闭且触发点 4 尚未触发过，展示推送开启提示。
- **形态与频次（2026-07-27 已确认）**：**通知中心顶部一次性引导条**（非模态打断）；仅在满足条件的**首次打开**通知中心时出现一次，触发后本触发点不再重复出现（与其它触发点"各一次"一致）。
- **⚠️ 触发点 4 永不唤起原生系统弹窗（2026-08-05 产品确认，本触发点的专属例外）**：**无论用户此前是否响应过原生权限弹窗**，触发点 4 一律只展示顶部引导条 + 点击后跳系统设置页，**不适用上方"从未响应→唤起原生弹窗"这条通用规则**。
  - **原因：** 通知中心铃铛位于首页顶部导航栏，用户装完 App 随手就会点开看看。若此处唤起原生弹窗，对相当一部分用户**触发点 4 会成为他们遇到的第一个触发点**——在"只是好奇点了下铃铛"这种零动机场景消耗掉 **iOS 只给一次**的原生弹窗机会；用户随手一拒，此后触发点 1（问诊后）/ 2（建档后）/ 5（兽医上线时）这些**真正有理由开通知的时刻**全部只能降级为"跳系统设置"，转化率低一个量级。
  - 这与 V1.0.0 FR-22D「**不在 App 首次启动时请求权限（授权率极低）**」的既定判断一致——触发点 4 的问题本质与冷启动请求权限相同：在用户没有动机的时刻索要权限。
  - **代价（已接受）：** 从未响应过原生弹窗的用户在触发点 4 只能被引导去系统设置页，路径比原生弹窗长、转化更低。换来的是**把原生弹窗这一次性资源保留给有价值锚点的触发点 1/2/5**。
  - **原生弹窗机会归属：** 仅触发点 1 / 2 / 5 可唤起原生弹窗（按"从未响应→原生弹窗"规则），其中最先到达的那个消耗掉这次机会。
  - 上线后用 §3.2 的 E-19 / E-20 交叉验证本决定：观测 `trigger_point=notification_center` 的 `prompt_type` 是否确实恒为 `in_app_guide`（护栏校验），以及触发点 1/2/5 的 `native_dialog` 授权率是否达到预期。

**触发计数的存储口径（2026-08-05 产品确认）：**

- **受"各一次"约束的三个触发点（1 / 2 / 4）的"已触发过"标记按设备存储（本地），不跟随账号。** 换设备、卸载重装后计数重置，用户会在新设备上重新获得这 3 次唤醒机会。
  - **触发点 5（兽医端）本就不受"各一次"限制**，不需要标记位，每次切换为在线且通知关闭时都判断当前权限状态即可（见上方「触发点 5 的专门说明」）。
- **理由：** 本 FR 的判断依据——系统通知开关是开还是关——**本身就是设备级状态**。用户换了新手机，新设备上的通知权限本来就是关闭的（一个真实的、需要重新解决的状态），此时重新给一轮唤醒机会是正确行为，而不是重复打扰。
- **过度打扰的风险由"已开启则跳过"这道前置闸门天然兜住**：只要用户在任一设备上开了通知，该设备上后续所有触发点全部跳过，不会有任何提示。真正会被重复唤醒的只有"换了设备且仍然不开通知"的用户，且每台设备上触发点 1/2/4 仍严格各一次。
- **与 FR-70 手机号软引导仍是两套独立计数**（见 FR-70 与下方「与 FR-70 的关系」），不可共用同一个标记位；手机号软引导的存储口径按其自身定义，不因本条而改变。

**边界：**

- 若用户在某触发点授权成功 → 系统通知开启 → 后续所有触发点因"已开启则跳过"自然不再提示。
- 若用户持续拒绝 → 每个触发点仍各有一次机会把他引导去系统设置（这是本 FR"打破不再弹"的核心意图：多点各一次，而非无限反复）。

V1.0.0 FR-14 原设计为双 CTA：主 CTA「给我的宠物创建同款档案」（面向有宠物用户）+ 副 CTA「查看 [宠物名] 的完整故事」（面向所有用户）。**但 FR-14 自己规定的两个 CTA 行为完全相同**——「未安装 App：两个 CTA 均跳转至 App 下载页」「已安装 App：两个 CTA 均通过 Deep Link 打开 App 并跳转至该宠物的成长档案页」。即：两套文案、一个行为，副 CTA 不提供任何新路径。

- **改为单个 CTA**，行为按设备状态分流（与 FR-14 原有的分流逻辑一致，未变）：
  - **已安装 App** → Deep Link 直接打开 App，落到**该宠物的 Diary 页面**（访客只读态，见上方 §②）
  - **未安装 App** → 跳转对应平台的应用商店下载页（iOS → App Store，Android → Google Play）
- **文案取「查看 [宠物名] 的完整故事」这一支**，并在按钮下方补一行轻提示「Gratis di App Store & Google Play」，让下载意图显式化——本页 KPI 是情感打动 → 下载，CTA 须指向下载而不是含糊
- **已接受的代价：** 原双 CTA 用文案区分了「有宠物用户 / 所有用户」两类受众，合并后这层区分消失。产品判断该区分只存在于文案、不存在于行为，且两个按钮抢注意力反而拉低单个 CTA 的点击率
- **V1.0.0 FR-14 文档不回改，以本 FR 为准**

**⑤ 明确不变更**

- 不改变 H5 的分享链路、Open Graph 标签、加载失败/链接失效处理（V1.0.0 FR-14 既有规则）
- 不新增 App 内从头像/昵称点进他人宠物主页的入口——迷你主页预览卡（V1.0.0 FR-26）仍是 App 内查看他人的唯一方式，完整个人主页仍按 FR-26 既定路径留待 1.6.0

## 3. 数据埋点需求（2026-08-05 新增）

**为什么本版本必须单独写一节埋点：** §1 版本目标里的第 2 项「增长与召回基建」——手机号采集、推送权限唤醒、分享卡片——**价值完全由数据定义**，功能"做完了"不等于"起作用了"。V1.1.2 的埋点清单开头已经自我记录过一次教训（`3.数据埋点/埋点文件/埋点清单v112.md` §0.3：因未取改版前基线，该版本的埋点回答不了"改版是对是错"）；本版本的 FR-70 / FR-85 若不预先定义口径，会原样重演，且损失更大——那两条 FR 本质上是**产品猜测**，上线后要判断的不是"涨没涨"，而是**哪个触发点/哪个入口值得留**。

**本节的定位（2026-08-05 产品确认）：** 只定义**要观测什么**与**怎么判读**，**不设目标值**。目标值等首个完整观测周期的实际分布出来后再定，避免现在拍一个没有依据的数字反过来绑住判读。

**命名口径：** 事件名沿用工程侧代码里已实现的长命名风格（如 `publish_page_sync_to_moment_toggled`、`bottom_nav_tab_switched`），本节给出的名称为**语义占位**，最终名称以工程实现为准，但**属性字段不可省略**——下表加粗的属性是判读的必要条件，缺一项对应结论就做不出来。

### 3.1 前置缺口：系统通知权限状态无快照（P0，阻塞 FR-85 的效果评估）

现有埋点**没有任何事件记录"用户当前的系统通知开关是开还是关"**。FR-85 整条 FR 的目的就是提高这个比例，但没有这个口径，上线后无法回答"推送授权率到底有没有涨"——只能看到各个提示弹了多少次，看不到净结果。

**要求：本版本必须新增 E-21 权限状态快照（见 §3.2），属 FR-85 的 P0 前置项，不可后置。**

> V1.1.2 §3.1 记录的 Tab 切换埋点缺口**已在 V1.1.2 修复**（`bottom_nav_tab_switched` 已实现），本版本不再重复要求。

| E-27 | `signup_succeeded`（**扩展既有事件**） | 注册成功 | 既有 `entry_source` **新增取值 `pet_card`** |

**实现口径（三条，缺一条对应数据就不可用）：**

- **E-24 走服务端**，与 `milestone_achieved` 同一条路径（复用既有 `PostHogAnalyticsClient`，不引入前端 SDK）。服务端拿不到"访客是否已有账号"，因此**本组不承诺 `viewer_state` 属性**——H5 是无登录态的公开页，那个判断做不出来，别写进验收标准。
- **E-25 与 E-26 必须拆成两个事件。** E-25 在点击瞬间发出，计数可靠；E-26 依赖 `pagehide` 时序推断（900ms 内隐藏 → `app_opened`，走到商店 → `store_redirected`，两者都没发生 → `unknown`），**属尽力上报、会丢**。合成一个事件会让不可靠性污染掉可靠的点击数。上报方式用 `navigator.sendBeacon` 打到后端接口再转发 PostHog，**不引入前端第三方 SDK**（沿用 V1.1.2 服务端埋点的既定原则）。
- **需要一个匿名 `distinct_id`**（H5 侧 cookie 或 localStorage 生成并持久化），否则 E-24 → E-25 → E-26 三步无法串成同一个人的漏斗，只能各看绝对值。

**判读：**

- **漏斗**：E-23 → E-24 → E-25 → E-26，这是 SM-2 第一次有数据。**E-24 ÷ E-23 是"分享出去有没有人点"**，若长期偏低说明问题在分享物本身（预览图/文案），不在 H5 页。
- **`page_state` 是本组最有价值的属性**：`empty` 占比 = 有多少访客打开后看到的是零数据降级态。这个比例高说明**用户在档案还很空的时候就在分享**，那么该优化的是"什么时候提示用户分享"，而不是 H5 页面本身。
- **E-26 的 `outcome` 分布 = 已装/未装比例**，直接决定 CTA 文案该写「打开 App」还是「下载 App」。
- **E-27 只能覆盖已装用户**（深链直接进 App，`entry_source` 可带）。**未装用户的「安装 → 打开 → 注册」这一段仍然归因不了**，需要 deferred deep link 基建（Firebase Dynamic Links / Branch.io），属独立基建议题，不在本版本范围内。
