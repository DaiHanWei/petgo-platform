## 1. AB-22：App 版本更新配置

**背景：** App 版本更新提醒（App 端 FR-124）需要一组配置值决定「谁看到推荐更新、谁被强制更新、点更新跳去哪」。这些值现存于后端 Spring 配置属性 `petgo.app-version.*`，**靠环境变量注入**——改一次需改 env 并重启服务，运营既无界面也无权限。

其中 `latestVersion` **每次 App 发版都必须变更**，而漏改的后果是**功能静默失效**：用户收不到更新提醒，且不产生任何报错，几乎不可能被发现。本条目把这些值搬到运营后台，由运营在发版后自助更新。**2026-10-07 起「最新版本号」按 iOS / Android 拆为两个字段**（App 端 FR-124 规则 g）：双端上架时间不同步，哪端上架了就只改哪端。

**上线现状（本条目开工前的基线）：**

| 配置值 | 现状 | 代码默认值 |
|---|---|---|
| `latestVersion` | env 注入，运营不可配 | `1.0.0` |
| `minSupportedVersion` | env 注入，运营不可配 | `1.0.0` |
| `iosStoreUrl` | env 注入，运营不可配 | **空字符串** |
| `androidStoreUrl` | env 注入，运营不可配 | **空字符串** |

> ⚠️ **开工前须先核实生产 env 的实际取值**。若两个商店 URL 在生产环境为空，则 App 端推荐更新横幅整条不出现、设置页弹窗也没有「前往更新」按钮（App 端规则 f / AC6），本功能等于没做——这种情况下本条目上线前**必须由运营补齐两个链接**。

**页面位置与流程：** 落在**运营配置页**，与既有的解锁定价组**并列新增一个分组卡「App 版本更新」**。不新增页面、不新增菜单项。

流程：进运营配置页 → 找到「App 版本更新」分组卡 → 修改字段 → 卡内保存钮（未修改禁用 → 修改激活并标「已修改」→ 高危确认弹层复述新旧值 → 提交），交互形态沿用解锁定价组。

**字段：**

| 字段 | 类型 | 作用 |
|---|---|---|
| **iOS 最新版本号** | 语义版本字符串 | 低于此版本的 iOS 用户看到「推荐更新」（可稍后）；**仅在 App Store 上架新版后修改** |
| **Android 最新版本号** | 语义版本字符串 | 低于此版本的 Android 用户看到「推荐更新」（可稍后）；**仅在 Google Play 上架新版后修改** |
| **最低支持版本** | 语义版本字符串 | **低于此版本的用户被强制更新，弹窗不可跳过** |
| iOS 商店链接 | URL | 点「前往更新」跳 App Store |
| Android 商店链接 | URL | 点「前往更新」跳 Google Play |

商店链接须以 `https://` 开头，否则拒绝保存（2026-10-08）。

### 1.1 🔴 最低支持版本的特殊防护（本条目的核心风险点）

**「最低支持版本」不是一个普通配置项**：它设错的后果是**全量用户被锁进设计上不可跳过的弹窗、无法自救**，且 App 端已明确该弹窗拦截系统返回键与遮罩点击。因此该字段须有高于其他配置项的防护：

- **格式校验**：必须为合法语义版本（`x.y.z`），非法输入拒绝保存
- **商店链接校验（2026-10-08 拍板）**：把「最低支持版本」调高（高于 `1.0.0`）时，**iOS、Android 两个商店链接必须都已填写**，否则拒绝保存。否则强制弹窗不能关、又没有「前往更新」按钮，用户会被卡死
- **逻辑校验**：**最低支持版本 ≤ iOS 最新版本号，且 ≤ Android 最新版本号**，否则拒绝保存。违反此条意味着「装了最新版的用户也被判为需强制更新」，是最容易犯且后果最严重的一种误配
- **独立的二次确认**：修改该字段时，高危确认弹层除复述新旧值外，须额外警示「**此操作将使低于该版本的全部用户无法继续使用 App，且提示不可跳过**」，并要求运营手动输入该版本号以确认（不是单纯点「确定」）
- **默认不启用**：按 App 端 FR-124 已拍板的口径，该值**默认永不上调**、长期保持 `1.0.0`，仅在出现安全问题或数据不兼容时才临时上调

### 1.2 ⚠️ 接入时的初始值（关键，不做会上线即误判）

配置项接入后初始值由数据迁移写入，**不得留空、不得取代码默认值**：

| 字段 | 迁移初始值 |
|---|---|
| iOS 最新版本号 | **迁移执行时 App Store 上的最新版本号**（不是 `1.0.0`） |
| Android 最新版本号 | **迁移执行时 Google Play 上的最新版本号**（不是 `1.0.0`） |
| 最低支持版本 | **`1.0.0`**（对应「默认永不启用强制更新」） |
| iOS / Android 商店链接 | 生产 env 现值；**env 为空则由运营在本条目上线前补齐** |

若任一端的「最新版本号」误取代码默认值 `1.0.0`，则所有用户都会被判定为「已是最新」、永远收不到提醒，且同样无任何报错。

**规则：**

- 保存即时生效，App 端在下一次版本检查时读到新值（冷启动，或回到前台且距上次检查 ≥6 小时）
- 各字段独立，无联动（除 §1.1 的「最低支持版本 ≤ 双端最新版本号」这一条跨字段校验）
- 所有改动经统一审计入口落审计日志
- 权限：「最低支持版本」单独收权限，见下方

#### 最低支持版本单独收权限（2026-10-07 拍板）

其余字段沿用既有运营配置项的 permission_code；**「最低支持版本」单独收至更高权限角色**（如仅超管可改）。理由是它与其他配置项的风险量级完全不同——改错定价损失的是收入，改错这一项是全量用户打不开 App。

需新增一个 permission_code。

#### UI 说明

**需要出稿。** 本条目在运营配置页新增一个分组卡，虽然分组卡形态在 V1.3.0 后台整合稿（`../V1.3.0/ui-admin-g0-templates-integrated-v1.html`）中已有先例，但两处是新的：① 字段类型不同（版本号字符串 / URL，非数字输入）；② **§1.1 要求的「输入版本号确认」弹层在现有稿中不存在**，需新画。

## 2. AB-30：运营弹窗配置

**背景：** App 端 FR-137 新增运营弹窗，内容由运营在后台配置。现有后台无此能力。

### 已确认项（2026-10-06 拍板）

- 运营可在后台配置 App 弹窗

### 功能与流程（2026-10-07 拍板）

- **位置**：⚙️ 配置与安全组新增侧栏项「运营弹窗」，独立列表页
- **列表**：名称、状态（未开始 / 进行中 / 已结束 / 已停用）、生效时间、频次、优先级；可按状态筛选。**本版本列表不显示曝光数 / 点击数**——效果数据走 App 埋点（`ops_popup_shown` / `_tapped` / `_closed`），在 PostHog 按 `popup_id` 查看；后台展示待后续版本由 App 回传后端计数后再加
- **新建 / 编辑**：右侧抽屉表单，字段：
  - **必填 / 选填（2026-10-08）**：标题、正文选填；其余全部必填
  - 名称（仅后台可见）
  - 图片（EN / ID 可分别上传，只传一张则两种语言共用）、标题与正文（可选，EN / ID 两种语言）、按钮文案（EN / ID）
  - 跳转类型与目标：商品 / 品类 / App 内页面 / 外部链接 / 无跳转（「优惠券」随 V1.4.2 优惠券上线后再补）。**选「无跳转」时，按钮点击即关闭弹窗，点图片无反应**（2026-10-08 拍板）
  - 生效时间：开始、结束，按 **WIB** 填写与生效；结束必须晚于开始，否则不能保存
  - 频次：每人一次 / 每天最多一次
  - 目标人群：全部用户 / 新用户（注册 N 天内）/ 老用户。N 在每个弹窗上单独设置，默认 7 天；只有「全部用户」会对未登录游客展示（见 App 端 FR-137）（2026-10-07 拍板）
  - 图片：**上传控件旁固定显示提示文字**「建议比例 4:5（1080 × 1350），单张不超过 1MB。右上角会压关闭按钮，请留出约 160 × 160 px 空白」，EN / ID 两个上传位都显示。**比例只提醒、不拦截；超过 1MB 拒绝上传**，并提示「图片超过 1MB，请压缩后再上传」（2026-10-07 拍板）
  - 「App 内页面」只能从固定清单中选：首页 / 发帖页 / Toko 首页 / Know Your Pet / 健康页（2026-10-07 拍板，见 App 端 FR-137）
  - 优先级：数字，越大越优先；**优先级相同时后创建的优先**
- **编辑**（2026-10-08 拍板）：任何状态都能编辑，保存后即时生效；**进行中的弹窗改了内容，已经看过的用户不会再弹**（频次记录不重置）
- **停用**：行内操作，二次确认
- **重新启用**（2026-10-08 拍板）：已停用的行有「启用」操作，二次确认后恢复；仍按原生效时间判断是进行中还是已结束
- **删除**（2026-10-08 拍板）：**只有「未开始」的弹窗能删除**（从未上线过），二次确认；上过线的（进行中 / 已结束 / 已停用）不能删，保留记录以便对照 PostHog 数据
- **预览**：抽屉内按 EN / ID 分别预览弹窗在手机上的样子
- **权限与审计（2026-10-08）**：新增「运营弹窗管理」权限项，无此权限的账号看不到该侧栏项；新建、编辑、停用均记审计日志

### UI 说明

**需要出稿。** 后台文案按中 / EN / ID 三语准备。

## 3. AB-31：运营系统通知发送

**背景：** App 端 FR-138。现有系统通知全部由系统事件自动触发，运营无法主动发送。

### 已确认项（2026-10-06 拍板）

- 运营可在后台**选择用户**并发送系统通知

### 功能与流程（2026-10-07 拍板）

- **位置**：⚙️ 配置与安全组新增侧栏项「系统通知发送」，列表页展示发送记录
- **新建发送**：列表页右上「新建通知」→ 新页面，四步填写后提交：
  1. **内容**：标题（≤120 字符）、正文（≤255 字符），EN / ID 两种语言必填；点击跳转目标（同 AB-30）。用户收到哪种语言按其**账号语言**决定（App 端 FR-138）
  2. **选择用户**：
     - 全部用户
     - 按条件筛选：注册时间、最近活跃时间、是否建了宠物档案、宠物物种、是否下过电商订单、是否填写手机号。**多个条件之间为「且」**（同时满足才发，2026-10-09 拍板）
     - 指定用户：粘贴用户 ID 列表或上传 CSV（一行一个 ID，单次最多 5 万行）。**无效 ID 跳过**——不存在、已注销、已封号、虚拟号都不发，页面提示「有效 X 人，跳过 Y 个」，可导出跳过清单（2026-10-08 拍板）
  3. **发送时间**：立即发送 / 定时发送（按 **WIB**，须晚于当前时间）。**定时发送创建后不能编辑，只能取消后重建**；进入「发送中」后不能取消
  4. **确认**：显示预计触达人数与内容预览，二次确认后提交
- **发送记录**：每次发送一行——内容摘要、人群、发送时间、状态（待发送 / 发送中 / 已完成 / **部分失败** / 已取消）、触达人数；定时发送在发出前可取消。**本版本不显示打开数**——打开效果在 PostHog 按 `campaign_id` 查看（与 AB-30 口径一致）
- **「触达人数」= 成功写入通知中心的人数**，推送是否送达不计（腾讯 IM 不回送达结果）
- **防误发**：
  - 选择「全部用户」或预计触达超过 1 万人时，确认弹层要求手动输入预计人数确认
  - 发送权限单独作为一个权限项，可与「查看发送记录」分开授权
- 已封号账号自动排除；**虚拟号、已注销账号同样自动排除**（虚拟号收不到推送，且会让触达人数虚高）
- **定时发送的人群按实际发送时刻计算**，确认页显示的人数只是创建时的预估；发送时实际人数写入发送记录
- **分批推送**：全量或大批量发送时，推送须分批下发，避免触发腾讯 IM 推送接口限流；发送记录的状态在全部批次完成后才置为「已完成」。**失败批次自动重试 3 次，仍失败则状态置为「部分失败」并显示失败人数**；已写入通知中心的不受影响（2026-10-08 拍板）
- **审计**：新建、取消发送均记审计日志
