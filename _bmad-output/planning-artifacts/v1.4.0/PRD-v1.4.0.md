# PRD：TailTopia 宠物 App V1.4.0 · 精选自营电商

## 0. 文档说明

本 PRD 为迭代版本文档，采用轻量结构——不重复 V1.0.0 已写明的产品愿景、用户旅程和术语表，仅记录电商板块范围内的新增/变更内容。产品整体定位见 `V1.0.0/V1-0-0PRD.md`。

**编号延续规则：** 全仓库现有最大 FR 编号为 **FR-92**（`1.项目总述/Roadmap.md` 1.1.4 章节），本文档 FR 从 **FR-93** 起。待解决问题延续现有最大 OQ-24（`V1.1.2/改版1-1-2prd.md`），本文档 OQ 从 **OQ-25** 起。假设索引延续现有最大 A-14，本文档从 **A-15** 起。管理后台编号见 `v1-4-0电商后台prd.md`，从 **AB-10A** 起（现有模块编号至模块 9）。

**版本定位：** 电商板块是「精选自营」模式的第一个版本——平台自行采购备货、自定零售价、自负履约与售后，收入来自进销毛利而非抽佣。本版本范围 = **最小可售闭环 + 复购引擎**。

**⚠️ 本版本覆盖 Roadmap 既有电商设计。** `1.项目总述/Roadmap.md` 中 1.4.0「精选电商 Phase A（导流模式，跳转 Tokopedia/Shopee 完成购买）」与 2.1.0「精选电商 Phase B（App 内下单、商家自行履约）」两条均为零库存零履约模式，与本版本的自营模式互斥。产品已拍板由自营直接覆盖两者，Roadmap 需同步改写，详见 §7 与同目录 `Roadmap-电商改动建议.md`。

## 1. 版本目标

1. **跑通实物商品交易闭环**：从商品浏览到下单、支付、履约、签收、售后的完整链路。这是 App 内**第一次出现实物商品**——此前所有订单（AI 问诊解锁 FR-43A、兽医咨询 FR-43D、PawCoin 充值 FR-50A、身份证高清下载 FR-49D）均为虚拟商品，系统中不存在收货地址、物流、实物退货、库存四类能力，本版本需从零建立。
2. **建立复购引擎，而非货架**（§3.9）：把已有的宠物档案（品种/年龄/体重）与结构化健康记录（FR-45A 疫苗/驱虫）转化为购买触发点。这是本版本区别于 Shopee/Tokopedia 的唯一理由，也是版本的核心主线。
3. **守住「精选」边界**：SKU 数量受控、不开放第三方入驻、不做全站搜索货架。产品定位是「你的宠物档案说该买什么」，不是「你自己搜」。

**范围性质说明：** 目标 1 是交付基础，目标 2 是版本存在的意义。若排期需要取舍，应压缩目标 1 的可选项（如物流 API 深度对接，见 FR-104 的分期建议），不应压缩目标 2——只做完目标 1 等于做了一个更差的 Shopee。

## 2. 新增术语表

| 术语 | 定义 |
|------|------|
| **Toko** | 电商板块的印尼语名称（意为「商店」），作为底部 Tab 显示文案。与既有 Tab 显示文案的语言策略一致（如 Discovery 显示为 Jelajah） |
| **精选自营** | 平台向本地授权经销商采购、自持库存、自定零售价、自负履约与售后的经营模式。平台收入 = 零售价 − 进货成本（进销毛利），**不是抽佣**。与 Roadmap 原「导流」「商家自行履约」模式互斥 |
| **商品（Produk）** | 用户可见的售卖单位，一个商品可包含多个规格 |
| **规格 / SKU（Varian）** | 商品下的具体可售单元，是库存与价格的实际承载者。如「Royal Canin 幼犬粮」是商品，「1.5kg」「3kg」「7.5kg」是三个 SKU |
| **可售库存** | 实际库存 − 锁定库存。用户在商品详情与购物车看到的售罄/可买判定以此为准（FR-95） |
| **锁定库存** | 已进入待支付订单、尚未支付成功的库存。支付成功转为扣减，支付超时则释放 |
| **复购触发卡** | 嵌在 Diary 时间线条目或推送中的一键补货入口，由结构化健康记录周期或粮量见底预估驱动（FR-109/FR-110） |
| **服务范围** | 平台可配送的行政区范围。首发限大雅加达 Jabodetabek，超范围地址不可下单（FR-100） |

## 3. 功能与需求

### 3.1 信息架构与入口

**功能描述：** 电商板块占用底部 Tab Bar 中已预留的位置。Tab 的最终位序、图标激活态设计、以及原位置模块的迁移方案由 Tab 改版负责人另行设计，**不在本 PRD 范围内**——本文档仅定义 Toko Tab 自身的内容与行为，并在 §8 依赖项中列出需对方确认的接口。

#### FR-93：Toko Tab 与首页结构

Toko 首页是精选流，**不是搜索驱动的货架**。页面自上而下固定为四个区域：

| 区域 | 内容 | 展示条件 |
|---|---|---|
| ① 补货提醒区 | 复购触发卡（驱虫/疫苗到期、粮量见底），最多 2 张 | 有触发时才出现，无触发则整区不渲染 |
| ② 为我的宠物精选 | 「Pilihan buat {宠物名}」，按档案推荐（FR-108），4–6 个商品 | 状态 A 且已建档 |
| ③ 分类入口 | 4 个固定品类：Makanan（粮）/ Obat & Vitamin（驱虫保健）/ Camilan（零食）/ Perawatan（洗护） | 常驻 |
| ④ 全部精选 | 全部在售商品，按运营排序 | 常驻 |

**后果：**
- **不提供全站搜索框。** 商品总数受 SKU 上限约束（见 OQ-25），四个分类 + 精选流已足够覆盖；搜索框会把产品心智推向通用货架，与战略边界冲突
- 区域 ①② 依赖宠物档案。用户状态与展示的对应关系：

| 用户状态 | ① 补货提醒 | ② 为我的宠物精选 | ③④ 分类与全部 |
|---|---|---|---|
| 游客（未登录） | 不展示 | 不展示 | **展示**（可浏览、可进详情，加购时触发 V1.0.0 FR-0B 软性登录引导） |
| 已登录 · 状态 A · 未建档 | 不展示 | 替换为建档引导卡（复用 FR-0G 引导文案，不新建） | 展示 |
| 已登录 · 状态 A · 已建档 | 按触发展示 | 展示 | 展示 |
| 已登录 · 状态 B/C（无宠物） | 不展示 | 不展示 | 展示 |
- 多宠物用户（FR-1.2.0 多宠物账号管理）：区域 ①② 按**当前选中宠物**渲染，切换宠物时刷新；选中态复用多宠物管理已有的全局当前宠物概念，不新建选择器

#### FR-93A：Toko 与既有 Tab 的关系

**后果：**
- Toko 是**非落地 Tab**。V1.1.2 FR-78 确立的落地 Tab 判定规则（只有真正建了宠物档案的用户落 Diary，其余已登录用户落 Discovery，游客落 Diary）不因本版本改变，Toko 不参与落地判定
- 游客点击 Toko **不触发登录引导**——Toko 与 Discovery 一样允许游客浏览。这与 V1.1.2 FR-78 中「未登录点击非落地 Tab 触发登录引导」的既有机制存在差异，是有意为之：商品浏览是转化漏斗的最上层，用登录墙拦截会直接杀掉转化。登录引导推迟到**加入购物车**这一步触发
- Tab 切换需上报埋点（V1.1.2 起底部 Tab 切换已改为手动上报，见 §6）

### 3.2 商品与库存

#### FR-94：商品模型与展示

**商品字段：**

| 字段 | 必填 | 说明 |
|---|---|---|
| 商品名称 | 必填 | 印尼语，≤60 字符 |
| 品牌 | 必填 | 用于详情页信任展示 |
| 品类 | 必填 | 四选一：Makanan / Obat & Vitamin / Camilan / Perawatan |
| 主图 + 图集 | 必填 | 主图 1 张 + 图集 ≤8 张 |
| 规格列表（SKU） | 必填，≥1 | 见 FR-94A |
| 适用物种 | 必填 | 犬 / 猫 / 通用。用于 FR-108 档案推荐过滤 |
| 适用体型 | 选填 | 小型 / 中型 / 大型 / 通用 |
| 适用年龄段 | 选填 | 幼年 / 成年 / 老年 / 通用 |
| 商品详情 | 必填 | 富文本（图文），含成分表 |
| 每日建议喂量 | 仅 Makanan 品类必填 | 结构化：`{体重区间, 克/日}` 数组。**FR-110 粮量见底预估的计算依据，不是展示文案** |
| 保质期说明 | 必填 | 展示文案 |
| 退换货规则标识 | 必填 | 枚举：`可退可换` / `开封不退` / `不可退换`。见 FR-105 |

#### FR-94A：规格（SKU）与价格

**后果：**
- 规格是价格与库存的实际承载者。同一商品的不同规格可有不同价格、不同库存、不同退换货标识
- 商品详情页规格选择器：未选规格时**加购按钮为禁用态**，不默认选中第一个规格（避免用户误购规格）
- 单一规格的商品不展示选择器，直接可加购
- 价格单位 IDR，展示格式 `Rp 185.000`（印尼千分位用点号），不展示小数

#### FR-95：库存与售罄

**库存口径：** `可售库存 = 实际库存 − 锁定库存`。用户侧一切售罄判定以可售库存为准。

**库存流转：**

| 动作 | 库存变化 |
|---|---|
| 提交订单（进入待支付） | 可售 → 锁定 |
| 支付成功 | 锁定 → 扣减（出库） |
| 支付超时 / 用户取消 | 锁定 → 释放回可售 |
| 退货入库并质检通过 | 增加可售（后台操作，见后台 PRD AB-10C） |

**后果：**
- **库存扣减必须由服务端原子操作完成**，不得依赖客户端读取后写入。并发下单时以服务端判定为准，失败方返回明确的「已售罄」错误而非静默失败
- 可售库存 = 0：商品卡与详情页展示「Stok habis」（售罄），加购按钮禁用；商品**不自动下架**，仍可浏览（保留搜索引擎与复购提醒的落点）
- 可售库存 ≤ 运营配置阈值：详情页展示「Sisa {n}」低库存提示，制造合理紧迫感但不虚构数字
- **购物车与结算是两次独立校验**：加购时校验一次，提交订单时再校验一次。第二次失败时，结算页明确标出是哪个 SKU 不可用，并允许用户移除后继续下单，不整单打回

### 3.3 购物车与结算

#### FR-96：购物车

**后果：**
- **单店模型，无店铺分组**。平台自营是唯一卖家，购物车是一个平铺列表——这是相对第三方电商的结构性简化，不要照搬 Shopee 的多店铺分组
- 行内可调数量（+/−）、可删除；数量上限受可售库存约束
- **失效商品单独分区**置于列表底部，包含：已下架、已售罄。失效商品不参与合计、不可勾选，提供「清空失效商品」入口
- 购物车角标显示商品件数（非种类数）
- 游客无购物车。游客点击加购时触发登录引导（复用 V1.0.0 FR-0B 软性登录），登录成功后**自动完成本次加购动作并停留原页**，不丢失意图

#### FR-97：结算页

**结算页自上而下：** 收货地址 → 商品清单 → 配送方式 → 支付方式 → 金额明细 → 提交按钮

**金额明细构成：**

| 项 | 说明 |
|---|---|
| 商品小计 | 各 SKU 单价 × 数量之和 |
| 运费 | 按配送方式与地址计算，见 FR-99 |
| 免运费抵扣 | 商品小计 ≥ 运营配置门槛时减免运费，展示为负数行 |
| **应付合计** | 上述之和 |

**后果：**
- 首版**不含优惠券/促销码/会员折扣**。会员制套餐在 Roadmap 中整体暂缓（2026-07-15），本版本不预留会员价字段，避免为暂缓功能提前埋成本
- 无收货地址时，地址区展示为「+ 新增收货地址」的引导态，提交按钮禁用
- 地址超出服务范围时，地址区展示范围外警示，提交按钮禁用并说明原因（见 FR-100）
- 提交订单 = 创建订单 + 锁定库存 + 进入待支付，此时**尚未扣款**

### 3.4 收货地址

#### FR-98：收货地址体系

App 内首次引入收货地址。**印尼行政区划为四级**，本版本采集到第三级 + 详细地址 + 邮编。

**字段：**

| 字段 | 必填 | 说明 |
|---|---|---|
| 收件人姓名 | 必填 | ≤40 字符 |
| 手机号 | 必填 | 印尼格式，+62 前缀，8–13 位 |
| Provinsi（省） | 必填 | 级联选择 |
| Kota / Kabupaten（市 / 县） | 必填 | 级联选择 |
| Kecamatan（区） | 必填 | 级联选择 |
| 详细地址 | 必填 | 街道、门牌、楼层、单元，≤120 字符 |
| Kode Pos（邮编） | 必填 | 5 位数字 |
| 地址标签 | 选填 | Rumah（家）/ Kantor（公司）/ 自定义 ≤10 字符 |
| 设为默认 | — | 开关，仅一个默认地址 |

**后果：**
- 地址簿上限 20 条
- 首个创建的地址自动设为默认
- 删除默认地址后，剩余地址中最近使用的一条自动升为默认；地址簿清空则无默认
- **手机号是履约联系方式，不与账号手机号（1.2.0 手机号采集入口）互通**——两者用途不同，不做自动填充也不做同步

#### FR-99：服务范围与运费

**后果：**
- 服务范围按 Kecamatan 粒度配置（后台 AB-11C）。首发限 Jabodetabek 范围内的 Kecamatan
- 地址保存**不校验服务范围**（允许用户存下未来可用的地址），**结算时校验**并阻断下单，提示文案需说明「暂不配送至该区域」而非笼统报错
- 配送方式两档：

| 配送方式 | 承运 | 时效 | 适用范围 |
|---|---|---|---|
| 当日达（Sameday） | GoSend / Grab Express | 当日 | 服务范围内的同城 Kecamatan |
| 标准快递（Reguler） | JNE / SiCepat / Anteraja | 2–4 日 | 服务范围全部 |

- 运费由后台按「配送方式 × 区域」配置固定值（AB-11C），**首版不接承运商实时计费 API**——首发仅 Jabodetabek，区域差异小，固定运费表足够，可省去一整条 API 对接工期
- 超重/超体积附加费：首版不做。SKU 上限受控且品类可预期（最大件为 7.5kg 级狗粮），差异由固定运费表吸收

### 3.5 支付

#### FR-100：电商订单支付

**复用 `V1.1.0/v1-1-0PRD.md` FR-43 通用支付组件**，不新建支付通道。

**支付方式两种：QRIS（真钱）与 PawCoin（余额），可混合使用。**

**⚠️ 真钱渠道口径以 Roadmap 更正为准：仅 QRIS。** `V1.1.0/v1-1-0PRD.md` FR-43 原文写「QRIS、DANA」，但 `1.项目总述/Roadmap.md` 1.1.0 条目于 **2026-07-15 更正为「目前仅支持 QRIS，DANA 尚未接入」**，后者更新。本版本按 QRIS 单渠道设计，不做真钱渠道选择器。**不支持 GoPay/OVO 直连、不支持银行转账/VA。**

**后果：**
- 支付失败/取消处理复用 FR-43F 通用规则，不另定义
- **待支付超时 = 60 分钟**（超时后自动取消订单、释放锁定库存）。此值明显长于兽医咨询的限时支付窗口，因为实物购买的决策与支付节奏不同，沿用短窗口会造成大量误失效订单
- 超时前 10 分钟推送一次提醒（复用 FR-38 深链接直跳订单详情）
- **PawCoin 可用于购买实物商品**（2026-08-10 产品拍板，覆盖原「首版不可」的建议），使用规则见 FR-100A

#### FR-100A：PawCoin 购买实物商品的使用规则

PawCoin 原本只用于虚拟商品（AI 问诊解锁 FR-43A、兽医咨询 FR-43D、身份证高清下载 FR-49D），这些场景**没有退货、没有实物、没有运费**。扩展到实物商品后，必须补齐以下规则，否则会击穿 FR-50D 的封闭币前提。

##### 规则 1 · 防套现（最承重，不可妥协）

> **PawCoin 支付的部分，退款只能退回 PawCoin，不提供「退回真钱」选项。**

`V1.1.0` FR-50D 明确 PawCoin **不支持一般性提现**。但实物商品**可以退货**——若允许 PawCoin 买的商品退货时退真钱，则形成 `充值 PawCoin → 购买实物 → 申请退货 → 退回真钱` 的路径，**等于变相提现，直接击穿 FR-50D**。

**后果：**
- 退款方式选择页对 PawCoin 支付的部分**不展示「退回真钱」入口**，而不是展示后再拒绝——不给用户产生预期再打破
- 该规则**不因退货原因而变**：即使是平台责任（商品破损/错发），PawCoin 部分仍只退 PawCoin。用户的真钱从未流出过这部分，退真钱不是"补偿"而是"兑现"
- 但平台责任下用户确实承受了"没有选择权"的代价，**补偿走 Coin 侧溢价而非开退现金的口子**——见规则 7
- 混合支付订单的 QRIS 部分**不受此限**，仍按既有 FR-43D 由用户选择退真钱或转 PawCoin

##### 规则 2 · 混合支付与按比例退款

**支持混合支付**：PawCoin 余额不足以覆盖订单时，**余额优先全额抵扣，差额由 QRIS 补足**，不阻断下单。

**为什么支持混合**：PawCoin 余额主要来自两个来源——4 个固定充值档位（FR-50A）与退款转入（FR-43D）。后者多为零头金额。若要求整单 PawCoin，绝大多数余额将无法用于实物商品，这个能力等于白开。

**退款按原支付比例拆分返还：**

```
订单实付：PawCoin 60.000 + QRIS 240.000 = 300.000（PawCoin 占比 20%）
退款 150.000 时：
  → 退 PawCoin 30.000（20%，只能退 PawCoin，规则 1）
  → 退 QRIS 部分 120.000（80%，用户可选退真钱或转 PawCoin，FR-43D）
```

**后果：**
- 比例按**订单实付金额**计算并在订单创建时固化，**不随后续部分退款重算**——否则多次部分退货会让比例漂移
- 该规则天然保证 **用户拿回的真钱永远不超过其投入的真钱**，是规则 1 在混合场景下的数学保证，可用于向法务/财务说明闭环性
- 结算页需**同时展示两段金额**（PawCoin 抵扣多少、还需 QRIS 支付多少），不能只显示一个总数

##### 规则 3 · 运费可用 PawCoin 支付

运费计入订单总额，一并参与 PawCoin 抵扣与比例拆分。

**后果：**
- 运费是平台向承运商支付的**真实现金支出**，用 PawCoin 覆盖等于用预收款抵现金成本。财务侧需知悉：后台对账（AB-13D）须能把「PawCoin 抵扣的运费」单独拆出，否则现金流量表会失真
- 退货运费由用户承担时（FR-104 非质量问题），**从退款金额中扣除后再退回**，不单独向用户发起收款

##### 规则 4 · 单笔上限

- 单笔订单的 PawCoin 支付金额设上限，**建议 Rp 1.000.000**，由后台配置（AB-6D）

**⚠️ 这个上限不是浮存工具，别当浮存工具用。**（2026-08-10 更正，原文误将其论证为「浮存的前置阀门」）

浮存的方向是：**充值 → 浮存增加；消费 → 浮存减少**——用户花掉 Coin 等于平台交付了价值、债务被核销。**因此限制单笔消费额度会让浮存降得更慢，与控制浮存的目标相反。**

**上限真正的用途只有两条：**

| # | 用途 | 说明 |
|---|---|---|
| 1 | **故障 / 欺诈的单次爆炸半径** | Coin 扣减链路若出现 bug 或被利用，上限把单次事故的损失锁死在一个可承受的量级 |
| 2 | **DEP-7 的监管姿态** | 闭环储值工具若单笔交易额不设任何限制，在 uang elektronik 的口径下更容易被认定为需要牌照的电子货币。自设上限是防御性姿态。⚠️ 但监管通常更关注**余额上限**而非单笔消费上限——具体以 DEP-7 的法务结论为准，必要时改为余额上限 |

**为什么 Rp 1.000.000 仍是合适的数**：客单约 Rp 285.000，即使多件订单也很少触及 100 万，**该上限在正常经营中几乎不会触发**——正因如此它才是廉价保险：拿到了上述两条防护，又基本不妨碍存量余额的正常消耗。**上限定得太低反而有害**，会把用户的余额锁在账上出不去。

##### 规则 5 · 与浮存门槛（AB-6C）联动

> **AB-6C 触发充值暂停时，已有余额仍可正常用于购物。**

**后果：**
- 暂停的是**充值入口**，不是**消费出口**。已持有余额的用户若因此买不了东西，等于对已付款用户违约
- 充值暂停期间，结算页 PawCoin 区正常可用，仅「余额不足 → 去充值」的引导按钮置为不可用并说明原因

##### 规则 6 · 不参与的场景

- PawCoin **不可用于**支付 PPN 增值税之外的任何平台外部结算（本版本无此场景，此条为防御性声明）
- PawCoin 余额**不可转让**给其他用户——维持封闭闭环，见 DEP-7 合规依赖

##### 规则 7 · 平台责任时的 Coin 溢价补偿

> **退货类型 = 质量问题时，PawCoin 退款部分按配置比例额外补偿 Coin。**

**这条规则解决的问题：** 规则 1 规定 PawCoin 段只退 Coin 且不因退货原因而变。但当退货是**平台的错**（商品破损 / 临期 / 错发）时，用户不仅东西有问题，还失去了拿回现金的选择权——这是本设计中最容易引发客诉、且 CS 手上没有变通手段的一处（后台按 AB-12C 不提供改判入口）。

**产品决定（2026-08-10）：补偿走 Coin 侧溢价，不开退现金的口子。** 既安抚了用户，又不破坏闭环——退回的现金依然永远不超过投入的现金。

**触发条件：**

| 退货类型（AB-12A 已有枚举） | 是否给溢价 |
|---|---|
| **质量问题**（破损 / 临期 / 错发） | ✅ **给** |
| 非质量问题（不想要了 / 买错规格） | ❌ 不给 |
| 拒收（未签收） | ❌ 不给 |
| 待发货前取消 | ❌ 不给 |

**后果：**
- **复用 AB-12A 已有的「退货类型」判定结果，不新增 CS 判定项**——CS 本来就要选退货类型，溢价由系统据此自动计算，不增加人工环节
- **溢价只作用于 PawCoin 段**。混合支付订单的 QRIS 段本来就可以选退现金（全额挽回），无需补偿
- **不给溢价的情形必须是默认**：用户自身原因退货若也给溢价，会变成"退货就有奖励"，诱发无意义退货
- 溢价比例与上限由后台配置，**必须与既有 AB-6A「用户主动选择转 PawCoin」的激励溢价分开配置**——两者触发条件与目的完全不同（一个是激励用户不走人工退现金，一个是补偿用户没有选择权），共用一个比例会导致调其一误伤其二。见 AB-6A（扩展）
- **溢价发放会增加 PawCoin 浮存**，须计入 AB-6C 监控；会计上属平台售后成本，须在 AB-13A 毛利看板与 AB-13D 对账中可拆出
- 刷单风险可控：质量问题需上传凭证图（FR-104）+ CS 判定 + AB-12D 判例库沉淀；且为拿一笔小额 Coin 溢价而走完整退货流程，成本远高于收益
- 比例建议值与上限见 **OQ-34**

### 3.7 退换货

#### FR-104：退换货规则

这是与既有虚拟商品退款的**本质差异**——虚拟商品退款是纯资金操作，实物退货需要退回实物、质检、并确定运费归属。

**可退情形与运费归属：**

| 情形 | 时限 | 是否需退回实物 | 退货运费 |
|---|---|---|---|
| 待发货前取消 | 发货前 | 否 | 无 |
| 拒收（未签收） | 配送中 | 否（承运商原路退回） | 平台承担 |
| 质量问题（破损/临期/错发） | 签收后 7 日内 | 是 | **平台承担** |
| 非质量问题（不想要了/买错规格） | 签收后 7 日内 | 是，且需未拆封 | **用户承担** |

**不可退情形：**
- **退换货标识为「开封不退」的商品一经开封不可退**（FR-94 字段）。宠物食品与保健品出于食品与用药安全，开封后无法二次销售，此规则须在**商品详情页、结算页、退货申请页三处**明示，不能只写在规则页里
- 标识为「不可退换」的商品不提供退货入口

**后果：**
- 退货申请需上传凭证图 ≤6 张，质量问题必填
- 申请提交后进入 CS 审核，**复用 `V1.1.0/v1-1-0后台prd.md` AB-5E 退款申请流程与 AB-5B 工单详情处理**，不另建审核通道
- CS 驳回时须填写理由并回告用户，复用既有工单回告机制（FR-52A）

#### FR-105：退款到账方式

**退款先按 FR-100A 规则 2 拆成两段，再分别处理。**

| 支付来源 | 退款去向 | 用户可选 | 成本 / 补偿 |
|---|---|---|---|
| **PawCoin 部分** | **只能退回 PawCoin** | ❌ 无选项 | 无手续费；**退货类型 = 质量问题时额外补偿 Coin 溢价**（规则 7） |
| **QRIS 部分** | 退回真钱 **或** 转 PawCoin | ✅ 用户选择（复用 FR-43D） | 退真钱：BCA 免手续费，OVO/GoPay 自付 Rp2,500<br>转 PawCoin：即时到账 + 激励溢价（AB-6A 既有配置） |

> ⚠️ 表中出现两种 Coin 溢价，**触发条件与目的不同，配置项必须分开**：QRIS 段的是**激励**（换取用户不走人工退现金流程）；PawCoin 段的是**补偿**（用户没有选择权）。

**后果：**
- **PawCoin 部分无选择权，是 FR-100A 规则 1 的直接体现**，不是遗漏。退款方式页对这一段只展示结果、不展示选项，避免先给预期再打破
- 纯 QRIS 支付的订单行为与既有虚拟商品退款完全一致，无新增
- 部分退款按 `实退金额 × 订单固化的支付比例` 执行；运费是否退回按 FR-104 的运费归属规则判定
- 退货运费由用户承担时，从退款金额中扣除后再拆分返还（FR-100A 规则 3）
- 转入的 PawCoin 可用于 AI 问诊、兽医咨询、身份证下载等既有场景，以及本版本新增的实物商品（FR-50C 消费范围需相应扩写，见 §6）

### 3.9 复购引擎（版本核心）

**功能描述：** 本节是电商板块存在的意义。狗粮与驱虫药是宠主唯一天然月月复购的品类，而 TailTopia 已经掌握了触发复购所需的全部数据——宠物档案（品种/年龄/体重）与结构化健康记录（FR-45A 疫苗/驱虫/绝育）。三条机制把这些既有数据转化为购买触发点，**全部复用现有数据源与推送通道，不新建提醒引擎**。

#### FR-107：档案推荐

**数据源：** 宠物档案（物种、品种、年龄、体重、绝育状态）— V1.0.0 FR-11 已有

**推荐逻辑（规则式，非算法）：**
1. 按 `适用物种` 硬过滤（FR-94 字段）
2. 按 `适用年龄段` 匹配档案年龄（幼年 <1 岁 / 成年 1–7 岁 / 老年 >7 岁，犬猫阈值可后台配置）
3. 按 `适用体型` 匹配档案体重
4. 结果按运营权重排序，取前 4–6 个

**后果：**
- 展示位：Toko 首页区域 ②（FR-93）与 Diary 档案页推荐区
- 卡片文案带出推荐理由，如「Untuk anjing dewasa 10–25 kg」（适合 10–25kg 成年犬），**让推荐可解释**——不可解释的推荐在信任驱动的产品里是负资产
- 档案数据不完整（缺体重/年龄）时降级为按物种推荐，并在推荐区尾部附一张「补全档案，推荐更准」的引导卡，跳转档案编辑
- **首版为规则式，不引入个性化算法**。SKU 数量受控（见 OQ-25），规则式已足够；算法推荐待 SKU 规模扩大后再议

#### FR-108：健康记录触发复购

**数据源：** FR-45A 结构化健康记录（疫苗 / 驱虫 / 月经 / 绝育 / 自定义）+ 1.2.0 健康提醒的间隔配置

**后果：**
- 当健康提醒判定某项（**仅限驱虫、疫苗两类**）临近到期时，除既有提醒外，额外在两处生成复购触发卡：
  1. **Diary 时间线**对应健康记录条目内嵌 CTA（宿主为 V1.1.2 FR-82 五类条目中的「结构化健康记录」条目）
  2. **健康提醒推送**内附商品直达（复用 FR-38 深链接规则，直跳商品详情）
- 触发卡内容：`{宠物名}的驱虫周期快到了` + 关联商品 1 个 + 「查看」按钮
- **仅驱虫与疫苗参与触发**。月经、绝育、自定义类型不触发——月经无对应商品，绝育是一次性事件，自定义类型无结构化语义（FR-45A 已明确自定义类型不参与任何联动）
- **疫苗触发的是「预约问诊/线下接种」而非直接卖疫苗**。疫苗为处方类医疗行为，平台不自营销售疫苗，该触发卡跳转健康模块而非商品详情
- 频控：同一宠物同一健康事件类型的复购触发卡 **30 日内最多出现一次**，避免提醒疲劳

#### FR-109：粮量见底预估

**数据源：** 电商订单历史（最近一次 Makanan 品类购买的 SKU 规格与日期）+ 商品的 `每日建议喂量`（FR-94）+ 宠物档案体重

**计算：**
```
日喂量(克) = 按档案体重在商品「每日建议喂量」区间表中匹配
预计可用天数 = SKU 净含量(克) ÷ 日喂量
预计耗尽日 = 上次购买日 + 预计可用天数
```

**后果：**
- 耗尽日前 **7 天**开始，在 Toko 首页区域 ① 展示补货卡，并推送一次
- 卡片文案给出估算依据而非断言，如「Makanan Mochi diperkirakan habis ~5 hari lagi」（预计约 5 天后吃完），**不写成确定事实**——这是估算值，档案体重不准或用户混喂时会有偏差
- 用户完成该 SKU 的再次购买后，预估周期从新订单日重新起算，旧提醒立即消失
- 缺少任一输入（无购买历史 / 商品未配日喂量 / 档案无体重）时不触发，**不做兜底猜测**

#### FR-110：问诊与商品的边界（约束性需求）

**这是一条限制性需求，不是功能。**

**后果：**
- **兽医在问诊会话中不得推荐具体 SKU**，不提供「兽医推荐商品」组件、不给兽医端任何商品链接插入能力
- 问诊结论页可出现的商品关联仅限一种形式：**按结论中的结构化健康记录类型（如驱虫）跳转对应品类**，由系统生成、非兽医选择
- 理由：`TailTopia-战略决策快照.md` 中「靠什么赢」的第一条是 AI 问诊与本地信任。问诊一旦被用户感知为销售前端，这条护城河即失效，其损失远大于电商的短期转化收益。此约束优先于任何转化率优化

## 4. 状态机汇总

### 4.1 订单状态机

```
                    ┌────────────────────────────────┐
                    ↓                                │
  [提交订单] → 待支付 ──支付成功──→ 待发货 ──发货──→ 已发货
                 │                    │                 │
       超时60min │           申请取消 │        承运商送达│
       /用户取消 │                    ↓                 ↓
                 ↓                 退款中 ←──申请退货── 已送达
              已取消(终)               │                 │
                                       ↓        确认收货 │
                                   已退款(终)   /7日自动 ↓
                                                    已完成(终)
                                                         │
                                            签收7日内申请退货
                                                         ↓
                                                      退款中
```

**终态：** `已取消` / `已退款` / `已完成`（`已完成` 在签收 7 日内仍可转入 `退款中`，7 日后为绝对终态）

### 4.2 退款状态机

```
[提交退货申请] → 待CS审核 ──驳回──→ 已驳回(终，可申诉复用FR-52)
                    │
                  批准
                    ↓
            待用户寄回 ──超时未寄回(7日)──→ 已关闭(终)
                    │
                 已寄回
                    ↓
                 质检中 ──质检不通过──→ 已驳回(终)
                    │
                质检通过
                    ↓
              退款执行中 ──→ 已退款(终)
```

**说明：** 「待发货前取消」与「拒收」两类情形跳过 `待用户寄回` 与 `质检中`，由 `待CS审核` 批准后直接进入 `退款执行中`。

### 4.3 库存状态机

```
可售 ──提交订单──→ 锁定 ──支付成功──→ 已扣减(出库)
  ↑                  │
  │      支付超时/取消 │
  └──────────────────┘
  ↑
  └── 退货质检通过后入库（后台操作）
```
