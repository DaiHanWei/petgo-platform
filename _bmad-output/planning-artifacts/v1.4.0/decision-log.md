| **C-15** | 手机号校验与存储口径（原 SPEC-13） | **归一化存 E.164：`+62` + 9–12 位有效位，首位必为 `8`；输入时自动剥前导 `0`。** 用户输 `08123456789` / `8123456789` / `+62 812-3456-789` 一律归一为 `+628123456789`。🔴 **下限由 PRD 原文的 8 位提到 9 位** —— 印尼手机号去 0 后常见 9–12 位，8 位会放进大量无效号码，而**无效号 = 快递员联系不上 = 真实履约失败**。**邮编 × Kecamatan 一致性做「警告不阻断」**（运费按 Kecamatan 计、承运商按邮编派送，两者不符值得提醒但不该挡住下单） | **08-16** |
| **C-16** | PawCoin 余额超单笔上限时的行为（原 SPEC-19） | **截断到上限，差额走 QRIS，结算页明示原因。** 例：余额 1.5M、订单 1.2M、上限 1M → 抵扣 1M + QRIS 200k，并在两段金额旁加一行「本单最多可用 Rp 1.000.000」。理由：与规则 4 的本意（故障/欺诈爆炸半径上限）一致，同时守住规则 2「不阻断下单」的初衷；不明示则用户会以为系统出错 | **08-16** |
| **C-17** | 锁定库存防滥用阈值（原 SPEC-12） | **三个阈值全做**：① 同用户**并发待支付订单 ≤ 3 单**；② **单 SKU 单用户锁定量 ≤ min(5 件, 该 SKU 可售的 20%)**；③ **连续 2 次超时后冷却 30 分钟**。三条均为纯服务端判定、纯 DB 实现，**无新依赖**（守 NFR-1）。针对的是 SKU 上限 30 + 自营备货受现金约束的实际处境——库存本就少，锁死一个爆款代价很大（N-2 / DEP-9） | **08-16** |

### L-1 · Roadmap 的电商模式与本版本互斥（矛盾，已由 C-2 决议）

`1.项目总述/Roadmap.md` 中：

### L-2 · 支付渠道口径两处不一致（矛盾，需拍板以哪份为准）

| 来源 | 表述 | 日期 |

### L-3 · FR-54 订单卡片类型需从 4 类扩为 5 类（缺口）

`V1.1.0/v1-1-0PRD.md` FR-54 定义了 4 类订单卡片（54A 兽医咨询 / 54B PawCoin 充值 / 54C AI 问诊解锁 / 54D 高清图购买），全部为虚拟商品。电商订单为第 5 类（本版本 FR-101），FR-54 主体结构需回写说明。

### L-4 · FR-50 体系需为「实物商品」补强（缺口，C-8 拍板后升级为必做）

`V1.1.0/v1-1-0PRD.md` 的 FR-50C（消费范围与限制）与 FR-50D（不支持一般性提现）都写于**系统内不存在实物商品**时。C-8 拍板 PawCoin 可购买实物后，两处都需回写：

| 条目 | 需补什么 |
|---|---|
| **FR-50C** | 消费范围**扩写纳入实物商品**，并引用 FR-100A 六条使用规则 |
| **FR-50D** | 「不支持一般性提现」的论证需补一句：**实物商品可退货，构成新出现的潜在提现路径**（`充值 → 买货 → 退货退真钱`），已由 FR-100A 规则 1「PawCoin 部分只退 PawCoin」封堵 |

**这不是电商板块的局部规则，而是对 FR-50 封闭币体系的实质性扩展。** 评审时应由 PawCoin 体系的负责人一并确认，而不是当作电商的附属条目放行。

### L-5 · 系统内首次出现实物商品，四类能力从零建立（缺口，非矛盾）

既有全部收费场景均为虚拟商品，因此系统中**完全不存在**：收货地址、物流、实物退货、库存。这四块是本版本的工程主要增量，其余（支付 FR-43、订单壳 FR-54、客服工单 FR-52、退款 AB-5E、退款溢价 AB-6A、支付记录 AB-8E）均为复用。

排期评估时应按此区分，不要把整个电商板块都当作新建。

### L-6 · 埋点基线缺失风险（缺口，有前车之鉴）

`3.数据埋点/埋点文件/埋点清单v112.md` §0.3 记录：V1.1.2 改版的埋点与改版**同版本发布**，用户装上新版时 Tab 顺序已变，采到的第一个数据点即为改版后，导致三项核心指标不可得、PRD 的「唯一裁决指标」与处置原则一并失效。

**电商 Tab 同样是替换既有 Tab，面临完全相同的风险。** 若 `toko_tab_viewed` 与被替换 Tab 的曝光事件不在前一个版本先行发布，本次替换的得失将同样无法评估。见 PRD §5。

### L-7 · 「单笔上限 = 浮存阀门」是错误论证（2026-08-10 设计侧自纠）

初稿把 PawCoin 单笔支付上限（FR-100A 规则 4 / AB-6D）论证为「浮存的前置阀门」。**这个论证是反的。**

**浮存的方向：**

| 通道 | 对浮存 | 有无现金垫底 |
|---|---|---|
| 充值 | **↑ 增加** | 有（等额现金流入） |
| 消费（含电商） | **↓ 减少** | — 债务核销 |
| 两类溢价发放 | **↑ 增加** | **无 ← 真正的风险源** |

用户花掉 Coin = 平台交付了价值、负债被核销。**限制单笔消费额度只会让浮存降得更慢。**

**连带被推翻的三处：**
1. **规则 4 的理由**已改写为「故障/欺诈爆炸半径 + DEP-7 监管姿态」，并注明上限应设在几乎不触发的水平，定低反而有害
2. **A-20 假设方向写反**——开放实物消费新增了 Coin 消费出口，且平台不做充值促销（`待讨论事项` #3），用户没理由先充值再买粮而不直接 QRIS 付，故净效应预期是**浮存下降**。已改写并新增 **A-21** 指向真正的风险源（溢价）
3. **AB-6D 的处置建议是有害的**：原写「浮存超预期时先下调单笔上限」，照做会让浮存更降不下来。已改为「收紧 AB-6A 溢价比例」

**Rp 1.000.000 这个数保留**——客单约 Rp 285.000，该上限几乎不触发，作为防故障保险是廉价且合理的。**数字对，原来的理由错。**

> **L-7 的传导核查（2026-08-14 validate）：** 用户端 FR-100A 规则 4、OQ-33、A-20、A-21 与后台 AB-6D 的「不该做」表**全部已改到位** ✅。**唯独后台 AB-6C 漏了一句**——仍写「为买粮而充值会显著改变浮存的增长斜率」，方向与自纠结论相反。已修正（见 L-13）。

### L-8 · 混合支付与 `PaymentIntent` 单渠道单金额模型冲突（**最高，阻塞整条退款/对账链**）

**代码事实：** `petgo-backend` 的 `pay/domain/PaymentIntent.java` 是**严格单渠道单金额**模型——`channel` 为单值枚举、`amount` 为单个数值，且**两者均 `updatable = false`**；`PayChannel` 仅 `{QRIS, PAWCOIN}` 二选一，无混合表达能力。

**PRD 要求：** FR-100A 规则 2 要求一笔订单同时含 PawCoin 段与 QRIS 段，且**支付比例须在订单创建时固化**，供后续多次部分退款按固定比例拆分。

**影响面：** FR-100A 全部 7 条规则 · FR-105 退款到账方式 · 后台 AB-12C 退款执行拆分 · AB-13D 对账。

**出口：** ✅ **已闭合 —— 2026-08-15 拍板方案 (a)，见 C-10。** 扩展既有 `PaymentIntent`：`PayChannel` 末尾追加 `MIXED`，新增 `coin_amount` / `cash_amount` / `coin_ratio` 三列（nullable，既有 4 个 purpose 全 NULL、行为不变），退款在同一笔 intent 内按 `coin_ratio` 拆分。**FR-100A / FR-105 / AB-12C / AB-13D 相关 story 已解除阻塞。** ⚠️ 触碰共享表，Flyway 须占独占号段 + 告知另两人。

PRD 正文原写「复用 FR-43 通用支付组件，**不新建支付通道**」——把最高风险项写成了零成本复用，已于 FR-100 就地修正。

### L-9 · `PetProfile` 无体重字段（高，复购引擎三缺一）

**代码事实：** `profile/domain/PetProfile.java` 字段全集为 `ownerId / avatarUrl / petType / name / systemDefaultName / breed / birthday / intro / cardToken / ogImageUrl / serialId` + 时间戳。**无体重，无绝育状态。**

**后果：** FR-109 明写「缺少任一输入时不触发，**不做兜底猜测**」→ 体重字段不加则 **FR-109 恒 100% 不触发**；FR-107 退化为按物种硬过滤（有降级路径，可活）。而复购引擎是 §1 与 N-1 共同认定的版本存在理由。

**出口：** 排入本版本 story——`pet_profiles` 加体重列 + 建档/编辑表单加字段 + 存量用户回填引导（FR-107 的「补全档案，推荐更准」引导卡正是入口，但字段须先有）。绝育状态若 FR-107 需按其过滤则一并加。PRD 正文原写体重「V1.0.0 FR-11 **已有**」，已于 §3.9「前置数据资产」修正。

### L-10 · `HealthRecord` 无周期/到期字段（高，属跨版本依赖）

**代码事实：** `HealthRecordType` 已含 `VACCINE` / `DEWORM`，FR-108「仅驱虫疫苗参与触发」的**类型假设成立** ✅。但 `profile/domain/HealthRecord.java` **仅有 `eventDate`，无 `next_due_date`、无 `interval`**。

**PRD 要求：** FR-108 数据源写为「FR-45A 结构化健康记录 **+ 1.2.0 健康提醒的间隔配置**」——**后半截在当前代码中不存在**（健康提醒排在 Roadmap 1.2.0）。

**出口：** ✅ **已闭合 —— 2026-08-15 拍板方案 (a)，见 C-11。** **本版本不补该字段，FR-108 整体挪 Roadmap 1.2.0**；`health_records` 零 schema 改动。

⚠️ **闭合方式是「移出范围」而非「补齐能力」，代价必须被排期看见：** 复购引擎由三条机制降为 **FR-107 + FR-109 两条**，冗余归零。FR-107 的前置（L-9 体重字段）在本版本 story 内可控；~~**FR-109 的前置（DEP-6 每日建议喂量数据，Rendy）不可控**~~ → ✅ **2026-08-17 DEP-6 已解除**（喂量数据印在包装上，录商品时照抄），FR-109 前置已全部可控。若 DEP-6 未到位，FR-109 按「缺输入不触发」恒不触发，复购引擎实际只剩 FR-107 的规则式过滤——**正是 N-1 与 PRD §1 共同警告的失败形态**。**DEP-6 已据此二次上调为最高。**

## 四、设计侧对业务前提的记录（非挑战，供追溯）

### N-1 · 复购引擎是本版本的存在理由，不是附加功能

`TailTopia-财务计划-2027年5月打平.md` §6 写明 Y1 只有两个胜负手且冗余仅约 13%：**月交易率**（基准假设 100%，达标需 ≥87%，Excel 台账仅假设 30%，原文称「全案最大缺口」）与 **ARPU**（基准 IDR 875k，达标需 ≥765k，调研食品口径仅 300k）。

寄养、洗护、问诊都是低频场景，撑不起「月月交易」。狗粮与驱虫是宠主唯一天然月月复购的品类——这是电商板块被提前的实际理由，也是 PRD §1 把复购引擎列为核心主线、把最小闭环列为交付基础的依据。

**排期取舍时应压缩最小闭环的可选项（如物流 API 深度对接），不应压缩复购引擎。**

### N-2 · 自营是三种模式里最压现金的一种

`TailTopia-变现模型-收费细则.md` §7 假设 D「自营电商进货押资金不拖垮跑道」至今未验证，其原文缓释措施正是「先抽佣/代采、控自营备货」。改为直接自营后，该缓释失效，需由商务与财务侧另行给出备货上限与周转纪律。**此项不属产品设计范围，本文档仅作记录以免遗漏。**

### N-3 · 问诊信任优先于电商转化

`TailTopia-战略决策快照.md`「靠什么赢」第一条是 AI 问诊与本地信任。FR-110 因此写成约束性需求：兽医不得推荐具体 SKU、不提供商品链接插入能力。该约束**优先于任何转化率优化**。
