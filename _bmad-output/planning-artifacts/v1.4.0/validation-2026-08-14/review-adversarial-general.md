# 对抗性评审 — V1.4.0 电商 PRD

评审对象：`_bmad-output/planning-artifacts/v1.4.0/PRD-v1.4.0.md`（用户端 FR-93~FR-110）与 `_bmad-output/planning-artifacts/v1.4.0/PRD-v1.4.0-后台.md`（后台模块 10–13 + 模块 6 扩展）。
配套输入 `decision-log.md` / `README.md` 仅作对照，不在评审范围内。README §4 已登记的 CODE-1~CODE-5 五处代码偏差不重复列出；下文若涉及其连带影响，均已注明增量部分。

---

- **FR-100A 规则 2 与规则 4 直接冲突，且冲突时的行为完全未定义。** 规则 2 写「PawCoin 余额不足以覆盖订单时，**余额优先全额抵扣**，差额由 QRIS 补足，不阻断下单」；规则 4 写「单笔订单的 PawCoin 支付金额设上限，建议 Rp 1.000.000」。当余额 1.5M、订单 1.2M 时，"全额抵扣"必然被上限截断，但 PRD 没有一句话说明此时是自动截断到上限、是拒绝下单、还是提示用户。这不是理论边界：AB-6D 把该上限做成了**可配置项**（"单笔订单 PawCoin 支付上限 / 建议默认 Rp 1.000.000"），而 PRD 与后台都没有对该配置设最小值校验或告警——运营把它调到 Rp 100.000，规则 2 的"全额抵扣"就在**每一单**上被截断，而结算页（规则 2「结算页需同时展示两段金额」）没有任何解释这个截断的文案位。爆炸点在支付前的最后一屏：用户看到余额 500k 却只被抵扣 100k，且找不到原因。

- **用户端全程没有"我不想用 PawCoin"的开关，与规则 1 的不可逆性叠加成陷阱。** FR-100A 规则 2 的抵扣是系统自动的（"余额优先全额抵扣"），FR-97 结算页的金额明细构成里没有 PawCoin 使用量的可调项，FR-100 也没有支付方式选择器（"不做真钱渠道选择器"）。同时规则 1 规定「PawCoin 支付的部分，退款只能退回 PawCoin，不提供「退回真钱」选项」，且「不因退货原因而变」。合起来：用户攒下的 Coin（主要来自 FR-43D 退款转入，PRD 自己说"多为零头金额"，本意是留着买 Rp 18k–30k 级的问诊）会在下第一单实物时被**强制吸干**，且退货也拿不回选择权。PawCoin 是不可提现不可转让的封闭币，剥夺使用时机的选择权比剥夺退现金选择权更伤——而后者 PRD 专门为它设计了规则 7 的溢价补偿，前者连提都没提。

- **FR-100A 规则 6 的第一句在合规方向上写反了，且措辞会被实现者读成授权。** 原文：「PawCoin **不可用于**支付 PPN 增值税**之外**的任何平台外部结算（本版本无此场景，此条为防御性声明）」。按字面，这句话把 PPN 排除在禁止范围外，即"PPN 可以用 PawCoin 支付"。而 PPN 是缴给印尼税务机关的、最典型的**平台外部现金结算**，恰恰是封闭币最不该触碰的一项——用无现金垫底的赠币（规则 7 溢价）去覆盖税款，等于用负债抵扣现金义务。这条与 DEP-8（"PPN 开票金额按商品零售价还是实付真钱"至今悬空）叠加，会让实现者在没有财务口径的情况下按字面写出一个把 Coin 计入 PPN 计税基数或抵扣基数的分支。一句"防御性声明"写反了防御方向，比不写更糟。

- **退货寄回的物流环节在两份 PRD 里整体缺失，而 FR-100A 规则 3 与 AB-12C 都依赖它算钱。** FR-100A 规则 3 与 AB-12C 用同样的措辞写「退货运费由用户承担时，**从退款金额中扣除后再退回**，不单独向用户发起收款」。但"退货运费"这个数从哪来：FR-99 只定义了**发货**方向的「配送方式 × 区域」固定运费表；退货寄回是用户自行下单快递、还是平台上门取件、寄到哪个地址、按什么标准计费，用户端（FR-104 只写"是否需退回实物"）与后台（AB-12A 只判"运费由谁承担"，AB-12B 只做质检）**没有任何一处定义**。AB-11C 的配置项里也没有"退货收货地址"。§4.2 退款状态机有 `待用户寄回 ──超时未寄回(7日)──→ 已关闭(终)` 这个状态，却没有告诉用户寄到哪里。这是最小可售闭环的必需环节，不在 §7 的排除清单里，也不在 DEP-1~8 里——是被静默省略的。

- **退货运费与免运费门槛在部分退款下没有任何分摊规则，构成可复现的套利路径。** FR-97 定义了「免运费抵扣 | 商品小计 ≥ 运营配置门槛时减免运费，展示为负数行」，AB-11C 定义该门槛"全局单值"。FR-105 写「部分退款按 `实退金额 × 订单固化的支付比例` 执行；运费是否退回按 FR-104 的运费归属规则判定」。三份规则都是**整单口径**，没有一条说明：用户凑单到 300k 触发免运费，收货后退掉 250k（非质量问题，未拆封）只留 50k——平台已实付承运商运费，此时是否向用户回收该运费？FR-105 与 AB-12C 都只说"从退款金额中扣除退货运费"，不涉及**发货运费的追回**。同理，一笔订单发生两次部分退货（一次质量问题运费由平台承担、一次非质量问题由用户承担）时，只有一份运费却要被两次判定争夺，PRD 没有定义按金额、按件数还是先到先得。这是电商最经典的凑单-退货口子，FR-97 / FR-104 / FR-105 / AB-12C 四处均未覆盖。

- **AB-13D 的对账口径对"溢价 Coin"是错的，会把无现金垫底的负债当成有垫底的预收款核销。** AB-13D 写「PawCoin 是**此前已收现金的预收款核销**」。这句话对充值来的 Coin 成立，对规则 7 与 AB-6A 发放的**两类溢价 Coin 不成立**——AB-6C 自己在同一份文档里明写「两类溢价发放都是"凭空新增的 PawCoin"…**不像充值那样有等额现金流入垫底**」。当一笔溢价 Coin 被用来买一袋有真实进货成本的狗粮时，平台交付实物、支出现金、却在对账上被记为"预收款核销"，现金流入被虚增。要拆开就必须在钱包侧区分"充值币 / 赠币"的余额批次与核销顺序（先进先出？赠币优先？），但两份 PRD 与 AB-6D 的配置项里没有任何一处要求余额分层。AB-13A 又在**发放时点**把补偿溢价「计入毛利扣减」，AB-13D 在**核销时点**再按预收款处理——两个时点各记一次且口径不一致，月度毛利与现金流对不上时无从追溯。

- **规则 7 的反刷单论证不成立，且没有任何频次风控。** FR-100A 规则 7 的"后果"里写「刷单风险可控：…且为拿一笔小额 Coin 溢价而走完整退货流程，成本远高于收益」。这个论证依赖"小额"，但 OQ-34 给的上限是 **Rp 50.000**——约等于两次 AI 问诊解锁的价格，在客单 Rp 285.000 的语境下不是小额。同时触发条件是「退货类型 = 质量问题（破损/临期/错发）」，凭据是「上传凭证图 ≤6 张」+ CS 主观判定；宠物食品的"包装破损"是所有品类里最容易制造和最难证伪的一种。AB-12D 判例库的目标是"让主观判定随时间收敛一致"，是一致性工具，**不是风控**。两份 PRD 里没有任何一条限制同一用户/同一收货地址/同一支付账号的质量问题退货频次、没有溢价累计上限、没有异常用户名单。AB-13A 只要求"售后成本需可按退货类型下钻"，是事后报表不是拦截。

- **`已发货` 是一个用户无操作、系统无自动出口的准死锁状态。** FR-102 表里 `已发货` 的"用户可执行操作"只有「查看物流」，§4.1 图中它只有一条出边指向 `已送达`；而 `已送达` 的进入条件是「承运商标记送达 **或** 后台标记」，AB-11B 又明说「**首版不接承运商 API**…因此「已送达」状态需后台手动标记或依赖用户确认收货」。于是自动通路实际不存在，`已发货 → 已送达` 100% 依赖运营手工点击。运营漏点一单，该订单永久停在 `已发货`：FR-102 的「送达后 7 日自动确认」计时器永不启动，`已完成` 永不到达，FR-106 评价入口永不出现，FR-109 依赖"最近一次 Makanan 购买"的粮量预估基准日也随之失真。AB-11B 给出的兜底是「后台需在待办中列出「已发货超过 N 日未确认收货」的订单供运营跟进」——把一个系统性死锁降级成了人工待办清单。丢件、承运商长期不更新、用户搬家想拦截这三种在途异常，用户端**没有任何入口**。

- **两张状态机的接缝处漏了"退款被驳回"的回边，FR-102「无悬空态」这句话按图论为假。** §4.2 退款状态机有两个 `已驳回(终)`（CS 审核驳回、质检不通过驳回）与一个 `已关闭(终)`（超时未寄回），但 §4.1 订单状态机中 `退款中` **只有一条出边指向 `已退款(终)`**。退货被驳回后订单该回到 `已送达` 还是 `已完成`、7 日退货窗口是否重新计算、能否二次申请，两份 PRD 都没写。FR-102 的"后果"却断言「**终态为 `已完成` / `已取消` / `已退款` 三个，无悬空态**」——按现有两张图，被驳回的订单恰恰就是悬空态。AB-12C 又要求「退款执行状态需与订单状态联动，不允许出现「订单已退款但退款单未完成」的不一致」，而反方向（退款单已驳回但订单仍在 `退款中`）没有任何约束。

- **"签收"在系统中不是一个存在的事件，但退货窗口的起点挂在它上面。** §4.1 的说明写「`已送达` → `已完成` 的自动确认为 7 日。自动确认后仍保留 7 日退货窗口（**自签收起算**），两者不冲突」，FR-102 的 `已完成` 行也写「申请退货（**签收后** 7 日内）」，FR-104 的时限列三次写"签收后 7 日内"。但 FR-102 的状态定义里只有 `已送达`（承运商或后台标记）与 `已完成`（用户确认或自动确认），**全文没有任何地方定义"签收"这个事件或它的时间戳**。既然不接承运商 API（FR-103 / AB-11B），签收时间根本无从采集。结果是退货窗口的起算点在实现层不存在，只能被迫落成"以后台标记送达时间为准"——而后台标记时间取决于运营什么时候点，用户的 7 天权利长度由运营的手速决定。D-3/OQ-27 在讨论"7+7 是否过长"的时候，讨论的是一个起点未定义的区间。

- **拒收商品在流程上跳过质检，却在库存上无法入库，形成账实分离的黑洞。** §4.2 说明写「「待发货前取消」与「拒收」两类情形跳过 `待用户寄回` 与 `质检中`，由 `待CS审核` 批准后直接进入 `退款执行中`」，FR-104 表也写拒收「否（承运商原路退回）」。但拒收的是**已出库的实物**，它会在几天后真实回到仓库。AB-12B 规定「**只有质检通过的退货才进入可售库存**」，AB-10C 规定「库存增加**只能通过入库单**」且入库单必填字段为「采购单号 · 供应商 · SKU · 数量 · 进货单价 · 入库日期 · 操作人」——拒收退回的货既没有采购单号也没有进货单价，且流程上已经跳过了质检。这批货因此既无法入库、也没有被记为报损（AB-10C 的报损需"填原因与操作人"，但没有触发点）。钱已退、货已回、系统里不存在，是账实分离的直接来源，也会污染 AB-13C 的"库存金额按进货价计算，是资金占用的直接读数"。

- **库存状态机 §4.3 缺三条必然发生的通路。** 图中只有 `可售→锁定→已扣减` 与 `锁定→可售`，加一条注释里的"退货质检通过后入库"。缺失：(a) **`已扣减 → 可售` 的回退**——AB-11D 写「缺货无法履约时，运营可发起整单取消或部分取消」，库存在支付成功时已扣减，取消后货必须回到可售，图上没有这条边；顺带这句话本身暴露了 PRD 未承认的前提：**系统库存与实物库存会脱节**（否则"已扣减库存的订单缺货"不可能发生）。(b) **报损与盘点调整**——AB-10C 明列这是库存减少的两条合法途径，§4.3 里完全没有，也没有任何约束禁止把实际库存调到低于当前锁定量（这才是超卖的真实来源）。(c) **下架时锁定库存的归属**——AB-10D 只处理了购物车（"转为失效商品"），没处理已进入 `待支付` 的订单所锁定的库存。

- **超卖处置在两份 PRD 之间自相矛盾，且后台只给了视图没给动作。** FR-95 断言「**库存扣减必须由服务端原子操作完成**…失败方返回明确的「已售罄」错误而非静默失败」；AB-11D 却写「超卖发生时（并发下单击穿库存）后台需有明确的异常订单视图；用户端已通过服务端原子扣减防护（FR-95），此视图是兜底而非主路径」。如果原子扣减在提交订单锁定这一步就生效，并发路径上的超卖不可能发生——真正会超卖的是上一条提到的盘点/报损/退货入库撤销，而 PRD 把它归因成了并发。更要命的是 AB-11D 只定义了"视图"，**没有定义任何处置动作**：哪一单被取消、按什么顺序（先到先得？大额优先？）、如何通知、是否补偿、库存回补到哪里，全部空白。CS 拿到这个视图之后无章可循。

- **锁定库存可被无成本占用 60 分钟，PRD 只论证了"别误杀"没论证"防滥用"。** FR-95 规定提交订单即"可售 → 锁定"，FR-100 规定「**待支付超时 = 60 分钟**」并论证「此值明显长于兽医咨询的限时支付窗口，因为实物购买的决策与支付节奏不同，沿用短窗口会造成大量误失效订单」。这个论证只覆盖了误杀方向。在 SKU 上限 30（C-7）、自营备货受现金约束（N-2）的前提下，单个账号或脚本反复提交不支付即可把爆款 SKU 的全部可售库存锁死 60 分钟并无限续期。两份 PRD 没有任何"同用户并发待支付订单数上限 / 单 SKU 单用户锁定量上限 / 连续超时取消后的冷却"约束，AB-11D 的异常视图也不覆盖此场景（这不是超卖）。爆炸点是上线首周的爆款断供，且 `out_of_stock_viewed` 埋点会把它记成真实缺货需求。

- **部分发货与"包裹"概念整体缺失，而多 SKU 订单在自营下是常态。** FR-102 的状态机是整单级的单一状态，AB-11A 列表字段的"物流单号"是单数，AB-11B 的发货操作是「选择承运商 + 录入物流单号 + 确认发货」的一次性动作。但 FR-96 购物车是多 SKU 的，FR-99 的两档配送在物理上必然分包（7.5kg 狗粮走同城骑手件 + 一盒驱虫药，不可能同一单号），AB-11D 又明确存在「**部分取消**」。部分发货后订单是什么状态？部分取消后是 `退款中` 还是 `待发货`？多个单号在 FR-103 的"展示单号、承运商名、复制按钮"里如何呈现？"送达"以哪个包裹为准、7 日自动确认以哪个为起点？两份 PRD 一个字都没有。这不在 §7 的排除清单里——被排除的只是"承运商 API 实时轨迹"，不是"一单多包"。

- **当日达的适用范围判定依赖一个从未定义的对象：平台仓库地址。** FR-99 的配送方式表写当日达适用范围为「服务范围内的**同城 Kecamatan**」。"同城"是相对发货地而言的，而**发货地/仓库地址在用户端与后台两份 PRD 里从未出现**：AB-11C 只配置"服务范围"与"配送方式 × 区域"运费表，没有仓库主数据；AB-10C 的入库单也没有仓库字段。没有发货地，结算页无法判定当日达是否可选，AB-11B 的承运商下拉与配送方式的"联动"也无从计算。首发只有一个仓时这一项可以硬编码，但 PRD 连"首版单仓"这个前提都没有写下来，架构侧会被迫自己发明。

- **FR-98 的地址字段在两处存在会直接导致面单被承运商拒收的模糊定义，且行政区划数据源无归属。** 手机号写「印尼格式，**+62 前缀，8–13 位**」——8–13 位是含 +62 还是不含、是否允许前导 0、与既有账号手机号（FR-98 明写"不与账号手机号互通"）用不用同一套校验，全部未定义；印尼手机号去 0 后常见为 9–12 位，8 位会放进大量无效号码。邮编写「5 位数字」正确，但没有任何一条要求邮编与所选 Kecamatan 的一致性校验——固定运费表按 Kecamatan 计费、承运商按邮编派送，两者不一致时无人拦截，差额直接落在 A-19 假设上。更根本的是三级级联（Provinsi / Kota-Kabupaten / Kecamatan）的**数据来源从未指定**：是内置静态表、第三方 API、还是 Kemendagri 码表？印尼有 7,000+ 个 Kecamatan 且行政区划持续调整；AB-11C 说"服务范围按 Kecamatan 粒度配置，**支持批量导入**"，导入的主键是什么码表也没说。这是一个必须在架构前定死的外部数据依赖，DEP-1~DEP-8 里没有一条覆盖它。

- **A-19 的验证方式在系统里无数据可用，因为承运成本从未被要求录入。** A-19 假设「固定运费表…不产生显著亏损或超收」，验证方式写「上线后按月核对**实际承运成本**与**收取运费**的差额」。但：收取运费在三种情形下是三个不同的数（正常收取 / FR-97 免运费抵扣为 0 / FR-100A 规则 3 被 PawCoin 抵扣，收的不是现金）；而实际承运成本**根本没有录入口**——AB-11B 的发货操作只录承运商和单号，不录运费实付金额，AB-10C 的入库单只覆盖采购成本。AB-13A 的指标清单是「GMV · 订单数 · 客单价 · 商品成本合计 · 毛利额与毛利率 · 退款额 · 净销售额」，**没有"运费收入"也没有"承运成本"**。AB-13D 只要求拆"被 PawCoin 抵扣的运费"。结论：A-19 声明的验证方式不可执行，而它承接的是 FR-99"省掉一整条 API 对接工期"的全部风险。

- **FR-109 的计算公式在三种主流场景下会给出确定错误的结果，而 PRD 的降级策略拦不住。** 公式为 `预计可用天数 = SKU 净含量(克) ÷ 日喂量`、`预计耗尽日 = 上次购买日 + 预计可用天数`。(a) **购买数量被完全忽略**——净含量是 SKU 级属性，公式里没有 × qty，用户囤三包 7.5kg 会在第 1 包吃完时收到补货提醒；囤货是宠粮最主流的购买行为，不是边缘情况。(b) **起算点用的是"上次购买日"而非收货日**——待支付 60 分钟 + 标准快递 2–4 日（FR-99），在只有 7 天提前量（"耗尽日前 7 天开始…展示补货卡"）的窗口里，这是一半以上的误差。(c) 多宠物共食一袋时日喂量应为同物种宠物之和，公式按单只算。PRD 的兜底是「缺少任一输入时不触发，**不做兜底猜测**」——但这三种情况**输入全部齐全，只是算错**，降级策略完全拦不住。文案「diperkirakan habis ~5 hari lagi」被 PRD 定位为"给出估算依据而非断言"，可当实际还剩 20 天时，这条推送在一个以信任为护城河的产品里是负资产。

- **FR-108 的疫苗分支在结构上不可能产生电商转化，却被计入 AB-13B 的生死判据分母。** FR-108 写「**仅限驱虫、疫苗两类**」参与触发，紧接着又写「**疫苗触发的是「预约问诊/线下接种」而非直接卖疫苗**…该触发卡跳转健康模块而非商品详情」。即疫苗类触发卡的转化率**结构上恒为 0**（它根本不通向商品）。而 AB-13B 的指标表按 `trigger_type`（驱虫/疫苗/粮量）统计"复购触发卡点击率"，并把「**触发卡转化率 vs 普通商品曝光转化率**」列为「判定 A-16 成立与否的直接依据」。把一个不可能转化的类型混进分母，会系统性地压低复购引擎的实测转化率——而 A-16 写明「若触发卡点击率不显著高于普通商品曝光，则本版本的核心论证不成立」。两份 PRD 没有一处要求在转化口径中剔除疫苗类。用一个自己制造的偏差去判本版本的生死。

- **复购引擎有一个未被承认的冷启动期，而 A-16 的验证恰好落在这个窗口内。** 三条机制的触发前置条件叠加后：FR-107 需要档案；FR-108 需要用户手动录过结构化健康记录**且**有周期配置；FR-109 需要「电商订单历史（最近一次 Makanan 购买）∧ 商品配了日喂量（DEP-6 未交付）∧ 档案体重」三者同时成立。其中 FR-109 的第一个条件在上线首月对**全体用户恒为假**——没有人有电商购买历史。也就是说上线初期"复购引擎"实际只剩 FR-107 一条规则式静态筛选在跑。PRD §1 宣称「目标 2 是版本存在的意义」，A-16 的验证方式是"上线后看 `repurchase_card_clicked` 与整体转化对比"——在冷启动期采到的数据必然低估复购引擎，并可能导致错误的 kill 决策。两份 PRD 没有一处承认存在冷启动期，也没有为它设计替代触发（例如按品种/年龄的通用周期先兜底）。这与 README §4 已登记的 CODE-2/CODE-3 是不同层面的问题：那两条讲字段不存在，这条讲即便字段全有、覆盖率仍不足以支撑 A-16 的判定。

- **复购卡的频控与位次竞争只做了一半。** FR-108 有频控（「同一宠物同一健康事件类型的复购触发卡 30 日内最多出现一次」），FR-109 只有一句「耗尽日前 7 天开始…展示补货卡，**并推送一次**」——"一次"是每个耗尽周期一次还是永久一次？用户不买时这张卡在 7 天里是否持续挂在首页？FR-107 的档案推荐区完全没有频控。而 FR-93 区域 ① 明确「复购触发卡…**最多 2 张**」：当驱虫到期 + 两个 SKU 同时粮量见底时是三张卡抢两个位，**PRD 没有定义任何优先级**。另外 decision-log D-5 已拍板「复购触发卡与 1.2.0 健康提醒**合并为一条推送**」，但 FR-108 正文仍写「**除既有提醒外，额外**在两处生成复购触发卡…健康提醒推送内附商品直达」——PRD 与已拍板决策的措辞不一致，照 PRD 实现就是两条推送。

- **AB-12C 与 AB-6A（扩展）在同一份后台 PRD 内对"溢价配置是否复用"给出相反指令。** AB-12C 的"复用既有机制"第一行写「PawCoin 退款溢价比例**复用 AB-6A** 配置」；§6"既有模块的扩展"表里写 AB-6A「**直接复用**于电商退款转 PawCoin」；而 AB-6A（扩展）写「**两条溢价必须是两个独立配置项，不可复用同一个数值。** 触发条件与目的完全不同，共用会导致调其一误伤其二」。三处措辞里有两处会把实现者引向单一比例。这条被 decision-log C-9 与 D-8 列为强制约束（"必须与 AB-6A 既有激励溢价分开取值"），用户端 FR-105 也用加粗警告重申过——但真正会被拿去写代码的是后台 PRD 的模块 12 章节，而那一行写的是"复用"。一旦写成单值，AB-13A 的售后成本口径与 AB-6C 的浮存归因跟着一起错，且是静默错误。

- **AB-13B 被称为"本版本最该盯的看板"，但它的每一个指标都算不出来——埋点缺归因字段与预估值。** §5 的 13 个事件里，`order_submitted` 的属性只有 `order_id, amount, shipping_method`，`payment_succeeded` 只有 `order_id, amount, channel`——**没有 `trigger_type`、没有 `entry_source`、没有 sku 级信息**。因此"从复购触发卡点进来最终下单"这条归因链在数据上无法闭合，AB-13B 的「触发卡转化率 vs 普通商品曝光转化率」直接不可计算。"粮量预估准确度（预估耗尽日与实际再购日的偏差分布）"需要把每次预估的 `predicted_depletion_date` 落进事件，§5 没有任何事件承载它。`profile_reco_clicked` 有 `reco_reason`，但分母"推荐区曝光"只能靠通用的 `product_impression`（zone 枚举含"精选"），口径能否对上未说明。此外缺 `cart_viewed`（购物车到结算的漏斗断了一节）与超服务范围阻断事件——FR-97/FR-99 的地址阻断是结算页最大的确定性流失点，README 说 17 屏里专门画了"结算页超服务范围"，却没有对应埋点，流失量永远不可知。

- **AB-13B 与 AB-13A/13C/13D 分别建在两套互不相通的数据源上，PRD 没有说它们如何合并进同一个后台。** AB-13B 的全部指标来自 §5 的 PostHog 事件（`repurchase_card_impression` / `_clicked` / `profile_reco_clicked`），AB-13C 的"缺货损失"也直接写成「（`out_of_stock_viewed` 事件量）」；而 AB-13A / AB-13D 的 GMV、毛利、对账来自业务库。PostHog 是第三方 SaaS，后台要么反向拉 PostHog API、要么补一套服务端埋点——两份 PRD 都没有提出这个要求，也没有列为依赖。同时 §5 的客户端事件天然带丢失率与广告拦截偏差，把它当作**对账级看板**的口径（AB-13C 的缺货损失会影响补货决策）而不加说明，是把分析口径当财务口径用。

- **FR-107 依赖一个后台从未提供的配置项：年龄段阈值。** FR-107 推荐逻辑步骤 2 写「按 `适用年龄段` 匹配档案年龄（幼年 <1 岁 / 成年 1–7 岁 / 老年 >7 岁，**犬猫阈值可后台配置**）」。翻遍后台 PRD 模块 10–13：AB-10A 只说"适用物种/体型/年龄段三字段决定 FR-107 档案推荐的过滤结果"，AB-10D 只有精选权重（0–100）与 SKU 上限告警，AB-11C 是服务范围与运费，**没有任何一处提供年龄段阈值的配置界面**。同类问题还有：FR-102 的"待支付超时 60 分钟"、"送达后 7 日自动确认"、FR-104 的"签收后 7 日退货窗口"、FR-108 的"30 日频控"、FR-109 的"耗尽日前 7 天"——这六个时间常量全部硬编码在用户端 PRD 里，后台没有一个对应配置项。而 OQ-27 正在讨论 7+7 是否过长、D-3 的结论是"保持"——一旦要改就得发版，这与 AB-6D「总开关…出问题时的一键回退，**不需发版**」体现的运营预期完全不一致。

- **AB-6D 定义了三个开关，用户端对其中两个的关闭态没有任何行为定义。** AB-6D 的配置项含「电商 PawCoin 支付总开关」与「是否允许 PawCoin 抵扣运费」。用户端 FR-100A 只有规则 5 处理了一种停用情形——那是 **AB-6C 充值暂停**（"暂停的是充值入口，不是消费出口…仅「余额不足 → 去充值」的引导按钮置为不可用"），**不是 AB-6D 的总开关**。总开关关闭时结算页的 PawCoin 区是消失还是置灰、已有余额的用户看到什么解释、FR-97 的金额明细是否回退成单段，全部空白。更尖锐的是 AB-6D 自己写「**配置变更不追溯已成立的订单**：已进入待支付的订单按下单时的规则执行」——而总开关的设计用途恰恰是"Coin 扣减链路出 bug 时一键回退"，那批"按下单时规则执行"的待支付订单仍会走进出了 bug 的扣减链路。开关管不到它被设计出来要救的那批订单。"是否允许抵扣运费 = 否"时同理：会出现用户 Coin 余额充足、却仍需 QRIS 单独支付 Rp 20.000 运费的组合，FR-97 与 FR-100A 规则 2 的"两段金额展示"都没有描述这种形态。

- **"30" 这个上限在两份 PRD 之间口径不一致，差三倍，而三项设计决策挂在它上面。** 用户端 OQ-25 写「**首批 SKU 数量上限**…上限锁 **30**（后台 AB-10D 超限告警）」并声明「这一确认同时坐实了三处依赖它的设计：规则式推荐（FR-107）、固定运费表（FR-99）、不做全站搜索（FR-93）」。后台 AB-10D 写「当**在售商品的 SKU 总数**超过配置上限（建议 30…）时…展示告警条」，而后台 OQ-30 又写「**SKU 上限 20–30**、供应商数量有限」。但 §2 术语表明确区分「商品（Produk）」与「规格/SKU（Varian）」，并举例一个商品含 3 个 SKU。30 个商品和 30 个 SKU 相差 3 倍——按后者，货架上只有约 10 个商品，四个品类各 2–3 个，"不做搜索"毫无疑问成立但精选流几乎无内容；按前者可到 90+ SKU，FR-93 的无搜索四分类流开始吃力。这个数同时是 C-7 的拍板结论、AB-10D 的告警阈值、和三项设计的论据，却没有统一口径。

- **AB-10D 的 SKU 上限只是一条告警条，与它自称的"做成产品约束"不符。** 原文：「后台顶部展示告警条。**这是把「精选不做货架」的战略边界做成产品约束**，而不是只写在文档里」。告警条不阻断任何操作、不需要审批、没有二次确认（对比 §7 权限里"库存报损、盘点调整、零售价低于进货价保存三类操作需二级确认"——那三个比 SKU 数量温和得多的动作反而有硬约束）。运营无视告警把 SKU 录到 200，FR-93 的"不提供全站搜索框"会立刻变成不可用的产品，而 PRD 里**没有任何触发点**要求产品重新评估 FR-93/FR-99/FR-107 三项决策。战略边界写成了一条可以一路点掉的黄条。

- **订单号规则违反仓库的强制护栏，且 PRD 把它写成了优点。** FR-102 写「订单号规则：`TT` + `YYYYMMDD` + **8 位自增**。与既有虚拟商品订单号规则隔离，便于对账区分自营实物与虚拟商品收入」。项目 CLAUDE.md 的强制护栏写明「对外暴露标识一律**不可枚举 token**，不用自增 id 直接外露」。`TT` + 日期 + 自增序列是教科书式的可枚举标识：任何用户从自己的订单号即可推断平台当日单量与累计单量（对一个还在验证 A-15"宠主是否愿意在 TailTopia 买粮"的产品，这是直接泄露最敏感的经营数据），且可枚举遍历他人订单号去探测接口。8 位自增是全局递增还是按日重置也没写——按日重置时可枚举性更强。对账区分的诉求用一个不可枚举 token + 独立的内部序列同样可以满足，不需要把序号外露。

- **本版本第一次建立 PII 数据集，两份 PRD 与依赖清单里没有一条涉及个人数据保护。** FR-98 引入收货人姓名、手机号、精确到门牌的详细地址，并明确「**手机号是履约联系方式，不与账号手机号互通**」——等于新建了一份与账号体系分离的个人数据集。后台 AB-11A 的**列表字段**直接包含「收货人/电话」，筛选支持「订单号/收货人/**电话** 关键词」，AB-11A 的详情「展示完整收货地址（含 Provinsi/Kota/Kecamatan/详细地址/邮编）」。而 §7 权限只为「进货价与毛利数据」单列权限位（理由是"采购成本是商业敏感信息"），对收货地址与手机号**没有任何脱敏、访问控制或访问审计要求**——一个能按手机号模糊搜全站订单的后台列表，对全体模块 11 运营开放。CLAUDE.md 的护栏写明日志"严禁记录 PII"，但 PRD 层面连产品行为都没有约束。DEP-3 关注 NIB/KBLI/PPN、DEP-7 关注 uang elektronik，**DEP-1~DEP-8 里没有一条涉及印尼 UU PDP 个人数据保护法**，而这是本版本第一次大规模采集地址与第二手机号。

- **发票/收据在用户端与后台都不存在，而 DEP-3 把开票列为"阻塞上线"。** DEP-3 原文：「经营范围合规：…**PPN 增值税登记与开票**」，阻塞程度「**高**，阻塞上线」。但用户端 FR-93~FR-110 里**没有任何一条 FR** 描述用户如何取得收据或发票；FR-97 结算页的金额明细构成只有「商品小计 / 运费 / 免运费抵扣 / 应付合计」——**没有税额行**，也没有说明零售价是否含税；FR-102 的订单详情没有票据入口；后台模块 10–13 里没有开票模块，AB-13D 只是对账导出（且其导出字段本身还是 OQ-32 未决项）。退款/部分退款后的票据冲红更是完全空白。一个被自己标注为"阻塞上线"的能力，在两份 PRD 中既没有需求也没有被 §7 排除——它只是没写。

- **「开封不退」被要求在三处明示，但其中两处在 PRD 里没有承载位。** FR-104 写该规则「须在**商品详情页、结算页、退货申请页三处**明示，不能只写在规则页里」。但 FR-97 定义的结算页结构是「收货地址 → 商品清单 → 配送方式 → 支付方式 → 金额明细 → 提交按钮」——**没有退换货规则的展示位**；退货申请页在 FR-104 里只定义了"上传凭证图 ≤6 张"，没有规则展示。更麻烦的是 FR-94A 明写「同一商品的不同规格可有**不同退换货标识**」而 AB-10A 又把默认值设为「**开封不退**」：用户在详情页选 1.5kg（可退可换）看到一套规则，切到 7.5kg（开封不退）时是否刷新提示？多 SKU 订单在结算页出现三种不同标识时如何在一处呈现？两份 PRD 都没有回答。A-18 假设「用户接受「开封不退」规则，不因此产生大量客诉」，而承载这条假设的全部执行细节缺失。

- **已下架 SKU 的退货入库会产生不可售的沉淀库存，且滞销预警是否覆盖它未定义。** AB-10D 写下架商品「用户端不再出现在任何列表与推荐中」，AB-12B 写「**只有质检通过的退货才进入可售库存**，且入库时需标记为退货入库批次」。当一个 SKU 在用户退货途中被下架（缺货断供、供应商换货、临期清理，都是自营的日常），质检通过后这批货会进入一个**已下架商品的可售库存**——永远卖不出去，但按 AB-13C「库存金额按进货价计算，是资金占用的直接读数」仍然占着资金。AB-13C 的滞销预警口径是"超过配置天数无销售"，下架商品必然满足该条件，是会被刷屏预警还是被排除在扫描外，PRD 没说；给出的建议动作「降价清货 / 停止补货 / 下架」对一个已下架的 SKU 全部无效。

- **注销用户与在途实物订单/PawCoin 余额的交叉，两份 PRD 零涉及。** 项目 CLAUDE.md 把注销的「级联删除/匿名化」（story 7.3，按 D1/D2 落实）列为三类安全攸关节点之一。本版本第一次让注销动作可能撞上：一个 `已发货` 的实物订单（收货人姓名/电话/地址是履约必需，删不得）、一笔待退款的 PawCoin（不可提现、不可转让，删了等于没收）、一个待质检的退货包裹。两份 PRD 没有任何一条说明注销时这些对象如何处理，FR-98 的地址簿也没有说明它是否随注销匿名化（它是履约凭证还是个人数据？两种定性导出相反的处置）。这不是电商的边缘场景——它是把一个已存在的安全攸关约束和一批新建的实物对象放在一起时必然出现的冲突，而没有任何一方承接。

- **FR 交叉引用有三处指向错误的需求编号，且都出现在会被直接照着实现的位置。** ① FR-93 的首页区域表写「② 为我的宠物精选 | 「Pilihan buat {宠物名}」，**按档案推荐（FR-108）**」——档案推荐是 **FR-107**，FR-108 是健康记录触发复购。FR-93 是整个 Toko 首页的定义，实现者按它去查 FR-108 会做出一个错误的区域 ②。② FR-94 商品字段表写「每日建议喂量 …**FR-110** 粮量见底预估的计算依据」——粮量见底预估是 **FR-109**，FR-110 是"兽医不得推荐 SKU"的约束性需求。③ §2 术语表写「**复购触发卡** …由结构化健康记录周期或粮量见底预估驱动（**FR-109/FR-110**）」——应为 FR-108/FR-109。三处错误都把指针挪到了 FR-110 这条**约束性需求**上，而 FR-110 恰恰是 N-3 认定优先于一切转化优化的护城河条款；把它当成功能条款引用，是最不该出现的错位。

- **FR-100A 被跨文档一致地称为"六条"，规则 7 在回写清单里被系统性漏掉。** FR-100A 实际下辖规则 1~7，但用户端 §6 跨文档影响表写「并写入 FR-100A 的**六条**使用规则」、OQ-26 写「规则见 **FR-100A** **六条**：防套现 / 混合支付与按比例退款 / 运费 / 单笔上限 / 浮存门槛联动 / 不参与场景」——枚举里没有规则 7；decision-log L-4 也写「引用 FR-100A **六条**使用规则」。规则 7（平台责任补偿溢价）是本版本最新、争议最大、直接涉及资金发放的一条，恰恰是 §6 要求回写到 `FR-50C` PawCoin 消费范围的那份清单里唯一被漏掉的。执行 §6 的人会把六条抄进 FR-50C，把发钱的那一条留在电商 PRD 里。

- **FR-106 的评价与订单终态、内容审核降级两条链都没有闭合。** FR-102 允许 `已完成` 的订单在"签收后 7 日内"申请退货，FR-106 允许 `已完成` 后评价——用户 5 星好评后成功退货并进入 `已退款`，这条评价是否保留、是否标注"该用户已退货"，PRD 没说；反向地，退货被驳回后能否再评价也没说（承接前述状态机回边缺失）。另外 FR-106 写「**复用既有内容审核机制**：评价提交时走三方同步过滤，命中高风险即拦截不发布」——三方服务超时或不可用时的降级完全未定义：是阻塞提交、是放行、还是转异步？PRD 明确排除了"先发布后审核"，等于把可用性风险全押在第三方同步调用上。评价含图 ≤6 张，图片是否也进审核范围同样未说明。
