## Overall verdict

这是一份**思考质量明显高于平均水平、但工程可用性尚未达标**的 PRD 集：它有真实的战略论点（复购引擎而非货架）、愿意为论点付出代价的约束（FR-110 禁止兽医荐货）、以及罕见的自我推翻记录（L-7 把「单笔上限=浮存阀门」判定为错误论证并连带改写三处）——theater 几乎为零，决策以决策的形式写出来而不是藏在「考量」里。

但它**不可直接交给下游拆 story**。三条硬伤：① 版本自称的存在理由（复购引擎）建立在三个数据输入上，其中两个在代码中不存在（CODE-2 体重字段、CODE-3 到期间隔），且 PRD 正文完全没有承认这一点；② §4 三张状态机不穷尽——`已送达` 的进入条件依赖被 FR-103/AB-11B 明确排除的承运商 API，部分退款在订单状态机中无表达，退款执行失败与拒收路径没有边；③ 花了约 100 行把 PawCoin 混合支付的 7 条规则论证得极细，却漏掉了取整规则、用户是否可以选择不用 Coin、以及归因属性——而后者恰恰使 AB-13B 那个「判定版本成败的直接依据」在埋点 schema 上无法计算。

**结论：返工后可进入 bmad-ux / bmad-architecture，返工是「补」不是「重写」。** 必须闭合的最小集为：CODE-1（架构选型）、CODE-2/CODE-3（范围决策）、4 处交叉引用偏移、状态机三处缺边、埋点归因属性、混合支付取整规则。

## Decision-readiness — adequate

决策以决策形式出现，且带日期与承担者：FR-100A 规则 1「不提供退回真钱选项」、规则 7「补偿走 Coin 侧溢价，不开退现金的口子（2026-08-10）」、FR-97「首版不含优惠券……不预留会员价字段，避免为暂缓功能提前埋成本」。取舍写明了**放弃了什么**而不只是选了什么：FR-99 用固定运费表换掉「一整条 API 对接工期」、FR-103 承认轨迹渲染的体验增量「在同城当日达场景下有限」。§1「范围性质说明」直接给出排期取舍的优先级方向（压缩目标 1，不压缩目标 2），这是决策者真正能用的东西。L-7 的自我更正尤其加分——一份敢于在文档里写「原文误将其论证为浮存的前置阀门」并连带推翻三处结论的 PRD，其余论证的可信度也随之提高。

扣分主要来自三处：**最该被拍板的事没有出现在待拍板表里**。FR-108 的数据源写作「FR-45A 结构化健康记录 + 1.2.0 健康提醒的间隔配置」，后半截在代码中不存在，README §4③ 明确这是「(a) 依赖 1.2.0 先落地 / (b) 本版本自带周期默认值」的范围二选一、「不可由实现者临场决定」——但 PRD 把 FR-108 写成一条已定型的功能，§9 OQ 表里没有它。反观 OQ-27/28/29 三条，「现状建议」栏里都直接给了答案（保持 / CS 判定 / 合并），责任方在 decision-log 里也都是「产品」自己，属于**等着盖章而非真正开放**的条目。结果是开放项表把三条伪开放项列了出来，把真正的范围分歧漏了。

其次是**没有目标值**。§1 三个目标全部是定性描述，§5 只有事件清单，AB-13B 只有指标口径，A-16 的判据是「若触发卡点击率不显著高于普通商品曝光」——「显著」没有数值、没有观察窗口、没有不达标时的处置（下一版继续投入还是收缩？）。对一个把版本存在意义押在单一机制上的 launch 级 PRD，缺 kill criteria 是硬伤。

### Findings

- **critical** CODE-3 · FR-108 的范围二选一未登记为待拍板项（§3.9 FR-108 / §9 / §8） — FR-108 数据源写为「FR-45A 结构化健康记录 **+ 1.2.0 健康提醒的间隔配置**」，后半截在当前代码中不存在（`HealthRecord.java` 仅有 `eventDate`，无 next_due_date / interval；健康提醒排在 Roadmap 1.2.0）。PRD 正文把 FR-108 写成已定型功能，§9 OQ 表与 §8 依赖表均未收录，决策者读 PRD 无从得知复购引擎三条机制里有一条悬空。*Fix:* 新增 OQ-35「FR-108 的到期判定间隔从哪来」，两个选项按 README §4③ 原样列出（(a) 依赖 1.2.0 先落地、本版本 FR-108 降级为不做；(b) 本版本自带犬猫驱虫/疫苗常规间隔默认表，作为 1.2.0 的前置资产），责任方=产品，阻塞=FR-108 定稿与 §3.9 版本论证；同时在 §8 加一条跨版本依赖行。
- **high** 版本没有成功指标目标值与 kill criteria（§1 / §5 / §10 A-16 / AB-13B） — §1 目标 2 称复购引擎是「版本存在的意义」，但全文没有任何一个数字门槛：A-16 的判据是「若触发卡点击率不**显著**高于普通商品曝光」，AB-13B 只给口径不给目标，§5 埋点只列事件。上线后没有任何一句话能裁决「复购引擎是否成立」。*Fix:* 在 §1 后增补一节 Success Metrics（建议给 SM-1 ~ SM-4 编号以便下游引用）：至少定义「触发卡→成单转化率 vs 全部精选区曝光→成单转化率的倍数门槛」「30 日复购率目标」「观察窗口（建议上线后 8 周）」以及不达标时的处置（收缩/继续/改机制），并把 A-16 的验证方式指向该 SM。
- **high** A-17 比 decision-log 更不诚实，掩盖了已失效的缓释措施（§10 A-17 vs decision-log N-2） — A-17「自营备货的资金占用不拖垮跑道」标致命度=中，验证方式写「承接变现模型假设 D，属财务侧，**不在本 PRD 验证**」。但 decision-log N-2 明确写：假设 D 的原文缓释措施是「先抽佣/代采、控自营备货」，「改为直接自营后，**该缓释失效**」。PRD 把一个「原有护栏已被本版本亲手拆掉」的假设写成了「照旧承接」。*Fix:* A-17 改写为承接 N-2 的原文：注明本版本的模式选择使原缓释措施失效，致命度上调，并在 §8 依赖表加一行「备货上限与周转纪律」（责任方=商务+财务），阻塞=首批采购。
- **medium** OQ-27 / OQ-28 / OQ-29 是伪开放项，无截止日与默认生效机制（§9） — 三条的「现状建议」栏即为答案，decision-log D-3/D-4/D-5 给的是同一答案，责任方均为产品自身。它们既不推动讨论，又抬高了开放项计数。*Fix:* 改为「默认生效」条目：写明「若 {日期} 前无异议，按现状建议执行」，或直接下沉为 FR 正文里的决定并从 OQ 表移除，把 OQ 表留给真正未决的 OQ-33/34 与新增的 FR-108 范围问题。
- **medium** DEP-7 若结论为否，降级路径未与已存在的开关关联（§8 DEP-7 / 后台 AB-6D） — DEP-7 标注「阻塞 PawCoin 购物上线（不阻塞电商本身）」，但 PRD 没有说清「不阻塞」在产品上如何实现。后台 AB-6D 的「电商 PawCoin 支付总开关」正是这个降级手段，两处却没有互相引用；且 AB-6D 把该开关的用途限定为「功能出故障时的一键回退」，未包含合规未决时的默认关闭。*Fix:* FR-100A 开头加一句「本节全部规则受 AB-6D 总开关控制；DEP-7 未回执前该开关默认关闭，电商按纯 QRIS 上线」，并在 AB-6D 说明栏补上这一用途。
- **medium** 承重常数「客单约 Rp 285.000」无出处（FR-100A 规则 4 / §9 OQ-33 / 后台 AB-6D / AB-6C） — 这个数字在四处被用来论证 Rp 1.000.000 上限「几乎不会触发」，是该决策唯一的支撑，但从未标注来源（推测来自变现模型/财务计划文档）。它一旦是估算值或口径不同（含运费？含 PPN？），整条论证随之松动。*Fix:* 首次出现处标注来源文档与口径（是否含运费/税），或降级措辞为「按变现模型估算的客单量级」。

## Substance over theater — strong

theater 含量极低，几乎每一段都在承担工作。没有 persona 章节（增量文档合理地把它留给 V1.0.0），没有可以平移到任何 PRD 的愿景段落，没有「系统必须可扩展/安全/可靠」式的 NFR 样板。差异化主张是具体的、可证伪的（「你的宠物档案说该买什么，不是你自己搜」），并且**用真实代价支撑**：FR-110 主动禁掉问诊侧的荐货变现，理由写明「其损失远大于电商的短期转化收益」；FR-93 主动砍掉搜索框，理由写明「搜索框会把产品心智推向通用货架」。这种「为论点付费」的写法是判断一份 PRD 有没有真实 thesis 的最好证据。

后台 PRD 同样扎实：AB-10B「进货价必填且不对用户端暴露……缺失进货价的 SKU 单独列为『成本未录』，**不静默按零成本计算利润**」、AB-10C「库存增加只能通过入库单，不提供直接编辑库存数字的入口」、AB-13A「补偿溢价须单列一行并计入毛利扣减——它虽以 PawCoin 形式发放、当期不流出现金，但会形成未来的兑付义务」。这些都是有人真的想过运营与财务会怎么被坑之后才写得出来的条款，不是模块清单。

但有一处 substance 的空心必须点名，而且它恰好落在版本的心脏上：**§3.9 复购引擎的论证是悬空的**。FR-107/108/109 三条机制依赖三个数据输入——档案体重、健康记录到期间隔、商品每日建议喂量。按 CODE-2，`PetProfile.java` 无体重、无绝育状态；按 CODE-3，`HealthRecord.java` 无 next_due_date/interval；每日建议喂量则依赖 DEP-6 尚未到位的供应商数据。也就是说，按当前代码上线：FR-109 因「缺少任一输入时不触发，不做兜底猜测」而**恒 100% 不触发**；FR-108 无到期判定源；FR-107 退化为「按物种硬过滤」，即「给狗的商品」——这与 §1 所警告的「只做完目标 1 等于做了一个更差的 Shopee」是同一种结果。PRD 正文对此一字未提，反而在 FR-107 数据源处写「V1.0.0 FR-11 已有」，把不存在的字段声明为既有资产。

另一处是 NFR 的**缺席**（不是 theater，是没有）：本版本首次引入收货地址（姓名/手机号/详细地址）、首次出现并发扣减、首次出现资金拆分，但两份文档没有任何性能边界、一致性保证级别、PII 留存与删除规则。项目 CLAUDE.md 把「注销级联删除/匿名化」列为三类安全攸关节点之一，§6 跨文档影响表却只登记了 Roadmap、FR-43、FR-54、FR-50C/D、埋点、图标六项，没有登记新增的地址/订单/物流/评价表需要纳入注销级联。

### Findings

- **critical** CODE-2 + CODE-3 · 复购引擎的三个数据输入两个不存在，版本论证悬空（§3.9 / FR-107 数据源 / FR-109 计算） — FR-107 数据源写「宠物档案（物种、品种、年龄、体重、绝育状态）— V1.0.0 FR-11 **已有**」，但 `PetProfile.java` 字段全集无体重、无绝育；FR-109 明写「缺少任一输入（无购买历史 / 商品未配日喂量 / 档案无体重）时不触发，**不做兜底猜测**」，字段不加即恒不触发。三条机制中 FR-109 归零、FR-108 无判定源、FR-107 退化为物种过滤，而 §1 与 decision-log N-1 都把复购引擎认定为「版本存在的意义」与财务月交易率缺口的答案。*Fix:* 在 §3.9 节首加一段「前置数据资产」，把三项输入逐条列出当前状态与补齐责任（体重+绝育字段=本版本 story；到期间隔=OQ-35 二选一；每日建议喂量=DEP-6），并把 FR-107 的「V1.0.0 FR-11 已有」改为「V1.0.0 FR-11 的档案模型 + 本版本新增体重/绝育字段」；同时在 §8 把 DEP-6 的阻塞面从「商品录入」上调为「FR-109 可用性」。
- **high** 首次引入 PII 与实物履约数据，未登记进注销级联删除/匿名化（§6 跨文档影响表 / FR-98） — FR-98 引入收件人姓名、手机号、详细地址、邮编，FR-101/103 引入订单与物流数据，FR-106 引入评价内容与图片。§6 表格未包含任何一行指向账号注销的数据生命周期处置，而该处置在本项目属安全攸关节点（CLAUDE.md 明列，对应基线 story 7.3 / 决策 D1/D2）。财务留存与用户删除权之间存在天然冲突（已完成订单需留存对账），PRD 未表态。*Fix:* §6 增加一行：新增表（收货地址簿 / 电商订单 / 订单地址快照 / 物流 / 评价 / 退货申请 + 凭证图）逐类标注注销时的处置（删除 / 匿名化 / 依法留存 N 年），冲突项（对账留存 vs 删除权）作为 OQ 登记，责任方=Legal。
- **medium** 差异化主张未给基线证据（§1 目标 2 / A-15 / A-16） — 「这是本版本区别于 Shopee/Tokopedia 的**唯一理由**」是全文最重的一句断言，但没有引用任何现有数据支撑其可行性：当前有多少比例的活跃用户建了档、档案里年龄/体重/健康记录的填写完整度是多少，全文未出现。若完整档案的用户只占个位数，复购引擎的可触达面从一开始就不成立，而这个数今天就能查。*Fix:* 在 A-16 的验证方式前置一条「上线前基线」：统计当前建档率与档案字段完整度，若低于阈值则 FR-107 的「补全档案，推荐更准」引导卡需从辅助位提升为主动运营动作。
- **low** FR-100A 规则 6 是全文唯一近似 furniture 的条目（§3.5 FR-100A 规则 6） — 该规则自述「本版本无此场景，此条为防御性声明」。保留防御性声明本身合理，但它同时把措辞写坏了（见 Done-ness clarity 中关于 PPN 的 high 项）。*Fix:* 与那条一并改写；若只是为 DEP-7 留痕，移入 §8 DEP-7 的说明栏而不占用 FR 编号下的规则位。

## Strategic coherence — adequate

thesis 清晰且贯穿：「把宠物档案转化为购买触发点」→ 由此推出不做搜索（FR-93）、SKU 上限 30（OQ-25/AB-10D）、规则式而非算法推荐（FR-107）、不做优惠券会员价（FR-97）、不开放三方入驻（§7）。这是一条自洽的收敛链，不是「一堆有人想要的能力」。MVP scope kind 也是自洽的 revenue + experience 混合体，§1 显式声明「目标 1 是交付基础，目标 2 是版本存在的意义」并给出取舍方向——这一句比大多数 PRD 的整节优先级论述更有用。后台 AB-13B 更直接点出判定依据：「触发卡转化率 vs 普通商品曝光转化率，二者对比是判定 A-16 成立与否的直接依据」。

问题在于**度量层接不住战略层**。AB-13B 指定的那个决定性对比，在 §5 的 13 个事件里算不出来：`repurchase_card_clicked` 带 `trigger_type` 与 `product_id`，但 `order_submitted` 只有 `order_id / amount / shipping_method`，`payment_succeeded` 只有 `order_id / amount / channel`——**下单侧完全没有归因属性**，且订单是多商品的，行级归因未定义。能算出的只有点击率，算不出转化率，而 A-16 的成败判据正是转化率对比。

其次是 **counter-metric 近乎为零**。13 个事件里只有 `out_of_stock_viewed`（缺货损失）与 `return_requested`（售后率）勉强算负向。本版本已知的四个自伤面——复购推送疲劳、被替换 Tab 的功能使用量下跌、FR-110 那条护城河被侵蚀、两类溢价的发放规模（A-21 自称「真正的浮存风险源」）——一个对应事件都没有。§5 只测量漏斗的上行方向。

### Findings

- **high** 判定版本成败的决定性指标在埋点 schema 上不可计算（§5 / 后台 AB-13B / §10 A-16） — AB-13B 把「触发卡转化率 vs 普通商品曝光转化率」列为判定 A-16 的直接依据，但 `order_submitted`（属性 `order_id, amount, shipping_method`）与 `payment_succeeded`（`order_id, amount, channel`）均无 `entry_source` / `trigger_type`，多商品订单也无行级归因。链路只到 `add_to_cart`（有 `entry_source`）为止。*Fix:* 给 `order_submitted` 增加行级数组属性 `items[]{sku_id, qty, entry_source, trigger_type}`，或在服务端订单行上持久化加购来源并由后台直接出数（后者更可靠，且不受客户端事件丢失影响）；`payment_succeeded` 同步补 `entry_source_mix`。

## Done-ness clarity — thin

这一维是下游拆 story 压得最重的一维，也是本 PRD 集失分最集中的地方。先说好的：相当一部分 FR 的完成判据是可测的，而且质量在同类文档里属上乘。FR-94/FR-98 的字段表带必填标记与长度上限（≤60 字符 / ≤120 字符 / 5 位数字 / +62 前缀 8–13 位）；FR-94A 明确「未选规格时加购按钮为禁用态，不默认选中第一个规格」；FR-95 明确「购物车与结算是两次独立校验……第二次失败时明确标出是哪个 SKU 不可用，允许移除后继续下单，不整单打回」；FR-96 明确「登录成功后自动完成本次加购动作并停留原页」；FR-100 明确「待支付超时 = 60 分钟」「超时前 10 分钟推送一次」；FR-109 给出了完整公式 + 7 天提前量 + 三条不触发条件；FR-104 明确「须在商品详情页、结算页、退货申请页**三处**明示」。这些都能直接转成验收条件。

但**越靠近钱与状态，判据越薄**，而这恰好是电商最不能含糊的两处。

**状态机不穷尽。** §4.1 中 `已送达` 的进入条件写「承运商标记送达 或 后台标记」，而 FR-103 与 AB-11B 都明确首版不接承运商 API——第一个条件在本版本不可能触发；AB-11B 也承认「『已送达』状态需后台手动标记或依赖用户确认收货」。于是存在一条真实的卡死路径：后台不标记 + 用户不点确认 → 订单停在 `已发货`，而「送达后 7 日自动确认」的计时起点根本不存在，订单永不进入 `已完成`，也永不开始退货窗口计时。AB-11B 给的补救只是一条「已发货超过 N 日未确认收货」的待办列表（N 还没定值），不是自动转移规则。其次，FR-104 明列「拒收（未签收）」为可退情形、发生在配送中（即 `已发货` 态），但 §4.1 中 `已发货` 只有一条出边指向 `已送达`——**拒收路径在状态机中不存在**。第三，AB-11D 允许运营「发起整单取消或部分取消」，图上 `待发货` 没有对应的后台取消边。第四，**部分退款在订单状态机中完全无法表达**：`退款中`/`已退款` 是订单级状态，一张三件商品的订单退掉一件之后应该是什么状态，两份文档都没答案，而 FR-105 与 AB-12C 都在按「部分退款」写规则。§4.2 退款状态机同样缺三条边：`已驳回` 标为终态却注明「可申诉复用 FR-52」，申诉成功后回到哪个状态没有；用户主动撤销申请没有；`退款执行中 → 已退款` 没有失败分支，而 FR-105 自己提到 OVO/GoPay 退款要收 Rp2,500 手续费，说明存在真实的资金通道，退款执行失败是常态异常而非边缘情况。

**钱的规则缺取整、缺选择权、缺一处措辞把方向写反了。** FR-100A 规则 2 的示例是 60.000/240.000 这种整除数，但 20% 比例遇到 `Rp 33.333` 级金额必然产生小数，而 IDR 不展示小数——**谁承担取整余额没有规则**。这不是洁癖：规则 2 自称「天然保证用户拿回的真钱永远不超过其投入的真钱，是规则 1 在混合场景下的数学保证，可用于向法务/财务说明闭环性」，一旦取整向现金侧上舍，这条对法务讲的不变式就被破坏了。同一条规则里还有一个更大的静默决策：「余额优先全额抵扣，差额由 QRIS 补足」——**用户没有「本单不使用 PawCoin」的选项**。叠加规则 1（Coin 段只退 Coin），意味着每一单都在把用户账上「本可退现金」的钱不可逆地转为「只能退 Coin」的钱，哪怕余额只有 Rp 5.000。这是一个会引发客诉、且与规则 1 的防套现目的无关的强制项，PRD 没有把它作为决策写出来。规则 6 则把话说反了：「PawCoin **不可用于**支付 PPN 增值税**之外的**任何平台外部结算」——字面意思是 PPN 之外都不行、PPN 可以，而 DEP-8 正把「PPN 开票金额按零售价还是实付真钱」列为未决问题。

**含糊措辞逐条点名：** FR-95「制造**合理**紧迫感」（同句后半「不虚构数字」是可测的，前半不是）；FR-98「剩余地址中**最近使用**的一条自动升为默认」（最近使用=最近下单？最近编辑？）；AB-11B「已发货超过 **N 日**未确认收货」（N 未取值）；FR-93「**4–6 个**商品」与 FR-107「取前 4–6 个」（何时 4 何时 6、不足 4 个时整区是否隐藏均未定义）；FR-93「最多 **2 张**」复购触发卡（三类触发同时命中时的优先级未定义）；FR-94「商品详情 富文本（图文）」（无体积/标签白名单约束）；AB-10A「表单需在此处**明示**该后果」（明示形式未定义，属可执行性存疑而非严格不可测）。

### Findings

- **critical** FR-102 的 `已送达` 依赖已被明确排除的能力，订单存在永不完成的卡死路径（§4.1 / FR-102 / 后台 AB-11B） — 状态表写「`已送达` 进入条件 = 承运商标记送达 **或** 后台标记」，而 FR-103「不接承运商 API」、AB-11B「首版不接承运商 API……『已送达』需后台手动标记或依赖用户确认收货」。若后台漏标且用户不点确认，订单停留 `已发货`，「送达后 7 日自动确认」无起算点，`已完成` 与退货窗口双双不可达。AB-11B 的「已发货超过 N 日未确认收货」只是待办提示，不是转移规则，且 N 无值。*Fix:* 删除「承运商标记送达」这一进入条件（本版本不可用），并补一条兜底自动转移：`已发货` 起 M 日（建议 7 日，与配送时效 2–4 日留余量）无人工标记则自动置 `已送达` 并开始 7 日自动确认计时；同时给 AB-11B 的 N 取值并与 M 对齐。
- **critical** 部分退款/部分退货在订单状态机中无表达（§4.1 / FR-105 / 后台 AB-12C / AB-11D） — FR-105「部分退款按 `实退金额 × 订单固化的支付比例` 执行」、AB-12C 同款表述、AB-11D「运营可发起整单取消或**部分取消**」，但 §4.1 只有订单级的 `退款中` / `已退款`，一张多商品订单退掉其中一件后处于什么状态没有定义；`已退款` 作为终态更是与「其余商品仍需履约」直接冲突。*Fix:* 明确两级状态模型——订单级状态与退货申请级状态分离（§4.2 已是申请级），订单在部分退款后**保持原状态**（`待发货`/`已完成`），仅在全部行退款完成时转 `已退款`；在 §4.1 下方补一张「退款单状态 → 订单状态」的映射表（AB-12C 已要求「不允许出现订单已退款但退款单未完成的不一致」，但没给映射）。
- **high** 混合支付按比例拆分无取整规则，可破坏 PRD 自称的闭环不变式（FR-100A 规则 2 / FR-105 / 后台 AB-12C） — 示例用 60.000/240.000 整除数掩盖了问题；IDR 不展示小数，`实退金额 × 固化比例` 必然产生余额。规则 2 明确宣称该机制「天然保证用户拿回的真钱永远不超过其投入的真钱……可用于向法务/财务说明闭环性」，取整方向选错即破坏此断言。多次部分退款的累计取整误差同样无规则（会出现全部退完后两段之和 ≠ 实付额）。*Fix:* 明确「现金段向下取整、Coin 段吸收全部余数」，并规定最后一笔退款按「实付额 − 已退累计」轧差而非按比例计算，保证轧平；在 AB-12C 与 AB-13D 同步该口径。
- **high** FR-100A 规则 2 未给用户「本单不使用 PawCoin」的选项（FR-100A 规则 2 + 规则 1 / FR-97 结算页） — 「余额优先全额抵扣，差额由 QRIS 补足」是无条件的，结算页只被要求「同时展示两段金额」，没有开关。叠加规则 1（Coin 段只退 Coin、平台责任也不例外），效果是每笔订单都在把用户可退现金的资金不可逆转为不可退现金的资金，哪怕余额只有几千盾。这是一个独立的产品决策，与规则 1 的防套现目的无关（不用 Coin 不会产生套现路径），却被当作实现细节隐含掉了。*Fix:* 结算页 PawCoin 区增加显式开关（默认值作为产品决策登记为 OQ），并在 FR-100A 补一条规则说明「不使用 Coin 不影响任何其他规则」；若坚持强制抵扣，须把「用户不可选择放弃使用余额」写成显式决定并给出理由。
- **high** FR-100A 规则 6 的措辞把 PPN 排除在禁止范围之外，读起来等于允许（FR-100A 规则 6 vs §8 DEP-8） — 原文「PawCoin **不可用于**支付 PPN 增值税**之外的**任何平台外部结算」，字面含义是 PPN 可以用 Coin 付；而 DEP-8 正把「PPN 开票金额按零售价还是实付真钱」列为未决。一条声称防御性的条款反而写成了未经拍板的授权。*Fix:* 改为「PawCoin 不可用于任何平台外部结算（含 PPN 等税费）」，或若确实允许 Coin 覆盖含税零售价，则改写为正向表述并在 DEP-8 中明确该口径。
- **high** FR-108 无触发提前量，同节 FR-109 有（§3.9 FR-108 vs FR-109） — FR-109 明写「耗尽日前 **7 天**开始」，FR-108 只写「当健康提醒判定某项临近到期时」——「临近」是多少天没有定义，而这正是与 CODE-3 叠加后最容易被实现者临场编造的数值。频控（30 日一次）反而定义了。*Fix:* 给出提前量（建议驱虫/疫苗各自取值，或统一 7 日与 FR-109 对齐），并明确到期后仍未处理时是否重复提醒。
- **high** 「签收」未定义，与 `已送达` / `确认收货` 三词混用，退货窗口起算点歧义（FR-102 / FR-104 / §4.1 / §9 OQ-27） — FR-104 时限栏写「**签收后** 7 日内」，FR-102 状态名是 `已送达`、终态是用户「确认收货」，FR-102 后果又写「自**签收**起算」。7 日退货窗口究竟从送达日还是用户点确认之日起算，相差最多 7 天；而 OQ-27 讨论的正是「自动确认 7 日 + 退货 7 日叠加是否过长」——起算点不定，这条 OQ 本身无法回答。*Fix:* 在 §2 术语表加入「签收」并绑定为 `已送达` 的进入时点（而非用户确认时点），全文统一措辞；OQ-27 的问题改写为「送达日 + 7 日自动确认 + 送达日起 7 日退货窗口」的明确叠加形式。
- **high** 无仓库/发货地模型，「同城 Kecamatan」不可判定（FR-99 / 后台 AB-10C / AB-11C） — FR-99 规定当日达适用范围为「服务范围内的**同城** Kecamatan」，但两份文档从未定义发货地：AB-10C 入库单字段为「采购单号·供应商·SKU·数量·进货单价·入库日期·操作人」，无仓库；AB-11C 的运费表是「配送方式 × 区域」二维，也无发货侧维度。实现者无法判定任一地址是否可选当日达。*Fix:* 引入单仓假设并写死（「本版本仅一个发货仓，位于 {Kecamatan}」），当日达资格判定改为「收货 Kecamatan ∈ 后台配置的当日达可达列表」（配置项加入 AB-11C）；多仓明确列入 §7 非本版本范围。
- **high** 原始运费（去程）在部分退货时是否退回无规则（FR-104 / FR-105 / 后台 AB-12A） — FR-104 的表格是「退货运费」（回程）的归属规则，FR-105 却写「运费是否退回按 FR-104 的运费归属规则判定」——把去程运费的退回问题指向了一张只讲回程的表。多商品订单只退其中一件时，用户已支付的去程运费该退多少（全退 / 不退 / 按金额比例）没有答案，而这笔钱同样要参与 PawCoin/QRIS 比例拆分。*Fix:* 在 FR-104 表格下方补一行去程运费规则（建议：整单退→全退；部分退→不退，并在退货申请页明示），AB-12A 的运费归属判定项相应拆为「去程/回程」两项。
- **medium** FR-109 公式漏掉购买数量（§3.9 FR-109） — `预计可用天数 = SKU 净含量(克) ÷ 日喂量`，未乘以本次购买件数。一次买两袋的用户会在第一袋用完时就收到补货卡，且 §5 无法区分这是预估错误还是用户行为。*Fix:* 改为 `(SKU 净含量 × 购买数量) ÷ 日喂量`；同时补一句多宠物共食时不触发或按当前选中宠物计算（与 CODE-4 联动）。
- **medium** FR-93 补货区「最多 2 张」缺三类触发同时命中时的优先级（§3.1 FR-93 区域① / FR-108 / FR-109） — 驱虫、疫苗、粮量三类可同时成立，区域①只放 2 张，孰先孰后未定义；且疫苗触发按 FR-108 跳转健康模块而非商品，与「补货提醒区」的语义不同，是否应占用这 2 个位也未表态。*Fix:* 给出优先级（建议 粮量 > 驱虫 > 疫苗，理由是前者时效最硬、后者本就不带交易），并说明疫苗卡是否计入 2 张上限。
- **medium** 「4–6 个」的取数规则与不足下限时的行为未定义（§3.1 FR-93 区域② / FR-107 步骤 4） — 两处都写 4–6 个，但没有说明何时取 4、何时取 6，也没说明命中商品少于 4 个（SKU 上限 30、四个品类、按物种+年龄+体型三重过滤后极易发生）时区域②是隐藏、是补位还是照常展示 N 个。*Fix:* 改为「最多 6 个，少于 2 个时整区不渲染并回落到区域④」之类的确定规则。
- **medium** FR-95 的「服务端原子扣减」与 AB-11D 承认超卖之间没有口径（FR-95 / 后台 AB-11D） — FR-95 断言「库存扣减必须由服务端原子操作完成……并发下单时以服务端判定为准」，AB-11D 却写「**超卖发生时**（并发下单击穿库存）后台需有明确的异常订单视图；用户端已通过服务端原子扣减防护，此视图是兜底而非主路径」。两句只能同时成立于「原子性有边界」的前提下，而该边界（隔离级别、是否允许可售库存瞬时为负、超卖容忍度目标）未声明；用户侧在超卖已发生（已付款但无货）时的处置流程也完全缺失。*Fix:* FR-95 补一句不变式（如「以行级条件更新实现，可售库存不得为负，超卖目标为 0」），并新增一条用户侧处置：超卖订单由后台发起整单/部分取消 + 全额退款 + 回告理由（复用 AB-11D + FR-52A），在 §4.1 上标出该边。
- **medium** 收货地址是否随订单快照固化未声明（FR-98 / 后台 AB-11A） — 地址簿可编辑可删除（上限 20 条、可删默认），AB-11A 要求「订单详情展示完整收货地址」，但没有一句说明订单持有的是快照还是引用。用户在发货前修改或删除地址时已成立订单的收货信息会不会变，直接影响履约。同理「发货前能否修改订单地址」也未表态。*Fix:* FR-98 补「下单时对地址做快照，后续编辑/删除地址簿不影响已成立订单」；「发货前修改订单地址」明确支持或写入 §7。
- **medium** AB-6D 两个开关关闭时的用户端行为未定义（后台 AB-6D vs FR-100A） — 后台定义了「电商 PawCoin 支付总开关」与「是否允许 PawCoin 抵扣运费」两个开关，但用户端 FR-100A 把规则 3（运费可用 Coin）写成无条件规则，也没有描述总开关关闭时结算页长什么样、与规则 5（充值暂停但消费可用）在界面上如何区分。运费开关关闭还会改变比例拆分的基数，FR-100A 规则 2/3 与 AB-13D 的口径随之变化。*Fix:* FR-100A 补一小节「开关关闭时的表现」，逐个描述结算页与退款页的降级形态，并说明运费开关关闭时比例基数改为「不含运费的商品小计」。
- **low** FR-106 评价的可修改性与边界情况未定义（§3.8 FR-106） — 「每个订单每个 SKU 各评一次」是可测的，但评价能否修改/删除、已退款或退货中的商品能否评价、评价被审核拦截后用户是否收到告知，均未定义。*Fix:* 补三句即可：不可修改不可删除（或可在 N 日内修改一次）、已全额退款的行不可评价、拦截时复用既有审核告知机制。
- **low** 失效商品在恢复后的行为未定义（§3.3 FR-96） — 失效分区含「已下架、已售罄」两类，售罄是可逆的，但商品补货后购物车中的该行是否自动移回有效区没有说明；「清空失效商品」是否连同可恢复的售罄项一并清掉也没说。*Fix:* 明确「售罄恢复后自动移回有效区，下架不可逆」。

## Scope honesty — adequate

§7「非本版本范围」做了真实的工作，不是聊胜于无：6 条排除项每条都带理由或指向（第三方入驻「与自营模式互斥，且违背战略边界」、全站搜索「见 FR-93」、优惠券「会员制套餐 Roadmap 整体暂缓」、承运商 API「见 FR-103 / FR-99 的分期理由」）。更值得肯定的是**散落在正文里的就地排除**——FR-99「超重/超体积附加费：首版不做」并给出为什么可以不做（SKU 受控、最大件 7.5kg、差异由固定运费表吸收）、FR-103 的分期理由、FR-106「首版不做追评、不做商家回复」并给出成本论证、FR-107「首版为规则式，不引入个性化算法」、AB-12D「首版不引入第三方质检」、OQ-30「首版建议供应商为文本字段，不建主数据」。这类「排除 + 触发再做的条件」的写法，正是 Non-Goals 应有的样子。§1 对「本版本是 App 内第一次出现实物商品，四类能力从零建立」的坦白同样加分。

失分在于**披露的位置不对，以及三个应排未排的洞**。最关键的：5 处代码偏差与 4 项高阻塞依赖的真实严重度，只活在 README §4/§5 与 decision-log 里，而 README 明确自述是「落库说明」、其 §11 甚至写明「validate 跑完后它们应当已在 PRD/decision-log 里有编号，本 README §4 退化为历史记录」。下游 bmad-ux / bmad-architecture / bmad-create-epics-and-stories 读的是 PRD——PRD 正文里 FR-100 写着「复用 FR-43 通用支付组件，**不新建支付通道**」，FR-107 写着体重字段「V1.0.0 FR-11 已有」，读者拿到的是一份「全部可复用」的乐观图景。

三个洞：**PPN 与发票在用户端完全缺席**（DEP-3/DEP-8 在讲 PPN 登记、开票与收入确认，但 FR-97 的金额明细只有「商品小计/运费/免运费抵扣/应付合计」四行，零售价是否含税一字未提，是否给用户开具收据/e-Faktur 也没有，§7 也没有排除）；**是否支持部分退货未表态**（FR-105 与 AB-12C 按部分退款写规则，FR-104 的流程却是整申请粒度，两者都没说用户能不能只勾选订单中的一件）；**超卖后的用户侧处置缺失**（见 Done-ness）。

开放项密度对 launch 级 stakes 而言偏高：**开放 OQ 8 条**（用户端 5 + 后台 3）、**待拍板 D 6 条**（与 OQ 大部分重叠）、**依赖 DEP 8 条（其中 4 条标高阻塞）**、**假设 7 条（3 条致命度高）**、**代码偏差 5 条（1 条 critical）**，去重后约 24–26 项。数量本身不是问题，问题是**高阻塞项全部压在版本主线上**：CODE-1 阻塞整条退款/对账链、CODE-2+CODE-3 打掉复购引擎三分之二、DEP-1 阻塞入口 FR-93/93A 定稿、DEP-3 阻塞上线本身。README §10 给出的推进顺序（先定混合支付模型、并行启动 DEP-1/3/4/7）是对的，但那份顺序不在 PRD 里。

## Downstream usability — thin

本维在 chain-top 场景下权重最高，也是必须最严的一维。基础条件是具备的：§2 有术语表（7 条，Toko / 精选自营 / 商品 / 规格SKU / 可售库存 / 锁定库存 / 复购触发卡 / 服务范围），FR 编号 93–110 连续唯一无重号，后台 AB-10A~13D 四段各自连续、AB-6D 追加位置正确，编号延续规则在两份文档的 §0 都做了显式交代（FR 从 93、OQ 从 25、A 从 15、后台模块从 10），这在多版本并行的仓库里是很有价值的纪律。后台文档对用户端 FR 的引用密度也高且大多可解析（AB-10A→FR-94/107/109、AB-12C→FR-100A 规则 2/FR-105、AB-6C→FR-100A 规则 5）。

但有三处会直接损坏下游自动化的问题。

第一，**4 处 FR 交叉引用系统性 +1 偏移**，全部集中在文档前半段：§2 术语表「由结构化健康记录周期或粮量见底预估驱动（FR-109/FR-110）」（应为 FR-108/FR-109）、§3.1 表格「按档案推荐（FR-108）」（应为 FR-107）、FR-94 表「用于 FR-108 档案推荐过滤」（应为 FR-107）、FR-94 表「**FR-110** 粮量见底预估的计算依据」（应为 FR-109）。偏移方向一致，像是编辑过程中删除或插入过一个 FR 而未回改引用。后果是确定的：按 FR-108 去找「档案推荐」的下游 agent 会拿到「健康记录触发复购」，按 FR-110 去找「粮量见底预估」会拿到「问诊与商品的边界」——**引用可解析但解析到错误对象**，比断链更危险，因为不会报错。

第二，**两份文档没有任何 User Journey**。这是一款消费级 App，本版本从零引入下单、支付、收货、退货四段全新流程（`页面/` 下已有 17 屏 UI 规格佐证其复杂度），同时牵动三类角色：用户、CS（退货审核 + 开封判定 + 运费归属判定）、财务（对账 + 毛利 + 浮存监控）。PRD 用「功能 + 后果」的写法把这些拆成了条目，但没有一条带主角的旅程把它们串起来。§0 说明「不重复 V1.0.0 已写明的……用户旅程」——可 V1.0.0 的旅程里不可能包含下单与退货。对下游 bmad-ux 而言，这意味着必须从 FR 后果和 HTML 预览里反向拼装旅程；对 CS/财务这两类没有 UI 预览的角色，则连拼装的素材都没有。

第三，**用户端定义、后台未实现的配置项**，以及缺少 FR↔AB 对照表。FR-107 步骤 2 写「幼年 <1 岁 / 成年 1–7 岁 / 老年 >7 岁，**犬猫阈值可后台配置**」，但后台 AB-10A/10B/10D 的字段与配置清单里没有这一项。在三人并行、共享 `OrderCenterService` 与三个共享枚举的开发形态下（README §6），缺一张 FR↔AB 双向对照表会让追溯成本显著上升。

## Shape fit — thin

作为 brownfield 增量文档，形态选择大体正确：轻量结构、显式声明「不重复 V1.0.0 已写明的产品愿景、用户旅程和术语表」、只写新增/变更、编号从既有最大值延续、§6 用一张表登记对既有文档的回写要求（Roadmap / FR-43 / FR-54 / FR-50C / FR-50D / 埋点 / icon-system）——这套做法与仓库既有的 v1.1 / v1.1.2 delta 惯例一致，也符合 README「增量并存，不改基线」的登记方式。作为 chain-top，它对下游的意识也是有的：§8 依赖表标了责任方与阻塞程度，§5 主动要求埋点先行发版取基线（并引用 V1.1.2 的真实翻车教训 L-6），这些都是为下游着想的写法。

但 rubric 对 brownfield 的硬条是「**existing-code references must be accurate**」，而这正是本 PRD 集最失分之处——五处代码偏差全部落在这一条上，且其中两处不是「信息滞后」而是**把最高风险项写成了零成本复用**：FR-100 开篇「**复用 FR-43 通用支付组件，不新建支付通道**」，读起来是这一节没有工程风险；代码事实是 `PaymentIntent.java` 为严格单渠道单金额模型（`channel` 单值枚举、`amount` 单值、两者 `updatable=false`，`PayChannel` 仅 {QRIS, PAWCOIN}），根本表达不了 FR-100A 规则 2 要求的「一笔订单 PawCoin 段 + QRIS 段并存且比例在下单时固化」。这不是一个可以在 story 里顺手解决的问题：README §4① 给出的两个方案（扩展共享 `PaymentIntent` vs 电商侧自建拆分表起两笔 intent）分别意味着「改动共享基座、影响另两位并行同事」或「订单-支付一对多、对账链路变长」——是需要架构 delta 拍板的分叉，而 PRD 完全没有把这个分叉暴露出来。同样地，CODE-5 是**PRD 内部自相矛盾**：§3.1 写「占用底部 Tab Bar 中**已预留的位置**」，§5 写「电商 Tab **会替换掉一个既有 Tab**」并据此提出基线埋点要求——两处不能同时为真，而代码里 `AppTab` 是 4 值枚举加中间 [+] 按钮、确实无空位。

另有一处形态观察值得记下：**篇幅分配与重要性排序相反**。FR-100A（PawCoin 支付实物的 7 条规则）约占 100 行，是全文最长最细的一节；而被 §1 与 decision-log N-1 共同认定为「版本存在意义」的复购引擎（FR-107/108/109）三条加起来约 50 行，且其中 FR-108 连触发提前量都没有。这不是说 FR-100A 写多了——它写得确实好——而是说注意力流向了争议最多的地方，而非最承重的地方。修复方向不是砍 FR-100A，是把复购引擎写到同等密度。

### Findings
