## Overall verdict

这是一份**思考质量明显高于平均、但工程可用性尚未达标**的 PRD 集。它有真实的战略论点（复购引擎而非货架），并愿意为论点付出代价——FR-110 主动禁掉问诊侧荐货变现、FR-93 主动砍掉搜索框，理由都写在正文里；`decision-log` L-7 甚至把自己初稿的「单笔上限 = 浮存阀门」判定为错误论证并连带推翻三处结论。theater 几乎为零，决策以决策的形式写出来而不是藏在「考量」里。后台 PRD 同样扎实（「不静默按零成本计算利润」「库存增加只能通过入库单」「补偿溢价须计入毛利扣减」都是被坑过的人才写得出的条款）。

但它**不可直接交给下游拆 story**。三条硬伤：① 版本自称的存在理由（复购引擎）建立在三个数据输入上，其中两个在代码中不存在（CODE-2 体重字段、CODE-3 到期间隔），PRD 正文却把它们声明为「V1.0.0 已有」；② §4 三张状态机不穷尽——`已送达` 的进入条件依赖被 FR-103/AB-11B 明确排除的承运商 API，部分退款在订单状态机中无表达，拒收/驳回回边/采购入库多条必然发生的转移在图上不存在；③ 花约 100 行把 PawCoin 混合支付的七条规则论证得极细，却漏掉了取整规则、用户能否选择不用 Coin、以及归因属性——而后者恰恰使 AB-13B 那个「判定版本成败的直接依据」在埋点 schema 上无法计算。

两名额外评审员显著改变了图景，方向不同但都指向同一结论。**adversarial** 把火力集中在「能不能跑起来」：退货寄回环节（寄到哪、怎么计费）在两份文档中整体缺失，而 FR-100A 规则 3 与 AB-12C 都在按它算钱；本版本首次建立 PII 数据集却零合规覆盖，DEP-1~8 无一条涉及印尼 UU PDP；FR-102 的订单号 `TT+YYYYMMDD+8位自增` 直接违反 CLAUDE.md「对外标识一律不可枚举」的强制护栏，**且被 PRD 当成优点写**。**跨文档一致性**评审员的结论则是分裂的：资金与售后链对得极齐（FR-100A ↔ AB-6D/AB-6A、FR-105 ↔ AB-12C 措辞逐字互锁），履约与状态机链却是断的——后台能做的运营动作多条在状态机上无落点，状态机上多条关键转移在后台无入口；它还用交叉表抓出了另外两名评审员都不易发现的一类错误：**用户端 4 处 FR 编号整体偏移一位，而后台在同一位置引的是正确编号**，两边各自读都通顺、合起来读却指向不同条目。

**结论：返工后可进入 `bmad-ux` / `bmad-architecture`，返工是「补」不是「重写」。** 必须闭合的最小集：CODE-1 混合支付模型选型（架构）、CODE-3 的 FR-108 范围二选一（产品）、4 处交叉引用偏移、`已发货` 死锁与状态机缺边、部分退款的状态表达、AB-12C 溢价单/双值矛盾、埋点归因属性、混合支付取整规则。

**[C4] `已发货` → `已送达` 无操作入口，7 日自动确认永不触发，`已发货` 成事实悬空态**（用户端 FR-102 / §4.1 ↔ 后台 AB-11B / AB-11A）— **三名评审员独立命中**
FR-102 写 `已送达` 进入条件为「承运商标记送达 **或** 后台标记」，但 FR-103 与 AB-11B 都明确首版不接承运商 API——**第一个条件本版本不可能触发**；而后台**并没有把「标记已送达」定义成一个操作**（AB-11B 只定义了「选择承运商 + 录入单号 + 确认发货」，那段话是在解释困难而非定义入口）。连锁后果：订单停在 `已发货` → 自动确认无起算点 → `已完成` 与退货窗口双双不可达 → FR-106 评价入口不出现 → FR-109 的「最近一次 Makanan 购买」基准日失真。且 `已发货` 状态下用户唯一可执行操作是「查看物流」，**没有确认收货入口**（挂在 `已送达`），用户收到货也无从自救。AB-11B 给的「已发货超过 N 日未确认收货」只是待办列表，不是转移规则，N 还没取值。用户端 §4.1「终态三个，无悬空态」的自我声明在首版不成立。

**[C5] 部分退款 / 部分取消在订单状态机中无法表达**（§4.1 / FR-105 / AB-12C / AB-11D）

### High (34)

#### 钱与对账

**[H1] 混合支付按比例拆分无取整规则，可破坏 PRD 自称的闭环不变式**（FR-100A 规则 2 / FR-105 / AB-12C）— 示例用 60.000/240.000 整除数掩盖了问题；IDR 不展示小数，`实退金额 × 固化比例` 必然产生余额。规则 2 明确宣称该机制「天然保证用户拿回的真钱永远不超过其投入的真钱……可用于向法务/财务说明闭环性」——取整方向选错即破坏此断言。多次部分退款的累计误差同样无规则。*Fix:* 明确「现金段向下取整、Coin 段吸收全部余数」，最后一笔退款按「实付额 − 已退累计」轧差而非按比例算；AB-12C 与 AB-13D 同步口径。

**[H2] FR-100A 规则 2 未给用户「本单不使用 PawCoin」的选项**（FR-100A 规则 1+2 / FR-97 结算页）— 「余额优先全额抵扣，差额由 QRIS 补足」是无条件的，结算页只被要求「同时展示两段金额」，没有开关。叠加规则 1（Coin 段只退 Coin、平台责任也不例外），效果是每一单都在把用户账上「本可退现金」的钱**不可逆地**转为「只能退 Coin」的钱，哪怕余额只有几千盾。而这些 Coin 多来自 FR-43D 退款转入（PRD 自称「多为零头」，本意是留着买 Rp 18k–30k 级问诊），会在下第一单实物时被强制吸干。剥夺使用时机的选择权比剥夺退现金选择权更伤，**而后者 PRD 专门设计了规则 7 的溢价补偿，前者连提都没提**。*Fix:* 结算页增加显式开关（默认值作为产品决策登记为 OQ）；若坚持强制抵扣，须写成显式决定并给理由。

**[H3] FR-100A 规则 6 把 PPN 排除在禁止范围之外，字面等于授权**（FR-100A 规则 6 ↔ DEP-8）— 原文「PawCoin **不可用于**支付 PPN 增值税**之外的**任何平台外部结算（本版本无此场景，此条为防御性声明）」。按字面 = PPN 可以用 Coin 付。而 PPN 是缴给税务机关的、最典型的平台外部现金结算，恰恰是封闭币最不该触碰的一项——用无现金垫底的赠币（规则 7 溢价）覆盖税款等于用负债抵扣现金义务。叠加 DEP-8（PPN 开票按零售价还是实付真钱至今悬空），实现者会在没有财务口径的情况下写出把 Coin 计入 PPN 计税/抵扣基数的分支。**一句「防御性声明」写反了防御方向，比不写更糟。**

**[H4] AB-13D 的对账口径对「溢价 Coin」是错的，会把无现金垫底的负债当预收款核销**（AB-13D ↔ AB-6C / AB-13A）— AB-13D 写「PawCoin 是**此前已收现金的预收款核销**」。这对充值币成立，对规则 7 与 AB-6A 发放的两类溢价 Coin 不成立——AB-6C 在同一份文档里明写这两类是「凭空新增的 PawCoin……不像充值那样有等额现金流入垫底」。溢价 Coin 买走一袋有真实进货成本的狗粮时，平台交付实物、支出现金、却被记为「预收款核销」，现金流入被虚增。要拆开必须在钱包侧区分「充值币 / 赠币」的余额批次与核销顺序（FIFO？赠币优先？），**两份 PRD 与 AB-6D 的配置项里没有任何一处要求余额分层**。且 AB-13A 在**发放时点**计入毛利扣减、AB-13D 在**核销时点**按预收款处理——两个时点各记一次且口径不一致。

**[H5] 去程运费在部分退货时无规则，构成可复现的凑单-退货套利**（FR-97 / FR-104 / FR-105 / AB-12C）— 三份规则都是整单口径。用户凑单到门槛触发免运费、收货后退掉大部分只留一小件，平台已实付承运商运费，是否回收无规定；FR-105 与 AB-12C 都只讲「扣除退货运费」，**不涉及发货运费的追回**。一笔订单发生两次部分退货（一次平台承担、一次用户承担）时，只有一份运费却被两次判定争夺，按金额、按件数还是先到先得也没定义。*Fix:* FR-104 表下补去程运费规则（建议：整单退→全退；部分退→不退，并在退货申请页明示），AB-12A 的运费归属判定拆为「去程/回程」两项。

**[H6] 规则 7 的反刷单论证不成立，且没有任何频次风控**（FR-100A 规则 7 / AB-12D / AB-13A）— 规则 7 的论证是「为拿一笔**小额** Coin 溢价而走完退货流程，成本远高于收益」，但 OQ-34 给的上限是 **Rp 50.000**——约等于两次 AI 问诊解锁，在客单 Rp 285.000 的语境下不是小额。触发条件是「退货类型=质量问题（破损/临期/错发）」，凭据是 ≤6 张图 + CS 主观判定；宠物食品的「包装破损」是所有品类里最易制造、最难证伪的一种。AB-12D 判例库是**一致性工具，不是风控**。两份 PRD 无任何同用户/同地址/同支付账号的质量问题退货频次限制、无溢价累计上限、无异常名单；AB-13A 只要求事后可下钻。

**[H7] AB-13A 毛利指标缺运费损益行，FR-105 的退款手续费在后台无承接**（AB-13A / AB-13D ↔ FR-99 / FR-105）— AB-13A 指标全集为「GMV·订单数·客单价·商品成本合计·毛利额与毛利率·退款额·净销售额」，**没有运费收入、没有承运成本**；但 FR-100A 规则 3 明写「运费是平台向承运商支付的真实现金支出」，AB-13D 还专门要求「被 PawCoin 抵扣的运费须单独可拆」——运费能在对账里拆出来，却进不了毛利表。同样 FR-105 定义的退款手续费（OVO/GoPay 自付 Rp2,500）在 AB-12C/AB-13A 全无口径。（顺带：FR-100 明写不支持 GoPay/OVO 直连、仅 QRIS，FR-105 的手续费文案是从 FR-43D 原样搬来的，在单渠道语境下需重新说明它指的是 QRIS 原路退回到的钱包。）

**[H8] A-19 的验证方式在系统里无数据可用，因为承运成本从未被要求录入**（§10 A-19 ↔ AB-11B / AB-13A）— A-19「固定运费表不产生显著亏损或超收」的验证方式写「按月核对实际承运成本与收取运费的差额」。但收取运费在三种情形下是三个不同的数（正常 / 免运费抵扣为 0 / 被 PawCoin 抵扣，收的不是现金），而**实际承运成本根本没有录入口**——AB-11B 只录承运商和单号，AB-10C 只覆盖采购成本，AB-13A 无这两行。**A-19 承接的是 FR-99「省掉一整条 API 对接工期」的全部风险，其验证方式不可执行。**

#### 履约与状态机

**[H9] 退货寄回的物流环节在两份 PRD 中整体缺失，而 FR-100A 规则 3 与 AB-12C 都依赖它算钱**（FR-99 / FR-104 / AB-11C / AB-12A / §4.2）— 两处用同样措辞写「退货运费由用户承担时，从退款金额中扣除后再退回」，但这个数从哪来：FR-99 只有**发货**方向的运费表；退货是用户自行寄、还是平台上门取件、**寄到哪个地址**、按什么标准计费——用户端（FR-104 只写"是否需退回实物"）与后台（AB-12A 只判运费归属、AB-12B 只做质检、AB-11C 无退货收货地址配置）**没有任何一处定义**。而 §4.2 已经画了 `待用户寄回 ──超时未寄回(7日)──→ 已关闭(终)`。**这是最小可售闭环的必需环节，不在 §7 排除清单、也不在 DEP-1~8 里——是被静默省略的。**

**[H10] 换货流程完全不存在，但 FR-94 已把「可退可换」作为必填商品标识对外承诺**（FR-94 / §3.7 / AB-10A / 模块 12 全部）— FR-94「退换货规则标识｜必填｜枚举：**可退可换** / 开封不退 / 不可退换」，AB-10A 完整承接三值枚举并设默认值。但「换」这条路径在两份文档中零实现：FR-104 可退情形表 4 行全是退款、§4.2 退款状态机无换货分支、FR-102 无「换货中/已换货」状态、AB-12A 退货类型 4 值无「换货」、AB-12B 质检结果只有「通过→退款 / 不通过→驳回」无「通过→补发」、AB-11B 无补发操作、AB-10C 无换货出入库配对。运营标成「可退可换」后用户端会据此展示「可换」承诺，**而平台没有任何执行能力**——直接可被用户援引的对外承诺缺口。*Fix:* 建议首版删除该枚举值改为二值，§3.7 与模块 12 标题改「退货与退款」，§7 显式列入「换货」。

**[H11] 拒收：AB-12A 有正式类型，用户端无入口、状态机无边**（FR-102 / FR-104 / §4.1 ↔ AB-12A）— FR-104 明确「拒收（未签收）｜时限：**配送中**｜承运商原路退回｜运费平台承担」，AB-12A 把拒收列为四个退货类型之一。但拒收发生在 `已发货` 态，而该状态用户可执行操作只有「查看物流」，§4.1 图中 `已发货` 唯一出边是 → `已送达`。**用户没有任何途径提交拒收申请，CS 队列里的「拒收」类型永远不会有来源。**（实务上拒收多为口头拒收后平台补录，若是这个设计则需要「后台代客建单」路径——两份文档也没有。）

**[H12] 拒收商品跳过质检却无法入库，形成账实分离黑洞**（§4.2 / FR-104 ↔ AB-12B / AB-10C / AB-13C）— §4.2 说明「『待发货前取消』与『拒收』两类跳过 `待用户寄回` 与 `质检中`，由 `待CS审核` 批准后直接进入 `退款执行中`」。但拒收的是**已出库的实物**，几天后会真实回到仓库。AB-12B 规定「只有质检通过的退货才进入可售库存」，AB-10C 规定「库存增加只能通过入库单」且必填「采购单号·供应商·进货单价」——拒收退回的货**既没有采购单号也没有进货单价，流程上已跳过质检**，既无法入库也没有被记为报损。钱已退、货已回、系统里不存在，并会污染 AB-13C 的「库存金额是资金占用的直接读数」。

**[H13] AB-10C 的三条库存变更路径在 §4.3 状态机上完全缺失**（AB-10C ↔ §4.3）— AB-10C 的措辞是排他性的：「库存增加**只能通过入库单**」「库存减少的合法途径**仅三条**：订单支付成功扣减·**报损**·**盘点调整**」。而 §4.3 只有 可售⇄锁定、锁定→已扣减、退货质检通过→可售。**① 采购入库 ② 报损 ③ 盘点调整 三条转移一条都没画——按图看，可售库存的唯一来源是「退货凭空产生」。** 另 `已扣减 → 可售` 的回退也缺（AB-11D 的取消要把货退回可售），且 AB-11D「缺货无法履约」这句话本身暴露了 PRD 未承认的前提：**系统库存与实物库存会脱节**。（顺带：用户端没有商品状态机，「在售/下架」只出现在 AB-10A 字段与 FR-96「失效商品」里，术语表未收录。）

**[H14] 退款被驳回后无回边，FR-102「无悬空态」按图论为假**（§4.1 / §4.2 / FR-102 / AB-12C）— §4.2 有两个 `已驳回(终)` 与一个 `已关闭(终)`，但 §4.1 中 `退款中` 只有一条出边指向 `已退款(终)`。退货被驳回后订单回到 `已送达` 还是 `已完成`、7 日窗口是否重算、能否二次申请，两份 PRD 都没写。而 FR-102 断言「终态为 `已完成`/`已取消`/`已退款` 三个，**无悬空态**」——按现有两张图，被驳回的订单恰恰就是悬空态。AB-12C 只约束了「订单已退款但退款单未完成」这一个方向，反方向无约束。

**[H15] 「签收」在系统中不是一个存在的事件，但退货窗口的起点挂在它上面**（FR-102 / FR-104 / §4.1 / OQ-27 ↔ AB-12A）— **三名评审员独立命中。** 用户端四处混用三个概念：状态名是 `已送达` / `已完成`，而 FR-102 后果写「自**签收**起算」、FR-104 时限三次写「签收后 7 日内」、§4.1 写「`已完成` 在签收 7 日内仍可转 `退款中`」。**「签收」既未在 §2 术语表定义，也不是任何一个状态名。** 若签收 = 进入 `已送达`，两个 7 日同起点，「自动确认后仍保留 7 日退货窗口」这句就是假的、OQ-27 追问的「叠加是否过长（14 日）」也不成立；若签收 = 用户确认收货，则未确认收货的用户永远没有窗口起点。既然不接承运商 API，签收时间根本无从采集，实现层只能落成「以后台标记送达时间为准」——**用户的 7 天权利长度由运营的手速决定**。后台侧完全没承接：AB-12A 无「距窗口截止 N 日」字段、无超窗自动拒绝。*Fix:* §2 定义「签收 = 订单进入 `已送达` 的时刻」，据此重写 FR-102 后果与 §4.1；AB-12A 加窗口截止字段与超窗拦截；**D-3/OQ-27 的问题描述需先修订再拍板**。

**[H16] 部分发货与「包裹」概念整体缺失，而多 SKU 订单在自营下是常态**（FR-102 / FR-103 ↔ AB-11A / AB-11B / AB-11D）— FR-102 状态机是整单级单一状态，AB-11A 的「物流单号」是单数，AB-11B 的发货是一次性动作。但购物车是多 SKU 的，FR-99 的两档配送在物理上必然分包（7.5kg 狗粮走同城骑手 + 一盒驱虫药不可能同一单号），AB-11D 又明确存在「部分取消」。部分发货后订单是什么状态？多个单号在 FR-103 里如何呈现？「送达」以哪个包裹为准、7 日自动确认以哪个为起点？**一个字都没有，而 §7 排除的只是「承运商 API 实时轨迹」，不是「一单多包」。**

**[H17] 无仓库/发货地模型，「同城 Kecamatan」不可判定**（FR-99 ↔ AB-10C / AB-11C）— FR-99 规定当日达适用范围为「服务范围内的**同城** Kecamatan」，而「同城」是相对发货地而言的——**发货地/仓库地址在两份 PRD 中从未出现**：AB-10C 入库单无仓库字段，AB-11C 的运费表是「配送方式 × 区域」二维、无发货侧维度。结算页无法判定当日达是否可选。首发单仓时这一项可以硬编码，**但 PRD 连「首版单仓」这个前提都没写下来，架构侧会被迫自己发明。**

**[H18] AB-11B 引用了 AB-11C 中不存在的「配送方式配置」；两档配送在后台只有一个服务范围集合**（AB-11B:94 ↔ AB-11C:100-103 / FR-99）— FR-99 的两档配送**适用范围不同**（当日达=同城 Kecamatan；标准快递=服务范围全部）。AB-11B 写「承运商为下拉枚举，**与 AB-11C 的配送方式配置联动**」，但 AB-11C 全节只有服务范围、运费二维表、免运费门槛、变更不追溯四条，**没有任何「配送方式配置」**，且只有一个服务范围集合，无法表达「这个 Kecamatan 可当日达、那个只能标准快递」。AB-11C 还是全后台唯一被用户端点名两次却零 FR 反向引用的条目。

**[H19] 锁定库存可被无成本占用 60 分钟，PRD 只论证了「别误杀」没论证「防滥用」**（FR-95 / FR-100 ↔ AB-11D）— FR-100 把待支付超时定为 60 分钟并论证「明显长于兽医咨询的限时窗口，因为实物购买的决策节奏不同，沿用短窗口会造成大量误失效订单」——**只覆盖了误杀方向**。在 SKU 上限 30、自营备货受现金约束的前提下，单账号或脚本反复提交不支付即可把爆款 SKU 的全部可售库存锁死 60 分钟并无限续期。两份 PRD 无任何「同用户并发待支付订单数上限 / 单 SKU 单用户锁定量上限 / 连续超时后冷却」约束，AB-11D 的异常视图也不覆盖（这不是超卖）。爆炸点是上线首周的爆款断供，且 `out_of_stock_viewed` 会把它记成真实缺货需求。

**[H20] 超卖处置在两份 PRD 之间自相矛盾，且后台只给了视图没给动作**（FR-95 ↔ AB-11D）— FR-95 断言「库存扣减必须由服务端**原子操作**完成……失败方返回明确的『已售罄』错误」，AB-11D 却写「**超卖发生时**（并发下单击穿库存）后台需有明确的异常订单视图；用户端已通过服务端原子扣减防护，此视图是兜底」。若原子扣减在提交订单锁定这一步生效，并发路径上的超卖不可能发生——**真正会超卖的是盘点/报损/退货入库撤销，而 PRD 把它归因成了并发**。更要命的是 AB-11D 只定义了「视图」，**没有定义任何处置动作**：哪一单被取消、按什么顺序、如何通知、是否补偿、库存回补到哪里，全部空白，CS 拿到视图无章可循；用户端也完全没有「已付款但无货」的处置流程。

#### 度量与验证

**[H21] 判定版本成败的决定性指标在埋点 schema 上不可计算**（§5 ↔ AB-13B / A-16）— **三名评审员独立命中。** AB-13B 把「触发卡转化率 vs 普通商品曝光转化率」列为「判定 A-16 成立与否的直接依据」，但 `order_submitted` 属性只有 `order_id/amount/shipping_method`、`payment_succeeded` 只有 `order_id/amount/channel`——**下单侧完全没有归因属性**，多商品订单也无行级归因。链路只到 `add_to_cart`（有 `entry_source`）为止：**能算点击率，算不出转化率。** 考虑到 L-6 已经为「基线缺失导致指标不可得」立了一次前车之鉴，这里再踩一次同类坑代价很高。*Fix:* 给 `order_submitted` 增加行级数组属性 `items[]{sku_id, qty, entry_source, trigger_type}`，或在服务端订单行上持久化加购来源由后台直接出数（更可靠，不受客户端事件丢失影响）；AB-13B 明确转化终点定义（加购 vs 下单 vs 支付成功）。

**[H22] 疫苗类触发卡结构上恒不转化，却被计入 A-16 生死判据的分母**（FR-108 ↔ AB-13B / A-16）— FR-108 写「仅限驱虫、疫苗两类」参与触发，紧接着又写「**疫苗触发的是「预约问诊/线下接种」而非直接卖疫苗**……跳转健康模块而非商品详情」——即疫苗类转化率**结构上恒为 0**。而 AB-13B 按 `trigger_type` 三值一视同仁地算转化率并据以判定 A-16（「若触发卡点击率不显著高于普通商品曝光，则本版本的核心论证不成立」）。**用一个自己制造的偏差去判本版本的生死。** *Fix:* AB-13B 明确「触发卡转化率仅统计驱虫/粮量两类；疫苗类单列为『问诊预约转化率』」。

**[H23] 复购引擎有一个未被承认的冷启动期，而 A-16 的验证恰好落在这个窗口内**（§3.9 / A-16）— 三条机制的前置条件叠加后，FR-109 需要「电商订单历史（最近一次 Makanan 购买）∧ 商品配了日喂量（DEP-6 未交付）∧ 档案体重」三者同时成立——**第一个条件在上线首月对全体用户恒为假**。即上线初期「复购引擎」实际只剩 FR-107 一条静态规则筛选在跑，而 A-16 的验证方式是「上线后看 `repurchase_card_clicked` 与整体转化对比」——**在冷启动期采到的数据必然低估复购引擎，并可能导致错误的 kill 决策**。两份 PRD 没有一处承认存在冷启动期，也没有替代触发（如按品种/年龄的通用周期先兜底）。（这与 CODE-2/CODE-3 是不同层面：那两条讲字段不存在，这条讲**即便字段全有、覆盖率仍不足以支撑 A-16 的判定**。）

**[H24] 版本没有成功指标目标值与 kill criteria**（§1 / §5 / A-16 / AB-13B）— §1 目标 2 称复购引擎是「版本存在的意义」，但全文没有任何数字门槛：A-16 的判据是「若触发卡点击率不**显著**高于普通商品曝光」——「显著」没有数值、没有观察窗口、没有不达标时的处置。**上线后没有任何一句话能裁决「复购引擎是否成立」。** 对一个把版本存在意义押在单一机制上的 launch 级 PRD，缺 kill criteria 是硬伤。*Fix:* §1 后增补 Success Metrics（建议 SM-1~SM-4 编号以便下游引用），含倍数门槛、30 日复购率目标、观察窗口（建议 8 周）、不达标处置，并让 A-16 指向该 SM。

**[H25] 无任何 counter-metric，13 个事件只测量上行**（§5）— 本版本已知的四个自伤面全部无事件：复购推送疲劳（无退订/权限关闭/触发卡关闭事件）、Tab 替换对被替换模块的伤害（§5 自己要求取基线，却没定义被替换 Tab 的对照事件名）、FR-110 边界侵蚀（问诊→商品跳转占比无事件）、两类溢价发放规模（A-21 认定的真正浮存风险源，无事件也无看板行）。另缺 `cart_viewed`（购物车→结算漏斗断一节）与超服务范围阻断事件——**17 屏里专门画了「结算页超服务范围」，却没有对应埋点，这个最确定的流失点永远不可知。**

**[H26] AB-13B 与 AB-13A/13C/13D 建在两套互不相通的数据源上**（AB-13B / AB-13C ↔ AB-13A / AB-13D / §5）— AB-13B 全部指标来自 §5 的 PostHog 事件，AB-13C 的「缺货损失」也直接写成 `out_of_stock_viewed` 事件量；而 AB-13A/13D 的 GMV、毛利、对账来自业务库。PostHog 是第三方 SaaS，后台要么反向拉其 API、要么补一套服务端埋点——**两份 PRD 都没有提出这个要求，也没有列为依赖**。同时客户端事件天然带丢失率与广告拦截偏差，把它当作影响补货决策的**对账级看板**口径而不加说明，是把分析口径当财务口径用。

**[H27] A-17 比 decision-log 更不诚实，掩盖了已失效的缓释措施**（§10 A-17 ↔ decision-log N-2）— A-17「自营备货的资金占用不拖垮跑道」标致命度=中，验证方式写「承接变现模型假设 D，属财务侧，**不在本 PRD 验证**」。但 N-2 明确写：假设 D 的原文缓释措施是「先抽佣/代采、控自营备货」，「改为直接自营后，**该缓释失效**」。**PRD 把一个「原有护栏已被本版本亲手拆掉」的假设写成了「照旧承接」。** *Fix:* A-17 改写为承接 N-2 原文，致命度上调，§8 加一行「备货上限与周转纪律」（责任方=商务+财务，阻塞=首批采购）。

#### 合规、安全与护栏

**[H28] 本版本首次建立 PII 数据集，两份 PRD 与依赖清单里零合规覆盖**（FR-98 ↔ AB-11A / §7 权限 / DEP-1~8）— FR-98 引入收货人姓名、手机号、精确到门牌的详细地址，并明确「手机号是履约联系方式，**不与账号手机号互通**」——等于新建了一份与账号体系分离的个人数据集。后台 AB-11A 的**列表字段**直接含「收货人/电话」，筛选支持按**电话关键词模糊搜全站订单**，详情展示完整地址。而 §7 权限只为「进货价与毛利」单列权限位（理由是"采购成本是商业敏感信息"），对地址与手机号**没有任何脱敏、访问控制或访问审计要求**。**DEP-1~DEP-8 里没有一条涉及印尼 UU PDP 个人数据保护法。**

**[H29] 新增 PII 与实物履约数据未登记进注销级联删除/匿名化——违反项目硬护栏**（§6 跨文档影响表 / FR-98 / FR-101 / FR-106）— CLAUDE.md 把「注销级联删除/匿名化」（story 7.3，按 D1/D2 落实）列为三类安全攸关节点之一。本版本第一次让注销动作可能撞上：一个 `已发货` 的实物订单（收货人信息是履约必需，删不得）、一笔待退款的 PawCoin（不可提现不可转让，删了等于没收）、一个待质检的退货包裹。**两份 PRD 零涉及**，§6 表也没有任何一行指向账号注销的数据生命周期处置；FR-98 的地址簿是履约凭证还是个人数据（两种定性导出相反的处置）也没定性。财务留存与删除权的天然冲突（已完成订单需留存对账）同样未表态。

**[H30] 订单号规则违反「对外标识不可枚举」护栏，且 PRD 把它写成了优点**（FR-102）— 原文「订单号规则：`TT` + `YYYYMMDD` + **8 位自增**。与既有虚拟商品订单号规则隔离，**便于对账区分**自营实物与虚拟商品收入」。CLAUDE.md 强制护栏写明「对外暴露标识一律**不可枚举 token**，不用自增 id 直接外露」。`TT`+日期+自增是教科书式可枚举标识：任何用户从自己的订单号即可推断平台当日单量与累计单量（对一个还在验证 A-15「宠主是否愿意在 TailTopia 买粮」的产品，这是直接泄露最敏感的经营数据），且可枚举遍历探测他人订单。8 位自增是全局递增还是按日重置也没写（按日重置可枚举性更强）。**对账区分的诉求用不可枚举 token + 独立内部序列同样可满足，不需要把序号外露。**

**[H31] §5 埋点未声明 PII 禁入规则**（§5）— 本版本首次采集姓名/手机号/详细地址，§5 定义了 13 个上报事件却**没有一句规定哪些字段禁止进入 PostHog**。CLAUDE.md 将「严禁记录 PII / 健康数据 / 令牌 / 签名 URL」列为强制护栏，而 `repurchase_card_impression` 还带 `pet_id`（关联健康数据语义）。*Fix:* §5 增加属性规约：禁止上报姓名/手机号/详细地址/邮编；`pet_id` 明确为不可反查的内部标识；商品图/凭证图仅传 id 不传签名 URL。

**[H32] PPN / 发票在用户端完全缺席，§7 也未排除，而 DEP-3 把开票标为「阻塞上线」**（FR-97 ↔ DEP-3 / DEP-8 / AB-13D）— DEP-3 原文含「PPN 增值税登记与开票」，阻塞程度「高，阻塞上线」。但 FR-93~FR-110 **没有任何一条 FR** 描述用户如何取得收据或发票；FR-97 金额明细只有「商品小计/运费/免运费抵扣/应付合计」四行，**没有税额行**，零售价是否含税一字未提；FR-102 订单详情无票据入口；后台模块 10–13 无开票模块；退款后的票据冲红完全空白。**一个被自己标注为「阻塞上线」的能力，在两份 PRD 中既没有需求也没有被 §7 排除——它只是没写。**

**[H33] FR-98 的地址字段有两处会导致面单被承运商拒收的模糊定义，且行政区划数据源无归属**（FR-98 ↔ AB-11C）— 手机号写「印尼格式，**+62 前缀，8–13 位**」：8–13 位是含 +62 还是不含、是否允许前导 0、与账号手机号是否同一套校验，全未定义（印尼手机号去 0 后常见 9–12 位，**8 位会放进大量无效号码**）。邮编「5 位数字」正确，但**没有任何邮编与所选 Kecamatan 的一致性校验**——固定运费表按 Kecamatan 计费、承运商按邮编派送，不一致时无人拦截，差额直接落在 A-19 上。更根本的是三级级联（Provinsi / Kota-Kabupaten / Kecamatan）的**数据来源从未指定**：内置静态表？第三方 API？Kemendagri 码表？印尼有 7,000+ 个 Kecamatan 且持续调整；AB-11C 说服务范围「支持批量导入」，导入主键是什么码表也没说。**必须在架构前定死的外部数据依赖，DEP-1~8 无一条覆盖。**

#### 配置、引用与下游

**[H34] AB-6D 的两个开关在用户端零行为定义，且「总开关」与 FR-100A 规则 5 的原则正面冲突**（AB-6D ↔ FR-100A 规则 3 / 规则 5 / FR-97）— AB-6D 三个配置项中，「电商 PawCoin 支付总开关」与「是否允许 PawCoin 抵扣运费」在用户端**完全没有对应的用户可见行为**：总开关关闭后结算页是消失、置灰还是报错？已有余额的用户看到什么解释？运费开关关闭后规则 2「订单创建时固化的支付比例」按含运费还是不含运费算、部分退款拆分怎么走？（FR-100A 规则 3 是**无条件陈述**：「运费计入订单总额，**一并**参与 PawCoin 抵扣与比例拆分」，通篇没有可开关的表述。）**更严重的是与规则 5 的原则冲突**——规则 5 立了一条原则「暂停的是充值入口，不是消费出口。已持有余额的用户若因此买不了东西，**等于对已付款用户违约**」，而总开关关闭做的恰恰就是这件事（后台自己也承认「体验代价大」）。同一件事被一处定性为「违约」、另一处定性为「可接受的故障回退」。另：AB-6D 写「配置变更不追溯已成立的订单」，而总开关的设计用途正是「Coin 扣减链路出 bug 时一键回退」——**开关管不到它被设计出来要救的那批订单**。

（相关）**规则 2 与规则 4 在余额超上限时行为未定义**：余额 1.5M、订单 1.2M 时，「余额优先全额抵扣」必然被 Rp 1.000.000 上限截断，PRD 没有一句说明此时是自动截断、拒绝下单还是提示用户；AB-6D 又把上限做成可配置项且**无最小值校验或告警**——运营调到 Rp 100.000，每一单都会被截断，而结算页没有任何解释截断的文案位。

**[H35] 用户端写死的四个时限，后台零配置零提及**（FR-100 / FR-102 / FR-104 / §4.2 ↔ 后台全文）— 待支付超时 **60 分钟**、自动确认收货 **7 日**、退货窗口 **7 日**、寄回超时 **7 日**——**四个全部硬编码，后台无一处提及或提供配置**；AB-11B 反而引入了另一个未定义的 **N**（「已发货超过 N 日未确认收货」），AB-12A 也无「超窗自动拒绝」规则、CS 只能肉眼算日期。decision-log D-3/OQ-27 只讨论了「两个 7 日叠加是否过长」，**从未讨论过它们是硬编码还是可配置**。全硬编码意味着任何调整都要发版——对一个刚上线的自营电商，7 日窗口几乎必然在前 3 个月内被调整；这与 AB-6D「一键回退，**不需发版**」体现的运营预期完全不一致。（同类还有 FR-108 的 30 日频控、FR-109 的 7 天提前量。）*Fix:* AB-11C 或新建「AB-11E 履约时限配置」收拢这些值，沿用 AB-6D「变更不追溯已成立的订单」的措辞。

**[H36] FR-107 声明「犬猫年龄阈值可后台配置」，后台无该配置项**（FR-107 步骤 2 ↔ AB-10A / 模块 10 全部）— FR-107「按 `适用年龄段` 匹配档案年龄（幼年 <1 岁 / 成年 1–7 岁 / 老年 >7 岁，**犬猫阈值可后台配置**）」；步骤 3「按 `适用体型` 匹配档案体重」同样隐含一组体重→体型映射阈值。后台只提供了商品侧三个过滤标签，**没有任何「宠物侧阈值」配置**。犬猫的年龄分段差异很大（猫的「老年」通常 >10 岁），**首版就会需要调**。

**[H37] AB-6C 关于「为买粮而充值」的论证方向，与 A-20 / L-7 的自纠结论相反**（AB-6C:276 ↔ A-20 / decision-log L-7）— AB-6C 写「为买粮而充值会**显著改变浮存的增长斜率**——这是用户端假设 A-20 的监控依据」，但 A-20 的结论是反向的：「平台不做充值促销，用户没有理由先充值再买粮而不直接 QRIS 付……**净效应预期为浮存下降**」。L-7 把这写成「连带被推翻的三处」之一，其自纠已传导到 AB-6D 与 AB-6C 的溢价段，**唯独漏了这一句**。后果是运营看着 AB-6C 建的监控视图预期浮存上涨、实际看到下降，进而怀疑数据或做出反向处置——正是 L-7 警告的镜像错误。
