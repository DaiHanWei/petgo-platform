## 1. 版本目标

1. **一个账号可以养多只宠物**：印尼养猫家庭普遍不止一只，单宠物限制把这部分用户挡在门外，也让他们的第二只、第三只宠物没有地方记录。
2. **宠物名额成为等级权益和付费点**：默认 1 只，靠 Tailrent Level 永久解锁，或按月租用，给升级和付费都提供理由。
3. **修掉单宠物假设留下的隐患**：现在代码里大量「按账号取唯一一只宠物」，账号一旦有两只宠物，首页推荐会静默退回时间倒序，访客统计会串宠。

**核心指标：** 多宠物账号占比 · 人均宠物数 · 月租名额购买人数与续租率 · 第二只宠物建档后 7 天内的 Diary 发布数

## 2. 现状（2026-10-13 核实代码）

| 维度 | 现状 |
|---|---|
| 单宠物限制 | 两层：DB 唯一约束 `uq_pet_profiles_owner_id`（V3）+ `ProfileService.create` 已有档案就返回 409 |
| 按账号取唯一宠物 | `PetProfileRepository.findByOwnerId` 返回单个，有第二条就会抛异常。后端约 **60 处**调用，加上 `PetProfileQueryService` 的 6 个跨模块读口 |
| 接口 | 「我的宠物」相关接口全部是 `/pet-profiles/me/*`，从登录态推出唯一一只宠物，**没有 petId 参数**（档案、时间线、日历、统计、里程碑、健康记录、身份证、Tailsonality、护照、登机牌、新手任务等） |
| App | `petProfileProvider` 单值，被 **17 个页面文件**使用；发布页、打卡都默认取唯一一只宠物，没有宠物选择器 |
| 内容与宠物 | `content_posts.pet_id` 单值，**只有 Diary（`GROWTH_MOMENT`）会写入**；Moment / Tips 从第一版起后端就把 pet_id 写死为空 |
| 已按宠物存的数据 | 里程碑、护照、打卡盖章（已是多对多 `place_checkin_pets`）、Tailsonality 结果与徽章、登机牌、健康记录、生日 / 纪念日推送、分享奖励（一宠一次）——**表结构不用改**，只是入口都先按账号取宠物 |
| 按账号存的数据 | 身份证 `id_cards`（只挂 user，不挂宠物）、年龄卡分享奖励、`tailsonality_owner_type` |
| 推荐物种 | 用户物种：取唯一一只宠物的物种，单个字符串。**多宠时取宠物抛异常 → 整个 Feed 退回时间倒序**。内容物种：`ContentSpeciesResolver` 按作者宠物取，多宠时静默取最后一只；文档里「Diary 按 pet_id 取物种」从未实现。FR-95 两个多物种分支在代码里只有注释 |
| 删除宠物 | 只有 `DELETE /pet-profiles/me`（按账号删唯一一只），没有按 petId 删除；删除时 `idCards.markProfileDeleted(userId)` 会给该用户**所有**身份证打「档案已删」标记 |
| 访客视图 | 按 petId 的站内访客接口已有；但访客统计和徽章墙按**账号**算，多宠后会串到别的宠物 |
| 他人主页 | `GET /users/{userId}/pet` 返回单只；1.3.4 PRD 要求「组件按列表实现」，代码未做 |
| pet_status | 只由用户在 `PATCH /me` 主动修改，与宠物数量无关 |
| 后台用户抽屉 | 「宠物档案」页签模板已经是列表，但服务端只取 1 条 |
| 订阅 / 有效期 | **不存在**，现有付费全部是一次性永久解锁。payment_intents 没有业务引用字段，靠业务表反向保存 `payment_intent_id`（可参考 `KeepsakePurchaseService` 的「业务行 + 购买行 + 幂等键」模式） |
| 定时任务 | Spring `@Scheduled` + DB 状态机；到期扫描可参考 `SipdhExpiryScanner`、`PaymentIntentExpiryScanner` |

## 3. 功能与需求

### 3.1 多宠物账号与切换（FR-145）

#### 已确认项

**建档与删除**
- 一个账号可以有多只宠物，**数量受名额限制**（见 FR-146）；名额已满时，「添加宠物」入口提示「名额已满」，并给出两条路：升级解锁 / 月租名额
- **删除单只宠物：** 在宠物档案编辑页删除，只删这一只。物理删除范围沿用 V1.0.0 FR-39A（健康事件与记录、里程碑、分享记录、打卡、护照、Tailsonality 结果与徽章；Diary 内容保留但解除与这只宠物的关联）。删除后**名额释放**，可以再建
- **防「删宠重建」刷成长值**（2026-10-13 拍板）：里程碑按宠物完成，每完成一个得 S/M/L 成长值；删掉宠物再建一只，里程碑可以重新完成。规则：**同一账号、同一里程碑代码的成长值，累计最多发 5 次**（= 账号宠物上限），超出部分里程碑照常完成、不发成长值。规则由 ① 的成长值引擎按（用户, 里程碑代码）计数实现，本分支只需在 `MilestoneCompletedEvent` 里带上里程碑代码（现状已带）
- 删除账号**最后一只**宠物后，沿用现状（2026-10-13 拍板）：`pet_status` **不自动改**（宠物去世的用户不该被系统改成「计划养宠」），Diary Tab 显示现有的「还没有宠物档案」空态；用户可以自己去设置里改

**切换当前宠物**
- **Diary Tab（成长档案页）顶部加宠物切换器**（头像一排，点击切换），时间线、日历、统计、里程碑、健康记录、「Know more about your pet」入口都跟着切换
- App 记住**上次查看的宠物**，下次进入 Diary Tab 默认显示它
- **首页 Discovery 推荐不跟随切换**，始终按账号全部宠物的比例（见 FR-147）

**「我的」页与他人主页**
- 「我的」页宠物区改为**宠物列表**（圆形头像一排，最后一格是「添加宠物」），点某只宠物进入它的 Diary Tab
- 他人主页宠物区按 1.3.4 已定的样式：**圆形头像一排，超过 4 只横向滑动**；点击进入该宠物的访客视图
- 访客视图的统计、徽章墙改为**按这只宠物**计算（修复现状按账号计算的问题）

**按宠物计算的功能**

付费项目**每只宠物单独计费**（2026-10-12 拍板）。下列功能在使用前都要确定是哪只宠物：

| 功能 | 宠物怎么定 |
|---|---|
| 里程碑、健康记录、宠物名片 H5、年龄换算卡、护照、登机牌、Tailsonality | 跟随 Diary Tab 当前选中的宠物（这些入口都在 Diary Tab 下） |
| 身份证 KTP | 创建时选择宠物并预填资料，只列正常状态的宠物（卡片本身仍只挂账号，沿用 1.3.4「卡快照不挂宠物档案」的口径） |
| Diary 发布 | 发布页选择宠物，**至少选一只、可多选**（见 FR-147） |
| 场所打卡 | 打卡时选择这次带了哪几只宠物（2026-10-13 拍板）：**默认一只都不选**，至少选一只才能打卡；只列正常状态的宠物；只有一只正常宠物时不显示选择器、自动选中。被选中的每只宠物各自盖章、各自完成里程碑。**「今日已打卡」按宠物算**（2026-10-13 拍板）：今天已在该场所打过卡的宠物在选择器里置灰，所有正常宠物都打过后按钮才变为已打卡。（不存在「全部宠物只读」：默认名额 1 永久有效，有宠物就至少 1 只正常） |
| AI 问诊 | 有两只及以上宠物时，**开始问诊前先选是哪只**（单选，2026-10-13 拍板），AI 回答参考这只宠物的物种、年龄、体重，结论存档到它的健康记录；只有一只时不弹选择。**只读宠物可以被选来问诊，但结论不能存档**，存档时提示「续租后可存档」 |
| 兽医咨询 | 与 AI 问诊同一规则（2026-10-13 设计评审补充）：有两只及以上宠物时，点「Mulai konsultasi」先单选宠物；只读宠物可选、结论不能存档 |

- **分享奖励维持「每只宠物各领一次」**：现有各类分享奖励已有账号级全局月度上限（FR-96 `share_reward_monthly_cap`），多宠物不会突破这个总量
- **新手任务按账号算**：N-3「宠物档案完整度 100%」任意一只宠物达到即完成；N-4「第 5 条快乐时刻」按账号累计
- 生日、陪伴纪念日推送**按每只宠物分别发**（2026-10-13 拍板；现状已按宠物去重，不用改），同一天多只宠物的推送不合并

**旧版本 App 兼容**
- 2026-10-13 拍板：旧版本（1.4.0 之前）仍然调用 `/pet-profiles/me/*`，这些接口保留，返回账号的「**默认宠物**」= 最早创建且处于正常状态的那只。旧版本里只能看到、只能给这一只发 Diary，也不能新建第二只（旧版本建档页已有「已有档案直达」守卫）。**不强制更新**。客服话术需知会：多宠物用户在旧版本上只看到一只宠物，更新 App 即可

#### 边界与不做项

- 不做宠物排序拖拽（按创建时间排列）
- 不做宠物转让给其他账号
- 不做多宠物合并成一个「家庭档案」
- 1.5.0 拼图「多宠用户开图规则」不在本版本，届时再定

#### 验收标准

- **AC1**：账号名额为 2 时可以建第二只宠物，建第三只时提示名额已满，并给出升级 / 月租两个入口
- **AC2**：Diary Tab 切换宠物后，时间线、日历、统计、里程碑、健康记录都只显示这只宠物的数据；退出再进入，默认停在上次查看的宠物
- **AC3**：删除其中一只宠物，另一只宠物的数据、身份证卡片都不受影响（身份证不再被误打「档案已删」标记）；删除后名额释放
- **AC3a**：有 3 只正常宠物的用户打卡时，选择器默认全不选，不选不能打卡；选 2 只后两只各盖一个章。只有 1 只正常宠物时不显示选择器
- **AC3b**：选一只只读宠物做 AI 问诊可以正常问诊，但存档时提示「续租后可存档」，健康记录没有新增
- **AC4**：他人主页显示对方全部宠物，超过 4 只可横向滑动；点进某只宠物，访客统计和徽章墙只显示这只宠物的
- **AC5**：有 2 只宠物的账号，首页推荐**仍按推荐排序**，不会退回时间倒序
- **AC6**：旧版本 App 登录多宠物账号，能正常看到默认宠物的档案，不报错
- **AC7**：同一账号两只宠物各分享一次宠物身份证，各领一次奖励；当月累计达到账号全局上限后不再发放

#### 影响面

- **DB：** 删除唯一约束 `uq_pet_profiles_owner_id`
- **后端：** 约 60 处 `findByOwnerId` / `existsByOwnerId` 和 `PetProfileQueryService` 的 6 个读口改为按 petId 寻址或返回列表；`findIdentitiesByOwners` 的 toMap 改为按账号聚合列表；新增 `/pet-profiles/{petId}/*` 系列接口（或给现有接口加 petId 参数，二选一由技术方案定），`/me/*` 保留为默认宠物；新增按 petId 删除；`ProfileDeletionService` 改为按宠物删除；**删除单只宠物时不再给身份证打「档案已删」标记**（身份证卡不挂宠物、是独立快照，无法判断属于哪只；账号注销时照旧随账号删除）
- **静默失效点逐一修复：** 推荐取用户物种（Feed 退回时间倒序）、`ContentSpeciesResolver`（取最后一只）、`LifecyclePushJob`（取最早一只）、访客统计与徽章墙（按账号算）、`MilestoneAutoCompleteListener`（按账号完成）、`MilestoneCheckInService`（不校验帖子属于哪只宠物）
- **App：** `petProfileProvider` 改为「宠物列表 + 当前宠物」；Diary Tab 切换器；「我的」页宠物列表；他人主页宠物列表；发布页、打卡、AI 问诊、身份证创建的宠物选择；`ApiPaths` 的 `/me` 路径按宠物改造
- **后台：** 用户抽屉「宠物档案」页签服务端改为取全部宠物（模板已是列表）
- **回归：** 单宠物账号的全部现有功能须完整回归，这是本次改动面最大的风险

### 3.2 宠物名额与月租（FR-146）

#### 已确认项

**名额怎么算**（2026-10-12 拍板）

```
名额 = 1（默认）
     + 1（Tailrent Level ≥ Lv5）
     + 1（Tailrent Level ≥ Lv10）
     + 当前有效的月租名额数
上限 5 只
```

- 等级名额是**永久的**（不需要续费），但按**当前等级**计算：因退款等原因降级、等级名额减少时，**已建的宠物保留、照常使用，只是不能再新建**
- 月租名额**不受等级限制**：Lv1 用户可以直接租 4 个，达到 5 只
- 名额**实时按当前等级 + 有效月租计算，不单独存储**（2026-10-13 拍板；读 ① 的 `GrowthQueryService.getLevel`），避免等级下降、月租到期、门槛调整等变化漏更新

**月租**
- **每个名额每月 Rp5,000**（2026-10-12 定 Rp15,000，**2026-10-13 改为 Rp5,000**；价格后台可配，见 AB-34），QRIS / PawCoin 都能付，**月租不设 QRIS 最低金额**（2026-10-13 拍板；与送礼「QRIS 单次 ≥ Rp10,000」不同），租 1 个 Rp5,000 也能用 QRIS
- 支付用途 `PET_SLOT_RENT`（由 ① 统一新增），按数字服务档返成长值（每 Rp1,000 = 5，由 ① 自动处理）
- **不自动续费**（2026-10-13 拍板）：QRIS 无法代扣，PawCoin 自动扣款容易引发「没同意就扣钱」的客诉。到期前 **3 天**发提醒，点通知直达名额管理页，用户手动续租
- **每个月租名额单独计算有效期**（2026-10-13 拍板）：自付款成功起 **30 天**；续租在当前到期日上顺延 30 天，提前续不吃亏（例：10/31 到期、10/28 续租 → 新到期日 11/30）。名额管理页可以勾选多个名额一次续租、一次付款；各名额分别提醒、分别到期
- **租用时可选数量**（2026-10-13 拍板）：1 ~ 「5 − 当前名额」个，显示总价（如 3 × Rp5,000 = Rp15,000），一次付款；同一次租的名额到期日相同，之后仍按名额分别续租
- **租用期间升级导致名额超过 5**（2026-10-13 拍板）：名额仍封顶 5，**多出的月租名额本期不退款**；到期后只能续到「5 − 等级名额」个。例：Lv4 用户默认 1 + 月租 4 = 5，升到 Lv5 后等级 +1，到期后最多续 3 个
- **升级提示（2026-10-13 拍板）：** 只要用户**有生效中的月租名额**、并因升级（Lv5 / Lv10）获得一个永久名额，升级庆祝页就显示一段**正向**提示。文案方向：「🎉 恭喜！你已永久解锁一个宠物名额。从下次续租开始，可以少租一个名额，这个永久名额会一直陪着你和毛孩子。」
  - **文案原则：** 只讲「得到了什么、以后能省什么」，**不出现**「闲置」「浪费」「本期不退款」等让用户觉得这个月月租白付了的字眼
  - 名额管理页同步显示：永久名额 +1，下次续租时默认少勾一个月租名额
  - EN / ID 最终文案由本地团队提供

**月租到期后的只读状态**（2026-10-12 拍板）
- 月租到期导致名额小于已建宠物数时，**超出名额的宠物进入只读状态**
- **用户自己选**保留哪几只继续正常使用；到期那一刻用户还没选的，系统先按「**最早创建的优先**」保留（2026-10-13 拍板），用户之后随时可以在名额管理页改选（Hewanku 标题右侧「Ubah pilihan ›」）；只读提示（Diary Tab 只读横幅、只读拦截抽屉）只提供续租，不提供改选（2026-10-15 拍板）。例：A、B、C、D 四只，名额剩 2 → 先保留 A、B
- **只读宠物禁止所有「新增记录」的操作**（2026-10-13 拍板）：发 Diary、被选为打卡宠物、里程碑打卡、新增健康记录、编辑档案、购买新的付费项目（KTP / Tailsonality / 护照快照 / 登机牌等）。**查看、分享、收礼照常**。只读的意义是「这只宠物暂停新增记录」，只禁 Diary 会让只读形同虚设
- **续租后立即恢复**正常状态
- 只读宠物在 Diary Tab 切换器上显示一个锁标，顶部提示「名额已到期，续租后可继续记录」+ 续租按钮

**名额管理页**（入口：「我的」页宠物列表、名额已满提示、只读提示）
- 显示：当前名额构成（默认 1 · 等级解锁 N · 月租 N）、每个月租名额的到期日
- 操作：租用新名额、续租、在多只宠物之间选择哪几只保持正常状态

**通知**
- `PET_SLOT_EXPIRING`：到期前 3 天，「你的宠物名额将于 X 月 X 日到期」
- `PET_SLOT_EXPIRED`：到期当天，「名额已到期，XX 已进入只读状态」（没有宠物因此变成只读时不发）
- 两个类型由 ① 在通知类型约束迁移中统一新增，本分支只写文案与触发；推送分类由 ④ 映射，**归「订单与账号」，用户不能关**（2026-10-13 拍板：与付费权益直接相关，错过提醒会变成客诉；每个名额每月最多 2 条）

#### 边界与不做项

- 不做自动续费
- 不做年租、季租等其他周期
- 不做名额退款（虚拟权益，付款后不退）
- 不做名额赠送给其他账号

#### 验收标准

- **AC8**：Lv1 无月租用户名额为 1；升到 Lv5 名额变 2；升到 Lv10 名额变 3；租 2 个后名额为 5，不能再租
- **AC9**：Lv10 用户有 3 只宠物，因退款降到 Lv9，3 只宠物都照常使用，但不能建第 4 只
- **AC10**：月租名额到期且未续租，超出名额的宠物变为只读：可以查看、分享、收礼，不能发 Diary、不能被选为打卡宠物、不能里程碑打卡、不能记健康记录、不能编辑档案、不能购买新的付费项目；续租后立即恢复
- **AC11**：到期前 3 天收到提醒通知；提前续租后，新到期日 = 原到期日 + 30 天
- **AC12**：月租付款成功后，名额即时增加；付款失败 / 过期不增加；回调和轮询同时到达只生效一次
- **AC13**：月租付款按数字服务档产生成长值（Rp5,000 → 25）
- **AC13a**：Lv4 用户默认 1 + 月租 1，升到 Lv5 时升级庆祝页出现「永久解锁一个宠物名额」的正向提示，文案中没有「闲置 / 浪费 / 不退款」；没有生效中月租的用户升级时不出现这段提示
- **AC13b**：运营在后台给用户补发 7 天名额后，用户名额即时 +1，7 天后到期并照常提醒；购买记录显示「运营补发」和操作人
- **AC13c**：月租到期时用户有 A、B、C、D 四只宠物、名额剩 2 且未做选择，A、B 保持正常、C、D 只读；用户在名额管理页改选 A、D 后即时生效

#### 影响面

- **后端：** 新增月租名额表（user_id、名额序号、生效时间、到期时间、状态）与购买记录表（参考 `keepsake_purchases`，保存 `payment_intent_id`）；`PaymentIntentPaidEvent` 新增 `PET_SLOT_RENT` 的处理器；纯 PawCoin 支付路径同样要有；到期扫描器（`@Scheduled`，参考 `SipdhExpiryScanner`）负责到期提醒、到期处理和只读状态切换
- **宠物状态：** `pet_profiles` 新增状态字段（正常 / 只读）；所有「新增记录」类接口校验宠物状态
- **App：** 名额管理页、租用 / 续租支付流程（复用通用 `showQrPaymentSheet`）、只读宠物的锁标与提示

### 3.3 内容多宠关联与推荐物种（FR-147）

#### 已确认项

**内容关联宠物**（2026-10-12 拍板）
- **Diary 类型内容必须至少选一只宠物，可以多选**（例如一条帖子同时涉及两只宠物）
- 一条关联多只宠物的 Diary **在 Feed 里只出现一次**，各关联宠物的 Diary Tab 时间线都收录它
- **Moment / Tips 不关联宠物**，发布页去掉宠物选择（后端现状本来就把这两类的 pet_id 写为空，存量数据也不会有关联）
- 只读宠物不出现在发布页的可选列表里
- 删除某只宠物时，只解除 Diary 与它的关联（2026-10-13 拍板，沿用现状 `detachPet`）：关联多只宠物的 Diary 在其他宠物的 Diary Tab 里照常显示；**只关联了这只宠物的 Diary，内容保留**，不再出现在任何 Diary Tab，但在作者的发布列表和 Feed 里照常存在，别人的点赞、评论都保留

**推荐物种（处理 1.2.0 补充 FR-95 的两个预留分支）**

| 分支 | 规则（2026-10-12 拍板） |
|---|---|
| **① 内容物种** | Diary：按关联宠物的物种；**关联了不同物种的多只宠物（如一猫一狗）→ 落通用池**。Moment / Tips：作者只有一个物种 → 取该物种；作者有多个物种 → 落通用池。运营的行级覆写 `species_override` 和虚拟号 `account_species` 优先级不变，仍高于上述规则 |
| **② 用户主物种** | 按账号各物种宠物数量比例分配权重与槽位，例如 2 猫 1 狗 → 猫 2/3、狗 1/3；余数向宠物数多的物种取整 |

- **首页 Discovery 不跟随 Diary Tab 的宠物切换**，始终按账号全部宠物计算
- 只读宠物**也计入**用户主物种（2026-10-13 拍板）：只读只是暂停记录，宠物还在、兴趣没变；只有删除的宠物不计入

#### 边界与不做项

- 不做按宠物切换首页推荐
- 不对存量内容回填物种（规则在读取时计算）

#### 验收标准

- **AC14**：发布 Diary 时不选宠物不能发布；选两只宠物发布后，两只宠物的时间线都有这条，Feed 里只有一条
- **AC15**：Moment / Tips 发布页没有宠物选择
- **AC16**：关联一猫一狗的 Diary 进通用池；只养猫的作者发的 Moment 进猫池；养猫又养狗的作者发的 Moment 进通用池
- **AC17**：养 2 猫 1 狗的用户，首页 10 个推荐槽位按 猫 2/3、狗 1/3 分配（余数给猫）

#### 影响面

- **DB：** 新增内容与宠物关联表（content_id, pet_profile_id，唯一键）；存量 Diary 的 `pet_id` 迁移进关联表；`content_posts.pet_id` **保留为「第一只关联宠物」的只读兼容字段**（2026-10-13 拍板），供旧版本 App 与未改造的查询使用，新代码一律读关联表；待旧版本用户占比足够低后再择版删除
- **后端：** Diary 时间线 / 日历 / 当天 / 统计、宠物名片 H5 最近内容、宠物推荐等按 pet_id 的查询改为走关联表；发布接口接收 `petIds` 列表并逐只校验归属与状态；`ContentPublishedEvent` 增加 `petIds`；里程碑 PUBLISH 来源改为按关联宠物逐只完成（复用 1.3.4 分支新增的 `completeForPet`）
- **推荐：** `ContentSpeciesResolver` 实现上表规则；`FeedRecommendationService` 的用户主物种从单个字符串改为物种权重；`FeedRankEngine` 槽位分配按权重；同步更新 `2.数据算法/首页推荐算法.md`

## 6. 开发注意与接口约定

### 6.1 合并顺序

**① Tailrent Level → ② 本分支 → ③ 送礼 → ④ 推送开关与收藏**（详见 ① PRD §6.1）。本分支排第二：改了「内容与宠物」的关联结构，③ 的送礼对象依赖它。① 合入 dev 后，跨线衔接在从 dev 切出的对齐分支上做（merge 本分支，不 rebase，见 ① PRD §6.1）。

### 6.2 本分支使用、由 ① 提供的部分（本分支不要再做）

| 内容 | 由 ① 提供 | 本分支只需要 |
|---|---|---|
| 支付用途 `PET_SLOT_RENT` | ① 的支付用途约束迁移 | 直接使用，**不改约束** |
| 通知类型 `PET_SLOT_EXPIRING` / `PET_SLOT_EXPIRED` | ① 的通知类型约束迁移 | 写文案与触发，**不改约束** |
| 月租的成长值 | ① 的消费返成长值（按支付用途自动归档） | **不写任何成长值逻辑** |
| 用户等级 | `GrowthQueryService.getLevel(userId)` | 计算名额时调用；虚拟号返回「不参与」，名额按默认 1 + 月租算 |
| 后台抽屉「宠物与名额」页签 | ① 加页签头和空容器 | 只往容器里填内容，**不改页签头** |

### 6.3 本分支对外提供的接口

| 接口 | 作用 | 调用方 |
|---|---|---|
| 内容与宠物关联表 + `ContentPetQuery.petsOf(postId)` | 查一条内容关联的全部宠物 | ③ 详情页送礼时选宠物；① 成长值流水写入全部关联宠物 ID |
| `ContentPublishedEvent.petIds` | 发布事件带全部关联宠物 | ① 成长值流水 |
| `PetQueryService.listByOwner(userId)` / `get(petId)`（含状态） | 按账号取全部宠物、按 petId 取宠物 | ③ 判断收礼宠物是否存在、取宠物主人 |
| `PetSlotService.quotaOf(userId)` | 当前名额与构成（含是否有生效中的月租名额） | App、后台；升级庆祝页的「永久名额」正向提示（见下方注） |

> **注：** 升级庆祝页属于 ① 的界面。「永久名额」正向提示由**本分支**在 ① 合并后、往升级庆祝页加一个条件提示块（升级获得永久名额且有生效中的月租名额时显示），不改庆祝页其他逻辑。

> **⚠️ 给 ③ 的提醒：** 只读宠物**可以收礼**，③ 不需要校验宠物状态；但宠物被删除后不能再收礼。
