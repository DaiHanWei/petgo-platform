## Story

As a 想 @ 朋友的用户,
I want 能 @ 我关注的人和关注我的人,
so that 不用先互动也能提到他们。

## Acceptance Criteria

> 层级：L0 = 纯单元 / 源码守卫（`mvn -B clean package` 可跑）；L1 = 需 Docker postgres + redis 的集成测试；L2 = 真机 / 真后端。本 story 无 L2。

**AC1 — 快捷列表（无 `q`）**〔L0 / L1〕（epics 5.1 AC1、PRD FR-157 AC1、D-15）
1. `GET /api/v1/me/mention-candidates`（不带 `q`，或 `q` 去空白后为空）**先放我关注的人**，按 `user_follows.created_at DESC, followee_id DESC`；不区分关注来源（`USER` / `SYSTEM` 都算，PRD「系统自动关注也算」）。
2. 我关注的人不足 30 人时，用**互动候选**（`mention_candidates`，`last_interacted_at DESC, id DESC`）补齐，**已在列表中的不重复**；合计最多 30 人。
3. 快捷列表**不含「关注我的人」**（PRD 规则：快捷列表 = 我关注的 + 互动补齐；粉丝只在带 `q` 时进范围）。
4. Given 我只关注了 10 个人、互动候选 40 人（其中 3 人与关注重叠），When 请求，Then 返回 30 人：前 10 个是关注的人（按关注时间倒序），后 20 个是不重叠的互动候选（按互动时间倒序）。

**AC2 — 带 `q` 的范围内查询**〔L0 / L1〕（epics 5.1 AC2、PRD FR-157 AC2、D-15）
1. `GET /api/v1/me/mention-candidates?q=ra`：只在「我关注 ∪ 关注我 ∪ 互动候选」三类范围内，按昵称**包含匹配、不区分大小写**（`ILIKE`，`%` `_` `\` 转义）；最多 **20** 条。
2. 排序：三类先后（我关注的 → 关注我的 → 互动过的），同类内按各自时间倒序（关注时间 / 被关注时间 / 互动时间）；**同一个人只出现一次**，取排序靠前的那一类。
3. **范围外的人搜不到**（不是全局用户搜索：昵称完全匹配但与我无任何关系的用户 → 结果为空）。
4. 昵称口径与展示一致：`COALESCE(users.nickname, users.display_name)`（同 `AccountQueryService.toAuthorView`）。
5. `q` 去首尾空白后长度 > 20 → 422 ProblemDetail（`AppException.validation`，App 端 `MentionDraft._maxKeywordLength` 同为 20，正常不会触发）。

**AC3 — 官方号**〔L1〕（epics 5.1 AC3、PRD FR-157 AC3）
1. Given 新用户只有注册时系统自动关注的官方号（`user_follows.source = 'SYSTEM'`），When 不带 `q` 请求，Then 快捷列表里有官方号。
2. Given 官方号（`role = 'ADMIN'`）作为作者，`mentionedUserIds` 含任一已自动关注官方号的普通用户，When 走 `MentionSanitizer.sanitize(officialId, …)`，Then 保留（官方号的粉丝 = 全体用户，D-15「官方号不特殊处理」）。本条在 **service 层** L1 验证（见「待确认 #1」：官方号经 App 端点发帖的入口在现有代码里不通）。

**AC4 — 排除规则**〔L0 / L1〕（epics 5.1 AC4、PRD FR-157 AC4、D-15、NFR1 / P-2）
1. 任一方向存在隐藏关系（拉黑或举报隐藏都算，口径同 `UserHideRelationReader.hiddenEitherWay`）→ 不出现在快捷列表与查询结果中。
2. 已注销（`users.deleted_at IS NOT NULL`）→ 排除。
3. **`DEACTIVATED`（封号）→ 排除**（本 story 新增；现有代码只排注销，架构 §1.2 第 15 条、§3.5 第 4 条）。
4. 自己永不出现在候选中。

**AC5 — 发帖 / 评论的服务端校验**〔L0 / L1〕（epics 5.1 AC5、PRD FR-157 AC5 / AC6、D-15）
1. `MentionSanitizer` 允许集合改为「互动候选表 ∪ 我关注 ∪ 关注我」，**按提交这一刻**判定；同样排除任一方向隐藏、已注销、`DEACTIVATED`（新增）、自己。
2. 范围外的 id **静默丢弃**，帖子 / 评论照常发布（201 / 200），被丢弃的 @ 退化为普通文字、对方不收到通知。
3. 原始条数 > 5 → 422（`MentionSanitizer.TOO_MANY_MESSAGE`，口径不变，先判条数再去重）。
4. 发帖（`POST /api/v1/content-posts`）、一级评论（`POST /api/v1/content-posts/{postId}/comments`）、回复（`POST /api/v1/comments/{parentId}/replies`）三处走同一套（PRD AC5「评论里的 @ 与发帖的 @ 范围相同」）。
5. 发布之后取关 / 被取关**不影响**已落库的 `mentioned_user_ids`（读路径不重新按关注校验）。

**AC6 — `relation` 字段**〔L0 / L1〕（epics 5.1 AC6、PRD §4 FR-157、P-5）
1. 每个候选带 `relation`：`following` / `follower` / `interacted`（小写，P-5）；命中多类时取排序靠前的一类（following > follower > interacted）。
2. 快捷列表里的项只会是 `following` 或 `interacted`（AC1.3）。
3. 既有字段 `userId` / `nickname` / `avatarUrl` / `level` / `tier` / `frame` 原样保留（只加字段不改语义，NFR7）。

**AC7 — 回归与守卫**〔L0〕
1. `./mvnw -B clean package -DskipTests` 绿；`MentionCandidateTest`、`MentionSanitizerTest`、`MentionCandidateViewContractTest`、`ContentServiceTest`、`CommentServiceTest`、`MentionEventPublishTest` 全绿（按 Dev Notes「必须改的既有测试」更新断言，不删不 skip 无关用例）。
2. 「不是全局用户搜索」的守卫从「端点不得有查询参数」改写为「查询只在三类范围内」（见 Dev Notes），不允许直接删掉守卫不补。

### SQL 写法（`MentionScopeDao`，D-15）

带 `q` 的查询（快捷列表同构：去掉 `follower` 一路、去掉 `ILIKE`、`limit 30`）：

```sql
WITH scope AS (
    SELECT f.followee_id AS uid, 1 AS rk, f.created_at AS at
      FROM user_follows f WHERE f.follower_id = :me
    UNION ALL
    SELECT f.follower_id, 2, f.created_at
      FROM user_follows f WHERE f.followee_id = :me
    UNION ALL
    SELECT c.candidate_id, 3, c.last_interacted_at
      FROM mention_candidates c WHERE c.owner_id = :me
),
best AS (
    SELECT DISTINCT ON (uid) uid, rk, at FROM scope ORDER BY uid, rk, at DESC
)
SELECT b.uid, b.rk
  FROM best b
  JOIN users u ON u.id = b.uid
 WHERE u.id <> :me
   AND u.deleted_at IS NULL
   AND u.status = 'ACTIVE'
   AND COALESCE(u.nickname, u.display_name) ILIKE :pattern ESCAPE '\'
   AND NOT EXISTS (SELECT 1 FROM user_hide_relations h
                    WHERE (h.holder_id = :me AND h.target_id = u.id)
                       OR (h.holder_id = u.id AND h.target_id = :me))
 ORDER BY b.rk, b.at DESC, b.uid DESC
 LIMIT :limit
```

- `rk` → `MentionRelation`：1 = `FOLLOWING`、2 = `FOLLOWER`、3 = `INTERACTED`。
- 快捷列表：`scope` 只留 rk 1 与 rk 3，无 `ILIKE`；`DISTINCT ON` 保证「已在关注里的互动候选不重复」且标为 `following`。
- **为什么排除条件写进 SQL 而不是先取再用端口过滤**：上限 30 / 20 必须在排除之后仍成立（先取 30 再剔拉黑会掉到 30 以下）——与 `UserFollowRepository.findSuggestionIds`（:118-146）、`findStripUserIds`（:155-175）同一「有意例外」。隐藏关系口径必须与 `hiddenEitherWay` 逐字一致（双向、不分 `BLOCK` / `REPORT`），类注释写明，并由 L1 用例钉住。
- 转义：`q.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")`，再拼 `"%" + escaped + "%"`；**绝不传 null 给 `:pattern`**（Postgres 推不出类型的坑，见 `PinnableContentPicker.page` 注释），快捷列表用不含 `ILIKE` 的独立 SQL。
- 性能：官方号自己作为 `:me` 时「关注我」一路 ≈ 全体用户，`DISTINCT ON` 会扫全量粉丝；现规模（≤ 500 DAU）可接受，L1 对官方号账号跑一次 `EXPLAIN ANALYZE` 记进 Completion Notes（NFR3 同口径）。

### 拍板点（按推荐实现，Completion Notes 复述）

- **① 快捷列表不含粉丝**：PRD 规则细节「快捷列表先放我关注的人，不足 30 用最近互动过的人补齐」，粉丝只在打字查询时进范围；epics AC1 同口径。
- **② 带 `q` 加限流 60 次 / 分钟 / 人**：前端 300ms 防抖后每次停顿最多一发，正常远低于此；防止脚本逐字枚举粉丝昵称。不带 `q` 不限流（与改造前一致）。429 由 App 落 E5 失败态。
- **③ `q` > 20 字 → 422**：与 App `MentionDraft._maxKeywordLength = 20`（`petgo_app/lib/features/mention/domain/mention_draft.dart`:61）同口径；不截断（截断会让结果与用户输入不一致）。
- **④ 不加 `enabled` 判断**：对外有效判据统一用 `isActive`（`deleted_at` + `status`），不额外看 `users.enabled`（推荐关注那条查询看了 `enabled`，属于另一口径，不在本 story 统一）。
- **⑤ `relation` 缺省不可能为 null**：每行都来自三类之一；DTO 仍是 NON_NULL，契约测试断言三类取值都能序列化。

### 待确认 / 发现的规划冲突（不改规划文档）

1. **「官方号发帖可 @ 任何用户」在现有代码里没有通路**（PRD FR-157 AC3 后半、epics 5.1 AC3）：官方号是 `users.role = 'ADMIN'`，签发的 JWT `role=ADMIN`（`JwtService.java`:41-58），`MentionCandidateController.currentUserId` 只认 `role=USER` → 官方号在 App 里取候选恒 401；后台两条发帖路径中 Lark 定时发帖走 `publishTrusted` **刻意不写 @**（`ContentService.java`:751-753），种子 / 批量发帖构造请求不带 `mentionedUserIds`。本 story 只在 `MentionSanitizer` 层保证「官方号作者 + 粉丝全集」可通过（AC3.2），不放开 `role=ADMIN` 访问候选接口、不改 `publishTrusted`。若产品要的是「运营在后台用官方号发帖时能 @ 人」，需另起需求。
2. **隐藏关系排除写在 SQL 里**：与 `MentionCandidateQueryService` 现有「走 `hiddenEitherWay` 统一出口（AD-7）」的写法不同，理由见「SQL 写法」；若评审坚持只走端口，则需接受「排除后可能不足 30 / 20」或做多轮补取。
3. **现有排除比 PRD 更严**：`hiddenEitherWay` 把「举报隐藏」也算在内（PRD 只写「拉黑任一方向」）。沿用现状（只升不降），不视为冲突，记录在此备查。
4. 架构 §2 / PRD 写「搜索归 1.5.4」，现有代码注释写「搜索留在 1.6.0」——改注释时统一按 PRD 写 1.5.4。
