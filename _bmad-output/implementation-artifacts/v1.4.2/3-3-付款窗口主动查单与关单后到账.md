## Story

As a 已付款的用户,
I want 回调丢了系统也能查到我的付款、码失效前订单不被关掉,
so that 付了钱的订单不会被错误取消。

## Acceptance Criteria

> 层级：`[L0]` 纯单元 / 静态 · `[L1]` 需 Docker postgres + redis（`petgo.pay.mode=stub`）· `[L2]` 真 GemPay（stag / sandbox，归 10.1）。
> 名词：**订单窗** = `shop_orders.expires_at`（建单 + 60 分钟，App 倒计时用，不变）；**码失效时刻** = `payment_intents.provider_expires_at`（出码 + 65 分钟，GemPay 固定不可调）；**宽限期** = 订单窗已过、该单仍有码未失效的这段（≤ 5 分钟）。

### AC2 — 出码：意图有效期 = 码失效时刻；出码只在订单创建后 10 分钟内 `[L0]` `[L1]`（S-1、I3，路径①）

4. `pay(...)`（`:134-178`）新判序：
   1. `requireOwn`（只读，见 AC3 路径④）；
   2. 非 `PENDING_PAYMENT`：纯币已结清（`cash_amount = 0` 且 `PENDING_SHIPMENT`）→ 兼容返回（3.2 AC5.5）；否则 409（沿用）；

   4. 订单当前意图「可复用」= `PENDING` 且 `gateway_ref != null` 且 `now < provider_expires_at` → **直接返回同一个码**（`payload` 取 `gateway_meta.payload`），不向网关再下单；
   5. 否则若 `now > order.created_at + QR_ISSUE_WINDOW` → **409 `shop-order-not-payable`**（detail「订单已无法支付」；I3：防第 55 分钟出码把库存与券占到 120 分钟）；
   6. 否则走现有 `ensureIntent` + `createCharge` + `attachCharge(…, PROVIDER_CODE_TTL)`；首次出码失败（E7）在 10 分钟内可重试，失败处理沿用 `failChargeAttempt`。
5. 推论（写进类注释）：关单最晚 = 建单 + 10 分钟（最晚出码）+ 65 分钟 = **建单 + 75 分钟**。

### AC4 — 关单前最后查单；查询失败不关单 `[L0]` `[L1]`（S-1、I2、D-11）

1. `ShopOrderPaymentService.closeOverdue(int limit)`（取代 `cancelOverdue`，**方法本身无事务**；`ShopOrderExpiryScanner.scan` 改调它，批量上限由 200 改为 50 —— 每单可能有一次网关往返）：对每个候选订单 id：
   1. `self.closeContext(orderId)`（只读事务）：重读订单与其全部意图（`shop_order_id = id`）；已非 `PENDING_PAYMENT` 或 `!isClosable` → 跳过。
   2. 取 `gateway_ref` 非空且状态 ≠ `PAID` 的意图；**一个都没有**（从未出码，或出码全失败）→ 直接 `self.closeOne(orderId)`。
   3. 否则对每个意图**在事务外**调 `PaymentReconciliationService.query(intent)`（AC5），汇总：
      - 任一 `PAID` → 交 `paymentIntentService.applyResult(cb)`（自身短事务；发 `PaymentIntentPaidEvent` → `ShopOrderPaidHandler` 按到账处理，订单此时仍 `PENDING_PAYMENT`，**正常转待发货**）→ 本单不关，清失败计数；
      - 全部为 `NOT_PAID` 且网关状态 ∈ {`FAILED`, `EXPIRED`} → 先逐个 `applyResult(cb)`（把意图推进到对应终态并发失败事件，幂等），再 `self.closeOne(orderId)`；
      - 任一 `UNKNOWN`，或任一 `NOT_PAID` 但网关状态仍为 `PENDING` → **本轮不关**，失败计数 +1（见 4.3）。
   4. `self.closeOne(orderId)`（`@Transactional`）：重读订单，仍 `PENDING_PAYMENT` 且 `isClosable` → `releaseUnpaid(order, CancelReason.PAYMENT_TIMEOUT)`（3.2：回补库存、**退币**、**按 PAYMENT_TIMEOUT 退券**、写原因与 `cancelled_at`、作废该单**所有**未终态意图）；并发已推进 → no-op（`@Version` 兜底）。
2. 3.2 的 `releaseUnpaid` 第 5 步「作废意图」在本 story 扩为：该单（`shop_order_id`）全部 `PENDING` 意图逐个 `failByToken(token, reason.name())`，不只 `payment_intent_token` 那一个。
3. 连续查询失败告警：Redis 计数 `shop:close-query-fail:{orderId}`（`INCR`，首次设 TTL 24 小时；成功关单或查到已付时 `DEL`）；计数**恰为 10 及其后每满 10** → `log.error`（只含订单 `display_no` 与次数）+ 飞书机器人（复用 `shop/order/notify/LarkMessageClient.sendText`，文案「电商订单关单前查单连续失败 {n} 次：{displayNo}，请检查 GemPay」，发送失败只 WARN 不抛）。GemPay 故障期间订单不关单、但有人知道。
4. 单笔异常不阻断其余（沿用 `cancelOverdue` 的 try/catch 逐笔写法），日志只记 orderId 与异常类名。

### AC5 — `queryCharge` 三态 + 网关调用移出事务 `[L0]` `[L1]`（I2、P-3、P-7）

### AC6 — 关单后到账：电商意图照常转 PAID + `paid_after_close`，记到原订单 `[L0]` `[L1]`（I1、D-11、FR-134.2）

1. `PaymentIntentService.applyResult`（原 `applyCallback` `:295-343`）改动 —— **只对 `purpose = SHOP_ORDER` 生效**：
   - 定义 `shopLate = purpose == SHOP_ORDER && cb.status == PAID && intent.status ∈ {FAILED, EXPIRED}`。
   - Redis 去重短路（`:306-312`）与终态守卫（`:314-316`）**对 `shopLate` 不生效**（否则先到的 FAILED 回调已占了去重键，后到的 `Failure => Success` 会被吞掉）；对其他情形**保持原样**。
   - 首次回填网关单号（`:319-321`）调用的 `attachGatewayRef` 要求 PENDING —— `shopLate` 分支不走它。
   - `shopLate` 分支：实体新方法 `markPaidAfterClose(String gatewayRef, Map meta)`（`FAILED | EXPIRED → PAID`，置 `paid_after_close = true`，`gateway_ref` 为空时顺带写入；对非电商意图调用即抛 `IllegalStateException`）→ `saveAndFlush`（`@Version` 裁决并发）→ 发布**现有** `PaymentIntentPaidEvent`（不加新事件）→ INFO 日志（只记意图 id）。
   - 送礼（`GIFT`）、充值、问诊、解锁、名额月租、门店进货单的意图：终态后到账**仍按原逻辑忽略**（送礼的「关单后到账退 PawCoin」走的是它自己的 `GiftPaidHandler` 分支，意图本身仍是 PENDING，不受影响）。
2. `ShopOrderPaidHandler.onPaid`（`:47-79`，同步 + `MANDATORY` 不变）：
   1. 找订单：`paymentIntents.findById(event.intentId())` 取 `shop_order_id` → `orders.findById`；为空时回退 `orders.findByPaymentIntentToken(event.publicToken())`（存量）；都找不到 → **ERROR** 日志（现为 WARN，`:57`）+ 飞书告警（「有一笔电商到账找不到订单：intentId={id}」），**不抛**（抛会回滚意图 PAID，那才是真丢账）。
   2. 订单 `PENDING_PAYMENT`（含宽限期、含 `paid_after_close=true` 的意图）→ `markPaid(order, GATEWAY)`，订单转 `PENDING_SHIPMENT`（S-7「宽限期内到账变待发货」）；存量单（`checkout_source IS NULL`）按 3.2 过渡规则扣币。
   3. 订单 `CANCELLED` → **记迟到款**：`ShopOrderRepository.recordLatePayment(orderId, amount, now, intentId)` 条件更新
      ```sql
      UPDATE shop_orders SET late_paid_amount = :amount, late_paid_at = :now, late_paid_intent_id = :intentId,
                             updated_at = :now, version = version + 1
       WHERE id = :orderId AND late_paid_intent_id IS NULL
      ```
      `amount` = 网关实收 = 意图 `cash_amount`（MIXED）或 `amount`（QRIS）；**不改订单状态**、不动库存 / 券 / 币；INFO 日志（订单 token、金额）。受影响 0 行且已有不同的 `late_paid_intent_id` → ERROR + 飞书（「同一订单第二笔迟到款」，交人工）。
   4. 订单为其他状态（已被另一意图付过：重复付款）→ 同第 3 步记录（若 `late_paid_intent_id` 为空）+ ERROR + 飞书；4.2 只允许对这类单「退款」，不允许「重新下单」。
   5. 第 3、4 步任何意外都 catch 后 ERROR 日志，**不向上抛**。
3. 报表：意图状态为 `PAID`，后台支付列表、财务导出等 21 处按 `PAID` 统计的口径**自动可见**这笔钱；`shop_payment_paid` 已在 3.2 改挂 `ShopOrderPaidEvent`，迟到款不会误报为一次成功下单。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 新增 `payment_intents.shop_order_id`**：没有它就无法枚举「该单所有意图」（判据）也无法给旧意图的迟到款找回订单（`shop_orders.payment_intent_token` 只存最新）。
- **② GemPay `/history` 行状态 `pending` 在关单时视为「未决」而不是「未付」**：严格按 S-1「明确 EXPIRED / FAILED 才关」；代价是若 GemPay 码过期后不翻 `Expired`，订单会停在待付款并在第 10 次触发告警。须在 10.1 / stag 用真 GemPay 验一次过期未付码的 `/history` 返回值（见「待确认」）。
- **③ 查不到订单的到账升级为 ERROR + 飞书**：这是唯一可能「钱进来了系统不认」的路径，必须有人知道。
- **④ 宽限期用户取消 = no-op**：避免把一笔即将正常到账的付款人为变成迟到款。
- **⑤ 定时查单用 Redis 锁而非 advisory xact 锁**：见 AC8.2。

### 实现提示

- 关单编排骨架（**方法无事务**，事务段全经 `self`）：
  ```java
  public int closeOverdue(int limit) {
      ShopOrderPaymentService self = selfProvider.getObject();
      int closed = 0;
      for (long orderId : orders.findClosableCandidateIds(Instant.now(), limit)) {
          try {
              CloseContext ctx = self.closeContext(orderId);            // readOnly 事务
              if (ctx == null) continue;                                 // 已推进 / 不可关
              Verdict v = Verdict.CLOSE;
              List<PaymentCallback> pendingTerminal = new ArrayList<>();
              for (PaymentIntent pi : ctx.chargedUnpaidIntents()) {
                  ChargeQueryResult r = reconciliation.query(pi);        // 事务外
                  if (r.outcome() == PAID) { paymentIntents.applyResult(r.callback()); v = Verdict.PAID; break; }
                  if (r.outcome() == UNKNOWN || r.callback().status() == GatewayStatus.PENDING) v = Verdict.HOLD;
                  else if (v == Verdict.CLOSE) pendingTerminal.add(r.callback());
              }
              switch (v) { case PAID -> clearFail(orderId); case HOLD -> bumpFail(ctx.order());
                           case CLOSE -> { pendingTerminal.forEach(paymentIntents::applyResult);
                                           if (self.closeOne(orderId)) { closed++; clearFail(orderId); } } }
          } catch (RuntimeException e) { log.warn("关单失败 orderId={} cause={}", orderId, e.getClass().getSimpleName()); }
      }
      return closed;
  }
  ```
- `applyResult` 的 `shopLate` 判定要放在 Redis 去重之前，且只在 `cb.status == PAID` 时成立；FAILED / EXPIRED 回调对终态意图仍按原逻辑短路。
- `ShopOrderPaidHandler` 在同一事务内运行（`MANDATORY`），`recordLatePayment` 用 `@Modifying` native 条件更新（不读实体再 save，避免 `@Version` 与 `markPaid` 抢同一行时把回调事务整体打回）。
- 飞书告警文本只含订单展示号 / 意图 id 与次数；不含金额以外的用户信息，不含 token。
- 时间一律服务端 `Instant.now()`；L0 测试注入 `Clock` 或把 `now` 作参数传入判据方法（`isClosable(order, intents, now)`、`displayStatusAt(now)`），避免 sleep。

## 待确认 / 发现的规划冲突

1. **`payment_intents.shop_order_id`（架构 P-8 ⑩ 未列）**：架构判据「该单所有意图都已过 `provider_expires_at`」与迟到款找回订单，都需要「订单 ↔ 全部意图」关联，现代码只有订单上的最新意图 token。本 story 在 ⑩ 迁移里新增该列并回填当前意图（AC1）。历史上已被替换的旧意图无法回填（上线后新意图都会写）。
2. **GemPay `/history` 对「过期未付」码返回什么尚未实测**：若返回 `Expired` → 正常关单；若返回 `Initial / Pending` 或 `04 data not found` → 按 S-1「只有明确 EXPIRED / FAILED 才关」，订单会一直不关并每 10 次告警。**上线前须在 stag / sandbox 用真 GemPay 下一单不付、等 65 分钟后看 `/history` 返回**（建议纳入 10.1），若是后两种需要回到规划层拍板（例如「码失效后 X 分钟仍 Pending 视为未付」）。
3. **定时查单的防重入锁**：架构 D-11 写 `pg_try_advisory_xact_lock`，但 xact 锁要求整轮在一个事务里，与 I2「网关调用移出事务」冲突。本 story 改用 Redis `SET NX PX` 锁（AC8.2），不引新中间件。
4. **宽限期在通用订单中心 `/api/v1/orders` 仍显示待支付**：架构 D-18 / 6.2 规定通用接口不动，而当前 App 订单列表用的正是它；9.1 切到新列表前，宽限期 ≤ 5 分钟内两处显示会不一致（详情已取消、列表待支付）。影响小，记录。
5. **同一订单被重复付款**（第二个意图也到账）：PRD 未覆盖。本 story 照迟到款记录到原单 + ERROR 告警（AC6.2 第 4 步），4.2 只允许对其「退款」。
6. **`StubPaymentGateway.queryCharge` 默认「已过期未付」**：stub 环境（dev / L1）的订单会在码失效后按时关单；stag 若用 stub 网关则「支付模拟器」仍可在关单前模拟到账，行为与线上一致。若 stag 实际挂的是真 GemPay 且 QRIS 不可用（P04），则未出码的单直接按无意图关单，不受影响。
