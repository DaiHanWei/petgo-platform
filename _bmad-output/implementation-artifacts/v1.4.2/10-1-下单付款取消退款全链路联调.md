## 场景

> 每个场景的「核对」全部通过才记 ✅；任一不符记 ❌ + 现象 + 已修 commit（修完重跑）。金额一律对照**服务端计价器（P-1）的期望值**，期望值由下文给出或由 1.2 / 4.1 的表驱动单测用例推出——**不以 UI 稿示例数字为准**（见「待确认」3 的取整差异）。

### S1 主链路（AC1，E2 + E1 核对）

1. U1 进 Toko → 首页「Kupon buat kamu」领 C-DISC、C-SHIP（toast「Kupon diklaim…」）。**核对**：`user_coupons` 两行 AVAILABLE；`shop_coupons.issued_count` 各 +1。
2. 进商品详情（送至 Mampang Prapatan、「Mulai Rp X」、免运进度）→ 加购 SKU-1 ×1（285.000）、SKU-2 ×2（32.000）→ 购物车底栏预估应付与「Hemat Rp X」。**核对**：`GET /me/cart` 的 `estimate` 与 1.2 计价器对同输入的输出一致；`shipping_quotes` 新增 1 行（邮编 12730）。
3. 去结算（D1）：默认地址 A、最便宜快递、保价未勾、券默认最优（C-DISC + C-SHIP 或满额免运，以 `PricingResult` 为准）、PawCoin 勾选（余额 50.000）。截图 D1。
4. 依次操作并各截一张图、记 `POST /me/checkout/preview` 响应的 `PricingResult`：换地址 B（重新询价，原快递若仍可选则保留）→ 换回 A → 换一家更贵的快递（运费减免封顶 = min(本单最低报价, 封顶)，D-7 例：最低 15.000、上限 20.000、选 28.000 → 减 15.000）→ 勾保价（保价费 = ceil(商品实付 × 0.5%)）→ 换券（把满减改为「不使用」再选回）→ 关 PawCoin（吸底「Bayar penuh lewat QRIS」）。**核对**：每次响应的应付 = 商品金额 − 满减 + 运费 − 减免 + 保价（手算核对）；`quoteToken` 在 30 分钟内同地址同商品不变。
5. 选地址 C → 提示「Wilayah ini belum bisa dikirim kurir」且提交不可用（D3）；切回 A。
6. 提交（关 PawCoin 的那一版）→ 直接拉起支付面板（E1）：倒计时、「Bayar via QRIS」金额 = 应付、保存二维码、「Saya sudah bayar」、无红色「取消支付」。**核对**：`shop_orders` 新行：`checkout_source=CART`、`coin_selected=false`、`coin_amount=0`、`cash_amount=total_amount`、券两列有值、`courier_*`、`shipping_quote_id`、`insurance_*` 与最后一次试算一致；`user_coupons` 两张 → LOCKED 且 `locked_order_id` = 本单；购物车被结算的行已删除、未勾选的行仍在；`payment_intents` 新行 `expires_at = provider_expires_at = 出码时刻 + 65 分钟`（S-1）。
7. 关掉面板 → 订单列表「Belum bayar」角标 +1、卡上倒计时 →「Bayar sekarang」再拉起**同一个码**（意图 `public_token` 不变）。
8. 点「Saya sudah bayar」（未付）→ 提示「Pembayaran belum masuk…」（E4）；10 秒内再点不重复查网关（日志只一次 `queryCharge`）。
9. 用 curl 模拟回调 settlement → 再点「Saya sudah bayar」→ 支付成功页（E6：应付金额、「Lihat pesanan」「Lanjut belanja」）→ 订单详情「Menunggu dikirim」。**核对**：订单 `PENDING_SHIPMENT`、`paid_at` 有值；券 → USED、`used_order_id`；`growth_ledger` 新增消费入账一行（规则以 1.4.0 成长值为准）；服务端事件 `shop_payment_paid` 发出（日志）；详情金额明细逐行至应付、支付方式卡只有 QRIS 行（截图 F6）。
10. 再下一单**开 PawCoin**（混合支付）：提交那一刻 `pawcoin_wallets.balance` 立即减少 `coin_amount`、`pawcoin_transactions` 有 SPEND 行且 `ref` 指向本单（**S-3：提交时扣，不是付款时扣**）；面板金额 = 现金段；回调后**余额不再变化**（付款时不二次扣）。
11. 埋点（debug 日志）：`toko_checkout_page_viewed{entry: cart}`、`toko_order_submitted{coupon_ids, coin_used, courier, shipping_fee, insurance, …}`、`toko_payment_qr_saved`（点了保存时）、`toko_order_payment_succeeded`。

### S2 立即购买（AC2，E2）

1. 记录购物车快照：`SELECT sku_id, qty, selected FROM shop_cart_items WHERE user_id=:uid ORDER BY sku_id;`
2. 详情页「Beli sekarang」→ 规格弹层选 SKU-3 ×2 → 直达结算（`toko_checkout_page_viewed{entry: buy_now}`），商品区只有 SKU-3 ×2。

## 待确认 / 发现的规划冲突

1. **D-24 stag 入口不全**：架构只列了建券、下运单、取消、标记已打款、重新下单五个；本 story 还需要**标记打款失败**（`markPayoutFailed`）、**迟到款退款**（`refundLatePayment`）、**确认入库**（`confirmReturnInbound`，S-8）、**签收后破损赔付**（S-9）四个 service 入口才能在没有后台页面时验 S5.4 / S6.4 / S6.5 / S6.6。建议 4.1 / 4.2 实现时一并加到 `ShopStagController`；没有则这些子场景记阻塞（不以手改库替代）。
2. ~~本地调 stag 入口需要内部端口~~：已收口为后台链 `/admin/stag/shop/**`（会话 + SUPER_ADMIN + CSRF 豁免），不需要内部端口。
3. **部分取消的取整方向与 UI 示例不一致**：架构 D-15「分摊满减 = floor(…)（向下取整，对用户有利）」推出 3.667 → 退 60.333（币 2.200 + 现金 58.133）；UI F17 示例写分摊 3.668、退 60.332（币 2.200 + 现金 58.132）。按决策 / 架构（floor）验收；UI 示例仅示意，App 只显示服务端值。请产品知悉 UI 示例差 1 盾。
4. **多退少补的造数方法**：重新下单「沿用原单快照、应付按原单快照」时，到账额与新单现金段天然相等，「多 / 少」只在用户 PawCoin 余额或券状态变化时出现。以 4.2 的 L1 用例构造为准；若 4.2 未定义，需架构补一句「新单币段如何取」（沿用原单币段 / 按当前余额重算）。
5. **迟到款退款是否扣成长值**：迟到款对应的原单从未「付款成功」入账成长值（关单在先），按理不应扣回；4.1 的「币段 / 现金选 PawCoin / 标记已打款各发一次 RefundSucceededEvent」若未排除 `LATE_PAYMENT`，会对没有入账的消费做扣回（`GrowthRefundListener` 找不到消费入账时只记 INFO，不会多扣，但仍需核对）。
6. **S8 只能在 stag + 真机做**：本地推送为桩；须用户明确下令部署 stag。未下令前 S8 记「待真机」。
7. **财务看板口径核对方法**：本地无后台 Lark 登录时只能用 service / SQL 复算；若需在后台页面目测，需 stag。
