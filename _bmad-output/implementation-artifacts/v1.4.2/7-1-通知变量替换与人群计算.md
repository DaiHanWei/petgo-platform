## Story

As a 运营,
I want 通知里写的「{用户昵称}」「{宠物昵称}」发出时变成每个人自己的名字,
so that 通知更亲切、打开率更高。

## Acceptance Criteria

> 层级：L0 = `mvn -B test`（纯单元 / 文件扫描，无 DB）；L1 = Docker postgres + redis 集成测试；L2 = 真机 / 浏览器视觉（本 story 无 L2，视觉验收在 7.2）。

**AC1 — 迁移 ⑧ `skipped_no_pet_count`**（R-3、D-16、P-8）`[L0]` `[L1]`
1. 新建 `petgo-backend/src/main/resources/db/migration/V20261104_2058__ops_notification_campaigns_skipped_no_pet_count.sql`：
   ```sql
   -- V1.4.2 social-topic · Story 7.1（AB-37 · 决策日志 R-3 · 架构 D-16 / P-8 迁移 ⑧）
   -- 只记「用了宠物昵称变量、因没有宠物被排除」的人数；原 skipped_count（IDS 模式无效 id 个数）口径不变。
   -- 新增 ALTER，不改 V20261012_1107 / V20261015_1209（均已应用于 stag / prod）。
   ALTER TABLE ops_notification_campaigns
       ADD COLUMN skipped_no_pet_count INTEGER NOT NULL DEFAULT 0;
   ALTER TABLE ops_notification_campaigns
       ADD CONSTRAINT ck_ops_notification_campaigns_skipped_no_pet_count CHECK (skipped_no_pet_count >= 0);
   COMMENT ON COLUMN ops_notification_campaigns.skipped_no_pet_count IS
       'AB-37：标题 / 正文任一语言用了 {{petName}} 时，因没有宠物被排除的人数（所有人群模式）；其余为 0';
   ```
2. 类型必须是 `INTEGER`（实体 `int`），**禁止 `SMALLINT`**（Hibernate `int` 映 `int4`，validate 全红）；不动 `ck_ops_notification_campaigns_counts`（已应用迁移里的约束，改它要重列且没必要）。
3. 实体 `OpsNotificationCampaign` 加 `@Column(name = "skipped_no_pet_count", nullable = false) private int skippedNoPetCount;` + getter；`ddl-auto=validate` 启动通过。
4. 存量行默认 0，列表不显示「跳过（没有宠物）」段。

**AC2 — 变量令牌与纯函数 `OpsTextVariables`**（D-16）`[L0]`
1. 新建 `com.tailtopia.notify.ops.domain.OpsTextVariables`（final 工具类，无 Spring 依赖）。存储令牌固定：`{{nickname}}`、`{{petName}}`（与界面语言无关，D-16）。
2. 提供：
   - `boolean usesPet(String... texts)` / `usesNickname(...)`：任一文本含对应令牌即 true；`usesPet(OpsNotificationCampaign c)` 看四个字段（`titleId / titleEn / bodyId / bodyEn`）。
   - `int countedLength(String text)`：每个令牌按 **20** 计，其余按 `String.length()`（与前端 JS `.length` 同口径）。
   - `String render(String template, String nickname, String petName, boolean en)`：`{{nickname}}` → 昵称（`null` / 去空白后为空 → EN `there`、ID `Sobat`）；`{{petName}}` → 宠物名；模板含 `{{petName}}` 而 `petName == null` → `IllegalArgumentException`（发送核心保证不会走到，见 AC5）。同一令牌出现多次全部替换。替换值**原样插入，不做任何转义 / 格式化**。
   - `boolean containsTyped(String text)`：检测「手打的变量」——① 任何不是两个合法令牌的 `{{…}}`（如 `{{Nickname}}`、`{{pet}}`）；② 三种语言的显示名，带半角 `{}` 或全角 `｛｝`、忽略大小写、括号内首尾空白：`用户昵称`、`宠物昵称`、`User nickname`、`Pet name`、`Nama panggilan pengguna`、`Nama hewan`（= PRD §7 `admin.opsNotify.var.tag.*` 三语去括号）。
   - `String toDisplay(String text, String nicknameLabel, String petLabel)`：令牌换成显示名（供 7.2 列表摘要 / 0 人预览「显示变量原样」用）。
3. 常量 `FALLBACK_NICKNAME_ID = "Sobat"`、`FALLBACK_NICKNAME_EN = "there"`、`VAR_WEIGHT = 20`、`DISPLAY_NAMES`（上面 6 个，供 7.2 前端检测下发）。

**AC3 — 收件人一条 SQL 批量带出昵称与宠物名**（D-16、PRD「取值规则」、AC2）`[L0]` `[L1]`
1. `OpsRecipient` 扩为 `record OpsRecipient(long userId, String locale, String nickname, String petName)`，保留 `OpsRecipient(long userId, String locale)` 兼容构造（两字段为 null），现有测试 `new OpsRecipient(i, "id")` 不用改。
2. `OpsAudienceSql.build(...)` 改为带出 `nickname`（`NULLIF(btrim(u.nickname), '')`）与 `pet_name`，宠物用 `LEFT JOIN LATERAL` 选：有物种筛选（`spec.filters().species()`）只在该物种内；**ACTIVE（非 READ_ONLY）优先，再按 `created_at, id` 最早**；全只读取最早只读；无宠物 → `pet_name IS NULL`。口径与 `profile.service.DefaultPetPolicy.pick` 一致（无物种筛选时逐条相同）。
3. **不逐人查**：整个人群一条 SQL；`OpsAudienceQuery.resolve` 的 RowMapper 读四列。
4. 不改基础过滤 `BASE_FILTER`、不改 FILTER / IDS / 四维条件的任何 WHERE 片段；`matchesUser`（开屏弹窗）不受影响。

**AC4 — 逐人替换（通知中心与推送一致）**（PRD AC1 / AC4）`[L0]` `[L1]`
1. `NotificationService.writeOpsAnnouncements` 对每个收件人：`en = "en".equalsIgnoreCase(locale)` 选语言（原逻辑），再 `OpsTextVariables.render(..., r.nickname(), r.petName(), en)` 得到该人的 title / body 写入 `notifications`。
2. 推送沿用 `OpsNotificationDispatcher.push` 取**该行** `n.getTitle() / n.getBody()`，天然与通知中心一致；不另算。
3. 空昵称：ID 文案收到「Sobat」、EN 文案收到「there」，照常发送（PRD AC4）。

**AC5 — 有宠物条件、跳过计数**（R-3、D-16、PRD AC3）`[L0]` `[L1]`
1. 任一语言的标题或正文含 `{{petName}}` → 本次发送排除没有宠物的人；排除人数写 `skipped_no_pet_count`（**ALL / FILTER / IDS 三种模式都写**）；原 `skipped_count` 只在 IDS 模式写「子表条数 − 基础过滤命中人数」，**口径不变**（无宠物的有效用户不计入它）。
2. 只用昵称变量 / 不含变量 → 不排除，`skipped_no_pet_count` 保持 0。
3. `planned_count` = 排除后的净人数（列表「已写入 / 计划」分母）。
4. 按物种筛选时 LATERAL 只在该物种内取，人群已要求有该物种宠物 → 排除数恒 0；人群「是否建了宠物档案 = 否」+ 宠物变量 → 全部排除（净 0，活动直接 DONE、recipient 0）。

**AC6 — 预计触达按净人数、净 0 拒绝**（D-16、P-5、PRD「预计人数扣除排除的人」「一个人都发不到时拦截」、AC3 / AC3b）`[L0]` `[L1]`
1. `OpsAudienceQuery` 计数一次返回 `total`（基础 + 人群条件）与 `withPet`（再加有宠物），ALL / FILTER 一条 SQL（`count(*) FILTER (WHERE …)`），IDS 分批同口径。
2. `AdminOpsNotifyService`：用了宠物变量时 净人数 = `withPet`、排除数 = `total − withPet`；否则净人数 = `total`、排除数 0。第 ② 步预估（`preview`）、第 ④ 步（`review` / `Prepared.count`）、预估闸 `checkPreview`、大范围手输门槛 `needsTypedConfirm`（> 10,000）、落库的 `estimated_count` **一律用净人数**。
3. `total == 0` → 沿用 `admin.err.ops-notify.audience-empty`（第 ② 步，现状）。
4. `total > 0 && 净人数 == 0`（只可能是用了宠物变量）：`review` **不抛**，返回带 `blockedNoPet = true` 的确认数据（7.2 渲染 I6）；`create` 抛 422 `admin.err.ops-notify.audience-empty-no-pet`（P-5「通知净人数 0 → 422」），且**先于** `checkPreview` 判（否则表单带回的 `previewCount = 0` 会先报 `preview-required`）。

**AC7 — 字数与手打校验（两处）**（D-16、PRD「长度校验」AC6 / AC8、架构 §1.2 第 16 条）`[L0]` `[L1]`
1. `AdminOpsNotifyService.prepare` 与 `OpsNotificationCampaignService.validate` **两处**都把 `String.length()` 换成 `OpsTextVariables.countedLength(...)`：标题 ≤ 120、正文 ≤ 255；超出 → 422 `admin.err.ops-notify.text.too-long`（文案改为带括号版，见 AC10）。
2. 两处都加手打检测：四个字段任一 `containsTyped` → 422 `admin.err.ops-notify.var.typed`；校验顺序 空 → 手打 → 超长（第 ① 步内）。
3. PRD AC6：标题 115 字 + 1 个变量 = 135 → 超长被拒；标题 100 字 + 1 个变量 = 120 → 通过。

**AC8 — 预览接口：本次人群随机 1 人**（D-16、PRD「预览与确认」AC7）`[L1]`
1. `AdminOpsNotifyService.sample(OpsNotifyForm f, Long excludeUserId)` → `Optional<Sample>`：从**本次人群**（同 `prepare` 的人群 + 用了宠物变量时有宠物）`ORDER BY random()` 取 1 人；尽量避开 `excludeUserId`（「换一个」），只剩他一人时仍返回他；0 人 → `Optional.empty()`。
2. `Sample(long userId, String nickname, String petName, String titleId, String bodyId, String titleEn, String bodyEn)`：四段文案为该用户替换后的真实效果（ID 段用 Sobat 兜底、EN 段用 there 兜底，同一人，UI 稿 I4「两种语言用同一人」）。
3. `review` 的结果带上首个 `Sample`；新端点 `POST /admin/ops-notifications/review/sample`（`EDIT_AUTH`，参数 = 整张表单 + `excludeUserId`）返回预览片段（片段结构见 Dev Notes「与 7.2 的边界」）。只读、不写审计、不落库。
4. 0 人时片段显示「—（扣除后没有可发送的用户）」、不出「换一个」、气泡显示变量显示名原文（I6）。

**AC9 — 定时按发送时刻取值、日志、摘要原样**（PRD「按发送时刻取值」「日志规则不变」、AC5 / AC7）`[L1]`
1. 定时活动由 `OpsNotificationScanner` → `dispatchAsync` → `run` 在**实际发送时**调 `resolve`，昵称 / 宠物名取那一刻的值（现有流程天然满足，本 story 不得把解析提前到新建时）。L1：建定时活动 → 改用户昵称 → 扫描发送 → 收到新昵称。
2. 日志：`OpsNotificationDispatcher` / `NotificationService` / `AdminOpsNotifyService` / 新增代码**不记**收件人 id 列表、昵称、宠物名、标题、正文（替换前后都不记）；只记活动 id、人数（可新增 `noPet=` 计数）。
3. 活动表存带令牌的原文（PRD「不改表结构：存的是带变量的原文」）；后台列表行 `summary` 用 `toDisplay` 显示 `{用户昵称}`（按后台当前语言的 `admin.opsNotify.var.tag.*`），**不出现任何收件人真实值**；审计详情里的标题同样是原文。

### 拍板点（按推荐实现，Completion Notes 复述）

- **① 排除放在 Java 里做、计数放在 SQL 里做**：`resolve` 一条 SQL 返回基础人群 + 宠物名（LEFT JOIN），dispatcher 按 `petName == null` 过滤并计数——同一时刻同一次查询得到「基础命中 / 净 / 排除」三个数，IDS 的 `skipped_count` 仍按「子表 − 基础命中」算，口径不变；预估 / 确认页走 `count(*) FILTER`，不拉全量。效果与「人群追加有宠物条件」（epics）等价。
- **② LATERAL 里用 `DISTINCT ON` 而非 `LIMIT 1`**：满足 `PetOwnerLookupGuardTest`（白名单文件禁 `LIMIT 1`），语义相同、每个用户至多 1 行。
- **③ 随机抽样的 `ORDER BY random() LIMIT 1` 拼在 `OpsAudienceQuery`**（该文件无 `pet_profiles` 字面量，不在守卫扫描集合内）：抽的是用户不是宠物，不违背守卫本意；类注释写明原因。若评审认为应改守卫加例外，二选一，**不得删守卫断言**。
- **④ 「换一个」避开上一位**：`excludeUserId` 作提示，候选只剩一人时返回同一人（不报错）。
- **⑤ `review` 净 0 不抛、`create` 才 422**：UI 稿 I6 要求停在第 ④ 步显示拦截；服务端提交兜底拒绝（P-5）。
- **⑥ 服务端也拦未知 `{{…}}`**：前端序列化只产出两个合法令牌，任何其它 `{{…}}` 只能是手打或伪造，统一报 `var.typed`（架构只写了「服务端对显示名再拦一次」，此为收紧，不改变正常路径）。
- **⑦ 宠物名不受物种筛选以外的条件影响**：「是否建了宠物档案 = 是」不影响 LATERAL 取法；四维条件里的物种（`filters().species()`）才限定 LATERAL。

### 实现提示

**收件人 SQL（`OpsAudienceSql.build`，伪 SQL）**
```sql
SELECT u.id, u.locale,
       NULLIF(btrim(u.nickname), '') AS nickname,
       pet.name                      AS pet_name
  FROM users u
  LEFT JOIN LATERAL (
        SELECT DISTINCT ON (p.owner_id) p.name
          FROM pet_profiles p
         WHERE p.owner_id = u.id
           /* 仅当 spec.filters().species() != null：*/ AND p.pet_type IN (:species)
         ORDER BY p.owner_id, (p.status = 'READ_ONLY'), p.created_at, p.id   -- false 在前 = ACTIVE 优先
       ) pet ON TRUE
 WHERE <BASE_FILTER> <ALL：无 | IDS：AND u.id IN (子表 :campaignId) | FILTER：appendFilter(...)>
 ORDER BY u.id ASC
```
- `:species` 与 `HAS_SPECIES` 共用同一个参数名、同一份排序后的列表（`appendTargeting` 已 `params.put("species", …)`；LATERAL 里引用即可，不要再 put 一次不同顺序的值）。
- 索引：`idx_pet_profiles_owner_created (owner_id, created_at, id)`（V20261018_1603）、`ix_pet_profiles_owner_status`（V20261018_1604）够用；≤ 5 万人可接受，L1 可 `EXPLAIN` 看一眼。
- `SELECT` 常量要从「`… FROM users u WHERE `」拆成「SELECT 列 + FROM + JOIN」与「WHERE」两段，`count` / `countIds` / `classifyIds` 不需要 JOIN。

**计数（`OpsAudienceSql.count` / `countIds`）**
```sql
SELECT count(*) AS total,
       count(*) FILTER (WHERE EXISTS (SELECT 1 FROM pet_profiles p WHERE p.owner_id = u.id)) AS with_pet
  FROM users u
 WHERE <同 build 的 WHERE>            -- IDS 预估：<BASE_FILTER> AND u.id IN (:ids)，按 10,000 一批累加两列
```

**抽样（`OpsAudienceQuery.sample`）**
```sql
<sampleBase：同 build 的 SELECT / JOIN / WHERE，无 ORDER BY>
   [AND pet.name IS NOT NULL]          -- requirePet
   [AND u.id <> :excludeUserId]        -- 先带着查；无结果再不带 exclude 查一次
 ORDER BY random() LIMIT 1             -- 在 OpsAudienceQuery 里拼（拍板 ③）
```
- IDS 模式（活动还没建，id 来自表单）：用 `u.id IN (:ids)`；先 `Collections.shuffle` 去重后的 id，按 10,000 一批依次查，命中即返回。
- 列很少，`random()` 全表扫在当前规模（几万用户）可接受。

**发送核心（`OpsNotificationDispatcher.run`，示意）**
```java
List<OpsRecipient> base = audience.resolve(spec, id);
boolean usesPet = OpsTextVariables.usesPet(campaign);
List<OpsRecipient> recipients = usesPet ? base.stream().filter(r -> r.petName() != null).toList() : base;
int noPet = base.size() - recipients.size();
log.info("运营通知开始发送 campaignId={} recipients={} noPet={}", id, recipients.size(), noPet);
if (repo.setPlanned(id, recipients.size(), now) == 0) { stopped(id); return; }
if (spec.mode() == IDS) { skipped = max(0, targets.countByCampaign(id) - base.size()); setSkipped(...) }   // 口径不变：用 base
if (usesPet && repo.setSkippedNoPet(id, noPet, now) == 0) { stopped(id); return; }
// 之后与现状相同，只是遍历 recipients
```

### 踩坑与禁止事项

1. **`PetOwnerLookupGuardTest`**：`OpsAudienceSql.java` 在白名单里，**任何 `LIMIT 1` 字面量都会让守卫变红**——LATERAL 用 `DISTINCT ON`；抽样的 `LIMIT 1` 放 `OpsAudienceQuery`。也不要在别的新文件里写含 `pet_profiles` + `owner_id` 的 SQL 字面量（会扩大白名单集合，守卫同样变红）。
2. 迁移：时间戳版本号、`INTEGER` 不用 `SMALLINT`；已应用的 `V20261012_1107` / `V20261015_1209` 一个字都不能改；打包 `mvn -B clean package`；改迁移后跑测试前 `test-compile` 让资源重拷（surefire 用 target 里的旧副本）。
3. `MessageFormat` 千分位：`previewUserValue` 的 `#{1}` 是用户 id，**传 `String.valueOf(id)`**，传 `long` 会渲染成 `10,234`；人数类 `{0}` 传数字（要千分位，稿上是 `3,000`）。
4. properties：含 `{0}` 的词条撇号写 `''`（EN 的 `can't` / `won't` 等）；不含占位符的保持单撇号（线上同例：`admin.err.ops-notify.audience-empty` 的 `can't`）。三份文件都要加，漏一份回落基线会显示错语言。
5. Thymeleaf 片段参数**一律具名**（3.1.5 行为）：`~{admin/fragments/tpl-shared :: inline-error(message=${…})}`、`~{… :: previewPane(sample=${sample})}`；`inline-error` 的 `data-code` 读模型变量 `code`，控制器要 `model.addAttribute("code", …)`。
6. 字数口径前后端一致：都用 UTF-16 长度（Java `length()` / JS `.length`），变量固定 20。昵称 / 宠物名列是 `VARCHAR(20)`（码点），替换后码点数 ≤ 计数值 ≤ 列长，`notifications.title/body`（120 / 255）不会溢出，不要再做截断。
7. `OpsRecipient` 加字段后，`OpsNotificationDispatcherTest` 等用两参构造的测试不用改；新断言另写。
8. `checkPreview` 在 `blockedNoPet` 判断之后（否则 `previewCount=0` 先报 `preview-required`）。
9. 不要改 `NotificationCenterService` 去「现拼」运营通知——标题正文就在行里，App 侧零改动（PRD「不改 App」）。
