## Story

As a 运营与买家,
I want 卡件、退回、丢件这些情况被标出来并暂停自动完成,
so that 有问题的订单不会被系统自动当成已收货。

## Acceptance Criteria

> 层级：`[L0]` 纯单元 / 静态（云端可跑）· `[L1]` 需 Docker postgres + redis（本地）· `[L2]` 本 story 无（Biteship 真实异常回传归 10.2）。
> 四类异常（PRD §3.10）：① 揽收失败 `PICKUP_FAILED`（Biteship 回传 `courier_not_found`）② 派送失败被退回 `RETURNED`（回传 `return_in_transit / returned`，原因分快递 / 用户）③ 卡件 `STALLED`（3 天无更新）④ 丢件破损 `LOST_DAMAGED`（运营标记）。

### AC1 — 领域方法 `[L0]`（D-13）
`ShopOrder` 新增（全部只改订单头列，不改订单状态）：
1. `flagLogisticsException(LogisticsException type, Instant at)`：当前为空 → 写入 `type`、`logistics_exception_at = at`、`logistics_exception_confirmed = false`；当前为 `STALLED` 且新类型非 `STALLED` → 覆盖（更严重的取代停滞）；当前为其他类型 → 不覆盖、返回 false（调用方 WARN）。
2. `confirmLogisticsException(LogisticsException type, boolean claimPending)`：要求当前异常 = `type`（或当前为空 / `STALLED` 时直接写入该 `type`，供运营手工标记丢件破损）；置 `logistics_exception_confirmed = true`；`claimPending = true` 时置 `claim_pending = true`（只置位不清除）。`type` 只允许 `RETURNED / LOST_DAMAGED`（`PICKUP_FAILED / STALLED` 不需要确认，用户侧本就不提示）。
3. `clearLogisticsException(Instant at)`：异常非空 → 清空 `logistics_exception / logistics_exception_at`、`logistics_exception_confirmed = false`、**`timer_resumed_at = at`**；`claim_pending` **不动**（PRD：已在索赔的由运营自行撤回）。为空 → 幂等返回 false。
4. `setClaimPending(boolean)`。
5. `isAutoDeliverDue(now)` / `isAutoCompleteDue(now)` 改为：**带任一异常标记 → false**；计时起点 = `max(shipped_at | delivered_at, timer_resumed_at)`（`timer_resumed_at` 为空时等同原逻辑）。
6. `hasUserVisibleDeliveryIssue()` = `logistics_exception_confirmed && logistics_exception ∈ {RETURNED, LOST_DAMAGED} && status ∈ {SHIPPED, DELIVERED}`（订单已进入 `REFUNDING / REFUNDED / CANCELLED / COMPLETED` 后不再显示配送异常——那时状态头已经是退款 / 取消 / 完成）。

### AC2 — 自动送达 / 自动完成排除异常、按 `timer_resumed_at` 重新计时 `[L0]` `[L1]`（D-13、PRD 旅程 D 第 7 条）
1. `ShopOrderRepository.findAutoDeliverDue` / `findAutoCompleteDue`（:186-202）JPQL 加条件：
   ```
   AND o.logisticsException IS NULL
   AND (o.timerResumedAt IS NULL OR o.timerResumedAt < :threshold)
   ```
   （与 `shippedAt < :threshold` / `deliveredAt < :threshold` 合起来即「`max(起点, timer_resumed_at) < threshold`」，不用 `GREATEST` 函数，避免方言差异。）
2. `ShopOrderFulfillmentService.autoDeliverOne / autoCompleteOne` 的二次判定走 AC1.5 的领域方法（并发下标记刚写入的订单不会被推进）。
3. Given 订单 `SHIPPED`、发货 20 天前、带 `STALLED` → 扫描不推进；Given 清除标记于 1 天前 → 仍不推进；Given 清除于 15 天前 → 推进为 `DELIVERED / AUTO_TIMEOUT`。自动完成同理（送达 10 天前、清除于 2 天前 → 不完成）。

### AC3 — 停滞检测 `LogisticsStallJob` `[L0]` `[L1]`（D-13、PRD ③）
1. 新类 `B/shop/logistics/LogisticsStallJob`：`@Scheduled(fixedDelayString = "${petgo.shop.logistics.stall-scan-ms:3600000}")`（每小时），事务内 `pg_try_advisory_xact_lock(hashtext('logistics_stall'))` 拿不到即跳过。
2. 候选：`shipments.provider = 'BITESHIP' AND superseded_at IS NULL AND status IN ('CREATED','SHIPPED') AND provider_status_at < now() − 3 天`（走 5.1 的 `ix_shipments_biteship_active`），且所属订单 `status IN ('PENDING_SHIPMENT','SHIPPED') AND logistics_exception IS NULL`，且 `provider_status` 不是 `cancelled / rejected / disposed / returned / courier_not_found`（这些已有其他处置）；单轮最多 500 单。
3. 命中 → `flagLogisticsException(STALLED, now)`（逐单独立短事务，单笔失败只 WARN）；**用户侧不提示**（AC5）；整轮新标数 > 0 时发一条飞书汇总提醒运营去 Biteship 追件（只列订单展示号，最多 20 个，其余写「等 N 单」）。
4. 3 天阈值做成配置 `petgo.shop.logistics.stall-after-hours:72`（默认 72）。手工运单（`provider = MANUAL`）没有物流状态来源，**不参与**停滞检测。

### AC4 — 新物流状态自动清除停滞 `[L0]` `[L1]`（决策日志 m7）
1. 5.1 的 `BiteshipTrackingService.applySnapshot`：当本次快照让活动运单的 `provider_status` **变化**（或 `provider_status_at` 前进到 > 标记时刻）且订单当前异常为 `STALLED` → 在同一短事务里 `clearLogisticsException(now)`（写 `timer_resumed_at`），再执行该状态本身的映射（如 `courier_not_found` 会随后写入 `PICKUP_FAILED`）。
2. 其他异常类型（`PICKUP_FAILED / RETURNED / LOST_DAMAGED`）**不会**被新物流状态自动清除，只由运营或用户确认收货清除。
3. 带 `PICKUP_FAILED` 的订单之后收到 `picked`：订单照常按 5.1 推进为 `SHIPPED`，标记保留（运营核实后清除），自动送达仍暂停。

### AC5 — 订单详情 `logistics.exception` 出参 `[L0]` `[L1]`（D-13 用户侧显示、F10、PRD 状态表）
1. 5.1 的 `Logistics` 记录中 `exception` / `exceptionType` 由本 story 填：
   - `order.hasUserVisibleDeliveryIssue()` 为真 → `exception = "DELIVERY_ISSUE"`、`exceptionType = "RETURNED" | "LOST_DAMAGED"`；
   - 其余一切情况（`PICKUP_FAILED`、`STALLED`、未确认的 `RETURNED`、订单已不在待收货）→ 两者都为 null，App 只显示最后物流状态（`statusKey` 不受异常影响）。
2. 配送异常时 `statusKey` 照常下发（App 决定是否隐藏五段状态；F10 稿只留快递与运单号）。
3. **订单无运单但带异常**（如手工运单前的揽收失败）：`logistics` 为 null 时不另造对象，用户侧本就不提示揽收失败。
4. 6.2 的订单列表项需要的同口径字段（`deliveryIssue`）调用同一个 `hasUserVisibleDeliveryIssue()`，本 story 不建列表。

### AC6 — 用户确认收货清除标记并提醒运营 `[L0]` `[L1]`（PRD「确认收货在任何异常下照常可点」）
1. `ShopOrderFulfillmentService.confirmReceipt`（:155-178）：在原有逻辑完成订单之后，若订单带任一物流异常 → `clearLogisticsException(now)`、写运营提醒（AC6.3）、INFO 日志 `"物流异常订单用户确认收货 token={} exception={}"`；`claim_pending` 保留。
2. 异常订单的确认收货**不弹任何阻拦**：状态校验仍只是 `SHIPPED / DELIVERED` 可确认（与现状一致）；带 `PICKUP_FAILED` 的 `PENDING_SHIPMENT` 订单本就不能确认收货（现状），不改。
3. 「运营提醒」落点（D-13「订单备注 + 日志」，架构未定义备注列）：
   - **若 4.1 已落地运营提醒的承载方式**（如订单备注列 / 提醒表，用于「退款去向 7 天未选」）→ 复用它，写 `LOGISTICS_EXCEPTION_USER_CONFIRMED`；
   - 否则本 story 只写 **WARN 日志 + 飞书提醒**（`[物流] 订单 {展示号} 在 {异常类型} 下被用户确认收货，请核对 / 撤回索赔`），并在 Completion Notes「待确认」写明「后台待办列表需要持久化落点」；**不自行新建表 / 列**。

### AC7 — 运营处置 service（供后台线）`[L0]` `[L1]`（D-13、D-14、PRD ① ~ ④）
新类 `B/shop/logistics/ShopLogisticsExceptionService`，方法均带 `Long actorAccountId` 并写审计（新常量见 AC7.6）。外部调用（Biteship）一律在事务外（P-7）。
1. **揽收失败的三种处置**，执行前**都先取消旧运单**（`BiteshipShipmentService.cancelWaybill`；结果 `NotCancellable` / `Unknown` → 整个处置中止并把原因返回给运营，订单与标记都不动）：
   - `resolvePickupFailureByRetry(orderId, actor)`：`cancelWaybill(…, "pickup_delay")` → `retryWaybill`；新运单建成后 `clearLogisticsException(now)`；建单失败 → 标记保留、失败原因按 5.1 AC5 记录。
   - `resolvePickupFailureByManualWaybill(orderId, carrier, trackingNo, carrierCost, actor)`：`cancelWaybill(…, "change_courier")` → `ShopOrderFulfillmentService.ship(...)`（手工运单，5.1 已放开「无活动 Biteship 运单」前提）→ `clearLogisticsException(now)`。
   - `resolvePickupFailureByCancel(orderId, actor)`：`cancelWaybill(…, "others")` → 调 4.1 的整单取消（`CancelReason.PICKUP_FAILED`，平台原因：全额退、退券、回补库存、补偿按 D-14 属性）→ 标记保留作为历史（订单已离开待收货，用户侧不显示）。
   - 前置：订单当前异常 = `PICKUP_FAILED`（否则 409）；三种处置**互斥**（以订单 `@Version` 乐观锁 + 处置后标记 / 状态变化保证同一订单不会被处置两次）。
2. **被退回**：`confirmReturned(orderId, ReturnCause cause, actor)`（`ReturnCause { COURIER_FAULT, USER_FAULT }`）：要求当前异常 = `RETURNED`；`confirmLogisticsException(RETURNED, claimPending = cause == COURIER_FAULT)`；之后：
   - `COURIER_FAULT` → 运营再调 5.1 `reshipForCourierFault`（重发成功后由本服务 `clearLogisticsException(now)`；`claim_pending` 保留）——提供组合方法 `reshipAfterCourierFault(orderId, actor)`。
   - `USER_FAULT` → 运营再调 4.1 的整单取消（`CancelReason.USER_FAULT_RETURNED`：订单 → `REFUNDING`、**不生成退款单**，待 `confirmReturnInbound`，S-8）；本 story 不实现取消本身。
3. **丢件破损**：`markLostDamaged(orderId, actor)`（客服接到用户反馈或长期卡件经 Biteship 确认）：`confirmLogisticsException(LOST_DAMAGED, claimPending = true)`；订单状态不变；后续赔付走 4.1（`LOST_DAMAGED` 整单取消，或已签收 / 已完成的 `COMPENSATION` 赔付单，S-9）。已签收 / 已完成订单也允许标记（S-9 场景），但 `hasUserVisibleDeliveryIssue()` 只在 `SHIPPED / DELIVERED` 时为真。
4. **清除**：`clearException(orderId, actor)`（运营核实无事，或停滞追回）→ `clearLogisticsException(now)`；**取消确认**不单独提供（清除即全清）。
5. **索赔提醒**：`setClaimPending(orderId, boolean, actor)`（后台「待索赔」完成后撤销）。
6. 新审计常量：`SHOP_LOGISTICS_EXCEPTION_CONFIRMED`、`SHOP_LOGISTICS_EXCEPTION_CLEARED`、`SHOP_LOGISTICS_PICKUP_FAILURE_RESOLVED`、`SHOP_LOGISTICS_CLAIM_PENDING_CHANGED`；四个 `messages*.properties` 补 `admin.audit.action.*` 键。审计摘要只记订单 token、异常类型、处置方式，不记收件人信息。
7. 供后台线列表用的只读查询：`ShopLogisticsExceptionService.listOpen(type?, page)` → 订单展示号、token、异常类型、标记时间、是否已确认、`claim_pending`、最新运单的 Biteship 状态（按 `logistics_exception_at` 倒序，走 5.1 的 `ix_shop_orders_logistics_exception`）；另 `listClaimPending(page)`。

### AC8 — `claim_pending` 置位规则 `[L0]` `[L1]`（D-13、PRD ② 快递原因 / ④）
1. 置 true 的唯一入口：`confirmReturned(…, COURIER_FAULT)`、`markLostDamaged`、`confirmLogisticsException(LOST_DAMAGED, …)`。
2. 置 false 的唯一入口：`setClaimPending(…, false)`（运营）。用户确认收货、清除异常、订单取消 / 退款**都不清** `claim_pending`。
3. `USER_FAULT` 退回不置位。

### AC9 — 与 Biteship 映射的衔接 `[L0]` `[L1]`
1. 5.1 `applySnapshot` 里写入 `PICKUP_FAILED / RETURNED` 改为调用 `ShopOrder.flagLogisticsException`（AC1.1 规则：不覆盖既有非停滞标记），写入成功后飞书提醒运营（5.1 已有）。
2. 订单带 `RETURNED / LOST_DAMAGED` 时收到 `delivered`：不推进订单（5.1 AC8.2 已定），本 story 补测试。
3. `RETURNED` 标记后又收到 `in_transit` 等正向状态：不自动清除（AC4.2），运营判断。

### 拍板点（按建议实现，Completion Notes 复述）

- **① `STALLED` 可被更严重的异常覆盖，其他异常互不覆盖**：卡件后经 Biteship 回传揽收失败 / 退回时，新信息更有价值；但已确认的退回不能被随后的「揽收失败」冲掉。
- **② 用户确认收货清标记但不清 `claim_pending`**：PRD「已在索赔的由运营自行撤回」。
- **③ 揽收处置中 Biteship 取消失败即整体中止**：不让一张仍在 Biteship 上有效的运单与新运单 / 手工运单并存（重复揽收、重复计费）。
- **④ 配送异常只在 `SHIPPED / DELIVERED` 显示**：订单一旦进入退款 / 取消 / 完成，状态头已有更准确的文案（PRD 状态表）。
- **⑤ 运营提醒不自建持久化**：架构未定义备注列；优先复用 4.1 的落点，没有则只发日志 + 飞书并记「待确认」。

### 实现提示

- 停滞候选查询（native，`@Query(nativeQuery = true)`）：
  ```sql
  SELECT DISTINCT o.id FROM shipments s JOIN shop_orders o ON o.id = s.shop_order_id
  WHERE s.provider = 'BITESHIP' AND s.superseded_at IS NULL AND s.status IN ('CREATED','SHIPPED')
    AND s.provider_status_at < :cutoff
    AND (s.provider_status IS NULL OR s.provider_status NOT IN ('cancelled','rejected','disposed','returned','courier_not_found'))
    AND o.status IN ('PENDING_SHIPMENT','SHIPPED') AND o.logistics_exception IS NULL
  ORDER BY o.id LIMIT 500
  ```
- 揽收处置骨架（外部调用不在事务内）：
  ```java
  public PickupResolution resolvePickupFailureByRetry(long orderId, Long actor) {
      tx.executeWithoutResult(s -> requireException(orderId, PICKUP_FAILED));   // 只读校验
      CancelResult c = waybills.cancelWaybill(orderId, "pickup_delay", actor);  // 内部事务外调 Biteship
      if (!c.ok()) return PickupResolution.aborted(c.reason());
      WaybillResult w = waybills.retryWaybill(orderId, actor);
      if (w.created()) tx.executeWithoutResult(s -> clearAndAudit(orderId, "RETRY", actor));
      return PickupResolution.of(w);
  }
  ```
- `hasUserVisibleDeliveryIssue()` 是**唯一判据**：详情（本 story）、列表（6.2）、埋点（App `toko_delivery_exception_shown`）都只看服务端给的 `exception` / `exceptionType`。

## 待确认 / 发现的规划冲突

1. **埋点 `exception_type` 三值 vs 异常两类**：PRD §4 `toko_delivery_exception_shown{exception_type: 退回 / 丢件 / 破损}`，但架构 D-13 只有 `LOST_DAMAGED` 一类（丢件与破损不分）。本 story 下发 `exceptionType ∈ RETURNED | LOST_DAMAGED`，App 埋点只能报两值；若要区分丢件与破损需回规划加枚举值。
2. **epics 5.2 写 `logistics.exception = DELIVERY_ISSUE`，未给类型**：为满足埋点，本 story 额外下发 `exceptionType`（字段在 5.1 的 `Logistics` 记录里已预留）。
3. **「运营提醒（订单备注 + 日志）」无持久化落点**：架构未定义订单备注列，后台线需要一个待办来源（确认收货清标记、停滞追件）。本 story 优先复用 4.1 的落点，没有则只发日志 + 飞书；需后台线 / 规划确认是否新增列或表。
4. **订单无 Biteship 运单时的揽收失败**：`PICKUP_FAILED` 只会由 Biteship 回传产生，订单必然有运单；手工运单不会出现揽收失败标记（没有回传来源），后台若要手工标记揽收失败需另提需求。
5. **`USER_FAULT` 退回与 4.1 取消的衔接**：本 story 只确认原因并不置 `claim_pending`，真正的取消（`REFUNDING`、待入库后退款）由运营再调 4.1；两步之间订单仍显示「配送异常」，属预期（客服正在联系用户）。
