## Story

As a 买家,
I want 按状态看我的电商订单、订单详情信息完整,
so that 清楚每单到哪一步了、钱怎么付和怎么退。

### AC1 — `GET /api/v1/me/shop-orders?group=&cursor=` 电商订单列表 `[L0]` `[L1]`（D-18、PRD FR-133.9）
1. 新 `B/shop/order/service/ShopOrderListService` + 控制器方法（可放 `MeCheckoutController` 或新 `MeShopOrderController`；路径与 `POST /me/shop-orders` 同前缀，安全规则已由 `SecurityConfig`:365 的 `/api/v1/me/shop-orders` USER 覆盖）。
2. `group` ∈ `all`（缺省）`| pending_payment | pending_shipment | to_receive | completed | cancelled`，非法值 → 422。分组**按 `displayStatus`**（S-7：宽限期待支付归已取消），判据统一用 3.3 的同一个判定（如 `ShopOrder.displayStatusAt(now)`；以 3.3 实际实现为准，**不另写一份**），SQL 等价条件：

   | group | 条件（`:now` = 服务端当前时刻） |
   |---|---|
   | `pending_payment` | `status = 'PENDING_PAYMENT' AND (expires_at IS NULL OR expires_at >= :now)`（T0 对齐：3.3 `isPaymentExpiredAt` 为 `now > expires_at`，恰在截止仍算待付款） |
   | `pending_shipment` | `status = 'PENDING_SHIPMENT'` |
   | `to_receive` | `status IN ('SHIPPED','DELIVERED')` |
   | `completed` | `status = 'COMPLETED'` |
   | `cancelled` | `status IN ('CANCELLED','REFUNDING','REFUNDED') OR (status = 'PENDING_PAYMENT' AND expires_at < :now)` |
   | `all` | 无状态条件 |

   （`expires_at IS NULL` 的待支付单是支付窗上线前的历史数据，按待付款处理，与 3.3 判定保持一致；若 3.3 判定不同以 3.3 为准并同步本表。）
3. 游标分页：`ORDER BY created_at DESC, id DESC`，每页 20，`(created_at, id) < (:ts, :id)` 行比较；游标为不透明 Base64url（T0 对齐：内容 `<epochSecond>:<nano>:<id>`——`created_at` 为微秒精度，截到毫秒会在同毫秒边界漏单），坏游标按首页；走现有 `ix_shop_orders_user (user_id, created_at DESC)`。
4. 响应 `{ items, nextCursor, hasMore }`，`items[]`（`ShopOrderListItem`）：
   ```
   orderToken, displayNo, status（原始状态）, displayStatus, totalAmount（订单应付总额，F1「列表金额统一为订单总额」）,
   createdAt, thumbnailUrl, itemTitle, itemCount（件数，同 ShopOrderCardService 口径）,
   paymentDeadline（仅 displayStatus = PENDING_PAYMENT 时下发 = expires_at）, canPay（同详情口径）,
   logisticsStatusKey（最新活动 Biteship 运单的 user_status_key；手工运单 / 无运单为 null）,
   deliveryIssue（= order.hasUserVisibleDeliveryIssue()，5.2）,
   refundActionRequired（存在 AWAITING_DESTINATION 或 PAYOUT_FAILED 的退款单，4.1）
   ```
   null 字段按全局 NON_NULL 不下发。
5. **禁止 N+1**：一页内的卡片摘要、最新运单、退款单状态各一次批量查询——`ShopOrderCardService` 新增 `ofAll(Collection<Long> orderIds) → Map<Long, CardInfo>`（行一次、SKU 一次、商品一次）；运单 `ShipmentRepository.findLatestActiveByOrderIds(ids)`；退款单用 4.1 仓库的批量方法（没有则补一个 `findOrderIdsNeedingUserAction(ids)`）。
6. 只返回本人订单；兽医 token 403（`hasRole("USER")` 已覆盖）。空集 `{items: [], hasMore: false}`。

### AC2 — `GET /api/v1/me/shop-orders/counts` `[L0]` `[L1]`（D-18、F1 角标）
1. 返回 `{ pendingPayment, toReceive }`（long），一条 SQL（T0 对齐：实现为等价的 JPQL `SUM(CASE …)` 单条查询 `ShopOrderRepository.countMyShopOrderBadges`，边界同 AC1.2 表）：
   ```sql
   SELECT count(*) FILTER (WHERE status = 'PENDING_PAYMENT' AND (expires_at IS NULL OR expires_at >= :now)) AS pending_payment,
          count(*) FILTER (WHERE status IN ('SHIPPED','DELIVERED'))                                       AS to_receive
   FROM shop_orders WHERE user_id = :uid
   ```
2. 口径与 AC1 分组完全一致（L0 测试用同一组样例订单同时断言列表分组与计数）。
3. 字面路径 `/counts` 优先于 `/{token}`（订单 token 为 22 位 Base62，不会等于 `counts`）。

- **⑤ 复购卡接口恒空、`dismiss` 保留**：旧版 App 兼容（不 404）。

### 实现提示

- 分组 → 查询：用一个 native 查询带 `:group` 分支太绕，推荐在 `ShopOrderRepository` 里写 6 个 `@Query`（或一个 `JpaSpecificationExecutor` 规格），共享同一 `ORDER BY created_at DESC, id DESC` 与行比较游标；`LIMIT 21` 判 `hasMore`。
- `displayStatus` 判据只在一处（3.3）：列表项在内存里对查出的订单再调一次同一方法赋值，SQL 条件只负责「归组」；L0 测试断言「SQL 条件表」与「内存判据」对同一组样例一致。
- `ShopOrderCardService.ofAll`：`lines.findByOrderIdInOrderByOrderIdAscIdAsc(ids)` → 每单首行 + 件数；首行 SKU → 商品 → 主图一次批量（`skus.findAllById`、`products.findAllById`）。
- `paymentMethods` 推导（纯函数 `PaymentMethodsView.of(order)`，L0 表驱动）：
  - `coinStatus`：`coin_amount` 为空或 0 → 整项 null；`paid_at != null` → `PAID`；`status == PENDING_PAYMENT` → `HELD`；已取消且 `paid_at == null` → `RETURNED`；
  - `cashStatus`：`cash_amount` 为空或 0 → 整项 null；`paid_at != null || late_paid_at != null` → `PAID`；`displayStatus == PENDING_PAYMENT` → `AWAITING`；其余 → `UNPAID`。
  - 退款后的「已退」不在这里表达，由 `refunds[]` 承载。
- 详情装配器的批量：行 1 次、运单 1 次、意图 1 次、退款单 1 次、重下单关联 1 次（新单 token / 原单展示号）、券退回状态 1 次。
