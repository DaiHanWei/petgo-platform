## Story

As a 付款晚于订单时限的用户,
I want 客服帮我用已到账的钱重新下单，或者退给我,
so that 钱不会停在网关。

## Acceptance Criteria

> 层级：`[L0]` 纯单元 / 静态 · `[L1]` 需 Docker postgres + redis · `[L2]` 真机推送（归 10.1）。
> 记号：原单 `O`（已取消且带迟到款），新单 `N`；`T = O.total_amount`；`origCoin = O.coin_amount`（null 视为 0）；`cashNeed = T − origCoin`；`L = O.late_paid_amount`（3.3 写入的网关实收现金）。

### AC1 — 处理权的唯一性（同一笔迟到款只能处理一次）`[L0]` `[L1]`（D-11「同一笔迟到款只能处理一次」）

1. `LatePaymentService`（`shop/order/service/`）两个方法都在**同一事务**的第一步做条件更新抢占处理权：
   ```sql
   UPDATE shop_orders SET late_payment_resolution = :resolution, updated_at = now(), version = version + 1
    WHERE id = :orderId AND late_paid_amount IS NOT NULL AND late_payment_resolution IS NULL
   ```
   （`ShopOrderRepository.claimLatePayment(orderId, resolution)`，`@Modifying` native；随后 `entityManager.refresh(order)` 或重新读取，避免托管实体的旧 `version` 在后续 save 时冲突。）受影响 0 行 → **409 `late-payment-already-resolved`**（含：无迟到款、已重下单、已退款）。
2. 后续任何一步失败抛异常 → 整个事务回滚，处理权一并释放（客服可改走另一条路）。
3. 库级兜底：3.2 已建部分唯一索引 `uq_shop_orders_reorder_of (reorder_of_order_id)`，同一原单不可能出现两张新单。
4. 并发：同一原单「重下单」与「退款」同时提交 → 恰好一个成功，另一个 409（L1 用两线程 + `CountDownLatch` 验证）。

### AC2 — `reorderFromLatePayment(orderToken, actorAdminId)` 校验 `[L0]` `[L1]`（FR-134.2、D-3 末条、D-11）

按序（任一失败 → 回滚、返回对应错误；后台线据 `code` 做 i18n，写 `AppException.code("admin.err.latePayment.*")`）：
1. 原单存在（404）；`status == CANCELLED`，否则 **409 `late-payment-not-reorderable`**（3.3 中「已付款订单又被另一意图付了一次」的重复付款只能退款，不能重下单）。
2. AC1 抢占 `REORDERED`。
3. **库存**：逐行（原单行全部，按原 `qty`）查可售量，不足的逐行收集 → **409 `unavailable-lines`**（复用 `CheckoutUnavailableException`，带 `unavailableLines[]`），PRD「没有库存时才退款」。
4. **原券**：`discount_user_coupon_id` / `free_shipping_user_coupon_id` 中非空的每张 → `CouponLedgerService.relockForReorder(userCouponId, newOrderId)`（**本 story 在 `CouponLedgerService` 新增此方法**，P-2：用户券状态只能在该类改）：
   - 仅当该用户券 `AVAILABLE` 时成功 → 置 `LOCKED`、`locked_order_id = 新单`；**不校验有效期**（「券已过期仍可用于这张新订单」，PRD FR-134.2）；
   - `LOCKED` / `USED`（已被别的订单占用或用掉）或 `VOIDED`（运营停用作废）→ 抛 `CouponInvalidException` → **409 `reorder-coupon-unavailable`**（PRD「原订单用过的券已被用掉时不能重新下单」）；
   - 不新建用户券行（D-3「不新建行，直接把原行重新 LOCKED 到新订单」）。
5. **PawCoin 足额**（S-6，见 AC3）：需要扣的币 > 当前余额 → **409 `reorder-coin-insufficient`**（「币不够只能退款」）。
6. **不重新询价**：快递、运费、减免、保价全部沿用原单快照（架构 §3.6 第 5 条）。

### AC3 — 多退少补的金额（S-6，计价器单点）`[L0]`（P-1）

1. 在 1.2 的 `ShopPricingCalculator` 新增纯函数 `reorderSettlement(long total, long originalCoin, long lateCash) → ReorderSettlement(coinAmount, cashAmount, excessToPawcoin)`：
   - `cashNeed = total − originalCoin`；
   - `lateCash ≥ cashNeed` → `cash = cashNeed`、`coin = originalCoin`、`excess = lateCash − cashNeed`；
   - `lateCash < cashNeed` → `cash = lateCash`、`coin = total − lateCash`（= 原币 + 差额，差额用币补）、`excess = 0`；
   - 断言 `coin + cash = total`、全部 ≥ 0；`lateCash ≤ 0` → `IllegalArgumentException`。
2. 表驱动用例（`ShopPricingCalculatorReorderTest`）：
   | # | total | originalCoin | lateCash | coin | cash | excess |
   |---|---|---|---|---|---|---|
   | 1 | 329,575 | 100,000 | 229,575 | 100,000 | 229,575 | 0（常见：迟到款 = 原现金段） |
   | 2 | 329,575 | 100,000 | 250,000 | 100,000 | 229,575 | 20,425（多出退为 PawCoin） |
   | 3 | 329,575 | 100,000 | 200,000 | 129,575 | 200,000 | 0（差额 29,575 用币补） |
   | 4 | 150,000 | 0 | 150,000 | 0 | 150,000 | 0（纯 QRIS 原单） |
   | 5 | 150,000 | 0 | 120,000 | 30,000 | 120,000 | 0 |
   | 6 | 150,000 | 0 | 0 | — | — | — 抛异常 |
3. 新单 `PaymentSplit`：`coin_amount = coin`、`cash_amount = cash`；channel：`coin > 0` → `MIXED`，否则 `QRIS`（`cash` 恒 > 0）。

### AC4 — 建新单并走统一「已付款」路径 `[L0]` `[L1]`（D-11、I4）

同一事务（接 AC2）：
1. 新工厂 `ShopOrder.placeReorder(ShopOrder original, String publicToken, String displayNo, Instant now)`：复制原单的地址快照、`goods_subtotal`、`discount_coupon_amount`、`shipping_fee`、`shipping_discount`（≤ 0 口径）、`insurance_fee`、`insurance_selected`、`total_amount`、`shipping_discount_source`、两个用户券 id、快递五列、`shipping_quote_id`、`coin_selected`、`referrer_merchant_id`（**沿用原单的归属门店**：购买决定发生在原单那一刻）；写 `checkout_source = REORDER`、`reorder_of_order_id = original.id`；状态 `PENDING_PAYMENT`、`expires_at = now + 60 分钟`（随即在本事务内转待发货，不会进入超时扫描）。`displayNo` 用 `ShopOrderDisplayNoGenerator.generateUnique(now, …)` 新生成。
2. 订单行：逐行复制原单行（`unit_price` 原快照、`qty`、`product_name`、`spec_name`、`return_policy`、`entry_source`、`trigger_type`、`discount_eligible`），`refunded_qty = 0`；逐行 `inventory.lock`。
3. 原券 `relockForReorder`（AC2.4）。
4. 扣币：`coin > 0` → `wallet.debit(userId, coin, SPEND, "SHOP_ORDER", newOrderId, "shop-order:" + newOrderToken)`（与 3.2 同键规则，`refType` 必须 `"SHOP_ORDER"`，成长值经 `ShopOrderPaidEvent` 入账、不经扣币事件）；余额不足 → 409 `reorder-coin-insufficient`。
5. 多出部分：`excess > 0` → `wallet.credit(userId, excess, REFUND, "SHOP_LATE_EXCESS", originalOrderId, "shop-late-excess:" + originalOrderToken)`；**无补偿**、**不发 `RefundSucceededEvent`**（不是退消费，S-6）、不调任何订单的 `recordRefund`。
6. `order.applyPaymentSplit(channel, split)`（AC3.3）；新单**不挂支付意图**（`payment_intent_token` 为空：现金来自原单的迟到意图，若也挂上同一 token，`findByPaymentIntentToken` 会命中两行）。
7. `ShopOrderPaidTransition.markPaid(newOrder, PaidSource.REORDER)`（3.2）：逐行 `inventory.commit`、写 `paid_at`（商家平台返佣游标不漏）、`CouponLedgerService.markUsed`（券 LOCKED → USED）、发 `ShopOrderPaidEvent`（飞书发货提醒入队、成长值按 `paidTotal` 入账、服务端 `shop_payment_paid`）→ 新单 `PENDING_SHIPMENT`。
8. 原单保持 `CANCELLED`，`late_payment_resolution = REORDERED`（AC1 已写）。审计：`AdminAuditService.record(actor, …, "SHOP_ORDER", originalToken, "迟到款重新下单 → {newDisplayNo}；迟到款 {L}；新单币 {coin} / 现金 {cash}；退回多余 {excess}")`（不含地址 / 手机号）。
9. 发布 `ShopOrderReorderedEvent(originalOrderId, newOrderId, userId)`（事务内发布），通知见 AC5。
10. 返回 `ReorderOutcome(newOrderToken, newDisplayNo, coinAmount, cashAmount, excessToPawcoin)`。

### AC6 — `refundLatePayment(orderToken, actorAdminId)` `[L0]` `[L1]`（D-11、FR-134.2 第 2 点）

1. 原单存在（404）；`late_paid_amount IS NOT NULL`；AC1 抢占 `REFUNDED`。原单状态**不限**（`CANCELLED` 或 3.3 记录的重复付款单都可退）。
2. 调 4.1 的 `ShopOrderRefundService.createLatePaymentRefund(order, L, actorAdminId)`：金额来自 `ShopRefundCalculator.latePayment(L)` → `scope = WHOLE`、`reason = LATE_PAYMENT`、`total = cash = L`、`coin = 0`、`goods_refund = L`、状态 `AWAITING_DESTINATION`。
3. **不**调 `order.recordRefund`（迟到款不在原单的 `total_amount` 收入里：原单 `CANCELLED` 被财务对账排除，若再记 `refunded_total` 会让现金净流入被多扣一次）；**不**退券（`LATE_PAYMENT.refundCoupon=false`，原单取消时券已退过）；**不**改原单状态；**不**发 `RefundSucceededEvent`（4.1 AC5.4）。
4. 之后用户在原单详情 `refunds[]` 中看到该退款单，经 4.1 的去向端点选 PawCoin（即时、**无补偿**，`LATE_PAYMENT.compensate=false`）或线下打款（扣渠道费、财务标记）。
5. 审计：`"迟到款退款：{L}，退款单 {refundToken}"`。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 新单沿用原单归属门店**（`referrer_merchant_id`）：购买决定发生在原单那一刻；新单 `paid_at` 让商家平台按游标计入返佣，原单从未付款不会计。
- **② 新单不挂支付意图**：现金来自原单的迟到意图（`late_paid_intent_id` 在原单上可查），避免同一意图 token 对应两张订单。
- **③ 多出部分退 PawCoin 用独立 `refType = "SHOP_LATE_EXCESS"`**：不计任何订单的 `refunded_total`、不发扣回事件；财务可按该 `refType` 单独统计。
- **④ 重复付款的单只能退款不能重下单**（AC2.1）：它本身已在履约，重下单会多发一份货。
- **⑤ 退款路径不发推送**：PRD 只为重新下单定义了 F22 推送。

  ```java
  @Transactional
  public ReorderOutcome reorderFromLatePayment(String orderToken, long actorAdminId) {
      ShopOrder o = orders.findByPublicToken(orderToken).orElseThrow(...404);
      if (o.getStatus() != ShopOrderStatus.CANCELLED) throw AppException.lateNotReorderable(...);
      if (orders.claimLatePayment(o.getId(), "REORDERED") == 0) throw AppException.lateAlreadyResolved(...);
      List<ShopOrderLine> lines = orderLines.findByOrderIdOrderByIdAsc(o.getId());
      requireStock(lines);                                          // 409 unavailable-lines
      ReorderSettlement s = ShopPricingCalculator.reorderSettlement(o.getTotalAmount(), coinOf(o), o.getLatePaidAmount());
      ShopOrder n = orders.save(ShopOrder.placeReorder(o, tokens.generate(), displayNos.generateUnique(now, orders::existsByDisplayNo), now));
      copyLinesAndLock(n, lines);
      relockCoupons(o, n);                                          // 409 reorder-coupon-unavailable
      debitCoin(n, s.coinAmount());                                 // 409 reorder-coin-insufficient
      creditExcess(o, s.excessToPawcoin());
      n.applyPaymentSplit(channelOf(s), PaymentSplit.of(o.getTotalAmount(), s.coinAmount(), s.cashAmount()));
      paidTransition.markPaid(n, PaidSource.REORDER);
      events.publishEvent(new ShopOrderReorderedEvent(o.getId(), n.getId(), o.getUserId()));
      audit.record(...);
      return new ReorderOutcome(...);
  }
  ```
  注意 `claimLatePayment` 是 native 条件更新，之后必须重读 `o`（或 `entityManager.refresh`），否则后续对 `o` 的任何 save 会因 `@Version` 不一致抛乐观锁异常。
- `PaymentSplit` 现只有 `compute(...)` 工厂（`PaymentSplit.java:33-54`）；按需加 `of(total, coin, cash)`（`coinRatio` 用同一公式，仅展示）。
- 日志只记订单 token / id、金额；不记地址、手机号。

## 待确认 / 发现的规划冲突

1. **S-6「多退少补」在常规情况下不会触发**：3.3 记下的迟到款 = 原意图的现金段 = `T − origCoin`，重下单若仍扣原币额则现金恰好对上。只有在原单当初的币额与本次不同（如运营改了 PawCoin 规则、存量单）时才出现多 / 少。本 story 按通用公式实现，计价器测试覆盖三种情形。
2. **重下单时用户余额不足以再扣原币额**（原单取消时币已退回，用户可能已花掉）：按 S-6「币不够只能退款」拒绝（409）。客服需改走退款并另行联系用户；PRD 未写客服话术。
3. **D-24 只列 `reorder` 入口**：本 story 增 `late-refund` stag 入口，供 10.1「另一例退款」验收。
4. **新单归属门店**沿用原单（拍板点 ①），PRD / 架构未明说；若要求取重下单时刻的绑定，改为 `merchantBindings.referrerOf(userId)`。
5. **重复付款单（3.3 记录）只允许退款**：PRD 未覆盖重复付款，本 story 与 3.3 一致按「只退款」处理。
