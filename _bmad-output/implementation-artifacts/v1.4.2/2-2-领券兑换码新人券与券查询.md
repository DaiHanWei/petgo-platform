## Story

As a 用户,
I want 在首页、详情、banner 领券，输入兑换码，新人自动拿到券,
so that 下单能省钱。

| 常量 | type 后缀 | HTTP | 场景 | App 文案（9.3 / 8.x，PRD §6） |
|---|---|---|---|---|
| `COUPON_NOT_FOUND` | `coupon-not-found` | 404 | 兑换码不存在；领券时券 token 不存在或不是可领券 | G7「Kode kupon tidak valid」 |
| `COUPON_CODE_USED` | `coupon-code-used` | 409 | 一次性码已被使用 | G7「Kode ini sudah dipakai」 |
| `COUPON_NOT_IN_PERIOD` | `coupon-not-in-period` | 409 | 发放期未开始 / 已结束，或券已停用 | G7「Kode ini tidak dalam masa berlaku」 |

### AC2 — 领券 `POST /api/v1/me/coupons/claim` `[L0]` `[L1]`（D-6、FR-130.4、FR-132.2）
1. 请求 `{couponToken: string, source: "HOME" | "DETAIL" | "BANNER"}`（大小写不敏感，非法值 422）。
2. `CouponClaimService.claim(userId, couponToken, source, now)`（`@Transactional`），校验顺序（逐条有测试）：
   1. 模板不存在，或 `acquire_type ≠ CLAIM` → 404 `coupon-not-found`（新人券、兑换码券不能直接领）；
   2. 锁模板行 `ShopCouponRepository.findLockedById`（`SELECT … FOR UPDATE`，串行同一模板的并发领取）；
   3. `status = STOPPED` 或 `now ∉ [issue_start_at, issue_end_at)` → 409 `coupon-not-in-period`；
   4. 该用户在此模板下已有行数 ≥ `per_user_limit`（**任何状态都算**，含 USED / VOIDED）→ 409 `coupon-already-claimed`；
   5. 条件扣总量 `incrementIssuedIfAvailable(id) == 0` → 409 `coupon-sold-out`；
   6. `CouponLedgerService.issue(userId, coupon, source == BANNER ? BANNER : CLAIM, now)`。
3. 响应 200 `CouponView`（AC8）。并发领最后一张：只成功一个，另一个 `coupon-sold-out`。
4. 领到的用户券有效期按模板物化（2.1 AC4.1）。

### AC3 — 兑换码 `POST /api/v1/me/coupons/redeem` `[L0]` `[L1]`（D-4、FR-130.9）
1. 请求 `{code: string}`；规范化 `trim().toUpperCase(Locale.ROOT)`；为空或不匹配 `^[A-Z0-9]{4,32}$` → 按「不存在」处理（计失败次数）。
2. `CouponRedeemService.redeem(userId, rawCode, now)`，顺序：
   1. **锁定检查**：Redis 键 `rl:coupon:redeem-lock:{uid}` 存在 → 429 `coupon-redeem-locked`（锁定期内任何兑换都拒，包括正确的码）；
   2. 码不存在 → **计一次失败** → 404 `coupon-not-found`；
   3. 锁模板行；一次性码已有 `redeemed_at` → **计一次失败** → 409 `coupon-code-used`；
   4. 模板 `STOPPED` 或不在发放期 → 409 `coupon-not-in-period`（不计失败）；
   5. 每人限领已满 → 409 `coupon-already-claimed`（不计失败）；
   6. 条件扣总量为 0 → 409 `coupon-sold-out`（不计失败）；
   7. 一次性码：条件核销 `redeemed_by_user_id / redeemed_at`（影响 0 行 = 被并发抢先 → 409 `coupon-code-used`，计失败）；
   8. `ledger.issue(userId, coupon, CODE, now)` → 200 `CouponView`（`isNew = true`，供 G6 列表顶部「Baru」标）。
3. **防暴力试码**（只对「不存在 / 已被使用」两类计数，D-4）：失败时 `INCR rl:coupon:redeem-fail:{uid}`，首次设 TTL 1 小时；计数达到 **10** → `SET rl:coupon:redeem-lock:{uid} 1 EX 3600` 并删除失败计数键。即「同账号 1 小时内输错 10 次，第 10 次照常返回该次的错误，之后 1 小时内一律 429」。
4. Redis 读写用 `StringRedisTemplate` 直接写在 `CouponRedeemService` 里（现 `RedisRateLimiter.check`（`B/shared/ratelimit/RedisRateLimiter.java:30-38`）是「每次调用都计数」语义，不适合「只数失败」）。**Redis 异常一律放行兑换、WARN 日志**（fail-open，防试码是防护不是业务正确性；与通知角标「Redis 抖动不阻断主流程」同口径）。
5. 码明文**不进日志**；日志只记 userId 与结果分类。

### AC4 — 新人券 `POST /api/v1/me/shop/entry` `[L0]` `[L1]`（D-5、FR-130.5、PRD「新人券细节」）
1. App 每次进入 Toko 调（8.1）；幂等；响应 200 `{newbieCouponIssued: boolean}`。
2. `NewbieCouponService.onEntry(userId, now)`（`@Transactional`）：
   1. 当前新人券 = `acquire_type='NEWBIE' AND status='ACTIVE' AND issue_start_at ≤ now < issue_end_at`（2.1 保证同一时刻最多一张；查到多张取 `issue_start_at` 最晚的一张并 WARN）；无 → `false`；
   2. 用户须为「有效的真实普通用户」：`AccountQueryService.isActiveRegularUser(userId)`（`B/auth/service/AccountQueryService.java:101`，`role=USER`、`account_type=REAL`、未注销、未封号）→ 否则 `false`；
   3. 注册时间：`users.created_at > now − 30 天`（**严格以进入时刻判断**；恰好 30 天整算超过 → 不发）；
   4. 从未有**已支付**电商订单：`ShopOrderRepository.existsByUserIdAndPaidAtIsNotNull(userId)` 为 false（下单未付、超时取消的不算，仍是新人）；
   5. 锁模板行；该用户在此模板下已有行 → `false`（幂等，重复进入不重复发）；
   6. 条件扣总量为 0（领完）→ `false`（静默，不报错）；
   7. `ledger.issue(userId, coupon, NEWBIE, now)` → `true`。
3. 「活动开始前进过 Toko」天然补发：每次进入都判。游客无此接口（`/me/**`）。
4. 返回 `true` 时 App 上报 `toko_coupon_claimed{source: newbie}`（8.1，m3）；后端不另发事件。

### AC6 — 首页「给你的券」`GET /api/v1/shop/coupons/for-you` `[L0]` `[L1]`（D-6、PRD「Toko 首页给你的券」）

2. 内容与顺序：
   1. 该用户 `source=NEWBIE`、`AVAILABLE` 且未过期的用户券（`newbie=true`、`claimed=true`）置顶；
   2. 发放期内、`ACTIVE`、`acquire_type=CLAIM` 的模板：用户未达限领且未领完 → `claimed=false`（显示「Klaim」）；用户已达限领 → `claimed=true`（显示「Diklaim」）；未领且已领完 → 不出现；
   3. 第 2 组内：未领的在前、已领的在后；同组按 `issue_start_at` 倒序；总数上限 20。
3. 不含 CODE 类模板（只能兑换）。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 领券 / 兑换的失败判序**：不存在 → 不在发放期 / 已停用 → 已领过 → 已领完。「已领过」先于「已领完」：用户已经有这张券时告诉他「已领取过」比「已领完」更准确。
- **② 兑换锁定时，正确的码也拒**（「锁定兑换 1 小时」原文）。
- **③ 防试码 Redis 故障时放行**（fail-open）。
- **④ 新人「30 天内」用严格小于**：`created_at > now − 30d`。
- **⑤ `GET /me/coupons/summary` 与 `isNew` 字段是本 story 补的**（App 9.1 / 9.3 需要），不改变任何已有契约。
- **⑥ `promo` 也算用户自己的可用券**（D-6 原文），因此同一商品对不同用户 `promo` 可能不同；列表接口因此需要可选 JWT。

### 实现提示

- 兑换失败计数：
  ```java
  private void recordFailure(long uid) {
      try {
          Long n = redis.opsForValue().increment("rl:coupon:redeem-fail:" + uid);
          if (n != null && n == 1L) redis.expire("rl:coupon:redeem-fail:" + uid, Duration.ofHours(1));
          if (n != null && n >= 10) {
              redis.opsForValue().set("rl:coupon:redeem-lock:" + uid, "1", Duration.ofHours(1));
              redis.delete("rl:coupon:redeem-fail:" + uid);
          }
      } catch (RuntimeException e) {
          log.warn("兑换失败计数写入失败（放行）userId={} cause={}", uid, e.getClass().getSimpleName());
      }
  }
  ```
  ⚠️ 失败计数在抛业务异常**之前**写（Redis 不随事务回滚，这正是想要的）。
- 范围匹配（`PromoResolver`、商品可领券、未来 3.1 的券分组共用）：抽一个 `CouponScopeMatcher.covers(ShopCoupon c, String productToken, ProductCategory category)` 静态方法，避免三处各写一遍。
- `CouponView` 由 `CouponViews.claimable(ShopCoupon, claimed, now)` 与 `CouponViews.owned(UserCoupon, ShopCoupon, now)` 两个工厂构造。
- 新人券的「同一用户不重复」靠「锁模板行 + 查已有行」，不靠唯一约束（`user_coupons` 不建 `(user_id, coupon_id)` 唯一索引，因为 CLAIM 券每人可领多张）。
- 日志只记 userId、模板内部 id、结果分类；**不记兑换码、券名**。

### 架构约束

- D-4：通用码 / 一次性码；失败码与文案一一对应；只对「不存在 / 已被使用」计数，1 小时 10 次锁 1 小时，键名照架构。
- D-5：新人判定、每次进入都判、游客活动接口、`campaignToken`。
- D-6：五个查询 / 写接口；可用列表不出 LOCKED；`expiringSoon` ≤ 48h；`promo` 批量算。
- P-2：发券只经 `CouponLedgerService.issue`（本 story 不得出现 `user_coupons` 写语句，2.1 守卫会拦）。
- P-5：错误 type；P-6：时间比较用服务端 `now`。
- 护栏：对外只有 `public_token`；兽医 token 不能落进 `/me/coupons`（AC10）；不引新依赖。
