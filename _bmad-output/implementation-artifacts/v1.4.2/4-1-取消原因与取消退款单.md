## Story

As a 被平台取消订单的用户,
I want 我付的 PawCoin 和现金都能退回、现金退到哪我自己选,
so that 不会因为平台缺货损失钱。

> 层级：`[L0]` 纯单元 / 静态 · `[L1]` 需 Docker postgres + redis · `[L2]` 真机（归 10.1）。
> 记号（全部取自订单头已有列，**不新增同义列**）：`G = goods_subtotal`（商品金额）、`D = discount_coupon_amount`、`F = shipping_fee`、`S = −shipping_discount`（运费减免，正数）、`I = insurance_fee`、`T = total_amount`（应付）、`C = coin_amount`（null 视为 0）、`RT = refunded_total`、`RC = refunded_coin`；`E` = 满减适用商品金额 = Σ(`unit_price × qty`，`discount_eligible = true` 的行，按**下单数量**）；「商品实付」= `G − D`；「实付运费」= `F − S`。

### AC2 — `ShopRefundCalculator`（纯函数，表驱动）`[L0]`（D-15、P-1、m2）

1. 位置 `shop/order/pricing/ShopRefundCalculator`（与 1.2 计价器同包，P-4）；无 IO、无 Spring；输入值对象 `RefundOrderSnapshot(T, C, RT, RC, G, D, F, S, I, insuranceSelected, List<RefundLine>(lineId, unitPrice, qty, refundedQty, discountEligible))`，由 service 从订单 + 行装配；输出 `RefundQuote(scope, lineId, qty, goodsRefund, shippingRefund, insuranceRefund, totalRefund, coinRefund, cashRefund, becameWhole)`。乘法一律 `Math.multiplyExact`（溢出即抛，不静默截断）。
2. **部分取消** `partial(snapshot, lineId, cancelQty)`：
   - `1 ≤ cancelQty ≤ qty − refundedQty`，否则 409（`AppException.conflict`，「取消数量超过可取消数量」）；
   - **若本次取消后全单已无剩余件**（所有行 `refundedQty` + 本次 = `qty`）→ 转 `whole(snapshot, reason)` 结果并 `becameWhole = true`（「最后一件按整单处理，退剩余未退应付（含运费、保价）」）；
   - 否则：`lineAmount = unitPrice × cancelQty`；`share = discountEligible && E > 0 ? floor(D × lineAmount / E) : 0`（向下取整，对用户有利 ≤ 1 盾）；`total = lineAmount − share`；`goodsRefund = total`、运费保价 0；
   - 币段 `coin = min(floor(total × C / T), C − RC)`（`T = 0` 时 0），零头入现金 `cash = total − coin`。
3. **整单** `whole(snapshot, reason, Long negotiatedAmount)`，`remaining = T − RT`：
   | reason | `total` | 运费 / 保价是否计入 |
   |---|---|---|
   | `OUT_OF_STOCK` / `WAYBILL_FAILED` / `PICKUP_FAILED` / `COURIER_FAULT`（平台原因） | `remaining` | 是：`shippingRefund = F − S`、`insuranceRefund = I`、`goodsRefund = total − 二者` |
   | `USER_FAULT_RETURNED` | `max(0, (G − D) − RT)`（= 应付 − 实付运费 − 保价费 − 已退） | 否（`goodsRefund = total`） |
   | `LOST_DAMAGED` 且 `insuranceSelected` | `max(0, (G − D) − RT)`（商品实付） | 否 |
   | `LOST_DAMAGED` 且未保价 | `negotiatedAmount` 必填且 `0 ≤ N ≤ G − D`，否则 422；`total = max(0, N − RT)` | 否 |
   - 币段：`total == remaining` → `coin = C − RC`（剩余币全退，零头精确归零）；否则 `coin = min(floor(total × C / T), C − RC)`；`cash = total − coin`。
   - `remaining == 0` → 409「该订单已无可退金额」。
4. **签收后赔付** `compensation(snapshot, Long negotiatedAmount)`（S-9）：金额规则与 `LOST_DAMAGED` 完全相同（复用同一私有方法），`scope = COMPENSATION`。
5. **补偿** `compensationPremium(long cashToPawcoin, int ratePercent, long cap)` = `cashToPawcoin × ratePercent / 100`，`cap > 0` 时取 `min`；`ratePercent ≤ 0` 或基数 ≤ 0 → 0（与 `AdminShopOrderExceptionService.payCompensationPremium` 现公式同口径，`:357-376`，但**基数改为现金段**）。
6. **渠道费** `payoutNet(long cash, PayoutChannel ch)` = `cash − ch.fee()`；`cash ≤ ch.fee()` → 422 `refund-below-payout-fee`。
7. **迟到款** `latePayment(long lateAmount)`（4.2 使用）：`coin = 0`、`cash = lateAmount`、`goodsRefund = lateAmount`、`scope = WHOLE`、`reason = LATE_PAYMENT`。

### AC3 — 按原因的库存、状态、券与退款单 `[L0]` `[L1]`（D-14、D-15「按原因的库存与状态」、S-8、S-9）

`ShopOrderRefundService`（`shop/order/refund/`，后台线与 stag 入口调用；方法全部 `@Transactional`，参数里的 `actorAdminId` 写 `created_by_admin_id` 并经 `AdminAuditService.record` 留痕）：

| 方法 | 允许的订单状态 | 库存 | 订单状态 | 退款单 | 券（`CouponLedgerService.releaseOnCancel(orderId, reason.couponReleaseMode(), now)`，2.1 签名 + 3.2 的 `CancelReason.couponReleaseMode()`；「退回」= `RETURN`，「不退」= `KEEP`） |

| `cancelWhole(orderToken, OUT_OF_STOCK / WAYBILL_FAILED, note, actor)` | `PENDING_SHIPMENT` | 剩余件回补（`InventoryMovementService.receiveReturn`，原因 = 订单号，沿用 `AdminShopOrderExceptionService.restock` `:323-331`） | → `REFUNDING` → 全部退款单完成后 `REFUNDED` | WHOLE | 退回 |

| `confirmReturnInbound(orderToken, actor)` | `REFUNDING` 且 `cancel_reason = USER_FAULT_RETURNED` 且尚无 WHOLE 退款单 | 剩余件回补 | 退款单完成后 `REFUNDED` | WHOLE（USER_FAULT 金额） | 不退 |
| `compensate(orderToken, negotiatedAmount, note, actor)`（S-9） | `DELIVERED` 或 `COMPLETED` | 不动 | **不变** | COMPENSATION（LOST_DAMAGED 金额，`reason = LOST_DAMAGED`） | 退回（丢件破损赔付退券） |
| `cancelLine(orderToken, lineId, qty, reason, note, actor)` | `PENDING_SHIPMENT`；`reason` 限平台原因 | 该行 `qty` 回补 | **不变**；若计算器 `becameWhole` → 按 `cancelWhole(reason)` 的整行规则（→ `REFUNDING`） | LINE（`becameWhole` 时 WHOLE） | 部分取消不退；`becameWhole` 按原因退 |

公共步骤（同一事务）：
1. 订单行 `refunded_qty`：LINE → 该行 `addRefundedQty(qty)`；WHOLE → 各行补齐到 `qty`（沿用 `cancelWholeOrder` `:127-133` 写法）；COMPENSATION → **不动**。
2. 订单：`order.recordRefund(total, coin)`（累加 `refunded_total / refunded_coin`，`ShopOrder.java:503-513`，超额即抛）；整单类写 `cancel_reason` 与 `cancelled_at`（3.2 的 `markCancelled` 不能用于此处 —— 那是转 `CANCELLED`；本处新增 `markRefunding(reason, at)`：写原因与时刻并 `transitionTo(REFUNDING)`）；清缺货标记（`clearShortageFlag`，沿用）。
3. 币段立即退回：`coin > 0` → `wallet.credit(userId, coin, REFUND, "SHOP_ORDER", orderId, "shopref:" + refundToken + ":coin")`，并发 `RefundSucceededEvent("SHOPREF:" + refundToken + ":COIN", …, coin, order.paidTotal())`（AC5）。
4. 退款单状态：`cash > 0` → `AWAITING_DESTINATION`；`cash == 0` → `COMPLETED`。
5. 结算订单：`settleOrderIfDone(order)` —— `status == REFUNDING` 且存在 WHOLE 退款单且该单 WHOLE / LINE 退款单**全部** `COMPLETED` → `transitionTo(REFUNDED)`。纯币单因此在同一事务内直接 `REFUNDED`。
6. 用户站内信：沿用 `AdminShopOrderExceptionService.notifyUser` 的 `SHOP_ORDER_EXCEPTION`（不新增通知类型；文案由 App 按 type 本地化），USER_FAULT 取消与 `confirmReturnInbound` 也发；发送失败不回滚（沿用 `:379-388`）。**选择退款方式不推送**（PRD 11-05 最终版删除了该推送）。
7. 非法状态 → 409（`AppException.conflict`，带 `code("admin.err.orderRefund.*", status)` 供后台线 i18n）。

### AC4 — 用户选择现金去向 `POST /api/v1/me/shop-orders/{token}/refunds/{refundToken}/destination` `[L0]` `[L1]`（D-15、FR-134.4）

1. 端点放 `MeCheckoutController`（路径已在 `SecurityConfig` `/api/v1/me/shop-orders/**` USER 表内）。订单非本人 / 退款单不属于该订单 → 404（不区分）。
2. 请求体 `{ destination: "TO_PAWCOIN" | "TO_BANK", channel: "BCA" | "OVO" | "GOPAY", account: "…", accountHolderName: "…" }`（`channel / account / accountHolderName` 仅 TO_BANK 必填；校验规则照 `ReturnRequest.chooseCashDestination` 的账号 / 户名校验，抽成共用静态方法，不复制）。**没有「PawCoin 段去哪」参数**（能力缺席，FR-100A 规则 1）。
3. 仅 `AWAITING_DESTINATION` 或 `PAYOUT_FAILED` 可选；其他 → 409 `refund-destination-locked`。
4. `TO_PAWCOIN`：`wallet.credit(cash, REFUND, "SHOP_ORDER", orderId, "shopref:{token}:cash-pawcoin")`；`reason.compensate()` 为真 → 补偿 = 计算器 `compensationPremium(cash, PawCoinConfig.compensationPremiumRate, compensationPremiumCap)`，`credit(premium, BONUS, "SHOP_ORDER_COMPENSATION", orderId, "shopref:{token}:compensation")`，写 `compensation_amount`（**只对现金段**；`USER_FAULT_RETURNED` / `LATE_PAYMENT` 无补偿）；→ `COMPLETED`；发 `RefundSucceededEvent("SHOPREF:{token}:CASH_PAWCOIN", …, cash, …)`（**补偿不计入**扣回基数）；`settleOrderIfDone`。从 `PAYOUT_FAILED` 改选 PawCoin 同样处理（补偿照给）。
5. `TO_BANK`：渠道费 = `PayoutChannel.fee()`（前端传费一律不采信），`cash ≤ fee` → 422 `refund-below-payout-fee`；写渠道、加密账户 / 户名、`payout_fee`、`destination_chosen_at` → `PAYOUT_PENDING`。**此时不发扣回事件**（标记已打款时才发）。
6. 响应 `ShopOrderRefundView`（同 AC6.1 的条目结构）。
7. 日志与审计不出现账号、户名（P-7、NFR4）。

### AC5 — 财务标记与成长值扣回 `[L0]` `[L1]`（D-15、FR-134.4 / .5、m1）

1. `markPaidOut(refundToken, actorAdminId)`：`PAYOUT_PENDING → COMPLETED`、写 `paid_out_at`；发 `RefundSucceededEvent("SHOPREF:{token}:CASH_BANK", userId, SHOP_ORDER, "SHOP_ORDER", orderId, null, cash_refund, order.paidTotal())`；`settleOrderIfDone`。重复调用（已 COMPLETED）→ 幂等返回，不重复发事件。
2. `markPayoutFailed(refundToken, note, actorAdminId)`：`PAYOUT_PENDING → PAYOUT_FAILED`、写 `payout_failed_at` 与备注（≤ 200 字，不含账户）；**不推送**（PRD：由客服联系）。用户可重选（AC4.3）。
3. 扣回事件三处各一次：币段退回（AC3 第 3 步）、现金选 PawCoin（AC4.4）、标记已打款（AC5.1）；`refundKey = "SHOPREF:{退款单 token}:{COIN | CASH_PAWCOIN | CASH_BANK}"`，同一退款单多段不被 `GrowthRefundListener` 去重吞掉（其幂等键 `REV:{原id}:REFUND:{refundKey}`）。金额 = 本次退款额，`originalAmount = order.paidTotal()`；`GrowthRefundListener` **不改**（已按占比扣回、累计封顶）。
4. **`reason = LATE_PAYMENT` 的退款单在任何环节（建单、选 PawCoin、标记已打款）都不发 `RefundSucceededEvent`**：迟到款不是这张订单的消费（原单从未入账成长值；若是「重复付款」的单，原单那笔合法付款入过账，发事件反而会错扣）。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 币段拆分按「每次 floor(本次 × C / T)，封顶剩余币；退到剩余全部时取剩余」**：严格按 PRD 11-05 与 epics 原文；不复用退货线的累计法 `RefundSplit.accumulate`（两者首笔相同，多笔部分取消后单笔可能差 1 盾，末笔都精确归零）。
- **② 补偿基数从币段改为「现金段选退为 PawCoin」**：PRD 11-05 拍板；现异常订单对币段发补偿的行为随 AC7 取消。
- **③ `refunded_total` 在退款单生成时即累加（含尚未打款的现金段）**：与退货线 `RefundExecutionService` 一致（「置 REFUNDED 即记账，TO_BANK 不等线下打款」），且 S-5 要求取消时 `refunded_total` 立即准确。
- **④ COMPENSATION 不改 `refunded_qty`**：货未退回；门店返佣是否扣回随 S-5 遗留由商家仓决定。
- **⑤ 退款单无 `COIN_REFUNDED` 状态**：架构列了该值但没有任何写入方（币段在建单同事务即退，现金为 0 直接 `COMPLETED`），不建悬空状态。

### 实现提示

  RefundOrderSnapshot snap = RefundOrderSnapshot.of(order, orderLines.findByOrderIdOrderByIdAsc(order.getId()));

## 待确认 / 发现的规划冲突

1. **币段取整方法与退货线不一致**：本线按 PRD / epics「每次 ⌊本次 × C / T⌋，零头入现金，最后一件取剩余」；退货线 `RefundSplit.accumulate` 用「累计 ⌊累计 × C / T⌋ − 已退币」。两者首笔相同、末笔都精确归零，多笔部分取消时中间单笔可能差 1 盾（AC2.8 例 4：第二次 A×1 本法 27,726，累计法 27,727）。如需统一请拍板。
2. **丢件破损「未保价协商额」是否再减已退**：epics 写「均减去此前部分取消已退金额」。本 story 解释为运营输入的是「这单总共赔多少」，`total = max(0, N − RT)`；若运营输入的是「本次再赔多少」请回改 AC2.3。
3. **架构 `status` 列有 `COIN_REFUNDED`**：无任何写入方，本 story 不建（拍板点 ⑤）。
4. **D-15 只列 `payout_account_enc`**：App 退款方式页（`refund_method_page_v2.dart:63-64`）同时收集户名，退货线也存了户名；本 story 增 `payout_account_holder_enc`。
5. **D-24 stag 入口只列「取消」「标记已打款」**：本 story 增「入库确认」「标记打款失败」两个入口，10.1 验收 S-8 与 F25 需要。
6. **COURIER_FAULT 整单取消不回补库存**（架构原文）：快递原因被退回的货物实际会回到仓库，若需要回补应由运营走入库流程；本 story 按架构不自动回补。
7. **D-15 表里 `refunded_qty` 对 S-9 赔付不累加**：货没退回，本 story 不动行数量；门店返佣是否扣回随 S-5 由商家仓决定。
8. **整单缺货取消的订单状态由 `CANCELLED` 变为 `REFUNDING / REFUNDED`**：符合 D-15，但后台既有页面 / 统计若按 `CANCELLED` 识别缺货取消，需后台线同步（`ShopFinanceDashboardService` 订单维度查询排除的是 `PENDING_PAYMENT, CANCELLED`，`REFUNDED` 单会被计入订单金额，其退款经 `refunded_total` 抵扣 —— 与退货线口径一致）。

### 复审修复（2026-11-05，协调者复审）

- **① 资金（近纯币单边界）**：部分取消的币段在 `⌊total × C / T⌋`（封顶剩余币）之后再施加下限 `coin ≥ total − 剩余现金`，剩余现金 = `(T − C) − (RT − RC)`，并保持 `coin ≤ C − RC`、`coin ≤ total`。原公式在近纯币单（复现：T = 100,000、C = 99,999、4 件各 25,000 逐件取消）会把币的零头累计成现金退出、超过用户实付现金，最后一件剩余币 > 剩余应付被截断 → 少退币多退现金。修正后累计现金 ≤ T − C、累计币 ≤ C，末件转整单币精确归零。**这是对 story 公式在近纯币单边界的修正，需产品 / 规划层确认（见「待确认」1）**。AC2.8 的 22 个例子期望值未改、结果全部不变。新增单测 `nearPureCoinPartialsKeepCoinSegment`。
- **② 运单钩子顺序**：`cancelWhole` / `cancelLine` 的全部校验（状态、注销、计算器）挪到 `ShopWaybillCanceller` 之前；部分取消只在计算器判定 `becameWhole` 后才调钩子。**给 5.1**：实现 `ShopWaybillCanceller` 时应只登记意图，**事务提交后（`afterCommit` / `AFTER_COMMIT`）再调 Biteship 取消**，避免 `@Version` 冲突等回滚时订单未取消而运单已取消（接口 Javadoc 已写明）。新增单测 `hookNotCalledWhenValidationFails`。
