## Story

As a 喜欢某只宠物的用户,
I want 单独追更这只宠物,
so that 不用关注主人也能跟进它的成长。

## Acceptance Criteria

> 层级：`[L0]` 纯单元 / 静态（云端可跑）· `[L1]` 需 Docker postgres + redis（本地）· `[L2]` 真机 / 视觉（本 story 无）。

### AC1 — 迁移 ① `V20261104_2000__create_pet_follows.sql` `[L0]` `[L1]`（D-1、P-8 ①）
1. 建表（复合主键，两个 FK 都 `ON DELETE CASCADE`）：
   ```sql
   CREATE TABLE pet_follows (
       follower_id     BIGINT      NOT NULL,
       pet_profile_id  BIGINT      NOT NULL,
       created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
       CONSTRAINT pk_pet_follows PRIMARY KEY (follower_id, pet_profile_id),
       CONSTRAINT fk_pet_follows_follower FOREIGN KEY (follower_id) REFERENCES users (id) ON DELETE CASCADE,
       CONSTRAINT fk_pet_follows_pet FOREIGN KEY (pet_profile_id) REFERENCES pet_profiles (id) ON DELETE CASCADE
   );
   CREATE INDEX idx_pet_follows_pet_created ON pet_follows (pet_profile_id, created_at);
   CREATE INDEX idx_pet_follows_follower_created ON pet_follows (follower_id, created_at);
   ALTER TABLE pet_profiles ADD COLUMN follower_count INTEGER NOT NULL DEFAULT 0;
   ```
2. 整数列一律 `INTEGER`，**禁止 SMALLINT**（Hibernate `int → int4`，validate 全红的老坑）。
3. 文件头注释写明：宠物删除是物理删除（`ProfileDeletionService.deletePetRows`）→ 追更行由 FK 级联清理；**账号注销只匿名化 users 行，`fk_pet_follows_follower` 的 CASCADE 在注销路径上永不触发**，追更者一侧必须走 AC7 显式清理。
4. 不回填（新功能，存量为 0）。提交前本地自查 `bash scripts/ci/check-flyway-versions.sh origin/main`（云端跑不通在 Completion Notes 记一句）。

### AC2 — 实体与计数 `[L0]` `[L1]`（D-1、P-4）
1. 新建 `com.tailtopia.social.domain.PetFollow`（`@Table(name = "pet_follows")`，`@IdClass(PetFollow.Key.class)`，字段 `followerId` / `petProfileId` / `createdAt`，写法照抄 `social/domain/UserFollow.java`）。1.3 的关注流 JPQL 要 join 它，所以**必须是 JPA 实体**。
2. `PetProfile` 增加 `followerCount`：`@Column(name = "follower_count", nullable = false, insertable = false, updatable = false) private int followerCount;` + getter。**只读映射**：`PetProfile` 带 `@DynamicUpdate`（只写脏列），但仍禁止任何代码读出 ±1 再 save（并发丢更新）；计数只走 AC2.3 的 native 条件 UPDATE。
3. `PetProfileRepository` 新增 `@Modifying` native：`UPDATE pet_profiles SET follower_count = GREATEST(follower_count + :delta, 0) WHERE id = :petId`（照 `UserRepository.addFollowerCount` 写法）+ 写后重读 `findFollowerCount`；拉黑联动 / 注销清理的批量扣减改为 `PetFollowRepository` 里「DELETE … RETURNING + UPDATE」单条 CTE（原子，被删的行才扣；见 AC6 / AC7，实现修订）。
4. `ddl-auto=validate` 下实体与表必须一致（`INTEGER ↔ int`、`TIMESTAMPTZ ↔ Instant`）。

### AC3 — `POST /api/v1/me/pet-follows/{petId}` 追更 `[L0]` `[L1]`（D-8、PRD FR-153 关注关系 / 拉黑）
拒绝顺序（照 `FollowService.follow` 的结构，逐条有测试）：
1. 限流：`rateLimiter.check("rl:social:follow:" + viewerId, 30, 1 分钟)`（**与关注人共桶**），超限 429。
2. 调用者本人必须 `accounts.isActive(viewerId)`，否则 401（同 `FollowService.follow` 的注释：注销后残留 access token 不能再长出新行）。
3. 宠物不存在，或主人 `!accounts.isActive(ownerId)`（已注销 / `DEACTIVATED`）→ **404**（ProblemDetail，不区分原因）。READ_ONLY 宠物可以被追更。
4. 宠物属于自己 → **422**（`AppException.validation`，「不能追更自己的宠物」）。
5. **我** BLOCK 了主人（`hideRelations.isBlocked(viewerId, ownerId)`）→ **403** `AppException.blockedUser`（type `blocked-user`，与站内访客页同口径）。
6. **主人 BLOCK 了我 → 照常成功**（不暴露被拉黑；通知抑制在 1.2）；`REPORT` 来源隐藏不拦。
7. 已追更 → 直接返回当前态（幂等，**不计入每日额度、不发事件、不改计数**）。
8. 每日额度（AC5）超限 → 429。
9. `INSERT … ON CONFLICT (follower_id, pet_profile_id) DO NOTHING`，**受影响行数 = 1 时**才在同一事务里 `follower_count + 1` 并发布 `PetFollowedEvent`（并发双击只算一次、只发一次）。
10. 响应 `PetFollowResultResponse(boolean iFollow, long followerCount)`（`followerCount` 写后重读，同 `FollowCounterService.followerCountOf`）。

### AC4 — `DELETE /api/v1/me/pet-follows/{petId}` 取消追更 `[L0]` `[L1]`（D-8）
1. 先限流（同桶）；**不校验主人状态**（主人 `DEACTIVATED` 期间也能取消，PRD AC11）；不校验拉黑。
2. 宠物不存在 → 404；存在但未追更 → 幂等成功（`iFollow=false`）。
3. `DELETE` 受影响行数 = 1 时才 `follower_count − 1`（`GREATEST(…,0)` 兜底）。**不发任何事件 / 通知**（PRD「取消追更不发任何消息」）。
4. 响应同 AC3.10。

### AC5 — 每日额度两表合计 `[L0]` `[L1]`（D-8、PRD「与关注人共用每分钟 30 次、每日 500 次」）
1. 当日（**WIB 自然日**，日界取 `ScheduleWindow.WIB`，P-6）「`user_follows` 中 `source='USER'` 且仍存在的新建行」+「`pet_follows` 中仍存在的新建行」≥ 500 → 429。
2. 追更（AC3）与**关注人**（`FollowService.checkDailyLimit`）都按这个合计判定 —— 关注人那边改为调用同一个合计方法（建议抽一个 `social.service.FollowDailyQuota` 组件，两个 service 共用，避免两处各写一遍）。
3. `FollowService.WIB` 常量改用 `ScheduleWindow.WIB`（行为不变）。
4. Given 当日已追更 500 只，When 关注一个人，Then 429（反之亦然）；Given 当日关注 + 追更合计 499，When 再追更一只，Then 成功。

### AC6 — 拉黑联动 `[L0]` `[L1]`（D-11、PRD 拉黑 4 条）
1. `UserHideRelationService.block(holderId, targetId)` 在**同一事务**内、`followService.removeOnBlock` 之后调用 `petFollowService.removeOnBlock(holderId, targetId)`：删除「holder 对 target 名下**所有宠物**」的追更行，并对每只被删的宠物 `follower_count − 1`（一条 `DELETE … RETURNING pet_profile_id` + 批量扣减，或逐只条件扣减，任选，但不得读后 save）。
2. `target` 对 `holder` 宠物的追更**不动**；不限流、不发任何事件 / 通知；重复拉黑删 0 行无副作用；`unblock` 不恢复；`hideByReport` 不碰追更。
3. Given A 拉黑 B，When 拉黑提交，Then A 对 B 全部宠物的追更消失、对应计数 −1，B 对 A 宠物的追更与计数不变。

### AC7 — 注销 / 删宠 / 封号 `[L0]` `[L1]`（D-11、PRD AC10 / AC11）
1. **宠物被删**：FK 级联删行，无需代码；因为宠物行本身也没了，计数无需修正。不发任何通知。
2. **追更者注销**：`PetFollowService.purgeFollower(userId)`（`@Transactional`，幂等可重跑）—— 先对他追更的每只宠物 `follower_count − 1`（一条 `UPDATE pet_profiles p SET follower_count = GREATEST(p.follower_count - 1, 0) FROM pet_follows f WHERE f.follower_id = :uid AND f.pet_profile_id = p.id`），再删他的全部追更行。
3. 在 `AccountDeletionService.execute` 中紧挨 `followService.purgeUser(userId)`（现 :244，`authDeletion.deleteByUserId`（:239）之后）调用，并加注释说明为什么放在 `authDeletion` 之后（此时 `deleted_at` 已写，AC3.2 拒绝新追更，清完不会再长出新行）。构造器末尾追加参数。
4. **主人注销**：`profileDeletion.deleteAllForAccount` 逐只物理删宠 → 追更行级联消失（无需代码），无通知；Then 该主人宠物从所有追更者的列表里消失。
5. **主人或追更者封号（`DEACTIVATED`）**：**不清理**、不改计数；追更者 Hewan 列表里该宠物仍在（AC8.3）、可取消（AC4.1）。

### AC8 — `GET /api/v1/users/{token}/pet-follows?cursor=` 某用户追更的宠物 `[L0]` `[L1]`（D-8、G-1、R-2）
1. 主页用户解析**照抄** `FollowListQueryService.resolveOwner`：不存在 / 已注销 / 封号 → 404；官方号（`role=ADMIN`）且非本人 → 403；我拉黑了他 → 403 `blocked-user`。
2. 行（按 `pet_follows.created_at DESC, pet_profile_id DESC` 游标分页，每页 20，游标 `KeysetCursor(createdAt, petProfileId)`，坏游标按首页）：
   `{ petId, name, petType, avatarUrl, ownerNickname, ownerToken, iFollow, iFollowOwner }`
   - `petId` 与站内访客路由 `/pets/{petId}` 同一标识（现有站内访客、推荐卡已以 petId 寻址，未新增可枚举暴露面）；
   - `avatarUrl` 走 `AliyunOssClient.exifStrippedThumbUrl`（他人宠物图一律服务端去 EXIF，同 `PetRecommendationService`）；
   - `ownerToken` = 主人公开 token（`accounts.publicTokensOf(ids, true)`，封号也给，供埋点 `owner_id`）；
   - `iFollow` = **查看者**是否追更该宠物；`iFollowOwner` = 查看者是否关注该宠物主人；游客两者恒 false；
   - 整页各一次批量查询（宠物、主人投影、token、我的追更集合、我的关注集合），**禁止 N+1**。
3. **主人 `DEACTIVATED` 的宠物仍列出**（PRD AC11，可取消）；主人注销 / 宠物删除的行因级联已不存在。
4. 信封 `{ items, nextCursor, hasMore, petFollowingCount }`；`petFollowingCount` = 该用户 `pet_follows` 行数（只在首页 `cursor == null` 时计算并下发，后续页省略，NON_NULL）。
5. 空集返回 `{items: [], hasMore: false, petFollowingCount: 0}`。

### AC9 — 访客 / 用户主页 / 统计新字段 `[L0]` `[L1]`（D-8、G-1、R-2）
1. 站内访客 `GET /api/v1/pets/{petId}/visitor/profile`（`InAppVisitorPetController.profile`）响应追加：`iFollow`（我是否追更）、`iFollowOwner`（我是否关注主人）、`ownerToken`（主人公开 token）。
   - ⚠️ `VisitorProfileResponse` 同时被**分享 token 公开路径**（`VisitorPetController`，permitAll、游客可读）使用 —— 公开路径**不填**这三个字段（装箱 null → 全局 NON_NULL 不下发），只有站内入口填。理由：该 record 是白名单（类注释「陌生人有必要知道这个吗？」），分享链接可外转，不在公开路径多吐主人 token。
2. 统计：`ArchiveStatsResponse` 末尾追加 `long followerCount`（= 该宠物 `pet_profiles.follower_count`，在 `TimelineService.getStats(ownerId, petId)` 里从已取到的 `profile` 直读，不加查询）；`VisitorStats` 末尾追加 `long followerCount`，`VisitorProjectionService.stats` 透传。App 两处共用一个模型类（`VisitorStats` 注释），**字段名必须同名**。主人 Diary Tab（作者态 `/api/v1/pet-profiles/me/archive-stats`）同步可用。
3. 用户主页 `GET /api/v1/users/{userId}/profile`（`PublicProfileResponse`）末尾追加 `long petFollowingCount`（该用户追更的宠物数，注销态 0）。auth 模块只经新读端口 `social.read.PetFollowReader.countFollowingOf(userId)` 取，**不引用 `social.repository`**（CROSS-STORY「content / notify / auth 三侧只依赖端口接口」）。
4. 只加字段、不改既有字段语义；更新所有构造调用点（`new ArchiveStatsResponse(` 1 处主代码 + 测试 2 处；`new VisitorStats(` 1 处 + 测试 1 处；`PublicProfileResponse` 工厂 `deactivated()` 等）。

### AC12 — 安全配置 `[L0]` `[L1]`
1. `SecurityConfig` 精确规则（照 `/api/v1/users/*/follow` 的注释写法，不写 `/api/v1/me/**` 通配）：

### 拍板点（按建议实现，Completion Notes 复述）

- **① 追更时「我拉黑了主人」用 403 `blocked-user`，不用关注侧的 409 `follow-blocked`**：架构 D-8 / epics 明写 403，且与站内访客页 `requireVisible` 同一个 type。App 侧（1.4）按 `!= 429` 一律顶部 toast 回滚，两种码都不影响体验。
- **② 取消追更时宠物不存在 → 404**：宠物已删则追更行已级联消失，无可取消对象；App 列表行不会再出现该宠物。
- **③ `petFollowingCount` 只在列表首页下发**：后续页不重复计数（计数是一次 `COUNT(*)`，首页附带即可）。用户主页另有同名字段（AC9.3），「Hewan N」胶囊优先取主页那份（App 进页即有）。
- **④ 公开分享路径不下发 `ownerToken` / `iFollow*`**：见 AC9.1。

### 实现提示

- `PetFollowService.follow` 骨架：
  ```java
  @Transactional
  public PetFollowResultResponse follow(long viewerId, long petId) {
      checkRate(viewerId);                                  // rl:social:follow:{uid}，30/min，共桶
      if (!accounts.isActive(viewerId)) throw AppException.unauthorized("登录已失效，请重新登录");
      PetProfile pet = pets.findById(petId).filter(p -> accounts.isActive(p.getOwnerId()))
              .orElseThrow(() -> AppException.notFound("宠物不存在"));
      if (pet.getOwnerId() == viewerId) throw AppException.validation("不能追更自己的宠物");
      if (hideRelations.isBlocked(viewerId, pet.getOwnerId())) throw AppException.blockedUser("你已拉黑该用户");
      if (!petFollows.existsByFollowerIdAndPetProfileId(viewerId, petId)) {
          quota.check(viewerId);                            // 两表合计 ≥500 → 429
          if (petFollows.insertIfAbsent(viewerId, petId) == 1) {
              pets.addFollowerCount(petId, 1);
              events.publishEvent(new PetFollowedEvent(viewerId, petId, pet.getOwnerId(), clock.instant()));
          }
      }
      return new PetFollowResultResponse(true, pets.findFollowerCount(petId));
  }
  ```
  social 读 `PetProfileRepository`（profile 模块）—— 如嫌跨模块，可在 profile 侧提供一个窄端口 `PetFollowTargetReader`（`findForFollow(petId) → (petId, ownerId)` + `addFollowerCount`）；任选其一，但**不要在 social 里直写 `pet_profiles` 的 SQL 字符串散落多处**。在 Completion Notes 写明选了哪种。
- 插入一律 `ON CONFLICT DO NOTHING` 单语句，不要「save + catch 唯一约束异常」（异常穿出 repo 代理会把外层事务标 rollback-only，见 `UserHideRelationService.insertIfAbsent` 注释）。
- 拉黑联动删除建议：
  ```sql
  WITH d AS (DELETE FROM pet_follows f USING pet_profiles p
              WHERE f.follower_id = :holder AND f.pet_profile_id = p.id AND p.owner_id = :target
          RETURNING f.pet_profile_id)
  UPDATE pet_profiles SET follower_count = GREATEST(follower_count - 1, 0) WHERE id IN (SELECT pet_profile_id FROM d)
  ```
  （一条语句，原子；`@Modifying` native。）
- 列表查询按 `(created_at, pet_profile_id) < (:ts, :id)` 行比较 + `ORDER BY created_at DESC, pet_profile_id DESC LIMIT 21`，走 `idx_pet_follows_follower_created`。

- Controller 的 `currentUserId` / `viewerId` 照 `FollowController`（`viewerId` :90、`currentUserId` :101）写法。
