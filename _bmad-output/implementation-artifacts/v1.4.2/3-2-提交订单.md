## Story

As a 买家,
I want 提交时锁定我选的快递、券和 PawCoin,
so that 付款金额就是我看到的金额。

### AC3 — `POST /api/v1/me/shop-orders` 重写（新结算模式）`[L0]` `[L1]`（D-8、FR-128.5 / .6、FR-172.2、I7）

1. 请求体 `PlaceOrderRequest`（**在原 record 上加字段**，旧三字段保留）：
   `{ addressToken, entrySource, triggerType, source, buyNow{skuToken, qty, entrySource}, quoteToken, courierKey, insurance, discountCouponToken, freeShippingCouponToken, useCoin, agreeReturnPolicy }`。
   **判别**：`quoteToken` 为空或空白 → 旧结算模式（AC5）；非空 → 新模式（本 AC）。
2. 新模式**同一个 `@Transactional`**，按序（任一步失败整体回滚：券、币、库存、订单、购物车全部不落）：
   1. 幂等：`Idempotency-Key` 沿用 `"shop-checkout:" + userId + ":" + key`（`CheckoutService.java:213-220` 写法），命中 → 返回既有订单。
   2. `agreeReturnPolicy != true` → **422**（`AppException.validation`，detail「请先同意退货规则」）。
   3. 行解析（复用 3.1 `CheckoutLineResolver`）：`CART` = 选中有效行（含选中失效行用于报错）；`BUY_NOW` = 单 SKU × qty（1..99）。无可结算行 → **422 `not-placeable`**；有不可买行（下架 / 售罄 / 库存不足 / 不可售）→ **409 `unavailable-lines`**，扩展成员 `unavailableLines[]` 逐行（`UnavailableLine` 新增 `REASON_NOT_SELLABLE = "NOT_SELLABLE"`）。
   4. 地址：`addressToken` 必填（空 → 422 `not-placeable`）；`ShippingAddressService.require`（非本人 404）；区域未开通 → 422 `not-placeable`。
   5. **报价锁定与绑定**（I7）：按 `quoteToken` 取 1.1 的 `shipping_quotes` 行 —— 不存在、已过 `expires_at`、`dest_postal_code ≠ 地址 kode_pos`、`items_hash ≠ 由本单行（SKU 包裹参数 × qty）重算的哈希`、`courierKey` 不在该报价的快递列表中，**任一** → **409 `quote-expired`**（App 重新试算）。**不再询价**（本步零网络调用）。
   6. 券：按两个用户券 token 取本人用户券 → 以 MANUAL 选择交计价器；计价器 `PricingResult.manualSelectionInvalid == true`（指定券未达门槛 / 不在范围 / 已过期 / 不是 AVAILABLE，1.2 AC1）→ **409 `coupon-invalid`**；免运券被判 `RULE_BETTER` → **不报错、不占用**（用户得到的减免只多不少；以 `appliedFreeShippingUserCouponToken` 为准决定是否占用）。
   7. 计价：`ShopPricingCalculator.price(PricingInput)`（1.2；**服务端重新计价，不信任客户端金额**；价格变动不比对、不提示，PRD FR-128.6）。入参：行、券、免运规则、所选快递价、本单最低报价、`insurance && 快递支持保价`、`useCoin && rules.enabled`、**当前**余额、上限。
   8. 建单：新工厂 `ShopOrder.placeCheckout(PlaceSnapshot)`（保留旧 `place(...)` 两个重载给存量调用），写：

   9. 订单行：`ShopOrderLine.of(...)` **`unit_price` 仍为原单价、不分摊券**（NFR7 返佣基数）；`discount_eligible` = 该行在**实际采用的**满减券适用范围内（无满减券 → false）。1.2 的 `PricingResult` 不含逐行范围信息，本 story 在 `ShopPricingCalculator` 公开其内部范围匹配为静态方法 `inScope(PricingLine, PricingCoupon)`（与计算 `eligible` 用的是同一段代码，不另写一份），提交时逐行调用；归因 `entrySource / triggerType`（CART 取购物车行记录，BUY_NOW 取 `buyNow.entrySource`）。

   14. 现金段为 0 → 同事务 `ShopOrderPaymentService.markPaid(order, PaidSource.PURE_COIN)`（AC4）。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 判别新旧模式只看 `quoteToken`**（架构 D-8 原文）。新版 App 必须总是带 `quoteToken`；询价失败时 App 不可提交，所以不存在「新版无 token」的合法请求。
- **② 免运券被判 `RULE_BETTER` 时静默不占用**，不报 `coupon-invalid`：用户实际得到的减免只会更多（满额免运更划算），报错反而让用户困惑。
- **③ 未付款作废退币用独立 `refType = "SHOP_ORDER_VOID"`**：与已付款退款（`SHOP_ORDER`）区分，财务 `coinSpent` 才能精确扣除「提交扣、取消退」的往返（AC7）。
- **④ 存量待付款单过渡**：`checkout_source IS NULL` 判定为旧规则订单（AC6.4），避免上线瞬间在途订单「到账不扣币白拿货」或「取消时退了从没扣过的币」两种资损。
- **⑤ `shop_payment_paid` 改挂 `ShopOrderPaidEvent`**：一处发，纯币 / 网关 / 重下单三条路径都覆盖，迟到款不误发。

## 待确认 / 发现的规划冲突

1. **`shop_order_lines.discount_eligible`（架构 D-8 未列）**：4.1 的满减分摊公式需要「适用商品金额」与「该行是否在适用范围」，而订单行既无品类也无券范围快照；从券模板现查有「模板范围事后被改」的风险。本 story 在同一迁移加该快照列（AC1.2），不是金额同义列。若规划方另有设计（例如订单头存适用金额）请回改 4.1 / 本 story。
2. **`checkout_source` 增加 `REORDER`（架构 D-8 只列 `CART | BUY_NOW | LEGACY`）**：4.2 迟到款重下单的新单需要一个来源值，且它的币在重下单时扣（与新模式一致，不能被当成 `NULL` 存量单走过渡规则）。本 story 在 CHECK 中加入 `REORDER`。
3. **未付款作废退币不计 `refunded_total`、不发 `RefundSucceededEvent`**：架构说「所有取消路径退回已扣币」，但没说记不记退款累计。本 story 定为不记（理由见 AC6.3），财务改用 `refType=SHOP_ORDER_VOID` 扣除（AC7）。
4. **上线过渡**：架构未提在途存量待付款单（上线前已下、币未扣）的处理。本 story 用 `checkout_source IS NULL` 判定并保留旧规则（AC6.4），需在 10.1 联调里用「上线前下单 → 上线后付款 / 取消」各验一例。
5. **2.1 的券转 USED 挂点**：2.1 只提供 `markUsed(orderId, now)`、由本线调用；本 story 定为只在 `markPaid` 内调用（AC4.1 第 3 步），不挂意图事件，以免 3.3 的迟到款意图误动券。
6. **计价器需公开范围匹配**：1.2 的 `PricingResult` 不含逐行适用信息，本 story 公开 `ShopPricingCalculator.inScope(...)`（AC3.2 第 9 步）供写 `discount_eligible`，属对 1.2 的增量，不改其对外出参。
