## Story

As a 追更者,
I want 在关注流看到追更宠物的新 Diary、推荐里不再出现已追更的宠物,
so that 关注流就是我关心的全部动态。

## Acceptance Criteria

> 层级：`[L0]` 纯单元 / 静态（云端可跑）· `[L1]` Docker postgres + redis（本地）。本 story 无 L2。

### AC1 — 关注流 = 关注的人 ∪ 追更宠物的公开 Diary `[L1]`（D-9、PRD AC3 / AC4）
改 `ContentPostRepository.findFollowingFeed`（:672-704）：
1. 公共条件**不变**：`deletedAt IS NULL`、`status = PUBLISHED`、`visibility = PUBLIC`、作者未注销且 `status = ACTIVE`、我没举报过这条、作者不在我的隐藏名单（`UserHideRelation h.holderId = :viewerId AND h.targetId = p.authorId`，不分来源）、游标 `(createdAt, id) <`。
2. 来源条件改为两路 OR（**一条查询天然按帖去重**，游标与排序 `createdAt DESC, id DESC` 不变）：
   - **关注的人**：`p.authorId IN (SELECT f.followeeId FROM UserFollow f WHERE f.followerId = :viewerId)` —— **维持 1.3.4 现状，一个谓词都不加**；
   - **追更的宠物**：`p.type = GROWTH_MOMENT AND EXISTS (SELECT 1 FROM ContentPet cp, PetFollow pf WHERE cp.id.postId = p.id AND pf.petProfileId = cp.id.petProfileId AND pf.followerId = :viewerId) AND NOT EXISTS (作者 BLOCK 了我：UserHideRelation h2 WHERE h2.holderId = p.authorId AND h2.targetId = :viewerId AND h2.source = BLOCK)`。
3. Given 只追更 Mochi、未关注主人，When 主人发公开 Diary（关联 Mochi），Then 出现在关注流；Mochi 的私密 Diary、主人的 Moment / Tips 不出现。
4. Given 同时关注主人并追更 Mochi，或一帖关联我追更的 Mochi 与 Kopi，Then 该帖只出现一次。
5. 宠物 READ_ONLY 照常出现；主人 `DEACTIVATED` / 注销 → 由公共条件排除。

### AC2 — 拉黑组合口径（R-1，收窄后的 PRD AC9）`[L1]`
1. Given 宠物主人 A BLOCK 了我（B）且**我未关注 A 本人**，Then A 宠物的 Diary 不出现在我的关注流。
2. Given A BLOCK 了我、**我同时关注 A 本人**，Then A 的内容（**含其宠物 Diary**）仍从「关注的人」一路出现 —— 维持 1.3.4 现状（拉黑只删 A→B 的关注，B→A 保留；不让被拉黑方察觉）。这条必须有组合用例。
3. Given 我拉黑 / 举报隐藏了 A，Then A 的任何内容都不出现（公共条件，两路都生效）。

### AC3 — 每条带 `reason`、首页带两个计数 `[L0]` `[L1]`（D-9、P-5、PRD §4、UI A11）
1. `FeedItemResponse` 末尾新增 `String reason`：**只在关注流出口**填值，其余出口为 null（全局 NON_NULL 不下发，Discover / 我的发布 / 他人主页 key 集合不变）。
   - 判据：作者在我的关注名单中 → `followed_user`；否则 → `followed_pet`（P-5 小写下划线）。
   - 取值直接用 `assemble` 已算好的 `authorFollowState.iFollow`（`FeedService.authorFollow`:119-131，整页一次 `followReader.followStates`），**不再加查询**。
2. `FeedPageResponse` 末尾新增 `Long followingUserCount`、`Long followingPetCount`：**只在关注流首页（`cursor == null`）**填值，其余（后续页、Discover、我的发布）为 null 不下发。
   - `followingUserCount` = 我当前关注的人数（`users.following_count`，含系统自动关注的官方号 —— 与「我的页四格 Mengikuti」同一个数）；
   - `followingPetCount` = 我追更的宠物数（`PetFollowReader.countFollowingOf(viewerId)`）。
   - 为现有 3 处 `new FeedPageResponse(…, rankMode)`（`FeedService`:403 / :551 / :601）保留 4 参兼容构造器，避免改动面扩散。
3. App 据此区分两种空态（1.5）：两者都为 0 → 现有空态；任一 > 0 且首页无帖 → 「暂无新动态」。

### AC4 — 可见性四件套与游标 `[L1]`（P-2、NFR1）
1. 追更一路与关注一路逐条一致：举报过的帖、我隐藏的作者、作者已注销、作者非 ACTIVE —— **每条各一个测试**（含追更一路）。
2. 翻页：两路混合 45 条，按 20 一页翻 3 页，无重、无漏、顺序严格 `createdAt DESC, id DESC`；同一 `createdAt` 的帖以 id 断开。
3. 空集：既无关注也无追更 → `items = []`、`hasMore = false`、`followingUserCount = 0`、`followingPetCount = 0`。

### AC5 — 性能核查 `[L1]`（§6.3、NFR3）
1. L1 以接近真实量级造数（建议：viewer 关注 300 人、追更 200 只宠物、库内 5 万帖 / 2 万条 content_pets），对新查询跑 `EXPLAIN (ANALYZE, BUFFERS)`，把计划摘要与耗时**记入 Completion Notes**。
2. 首页 p95 明显劣化（>200 ms 量级）时，改为「两路各取 `PAGE_SIZE+1` 再在内存按 `(createdAt, id)` 归并去重」的两段查询（游标契约不变），并在 Completion Notes 说明。可借助的现有索引：`idx_pet_follows_follower_created`（1.1）、`idx_content_pets_pet_post`、`user_follows` 主键。

### AC6 — 宠物推荐排除已追更 `[L0]` `[L1]`（D-17、PRD「列表」、UI A8）
1. `PetRecommendationService.pageFor`（:119）：在候选循环前对**本页候选 petId 一次批量**取 `petFollowReader.followedAmong(viewerId, petIds)`（**不在循环里逐个查**），循环中与「不推给自己」（:173）并列跳过已追更的宠物。
2. 接口级生效：首页「Kenalan sama anabul lain」横滑行（`recommendFor` → `pageFor`）与「Lihat semua」集合页一起不再出现已追更的宠物（合理，PRD 已知悉）。
3. 游标仍取「最后**看过**的候选」（被排除的已追更宠物是确定性排除，越过它们是对的，见方法注释）；`hasMore` 两条判据不变。

### AC7 — 推荐排序改用近 14 天点赞 `[L1]`（D-17、PRD 2026-11-03 拍板、§1.2 第 13 条）
1. `ContentPostRepository.findRecommendablePets` 的 `liked` CTE（:101-112）加 `AND l.created_at >= :since`（`:since` 即已有的「14 天前」参数，与入选窗口同一个值）；其余谓词、`ORDER BY`、行比较游标**一字不改**。
2. 排序结构不变：WIB 日期桶 DESC → 近 14 天点赞数 DESC → 最后发帖时刻 DESC → petId DESC。
3. 已知存量现象（不在本 story 修）：多宠帖的一个赞会计入每只关联宠物（§1.2 第 13 条），保持现状。
4. Given 两只宠物同一天更新、老宠物累计 500 赞但近 14 天 0 赞、新宠物近 14 天 3 赞，Then 新宠物排在前。

### 关注流 JPQL 示意（以实际字段名为准）

```java
@Query("""
        SELECT p FROM ContentPost p
        WHERE p.deletedAt IS NULL
          AND p.status = com.tailtopia.content.domain.PostStatus.PUBLISHED
          AND p.visibility = com.tailtopia.content.domain.ContentVisibility.PUBLIC
          AND p.authorId IN (SELECT u.id FROM User u
                             WHERE u.deletedAt IS NULL
                               AND u.status = com.tailtopia.auth.domain.UserStatus.ACTIVE)
          AND NOT EXISTS (SELECT 1 FROM ContentReport r WHERE r.postId = p.id AND r.reporterId = :viewerId)
          AND NOT EXISTS (SELECT 1 FROM UserHideRelation h WHERE h.holderId = :viewerId AND h.targetId = p.authorId)
          AND (
                p.authorId IN (SELECT f.followeeId FROM UserFollow f WHERE f.followerId = :viewerId)
             OR (p.type = com.tailtopia.content.domain.ContentType.GROWTH_MOMENT
                 AND EXISTS (SELECT 1 FROM ContentPet cp, PetFollow pf
                             WHERE cp.id.postId = p.id AND pf.petProfileId = cp.id.petProfileId
                               AND pf.followerId = :viewerId)
                 AND NOT EXISTS (SELECT 1 FROM UserHideRelation hb
                                 WHERE hb.holderId = p.authorId AND hb.targetId = :viewerId
                                   AND hb.source = com.tailtopia.social.domain.HideSource.BLOCK))
          )
          AND (:hasCursor = false OR p.createdAt < :cursorTs OR (p.createdAt = :cursorTs AND p.id < :cursorId))
        ORDER BY p.createdAt DESC, p.id DESC
        """)
```
- `UserHideRelation.source` 的映射类型以实体为准（`HideSource` 枚举或字符串）；先读 `social/domain/UserHideRelation.java` 再写。
- 不要在这里改成 native SQL —— 现有方法是 JPQL，保持一致；若 AC5 需要两段查询，再新增 native 方法。

### 拍板点（按建议实现，Completion Notes 复述）

- **① `reason` 用「作者是否在我的关注名单」判定**：一条帖子同时命中两路时记 `followed_user`（与 D-9「作者在我关注中 → followed_user，否则 followed_pet」一致），复用已算好的 `authorFollowState`，零额外查询。
- **② `followingUserCount` 含系统自动关注的官方号**：与我的页四格 / 关注列表 Pengguna N 同一个数（`users.following_count`）。后果：几乎所有用户都 > 0，「关注与追更都为 0 才显示现有空态」实际只在用户主动取关官方号后出现 —— 这是 PRD 规则的自然结果，不另加口径。
- **③ 两个计数只在首页下发**：App 只在首页判断空态；后续页省略省体积。
