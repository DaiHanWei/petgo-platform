## Story

## Acceptance Criteria

### 后端

**AC0 — 话题标识与可见状态（全部接口共用）** `[L0]`（D-13、§3.5 第 1 条、P-5）
1. 路径里的 `{name}` 是话题**标准名**：服务端一律先 `TopicNameRules.normalize`（NFC + `toLowerCase(Locale.ROOT)`）再查，`/topics/KucingLucu` 与 `/topics/kucinglucu` 等价；`isValidName` 不通过直接 404（不查库）。App 对非 ASCII 名做 `Uri.encodeComponent`，Spring 自动解码。
2. 「可访问」= `status IN ('ACTIVE','HIDDEN')`；DISABLED 与不存在**同一个 404 ProblemDetail**（`AppException.notFound("话题不存在")`，不区分、不外泄状态）。
3. 对外只出标准名 `name` 与显示写法 `displayName`，**不出 `topics.id`**。
4. 查看者：沿用 `ContentDetailController.viewerId`（`ContentDetailController.java:75-89`）的口径——只认 `role=USER` 的 JWT，其余（游客 / 兽医 / 运营）按游客处理。

**AC1 — `GET /api/v1/topics/{name}` 详情** `[L1]`（D-13、epics 4.2 AC1、PRD FR-69「话题详情页」AC10 / AC11）
- 200：`TopicDetailResponse { name, displayName, official, description }`。`displayName` 读 `name_display`（后台改大小写后即刻生效，AC11）；`description` 仅 OFFICIAL 有：按 `Accept-Language`（`@RequestHeader(value = "Accept-Language", required = false)`，写法同 `TriageController:56`）以 `id` 开头取 `desc_id`、否则取 `desc_en`，所选语言为空则退回另一语言，两者皆空 → 省略（NON_NULL）。**不返回帖子数**（PRD「本版本不显示帖子数」）。
- HIDDEN 照常 200（隐藏只是不推荐，页面仍可访问）；DISABLED / 不存在 → 404；游客可访问。

**AC2 — `GET /api/v1/topics/{name}/posts?sort=latest|popular&cursor=&page=`** `[L1]`（D-13、P-2、P-5、§3.5 第 3 条、epics 4.2 AC2、PRD FR-69 AC5 / AC6）
1. `sort` 缺省 `latest`；非法值 422。
2. **latest**：`created_at DESC, id DESC` + `FeedCursor` 游标（同关注流，`FeedService.loadFollowingFeed` 写法），每页 `PAGE_SIZE = 20`，多取 1 条判 `hasMore`；响应 `FeedPageResponse(items, nextCursor, hasMore, rankMode=null)`。
3. **popular**：按「累计点赞数 + `comment_weight` × 累计评论数」倒序，并列按 `created_at DESC, id DESC`；**页码分页** `page`（1 起，缺省 1，> 50 → 422，防深翻全表聚合）、每页 20、`OFFSET (page-1)*20 LIMIT 21` 判 `hasMore`；响应 `nextCursor = null`，App 自己递增 `page`。`comment_weight` 每次请求读一次 `PlatformConfigService.feedRank().getCommentWeight()`（单行无缓存，D-14 / §1.2 第 17 条），运营改参数即时生效。翻页间排名变化可能少量重复 / 遗漏（§3.5 第 3 条，接受）。
4. 过滤（**P-2 可见性四件套照抄 `ContentPostRepository.findFollowingFeed`（`:681-705`），每条各一个测试**）：
   - `deleted_at IS NULL`、`status = PUBLISHED`、`visibility = PUBLIC`（私密 / 审核中 / 下架都不出现，PRD AC5）；
   - 作者未注销且 `status = ACTIVE`（`p.authorId IN (SELECT u.id FROM User u WHERE u.deletedAt IS NULL AND u.status = ACTIVE)`）——四件套中「作者已注销」「作者非 ACTIVE」两条**游客也要套**（与人无关）；
   - 「我举报过的帖」「我隐藏的作者（不分 BLOCK / REPORT）」两条：登录才套，游客不套——照 `findFeed`（`:639-659`）的 `:hasViewer` 布尔门控写法（避免 PG 42P18）；
   - **不加**「作者 BLOCK 了我」（P-2：那条只在追更宠物一路加）；**不读** `rank_throttles`（被限流内容照常出现）。
5. 帖子出参与 Feed 同构（`FeedItemResponse`，含 4.1 的 `topicNames`、作者 token / 关注态、赞评数、@ 投影）——**复用 `FeedService.assemble`，不另写组装**（AD-7 Rule 4「复用同一投影的出口口径不得分叉」）。
6. 话题 DISABLED / 不存在 → 404（同 AC0）。

**AC3 — 联想 `GET /api/v1/topic-suggestions?q=`**（⚠️ 路径见「待确认」第 1 条） `[L1]`（D-13、epics 4.2 AC3、PRD FR-69 AC4）
- 需登录（`role=USER`，游客 401、兽医 403）。
- 无 `q`（或空白）：`status = ACTIVE` 的话题按「官方在前 → `heat_score DESC` → `name_norm ASC`」取前 20。
- 有 `q`：先 `normalize`；`q` 含非话题字符或长度 > 30 → 直接返回空表（不查库）；否则 `name_norm LIKE :prefix ESCAPE '\'`（`prefix = q` 中 `\` `%` `_` 逐个转义 + `%`；**`_` 是合法话题字符，不转义就会变成通配**）、`status = ACTIVE`，同样官方在前 → 热度 → 名字，取前 20。
- 排除 HIDDEN / DISABLED。每项 `TopicSummaryResponse { name, displayName, official }`。
- 无匹配返回空表即可——「#名字 · Topik baru」那一行由 App 自己加（4.4）。

**AC4 — `GET /api/v1/topics/home-row` 首页话题行** `[L1]`（D-13、§3.5 第 5 条、epics 4.2 AC4、PRD FR-69 AC9）
- 先取 `featured_order IS NOT NULL AND status = 'ACTIVE'` 按 `featured_order ASC`；不足 5 个再按 `heat_score DESC, id DESC` 补 `status = 'ACTIVE' AND featured_order IS NULL AND heat_score > 0`，合计最多 5。
- 每项 `TopicSummaryResponse { name, displayName, official, featured }`（`featured` = 是否运营指定，App 埋点 `is_pinned_by_ops` 用）。HIDDEN / DISABLED 不出现；一个都没有返回空表（App 整行隐藏）。游客可访问。

**AC5 — `GET /api/v1/topics/{name}/related` 推荐话题** `[L1]`（D-13、epics 4.2 AC5、PRD FR-69 空态「推荐话题 10 个」、UI C9）
- 当前话题可访问（否则 404）时，返回 `status = 'ACTIVE' AND id <> 当前 AND heat_score > 0`，按 `heat_score DESC, id DESC` 前 10，每项 `{ name, displayName, official }`；不足 10 有几个给几个。游客可访问。

**AC6 — `GET /api/v1/content-posts/pinned?topic={name}` 与话题页让位** `[L1]`（D-6、D-13、epics 4.2 AC6、PRD FR-69 AC7、决策日志「评审中直接更正」末条）
1. `ContentPin` 加 `public static final String SLOT_TOPIC_PREFIX = "TOPIC:"` 与 `public static String topicSlot(long topicId)`（6.1 / 6.2 共用，**不要各自拼字符串**）。
2. `ContentFeedController.pinnedSlot`（`ContentFeedController.java:58-62`）加 `@RequestParam(value = "topic", required = false) String topic`：给了 `topic` → 话题可访问则 `slot = ContentPin.topicSlot(id)` 走现有 `FeedService.loadPinnedSlot`（`:417`，推广卡 / 内容顶置 / 可展示判定 / 「作者被查看者隐藏 → 坑位为空」全部复用）；话题 DISABLED / 不存在 → `{}`（坑位为空，**不是 404**——与首页「无生效配置返回 {}」一致，App 不渲染）。不带 `topic` → 行为与现状逐字节一致。
3. 防用内部 id 绕过：`slot` 参数以 `TOPIC:` 开头时直接返回 `{}`（话题坑位只能经 `?topic=` 按标准名访问）。
4. **让位**：话题页**第一页**（latest 无游标 / popular `page=1`）排除该话题坑位当前生效的**内容顶置**那条帖子（推广卡无内容 id，天然不参与）；后续页照常可出现——照 `FeedService.pinnedContentIdToYield`（`:159-170`）写法抽一个 `pinnedContentIdToYield(String slot, boolean firstPage)`，**查顶置出错按无顶置继续**（不得连带列表 500）。

**AC7 — 热度任务 `topic.service.TopicHeatJob`** `[L0]` `[L1]`（D-14、FR-69.6、PRD「热度算法」口径、epics 4.2 AC7）
1. 公式（PRD 2026-11-02 口径）：`heat = 近 7 天新发帖数 × 1 + 近 7 天按天浏览人数之和 × 0.1 + 近 7 天发生的点赞数 × 1 + 近 7 天发生的评论数 × 1`；同时重算 `post_count`（该话题下全部可计入帖子数，不限 7 天）。
2. 「可计入帖子」= `PUBLIC + PUBLISHED + deleted_at IS NULL`（与 AC2 一致；作者注销后内容为 `AUTHOR_DEACTIVATED` 自然排除）。
3. 窗口：`since = now() - 7 天`（帖子 `created_at`、点赞 `created_at`、评论 `created_at`）；按天浏览 `view_date >= LocalDate.now(ScheduleWindow.WIB).minusDays(6)`（含今天共 7 个 WIB 日）。
4. 评论计数按 **CROSS-STORY 2026-08-16「平台口径 / 互动量」**：只数 `deleted_at IS NULL AND moderation_status = 'VISIBLE'`；R1（查看者隐藏）不套；**R2 影子评论必须排除**——帖子作者隐藏了评论者（`user_hide_relations.holder_id = 帖子作者 AND target_id = 评论作者`）的评论，以及父评论是影子评论的回复，一律不计（否则骚扰评论变「热度」）。AC2 的 Populer 评论数用同一口径。
5. 一条集合 SQL 更新**所有**话题（无数据的话题置 0，不能残留旧值）；**不改 `updated_at`**（那是运营编辑时间，6.1 列表会展示）。
6. 调度：`@Scheduled(cron = "${petgo.topic.heat-cron:0 20 * * * *}", zone = "Asia/Jakarta")`；`application.yml` 加 `petgo.topic.heat-cron: ${TOPIC_HEAT_CRON:0 20 * * * *}`；事务内先 `SELECT pg_try_advisory_xact_lock(hashtext('topic_heat'))`，拿不到即跳过本轮（防重入）；整体 try/catch 只 `log.warn(异常类名)`（照 `DashboardMaterializer.run` `:83-89` 范式，用 `TransactionTemplate`）。
7. 权重常量放 `topic.domain.TopicHeat`（`POST_WEIGHT=1`、`VIEW_WEIGHT=0.1`、`INTERACTION_WEIGHT=1`），SQL 由常量拼出，同时提供纯函数 `TopicHeat.score(newPosts, viewerDays, likes, comments)` 供单测——**公式只此一份**。

### 实现提示

- **控制器拆分（守 §5.3 边界）**：`topic.web.TopicController` 只调 `TopicQueryService`（详情 / 联想 / 首页行 / 推荐）；`/topics/{name}/posts` 放 `content.web.TopicPostsController`，先调 `TopicQueryService.requireVisible(name)` 拿 `topicId`，再调 `FeedService.loadTopicPosts(...)`——依赖方向恒为 content → topic，topic 模块不注入任何 content service，避免 bean 循环。
- **`findTopicFeed`（JPQL，`ContentPostRepository`）**：
  ```sql
  SELECT p FROM ContentPost p
  WHERE p.deletedAt IS NULL
    AND p.status = com.tailtopia.content.domain.PostStatus.PUBLISHED
    AND p.visibility = com.tailtopia.content.domain.ContentVisibility.PUBLIC
    AND EXISTS (SELECT 1 FROM ContentTopic ct WHERE ct.postId = p.id AND ct.topicId = :topicId)
    AND p.authorId IN (SELECT u.id FROM User u
                       WHERE u.deletedAt IS NULL AND u.status = com.tailtopia.auth.domain.UserStatus.ACTIVE)
    AND (:hasViewer = false OR NOT EXISTS (SELECT 1 FROM ContentReport r
                                           WHERE r.postId = p.id AND r.reporterId = :viewerId))
    AND (:hasViewer = false OR NOT EXISTS (SELECT 1 FROM UserHideRelation h
                                           WHERE h.holderId = :viewerId AND h.targetId = p.authorId))
    AND (:hasExclude = false OR p.id <> :excludeId)
    AND (:hasCursor = false OR p.createdAt < :cursorTs OR (p.createdAt = :cursorTs AND p.id < :cursorId))
  ORDER BY p.createdAt DESC, p.id DESC
  ```
  JPQL 引用 topic 模块实体 `ContentTopic` 与引用 `ContentReport` / `UserHideRelation` 同属既定破例（`CommentRepository` 类注释 AD-5 > AD-8）。
- **Populer 伪 SQL（原生，返回 id 列表；`:w` = comment_weight）**：
  ```sql
  SELECT p.id
  FROM content_posts p
  JOIN content_topics ct ON ct.post_id = p.id AND ct.topic_id = :topicId
  JOIN users u ON u.id = p.author_id AND u.deleted_at IS NULL AND u.status = 'ACTIVE'
  LEFT JOIN LATERAL (SELECT COUNT(*) AS n FROM content_likes l WHERE l.post_id = p.id) lk ON true
  LEFT JOIN LATERAL (
      SELECT COUNT(*) AS n FROM comments c
      WHERE c.post_id = p.id AND c.deleted_at IS NULL AND c.moderation_status = 'VISIBLE'
        AND NOT EXISTS (SELECT 1 FROM user_hide_relations h                       -- R2：作者隐藏了评论者
                        WHERE h.holder_id = p.author_id AND h.target_id = c.author_id)
        AND (c.parent_id IS NULL OR NOT EXISTS (                                  -- R2：父评论是影子评论
                SELECT 1 FROM comments pc JOIN user_hide_relations h2
                  ON h2.holder_id = p.author_id AND h2.target_id = pc.author_id
                WHERE pc.id = c.parent_id))
  ) cm ON true
  WHERE p.deleted_at IS NULL AND p.status = 'PUBLISHED' AND p.visibility = 'PUBLIC'
    AND (:hasViewer = false OR NOT EXISTS (SELECT 1 FROM content_reports r
                                           WHERE r.post_id = p.id AND r.reporter_id = :viewerId))
    AND (:hasViewer = false OR NOT EXISTS (SELECT 1 FROM user_hide_relations h3
                                           WHERE h3.holder_id = :viewerId AND h3.target_id = p.author_id))
    AND (:hasExclude = false OR p.id <> :excludeId)
  ORDER BY (lk.n + :w * cm.n) DESC, p.created_at DESC, p.id DESC
  LIMIT 21 OFFSET :offset
  ```
  取回 id 后 `posts.findAllById(ids)` 再**按 id 列表顺序重排**（`findAllById` 不保序），截前 20 进 `assemble`。原生查询里 `:viewerId` 为 null 时要显式 `CAST(:viewerId AS BIGINT)` 或用布尔门控 + 传 `-1`，避免 42P18。
- **热度伪 SQL（一条集合 UPDATE；`:since` = now − 7 天，`:fromDate` = WIB 今天 − 6）**：
  ```sql
  WITH vis AS (                       -- 可计入帖子（与 AC2 同口径）
      SELECT ct.topic_id, p.id AS post_id, p.author_id, p.created_at
      FROM content_topics ct JOIN content_posts p ON p.id = ct.post_id
      WHERE p.deleted_at IS NULL AND p.status = 'PUBLISHED' AND p.visibility = 'PUBLIC'
  ),
  agg_posts AS (
      SELECT topic_id, COUNT(*) AS post_count,
             COUNT(*) FILTER (WHERE created_at >= :since) AS new_posts
      FROM vis GROUP BY topic_id
  ),
  agg_views AS (                      -- 各帖近 7 个 WIB 日每天浏览人数之和
      SELECT v.topic_id, COUNT(*) AS viewer_days
      FROM vis v JOIN content_post_view_days d ON d.post_id = v.post_id AND d.view_date >= :fromDate
      GROUP BY v.topic_id
  ),
  agg_likes AS (
      SELECT v.topic_id, COUNT(*) AS likes
      FROM vis v JOIN content_likes l ON l.post_id = v.post_id AND l.created_at >= :since
      GROUP BY v.topic_id
  ),
  agg_comments AS (                   -- 平台口径：VISIBLE + 未删 + 排除 R2 影子及其回复
      SELECT v.topic_id, COUNT(*) AS comments
      FROM vis v JOIN comments c ON c.post_id = v.post_id AND c.created_at >= :since
       AND c.deleted_at IS NULL AND c.moderation_status = 'VISIBLE'
      WHERE NOT EXISTS (SELECT 1 FROM user_hide_relations h
                        WHERE h.holder_id = v.author_id AND h.target_id = c.author_id)
        AND (c.parent_id IS NULL OR NOT EXISTS (
                SELECT 1 FROM comments pc JOIN user_hide_relations h2
                  ON h2.holder_id = v.author_id AND h2.target_id = pc.author_id
                WHERE pc.id = c.parent_id))
      GROUP BY v.topic_id
  )
  UPDATE topics t SET
      post_count = COALESCE(ap.post_count, 0),
      heat_score = COALESCE(ap.new_posts, 0) * 1
                 + COALESCE(av.viewer_days, 0) * 0.1
                 + COALESCE(al.likes, 0) * 1
                 + COALESCE(ac.comments, 0) * 1
  FROM topics t2
  LEFT JOIN agg_posts ap    ON ap.topic_id = t2.id
  LEFT JOIN agg_views av    ON av.topic_id = t2.id
  LEFT JOIN agg_likes al    ON al.topic_id = t2.id
  LEFT JOIN agg_comments ac ON ac.topic_id = t2.id
  WHERE t.id = t2.id
  ```
  （`* 1` / `* 0.1` 由 `TopicHeat` 常量拼入；`heat_score NUMERIC(12,1)` 自动四舍五入到 1 位。）现规模可接受；若 L1 `EXPLAIN` 显示 `vis` 全扫过慢，可先把 `vis` 限定为「近 7 天有任一事件的帖子」再算热度、`post_count` 单独一句——**口径不变**。
- **DTO 位置**：`topic/web/dto/{TopicDetailResponse, TopicSummaryResponse}`，Jackson NON_NULL（`featured` 用 `Boolean`，只有首页行给值）。
- **联想 `q` 校验**直接用 `TopicNameRules.isValidName` 的字符集判断（长度下限 1 即可查——用户打 1 个字也要出联想），**不在 controller 里另写正则**（P-1）。

## 待确认 / 发现的规划冲突（不改规划文档）

1. **联想路径与话题详情撞路由**：架构 D-13 定 `GET /api/v1/topics/suggest` 与 `GET /api/v1/topics/{name}`。`suggest` 本身是合法话题名（字母 2–30），用户一旦写了 `#suggest`，Spring 会把它的详情请求匹配到联想端点（字面路径优先），该话题页永远打不开（游客还会 401）。本 story 改为 **`GET /api/v1/topic-suggestions?q=`**（4.4 同步按此调用）。若主会话坚持原路径，按 AC9 末条调整安全配置顺序，并接受 `#suggest` 话题页不可达。`home-row` 含连字符、不可能是话题名，不受影响。
2. **推荐话题是否要求热度 > 0**：架构 D-13 只写「近 7 天热度倒序」。本 story 按首页话题行同一口径加 `heat_score > 0`（否则会推荐一堆 0 热度、点进去又是空态的话题）。若要不加，删掉那个条件即可。
3. **PRD 坑位写法 `SLOT_TOPIC:{topicId}`** 与代码现状不符（代码常量名 `SLOT_HOME_FEED`、实际值 `HOME_FEED`），按架构 §1.2 第 2 条以代码为准，值写 `TOPIC:{topicId}`。
4. **既有 `pinned?slot=` 可传任意字符串**：本 story 拦掉 `TOPIC:` 前缀（防按内部 id 枚举话题坑位），首页行为不变。若有内部工具依赖 `slot=TOPIC:…` 直取，需另说。
5. **Populer 页码上限 50**（1000 条）为本 story 自定的防滥用阈值，PRD / 架构未写。
6. **`FeedRankInteractionStats` 现有评论口径未排 R2 影子评论**（与 CROSS-STORY 2026-08-16 不一致的存量现象），本 story 的热度 / Populer 按 CROSS-STORY 排除，不顺手改推荐序（越界）；建议另起 bug 跟踪。
