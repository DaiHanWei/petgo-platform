## Story

As a 运营,
I want 所有要处置的订单进一个队列、取消时明确原因,
So that 钱退得对.

## Acceptance Criteria

1. 队列 **Then** 收缺货、运单失败、揽收失败、退回、丢件破损（含已签收 / 已完成且无赔付单），标来源，优先级按 AD-9（D1）；空态 D2〔L0 / L1〕
2. 取消后的订单出队，运单失败标记随取消清除；「联系用户后继续」只对缺货来源显示〔L1〕
3. `confirmReturned` 落库 `return_cause`，判定后不可改；重发要求快递原因〔L1〕
4. 类别映射与绑定由服务端校验，不符 409，运营不能单独开关补偿与退券；退回待判定不能取消（表驱动单测）〔L0〕
5. 整单取消先选类别，显示试算明细；试算与落库同一计算（D3~D5）〔L0 / L1〕
6. 平台原因全额、给补偿、退券；用户原因扣用户实付运费与保价、不补偿、不退券；丢件破损按保价或协商额，协商额 ≤ 商品实付〔L0〕
7. 此前部分取消已退的，各类退款都减去已退额〔L0〕
8. 用户原因须 `return_inbound_at` 非空，否则按钮置灰、服务端 409（D4）；取消时直接出退款单、不回补库存〔L1〕
9. 已签收 / 已完成的丢件破损走 `compensate`，订单状态不变〔L1〕
10. 揽收失败取消走 `resolvePickupFailureByCancel`，旧运单取消失败则中止、不回补库存〔L1〕
11. 部分取消显示拆分明细（D6）；最后一行转整单，类别只能平台原因（D7）；有活动运单时拒绝〔L0 / L1〕
12. 处置成功 toast 含现金段去向，队列刷新（D8）〔L1〕
13. 审计记类别、退款合计、币现拆分、退券、库存回补（门店返佣按 O-23 不记）〔L1〕

### 代码核对（2026-11-06，基线 `fd94b3ffa`，电商线 PR#49 已合入）

- 🔴 **PR#49 踩过的坑**：`movements.receiveReturn` → `SkuInventoryRepository.restock` 是 `@Modifying(clearAutomatically = true)`，会清一级缓存。`confirmReturnedInbound` 循环回补后必须重读订单与订单行，照 `ShopOrderRefundService.reloadOrder`，否则乐观锁异常。
- 🔴 `ShopLogisticsExceptionService`、`BiteshipShipmentService` 自带 `REQUIRES_NEW` 短事务，调用方不得开外层事务；而 `AdminShopOrderExceptionService` 现有方法都带 `@Transactional`。揽收失败取消要在事务外分流，不能从这些方法里调 `resolvePickupFailureByCancel`。
- `AdminShopOrderExceptionService` 现状：`requireHandleable` 只收 `PENDING_SHIPMENT`；`cancelWholeOrder`、`cancelLine` 写死 `OUT_OF_STOCK`；`exceptionCandidates / flagged / isCandidate` 只认缺货，`isCandidate` 注释写明是列表「异常」标、工作台左栏、处置后去留的唯一判据，AD-9 队列要从这里改。
- `ShopOrderRefundService.cancelWhole` 现在用户原因不算 quote、返回空退款单，本 story 改掉；`Outcome.refund` 的空值注释一并更新。`requireWholeAllowed` 的状态集合保持不变。
- `findLogisticsExceptionOpen` 不滤订单状态（G15）。`confirmReturned`、`markLostOrDamaged` 等入参是内部 `long orderId`，Controller 先按 token 查。
- `ReturnCause` 在 `com.tailtopia.shop.logistics`，值 `COURIER_FAULT / USER_FAULT`，`return_cause` 列直接存它。已有测试类 `ShopRefundCalculatorTest` 在 `shop/order/pricing/`。
