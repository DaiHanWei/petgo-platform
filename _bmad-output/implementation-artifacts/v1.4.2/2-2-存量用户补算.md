## Story

As a 上线前就关注过人、收藏过帖子的老用户,
I want 升级后这两个里程碑直接是已完成,
so that 不用重做一遍也拿到成长值。

## Acceptance Criteria

**AC1 — 有宠物的老账号** `[L1]`（FR-154.4、PRD AC6）
Given 上线前有 `user_follows.source = 'USER'` 关注记录、或有 `content_collections` 帖子收藏记录的账号，When 迁移 ⑥ 执行，Then：
1. 写 `user_milestone_flags`（`FIRST_FOLLOW_USER` / `FIRST_COLLECT_CONTENT` 各按是否有记录），`occurred_at` = 该账号最早一条记录的 `created_at`；
2. 其 **ACTIVE** 宠物按物种写对应编码完成行（C/D-S19、S20，G-S12、S13），`source = 'SYSTEM_AUTO'`、`celebrated_at = completed_at`（= 已庆祝）；READ_ONLY 宠物不写（之后恢复时由 2.1 的 reconcile 钩子补「已完成且已庆祝」）；
3. **不发通知**（迁移直接写表，不经任何 Java 服务 / 事件）；之后进里程碑列表**不补弹**（`celebrated_at` 非空）。

**AC2 — 上线时没有宠物的账号** `[L1]`（PRD AC9、§3.2「补算时还没有宠物的账号」）
Given 上线时 0 只宠物但有关注 / 收藏记录的账号，Then 同样写 flag、成长值照发；之后取关 / 取消收藏再建宠，新宠物这两项直接已完成（由 2.1 `assignRoster` 钩子实现），无庆祝、无成长值。

**AC3 — 成长值流水与总额 / 等级同步** `[L1]`（D-4、P-7）
1. 每「账号 × flag」写一条 `growth_ledger`：`rule_code = 'LAUNCH_BACKFILL'`、`delta = 5`、`idem_key = 'BACKFILL142:' || user_id || ':' || flag_key`（P-7 定死，`ON CONFLICT (idem_key) DO NOTHING`）、`ref_type = 'MILESTONE'`、`ref_id = flag_key`、`wib_date = (now() AT TIME ZONE 'Asia/Jakarta')::date`。
2. 只给「参与成长值」的账号发：口径与 `V20261018_1503` 的 `eligible` CTE 逐字一致（`role='USER' AND account_type='REAL' AND deleted_at IS NULL AND status='ACTIVE'` 且无非 PENDING 的 `account_deletions`）。
3. `growth_accounts`：只对本次 `RETURNING` 真正插入了流水的用户累加 `lifetime_total`、按 `growth_levels` 重算 `level`、`version + 1`、`updated_at = now()`；没有账户行的插一行（`balance = 0`、`backfill_popup_pending = false`）。
4. **不弹升级、不弹存量汇总**：不写 `celebrate_from_level / celebrate_to_level`，不改 `backfill_popup_pending` 与 `backfill_*` 三个快照列（那是 1.4.0 上线汇总弹窗用的，不能被本次覆盖）；不发 `GrowthLevelChangedEvent`、不发通知。

**AC4 — 幂等与验证** `[L1]`
1. 迁移重放（L1 用 `ScriptUtils` 在自动提交下再执行一次）：flag、完成行、流水、账户总额都不重复、不翻倍。
2. scratch 库造数验证：①有宠物 + 关注过 ②有宠物 + 只收藏过 ③两者都有（流水 2 条 +10）④无宠物 + 关注过 ⑤只有 SYSTEM 关注（官方号）→ **无** flag ⑥只收藏过场所（`place_collections`）→ **无** flag ⑦混养 + 1 只 READ_ONLY ⑧VIRTUAL / 已注销 / DEACTIVATED → 有 flag（DEACTIVATED）或无（已注销），但都**无**流水 ⑨roster 缺失的老宠物 → 不写完成行、不报错。
3. Completion Notes 记录：本地 scratch 造数结果；**stag 补算账号数**（flag 行数按 flag_key 分组、完成行数、流水行数）——stag 上的数在本地验收部署 stag 后用只读查询取，云端不执行。

## Dev Notes

### 现状（核 `dev_1.4.2` @ c496e3c3）

- 关注表 `user_follows(follower_id, followee_id, created_at, source VARCHAR(16) DEFAULT 'USER' CHECK IN ('USER','SYSTEM'))`（`V20261014_1600`）；`source` 列加之前的存量关注默认都是 USER（含当时用户手动关注官方号——属用户行为，算）。
- 帖子收藏表 `content_collections(id, user_id, post_id, created_at)`，场所收藏是另一张 `place_collections`（`V20261018_1801`）——**只读前者**。
- 宠物 `pet_profiles.status VARCHAR(16)`（`ACTIVE` / `READ_ONLY`），`owner_id`、`pet_type`（`CAT` / `DOG` / `OTHER`）、`created_at`。
- 完成表 `milestone_completions(pet_milestone_id UNIQUE, source, linked_content_id, completed_at, celebrated_at)`；roster `pet_milestones(pet_profile_id, code, …)`，⑤ 已给「有 roster 的宠物」补了新编码行。
- 成长值：`growth_ledger(user_id, rule_code, delta CHECK <> 0, ref_type, ref_id, pet_ids, idem_key UNIQUE, …, wib_date, created_at)`；`growth_accounts(user_id PK, lifetime_total, balance, level, display_level, celebrate_from_level, celebrate_to_level, backfill_popup_pending, backfill_*, version, created_at, updated_at)`；`growth_levels(level, threshold)`；规则行 `LAUNCH_BACKFILL` 已存在（`V20261018_1500`:102，points 0，补算写死分值不读规则表）。
- 运行时等价路径（2.1）：flag 冲突 no-op；补算写的 flag 会让之后的真实关注 / 收藏**不再触发**——这正是期望（老用户不再收通知、不再拿第二次分）。

### SQL 骨架（照此写，按需微调列名；不要用后缀切分）

```sql
-- ① flag
INSERT INTO user_milestone_flags (user_id, flag_key, occurred_at)
SELECT f.follower_id, 'FIRST_FOLLOW_USER', MIN(f.created_at)
FROM user_follows f
JOIN users u ON u.id = f.follower_id AND u.deleted_at IS NULL
WHERE f.source = 'USER'
GROUP BY f.follower_id
ON CONFLICT (user_id, flag_key) DO NOTHING;

INSERT INTO user_milestone_flags (user_id, flag_key, occurred_at)
SELECT c.user_id, 'FIRST_COLLECT_CONTENT', MIN(c.created_at)
FROM content_collections c
JOIN users u ON u.id = c.user_id AND u.deleted_at IS NULL
GROUP BY c.user_id
ON CONFLICT (user_id, flag_key) DO NOTHING;

-- ② ACTIVE 宠物完成且已庆祝（显式码表，不拼后缀）
INSERT INTO milestone_completions (pet_milestone_id, source, completed_at, celebrated_at)
SELECT pm.id, 'SYSTEM_AUTO', GREATEST(fl.occurred_at, p.created_at), GREATEST(fl.occurred_at, p.created_at)
FROM user_milestone_flags fl
JOIN pet_profiles p ON p.owner_id = fl.user_id AND p.status = 'ACTIVE'
JOIN (VALUES ('FIRST_FOLLOW_USER','CAT','C-S19'), ('FIRST_FOLLOW_USER','DOG','D-S19'), ('FIRST_FOLLOW_USER','OTHER','G-S12'),
             ('FIRST_COLLECT_CONTENT','CAT','C-S20'), ('FIRST_COLLECT_CONTENT','DOG','D-S20'), ('FIRST_COLLECT_CONTENT','OTHER','G-S13'))
     AS v(flag_key, pet_type, code) ON v.flag_key = fl.flag_key AND v.pet_type = p.pet_type
JOIN pet_milestones pm ON pm.pet_profile_id = p.id AND pm.code = v.code
WHERE NOT EXISTS (SELECT 1 FROM milestone_completions mc WHERE mc.pet_milestone_id = pm.id);

-- ③ 成长值（一条 CTE；eligible 与 V20261018_1503 逐字一致）
WITH eligible AS (...), ins AS (
    INSERT INTO growth_ledger (user_id, rule_code, delta, ref_type, ref_id, idem_key, wib_date, created_at)
    SELECT fl.user_id, 'LAUNCH_BACKFILL', 5, 'MILESTONE', fl.flag_key,
           'BACKFILL142:' || fl.user_id || ':' || fl.flag_key, (now() AT TIME ZONE 'Asia/Jakarta')::date, now()
    FROM user_milestone_flags fl JOIN eligible e ON e.user_id = fl.user_id
    ON CONFLICT (idem_key) DO NOTHING
    RETURNING user_id, delta
), per_user AS (SELECT user_id, SUM(delta)::int AS add FROM ins GROUP BY user_id)
INSERT INTO growth_accounts (user_id, lifetime_total, balance, level, backfill_popup_pending, version, created_at, updated_at)
SELECT pu.user_id, pu.add, 0, (SELECT COALESCE(MAX(l.level), 1) FROM growth_levels l WHERE l.threshold <= pu.add),
       false, 0, now(), now()
FROM per_user pu
ON CONFLICT (user_id) DO UPDATE SET
    lifetime_total = growth_accounts.lifetime_total + EXCLUDED.lifetime_total,
    level = (SELECT COALESCE(MAX(l.level), 1) FROM growth_levels l
             WHERE l.threshold <= growth_accounts.lifetime_total + EXCLUDED.lifetime_total),
    version = growth_accounts.version + 1,
    updated_at = now();
```

- ⚠️ 段 ③ 的 `ins` 只覆盖 flag 表里**所有**行（含运行时 2.1 写的）：迁移在应用启动前跑，此时不会有运行时 flag；L1 重放时 `ON CONFLICT (idem_key)` 保证不重复。若担心与运行时 `MILESTONE_ACCT:` 键重复入账（理论上不会同时存在），可加 `AND NOT EXISTS (SELECT 1 FROM growth_ledger g WHERE g.idem_key = 'MILESTONE_ACCT:' || fl.user_id || ':' || fl.flag_key)`——**推荐加上**，零成本防双发。
- ⚠️ 不要照抄 `V20261018_1503` 的 `backfill_popup_pending = true` 与 `backfill_*` 赋值——那会让 1.4.0 的存量汇总弹窗再弹一次，且覆盖原快照。
- `growth_ledger.delta CHECK (delta <> 0)`：恒为 5，OK。
- 等级跨档：SQL 改等级不发 `GrowthLevelChangedEvent`，等级对应的宠物名额由 `GrowthQueryService` 实时读落库等级（同 `V20261018_1503` 头注释）；跨档后只读宠物不会立刻自动恢复，等下次 reconcile 触发——与 1.4.0 补算同口径，可接受（+5 / +10 跨档概率极低）。

## 待确认 / 发现的规划冲突

1. **`completed_at` 取值**未在规划写死：本 story 取 `GREATEST(最早一次关注/收藏时间, 宠物建档时间)`（时间线上不会出现「宠物还没建档就完成」），`celebrated_at` 同值（同 `V20261012_1105`）。若产品要统一用上线时刻，改成 `now()` 即可。
2. **DEACTIVATED 账号**：flag 照写（是事实），成长值按 `eligible` 口径不发；解封后再关注不会再触发、也拿不到这 +5。与 1.4.0 补算对 DEACTIVATED 的处理一致，提示产品知悉。
3. **stag 补算账号数**需要部署 stag 后才能取，云端无法完成，留本地验收（部署仍需操作者明确指令）。
4. **注销受理中的账号**（复审 2-2 已处置）：段 ① 两条 flag INSERT 均加 `AND NOT EXISTS (SELECT 1 FROM account_deletions ad WHERE ad.user_id = u.id)`，account_deletions 有任何状态的行（PENDING / PROCESSING / DONE / FAILED）即不写 flag → 也不写完成行、不发分，与运行时 `AccountMilestoneService.onFlagTriggered` 的 `deletions.findByUserId(..).isPresent()` 逐字对齐。段 ③ eligible 维持与 V20261018_1503 逐字一致不动（flag 已排除，实际不会给这类账号发分）。代码里不存在撤销注销的路径，故不存在「撤销后保留 flag」的情形。
