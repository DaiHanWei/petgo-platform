### AC5 — `CouponExpiryReminderJob` `[L0]` `[L1]`（D-22、I8、FR-130.10）
1. 位置 `B/shop/coupon/service/CouponExpiryReminderJob`（任务）+ `CouponExpiryReminderService`（单用户处理，便于测试直调）。
2. 调度：`@Scheduled(cron = "${petgo.shop.coupon.expiry-reminder-cron:0 0 10 * * *}", zone = "Asia/Jakarta")`（每天 WIB 10:00）；`application.yml` 在 `petgo.shop` 下加 `coupon.expiry-reminder-cron: ${SHOP_COUPON_EXPIRY_REMINDER_CRON:0 0 10 * * *}`；**`T/support/ApiIntegrationTest.java` 的属性列表（:66-89）追加 `"petgo.shop.coupon.expiry-reminder-cron=-"`**（`-` = 关闭，测试直调 `run(now)`；否则套件跨 10:00 时会给共享库用户发通知，让「未读数 = N」类断言随机红——同 `pet-slot.expiry-scan-cron=-` 的理由）。
3. 防重入：外层 `TransactionTemplate` 执行 `SELECT pg_try_advisory_xact_lock(hashtext('coupon_expiry_reminder'))`，拿不到即跳过本轮（照 `B/topic/service/TopicHeatJob.java:47 / :152`）；外层事务持锁期间，逐用户处理用 **`REQUIRES_NEW`** 独立事务（另一连接），一人失败不影响他人。幂等另有两道保险：日志表主键 + 券的条件置位。
4. 候选：`now` = 本轮开始时刻，`until = now + 48h`；分批取用户 `SELECT DISTINCT user_id FROM user_coupons WHERE status='AVAILABLE' AND expiry_notified_at IS NULL AND valid_until > :now AND valid_until <= :until ORDER BY user_id LIMIT 500`（走 2.1 的部分索引 `idx_user_coupons_expiry_scan`），循环直到取空或本轮处理满 20,000 人（剩余下一天再扫，WARN 一行）。
5. 单用户处理（`CouponExpiryReminderService.remindUser(userId, now, until)`，`REQUIRES_NEW`）：
   1. `INSERT INTO coupon_expiry_notify_log (user_id, wib_date, coupon_count) VALUES (:uid, :wibToday, 1) ON CONFLICT DO NOTHING`——影响 0 行 = 今天已提醒过 → 直接返回（**同一用户同一 WIB 日只 1 条**）；`wibToday = now` 的 `ScheduleWindow.WIB` 日期；
   2. `CouponLedgerService.markExpiryNotified(userId, now, until)`（**本 story 在 2.1 的账本类里新增**，P-2：`user_coupons` 的写只在账本里）：`UPDATE user_coupons SET expiry_notified_at = :now, updated_at = :now WHERE user_id = :uid AND status = 'AVAILABLE' AND expiry_notified_at IS NULL AND valid_until > :now AND valid_until <= :until RETURNING valid_until` → 返回本次置位的到期时刻列表（**每张券只被提醒一次**，I8：连续两天都落在 48 小时窗口的券第二天不会再被数进去）；
   3. 置位 0 张 → 回滚本事务（`setRollbackOnly`，日志行一并撤销）并返回；
   4. 把日志行的 `coupon_count` 更新为置位张数；提交。
   5. **提交之后**（事务外）发通知：`notificationService.sendWithCopy(userId, NotificationType.COUPON_EXPIRING, "COUPON_EXPIRING", args, title, body, String.valueOf(n))`，其中 `title / body` 按收件人 locale 先渲染好（落库给通知中心显示，旧版 App 读后端 title / body），推送由 `sendWithCopy` 同键同参渲染（`B/notify/service/NotificationService.java:615`）。`deepLinkType` 由 `sendWithCopy` 写成类型名 `COUPON_EXPIRING`，App 9.3 映射到 `/me/coupons`。
   6. `targetRef` = 张数字符串（App 推送点开埋点 `toko_coupon_expiry_push_opened{coupon_count}` 从推送载荷 / 通知列表的 `targetRef` 取；`NotificationItem` 不下发 `variant`，所以不用 `variant` 承载，见「待确认」①）。
6. **关闭 PROMO 不推送**：由 `sendWithCopy` 内部的 `pushAllowed`（`PushPreferenceService.isEnabled(userId, type)`）自然实现——通知中心照常写入、不推送（D-22「走现有推送偏好」）。虚拟号由 `sendWithCopy` 跳过推送。
7. **埋点** `toko_coupon_expiry_push_sent{coupon_count}`（服务端，PRD §4）：只在**确实推送**时上报——发送前判 `prefs.isEnabled(userId, COUPON_EXPIRING) && !accounts.isVirtual(userId)`，为真才在 `sendWithCopy` 成功返回后 `analytics.capture(AnalyticsDistinctId.of(userId), "toko_coupon_expiry_push_sent", Map.of("coupon_count", n))`。事件名写字面量（P-9）。**必须**在 `B/shared/analytics/AnalyticsEventGuard.java` 的 `ALLOWED_EVENTS`（:46-）登记事件名、在 `ALLOWED_PROPERTY_KEYS`（:81-）登记 `coupon_count`（漏登记 = 静默丢弃）。
8. 失败处理：发送或埋点异常只 WARN（userId + 异常类名），**不重推**（at-most-once，同「604 推送限频」拍板：重复比漏发更糟）；推送全局限速由 `LiveTencentImClient` 的 `PushRateLimiter` 统一处理，本任务不另限速。
9. 跳过非有效账号：`accounts.isActiveAccount(userId)` 为 false（注销 / 封号）→ 仍执行 5.2 置位（避免每天重复扫到它）但不发通知、不埋点。注销用户的可用券已在 2.1 作废，正常不会出现。
10. 收尾：同一轮最后删除 `wib_date < 今天 − 30 天` 的日志行（单条 DELETE）。
11. 日志：INFO 一行汇总（候选人数、发送数、跳过数）；**不记券 token、券名、用户手机号**。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 张数放 `targetRef`，不放 `variant`**：架构 D-22 写「`variant` = 张数」，但 `sendWithCopy` 不写 `variant`、`NotificationItem` 也不下发 `variant`；`targetRef` 既进通知列表又进推送载荷，App 9.3 两条路径都能拿到张数。
- **② 「提醒过」双保险**：`coupon_expiry_notify_log`（同人同日一条）+ `expiry_notified_at`（同券一次）；置位 0 张时连日志行一起回滚，不留空记录。
- **③ 发送在提交之后、事务之外**：通知是外部可见副作用，状态先落定再发；失败不重推。
- **④ 埋点只在真推送时报**（关了 PROMO 或虚拟号不报），否则「推送发送量」虚高。

### 实现提示

- 单用户处理骨架：
  ```java
  public Outcome remindUser(long userId, Instant now, Instant until) {
      List<Instant> marked = newTx.execute(status -> {
          if (logDao.insertIfAbsent(userId, wibDate(now)) == 0) return List.of();      // 今天已提醒
          List<Instant> m = ledger.markExpiryNotified(userId, now, until);
          if (m.isEmpty()) { status.setRollbackOnly(); return List.of(); }
          logDao.updateCount(userId, wibDate(now), m.size());
          return m;
      });
      if (marked.isEmpty()) return Outcome.SKIPPED;
      if (!accounts.isActiveAccount(userId)) return Outcome.MARKED_ONLY;
      int n = marked.size();
      Instant earliest = Collections.min(marked);
      boolean willPush = safePushAllowed(userId) && !accounts.isVirtual(userId);
      try {
          Locale locale = accounts.localeOf(userId);
          Object[] args = copy.args(n, earliest, locale);                          // {"3", "6 Nov, 23:59"}
          notifications.sendWithCopy(userId, NotificationType.COUPON_EXPIRING, "COUPON_EXPIRING", args,
                  copy.render("title", args, locale), copy.render("body", args, locale), String.valueOf(n));
          if (willPush) analytics.capture(AnalyticsDistinctId.of(userId), "toko_coupon_expiry_push_sent",
                  Map.of("coupon_count", n));
          return Outcome.SENT;
      } catch (RuntimeException e) {
          log.warn("券快过期提醒发送失败（不重发）userId={} cause={}", userId, e.getClass().getSimpleName());
          return Outcome.FAILED;
      }
  }
  ```
- `markExpiryNotified` 用 native `UPDATE … RETURNING valid_until`（写在 2.1 的 `UserCouponLedgerDao`，被 `CouponLedgerService` 调；2.1 的单入口守卫会检查）。
- 窗口边界 `(now, now + 48h]`：`valid_until > now AND valid_until <= until`（恰好 48 小时后到期的券本轮提醒；已到期的不提醒）。
- 迁移复制时连同原文件的分组注释一起复制（注释不含引号大写值，原文件已保证），最后一组加电商两值。
