# Story 6.2: 运营通知发送核心（人群、分批推送、重试、定时）

Status: review

## Story

As a 运营,
I want 发送后系统自动筛掉无效账号、分批推送并在失败时重试，定时的到点自动发,
so that 大批量发送不会因限流整批失败，发送结果可信。

> 范围（D-2 / AD-1）：本 story 交付**服务方法**（新建 / 取消 / 发送 / 定时扫描），供 admin 主题（AB-31）的新建 / 取消接口调用。**不做**任何后台页面、Controller、写接口。依赖 Story 6.1（表、实体、`AudienceSpec`、`NotificationService.writeOpsAnnouncements`）。

## 运行参数（决策日志 D-20，写死，不得自定）

| 参数 | 值 |
|---|---|
| 每批人数 | **500** |
| 批与批之间间隔 | **1 秒**（最后一批之后不等） |
| 单批推送失败重试 | **3 次**，退避 **1s / 2s / 4s** |
| 定时扫描周期 | **每 60 秒**（`fixedDelay`） |
| SENDING 无进展判定 | `last_progress_at` 超过 **15 分钟**未刷新 → 置 `PARTIAL_FAILED`，**不自动重发** |
| 进展刷新频率 | 每批写库后、每推送 **50** 人后、每批结束后各刷新一次 `last_progress_at` |
| 推送方式（D-19） | **逐人调用既有单人推送**（`/v4/timpush/batch` 单收件人，即现有 `pushOffline` 的请求形态），**不**新接批量多收件人推送 |

以上值放 `OpsNotifyParams`（record，`static final OpsNotifyParams DEFAULTS`）；扫描周期走 `@Scheduled(fixedDelayString = "${petgo.ops-notify.scan-ms:60000}")`、`initialDelayString = "${petgo.ops-notify.scan-initial-delay-ms:60000}"`。

## Acceptance Criteria

**AC1 — 人群解析（基础过滤 + D-16 条件）** `[L0]` `[L1]`
在 **auth 模块**新建只读查询 `com.tailtopia.auth.service.OpsAudienceQuery`（notify 模块不直访 users 表，沿用 `AccountQueryService` 作读口的约定），方法 `List<OpsRecipient> resolve(AudienceSpec spec, long campaignId)`，返回 `(userId, locale)`，**按 `users.id` 升序**。SQL 用 `NamedParameterJdbcTemplate`，只读事务。
1. **基础过滤（任何模式都加，与 `UserRepository.findLifecyclePushCandidates` 逐字同口径）**：`u.role = 'USER' AND u.account_type = 'REAL' AND u.deleted_at IS NULL AND u.enabled = TRUE AND u.status = 'ACTIVE'`——封号、注销、停用、虚拟号、兽医 / 管理员一律排除（FR-138.5，PRD AC5）。
2. **mode = ALL**：只有基础过滤。
3. **mode = FILTER**（各条件之间为「且」；键缺失 = 该条不筛；日期按 WIB 自然日含两端：`from` → `>= from 当天 00:00 WIB`，`to` → `< (to + 1 天) 00:00 WIB`，在 Java 侧换算成 `Instant` 绑参）：
   | 键 | SQL 条件 |
   |---|---|
   | `registeredFrom` / `registeredTo` | `u.created_at >= :regFrom` / `u.created_at < :regToExcl` |
   | `activeFrom` / `activeTo` | `u.last_active_at >= :actFrom` / `u.last_active_at < :actToExcl`（`last_active_at` 为 NULL 的用户在给了任一活跃键时**不命中**；列来自 `V20260821_1646`） |
   | `hasPet: true` / `false` | `EXISTS (SELECT 1 FROM pet_profiles p WHERE p.owner_id = u.id)` / `NOT EXISTS (...)` |
   | `species: [...]` | `EXISTS (SELECT 1 FROM pet_profiles p WHERE p.owner_id = u.id AND p.pet_type IN (:species))` |
   | `hasShopOrder: true` / `false` | `EXISTS (SELECT 1 FROM shop_orders o WHERE o.user_id = u.id AND o.status IN ('PENDING_SHIPMENT','SHIPPED','DELIVERED','COMPLETED','REFUNDING','REFUNDED'))` / `NOT EXISTS (...)`——「下过电商订单」= **有过已支付的商城订单**（D-16）；`PENDING_PAYMENT`（未付）与 `CANCELLED` 不算 |

5. SQL 片段由纯函数 `OpsAudienceSql.build(AudienceSpec spec, long campaignId, ZoneId wib) → (String sql, Map<String,Object> params)` 生成（L0 可测），`OpsAudienceQuery` 只负责执行。
6. 🔒 不得 log 任何收件人 id 列表、手机号、语言；只允许 log 活动 id 与人数。

**AC3 — 发送（状态机 + 分批写通知中心 + 逐人推送 + 重试）** `[L0]` `[L1]`
新建 `com.tailtopia.notify.ops.service.OpsNotificationDispatcher`，核心方法 `void dispatch(long campaignId)`（本身不加事务；每一步各自短事务）：
1. **抢占**：`int claimed = repo.claimForSending(id, now)` ——
   `UPDATE OpsNotificationCampaign c SET c.status = SENDING, c.startedAt = :now, c.lastProgressAt = :now, c.updatedAt = :now WHERE c.id = :id AND c.status = PENDING AND (c.scheduledAt IS NULL OR c.scheduledAt <= :now)`；`claimed == 0` → 直接返回（已被别的线程 / 实例抢走、已取消、或未到点）。多实例与重复投递都靠这一条防重（epics 6.2「只有一个实例执行」）。
2. **解析人群**（按**实际发送时刻**，定时活动也一样）：`OpsAudienceQuery.resolve(spec, id)`；IDS 模式写 `skipped_count`。人群为空 → 直接 `finish(DONE)`。
3. **按 500 人一批**循环（`recipients` 按 id 升序切片）：
   a. **写通知中心**：`notificationService.writeOpsAnnouncements(campaign, batch)`（6.1 AC5，REQUIRES_NEW，整批一个事务）。抛异常 → 整批回滚，按 1s / 2s / 4s 退避重试 3 次；仍失败 → 该批人数计入 `failed_count`、**跳过该批推送**、继续下一批。
   b. 写成功 → `repo.addRecipients(id, written.size(), now)`（`recipient_count += n`，刷 `last_progress_at`）。
   c. **逐人推送**：对每条已写入的通知调用 `NotificationPusher.pushToUserNow(userId, n.getTitle(), n.getBody(), "OPS_ANNOUNCEMENT", n.getDeepLinkToken(), campaign.getPublicToken())`（**同步**，返回 `boolean`，见 AC4）；推送文案直接用该行 title / body（与通知中心同一语言，PRD AC2）。每推完 50 人刷一次进展（`repo.touchProgress(id, now)`）。
   d. **重试只针对本批推送失败的人**（不对已成功的人重推，防重复打扰）：最多 3 轮，第 k 轮前等待 1s / 2s / 4s；3 轮后仍失败的人数计入 `failed_count`（`repo.addFailed(id, n, now)`）。
   e. 每一次 `addRecipients` / `touchProgress` / `addFailed` 都是 `... WHERE id = :id AND status = SENDING` 的条件更新；**返回 0 行 = 活动已被超时扫描置为 `PARTIAL_FAILED`，立即停止后续所有批次**（不再写、不再推）。
   f. 非最后一批 → 等待 1 秒再开始下一批。
4. **收尾**：`failed_count > 0` → `PARTIAL_FAILED`，否则 `DONE`；`UPDATE ... SET status=:final, finished_at=:now, updated_at=:now WHERE id=:id AND status=SENDING`（已被超时扫描改掉的不覆盖）。
5. 已写入通知中心的行**任何情况下都不回滚、不删除**（PRD AC6）。
6. 用户未授权系统推送时腾讯侧静默不投、接口仍返回成功——这类用户「只在通知中心」，不计失败（FR-138.1 / 138.6）。
7. 等待动作走可替换的 `OpsDispatchPacer`（`void sleep(Duration d)`，生产实现 `Thread.sleep`，中断时恢复中断标志并停止发送），测试注入记录型实现，**测试里不得真睡**。
8. 日志只记：活动 id、批次序号、本批写入数、本批失败数、最终状态。**不记**收件人 id、标题、正文、token。

**AC6 — 专用执行器** `[L0]`
`shared/async/AsyncConfig.java` 新增 bean（照 `analyticsExecutor` L38-48 写法）：
```java
@Bean("opsNotificationExecutor")
public TaskExecutor opsNotificationExecutor() {  // 单线程：同一时刻只发一个活动，天然限速；后来者排队
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setThreadNamePrefix("ops-notify-");
    executor.setCorePoolSize(1);
    executor.setMaxPoolSize(1);
    executor.setQueueCapacity(100);
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.DiscardPolicy()); // 丢了也无妨：仍是 PENDING，下一轮扫描再投
    executor.initialize();
    return executor;
}
```
并在注释写明：抢占在执行线程内做（AC3.1），所以被丢弃的任务不会留下卡在 SENDING 的活动。**不得**改 `spring.task.execution.mode=force`。

### 关键设计点

- **为什么推送要改出一个有返回值的方法**：D-19 要求逐人调用既有单人推送；但现有链路（`@Async` + `postRest` 吞错）调用方拿不到成败，epics 6.2 的「失败重试 3 次 / 计入 failed_count」就无从实现。最小改动是给接口加 **default** 方法（Stub 与任何测试替身零改动），Live 只把 `postRest` 的成败往外报，请求体、日志、既有调用方行为全部不变。
- **为什么重试只重推失败的人**：整批重推会让已成功的人收到第二条系统推送——运营通知是营销内容，重复推送直接导致关推送 / 卸载。`failed_count` 的单位因此是「人」，不是「批」。
- **为什么写通知中心与推送分开**：通知中心是触达的权威（`recipient_count` = 写入成功人数）；推送失败不影响已写入的通知（PRD AC6）。
- **为什么单线程执行器**：逐人同步推送本身就是限速；单线程保证同一时刻只有一个活动在推，不会两个全量活动叠加打爆腾讯 IM 频控。代价是后来的活动排队——可接受（≤500 DAU 规模，V1 架构姿态）。
- **为什么 15 分钟能判「无进展」**：单人推送最坏 10s（连接 5s + 读 5s 超时），每 50 人刷一次进展 → 正常情况下两次刷新间隔 ≤ 50 × 10s ≈ 8.3 分钟，加重试退避 7s 仍 < 15 分钟。超过即视为线程已死（进程重启 / 卡死）。
- **为什么超时后不重发**：已写入通知中心的人数无法与「推到第几个」精确对齐，重发必然重复推送（D-20）。
- **WIB 日期**：`ZoneId.of("Asia/Jakarta")`；`registeredTo = 2026-10-12` 表示 `created_at < 2026-10-13T00:00+07:00`。
- **定时活动按实际发送时刻解析人群**：注册时间 / 活跃时间等条件在到点那一刻算，不在创建时算（epics 6.2）。
