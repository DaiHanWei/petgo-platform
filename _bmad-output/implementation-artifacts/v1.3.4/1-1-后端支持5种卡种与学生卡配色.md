# Story 1.1: 后端支持 5 种卡种与学生卡配色

Status: review

> 版本 v1.3.4 · 主题 ktp · 分支 `feat/1.3.4-ktp-revamp`
> 口径优先级：`决策日志-ktp.md` > `PRD-v1.3.4-ktp.md` > `architecture-v1.3.4-ktp-delta.md` > `ui-v1.3.4-ktp.html`（均在 `_bmad-output/planning-artifacts/v1.3.4/`）

## Story

As a 用户,
I want 系统能建居住证、SIM 和三款新配色的学生卡,
so that 我有更多卡可以做。

## Acceptance Criteria

**AC1 — 迁移：`card_variant` 与卡种约束** `[L0]` `[L1]`
1. 新迁移 `V<yyyyMMdd_HHmm>__id_cards_card_variant_and_checks.sql`（取创建时刻；提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`）：
   - `ALTER TABLE id_cards ADD COLUMN card_variant VARCHAR(16)`；
   - `UPDATE id_cards SET card_variant = 'KLASIK' WHERE card_type = 'STUDENT'`；
   - 加约束前自检：`card_type` 只能是 `KTP / PASSPORT / STUDENT`（V93 起请求白名单保证）；迁移注释写明自检 SQL 与本地 / stag 库的结果；
   - 三条 CHECK：`ck_id_cards_card_type CHECK (card_type IN ('KTP','PASSPORT','KITAS','SIM','STUDENT'))`、`ck_id_cards_card_variant CHECK (card_variant IS NULL OR card_variant IN ('BINTANG','MALAM','CERIA','KLASIK'))`、`ck_id_cards_variant_only_student CHECK ((card_type = 'STUDENT') = (card_variant IS NOT NULL))`；
   - `COMMENT ON COLUMN id_cards.card_variant`（学生卡配色；非学生卡 NULL；存量学生卡回填 KLASIK）。
2. 实体 `IdCard` 加 `cardVariant` 字段与 getter；`IdCard.snapshot(...)` 增加 `cardVariant` 参数。

**AC2 — 卡种 / 配色枚举与建卡请求** `[L0]` `[L1]`
1. 新增 `com.tailtopia.profile.domain.IdCardType { KTP, PASSPORT, KITAS, SIM, STUDENT }` 与 `StudentVariant { BINTANG, MALAM, CERIA, KLASIK }`；`CreateIdCardRequest` 的 `cardType` `@Pattern` 改为 `KTP|PASSPORT|KITAS|SIM|STUDENT`，新增 `@Pattern(regexp = "BINTANG|MALAM|CERIA|KLASIK") String cardVariant`。单测断言两个正则与枚举值集合一致（同源）。
2. 规则（`IdCardService.createCard` 内校验，失败统一 422 `validation`）：
   - `cardType` 为 null → 仍按 `KTP`（兼容旧客户端，沿用 `normalizeCardType`）；
   - `STUDENT` 且 `cardVariant` 为 null → **按 `KLASIK`**（旧版 App 只有紫色学生卡，见 Dev Notes「兼容说明」）；
   - 非 `STUDENT` 却带 `cardVariant` → 422。
3. 必填（AD-4 / D-9）：`petType` 必填且限 `CAT|DOG|OTHER`；`gender` 必填且限 `MALE|FEMALE|UNKNOWN`（**删除** `normalizeGender` 的 null→UNKNOWN 回落）；`birthday` 仍必填；`cardType` 为 `KTP` 或 `KITAS` 时 `breed` 必填（非空白）。
4. `intro`：DTO 字段保留（旧版 App 仍会传），**一律不写入**——`snapshot` 传 `null`（PRD §3.4 / FR-142D.4）。
5. 快照写入 `card_type` 与 `card_variant`；新卡种照常分配 `serial_id` + `card_no` + `passport_no`（与现状相同，编号沿用在 Epic 2）。

**AC3 — 响应** `[L0]`
1. `IdCardResponse` 增加 `String cardVariant`（列表、详情、建卡响应共用）；存量学生卡返回 `KLASIK`。
2. 建卡响应增加 `boolean numberReused`，**本 story 恒为 `false`**（Epic 2 Story 2.3 接真值）。实现方式：建卡接口返回 `IdCardResponse` 的扩展（如 `IdCardCreateResponse`，含 `IdCardResponse` 全部字段 + `numberReused`），列表 / 详情不带该键。按 Dev Notes 选一种并在 Completion Notes 写明。
3. App 侧 `IdCard.fromJson` 读 `cardVariant`（缺省 null），`effectiveCardType` 逻辑不变——本 story **不改任何 App 页面**，只保证 App 能解析新字段、旧版 App 忽略新字段不崩。

**AC4 — 后台「用户购买记录」显示卡种** `[L1]`（决策日志 D-6）
1. `AdminUserPurchasesQuery.KTP_SQL` 增选 `c.card_type, c.card_variant, c.card_no`；`UserPurchasesView.KtpCard` 增加 `cardType`、`cardVariant`、`cardNo`。
2. `drawer-users.html` 购买记录行改为「{卡种名} · No. {编号} · {宠物名}」：编号 = `card_no`，为空时用 `serial_id` 左补零到 4 位（与 App 列表 `id_card_page.dart:119` 同口径）。
3. 卡种名 8 个 i18n key（`admin.v134.idcard.style.KTP` / `PASSPORT` / `KITAS` / `SIM` / `STUDENT.BINTANG` / `STUDENT.MALAM` / `STUDENT.CERIA` / `STUDENT.KLASIK`），zh / en / id 三语 + `messages.properties` 默认：
   - zh：KTP · 护照 · 居住证 · SIM 驾照 · 学生卡 Bintang · 学生卡 Malam · 学生卡 Ceria · 学生卡 Klasik
   - en：KTP · Passport · Residence Permit · Driving License · Student Star · Student Night · Student Cheerful · Student Classic（D-11）
   - id：KTP · Paspor · Kartu Izin Tinggal · SIM · Pelajar Bintang · Pelajar Malam · Pelajar Ceria · Pelajar Klasik
4. `AdminUserPurchasesIntegrationTest` 覆盖：护照卡显示「护照」而非「KTP」；学生卡显示配色名；V95 前无 `card_no` 的卡显示补零流水号。

**AC5 — 回归** `[L0]` `[L1]`
1. 既有接口行为不变：列表可见性（付费恒可见 / 删档隐藏未付费）、HD 解锁、分享奖励、宠物护照取号（`findReusableKtpPassportNo`）。
2. `IdCardServiceTest`、`IdCardEndpointIntegrationTest`、`AdminUserPurchasesIntegrationTest` 按新口径更新并通过；新增用例：5 种卡种各建一张成功；学生卡四配色各一张；非学生卡带 `cardVariant` 422；缺 `petType` / `gender` 422；KTP / KITAS 缺 `breed` 422；`STUDENT` 不带 `cardVariant` 落 `KLASIK`；带 `intro` 不落库。
3. `mvn -B clean package` 绿（L0）；L1 在本地连本分支库跑集成测试。

## Dev Notes

### 现状（改动前必读）

- `CreateIdCardRequest`（`petgo-backend/src/main/java/com/tailtopia/profile/dto/CreateIdCardRequest.java`）：`cardType` 白名单 `KTP|PASSPORT|STUDENT`、`gender` 可空、`petType` 只有 `@Size(16)`、`intro` 可传。
- `IdCardService.createCard`（`…/profile/service/IdCardService.java:78-91`）单事务：`normalizeGender`（null→UNKNOWN）→ `serialAllocation.allocate()` → `cardNumbers.allocateCardNo(birthday, gender, petType)` → `allocatePassportNo(petType)` → `IdCard.snapshot(...)`。**不读宠物档案**（卡与档案解耦，表单值即快照）。
- `IdCard.snapshot(...)`（`…/profile/domain/IdCard.java:115`）18 个参数，按位置传；加参数时注意所有调用点（含测试夹具）。
- `id_cards` 当前**没有任何 CHECK**（V91 / V93 / V95 / V96 / V100 / V108）；`card_type` 默认 `'KTP'`（V93）。
- 后台：`AdminUserPurchasesQuery.KTP_SQL`（`…/admin/usermgmt/service/AdminUserPurchasesQuery.java:35`）与模板 `templates/admin/fragments/drawer-users.html:274-281`（现在一律渲染 `'KTP #' + serialId`）。`unlocked_at` 的取法（QRIS 取到账、PawCoin 取扣币）**与决策日志 D-8 口径相同**，Story 2.1 回填 `hd_unlocked_at` 时可复用这段 SQL。

### 兼容说明（与 epics 原文的一处差异）

epics Story 1.1 写「学生卡缺 `cardVariant` → 422」，但同文 NFR4 要求「旧版建卡请求（无 cardVariant）仍可处理」。线上 1.3.3 App 建学生卡时**不会**带 `cardVariant`，按 422 处理会让所有旧版用户建不了学生卡。本 story 按 NFR4 处理：`STUDENT` 缺配色落 `KLASIK`（旧版只有这一款，语义一致）。**已确认（决策日志 D-12）**。

`petType` 必填对旧版的影响已由 D-9 接受（仅档案无物种的极少数旧版用户会 422）。

### 架构约束

- AD-1：枚举 + CHECK 同源；`card_variant` 非学生卡必须为 NULL。
- AD-4：必填与白名单；`intro` 不写入。
- 迁移一律时间戳命名；改 `id_cards` 不需要动 `ck_notifications_type` 之类共享约束。
- 错误统一 RFC 9457 ProblemDetail（`AppException.validation(...)`），不外泄堆栈。

### 本 story 不做

- 不改任何 App 页面 / 卡面（Story 1.2 起）；不做编号沿用、`hd_unlocked_at`、归属表（Epic 2）。
- 不改 HD 价格与解锁流程、分享奖励口径。

### 测试

- 后端单测：`IdCardServiceTest`（mock `CardNumberService` / `SerialAllocationService`）补规则用例；正则与枚举同源断言。
- 集成：`IdCardEndpointIntegrationTest`、`AdminUserPurchasesIntegrationTest`（需本分支库：本地 `DB_NAME=<新建空库> ./mvnw -B test`，见记忆「后端测试要连本分支的库」；`JAVA_HOME` 指向 Android Studio JBR 21）。
- App：`IdCard.fromJson` 读 `cardVariant` 的单测（缺键为 null）。
