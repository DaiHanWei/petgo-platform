# Story 3.3: 通知列表返回拼好的文案与触发人

Status: review

> 版本 v1.3.4 · 主题 follow · 分支 `feat/1.3.4-follow-notify`
> 口径优先级：`决策日志-follow.md` > `PRD-v1.3.4-follow.md` > `architecture-v1.3.4-follow-delta.md` > `ui-v1.3.4-follow.html`（均在 `_bmad-output/planning-artifacts/v1.3.4/`）
> 范围：**只改后端**（`petgo-backend`）。App 侧显示在 Story 3.4。
> 前置：Story 3.1（`notification_actors` 表、`notifications.aggregate_key / comment_id / variant / updated_at`、`notify.tpl.*` 模板与拼装组件、`sendInteraction`）、Story 3.2（`USER_FOLLOWED` / `PLACE_COMMENTED` 两种类型）、Story 1.1（`users.public_token`、`FollowReader`）。

## Story

As a 用户,
I want 通知中心显示「谁 + 做了什么」以及合并人数,
so that 我不用点开就知道发生了什么。

## Acceptance Criteria

**AC1 — 列表项新增字段** `[L0]`
1. `notify/dto/NotificationItem` 新增 5 个字段（record 组件名即 JSON 键）：
   - `String actorName`：要加粗显示的触发人昵称；没有可显示的触发人时为 `null`；
   - `int actorCount`：过滤后的触发人**总数**（含 `actorName` 那一位）；没有时为 `0`；
   - `Long actorUserId`：该触发人的数字 id（App 跳现有主页路由 `/users/:userId` 用，D-2）；没有时为 `null`；
   - `String actorToken`：该触发人的 `users.public_token`（App 回关调 `PUT /api/v1/users/{token}/follow` 用）；没有时为 `null`；
   - `Boolean actorIFollow`：**只对 `USER_FOLLOWED`** 填「我（接收方）是否已关注该触发人」；其余类型一律 `null`。
2. 原有 8 个字段（`type / title / body / deepLinkType / deepLinkToken / targetRef / read / createdAt`）名称、类型、含义不变；**不新增** `id`、`commentId`、`aggregateKey`、`variant` 等任何内部字段（`NotificationControllerEndpointTest.list_returnsOnlyOwnNotifications` 的「`$.items[0].id` 不存在」断言继续成立）。
3. `NotificationItem.from(Notification)` 保留给「无需拼文案」的条目；新增一个带拼装结果的构造方法（如 `NotificationItem.of(Notification n, RenderedCopy copy, ActorInfo actor)`），名字自定，Completion Notes 写明。

**AC2 — 哪些条目拼文案** `[L0]` `[L1]`
1. 同时满足以下两条的条目走「现拼」：类型为 `CONTENT_LIKED` / `CONTENT_COMMENTED` / `USER_FOLLOWED` / `PLACE_COMMENTED` 之一，**且**该通知在 `notification_actors` 里有行。
2. 现拼条目：`title` / `body` 用拼好的文案**覆盖**库里的 `title` / `body` 列；其余字段照原样。
3. 不满足的条目（其余类型；或上线前的存量 `CONTENT_LIKED` / `CONTENT_COMMENTED`，没有 actor 行）**完全原样返回**，5 个新字段为 `null / 0 / null / null / null`；不回填、不改库（PRD「存量通知」、FR-141.13）。
4. 有 actor 行、但过滤后（AC3）一个可显示的人都不剩 → 本 story 先按第 3 条「原样返回 + 新字段为空」处理，**不报错、不从列表里删掉**；最终口径见 Completion Notes「待确认 2」。

**AC3 — 最新触发人与人数（FR-141.9）** `[L0]` `[L1]`
1. 可显示的触发人 = 该通知的 actor 行里，**未注销**（`users.deleted_at IS NULL`）且**未被接收方隐藏**的人（隐藏判据见 Dev Notes「隐藏关系判据」，与写入时 `ContentNotifyListener.suppressed` ① 同口径）。
2. `actorName` / `actorUserId` / `actorToken` = 可显示的人里 `acted_at` 最新的那一位（`acted_at` 相同按 `actor_user_id` 倒序，保证确定）；`actorCount` = 可显示的总人数；模板里的「N」= `actorCount - 1`。
3. 举例：同帖 A、B、C 依次点赞且未读，接收方之后拉黑了 C、B 注销 → `actorName = A`，`actorCount = 1`，标题为单人模板「A menyukai postinganmu」。
4. 昵称取**当前**昵称（读取时现查，不落库，PRD 影响面）：`nickname` 为空时回落 `displayName`，与 `AccountQueryService.toAuthorView` 同一规则。

**AC4 — 文案模板与语言（FR-141.4 / 141.5）** `[L0]`
1. 拼装**必须**调用 Story 3.1 建的同一个模板拼装组件（推送也调它；若 3.1 没有抽成独立组件，本 story 把它抽到 `notify/service/InteractionCopyRenderer` 并让推送改用它）。列表里**不允许**另写一份模板拼接代码——这是「推送文案与列表一致」的唯一保证。
2. 模板（i18n key 前缀 `notify.tpl.`，键名以 3.1 / 3.2 实际落地为准；文案取 UI 稿「新增印尼语文案」表）：

   | 情形 | `title`（ID） | `title`（EN） | `body` |
   |---|---|---|---|
   | `CONTENT_LIKED`，1 人 | `{nama} menyukai postinganmu` | `{name} liked your post` | `null` |
   | `CONTENT_LIKED`，多人 | `{nama} dan {n} lainnya menyukai postinganmu` | `{name} and {n} others liked your post` | `null` |
   | `CONTENT_COMMENTED`，`variant` 为空 | `{nama} mengomentari postinganmu` | `{name} commented on your post` | 评论原文 |
   | `CONTENT_COMMENTED`，`variant = REPLY` | `{nama} membalas komentarmu` | `{name} replied to your comment` | 回复原文 |
   | `PLACE_COMMENTED`，1 人 | `{nama} mengomentari tempat yang kamu tambahkan` | `{name} commented on the place you added` | `null` |
   | `PLACE_COMMENTED`，多人 | `{nama} dan {n} lainnya mengomentari tempat yang kamu tambahkan` | `{name} and {n} others commented on the place you added` | `null` |
   | `USER_FOLLOWED` | `{nama} mulai mengikutimu` | `{name} started following you` | `null` |

3. 语言：取本次请求头 `Accept-Language`，归一规则与 `MeService.captureLocale`（`auth/service/MeService.java:50`）相同——以 `en` 开头为英语，其余（含缺失）为印尼语。`NotificationController.list` 加 `@RequestHeader(value = "Accept-Language", required = false)` 并传给 service（选择理由见 Dev Notes「语言来源」；见「待确认 4」）。
4. 新增 i18n 键 `notify.tpl.commentDeleted`：id `Komentar telah dihapus`、en `Comment deleted`；`messages.properties`（英文基线）同 en；`messages_zh_CN.properties` 写 `评论已删除`（四个文件键集对齐，`AdminMessagesParityTest` 类测试照常绿）。如果 3.1 已加了同义键就复用、不重复加。
5. 模板串带参数走 `MessageFormat`：新增串里**不得**出现裸单引号（`NotificationService.sendWithCopy` 注释 :157 的坑）；昵称、评论原文只作为参数传入，不拼进模板串本身。

**AC5 — 评论已删除（FR-141.13）** `[L0]` `[L1]`
1. `CONTENT_COMMENTED` 现拼条目按 `notifications.comment_id` 一次批量取评论当前状态（Dev Notes「评论状态端口」）。
2. 评论 `deleted_at` 非空、或评论行不存在 → `body = notify.tpl.commentDeleted`（按 AC4.3 语言）；`title` 不变（仍是「X mengomentari postinganmu」/「X membalas komentarmu」）。
3. 评论 `moderation_status` 不是 `VISIBLE`（巡查下架 / 作者注销隐藏等）→ 本 story 先同样显示 `Komentar telah dihapus`，不把已下架原文返回给客户端；见「待确认 3」。
4. 评论正常 → `body` = 评论当前全文（App 单行截断，后端不截断）。
5. `comment_id` 为空的 `CONTENT_COMMENTED` 现拼条目（理论上不该出现）→ `body = null`，不报错。

**AC6 — 新粉丝关注态** `[L0]` `[L1]`
1. 对本页所有 `USER_FOLLOWED` 现拼条目，用 `FollowReader.followStates(接收方 id, 这些条目的 actorUserId 集合)` **一次**取关系，`actorIFollow = followStates.get(actorUserId).iFollow()`。
2. 我已回关 → `actorIFollow = true`（App 不显示按钮）；未回关 → `false`。

**AC7 — 批量、禁止逐条（NFR3 / AD-16）** `[L0]`
1. 一页（默认 20、上限 50）现拼所需的外部取数**各一次**，与条目数无关：
   ① actor 行（按本页现拼候选通知 id 一次取全）；② 触发人昵称 + `public_token` + 是否注销（`AccountQueryService` 批量方法一次）；③ 接收方隐藏了谁（`UserHideRelationReader` 批量方法一次）；④ 评论状态（一次，只在本页有 `CONTENT_COMMENTED` 现拼条目时调）；⑤ 新粉丝关注态（一次，只在本页有 `USER_FOLLOWED` 现拼条目时调）。
2. 本页没有任何现拼候选（全是系统通知 / 存量）→ ①~⑤ 一个都不调。
3. `NotificationCenterServiceTest` 用 mock 断言：一页 20 条混合类型时，①~⑤ 各 `times(1)`；纯系统通知页各 `never()`。

**AC8 — 既有行为不变** `[L0]` `[L1]`
1. 游标分页（`KeysetCursor`，`(created_at, id)` 复合）、`hasMore`、`nextCursor`、坏游标退化首页（`NotificationCenterService.java:131-148`）不变。
2. 首页（`cursor == null`）按库校准 Redis 角标、漂移 `log.warn`（`:58-73`）不变；`unreadCount` / `markRead` / `markAllRead` 不变。
3. 日志不记录昵称、评论原文、token（CLAUDE.md 日志护栏）。
4. `NotificationControllerEndpointTest` 现有用例全部继续通过。

## Dev Notes

### 现状（改动前必读）

- `NotificationCenterService.list`（`petgo-backend/src/main/java/com/tailtopia/notify/service/NotificationCenterService.java:47-75`）：`repo.findPageBefore(userId, cursor.createdAt, cursor.id, PageRequest.of(0, limit + 1))` → 截 `limit` 条 → `map(NotificationItem::from)` → 首页时按库校准角标。构造器只有 `(NotificationRepository, StringRedisTemplate)`，类注释写着「**不跨模块 join**」——本 story 新增的依赖一律走其它模块的 service / 读端口，不写跨模块 SQL。
- `NotificationItem`（`…/notify/dto/NotificationItem.java:14-27`）：8 个字段，`from(n)` 原样搬库里的 `title / body`。库里的这两列是写入方给的**兜底中文**（如 `ContentNotifyListener.java:84`「有人赞了你的内容」），App 一直不读——所以存量条目「原样返回」后，App 仍须靠 `actorName == null` 判断走旧文案（Story 3.4）。
- `NotificationController.list`（`…/notify/web/NotificationController.java:39-45`）：`limit` 缺省 20、上限 50；目前不读 `Accept-Language`。
- 拼文案用的 `MessageSource`：`shared/i18n/AdminLocaleConfig.java:59-75`，basename `classpath:i18n/messages`，缺键回退英文基线 `messages.properties`；四个文件 `src/main/resources/i18n/messages{,_id,_en,_zh_CN}.properties`。推送现在用 `notify.<TYPE>.title/body` 静态键（`NotificationService.pushText` :56），3.1 起互动类改用 `notify.tpl.*`。
- 昵称批量：`AccountQueryService.findAuthorViewsWithoutTags`（`…/auth/service/AccountQueryService.java:147`）一次 `findAllById`，注销者给 `AuthorView.anonymized`（`deleted = true`、昵称 null）；昵称规则 `nickname ?: displayName`（`:261-268`）。`AuthorView` **没有** `publicToken`（`auth/dto/AuthorView.java`）。
- 隐藏关系：`UserHideRelationReader`（`…/social/read/UserHideRelationReader.java`）单条 `isHidden`（不分来源）/ `isBlocked`（只 BLOCK）；批量只有 `hiddenEitherWay`（:75，**双向**、不分来源）。仓储已有单向按来源批量查询 `findTargetIdsByHolderAndSourceIn`（`social/repository/UserHideRelationRepository.java:38-41`）。
- 写入时抑制：`ContentNotifyListener.suppressed`（`…/notify/service/ContentNotifyListener.java:66-72`）用 `isHidden`（拉黑与举报隐藏都算）。读取时过滤与它同口径。
- 评论：`content/domain/Comment.java`——软删 `deleted_at`（:65）、`moderation_status`（:58，`VISIBLE / UNDER_REVIEW / TAKEN_DOWN / REJECTED / AUTHOR_DEACTIVATED`）、`body` 最长 1000。notify 模块目前**不直访 content repository**（`ContentNotifyListener` 类注释），已有跨模块读 service 的先例（`PetProfileQueryService`、`AccountQueryService`）。
- 测试：`src/test/java/com/tailtopia/notify/service/NotificationCenterServiceTest.java`（纯 Mockito，`new NotificationCenterService(repo, redis)`，构造器变了要一起改）；`src/test/java/com/tailtopia/notify/web/NotificationControllerEndpointTest.java`（`ApiIntegrationTest`，L1，`persist(...)` 直写行）。

### 昵称与 token 端口

- 需要的是「id → 昵称、`publicToken`、是否注销」一次取齐。先看 Epic 1 / 2 落地后的代码：若 Story 2.1（`FeedItemResponse.authorToken`）已经让 `AuthorView` 带上 `publicToken`，直接用 `findAuthorViewsWithoutTags`（通知中心不显示运营标签，用不带标签的版本，不白查 `user_tag_assignments`）；否则在 `AccountQueryService` 加一个批量方法（如 `findActorViews(Collection<Long>)`，一次 `findAllById`）。**不要**为 token 再单独多查一次。
- 加新调用方前按 `findAuthorViewsWithoutTags` 的注释自查：通知中心确实不展示标签。

### 隐藏关系判据

- 「未被我拉黑」按写入时抑制同口径实现：**接收方（holder）对触发人有任何隐藏关系**（`BLOCK` 或 `REPORT`）即不显示——单向，只看接收方这一侧。
- 端口上没有现成的单向批量方法：在 `UserHideRelationReader` 加 `Set<Long> hiddenBy(long holderId, Collection<Long> targets)`（名字可调，空集合不发查询），仓储加 `SELECT r.targetId FROM UserHideRelation r WHERE r.holderId = :holderId AND r.targetId IN :targetIds`。若 Story 2.2（`FollowListItem.blockedByMe`）已加了单向批量方法且口径一致（不分来源），复用它；口径只认 `BLOCK` 的不能直接拿来用。
- **不用** `hiddenEitherWay`：它把「触发人拉黑了我」也算进去，与写入口径不一致。
- 是否把 `REPORT` 也算作「已拉黑」见「待确认 1」。

### 评论状态端口

- 在 content 模块加只读批量方法（如 `CommentQueryService.notificationSnapshots(Collection<Long> commentIds) → Map<Long, CommentSnapshot(String body, boolean gone)>`，一次 `findAllById`）；`gone = 行不存在 || deleted_at != null || moderation_status != VISIBLE`。notify 只依赖这个方法，不引用 `CommentRepository`。

### 语言来源

- 选请求头而不是 `AccountQueryService.localeOf`：同一页里系统类通知由 App 按 App 语言渲染，互动类若按账号存的语言拼，两者可能一中一英混排；App 每个请求的 `Accept-Language` 就是 App 当前生效语言（`petgo_app/lib/core/network/dio_client.dart:62-70`，只会是 `id` / `en`），`/me` 也用同一个头回写账号语言（`MeService.captureLocale`），推送用的账号语言最终与它一致。
- 推送仍按 `localeOf`（3.1 不变）。

### 架构约束

- AD-11：只对四类且有 actor 行的条目现拼；一页一次批量；存量原样返回。
- AD-3：`notification_actors` 只存 id，昵称读取时现查。
- AD-10 / FR-141.4：推送与列表共用同一个模板拼装组件。
- 模块边界：notify 不写跨模块 SQL；social 只经 `UserHideRelationReader`；content 只经 content 的 service 方法。
- 对外不暴露通知 id、评论 id；`actorUserId` 是数字 id——D-2 允许（只用于跳现有数字 id 主页路由），关注操作一律用 `actorToken`。
- 日志不记 PII / 评论原文 / token；错误统一 ProblemDetail。

### 已知限制（写进代码注释）

- actor 行是「整页一次取全」：点赞未读期间持续合并的爆款帖，一条通知可能挂很多 actor 行，`IN` 列表随之变长。V1 规模可接受；若日后成为瓶颈，再改为库内聚合（需另行评审模块边界）。
- 3.1 合并时把 `created_at` 刷到当前时刻：用户翻页期间被合并的那条会跳到首页，本次翻页看不到，重新进入即可——游标逻辑不为此改动。

### 本 story 不做

- 不改 App（Story 3.4）；不改写入、聚合、推送、去抖（Story 3.1 / 3.2）。
- 不回填存量通知的 actor；不改 `unreadCount` / 已读接口；不加接口参数（除 `Accept-Language` 头）。

**待确认**

- T-36「角标同口径不计」只在首页校准与 Redis 缺键回算时生效：日常 `unread-count` 读 Redis 计数，若某条通知在写入后才变成「触发人全被过滤」（例如触发人事后被封号 / 被我拉黑），角标会多 1，直到下次打开通知中心首页校准。按最保守做法未让每次读角标都跑一遍过滤（会把轮询接口变重）。
- 首页请求在校准角标时会对全部未读互动条目再跑一遍 ①②③ 批量（与本页的 ①②③ 分开），首页因此多 3 次查询；非首页不受影响。
- 被隐藏的条目只是不出现在本页，游标仍按原始行推进：某一页可能少于 `limit` 条（`hasMore` 照常）。
- 原 Completion Notes 的待确认 1~5 已被裁定 T-30 / T-36 / T-37 / T-38 / T-39 覆盖，按裁定实现（待确认 2「全部被过滤」按 T-36 改为隐藏；待确认 4 语言按 T-38 改为账号语言）。


- 待确认 1：「and N others 不含已拉黑」的「拉黑」是否包含**举报隐藏**（`REPORT`）。本 story 按写入时抑制同口径（`isHidden`，BLOCK + REPORT 都算）实现；若只认 BLOCK，换用只认 BLOCK 的批量查询即可。
- 待确认 2：有 actor 行但触发人**全部**被过滤（都注销 / 都被我拉黑）时怎么显示。本 story 先原样返回（新字段为空）；对 `CONTENT_LIKED` / `CONTENT_COMMENTED`，App 会显示旧通用文案，但 `USER_FOLLOWED` / `PLACE_COMMENTED` 没有旧文案（App 会落到「系统通知」兜底）。可选：从列表中隐藏这类条目，或为两种新类型补通用文案。PRD / 决策日志都没写。
- 待确认 3：评论处于非 `VISIBLE` 状态（巡查下架 `TAKEN_DOWN`、作者注销 `AUTHOR_DEACTIVATED` 等）时，PRD 只写了「评论已删除」。本 story 先一律显示「Komentar telah dihapus」，不把下架原文返回给客户端。
- 待确认 4：列表文案语言取请求头 `Accept-Language`（= App 当前语言），而 PRD / AD-11 写的是「接收方语言」。两者通常一致；在 App 里刚切语言、`/me` 还没回写时，列表与推送会短暂不同语言。若要求严格取账号语言，改用 `AccountQueryService.localeOf`。
