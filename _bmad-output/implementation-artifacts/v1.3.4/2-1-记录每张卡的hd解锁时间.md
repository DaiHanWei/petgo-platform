# Story 2.1: 记录每张卡的 HD 解锁时间

Status: review

## Story

As a 系统,
I want 知道每张卡是什么时候解锁 HD 的,
so that 多张学生卡都符合条件时，能找到最早解锁的那张。

## Acceptance Criteria

**AC1 — 迁移：新增 `hd_unlocked_at` 并回填存量** `[L0]` `[L1]`
1. 新迁移 `V<yyyyMMdd_HHmm>__id_cards_hd_unlocked_at.sql`（取创建时刻；须晚于 Story 1.1 的 `…__id_cards_card_variant_and_checks.sql`；提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`）：
   - `ALTER TABLE id_cards ADD COLUMN hd_unlocked_at TIMESTAMPTZ`（可空，UTC）；
   - 回填只动 `hd_unlocked = true` 的卡，取值口径按决策日志 D-8（与 `AdminUserPurchasesQuery.KTP_SQL` 的 `unlocked_at` 子查询**同一个表达式**，直接复用）：
     ```sql
     UPDATE id_cards c
        SET hd_unlocked_at = COALESCE(
              (SELECT MIN(CASE WHEN h.pay_channel = 'PAWCOIN' THEN h.purchased_at
                               WHEN pi.status = 'PAID'      THEN pi.updated_at END)
                 FROM id_card_hd_purchases h
                 LEFT JOIN payment_intents pi ON pi.id = h.payment_intent_id
                WHERE h.card_id = c.id),
              c.created_at)
      WHERE c.hd_unlocked;
     ```
     即：PawCoin 行取扣币时间 `purchased_at`；QRIS 行取其支付意图到账（`PAID`）的 `updated_at`，**不用** QRIS 行的 `purchased_at`（那是下单时间）；都没有（V92 回填生成的老卡等）取卡的 `created_at`。
   - 未解锁卡（`hd_unlocked = false`）保持 `NULL`；
   - `COMMENT ON COLUMN id_cards.hd_unlocked_at`：HD 解锁（到账）时刻，UTC；未解锁为 NULL；存量按 D-8 回填；用于编号沿用「取最早解锁的学生卡」。
   - 迁移注释记录回填自检：已解锁卡总数、其中走 `created_at` 兜底的张数（在本地库 / `petgo_stag` 上跑一遍，把结果写进注释，与 Story 1.1 的自检注释同一写法）。
2. 回填后断言（迁移末尾或集成测试里查）：`SELECT count(*) FROM id_cards WHERE hd_unlocked AND hd_unlocked_at IS NULL` = 0；`SELECT count(*) FROM id_cards WHERE NOT hd_unlocked AND hd_unlocked_at IS NOT NULL` = 0。

**AC2 — 实体：解锁时同时写时间，重复解锁不改写** `[L0]`
1. `IdCard`（`profile/domain/IdCard.java`）新增 `@Column(name = "hd_unlocked_at") private Instant hdUnlockedAt;` 与 getter `getHdUnlockedAt()`。
2. `markHdUnlocked()`（现 `IdCard.java:144`）改为：**仅当本卡尚未解锁时**置 `hdUnlocked = true` 且 `hdUnlockedAt = Instant.now()`；已解锁再调用**不改写** `hdUnlockedAt`（保持方法签名无参、幂等语义不变）。
3. `IdCard.snapshot(...)` 新建卡 `hdUnlockedAt = null`（不新增参数）。
4. `IdCardResponse` **不新增**该字段（App 不需要；本 story 不改接口契约）。

**AC3 — 两条解锁路径都经 `markHdUnlocked()` 写入** `[L1]`
1. PawCoin：`IdCardHdService.purchaseCard`（`:86`，PAWCOIN 分支 `:97`）当场解锁 → 卡 `hd_unlocked_at` 非空，且落在请求前后时间窗内。
2. QRIS：`POST /me/id-cards/{cardId}/hd-download` 下单后，`PaymentIntentService.applyCallback(PAID)` → `IdHdPaidHandler.onPaid` → `IdCardHdService.completeHdPaid`（`:149`）→ `completeCardByIntent`（`:128`）→ `markHdUnlocked()` → `hd_unlocked_at` 非空，且**晚于**该卡 QRIS attempt 行的 `purchased_at`（证明取的是到账时刻不是下单时刻）。
3. 重复：同一卡先 PawCoin 解锁，再让该卡早先建好的 QRIS 意图到账（`completeCardByIntent` 对已解锁卡再次 `markHdUnlocked()`）→ `hd_unlocked_at` 等于第一次写入值，不变；QRIS 回调重放（意图已终态）同样不变。
4. 旧版单卡端点 `/me/id-card/hd-download`（`IdCardHdService.purchase` / `completePurchase`，v1.0.x 客户端）不碰 `id_cards`，行为不变（无卡可写时间）。

**AC4 — 回归** `[L0]` `[L1]`
1. 解锁真相仍是 `id_cards.hd_unlocked`；卡可见性（`IdCardService.visible`）、`AdminUserPurchasesQuery` 后台购买记录、分享奖励不受影响。
2. `mvn -B clean package` 绿（L0）；`IdCardHdIntegrationTest` 在本地连本分支库跑通（L1）。

## Dev Notes

### 现状（改动前必读）

- **没有解锁时间**：`id_cards` 只有 `hd_unlocked BOOLEAN`（V91 `:19`）。`IdCard.markHdUnlocked()`（`profile/domain/IdCard.java:143-146`）只置布尔，注释「幂等：已解锁再调无副作用」——本 story 必须保持这一幂等，且时间只在第一次写。
- `markHdUnlocked()` 全仓**只有两个调用点**（已 grep 核实）：
  - `IdCardHdService.purchaseCard`（`profile/service/IdCardHdService.java:86-121`）：入口 `card.isHdUnlocked()` 已解锁直接 `granted()` 短路（`:89`）；PAWCOIN 分支 `wallet.debit` → `card.markHdUnlocked()`（`:97`）→ `idCards.save` → 建 attempt 行 `IdCardHdPurchase.of(userId, null, cardId, PAWCOIN, null)`（`:99`）。
  - `IdCardHdService.completeCardByIntent`（`:128-139`，`Propagation.MANDATORY`）：按 intentId 反查 attempt 行取 `cardId` → `findById` → `markHdUnlocked()`。由 `completeHdPaid`（`:149-156`）在「有 attempt 行」时调用；`IdHdPaidHandler.onPaid`（`profile/service/IdHdPaidHandler.java:28-37`）同步 `@EventListener` + MANDATORY 加入 `applyCallback` 事务调用 `completeHdPaid`。
  - 「已解锁卡再被 `markHdUnlocked()`」的真实场景：用户对同一卡先下 QRIS 单未付，又改用 PawCoin 解锁，之后那张 QRIS 单到账 → `completeCardByIntent` 会对已解锁卡再调一次。这正是 AC3.3 要测的。
- `completeHdPaid` 无 attempt 行时走 `completePurchase`（`:260-267`，旧版单卡端点 profile 级建购买行），**不碰 `id_cards`**。
- 购买记录表 `id_card_hd_purchases`（V75 建、V92 改按卡）：`purchased_at` = 行创建时刻。QRIS 下单即建 attempt 行（`:110-112`），超窗重开会新建意图 + 新 attempt 行（V92 注释 `:33-34`），所以 QRIS 行的 `purchased_at` 是**下单**时间，不能当解锁时间（PRD §3.5）。
- V92 回填（`V92__alter_id_card_hd_purchases_per_card.sql:11-25`）为老用户建的快照卡 `hd_unlocked = true`、`created_at = COALESCE(h.purchased_at, now())`，并把购买行 `card_id` 指过去——所以这批卡多数能从购买行取到时间，取不到的走 `created_at` 兜底（D-8）。
- **可复用 SQL**：`AdminUserPurchasesQuery.KTP_SQL`（`admin/usermgmt/service/AdminUserPurchasesQuery.java:35-45`）的 `unlocked_at` 子查询就是 D-8 口径（PawCoin `purchased_at`、QRIS 意图 `PAID` 的 `updated_at`、一卡多行取最早）。回填直接复用该表达式，外面套 `COALESCE(…, c.created_at)`。注意它按 `pay_channel = 'PAWCOIN'` 判 PawCoin 行；`ck_id_card_hd_purchases_channel` 只允许 `QRIS / PAWCOIN`，PawCoin 行恒无 `payment_intent_id`，与架构 AD-2「无 `payment_intent_id` 的行」等价。
- `payment_intents.updated_at` 由实体 `@PreUpdate` 维护（`pay/domain/PaymentIntent.java:104,228`）；只取 `status = 'PAID'` 的，退款等其他终态不计入。
- 测试现状：`IdCardHdIntegrationTest`（`src/test/java/com/tailtopia/profile/service/`）**只测旧版单卡端点** `/me/id-card/hd-download`，按卡端点 `/me/id-cards/{cardId}/hd-download`（`ProfileApiController.java:347-353`）目前**没有集成测试**；`IdHdPaidHandlerTest` 是纯 mock 单测，只验证委派到 `completeHdPaid`。

### 架构约束

- AD-2：`hd_unlocked_at TIMESTAMPTZ NULL`，经 `markHdUnlocked()` 写入；存量回填口径以**决策日志 D-8** 为准（订正了 PRD【建议】「取最早一条 `purchased_at`」）。
- 到账写入必须留在 `applyCallback` 同一事务内（`MANDATORY`，绝不 AFTER_COMMIT），本 story 不动事务边界。
- 时间一律 UTC `Instant` / `timestamptz`。
- 迁移时间戳命名；`ddl-auto=validate`，实体字段与列类型一致（`Instant` ↔ `timestamptz`）。

### 本 story 不做

- 不改后台购买记录 `KTP_SQL` 改读 `hd_unlocked_at`（后台口径维持现状，Story 1.1 只加卡种字段）。
- 不加 `hd_unlocked = (hd_unlocked_at IS NOT NULL)` 之类的 CHECK（架构未要求；现有测试夹具如 `AdminUserPurchasesIntegrationTest:77` 直接插 `hd_unlocked = true` 的卡而不带时间，加约束会连带改一批夹具）。Story 2.3 的取数对 `hd_unlocked_at` 为空做 `NULLS LAST` 兜底。
- 不在接口响应里暴露 `hdUnlockedAt`；不做编号沿用（Story 2.3）、不动唯一约束（Story 2.2）。
