## Story

As a 用户,
I want 有人关注我、有人在我创建的场所下评论时收到通知,
so that 我能及时回关、看到别人对我推荐的地方的反馈。

## Acceptance Criteria

**AC1 — 关注成功发事件（改 Story 1.1 的 `FollowService`）** `[L0]`
1. 新事件 `com.tailtopia.social.event.UserFollowedEvent(long followerId, long followeeId, Instant followedAt)`（social 不直调 notify，沿用「领域事件跨模块」范式，同 `ContentLikedEvent`）。
2. `FollowService` 的关注方法里，**只在关注行真正新建的那个分支**（即与「两端计数 +1」同一分支）`events.publishEvent(new UserFollowedEvent(...))`：
   - 幂等重复关注（行已存在）→ 不发；
   - 被拒（关注自己 422 / 我拉黑了对方 409 `follow-blocked` / 对方不存在 · 注销 · 封号 404 / 限流 429）→ 不发；
   - **对方拉黑了我** → 照常建行、照常发事件（D-4），由通知侧抑制（AC2.3），`FollowService` 里**不判**接收方隐藏关系，避免把「被拉黑」泄露到关注结果上（NFR2）。
3. 取关、拉黑导致的取关（Story 1.2 `UserHideRelationService.block`）、注销删关系 → **一律不发事件**（FR-140.12）。
4. 事件在 `FollowService` 的事务内发布，通知监听器 `AFTER_COMMIT` 后才执行；关注事务回滚则不发通知。

**AC2 — `USER_FOLLOWED` 通知** `[L0]` `[L1]`（FR-141.11 / AD-4 / D-4）
1. 新监听器 `com.tailtopia.notify.service.FollowNotifyListener`，`@TransactionalEventListener` 消费 `UserFollowedEvent`。
2. 发送：`notificationService.sendInteraction(followeeId, NotificationType.USER_FOLLOWED, followerId, null, String.valueOf(followerId), null, null, null)`——不聚合、`comment_id` / `variant` 为空、每次都推送（无去抖）；推送标题用 `notify.tpl.followed`（「{nama} mulai mengikutimu」/「{nama} started following you」），正文空。
3. **不发**的情况（任一命中即 return，不写行、不加角标、不推送）：
   - `followerId == followeeId`（双重保险，1.1 已拒）；
   - 接收者隐藏了关注者：`hideRelations.isHidden(followeeId, followerId)`（拉黑与举报隐藏都算，与 `ContentNotifyListener.suppressed` 第一条同口径；含 D-4「B 拉黑 A，A 关注 B」）；
   - **24 小时去重**：`NotificationRepository` 新增原生查询 `existsFollowedNotificationSince(recipientId, actorId, since)` =
     `SELECT EXISTS (SELECT 1 FROM notifications n JOIN notification_actors a ON a.notification_id = n.id WHERE n.recipient_user_id = :recipientId AND n.type = 'USER_FOLLOWED' AND a.actor_user_id = :actorId AND n.created_at > :since)`，`since = now - 24h`；命中则不发（取关后再关注 24 小时内不重复通知）。
4. 被抑制的那次关注**不产生**通知行，因此不计入 24 小时去重（之后解除拉黑再关注会正常通知）。

**AC3 — 场所评论审核通过发事件（改 `PlaceCommentService.approve`）** `[L0]`（AD-9）
1. 新事件 `com.tailtopia.place.event.PlaceCommentApprovedEvent(long placeId, String placeToken, long placeCreatorId, long commentId, long commenterId, Instant approvedAt)`。AD-9 写的是 `(placeId, commentId, authorId)`，这里多带 `placeToken`（推送 / 通知的 `targetRef`）与 `placeCreatorId`（接收者），让 notify 侧**不必读 place 仓储**。javadoc 写明「不带评论正文」（场所评论通知不展示评论内容，FR-141.12）。
2. `PlaceCommentService.approve`（`place/service/PlaceCommentService.java:172-180`）在 **`approveModeration()` 返回 true 的分支内**（与 `counters.onCommentBecameVisible` 同一分支，保证幂等、重复 approve 不重发）：`places.findById(c.getPlaceId())` 取场所，`c.getAuthorId() != null` 且场所存在时 `events.publishEvent(new PlaceCommentApprovedEvent(place.getId(), place.getPublicToken(), place.getCreatedBy(), c.getId(), c.getAuthorId(), Instant.now()))`。
3. 审核未通过（`HIGH_RISK` / `DEGRADED` / 审核异常 → 留 `UNDER_REVIEW`，`PlaceCommentModerationListener.java:52-71`）→ 不调 `approve` → 不发事件 → 不通知。
4. 打卡（`PlaceCheckinService`）、收藏、照片贡献**不改**，不发任何通知。

### 为什么用事件、不在 `FollowService` 直接调 `NotificationService`

- 与现有互动通知同一范式（`ContentLikedEvent` → `ContentNotifyListener`），social 模块不依赖 notify；
- `@TransactionalEventListener`（默认 AFTER_COMMIT）保证关注事务回滚时不发；`sendInteraction` 是 `REQUIRES_NEW`，在 AFTER_COMMIT 阶段能真正提交（`NotificationService.send` javadoc :63-69 记录过用 REQUIRED 会静默丢行的事故）；
- 抑制（接收者隐藏了关注者）放在 notify 侧监听器，`FollowService` 的返回值与计数完全不受影响——被拉黑方从关注结果里察觉不到（NFR2）。

### 架构约束

- AD-4：24 小时去重查 `notifications` + `notification_actors`；接收方隐藏 actor 不发；取关 / 拉黑取关一律不发。
- AD-9：场所评论 `aggregate_key = COMMENT:PLACE:{placeId}`、`target_ref = placeToken`；既有 `suppressed` 口径沿用。
- AD-10 / D-7：场所评论推送 `notify:placecommentpush:{placeId}` 10 分钟最多一条；关注每次推送；虚拟号不推。
- 抑制只写在监听器，不写进 `NotificationService`。
- 日志只记 id 与异常类名，不记昵称 / 评论内容。
- 24 小时去重是「先查后写」，同一对用户在毫秒级内连续两次新建关注（关注→取关→关注，受 30 次 / 分钟限流）理论上可能各发一条；本 story 不为此加锁（代价与收益不对等），在 Completion Notes 如实记录。

- 不改关注接口本身的规则（Story 1.1）、拉黑联动（Story 1.2）。
