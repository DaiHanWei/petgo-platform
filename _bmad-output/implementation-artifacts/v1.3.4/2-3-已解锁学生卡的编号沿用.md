# Story 2.3: 已解锁学生卡的编号沿用

Status: ready-for-dev

> 版本 v1.3.4 · 主题 ktp · 分支 `feat/1.3.4-ktp-revamp`
> 口径优先级：`决策日志-ktp.md` > `PRD-v1.3.4-ktp.md` > `architecture-v1.3.4-ktp-delta.md` > `ui-v1.3.4-ktp.html`（均在 `_bmad-output/planning-artifacts/v1.3.4/`）
> 纯后端。前置：Story 1.1（`card_variant`、`IdCardCreateResponse.numberReused` 恒 false）、Story 2.1（`hd_unlocked_at`）、Story 2.2（归属表 + `claimNumbers`，去掉全局 UNIQUE）。

## Story

As a 已为学生卡解锁 HD 的用户,
I want 再给同一只宠物建其他卡时用同一个号,
so that 我家宠物在所有卡上都是同一个身份码。

## Acceptance Criteria

**AC1 — 沿用命中** `[L0]` `[L1]`
1. 用户有一张满足以下全部条件的「沿用来源」卡：本人（`user_id = ownerId`）、`card_type = 'STUDENT'`（任意 `card_variant`）、`hd_unlocked = true`、`card_no` 非空（且 `passport_no` 非空）、快照 `birthday` / `gender` / `pet_type` 与新卡请求值**逐项相等**。
2. 新建**任意款式**的卡（8 款任一，含其他配色学生卡与同款学生卡）且三项与来源相同 →
   - 新卡 `card_no`、`passport_no` 直接复制来源卡；**不调用** `CardNumberService.allocateCardNo` / `allocatePassportNo`（计数器不前进）；
   - `serial_id` 照常 `serialAllocation.allocate()` 新取；
   - 新卡 `hd_unlocked = false`、`hd_unlocked_at = NULL`（只共号、不共解锁）；
   - 建卡响应 `numberReused = true`（`IdCardCreateResponse`，Story 1.1 建好的字段，本 story 接真值）。
3. 归属登记照常走 `cardNumbers.claimNumbers(ownerId, cardNo, passportNo)`（Story 2.2）：号已属本人 → 通过。

**AC2 — 不命中则照常发号** `[L0]` `[L1]`
1. 三项中任一不同 → 照常发新号，`numberReused = false`。性别 `UNKNOWN` 与 `MALE` / `FEMALE` 互不相等（UNKNOWN 是一个值，PRD §3.5）。
2. 以下情况都不作为来源，照常发新号：学生卡**未解锁**；V95 前旧卡（`card_no` 为空）；已解锁的是 `KTP` / `PASSPORT` / `SIM` / `KITAS` 而非 `STUDENT`；来源卡属于其他用户。
3. 比对的是**两张卡的快照值**（来源卡 `id_cards.birthday / gender / pet_type` vs 新卡请求值），不读宠物档案当前值。

**AC3 — 多张来源取最早解锁** `[L1]`
1. 两张以上已解锁学生卡都满足条件 → 沿用 `hd_unlocked_at` 最早的那张；同刻按 `id` 最小（FR-142E.3）。
2. 来源卡 `hd_unlocked_at` 为空（理论上 Story 2.1 回填后不存在，测试夹具可能造出）排在最后（`NULLS LAST`），不致使查询报错。

**AC4 — 判定的事务与并发** `[L1]`
1. 判定在 `IdCardService.createCard` 的同一事务内完成；进入判定前先对该用户取事务级 advisory 锁 `pg_advisory_xact_lock(:ns, :uid)`（两参形式，`ns` 用本 story 新常量，`uid = (int) (ownerId % Integer.MAX_VALUE)`，照 `PetCardShareRewardChannel:153-156` 写法），随事务提交 / 回滚自动释放。
2. 同一用户并发两次建卡（三项相同、已有来源）→ 两张新卡都拿到来源卡的号、`numberReused` 都为 true；（无来源时）两张各自发到不同新号。

**AC5 — 跨用户冲突兜底** `[L1]`
1. 若沿用来的号在归属表里属于他人（数据异常，夹具造出）→ `claimNumbers` 抛错，整笔建卡回滚：不写卡、不写归属行（序列 / 计数器空耗可接受），返回 500 ProblemDetail（与 Story 2.2 一致）。

**AC6 — 前端无感** `[L0]`
1. 接口不新增字段（`numberReused` 已由 Story 1.1 定义）；列表 / 详情 `IdCardResponse` 原样返回该卡的 `cardNo` / `passportNo`。卡面、列表、付费抽屉显示该号，不提示「沿用 / 已沿用」，HD 仍需单独付费——均为现有 App 行为，本 story 不改 App（FR-142E.6）。

**AC7 — 回归** `[L0]` `[L1]`
1. 无来源用户建卡与现状完全一致（同日同物种序号递增、号格式）；宠物护照取号（`findReusableKtpPassportNo`）对共号卡行为不变（Story 2.2 已加回归，本 story 保持通过）。
2. `mvn -B clean package` 绿（L0）；L1 在本地连本分支库跑。

## Dev Notes

### 现状（改动前必读）

- `IdCardService.createCard`（`profile/service/IdCardService.java:78-91`，Story 1.1 改过校验 / 返回类型后以实际代码为准）：单事务 `serialAllocation.allocate()` → `cardNumbers.allocateCardNo(birthday, gender, petType)` → `allocatePassportNo(petType)` → `idCards.save(IdCard.snapshot(...))` → 返回。Story 2.2 在 `save` 前插入了 `claimNumbers`。本 story 在发号前插入「锁 + 查来源」，命中时跳过两个 `allocate*`。
- 编号含义（`CardNumberService.java:13-19`）：`card_no` = `TT + (生日日+性别加码) + 月 + 年后两位 + 物种码 + 序号`；`passport_no` = `TT + 物种码 + P + 签发年 + 序号`。所以「生日 / 性别 / 物种三项相同」保证复制来的号与新卡卡面信息一致（NFR2）。注意 `speciesCode` 把 `OTHER` 与 `null` 都映射为 `00`，但比对按快照**原值**，不按物种码（见「待确认」）。
- 快照字段：`IdCard.birthday`（`LocalDate`）、`gender`（`MALE/FEMALE/UNKNOWN`，V95 起建的卡恒非空，`normalizeGender` 保证）、`petType`（V95 ~ Story 1.1 之间请求未强制，存量可能为 `null`；Story 1.1 起新卡必填 `CAT|DOG|OTHER`）。
- `hd_unlocked_at`：Story 2.1 新增，`markHdUnlocked()` 首次解锁写入，存量按 D-8 回填。
- 新卡未解锁：`IdCard.snapshot(...)` 恒置 `hdUnlocked = false`（`IdCard.java:129`），无需改。
- advisory 锁先例：`SerialAllocationService:27,40`（单参全局锁 `SERIAL_ALLOC_LOCK_KEY`，`allocate()` 内部也会取——本 story 的用户锁与它是两把不同的锁，先取用户锁、再在 `allocate()` 里取号池锁，顺序固定，不会死锁）；两参按用户锁见 `share/service/PetCardShareRewardChannel.java:153-156`、`AgeCardShareRewardService.java:71,162`。
- 号码回收：`card_no` / `passport_no` 计数器单调、无回收；卡快照不删除（删档只打 `profile_deleted_at`）；所以沿用不会撞上回收号（PRD §3.5「号码回收核查结论」）。
- 测试基础：`IdCardServiceTest`（`src/test/java/com/tailtopia/profile/service/`）Mockito 单测，`CardNumberService` / `SerialAllocationService` / `IdCardRepository` 均为 mock；集成测试基类 `ApiIntegrationTest`，用 `newUser()` / `userBearer(id)` / `JdbcTemplate`。

### 来源查询（建议 SQL）

```sql
SELECT * FROM id_cards c
 WHERE c.user_id = :userId
   AND c.card_type = 'STUDENT'
   AND c.hd_unlocked
   AND c.card_no IS NOT NULL
   AND c.passport_no IS NOT NULL
   AND c.birthday = :birthday
   AND c.gender = :gender
   AND c.pet_type = :petType
 ORDER BY c.hd_unlocked_at ASC NULLS LAST, c.id ASC
 LIMIT 1
```

- 用 `=` 而非 `IS NOT DISTINCT FROM`：新卡三项在 Story 1.1 后恒非空，`=` 天然排除快照为 `NULL` 的来源。
- `passport_no IS NOT NULL` 是防御条件（V95 起两号同时写入，不会只有一个）。
- **不**按 `profile_deleted_at` 过滤：已解锁卡恒可见（`IdCardService.visible`），且 PRD 明确「同一只宠物」在系统里就靠三项一致认定（卡只挂 `user_id` 不挂档案）。见「待确认」。
- 现有索引 `ix_id_cards_user_created (user_id, created_at DESC)` 足够（单用户卡数极少），不新增索引。

### `createCard` 伪代码

```java
cardNumbers.lockOwnerForCardCreation(ownerId);
long serial = serialAllocation.allocate();
Optional<IdCard> source = idCards.findNumberSourceCard(ownerId, birthday, gender, petType);
String cardNo   = source.map(IdCard::getCardNo).orElseGet(() -> cardNumbers.allocateCardNo(birthday, gender, petType));
String passport = source.map(IdCard::getPassportNo).orElseGet(() -> cardNumbers.allocatePassportNo(petType));
cardNumbers.claimNumbers(ownerId, cardNo, passport);
IdCard card = idCards.save(IdCard.snapshot(... cardNo, passport ...));
return IdCardCreateResponse(…card…, numberReused = source.isPresent());   // 按 Story 1.1 实际落地的构造方式
```

### 架构约束

- AD-5：条件、取最早、只共号不共解锁、`serial_id` 照新取、事务内判定 + 按用户事务级 advisory 锁、不提示用户。
- AD-3（Story 2.2）：同号多卡依赖归属表，`claimNumbers` 是跨用户兜底；本 story 不得绕过它。
- 不新增接口、不新增 MQ / 缓存；日志不记号码（编码宠物生日）。

### 本 story 不做

- 不改 App（`numberReused` 的埋点 `id_card_create.number_reused` 由 Story 1.7 读响应上报）。
- 不让 KTP / 护照 / SIM / 居住证成为来源；不让沿用连带解锁 HD；不做「沿用」提示。
- 不改宠物护照取号逻辑。

### 测试

- `IdCardServiceTest`（L0，mock）：
  - 命中 → 不调 `allocateCardNo` / `allocatePassportNo`（`verify(never())`），`save` 的快照号 = 来源号，`serialAllocation.allocate()` 调用一次，响应 `numberReused = true`，新卡 `hdUnlocked = false`；
  - 未命中（`findNumberSourceCard` 返回 empty）→ 两个 `allocate*` 各一次，`numberReused = false`；
  - 调用顺序（`InOrder`）：`lockOwnerForCardCreation` → `findNumberSourceCard` → `claimNumbers` → `save`。
- 集成（L1，真库，走 `POST /api/v1/pet-profiles/me/id-cards` 建卡；来源卡用「建学生卡 + 按卡端点 PawCoin 解锁」造，或 JDBC 直接置 `hd_unlocked = true, hd_unlocked_at = …`）：
  1. 命中：KTP 新卡复制来源学生卡两个号、`numberReused = true`、`hdUnlocked = false`、`serialId` 与来源不同；同款学生卡（同 `cardVariant`）再建一张同样命中；
  2. 三项各不同：生日不同 / 性别 `UNKNOWN` vs `MALE` / 物种 `CAT` vs `DOG` 各一条 → 新号、`numberReused = false`；
  3. 来源学生卡未解锁 → 新号；
  4. V95 前旧卡（JDBC 插 `card_no = NULL` 的已解锁 STUDENT 卡）→ 新号；
  5. 已解锁的是 KTP（三项相同）→ 新号；
  6. 多张已解锁学生卡（JDBC 设不同 `hd_unlocked_at`，且让较晚解锁的那张 `id` 更小）→ 取 `hd_unlocked_at` 最早的；同刻时取 `id` 小的；
  7. 并发：已有来源时用两个线程各自 `TransactionTemplate` 调 `idCardService.createCard`（或并发两次 HTTP），`CountDownLatch` 同时放行 → 两张新卡号都等于来源号；无来源时两张号互不相同；
  8. 跨用户冲突兜底：JDBC 给用户 A 插一张已解锁 STUDENT 卡（号 X / Y，**不**登记归属），再把 `(C, X)` 登记给用户 B → A 以相同三项建卡 → 500，A 的卡数不变、归属表无 A 的 X；
  9. 来源属于他人：用户 B 有满足条件的已解锁学生卡，用户 A 三项相同建卡 → 新号。
- 集成测试需本分支专用库：本地 `DB_NAME=<新建空库> ./mvnw -B test -Dtest='IdCardServiceTest,IdCardNumberReuseIntegrationTest,IdCardEndpointIntegrationTest,PetPassportIntegrationTest'`。
