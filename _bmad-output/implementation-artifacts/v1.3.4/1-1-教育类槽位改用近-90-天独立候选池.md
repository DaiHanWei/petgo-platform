# Story 1.1: 教育类槽位改用近 90 天独立候选池

Status: review

## Story

As a 刷首页的用户,
I want 推荐里的科普内容来自近 90 天的全部科普、而不只是最近 10 天的 50 来条,
so that 我不会一两天就把科普刷完、之后反复看到同样的内容。

> 范围：**纯后端**（FR-122.1 / 122.2 / 122.5 / 122.6；AD-2）。App 与后台零改动。半衰期 720h 是 Story 1.2，抖动打散是 Story 1.3，本 story 都不碰。

## Acceptance Criteria

**AC1 — 教育池查询 + 与主池合并** `[L0]` `[L1]`
1. `ContentPostRepository` 新增 `findEduCandidatePool(boolean hasViewer, Long viewerId, Instant since, Pageable pageable)`：过滤 = 主池全部过滤（见 AC2），另加 `p.type = KNOWLEDGE AND p.createdAt >= :since`，`ORDER BY p.createdAt DESC, p.id DESC`。
2. `since = now − 90 天`（`now` 即 `generate()` 收到的那个 `Instant now`），上限 = `FeedRankProperties.eduPoolSize()`（默认 **1000**）。
3. `FeedRecommendationService.generate()` 先取主池（不变），再取教育池，**按 id 去重合并**（主池在前、教育池中主池没有的追加在后，`LinkedHashMap.putIfAbsent`），之后才套 `exclude` 过滤，合并结果作为**唯一**候选列表走后续全部流程（赞评批量聚合、装饰标签、物种、曝光衰减、限流、冷启动 P95、`engine.rank`）。
4. 场景：库中有 91 天前、60 天前、5 天前的公开 KNOWLEDGE 帖，主池只覆盖近期 → 60 天前与 5 天前的进候选，91 天前的不进。
5. `FeedRankEngine` / `AttributeTemplate` / `AttributeSchedule` / `FeedAttribute` / `RankParams` / `FeedRankScorer` **本 story 一行不改**（槽位挑选、5 级放宽、降级链、防扎堆原样）。

**AC2 — 过滤只有一份代码** `[L0]` `[L1]`
1. 把 `findRankCandidatePool` 现有 WHERE 子句（`ContentPostRepository.java` L538-546：未软删 / `PUBLISHED` / `PUBLIC` / 未被本人举报 / 作者未被本人屏蔽）原样抽成接口常量 `String RANK_POOL_FILTER`，两个查询都用 `"SELECT p FROM ContentPost p WHERE " + RANK_POOL_FILTER + ...` 拼成 `@Query`（编译期常量，注解里可用）。**不得**为教育池另写一份过滤。
2. 一条 60 天前的科普，作者被当前用户屏蔽 / 被当前用户举报 / 已软删 / `PRIVATE` / 状态 `UNDER_REVIEW`（举报下架）→ 不进教育池，也不出现在该用户 ALL Tab 任何一页。
3. L0 守卫：反射读两个方法的 `@Query.value()`，断言都 `contains(ContentPostRepository.RANK_POOL_FILTER)`。

### JPQL（写死）

```java
/**
 * 推荐序候选池的过滤口径 —— 主池 {@link #findRankCandidatePool} 与教育池 {@link #findEduCandidatePool} 共用
 * （V1.3.4 FR-122.2 / NFR3：任何池子都不得绕过）。🔴 不要复制一份给新池子，加池子就拼这个常量。
 */
String RANK_POOL_FILTER = """
        p.deletedAt IS NULL
          AND p.status = com.tailtopia.content.domain.PostStatus.PUBLISHED
          AND p.visibility = com.tailtopia.content.domain.ContentVisibility.PUBLIC
          AND (:hasViewer = false
               OR NOT EXISTS (SELECT 1 FROM ContentReport r
                              WHERE r.postId = p.id AND r.reporterId = :viewerId))
          AND (:hasViewer = false
               OR NOT EXISTS (SELECT 1 FROM UserHideRelation h
                              WHERE h.holderId = :viewerId AND h.targetId = p.authorId))
        """;

@Query("SELECT p FROM ContentPost p WHERE " + RANK_POOL_FILTER
        + " ORDER BY p.createdAt DESC, p.id DESC")
List<ContentPost> findRankCandidatePool(@Param("hasViewer") boolean hasViewer,
        @Param("viewerId") Long viewerId, Pageable pageable);

/** 教育类独立候选池（V1.3.4 FR-122.1）：近 {@code since} 起的全部 KNOWLEDGE 公开内容，过滤与主池同一份。 */
@Query("SELECT p FROM ContentPost p WHERE " + RANK_POOL_FILTER
        + " AND p.type = com.tailtopia.content.domain.ContentType.KNOWLEDGE"
        + " AND p.createdAt >= :since"
        + " ORDER BY p.createdAt DESC, p.id DESC")
List<ContentPost> findEduCandidatePool(@Param("hasViewer") boolean hasViewer,
        @Param("viewerId") Long viewerId, @Param("since") Instant since, Pageable pageable);
```
`Instant` 已在该文件 import（L7）。仓库里此前没有「常量拼 `@Query`」的先例，这是本 story 首次引入；JPQL 拼错只有 Spring 上下文启动时才暴露（L1），L0 只能保证编译通过 + AC2.3 守卫。

### `generate()` 改法（写死）

```java
List<ContentPost> pool = posts.findRankCandidatePool(viewerId != null, viewerId,
        PageRequest.of(0, props.candidatePoolSize()));
// V1.3.4 FR-122：教育类槽位另取近 90 天全部 KNOWLEDGE（不受主池「最近 N 条」截断），与主池按 id 合并。
List<ContentPost> eduPool = posts.findEduCandidatePool(viewerId != null, viewerId,
        now.minus(FeedRankProperties.EDU_POOL_WINDOW), PageRequest.of(0, props.eduPoolSize()));
Map<Long, ContentPost> merged = new LinkedHashMap<>();
for (ContentPost p : pool) { merged.putIfAbsent(p.getId(), p); }
for (ContentPost p : eduPool) { merged.putIfAbsent(p.getId(), p); }
List<ContentPost> usable = merged.values().stream()
        .filter(p -> !exclude.contains(p.getId())).toList();
```
（`java.util.LinkedHashMap` 需 import。）合并顺序不影响结果：引擎按「分数降序 + id 升序」排序（`FeedRankEngine.java` L121-122），输入顺序无关，同种子可重放不受影响。

### 关键设计点

- **为什么教育池上界做成属性而不是常量**：生产默认 1000（FR-122.1）；集成测试上下文必须能压小——共享测试库有大量历史 KNOWLEDGE 帖，配上 Story 1.2 的 720h 半衰后它们会挤掉测试里刚造的新科普帖。90 天是产品口径、不做成属性（`EDU_POOL_WINDOW` 常量）。
- **续算排除**：`exclude`（已缓存序列 id）在合并**之后**套，保证教育池里已下发过的内容续算时同样被排掉（`extend()` L229-231 的契约）。
- **读页再过滤不变**：快照里的教育池 id 读回时照样走 `findRankableByIds`，安全规则层在读页时再兜一次。
- **冷启动 P95**：`percentile95(candidates)` 自动按合并后的池算（AD-2 已接受，P95 已配置时不生效）。
- **性能**：教育池行数 ≤ 1000，走新部分索引；赞评/标签/物种批量聚合的 IN 列表最多 2000 个 id，量级可接受。
- **已知 L1 风险（不是本 story 的 bug）**：既有 L1 测试若断言「刚造的 KNOWLEDGE 帖出现在首页第一页」，在本 story + Story 1.2 后可能因老科普竞争而变红。本地 L1 时若出现，先确认是这一原因，再在 Completion Notes 记录与处理（优先把该测试的科普帖改成在 L1 里给足互动或改到查询层断言，**不要**把 `edu-pool-size` 测试值调大或删断言）。
