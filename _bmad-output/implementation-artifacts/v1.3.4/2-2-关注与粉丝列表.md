## Story

As a 用户,
I want 查看我和别人关注了谁、被谁关注，并在列表里关注,
so that 我能发现更多值得关注的人。

## Acceptance Criteria

**AC1 — 列表接口** `[L0]` `[L1]`
1. `social/web/FollowController` 新增两个端点：
   - `GET /api/v1/users/{token}/following?cursor=` —— `{token}` 用户关注的人；
   - `GET /api/v1/users/{token}/followers?cursor=` —— 关注 `{token}` 用户的人。

2. `FollowListItem`（新 record `social/dto/FollowListItem`，2.3 推荐接口复用）字段**逐字**为：`userId`(long)、`userToken`(String)、`nickname`(String)、`avatarUrl`(String)、`deleted`(boolean)、`iFollow`(boolean)、`followsMe`(boolean)、`blockedByMe`(boolean)、`self`(boolean)。⚠️ Jackson 对 `iFollow` 这类 `is`/单字母前缀的 record 组件须显式 `@JsonProperty("iFollow")`，契约测试断言 JSON 键名就是 `iFollow`（不是 `ifollow` / `IFollow`）。
3. **分页**：keyset，排序 `user_follows.created_at DESC, <对方 user id> DESC`（following 取 `followee_id`、followers 取 `follower_id` 作 tie-breaker——表是复合主键、没有 `id` 列），每页 **20**，取 21 行判 `hasMore`。游标复用 `shared/paging/KeysetCursor`（`createdAt` + `id` = 对方 user id），对外 base64url 不透明串；首页用 `KeysetCursor.firstPage()`；**坏游标按首页处理、不报错**（同 `NotificationCenterService.parseCursor`）。
4. **关系字段相对当前查看者**（viewer）：`iFollow` = viewer→该行用户、`followsMe` = 该行用户→viewer，**整页一次**用 `FollowReader.followStates(viewerId, rowIds)` 批量取；`blockedByMe` = viewer 对该行用户存在 `source=BLOCK` 的隐藏行（只认 BLOCK，`REPORT` 不算——与 AD-4「REPORT 来源不影响关注」同口径），整页一次用 `UserHideRelationRepository.findTargetIdsByHolderAndSourceIn(viewerId, BLOCK, rowIds)`；`self` = 该行用户 == viewer。**禁止逐行查询**（NFR3），测试用 SQL 计数或 mock 调用次数钉住。
5. **游客**（无 JWT / 非 `role=USER` 的 token，判定照 `PublicProfileController.viewerId`）：四个布尔全 `false`，不发关系查询。
6. 展示字段：`nickname` / `avatarUrl` / `deleted` 一次 `AccountQueryService.findAuthorViewsWithoutTags(rowIds)`（列表不展示运营标签）；`userToken` 一次批量取（见 Dev Notes「token 批量取」）；`deleted=true` 的行 `nickname` / `avatarUrl` / `userToken` 为 null（键消失，全局 `non_null`）。
7. **主页用户解析**：`{token}` 经 `AccountQueryService.findActiveByPublicToken`；不存在 / 已注销 / 封号 → 404 `not-found`（三者不可区分）。
8. **封号用户照常列出**（不过滤 `status`；点进去由主页显示「Pengguna tidak ditemukan」）；已注销用户由 Story 1.1 注销流程删行，列表天然不含（见 Dev Notes「注销不是物理删」）。
9. 安全配置 `SecurityConfig`：两条**精确路径** `GET /api/v1/users/*/following`、`GET /api/v1/users/*/followers` `permitAll`（游客可看，与 `/users/*/profile` 同口径；**不写 `/users/**` 通配**）。
10. 拉黑相关的访问规则（主页用户与查看者之间）按 Completion Notes「待确认 1」的结论实现；结论未出前按其「默认建议」实现。

### 实现要点

**列表 SQL（native，放 `UserFollowRepository`）**
```sql
-- following：:ownerId 关注的人
SELECT f.followee_id AS user_id, f.created_at
  FROM user_follows f
 WHERE f.follower_id = :ownerId
   AND (:hasCursor = false
        OR f.created_at < :cursorTs
        OR (f.created_at = :cursorTs AND f.followee_id < :cursorId))
 ORDER BY f.created_at DESC, f.followee_id DESC
 LIMIT :limitPlusOne;
-- followers：把 follower_id / followee_id 对调
```
- 索引：Story 1.1 的 `(follower_id, created_at DESC)` / `(followee_id, created_at DESC)` 已能按序扫并在同刻组内做增量排序，够用；若 1.1 尚未落库，可建议其改为三列 `(follower_id, created_at DESC, followee_id DESC)` 让 tie-breaker 也走索引（非阻塞，见「待确认 5」）。
- 游标 `id` 存的是**对方 user id**（不是行 id）——KeysetCursor 注释所说「内部 id 只作 tie-breaker」同样成立；它是用户 id，但游标是不透明 base64 串且本就能从 `userId` 字段看到，不新增暴露面。

**token 批量取**：行需要 `userToken`。`AuthorView` 是全仓共用 record，不在本 story 给它加字段。新增 `AccountQueryService.publicTokensOf(Collection<Long>) → Map<Long, String>`（一次 `SELECT id, public_token FROM users WHERE id IN (…) AND deleted_at IS NULL`）。Story 2.1 给 Feed 下发 `authorToken` 时也需要同一能力——**先看 2.1 是否已加同义方法，有则复用、不要再加一个**。

**为什么不用 extra 传 token**：页面只拿路由里的 `userId`，用 `publicProfileProvider(userId)` 取 `userToken` / `nickname` / `self`。好处：①深链 / 进程恢复后 `extra` 会丢，路径参数不会；②标题昵称与主页同源；③被拉黑 / 注销的判定直接复用主页接口的结论，App 与服务端规则天然一致；④从主页进入时 provider 有缓存、零额外请求，从我的页进入多一次主页请求，可接受。

**常驻 vs 非常驻**：页面算出 `persistent = profile.self && tab == following`，传给 `FollowButton`（参数名以 Story 2.1 实现为准）。下拉刷新成功后按 Story 2.1 提供的方式清除本页出现过的 userId 的覆盖（AD-7「刷新数据后覆盖清除」）。
