# Story 1.3: 下拉刷新真正「换一批」——抖动系数打散

Status: ready-for-dev

## Story

As a 刷首页的用户,
I want 每次下拉刷新后首页顺序明显不同、第一条会换,
so that 「刷新换一批」名副其实。

> 范围：**纯后端，只改 `FeedRankEngine.jitterFactor()` 一处**（FR-135；AD-4）。无迁移、无字段、无接口变更；App 与后台零改动。抖动幅度（后台 `shuffle_strength`，现值 0.4）与区间 `(1 − 幅度, 1]` 不变。

## Acceptance Criteria

**AC1 — 充分打散，相邻 id 互不相关** `[L0]`
1. `jitterFactor` 改为 SplitMix64 终混（代码见 Dev Notes，写死）：`h = mix64(seed.hashCode() * 0x9E3779B97F4A7C15L ^ mix64(id))`，`rand = (mix64(h) >>> 11) * 0x1.0p-53`（∈ `[0,1)`），`factor = 1 − strength × rand`。
2. 生产代码 `FeedRankEngine.java` 中不得出现 `new Random(` / `new java.util.Random(` / `Math.random(` / `ThreadLocalRandom.`（L0 源码扫描，按正则匹配调用形式，注释里的字样不算）。
3. 统计断言（种子 `"s:fr135"`、强度 1.0、id 5000–5999 共 1000 个，取 `rand_i = 1 − factor_i`）：
   - 相邻 999 对中 `|rand_{i+1} − rand_i| < 0.001` 的对数 **≤ 10**（独立均匀期望约 2 对）；
   - 相邻对 Pearson 相关系数 `|ρ| < 0.1`；
   - id 5000 / 5001 / 5002 三个系数两两差值**不全** `< 0.001`。
4. 敏感性对照（证明测试真能抓住旧 bug）：同一测试里用旧公式 `new java.util.Random(seed.hashCode() * 1_000_003L + id).nextDouble()`（仅测试代码里出现）跑同样 999 对，`|diff| < 0.001` 的对数 **≥ 900**。

**AC2 — 离线模拟：首条种数与理想随机同量级** `[L0]`
同口径模拟（参数写死，见 Dev Notes「模拟口径」）：1000 条候选、连续刷新 50 次（候选里不含顶置与本人待审帖——它们本就不进引擎）：
- 新算法：每次刷新 `engine.rank(..., 1)` 的第一条 id；
- 理想：同一批候选、同一基础分，每次刷新用 `new java.util.Random(31L * i + 17)` 按 id 升序依次 `nextDouble()` 作 `u`，取 `argmax(base × (1 − 0.4 × u))`（同分 id 小者胜，与引擎 tie-break 一致）。
断言：`distinct(新) ≥ max(5, distinct(理想) / 2)`，且新算法中出现次数最多的那条 **≤ 25 次**（PRD 现状为 40 次）。断言失败信息里打印两边的种数与最大频次。

**AC3 — 确定性与翻页** `[L0]` `[L1]`
1. 同一 `(seed, id)` 调用两次 `jitterFactor` 结果逐位相等；同一种子两次 `engine.rank` 序列逐条一致（既有 `FeedRankEngineTest.sameSeedIsReplayable` L414-419 保持绿）。
2. 翻页不重不漏：既有 `FeedRecommendationServiceTest.pagesDoNotOverlap`（L222-248）保持绿 `[L0]`；既有 ALL Tab 翻页集成测试（`PinnedSlotIntegrationTest`、`FeedRankConfigLiveIntegrationTest`）本地回归 `[L1]`。

**AC4 — 关闭开关** `[L0]`
`strength ≤ 0` 或 `seed == null` → 恰为 `1.0`；强度 0 时带种子的排序与无种子逐位一致（既有 `zeroStrengthDisablesShuffle` L432-445 保持绿）。

**AC5 — 区间不变** `[L0]`
强度 0.4、种子 `"s:range"`、id 1–10000：所有系数 `> 0.6` 且 `≤ 1.0`；强度 1.0 时所有系数 `> 0` 且 `≤ 1.0`。

### 实现（写死）

```java
static double jitterFactor(String seed, long id, double strength) {
    if (seed == null || strength <= 0) {
        return 1.0;
    }
    // SplitMix64 终混：种子与 id 先各自充分打散再合并，任一位变化都让结果整体改变（FR-135）。
    // String.hashCode 与下面的常数运算都是规范钉死的 —— 跨 JVM、跨重启同一（种子, id）永远同一个数。
    long h = mix64(seed.hashCode() * 0x9E3779B97F4A7C15L ^ mix64(id));
    double rand = (mix64(h) >>> 11) * 0x1.0p-53;   // 53 位尾数 → [0, 1)
    return 1.0 - strength * rand;                    // ∈ (1 - strength, 1]
}

/** SplitMix64 的终混（Steele / Lea / Flood 2014）：三次 xor-shift-multiply，雪崩性好。 */
private static long mix64(long z) {
    z = (z ^ (z >>> 30)) * 0xBF58476D1CE4E5B9L;
    z = (z ^ (z >>> 27)) * 0x94D049BB133111EBL;
    return z ^ (z >>> 31);
}
```
`seed.hashCode()` 是 `int`，与 `long` 常数相乘自动提升为 `long`，无需强转。`rand < 1` 恒成立 ⇒ `factor > 1 − strength`；`rand ≥ 0` ⇒ `factor ≤ 1`。

### 关键设计点

- **为什么旧实现失效**：`java.util.Random` 的种子只做一次线性变换（`(seed ^ 0x5DEECE66D) × 0x5DEECE66D`），种子差 1 时第一个 `nextDouble` 只差约 `0x5DEECE66D / 2^48 ≈ 9e-5`；id 直接加在种子上 ⇒ id 相邻的系数几乎相同，新内容同涨同落（PRD §3.5 实测 0.4215 / 0.4211 / 0.4210）。
- **确定性是硬约束**：同一刷新内的翻页续算（`FeedRecommendationService.extend()` L232-248）与 Redis 不可用时的级别 3 实时重算（`slice()` L211-224）都依赖「同一（种子, id）永远同一系数」。
- **上线影响**：已缓存的序列快照（TTL 30 分钟）自然过期后切到新序列，无需清缓存（PRD §3.5 影响面）。抖动真正生效后，已曝光内容借抖动排到未看内容之前的概率会上升——上线后与 FR-122 教育类曝光覆盖率一并观察，重复感回升时由运营在后台下调 `shuffle_strength`（不在本 story 处理）。

### ⚠️ 已知存量问题（不是本 story 的范围，不要修、不要改测试迁就）

`FeedRecommendationService.page()` L174-183：首屏让位的顶置帖在 `consumed++` 之后才 `continue`，即被计入「已消费」；它若落在首屏窗口内，后续页从更大的 `consumed` 读起，**这条顶置帖之后不会再出现**。`PinnedSlotIntegrationTest.pinnedContentYieldsOnFirstPageOnly`（`content/web/PinnedSlotIntegrationTest.java` L149-177）断言「后续页必须出现」，结果取决于顶置帖在随机种子下排到哪里——**本就 flaky**。本 story 让抖动真正生效后，它变红的概率可能上升。
