# Story 2.3: 自己的空列表推荐关注

Status: ready-for-dev

> 版本 v1.3.4 · 主题 follow · 分支 `feat/1.3.4-follow-notify`
> 口径优先级：`决策日志-follow.md` > `PRD-v1.3.4-follow.md` > `architecture-v1.3.4-follow-delta.md` > `ui-v1.3.4-follow.html`（均在 `_bmad-output/planning-artifacts/v1.3.4/`）

## Story

As a 刚开始用的用户,
I want 我的关注列表为空时看到值得关注的人,
so that 我能快速开始关注。

- **Story 1.1**：`user_follows`、`FollowController`、`FollowReader`、关注接口。
- **Story 2.1**：`FollowButton`（`listCompact`）、`followStateProvider`。
- **Story 2.2**：`FollowListItem`（后端 record 与 App 模型）、`FollowListPage` 页面、`AccountQueryService` 批量取 token 方法、`follow_list_viewed`、`follow_` 前缀登记、l10n `followListEmptyFollowers`。

## Acceptance Criteria

**AC1 — 推荐接口** `[L0]` `[L1]`
1. `GET /api/v1/me/follow-suggestions`（写在 `social/web/FollowController`），**仅 `role=USER`**：`SecurityConfig` 加精确规则 `.requestMatchers(HttpMethod.GET, "/api/v1/me/follow-suggestions").hasRole("USER")`（理由同场所端点：controller 把 `jwt.sub` 当 `users.id`，兽医 token 的 sub 是 vetId）；游客 401。
2. 返回 `FollowSuggestionsResponse{ items: FollowListItem[] }`（新 record `social/dto/FollowSuggestionsResponse`；行复用 Story 2.2 的 `FollowListItem`，**不新增行类型**），最多 **30** 条，无分页、无游标。
3. 候选条件（FR-140.11，AD-4），全部在**同一条 SQL 的 WHERE 里**完成（不得取 30 条后在 Java 侧再剔除——会导致不足 30 条）：
   - `users.role = 'USER'`、`deleted_at IS NULL`、`enabled = true`、`status = 'ACTIVE'`；
   - 至少一条帖子满足 `visibility = 'PUBLIC' AND status = 'PUBLISHED' AND deleted_at IS NULL`；
   - 排除：自己；`user_follows` 中 viewer 已关注的人；viewer 作为 holder 存在**任意来源**（BLOCK / REPORT）`user_hide_relations` 行的人；
   - 虚拟号（`account_type = VIRTUAL`）与真人都包括，不按 `account_type` 过滤。
4. 排序：近 30 天（`content_likes.created_at >= now() - 30 天`）在该用户 **PUBLIC + PUBLISHED + 未软删** 帖子上产生的点赞数倒序；30 天内零赞的候选按「待确认 1」的次序排在后面（默认建议见 SQL 草案）。
5. 行字段：`iFollow` 恒 false、`self` 恒 false、`blockedByMe` 恒 false、`deleted` 恒 false（均由 WHERE 保证）；`followsMe` 一次 `FollowReader.followStates(viewerId, ids)` 批量取；`nickname` / `avatarUrl` 一次 `findAuthorViewsWithoutTags`；`userToken` 一次批量取（Story 2.2 的方法）。全程固定查询次数（NFR3）。
6. 查询性能：按 Dev Notes「SQL 草案与索引评估」落地；若采纳新索引，迁移 `V<yyyyMMdd_HHmm>__content_likes_created_at_index.sql`（取创建时刻；提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`）。在本地造数（≥ 5 万条点赞）后 `EXPLAIN (ANALYZE, BUFFERS)` 结果贴进 Completion Notes。

## Dev Notes

### 现状（改动前必读）

- **点赞表** `content_likes`（`petgo-backend/src/main/resources/db/migration/V10__init_content_likes.sql`）：`id, post_id, user_id, created_at`；唯一键 `(post_id, user_id)` + `idx_content_likes_post (post_id)`。**没有 `created_at` 索引**。注销不删点赞行（`V20260831_1254__init_content_post_views.sql:5`「与 content_likes 一致：账号就地匿名化、行为数据保留」）；帖子删除时物理清该帖点赞（`ContentLikeRepository.deleteByPostId`）。
- **帖子表** `content_posts`（`V4__init_content.sql`）：`author_id, status, visibility(V98), deleted_at, created_at`；索引 `idx_content_posts_author_id (author_id)`（V4:23）、`idx_content_posts_visibility_created_at (visibility, created_at DESC)`（V98）、`idx_content_posts_feed (created_at DESC, id DESC) INCLUDE (type, pet_id) WHERE deleted_at IS NULL`（V8）。`PostStatus` = `PUBLISHED / UNDER_REVIEW / AUTHOR_DEACTIVATED`。
- **获赞口径的现成先例** `content/repository/ContentLikeRepository.java:35-45` `sumLikesOnPublicPostsByAuthor`：只数 `PUBLIC + PUBLISHED + deletedAt IS NULL` 的帖、**不排除自赞、不按点赞人状态过滤**。本 story 的「近 30 天获赞」默认沿用同一帖子口径，只多一个 `l.created_at` 时间窗。时间窗写法先例 `:63-67` `countInWindow`（`l.createdAt >= :from`）。
- **用户表** `users`：`role`（USER / VET / ADMIN）、`account_type`（REAL / VIRTUAL，V82）、`enabled`、`status`（ACTIVE / DEACTIVATED）、`deleted_at`（`auth/domain/User.java:83-126`）。「对外有效」判据现成：`UserRepository.findActiveIds`（`auth/repository/UserRepository.java:28-30`，未软删 + ACTIVE）；虚拟号推送候选 `findLifecyclePushCandidates`（:137-141）多一个 `enabled = true`——推荐条件就是这两者之并加 `role = USER`。`users.published_count` 只记虚拟号种子内容（V86 注释「真实用户恒为 0」），**不能**用来判断「发过 PUBLIC 帖」。
- **隐藏关系表** `user_hide_relations`（`V101__init_user_hide_relations.sql:14-29`）：`holder_id, target_id, source`，索引 `idx_user_hide_relations_holder_target (holder_id, target_id)`。在 content 原生 SQL 里直接引用该表已有先例：`ContentPostRepository` Feed 查询的相关子查询（`content/repository/ContentPostRepository.java:462-469`，并注明「安全规则层过滤必须留在 SQL WHERE 内，挪到 Java 侧会破坏分页契约」）。
- **跨表取推荐的先例** `profile/recommend/PetRecommendationService.java:150-176`：先取候选，再 `accounts.activeIdsAmong` + `hideRelations.hiddenEitherWay` 在 Java 侧过滤。那里能这样做是因为候选池远大于展示数；本接口**硬上限 30 且要求「最多 30 个」都有效**，在 Java 侧剔除会掉到 30 以下，故改为 SQL 内过滤。
- App 侧现状见 Story 2.2 Dev Notes（拉黑列表行 / 骨架、`publicProfileProvider`、分页 controller 范本）。`AppColors.cream2` 已被拉黑页「已举报」标签使用（`blocked_users_page.dart:284`）。

### SQL 草案与索引评估

```sql
-- :viewerId 当前用户；:since = now() - interval '30 days'（应用侧传 Instant，便于测试）
WITH publishers AS (            -- 至少一条 PUBLIC 已发布帖的作者 + 最近一条公开帖时间（零赞并列时用）
    SELECT p.author_id, MAX(p.created_at) AS last_public_at
      FROM content_posts p
     WHERE p.visibility = 'PUBLIC' AND p.status = 'PUBLISHED' AND p.deleted_at IS NULL
     GROUP BY p.author_id
),
recent_likes AS (               -- 近 30 天在其公开帖上产生的赞
    SELECT p.author_id, COUNT(*) AS likes_30d
      FROM content_likes l
      JOIN content_posts p ON p.id = l.post_id
     WHERE l.created_at >= :since
       AND p.visibility = 'PUBLIC' AND p.status = 'PUBLISHED' AND p.deleted_at IS NULL
     GROUP BY p.author_id
)
SELECT u.id AS user_id
  FROM publishers pb
  JOIN users u ON u.id = pb.author_id
  LEFT JOIN recent_likes r ON r.author_id = pb.author_id
 WHERE u.role = 'USER' AND u.deleted_at IS NULL AND u.enabled = true AND u.status = 'ACTIVE'
   AND u.id <> :viewerId
   AND NOT EXISTS (SELECT 1 FROM user_follows f
                    WHERE f.follower_id = :viewerId AND f.followee_id = u.id)
   AND NOT EXISTS (SELECT 1 FROM user_hide_relations h
                    WHERE h.holder_id = :viewerId AND h.target_id = u.id)
 ORDER BY COALESCE(r.likes_30d, 0) DESC,
          pb.last_public_at DESC,      -- 并列次序：待确认 1 的默认建议
          u.id DESC
 LIMIT 30;
```

| 片段 | 走什么 | 评估 |
|---|---|---|
| `recent_likes` 的 `content_likes.created_at >= :since` | **无可用索引 → 全表顺扫 `content_likes`** | 主要成本，随点赞总量线性增长。建议新增 `CREATE INDEX IF NOT EXISTS idx_content_likes_created_at ON content_likes (created_at) INCLUDE (post_id);`——范围扫描 + index-only 拿 `post_id`，成本只与近 30 天点赞量相关；顺带让运营周报 `countInWindow`（同样按 `created_at` 取窗）受益。写放大：每次点赞多维护一棵小索引，可接受。表量级小，普通 `CREATE INDEX`（Flyway 事务内不能 `CONCURRENTLY`，与仓库既有索引迁移同做法）锁表时间可忽略。 |
| `recent_likes` 回表 `content_posts` | PK `content_posts.id` | 每条近 30 天点赞一次 PK 查找；量级 = 近 30 天点赞数，可接受。 |
| `publishers` | `idx_content_posts_visibility_created_at (visibility, …)` 或顺扫 | 结果 = 发过公开帖的作者数（几百~几千）。帖子总量万级，顺扫亦可；不建议为此单独加索引。 |
| `users` | PK | 只对 `publishers` 里的作者逐个 PK 查找。 |
| 已关注排除 | `user_follows` PK `(follower_id, followee_id)` | 精确点查，O(1)。 |
| 隐藏排除 | `idx_user_hide_relations_holder_target` | 精确点查，O(1)。 |
| 排序 + LIMIT 30 | 内存 top-N heapsort | 候选数千以内，可忽略。 |

- **结论**：不加索引时一次请求 ≈ 顺扫全量 `content_likes` + 全量公开帖聚合；推荐只在「自己的列表为空」时请求，频次低，现阶段可用。**建议加 `idx_content_likes_created_at`** 把主要成本从「全量点赞」降到「近 30 天点赞」，以 `EXPLAIN ANALYZE` 结论为准，并把是否采纳写进 Completion Notes。
- 本地基线（2026-10-12，本机 `petgo` 库，仅供量级参考，非生产）：`content_likes` 262 行、`content_posts` 13 194 行、`users` 42 928 行——本地点赞太少，评估前须造数。
- **禁止**为推荐结果加 Redis / 本地缓存（CLAUDE.md 护栏：不引通用缓存层）。
- 放置位置：native 查询放 `social/repository/UserFollowRepository`（推荐属关注功能，归 social）。它会读 `users` / `content_posts` / `content_likes` / `user_hide_relations` 四张表——这是对「social 不 join users」约束的**有意例外**，理由同 `ContentPostRepository` Feed 查询：过滤必须在 SQL 内完成才能保证「最多 30 个且都有效」。在方法 Javadoc 写明该理由；展示字段（昵称 / 头像 / token）仍经 `AccountQueryService` 批量取，不在这条 SQL 里取。
