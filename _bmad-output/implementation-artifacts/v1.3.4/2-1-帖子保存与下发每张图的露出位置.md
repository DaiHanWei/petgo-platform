# Story 2.1: 帖子保存与下发每张图的露出位置

Status: ready-for-dev

> 版本 V1.3.4 · 主题 app · Epic 2「发图不丢画面」· FR-125.4 / 125.8 · AD-5 · NFR7
> 本 story **只动后端**（迁移 + 实体 + 请求校验 + 两个响应 DTO）。App 侧读字段在 2.2、写字段在 2.4。

## Story

As a 发帖用户,
I want 我为每张图选的露出位置随帖子一起保存、并在看帖时下发,
so that 别人刷到我的帖子时看到的是我选的那一段。

## Acceptance Criteria

**AC1 — 迁移** `[L0]` `[L1]`
1. 新迁移 **`V20261012_1103__image_crop_offsets.sql`**（预分配号，不得另取），内容固定为：
   ```sql
   -- V1.3.4 Story 2.1 · AD-5：每张图在 Feed 里的露出位置（FR-125）。
   -- 形状：与 image_urls 同序等长的数组 [0.0~1.0 | null, ...]；0 = 贴起始边、0.5 = 居中、1 = 贴结束边
   --（宽图为左右、竖图为上下）。null = 该图在容差区间内 / 无需开窗。
   -- 存量行一律 NULL、不回填（NFR7：无该值即沿用居中 cover，与改动前逐像素一致）。
   -- 与 image_sizes 同一模式（V20260818_1344），不新建图片表。
   ALTER TABLE content_posts ADD COLUMN IF NOT EXISTS image_crop_offsets JSONB;

   COMMENT ON COLUMN content_posts.image_crop_offsets IS
     'V1.3.4 Story 2.1：与 image_urls 同序等长的露出位置数组 [0~1|null]。'
     '仅超出 0.75~1.78 容差区间的图有值；存量为 NULL、不回填。';
   ```
2. 不加 CHECK 约束（与 `image_sizes` 同理：JSONB 数组形状由服务层把关，见 AC3）。
3. `ContentPost` 新增字段 `imageCropOffsets`（`List<Double>`，`@JdbcTypeCode(SqlTypes.JSON)` + `@Column(name = "image_crop_offsets")`），getter / setter 照 `imageSizes` 写法；`ddl-auto=validate` 下启动不报错 `[L1]`。

**AC2 — 合法请求原样落库** `[L0]` `[L1]`
`POST /api/v1/content-posts` 请求体新增可选字段 `imageCropOffsets`（JSON 数组，元素为数字或 `null`，`@Size(max = 9)`）。当它**与 `imageUrls` 等长**、且每个非 null 元素都在闭区间 `[0, 1]` 内时：
1. 帖子创建成功（`201`，与现状相同）；
2. `content_posts.image_crop_offsets` 存的就是请求里那份数组（含 null 占位、顺序不变、数值不改写）；
3. **正常发布分支与「人工审核挂起」分支都要写**（同 `image_sizes` / @ 名单 / 打卡关联那条「挂起分支同样要写」的坑）。

**AC3 — 非法请求 422，帖子不创建** `[L0]` `[L1]`
以下任一成立 → 抛 `AppException.validation(...)`（HTTP **422**，ProblemDetail `type` = `.../validation`），**不落库、不发事件、不调三方审核**：
1. `imageCropOffsets` 非 null，且长度 ≠ `imageUrls` 长度（`imageUrls` 为 null 时按长度 0 计）——detail 固定为 `图片露出位置与图片数量不符`；
2. 任一非 null 元素 `< 0`、`> 1`、或非有限数（NaN / ±Infinity）——detail 固定为 `图片露出位置超出范围`；
3. 超过 9 个元素 → 走 DTO 的 `@Size(max = 9, message = "最多 9 张图片")`，由 `GlobalExceptionHandler.handleValidation` 出 422（既有机制）。

严格校验，**不静默丢弃**（AD-5：长度不齐说明客户端有 bug，丢了就退化为居中，用户选的位置无声消失——与 `imageSizes` 的「整组作废」刻意不同）。

**AC4 — 不带该字段照常发帖** `[L0]` `[L1]`
1. 请求不带 `imageCropOffsets`（或为 `null`）→ 正常创建，列为 `NULL`；
2. 请求带空数组 `[]` 且无图 → 视为未带，列为 `NULL`；带 `[]` 但有图 → 按 AC3.1 长度不符 422；
3. `publishTrusted`（Lark 定时发帖）与后台种子发布（`AdminContentService` / `SeedBatchPublishService`）**不读、不写**该字段（它们从不传；`publishTrusted` 路径不加任何代码）。

**AC5 — Feed 与详情下发** `[L0]` `[L1]`
1. `FeedItemResponse` 新增末位字段 `List<Double> imageCropOffsets`，`of(...)` 工厂内取 `p.getImageCropOffsets()`（库里原值，不对齐、不改写）。首页推荐 / 时间序 / 「我的发布」/ 顶置坑位（`FeedService` L332 / L392 / L462 / L508 四处都走 `FeedItemResponse.of`）因此自动带上，**调用点不改**。
2. `ContentDetailResponse` 新增末位字段 `List<Double> imageCropOffsets`，两个 `of(...)` 工厂内取 `p.getImageCropOffsets()`；`ContentDetailService.detail` 调用点不改。
3. 为 `null` 时按全局 `non_null` 省略该键；有值时元素中的 `null` 原样下发（`[0.0, null]`）。

### 关键设计点

- **为什么严格 422 而不像 `imageSizes` 整组作废**：尺寸丢了服务端还能异步兜底测量；露出位置丢了**没有任何兜底**，会无声退化为居中——用户在露出区域页的选择白做（AD-5）。新客户端是唯一写入方，长度不齐只可能是 bug，暴露出来比吞掉好。
- **不在服务端判「哪张图超界」**：服务端拿不到可靠宽高（`image_sizes` 可能是 null 待兜底）。区间内的图客户端恒传 `null`（2.4），服务端只校验形状与取值范围，不校验「该不该有值」。
- **读路径不对齐**：写入时已保证等长，读路径原样下发库值；App 侧按下标安全取（越界 / 缺失 → 居中，2.2 实现）。不新增 `alignForRead` 式的补齐（与尺寸不同：尺寸缺失有占位策略要靠下标，偏移缺失本来就等于居中）。
- **字段放 record 末位**：最少扰动既有位置参数（契约测试只需在末尾补一个实参）。
- **数值不改写**：服务端不四舍五入；客户端发送前已截到 3 位小数（2.4）。
