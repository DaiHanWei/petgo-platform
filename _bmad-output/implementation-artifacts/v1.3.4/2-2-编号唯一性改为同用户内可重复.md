# Story 2.2: 编号唯一性改为「同一用户内可重复、跨用户不可重复」

Status: review

> 版本 v1.3.4 · 主题 ktp · 分支 `feat/1.3.4-ktp-revamp`
> 口径优先级：`决策日志-ktp.md` > `PRD-v1.3.4-ktp.md` > `architecture-v1.3.4-ktp-delta.md` > `ui-v1.3.4-ktp.html`（均在 `_bmad-output/planning-artifacts/v1.3.4/`）
> 纯后端。Epic 2 第二条：去掉 `card_no` / `passport_no` 的全局唯一，为 Story 2.3 编号沿用让路，同时保留「跨用户不撞号」的兜底。

## Story

As a 系统,
I want 允许同一用户的多张卡共用一个号、同时保证不同用户的号永不重复,
so that 编号沿用可行，发号出错时仍有兜底。

## Acceptance Criteria

**AC1 — 迁移：归属表 + 去重回填 + 删全局唯一** `[L0]` `[L1]`
1. 新迁移 `V<yyyyMMdd_HHmm>__id_card_number_owners.sql`（取创建时刻；提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`），按顺序：
   - **自检**（`DO $$ … $$` 块）：分别对 `card_no`、`passport_no` 查「同一个号被不止一个 `user_id` 持有」的记录（`GROUP BY` 号 `HAVING COUNT(DISTINCT user_id) > 1`，`NULL` 不计）；有任何一条 → `RAISE EXCEPTION`，消息列出类别（C / P）、号、涉及的 `user_id`，迁移失败（理论上不会出现：V95 起两列全局 `UNIQUE`）。
   - 建表：
     ```sql
     CREATE TABLE id_card_number_owners (
         kind    CHAR(1)     NOT NULL,   -- C = 身份码 card_no；P = 护照号 passport_no
         number  VARCHAR(16) NOT NULL,
         user_id BIGINT      NOT NULL,
         CONSTRAINT pk_id_card_number_owners PRIMARY KEY (kind, number),
         CONSTRAINT ck_id_card_number_owners_kind CHECK (kind IN ('C', 'P')),
         CONSTRAINT fk_id_card_number_owners_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
     );
     ```
     （FK 与 `id_cards.fk_id_cards_user` 同为 `ON DELETE CASCADE`，号的归属与卡同生命周期；注销走匿名化不删 `users` 行，不受影响。）
   - 回填：`INSERT INTO id_card_number_owners (kind, number, user_id) SELECT DISTINCT 'C', card_no, user_id FROM id_cards WHERE card_no IS NOT NULL`；`passport_no` 同理 `'P'`。
   - `ALTER TABLE id_cards DROP CONSTRAINT uq_id_cards_card_no;`、`ALTER TABLE id_cards DROP CONSTRAINT uq_id_cards_passport_no;`
   - **`uq_id_cards_serial` 不动**（`serial_id` 仍每卡新取、全局唯一）。
   - `COMMENT ON TABLE` / 各列 `COMMENT`：同一个号只属于一个用户；同一用户多张卡可共用（Story 2.3 编号沿用）；建卡写号时登记；V95 前旧卡（两列 NULL）不登记。
   - 迁移注释记录回填自检结果（本地 / `petgo_stag`：`card_no` 非空行数、去重后登记数，`passport_no` 同）。
2. 回填后：`id_cards` 中每个非空 `card_no` / `passport_no` 在归属表里都有且仅有一行，且 `user_id` 与卡一致（集成测试断言）。
3. 不建 JPA 实体：归属表只经 `CardNumberService` 的原生 SQL 读写（`kind CHAR(1)` 映射到实体容易在 `ddl-auto=validate` 下出类型不一致）。

**AC2 — 建卡写号时登记归属** `[L0]` `[L1]`
1. `CardNumberService` 新增 `public void claimNumbers(long userId, String cardNo, String passportNo)`（默认 `REQUIRED`，加入 `IdCardService.createCard` 事务）：对两个号各执行
   - `INSERT INTO id_card_number_owners (kind, number, user_id) VALUES (:kind, :no, :uid) ON CONFLICT (kind, number) DO NOTHING`；
   - 再 `SELECT user_id FROM id_card_number_owners WHERE kind = :kind AND number = :no`；
   - 归属是本用户 → 通过（号未登记时刚登记为本用户，或本用户早已登记）；**归属是其他用户 → 抛 `IllegalStateException`**，整笔建卡事务回滚（不写卡、计数器序号作废成空洞，可接受）。
   - 参数为 `null` 的号跳过（防御；新卡两个号恒非空）。
2. `IdCardService.createCard`（现 `:78-91`）在拿到 `cardNo` / `passportNo` 之后、`idCards.save(...)` 之前调用 `cardNumbers.claimNumbers(ownerId, cardNo, passportNo)`。Story 2.3 的「沿用」分支同样经过这一步（自己的号 → 通过）。
3. 冲突时日志 `log.error` 只记 `userId`、类别（C / P），**不记号码本身与对方 user_id**（号码编码了宠物生日，按日志纪律不外泄）；响应走全局兜底 500 ProblemDetail，不外泄堆栈（发号出错属系统缺陷，与现有「序号超上限」同为 500）。

**AC3 — 发号「号是否已存在」改查归属表** `[L0]` `[L1]`
1. `CardNumberService.cardNoExists`（现 `:138-144`）改为 `SELECT EXISTS(SELECT 1 FROM id_card_number_owners WHERE kind = 'C' AND number = :no)`，**不再查 `id_cards`**，也不区分用户（任何人登记过的号都跳过，新发的号必须全新）。
2. 发号格式、计数器表 `id_card_no_counters` / `passport_no_counters`、`allocateCardNo` 的撞号循环与 9999 上限、`allocatePassportNo`（无撞号循环，计数器单调）**全部不变**。
3. 类注释（`:10-35`）里「DB UNIQUE 约束（V95）为终极兜底」改为「归属表主键 + `claimNumbers` 为终极兜底」。

**AC4 — 宠物护照取号不受影响** `[L1]`
1. `IdCardRepository.findReusableKtpPassportNo`（`:32-39`）SQL 不改。多张卡共用同一护照号时：该号一旦被 `pet_passports` 占用，`NOT EXISTS` 把所有持有它的卡一并排除，不会再被取。
2. 新增回归（`PetPassportIntegrationTest`）：同一用户两张卡 `passport_no` 相同 → 首次签发沿用该号（`source = KTP`）；再建第三张同号卡后重新走签发 → 返回已签发那本，不新建、不撞 `uq_pet_passports_passport_no`。并另起一个宠物 / 用户验证「已被占用的号」不会被取（返回 `ISSUED` 新号）。
3. `PetPassportSqlShapeTest`、`PetPassportServiceTest` 原样通过。

**AC5 — 回归** `[L0]` `[L1]`
1. 建卡现有行为不变：同日同物种序号递增（`IdCardEndpointIntegrationTest.createCardSameDaySameSpeciesIncrementsSequence`）、规则号格式（`createCardAllocatesRuleBasedNumbers`）。
2. `SerialAllocationIntegrationTest` 原样通过（`serial_id` 与 `uq_id_cards_serial` 不动）。
3. `mvn -B clean package` 绿（L0）；L1 在本地连本分支库跑。

## Dev Notes

### 现状（改动前必读）

- 全局唯一：`V95__add_id_card_numbers.sql:15-17` 建了 `uq_id_cards_card_no UNIQUE (card_no)`、`uq_id_cards_passport_no UNIQUE (passport_no)`，注释写的是「撞号终极兜底」。`NULL` 不参与唯一性（V95 前旧卡两列为 NULL）。`uq_id_cards_serial` 在 V91 `:21`。
- `CardNumberService`（`profile/service/CardNumberService.java`）：
  - `allocateCardNo`（`:49-63`）：`nextCardSeq` 用 `id_card_no_counters` 按 (WIB 登记日, 物种) upsert 取序号（行锁串行），拼号后 `cardNoExists` 查重，撞了就取下一个序号，直到 9999 上限抛 `IllegalStateException`。
  - `allocatePassportNo`（`:67-81`）：`passport_no_counters` 按 WIB 年 upsert，单调不撞，**没有**查重——撞号唯一的兜底就是 `uq_id_cards_passport_no`。删掉它之后，兜底改由归属表主键 + `claimNumbers` 承担。
  - `cardNoExists`（`:138-144`）：`SELECT EXISTS(SELECT 1 FROM id_cards WHERE card_no = :no)`。共用编号后同一个号会出现在多行，查 `id_cards` 语义上仍成立，但架构 AD-3 统一改查归属表（单行主键查找，且与兜底同源）。
  - 两个取号方法都是 `@Transactional`（REQUIRED）加入调用方事务。
- `IdCardService.createCard`（`profile/service/IdCardService.java:78-91`）：`serialAllocation.allocate()` → `allocateCardNo` → `allocatePassportNo` → `idCards.save(IdCard.snapshot(...))`。**唯一**写 `id_cards.card_no` / `passport_no` 的生产代码（已 grep 核实）。Story 1.1 会改它的参数校验与返回类型，本 story 在其基础上只插一行 `claimNumbers`。
- 宠物护照（V1.3.2）：
  - `pet_passports`（`V20260930_1208__init_pet_passports.sql`）有自己的 `uq_pet_passports_passport_no`，与 `id_cards` 同号段、同计数器（`PetPassportService` `:105-118` 先查 `findReusableKtpPassportNo`，没有再 `allocatePassportNo`；`insertIfAbsent` 撞了换新号重试一次）。
  - `ISSUED` 来源的护照号只存在 `pet_passports`，**不登记**进归属表（架构 AD-3 的归属表只管 `id_cards` 的号；计数器单调，`id_cards` 将来不会再发到同一个号）。
  - `findReusableKtpPassportNo`（`profile/repository/IdCardRepository.java:32-39`）：本人、未打删档标、建于当前宠物建档之后、有护照号、物种段一致、号未被任何 `pet_passports` 占用，取最早一张。共用后 `NOT EXISTS` 对同号的每一行都成立/不成立一致，行为不变（架构 §0 已核实）。
  - 测试夹具常绕过 `createCard` 直接 `idCards.save(IdCard.snapshot(...))`（如 `PetPassportIntegrationTest:83`）——这类卡不会进归属表，对这些测试无影响；新写的「归属」类测试必须走 `createCard` 或手工插归属行。
- 并发：同 (登记日, 物种) 的两次建卡被计数器行锁串行到提交，不会拼出同一个候选号；跨日撞号由 `cardNoExists` 跳过。不同用户在极端情况下仍撞到同一号时：PG `INSERT … ON CONFLICT DO NOTHING` 会等待对方未提交的同键插入，对方提交后本方看到冲突、`SELECT` 读到对方 `user_id` → 抛错回滚。这就是 AD-3 说的「发号出错的兜底」。
- 注销：`AuthAccountDeletionService` 对 `users` 做匿名化（`anonymizeForDeletion`），不删行；`id_cards` 也不随注销删除。归属表跟随 `id_cards` 的生命周期，无需额外清理逻辑。

### 架构约束

- AD-3：归属表 `id_card_number_owners(kind, number, user_id, PK(kind, number))`；写号 `INSERT … ON CONFLICT DO NOTHING` 再查归属，非本人抛错回滚；**不用**排他约束（需 `btree_gist` 扩展，生产库装扩展有权限与发布风险）、**不用**触发器。
- NFR2：跨用户编号不重复；NFR6：迁移时间戳命名、动约束前自检存量。
- 不引入任何缓存 / 中间件；全部在 DB 事务内完成。
- 日志不记号码（编码了宠物生日）与他人 user_id；错误走 RFC 9457，不外泄堆栈。

### 本 story 不做

- 不实现编号沿用（Story 2.3）；本 story 结束时每张新卡仍各自发新号，行为与现状一致，只是兜底从 UNIQUE 换成了归属表。
- 不把 `pet_passports` 的 `ISSUED` 号登记进归属表；不改 `findReusableKtpPassportNo`。
- 不动 `serial_id` / `uq_id_cards_serial` / `SerialAllocationService`。
