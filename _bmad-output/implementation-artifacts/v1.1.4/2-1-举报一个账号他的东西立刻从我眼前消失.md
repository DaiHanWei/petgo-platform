# Story 2.1: 举报一个账号，他的东西立刻从我眼前消失

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 2 第一个 Story（**纯后端**）。Epic 2 的地基。
> **交付**：`account_reports` + `account_report_entries` 两张表（V102）· 账号举报提交接口 · **举报即隐藏（同事务）** · 五类新枚举 · 「已举报」状态。
> ⚠️ **本 story 最大的风险是「照抄既有内容举报」**。既有 `ReportService.submit` 用两处裸 `return` 把重复举报**幂等吞掉、什么都不写**；账号举报**必须反过来**——每次都留一行明细。
> ⚠️ 举报隐藏一旦写入**永不删除**，且六处过滤自动生效——**唯一例外是主页访问仍可进入**（Story 1.1 AC7 已保证）。

## Story

As a **遇到骚扰、仿冒或恶意账号的用户**,
I want **举报这个账号并说明原因**,
so that **平台能整体处置他，同时我不用再逐条举报他的每一篇内容**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package`）· **L1**（Docker postgres 真跑）。本 story 无 L2。

### AC1 — 工单与明细两张表（L1）

**Given** 数据库已执行本 story 的迁移（**接 Story 1.1 之后的号，实际序号按执行顺序顺延**；预期 `V102`）
**When** 检查表结构
**Then** `account_reports`（工单）的 `target_user_id` **唯一**，含 `status` / `first_reported_at` / `handled_by` / `handled_at` / 时间戳
**And** `account_report_entries`（明细）含 `report_id`(FK) / `reporter_id` / `reason` / `detail` / `created_at`，索引 `(report_id, reporter_id)` 供优先级公式聚合
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md` 的「表归属总表」

### AC2 — 工单粒度 = 被举报账号（L1）

**Given** 同一个被举报账号 B 被 12 个不同用户举报，其中甲报了 7 次
**When** 查询工单
**Then** **只存在一条工单**（`target_user_id = B`）
**And** 明细表有 **18 行**（12 人中 11 人各 1 次 + 甲 7 次）
**And** 「同一举报人对同一账号只占一条工单」这条要求由本粒度**天然满足**

### AC3 — 每一次举报的类型与说明都要留（L1）

**Given** 甲第一次选「持续骚扰」，第二次选「仿冒他人」并填了补充说明
**When** 查询该工单的明细
**Then** **两次的类型都在**，第二次的说明**追加保存、不覆盖**
**And** 后台可按时间倒序取出全部明细

> ⚠️ **不得照抄既有内容举报的做法** —— `ReportService.submit` 有**两处裸 `return`**：
> ```java
> if (reports.existsByPostIdAndReporterId(postId, reporterId)) {
>     return; // 幂等：已举报过
> }
> try { reports.save(...); }
> catch (DataIntegrityViolationException e) { return; } // 并发撞唯一约束，幂等吞掉
> ```
> 照抄会让**次数、类型变化、补充说明全部丢失**，PRD 重复举报要求的第 2、3 条直接落空。
> ⚠️ 决策日志 **C-50** 曾建议「一对(举报人,账号)只存一行 + 次数累加」，**该建议已被 PRD 正文取代**（一行存不下每次的类型与说明）。

### AC4 — 五类账号维度理由（L1）

**Given** 举报提交接口
**When** 传入理由
**Then** 只接受**账号维度五类**：垃圾信息/恶意营销 · 仿冒他人 · 持续骚扰 · 发布违规内容 · 其他
**And** 落库为 `varchar` + `UPPER_SNAKE`（`AccountReportReason{SPAM, IMPERSONATION, HARASSMENT, VIOLATING_CONTENT, OTHER}`）
**And** **是新枚举、未复用内容维度的 `ReportReason`**
**And** 选「其他」时 `detail` **必填**，上限 **200 字**，不填则返回校验错误
**And** 其余四类**不接受也不要求** `detail`

> ⚠️ 既有 `ReportReason` 是内容维度五类（`ILLEGAL / MISINFO / INAPPROPRIATE / HARASSMENT / OTHER`），**与账号维度只有「骚扰」和「其他」能对上**。研发极易直接套用。

### AC5 — 举报即隐藏，同一事务（L1）

**Given** 用户 A 举报 B
**When** 提交成功
**Then** 写入工单/明细 **与** 写入一条 `source=REPORT` 的隐藏关系**在同一事务内完成**
**And** 任一失败则整体回滚，不出现「有工单没隐藏」或「有隐藏没工单」
**And** ⚠️ **若该 `(holder, target)` 已存在 `source=BLOCK` 行（先拉黑、后举报），写入 `REPORT` 行不得修改 `BLOCK` 行的任何字段**（含时间戳）—— 两条隐藏关系是彼此独立的行

> ⚠️ **这条与 Story 1.5 AC2 的排序约束是一对**：读侧钉死「排序取 `BLOCK.created_at`」，写侧钉死「举报不碰 `BLOCK` 行」，**两边都做才保证先拉黑后举报不会把条目顶到黑名单最前面**。只做一边，另一边的实现细节一变就会重新穿帮。
> ⚠️ **调用方向**：`moderation` 调 `social` 的写服务建 `REPORT` 行，**不反向依赖**（AD-8）。

### AC6 — 举报隐藏的生效范围（复用 Epic 1 机制的回归验证）（L1）

**Given** A 举报了 B
**When** 检查各处
**Then** B 的内容**不出现在 A 的首页**
**And** B 的评论**对 A 不展示**（R1）
**And** B 在 **A 的内容下**的评论**对所有人不展示**（R2，影子评论**同样因举报触发**）
**And** 来自 B 的互动通知**不再发给 A**
**And** B 的帖子详情页**对 A 返回 404**（Story 1.1 AC10）
**And** **但 A 仍可进入 B 的迷你主页**（唯一例外，闭环需要它）

### AC7 — 举报隐藏不可解除、不进黑名单页（L1）

**Given** 存在 `source=REPORT` 的隐藏关系
**When** 尝试解除或查询黑名单
**Then** **不存在任何解除该关系的接口或入口**
**And** 该关系**不出现在黑名单页**（黑名单页只收录含 `source=BLOCK` 的条目）

### AC8 — 「已举报」状态服务端持久化（L1）

**Given** A 举报过 B
**When** A 重启 App 后再查询 B 的迷你主页
**Then** 返回中带「已举报」标记，该标记**由 `source=REPORT` 行是否存在派生**，不是前端会话态
**And** 黑名单页中若该用户也在（含 BLOCK 层），同样带该标记

### AC9 — 工单被处理后再收到举报（L1）

**Given** 某工单已被运营处理（`status` 非待处理）
**When** 又有用户举报该账号
**Then** **同一条工单翻回待处理**，**不新建工单**
**And** 新的明细行照常追加
**And** 历史处置留痕**不因翻回而丢失**（留痕在 Epic 3 的处置记录表）

### AC10 — 边界（L1）

**Given** 举报提交接口
**Then** **用户不可举报自己**（目标为本人时返回校验错误）
**And** 举报行为**对被举报人完全不可见**（不发通知、不产生任何可感知变化）
**And** **不设任何自动预处置** —— 无论多少人举报、什么理由，都不会自动挂起该账号的内容
**And** 既有帖子级举报的两条自动通道**保持不变、未被改动**
**And** ⚠️ **不设任何频率限制或冷却窗口** —— 同一举报人对同一账号**可无限次举报**，每次照常落一行明细

> ⚠️ **「不设冷却」是一条主动决定，不是遗漏**（A-A23）：单个举报人对优先级分的贡献**已由公式从结构上封顶 2 分**，加冷却只会多一处逻辑、并多一处需要向用户解释的静默失败。
> **为什么必须写进 AC**：AC3 要求「每次都留一行」，研发看到「同一人可无限次写库」时，**防刷直觉几乎必然驱使他自行加一道冷却**。
> ⚠️ **与 AC11 的短窗去重不矛盾**：AC11 防的是**误触**，本条禁的是**限制用户意图**。
> ✅ **实证：既有内容举报的两条自动通道是** `ReportService.maybeApplyP0PreDisposal` —— ① `reason == ILLEGAL` 单次即触发；② `countByPostId >= P0_REPORT_COUNT_THRESHOLD`（**= 10，硬编码在 Java 里，运营改不了**）。**本 story 一行不改它们。**

### AC11 — ⚠️ 服务端防重复提交（L1）

**Given** 用户在举报抽屉点击提交
**When** 因双击穿透、或提交中的网络重试，同一举报人对同一账号在**极短窗口内**（建议 5 秒，具体值实现时定并在 Dev Notes 记录）发生重复提交
**Then** 该重复提交**视为同一次举报，不新增 `account_report_entries` 明细行**，接口返回成功（幂等）
**And** **服务端不依赖前端防连点**——Story 2.2 AC5 的「提交中禁用」照做，但服务端自身必须成立
**And** 该去重**不改变** AC3 的要求：超出窗口后的再次举报**照常追加一行**，每次的举报类型与「其他」补充说明**照常独立留存**

> ⚠️ **为什么需要这条**：拉黑侧 Story 1.1 AC3 已明写「服务端不依赖前端防连点」，**举报侧原先没有对应条款**。
> **后果不是数据错误，是污染两个直接给运营看的数字**：① AB-3D 工单展示的「12 人 / 27 次」；② **≥5 次高频阈值判定**（Story 3.1 AC4）—— 一个举报 3 次的人被双击刷到 5 次就会被计入高频加成。

### AC12 — 日志与护栏（L0）

**Given** 举报的「其他」补充说明是**用户自由文本**
**When** 记录日志
**Then** **该文本不得进入任何日志**（继承日志禁 PII 红线）
**And** 未引入任何 MQ / 缓存 / 新中间件；举报写入为同步小写
**And** `mvn -B package` 全绿

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段实证扫描。

### 🔴 最大的风险：照抄既有内容举报

**既有 `ReportService.submit` 全文（要反着做的地方）：**

```java
@Transactional
public void submit(long postId, long reporterId, ReportReason reason) {
    if (!contentService.isVisible(postId)) {
        throw AppException.notFound("内容不存在");
    }
    if (reports.existsByPostIdAndReporterId(postId, reporterId)) {
        return; // 幂等：已举报过（隐藏已成立，计数/预处置状态不变）
    }
    try {
        reports.save(ContentReport.create(postId, reporterId, reason));
    } catch (DataIntegrityViolationException e) {
        return; // 并发撞唯一约束：本次未新增，预处置交由胜出线程处理，幂等吞掉。
    }
    maybeApplyP0PreDisposal(postId, reason);
}
```

**两处裸 `return` 的后果**：同一举报人换个原因再报 = **无效**；端点仍返回 202，**用户侧完全感知不到「你已经举报过」**，前端照样弹成功态。

**➜ 账号举报必须反过来**：每次都追加一行明细、保留每次的类型与说明。**AC11 的短窗去重是唯一允许的「吞掉」，且只针对秒级误触。**

### 既有的两条自动预处置（本 story 一行不改）

```java
static final long P0_REPORT_COUNT_THRESHOLD = 10;   // ⚠️ 硬编码在 Java，不在配置表，运营改不了

private void maybeApplyP0PreDisposal(long postId, ReportReason justReported) {
    boolean legalReport = justReported == ReportReason.ILLEGAL
            || reports.existsByPostIdAndReasonType(postId, ReportReason.ILLEGAL);
    long count = reports.countByPostId(postId);
    if (legalReport || count >= P0_REPORT_COUNT_THRESHOLD) {
        contentService.applyReportHoldIfPublished(postId);
    }
}
```

① `ILLEGAL` **单次即触发**；② 唯一举报人数 ≥ 10。**或**关系。命中 → `PUBLISHED → UNDER_REVIEW` + 写 `report_hidden_at`，**内容不删**。

**➜ 账号举报零自动预处置（AC10）**，且**这两条继续只作用于内容举报**。

### ⚠️ `MiniProfileResponse` 加「已举报」字段的陷阱（AC8）

```java
public record MiniProfileResponse(
        String nickname, String avatarUrl, String signature,
        long postCount, boolean isDeactivated) {}
```

全局 `spring.jackson.default-property-inclusion: non_null`。
**新增一个 primitive `boolean` 会永远出现在 JSON 里**（primitive 不为 null）→ **游客响应体的 key 集合就变了**，而 Story 1.1 AC6 要求「游客行为一字不变」，既有 L1 测试 `MiniProfileControllerEndpointTest` 有 3 条断言守着。

**➜ 必须用装箱 `Boolean` 且游客时置 null**（靠 NON_NULL 省略），或另想办法。

### 实体与迁移惯例（照抄 `ContentReport` / `V91__init_id_cards.sql`）

- **无 `BaseEntity`、无 `@MappedSuperclass`、无 `@EnableJpaAuditing`**（全仓零命中）
- 时间戳自写 `@PrePersist` / `@PreUpdate` + `Instant.now()`，配 DB 侧 `DEFAULT now()`
- **无 Lombok**（手写 getter）· `protected` 无参构造 + 静态工厂 `create(...)` · 外键存裸 `Long xxxId`（**不用 `@ManyToOne`**）
- 枚举 `@Enumerated(EnumType.STRING)` + 显式 `length`；时间用 `java.time.Instant`
- 迁移：`TIMESTAMPTZ` 显式写 · 主键取 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（较新惯例）· 约束前缀 `ck_`/`uq_`/`fk_`、索引 `idx_` · 全中文 `--` 注释 + 文件头块注释
- `Instant` → JSON **ISO-8601 字符串**
