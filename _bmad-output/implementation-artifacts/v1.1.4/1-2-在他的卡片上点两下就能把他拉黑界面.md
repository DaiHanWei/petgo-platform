# Story 1.2: 在他的卡片上点两下就能把他拉黑（界面）

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第二个 Story（**纯前端 Flutter**）。服务端能力由 **Story 1.1** 提供。
> **交付**：A 泳道 4 屏（A1 / A1b / A4 / A5）+ C 泳道 4 屏（C1–C4）。
> ⚠️ **本 story 的风险在「改既有共享件」**：`showMiniProfile` 是全 App 唯一的迷你卡入口、`confirm_sheet` 是全 App 通用确认抽屉，两者都有既有调用方与回归测试。**加东西容易，不碰坏既有的难。**
> ⚠️ **一处 UI 稿写错了，别照着做**：A2 框外说明写「菜单锚在「⋯」下方」，**与决策日志 C-76 原文相反**。定案见 AC1。

## Story

As a **被某个账号打扰的 TailTopia 用户**,
I want **点开他的迷你主页卡、从右上角「⋯」里选拉黑并确认**,
so that **我不需要知道任何技术细节，两三下点击就能让他从我眼前消失**。

## Acceptance Criteria

> **验证层**：**L0**（`flutter analyze` / `flutter test`）· **L2**（模拟器视觉，本 story 主战场）。
> 云端 headless **只能跑 L0**；**L2 全部留本地**，在 Completion Notes 标注「L2 待本地验收」。

### AC1 — 迷你卡「⋯」菜单（UX-DR1，A2）（L2）

**Given** 用户点开某人的迷你主页卡
**When** 点击右上角「⋯」
**Then** 菜单**锚在卡片右上角向上弹**，浮在遮罩区
**And** ⚠️ **不向下弹** —— 向下会溢出屏幕底部并盖住头像（决策日志 C-76 原文：「试过向下弹：溢出屏幕底部且盖住头像」）
**And** **不是第三层抽屉**
**And** 卡片内容**不省略、不压暗**
**And** 菜单含「举报 / 拉黑」两项**并列、不分主次**，各带副标题（举报「TA 违反了社区规定，请平台尽快处理 TA」/ 拉黑「我不想再看见 TA」）
**And** 视觉规格逐项取自既有 `report_sheet.dart` / `confirm_sheet.dart`（UX-DR22），**无自创数值**
**And** ⚠️ **目标为当前登录用户本人时，「⋯」入口整体不渲染**（不是渲染后禁用、也不是点了报错）

> ⚠️ **UI 稿 A2 的框外说明「菜单锚在「⋯」下方」是错的**，它把自己已否决的方案写进了说明。**以本 AC 与 C-76 为准：向上弹。** L2 视觉验收时别照 A2 那句话对。
> 本 story 只接通「拉黑」项；**「举报」项的动作由 Story 2.2 接入**（纯加一项，非返工）。在此之前该项**不渲染**，避免出现点了没反应的死菜单项。
> ⚠️ 「本人不渲染」这一态 UI 稿 28 屏未画（IR-5 补入），实现时按本条处理，无需另等出图。

### AC2 — 拉黑二次确认全流程（UX-DR13/14，C1–C4）（L2）

**Given** 用户在菜单点「拉黑」
**When** 弹出二次确认
**Then** 主按钮用**危险色 `#F0425A`**（既有 `AppColors.popRed`）
**And** **头像重复出现**（确认拉黑谁比确认动作本身更重要 —— 这是刻意的，不是冗余）
**And** 文案只说「拉黑后你将不再看到 TA 的内容和评论」——**刻意不提影子评论、不提「对方不会收到通知」**（A-A27）
**And** 提交中：**选项与取消一并禁用**，抽屉不关闭
**And** 成功：**两层一并收起** + Toast「拉黑成功，请在黑名单里查看」，且**该用户的卡片已从当前 Feed 列表消失**
**And** 失败：**抽屉保持打开** + Toast「拉黑失败，请重试」，可直接再点

> 成功收起、失败保持打开，两者**行为相反是刻意的** —— 失败不该让用户重新走一遍入口。

### AC3 — ⚠️ 迷你卡三处既有行为（高风险点 R4，UX-DR4，A4 / A5）（L2）

### 📌 两个必须先定的设计决策（本 story 已定案）

#### ① `showConfirmSheet` 没有头像插槽 —— 加可选参数，不另写抽屉

**现状**（`shared/widgets/confirm_sheet.dart`）：

```dart
Future<bool> showConfirmSheet(
  BuildContext context, {
  required String title,
  String? message,
  required String confirmLabel,
  required String cancelLabel,
  IconData icon = Icons.help_outline_rounded,   // ← 只能给 IconData
  bool danger = false,
  Key? confirmKey,
  Key? cancelKey,
}) async
```

`danger: true` 会把主按钮与圆形图标底色切成 `AppColors.popRed` —— **正好是 C1 要的**。但图标位只接受 `IconData`，渲染成 60×60 圆形（底色 `accent.withValues(alpha: 0.12)`、`Icon(size: 28)`）。而 **C1 明确要求头像重复出现**（「确认拉黑谁比确认动作本身更重要」）。

**定案：给 `showConfirmSheet` 加一个可选 `Widget? leading`，为 null 时走原来的 `IconData` 路径，既有调用零影响。**
理由：另写一个平行的确认抽屉会产生两套同义视觉规格（手柄 36×4、圆角 24、内边距 22/12/22/30、主按钮 radius 14…），日后必然漂移。既有 danger 用法样板见 `content_detail_page.dart:328–338`（删除内容二次确认）。

#### ② Toast 只有底部实现，不为本 story 改共享件

**实证**：`shared/widgets/app_toast.dart` 的 `showAppToast` 挂 **root Overlay**，位置**硬编码在底部**：

```dart
final bottom = mq.padding.bottom + mq.viewInsets.bottom + 90;
return Positioned(left: 24, right: 24, bottom: bottom, child: IgnorePointer(...));
```

**全仓只有这一个 toast 实现，无顶部变体、无位置参数**，改它会影响 30+ 处调用。

**定案：C4（拉黑失败，抽屉保持打开）用既有 `showAppToast`，不改共享件。**
⚠️ **但要在 L2 验收时确认叠放关系**：toast 挂 root Overlay 所以 z 序在抽屉之上（不会被遮挡），但 `bottom + 90` 的位置可能正好落在抽屉区域上。**若视觉不可接受，回来找产品定，不要擅自改共享件。**
（这一条对应 IR 阶段记录的 W-2「C4 失败 Toast 位置未指定」—— 现在有了实证：没有顶部选项可选。）

### `showMiniProfile` 现状全貌（要改的就是这段）

```dart
Future<void> showMiniProfile(BuildContext context, WidgetRef ref, int userId) async {
  final MiniProfile profile;
  try {
    profile = await ref.read(miniProfileRepositoryProvider).getMiniProfile(userId);
  } catch (_) {
    return; // 拉取失败：静默不弹（非关键路径）      ← ⚠️ AC3 要改的就是这里
  }
  if (profile.isDeactivated) return; // 已注销：不触发迷你卡   ← 保持原样

    context: context,
    backgroundColor: AppColors.surface,
    showDragHandle: true,          // ← 系统手柄，与 report/confirm 的手搓手柄不同
    builder: (_) => _MiniProfileCard(profile: profile),
```

3. 昵称 `AppTypography.title`（18/w600）
4. `SizedBox(AppSpacing.xs = 4)`
5. 发布数 `AppTypography.caption`（13）
6. `SizedBox(AppSpacing.md = 12)`

#### 三处「按 story 定案但需要在 review 时知情」的实现决定

1. **`showConfirmSheet` 除了 `Widget? leading` 还加了 `Future<bool> Function()? onConfirm`。**
   story 只点名了 `leading`，但 AC2 要求「提交中抽屉不关闭 / 失败抽屉保持打开」——原实现点主按钮**立刻 `pop(true)`**，提交态根本无处安放。要么让共享抽屉自己持有提交态，要么另写一个平行抽屉（story 明令禁止）。故按同一思路继续加**可选参数**：为 null 时行为与改动前逐字节一致（立刻 pop(true)），既有 6+ 处调用零影响。附带：有 `onConfirm` 时 `isDismissible`/`enableDrag` 收紧为 false（请求在飞时拖走抽屉，成功/失败提示会落在没有上下文的界面上）。
2. **迷你卡外层新增的 `Stack` 用了 `fit: StackFit.passthrough`。**
   默认的 `StackFit.loose` 会把外层的紧宽度约束**放松**后再传给 `Column` —— 正是文件里那段长注释修过的「卡片缩成半屏」bug 换个位置复发。而宽度回归用例量的是更外层的 `SingleChildScrollView`，**那种情况下它照样绿**（T7 预警的正是这个）。已在代码里就地写了警告注释。
3. **游客点「拉黑」走 `requireLogin`（FR-0C），不是隐藏入口。**
   story 只规定了「本人不渲染」，没说游客。选择与 `openReport` 同一门控惯例：游客照常看到「⋯」，点动作时弹强登录引导——而不是发一个注定 401 的请求。Story 2.2 往这个菜单加「举报」时可直接沿用。
