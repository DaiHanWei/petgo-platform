# Story 1.6: 只在评论区骚扰、从不发帖的人，我也能就地处理

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第六个 Story（**纯前端 Flutter**）。
> **交付**：评论区（一级评论 + 二级回复）的头像/昵称接入 `showMiniProfile`（**UI 稿 A6，1 屏**）。
> ⚠️ **本 story 是本版本最大闭环缺口的补丁** —— 影子评论 / R1 / R2 / 通知抑制**全部为评论区骚扰设计**，而举报与拉黑的发起入口原先在评论区**根本不存在**。
> ⚠️ **代码量极小（挂一个回调），但它决定了整个版本的主场景能不能用。**

## Story

As a **在评论区被某人反复骚扰的用户**,
I want **直接点评论里的头像就能弹出那张卡**,
so that **我不用等他哪天发一条帖子、再去首页把他找出来才能拉黑他**。

## Acceptance Criteria

> **验证层**：**L0**（`flutter analyze` / `flutter test`）· **L2**（模拟器视觉）。
> 云端只跑 L0；**L2 留本地**。

### AC1 — 评论区接入迷你卡（UX-DR5，A6）（L2）

**Given** 用户在内容详情页的评论区
**When** 点击**一级评论或二级回复**的头像或昵称
**Then** 弹出迷你主页卡，与首页卡片作者、详情页作者入口**完全一致**（同一张卡、同一套「⋯」菜单）
**And** **不在评论行内另设「⋯」，不使用任何滑动手势**

> **为什么这条最要紧：** 本版本的影子评论、R1、R2、通知抑制**全部是为「评论区骚扰」设计的**，而发起入口原先在评论区**根本不存在** —— 实证确认 `showMiniProfile` 在全 App 只有 `home_page.dart:190`（Feed 卡片作者）与 `content_detail_page.dart:213`（详情页作者）两个触发点。**一个只在评论区骚扰、从不发帖的账号，用户既举报不了也拉黑不了。**

### AC2 — 已注销分支复核（L2）

**Given** 评论作者已注销
**When** 用户点击其头像
**Then** **不弹卡**（NFR-8），与首页侧行为一致
**And** 不给任何 Toast（与「已拉黑」「网络失败」两种有提示的情况区分开）

> ⚠️ 这个判断此前**只在首页侧考虑过**（`masonry_card.dart:91` 有 `onTap: (item.authorDeleted || onAuthorTap == null) ? null : onAuthorTap` 的前置拦截）。**评论列表与迷你卡是两条独立的读路径**，须显式验证。
> ✅ **实证：`Comment` 模型已有 `authorDeleted` 字段**（`comment.dart:47`，`(json['authorDeleted'] ?? false) as bool`），前端有足够信息做判断，**无需后端补字段**。

### AC3 — 已隐藏用户不构成新分支但仍需判断（L2）

**Given** 评论作者已被当前用户隐藏
**When** 评论列表渲染
**Then** 其评论已被 R1 隐藏、头像根本不会出现
**And** 实现时**不因此省掉判断** —— 两条读路径独立，不得假设另一条一定生效

### AC4 — 三处入口行为一致性回归（L2）

**Given** 首页卡片作者、详情页作者、评论区头像三处入口
**When** 分别点击同一个用户
**Then** 弹出的卡片内容、菜单项、以及**已拉黑/已注销/网络失败三种不弹卡分支**表现完全一致

> **⚠️ 验收时序说明（非验收条件，不占 AC 编号）**
> **AC4 里的「已拉黑」与「网络失败」两个分支由 Story 1.2 AC3 交付**，本 story 只负责让评论区头像调用 `showMiniProfile`。
> → 本 story 的**实现**可与 1.2 完全并行（它只是给评论行挂上调用），但 **AC4 的三分支一致性回归必须待 1.2 完成后进行**。
> → **本 story 单独验收时只验 AC1 / AC2 / AC3 三条**；AC4 标记为「待 1.2 完成后回归」。**这不是本 story 的缺失。**
> ⚠️ epics「Epic 依赖关系」写的「1.2 / 1.5 / 1.6 三条前端可并行」指的是**实现可并行**，不代表**验收无先后** —— 本条即是那个例外。

### AC5 — 护栏（L0）

**Given** 本 story 的实现
**Then** 未新增第三方依赖、未新增 l10n 键（复用既有）
**And** 未改 `showMiniProfile` 本身（那归 Story 1.2）
**And** `flutter analyze` / `flutter test` 全绿

**评论列表未接入** —— `comment.dart` 已有 `authorId` / `authorDeleted` 字段但从未调用 `showMiniProfile`。**与 PRD §3.1 的核查结论一致。**

**➜ 本 story 就是把这个调用挂上去，代码量极小。**

### 已注销用户的渲染惯例（照抄这三步）

`content_detail_page.dart:175-215`（最完整）：

```dart
final name = detail.authorDeleted ? l10n.feedDeletedUser : (detail.authorNickname ?? l10n.feedDeletedUser);
...
LetterAvatar(
  url: detail.authorDeleted ? null : detail.authorAvatarUrl,
  name: name,
  deleted: detail.authorDeleted,
  size: 36,
),
...
// 作者点击触发迷你卡（Story 3.8）：注销作者不可点（NFR-8）。
if (detail.authorDeleted) return row;
return GestureDetector(
  key: const ValueKey('detailAuthorRow'),
  onTap: () => showMiniProfile(context, ref, detail.authorId),
  child: row,
);
```

`LetterAvatar` 的 `deleted: true` 渲染默认 person 图标而非首字母（`letter_avatar.dart:38-46`）。

**评论侧已有同款处理**：`comment_section.dart:228` 有一行同样的 `name` 三元兜底，且 `_canDelete` 里 `!c.authorDeleted` 参与判定（152-157 行）。**➜ 本 story 只需补「点击手势」这一步。**

l10n 键 **`feedDeletedUser`** 已存在（id: `Pengguna terhapus` / en: `Deleted user`），**复用即可，不新增键**。

---

### `showMiniProfile` 内部还有第二道防线

```dart
if (profile.isDeactivated) return; // 已注销：不触发迷你卡
```

所以即使前端漏判，服务端返回 `isDeactivated=true` 时也不会弹卡。**但不要因此省掉 AC2 的前端判断** —— 漏判会让用户点了之后经历一次无谓的网络往返再什么都不发生，体验上与「网络失败」不可区分。

---

### ⚠️ 一处待确认：评论区拉黑成功后，列表怎么刷新

Story 1.2 会把 `showMiniProfile` 改为带 `{VoidCallback? onBlocked}` 回调，Feed 与详情页两处分别做「移除该作者卡片」。

**但评论区拉黑成功后该怎么办，PRD / UI 稿 / epics 都没写**：
- 被拉黑者的评论会被 R1 隐藏（Story 1.3 服务端已保证），但**那是下次拉取时**；
- 当前这一屏的评论列表**不会自动消失**。

**候选处理**：① 刷新评论列表（`ref.invalidate` 评论 provider）；② 乐观移除该作者的评论行；③ 什么都不做，等用户自己下拉。

**本 story 倾向 ①（刷新评论列表）** —— 与 Story 2.3「举报后立即兑现在当前屏」的产品取向一致，且实现最简单、无乐观状态一致性风险。
⚠️ **但这属于 PRD 未定义的行为，实现前请与产品确认一次。** 若产品选 ③，也要在 story 的 Completion Notes 里记下来，避免日后当 bug 报。
