# Story 1.1: 拉黑一个人，他的帖子立刻从我首页消失（服务端）

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第一个 Story（**纯后端**）。**本版本唯一的硬串行项**——Epic 1 其余 5 条、Epic 2 全部都建立在本 story 交付的表、模块与只读端口之上。
> **交付**：`user_hide_relations` 表（V101）· `com.tailtopia.social` 模块 · **唯一对外只读端口** · 拉黑/解除接口 · Feed 过滤 · 主页访问服务端拦截。
> ⚠️ **界面在 Story 1.2**，两条一起才构成用户可用的完整体验。**本 story 的验收走接口层**（Story 1.2 交付后再做端到端 L2 回归）。
> ⚠️ **本 story 的风险不在代码量，在两处"写反了照样能跑"**：AC7 的主页拦截**只认 `source=BLOCK`**（写成"存在隐藏关系即拦"会当场打死 FR-58 闭环）；AC2 的只读端口**必须提供两种查询**（少提供一种，研发就会拿"存在任意隐藏"去拦主页）。这两处编译能过、单测也能过，只有按 AC 逐条验才发现得了。

## Story

As a **被某个账号打扰的 TailTopia 用户**,
I want **系统记住「我不想看见这个人」，并让他的内容从我的首页消失、他的主页我也进不去**,
so that **我的屏蔽是真的生效的，而不是只在界面上做做样子、换个入口就能绕过（FR-94 生效范围第 1/4 条）**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package`，静态与护栏）· **L1**（Docker postgres 真跑，落库与接口行为）· **L2**（模拟器视觉，本 story 无）。
> 云端 headless 只跑到 L0 绿灯，**L1 全部留本地**，在 Completion Notes 标注「L1 待本地验收」。

### AC1 — 隐藏关系落库（L1）

**Given** 数据库已执行本版本首个迁移（**Flyway 从 V101 起**，序号按实际执行顺序单调分配）
**When** 建立一条隐藏关系
**Then** `user_hide_relations` 表存在且含 `holder_id` / `target_id` / `source`(BLOCK|REPORT，varchar + UPPER_SNAKE) / `created_at` / `updated_at`(`timestamptz`, UTC)
**And** 唯一索引是**三元 `(holder_id, target_id, source)`**，不是二元
**And** 另有查询索引 `(holder_id, target_id)` —— 供四处 `EXISTS` 走索引（架构 §4）
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md` 的「表归属总表」，创建者标注为本 story

### AC2 — 模块边界与只读端口（L0）

**Given** 新建的社区关系模块 `com.tailtopia.social`
**When** 其他模块需要判断隐藏关系
**Then** 该模块**只对外暴露一个只读端口**，且该端口提供**两种**查询：「存在任意隐藏」与「**存在主动拉黑**」
**And** `content` / `notify` / `auth` 三侧**只依赖端口接口，不得引用其仓储**
**And** 端口接口放在**提供方** `social.read`（**有意偏离** `ViolationCountReader` 把接口放消费方的既有先例，理由：本次有三个消费方，照搬会产出三份同义接口 —— AD-8）
**And** 静态检查通过：仓储类未被模块外任何 import

> ⚠️ **少提供「存在主动拉黑」这一种查询，研发就会拿「存在任意隐藏」去拦主页，直接打死 FR-58 的闭环**（见 AC7 与风险点 R1）。这不是理论风险——端口只给一种查询时，AC7 的正确实现根本无从写起。

### AC3 — 拉黑与解除的接口行为（L1）

**Given** 当前登录用户 A 与目标用户 B
**When** A 调用 `POST /api/v1/me/blocked-users` 拉黑 B
**Then** 建立一条 `source=BLOCK` 的隐藏关系并返回成功
**And** **重复拉黑幂等**：不报错、不新增记录、**不刷新拉黑时间**（避免反复点击把自己顶到列表最前）
**And** `DELETE /api/v1/me/blocked-users/{userId}` **只删除 `BLOCK` 行**；重复解除**静默成功**
**And** **服务端不依赖前端防连点**（前端另做，但服务端自身幂等）
**And** **A 不可拉黑自己**：目标为本人时返回校验错误

### AC4 — 幂等只在同源之间生效（L1）

**Given** A 与 B 之间**已存在 `source=REPORT` 的隐藏关系**
**When** A 发起主动拉黑
**Then** **照常新增一条 `source=BLOCK` 记录**（不被幂等吞掉），两条并存
**And** A 出现在黑名单页中

> ⚠️ 写成二元唯一键或「已存在隐藏就跳过」，会让用户点了拉黑、Toast 说「请在黑名单里查看」、去了却找不到人（C-91）。

### AC5 — 首页过滤（L1）

**Given** A 已拉黑 B，且 B 有多条已发布内容
**When** A 请求首页 Feed
**Then** B 的内容**不出现在任何一页**
**And** 该过滤**写在 `findFeed` 的 JPQL `WHERE` 内**，不是取回后在 Java 侧 filter（AD-5）
**And** 既有的「排除本人已举报的帖」子查询**原样保留、未被改写或合并**（AD-9）
**And** 新增条件**照抄既有的 `hasViewer` 布尔标志门控形状**，不得另起一种判空写法（见 Dev Notes「42P18 陷阱」）
**And** 每页仍返回满额条数（过滤后凑够 N），**不出现近乎空白的页**
**And** 游客（未登录）请求 Feed 时行为**完全不变**

### AC6 — 主页访问服务端拦截（L1）

**Given** A 已**主动拉黑** B
**When** A 请求 `GET /api/v1/users/{B}/mini-profile`
**Then** 返回 **403** + RFC 9457 ProblemDetail，`type` = `https://petgo/errors/blocked-user`
**And** 响应中**不含 B 的昵称、头像、签名、发布数等任何展示字段**（AD-11：「200 + 标记字段」等于拦了一半）
**And** 该端点**保持 `permitAll`**（`SecurityConfig` 那行不动），**游客请求行为完全不变**——响应体的 key 集合、状态码一字不改
**And** 登录用户的身份经 `@AuthenticationPrincipal Jwt` 解析，照抄 `ContentDetailController.viewerId(Jwt)` 的**返回 `Long`、游客 null、异常吞掉不抛 401** 模式

> **状态码取 403（本 story 定，架构只定了「专用 type」未定 status）**：语义是「你屏蔽了这个人」而非「这个人不存在」，且**不构成枚举泄漏**——能触发该分支的前提是调用者自己建立过拉黑关系，他本就知道对方存在。前端按 `type` 分流，不依赖 status。
> ⚠️ **不要用「200 + 新增布尔字段」的做法**，除了违反 AD-11，还有一个具体原因见 Dev Notes「Jackson NON_NULL 陷阱」。

### AC7 — ⚠️ 拦截只认主动拉黑（高风险点 R1）（L1）

**Given** A **只举报过** B（存在 `source=REPORT`，不存在 `BLOCK`）
**When** A 请求 B 的迷你主页接口
**Then** **照常返回卡片数据、不拦截**

> ⚠️ 把条件写成「存在隐藏关系即拦」会一并把举报隐藏拦掉——「已举报」状态无处显示、重复举报无入口，**FR-58 闭环当场作废**。
> **这是全版本唯一需要区分 `source` 的地方**（架构「六处生效点」图）。其余五处一律不区分。

### AC8a — 被拉黑方一侧的「仍然可以」（AD-20，防止做成双向隔断）（L1）

**Given** A 已拉黑 B
**When** 检查 B 一侧的行为
**Then** B **仍可正常查看** A 的内容、主页、对外分享 H5 页
**And** B **仍可对 A 的内容点赞**，点赞**照常写入、照常计入点赞数、不做逐人扣减**
**And** B **收不到任何通知、看不到任何标记**
**And** B 自己发的帖对第三方可见性**完全不变**

### AC8b — 统计与历史数据一概不动（L1）

**Given** A 已拉黑 B
**When** 检查数据侧
**Then** A 的曝光/浏览/点赞统计**不因拉黑扣减**
**And** 拉黑**不回溯清理**已产生的数据（此前的赞与互动记录保留不动）
**And** **后台不展示「被拉黑数」**，该数字不作为任何风控或运营处置依据

### AC8c — 适用范围的四条边界（L1）

**Given** 拉黑能力已上线
**When** 检查其作用范围
**Then** **运营虚拟账号（种子内容作者）同样可被拉黑，不做豁免**
**And** 拉黑关系**不参与兽医问诊的匹配/展示逻辑**
**And** 未登录游客与对外分享 H5 访客页**不做拉黑过滤**
**And** 拉黑数量**不设上限、不设频次限制**

> ⚠️ **AC8a / AC8b / AC8c 须各自独立验收、分别签字，不得合并勾选。** 这三条分散在点赞、通知、统计、问诊、游客视图五条完全不同的代码路径上——它们的存在理由是**防止研发按业界常见的 Block 语义做成双向隔断**，这是本版本产品语义最反直觉的一处。

### AC9 — 通用规则：凡展示他人内容的位置一律套用，不做逐场景例外（L0）

**Given** 隐藏过滤属**安全规则层**（只升不降、不可绕过 —— 架构 S1）
**When** 本 story 建立该过滤能力
**Then** 在只读端口与相关代码处**显式声明这条通用规则**：**凡是向用户展示他人内容的位置，一律套用同一层隐藏过滤**
**And** 若某个运营干预位（顶置位、推荐位等）命中被隐藏作者，则对该用户**视为该位为空**，按该功能自身已定义的「位为空」回退逻辑处理——本版本**不为其单独选替补内容、也不定义该功能本身**
**And** 本版本上线时平台**尚无此类运营位、也无用户搜索能力**，该规则**不触发**，但不得因此省略声明
**And** 该规则同步登记到 `CROSS-STORY-DECISIONS.md`，供后续版本新增内容列表时对照

> ⚠️ 这条是 FR-94 生效范围**第 2 条与第 5 条**的落点。不写成通用规则而逐场景处理，**漏一处等于拉黑白拉**。
> **跨版本待办（不阻塞本版本）**：V1.1.6 的 FR-68 顶置坑位实现时须接上本规则，已记入 1.1.6 查漏补做清单 A-1。

### AC10 — 内容详情页同样不可达（L1）

> **📌 本条为 CS 阶段代码实证新增，非 epics 原文** —— 依据是 AC9 已声明的通用规则 + 架构 AD-9 的 Binds（「`findFeed` 的 WHERE 构成；**内容详情对举报人的 404 判定**」）。详细论证见 Dev Notes「为什么必须加 AC10」。

**Given** A 已隐藏 B（**主动拉黑或举报，两种来源都算**——本条不区分 source）
**When** A 通过任意路径直达 B 某条帖子的**详情接口**（外部分享链接 / 推送深链 / 历史通知记录 / 手输 id）
**Then** 返回与既有「已举报该帖」完全一致的**统一 404**，复用同一句防枚举文案（`GONE_DETAIL`）
**And** 实现**复用既有的「取回后 exists 检查再抛 404」模式**，不改为 SQL 子查询（详情路径与列表路径的这处不对称是既有的刻意设计，注释已写明防枚举理由，**不要顺手"统一"掉**）
**And** 游客（未登录）请求详情时行为**完全不变**

### AC11 — 护栏（L0）

**Given** 本 story 的全部实现
**When** 静态检查与评审
**Then** **未引入任何 MQ / 缓存层 / 新中间件**；隐藏关系**每次查库、走唯一索引**（AD-18 明确：OQ-A5 原文提的「避免每次列表查询回表」**不构成引缓存的理由**）
**And** `spring.jpa.hibernate.ddl-auto` 仍为 `validate`，schema 全部归 Flyway
**And** 日志中**不出现**用户昵称等 PII、不出现令牌与签名 URL
**And** 无定时任务、无 `@Async`（拉黑与举报均为同步小写）
**And** `mvn -B package` 全绿

### 📌 实证结论：三处直接改变实现方式的发现

> 以下均为 CS 阶段扫 `petgo-backend` 实测所得，**不是文档推演**。

#### ① `findFeed` 是 JPQL，且所有 viewer 条件都被一个布尔标志门控（42P18 陷阱）

`content/repository/ContentPostRepository.java` 的 `findFeed` 是 **JPQL 文本块**，子查询写的是**实体名** `ContentReport r` 而非表名。既有举报过滤原文：

```java
AND (:hasViewer = false
     OR NOT EXISTS (SELECT 1 FROM ContentReport r
                    WHERE r.postId = p.id AND r.reporterId = :viewerId))
```

`viewerId` 是**装箱 `Long`、游客传 `null`**，但**从不裸判空**——每个碰 `:viewerId` 的子句都由独立的 `@Param("hasViewer") boolean hasViewer` 门控。方法 Javadoc 写明了原因：

> 用布尔标志而非裸 `:cursorTs IS NULL`：后者令 PG 无法推断 NULL 参数类型（**42P18 could not determine data type**）

**➜ 本 story 新增的隐藏过滤必须照抄这个形状**，写成 `AND (:hasViewer = false OR NOT EXISTS (SELECT 1 FROM UserHideRelation h WHERE h.holderId = :viewerId AND h.targetId = p.authorId))`。另起一种判空写法 = 游客请求 500。

其余必须保持**逐字不动**的 WHERE 条件：`p.deletedAt IS NULL` · `status = PUBLISHED OR 本人 UNDER_REVIEW` · `p.visibility = PUBLIC` · `:type IS NULL OR p.type = :type` · `:requirePet = false OR p.petId IS NOT NULL` · 游标三段式。排序 `ORDER BY p.createdAt DESC, p.id DESC`。

**过滤 100% 在 JPQL 里，Java 侧零 `filter`**（`FeedService.loadFeed` 取 `PAGE_SIZE + 1 = 21` 只为算 `hasMore`，再 `subList` 裁掉）。**这实证了 AD-5 的「页恒满」判断，也确认 OQ-A6 是伪问题。**

**索引方向**：既有 `V52` 专门为这个相关子查询补过 **reporter 前导**索引 `idx_content_reports_reporter (reporter_id, post_id)`，理由注释写明「与 `uq_(post_id, reporter_id)` 前导列相反」。➜ 本 story 的 `idx_user_hide_relations_holder_target (holder_id, target_id)` **正是同一道理**，不能只靠三元唯一键（那个前导是 `holder_id` 正好够用，但顺序必须是 holder 前导）。

#### ② 迷你主页端点当前**完全不认调用者**，且加字段会改变游客响应体（Jackson NON_NULL 陷阱）

`auth/web/MiniProfileController.java` 现状：

```java
@GetMapping("/api/v1/users/{userId}/mini-profile")
public MiniProfileResponse miniProfile(@PathVariable long userId) {
    AuthorView author = accountQueryService.findAuthorViews(List.of(userId)).get(userId);
    if (author.deleted()) {
        return MiniProfileResponse.deactivated(); // 注销不暴露身份信息（NFR-8）
    }
    return MiniProfileResponse.of(author,
            accountQueryService.activeSignatureOf(userId).orElse(null),
            contentService.countPublishedByAuthor(userId));
}
```

它是**全仓 permitAll GET 端点里唯一一个不接 viewer 的**。要照抄的模式在 `content/web/ContentDetailController.java`：

```java
/** 登录用户 id（游客 null）。 */
private static Long viewerId(Jwt jwt) {
    if (jwt == null || jwt.getSubject() == null) { return null; }
    try { return Long.parseLong(jwt.getSubject()); }
    catch (NumberFormatException e) { return null; }
}
```

⚠️ **不要抄 `MeController.currentUserId(Jwt)`** —— 那个游客会抛 401，会把游客可读的端点变成必须登录。

**⚠️ Jackson NON_NULL 陷阱（这条决定了为什么必须走 4xx 而不是「200 + 标记字段」）**：
`MiniProfileResponse` 是 record，全局 Jackson `NON_NULL` 生效（既有测试断言 `jsonPath("$.nickname").doesNotExist()`）。**新增一个 primitive `boolean` 字段会永远出现在 JSON 里**（primitive 不为 null），于是**游客响应体的 key 集合就变了**——直接违反 AC6 的「游客行为一字不变」。走 403 ProblemDetail 分支则 DTO 一个字段都不用动。

**⚠️ 判定必须走 service 层**：全仓纪律是 `auth` 不直 join `content`、`content` 不直 join `users`，postCount 都是经 `ContentService.countPublishedByAuthor` 拿的。➜ **不要在 `MiniProfileController` 里注入 `social` 的 repository**，走 `social.read` 端口。（这正是 epics IR-6 那条 AC 关心的同一件事。）

**另一个既有行为别改**：不存在的 `userId` 返回 **200 + `isDeactivated=true`**（不是 404），是刻意的防枚举设计，既有 L1 测试有断言。

#### ③ 「封号」与「注销」是两个不同的字段，而 `isDeactivated` 指的是**注销**

| | **封号 / 运营停用** | **用户自己注销** |
|---|---|---|
| 字段 | `users.status` varchar(16) → **`UserStatus.DEACTIVATED`** | `users.deleted_at` timestamptz |
| 写入 | `User.deactivate()` / `User.reactivate()` | `User.anonymizeForDeletion(Instant)` |
| 可逆 | ✅ 可 reactivate | ❌ 不可逆（`googleSub` 置墓碑 `deleted:<id>`） |
| PII | 保留 | 擦除 + 快照到 `deleted_email` / `deleted_display_name` |
| 谁读 | **只有登录/刷新门控** `isActiveStatus()` | 所有展示投影：`activeSignatureOf()` / `toAuthorView()` |
| 对外投影 | **不投影到任何对外 DTO** | `AuthorView.deleted` → `MiniProfileResponse.isDeactivated` |

**➜ `MiniProfileResponse.isDeactivated = true` 走的是 `deletedAt`（注销）路径，与 `UserStatus.DEACTIVATED`（封号）毫无关系。** `UserStatus` 的 Javadoc 自己写了「与『删除/注销』正交」。

**当前迷你主页端点完全不看 `UserStatus`** —— 被运营封号的用户，迷你卡照常返回昵称/头像/签名/发布数。**这恰好就是 PRD 要的**（封号者在黑名单里照常展示、不做标记），本 story **不要"顺手修正"它**。

⚠️ 本 story 只碰到这个坑的边缘；**真正会做反的是 Story 1.5（黑名单渲染）与 Story 3.2（封号处置）**，架构 S3 / 高风险点 R5 说的就是那两条。

### 为什么必须加 AC10（内容详情页）

**这条是 CS 阶段代码实证新增的，epics 原文没有。** 论证如下：

1. **架构 AD-9 的 Binds 写了两处**：「`findFeed` 的 WHERE 构成；**内容详情对举报人的 404 判定**」。但 AD-9 的 Rule 三条**只讲 findFeed**，内容详情一个字没落实——这是架构自身的一处不闭合。
2. **代码实证：两条路径是独立的，Feed 改了详情页不会跟着生效。** `ContentDetailService.getDetail` 对"本人已举报的帖"用的是**取回后 Java 侧 `reportService.hasReported(...)` 再抛 404**，而 Feed 用的是 JPQL 子查询。这个不对称是**刻意的**（注释写明防枚举），不要"统一"掉。
3. **不加会复活 PRD §7 花一整节要消灭的那种塌陷**：
   > 举报**一条帖** → 那条帖详情页 404 打不开（既有行为）
   > 拉黑**整个人**（更重的动作）→ 他的**每一条**帖详情页照样能开

   PRD §7 的方案甲整个论证建立在「动作越重、效果越强，绝不出现更重的动作反而没反应」之上。详情页这一处正好破了它。
4. **授权来源**：本 story AC9 已声明通用规则「**凡是向用户展示他人内容的位置，一律套用同一层隐藏过滤，不做逐场景例外**」。内容详情页显然属于此列。**AC10 不是扩大范围，是把已声明的规则落到一个具体位置。**
5. **实现成本**：复用既有 `hasReported` 那一处的模式加一个判断，复用同一句 `GONE_DETAIL` 文案。
