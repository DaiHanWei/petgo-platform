## Story

As a **运营人员**,
I want **在一个列表里看到全部待处理工单、自动按轻重缓急排好序、并能筛选和检索**,
so that **我不用在三个入口之间来回切，也不用对着一堆互不可比的标记猜先处理哪个**。

### AC1 — 处置记录表（L1）

**When** 检查表结构
**Then** `account_disposals` 含 被处置账号 / 处置类型(`WARNING`|`SUSPEND`，varchar + UPPER_SNAKE) / 处置人 / 关联工单(可空) / `created_at`
**And** 索引 `(target_user_id, created_at DESC)` 供「历史处置次数」与时间倒序展示
**And** 表归属已回写 `CROSS-STORY-DECISIONS.md`

> 本 story 建表是因为工单列表要**读**它（历史处置次数）。**此时表为空、次数显示 0，属逻辑完整状态**，**写入**由 Story 3.2 接入。

### AC2 — 三类工单读时联合（L1）

**Given** **三个业务类别落在四张表上**：内容举报 `content_reports`（既有）· **账号标识字段审核 `name_moderation_records` + `avatar_reviews`（两张既有表）** · 账号举报 `account_reports`（本版本新增）
**When** 运营打开统一工单页
**Then** 一条**跨四表的联合查询**产出统一列表，**在数据库内排序分页**
**And** **未新增任何统一索引表、未双写、存量数据零回填**
**And** 各类工单的状态**仍由各自源表权威持有**
**And** **未为后台引入任何缓存**
**And** ⚠️ 账号标识字段那两张表**只取 `status = 'MANUAL_PENDING'` 的行**（自动过 / 陈旧作废本就不该进运营队列）
**And** ⚠️ 两表的**状态机与时间字段不同构，须做映射**：**违规终态 → 已处理；通过终态 → 无需处置**（见 Dev Notes「第三类的三处不同构」）
**And** ⚠️ `name_moderation_records.submitted_value` 与 `avatar_reviews.avatar_url` **可展示、但严禁进日志**

### AC3 — 工单类型三类，不留空分类（L2）

**Given** 类型筛选器
**When** 渲染
**Then** 只有**三类**：内容举报 / 用户举报 / 账号标识字段
**And** **不保留「评论举报」分类** —— 该能力至今未上线，留一个永远没数据的筛选项只会让运营以为漏了什么

### AC4 — 优先级公式（L1）

**Given** 某被举报对象的举报明细
**When** 计算优先级分
**Then** `分 = 举报人数 + 高频举报人数`；举报人数 = 举报过该对象的**不同账号数**（去重）；高频举报人数 = 其中**对该对象累计举报 ≥ 5 次**（含 5）的账号数
**And** **单个举报人对分数的贡献上限为 2 分**（1 基础 + 1 高频）
**And** 校验用例：甲报3次+乙报7次 → **3 分**；甲报5次+乙报6次 → **4 分**；10人各报1次 → **10 分**；1人报100次 → **2 分**
**And** 分数**实时计算、不落库快照**
**And** 列表按分**倒序**，同分按**最早一次举报时间升序**（先报的先处理）

### AC5 — 分数必须拆开展示（L2）

**Given** 列表每一行
**When** 渲染优先级
**Then** **同时展示 举报人数 / 举报次数 / 高频人数 / 算出的总分**，不能只给一个总分
**And** 「举报人数」与「举报次数」**并列展示**（如「12 人 / 27 次」）

> 只看次数会把「1 个人报了 27 次」当成众怒；只看人数会丢掉「同一人反复纠缠」这个信号。只给总分等于让运营对着黑盒排队。

### AC6 — ⚠️ 第三类工单没有举报人，必须显式定义分数（L1）

**Given** 账号标识字段审核工单（**没有任何举报人**）
**When** 参与统一排序
**Then** 其分数按该类工单的 `priority` 字段映射：**`HIGH → 10` / `NORMAL → 2`**
**And** 锚点取自公式自身的两个例子（10 人各报 1 次 = 10 分；1 人报 100 次 = 2 分），即 **`HIGH`（≥0.8 高置信违规）视为等同于十人举报的众怒、`NORMAL` 等同于一个纠缠的举报者**
**And** ⚠️ **`NORMAL` 不得映射成 0** —— 它是这两张表的 `DEFAULT` 值、绝大多数记录都是它，映射成 0 会让这类工单几乎全部永远沉底

> ⚠️ 不显式定义的话，公式对这类工单**恒为 0 分，会永远沉底没人看**。
> ✅ **产品已确认（2026-08-16，C-102）**，OQ-CA1 关闭。规格已回写 PRD §4.1 正文，直接按 `HIGH → 10` / `NORMAL → 2` 落两个常量。

### AC7 — 既有 P0 判定退出排序、保留自动挂起（L1）

**Given** 既有内容举报的 P0 判定
**When** 本 story 上线后
**Then** P0 判定**保留不变**（违法违规原因单次触发 / 举报人数达阈值），**仅作用于内容举报**
**And** 它只负责「**自动把帖子挂起**」这一个动作，**不再参与列表排序**
**And** 列表里**不再出现两套互不可比的优先级标记**
**And** **账号举报没有任何自动预处置**（Story 2.1 AC10 已保证），只受新公式排序影响

> ✅ **实证：这条比预想的容易** —— 举报侧的 P1/P2 **在代码里根本不存在**（`ReportQueueItem` 无 priority 字段、`admin/reports.html` 无优先级列、`AdminModerationService.queue` 纯 `created_at DESC`）。「既有 P0 退出排序」这句话的实际含义是：**它本来就没参与过排序**，本 story 只需**不把它引进来**。P0 的唯一实现是 `maybeApplyP0PreDisposal` 里的自动挂起副作用，那个**一行不改**。

### AC8 — 工单展示字段（L2）

**Given** 任一工单
**When** 展开查看
**Then** 展示 举报类型 + 举报原因
**And** 被举报对象原文/缩略图（含上下文：所属帖子、父评论等）
**And** **被举报账号的历史违规记录**（同账号历史处置次数，**含每一次警告**）
**And** **被举报账号的个性签名原文**，为空时显示「未设置」；签名取**当前值**（经既有账号查询服务读，不快照、不落工单表）
**And** 账号举报工单可展开看到**每一次举报的类型与「其他」补充说明，按时间倒序**

> **为什么签名必须在工单里**：举报「仿冒他人」「持续骚扰」时，**签名往往就是证据本身**（冒充某人的自我介绍、指名道姓的攻击）。运营不该还要再跳一步去别处看。
> ✅ 签名取数走 `AccountQueryService.activeSignatureOf(userId)`（既有方法，注销/未设置返回 empty）。

### AC9 — 筛选与检索（L2）

**Given** 统一工单页
**When** 运营需要专注处理某一类
**Then** 支持**按工单类型筛选**（三类）
**And** 支持**按状态筛选**（**待处理 / 已处理 / 无需处置**）
**And** ⚠️ 第三档用中性词**「无需处置」**（`Tidak Perlu Tindakan` / `No Action Needed`，C-103），**不叫「已驳回」**
**And** 支持**按被举报账号检索** —— 处理一条账号举报时能立刻查到「这个人之前是不是被报过、被处置过几次」

> ⚠️ **筛选不是锦上添花，是统一视图成立的前提**。三类混进一个队列、没有筛选，等于没法专注处理某一类。必须与列表同 story 交付。

### ⚠️ 第三类的三处不同构（联合查询必须处理）

两张表是「并列同构」的设计，但**对统一视图而言有三处不同**：

| # | 差异 | 处理 |
|---|---|---|
| ① **状态机不同** | name：`SCORING / AUTO_PASSED / MANUAL_PENDING / RESOLVED_PASS / RESOLVED_VIOLATION / SUPERSEDED / FAILED_TO_QUEUE`（7 值）<br>avatar：`QUEUED / AUTO_PASSED / MANUAL_PENDING / RESOLVED`（4 值） | **两表都有 `MANUAL_PENDING`** —— 这是「待处理」的共同锚点。**只取该状态的行** |
| ② **终态无直接对应** | name 有 `RESOLVED_PASS` / `RESOLVED_VIOLATION` 两个；avatar 只有 `RESOLVED`（靠 `verdict` 区分） | 三态筛选映射：`MANUAL_PENDING → 待处理`；**违规终态 → 已处理**；**通过终态 → 无需处置**。**须在实现时固化并写进注释**（✅ 语义已确认，C-103） |
| ③ **时间锚点字段名不同** | name 用 `submitted_at`；avatar 用 `created_at`（**无 `submitted_at`**） | 联合查询里各自 `AS` 成同名列，供「同分按最早时间升序」用 |

✅ **两表都有 `MANUAL_PENDING` 的部分索引**（`idx_nmr_pending_queue ON (submitted_at) WHERE status='MANUAL_PENDING'` / `idx_avr_pending_queue ON (created_at) WHERE status='MANUAL_PENDING'`），取待处理项走索引，无性能问题。

⚠️ **PII 红线**：`name_moderation_records.submitted_value`（送审名称原文）与 `avatar_reviews.avatar_url` 两列的迁移注释都写明「**严禁写入业务日志**」。统一视图**展示**它们是允许的（那正是 AC8 的「被举报对象原文」），但**日志一律不得记录**。

### ⚠️ 既有举报队列的 N+1（本 story 别照抄）

```java
private static final int QUEUE_LIMIT = 50;

public List<ReportQueueItem> queue(ReportStatus status) {
    List<ReportQueueItem> items = new ArrayList<>();
    for (ContentReport r : reportService.byStatus(status, QUEUE_LIMIT)) {
        var summary = contentService.findSummary(r.getPostId());        // ← 循环内查询
        ...
        items.add(new ReportQueueItem(..., reportService.countForPost(r.getPostId()), ...));  // ← 又一次
    }
    return items;
}
```

**一条工单一行、无分页、50 条硬上限、循环内两次查询。** V1 靠上限勉强撑住。

#### 三个值得 review 的实现判断

1. **内容举报按帖聚合，不是按单条举报行。** 旧的 AB-3A 是一条举报一行；但 AC4/AC5 说的「举报人数 / 举报次数」只有在「被举报对象」这个粒度上才有意义。所以统一视图里 `sourceId` = **post_id**。⚠️ Story 3.2/3.3 接处置动作时要知道这一点：一行工单对应的是一条帖子的**全部**举报。

#### ⚠️ AC2 的一处字面冲突，我这样解的

AC2 说「那两张表**只取 `MANUAL_PENDING`**」，AC9 又要求能按**已处理 / 无需处置**筛选、AC2 自己还给了终态映射表 —— 若真的只取 `MANUAL_PENDING`，那两个筛选档对这一类**永远是空的**，映射表也就没用了。

实现取：**只收 `MANUAL_PENDING` + 两个终态**，其余（`SCORING`/`QUEUED`/`AUTO_PASSED`/`SUPERSEDED`/`FAILED_TO_QUEUE`）一律不进队列。这样待处理队列里确实只有 `MANUAL_PENDING`（AC2 的本意：自动过的、被顶掉作废的不该出现在运营面前），而终态映射也真的有地方用。有两条用例分别钉死「自动过的不进队列」与「终态映射到正确的档」。
