# Story 3.3: 一批同类的工单能一次处理完，但不会一不小心封掉几百个人

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 3 第三个 Story（**后端 + 运营后台**）。
> **交付**：批量处置的四项边界（上限 50 / 跨类型不可批量 / 批量封号二次确认逐条列出 / 部分失败逐条回报）。
> ✅ **有一个可直接照抄的既有实现**：`/admin/reports/batch`（全仓唯一的批量入口），**事务语义完全对得上**。
> ⚠️ **但「全选 / 选中计数 / 批量确认弹窗 / 跨类型置灰」全都没有，要从零写。**

## Story

As a **面对一长串同类工单的运营人员**,
I want **勾选多条一次性执行同一个处置**,
so that **我不用逐条点一百次；同时我不会因为手滑全选就把一整个队列的人都封了**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package` / 门控测试）· **L1**（Docker postgres 真跑）· **L2**（后台页面，⚠️ 无 UI 稿基准）。

### AC1 — 单次上限 50 条（L2）

**Given** 运营勾选工单
**When** 勾选数量达到 50
**Then** **不允许再勾选更多**，或提交时被拒绝并提示上限

> 不设上限的话，全选一个长队列再点封号，可以一次封掉几百个账号。
> ⚠️ **服务端也要校验**，不能只靠前端限制（勾选框可被绕过）。

### AC2 — 跨类型不可批量（L2）

**Given** 运营勾选了第一条工单
**When** 界面更新
**Then** **其余类型的工单一律置灰不可选**

> 不同类型工单的处置对象含义不同——内容举报的处置对象是**内容**，账号举报的处置对象是**人**。
> ⚠️ **服务端同样要校验**：收到跨类型的 id 集合时拒绝整批。

### AC3 — 批量封号必须二次确认并逐条列出（L2）

**Given** 运营对多条工单批量执行**封号**
**When** 点击执行
**Then** 弹出二次确认，**弹窗内逐条列出将被封的账号**（昵称 + 被举报次数）
**And** 确认后才执行
**And** **批量警告不需要二次确认**（警告不影响用户使用，可逆性完全不同）

> ⚠️ **既有 `data-confirm` 只能弹一句纯文本 `window.confirm`，装不下逐条清单** —— 本条要用 `data-open-dialog` + `<dialog>` 模式（人工审核的拒绝弹窗是范例）。见 Dev Notes。

### AC4 — 逐条独立事务（L1）

**Given** 批量处置 N 条
**When** 执行
**Then** **每条一个独立事务**
**And** 每条同样先写处置记录再触发后果（Story 3.2 AC2）

> ✅ **既有实现的做法可直接照抄**：`AdminModerationService.batch` **不开外层事务**，经 `ObjectProvider` 自引用代理逐条调用。⚠️ **必须走自引用代理**，否则 `@Transactional` 不生效、逐条独立事务的语义就没了。

### AC5 — 部分失败逐条回报，不整批回滚（L1）

**Given** 批量 20 条，其中 18 条成功、2 条失败
**When** 执行结束
**Then** 界面**明确列出失败的那 2 条及其原因**
**And** 成功的 18 条**保持成功、不回滚**
**And** 运营可**对失败项重试**
**And** **不得静默吞掉任何失败项**

> ⚠️ **既有实现只回报数量，不回报明细**：`flash.addFlashAttribute("notice", "批量完成：成功 N 条，失败 M 条")`。
> 虽然 `BatchResult` 里**有** `List<String> failed`（每项含「工单 X：原因」），但**模板没渲染它**。**本 story 要把这份明细真正展示出来。**

### AC6 — 审计（L0）

**Given** 批量处置
**When** 每条执行
**Then** 处置记录与既有审计链路**逐条留痕**，与单条处置口径一致

> ✅ 既有做法即如此：批量**不是一条汇总审计，而是 N 条单条审计**（`takedown`/`dismiss` 内部各自调 `auditService.record`）。
> ⚠️ **注意规模成本**：`AdminAuditService.record` 内有 `chainLock.acquire()`（Postgres advisory 锁）串行化 + 链尾查询。**批量 50 条 = 50 次取锁 + 50 次链尾查询**。50 条上限下可接受，但**不要在此基础上放宽上限**。

### AC7 — 护栏（L0）

**Given** 本 story 的实现
**Then** ⚠️ CSRF 开着，批量提交必须是**真表单 POST**
**And** 未引入任何 JS 框架（admin 是原生 JS + HTMX）
**And** 新增文案已补三份 i18n properties
**And** `mvn -B package` 全绿

### ✅ 可直接照抄：全仓唯一的批量实现

**`/admin/reports/batch`** 是全仓库唯一的批量入口（grep 全部 admin 模板，只有 `reports.html` 一处 `/batch`）。

**Controller**（`AdminWebController.java:137`）：

```java
@PostMapping("/admin/reports/batch")
@PreAuthorize("hasRole('SUPER_ADMIN') or hasAuthority('content.takedown')")
public String batchReports(@AuthenticationPrincipal AdminUserDetails admin,
        @RequestParam("action") String action,
        @RequestParam(value = "reportIds", required = false) List<Long> reportIds,
        RedirectAttributes flash) {
    boolean takedown = "takedown".equals(action);
    AdminModerationService.BatchResult result = adminModerationService.batch(reportIds, takedown, admin);
    flash.addFlashAttribute("notice",
            "批量完成：成功 " + result.ok() + " 条，失败 " + result.failedCount() + " 条");
    return "redirect:/admin/reports";
}
```

**Service**（`AdminModerationService.java:142`，**事务语义是必须照抄的点**）：

```java
/**
 * 批量下架/驳回（Story 4.1 AC5）：**不开外层事务**，逐条经自引用代理调用（各自独立事务）；
 * 部分失败不影响已成功项，汇总结果回报。
 */
public BatchResult batch(List<Long> reportIds, boolean takedown, AdminUserDetails admin) {
    AdminModerationService self = selfProvider.getObject();   // ⚠️ ObjectProvider 自引用
    int ok = 0;
    List<String> failed = new ArrayList<>();
    for (Long id : reportIds == null ? List.<Long>of() : reportIds) {
        try {
            if (takedown) { self.takedown(id, admin); } else { self.dismiss(id, admin); }
            ok++;
        } catch (RuntimeException e) {
            failed.add("工单 " + id + "：" + e.getMessage());
        }
    }
    return new BatchResult(ok, failed);
}

public record BatchResult(int ok, List<String> failed) {
    public int failedCount() { return failed.size(); }
}
```

⚠️ **`self` 必须来自 `ObjectProvider<AdminModerationService> selfProvider`** —— 直接 `this.takedown(...)` 会绕过 Spring 代理，`@Transactional` 不生效，逐条独立事务的语义就没了。

#### ⚠️ 为什么勾选框的 value 是「类型:id」而不是纯 id

**光有 id 分辨不出类型**：内容举报工单的 sourceId 是**帖子 id**、账号举报是**工单 id**、账号标识字段是**审核记录 id** —— 三者的数字空间会重叠。只传 id 的话，服务端根本没法判断这一批是不是跨类型，AC2 的「收到跨类型的 id 集合时拒绝整批」就无法实现（只能退化成逐条查、逐条失败）。

复合串还顺带堵住了一个更难看的场景：**拿着一个内容举报的 id 去封某个账号**。

#### ⚠️ 三处「前端只是体验、服务端才是边界」

勾选框在浏览器里可以被随便改，所以上限 50、跨类型拒绝、封号权限**三条都在服务端又做了一遍**：

- 批量封号**额外还要 `user.deactivate`**（与单条口径一致）——否则批量就成了绕过单条门控的后门。有专门用例。
- 前端的置灰/计数/上限只是让运营少走弯路，不承担安全责任。

#### 逐条独立事务：为什么不能图省事包一个大事务

批量**不开外层事务**，逐条经 `ObjectProvider` 自引用代理调用。⚠️ **必须走代理**，`this.warn(...)` 会绕过 Spring 代理导致 `@Transactional` 直接不生效 —— 那样第 30 条失败会把前 29 条一起回滚，**而那 29 个人已经收到通知了**。通知发出去是收不回来的，数据库回滚也追不回来。

有一条 20 项（18 成功 + 2 个不存在的工单）的用例正面验证：18 条真的落库、2 条逐条回报原因。

#### AC5 的失败明细这次真的渲染出来了

既有内容举报的批量**返回了** `failed` 列表，但**模板从没渲染它** —— 运营只看得到「失败 2 条」，不知道是哪 2 条、为什么，也就无从重试。本 story 把明细 flash 到页面上逐条列出（含工单号与原因）。

#### `admin.js` 的改动范围

新增的全选/计数/跨类型置灰逻辑加在 `admin.js` 末尾（该文件**全后台共享**），全部用 `[data-batch-scope]` 限定作用域 + 事件委托，**不影响其他页面的表格**。全选也受两条边界约束：只选同一类型、最多 50 条。

#### ⚠️ 审计的规模成本（已知并刻意接受）

`AdminAuditService.record` 内有 Postgres advisory 锁 + 链尾查询，**批量 50 条 = 50 次取锁 + 50 次链尾查询**。50 条上限下可接受（后台 QPS 极低），但：
- **不要在此基础上放宽上限**；
- **不要把 N 条审计「优化」成一条汇总** —— 部分失败时汇总审计说不清到底哪几条成了。
