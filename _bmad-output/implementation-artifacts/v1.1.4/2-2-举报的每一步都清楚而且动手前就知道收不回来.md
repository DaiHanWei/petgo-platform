# Story 2.2: 举报的每一步都清楚，而且动手前就知道收不回来

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 2 第二个 Story（**纯前端 Flutter**）。**B 泳道 7 屏（B1–B7）+ A 泳道 1 屏（A3 已举报态）**。
> **交付**：账号举报抽屉全流程 · 五类账号维度选项 · 「提交后无法撤销」· 六个表单态。
> ⚠️ **本 story 的最大诱惑是复用 `report_sheet.dart`** —— 视觉规格该抄，**但枚举必须新建、失败处理必须重写**。
> ⚠️ **既有 `report_sheet.dart` 的失败分支只把按钮解禁、不给任何提示**，用户看到的就是「按了一下，按钮又能按了」。**这是本 story 明确不该照抄的地方。**

## Story

As a **准备举报某个账号的用户**,
I want **看到专为账号设计的举报理由、必要时能补充说明、并在提交前知道这不可撤销**,
so that **我选得准、说得清，也不会因为三次点击就造成自己后悔的结果**。

## Acceptance Criteria

> **验证层**：**L0**（`flutter analyze` / `flutter test`）· **L2**（模拟器视觉，本 story 主战场）。
> 云端只跑 L0；**L2 留本地**。

### AC1 — 菜单举报项接通（UX-DR1，A2）（L2）

**Given** Story 1.2 已在迷你卡建好「⋯」菜单
**When** 用户点击菜单里的「举报」
**Then** 弹出账号举报抽屉（**纯接通已有菜单项，不改菜单结构**）
**And** 「举报」与「拉黑」仍**并列、不分主次**，各自副标题按 PRD 定稿口径

### AC2 — 已举报态菜单（UX-DR3，A3）（L2）

**Given** 用户已举报过该账号
**When** 打开「⋯」菜单
**Then** 举报项显示为「已举报 / 点击可再次举报」（紫色，**明示可再点**，不能被误认为禁用态）
**And** **拉黑项此时仍可点、不置灰**

> ⚠️ 举报后再拉黑**不是多余操作** —— 拉黑带来一个举报没有的效果：**禁止再进入对方主页**。不得以「已举报」为由置灰或隐藏拉黑项。
> ✅ 「已举报」状态来自 Story 2.1 AC8 下发的服务端标记，**不是前端会话态**。

### AC3 — 举报表单（UX-DR6/7，B1/B2/B3）（L2）

**Given** 举报抽屉打开
**When** 渲染
**Then** 标题为**「举报这个账号」**（对象是账号不是内容，**与既有 `reportTitle`「Laporkan konten ini」是不同的键**）
**And** 展示**账号维度五类**选项，副标题**复用既有 `reportSubtitle`**「选择最合适的理由」
**And** **未选中任何类型时提交按钮禁用**
**And** 仅选中「其他」才展开必填文本框，**其余四类不展开**，文本框右下角显示 **0 / 200** 计数
**And** 选中态 = **紫边 `#845EC9` + 紫浅底 `#F8F2FF` + 实心 radio**，逐项取自既有实现

> ⚠️ **`AppColors.mint` 实际是品牌紫 `#845EC9`，不是绿色**（历史遗留命名）。选中底色是 `AppColors.cream2` = `#F8F2FF`。

### AC4 — ⚠️「提交后无法撤销」出现在全部表单态（UX-DR8）（L2）

**Given** 举报抽屉处于任一表单态
**When** 渲染提交按钮上方
**Then** **B1 未选 / B2 其他展开 / B3 已选 / B4 提交中 / B6 失败 / B7 重复举报——六个态全部**显示一行小字「提交后无法撤销」
**And** 该文案**只说不可撤销、不说会隐藏**（不破坏「成功态不提隐藏」那条取舍，A-A27）

> ⚠️ UI 稿的待改清单原文只列了 B1/B2/B3，**但 B4 提交中与 B6 失败态同样是表单态**，实际稿件已六个态全加。**按六个走。**

### AC5 — 提交中（UX-DR9，B4）（L2）

**Given** 用户点击提交
**When** 请求进行中
**Then** **选项与取消按钮一并禁用**（防重复提交），抽屉**不关闭**，提交按钮内显示转圈

> ✅ 既有 `report_sheet.dart` 的做法是 `_submitting = true` → 两个按钮 `onPressed: null`（第 108 / 117 行），**但没有 loading 指示器**。本 story 要求加转圈。
> ⚠️ 前端禁用是第一道防线，**服务端还有短窗去重**（Story 2.1 AC11）—— 两者都要有。

### AC6 — 成功态（UX-DR10，B5）（L2）

**Given** 提交成功
**When** 抽屉切换
**Then** **在抽屉内原地切换为成功态**（✅ + 「已收到你的举报」+「我们会尽快处理」+「关闭」），**不用 Toast、不自动收起**
**And** 点「关闭」→ **两层一并收起**（迷你卡 + 确认抽屉），回到点开迷你卡之前的页面
**And** 中途取消（点「取消」未提交）**只收起第二层**，回到迷你卡本身
**And** 成功态**刻意不提「内容将被隐藏」**

> **已知不一致，产品复核后接受**：既有内容举报的 `reportHiddenToast`「Kamu tidak akan melihat konten ini lagi」（你将不再看到这条内容）是**会告知**的 —— **举报帖子告知、举报账号不告知**。这是实锤差异，不是疏漏。
> ✅ 成功态文案可**复用既有键** `reportDoneTitle`（Laporan diterima）+ `reportDoneBody`（Kami akan segera memprosesnya.）—— 与 PRD 定稿完全对应。

### AC7 — 失败态（UX-DR11，B6）（L2）

**Given** 提交失败
**When** 处理错误
**Then** **抽屉不关闭、不清空已选类型与已填说明**，用户可直接重试
**And** 弹 Toast「举报失败，请刷新网络状态重试或联系客服」，Toast **放在顶部**避开抽屉

> ⚠️ **既有 `report_sheet.dart` 的 catch 分支只把提交中状态复位、不给任何提示**：
> ```dart
> } catch (_) {
>   if (mounted) setState(() => _submitting = false);
> }
> ```
> 用户看到的就是「按了一下，按钮又能按了」。**本 story 必须补上提示，不要照抄。**
> ⚠️ **「Toast 放顶部」全项目无既有实现** —— `showAppToast` 位置硬编码在底部（`Positioned(bottom: mq.padding.bottom + mq.viewInsets.bottom + 90)`），且是全站唯一 toast 实现、改它影响 30+ 处调用。**处理方式见 Dev Notes「Toast 位置的取舍」。**

### AC8 — 重复举报（UX-DR12，B7）（L2）

**Given** 用户已举报过该账号，再次进入举报抽屉
**When** 渲染
**Then** 副标题替换为紫底说明块「你已举报过该用户，再次举报会让我们知道问题仍在持续，我们会加快处理」
**And** 类型**重新选、不预填上次的选择**（每次的类型都要独立留存，第一次选骚扰、第二次选仿冒正是问题升级的证据）

### AC9 — 文案与视觉规格（L0/L2）

**Given** 本 story 的全部用户可见文案
**Then** 能复用既有 `app_id.arb` 键的一律复用：`commonClose`（Tutup）· `commonCancel`（Batal）· `reportSubtitle` · `reportDoneTitle` + `reportDoneBody` · `reportSubmit`（Kirim Laporan）
**And** 新增键按 UI 稿文案清单落地，**「提交后无法撤销」已有印尼语草稿**（`Laporan tidak dapat dibatalkan setelah dikirim`）可直接用
**And** 抽屉视觉规格逐项照搬既有实现：内边距 22/12/22/28 · 手柄 36×4 · 原因卡圆角 13 / 边框 1.5px / 内距 14·12 / 间距 10 · 提交按钮圆角 14 / 垂直内距 14 · 取消按钮描边 1.5px

### 既有 `report_sheet.dart` 的三态处理（照抄前先看清）

```dart
Future<void> _submit() async {
  if (_selected == null || _submitting) return;
  setState(() => _submitting = true);
  try {
    await widget.ref.read(detailRepositoryProvider).submitReport(widget.postId, _selected!.wire);
    if (mounted) setState(() => _done = true); // 切 sheet 内成功态（不再 toast）
  } catch (_) {
    if (mounted) setState(() => _submitting = false);   // ⚠️ 只解禁，不提示、不区分错误
  }
}
```

**提交中**：`_submitting = true` → 提交按钮（108 行）与取消按钮（117 行）都 `onPressed: null`，**无 loading 指示器**。
**成功**：`_done = true` → sheet 内切成功态，**不弹 toast**；成功态关闭按钮 `Navigator.pop(true)` → `openReport` 触发 `onReported`。
**失败**：⚠️ 见上，**这是本 story 不该照抄的地方**。

### ⚠️ Toast 位置的取舍（AC7）

**实证**：`shared/widgets/app_toast.dart` 的 `showAppToast` 挂 root Overlay，**位置硬编码在底部**：

```dart
final bottom = mq.padding.bottom + mq.viewInsets.bottom + 90;
return Positioned(left: 24, right: 24, bottom: bottom, child: IgnorePointer(...));
```

**全仓只有这一个 toast 实现，无顶部变体、无位置参数**，改它会影响 30+ 处调用。

**➜ 本 story 的处理**：
- **优先方案**：给 `showAppToast` **加一个可选的位置参数**（如 `bool top = false`），默认 false 时行为与现在完全一致 —— 既满足 AC7 的「放顶部避开抽屉」，又不影响既有 30+ 处调用。
- **若不加参数**：用底部 toast，但**必须在 L2 验收时确认它不与抽屉视觉打架**（toast 挂 root Overlay 所以 z 序在抽屉之上，不会被遮挡，但位置可能叠在抽屉上）。
- ⚠️ **无论选哪个，都要在 Completion Notes 记录**，因为 Story 1.2 的 C4（拉黑失败）面临同样问题，两处口径要一致。
