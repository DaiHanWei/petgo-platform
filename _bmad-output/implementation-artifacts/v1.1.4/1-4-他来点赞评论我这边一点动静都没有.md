# Story 1.4: 他来点赞评论，我这边一点动静都没有

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第四个 Story（**纯后端**）。**可与 Story 1.3 完全并行**（两者都只依赖 Story 1.1）。
> **交付**：三类互动通知的抑制（赞 / 评论 / 回复我的评论）。
> ⚠️ **本 story 含高风险点 R3**：抑制判据**有两条**，只做第一条会漏掉第三方 —— 那个人没拉黑任何人，却收到点进去空白的通知。
> ⚠️ **抑制点位置错一层就会误伤系统通知**：`NotificationService.send` 是全站通用发送方法，**12 个调用点**里包含封号/审核结果/退款驳回/工单结案等系统通知。

## Story

As a **拉黑了某人的用户**,
I want **他的点赞、评论、回复不再给我发任何通知**,
so that **我不会被他打扰，也不会收到点进去什么都没有的通知**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package`）· **L1**（Docker postgres + redis 真跑）。本 story 无 L2。

### AC1 — 三类互动通知抑制（L1）

**Given** A 已隐藏 B（**两种来源都算**，不区分 `source`）
**When** B 点赞 A 的内容 / 评论 A 的内容 / 回复 A 的评论
**Then** A **收不到对应通知**
**And** 抑制点在 `ContentNotifyListener` 的 **`onContentLiked` 与 `onContentCommented` 两个方法内**
**And** ⚠️ `onContentCommented` **内部有两处 `send`，两处都要判**（一次给内容作者、一次给被回复的一级评论作者）

### AC2 — 是「不发」而不是「发了再隐藏」（L1）

**Given** 通知被抑制
**When** A 打开通知中心
**Then** **通知记录不存在**（未写库）
**And** **未读角标不 +1**

> ✅ **实证：只要不调 `NotificationService.send`，这两条自动成立** —— 角标自增 `bumpUnreadBadge` 在 `send` 内部，不调 `send` 就既不写 `notifications` 行、也不碰 Redis 计数。**不要另想办法「发了再删」。**

### AC3 — ⚠️ 抑制判据有两条，缺一会漏第三方（高风险点 R3）（L1）

**Given** A 已拉黑 B；B 在 **A 的帖子下**回复了 **C 的一级评论**；C 未拉黑任何人
**When** 该回复因 R2 对所有人隐藏
**Then** **C 同样收不到「有人回复了你的评论」通知**
**And** 判据实现为两条，**任一命中即不发**：
　① **接收者隐藏了 actor**（`holder = 接收者`，`target = actor`）—— 对应 R1
　② **该内容的作者隐藏了 actor**（`holder = contentAuthorId`，`target = actor`）—— 对应 R2

> ⚠️ **PRD §3.2 生效范围第 6 条列的三种场景，收通知的人全是拉黑发起方本人**，第三方这一支是 PRD 的空白。只做判据 ① 会让 C 收到点进去空白的通知，**一对比就能推断出屏蔽机制存在**。
> ✅ **实证：两条判据所需的全部输入在监听器内都是现成的** —— `ContentCommentedEvent` 是 record，含 `postId / commentId / commenterId / contentAuthorId / parentAuthorId / createdAt`；`ContentLikedEvent` 含 `postId / likerId / authorId`。**无需新增事件字段、无需回查数据库。**

### AC4 — 系统通知不受影响（L1）

**Given** 封号通知、审核结果通知、内容被移除通知、退款驳回、工单结案等系统通知
**When** 这些通知被触发
**Then** **一律不接入隐藏判断，照常发送**
**And** 抑制逻辑**只存在于 `ContentNotifyListener` 的 `onContentLiked` / `onContentCommented` 两个方法内**，**未写进 `NotificationService.send`**
**And** ⚠️ **同类中的 `onContentRemoved` 不接入抑制** —— 它是「你的内容被运营移除」的系统通知，语义上属平台告知，别误伤

> ⚠️ **实证：`NotificationService.send` 是全站唯一通用发送方法，有 12 个调用点**，覆盖 `AdminCommentManageService` / `ManualReviewService` / `ScheduledPushDispatcher` / `AvatarResetNotifyListener` / `ConsultNotifyListener` / `MilestoneNotifyListener` / `ModerationNotifyListener` / `NameResetNotifyListener` / `RefundService` / `SupportTicketService` 等。**把抑制写进 `send` 会把这些全部一起抑制掉。**

### AC5 — 解除与历史（L1）

**Given** A 解除了对 B 的拉黑
**When** 检查抑制期间的通知
**Then** **不补发**，抑制期间的通知永久丢弃
**And** 拉黑**之前**已产生的历史通知**不回溯清理**（继承「拉黑不回溯清理已产生数据」原则，A-A30）

### AC6 — 对被拉黑方无影响（L1）

**Given** B 的点赞与评论操作
**When** 通知被抑制
**Then** B 的操作**照常成功**，B 无从知晓对方是否收到通知
**And** 既有的「自赞不推 / 自评不推 / 自回复不推自己 / parent 恰是内容作者只推一条」四条去重守卫**原样保留**

### AC7 — 护栏（L0）

**Given** 本 story 的实现
**Then** **无 Flyway 迁移**（不新增通知 type、不加列）
**And** 未引入 MQ / 缓存 / 新中间件；抑制判定为同步查库
**And** 未改 `NotificationService` / `notifications` 表 / `NotificationType` 枚举
**And** `mvn -B package` 全绿

### `ContentNotifyListener` 现状（要改的就是这个文件）

三个 `@TransactionalEventListener`（**默认 AFTER_COMMIT，同步，无 `@Async`**）：

| 方法 | 事件 | 通知类型 | 本 story 要不要接抑制 |
|---|---|---|---|
| `onContentLiked` | `ContentLikedEvent` | `CONTENT_LIKED` | ✅ 要 |
| `onContentCommented` | `ContentCommentedEvent` | `CONTENT_COMMENTED` | ✅ 要（**内部两处 send 都要**） |
| `onContentRemoved` | `ContentRemovedEvent` | `CONTENT_REMOVED` | ❌ **不要**（系统通知） |

`onContentCommented` 的两处发送点：

```java
String ref = String.valueOf(event.postId());
// 发送点 ①：通知内容作者（自评不推）
if (event.commenterId() != event.contentAuthorId()) {
    notificationService.send(event.contentAuthorId(), NotificationType.CONTENT_COMMENTED,
            "有人评论了你的内容", "点击查看", NotificationType.CONTENT_COMMENTED.name(), ref);
}
// 发送点 ②：Bug 20260625-088 —— 回复二级评论时另行通知被回复的一级评论作者
Long parent = event.parentAuthorId();
if (parent != null && parent != event.commenterId() && parent != event.contentAuthorId()) {
    notificationService.send(parent, NotificationType.CONTENT_COMMENTED,
            "有人回复了你的评论", "点击查看", NotificationType.CONTENT_COMMENTED.name(), ref);
}
```

**➜ 发送点 ② 就是 R3 的落点。** 那里的接收者是 `parentAuthorId`（第三方 C），而要判的第二条是 `holder = contentAuthorId`（A）—— **两个不同的人**，这正是最容易漏的原因。

---

### ✅ 两条判据所需的输入全部现成，无需新增事件字段

```java
public record ContentCommentedEvent(
        long postId, long commentId,
        long commenterId,      // ← actor
        long contentAuthorId,  // ← 内容作者（判据 ② 的 holder）
        Long parentAuthorId,   // 被回复的一级评论作者（一级评论时 null）
        Instant createdAt) {}

public record ContentLikedEvent(long postId, long likerId, long authorId, Instant createdAt) {}
```

三个发送点（liked ×1、commented ×2）**全都同时持有 actor id 与内容作者 id**。**不需要回查数据库、不需要改事件定义。**

---

### 角标与落库：不调 `send` 就自动满足 AC2

`NotificationService.send` 一次调用 = **写库 + 角标自增 + 离线推送** 三件事：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public Notification send(long recipientUserId, NotificationType type, String title, String body,
        String deepLinkType, String targetRef) {
    Notification saved = repo.save(Notification.of(...));
    bumpUnreadBadge(recipientUserId);        // ← Redis notify:unread:{userId} 自增
    pusher.pushToUser(...);                  // 离线推送
    return saved;
}
```

⚠️ `REQUIRES_NEW` 是**必需**的（`@TransactionalEventListener` 在 AFTER_COMMIT 触发，用默认 REQUIRED 会加入已提交事务导致 INSERT 静默丢弃）—— **别动它**。

**角标机制**：Redis `notify:unread:{userId}` 计数为主 + DB `countByRecipientUserIdAndReadIsFalse` 回算兜底（`NotificationCenterService.unreadCount` 缺值时回算并回填）。
**➜ 不调 `send` → 不写行、不碰 Redis → 角标自然不涨。AC2 无需额外代码。**
