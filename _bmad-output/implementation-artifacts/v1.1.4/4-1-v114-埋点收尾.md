# Story 4.1: V1.1.4 埋点收尾

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 4 唯一 Story（**前端为主 + 非代码交付项**）。**排最后** —— 沿用 V1.1.2 既定做法：埋点在功能逻辑全部理清后集中实现，避免边做边改、口径散在各处。
> **交付**：拉黑/解除埋点分来源分入口 · 黑名单页举报点击单独打点 · 成功度量的数据来源核对。
> 🚩 **AC7 是产品任务不是代码任务，但漏了会让整节度量作废** —— 上线前必须先量基线。
> ⚠️ **本仓埋点治理靠「测试从源码正则提取事件名再断言」**，新事件名必须落在白名单前缀/后缀内，否则测试直接红。

## Story

As a **产品负责人**,
I want **拉黑与举报的行为被分来源、分入口地记录下来**,
so that **上线后我能判断这一版的赌注押对了没有，而不是只能凭感觉说「好像有用」**。

## Acceptance Criteria

> **验证层**：**L0**（`flutter analyze` / `flutter test`，命名规范与源码提取断言）· **L1**（真后端 + PostHog 后台确认事件到达）。
> ⚠️ **L1 需要 PostHog 后台实测**，云端跑不了，**留本地并在 Completion Notes 标注**。

### AC1 — 拉黑 / 解除拉黑事件必须分来源（L1）

**Given** 一条隐藏关系被建立或解除
**When** 上报埋点
**Then** 事件属性含**产生来源**：`BLOCK`（用户主动拉黑）/ `REPORT`（举报自动产生）

> ⚠️ 不分来源的话，**隐藏关系总量会被举报量灌大**，完全看不出主动拉黑的真实使用情况——而这两件事的产品含义截然不同。

### AC2 — 拉黑事件必须分入口（L1）

**Given** 用户发起拉黑
**When** 上报埋点
**Then** 事件属性含**操作入口**：`mini_profile`（迷你主页卡）/ `blocklist`（黑名单页）/ `report_flow`（举报流程自动产生）/ `comment`（评论区头像）
**And** 四个入口的埋点在各自 story 实现时**已预留参数**（`mini_profile` → Story 1.2 · `blocklist` → Story 1.5 / 2.4 · `comment` → Story 1.6 · `report_flow` → Story 2.1），本 story 负责**统一收口与校验**

### AC3 — 黑名单页举报点击单独打点（L1）

**Given** 用户在黑名单页点击行内「⋯」→ 举报
**When** 上报埋点
**Then** 该点击**单独成事件**，来源标记为 `blocklist`

> 这个数字直接验证「拉黑后仍需举报入口」这个设计判断是否成立：**若长期为 0，说明该入口可以撤掉**；若量不小，说明原来的设计确实堵死了一条重要路径。

### AC4 — 明确不埋的（L0）

**Given** 影子评论（R2）机制
**When** 设计埋点
**Then** **不对影子评论做任何单独埋点**

> 被拉黑方无感知是设计前提，任何针对他的行为埋点都不改变产品行为，本版本不做。

### AC5 — 度量所需数据的来源核对（L0）

**Given** PRD §4.3 定义的成功度量
**When** 核对数据来源
**Then** 确认全部指标**可由本 story 的埋点 + 后台工单数据得出，无需再新增埋点**：
- 工单总量 / 工单构成 → 后台工单数据（Epic 3 的统一视图）
- 人均举报次数 → 举报人数与举报次数的比值（Story 3.1 AC5 已展示）
- 主动拉黑真实使用量 → 本 story AC1 的来源区分
- 黑名单页举报入口使用量 → 本 story AC3

### AC6 — 四条反向指标可被观测（L1）

**Given** PRD §4.3 定义的四条反向指标
**When** 上线后监控
**Then** 以下四条**均有数据可查**：
1. 账号举报量周环比翻倍且持续两周 → 后台工单数据
2. 单账号被举报**人数**分布出现异常尖峰 → 后台工单数据（Story 3.1 AC5 的人数指标）
3. 客服工单出现「为什么刷不到某人内容」类咨询 ≥5 起/月 → 既有客服工单（FR-52），**需人工归类，非埋点**
4. 黑名单页举报入口点击长期为 0 → 本 story AC3

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段实证扫描。

### 埋点 SDK：PostHog，唯一门面 `Analytics`

`lib/core/analytics/analytics.dart`（208 行）。三个上报入口：

| 入口 | 签名 | 用途 |
|---|---|---|
| 自定义事件 | `Analytics.capture(String event, [Map<String, Object>? properties])` | **主入口**（属性是**位置可选参数**，不是命名参数） |
| 页面浏览 | `Analytics.screen(String name)` | 手工 `$screen` |
| 按钮点击 | `Analytics.buttonTapped(String id, {String? screen})` | id 必须是 `ButtonId` 常量 |

典型写法：

```dart
Analytics.capture('triage_submitted', {'consult_type': 'AI'});
```

**三条内建护栏**（都在 `capture` 内自动生效，但**不要依赖兜底**）：
- `_piiKeys` 黑名单（email/name/phone/symptom/diagnosis/token/lat/lng...）整键丢弃
- `_freeTextKeys` 黑名单（buttonname/title/label/text/content/caption）整键丢弃
- 字符串值 **> 64 字符**整键丢弃（大概率是用户内容）

⚠️ **举报的「其他」补充说明是用户自由文本，绝不能进埋点属性。**

### 🔴 命名规范由测试强制，先定名再写代码

`test/analytics/v112_events_test.dart`（579 行）**从 `lib/` 源码正则提取事件名**再断言：

```dart
@visibleForTesting
Set<String> eventNamesInSource() =>
    _literalsOf(RegExp(r"""Analytics\.capture\(\s*'([A-Za-z0-9_]+)'"""));
```

**为什么这么做**（code-review 2026-08-04 的原话）：维护一份手抄清单会与代码脱节，**而脱节时测试仍绿**。

**断言内容**：

```dart
const allowedPrefixes = <String>[
  'app_', 'bottom_nav_', 'diary_', 'social_', 'health_', 'publish_', 'me_',
  'signup_', 'milestone_', 'consult_', 'ai_',
];
const allowedSuffixes = <String>[
  '_viewed', '_shown', '_tapped', '_selected', '_toggled', '_switched',
  '_succeeded', '_completed', '_landed_on_tab', '_achieved', '_submitted', '_started',
];
```

**➜ 只要在 `lib/` 里新加 `Analytics.capture('xxx')`，这个测试会自动对它生效。**

⚠️ **注意 `_blocked` / `_reported` 不在后缀白名单里。** 两个选择：
1. 改用白名单内的后缀（如 `social_user_block_submitted` / `social_account_report_submitted`）
2. **在测试的 `allowedSuffixes` 与 `docs/analytics-posthog-tracking.md §8.1` 两处同步登记新后缀**

**推荐 1**，避免放宽规则。

#### 四个事件（**没有放宽任何白名单**）

| 事件 | 何时报 | 属性 |
|---|---|---|
| `social_user_hide_submitted` | 隐藏关系建立成功后 | `origin`: BLOCK\|REPORT · `entry`: mini_profile\|comment\|blocklist\|report_flow |
| `social_user_unhide_submitted` | 解除拉黑成功后 | `origin`: 恒 BLOCK · `entry`: 恒 blocklist |
| `social_account_report_submitted` | 举报**提交成功**后 | `entry` · `reason`（受控词表五值） |
| `social_blocklist_report_tapped` | 黑名单页点「⋯→举报」的**那一下** | `entry`: 恒 blocklist |

前缀 `social_` + 后缀 `_submitted` / `_tapped` **都在既有白名单内** —— story 提示的 `_blocked` / `_reported` 不在白名单，按建议**改名而不是放宽规则**。所以 `v112_events_test`（从源码正则提取事件名再断言）自动纳管了这四个，一行都没改它。

#### 两个维度分开落 key

`source` 这个 key 在既有事件里已被占用（做多入口区分），所以用 **`origin`（产生来源）+ `entry`（操作入口）**。
⚠️ 不分 `origin` 的话，**隐藏关系总量会被举报量灌大**，完全看不出主动拉黑的真实使用情况 —— 而这两件事的产品含义截然不同。

#### ⚠️ 一次举报会连发两条事件（刻意）

举报成功时服务端**同时**建了一条 `source=REPORT` 的隐藏关系（Story 2.1 AC5），所以端上补一条 `social_user_hide_submitted {origin: REPORT, entry: report_flow}`。
不补的话「隐藏关系」这条口径是**残缺的**（举报产生的那部分全漏），而补成同一个事件名又能靠 `origin` 分开看。

#### 「多入口不拆事件名」的唯一例外

四个入口共用同一个事件名靠 `entry` 区分（沿用 V1.1.2 的教训「拆了转化率分母就碎了」）。
**唯一例外是 `social_blocklist_report_tapped`** —— 它测的不是「举报提交」而是「**这个入口有没有人用**」，是另一个问题，且 AC3 明确要求单独成事件。它也**按点击记、不等提交**：这个数字要回答的是「拉黑之后还需不需要举报入口」，**长期为 0 就说明该入口可以撤掉**。

#### 上报点一律在成功之后（4 条断言守着）

拉黑失败 / 举报失败 / 中途取消 —— **一条事件都不留**。沿用 V1.1.2 code-review 抓到的教训：门控前上报会让指标**系统性高估**（当时是「游客点受控 Tab 只弹了登录、页面根本没开，却记了一条浏览」）。

#### 顺带补上的一处参数贯通

Story 1.2 建拉黑入口时**没有**把「从哪儿点开的」传下来（当时还没有埋点需求），Story 2.4 只给举报侧加了 `entry`。本 story 给 `showMiniProfile` 加了 `entry` 参数并在评论区传 `comment` —— 否则**评论区拉黑与 Feed 拉黑在数据上无法区分**，而评论区骚扰正是本版本的主场景。

#### 明确不埋的（AC4）

- **影子评论（R2）零埋点**：被拉黑方无感知是设计前提，针对他的行为埋点不改变产品行为。有测试断言全 `lib/` 下不存在任何 shadow 相关事件名。
- **举报的「其他」补充说明绝不进属性**：上报的是受控词表 `reason`，不是原文。有专门用例（塞一段中文自由文本，断言它没出现在任何属性值里）。
- **四个事件都不进 AppsFlyer 白名单**：治理行为不是归因事件。有断言。

#### ⚠️ L1 待本地：PostHog 后台确认事件到达

AC1–AC3 的 L1 需要**真后端 + PostHog 后台**看到事件落地，**云端跑不了**。
本轮只跑到 L0（端上发出的形态由 `debugCaptureSink` 断言，那是 `scrub()` 之后的形态，与真正发出去的一致）。
> 📌 同样的 L1 挂起项在 V1.1.2 的埋点收尾里也存在（那条 story 至今 in-progress，就差这一步）。

#### 🚩 非代码交付项 —— **产品负责**（🔄 2026-08-16 产品改定，决策 C-105）

**原定「上线前量 4 周基线」已作废**，改为**上线后先观测数量、再设定基线**：

| 阶段 | 周次 | 做什么 |
|---|---|---|
| 观测期 | 第 1–2 周 | **只看不算**（存量骚扰账号的一次性清算 + 入口爬坡，计进去会把基线定歪） |
| 基线期 | 第 3–6 周 | 取周均为稳态基线 |
| 回看 | **第 10 周** | 只一次，产出结论（达成 / 未达成 / **数据不足**）记入决策日志 |
| 反向指标 | **第 1 天起** | 四条照常监控，任一触发即回看 |

⚠️ **这条改动放弃了什么（已写进 C-105 与 PRD §4.3，不糊过去）**：
没有上线前的 before，**「工单总量不上升」这个主指标从此无法被证伪** —— 「这一版到底有没有降低工单量」永远答不了。
**但四条反向指标一条都不受影响**（周环比 / 分布形状 / 绝对阈值都不依赖前置基线），最要紧的风险警报照常生效。
**埋点侧无需任何改动**：4 个事件在两种方案下都够用。

→ 故 **T7 的执行项与 T8 的「产出结论」刻意不勾**：那是上线后第 3–6 周 / 第 10 周才会发生的事，现在勾上就是假的。
