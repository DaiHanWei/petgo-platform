# Story 3.4: 举报处理完，用户收到的那句话终于统一了

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 3 第四个 Story（**纯后端**）。**与 3.1–3.3 零依赖，可任意时点插入。**
> **交付**：FR-51 举报处理完成的回告文案改为 PRD 定稿那句。
> ⚠️ **工程量只是改一行字，但它不是文档订正** —— 这是一条**独立交付项**，且**会连带改变已上线的内容举报回告**。
> ⚠️ **PRD §6 原文以「描述既有机制」的口吻写这句文案，既不是在描述现状、也没声明自己是在提变更** —— 若不显式列出，上线后没人知道这是有意改的。

## Story

As a **举报过内容或账号的用户**,
I want **在举报被处理后收到一句一致、得体的回告**,
so that **我知道我的举报被认真对待了，而不是收到一句机械的「已完成审核」**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package`）· **L1**（Docker postgres 真跑，通知内容）。本 story 无 L2。

### AC1 — 文案改为 PRD 定稿那句（L1）

**Given** 举报处理完成的闭环通知
**When** 发送给举报人
**Then** 文案改为「**你的举报已处理，感谢你帮助维护社区环境**」
**And** 仍**不透露具体处置结果**（继承 FR-51 既有口径）

> **线上现状**：「举报已处理 / 感谢你的举报，我们已完成审核。」
> ✅ 该通知由 `ModerationNotifyListener` 经 `NotificationService.send(..., NotificationType.REPORT_REVIEWED, ...)` 发出。

### AC2 — ⚠️ 影响面不止本版本（L1）

**Given** 该通知是**内容举报与账号举报共用的同一条**
**When** 文案变更上线
**Then** **已经上线的内容举报回告也会跟着变**
**And** 这是**有意为之，不是副作用**

### AC3 — ⚠️ 这是一条独立交付项（L0）

**Given** 本变更的工程量只是改一行字
**When** 提交实现
**Then** 该变更**必须作为独立的可追溯改动出现**，**不得混在其他改动里悄悄改掉**

> ⚠️ PRD §6 原文以「描述既有机制」的口吻写这句文案，**既不是在描述现状、也没声明自己是在提变更**。若不显式列出，上线后没人知道这是有意改的 —— 日后有人对着线上文案与 PRD 比对，会以为是 bug。
> **具体要求**：独立 commit（或至少在 commit message / Completion Notes 里显式点名），并在 `CROSS-STORY-DECISIONS.md` 留一条。

### AC4 — 文案送审（L0）

**Given** 新文案的印尼语措辞
**When** 实现
**Then** 与警告通知、封号通知**同批送法务/运营确认**（OQ-A4）
**And** 该条**不阻塞**本 story 的代码实现

### AC5 — 护栏（L0）

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段实证扫描。

### 落点：`ModerationNotifyListener`

**`REPORT_REVIEWED` 已在 `V40__extend_notification_types_report_reviewed.sql` 加入枚举白名单** → **本 story 零迁移**。

---

### ⚠️ 两条文案路径，都要确认

`NotificationService.send` 内部：

```java
Notification saved = repo.save(Notification.of(
        recipientUserId, type, title, body, deepLinkType, token, targetRef));   // ← ① 落库的 title/body
...
java.util.Locale locale = accountQuery.localeOf(recipientUserId);
pusher.pushToUser(recipientUserId,
        pushText(type, "title", locale, title),                                 // ← ② 推送的本地化文案
        pushText(type, "body", locale, body),
        deepLinkType, token, targetRef);
```

代码注释写明：「push 文案按收件人语言渲染（bug 20260625-105）；**站内通知中心不用这里的文本**（App 端按 type 自行本地化），故落库 title/body 保持不变。」

**➜ 意味着：**
- **落库的 title/body** 是给谁看的？按注释说 App 端按 type 自行本地化，所以站内展示可能不读它 —— **但仍要改对**，因为它是数据记录。
- **推送文案**走 `pushText(type, ...)` 的本地化查表 —— **新文案要落到那套本地化资源里**，否则推送出去的还是旧的。

⚠️ **实现时先确认这两条路径各自的文案来源**，改一处漏一处会出现「站内看到新文案、推送收到旧文案」。

---

### 为什么这条要单独立 story（AC3 的理由）

PRD §6 第 2 条的原文以**「描述既有机制」的口吻**写：

> 通知文案统一为「你的举报已处理，感谢你帮助维护社区环境」

但代码实证发现**线上实际发出的是另一句**：「举报已处理 / 感谢你的举报，我们已完成审核。」

**两句并不相同，而 PRD 既不是在描述现状、也没声明自己是在提变更。**

**➜ 产品 2026-08-15 决定：采用 PRD 这句，本版本把线上文案改过来。**
**➜ 但必须显式列为交付项**，否则：
- 上线后没人知道这是有意改的
- 日后有人对着线上文案与 PRD 比对，会以为是 bug 又改回去
- **内容举报的用户会突然收到不一样的回告**，而没有任何记录说明为什么
