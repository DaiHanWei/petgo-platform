# Story 1.5: 我能看到自己拉黑了谁，随时放人出来

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第五个 Story（**跨前后端**：AC2 / AC7 / AC9 后端，其余前端）。
> **交付**：`GET /api/v1/me/blocked-users` 列表接口 + 黑名单管理页（**D 泳道 10 屏**：D1–D7 · D7b · D8 · D9 的布局位）。
> ⚠️ **本 story 踩的是全版本最高风险点 R5「封号 ≠ 注销」**（架构 S3）——代码里两个概念命名几乎一样，而本 story 对它们的要求**正好相反**。见 AC8 与 Dev Notes。
> ⚠️ **D9 的行内「⋯」本 story 只预留布局、不渲染**，随 Story 2.4 出现。

## Story

As a **拉黑过若干账号的用户**,
I want **在设置里找到黑名单、看到拉黑了谁和什么时候拉的，并能逐个解除**,
so that **我不会忘记自己屏蔽过谁，也能在改变主意时把人放出来**。

## Acceptance Criteria

> **验证层**：**L0**（`flutter analyze` / `flutter test` / `mvn -B package`）· **L1**（Docker postgres 真跑，接口行为）· **L2**（模拟器视觉）。
> 云端只跑 L0；**L1 / L2 留本地**，在 Completion Notes 标注。

### AC2 — 列表内容与排序（UX-DR16，D2）（L1）

**Given** 用户打开黑名单页
**When** 列表加载完成
**Then** **只收录含主动拉黑（`source=BLOCK`）的条目**，举报产生的隐藏**不出现在本页**
**And** 每项展示 头像 + 昵称 + 拉黑时间，按**拉黑时间倒序**
**And** ⚠️ **排序取 `BLOCK` 行的 `created_at`，不取 `updated_at`**
**And** ⚠️ **对同一目标追加 `REPORT` 行（即事后又举报了这个人）不得改变该条目在列表中的位置** —— 两条隐藏关系是独立的行，举报不触碰 `BLOCK` 行的任何字段
**And** 被举报过的条目在昵称后带「已举报」小标签
**And** 顶部有说明句「他们不会知道你拉黑了他们」
**And** 拉黑数量不设上限；**本 story 采全量返回不分页**（理由见 Dev Notes）

> ⚠️ **为什么排序字段要钉死**：三元唯一键 `(holder, target, source)` 保证举报写的是 `REPORT` 行、碰不到 `BLOCK` 行——**但那只保证行不被覆盖，不保证列表顺序不被搅乱**。若实现取 `updated_at`、或举报流程顺手 touch 了同一 `(holder, target)` 下的记录，用户就会看到「**我今天什么都没做，这个三个月前拉黑的人怎么跑到最前面了**」。写入侧的对应约束在 Story 2.1 AC5。

### AC3 — 主动作与次要动作分开（UX-DR16）（L2）

### AC6 — 解除成功的两句文案（UX-DR19，D7 / D7b）（L2）

**Given** 解除成功
**When** 对象**只被主动拉黑过**
**Then** Toast 为「已解除拉黑，刷新后可重新看到 TA 的内容」（**措辞用「刷新后」不用「立即」**，为后续带序列缓存的推荐算法留余地）
**And** 当对象**同时也被举报过**时，Toast 改为「已解除拉黑。你举报过 TA，内容仍不会展示给你」
**And** **两种情况条目都从列表移除**（拉黑关系确实解除了），只是后者内容不恢复

> ⚠️ 这是**全产品唯一会向用户揭示「举报会隐藏内容」的地方**，而举报成功态刻意不提。两处口径不同**是有意为之**，复盘时别当成漏了。

### AC8 — ⚠️ 封号与注销要求相反（高风险点 R5，UX-DR20，D8）（L2）

**Given** 黑名单里有一个**已被运营封号**的账号和一个**已自行注销**的账号

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段对前后端的实证扫描，**不是文档推演**。

### 🔴 本 story 的最高风险：封号 ≠ 注销（R5 / 架构 S3）

| | **封号 / 运营停用** | **用户自己注销** |
|---|---|---|
| 字段 | `users.status` varchar(16) → **`UserStatus.DEACTIVATED`** | `users.deleted_at` timestamptz |
| 写入 | `User.deactivate()` / `User.reactivate()` | `User.anonymizeForDeletion(Instant)` |
| 可逆 | ✅ 可 reactivate | ❌ 不可逆 |
| 谁读 | **只有登录/刷新门控** `isActiveStatus()` | 所有展示投影：`AccountQueryService.toAuthorView()` |
| 对外投影 | **不投影到任何对外 DTO** | `AuthorView.deleted` → 前端 `authorDeleted` / `isDeactivated` |
| **本 story 要求** | **照常展示、不做标记、仍可被拉黑** | **匿名态 + 去点击态 + 条目保留** |

**➜ 关键推论：后端根本不下发「是否被封号」这个信息**（`AuthorView` 只有 `deleted`）。所以 AC8 的封号那半条，**前端什么都不用做就自动满足了** —— 被封号的用户在 `findAuthorViews` 眼里就是个正常用户。
**➜ 真正要做的只有注销那半条。** 但**不要因此以为 AC8 是空的** —— 它的价值在于**阻止有人"顺手"给封号用户加标记**，那会把平台侧处置透露给用户。

⚠️ **`MiniProfileResponse.isDeactivated` 指的是「注销」不是「封号」**，`UserStatus` 的 Javadoc 自己写了「与『删除/注销』正交」。**看串一个词就会把两条相反的要求做反。**

`findAuthorViews` 有两个对本 story 极其有利的行为：

```java
@Transactional(readOnly = true)
public Map<Long, AuthorView> findAuthorViews(Collection<Long> userIds) {
    Map<Long, AuthorView> found = users.findAllById(userIds).stream()
            .map(AccountQueryService::toAuthorView)
            .collect(Collectors.toMap(AuthorView::userId, Function.identity()));
    // 缺失的（不存在）也按匿名化补齐，调用方按 id 取必有值。
    return userIds.stream().distinct()
            .collect(Collectors.toMap(Function.identity(),
                    id -> found.getOrDefault(id, AuthorView.anonymized(id))));
}
```

> 📌 这条正是 IR-6 要求「指名到具体的投影类与端口接口」的答案 —— **答案是：`AccountQueryService.findAuthorViews`，不需要端口。**

#### ⚠️ 踩到一个 Riverpod 3 的默认行为，值得记住

**Riverpod 3 默认会对抛错的 provider 自动指数退避重试。** 第一版写完，「加载失败」用例红了 —— 页面上**一个错误字都没有**，body 空白，还留了个 pending timer。原因是 provider 一直在「错误 → 自动重试 → 加载中」之间横跳，用户根本点不到那个「重试」按钮。

而 AC4 要的恰恰是**一条明确的恢复路径**。所以给这个 provider 显式关掉自动重试（`retry: (_, _) => null`），失败就停在失败态，重试由用户按钮触发。已在代码里就地写明理由，免得后人当成漏写给删了。

> 📌 **这条对其他列表页可能同样成立**（订单/工单/退款都用了 `AsyncNotifier` + 错误态 + 重试按钮）。**本 story 没有顺手去改它们**——那是既有行为变更，超出范围。但值得单独起一条排查：**它们的「重试」按钮在真实断网时可能同样点不到。**

#### AC8「封号 ≠ 注销」的实际落点

后端**根本不下发封号信息**（`AuthorView` 只有 `deleted` = 用户自己注销），所以：

- **封号那半条，代码上什么都不用做就自动满足**——被封号的人在这份数据里跟正常人一模一样。
- 但**它不是一条空 AC**：价值在于挡住「顺手给封号用户加个标记」。所以两侧各钉了一条：后端断言响应的**字段集恰好是那 5 个**（有人加 `banned`/`suspended` 就红），前端断言普通行**无任何附加标记**。
- 真正要写代码的只有注销那半条：匿名昵称 + 默认头像 + 去点击态，**但「解除拉黑」按钮必须仍可用**（有用例断言 `onPressed` 非 null）——禁用了用户就永远清不掉这一行。

#### 两处口径说明（不是遗漏）

1. **解除成功的 Toast 说「刷新后」不说「立即」** —— 给后续带序列缓存的推荐算法留余地。
2. **「你举报过 TA，解除拉黑后内容仍不会展示」是全产品唯一会向用户揭示「举报会隐藏内容」的地方**，而举报成功态刻意不提。两处口径不同**是有意为之**，复盘时别当成漏了。

**本 story 复用了既有的 `feedDeletedUser`**，理由：① 全 App 一致（Feed / 详情 / 评论三处都用它）；② `terhapus`（已删除）比 `nonaktif`（未激活）更准确地对应「注销」；③ `nonaktif` 在站内还容易与兽医封禁的 `diblokir` 语义打架。**若产品坚持 UI 稿的写法，那三处也要一并改**，否则同一概念两种说法——这是产品决定，不是实现细节。
