# Story 1.3: 评论区里再也看不到他，他也没法在我地盘上冲别人喊话

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 1 第三个 Story（**纯后端**）。可与 Story 1.4 并行，两者都只依赖 Story 1.1 的表与端口。
> **交付**：评论查询的两条过滤 **R1（按查看者）+ R2（影子评论，按内容作者）** + 评论数口径。
> ⚠️ **本 story 含高风险点 R2**：判据是「**内容作者**」不是「当前查看者」。做成按 viewer 过滤 → 第三方仍然看得到，**等于没做**。
> ⚠️ **本 story 有三处「写法差一点就全错」**，见 Dev Notes 开头。R1 与 R2 的「作者自视豁免」**处理方式不一样**，这是最容易做反的地方。

## Story

As a **拉黑了某人的用户**,
I want **他的评论从我看到的所有评论区消失，而且他在我内容下的评论对所有人都不显示**,
so that **我不用再看见他，也不会出现「全平台都看得见、唯独我看不见因而删不掉」的攻击性评论**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package`）· **L1**（Docker postgres 真跑）。本 story 无 L2。
> 云端只跑 L0；**L1 留本地**，在 Completion Notes 标注。

### AC1 — R1 按查看者隐藏（L1）

**Given** 查看者 A 已隐藏 B（**主动拉黑或举报，两种来源都算**，不区分 `source`）
**When** A 请求任何内容下的评论列表
**Then** B 的评论**对 A 不展示**
**And** 隐藏方式是**直接不展示该条**，不占位、不显示「该内容已隐藏」占位符（A-A5）
**And** 对其他人的可见性**无影响**
**And** 该条件写在**四个评论查询方法**的 JPQL 内：`findTopLevel` / `findReplies` / `findRepliesForParents` / `countVisibleForViewer`
**And** ⚠️ 新条件与既有的「作者自视」括号**并列 `AND`**，**绝不塞进那个 `OR` 括号里**（见 Dev Notes 陷阱 ①）

### AC2 — ⚠️ R2 影子评论判的是内容作者（高风险点 R2）（L1）

**Given** 内容作者 A 已隐藏 B，第三方 C 与谁都无隐藏关系
**When** B 在 A 的内容下发表评论
**Then** **A 看不到、C 也看不到**，**只有 B 自己看得到**
**And** R2 的判据是 `holder = 该内容的作者`，**不是 `holder = 当前查看者`**
**And** 内容作者 id **由 service 作为参数传入查询**，不在 SQL 里 join 内容表（AD-3）
**And** R1 与 R2 两条件**独立并列**，任一命中即隐藏

> ⚠️ 做成按查看者过滤 → 第三方仍然看得到，**等于没做**。验收必须**三个视角各看一遍**（A / B / C）。

### AC3 — 影子评论对评论者本人无感知（L1）

**Given** B 的评论已被 R2 影子
**When** B 自己查看该内容的评论区
**Then** 他看到**自己那条评论正常展示**，与发布成功的状态完全一致
**And** **无任何失败提示、无视觉差异、无标记**
**And** B **能看到他人对他那条的回复**

> ⚠️ **这一条决定了 R2 的 SQL 写法与 R1 不同**：R2 的 `NOT EXISTS` 必须**放过 `c.authorId = :viewerId` 的行**（即评论作者本人自视豁免），而 R1 不需要这层豁免（R1 是「我不看」，作者本人天然不受影响）。**两条的豁免处理不对称，是本 story 最容易做反的点。** 见 Dev Notes 陷阱 ②。

### AC4 — 回复串随父一并隐藏（L1）

**Given** B 的一条评论被 R2 影子，C 回复了 B 那条
**When** A 或第三方查看评论区
**Then** **B 那条与 C 的回复一并不展示**，不论回复者是谁
**And** R1 同理：被 R1 隐藏的评论，其回复串对该查看者一并隐藏
**And** 不出现「回复了某条看不见的评论」的孤儿回复

### AC5 — 评论数口径（L1）

**Given** 某内容下有 5 条评论，其中 1 条被 R2 影子
**When** 第三方查看该内容
**Then** 对外展示的评论数为 **4**，与实际渲染出的条数一致
**And** 被 R2 影子的评论**及其回复串不计入对外评论数与互动量统计**
**And** **被 R1 隐藏的评论照常计入评论数**（R1 只是「我不看」，该评论对平台真实存在且公开可见）
**And** 评论作者本人视角下数字比他人多 1（影子机制固有特性，可接受）
**And** ⚠️ **两条计数口径都要处理**：详情页的 `commentCount`（`countVisibleForViewer`）与一级评论的 `replyCount`（`findRepliesForParents` 的返回条数）—— 见 Dev Notes「两条独立的计数口径」
**And** ⚠️ **运营看板的 `countByRealAuthor()` 不套 R1/R2**（那是平台口径，与 viewer 无关）

### AC6 — 被拉黑方仍可「评论成功」（L1）

**Given** B 被 A 拉黑
**When** B 在 A 的内容下提交评论
**Then** 接口**返回成功**，界面表现与正常评论完全一致
**And** 评论**正常落库**，只是读取时被 R2 过滤
**And** 写路径（`CommentService`）**一行不改**

### AC7 — 下游口径同步（L0）

**Given** 本 story 确立的评论数口径
**When** 后续任何依赖评论数或互动量的功能被开发
**Then** 该口径已在代码注释与 `CROSS-STORY-DECISIONS.md` 中留痕，避免影子评论被当作真实互动信号

### AC8 — 不做的（L0）

**Given** 本 story 范围
**Then** **不做** Instagram Restrict 的「查看 / 批准」二次操作——内容作者不需要能看到、也不需要能放行被影子的评论
**And** **不新增任何 DTO 字段** —— R1/R2 是纯隐藏（行不返回）。⚠️ 契约金标测试用 `isEqualTo(Set.of(...))` 精确锁死了 `CommentResponse` 的 10 个键与 `ContentDetailResponse` 的 13 个键，**加字段会立刻变红且需三方同步**

### AC9 — 护栏（L0）

**Given** 本 story 的实现
**Then** 过滤**全部写在 JPQL `WHERE` 内**，禁止取回后在 Java 侧 filter（AD-5）
**And** 未引入 MQ / 缓存 / 新中间件
**And** 日志中不出现评论正文等 PII
**And** `mvn -B package` 全绿

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段对 `petgo-backend` 的实证扫描。

### 🔴 三处「写法差一点就全错」

#### 陷阱 ① — 新条件塞错位置，会让「作者本人」绕过拉黑过滤

既有过滤是一条 **`OR`（放行式）** 条件，四条 JPQL 里**逐字相同**：

```sql
AND (c.moderationStatus = com.tailtopia.content.domain.CommentModerationStatus.VISIBLE
     OR (:viewerId IS NOT NULL AND c.authorId = :viewerId))
```

语义是「**公开可见 或 是我自己写的**」。

**➜ 新的 R1/R2 必须写成与整个括号并列的 `AND NOT EXISTS`：**

```
AND ( 既有的 VISIBLE OR 自己 括号 )      ← 原样不动
AND NOT EXISTS ( R1 … holder = :viewerId … )
AND NOT EXISTS ( R2 … holder = :postAuthorId … )
```

**一旦塞进那个 `OR` 括号里面，「作者本人」这条 OR 支路就会绕过拉黑过滤** —— 编译通过、大部分场景也正常，只在「被隐藏者恰好是评论作者本人」时暴露。

#### 陷阱 ② — R1 与 R2 的「作者自视豁免」处理**不一样**

| | R1 | R2 |
|---|---|---|
| 判据 | `holder = :viewerId` | `holder = :postAuthorId` |
| 语义 | 「我不看」 | 「让我的地盘干净」 |
| **评论作者本人自视** | **不需要豁免** —— 我不会拉黑我自己，天然不受影响 | ⚠️ **必须豁免** —— 被 R2 影子的人**要能看见自己那条**（AC3「无感知」的前提） |

**➜ R2 的 `NOT EXISTS` 需要放过 `c.authorId = :viewerId` 的行。**
写成对称的两条 `NOT EXISTS` 会让被影子者自己也看不见自己的评论 → **直接破坏「无感知」，对方立刻知道被屏蔽了**。

#### 陷阱 ③ — 42P18：游客分支不能裸判空

照抄 `findFeed` 的既有形状（`ContentPostRepository`）：

```java
AND (:hasViewer = false
     OR NOT EXISTS (SELECT 1 FROM ContentReport r
                    WHERE r.postId = p.id AND r.reporterId = :viewerId))
```

方法 Javadoc 写明原因：裸 `:x IS NULL` 会让 PG 推不出 NULL 参数类型（**42P18 could not determine data type**）。

⚠️ 注意评论侧既有条件用的是 `:viewerId IS NOT NULL`（不是裸 `IS NULL`），它能定型是因为紧接着与 `c.authorId`（bigint 列）比较。**新增的 `NOT EXISTS` 若把 `:viewerId` 放在没有列比较的位置，仍会踩 42P18** —— 稳妥做法是沿用 `:hasViewer` 布尔标志。

### 📌 对架构 AD-3 的一处订正（实证）

> **AD-3 原文**：「`:postAuthorId` 由 service 传入：`CommentQueryService.requireVisiblePost(postId)` 已 `findById(postId)`，作者是现成的；`replies(parentId)` 分支经 `Comment.postId` 反查一次。」

| 半句 | 实证结论 |
|---|---|

**➜ 写工时评估时不要照抄「已现成」的措辞。** `topLevel` 分支几乎零成本，`replies` 分支要新增查询。

### 两条独立的计数口径，都要同步（AC5）

| 口径 | 来源 | 展示位置 |
|---|---|---|
| `commentCount` | `countVisibleForViewer(postId, viewerId)` | **仅详情页两处**：`content_detail_page.dart:135`（「评论 (N)」小节标题）与 `:237`（底部互动条） |

### `comments` 表结构

**建表** `V9__init_comments.sql`：`id BIGSERIAL PK` / `post_id` / `parent_id`（**自引用 FK**，NULL=一级、非空=二级）/ `author_id` / `body VARCHAR(1000)` / `deleted_at` / `created_at` / `updated_at`。

**三次 ALTER**：`V49` 加 `moderation_status`（默认 VISIBLE）+ `content_version`；`V56` 扩 CHECK 容纳 `AUTHOR_DEACTIVATED`；`V94` 把 `moderation_status` 加宽到 `VARCHAR(32)`（`AUTHOR_DEACTIVATED` 18 字符溢出 varchar(16) 的线上 bug 20260724-360）。

**三级由 service 层强制归并**，DB 无约束阻止。

**索引**：`idx_comments_post_toplevel (post_id, created_at, id) WHERE parent_id IS NULL` · `idx_comments_parent (parent_id, created_at, id)` · `idx_comments_moderation (post_id, moderation_status)`。

⚠️ **`author_id` 上无索引**（PG 不为 FK 自动建索引）。但 R1/R2 的 `NOT EXISTS` 是拿 `comments.author_id` 当参数去打**新隐藏关系表**的索引，所以**关键索引在新表上**（Story 1.1 已建 `idx_user_hide_relations_holder_target`），`comments.author_id` 侧**无需新增索引**。

**本 story 无 Flyway 迁移** —— 不改表结构。

### DTO 不加字段（AC8）

`CommentResponse` 是 record，作者投影**摊平**为 `authorNickname / authorAvatarUrl / authorDeleted`（不嵌套 `AuthorView`）：

```java
public record CommentResponse(
        Long id, long authorId, String authorNickname, String authorAvatarUrl,
        boolean authorDeleted, String body, Instant createdAt,
```
