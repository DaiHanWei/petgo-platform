# Story 3.2: 运营能给出警告或封号，用户也真的收得到

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **所属**：V1.1.4 Epic 3 第二个 Story（**后端 + 运营后台**）。
> **交付**：警告 / 封号两档处置 · 处置记录落库 · 用户侧通知。
> ✅ **AC9 的法务阻塞已解除（2026-08-16，C-101）** —— 封号通知措辞经法务审核通过。**仍有两条印尼语待运营产出**（警告通知 · FR-51 回告），但**不再阻塞发版**。
> ⚠️ **含高风险点 R5 的服务端侧**：封号 ≠ 注销，两者命名几乎一样而要求正好相反。
> ⚠️ **实证发现两处 epics 未预料的工作量**，见 Dev Notes：① **封号通知 type 当前不存在**，要新增枚举值 + 写 Flyway 迁移；② **停用不作废 access token**，「即时无法登录」有既有缺口。

## Story

As a **运营人员**,
I want **对一条工单执行警告或封号，并留下可追溯的处置记录**,
so that **违规的人受到实际处置，而我下次再遇到这个人时一眼能看到他已经被警告过几次**。

## Acceptance Criteria

> **验证层**：**L0**（`mvn -B package` / 门控测试）· **L1**（Docker postgres 真跑）· **L2**（后台页面，⚠️ 无 UI 稿基准）。

### AC1 — 两档处置动作（L1）

**Given** 一条待处理工单
**When** 运营执行处置
**Then** 可选**警告**或**封号**，两者**可组合使用**
**And** **不提供「限流曝光」选项，也不为它预留 UI**（该动作依赖推荐算法打分链路，随 FR-95 移至 1.1.8）

### AC2 — 处置必先落记录，且同一事务（L1）

**Given** 运营点击警告或封号
**When** 执行
**Then** **先写入 `account_disposals` 一行**（被处置账号 / 类型 / 处置人 / 关联工单 / 时间），**再触发用户侧后果**
**And** 写记录与触发后果**在同一事务内**

> ⚠️ 不同事务会出现「**用户登不上了，但工单页显示从没处置过**」—— 既有停用链路自带审计留痕，处置记录必须与它同生共死。
> ✅ **既有停用链路本就是同事务的**（`AdminUserService.deactivate` 上有 `@Transactional`，内部依次调 `authService.deactivateUser` → `consultInterrupt.interruptByUser` → `auditService.record`）。本 story 只需把 `account_disposals` 的写入插进这个事务。

### AC3 — 警告的完整定义（L1）

**Given** 运营对某账号执行警告
**When** 处理完成
**Then** 用户收到**一条系统通知**，中文语义为「你的账号因违反 TailTopia 社区规范收到一次警告，请遵守社区规范」
**And** 通知**不告知**是谁举报的、因哪条内容、也不告知这是第几次警告
**And** 警告**不影响用户使用** —— 能登录、能发内容、内容可见性不变
**And** 警告**不需要异议渠道**（不引导联系客服，与封号不同）

### AC4 — 警告可重复、不合并、不自动升级（L1）

**Given** 同一账号被多次警告
**When** 每次执行
**Then** **每次都发一条独立通知，不做合并、不做去重**
**And** **每次都写入一行处置记录**，工单页的「历史处置次数」相应递增
**And** 警告累计到**任何次数都不会自动触发封号、也不会自动置顶工单**
**And** 是否升级**完全由运营看到历史记录后人工判断**

### AC5 — 封号的后果与告知（L1）

**Given** 运营对某账号执行封号
**When** 处理完成
**Then** 该账号状态置为运营停用，**即时无法登录**，refresh token 一并撤销
**And** 用户收到系统通知，中文参照「你的账号因违反 TailTopia 社区规范已被停用。如有异议，请联系客服团队。」
**And** 异议走 **FR-52 通用客服工单**，由客服按个案人工判断
**And** **不建立独立的申诉审核工作流或 UI** —— 客服只是唯一的异议反馈渠道
**And** ⚠️ **「即时无法登录」的既有实现有一处缺口**：停用只删 refresh 行 + 置状态位，**已签发的 access JWT 在其自然过期前仍可用**（无黑名单）。**本 story 沿用既有行为**，但须在 Completion Notes 记录该取舍

### AC6 — ⚠️ 封号不等于注销（高风险点 R5 的服务端侧）（L2）

**Given** 被封号的账号
**When** 检查其在各处的表现
**Then** 其**存量内容不因封号而全部删除**
**And** 该账号在**其他用户的黑名单里照常展示、不做特殊标记、仍可被拉黑**
**And** 封号**不触发**任何注销才有的匿名化处理

> ⚠️ 代码里「运营停用」（`UserStatus.DEACTIVATED`）与迷你卡投影的「已注销」（`User.deletedAt` → `AuthorView.deleted`）命名几乎一样，而本版本对两者要求**正好相反**。**以中文定义为准，不要凭字段名推断语义。**
> ✅ **实证：后端 `AuthorView` 只有 `deleted` 一个字段，根本不下发「是否被封号」** —— 所以「黑名单里照常展示」**前端什么都不做就自动满足**。本 AC 的价值在于**阻止有人「顺手」加标记**。

### AC7 — 工单状态流转（L1）

**Given** 工单被处置或驳回
**When** 状态更新
**Then** 工单状态相应流转（已处理 / 已驳回），记录处理人与处理时间

> ⚠️ **数据层与展示层要分清（C-103）**：**工单内部状态名与「驳回」这个动作一律不改** —— 对举报而言「驳回」是准确的（驳的是举报人的主张），既有 `ReportStatus.DISMISSED` 枚举、「驳回」按钮、「批量驳回」按钮**全部保持原样**。
> **改的只有统一视图的状态筛选档标签**：第三档展示为**「无需处置」**而不是「已驳回」，因为那一档现在同时装着「举报不成立」与「账号标识字段审核通过」两类，后者没有请求方可驳。
**And** 若该账号**之后又被举报**，同一条工单**翻回待处理**（Story 2.1 AC9），而**历史处置记录不受影响、照常累计**

### AC8 — 零自动处置的回归确认（L1）

**Given** 任意数量的用户举报同一账号
**When** 举报累积
**Then** **系统不会自动执行警告或封号**，也**不会自动挂起该账号的内容**
**And** 所有处置**均需运营确认**

### AC9 — 文案（法务已闭环，两条印尼语待运营）（L0/L2）

**Given** 警告通知与封号通知的印尼语措辞
**When** 实现
**Then** ✅ **封号通知的印尼语已经法务审核通过（2026-08-16，C-101）**，可直接落 ARB：<br>`Akun Anda telah dinonaktifkan karena melanggar Pedoman Komunitas TailTopia. Jika Anda ingin mengajukan keberatan, silakan hubungi tim dukungan pelanggan kami.`
**And** ⚠️ **警告通知的印尼语尚未产出**（待运营），代码可先完成、文案位留出，**上线前收口**
**And** 该待办**不阻塞发版**（法务阻塞已解除）

### AC10 — 护栏（L0）

**Given** 本 story 的实现
**Then** ⚠️ **新增通知 type 的 Flyway 迁移必须基于 `V97` 的完整 19 值追加**（见 Dev Notes）
**And** 未引入 MQ / 缓存 / 新中间件
**And** 处置记录与既有审计链路**双留痕**（`account_disposals` + `admin_audit_logs`）
**And** 新权限码已补三份 i18n 并加进 `AdminPermissions.GROUPS`
**And** `mvn -B package` 全绿

## Dev Notes

> ⚠️ 本节代码事实来自 CS 阶段实证扫描。

### 🔴 两处 epics 未预料的工作量

#### ① 封号通知 type 当前**不存在** —— 要新增枚举 + 写 Flyway 迁移

**实证**：`NotificationType` 的 19 个值里**没有任何封号/警告类**；`admin` 包内 ban/suspend 逻辑与 notify **无交集**。
**➜ V1 的封号处置根本不发站内通知。** AC3/AC5 要求发通知，**是新增能力**。

`notifications` 表自 `V19` 建表后**没有任何 ADD COLUMN 型 ALTER** —— 后续 6 个迁移全是 `DROP CONSTRAINT ck_notifications_type` + `ADD CONSTRAINT` 重建白名单：

| 迁移 | 新增值 |
|---|---|
| `V21` | `PET_BIRTHDAY`, `COMPANION_ANNIVERSARY`, `MILESTONE_NODE` |
| `V40` | `CONTENT_REMOVED`（补漏）, `REPORT_REVIEWED` |
| `V43` | `CONTENT_REVIEW_APPROVED`, `CONTENT_REVIEW_REJECTED` |
| `V53` | `NAME_RESET`, `AVATAR_RESET`, `CONTENT_REVIEW_TIMED_OUT` |
| `V72` | `REFUND_REJECTED`, `TICKET_RESOLVED`, `CSAT_SURVEY`, `IDENTITY_REQUIRE_MODIFY` |
| **`V97`** | **两条工作线并集重建，为当前权威的 19 值** |

⚠️ **必须基于 V97 的完整 19 值追加**，否则会重蹈 **V72 覆盖审核线三值**的覆辙。

#### ② 「即时无法登录」有既有缺口 —— access token 不作废

`AuthService.deactivateUser`：

```java
@Transactional
public void deactivateUser(long userId) {
    User user = users.findById(userId).orElseThrow(() -> AppException.notFound("用户不存在"));
    user.deactivate();                                              // 置 UserStatus.DEACTIVATED
    users.save(user);
    refreshTokens.deleteByUserIdAndSubjectType(userId, SubjectType.USER);  // 撤销点：物理删 refresh 行
}
```

刷新端有二次门控：

```java
if (!user.isActiveStatus()) {
    throw AppException.forbidden(DEACTIVATED_MESSAGE);
}
```

**➜ 只删 refresh 行 + 置状态位，已签发的 access JWT 在其自然过期前仍可用（无黑名单）。**
本 story **沿用既有行为**（不新建 token 黑名单，那是独立议题），但 **AC5 要求在 Completion Notes 记录这个取舍** —— 否则验收时「即时无法登录」这句话会被当成没做到。

### 既有停用链路（可复用，但注意一处副作用）

```java
@Transactional
public void deactivate(long userId, String reason, long actorAccountId) {
    if (reason == null || reason.isBlank()) {
        throw AppException.validation("停用原因不能为空");     // ⚠️ 原因必填
    }
    accountQuery.findUserById(userId).orElseThrow(() -> AppException.notFound("用户不存在"));
    authService.deactivateUser(userId);
    consultInterrupt.interruptByUser(userId);                  // ⚠️ 强关进行中问诊会话
    auditService.record(actorAccountId, AuditActions.USER_DEACTIVATED, "USER",
            String.valueOf(userId), "停用用户（原因：" + reason.trim() + "）");
}
```

**三点注意**：
1. ⚠️ **原因必填**（空白直接 400）—— 从工单页封号时要带上原因，或另开一个不校验原因的路径
2. ⚠️ **会强关进行中问诊会话** —— 若从举报工单封号也走这条，这个副作用会一并发生。**需确认产品是否接受**
3. ✅ **已是 `@Transactional`** —— `account_disposals` 的写入插进这个事务即可满足 AC2

### `violation_counts` 为什么不复用（架构 AD-10 的判断是对的）

```sql
CREATE TABLE violation_counts (
    account_id          BIGINT      NOT NULL,
    violation_type      VARCHAR(16) NOT NULL,           -- POST / COMMENT / NAME / AVATAR
    violation_count     INTEGER     NOT NULL DEFAULT 0,
    first_violation_at  TIMESTAMPTZ,
    last_violation_at   TIMESTAMPTZ,
    ...
    CONSTRAINT uq_violation_counts_account_type UNIQUE (account_id, violation_type)
);
```

**它是纯聚合计数快照** —— 没有单条处置记录、没有时间线、**没有处置类型/操作人/关联工单**。实体 javadoc 明写「**仅记录、不处置** —— 不进任何审核/发布/风控判定链」。

**➜ 天然承载不了「上次什么时候因什么警告的」这类信息**，`account_disposals` 是必要的新表。
⚠️ 若产品另要求账号举报判定成立也计入违规计数，那需要扩它的 `ck_violation_counts_type` —— **需产品明确表态，不要自作主张**。

### 审计现状

`admin_audit_logs` 是 **append-only 哈希链**（`prev_hash` + `row_hash`，DB 触发器阻断 UPDATE/DELETE）。写入唯一入口 `AdminAuditService.record`，`@Transactional(REQUIRED)`（业务回滚则审计一并回滚，无悬挂审计）。

⚠️ **`record` 内有 `chainLock.acquire()`（Postgres advisory 锁）串行化** —— 单条处置无所谓，但 **Story 3.3 的批量处置会是 N 次取锁 + N 次链尾查询**，那里要注意规模成本。

**账号级处置目前的留痕只有 `admin_audit_logs` 里的一行中文 detail**（`USER_DEACTIVATED`，detail 含运营填的原因），**无结构化字段** —— 这正是 `account_disposals` 的立项理由。

---

### 后台动作按钮的既有能力

`admin.js`（全文仅 61 行，原生 JS + 事件委托，**无框架**）提供：
- **`data-confirm`**：表单带该属性时提交前弹 `window.confirm`，取消则阻止提交 ← **危险操作二次确认直接用它**
- **`data-open-dialog` / `data-close-dialog`**：原生 `<dialog>` 开关（人工审核的拒绝弹窗就是范例）← **若封号要填原因，用这个**
- `data-lightbox` 图片灯箱 · `.toast` 自动消失

⚠️ **没有全选/选中计数/表格排序/AJAX 提交** —— 那些是 Story 3.3 要新写的。
