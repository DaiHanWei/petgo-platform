**AC1（前置实测）结论：假设成立 —— Tab 切换确实不产生浏览事件。**

`goBranch` 在 `StatefulShellRoute.indexedStack` 内部切换 branch 的 `IndexedStack` index，
**不产生任何 `Route` 的 push/pop**，而 `PosthogObserver` 只挂在 `NavigatorObserver` 的
`didPush`/`didPop`/`didReplace` 上 —— 收不到就不会有 `$screen`。因此
`architecture-v1.1.2-delta.md#§8` 的 `[ASSUMPTION]` **无需修改**，实现走「手动上报」路线。

⚠️ 遗留给你的一步：**PostHog 后台的眼见为实（J1）**本地/真机跑一遍即可确认到达，
本轮属 L1，未执行。代码级结论不会因此变化，后台核对只是验证「事件确实送达且属性完整」。

**AC2 的实现选择**：除 `tab_switched` 外，另加一条显式 `$screen`（`Analytics.screen()`），
屏名 `tab_<AppTab.name>`；冷启动落地用**同一套字面量**（`_landingScreenNames`），
否则「冷启动落在 Diary」与「切到 Diary」会被算成两个不同页面。
详情页仍由既有 observer 自动上报，两条通路不重复（observer 只在 push 时触发，goBranch 不触发）。

**事件命名已按「产品一眼可读」重做（2026-08-04 第二轮，用户要求）**：
格式统一为 `<模块前缀>_<对象>_<动作>`，模块前缀用**产品叫法**。
改掉的反例：`tab_switched`（分不清底部导航还是页内 Tab）、`diary_sync_toggled`
（听着像 Diary 页上的开关、其实在发布页）。
⚠️ 顺带修掉一个会让看板读不懂的坑：`AppTab` 的枚举名与产品叫法**并不对应**
（`profile` 其实是 Diary、`triage` 其实是 Health、`home` 其实是 Discovery），
直接送枚举名会出现「进入 home」却指 Discovery。现由 `AppTab.analyticsName` 统一映射。
规范由测试守着（前缀 / 后缀白名单断言），起名不合规会红。

**AC3 的两处口径与 story 原文不同（有意，看板以实现为准）**：
1. `user_state` 取值用 `AppUserState.wire`（`guest`/`vet`/`owner_with_profile`/
   `owner_without_profile`/`planning`/`enthusiast`），而非 AC3 表里的 `A_with_profile`/`B`/`C`。
   语义等价，但**与 Story 2.4 的落地矩阵天然同源**（Dev Notes 明确要求不另写一份判定），
   且可读性更好。已在埋点文档 §8.3 标注「看板配置以此为准」。
2. T-4 的 `source` 词表在 AC3 三值之外多一个 `header_entry`：Story 2.2 AC8 列举「三个入口」时
   漏了页头的四个入口（编辑资料/身份证/健康记录/里程碑），它们确实也走建档引导。
   仍是**同一个事件名 + source**，不拆事件（拆了转化率分母会碎）。

**T-7 移到前端实现（原 B1 后端）**：`entry_source` 只有前端知道（是游客态 Diary 引导来的、
还是 FR-0B 浮层来的、还是登录页直登），而后端至今零埋点 SDK。给后端引入 PostHog 客户端
属于「新增依赖」，护栏要求先经你决策 —— 故改由前端在**注册真正成功**处上报（取消/失败都不报）。
取值：`diary_cta` / `soft_login` / `other`。

**T-12 与 AC5 已补做（2026-08-04 第二轮，用户拍板「后端要埋点」）**：

- **没有引入第三方 SDK**。PostHog 的 capture 就是一个 HTTP POST，用既有 `RestClient`
  十几行够了；引 SDK 要多背一条供应链依赖 + 它自带的后台线程池，与「异步只用 `@Async`、
  不加中间件」的护栏也别扭。故实现为 `AnalyticsClient`（接口）+ `PostHogAnalyticsClient`（HTTP）。
  **这一点与用户原话「要 SDK」有出入，已在交付说明里讲清**：能力等同，依赖为零。
- 挂在既有领域事件 `MilestoneCompletedEvent` 上（`@TransactionalEventListener` + `@Async`），
  不动 `MilestoneCompletionService` 那段「幂等写入 + 不可撤销」的核心逻辑。
  **提交后才上报**：事务回滚了看板上却多一条达成，比没有更糟。
- `MilestoneCompletedEvent` 追加 `source` 字段（notify 侧不读它）—— 这是判定 `path` 的唯一输入。
- `path` 由纯函数 `MilestoneAnalyticsPath` 映射：落库的 source 只有三值
  （SYSTEM_AUTO/USER_CHECKIN/PUBLISH），而产品要区分的是「由什么点亮的」，两个口径不同，
  不能直接把 source 名当 path 用。M5→consult、其余健康类→health_record、其它自动→system_auto。
- **AC5 线上校验成立**：健康类 + `path=checkin` 这个组合刻意**不做改写**照实上报 ——
  改写等于把护栏失效的现场擦掉。有专门断言守着（`healthPlusCheckinIsNotRewritten`）。
- 凭证 `POSTHOG_SERVER_KEY` env 注入，**留空 = 整个服务端上报静默关闭、不出网**（测试与本地默认态）。
- `distinctId` 与前端**逐字一致**（`sha256("tailtopia-user-"+id)`），两端各钉一条同样的已知向量 ——
  差一个字节，「点了按钮」（前端）与「达成里程碑」（后端）就拼不到同一个人身上。

**AC6 核查结论**：FR-0H 提示条本体已在 Story 2.3 整条废止，代码里**无残留事件**
（`profile_prompt_*` / `profile_banner_*` 一个都不存在），无需清除动作。

**AC8**：零新依赖 —— 复用既有 `Analytics` 门面（PostHog 已接入），新增的只有一个
`screen()` 方法和一个 `@visibleForTesting` 的测试观察钩子 `debugCaptureSink`。
该钩子挂在 `scrub()` **之后**，所以测试断言看到的就是端上真正发出的形态；
生产路径恒为 null。

**顺手补掉的既有缺口**：埋点文档 §7.5 记的「无埋点单测」—— 本 story 建了
`test/analytics/`，14 例锁死命名规范、取值词表、单一事件不被拆、曝光埋点位于 session 去重之后。
