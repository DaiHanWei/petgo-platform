# Story 1.1: 健康记录与档案字段迁移（后端）

Status: ready-for-dev

> 版本 v1.5.0 · 会话 ① 健康记录提醒 · 分支 `feat/1.5.0-health-reminder`
> 口径优先级：CROSS-STORY-DECISIONS「2026-11-14 V1.5.0 六会话共用地基」> `planning-artifacts/v1.5.0/architecture-v1.5.0-health-reminder-delta.md`（§0 Z-9/Z-10/Z-14、§1.1、§1.2、§6.1、§6.2）> PRD FR-158/159/160/161/162/168 > UI 稿。
> 范围层：**只后端**。规则计算（预填、显示状态、关键词匹配）归 1.2；回填归 1.3。本 story 只把字段、类型、读写通路与事件铺好。
> 迁移（预分配，不得另取）：`V20261115_0100__health_records_reminder_fields.sql`、`V20261115_0110__pet_profiles_health_status_fields.sql`。

## Story

As a 宠物主人,
I want 健康记录和宠物档案能存下 Next date、疫苗预设、剂次、驱虫类型、产品时长、Kontrol dokter 类型，以及绝育 / 家里有猫 / 怀孕哺乳状态,
so that 后续的提醒、预填和安全提示有数据可依，且旧版 App 照常能用。

## Acceptance Criteria

> 层级：`[L0]` 单元 / 静态（云端可跑）· `[L1]` Docker postgres + redis（本地）· `[L2]` 真机（本地）。

### AC1 — 迁移 `V20261115_0100` `[L0]` `[L1]`
1. 内容**逐字**按架构 §1.1：`health_records` 加 `next_date`、`vaccine_preset`、`dose`(INTEGER)、`deworm_type`、`product_duration_months`(INTEGER)、`record_origin`（存量落 `BACKFILL`，之后默认 `APP`）；DROP + ADD 重建 `ck_health_records_type`（全集 = V76 的 5 值 + `VET_VISIT`，开工先 `grep -l "ck_health_records_type" petgo-backend/src/main/resources/db/migration/*.sql` 确认 V76 之后无人重建过；有则以最后一条为基数）；新增 5 个 CHECK 与索引 `ix_health_records_pet_type`。
2. 文件头注释：值来源、核对日期、「禁 SMALLINT」原因、`record_origin` 三值含义。
3. **不碰** `ck_notifications_type`（地基所有）。

### AC2 — 迁移 `V20261115_0110` `[L0]` `[L1]`
1. 按架构 §1.2：`pet_profiles` 加 `cat_in_home BOOLEAN`、`pregnant_nursing BOOLEAN NOT NULL DEFAULT FALSE`、`pregnant_set_at TIMESTAMPTZ`、`sex_set_at TIMESTAMPTZ`。不回填。

### AC3 — 实体与枚举 `[L0]`
1. `HealthRecordType` 末尾追加 `VET_VISIT`（不改既有顺序）；`HealthRecordService.parseType` 报错文案同步。
2. 新枚举 `VaccinePreset`（10 值，含标签常量，见架构 §3.1）、`DewormType`（4 值）放 `profile.domain`；`RecordOrigin`（APP / LEGACY_APP / BACKFILL）。
3. `HealthRecord` 实体加对应字段（`Integer` / `LocalDate` / 枚举 `@Enumerated(STRING)`，长度与列一致）；`PetProfile` 加 `catInHome`(Boolean)、`pregnantNursing`(boolean)、`pregnantSetAt`(Instant)、`sexSetAt`(Instant)。
4. `ddl-auto=validate` 下能启动（L1 验）。

### AC4 — 健康记录读写分流 `[L0]` `[L1]`（架构 §6.1，PRD FR-168「Old app versions」）
1. `HealthRecordCreateRequest` / `HealthRecordUpdateRequest` 末尾追加 `vaccinePreset`、`dose`（`@Min(1) @Max(5)`）、`dewormType`、`productDurationMonths`（只允许 1/3/8）、`nextDate`、`clearNextDate`(Boolean)。保留现有构造器的兼容重载（现有调用方 / 测试不改）。
2. `HealthRecordController` 三个写端点与列表端点读 `@RequestHeader(value = ClientAppVersion.HEADER, required = false)`，传 `ClientAppVersion.isV150OrLater(header)` 进 service。
3. **1.5.0 客户端**：
   - DEWORM 必须带 `dewormType`（新建与编辑都要，编辑一条存量无类型记录时哪怕只改备注也要）→ 否则 `AppException.validation`（ProblemDetail 400）。HEARTWORM 对非 DOG 宠物 → 400。
   - VACCINE：`vaccinePreset` 可空；`vaccinePreset=OTHER` 或物种非 CAT/DOG 时 `vaccineName` 为自由文本；`dose` 只在系列预设（F3/F4/FELV/PUPPY_DP/COMBO_DHPPI_L/LEPTO）上落库，其余预设一律存 null。
   - `productDurationMonths` 只在 EXTERNAL 落库（缺省 1）；FLEA_WORM 恒 null（规则里按 1 个月算）。
   - `nextDate`：给值 → 校验 `eventDate < nextDate ≤ eventDate + 3 年`（否则 400）；`clearNextDate=true` → 存 null；两者都没给 → 新建不设、编辑不改。
   - `VET_VISIT`：只有 eventDate / note / nextDate 有意义，其余字段忽略。
   - 新建 `record_origin = APP`；编辑一条 `BACKFILL` 记录且请求里给了 `nextDate` 或 `clearNextDate=true` → 改为 `APP`（用户亲手定过日期，不再「回填静默」）；其余编辑不改 origin。
4. **旧版客户端**（无头 / <1.5.0）：新建写 `record_origin = LEGACY_APP`；新字段**一律不从请求读**（即使带了也忽略）；编辑时新字段保留原值；`type=VET_VISIT` → 400（旧版发不出，双保险）。默认 Next date、关键词匹配、改名重匹配、改日期重算留给 1.2 / 1.3 接入（本 story 留好调用点 `HealthRecordDefaults.applyForLegacyClient(record, change)`，先空实现 + TODO 引用 1.3）。
5. 列表 `GET`：旧版客户端过滤掉 `type=VET_VISIT`；`HealthListItemResponse` 追加 `vaccinePreset`、`dose`、`dewormType`、`productDurationMonths`、`nextDate` 五个原样字段（`displayNextDate` / `recordStatus` / `nextDateLocked` 在 1.2 加）。
6. 保存 NEUTER（新建，或编辑把类型改成 NEUTER）→ 同一事务把宠物 `neuter_status` 置 `NEUTERED`；删除 / 再改该记录**不回退**（PRD AC16）。
7. 不改限流（30 次 / 分钟）、不改 `@PastOrPresent`（只在 eventDate）。

### AC5 — 宠物档案字段 `[L0]` `[L1]`（架构 §6.2，PRD FR-162）
1. `PetProfileUpdateRequest` 末尾追加 `catInHome`(Boolean)、`pregnantNursing`(Boolean)（null = 不改）；保留现有便捷构造器。
2. `ProfileService.update`：`pregnantNursing=true`（包括 true → true）→ 写 `pregnant_set_at=now`；`false` → 清 `pregnant_set_at`；宠物 sex=MALE 时忽略写入、读出恒 false。`catInHome` 只对 DOG 落库（其他物种忽略）。sex 从 null 首次变为非 null → 写 `sex_set_at=now`。
3. `PetProfileResponse` 追加 `catInHome`、`pregnantNursing`（MALE 恒 false）、`pregnantAutoOffDate`（本 story 先返回 `pregnant_set_at` 的 WIB 日期 + 4 个日历月，`pregnantNursing=false` 时 null）。
4. `neuterStatus` 现有读写不变（null = 没填、UNKNOWN = 不确定，见架构 Z-9）。

### AC6 — 变更事件 `[L0]`（架构 §4.3 触发表）
1. 新增 `profile/event/HealthRecordChangedEvent(long ownerId, long petId, long recordId, Change change, boolean reminderRelevant)`，`Change ∈ {CREATED, UPDATED, DELETED}`；在 create / update / delete 事务内 `publishEvent`（监听方用 AFTER_COMMIT）。update 时 `reminderRelevant` = 除 `note` 外任一字段实际变化（type、vaccinePreset、vaccineName、dose、dewormType、productDurationMonths、eventDate、nextDate、customName）。
2. 新增 `profile/event/PetHealthProfileChangedEvent(long ownerId, long petId, boolean birthdayChanged, boolean sexChanged, boolean neuterChanged, boolean pregnantSetYes, boolean pregnantCleared, Instant changedAt)`；`ProfileService.update` 在任一相关字段变化时发布。NEUTER 记录导致的置 NEUTERED 也发一次（`neuterChanged=true`）。
3. 现有 `HealthRecordCreatedEvent`（里程碑）照旧发，不合并。

### AC7 — 里程碑 G-M2 `[L0]`（架构 Z-10，PRD FR-161 Milestone）
1. `MilestoneAutoEvent` 加 `HEALTH_RECORD_VET_VISIT`；`MilestoneAutoCompleteMap.put(t, HEALTH_RECORD_VET_VISIT, null, null, "G-M2")`；`MilestoneAutoCompleteListener` 的 type → event 映射加 `VET_VISIT`。
2. 守卫测试（如 `MilestoneAutoCompleteMapTest`）同步更新断言，不删不 skip。
