## Story

As a 帖子作者,
I want 在计划时刻收到一条和真人一模一样的点赞（通知、推送、点赞人列表）,
so that 我的冷清帖子会在之后两天把我叫回 App 几次。

## Acceptance Criteria

**AC1 — 派发器 `AutoLikeDispatcher`** `[L0]` `[L1]`（L-6、L-9）
```java
@Scheduled(fixedDelayString = "${petgo.auto-like.dispatch-interval-ms:60000}", initialDelayString = "30000")
public void tick()
```
- 整体 `try/catch RuntimeException` 只 `log.warn` 类名。
- Redis 锁 `lock:auto-like-dispatch`：`SET NX PX 300000`，uuid 比对后删除（Lua 脚本照 `shop/logistics/BiteshipJobLock.java` 在本包内写一个私有小工具 `AutoLikeDispatchLock`，**不要跨包引用**那个包私有类）。拿不到 → `log.debug` 返回。
- 每 tick 按序：
  1. **收口**：`UPDATE auto_like_logs SET status='MISSED', updated_at=now() WHERE status='PLANNED' AND window_end <= now()`；`UPDATE auto_like_runs SET status='DONE', updated_at=now() WHERE status='ACTIVE' AND window_end <= now()`（A-AC45；MISSED 不计失败）。
  2. 开关关 → 返回（已排的会在窗口结束后被第 1 步收成 MISSED）。
  3. 到期行：`status='PLANNED' AND planned_at <= now() AND window_end > now()` 且所属 run `status='ACTIVE'`，按 `planned_at, id` 升序，`LIMIT dispatchBatch`。
  4. `AutoLikeVirtualPool.load()`（2.2）为空 → 所有 ACTIVE run 置 `STOPPED / NO_POOL`，`log.warn(...)`，返回；**不改任何日志行与目标集**（A-AC26）。
  5. 逐条 `processOne(logId, pool)`；单条异常不影响后续（A-AC36）。

**AC2 — 单条处理（一个事务）** `[L0]` `[L1]`（FR-215、FR-216、A-AC35）
`TransactionTemplate` REQUIRES_NEW 内：
1. **认领**：`UPDATE auto_like_logs SET updated_at = now() WHERE id = :id AND status = 'PLANNED'` 返回 0 → 别的实例处理过，直接返回（不计任何数）。
2. **复查帖子**（`ContentPostRepository.findById` + 作者 `UserRepository.findById`）：
   | 情况 | 日志 | 目标集 |
   |---|---|---|
   | 帖子不存在 / `deleted_at` 非空 / `visibility != PUBLIC` / `status == AUTHOR_DEACTIVATED` / 作者不是 `REAL + USER + 未注销 + ACTIVE`（Q-8） | `POST_GONE` | `left_at = now, POST_GONE`（A-AC20） |
   | `status == UNDER_REVIEW` | `SKIPPED_REVIEW` | 不动（A-AC19） |
   | `countByPostId >= likeTarget` | `REACHED_TARGET`，记 `like_count_before` | `left REACHED_TARGET`（A-AC18） |
3. **选号**（FR-216）：`List<Long> already = likes.findLikerIdsAmong(postId, poolIds)`（新 JPQL：`SELECT l.userId FROM ContentLike l WHERE l.postId = :postId AND l.userId IN :ids`）；`filtered = pool − already`；`species = speciesResolver.resolve(post).species()`，空 → `ContentSpecies.GENERAL`（同 `AutoCommentService.speciesOf`）；`identity = picker.pick(filtered, authorId, species)`。`VirtualIdentityPicker` 本身**不改**（隐藏过滤、同物种 → GENERAL → 其余、随机都在它里面）。
   - `identity == null` → `NO_IDENTITY` + `left NO_IDENTITY`（A-AC25），继续下一条。
4. **点赞**：`r = likeService.likeAutomated(postId, identity.getId(), authorId)`：
   - `r.created()` → 日志 `LIKED`：`virtual_user_id`、`like_count_before = r.likeCount() − 1`、`attempted_at = now`；目标集 `last_liked_at = now`；`r.likeCount() >= likeTarget` → `left REACHED_TARGET`（A-AC16、AC17：从不超过 5）。
   - `!r.created()`（该号恰好已赞，并发竞态）→ 日志 `FAILED`、`error_code = 'ALREADY_LIKED'`，**不**加帖子失败数、**不**加连续失败数（Q-2，A-AC21：不写 LIKED、赞数不变）。
5. 结果为非 FAILED（或 `ALREADY_LIKED`）→ 所属 run `consecutive_failures = 0`。
6. 所有结果都写 `attempted_at = now`。

**AC3 — 异常与叫停** `[L0]` `[L1]`（FR-219、L-10、A-AC36 ~ AC38）
- `processOne` 事务抛异常 → 整个事务回滚（赞、日志、目标集一起回滚——日志写不进去则赞也不存在，A-AC35）；随后另开一个 REQUIRES_NEW 小事务：日志 `FAILED`（`error_code` = 异常类名截 64，`attempted_at`）、`auto_like_targets.failed_attempts + 1`、run `consecutive_failures + 1`。
- `consecutive_failures >= stopAfterConsecutiveFailures`（默认 10）→ 同一小事务里叫停：run `STOPPED / CONSECUTIVE_FAILURES`；`UPDATE auto_like_targets SET failed_attempts = failed_attempts - 1 WHERE failed_attempts > 0 AND post_id IN (SELECT post_id FROM auto_like_logs WHERE run_id = :runId AND status = 'FAILED' AND (error_code IS NULL OR error_code <> 'ALREADY_LIKED'))`；本 run 剩余 `PLANNED` → `MISSED`；`log.warn("auto like run stopped after {} consecutive failures", n)`。没有帖子因叫停离开（A-AC38）。
- 小事务本身失败（如库不可用）→ 只 `log.warn` 类名，结束本 tick；行仍是 `PLANNED`，下个 tick 窗口内重试。
- 「第 3 次 FAILED 离开」由 2.1 的 `AutoLikeCheckStep` 在下一轮计划开头执行（Q-4）；本 story 只负责累加。

**AC4 — 通知与推送同真人** `[L1]`（FR-217、A-AC27 ~ AC29、AC31、AC32）
`likeAutomated` 发 `ContentLikedEvent(automated=true)`，事务提交后：作者收到 `CONTENT_LIKED`（未读时与上一条合并、刷新时间、角标不再 +1，推送文案 `{0} dan {1} lainnya menyukai postinganmu`）、10 分钟推送防抖照旧；作者隐藏 / 推送设置照旧生效；宠物 `FIRST_LIKE` 里程碑照常完成；虚拟号成为作者 @ 候选。L1 用 `ApiIntegrationTest` 现有通知断言写法验证通知行与合并键（推送本身不真发，断言调用即可）。

**AC5 — 补发与错过** `[L1]`（A-AC45）
- 10:30 轮：把 now 拨到 11:00 再跑 tick → `planned_at ∈ [10:30, 11:00]` 的全部发出；之后的按各自时刻发。
- 拨到 14:00 再跑 → 未发的全部 `MISSED`，帖子仍在集合、失败数不变。
- 时间：派发器与 SQL 用的 `now` 从注入的 `Clock` 取（仓库没有 `Clock` bean，照 `FollowSuggestionService.java:41-46` 的双构造器写法，`@Autowired` 主构造器默认 `Clock.systemUTC()`），SQL 里写 `:now` 参数而不是 `now()`，以便 L1 拨钟。⚠️ AC1 第 1 步的 SQL 同样用 `:now`。

**AC6 — 与自动评论互不影响** `[L1]`（A-AC3）
`AutoCommentService.runOnce` 抛异常时派发与计划照常；反之亦然（两边 Bean 无依赖，测试里分别让对方抛异常）。

### 为什么同时要 Redis 锁和行级认领
Redis 锁让同一时刻只有一个派发器在扫（省重复劳动）；行级条件 UPDATE 保证就算锁过期或 Redis 抖动，同一行也只会被点一次；`uq_auto_like_logs_post_slot` 保证同一帖同一槽最多一行。三层各兜一种失败。

### 日志口吻
只记数字与类名：`auto like dispatched: due={} liked={} missed={} failed={} tookMs={}`；不记帖子 id 列表、不记昵称、不记正文。
