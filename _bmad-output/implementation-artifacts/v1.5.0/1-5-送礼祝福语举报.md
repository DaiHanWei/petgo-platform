## Story

As a 看到不当祝福语的用户 / 运营,
I want 能举报一条祝福语、运营在现有举报后台处理后隐藏它,
so that 祝福语不做人工复审也能把问题内容收掉。

## Acceptance Criteria

### AC1 — 迁移 `[L0]` `[L1]`
逐字照架构 §3.3。L0：`GiftMessageReportMigrationTextTest`（reason 五值 = `ReportReason` 枚举；status 三值；唯一键）。

### AC2 — 举报接口 `POST /api/v1/gift-orders/{orderToken}/message-reports` `[L0]` `[L1]`
1. body `{reasonType}`（`ReportReason`）；204。
2. 订单不存在 / 非 DELIVERED / 宠物对举报人不可见 → 404；无祝福语、已隐藏、举报人 = 送礼人 → 422 `gift-message-not-reportable`（登记 `ErrorTypes`）。
3. 同人同单重复举报幂等（`ON CONFLICT DO NOTHING`），仍 204。
4. 限流：`RedisRateLimiter` 键 `rl:gift:msgreport:{userId}`，10 次 / 10 分钟（照 `PlaceController.report` 写法）。
5. L1：`GiftMessageReportIntegrationTest`：正常、重复、自举 422、无祝福语 422、限流。

### AC3 — 统一工单分支 `[L1]`
1. `TicketType` 末尾加 `GIFT_MESSAGE_REPORT`（javadoc：源表 `gift_message_reports`，**按订单聚合**）。
2. `UnifiedTicketQueryService` 混排 SQL 加一个 UNION 分支，写法照 `PLACE_REPORT`：分数 = 举报人数；`preview` = 祝福语前 60 个字符（已隐藏的订单不进待处理列表）；`content_ref` = gift order id；`action_ref` = 任一 PENDING 举报 id。
3. 两个动作（Controller 挂在现有统一工单处置路由下，照 PLACE_REPORT 的处置写法与权限码）：
   - 「隐藏祝福语」：同一订单全部 PENDING → ACTIONED、`handled_by/at`；`UPDATE gift_orders SET message_hidden_at = now() WHERE id = :id AND message_hidden_at IS NULL`；审计 `GIFT_MESSAGE_HIDDEN`。
   - 「驳回」：全部 PENDING → DISMISSED；审计 `GIFT_MESSAGE_REPORT_DISMISSED`。
   两个审计常量四语文案（`admin.audit.action.*`）齐全。
4. 筛选下拉 / 类型标签：`admin.ticket.type.GIFT_MESSAGE_REPORT`（或现有 key 规律）三语：中「礼物祝福语」/ EN「Gift message」/ ID「Ucapan hadiah」。工单详情抽屉显示：祝福语全文、礼物名 × 数量、送礼人昵称、收礼宠物名、举报理由分布。
5. L1：`UnifiedTicketGiftMessageIntegrationTest`：举报后进列表、隐藏后 `message_hidden_at` 非空且离开待处理、驳回后离开待处理、详情 / 列表接口随之 `message = null`。

### AC4 — 隐藏的效果 `[L1]`
1-4 的详情 / open 接口在 `message_hidden_at` 非空时 `message = null`、`messageHidden = true`；礼物本身照常显示。
