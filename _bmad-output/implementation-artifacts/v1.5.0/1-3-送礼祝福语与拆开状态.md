## Story

As a 送礼人,
I want 送礼时附一段祝福语，含违规词时在扣款前就被拦下,
so that 礼物有温度，也不会因为文字问题白扣钱。

## Acceptance Criteria

### AC1 — 迁移 `[L0]` `[L1]`
- 内容**逐字**照架构 §3.2：三个新列、长度 CHECK、**全部存量订单** `opened_at = COALESCE(delivered_at, created_at)`、两个部分索引。
- L0：`GiftOrderMessageMigrationTextTest`（列名、CHECK、回填 UPDATE、索引名）。
- L1：迁移前插 DELIVERED / PENDING 各一笔，迁移后两笔 `opened_at` 都非空。

### AC2 — 实体 `[L0]`
`GiftOrder` 加 `message`（`updatable = false`）、`openedAt`、`messageHiddenAt`；`GiftOrder.pending(...)` 增加 `message` 参数（放在 `source` 之前或末尾均可，所有调用点同步改）；新增 `boolean isOpened()`。`@DynamicUpdate` 保持。`opened_at` / `message_hidden_at` 的写入只经条件 UPDATE（1-4 / 1-5 写），实体上不提供 setter。

### AC3 — 送礼请求加祝福语 `[L0]` `[L1]`（D-6）
1. `GiftSendRequest` 末尾追加 `@Size(max = 2000) String message`（可空；`@Size` 只防超大包体，真正上限在服务里按码点算）。
2. `GiftSendService.send` 校验顺序：**幂等重放判断仍在最前**（已有订单 → 不校验、不扣款，原样返回）→ ① ~ ⑨ 原有校验不变 → **⑩ 祝福语**：`trim()`；空串 → `null`；`codePointCount > 500` → 422 `validation`「祝福语不能超过 500 字」；`KeywordRuleEngine.classify(message).l1Blocked()` → 422 `gift-message-blocked`（登记进 `ErrorTypes`）。⑩ 在任何写库之前。
3. 订单落库带 `message`。
4. 响应 `GiftSendResponse` 新增 `int senderExp`（record 末尾追加）：`delivered = true` 时 = 送礼人参与成长体系 ? `pointsForAmount(GIFT_SENT, unitPrice × quantity)` : 0；其他状态 0。QRIS 到账后的 E3 由 App 用目录里的 `senderExp × quantity` 显示（2-3），不再查接口。
5. 日志**不记**祝福语正文。
6. L0：`GiftSendServiceTest` 补：祝福语 501 码点被拒、500 码点（含 emoji 代理对）通过、全空白 → null、命中 L1 → 422 且 `orders.saveAndFlush` / `wallet.debit` 均未调用、L3 白名单豁免通过、重放旧单不校验祝福语。
7. L1：`GiftSendIntegrationTest` 补：带祝福语 PawCoin 送达后库里 `message` 正确、`opened_at` 为空（新订单 = 未拆）；命中敏感词余额不变、无订单行。

### AC4 — 送达不改 `opened_at` `[L0]`
`GiftDeliveryService.deliver` 不写 `opened_at`；新送达订单一律未拆。现有交付测试不受影响。
