# Story 1.5: 运营活动排名结算与发放（后端）

Status: ready-for-dev

> 版本 v1.5.0 · 会话 ⑥ ops-activity · 分支 `feat/1.5.0-ops-activity`
> 口径优先级：`decision-log.md`（11-13：热度按人数、评论同人一次、剔人不剔帖、剔除可撤销、发放失败可重发、排名不设总份数）> PRD §3.5、§3.7、§6「排名结算」、附录 A.1 > 架构 OA-16 ~ OA-18。
> 前置：1-2（执行器、通知器、文案渲染器）、1-4（下架联动名单行）。
> 范围层：**只后端**（任务、名单服务、确认发放、获奖通知）。后台页面归 2-3。

## Story

As a 运营,
I want 排名活动结束后系统 1 小时内按热度生成待发放名单，我核对剔除后一键发放,
so that 「谁的帖子最火谁得奖」不用我自己拉数据、也不会发两次。

## Acceptance Criteria

### AC1 — 名单生成任务 `[L0]` `[L1]`（架构 OA-16）
`B/opsactivity/job/OpsActivityRankBuildJob`：`@Scheduled(fixedDelayString = "${petgo.ops-activity.rank-build-ms:300000}", initialDelayString = "${petgo.ops-activity.rank-build-initial-ms:300000}")`。
1. 扫 `status = 'PUBLISHED' AND grant_mode = 'RANKING' AND rank_state = 'NONE' AND end_at <= now` 的 id（每轮 ≤ 20，按 `end_at`）。
2. 每个活动在独立事务（`OpsActivityRankBuilder.build(id, now)`，REQUIRES_NEW）：`SELECT … FROM ops_activities WHERE id = :id AND rank_state = 'NONE' FOR UPDATE SKIP LOCKED`，拿不到 → 跳过（另一实例在建 / 已建）。
3. 热度 SQL **逐字照**架构 OA-16 第 3 条（`cand / lk / cm / co / scored / best`），参数：活动起止、话题 id 集合、`content_types`；作者资格条件用 1-2 的 `activityEligible` 同口径谓词（以 `au` 为别名的 SQL 片段，常量放 growth 包公开，不复制）。
4. 结果按序写 `ops_activity_rank_entries`（`base_order` 从 1 连续，`score / like_users / comment_users / collect_users / post_created_at`），再调 `reassignRanks`（AC2）；`rank_state = READY`、`rank_built_at = now`；结果为空 → `EMPTY`。
5. 事务失败整体回滚、下一轮重来；日志记活动 id、人数、耗时。
6. L0：`OpsActivityRankSqlTextTest`：SQL 常量包含「`count(DISTINCT l.user_id)`」「`count(DISTINCT m.author_id)`」「`count(DISTINCT k.user_id)`」「`* 1`、`* 3`、`* 2`」「`<> c.author_id`」「`account_type = 'REAL'`」「`created_at <= :end`」「`DISTINCT ON (author_id)`」「`ORDER BY score DESC, created_at ASC, id ASC`」——防止改坏口径。
7. L1：`OpsActivityRankBuildIntegrationTest`：
   - 构造：作者 A 两帖（热度 10、30）、B 一帖 30（比 A 的 30 后发）、C 一帖 5；某帖 1 个人评论 3 条（只算 1 人）；作者自己点赞自己（不算）；虚拟号点赞（不算）；结束后的点赞（不算）；私密帖 / 未过审帖 / 无话题帖 / 类型不符的帖（不参赛）。
   - 断言：A 只留 30 那帖、A 在 B 前（同分先发）、热度分解正确、C 第 3。
   - 两个线程同时 `build` 同一活动 → 只建一份（第二个 SKIP LOCKED 跳过）。
   - 无参赛帖 → `EMPTY`。

### AC2 — 名次分配 `[L0]`（架构 OA-17 第 1 条）
`OpsActivityRankService.reassignRanks(activityId)`（调用方已持活动行锁）：非 `EXCLUDED` 行按 `base_order` 编号 1..n 写 `rank`，`EXCLUDED` 行 `rank = NULL`；`NOT_GRANTED` 保留名次（不递补）。
- 纯函数 `RankAssigner.assign(List<EntryState>)` + `TierResolver.tierFor(rank, tiers)`（超出末档 = 无奖）。
- L0：`RankAssignerTest`：剔除第 2 名 → 原第 3 名变第 2；撤销后复原；`NOT_GRANTED` 不让位；`TierResolverTest`：1 / 2–3 / 4–10 三档边界、第 11 名无奖。

### AC3 — 剔除与撤销 `[L0]` `[L1]`
`OpsActivityRankService`（`@Transactional`，先 `SELECT … FOR UPDATE` 活动行；`rank_state ≠ READY` → 409 `activity-ranking-not-pending`）：
1. `exclude(token, entryId, reason, adminId)`：原因 trim 后 1–200（否则 422 `admin.v150.activity.err.reasonRequired`）；行须属该活动且 `PENDING / NOT_GRANTED` → `EXCLUDED`、`reason`、`excluded_by`、`excluded_at`；`reassignRanks`。重复剔除已剔除行 → 幂等。
2. `restore(token, entryId, adminId)`：`EXCLUDED` → 复核（帖子 `deleted_at` 非空 → `NOT_GRANTED / POST_REMOVED`；作者不合格 → `NOT_GRANTED / USER_INACTIVE`；否则 `PENDING`），清空剔除字段；`reassignRanks`。
3. 审计由后台服务写（2-3）。
4. L0：`OpsActivityRankServiceTest`（Mockito）：状态机分支、原因校验。L1：剔除后名次递补、撤销复原、已发放后剔除被拒。

### AC4 — 确认发放 `[L0]` `[L1]`（架构 OA-17 第 4 条）
1. `grantPreview(token)`：只读，先在内存里做第 3 条复核（不落库），返回 `{winners, expTotal, pawcoinTotal, couponCount, ktpTotal, tailsonalityTotal, giftTotal, hasPawcoin}`，只算 `rank ≤ 末档 to` 且 `PENDING` 的行。
2. `confirmGrant(token, adminId, boolean canGrantPawcoin)`：
   - 总开关关 → 422 `admin.err.growth.campaignDisabled`（复用现有码）；任一档含 PawCoin 且 `!canGrantPawcoin` → 403。
   - 事务 A：锁活动行；`rank_state = GRANTED` → 返回已有结果（**不重复发**）；`≠ READY` → 409。复核：`rank ≤ 末档` 的 `PENDING` 行，帖子已删 → `NOT_GRANTED / POST_REMOVED`，作者不合格（`activityEligible` 否）→ `NOT_GRANTED / USER_INACTIVE`。对剩余 `PENDING` 获奖行：插 `ops_activity_grants`（`trigger_kind = RANK`、`rank`、`post_id`、`occurred_at = now`、`wib_date`、`reward` = 所在档奖励、`idem_key = GrowthIdemKeys.activityRank(a, u)`、`ON CONFLICT DO NOTHING`），行 `status = GRANTED`、`grant_id`。`rank_state = GRANTED`、`rank_granted_at = now`、`rank_batch_no = "RANK" + yyMMddHHmm(WIB) + "-" + activityId`。提交。
   - 然后逐条 `OpsActivityGrantService.execute(grantId)`（同步）；**不**检查参与即奖的次数 / 份数 / 停发名单。
   - 返回 `{batchNo, succeeded, failed}`（从发放记录现算）。
3. `rankResult(token)`：批次号 + 成功 / 失败数 + 名单行（含发放记录状态与失败原因），供 F5。
4. L1：`OpsActivityRankGrantIntegrationTest`：三档（1 / 2–3 / 4–10）发放 → 各档奖励正确、`ACTRANK:` 键；重复 `confirmGrant` 不新增任何记录与到账；某帖在确认前被下架 → 该行 `NOT_GRANTED`、不递补（第 n 名空缺）；某用户发放时权益服务故障 → 该行 `FAILED`，修复后 `execute` 重发成功且只一份；含 PawCoin 无权限 → 403。

### AC5 — 获奖通知与推送 `[L0]` `[L1]`（架构 OA-18）
`OpsActivityNotifier.afterExecuted` 对 `trigger_kind = RANK` 且 `SENT`：
1. `UPDATE ops_activity_grants SET notified_at = now() WHERE id = :id AND notified_at IS NULL` 影响 1 行才发（失败重发成功后也只通知一次）。
2. `NotificationService.send(userId, OPS_ACTIVITY_RANK_WON, title, body, "OPS_ACTIVITY_RANK_WON", String.valueOf(postId))`（站内 + 推送；`PROMO` 偏好、虚拟号跳过由 `send` 处理）。
3. 文案键（逐字照 PRD 附录 A.1，写进 1-2 同一组 properties）：`notify.opsActivity.rankWon.title` = `Selamat! Postinganmu juara #{0} di {1} 🏆` / `Congrats! Your post won #{0} in {1} 🏆`；`notify.opsActivity.rankWon.body` = `Hadiahmu: {0}. Terima kasih sudah ikut!` / `Your reward: {0}. Thanks for joining!`。奖励列表用 1-2 的 `OpsActivityCopy.rewardsText`（含 EXP、只列实际发出的；券被跳过不列）。
4. 获奖**不再**发到账通知（`OPS_ACTIVITY_REWARDED`）。
5. L0：`OpsActivityCopyTest` 补获奖标题正文 ID / EN。L1：获奖用户收到 1 条通知 + 推送调用 1 次，`target_ref = 帖子 id`；重发成功不重复通知。
