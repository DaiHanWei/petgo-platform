# Story 2.3: 健康提醒日跑与投递规则（后端）

Status: review

> 版本 v1.5.0 · 会话 ① 健康记录提醒 · 分支 `feat/1.5.0-health-reminder`
> 口径优先级：CROSS-STORY-DECISIONS 地基段（`AppVersionGate`、`RetentionPushCalendar` 只调用）> 架构增量 §0 Z-3/Z-12、§4.6、§5.1、§5.2 > PRD FR-166（全部）、FR-171 Pregnant、FR-164「Real reminders come first」、AC36 ~ AC45 > UI 稿（无）。
> 前置：2.1、2.2。
> 范围层：**只后端**。文案渲染、通知落库与推送由 2.4 的 `HealthReminderDispatcher` 完成——本 story 先定义接口 `HealthDispatchPort.dispatch(SendGroup) → DispatchOutcome`，用测试替身跑通；2.4 提供真实实现。

## Story

As a 宠物主人,
I want 健康提醒每天 10:00 WIB 发，同一只宠物一天最多一条普通提醒（重要的不受限），撞车的按优先级顺延或跳过,
so that 提醒及时又不打扰。

## Acceptance Criteria

### AC1 — 日跑 Job `[L0]` `[L1]`（架构 §5.1，PRD AC36）
1. `healthreminder.schedule.HealthReminderJob`：`@Scheduled(cron = "${petgo.health-reminder.cron:0 0 3 * * *}", zone = "UTC")`；`runDaily()` → `runFor(LocalDate.now(ScheduleWindow.WIB))`。
2. `runFor(D)` 顺序：读 settings（`enabled=false` → 记日志返回）→ `PregnancyAutoClearService.clearExpired(D)` 并对每只走恢复处理（AC5）→ `LaunchService.onRun(D)` → 过期作废（AC2）→ 取当天待发、版本门槛、占用（AC3）→ 每宠物决策（AC4）→ 投递 → 每用户出队（2.2 `LaunchQueueService.pickForUser`）。
3. 每只宠物一个 `REQUIRES_NEW` 事务；单只失败只 warn（异常类名），继续下一只。日志汇总计数（宠物数、发送组数、各取消原因计数），不记 PII。
4. **同日重跑安全**：只处理 `PENDING AND send_date = D`；已 SENT 的不再动；埋点只在状态迁移那次发（PRD AC63 Re-run）。

### AC2 — 过期作废 `[L0]`（PRD FR-166「Reminders not sent by the end of their day are dropped」）
1. `PENDING AND send_date < D AND origin <> LAUNCH_QUEUE` → `CANCELLED missed_run`；用户 ≥1.5.0 才发 `cancelled` 埋点。排队行：`send_date < D` → 改成 D（排队永不丢）。

### AC3 — 门槛与占用 `[L0]` `[L1]`（PRD FR-166 App version、Birthday、Other automated pushes；架构 Z-3、Z-12）
1. 当天待发行按 owner 分组，`AppVersionGate.usersOnV150OrLater(ownerIds)` 一次批量；不在集合里的 owner 的行 → `CANCELLED old_app`（无埋点），排队行不动。
2. 占用一次批量取（只对有待发行的宠物 / 用户）：
   - 生日 / 第一个生日：`scheduledPushPlanner.plan(D, 这些宠物的 PetProfileSnapshot, Set.of())` 结果里 `type ∈ {PET_BIRTHDAY, MILESTONE_NODE}` 的 `petProfileId`（**只调用，不改 `ScheduledPushPlanner`**；③ 线若改了它的签名 / 拆了类，合并时改这一处调用即可）。
   - 纪念日：`retentionPushCalendar.anniversaryPushPets(petIds, D)`。
   - 召回日：`retentionPushCalendar.recallNodeUsers(ownerIds, D)`（只影响档 8）。
3. 测试里 mock `RetentionPushCalendar` 与 `AppVersionGate`。

### AC4 — 每宠物决策 `[L0]`（架构 §5.2，PRD FR-166 Same-type merge、Per-pet cap、Priority、Moves；AC37 ~ AC42）
1. `HealthReminderPlanner.decide(PetDayInput)` 纯函数 → `PetDayDecision(sendGroups, cancellations, deferrals)`，步骤逐字按架构 §5.2：只读 → `read_only`；怀孕处置（AC5）；档案类发送日再校验（FIRST_VACCINE 已满 6 个月或已有疫苗记录、FIRST_DEWORM 已有驱虫、SPAY_NEUTER 已满 12 个月 / 已绝育 / 有 Neuter 记录 / sex 空、CHECKUP 区间内有到访 → 取消：有记录 → `satisfied`，否则 `rebuilt`）；同类同推送点合并；档 1–2 全发；档 3–8 选一个赢家；输家不可移动 → `skipped_cap`（`displaced_by` = 赢家 kind）、可移动 → 顺延；生日 / 纪念日占用 → 档 3–8 不可移动的 `skipped_scheduled_push`（`displaced_by = scheduled_push`）、可移动的顺延；召回日 → 只有档 8 顺延。
2. 顺延：从 D+1 起第一个「该宠物没有 PENDING 行（排队行不算）、且非生日 / 纪念日占用（档 8 再加非召回日）」的日子；超过 `due_date + 3` → `expired_defer`（`displaced_by` 同上）。顺延写 `send_date` 与 `deferred_days = send_date − due_date`。
3. 参数化用例逐条对 PRD：AC37 三段（F4 D-Day + Rabies D-Day 合并为一组、generic 文案标记、route PAGE；F4 D-Day vs Rabies D-7 → 发 F4，Rabies D-7 挪到 3/2 且 `{hari_lagi}`=6；两个可移动 → Next date 早者先发、另一个挪 3/2）；AC38；AC39（Rabies D-7 胜驱虫 D-Day，驱虫 D-Day `skipped_cap displaced_by=VACCINE_D_MINUS_7`，D+3 照发）；AC40 四句（生日日：子宫蓄脓、Vet D-1 / Custom D-Day 照发，疫苗 D-Day `skipped_scheduled_push`，体检挪到次日）；AC41 五句（档 1–2 不占名额）；AC42（D+7 挪 3/2，下午有人把另一个疫苗 Next 改到 3/2 → 3/2 发 D-Day、D+7 再挪 3/3；3/3、3/4 也占 → `expired_defer`）；召回日档 8 顺延、档 3–7 照发。

### AC5 — 怀孕暂停与恢复补发 `[L0]` `[L1]`（架构 §4.6，PRD FR-166 Pregnant/nursing、FR-171 Pregnant、AC35 末段、AC45 全部）
1. 暂停（日跑当天 `PregnancyFlag.isActiveOn(pet, D)`）：`VACCINE_*` → `paused`；`PYOMETRA_WATCH`、`HEAT_DOG_D_MINUS_7` → `paused`；`FIRST_VACCINE` → 保持 PENDING、`send_date = D+1`、**不改 deferred_days**（挂起，不触发 `expired_defer`）；驱虫照常。
2. 实现 2.1 留的 `PregnancyResumeHandler.onCleared(petId, Instant clearedAt)`：`R = nextRunDate(clearedAt)`；对每个疫苗覆盖组的最新记录（N = next_date，非空、组未被覆盖）按架构 §4.6 三分支：R ≤ N → 普通 `rebuildPet`；N+1 ≤ R ≤ N+14 → 插 `VACCINE_D_PLUS_7`（`push_point=RESUME_CATCH_UP`、`origin=RESUME_CATCH_UP`、`due_date=send_date=R`、`next_date_ref=N`、movable、tier 3）并把同 N 其余 PENDING 点 `CANCELLED catch_up_sent`；R > N+14 → 无。之后对非疫苗部分照常 `rebuildPet`。
3. 文案 `{hari}` = 实际发送日 − N（顺延后按实际）——由 2.4 渲染；本 story 保证行上有 `next_date_ref`。多只疫苗同日补发 → 同类同推送点合并、`{hari}` 取最大。
4. 用例：AC45 全部 8 句（Next 2027-06-01：5/20 清 → 照常；5/28 清 → 不补 D-7，D-Day / D+7 照常；6/1 15:00 清 → 6/2 补发 `{hari}`=1、6/8 D+7 取消；6/5 15:00 → 6/6 `{hari}`=5、6/8 取消且总共一条；6/5 08:00 → 当天 `{hari}`=4；6/10 15:00 → 6/11 `{hari}`=10；6/14 15:00 → `{hari}`=14；6/15 15:00 → 不发；6/6 补发被高档挪到 6/7 → `{hari}`=6、6/8 不发；2027-01-01 设为是从未改 → 5/1 00:00 视为清除）；AC35 末段（怀孕时子宫蓄脓 / 母狗发情 D-7 `paused`）。

### AC6 — QA 端点 `[L0]` `[L1]`（PRD AC36、AC60，§9 QA endpoint）

## Dev Notes

- 数据量：≤ 数千只宠物，单机单实例；不引 Quartz / MQ / 缓存。多实例时靠部分唯一索引 + 状态迁移 `UPDATE … WHERE status='PENDING'` 的行数判断防重。
- 档位与可移动性只从 `ReminderKind` 读，不在 Planner 里硬编码。
- 「同类」= `ReminderKind.family` 相同（疫苗 / 驱虫 / Vet visit / Custom）；其余 family 不合并。
- `next_date_ref` 为空（档案 / 事件类）时，同档比较用 `due_date`。
- WIB 一律 `ScheduleWindow.WIB`；cron 用 UTC 写死 03:00。

**与 story 文字的出入**
- 投递出口 `HealthDispatchPort.dispatch(SendGroup) → DispatchOutcome(sent, healthNotificationId)`；本 story 的生产实现是占位 `UndeliveredHealthDispatchPort`（只 warn、不发，行保持 PENDING），2.4 换成真实 `HealthReminderDispatcher`。上线开关默认关，占位期间日跑不会走到投递。
- 日跑拆成：`HealthReminderJob`（编排）、`DailyRunStore`（③ 过期作废、④ 当天待发 + 版本门槛、当天已通知用户、有排队的用户）、`OccupancyCalendar`（⑤ 当天起 4 天的生日 / 第一个生日 / 纪念日 / 召回日）、`PetDayProcessor`（每宠物 REQUIRES_NEW）、`QueueDayProcessor`（每用户出队 + 投递 + 记发送日同一事务）。
- `HealthReminderPlanner.decide` 的输出为 `PetDayDecision(sendGroups, cancels, moves)`，「挂起」与「顺延」合并为 `Move(row, to, countsAsDeferral)`。
- `PregnancyResumeHandler` 由 `PregnancyResumeService` 实现（删除 2.1 的空实现）；补发行的疫苗快照复用 `ReminderPlanRules.vaccineSnapshot`。
- `PetHealthProfileChangedEvent` 追加 `autoCleared`（保留旧 8 参构造器）：日跑自动清除时为 true，恢复表由日跑同步执行一次，异步监听跳过；`PregnancyAutoClearService.clearExpiredPets(day)` 返回业务上由「是」变「否」的宠物 id（公的残留落库值只清不计）。
- stag 控制器放新包 `com.tailtopia.admin.stag`（架构 §2 指定），`@StagOnly` + `SUPER_ADMIN`，路径前缀 `/admin/stag/` 已免 CSRF。

**待确认（按最保守做法实现）**
- **怀孕自动清除不受上线开关影响**：它属档案规则（PRD FR-162），开关关着也要每天清；恢复表在开关关时照样插补发 / 重建（行只在开关打开后才会被投递）。
- 生日占用直接用 `ScheduledPushPlanner.plan(D, 快照, Set.of())` 里 `PET_BIRTHDAY` / `MILESTONE_NODE` 的宠物（现状是「生日前一天推」，③ 改到生日当天 11:00 后语义自动跟随）；快照建档日按 UTC 折算，与 `PetProfileQueryService.allSnapshots` 同口径。
- 召回日让档 8 顺延时 `displaced_by` 记 `scheduled_push`（PRD §4 只列了赢家 kind 与 `scheduled_push` 两种取值）。
- 合并组顺延按组内最早原定日找目标日；组内某条超过自己原定日 + 3 天则单独 `expired_defer`。
- 档案类发送日再校验：体检在区间内有到访（重算到期日晚于今天）→ `satisfied`，`by_record_id` 取最近一条 Vet visit 记录（兽医问诊引起时可能为空）。
- 「当天该用户已有推送」= 本次或同日早先一次日跑已写过健康通知（`health_notifications.send_date = D`）、任一宠物今天有生日 / 第一个生日 / 纪念日、或今天是召回日。

**复审结论**：CONFIRMED 并已修——自动清除的恢复处理跑两次、出队投递不在事务 / 锁内、先读后锁导致覆盖并发重建、自动清除受上线开关限制、清除计数与日志不一致、挂起的首针没占住次日、出队逐用户扫全部宠物。未改：过期作废一次读全部 PENDING（单机 ≤ 数千宠物，story Dev Notes 的规模假设）。
