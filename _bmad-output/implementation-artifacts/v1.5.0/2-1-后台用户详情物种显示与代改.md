## Story

As a 处理客诉的运营,
I want 在用户详情看到每只宠物的细分类型、大类、下次可改日期与修改记录，并能代改类型,
so that 用户选错类型找客服时，我能当场帮他改，又不占他自己的修改次数。

### AC3 — 代改弹层与接口（G2 / G3）`[L0][L1]`（D-14）
1. 「代改类型」按钮打开通用 `fragments/confirm-modal.html`（事实行 + 黄色提示条 + 输入项，错误写在弹层内 `#confirm-modal-err`、弹层不关——照现有用法，不另写组件）：
   - 事实行：宠物 {名字}（档案 ID {id}）；当前类型 {中文名} · 品种 {品种或 —}；用户下次可改 {日期或「现在可改」}。
   - 提示条：「改类型会清空品种。运营代改不占用户的 90 天修改次数，也不重置冷却期。」
   - 「新类型 *」`<select name="species">`：15 个类型（顺序同 PRD 3.1，「其他」= `OTHER`）+ `<optgroup label="其他">` 下 12 个物种（附录 B 顺序），共 27 项；默认选中当前值。
   - 「修改原因 *」`<textarea name="reason" maxlength="200">`，占位「写清为什么改，比如客诉工单号」。
   - 按钮「取消」/「确认修改」。
2. `POST /admin/users/{userId}/pets/{petId}/species`（新 `admin.usermgmt.web.AdminPetSpeciesController`，结构照 `admin/petslot/web/AdminPetSlotController.grant`：`@PreAuthorize("hasRole('SUPER_ADMIN') or hasAuthority('" + USER_PET_TYPE_CHANGE + "')")`、HX 分支换片段 + toast、非 HX 分支 flash + `redirect:/admin/users?open={userId}`）。
3. 服务 `admin.usermgmt.service.AdminPetSpeciesService.change(adminId, userId, petId, species, reason)`，`@Transactional`：
   1. 宠物不存在或不属于该用户 → 404。
   2. `reason` trim 后为空 → 422 `.code("admin.err.petSpecies.reasonRequired")`（G3：原因框红框 + 红字「请填写修改原因」，弹层不关）；> 200 字 → 422 `admin.err.petSpecies.reasonTooLong`。
   3. `species` 非法 → 422 `admin.err.petSpecies.invalid`；与当前相同 → 422 `admin.err.petSpecies.same`。
   4. 只读宠物 → 沿用 `PetWriteGuard.requireWritable` 的 409，弹层内显示其文案（待拍板 Q-6 默认）。
   5. 行锁（复用 1.2 的 `findByIdForUpdate`）→ `applySpecies(new)` → **品种清空**（`setBreed(null)`，运营不填品种，11-13 定）→ **不写、不改 `pet_type_changed_at`**（不占次数、不重置冷却）。
   6. 大类改变 → `MilestoneTrackSwitcher.switchTo(pet, new.group())`（运营应用户要求代改算用户主动修改，PRD 3.3.3）。
   7. `PetSpeciesChangeLog.append(petId, old, new, ADMIN, adminId, reason)`。
   8. 审计 `adminAudit.record(adminId, AuditActions.PET_SPECIES_CHANGED, "PET", String.valueOf(petId), "<OLD>→<NEW> user=<userId>")`——**summary 不含原因**（原因可能有工单号，留在修改记录表）；`AuditActions` 新增常量 `PET_SPECIES_CHANGED`（若审计 action 有 CHECK / 白名单测试，一并更新）。
   9. 埋点 `pet_type_changed`（`source:"admin"`，复用 1.2 方法，AFTER_COMMIT）。
4. 成功（G4）：弹层关闭、toast「已修改」（`admin.flash.petSpecies.changed`）、宠物档案页签片段刷新并**展开该宠物的修改记录**；卡片类型变为新值、品种「—」、下次可改日期不变。
5. 测试用例（L1）：无权限账号 POST → 403；原因为空 → 422 且片段含错误文案；相同类型 → 422；兔 → 仓鼠成功：库内 `pet_species=HAMSTER`、`breed=null`、`pet_type_changed_at` 不变、修改记录 1 条 ADMIN（操作人、原因）、审计 1 条、里程碑 track 不变；猫 → 兔：track 切到 OTHER；用户冷却中运营仍能改、改完用户冷却日期不变。

### 设计要点
- 运营代改**不碰** `pet_type_changed_at`：PRD「不占用户次数、不重置用户的冷却期」。所以用户若在冷却中，运营改完他仍要等到原日期；用户从没改过，运营改完他仍可立即改一次。
- 运营代改会换里程碑清单（大类变时），迁移不会——两者唯一的区别就在是否调切换器。
- 代改不填品种：11-13 定，留给用户自己在 App 里选（App 品种框会显示「Pilih ras」）。
