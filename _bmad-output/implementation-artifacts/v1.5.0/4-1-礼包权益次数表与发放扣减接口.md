## Story

As a 会话 ⑥（运营活动）与本线后续 story,
I want 一张按批记录的权益次数表和唯一的发放 / 扣减入口,
so that 礼包、活动、后台补发发出的次数规则一致、不会重复到账、不会多扣。

### AC3 — `grant` `[L0]` `[L1]`
`EntitlementCreditService.grant(GrantCommand)`，`@Transactional(propagation = REQUIRED)`，语义逐条照架构 §5：
1. 校验顺序（全在写库前）：`quantity` 1..100 → 422 `entitlement-quantity-invalid`；`idemKey` 非空 ≤ 160、`sourceRef` 非空 ≤ 64、`labelId/labelEn` ≤ 80 → 422 `validation`；`type == KTP_HD_ANY && source != ACTIVITY` → 422 `entitlement-type-not-allowed`；`source == ADMIN` 且 `operatorAdminId == null || reason 为空` → 422 `validation`；用户不存在 / `deletedAt != null` / 注销受理中（`account_deletions` 有行，同 `PetSlotPurchaseService.grantByAdmin` 的判法）/ 虚拟号 → 422 `entitlement-user-inactive`。错误码登记进 `ErrorTypes`。
2. 有效期：`grantedAt = clock.instant()`；`expiresAt = grantedAt.atZone(ZoneId.of("Asia/Jakarta")).plusMonths(3).toInstant()`。`Clock` 可注入（测试用）。
3. 幂等：`INSERT … ON CONFLICT (idem_key, credit_type) DO NOTHING RETURNING id, expires_at`；无返回 → 按 `(idem_key, credit_type)` 查回，返回 `replayed = true`；若查回的 `quantity` 与本次不同 → WARN 日志（只记 creditId 与两个数量）。同一 `idemKey` 不同 `type` 各自成功。
4. 不发通知、不发埋点、不写审计。日志只记 `userId`、`type`、`quantity`、`source`。
5. L0：`EntitlementGrantRulesTest`（纯函数部分：有效期计算含月末——1 月 31 日 → 4 月 30 日、闰年 11 月 30 日 → 次年 2 月 28/29 日；校验分支）。
6. L1：`EntitlementCreditServiceIntegrationTest`：同键同类型重放只一行；同键不同类型两行；ANY + PACK 被拒；已注销用户被拒；在外层事务里调用、外层回滚后表里无行（证明并入调用方事务）。

### AC4 — `consume` `[L0]` `[L1]`（D-25）
`EntitlementCreditService.consume(ConsumeCommand)`，`@Transactional(propagation = MANDATORY)`：
1. `quantity ≥ 1`（KTP / 性格测试恒为 1；送礼 = 礼物数量）；`kind` 与 `type.family()` 必须匹配（KTP_HD↔KTP 款、TAILSONALITY↔TAILSONALITY、GIFT↔GIFT_1K），否则 `IllegalArgumentException`（编程错误）；KTP 传 `KTP_HD_ANY` 也是编程错误（调用方必须传具体款）。
2. 先 `SELECT pg_advisory_xact_lock(hashtext('entitlement:' || :userId))`；再查 `use_key = '{kind}:{targetId}'` 是否已有行 → 有则返回 `alreadyUsed = true, consumed = 0`，不再扣。
3. 候选批：`user_id = :uid AND used < quantity AND expires_at > :now AND credit_type IN (:types)`，`:types` = KTP 时 `[该款, KTP_HD:ANY]`、其他时 `[type]`；排序 `CASE WHEN credit_type = :exact THEN 0 ELSE 1 END, expires_at, id`（先该款后 ANY，同组先到期先扣），`FOR UPDATE`。
4. 可用合计 < quantity → 抛 `AppException.conflict(...)` 码 `entitlement-insufficient`（调用方事务随之回滚）。
5. 逐批扣：`UPDATE entitlement_credits SET used = used + :n WHERE id = :id AND used + :n <= quantity`（影响 0 行 → `IllegalStateException`，不应发生）；每扣一批插一行 `entitlement_credit_uses`（`credit_type` = 该批类型，`pet_name` 截到 20 字符）。
6. 返回 `consumed = quantity`、`creditIds`（按扣的顺序）、`firstSource` = 第一批来源。
7. 「到期判断按扣减时刻」：`:now = clock.instant()`。
8. L1：`EntitlementConsumeIntegrationTest`：该款优先于 ANY；同类先到期先扣；跨两批扣 5 个写两行流水；过期批不参与；不足时抛 409 且无任何写入；同 `use_key` 第二次调用 `alreadyUsed`；**并发**两个线程对同一用户同一目标各调一次只扣一次（advisory lock）；两个不同目标并发不超扣。

### AC5 — `summary` `[L0]` `[L1]`
`summary(userId)`：只统计 `used < quantity AND expires_at > now`；按 family 聚合 `remaining = Σ(quantity − used)`、`earliestExpiry = min(expires_at)`；KTP family 下按类型（含 ANY）列 `TypeSummary`，剩余 0 的类型不列；`totalRemaining` = 全部 family 之和。L1 覆盖：两批不同到期的合计与最早到期；过期批不计。

### AC6 — 写入单点守卫 `[L0]`
`EntitlementWriteGuardTest`：扫描 `B/` 源码，`INSERT INTO entitlement_credits` / `UPDATE entitlement_credits` / `INSERT INTO entitlement_credit_uses` 只出现在 `B/entitlement/` 包内（照 v1.4.2 `UserCouponLedgerDao` 守卫写法）。
