> 迁移（预分配）：`V20261115_0120__create_health_reminder_tables.sql`。

## Story

As a 宠物主人,
I want 每次保存、修改、删除健康记录后，系统马上把这只宠物未来的提醒排好（被新记录满足或被覆盖的自动撤掉）,
so that 我只会收到仍然需要的提醒。

## Acceptance Criteria

### AC1 — 迁移 `[L0]` `[L1]`
1. **逐字**按架构 §1.3 建 `health_reminder_settings`（插入 id=1）、`health_notifications`、`health_reminders`（含部分唯一索引 `ux_health_reminders_once`）、`health_reminder_user_launch`。文件头注释：每张表一句用途、`cancel_reason` 多出的 `old_app`、「不碰 `ck_notifications_type`」。
2. 实体或 JDBC DAO 二选一；用实体时列类型 `Integer/Boolean/LocalDate/Instant`、枚举 `@Enumerated(STRING)`，validate 通过。
3. 1.2 的 `LaunchDateProvider` 改为读 `health_reminder_settings.launch_date`（为空 → 今天 WIB）；1.3 的 Runner 开头见 `backfill_done_at` 非空即跳过、结束时写入。

### AC2 — 提醒目录 `[L0]`（PRD 附录 C）
1. `healthreminder.domain.ReminderKind`：23 值，名字与附录 C 的 ID 完全一致，字段 `tier`、`movable`、`route`（FORM / FORM_DATE_EMPTY / PAGE）、`family`（VACCINE / DEWORM / VET_VISIT / CUSTOM / HEAT / NEUTER / SUGGESTION / CHECKUP，用于同类合并）、`catalogueOrder`；`notificationType()` = `NotificationType.valueOf("HEALTH_" + name())`。
2. 守卫测试 `ReminderKindTest`：23 个值与 `NotificationType` 里的 `HEALTH_*` 一一对应（地基已建，**不改** `NotificationType`）；与迁移 `ck_health_reminders_kind` 文本一致；档位 / 可移动性逐条对附录 C。
3. `PushPoint`（D_MINUS_7 / D_MINUS_1 / D_DAY / D_PLUS_3 / D_PLUS_7 / RESUME_CATCH_UP / NONE，带 `wire()` → `d_minus_7` 等小写）、`ReminderOrigin`、`CancelReason`（值与 CHECK 一致，`wire()` 即小写原文）。

### AC3 — 记录类与事件类规则 `[L0]`（架构 §4.3「期望集合」，PRD FR-163 表、FR-171、AC14、AC18、AC20、AC21、AC22、AC31、AC33 ~ AC35、AC53）
1. `ReminderPlanRules.recordAndEventReminders(PetHealthSnapshot, List<HealthRecordSnapshot>, ReminderHistory, LocalDate fromDate, LocalDate effectiveLaunchDate)` → `List<DesiredReminder>`（键 = 宠物、来源记录、kind、point、due_date；附带 tier、movable、next_date_ref、到期疫苗 / 剂次 / 驱虫类型 / custom 名快照）。只输出 `due_date ≥ fromDate` 的点。
2. 记录类：每个覆盖组的最新记录、组未被覆盖、有 next_date、非回填静默 → 按 PRD FR-163 表生成：疫苗 D-7 / D-Day / D+7；INTERNAL、HEARTWORM D-Day + `DEWORM_INTERNAL_D_PLUS_3`；EXTERNAL、FLEA_WORM D-Day + `DEWORM_EXTERNAL_D_PLUS_3`；LEGACY `DEWORM_LEGACY_D_DAY` + `DEWORM_LEGACY_D_PLUS_3`；Vet visit **每条**（未满足时）D-1 + D-Day；Custom D-Day；母狗未绝育发情周期首条 → `HEAT_DOG_D_MINUS_7`。
3. `ReminderHistory`（从库读：该宠物已 SENT 的 kind 集合与日期、已有的 RESUME_CATCH_UP 行）：某 (记录, next_date_ref) 已有补发 → 不再生成该 Next date 的任何点（PRD FR-163 Pregnant/nursing catch-up）。
4. 事件类（只看 `record_origin <> BACKFILL`）：`STITCH_CHECK`（NEUTER，event+10）；`PYOMETRA_WATCH`（DOG+FEMALE+未绝育，每个周期首条 event+42）；`HEAT_CAT_SECOND`；`HEAT_MALE_FIRST`——条件逐字按架构 §4.3；已过日期不生成（AC34：3 May 的 Neuter 20 May 才存 → 无拆线提醒）。
5. 全局过滤：READ_ONLY → 空集；NEUTERED → 去掉 `HEAT_*`、`PYOMETRA_WATCH`、`SPAY_NEUTER_SUGGESTION`；sex=null → 去掉全部发情相关；OTHER 物种（非 CAT/DOG）→ 只留记录类点（OTHER 永不预填，所以凡有 next_date 都是用户手填的：Custom、Vet visit、疫苗、驱虫）；无事件类、无发情、无档案类。
6. 参数化用例对 PRD：AC18（F4 Next 1 Dec → 24 Nov / 1 Dec / 8 Dec；26 Nov 记 F4 → 1 Dec、8 Dec 消失）；AC14（Vet visit Next 14 Nov → 13 Nov D-1、14 Nov D-Day；记 13 Nov 的 Vet visit 后都消失；记 5 Nov 的不影响）；AC20（删最新恢复上一条未来点；改 Next 挪点）；AC21 全部四句（覆盖单向、改备注不复活、删覆盖记录复活、15 Feb Internal 不碰 Flea+worm 的 1 Mar）；AC22（回溯 Rabies 预填已过 → 无点）；AC31 / AC35 的 PYOMETRA 日期（12 Feb、12 Aug；1/3/6 Jan 只一个）；AC33（1 Mar、20 Mar 母猫 → 一次 `HEAT_CAT_SECOND`；10 Apr 不再有）；AC53（Legacy 15 Oct → 15 Jan D-Day、18 Jan D+3；记任意已分型驱虫后都消失）；AC8（F3 撤 F4 提醒）；AC9 撤 DP 部分（20 Mar 记 Combo → DP 的点撤掉）。

### AC4 — 整宠重建对账 `[L0]` `[L1]`（架构 §4.3 第 1 ~ 4 步）
1. `HealthReminderRebuilder.rebuildPet(long petId, RebuildTrigger trigger)`（`@Transactional(REQUIRES_NEW)`，在独立 bean 上）：`fromDate = HealthDates.nextRunDate(now)`；读快照与历史 → 规则得期望集合 → 与该宠物 `PENDING` 且 `origin ∉ {LAUNCH_QUEUE, RESUME_CATCH_UP}` 且 `send_date ≥ fromDate` 的行对账：同键保留（不动 send_date / deferred_days）；多余的取消（原因按架构 §4.3 第 2 步：`satisfied`+`satisfied_by_record_id` / `record_deleted` / `neutered` / `read_only` / `rebuilt`）；缺的插入（同键已有 SENT → 跳过）。
2. 已发行补 `satisfied_at`（架构 §4.3 第 4 步）。
3. 每条取消都调 `HealthReminderAnalytics.cancelled(row, reason, displacedBy, byRecordId)`——本 story 先定义接口与空实现（2.4 接 `AnalyticsClient`）。
4. 档案类建议的生成入口留一个扩展点 `ProfileReminderSource`（本 story 默认返回空；2.2 实现），由 Rebuilder 一并对账（origin=PROFILE 的行也在第 1 步范围内）。
5. 并发：同一宠物的两次重建串行（`SELECT … FOR UPDATE` 锁 `pet_profiles` 行或 `pg_advisory_xact_lock(petId)`）；唯一索引冲突视为已有，吞掉重试一次。

### AC5 — 触发监听 `[L0]` `[L1]`（架构 §4.3 触发表）
1. `HealthReminderTriggers`：`@TransactionalEventListener(AFTER_COMMIT)` + `@Async`，内部调用**另一个 bean** 的 `rebuildPet`（禁止自调用 `@Transactional`）。
   - `HealthRecordChangedEvent`：`reminderRelevant=false` 的 UPDATED 不重建；其余重建（DELETED 时取消原因 `record_deleted` 只给来源 = 被删记录的行）。
   - `PetHealthProfileChangedEvent`：`birthdayChanged || sexChanged || neuterChanged || pregnantSetYes` → 重建；`pregnantCleared` → 交给 2.3 的恢复处理（本 story 只留调用点 `PregnancyResumeHandler`，空实现）。
   - `ProfileCreatedEvent` → 重建（档案类由 2.2 生效）。
   - 新增 `profile/slot/PetStatusChangedEvent(ownerId, petId, newStatus)`，在 `PetSlotStateService` 里 `markActive()` / `markReadOnly()` 实际改变状态处发布 → 重建。
2. 监听异常只 warn（异常类名），不影响原业务事务。

### AC6 — 删宠 / 注销清理 `[L0]` `[L1]`（架构 §4.8，PRD FR-166 Pet deleted）
1. `HealthReminderCleanup.deleteForPet(petId)`：PENDING 行逐条 `cancelled(pet_deleted)` 埋点 → 删除该宠物 `health_reminders`、`health_notifications`（`health_vet_consult_visits` 由 2.2 加）。`ProfileDeletionService.deletePetRows` 在删宠物行**之前**调用；`deleteAllForAccount` 额外删 `health_reminder_user_launch`（该用户）。
2. 删除 / 注销级联测试（现有 `ProfileDeletion*` 集成测试）不红；新增断言健康提醒行被删。

**待确认（按最保守做法实现）**
- 只读宠物：重建只取消对账范围（RECORD/PROFILE/EVENT 且 send_date ≥ 下一跑）内的 PENDING；排队 / 恢复补发行按架构 §5.2 由 2.3 日跑在发送日判 `read_only`。
- 「下一跑」类事件提醒（猫二次发情 / 公的首次发情）的原定日取该 (记录, kind) 任一历史行的原定日，被日跑取消（名额 / 顺延到期）后不会换日期复活。
- 发情 D-7 只取最新发情周期首条（与列表显示一致）；`HEAT_CAT_SECOND` 的 6 个月冷却按「原定日前 6 个月内有已发」判。
- 保存 NEUTER 记录会同时触发记录变更与档案变更两次重建（幂等，只是重复计算）。

**复审结论**：CONFIRMED 并已修——埋点在提交前发（重试会重复 / 回滚会误发）、清理不取宠物锁、被取消的「下一跑」提醒以新日期复活、全限定名风格。未改：只读宠物的排队 / 补发行（2.3 日跑负责）、NEUTER 双重建（幂等）。
