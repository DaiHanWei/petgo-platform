## Story

As a 浏览别人宠物、送礼、看卡、问诊的用户,
I want 到处看到的都是准确的宠物类型、AI 也知道我养的是兔子,
so that 兔子不再处处显示成「其他」，分诊建议也更贴切。

### AC3 — 迁移 ④ 与身份证建卡 `[L0][L1]`（D-6、D-13）
1. `V20261115_0430__id_cards_add_pet_species.sql`：`ALTER TABLE id_cards ADD COLUMN pet_species VARCHAR(32);` + `COMMENT`（「建卡时细分类型快照，V1.5.0 起写；旧卡为 null，按 pet_type 显示」）。**不回填、不加 CHECK**（快照；取值由 DTO 白名单保证）。
2. `IdCard` 追加 `@Column(name = "pet_species", length = 32) String petSpecies` + getter；`IdCard.snapshot(...)` 加重载带 `petSpecies`（原签名保留）。
3. `CreateIdCardRequest` **末尾**追加 `@Pattern(regexp = PetSpecies.WIRE_PATTERN) String species`；`PET_TYPES` 白名单不变。
4. `IdCardService.create` 开头归一：
   - `species` 非空 → `petType` 非空且 `≠ species.group().name()` → 422「宠物类型与细分类型不一致」；有效 `petType = species.group().name()`；
   - `species` 空 → 原逻辑，`petSpecies = petType`（可能为 null）。
   - **卡号物种码、`findNumberSourceCard`、`allocateCardNo`、`allocatePassportNo` 继续用归一后的大类 `petType`**（PRD「卡号里的物种码不变，新建卡按新类型」——新类型的大类）。
   - V2 严格模式「物种必填」= `species` 或 `petType` 至少一个（`requireStrictFields` 调整判断）。
5. `IdCardResponse` 末尾追加 `species`（= 卡快照 `pet_species`，旧卡 null → NON_NULL 省略，App 回退 `petType`）。
6. 用例：建卡 `{species:"RABBIT"}` → 快照 `pet_type=OTHER`、`pet_species=RABBIT`、卡号物种段 `00`；旧版 `{petType:"CAT"}` → `pet_species=CAT`、物种段 `02`；`{petType:"DOG", species:"CAT"}` → 422；已有旧卡 `GET /me/id-cards` 不含 `species`。
7. 宠物之后改类型，已生成的卡**不变**（快照，PRD 3.3.3）——L1 断言。

### 设计要点
- **为什么身份证不改存 `pet_type`**（PRD §6 写「快照的 pet_type 列改存细分类型时注意长度」）：`pet_type` 快照同时是「编号沿用」的查询键（同用户同生日同性别同物种复用卡号）与物种码来源，改存细分类型会让兔子查不到它以前按 OTHER 建的卡、也会让物种码规则要再写一遍映射。加一列最稳，长度问题也随之消失。
- **只加不改**：这些返回体被送礼线 ②、首日线 ③ 同时在改（例如送礼面板、推荐卡），追加在末尾、合并时只是两边各加一行。

### 不做
- 不改任何按大类的逻辑（推荐分池、内容物种、运营人群、礼物适用物种、性格测试、自动评论、护照号）。
- 不改兽医端（Q-5）。
