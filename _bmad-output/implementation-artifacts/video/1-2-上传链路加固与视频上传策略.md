# Story 1.2：上传链路加固与视频上传策略

Status: review

> 专题线 video · Epic 1 · 只改后端。分支 `feat/video`。
> 权威顺序：决策日志-video.md > PRD-video.md > architecture-video-delta.md > epics-video.md。

## Story

As a 平台，
I want 通用上传只接受图片并禁止覆盖，视频走独立的、受严格约束的上传策略，
so that 上传链路不会被当成免费网盘用，也不能在审核之后偷换内容。

**范围**：FR-11、FR-23；架构 AD-3、AD-4；一致性规则 7（本 Story 不碰 HEAD，规则 7 只是提醒：签发策略是本地计算，不发网络请求）。
**不在范围**：视频帖发布接口与归属校验（1.3）、`media.video.cdn-base-url` 与 CDN（1.4 / 3.4）、App 侧上传（1.6）。

## Acceptance Criteria

1. **通用 upload-url 类型白名单【L1】**
   - `POST /api/v1/media/upload-url`，`contentType ∈ {image/jpeg, image/png, image/webp, image/heic}`（大小写不敏感，前后空白去掉）→ 正常签发。
   - `video/mp4`、`text/html`、`application/octet-stream`、空串、缺省 → 422，ProblemDetail `type` 以 `upload-content-type-not-allowed` 结尾；不调用 OSS 签名。
   - 白名单对 PUBLIC 与 PRIVATE 两个 scope 都生效。

2. **禁止覆盖【L1 + L2】**
   - 所有通用预签名 PUT 都把 `x-oss-forbid-overwrite: true` **签进签名**，并且**同时放进响应 `headers`**（旧版 App 原样带回 `ticket.headers`，所以旧版不受影响）。【L1：断言响应 headers；L0：断言签名请求带了该头】
   - 用 1.3.4 版 `OssUploader` 的方式（原样带回 `ticket.headers` + `Content-Length`）第一次 PUT 成功；同一凭证再 PUT 一次被 OSS 拒绝（409 FileAlreadyExists），原文件不变。【L2：真实 OSS】

3. **封面用途 `purpose=VIDEO_COVER`【L1】**
   - 请求体新增可选字段 `purpose`（枚举，本期只有 `VIDEO_COVER`）。不带 `purpose` 的请求行为与现在完全一致（除 AC1/AC2 的加固）。
   - `purpose=VIDEO_COVER` 且调用者等级 ≥ 10：
     - 必须 `scope=PUBLIC`，否则 422 `validation`；`contentType` 必须是 `image/jpeg`（FR-8 封面为 JPEG），否则 422 `upload-content-type-not-allowed`；
     - 签名里带 `x-oss-object-acl: private`（**不是** public-read），响应 `headers` 同步给出 `x-oss-object-acl: private`；
     - key 仍是 `{keyPrefix}public/{userId}/{随机}.jpg`（1.3 的封面归属校验靠这个前缀），`publicUrl` 照常返回（发布后由 1.4 的对账器改为 public-read 才能匿名访问）。
   - `purpose=VIDEO_COVER` 且等级 < 10 → 403，`type` 以 `video-permission-denied` 结尾。

4. **视频上传策略 `POST /api/v1/media/video-upload-policy`【L1】**
   - 需要 JWT；等级 ≥ 10 才签发，否则 403 `video-permission-denied`。
   - 返回 `{host, key, fields}`：
     - `host` = `https://{publicBucket}.{endpoint 主机名}`（如 `https://tailtopia.oss-ap-southeast-5.aliyuncs.com`）；
     - `key` = `{keyPrefix}video/{userId}/{16 字节随机 base64url}.mp4`，服务端生成；
     - `fields`（有序）包含：`key`、`policy`（base64）、`OSSAccessKeyId`、`signature`、`success_action_status=200`、`Content-Type=video/mp4`、`x-oss-object-acl=private`、`x-oss-forbid-overwrite=true`。
   - policy 条件逐条为：`["eq","$key",<完整 key>]`、`["content-length-range",1,104857600]`、`["eq","$Content-Type","video/mp4"]`、`["eq","$x-oss-object-acl","private"]`、`["eq","$x-oss-forbid-overwrite","true"]`、`["eq","$success_action_status","200"]`；过期时间 = 现在 + `media.video.upload-ttl-seconds`（默认 1800）。【L0：断言条件 JSON】
   - 同一账号在同一个 **WIB 自然日**内第 51 次申请 → 429，`type` 以 `video-upload-quota-exceeded` 结尾；WIB 次日 0 点后重新计数。等级不足的请求**不计数**。
   - 响应、日志里都不出现 AccessKeySecret；`signature` / `policy` 不进 INFO 日志。

5. **OSS 侧拒绝【L2：真实 OSS】**
   - 拿到视频策略后：上传 > 100MB 的文件、Content-Type 不是 `video/mp4`、改写 key、向同一个 key 再传一次 → 全部被 OSS 拒绝；合规文件上传成功，对象 ACL 为 private（匿名 GET 403）。

6. **回归【L0 + L1】**
   - App 现有图片发帖、头像、AI 分诊图等调用（都是 `image/jpeg`）不受影响；`MediaControllerTest` / `MediaControllerEndpointTest` / `PresignedUploadServiceTest` 按新行为更新后全绿。

## Dev Notes

### 现状（改动前，已逐行读过）

- `shared/media/PresignedUploadService.issue(scope, userId, contentType)`：
  - contentType 为空回落 `application/octet-stream`，未知类型扩展名 `bin` —— **这就是「免费网盘」漏洞**，本 Story 关掉。
  - PUBLIC 域要求 `cdnBaseUrl` 非空，否则 `mediaCredential`(502)；PUBLIC 把 `x-oss-object-acl: public-read` 签进签名并放进 headers；PRIVATE 不带 ACL、`publicUrl=null`。
  - key：`{normalizedKeyPrefix}{scope.prefix}/{userId}/{16 字节 base64url}.{ext}`。
- `AliyunOssClient.presignedPutUrl(bucket, key, contentType, ttl, publicRead)`：`GeneratePresignedUrlRequest` + `addHeader` —— `x-oss-*` 头经 `addHeader` 加入会进入 V1 签名的 CanonicalizedOSSHeaders，客户端必须原样发送，否则 `SignatureDoesNotMatch`。`x-oss-forbid-overwrite` 同理。
- `MediaController`：`POST /api/v1/media/upload-url`，JWT subject 解析 userId，`RedisRateLimiter` 每用户 30 次/分钟。
- App（1.3.4 及以前）：唯一调用点 `media_upload_use_case.dart:105-108`，固定 `contentType: 'image/jpeg'`；`OssUploader.put` 原样展开 `ticket.headers` 再补 `Content-Length`；**每次上传都新申请票据**，不存在用同一票据重试的情况 —— 所以加 forbid-overwrite 不会让正常重试失败。
- 后台的各种图片上传（`data-upload-url=/admin/...`）走服务端 `putPublicObject`，**不经过** `PresignedUploadService`，不受影响。
- `VipLevelService`（Story 1.1）：`canPublishVideo(userId)` 直接查库（`findVipLevel`），`VIDEO_PUBLISH_LEVEL = 10`。**复用它，不要另写等级查询。**
- `shared` 包已经依赖 `auth`（`JwtService`、`ImAccountRegistrationListener`），无 ArchUnit 约束；`MediaController` 注入 `VipLevelService` 合规。
- 项目里没有 `Clock` bean；WIB 一律 `ZoneId.of("Asia/Jakarta")`（如 `OpsAudienceQuery.WIB`）。

### 必须保留

- 不带 `purpose` 的图片上传：key 形态、PUBLIC 的 public-read、`publicUrl`、PRIVATE 的无 ACL、30 次/分钟限流 —— 全部不变。
- PUBLIC 域缺 `cdnBaseUrl` 的 fail-fast 不变（VIDEO_COVER 也走 PUBLIC，同样需要）。
- F21：不新增任何删除对象的封装。

### OSS PostObject 要点（SDK 3.18.1，已在本机 jar 上核实 API）

- `OSS.generatePostPolicy(Date, PolicyConditions)` → policy JSON 原文；`OSS.calculatePostSignature(String postPolicy)` 参数是**原文**，内部 base64 后 HMAC-SHA1。表单里 `policy` 字段要放 **base64(原文)**。
- `PolicyConditions.addConditionItem(MatchMode.Exact, name, value)` 生成 `["eq","$name","value"]`；`addConditionItem(PolicyConditions.COND_CONTENT_LENGTH_RANGE, 1, max)` 生成 content-length-range。
- 表单字段要求：`file` 必须是最后一个字段（App 侧 1.6 处理，`fields` 用 `LinkedHashMap` 保持顺序方便调试）。
- ⚠️ **L2 风险**：`x-oss-forbid-overwrite` 作为 PostObject 表单字段 OSS 文档明确支持；把它写进 policy `eq` 条件是否被 OSS 接受，需 L2 实测。若 OSS 因该条件报 `InvalidPolicyDocument`，改为**只保留表单字段、去掉这条 policy 条件**，并在 Completion Notes 记录（此时客户端理论上可删掉该字段，但 key 已用 eq 锁死且每次随机，覆盖风险只剩「本人覆盖本人刚拿到的 key」，可接受）。不要为此改成别的方案。

### L2 curl 模板（真实 OSS，本地验收用）

```bash
# 通用 PUT（AC2）：用 upload-url 返回的 uploadUrl + headers
curl -X PUT "$UPLOAD_URL" -H "Content-Type: image/jpeg" -H "x-oss-object-acl: public-read" \
     -H "x-oss-forbid-overwrite: true" --data-binary @a.jpg   # 第一次 200
# 同命令再执行一次 → 409 FileAlreadyExists

# PostObject（AC5）：fields 逐个 -F，file 放最后
curl -X POST "$HOST" -F key=$KEY -F policy=$POLICY -F OSSAccessKeyId=$AK -F signature=$SIG \
     -F success_action_status=200 -F Content-Type=video/mp4 -F x-oss-object-acl=private \
     -F x-oss-forbid-overwrite=true -F file=@ok.mp4
```
