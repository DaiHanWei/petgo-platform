# Story 1.3：视频帖发布接口（校验与审核路由）

Status: review

> 专题线 video · Epic 1 · 只改后端。分支 `feat/video`。依赖 1.1（等级、免审名单端口）、1.2（错误类型、视频 key 规则、封面 `VIDEO_COVER`）。
> 权威顺序：决策日志-video.md > PRD-video.md > architecture-video-delta.md > epics-video.md。

## Story

As a 官方号，
I want 用视频和封面发布一条视频帖，
so that 视频帖能进入社区；名单内直接公开，名单外进入人工审核。

**范围**：FR-4、FR-10、FR-12；架构 AD-1、AD-2（content_posts 列）、AD-5，AD-6 中的 `desiredOf` 与实体内推导。
**不在范围**（别提前做）：
- 帖子 DTO 下发 `mediaType` / `video`、签名地址 → 2.1（本 Story 的发布响应仍用现有 `ContentPostResponse.from`，不加字段）。
- `MediaAclReconciler`、`reconcileOne`、`VideoUrlResolver`、CDN → 1.4。
- 注销批量 SQL 写 desired、全部可见性入口的 L1 覆盖 → 3.1。
- `scanTimeouts` 对 `VIDEO_FORCED` 不受总开关影响 → 3.2。
- 旧版过滤 → 2.2。

## Acceptance Criteria

1. **迁移【L1】** 新迁移执行后：
   - `content_posts` 新增 `media_type VARCHAR(8) NOT NULL DEFAULT 'IMAGE'`（CHECK IN ('IMAGE','VIDEO')）、`video_object_key VARCHAR(256)`、`video_duration_ms INTEGER`、`video_width INTEGER`、`video_height INTEGER`、`video_size_bytes BIGINT`、`media_acl_desired VARCHAR(8)`、`media_acl_applied VARCHAR(8)`（两列 CHECK IN ('PUBLIC','PRIVATE')）、`media_acl_desired_at TIMESTAMPTZ`；
   - 一致性约束：`media_type='IMAGE' OR (video_object_key IS NOT NULL AND media_acl_desired IS NOT NULL AND media_acl_applied IS NOT NULL)`；
   - 部分索引：`ON content_posts (id) WHERE media_type='VIDEO' AND media_acl_desired <> media_acl_applied`；
   - `ck_content_posts_review_reason` 按**全集**重建为 `('RISK_HIGH','DEGRADED_FAILCLOSED','REPORT_P0','VIDEO_FORCED')`（当前树最后一次重建在 `V52__report_triage_auto_hidden.sql`，已核实其后无人改过）；
   - 存量行全部 `media_type='IMAGE'`、视频列与 ACL 列为 NULL；`ddl-auto=validate` 启动通过。

2. **请求体与兼容构造器【L0】**
   - `ContentPostCreateRequest` 末尾新增 `MediaType mediaType`（省略 = IMAGE）与 `VideoPayload video`（`objectKey, durationMs, width, height`）。
   - 现有 6 个兼容构造器全部改为补 `null, null`，并新增一个 10 参兼容构造器（即当前 10 分量形态），**现有调用方一行不改**能编译。

3. **名单内发布【L1】** 名单内、等级 10 的账号提交视频帖（`imageUrls=[本人 VIDEO_COVER 封面的 publicUrl]`，`video.objectKey` 指向本人 `video/` 前缀下、HEAD 存在的 mp4）：
   - 走 `publish()` 主流程，**跳过 `moderation.evaluate`（文本和图片都不审）**，状态 PUBLISHED；
   - 落库：`media_type=VIDEO`、视频四列 + `video_size_bytes`（取 HEAD 的实际大小）、`image_sizes=[{width,height}]`（**服务端用请求里的视频显示宽高写**，忽略客户端 `imageSizes`）、`image_crop_offsets=NULL`、`visibility=PUBLIC`、`media_acl_desired=PUBLIC`、`media_acl_applied=PRIVATE`、`media_acl_desired_at` 有值；
   - 发 `ContentPublishedEvent`；@ 名单经 `MentionSanitizer` 清洗后落库并发 @ 通知；幂等键生效；
   - **没有调用 `publishTrusted`**；**没有调用尺寸兜底测量**（`ImageSizeBackfillService.backfill` 零调用）。

4. **名单外发布【L1】** 不在名单、等级 10 的账号提交视频帖：
   - 先跑**文本审核**：`moderation.evaluate(text, List.of())`（图片列表传空，封面是私有的，三方拉不到）；L1 词库命中照样 422 `content-text-blocked`、不落库；
   - 其余结果（PASS / RISKY / DEGRADED）**一律**落 `UNDER_REVIEW`、`review_reason=VIDEO_FORCED`，调用 `manualReviewGate.enqueue`；**人工审核总开关关闭时也照样入队**；
   - `media_acl_desired=PRIVATE`、`media_acl_applied=PRIVATE`；不发 `ContentPublishedEvent`、不发 @ 通知（与现有挂起分支一致）；
   - 挂起分支同样写 @ 名单、`image_sizes`、视频列（与现有挂起分支「尺寸 / @ 名单 / 打卡」同一个坑）。

5. **逐条校验【L1】** 以下每一种失败都返回对应错误码，且**不产生任何帖子**（`content_posts` 行数不变）：

   | 情况 | 错误 |
   |---|---|
   | 等级 < 10（含等级 10 被降回 1 后） | 403 `video-permission-denied` |
   | `mediaType=VIDEO` 但 `imageUrls` 不是恰好 1 个，或 `video` 为空 | 422 `video-mixed-media` |
   | `mediaType` 省略 / IMAGE 但带了 `video` | 422 `video-mixed-media` |
   | `type` 不是 DAILY / KNOWLEDGE；带了 `petId` / `eventDate` / `placeCheckinToken`；`imageCropOffsets` 不是 null | 422 `validation` |
   | `durationMs` 不在 3000–90000；`width`/`height` ≤ 0；短边 > 720 | 422 `video-object-invalid` |
   | 视频 key 不在 `{keyPrefix}video/{本人id}/` 下，或不以 `.mp4` 结尾，或含 `..` | 422 `video-object-invalid` |
   | 封面 URL 不是本平台公开地址，或 key 不在 `{keyPrefix}public/{本人id}/` 下 | 422 `video-object-invalid` |
   | HEAD：对象不存在 / Content-Type 不是 `video/mp4` / 大小 > 100MB | 422 `video-object-invalid` |

   `visibility` 传 PRIVATE 时**不报错**，强制改为 PUBLIC。

6. **HEAD 在事务外【L0 + L1】**
   - L0：`ContentApiController.publish` 对视频帖先调 `VideoPostValidator.verifyObjects`，再调 `ContentService.publish`（Mockito `InOrder`）；`verifyObjects` 所在类/方法没有 `@Transactional`。
   - L1：HEAD 桩的 `Answer` 里断言 `TransactionSynchronizationManager.isActualTransactionActive() == false`。

7. **`desiredOf` 与实体推导【L0】**
   - 纯函数 `MediaAcl desiredOf(PostStatus, Instant deletedAt, ContentVisibility)`：只有 PUBLISHED + 未删 + PUBLIC → PUBLIC，其余全是 PRIVATE（对三个维度的全组合逐一断言）。
   - `ContentPost` 的 `approveReview`、`applyReportHold`、`releaseReportHold`、`softDelete`、`restore`、`setVisibility`、`attachVideo` 内部都重算 desired；**只对 `media_type=VIDEO` 生效**（IMAGE 帖三列始终为 null）；desired **值变化时**才刷新 `media_acl_desired_at`。
   - `restore` 一条仍处 UNDER_REVIEW 的视频帖 → desired 仍为 PRIVATE。

8. **不触发 AI 自动评论与运营暖评【L1】**
   - `AutoCommentLogRepository.findCandidatePostIds` 不返回视频帖；
   - 运营暖评的分发列表（`PostDistributionQuery`）不出现视频帖；对视频帖调用 `VirtualCommentService.postAsVirtual` → 422（新文案码 `admin.err.virtualComment.videoPost`，三语）。

9. **回归【L0 + L1】** 图文帖发布（含挂起分支、私密、@、打卡、露出位置、尺寸）行为不变；现有 `ContentService` / `ContentApiController` 相关测试全绿。

## Dev Notes

### 现状（改动前，已读过）

- **`ContentApiController.publish`**（`content/web/ContentApiController.java:43-51`）：JWT → 限流 `rl:content:publish:` → `contentService.publish(authorId, req, idempotencyKey)`。Controller **没有事务**，这是放 HEAD 的位置。
- **`ContentService.publish`**（`:451-620`，`@Transactional`）顺序：幂等重放 → 图片数 / 最低门槛 → `mentions.sanitize` → `cropOffsets.validate` → 打卡 token → 宠物 / 事件日期 → `moderation.evaluate(text, imageUrls)` → TEXT/IMAGE_BLOCKED 抛 → RISKY/DEGRADED 且 `manualReviewGate.enabled()` 才挂起（关着就放行发布）→ 正常发布写尺寸 / 露出 / @ / 打卡 → `scheduleSizeBackfill` → 幂等 → `ContentPublishedEvent` → `publishMentioned`。
  - 挂起分支的注释反复强调「挂起分支同样要写 X」：视频挂起分支一样，**@ 名单、image_sizes、视频列都要写**。
  - `publishMentioned` 只在 PUBLIC 且名单非空时发；挂起帖在 `approveReview` 里再发 —— 视频帖复用这套，无需改。
- **`publishTrusted`**（`:641-693`）：只给 Lark 定时发帖；跳过审核但**不写 @ 名单**。视频帖不能走它（AD-5、V-40）。
- **`ManualReviewGate.enqueue`** 本身不读开关（接口注释写明「仅在 enabled 为 true 的挂起路径调用」——那是调用约定，不是实现限制）。视频名单外分支是第二个**无条件**调用方，在调用点写注释说明。
- **审核超时**：`ManualReviewService.scanTimeouts` 目前只在总开关开着时丢弃帖子 —— 总开关关着时 VIDEO_FORCED 帖会一直挂着，这是 **Story 3.2** 要改的，本 Story 不动；在 Completion Notes 里提一句。
- **`ContentModerationService.evaluate(text, imageUrls)`**：`imageUrls` 传空列表即只审文本（`imgCount=0`）。
- **`ContentPost`**：`pendingReview(..., riskScore, reviewReason)` 工厂、`REVIEW_REASON_REPORT_P0` 常量、`approveReview / applyReportHold / releaseReportHold / softDelete / restore` 都是一行赋值，往末尾加 `recomputeMediaAcl()` 即可。`discardReview` 在 service 里调 `softDelete`。
- **自动评论候选**（`AutoCommentLogRepository:24-38`）：PUBLISHED + PUBLIC + 未删 + 作者 `account_type='REAL' AND role='USER'` —— 视频官方号就是普通 REAL 用户，**不排除就会被评**。
- **暖评**：运营从 `PostDistributionQuery` 的列表进入抽屉 → `VirtualCommentService.postAsVirtual`（`requirePost(postId, true)`）。两处都要挡。
- **review_reason CHECK**：V48 建、V52 重建为三值，之后无迁移再动（已 grep `migration/` 全目录核实）。列宽 24，`VIDEO_FORCED` 12 字符够用。
- **`VipLevelService.canPublishVideo`**（1.1）直接查库；**`VideoTrustedPublisherService.isTrusted`**（1.1，content 定义的端口）—— 免审**只认名单**，不要用 `isOfficialAccount` / `role`（一致性规则 6）。
- **`AliyunOssClient.objectKeyOfPublicUrl`** 已能把 `media.oss.cdn-base-url` 前缀的 URL 反解成 key（剥查询串、拒 `..`）；**`MediaObjectKeys.belongsTo(props, PUBLIC, userId, key)`** 校验 `{prefix}public/{uid}/`。1.2 的封面 key 正好在这个前缀下。
- 1.2 的视频 key：`{keyPrefix}video/{userId}/{22 位随机}.mp4`，在公开桶，私有 ACL。

### 设计取舍（照做，别改）

- **为什么 HEAD 不放进 `publish`**：`publish` 是 `@Transactional`，HEAD 是一次外网往返（一致性规则 7）。所以拆成「Controller 事务外 `verifyObjects` → 事务内 `publish(…, verified)`」。事务内再判一次等级，是因为等级可能在两步之间被后台降级（AD-5 表把等级标为「内」）。
- **为什么 `mediaAclApplied` 不可更新**：见 T2 🔴。1.4 的对账器靠条件 UPDATE 写它，实体整行 save 会把它写回旧值。
- **为什么 desired 只在值变化时刷新 desiredAt**：`desiredAt` 是 1.4「超过 5 分钟仍不一致就告警」的计时起点；无变化也刷新会让卡住的帖子永远不报警。
- **为什么不信任客户端 `imageSizes`**：AD-1，视频帖的尺寸就是视频显示宽高，由服务端写；而且封面是私有的，兜底测量拉不到，所以也不排兜底测量。
- **visibility 传 PRIVATE 不报错而是强改 PUBLIC**：AD-5 表「忽略请求值」。视频帖只有日常 / 科普，本来就没有私密入口。
