# Story 13.4: 校验预览、确认发布与去重口径修正

Status: review

## Story

As a 运营，
I want 批量提交前能逐行看到校验结果、只发通过的行，
so that 50 行里错 3 行不会变成 3 条线上真帖。

---

> 🔴 **前置：13-1 / 13-2 / 13-3**。本 story = AB-3K 的 Step 3 + 去重口径修正。
>
> **现状最严重的一点**（已实读确认）：**没有校验预览、没有确认入库，提交即上线** ——
> 50 行错 3 行就是 3 条线上真帖，只能逐条去找、逐条下架。

---

## Acceptance Criteria

### AC1 — 逐行校验预览（L1）

**Then** 逐行展示：行号 / 正文摘要 / 图片缩略图 / 发布账号 / 内容类型 / 关联物种 / 计划发布时间 / 校验结果 `[L1]`

### AC2 — 🔴 只发通过的行，失败行不阻塞整批（L1）

**Then** 🛡 校验失败的行**不阻塞整批**，通过的行可直接确认发布 `[L1]`
**And** 失败行以**草稿态保留在该批次内，可修改后再次提交** `[L1]`
**And** 确认发布后，按批次级 / 行级的计划发布时间决定**立即发布**还是**转入排期**（13-5）`[L1]`

### AC3 — 异常场景处理（L1）

**Then** `[L1]`：

| 场景 | 处理 |
|---|---|
| 图片文件名在本批素材中找不到 | 该行失败，注明缺失的文件名；其余行不受影响 |
| 图片格式 / 大小不符 | 13-2 上传阶段即拦截，不进入录入 |
| 同批图片文件名重复 | 13-2 上传阶段即拦截 |
| 单批素材超 200 张 / 500MB | 13-2 **选择文件时**即拦截 |
| 发布账号不在身份池内 / 已禁用 / 已移出 | 该行失败，注明行号与原因 |
| 发布账号**留空** | 🔴 **正常放行**，继承批次默认（**覆盖** V1.1.0 原「留空报错」） |
| 内容类型 / 关联物种值不在枚举内 | 该行失败，注明合法取值 |
| 内容类型填了 `GROWTH_MOMENT` | 该行失败，注明批量不支持、请走 12-2 单条发布（模板下拉已不含该值，此处拦手工改写模板的情形） |
| 与已发布内容重复（去重命中） | 🔴 **标记为提示，不静默跳过**（见 AC4） |
| 正文与图片皆空 | 该行失败（沿用 App 端的最低内容门槛） |

### AC4 — 🔴 去重口径三处修正（L1）

**Then** 🔴 去重维度**加入作者** —— 同一文案不同账号各自独立 `[L1]`
**And** 🔴 命中**不再静默跳过**，改为在预览里标记提示、由运营决定是否仍要发布 `[L1]`
**And** 🔴 **内容被删除时清理对应的指纹记录** `[L1]`

> 三处现状均已实读确认：`seed_content_hashes` 以 **`content_hash` 单列为主键**
> （表里有 `author_id` 列，但**不参与键**），命中即静默跳过、界面只显示一个跳过条数，
> 且**没有任何清理逻辑**。
>
> 两个实际后果：
> ① 同一文案想用两个不同账号各发一遍（内容运营常规操作，引入运营真实账号后会更频繁），
>    **第二次会被吞掉**；
> ② 已发布内容被删除后指纹记录不清理，**同样的文案永久无法重发**。
>
> ⚠️ 加作者维度 = **改这张表的主键**。既有行的 `content_hash` 本就唯一，
> 所以 `(content_hash, author_id)` 也必然唯一，改键安全、无需去重清理。
> 🔴 迁移用**时间戳号**（E6）。
>
> ⚠️ 「删除时清理」要挂在**所有**删除路径上：作者自删、运营下架、账号注销级联。
> 漏一条就是那条路径删掉的内容对应的文案永久无法重发。

### AC5 — 批次审计（L1）

**Then** 每个批次记录操作人、时间、以及批次内容清单（**含各行最终生成的内容 ID**）`[L1]`

> 内容清单同时是后续「整批撤回」的数据基础（本版本不做，OQ-22）。

### AC6 — 内容类型范围（L0）

**Then** 放开为 `DAILY` + `KNOWLEDGE` `[L0]`
**And** 🛡 `GROWTH_MOMENT` **仍不纳入批量** `[L0]`

> 已实读确认现状硬编码为单一类型（`new ContentPostCreateRequest(ContentType.DAILY, ...)`）。
> 这是 V1.1.0 AB-1.1-02 的**原有要求**，属**实现偏差而非需求变更** —— 本 story 只是把它恢复。
>
> 🔴 PRD 写的 `MOMENT` 在代码里不存在，就是 `DAILY`。

### Completion Notes List

#### 🔴 一、改主键这一步，编译器帮我把老调用点揪出来了

`seed_content_hashes` 从 `content_hash` 单列主键改成 `(content_hash, author_id)` 之后，
仓储的 id 类型跟着变，于是**老路径那句 `hashes.existsById(hash)` 直接编译不过** ——
而那一句正是 AC4 说的"命中即静默跳过"的现场。

⚠️ 改键**安全无需去重**：既有行的 `content_hash` 本就唯一，所以复合键也必然唯一。

**两条路径的去重判据已统一，但"命中之后怎么办"刻意不同**：
- 新工作台（有预览）⇒ **提示**，由运营决定；
- 老路径（Story 9.8 的"贴进去就发"，没有预览这一步）⇒ **仍然静默跳过**，因为它无处展示提示。
这一点写在代码注释里，免得后来人以为漏改了一处。

顺带把指纹算法抽成 `SeedContentFingerprint` 共享：两条路径写进的是**同一张表**，
各算一份的表现是"老路径发过的文案，新工作台判不出重复" —— 而那种不一致没人会想到去查。

#### 🔴 二、"挂在所有删除路径上"这条要求，我没有逐个入口去挂

story 自己写了风险：「要挂在**所有**删除路径上，**漏一条就是那条路径删掉的内容对应的文案
永久无法重发**」。而删除路径不止一条（作者自删 / 运营下架 / 按作者批量下架 / 审核判违规丢弃），
将来还会加。

实读发现 **Story 4.1 已经建好了正确的缝**：`ContentUnavailableEvent` ——
"这条内容没了，凡是引用它的地方都该收手"，且**软删时无论什么原因都发**。
订阅它 ⇒ 现有路径一次覆盖，**将来新增的删除路径自动覆盖**。

**🔴 但订阅时发现那个事件本身漏了一条路径**：`discardReview`（人工审核判违规丢弃）
直接调 `p.softDelete()`，**不发事件**。它此前没被注意到，是因为 4.1 的顶置联动碰不到挂起内容
（顶置选择器只挑得到公开内容）。**但去重指纹会碰到**：批量发布记指纹是在 publish 之后，
而开了人工审核时 publish 落的就是 `UNDER_REVIEW` —— 审核丢弃之后指纹留着、内容没了，
**正是 AC4 要修的那个后果**。已补上事件发布，并写明为什么用 `AUTHOR_DELETE` 作 reason
（`ADMIN_TAKEDOWN` 会触发"你的内容因违规被移除"的通知，而审核丢弃不该给作者发那条）。

监听器用 `@EventListener` + `@Transactional`（汇入调用方事务），**不是提交后触发** ——
与 `ContentPinTakedownListener` 同一判断：这是**数据副作用**，删除回滚了指纹清理也必须跟着回滚，
否则会出现"内容还在、但指纹没了"，于是同一文案能被重复发布两遍。

#### 🔴 三、硬错误与提示是两类东西，混在一起就等于没提示

- **硬错误** ⇒ 该行不发、留草稿可改后重提，🛡 **不阻塞整批**。
- **去重命中** ⇒ 只是**提示**。原先是静默跳过、界面只显示一个跳过条数，
  运营根本不知道**哪一条**被吞了。

🔴 「重复的也发」这个勾选框**默认不勾**：去重命中在预览里是提示，
但"提示了却默认照发"等于没提示。

**每条错误都要能对上运营那份表格**：素材报**文件名**、类型报**合法取值**、账号报**原因**。
其中 `GROWTH_MOMENT` 单独给一句话**指向单条发布** —— 只说"类型不合法"会让运营以为是填错字，
而实际是"这条得换个入口发"。

录入阶段已经记下的问题（缺账号/缺类型/素材名对不上）**原样带出来**，
🛡 在校验里重算一遍会和录入时的措辞分叉，而运营看到两种说法会以为是两个问题。

#### 多校验了一条 AC 没列的场景

**录入之后素材被清理掉**（13-2 的废弃回收）。不再看一遍的话会发出一条**图片 404** 的内容 ——
而运营在预览页上完全看不出问题（缩略图是坏的，但他可能以为是加载慢）。

#### 单行失败不拖垮整批

`publishNow` 抛异常时捕获 **`RuntimeException` 而不是 `AppException`**：
对象存储抖动之类会抛别的类型，而"一行挂了整批回滚"是最糟的结果。
记失败用 `REQUIRES_NEW`：外层事务可能已因那次异常被标记回滚，
在同一事务里写"失败原因"会连带丢掉 —— 于是运营看到一行没有任何说明的失败。

#### AC6 是恢复一处实现偏差，不是需求变更

老路径把内容类型硬编码成 `ContentType.DAILY`。V1.1.0 AB-1.1-02 本来就要求
`DAILY` + `KNOWLEDGE` —— 这是**实现偏差**。现在类型取自该行。
（🔴 PRD 写的 `MOMENT` 在代码里不存在，就是 `DAILY`。）

#### 立即发布不硬走 SCHEDULED

有计划时间 ⇒ 转 `SCHEDULED`（13-5 到点发）；没有 ⇒ `VALIDATED → PUBLISHED` 直接发。
硬走 SCHEDULED 得编一个假的计划时间，排期列表里会出现一堆从未被排期的行
（13-1 的状态机注释里记着同一条理由）。

#### 重复点确认不会重发

运营可能把预览页刷两遍再点确认。已发/已排期的行直接跳过。

#### 一处存量口径变化，写在这里备查

12-1 的「其中 N 条已被删除」计数（`countDeletedByAuthorId`）在新数据上**会恒为 0** ——
因为指纹现在随内容删除被清掉了。它仍然保留，是为了存量（13.4 之前发的、已被删的）那部分仍能被看见。
已在仓储注释里写明。
