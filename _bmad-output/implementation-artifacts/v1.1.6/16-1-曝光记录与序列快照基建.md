# Story 16.1: 曝光记录与序列快照基建

Status: review

## Story

As a 首页推荐算法，
I want 有地方记「这个人看过哪些内容」和「这次刷新算出来的序列」，
so that 曝光衰减能生效、翻页不会重复。

---

> 🔴 **本 story 必须最先做**：它是 FR-95 的两项工程硬前置（补充 PRD §8.1），
> 缺前者则「已看过的反复出现」这一半问题**不会被解决**，缺后者则**翻页重复**。
>
> ✅ **Redis 已在平台内广泛使用**（在线状态 / 通知未读 / 登录限流），无基建风险。

---

## Acceptance Criteria

### AC1 — 曝光记录（L1）

**Then** 「用户 × 内容」曝光记录：Redis set，键 `feed:seen:{userId}`，**7 天 TTL** `[L1]`
**And** 🛡 **不入 PG** `[L0]`（写入量大、无查询价值；PRD §8.1 明确建议）
**And** 序列生成时读该集合，命中的内容施加**曝光衰减系数**（默认 0.3，可配）`[L1]`
**And** 🛡 **是降权不是硬过滤** `[L0]`

> 池子只有几百条，硬过滤已看过的内容会让活跃用户**直接刷空**。

### AC2 — 🔴 什么时候算「已曝光」（L1）

**Then** 🔴 序列**返回给客户端时**即记入曝光，**不等客户端上报** `[L1]`

> 🔴 **这条必须定死**：等客户端上报"我真的看到了"需要一套曝光埋点回传，
> 而 PRD §8.3 已核实**数据侧没有曝光类埋点**。用"下发即记"是唯一现在做得到的口径。
> ⚠️ 代价是**下发但用户没滚到**的内容也会被记入，下次被降权 —— 这是已知偏差，
> 因为它是**降权不是过滤**，偏差的后果只是那条内容排得靠后一点，可接受。

### AC3 — 序列快照（L1）

**Then** 键 `feed:seq:{userId}:{seed}`，**TTL 30 分钟**；冷启动/下拉刷新时按
`用户 id + 刷新时间戳` 生成种子，一次性算出**前 100 条**完整序列 `[L1]`
**And** 翻页只按游标读缓存序列，🛡 **不重算分数** `[L1]`
**And** 下拉刷新 = 换种子 = 重新生成序列 `[L1]`
**And** 游标超出 100 条 → 用**同一种子**续算下一段 `[L1]`

> 🔴 **为什么是必要项不是优化项**：分数随点赞/评论变化，每次翻页实时重算会让
> 第 2 页**重复**第 1 页的内容、也会**跳过**某些内容。这不是性能问题，是正确性问题。

### AC4 — 游客（L1）

**Then** 未登录游客用**客户端生成的匿名会话 id** 作缓存键 `[L1]`
**And** 🛡 **曝光衰减对游客不生效** `[L0]`（无跨会话曝光记录）

### AC5 — 🛡 Redis 不可用时不能白屏（L1）

**Then** 🛡 Redis 不可用 ⇒ **实时计算当页**，接受翻页可能重复，**记告警** `[L1]`
**And** 🛡 **绝不因缓存不可用而返回空页或报错** `[L1]`

> 对应降级链级别 3。⚠️ 级别 3 与 4 **需要告警**，级别 1、2 是预期行为**不告警**（§6.2）。

### AC6 — 索引重估（L0）

**Then** ⚠️ 既有 `(visibility, created_at DESC)` 是为**时间倒序** Feed 建的，
推荐序**不按 `created_at` 翻页** —— 须评估推荐序候选池查询实际走什么索引，必要时另建 `[L0]`
**And** 🛡 **不删除既有索引** `[L0]`（非 ALL Tab 与降级链级别 4 仍走时间倒序）

### AC7 — 本 story 不做的（L0）

**Then** 🛡 `[L0]`：不做打分（16-2）、不改 Feed 接口（16-3）、不做参数配置化（16-4）

### Completion Notes List

**1. 🔴 有意偏离 AC1 字面：用 ZSET 而不是 SET**

AC1 写「Redis set，7 天 TTL」。**SET 做不到这个意图**：Redis 的 TTL 只能设在**键**上，
SET 成员没有各自的过期；而每次曝光都要写入 ⇒ 键 TTL 必然被反复续期 ⇒ 对天天刷首页的用户
那个键**永不过期**，半年前看过的内容仍算「已曝光」。
后果不报错，只是排序悄悄失真：几乎所有内容都挂 0.3 系数，**曝光衰减这一维等于被抹平** ——
而这正是本 story 要解决的那半个问题。

改用 `ZSET member=contentId score=曝光时刻`：7 天是**每条曝光各自的**窗口。
读路径按 score 判窗（出窗即视为未曝光），写路径顺带 `ZREMRANGEBYSCORE` 修剪防止键无界增长。
顺带也让 16-4 的「曝光窗口天数」可调真正有意义 —— 改 SET 的键 TTL 改不动存量成员。

**2. AC2「下发即记」的落点在 16-3**

本 story 交付 `markSeen(...)`，**调用点在 16-3**（序列返回给客户端时调）。
这里只保证「调了就记对、不调就不记」。

**3. ⚠️ 匿名会话 id 是键注入面（AC 没写，但必须做）**

游客键空间来自**客户端传来的字符串**。直接拼进 Redis 键有两个洞：
冒号能伪造别人的键空间（`a:x` + `":u:1"` 落到 `feed:seen:a:x:u:1`），超长串能刷内存。
`FeedRankCacheKey.forGuest` 只保留 `[A-Za-z0-9_-]`、截断到 64 字符；
规范化后为空则落一个共享兜底键空间（**不抛错** —— 游客刷首页不该因客户端传了怪串就 500，
代价是这类游客共用序列快照、可能互相覆盖，只影响翻页体验）。

**4. 🛡 游客的两个键待遇不同（AC4 只写了一半）**

- 曝光记录：**不生效**（不写不读）—— 匿名会话 id 换个会话就全忘，记了只会得到假记录
- 序列快照：**照常生效** —— 它解决的是同一会话内的翻页重复，与跨会话无关

AC4 只说了「曝光衰减对游客不生效」，容易被读成「游客整套缓存都不用」。已在代码注释里写明。

**5. T4 索引重估结论：不新建索引，也不删既有索引**（真库 EXPLAIN，`petgo_rebased`，池 7127 条）

| 查询 | 计划 | 耗时 |
|---|---|---|
| 推荐序候选池（无 `created_at` 游标） | **Seq Scan** | 0.95 ms |
| 时间倒序 + `LIMIT 21` | Index Scan using **`idx_content_posts_feed`**，21 行即停 | 0.53 ms |
| 候选池 + 近 30 天窗口 | 仍 Seq Scan（窗口没筛掉东西） | 3.0 ms |

- **推荐序不需要新索引**：候选池条件命中全表约 90%，任何索引扫回这么多行都比顺序扫慢 ——
  PG 选 Seq Scan 是**正确**的，加索引只会多一份写放大且用不上。
- 🛡 **既有索引一个都不能删**：时间倒序路径实际走的是 **V8 的 `idx_content_posts_feed`**
  （不是 V98 的 `idx_content_posts_visibility_created_at`），而非 ALL Tab 与降级链级别 4 都靠它。
- ⚠️ **留给 16-3 的一条**：候选池是全表扫，成本随总帖数**线性增长**。
  现在 7k 行 1ms 无所谓；序列快照的作用之一正是让这次扫描**每次刷新只发生一次**而不是每页一次。
  重估阈值：**总帖数超过 ~10 万**时需要给候选池加时间窗或物化，那时才需要新索引。

**6. 三次反证（改坏实现 → 确认指定断言按预期变红 → 还原）**

| 反证 | 变红的断言 | 变红原因 |

换成合法 score（0）重做才拿到干净的一条红。这与 15-1 那次「反证红得不是地方」同类。
