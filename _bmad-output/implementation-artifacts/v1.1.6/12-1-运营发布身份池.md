# Story 12.1: 运营发布身份池

Status: review

## Story

As a 运营，
I want 后台的「发布账号」除了虚拟号，还能选公司那几个人格化 IP 真实账号，
so that 那类内容（有宠物档案、有粉丝、主页不空）真的发得出来。

---

> 🔴 **本 story 必须最先做**：12-2 与 Epic 13 的「发布账号」选择器数据源就是它。
>
> **背景**：虚拟账号没有宠物档案（发不了成长日历）、没有粉丝积累、主页是空的 ——
> 替代不了人格化 IP 号。而当前后台的发布账号只接受虚拟账号。

---

## Acceptance Criteria

### AC1 — 身份池容纳两类账号（L1）

**Then** 「虚拟账号管理」页升格为「运营发布身份」管理，分两区：【虚拟账号】【运营真实账号】`[L1]`
**And** 🛡 虚拟账号侧的既有能力**全部不变**（创建 / 列表 / 启停 / 导出）`[L1]`

### AC2 — 🛡 不新增账号类型（L0）

**Then** 🛡 运营真实账号的 `account_type` **保持"真实用户"不变** `[L0]`
**And** 只加一张授权关联表（用户 ID + 授权说明 + 纳入人 + 纳入时间 + 状态）`[L0]`
**And** 🔴 唯一需要放开的是批量发布服务里那句作者类型硬断言 `[L1]`

> 已实读确认现状：`AdminSeedBatchService` 里有
> `if (author.getAccountType() != AccountType.VIRTUAL) { ... }`。
> 改为"在身份池内即可"，**不要**去改账号类型 —— 一旦真实号被改成别的类型，
> 它在 App 内的一切行为（登录、发帖、被查看）都会走进未被验证的分支。

### AC3 — 纳入与移除（L1）

**Then** 纳入：按用户 ID / 昵称搜索既有真实用户 → 填**授权说明（必填）** → 确认 `[L1]`
**And** 🛡 **不做 App 端验证**（不要求员工扫码或输验证码）`[L0]`（A-6：风险边界是"内部人冒充内部人"，审计追责比技术强绑定划算一个量级）
**And** 移除后该账号**不可再被选为新内容的发布者**；历史内容作者归属与内容本身**完全不受影响** `[L1]`
**And** 🛡 **移出 ≠ 封号** —— 只收回"后台可代其发布"这一项，该账号在 App 内的一切行为不受影响 `[L1]`

### AC4 — 🔴 移出前必须提示待发布排期数（L1）

**Then** 🛡 移出确认弹窗须显示「该账号当前有 **N 条**待发布排期，移出后这些内容到点将发布失败」`[L1]`
**And** 提供跳转链接直达按该账号过滤的排期列表 `[L1]`
**And** 🛡 **不阻止移出** —— 运营可能正是要停掉这个号 `[L1]`
**And** 🛡 排期**不自动取消、不自动转草稿** —— 保持"到点标记失败并注明原因" `[L1]`
**And** ⚠️ 虚拟账号的**「禁用」操作同样适用本提示** `[L1]`

> 不做这条的后果很具体：那 N 条会在未来若干天里**陆续、分散地失败**，运营要等到失败才发现，
> 而届时内容的时间窗（如配合某活动）多半已经错过。
> 移出是个瞬间的、有明确操作人的动作，是成本最低的提示时机。
>
> **为什么不自动改状态**：自动取消是替运营做决定；失败记录带原因比静默转草稿更可追溯。
>
> ⚠️ 虚拟账号禁用这条 V1.1.0 原文没有（当时还没有定时发布能力），属本次引入排期后的连带影响。

### AC5 — 🔴 独立权限码，与虚拟账号管理解耦（L0）

**Then** 🛡 新增独立权限码 `seed.publish_as_real`，控制两件事 `[L0]`：
① 运营真实账号的纳入 / 移除；② **以运营真实账号身份发布内容**（12-2 单条 / 13-x 批量 / 13-5 定时，三处）
**And** 🛡 与既有 `virtual_account.manage` / `virtual_account.view` **完全解耦** `[L0]`
**And** **本版本仅分配给超级管理员**，不下放（OQ-24）`[L0]`
**And** 后台账号权限勾选清单同步新增该项 `[L1]`

> **能管虚拟账号 ≠ 能以真人身份发言。** 权限码独立存在的意义是后续如需下放，
> 只改权限配置、不改代码。
> ⚠️ 权限码一旦落地即**冻结**（改名会切断已授予关系），只有显示名可改。

### AC6 — 🔴 选错身份的防呆（三处发布入口统一）（L1）

**Then** 🛡 所有「发布账号」选择器统一遵守 `[L1]`：
- **分组展示，不平铺**：【虚拟账号】/【运营真实账号】
- 真实账号项带**显著视觉标记 + 后果说明**（建议：「⚠️ 真实账号 · 内容会出现在该账号个人主页并推送给其粉丝」）
- 🛡 **默认不预选任何账号**，强制显式选择
- 🛡 **仅当选中运营真实账号时**弹二次确认（虚拟账号不弹，避免拖慢常用路径）

> 以运营真实账号误发的后果**不可撤回** —— 内容会出现在那个真人的个人主页并推送给他的粉丝，
> 事后删除也已经推送过了。

### AC7 — 列表字段与审计（L1）

**Then** 列表：用户 ID / 昵称 / 头像 / 授权说明 / 纳入时间 / 纳入操作人 / 状态 / **经后台发布内容数** / **物种推导结果 + 来源** `[L1]`
**And** 🛡 **「经后台发布内容数」只统计经后台代发的内容** —— 该账号在 App 内自主发布的不计入 `[L1]`
**And** 纳入 / 移除记审计（操作人、时间、目标账号、授权说明）`[L1]`
**And** 🛡 **以运营真实账号发布的每条内容，记录实际操作的后台账号** `[L1]`

> 最后一条是与虚拟账号最大的差别：虚拟账号是平台身份，运营真实账号是**某个真人的账号**，
> 出事要能追到具体是谁操作的。
>
> 「物种推导结果 + 来源」是只读自查列：运营真实账号**没有**「账号物种定位」字段
> （那是虚拟账号补偿"无宠物档案"的专属字段），所以**未建档或养多物种的号推不出具体物种**。
> 本列的用途就是让运营提前知道哪些号属于这种情况，否则无从察觉。

### AC8 — 两个写入方的边界（L1）

**Then** 🛡 **后台不阻止持有人在 App 内删除后台代发的内容** —— 那是他自己的账号，系统去锁定反而越权 `[L1]`
**And** 但**后台的批次记录须能反映该条"已被删除"**，不可继续显示为在线 `[L1]`
**And** 🛡 持有人在 App 内自主发布的内容**不进后台批次/排期记录**，也不计入「经后台发布内容数」`[L1]`

> 运营真实账号有**两个写入方**（后台代发 / 持有人本人），这是"引入真实账号"这一决策的
> **固有代价，不是能设计掉的问题**。本条只把边界写明，使运营有预期。虚拟账号不存在此问题。

### AC9 — 不做的（L0）

**Then** 🛡 `[L0]`：
- **不支持员工私人账号** —— 身份池只接纳公司资产性质的 IP 号（A-7：一旦支持，技术上就再无法区分公司号与私人号，风险敞口无法收口）
- **不做 App 端绑定验证**（A-6）
- **运营真实账号的点赞 / 评论不在本条范围** —— 那仍归 AB-3F（未上线版本），本条只放开**发布**

### Completion Notes List

#### 🔴 一、核心判断：把"谁能当作者"从**账号类型**换成**在不在池内**

原先挡着真实账号的就是一句
`author.getAccountType() != AccountType.VIRTUAL`。改它，**不是**去改那个真人号的
`account_type` —— 后者是"看起来更省事"的做法，代价是它在 App 内的登录、发帖、被查看
全部走进为虚拟账号写的分支，而那些分支从来没被真人流量验证过。

所以落地是**加一张授权关联表**（`seed_real_account_grants`），发布链路只问
`isInPool(author)`。已由 `grantingKeepsTheAccountTypeUntouched` 钉住类型不变。

**授权是有历史的**：纳入 → 移出 → 再纳入。每次纳入一行新记录，移出只把该行标成
`REMOVED` 而**不删行** —— 否则"谁在什么时候把谁移出去的"就查不到了。
同一账号同时只允许一条 `ACTIVE`，DB 侧用 partial unique index 兜底
（`where status = 'ACTIVE'`），不是只靠应用层判断。

#### 🔴 二、`seed.publish_as_real` 的检查做成**显式入参**，而不是服务里偷读 SecurityContext

`publishBatch` 多了一个 `boolean callerMayPublishAsRealIdentity`。理由：
这个检查要在**三处**发布入口都成立（12-2 单条 / 13-x 批量 / 13-5 定时），
而"忘记检查"是**静默的** —— 做成参数就让漏掉变成**编译错误**。
从 SecurityContext 里偷偷读的话，13-5 的作者不会知道有这回事。

**这个决定当场就见效了**：加上参数后，三处手写 `new AdminSeedBatchService(...)` /
`new AdminWebController(...)` 的既有测试立刻编译失败，被迫逐个看过一遍。

#### 🔴 三、AC4 的排期提示：机制在本 story，数据源留给 13.5

「移出前告诉运营还有 N 条待发布排期」属本 story，但**排期这个概念要到 13.1/13.5 才存在**。
所以抽了一个只读端口 `PendingPublishScheduleCounter`，当前实现 `NoContentScheduleYet` 恒返回 0 ——
🔴 **这个 0 是正确答案，不是占位假数据**：系统里确实还没有任何内容排期。

本 story 交付的是提示的**机制与三条护栏**（不阻止移出 / 排期不自动取消 / 不自动转草稿），
13.5 只需换掉那一个实现。🛡 **story 里特意写明：不要在 13.5 里另写一处提示** ——
虚拟账号禁用与真实账号移出会各判一次，两处口径迟早分叉。

⚠️ **虚拟账号「禁用」走的是同一个确认页**（V1.1.0 原文没这条，是引入排期后的连带影响）。
顺带把列表页的启停按钮拆开了：**禁用**先过确认页，**启用**仍直接提交（启用是无害的）。

**为什么是服务端渲染的一整页，而不是浏览器 `confirm()`**：那一页要显示 N，
而 N 只有服务端算得出来。不提示的后果很具体 —— 那 N 条会在未来若干天里
**陆续、分散地失败**，运营要等到失败才发现，届时内容的时间窗多半已经错过。

#### 🔴 四、`has_milestone` 那类坑的同款：物种推导的"多物种"分支**故意不留**

AC7 的说明写着「未建档或**养多物种**的号推不出具体物种」。实读后确认：
`PetProfileRepository#findByOwnerId` 返回 `Optional` —— **一个用户至多一份宠物档案**，
所以"养多物种"在当前数据模型里**不可能出现**。

故只写"有档案 / 没档案"两支，并在代码注释里写明为什么不提前留第三支：
留了也没人能走到，反而让读代码的人以为系统支持多宠物。真要支持那是另一件事（会改 V1 的档案模型）。

#### 🔴 五、AC6 的防呆做成一个**共用 Thymeleaf 片段**

`admin/fragments/publish-identity-select.html` + `admin.js` 里一段
`data-real-identity-confirm`。四条行为：分组不平铺 / 真实账号带 ⚠️ 与后果说明 /
**默认不预选**（占位项 `disabled selected`）/ **仅选中真实账号时**弹二次确认。

🔴 **二次确认为什么不用既有的 `data-confirm`**：那个是静态文案、每次提交都弹。
虚拟账号是常用路径，每次都拦会让运营养成"不看就点确定"的习惯 ——
**那时真正危险的那一次也会被闭着眼点过去**。所以判据取选项上的 `data-real="true"`。

顺序也不是审美：**虚拟账号在前、真实账号在后**，手滑选到靠前项时选到的是危害最小的那类。

🛡 前端这一层只是体验，服务端另有一道 `seed.publish_as_real` 硬校验（勾选框在浏览器里改得动）。

#### 页面改名按"四处同源"办

导航名 / 页内标题 / 页面说明 / 仪表盘磁贴一起改成「运营发布身份」；虚拟账号那一区降为二级标题。
⚠️ **URL 刻意不改**（`/admin/virtual-accounts`）：改路径会让运营的收藏夹与既有测试一起失效，
而"这一页管什么"是界面上的事、不是路径上的事。

`virtual_account.manage` 的权限显示名**没动** —— 它现在确实只管虚拟账号那一区，
和新的 `seed.publish_as_real`（"以运营真实账号发布内容"）并列不矛盾。

**入口门与侧栏条件逐字一致**：列表页的 `VIEW_AUTH` 加上了 `seed.publish_as_real`
（只持该码的人否则会看得见入口、点进去 403），侧栏那两处 `sec:authorize`（外层折叠区 + 链接本身）
同步加上。已由 `seedPublishAsRealAloneCanOpenThePage` 钉住。

#### 🔴 踩到的一个真实陷阱：`==` 比装箱 Long

补强「持有人自主发布的不计入」那条断言时，我先写了
`posts.findAll().stream().filter(p -> p.getAuthorId() == u.getId())`。
`ContentPost#getAuthorId()` 返回的是**装箱 `Long`**，`==` 比的是**对象引用** ——
id 超过 127 就跳出 Long 缓存，恒为 `false`。

🔴 **而 `false` 恰好让计数为 0，而 0 正是这条断言期望的另一半** —— 于是它会**安静地通过**。
是因为我先加了一句"证明他确实发出去了"才暴露出来（那句本来就是为了让断言不空转加的）。
改用 `Objects.equals`。**这类错误在断言"应该为 0"的测试里格外危险。**

#### 明确没做的（AC9）

- **不支持员工私人账号**（A-7）：这条**靠流程与审计守，代码里守不住** ——
  所以「授权说明」是必填的，它是这条链上唯一记录"为什么可以"的地方。
- **不做 App 端绑定验证**（A-6）：风险边界是"内部人冒充内部人"，技术强绑定挡不住。
- **点赞 / 评论不在本条范围**（仍归 AB-3F，未上线版本），本条只放开**发布**。
- **单条发布（`/admin/seed-post` POST）没动**：它现在仍以操作人自己关联的官方作者身份发布，
  改成可选身份是 **12-2** 的事。本 story 只交付身份池 + 共用选择器组件。

**留 L2 的**：真机/浏览器上确认二次确认弹窗只在选中真实账号时出现（widget 层无法验 `window.confirm`）。
