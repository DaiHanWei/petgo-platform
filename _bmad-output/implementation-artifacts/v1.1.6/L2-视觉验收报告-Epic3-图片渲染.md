# V1.1.6 Epic 3「Feed 卡片改造」图片渲染 L2 视觉验收报告

- **日期**：2026-08-24
- **环境**：模拟器 `petgo_phone`（Android 16 / API 36.1，1080×2400 / density 420 / DPR 2.625）
  \+ 本地后端（真 PostgreSQL `petgo_rebased` / Redis）
- **范围**：Story 3.3（图片高度护栏与 clamp）、Story 3.4（多图轮播）
- **触发**：做 Epic 16（首页推荐算法）的 L2 时发现测试库内容**全是纯文字**，
  图片渲染这条链路从未实机看过。用户提供了 7 张城市风格参考图，据此造了带图内容补验。
- **结论**：**功能全部按设计工作**；发现 **3 项待决**（都不是 bug，是标定与产品取舍）。
  其中「混合比例」那项已当场实机试过一种改法（纯白填充），**结论是不建议**，见 §4.1

---

## 一、验收方法

⚠️ **注入的是非 OSS 直链**（本地 HTTP 服务 + `image_urls` / `image_sizes` 直接落库），
所以**绕过了 OSS 缩略图管线** —— 生产环境会经 `x-oss-process` 缩放，本地拿的是原图。
这只影响下载体积与解码耗时，**不影响布局**（布局只看 `image_sizes`），故布局结论有效。
🔴 但**性能相关的观察在本地不成立**，别拿本地的加载速度推断线上。

造的数据（比例刻意覆盖 clamp 区间内外）：

| 内容 | 比例 | 目的 |
|---|---|---|
| 单图 × 7（原始参考图） | 0.67 / 0.75 / 0.80 | 0.67 在 clamp 下界外，验夹紧 |
| 多图 × 1（3 张） | 0.67 → 0.80 → 0.80 | 验轮播 |
| 有图**无尺寸** × 1 | — | 验存量内容兜底（零回填） |
| 混合比例 × 4（各 3~4 张） | 首图分别为 0.67 / 1.25 / 1.00 / **2.00** | 验「首图锁定高度」的代价 |

## 二、通过的项（实机量测，非肉眼判断）

| 项 | 期望 | 实测 |
|---|---|---|
| clamp 下界 | 0.67 → 夹到 **0.75** | 图片框比例**正好 0.750** ✅ |
| clamp 上界 | 2.00 → 夹到 **1.34** | 图片框比例**正好 1.340** ✅ |
| 有图无尺寸 | 按 1:1 预留 → 解码后落到真实（clamp 后）比例 | 未撑破、未塌陷 ✅ |
| 翻页不改高 | 容器高度恒定 | 4 张翻完，比例全程 0.750（另一条全程 1.340）✅ |
| 多图轮播可滑 | 横滑翻页 | 快滑 / 慢滑（0.9s）/ 斜滑（横 500 竖 350）**均可翻页** ✅ |
| 单图不接横向手势 | 单图卡横滑无反应 | 确认无反应 ✅（这是**设计如此**，防斜滑截胡列表滚动） |
| 轮播圆点 | 显示张数与当前页 | 显示正确，翻页同步 ✅ |

## 三、🔴 待决项一：正文两行时「露出余量」失效

**现象**：卡片对齐视口顶部时，正文**一行**→ 下一条头像正常露出；正文**两行**→
连本条自己的时间行都被底部导航挡住，下一条完全不露。

**实测数字**（正文两行那条）：

| | 逻辑像素 |
|---|---|
| 卡片顶（作者行）起始 | 132 |
| 图片高（0.75 框） | 549 |
| 卡片底 | **823** |
| 底部导航上边 | **≈823** |

**为什么要紧**：`feed_image_layout.dart` 自己的注释写着 ——

> 判据始终不是这个数字，而是可观测的那句：**下一条内容的顶部总能露出来**。

按公式该留 40 逻辑像素，实测 0。

**推断的原因**：`FeedCardMetrics` 的减项估小了。嫌疑最大的是
`bodyRows = 50`（按 2 行满行估）—— 中文两行在本机的实际行高加上边距略超 50；
`authorRow = 42` 在带内容类型角标时也可能偏小。合计差约 25~40。

**🛡 未自行修改**。理由：`kFeedRevealMargin` 是 2026-08-18 靠一次**小屏实机复核**
定死的（56 → 40，OA-1 闭合），当时的结论是「改为 40 后在最小屏上也不会比改版前更差」。
在一台 1080×2400 上量出的数**不该直接推翻小屏那次的结论** —— 要调得在小屏上一并复核。

**建议**：在 360×640 与本机两档上各量一次「正文两行 + 竖图」的组合，再定 `bodyRows`。

## 四、🔴 待决项二：混合比例多图的裁剪代价（产品取舍）

**规则**：高度**只按首图**锁定，其余图 `BoxFit.cover`（居中裁剪填满）。
代码理由正当：Feed 是长列表，翻图时改高会把下方所有卡片整体推动。

**代价（实测，可算）**：

| 框（首图） | 后续图 | 可见部分 | 被裁掉 |
|---|---|---|---|
| 0.75（竖） | 横 1.25 | 60% 宽 | 40% |
| 0.75（竖） | 方 1.00 | 75% 宽 | 25% |
| 0.75（竖） | **超宽 2.00** | **37.5% 宽** | **62.5%** |
| 1.34（超宽） | 方 1.00 | 75% 高 | 25% |
| 1.34（超宽） | **竖 0.67** | **50% 高** | **50%** |

**为什么要紧**：真实用户**会在一条帖里混着竖拍和横拍**，而**首图是哪张往往是随手选的** ——
用户不会意识到它决定了后面所有图的裁剪。

**可选方向**（产品判断，未实施）：
1. 发布时提示「第一张决定所有图的显示比例」（成本最低，不改渲染）
2. 后续图改「整图可见 + 留白」（`BoxFit.contain`）——
   代价是最极端那张**六成面积是留白**；留白用纯色显空，用「图本身模糊放大」当底更好看但多一次渲染。
   ⚠️ 顺带会改变**首图**：0.67 现在是裁掉上下 11%，改后变成左右各 11% 白边
3. 框高按**该帖最极端那张**算而非首图（所有图都能整图显示，留白只出现在需要处）——
   代价是一条竖拍帖里混进一张超宽图，整卡会变得很高
4. 允许翻页改高 —— ❌ **不建议**，就是代码注释里说的「把下方卡片整体推动」

### 4.1 已实机试过「方向 2（填充不裁）」—— 结论是**不建议全局换**

2026-08-24 当场把 `BoxFit.cover` 临时改成 `BoxFit.contain` 重新打包实测
（**已还原，未提交**）。实测数字：

| 情况 | 裁剪（现状） | 填充（试验） |
|---|---|---|
| 超宽 2.00 在 1.34 框 | 左右各切 16% | 上下留白 **280 物理px**（观感尚可） |
| **竖 0.67 在 1.34 框** | 上下各切 25% | **左右留白 520 物理px ≈ 卡片宽度的一半是白的** |

**两条实测结论**：

1. 🔴 **比例差得多时填充更糟**：竖图缩成中间一条，像缩略图漂在白底上，不像 Feed 里的照片。
   填充只在比例接近时好看。
2. 🔴 **填充会搞坏轮播圆点**：圆点画在**框底部**，改填充后那里是白底 ——
   **白点白底直接消失**。这是纯白留白的连带损伤，之前没人想到。

**修正后的建议排序**：

| 优先 | 方向 | 理由 |
|---|---|---|
| ⭐ 1 | 发布时提示「第一张决定所有图的显示比例」 | **最便宜、零视觉风险**。用户知道后会把有代表性的那张放前面，问题自然消掉大半 |
| 2 | 填充 + **用图本身模糊放大当底** | 留白处不再是死白，圆点也有得靠（Instagram 做法）。代价：多一次渲染 |
| 3 | 框高按该帖最极端那张算 | 所有图整图可见；代价是混进一张超宽图会让整卡很高 |
| ❌ | 纯白填充（本次试验） | 见上，比例差得多时更糟且搞坏圆点 |
| ❌ | 允许翻页改高 | 代码注释已说明：会把下方卡片整体推动 |

## 五、⚠️ 待决项三：「可横滑」的提示几乎看不见

**现象**：我自己第一次看那条多图卡时**没看见圆点**，据此判断「组件收到的是单图」，
还去查了 JSON 解析 —— 查完才发现圆点一直在。

**原因**：两个提示都太弱 —— 圆点直径 5 逻辑像素、距底 9；右缘暗渐变透明度仅 **6%**。
在**内容密集的图**上基本不可见；换到深底图圆点立刻清楚。

**为什么要紧**：**功能没问题，是没人知道它能滑**。
⚠️ 顺带一条：在模拟器上用**鼠标拖**很容易拖不够距离（轮播翻页门槛是「过半屏宽」或「甩得够快」），
拖不够会**回弹**，看着就是"滑不动" —— 这是本次用户报「滑不动」的最可能原因之一，**不是缺陷**。

**可选方向**（视觉决策，未实施）：给圆点加半透明底衬 / 加深右缘暗示 / 首次出现时做一次轻微提示动效。

## 六、本次未能覆盖的

- **性能**：本地绕过了 OSS 缩略图管线，加载耗时不代表线上（见 §一）
- **小屏**：只在 1080×2400 上量过；待决项一必须在 360×640 复核
- **真实照片**：用的是插画类参考图（内容密集、无明显主体）。
  真实宠物照有明确主体，「居中裁剪」切掉主体的观感可能比插画更糟 —— 待决项二应拿真实照片再看一次
