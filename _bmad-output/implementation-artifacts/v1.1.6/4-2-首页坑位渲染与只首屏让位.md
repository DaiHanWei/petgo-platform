# Story 4.2: 首页坑位渲染 + 只首屏让位

Status: review

## Story

As a 用户，
I want 首页顶部那条运营内容看起来跟普通内容一样自然，
so that 我不觉得被硬塞了广告。

## Acceptance Criteria

**AC1 · 与普通条目完全同构**
**Then** 除了多一个顶置角标，其余部分（作者行 / 图片 / 操作行 / 正文 / 时间）与普通条目完全一致 `[L2]`
**And** 顶置角标固定在**图片区内右上角**，挂在 Story 3.4 交付的叠加层上 `[L2]`
**And** 多图的顶置帖**同样适用轮播规则**（可左右滑、有圆点、高度按首图锁定）`[L2]`

**AC2 · 只首屏让位**
**Then** 🛡 被顶置的内容**仅从第一页排除**，后续页仍可正常出现 `[L1]`
**And** 🛡 **排除后须补足页大小**（继续向后取一条），不得让第一页少一条 —— 页大小抖动会影响"还有更多"的判断 `[L1]`
**And** 推广卡片无内容编号，不涉及排除 `[L1]`

**AC3 · 坑位不该拖累首页**
**Then** 🛡 顶置取数失败**不得连带整个首页失败**，降级为坑位不展示 `[L1]`
**And** 坑位走**独立取数**，首页的游标分页逻辑不因顶置改变形态 `[L0]`

**AC4 · 坑位为空**
**Then** 坑位不展示、该位置由普通内容按正常排序填充，不留空白占位 `[L2]`

**AC5 · 埋点**
**Then** 上报**曝光**（坑位配置标识 / 顶置类型 / 内容编号）与**点击**（跳转目标类型）`[L1]`
**And** 🛡 **重复曝光事件必须如期交付** —— 它是**下游版本判断"要不要为顶置做去重"的唯一数据来源**，
须带该内容在算法序列里的位次 `[L1]`

## Dev Notes

### 🔴 「只首屏让位」的排除必须写在查询条件里

排除后要补足页大小。若做成"照常取一页、再在内存里把顶置那条剔掉"，会同时坏两件事：
第一页少一条、以及"还有更多"的判断依据（多取一条判 hasMore）跟着失真。
放进查询条件里则天然补足 —— 数据库会自己往后多给一条。

### 🔴 取数失败降级的确切含义

「顶置取数失败不得连带整个首页失败」在**两处**都要落实：
1. **坑位端点**失败 → 客户端当作没有顶置，首页照常显示（客户端侧）
2. **首页取数内部**查顶置（为了排除）出错 → **当作没有顶置继续走**（服务端侧）

第二处容易漏。它的代价是那一次可能出现重复展示 —— 明确接受，比整个首页 500 好得多。

### ⚠️ 重复曝光事件的语义已经变过一次

原本的意思是"观测同一屏是否重复"，但 AD-8 定了「只首屏让位、后续页仍可出现」之后，
首屏不可能重复了。该事件的语义**随之改写为"观测后续页的重复曝光频率与位次"**，仍有效、不作废。

🛡 它是**下游版本 V1.1.8 判断"要不要为顶置做去重"的唯一数据来源**，
所以必须随本功能一并上线，不能推到埋点收尾。

### 角标挂在 3.4 交付的角位上，不要碰图片区

Story 3.4 已经把图片区做成了带三个具名角位的叠加层，右上角位就是留给顶置角标的。
本 story **只往那个入参里传内容**，一行图片区结构都不该改 —— 那正是 3.4 那条契约测试防的事。

#### 1. 🔴 只首屏让位：排除写在查询条件里
排除条件放进 SQL 的 WHERE，数据库会自己往后多给一条 —— 第一页天然还是满页。
若做成"照常取一页、再内存里剔掉顶置那条"，会同时坏两件事：第一页少一条、
以及"还有更多"的判断（它依赖多取一条）跟着失真。

反向验证：把"只首屏"去掉、改成每页都让位 → **前端那条与后端那条同时红**
（后端那条的报错直接写着"被顶置的内容只从第一页排除，后续页仍应正常出现"）。

#### 2. 🔴 降级要在两处落实，第二处最容易漏
大家通常只想到"坑位端点挂了、客户端不显示"。但**首页取数内部也查了一次顶置**（为了让位），
那一次若不接住异常，整个首页会 500 —— 一个运营位把主功能带崩。

写了一条单测：让顶置查询抛异常，断言首页照常返回**且不排除任何内容**。
反向验证：把降级去掉 → 那条立刻炸在异常上。

降级的代价是那一次可能出现重复展示，明确接受。

#### 3. ⚠️ 三个埋点全部改了名（已回写 PRD）
PRD 原名是 `feed_pinned_slot_viewed` / `feed_pinned_slot_tapped` / `feed_pinned_duplicate_exposed`，
三条都过不了本项目的埋点命名规范：
- **模块前缀须取自既有词表**，首页 Feed 属 **Social（Jelajah）** 页 → 前缀 `social_` 而非 `feed_`
- **动作须落在词尾**，`_exposed` 不在允许的动作词尾里，曝光统一用 `_viewed`

改为 `social_pinned_slot_viewed` / `social_pinned_slot_tapped` / `social_pinned_duplicate_viewed`，
**属性一个没动**。PRD §3.2 已同步订正并注明理由。

另有一处**刻意的双词表**：接口下发的类型是 `CONTENT`/`PROMO`（线格式惯例），
而埋点取值按 PRD 定死为 `post`/`promo_card`。客户端做一次显式映射 ——
直接把线格式发上去会切断已有的埋点序列。

#### 4. 重复曝光那条的语义已经变过一次
原意是"观测同一屏是否重复"，但 AD-8 定了「只首屏让位、后续页仍可出现」之后，
首屏不可能重复了。语义随之改写为"观测**后续页**的重复曝光频率与位次"。

🛡 它是**下游版本判断"要不要为顶置做去重"的唯一数据来源**，所以随本功能一并上线，没有推到埋点收尾。

⚠️ 一处如实标注的口径：本项目**没有"进入视口才算曝光"的基建**，两个曝光事件按**渲染即曝光**上报。
顶置位是首屏第一条，渲染与看到之间的差距可忽略；重复曝光本就是统计频率与位次，
精确到视口对判读没有实际影响。这条写在代码注释里，免得日后有人以为漏做了。

渲染出来一看：顶置卡的作者行**没有「···」**。AC 要求"其余部分与普通条目完全一致、
常规互动入口位置不变" —— 少了它，用户对顶置内容反而没法举报。

原因是我只接了点击与评论两个回调，漏了举报（长按 + 「···」）。已补上并加了一条测试钉住。
**这是纯靠实机看出来的**，L0 全绿时它一样是绿的。
