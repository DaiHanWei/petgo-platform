# Story 3.5: 发布页图片上传裁剪

Status: review

## Story

As a 用户，
I want 只有真正的长图才让我裁，
so that 我随手拍的照片能一路发出去、不被反复打断。

## Acceptance Criteria

**AC1 · 实现选择**
**Given** 项目现在只有选图能力、**没有任何裁剪库**
**Then** 引入第三方裁剪库或自研选区交互（**属实现选择**）—— 这是本版本 App 端唯一可新增的依赖 `[L0]`

**AC2 · 容差区间内免裁剪**
**Then** 比例落在 `0.75~1.34` **闭区间**内的**直接使用、不弹裁剪框、不做任何裁切** `[L2]`
**And** 超出区间的弹出裁剪框，提供 **1:1 / 4:5 两档预设** `[L2]`
**And** 🛡 **不提供横图预设** —— 超宽图（16:9、全景）只能裁成这两档，属**已知且接受**的结果，不是缺陷 `[L0]`

**AC3 · 批次锁定**
**Then** 第一张触发裁剪的图选定的目标比例，锁定为本批次**其余同样需要裁剪的图**的目标比例 `[L2]`
**And** 🛡 **批次内落在容差区间内的图不受锁定影响**，始终保持原比例 `[L2]`
**And** 若批次内全部落在区间内，**全程不出现裁剪框**，也不涉及比例锁定 `[L2]`

**AC4 · 裁剪页的按钮位置**
**Then** 退出按钮为**左上角 ✕**，前进动作（应用裁剪 / 继续）由**底部主按钮**承担 `[L2]`

**AC5 · 埋点 E-8**
**Then** 弹出裁剪框时上报 `publish_image_crop_required`，带 `original_ratio`（原始宽:高比例数值）与 `batch_size` `[L1]`
**And** 该分布是**判断 0.75~1.34 取值是否合适的唯一依据** —— 理想结果是这个事件本身**量很小** `[L1]`

## Dev Notes

### T0 拍板：自研，不引第三方裁剪库

AC 明说「第三方库或自研」属实现选择。选**自研**，三条理由：

1. **AC4 规定了裁剪页的按钮位置**（左上 ✕ / 底部主按钮）。第三方裁剪库基本都自带一整套
   不可重塑的界面，改不成这个规格 —— 这条 AC 本身就在排除"整页交给库"。
2. **只有两档固定预设、无旋转、无自由选区**，交互面极小。
3. **像素级裁剪能力仓库里已经有了**：发布路径为了剥 EXIF 本来就在纯 Dart 解码/重编码，
   裁剪只是多一步。

结论：**本版本 App 端不新增任何依赖**。

### 🔴 容差区间只能有一份

`0.75~1.34` 在 Story 3.3 已经是常量了。上传端**必须复用同一份**。

两份常量一旦漂移，用户会遇到最费解的一类行为：**上传时被判定"不用裁"，展示时却被裁了**
（或反过来，白白裁了一次）。这类不一致没有任何错误信息，只会被当成玄学。

### 🔴 裁剪页之外还有一笔账：客户端从来没上报过尺寸

后端 Story 3.1 建好了接收 `imageSizes` 的接口，也写明「App 发布由客户端上报，
缺失或明显不合理时服务端兜底测量」。**但客户端这一半从来没接** ——
现在每条新帖都是发完之后由服务端异步下载图片再测一遍。

后果：Story 3.3 说的「新内容零跳动」**要等那个异步任务跑完才成立**，
刚发完就刷首页的人看到的仍是占位比例。

发布路径本来就要解码图片，宽高顺手就有。**本 story 顺带收口**。

⚠️ 上报数组必须**与图片同序等长**，后端对长度不符的处理是**整组作废**（不做部分采信）。

### 🛡 批次锁定容易做反的两处

1. **区间内的图不参与锁定**。规则原文强调过两遍：锁定范围**仅限于"同一批次里需要裁剪的图之间"**。
   同一帖里图 1 保持 0.8、图 2 被裁成 1:1 —— 这是**符合规则的正确结果，不是 bug**。
2. **全在区间内时连"选比例"这一步都不该出现**。比例锁定只在真正需要裁剪时才发生，
   不是每次上传都强制走一遍。

### ⚠️ UI 稿有一处未同步订正

屏 08 的图注仍写「**右上角**返回按钮」，而 PRD 已于 2026-08-07 订正为「**左上角 ✕**」——
右上角按 iOS/Material 惯例是前进/确认位，退出放那里会画出"左箭头放在右上角"这种
方向与位置互相矛盾的控件（设计稿一度确实这么画了）。**以 PRD 为准**，并把 UI 稿图注一并订正。

### 现状实读（2026-08-18）

| 位置 | 现状 |
|---|---|
| 选图 | 单张与多张两条路径，都是"选完 → 剥 EXIF 压缩 → 直接入列上传"，**中间没有任何判定** |
| 图片处理 | 纯 Dart 解码 → 清空 EXIF → 按需降质降分辨率重编码。**解码后宽高唾手可得**，但目前没人用 |
| 选图上限 | 每帖 9 张；选图时原生层已降采样到 ≤2048（等比，不影响比例判定） |
| 发布请求 | 只传图片地址，**不传尺寸** |
| 裁剪 | **完全没有**，也没有任何裁剪库 |

### 不在本 story 范围

- 首页/详情页的渲染口径（Story 3.3 / 3.4 已完成）
- 存量内容回填（零回填是硬要求）
- 旋转、自由选区、横图预设档

#### 1. 拍板自研，本版本 App 端**没有新增任何依赖**

#### 2. 🔴 容差区间锁在了展示端那对常量上
判"要不要裁"直接用 Story 3.3 的 `kFeedRatioMin/Max`，**没有另立一份**。
写了一条专门的耦合测试：反向验证时把展示端的下界从 0.75 改成 0.80、
同时让上传端自立一份 0.75 —— **那条耦合测试立刻红**。
这正是它要防的事：两份常量漂移会让用户遇到"上传时说不用裁、展示时却裁了"这种
没有任何错误信息的行为。

#### 3. 批次编排与界面拆开，两条最容易做反的规则都用 L0 钉住
- **区间内的图完全不参与**：混合批次测试断言免裁那张的字节**与输入是同一个对象**（一个字节都没动）
- **第二张不能换档**：测试里让"问用户"在第二次故意返回 4:5，编排层必须不听它的

反向验证两次：让第二张听自己的档位 → 只红"沿用第一张档位"；让区间内的图也去裁 → 红 5 条，全部集中在批次规则。

#### 4. ⚠️ 埋点名与 PRD 原文不同（已回写 PRD）
PRD 写的是 `publish_image_crop_required`，但本项目的埋点命名规范要求**动作落在词尾**
（`_shown`/`_tapped` 之类，好让产品一眼分得清曝光与点击），`_required` 是状态不是动作，
被命名规范测试当场拦下。

改为 **`publish_image_crop_shown`** —— 语义也更准，事件确实是在裁剪页出现的那一刻上报。
PRD §3.2 已同步订正并注明理由。

#### 5. 🔴 顺带收口了一笔旧账：客户端从来没上报过图片尺寸
后端 Story 3.1 的接口早就收 `imageSizes`，也写明"App 发布由客户端上报"，
但**客户端这一半从来没接** —— 每条新帖都是发完之后由服务端异步下载图片再测一遍。

后果是 Story 3.3 说的「新内容零跳动」**要等那个异步任务跑完才成立**，
刚发完就刷首页的人看到的仍是占位比例。

发布路径本来就在解码图片，宽高顺手就有。已补上，并守住后端那条硬要求：
**与图片同序等长**，量不出来的位置留 null（后端对长度不符的处理是**整组作废**，
所以绝不能"跳过不放"）。

#### 6. 两个实现上的小坑
- **只读文件头拿宽高**：判定要对每张选中的图各做一次，整张解码 9 遍会让"选完图"之后卡住好几秒。
  改用解码器的头部解析，代价可忽略；真正的整张解码只发生在**确实要裁**的那几张上。
- **解码器对坏字节是抛异常、不是返回 null**：实测某些格式的探测器会直接下标越界。
  发布流程不能因为一张坏图整个崩掉，所以裁剪入口必须 try/catch。这是写测试时撞出来的。

#### 7. UI 稿订正了一处
屏 08 图注仍写「右上角返回按钮」，与 PRD 2026-08-07 的订正冲突（右上角按平台惯例是前进位，
退出放那里会画出"左箭头放在右上角"这种方向与位置互相矛盾的控件）。已随本 story 一并改掉。

#### L2 实机验收记录（2026-08-18，模拟器 411×914）
往模拟器相册塞了两张已知比例的图（3:4 = 0.75 免裁；16:9 需裁），一次选中两张：

| 免裁主路径 | **3:4 那张全程没出现裁剪框**，直接进了图片行 —— 用户完全感知不到"裁剪"这一步存在 |
| 触发裁剪 | 只有 16:9 那张弹出裁剪页 |

| 混合结果 | 应用后图片行里两张并存：第一张仍是原始 3:4、第二张是裁过的 —— 同一帖里比例不同，**这是符合规则的正确结果** |
