# Story 8.1: 系统通知权限状态快照

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 产品与运营，
I want 每次冷启动上报一次「这台设备的系统通知开关是开还是关」，
so that FR-85 改版一个周期后，我能回答「授权率到底涨没涨」这个唯一真正重要的问题。

---

> **本 story 是 Epic 8 的 P0 前置，且必须先于 8-2 / 8-3 落地。**
>
> FR-85 做了四个触发点去引导用户开通知，但**其余埋点都只能解释过程、不能证明结果**：
> 提示弹了多少次（E-19）、各触发点的响应分布（E-20），都回答不了「净授权率涨没涨」。
> 只有这个快照的**趋势**能回答，它是 FR-85 唯一的裁决指标（AD-16 Rule 6、埋点清单 §0.3）。
>
> 🔴 **它必须比四个触发点先上线，否则永远拿不到「改版前基线」。**
> 埋点清单 §0.3 记着上一次的教训：Tab 改版因为缺基线，五项核心指标里三项直接作废。
> 晚一个版本 ≠ 晚一点拿到数据，而是**那段基线永久不存在**。
>
> **交付**：一个事件、一个属性、一处调用点。**不含任何引导界面**（那是 8-2 / 8-3）。

## Acceptance Criteria

### AC1 — 每次冷启动上报一次（L1）

**Given** App 冷启动
**When** 本次启动的通知权限流程已落定
**Then** 上报一次 `push_permission_state_reported`，带属性 `granted`（bool = 当前系统通知开关状态）`[L1]`
**And** 🛡 **一次冷启动只报一次** —— 回前台（resume）、切 Tab、重进页面**一律不再报** `[L1]`

> 为什么强调"只报一次"：这个指标是**按启动数算授权率**的分母基础。若 resume 也报，
> 重度用户会被反复计入、把授权率拉向他们的个人状态，趋势就失真了。

### AC2 — 事件名与属性按定稿（L0）

**Given** 事件名与属性是判读的必要条件
**When** 实现埋点
**Then** 事件名必须是 **`push_permission_state_reported`** `[L0]`
**And** 🔴 **不得使用旧名 `push_permission_state_snapshot`** —— 2026-08-18 按命名规范
（`模块_对象_动作`，动作在词尾且须是动词）改名，OA-7 已闭合，PRD 与埋点清单均已是新名 `[L0]`
**And** 属性 `granted` 必须存在且为布尔 `[L1]`

> ⚠️ **这四个事件一旦发版就锁死**：改名会切断历史序列。V1.1.2 有 9 个旧事件正是因为已发版才故意不改。
> 本 story 是这个名字的**首次落地**，写错就等于把锁死在错的名字上。

### AC3 — 报的是「落定后」的状态（L1）

**Given** 首次启动会在冷启动流程里申请通知权限（第二代「首启即申请」，2026-08-07 上线）
**When** 上报快照
**Then** 上报点必须在**本次启动的通知权限流程落定之后** `[L1]`
**And** 🛡 若本次启动因 ATT 未落定而**推迟**了通知权限申请（既有链路，见 Dev Notes），
仍照实上报**当前**状态、不跳过、不补报 `[L1]`

> 报「申请之前」的状态会让首启永远是 `false`，授权率被系统性低估。
> 而推迟的那种启动如实报当前状态即可 —— 它确实是一次真实观测；不要为了"好看"而跳过，
> 跳过会让分母缺失、且缺失是**非随机**的（只缺 ATT 未落定的那部分设备）。

### AC4 — 不得动既有启动时序（L0）

**Given** `main.dart` 里 AppsFlyer init / ATT / 通知权限 / AppsFlyer start 四者的先后**有硬性理由**
（注释明写「不可随手改」：ATT 与通知权限同帧会互相遮挡 → 2026-08-06 与 2026-08-09 两次审核拒信的修复点）
**When** 插入本 story 的上报点
**Then** 🛡 **四者相对顺序一字不动**，只在末尾追加上报 `[L0]`
**And** 🛡 上报**不得阻塞**启动关键路径：失败只吞掉并记日志，绝不向上抛 `[L1]`

### AC5 — 不扩散到本 story 范围外（L0）

**Given** 加了这个事件之后，"顺手"就能把四个触发点的埋点一起做了
**When** 实现本 story
**Then** 🛡 以下**明确不做** `[L0]`：
- **E-19 / E-20**（触发点曝光与响应）与四个触发点的**任何引导界面** —— 归 8-2（用户侧三点）/ 8-3（兽医端）
- **AD-14 的四个标记键**（触发点各一次的 prefs 键）—— 归 8-2 / 8-3；本 story 一个键都不加
- **既有 `pushPermissionAsked` 标记** —— 只读不写、不迁移、不删（AD-14 Rule 3）
- 设置页开关、通知中心引导条 —— 归 8-2

## Dev Notes

### 🔴 上报点为什么必须在权限流程之后 —— 时序是硬约束

`main.dart` 的 `addPostFrameCallback` 里有一段注释明写「四者的先后不可随手改」，理由是两次真实的审核拒信：

| 约束 | 理由 |
|---|---|
| AppsFlyer `init` 与 ATT **并发**发起 | 串行会让 ATT 弹窗被 initSdk 拖后最多 3s；「等 resumed 再弹 ATT」正是 2026-08-06 Guideline 2.1 拒信的修复点 |
| **通知权限必须排在 ATT 之后** | 两个系统弹窗同帧抛出会互相遮挡、两者授权率一起掉（2026-08-07） |
| `start()` 晚于 ATT 结果与 init | 未 init 时 `start()` 是 no-op |

本 story **只在末尾追加**一次上报，不参与上面任何一条的排序。

### ⚠️ ATT 未落定的那条分支容易漏

既有代码是这个形状（简化）：

```
final attSettled = await AttGate.requestIfNeeded();
if (attSettled) {
  await askNotificationOnce();     // ← 走到这里才申请通知权限
} else {
  debugPrint('deferred to settle/next launch');   // ← 这条路径不申请
}
```

⚠️ **两条分支都要上报。** 只在 `if` 里加，就会漏掉所有"ATT 尚未落定"的启动 ——
那不是随机缺失，而是**只缺 iPad 兼容模式 / 系统吞掉请求**这类特定设备，趋势会被带偏。

另有一条 `AttGate.installForegroundRetry(onSettled: askNotificationOnce)` 的前台补弹链路：
它是**同一会话内**的补弹，不是新的冷启动，**不要在它的回调里再报一次**（会违反 AC1）。

### 🔴 一次性闸不要落盘

"本次启动是否已报过"用**进程内布尔**。冷启动会天然重置它，正是我们要的语义。
若落 prefs，语义会变成"这台设备永远只报一次"，那么第二次启动之后授权率就再也没有数据 ——
**这个指标要的恰恰是趋势**，一次快照没有任何用。

### 权限状态怎么读（与既有实现同口径）

`PushPermissionBootstrap` 内部用的是 `Permission.notification.status).isGranted`（`permission_handler`，已在依赖里）。
本 story 用**同一口径**，但读取函数要可注入，否则单测跑不动（插件在测试环境没有平台实现）。

⚠️ **判读注记（给看数的人，不是给实现的）**：Android 13 以下没有通知权限这个概念，
`isGranted` 反映的是"用户有没有在系统设置里关掉通知"。所以 `granted=true` 在低版本 Android 上
偏多是正常的，**不要把跨平台的绝对值直接比**；FR-85 要看的是**同一群体的趋势**。

### 事件名：这是首次落地，写错就锁死

`push_permission_state_reported` 是 2026-08-18 改名后的新名（旧名 `push_permission_state_snapshot`，
`snapshot` 是名词、不符合"动作在词尾且须是动词"）。埋点清单里有新旧对照表，供看旧文档的人对号。
🔴 一旦发版，名字就锁死（改名会切断历史序列），而**本 story 就是那次发版**。

### 埋点封装现状（实读 2026-08-20）

- `Analytics.capture(event, [properties])` —— 内部先 `scrub` 剥敏感键，再 `Posthog().capture`，
  **已 try/catch 吞异常**（失败只 `debugPrint`），符合 AC4「不得阻塞启动」
- `Analytics.debugCaptureSink` —— Story 6.1 建立的测试观察点，挂在**净化之后**，
  生产路径恒为 null。埋点断言一律用它，看到的就是端上真正发出的形态
- 通知模块此前只有 Story 6.1 加的那一个点击事件；权限相关**零埋点**，本 story 是从零加

### Completion Notes List

#### 1. 抽成独立类，而不是把逻辑写进 `main.dart`

两个硬理由，不是洁癖：`main.dart` 那段 `addPostFrameCallback` 没有任何测试入口；
而 `permission_handler` 在测试环境没有平台实现，读取函数**必须可注入**才测得动。
故新建 `PushPermissionStateReporter`，与 `PushPermissionBootstrap` 同层同口径。

#### 2. 🔴 上报点放在 `if/else` **之外** —— 这是本 story 最容易做错的一处

既有代码只在 `if (attSettled)` 里申请通知权限，`else` 分支只打日志。
若把上报写进 `if` 里，会漏掉**全部「ATT 未落定」的启动**；而那不是随机缺失 ——
只缺 iPad 兼容模式、请求被系统吞掉这类设备，趋势会被系统性带偏。
`main.dart` 里为此写了注释，防止后人"顺手"挪进 `if`。

同时确认：`AttGate.installForegroundRetry` 的补弹回调里**没有**加上报 ——
那是同一会话内的补弹、不是新的冷启动，报了会违反 AC1。类内的进程内闸也兜住了误调。

#### 3. 一次性闸是进程内布尔，且**异常不消耗它**

落 prefs 会把语义从「每次冷启动一次」变成「这台设备永远只报一次」——
而这个指标要的恰恰是趋势，单点毫无用处。
异常路径刻意不置位：一次偶发失败不该让本次启动彻底没数据。两条都有测试钉住。

#### 4. 🔴 与既有命名契约撞了一次 —— 扩白名单，不改名字

`test/analytics/v112_events_test.dart` 有一条契约测试守埋点命名，两张白名单
（允许的模块前缀 / 允许的词尾动作）。产品定的 `push_permission_state_reported`
**两条都踩**：`push_` 不在前缀表、`_reported` 不在后缀表。

处理：**扩白名单**。改名等于推翻已闭合的 OA-7，而规范的**用意**这个名字是满足的
（`push_permission` 就是模块、`reported` 是词尾动词）。两处都写了理由：
- `push_`：该模块跨冷启动与四个触发点，本就不属于任何单页，其"模块"是功能而非页面；
  并注明这是**新模块入表**，不是给遗留事件放宽规则（那条路是 `legacyEvents`）
- `_reported`：这类事件**没有用户动作**，分母是启动数而非曝光数，与 `_tapped`/`_selected`
  混在一起会让判读口径错位

⚠️ Story 8-2 将来会需要再加 `_responded`，**本次刻意没提前加** ——
白名单里放尚未用到的条目，就失去了"改动时被迫想一次"的作用。

#### 5. 顺带修掉一处与本 story 无关的环境问题（如实记录）

并导致 104 个测试文件加载失败。跑 `flutter gen-l10n` 即恢复（`petgo_app/CLAUDE.md`
写明改 ARB 后必须重跑）。**与本 story 的改动无关**，只是同一次跑测试时暴露出来。

那属上线后看板核对，不是模拟器视觉验收。
