# Story 2.2: 日历视图与某天详情的访客版

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 收到分享链接的人，
I want 也能按日历翻看这只宠物的记录，
so that 我不会因为只有时间线一种视图而觉得残缺。

## Acceptance Criteria

**AC1 · 两个视图都能返回**
**Given** 日历视图对访客可见（PRD §2.9 可见范围表：日历 = ✅，理由「它是 Diary 的另一种视图，不给会造成割裂」）
**When** 访客切到日历
**Then** 日历格子与某天详情都能正常返回 `[L1]`
**And** 两者都经 `VisitorProjectionService` 这一个出口，**不得**给作者态的 `TimelineService.getCalendarMonth` / `getDayDetail` 加访问者参数（AD-1 Rule 3）`[L0]`

**AC2 · 🛡 后端剔除，不是前端不画**
**Given** 健康记录与问诊存档绝对不能给访客看
**When** 实现访客版日历与某天详情
**Then** 🛡 两者同样**在后端剔除**这两个数据源，**不得只在前端不画** `[L1]`
**And** 🛡 访客的日历格子 DTO **在结构上没有**健康相关字段（作者态 `DayCell` 有 `hasHealthEvent` / `healthRecordType` / `healthRecordCount` 三个）`[L0]`
**And** 🛡 访客的某天详情**复用 `VisitorTimelineItem`**，不得改用作者态那个带 `symptomSummary` / `aiLevel` / `healthRecordId` 的 `TimelineItemResponse` `[L0]`

**AC3 · 同一天两类记录的分叉**
**Given** 访客态与作者态的日历取数是两条路径
**When** 同一天既有 Diary 又有健康记录
**Then** 作者看到两类标记、访客只看到 Diary 标记 `[L1]`
**And** ⚠️ **只有健康记录、没有 Diary 的那一天，在访客侧是「无记录日」** —— 该天**整格不下发**（接口只返回有记录日），而不是「下发一个没有标记的格子」。后者会让访客数出「这天有事发生但不给我看」`[L1]`

**AC4 · 🛡 只含已发布且未删除**
**Given** 作者自己能看到被下架 / 审核中的内容（AD-1 Rule 7）
**When** 访客请求日历或某天详情
**Then** 🛡 **只返回已发布且未删除**的内容 `[L1]`
**And** 🔴 作者态现有的两个查询**只过滤了删除、没过滤审核状态**，**照搬即泄露** —— 见 Dev Notes「最大的坑」`[L1]`

**AC5 · 私密条目照常可见**
**Given** 分享宠物主页 = 授权访客查看该宠物完整 Diary（PRD §2.9 §② 定稿）
**When** 某天有作者关闭同步的私密 Diary
**Then** 该条目**出现**在访客的日历标记与某天详情里（与 Story 2.1 时间线同口径）`[L1]`
**And** ⚠️ 这条容易搞反，**别顺手加 visibility 过滤**

**AC6 · 失效口径防枚举**
**Given** 访客接口以 `cardToken` 为入口
**When** token 不存在 / 档案已删 / 账号注销 / 账号封号
**Then** 🛡 返回**同一失效响应**，不区分状态码与错误文案（沿用 Story 2.1 的 `findVisibleProfile`，**不另写一套判定**）`[L1]`

**AC7 · 对外图去 EXIF**
**Given** 日历格子会下发当天首图
**When** 组装访客日历
**Then** 该图 URL 必须经服务端去 EXIF 分发（拍摄地点等元数据不得随图外泄）`[L1]`
**And** ⚠️ 作者态的 `firstImageUrl` **是原样下发的**（自己看自己的图，无需脱敏），照抄即漏

**AC8 · 视图切换控件文案**
**Given** 视图切换是两个等宽按钮
**When** 渲染切换控件
**Then** 文案为 `⏱ Linimasa` / `📅 Kalender`（**印尼语是 Linimasa，不是 Timeline**），选中态品牌紫底、未选中白底描边 `[L2]`
**And** ✅ **作者态已满足此条**（`growthArchiveViewTimeline` = `Linimasa`、`growthArchiveViewCalendar` = `Kalender`，样式见 Dev Notes）。访客态按 AD-4「复用作者态结构做减法」自然继承 —— **本 story 不改这里**，实际渲染在 Story 2.3 `[L2]`

## Dev Notes

### 🔴 最大的坑：作者态这两条链路**没有过滤审核状态**

代码实读（2026-08-18，已逐条核对方法名）：

| 链路 | 底层查询 | 过滤了什么 |
|---|---|---|
| 作者日历 | `ContentPostRepository.findByAuthorIdAndPetIdAndTypeAndDeletedAtIsNullAndEventDateBetween...` | 仅**删除** |
| 作者某天详情 | `...AndDeletedAtIsNullAndEventDateOrderByCreatedAtAsc` | 仅**删除** |
| 访客时间线（2.1 已用） | `...AndDeletedAtIsNullAndStatusOrderByEventDateDescCreatedAtDesc(..., PUBLISHED, ...)` | 删除 + **PUBLISHED** ✅ |

`ContentService` 的 Javadoc 自己写着「作者本人自看时间线**含挂起帖**，口径不同」—— 那是作者态的**刻意**设计（得让作者知道自己的帖出了什么事）。
**访客态照搬 = 违规内容被下架后仍能通过分享链接对全网可见。**

> 🔴 现有三个 `findGrowthMoments*` **没有一个能直接用**：前两个漏 status，第三个（访客时间线在用的）不按月/日切。**必须新增。**

### 架构约束（architecture-v1.1.6-delta.md）

- **AD-1 Rule 4**：白名单**明确列入**「日历视图与某天详情」→ 本 story 是被授权的可见范围，不是灰区
- **AD-1 Rule 3**：🛡 **禁止**给 `/me` 作用域查询加访问者参数来复用 —— 访客与作者是两条**物理独立**的取数路径
- **AD-1 Rule 6**：类④（健康记录 / 问诊存档）**整类剔除**
- **AD-1 Rule 7**：只含已发布且未删除
- **AD-1 Rule 9**：**不套拉黑过滤**，响应体不得下发任何拉黑信号（与 V1.1.4「拉黑后进不去对方主页」方向相反，**刻意的**，别顺手对齐）
- **AD-2 Rule 6**：访客必须是**带 token 的独立路由**，不得复用作者态档案路由
- **AD-4**：视图切换文案用 `Linimasa` / `Kalender`

> ⚠️ 架构 delta 里**没有**专门讨论「访客日历如何取数」的条目 —— AD-1 Rule 4 只把它列入白名单。
> 实现口径由本 story 自定，但 Rule 7 的 PUBLISHED 过滤对它**同样成立**。

**2. 首图聚合规则改为与作者态<b>完全一致</b>（实现中途的一次自我修正）**

初版给访客写了个「当天最早那条若无配图，就让位给下一条有图的」回退逻辑，
理由是「否则当天第一条是纯文字日记时格子就永远没缩略图」。
但作者态的规则是**严格的「第一条胜出，即便它没图」**——两边算法不一致会让同一只宠物
在作者页和访客页看到不同的缩略图。已改回与作者态同规则、同容器（TreeMap），
两个日历现在**只差「健康那两源」，不差算法**。

**3. ⚠️ 发现一处作者态既有的口径不一致（非本 story 引入，未改）**

作者态日历/某天详情里，**问诊存档是按 `created_at` 落格的**（`healthEventsInRange` 查的是
created_at 区间），而**结构化健康记录是按 `event_date` 落格**。
也就是说：一次 3 个月前的问诊，如果是今天才归档的，会显示在**今天**那一格。
本 story 不碰这条链路（访客侧两源整个剔除），故**未改动**，仅在测试夹具里注明。
> 供产品判断：若认为这会让作者的日历「记错日子」，需单独开条目修。

**4. 失效响应的比较方式（测试写法上的一次订正）**

初版断言四种失效的响应体**一字不差**——但 API 的 ProblemDetail 必然含
`instance`（回显你自己请求的路径）与 `traceId`（随机排查号），永远不可能逐字节相同。
已改为剔除这两项后再比：真正会泄漏的是 **status / title / type / detail**，
这四项一致就足以让扫描者无法区分「token 不存在」与「这个人被封了」。
（Story 2.1 的 H5 页面能逐字节比，是因为那是 HTML 页、不带 traceId。）

**5. 接口挂 `/api/v1/public/**`，未改安全配置**

那条规则已是 `GET → permitAll`，正好满足「未登录也能看」（否则会把用户推回浏览器）。
**副作用是刻意的**：规则只放行 GET，所以在这个控制器里加任何写方法都会立刻 401 ——
等于给「访客只读」这条约束上了一道机械保险。

**6. AC8 无需改动**：作者态的视图切换文案已是 `⏱ Linimasa` / `📅 Kalender`
（ARB key `growthArchiveViewTimeline` / `growthArchiveViewCalendar`），样式也已是
选中品牌紫底、未选中白底 1.5px 描边。访客态按 AD-4 复用作者态结构，自然继承，实际渲染在 Story 2.3。

**7. 🐞 全量回归时撞见一个<b>与本 story 无关的既有缺陷</b>（未修，供决策）**

`NotificationControllerEndpointTest.list_paginatesWithCursor` 在一次全量跑中变红、单独跑与复跑全量都通过。
查了根因，<b>不是测试脆，是通知分页的游标实现有真实缺陷</b>：
游标只存「上一页末条的毫秒时间戳」，翻下一页查的是 `created_at` <b>严格小于</b>该值。
于是<b>同一毫秒内产生的多条通知，翻页时会被整段跳过</b>——用户直接少收到通知，且无声无息。
（Postgres 的 `created_at` 是微秒精度，截断到毫秒进一步加大了撞车概率。）
批量扇出、或高负载下的通知突发，都会触发。
> 修法是给游标补一个 id 作为并列打破符（`(created_at, id)` 复合游标）。
> <b>属 notify 模块，与 Epic 2 无关，本 story 未改</b>——需要单开一条来修。

**8. 📐 访客日历/某天详情<b>无 UI 稿</b>**（story 已标注）：`ui-v1.1.6.html` 访客泳道只有 P1 一屏且是时间线态。
Story 2.3 渲染时若视觉口径不明，需回头请示产品。
