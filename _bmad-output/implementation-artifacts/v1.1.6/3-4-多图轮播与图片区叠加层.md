# Story 3.4: 多图轮播 + 图片区叠加层

Status: review

## Story

As a 用户，
I want 在首页就能左右滑动看完一个帖子的多张图，
so that 我不必为了看第二张图点进详情页。

## Acceptance Criteria

**AC1 · 轮播与圆点**
**Given** 首页每条内容此前只显示一张图
**Then** 图片区可**左右滑动翻图**，圆点叠在**图片区内底边居中**，圆点数 = 图片数、当前图高亮 `[L2]`
**And** 圆点**同时承担"有几张图"与"当前第几张"两个信息**，不再需要独立的数字角标 `[L2]`
**And** **单图帖不显示圆点、也不响应横向滑动** `[L2]`
**And** 右缘一道极窄暗渐变作为「可横滑」的暗示 `[L2]`

**AC2 · 手势不能互相抢**
**Then** **横向滑动 = 翻图**（不跳转）；**纵向滑动 = 继续滚动列表**（不被轮播吃掉）；**点击 = 进详情页** `[L0]`

**AC3 · 🛡 滑动时高度不变**
**Then** 容器高度按**首图**走完三段口径后锁定，非首图居中裁剪填满，**滑动时高度不变** `[L0]`

**AC4 · 🛡 必须交付叠加层结构**
**Then** 🛡 现状图片区是裸的图区、**无叠加能力**；本 story 必须交付叠加层，**三个角位写死**：
圆点 = 底边居中、顶置角标 = 右上、装饰标签 = 左下 `[L0]`
**And** 🛡 该结构是 **Epic 4 与 Epic 5 的地基**，它们只往里挂自己那个角位、
**不得各自再改图片区结构** `[L0]`

**AC5 · 预加载**
**Then** 只预加载当前图与下一张，其余滑到时再加载 —— 避免首屏请求量随多图帖数量线性膨胀 `[L2]`

### 现状实读（2026-08-18）

| 位置 | 现状 |
|---|---|
| 首页图片区 | 3.3 刚改成按三段口径定高的**单图**；`Stack` 结构**还没有**，叠加层是本 story 的活 |
| 卡片数据 | 只有**首图**一个字段，整组图片客户端还没接（后端已下发） |
| 详情页 | **已有**一套轮播：左右滑 + 右上角 `x/y` 数字角标 + 点击进全屏灯箱，固定 1:1 |
| 尺寸 | 3.3 已接；本 story 只取首图那一项 |

### ⚠️ 详情页那套轮播不要直接搬

两处的指示形态**产品明示不强制统一**（首页圆点 / 详情页数字角标各自成立，架构文档已把这条交给 UX）。
而且详情页是固定 1:1 + 圆角 + 点击进灯箱，首页是三段口径定高 + 通栏出血 + 点击进详情 ——
共用一套只会把两边的差异揉成一堆条件分支。**各写各的，但圆点/角位做成可复用件。**

### 🔴 叠加层不是"顺手加个 Stack"

AD-8 第 6 条把三个角位**写死**了：顶置角标右上、装饰标签左下、轮播圆点底边居中，三者互不重叠。
本 story 的交付物是**结构本身**，Epic 4（顶置）与 Epic 5（装饰标签）只往里挂内容。

若不把角位做成入参，两个 Epic 会各自去改图片区 —— 那正是这条 AC 要防的事。
**建议写一条测试把三个角位钉住**，让后来者改坏了会红。

### 🔴 单图帖是"不接横滑"，不是"滑不动"

单图帖若仍挂着横向手势，用户斜着滑一下就可能被横向手势截胡、列表滚不动。
这类"偶尔滚不动"最难复现也最恼人。单图时应当**完全不接**横向手势。

### 视觉数值（UI 稿 屏 09b）

- 圆点：距底 9，间距 5，直径 5（白色 55% + 淡阴影），当前点 5.5 纯白
- 右缘暗示：宽 9，从透明渐变到黑 6%

### 不在本 story 范围

- 顶置角标的内容与取数（Epic 4）、装饰标签的内容与取数（Epic 5）—— 本 story 只交付**空的角位**
- 详情页轮播形态调整（产品明示不强制统一）
- 发布页裁剪（Story 3.5）

### Completion Notes List

**全绿**：`flutter analyze` 零问题；`flutter test` **829 通过**（本 story 新增 11 条）。

#### 1. 叠加层做成了两个具名入参，不是一个"随便往上叠"的口子
图片区从"一张图"变成"一个层叠结构"，三个角位**写死**：
底边居中（圆点，本组件自己出）、右上（顶置角标）、左下（装饰标签）。
后两个是**入参**，Epic 4 与 Epic 5 只往里传内容。

写了一条测试量三个角位的**实际位置与互不重叠**（不是"有没有渲染"，是"在不在该在的地方"）。
反向验证：把顶置角标从右上挪到左上 → **只有这一条红**。这样 Epic 4/5 若绕开入参去改图片区结构，会立刻被拦下。

#### 2. 单图帖是"压根不接横向手势"，不是"接了但滑不动"
这条区别不是文字游戏。单图帖若仍挂着横向识别器，用户斜着滑一下就可能被横向手势截胡、
列表偶尔滚不动 —— 这类 bug 最难复现也最招人烦。
所以单图直接渲染图片、**根本不构造轮播控件**，测试断言的也是"轮播控件不存在"。
反向验证：改成"单图也走轮播但禁用滑动" → **只有这一条红**。

#### 3. 高度只听首图的
容器比例只由**首图**的尺寸算（走 3.3 的三段口径），非首图一律居中裁剪填满。
Feed 是长列表，滑图时若容器变高，下方所有卡片会被整体推动。
两条测试钉住：翻页后容器比例不变；尺寸数组里第二三张是横图也不影响容器。

#### 4. 预加载只到下一张
翻到第 n 张时才预取第 n+1 张。反面是"整组一次性预载" ——
一屏 5 条多图帖会直接放大成几十个请求，首屏请求量随多图帖数量线性膨胀。

#### 5. ⚠️ 详情页那套轮播没有动
详情页早就有一套（左右滑 + 右上角 `x/y` 数字角标 + 点击进全屏灯箱，固定 1:1）。
**两处形态产品明示不必统一**，且详情页是圆角 + 点击进灯箱、首页是通栏出血 + 点击进详情，
共用一套只会揉出一堆条件分支。各写各的。

#### 6. 一个测量上的坑（记一下，免得下次再踩）
圆点原先用 `margin` 拉间距 —— 而 `margin` 会被算进控件**自身的尺寸**，
于是"圆点多大 / 在哪"根本没法被断言（第二个圆点量出来是 10 而不是 5）。
改成外层 `Padding` 之后才测得准。

#### L2 实机验收记录（2026-08-18，模拟器原生 411×914）
造了一条三图帖（首图 3:4）与一条单图帖，实机确认：

| 验的东西 | 结果 |
|---|---|
| 圆点 | 三图帖底边居中出 3 个点，当前点高亮；单图帖**无圆点** |
| 横滑翻图 | 翻到第二张，圆点跟着走 |
| 🛡 滑动不变高 | 翻页前后图片区**上下边缘像素级一致**，下方点赞行/正文/时间纹丝不动 |
| 非首图填满 | 第二张（0.855）居中裁剪填满首图锁定的框 |
| 纵滑 | 手指落在**图片区上**纵向滑动，列表正常滚动，轮播不抢 |
| 单图不接横滑 | 在单图帖图片区横滑 → 画面**完全没有变化**（没翻页、没跳转、没滚动） |

验收用的两条测试内容**已从本地库删除**。

**未验**：真机；顶置角标 / 装饰标签的实际观感（本 story 只交付空角位，等 Epic 4/5 挂上内容后才有得看）。
