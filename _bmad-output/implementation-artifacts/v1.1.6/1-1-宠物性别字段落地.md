# Story 1.1: 宠物性别字段落地

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 宠物主，
I want 在档案编辑页选的性别能真正保存下来，
so that 我分享出去的宠物主页上能显示它是男孩还是女孩。

---

> **本 story 的实质是「修一个已知缺陷」，不是做新功能。**
> 性别选择器 2026 年就画好了、能选、能显示，**唯独选完不提交、不入库**——代码里有一行注释明写着这件事
> （`pet_profile_edit_page.dart:42`：「⚠️ 仅前端占位——后端 PetProfile 暂无 sex 字段，不随 PATCH 提交、不持久化」）。
> 用户选了性别、点了保存、退出再进来，发现又变回「请选择」。
>
> **交付**：一列可空的数据库字段（Flyway **V105**，见下方 🔴）· 更新接口收下这个字段 · 查询接口下发 · 编辑页提交与回填。
> **本版本的零依赖起点之一，同时是 Epic 2 的前置**（访客视图的基础档案区要展示性别）。

---

## Acceptance Criteria

### AC1 — 选了能存住（L1）

**Given** 档案编辑页当前的性别选择器是纯前端占位（代码注释明写「不随 PATCH 提交、不持久化」）
**When** 用户选择性别并保存，退出后重新进入编辑页
**Then** 之前选择的性别仍然显示 `[L1]`
**And** 该字段随档案更新接口一并提交、落库 `[L1]`

### AC2 — 数据库字段（L1）

**Given** 数据库尚无该字段
**When** 执行本 story 的迁移
**Then** 宠物档案表新增**可空**的性别列，取值 `MALE` / `FEMALE`，`NULL` 表示未填 `[L1]`
**And** 🛡 **存量宠物一律为 `NULL`，不做任何回填** `[L1]`
**And** 🔴 **Flyway 号取 `V105`，不是 `V101`** —— 理由见下方「🔴 头号陷阱」，**这条错了会炸生产库** `[L0]`

### AC3 — 存量为空要容错（L1 / L2）

**Given** 存量宠物没有性别
**When** 打开档案编辑页 / 打开该宠物的 H5 分享页
**Then** 两处都正常渲染、不报错、不显示空白占位符 `[L1]`
**And** 编辑页显示未选择态的提示文案 `[L2]`

> ⚠️ **H5 那一半在本 story 是「回归验证」，不是「新增展示」**：当前 `card.html` **压根没有性别字段**
> （模板里没有，`CardPageController` 也没有 `addAttribute`）。**H5 上展示性别是 Story 1.2 的事**
> （1-2 的 AC 明写「页面新增展示宠物生日与性别（数据来自 Story 1.1）」）。
> **本 story 不得改 `card.html` 与 `CardPageController` 的渲染**，只需确认它们没被弄坏。
> 擅自加会与 1-2 撞车 —— Epic 1 把埋点与模板改造合并成一个 Epic，正是为了避免两次改动同一文件。

### AC4 — 身份证性别不联动（L1）

**Given** 该宠物已经生成过身份证（身份证上另有一个性别字段）
**When** 修改档案性别
**Then** 🛡 **身份证上的性别不随之变化**——身份证是生成时的快照，两者不联动 `[L1]`

> 🛡 **这条比 story 原文写的更硬，理由是实读出来的**：身份证的性别**参与身份码生成**
> （`CardNumberService.allocateCardNo(birthday, gender, petType)` → 身份码格式 `TT+DDMMYY+SP+XXXX`，
> 性别编在里面）。若联动，已发出的身份码会与卡面对不上，甚至要重新分配号码、撞唯一约束。
> **两套性别字段的取值域也不同**：身份证是 `MALE/FEMALE/UNKNOWN`（三值，`@Pattern` 校验），
> 档案是 `MALE/FEMALE/NULL`（两值 + 空）。**不要把两者归一化到一起。**

### AC5 — 不扩散到本 story 范围外（L0）

**Given** 加了字段之后，很多地方"顺手"就能带上性别
**When** 实现本 story
**Then** 🛡 **只动档案自己的读写路径**，以下三处**明确不动** `[L0]`：
- **`PetProfileSnapshot`**（notify 模块定时推送扫描用的只读快照）—— 它刻意只暴露最小字段集，加字段等于扩大跨模块暴露面
- **兽医端**（`vet_inbox_item.dart` / `vet_request_detail_page.dart` 等三处注释写着「后端不下发 petSex」）—— 兽医端要不要显示性别是**独立的产品决定**，本 story 不替它做
- **访客只读视图 / 名片响应** —— 归 Epic 2 与 Story 1.2

**And** 🛡 **建档流程也不动** `[L0]`：`pet_profile_create_page.dart` 与 `PetProfileCreateRequest` **当前都没有性别**（已实读确认），本 story **只做"编辑时可填"**，不给建档流程加性别选择——那会改动新用户引导链路（F6 建档流是有独立验收标准的路径），且 epics 未要求。新建档案的性别自然为 `NULL`，与存量档案同一形态。

### AC6 — 不引入"清空"能力（L0）

**Given** 现有 `PATCH /api/v1/pet-profiles/me` 的语义是「**全字段可空，仅非空字段被更新**」
**When** 实现性别的更新
**Then** 🛡 **照抄这个语义**（`if (req.sex() != null) { ... }`），**不为性别单独引入"传 null 即清空"** `[L0]`
**And** UI 的性别选择底部菜单**保持只有两项**（`MALE` / `FEMALE`），**不加"清除"选项** `[L0]`

> ⚠️ **别照抄手机号的口径**。架构 AD-17 把「宠物性别」和「手机号」写在同一条决策里，但两者要求**不同**：
> 手机号**明确要求"允许清空写 null"**（FR-70 / Story 7-1），性别**没有这个要求**。
> 当前 PATCH 机制本身不支持清空，为性别单开一条特例会破坏该接口的统一语义。
> 后果是「选了就改不回未填」——这与现有机制自洽，**是已知且接受的行为，不是缺陷**。

### 命名映射链（照 CLAUDE.md）

DB `sex`（snake，此处单词本身无下划线）↔ Java `PetSex sex` ↔ JSON `sex`。
枚举落库 **varchar + UPPER_SNAKE**（`MALE` / `FEMALE`），不用 ordinal。

### 为什么字段叫 `sex` 而不是 `gender`

前端已有的状态变量、组件 key、ARB 词条全部用 `sex`（`_sex` / `petProfileEditSexTile` / `petSexMaleOption` / `petProfileSexMale`），
UI 稿的印尼语标签是 `KELAMIN`。**沿用 `sex` 与前端对齐**。
⚠️ 身份证那套用的是 `gender`（`CreateIdCardRequest.gender` / `IdCardResponse.gender`）——
**两套字段本就不联动（AC4），命名不同反而是好事，能防止误改。不要为了"统一"去重命名任何一边。**
