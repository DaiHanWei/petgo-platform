# Story 4.1: 顶置配置数据模型 + 时间窗判定

Status: review

## Story

As a 工程，
I want 有一套坑位配置模型与一份到点自动生效失效的判定，
so that 后台配置界面接上来之后，运营配的排期能自动上下线、不必守着时间手动操作。

> ⚠️ **本条本轮没有可观测的用户价值** —— 后台配置界面（AB-10A）不在本轮范围，运营还无处配置。
> 它交付的是**机制**：数据模型 + 时间窗判定 + 下架事件联动。如实标注，不假装它是一条面向运营的可用功能。

## Acceptance Criteria

**AC1 · 坑位维度必须是配置项**
**Then** 🛡 **不得把首页写死** —— 新增坑位时只需增加坑位记录、不需重构界面与数据结构 `[L1]`
**And** 🛡 这是**下游版本的前置**：话题页坑位直接复用本机制，写死即导致下游重构 `[L0]`

**AC2 · 一律查询时判定**
**Then** 🛡 生效中 = 当前时刻落在 `[开始, 结束)` 内，**查询时判定**；**不落状态列、不建定时扫描器** `[L1]`
**And** 🛡 **该判定必须只有一份实现，由四处共用**：顶置取数、用户标签取数、装饰标签取数、
**以及后台列表展示的「待生效 / 生效中 / 已结束」** `[L0]`
**And** 若各写一遍，左闭右开的边界会在某处被写成全闭，出现「App 上已失效、后台还显示生效中」`[L1]`

**AC3 · 时区口径**
**Then** 运营配的时间按 **WIB（`Asia/Jakarta`）** 解释，入库转 UTC 绝对时刻，
**不按客户端本地时区二次换算** `[L1]`
**And** 已接受的影响：一条配置对三个时区的用户是三个当地时刻，**本版本不做分区上线** `[L0]`

**AC4 · 同坑位时间窗不可重叠**
**Then** 提交重叠时间窗 → 校验拦截并提示调整 `[L1]`

**AC5 · 下架联动**
**Given** 顶置的内容可能在生效期间被下架
**When** 内容被**作者删除 / 审核判违规下架 / 作者账号被封禁**
**Then** 🛡 **订阅下架事件即时结束该顶置配置**（视为提前到达结束时间），坑位回退为普通内容填充，
不需要运营手动摘除 `[L1]`
**And** 🛡 该副作用**走事件订阅，不靠定时扫描器** `[L0]`

## Dev Notes

### 🔴 最重要的一处：现有下架事件只覆盖三种触发里的两种

AC 要求**三种**触发都要联动：作者删除、审核判违规下架、作者账号被封禁。
代码实读的结果是：

| 触发 | 走的路径 | 现在发事件吗 |
|---|---|---|
| 审核判违规下架 | 软删（原因 = 运营下架） | ✅ 发 |
| 作者账号被封禁 | 逐条软删（原因同上） | ✅ 发（复用同一条路径） |
| **作者自己删除** | 软删（原因 = 作者删除） | ❌ **不发** |

而且"不发"是**刻意的**：那个事件被通知模块消费，用来推送「你发布的内容因违反社区规范已被移除」——
作者自删也发的话，用户删自己的帖会收到一条说自己违规的通知。

所以**不能**简单地让顶置去订阅那个事件，也**不能**把它改成所有原因都发。

处置：**新增一个语义更宽的事件**（「这条内容不再可展示」），在软删时**无论什么原因**都发；
通知模块继续用原来那个事件，**一行都不改**。两个事件语义不同、消费方不同，不是重复。

⚠️ 还有第四种情况 AC 没列但性质相同：**作者注销账号**。
注销走的是另一条路（内容不软删，改成「作者已注销隐藏」态），同样会让顶置内容对别人不可见。
本 story 一并覆盖，**这一条超出 AC 范围，如果不认可可以摘掉**。

### 🔴 时间窗判定"只有一份"这件事，光写注释防不住

AC 的原话是「若各写一遍，左闭右开的边界会在某处被写成全闭，出现『App 上已失效、后台还显示生效中』」。

现实是：Java 侧要有一份（后台列表算三段），数据库侧也要有一份（取数时过滤，**不能捞出来再在内存里筛** ——
那会破坏分页）。这两份**语言不同，物理上没法共用同一行代码**。

所以"唯一实现"要落成一条**可执行的约束**：写一条集成测试，拿一组边界时刻
（开始前一毫秒 / 开始整点 / 中间 / 结束前一毫秒 / 结束整点 / 结束后）
**逐一对照 SQL 与 Java 的结论**。谁哪天把某一侧改成全闭，这条立刻红。

### 坑位为什么是"一个字段"而不是"一张坑位表"

AC 说「新增坑位时只需增加坑位记录、不需重构界面与数据结构」。
两种做法都能满足：单表加坑位字段，或者坑位单独一张表 + 配置外键指过去。

选**单表加字段**：本版本只有一个坑位，坑位表除了主键和名字没有任何属性，
建了它就得连带一套后台增删改查，属于为"以后可能"付现在的钱。
新增坑位时写一个新的坑位取值即可，数据结构不变 —— AC 的要求已经满足。

⚠️ 若哪天坑位本身要带属性（展示条数、样式、开关），再拆表不迟，那时拆的成本与现在一样。

### 提前结束为什么不覆盖原结束时间

「视为提前到达结束时间」最省事的实现是直接把结束时间改成现在。但那样：
- 运营在后台只会看到"这条 14:32 结束了"，**无从知道是排期到点还是被下架带走的**
- 排期冲突校验也失去了原始意图的记录

所以单列一个"提前结束时刻"，生效判定取两者中**较早的那个**。

### 时区：入库即 UTC，判定不再换算

运营配的是 WIB 墙上时间 → 入库转成 UTC 绝对时刻 → 上下线按这个绝对时刻执行。
**不按客户端本地时区二次换算** —— 同一条配置对全部用户在同一物理时刻上下线。

已接受的代价：印尼横跨三个时区，WIB 08:00 上线的内容对最东边的用户是当地 10:00。
本版本不做分区上线。

所以既**不能**直接订阅它，也**不能**把它改成所有原因都发。

原来那个事件**一行都没改**，通知行为零风险。两者消费方不同、语义不同、触发条件不同，不是重复。

#### 2. 🔴「唯一实现」落成了一条可执行的约束，不是一句注释
AC 原话是「若各写一遍，左闭右开的边界会在某处被写成全闭，出现『App 上已失效、后台还显示生效中』」。

现实是这份判定**必须存在两处**：Java 侧（后台算三段状态）和 SQL 侧（取数过滤 ——
捞出来再内存筛会破坏分页与游标契约）。两种语言，物理上共用不了同一行代码。

所以写了一条集成测试，拿六个边界时刻（开始前一毫秒 / 开始整点 / 开始后 /
结束前一毫秒 / 结束整点 / 结束后）**逐一对照两侧结论**。

反向验证：把 SQL 侧的 `<` 改成 `<=`（正是 AC 担心的"写成全闭"）→ 那条测试立刻红，
且报错直接指出是哪个时刻不一致。

#### 3. 坑位做成字段而不是独立坑位表
两种做法都满足 AC。选单表加字段的理由：坑位本身除主键和名字外**没有任何属性**，
建了它就得连带一套后台增删改查，属于为"以后可能"付现在的钱。

配套的一个刻意决定：**slot 不加 CHECK 约束**。约束住取值就等于把"新增坑位"变成一次数据库迁移，
与 AD-8「新增坑位不需重构」直接冲突。有一条测试用一个从未出现过的坑位名直接插入并验证独立生效，
钉住这条。

#### 4. 提前结束不覆盖运营配的结束时间
「视为提前到达结束时间」最省事的做法是直接改结束时间。但那样运营在后台只会看到
「这条 14:32 结束了」，**无从知道是排期到点还是被下架带走的**，排期意图的记录也丢了。

单列一个"提前结束时刻"，生效判定取两者中较早的那个。
写入时保证它不晚于排期结束（数据库也有约束），因此 SQL 侧可以直接用 COALESCE、不必取较小值。

#### 5. ⚠️ 顺带覆盖了 AC 没列的第四种情况：作者注销
AC 列的是删除 / 违规下架 / 封禁三种。**注销**走的是另一条路（内容不软删，改成「作者已注销隐藏」态），
但性质完全相同：顶置位会继续展示一条别人已经看不到的内容。

已一并覆盖。注销走**批量隐藏**、拿不到逐条 id，发不出上面那种逐条事件，
故在模块内直接收口（一条带子查询的更新）。
**这一条超出 AC 范围，如果不认可可以摘掉** —— 摘掉的后果是注销用户的顶置内容会挂到排期自然结束。

#### 6. 联动用的是"同事务"而非"提交后"
通知那批监听器都是**提交后**触发（通知是事后告知，发失败不该回滚业务）。
顶置联动刻意相反 —— 它是**数据副作用**：下架回滚了，顶置也必须跟着回滚。
换成提交后触发会出现"下架失败但顶置已被结束"的状态漂移。

#### 7. WIB 时区常量收拢了
仓库里原先至少**三处各写了一遍** `Asia/Jakarta`，且都只用于展示格式化、没有一处是判定用的。
现在判定所需的那份收在共享判定类里，与三段状态、重叠判定同一处。
