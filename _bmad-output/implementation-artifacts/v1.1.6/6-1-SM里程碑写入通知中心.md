# Story 6.1: S/M 级里程碑写入通知中心

Status: review

## Story

As a 宠物主，
I want 别人给我点赞评论触发的里程碑达成也能告诉我，
so that 我不用自己回头翻列表才发现已经达成了。

## Acceptance Criteria

**AC1 · 新增一种通知类型**
**Given** 现在只有一种里程碑通知类型（L 级在用，含系统推送）
**Then** 新增一种类型：**写通知中心记录、不发系统推送** `[L1]`
**And** L 级维持现状不变（推送 + 通知中心两者都有）`[L1]`
**And** 文案复用现有的里程碑庆祝文案 `[L1]`

**AC2 · 🛡 必须让未读角标递增**
**Given** 铃铛角标的数字由 Redis 计数器维护、**不是查库算出来的**
**Then** 🛡 **必须同步让该未读计数器递增** —— 否则通知进了中心、角标不动，
本 FR 的核心诉求（让本人不在场时也能被告知）**直接落空** `[L1]`
**And** 计数为 0 时隐藏角标、大于 99 显示 `99+`（沿用现状）`[L2]`

**AC3 · 点击落点**
**Then** 落**成长档案 → 里程碑列表页**，与 L 级一致、不做差异化 `[L2]`

**AC4 · 一次解锁多个**
**Then** 🛡 **写 N 条，每个达成的里程碑各一条** `[L1]`
**And** 🛡 每条**必须写明该里程碑的具体名称**（取庆祝文案中对应目录码的具体文案）——
**不得使用「你完成了一个里程碑」这类看不出是哪一条的泛化文案** `[L1]`
**And** 庆祝弹层仍按既定只弹一次，两者不冲突 `[L2]`

**AC5 · 🛡 存量不回填**
**Then** 🛡 **存量已完成的不回填**，仅对上线后新完成者生效 —— 否则升级后通知中心一次性涌入
大量历史记录、未读数字异常，观感等同故障 `[L1]`

**AC6 · 埋点**
**Then** 点击通知列表条目时上报事件并带上通知类型（可与 L 级、点赞 / 评论类横向对比点击率）`[L1]`

## Dev Notes

### 🔴 「不发系统推送」不是加个 if 就完事 —— 现有发送方法恒发推送

代码实读：通知模块的"发送"方法**一定会**做三件事：写通知行、未读角标 +1、**投递离线推送**。
没有"只写不推"的口子。

所以要新增一条发送路径。⚠️ 关键是**它必须仍然走同一处角标自增** ——
AC2 那条 🛡 之所以是"白送的"，前提是不另起一套发送逻辑。自己写一遍就等于把那条护栏丢了。

### ✅ 「写 N 条」与「存量不回填」都是白送的（但仍要写测试钉住）

看了里程碑完成的落库逻辑：**每完成一条就发一个事件，且只在"新"完成时发**
（已完成的会被幂等挡掉、不重复发）。

- **写 N 条** → 事件本来就是一条一个，天然成立
- **存量不回填** → 只对事件反应、不扫历史，天然成立

两条都是"结构上不可能做错"，但**仍要写测试**：它们是 AC 里带 🛡 的项，靠"碰巧对"守不住 ——
哪天有人为了别的需求把事件改成批量发一条，这两条会同时静默失效。

### 🔴 只改后端等于没做 —— 通知中心的文案在 App 侧

通知中心的**标题与正文是 App 按类型 switch 出来的，完全不读后端下发的 title/body**
（这是项目一贯做法：后端不下发展示文案，杜绝中文泄漏到印尼语界面）。

后果：**只在后端加一个新类型，App 会把它落到"未知类型兜底"，渲染成中性的「系统通知」**——
而 AC4 明确禁止"看不出是哪一条"的泛化文案。

所以这条**必须前后端一起做**。具体名称的来源：App 已有一份**按里程碑编码的中英双语标题表**，
而通知记录里本来就带着编码（L 级那条就是这么传的）。让 App 拿编码去查自己那份表即可，
**不要让后端把名字塞进通知正文** —— 那会把中文/印尼语的选择权从客户端拿走。

⚠️ 已有先例可循：审核类通知就是用同一个字段区分"用户/宠物"两种变体的。

### ⚠️ 埋点是从零加，且 PRD 给的两个事件名都过不了命名规范

通知模块**目前一个埋点都没有**。

PRD §3.2 在本 FR 名下列了两个事件，但：
- 两个名字都**缺少模块前缀**（规范要求前缀取自既有词表，好让产品一眼看出是哪个页面）
- 其中一个的动作词尾（"opened"）不在允许词表内

处置同前几条 story：**按规范改名并回写 PRD**，属性不动。

另一处**范围判断**：PRD 那两个事件里，"打开通知中心"那条要带**推送权限状态**，
而推送权限的模型属 FR-85（Epic 8 推送权限重构）。本 story 只做 AC6 要求的**点击**那一条，
"打开通知中心"那条**留给 Epic 8**（它同时是那边的曝光分母）。已在此显式标注，避免被当成漏做。

### 现状实读（2026-08-19）

| 位置 | 现状 |
|---|---|
| 里程碑通知 | 监听器里写着「**仅 L 级触达（S/M 不推，避免打扰）**」，非 L 直接 return |
| 通知类型 | 枚举里只有 L 级那一种里程碑类型；取值有 CHECK 约束（改动要走迁移）|
| 未读角标 | Redis 计数器，**自增已做在"发通知"这个统一动作里** |
| 发送方法 | **恒发推送**，无"只写不推"的口子 |
| 里程碑名 | 后端有印尼语标题（Epic 1 加的）；**App 有一份按编码的中英双语表**（显示走它）|
| 通知中心 | 标题/正文按类型 switch，未知类型落中性兜底 |
| 通知埋点 | **一个都没有** |
| Flyway | 本线最新 V110，下一个是 **V111** |

### 不在本 story 范围

- 推送权限本身（Epic 8）
- 里程碑庆祝弹层（V1.1.2 已定，本条不碰）

#### 1. 🔴 途中撞出一个**跨分支的定时炸弹**（本 story 之外，但已顺手拆掉）
迁移一跑就炸：本地库里有两个本分支不认识的通知类型（警告 / 封号），它们来自并行的 **hex/v1.1.4**。

追下去发现的是**结构性问题**，不是本地脏数据：
这个约束的改法是「DROP 掉再按完整清单 ADD 回去」。两条工作线各写一份完整清单时，
**合并后跑在后面的那份会把另一份的取值悄悄踢掉**。

🔴 **V97 就是为了修这个才存在的** —— 当时审核线与 v1.1 线各加各的，合并后审核类通知全断。
同一个坑正要再踩一次。

处置：本次迁移的清单**取并集**，把 v1.1.4 那两个值也写进去。
本分支的代码写不出它们（枚举里没有），多几个允许值是零成本的；
换来的是**两条线无论谁先合入都不会互相踢掉对方的通知类型**。迁移文件里写明了原因与"下次先查并行分支"。

#### 2. 🔴「不发系统推送」需要新增一条发送路径，且必须与旧路径共用同一段逻辑
现有的"发通知"方法**一定会**做三件事：写通知行、角标 +1、投递推送。没有只写不推的口子。

新增了一条只写不推的路径，但**刻意与原路径共用同一段落库 + 角标逻辑**，只切掉推送那一步。
AC2 那条 🛡「必须让角标递增」之所以是白送的，前提就是这个 ——
另写一套"只落库"的实现，角标就不会涨：通知进了中心而铃铛不动，用户仍需主动去翻，本 FR 直接失效。

反向验证：把 S/M 改成走推送那条路 → **3 条测试同时红**。

#### 3. 🔴 只改后端等于没做
通知中心的标题/正文是 **App 按类型 switch 出来的、完全不读后端下发的文案**
（项目一贯做法：后端不下发展示文案，杜绝中文泄漏到印尼语界面）。

所以只在后端加类型，App 会把它落到「未知类型兜底」渲染成中性的**「系统通知」**——
正是 AC4 明令禁止的"看不出是哪一条"。

做法：后端只下发**里程碑编码**，App 拿编码查自己那份表。
- 有宠物名 → 用**庆祝文案**（AC 要求复用它，文案里带 `{name}` 占位符）
- 拿不到宠物名 → 退化成里程碑的**简短标题**，仍然具体，**绝不会落到中性兜底**

反向验证：把新类型的文案映射删掉 → **两条测试同时红**。

#### 4. ✅ 两条 AC 是结构上白送的（仍写了测试）
- **一次解锁多个写 N 条**：完成事件本来就是**每完成一条发一个**
- **存量不回填**：只对事件反应、不扫历史；完成落库幂等，已完成的不会再发事件

两条都不需要写额外逻辑，但都写了测试钉住 ——
哪天有人为了别的需求把事件改成"批量发一条"，这两条会**同时静默失效**。

#### 5. ⚠️ 埋点：改了名，且只做了两条里的一条

两个名字都过不了命名规范（缺模块前缀 / 动作词尾不在词表），已按规范改名并回写 PRD，属性未动。
