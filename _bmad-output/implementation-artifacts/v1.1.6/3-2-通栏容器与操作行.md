# Story 3.2: 通栏容器 + 操作行（点赞与评论）

Status: review

## Story

As a 用户，
I want 在首页就能点赞、并看到有多少条评论，
so that 我不必为了点个赞专门点进详情页。

## Acceptance Criteria

**AC1 · 通栏容器**
**Given** 现状是白底圆角带描边、左右各 16px 屏边距的卡片
**When** 改为通栏式
**Then** 去掉描边 / 圆角 / 屏边距，图片**全宽出血**贴屏幕左右边缘 `[L2]`
**And** 条目之间改为 **1px 分隔线 + 上下 12px 间距** `[L2]`
**And** 🔴 **只有图片出血** —— 作者行 / 操作行 / 正文 / 时间**各自仍保留左右 16px 内边距**（UI 稿里这四块都写着 `padding:0 16px`）。这是本 story 最容易读错的一条

**AC2 · 元素顺序与作者行**
**Then** 顺序为 **作者行 → 图片 → 操作行 → 正文 → 时间** `[L2]`
**And** 作者行 = 32px 圆头像 + 昵称（13.5px/700）+ 内容类型徽章 + 右侧「···」`[L2]`
**And** 正文两行截断；**保留内容类型徽章**（三类内容需在首页可辨识）；**正文不加作者名前缀** `[L2]`
**And** ⚠️ 现状是「作者行 → 正文 → 图片」，且**时间在昵称正下方**——两处都要挪

**AC3 · 🛡 点赞直接复用既有组件**
**Given** 点赞组件已实现未登录门控、乐观更新、后端真值校正、失败回滚
**Then** 🛡 **直接复用该组件，不新写点赞逻辑** `[L0]`
**And** 未点赞为描边心形；已点赞为实心 + 品牌红 `#F0425A`，**数字同步变色** `[L2]`
**And** ⚠️ 现状数字**不随点赞变色**，需要改
**And** 未登录点赞触发既有登录引导、不发请求；点赞成功仍触发既有推送；用户对自己内容点赞不通知 `[L1]`

**AC4 · 评论跳详情并定位评论区**
**Then** 点击评论按钮 → 跳详情页并滚动定位到评论区 `[L2]`
**And** 🛡 路由须带统一的「定位评论区」参数，**首页侧与详情页侧必须用同一参数名** `[L0]`
**And** ✅ **该参数已经存在**：`?focus=comments`，通知深链早就在产出它，**但至今没人消费**。
      直接沿用即可 —— 顺带把通知深链的评论锚点一并接通（见 Dev Notes）
**And** **不做首页内联评论** `[L0]`

**AC5 · 点击分区**
**Then** 点赞**就地切换、不跳转**；评论跳详情页定位评论区；**其余区域**（作者行 / 图片 / 正文 / 时间）仍整块点击进详情页顶部 `[L2]`

**AC6 · 🛡 埋点来源属性两侧都要传**
**Then** 既有点赞事件新增来源属性（`feed` / `detail`），**两侧都必须传** —— 只改一侧则该对比彻底失效 `[L1]`
**And** 🛡 **只加属性、不改事件名**（改名会切断已有的点赞历史序列；有护栏测试盯着事件名）

**AC7 · 🛡 颜色不得按名字猜**
**Then** ⚠️ **`AppColors.mint` 的实际值是品牌紫 `#845EC9`，不是绿色**（早期命名遗留）—— 不得按名字猜颜色 `[L0]`
**And** ✅ 品牌红**已有现成常量**，不要新建（见 Dev Notes 的对照表）

## Dev Notes

### 🔴 最容易读错的一条：只有图片出血

AC 说「去掉屏边距、图片全宽出血」，容易被读成「整张卡贴边」。**不是。**

UI 稿里作者行 / 操作行 / 正文 / 时间**四块各自都写着 `padding:0 16px`** ——
去掉的是**列表容器**的 16px 屏边距，让**图片**能贴边；文字区的 16px 由各块自己补回来。

做成整张贴边，文字会顶到屏幕边缘，一眼就能看出不对。

### 🔴 颜色：有现成常量，别新建也别按名字猜

| 要用的 | 现成常量 | 实际色值 |
|---|---|---|
| 已赞态红 | **点赞红心专用别名**（组件已在用） | `#F0425A` |
| 条目分隔线 | 浅线色（**不是**卡片描边那个） | `#F0F0F0` |
| 卡片描边（要去掉） | 边框色 | `#E6E6E6` |

⚠️ **`AppColors.mint` 是品牌紫 `#845EC9`，不是绿色**，整个 `mint*` 色阶都是紫的。架构文档专门列了这条陷阱。

⚠️ **UI 稿与 PRD 的红色对不上**：UI 稿的 CSS 变量写的是另一个红（`#E5604D`），而 PRD、epics AC、架构文档三处都写 `#F0425A`。
**以 `#F0425A` 为准**（UI 稿那处是变量取错）。

### ✅ 评论定位的参数已经存在，且接通它能顺带修好一处

`?focus=comments` 这个参数**早就在仓库里被产出了** —— 通知深链在生成带评论锚点的跳转时就用它，
测试里也断言了这个字符串。**但详情页从来没有消费过它**，所以那条链路点进去只是打开详情页、不定位。

本 story 直接沿用这个参数名（正好满足「两侧同名」的要求），接通之后：
- Feed 的评论按钮能定位 ✅
- **通知深链的评论锚点也跟着好了** ✅（附带收益，不额外花成本）

⚠️ 另有一条路由也用 `focus`，但那边的值是「记录编号」。路由不同不冲突，别把两者混为一谈。

### 🔴 点赞组件进列表的两个坑

组件本身是好的（乐观更新、真值校正、失败回滚、未登录门控齐全），**别重写**。但它是为详情页写的，进列表有两处要补：

1. **key 写死成详情页专用的名字** → 一屏多张卡会重复 key。改成能区分的。
2. **没有跟随属性更新的处理** → 它只在首次创建时读初始值。列表下拉刷新后，若组件被复用，
   显示的可能还是旧的点赞态。

### 🔴 骨架屏是另一份拷贝

加载中的骨架屏**复制了同一套圆角/描边/屏边距**。只改卡片不改它，会在「加载中 → 加载完」之间**跳一次布局**。

### ⚠️ 三处注释写着「不含点赞/评论数」

客户端模型、卡片组件、后端 DTO 的注释里都写着这句（引 FR-17）。本 story 正是要打破它 ——
**注释一并改掉**，否则后来的人会以为这是当前约束。

### 现状实读（2026-08-18）

| 组件 | 现状 |
|---|---|
| 卡片 | 白底 + 14px 圆角 + 描边；顺序是 **作者行 → 正文 → 图片**（与目标不同）；时间在昵称正下方 |
| 头像 | 默认 34px（目标 32） |
| 点击 | **整块一个手势**，无分区；长按 = 举报；作者行单独可点（迷你主页） |
| 「···」 | Feed 侧**不存在** |
| 点赞 / 评论数 | **都不存在** |
| 列表容器 | `SingleChildScrollView + Column`，**一次性全量构建**、无懒加载；条目间只有 12px 间距、无分隔线；左右 16px 屏边距在这里 |
| 详情页 | 单一滚动容器、**无滚动控制器**；评论标题行**无锚点** |
| 埋点 | 点赞事件只带「点后是否为已赞」，**没有来源属性** |

**只影响首页**：卡片组件全仓只有一个引用点；「我的发布」虽然复用同一个后端投影，但**有自己的模型和自己的卡片**，不受本 story 影响。

### 不在本 story 范围

- 图片三段渲染口径、加载期占位（→ 3.3）
- 多图轮播、**图片区叠加层**（→ 3.4；顶置角标与装饰标签将来往那里挂）
- 发布页裁剪与其埋点（→ 3.5）

### ⚠️ 一条明确不做、但需要记下的事

列表容器是**一次性全量构建**的（不是懒加载）。通栏化之后每张卡更高、3.4 还要加多图轮播，
首屏与内存压力会放大。

**本 story 不改它** —— 换成懒加载列表会牵动滚动到顶、预加载、页头页脚插槽等一串既有逻辑，
与「改容器样式」不是一件事，混在一起会让回归面失控。
**记为待评估项，建议在 3.4（多图轮播）时一并判断。**

### Completion Notes List

**1. 「只有图片出血」按 story 的提醒实现了**

列表容器只去掉**左右**屏边距（上下保留），图片因此贴到屏幕边缘；
作者行 / 操作行 / 正文 / 时间**各自补 16px 左右内边距**。
做成整张贴边的话文字会顶到屏幕边上 —— 这条在卡片的类注释里也写了一遍，防后人"顺手对齐"。

**2. 点赞组件的两个坑都补了，状态机一行没动**

- key 改成带内容编号（原先写死成详情页专用名，进列表会重复）
- 补了**跟随外部数据更新**的处理。⚠️ 这里有个细节：**只在「换了另一条内容」或「请求不在飞行中」时才跟随** ——
  否则下拉刷新回来的旧值会把用户刚点出来的乐观更新盖回去
- 数字随点赞态变色（改前只有图标变红、数字仍是灰的，看上去像"没点上"）
- 乐观更新 / 真值校正 / 失败回滚 / 未登录门控**原样保留**

**3. `source` 设成了必填参数**

不是可选带默认值 —— **漏传直接编译不过**。理由：这个属性一旦有一侧没传，
「首页点赞是净增长还是把详情页的点赞前移了」这个对比就彻底失效，而那正是本版本要回答的问题。
用编译错误挡住比用约定挡住可靠。

**4. 评论定位沿用既有参数，顺带修好了通知深链**

`?focus=comments` 早就被通知深链产出、测试也断言着，但详情页从没消费过。
本 story 接通后，**通知里那条"评论锚点"的深链也跟着生效了**——零额外成本。

实现上没有给详情页加滚动控制器，而是给评论标题包了一个「挂载后把自己滚进视野」的小组件：
详情页是单一滚动容器，可以自己找到外层可滚动祖先，不必改造整页结构、也不用管控制器生命周期。
⚠️ 必须等下一帧再滚 —— 挂载当时布局还没完成。

**5. 骨架屏同步改了**（圆角/描边/屏边距），否则「加载中 → 加载完」会跳一次布局。

**6. 「···」与长按举报走同一个动作**

Feed 此前只有长按举报、没有显式入口。新加的「···」接的是同一个举报流程 ——
不新造一套菜单，因为目前那里只有这一个动作。

**7. ⚠️ 发现一条旧用例名不副实**

`feed_test.dart` 里那条「MasonryCard 纯文字卡渲染昵称与正文（**无点赞评论数**）」——
标题写着"无点赞评论数"，但**断言里根本没检查这件事**，所以加了操作行之后它照样绿。
已把标题订正、并把操作行的行为交给新测试专门覆盖。
（这类"标题在说谎的测试"值得留意：它给的是虚假的安心感。）

**8. 未做（按 story 的明确划分）**：图片三段渲染口径与占位（3.3）· 多图轮播与图片区叠加层（3.4）· 发布页裁剪（3.5）。
