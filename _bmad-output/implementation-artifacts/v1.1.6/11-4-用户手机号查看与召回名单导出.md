# Story 11.4: 用户手机号查看与召回名单导出

Status: review

## Story

As a 运营，
I want 在后台看到用户填的手机号、按已填/未填筛选、并导出召回名单，
so that FR-70 采集到的手机号真的能被用上（而不是只躺在库里）。

---

> App 侧 FR-70 已交付（Epic 7，story 7-1 / 7-2），列 `users.phone` 已建（V112）。
> **后台看不到这个字段** —— 采集了但用不上。
>
> **本 story 是 AB-11A 的前半。** 后半「批量催填推送」**已决定后移**（2026-08-21）——
> 后台目前没有任何面向用户的群发推送能力（现存 broadcast 只给兽医广播接单请求），
> 那是一整套新基建：名单筛选 + 文案 + 发送任务 + 失败处理 + 送达统计。
> **导出名单已足够让运营开工**（走 WhatsApp 触达本就是 FR-70 的目的）。

## Acceptance Criteria

### AC1 — 🔴 手机号是 PII：双权限，导出单独一个（L0 / L1）

**Then** 🛡 **查看手机号**一个独立权限码 `[L0]`
**And** 🛡 **导出召回名单**再一个独立权限码 `[L0]`
**And** 无查看权限时，手机号字段**不下发到页面**（不是前端隐藏）`[L1]`
**And** 🛡 入口门与侧栏 `sec:authorize` 条件逐字一致 `[L0]`

> 🔴 **本条覆盖后台 PRD 的原口径。** PRD AB-11A 写「沿用现有用户详情只读权限，
> **不新增独立权限项**」—— 2026-08-21 决定改为双码，理由两条：
> ① 本项目既定约定是"新后台功能必须配自己的查看/编辑权限"；
> ② 手机号是 PII，让所有能看用户详情的账号都能看明文号码 + 导出名单，与最小权限相悖。
>
> **导出为什么要单独一个码**：查看是一次看一个人，导出是把 PII **批量带出系统**，
> 风险高一档，且带出之后平台再也管不到它。
>
> ⚠️ **无权限时必须在服务端就不下发**。只在模板里隐藏 = 数据已经到了浏览器，
> 查看源码/接口就能拿到。

### AC2 — 🔴 禁止入日志（L0）

**Then** 🛡 手机号**绝不出现在任何日志**（含审计日志的明文字段、异常堆栈、请求日志）`[L0]`
**And** 🛡 传递该值的中间变量/DTO 字段**一律沿用 `phone` 这个名字** `[L0]`

> 🔴 **这条有一个非常具体的机制**：V112 迁移的注释写着
> 「日志脱敏名单里已经有 `phone` —— 所以这一列**必须叫 phone**。
> 叫 phoneNumber / mobile / contact 都不会命中，日志里就会明晃晃出现真实号码」。
>
> 也就是说**脱敏是按字段名匹配的**。任何以别名转手该值的变量都会**绕过脱敏** ——
> 这不是风格问题，是会直接导致明文号码落盘的实现缺陷。

### AC3 — 用户详情展示（L1）

**Then** 用户详情页展示手机号字段（有查看权限时）`[L1]`
**And** 未填写时展示明确的"未填写"占位，不是空白 `[L1]`

### AC4 — 按已填 / 未填筛选（L1）

**Then** 用户列表支持按**手机号已填写 / 未填写**筛选 `[L1]`

> ⚠️ 「已填写」的判据是 `phone IS NOT NULL AND phone <> ''`。
> FR-70 **允许留空保存以撤回号码**（写 null），所以两种空都要算作"未填写"。

### AC5 — 召回名单导出（L1）

**Then** 导出筛选结果，供运营做触达名单 `[L1]`
**And** 🛡 每条记录**标注该账号当前状态**（正常 / 已封号）`[L1]`
**And** 🛡 **不自动剔除已封号账号** —— 由运营按标注自行判断 `[L1]`
**And** 导出动作记审计（操作人、时间、导出条数、筛选条件）`[L1]`

> 不自动剔除是产品的明确选择（PRD AB-11A）：运营有时确实要联系已封号用户。
> 但**必须标注** —— 不标注就等于让运营在不知情的情况下给封号用户发召回。
>
> ⚠️ 导出记审计是本 story 自己加的要求（PRD 未写）：PII 批量出库必须留痕，
> 否则事后无从回答"这份名单是谁什么时候导的"。

### AC6 — 不做的（L0）

**Then** 🛡 以下**明确不做** `[L0]`：
- **批量催填推送** —— 已决定后移，见文首
- **手机号编辑 / 代填** —— 手机号只由用户自己填（FR-70），后台不代改
- **手机号验证** —— FR-70 明确不做 OTP

### Completion Notes List

**实现落在既有的用户管理页上，没有另起新页面** —— story 的 AC3/AC4/AC5 说的就是
「用户详情页展示手机号、用户列表支持筛选、导出筛选结果」，都是既有页面的扩展。

**🔴 无查看权限时，号码在服务端就不装。**
`detail(userId, includePhone)` 由控制器按权限传入；无权限时 DTO 那个字段恒为 null，
**号码根本没进这份 HTML**。测试断言的是「响应里不含这串字符」，
而不是「页面上看不见」—— 后者用 CSS 就能"实现"，而数据其实已经发到浏览器了。

**🛡 列表页只显示"填了 / 没填"，不显示号码本身。**
`AdminUserRow` 只带一个布尔。少一处出现 PII 就少一个泄漏面 ——
运营挑名单时并不需要在列表上看到明文，需要看具体号码时点进详情页（且要有权限）。
这一条也写了测试：列表 HTML 里不得出现明文号码。

**🔴 两个权限码**：`user.phone_view`（看）/ `user.phone_export`（导出）。
测试钉住「只有查看权限 → 导出 403」。
两个都归**查看组** —— 导出不改任何数据，它是"看得更狠的一种看"。
🔴 本 story 因此**覆盖了后台 PRD 的原口径**（原写「不新增独立权限项」）。

**🔴 「未填写」的判据是 NULL **或**空串。**
FR-70 允许用户留空保存以**撤回**号码（保存时写 null），历史上也可能存在空串。
只判 NULL 会把撤回过的人错分到"已填写"，于是运营的催填名单里**永远少了这批人**，
而且这个漏洞不会报错、没人会发现。测试对两种空各造了一条数据。

**导出：不剔除封号账号，但每行标注状态**（ACTIVE / DEACTIVATED / DELETED）。
运营有时确实要联系已封号用户，但不标注就等于让他在不知情的情况下发召回。
**导出记审计**（PRD 未要求，本 story 加的）：操作人、时间、条数、筛选条件 ——
⚠️ 审计摘要里**只有条数与筛选条件，绝不含号码本身**。
CSV 的姓名列做了转义：昵称里一个逗号就能把整份名单的列错开。

**🔴 别名字段写成了静态断言。**
机制很具体：日志脱敏是**按字段名匹配**的（`users.phone` 那条迁移的注释原话：
「叫 phoneNumber / mobile / contact 都不会命中，日志里就会明晃晃出现真实号码」）。
所以本 story 涉及的四个文件里，任何以 `phoneNumber` / `mobile` / `contactNumber`
形态转手该值的写法都会让测试红。它不验证运行时行为，验证的是**没人在这里起了别名**。

**踩到并修掉的三处**

1. **导出端点 500：我把它标成了 `@Transactional(readOnly = true)`，而它要写审计行。**
   报错是 `cannot execute INSERT in a read-only transaction` —— 读的部分没问题，
   是那条审计插入被只读事务挡了。⚠️ 「这个方法主要是读」不等于「可以标 readOnly」：
   只要它写一行审计，就不是只读的。
2. **改了构造器与控制器签名，打断两个既有测试**（`AdminUserServiceTest` 直接 new 了 service、
   `AdminUserAccessControlTest` 直接调了 controller 方法）。已跟改并在注释里注明为什么多了参数。
3. 🔴 **一条我原先不知道的护栏抓住了真问题**：`AdminPermissionWiringTest` 要求
   `AdminPermissions.ALL` 里每个码都至少有一处 `hasAuthority('x')` 落点（防"勾了也没用"的死码）。
   我的 `user.phone_view` 是**用 Java 手写权限判断**实现的门控，源码里没有那种表达式，
   于是被判成死码 —— **判得对**：只留 Java 那一处，权限码在勾选页上就成了勾了不生效的摆设。
   修法是在模板上补一道 `sec:authorize`，表达式与控制器判定的同一个码一致。
   两道门是有意的分工：**服务端不装值是真正的保护**（号码根本不进 HTML），
   模板那道是双重保险 + 让接线护栏看得见落点。

**⚠️ 一件文档动作，未在本 story 内执行**：后台 PRD 的 AB-11A 里仍写着
「App 侧的软引导严格为『首次问诊后 / 建档后取最早、全局仅弹一次』」——
**该双时机已被 X-20 判为死代码、X-21 改为「用户第 3 天打开 App 时」**（产品 2026-08-21 确认）。

**明确没做**（AC6）：批量催填推送（已决定后移 —— 后台无任何面向用户的群发能力）、
手机号编辑/代填（手机号只由用户自己填）、手机号验证（FR-70 明确不做 OTP）。

**留 L2 的**：浏览器上下载 CSV 的实际观感、Excel 打开中文与转义是否正常。
