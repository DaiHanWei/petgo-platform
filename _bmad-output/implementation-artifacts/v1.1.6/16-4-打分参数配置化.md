# Story 16.4: 打分参数配置化

Status: review

## Story

As a 产品与数据，
I want 打分公式的参数在后台改一下就生效，
so that 发版后那次必然要做的校准不用再走一次完整发版。

---

> 🔴 **这不是优化项，是工程硬前置**（补充 PRD §8.1 第四项）。
>
> 理由：本 FR 与首页点赞（FR-93）**同批发版** ⇒ 开发阶段线上**不存在** `source=feed` 的点赞数据
> ⇒ `P95`、评论权重、0.6/0.4 **在开发阶段无从校准** ⇒ **第一次校准必然发生在发版之后**（OQ-B1）。
> 写死意味着那次校准要走一次完整发版流程 —— 而它**必然会发生**，不是可能。

---

## Acceptance Criteria

### AC1 — 参数清单（L1）

**Then** 下列参数由**配置下发**承载，调整后**无需发版**即可生效 `[L1]`：

| 参数 | 初始值 | 为什么必须可调 |
|---|---|---|
| 新鲜度 / 互动度权重 | 0.6 / 0.4 | 首页点赞上线后互动量整体跳升，相对关系要重定 |
| 评论权重 | ×2 | 点赞门槛降低后被稀释，可能需提到 ×3 或更高 |
| `P95` 归一化基准 | 全池近 30 天互动量的 95 分位 | 🔴 应为**定期重算的动态值**，不是一次写死的常数 |
| 曝光衰减系数 | 0.3 | 池子体量变化时要调 |
| 属性配比 / 物种配比 | 5/3/2 · 6/2/2 | OQ-B2 / OQ-B7 |
| 窗口大小 / 曝光窗口天数 | 10 · 7 天 | 同上 |

**And** 🛡 限流系数（0.2）与荣誉加成（1.3）**另有载体**，本 story 不重复承载 `[L0]`

### AC2 — 🛡 用既有配置中心，不新建模块（L0）

**Then** 🛡 **不新建「算法参数管理」后台模块** —— 既有配置中心加一组配置项 `[L0]`
**And** 复用其 **diff 审计**与**实时下发**机制 `[L1]`

### AC3 — `P95` 是动态值（L1）

**Then** `P95` 须能**定期重算**（近 30 天互动量的 95 分位）`[L1]`
**And** 🛡 重算失败时**沿用上一次的值**，不得回落到 0 或抛错 `[L1]`

> 🔴 `ln(1 + P95)` 做分母 —— `P95 = 0` 会**除零**。这条不是防御性编程，是必须的。

### AC4 — 🛡 配比参数的取值必须自洽（L1）

**Then** 🛡 属性配比三项之和须等于窗口大小；物种配比三项之和须等于窗口大小 `[L1]`
**And** 不自洽的配置**拒绝保存**并说明原因 `[L1]`

> 不校验的后果：运营把 5/3/2 改成 5/3/3，窗口凑不满或溢出 —— 而那**不会报错**，
> 只会让节奏莫名其妙，且极难被想到去查配置。

### AC5 — 本 story 不做的（L0）

**Then** 🛡 `[L0]`：不做 A/B 参数组、不做按用户分层的差异化参数、不做参数变更的效果看板

### Completion Notes List

**1. 🔴 补上了 16-2 留的那处硬接缝（本 story 最有价值的一件事）**

16-2 时 A/B 属性模板是**手写字面量**，而本 story 要让「属性配比」可调 ——
改那三个数**不会自动改变模板顺序**。配置改了却不生效是最坏的一类 bug：
不报错、不告警、只是节奏不对，且极难被想到去查配置。

选的是**两条都做**，不是二选一：
- `AttributeTemplate.forQuotas(fun, edu, life, window)` 由配比生成排期 ⇒ 改配比真的改顺序
- 🔴 **配比恰为 5/3/2 且窗口为 10 时原样返回手写的 A/B** ——
  16-2 的 AC1 把那两张表**逐槽位**钉死了，默认行为一个字都不能变。
  让生成器顺手把默认顺序也换掉，等于悄悄改了已上线的首页节奏。
- `rejectUnusableQuotas` 把不可用的配比挡在保存之前

生成规则：每槽取「剩余配额最多、且与上一槽不同」的属性，平手按变体偏好序打破
（A 偏 EDU、B 偏 LIFE）。⚠️ 巧合：5/3/2 下生成的 B **恰好等于**手写的 B，生成的 A 与手写 A 不同
—— 所以默认走字面量这一条不只是"保险"，是真的必要。

**2. 🔴 属性配比多一道校验：单项不得超过窗口的一半**

超过就**必然**出现同属性相邻（鸽巢原理：10 槽放 6 个 FUN），「穿插」这件事本身失去意义。
5/10 正好在边界上、可行（位次 1,3,5,7,9）。
🔴 **校验与生成用同一处规则** —— 两处各写一遍会出现「保存通过了但生成出来的模板是坏的」，
那种不一致没有任何报错，只能靠人肉刷首页发现。有一条测试专门钉这个等价关系。

**3. P95 做成动态值，失败路径是本 story 的重点**

`FeedRankP95Scanner` 每 6 小时算一次近 30 天的 95 分位。
🔴 **只在算出结果后才写库，出错就什么都不动**：`ln(1 + P95)` 是分母，
写成 0 会让互动度对**所有内容**记 0（打分器有除零保护，不会崩，但排序退化成纯新鲜度）——
表现是「首页又变回时间倒序了」，而且不报错。

四条失败路径各有用例：无数据 / 全零互动 / 查询抛错 / 配置行缺失，**一律沿用旧值**。
⚠️ 异常也不向外抛 —— 抛了会污染调度线程的后续执行。

⚠️ **冷启动兜底**：配置里 P95 为 0（还没跑过重算）时，回落到「本次候选池现算」
（16-3 那个算法保留下来了）。🔴 这是兜底不是第二个事实源：一旦重算跑过，永远用配置里的值。

**4. 参数的分工：什么进配置表，什么不进**

| | 进 `feed_rank_config` | 理由 |
|---|---|---|
| 权重 / 评论权重 / P95 / 曝光衰减 / 曝光窗口 / 两项配比 / 窗口大小 | ✅ | AC1 清单，发版后必然要调 |
| 荣誉加成 1.3 | ❌ | 唯一事实源是既有 `ContentTagQueryService.RANK_WEIGHT_MULTIPLIER`；存两份就会「改了一处没改另一处」 |
| 限流系数 0.2 | ❌ | 归 Epic 17 |
| 防扎堆四条阈值 | ❌ | AC1 清单里没有，且它是「节奏底线」：调松等于允许刷屏，调紧会让小池子频繁挑不出人 |
| 序列 TTL / 序列长度 / 候选池上界 | ❌ 留 yml | 改了要发版也无所谓的基建量；调错的表现是缓存失效或查询变慢，不是排序效果差。放后台只会多三个没人敢动的输入框 |

`FeedRankProperties` 因此从 5 个字段收窄到 3 个。

**5. 🔴 `ddl-auto=validate` 拦下一次类型不匹配**

迁移里写 `NUMERIC(5,3)`、实体是 `double` ⇒ Hibernate 期望 `float(53)` ⇒
**整个上下文启动失败**，5 条 L1 全 Error（耗时 0s）。
改成 `DOUBLE PRECISION`：打分权重不需要十进制精确存储，对齐 Java 类型比省几个字节重要。
⚠️ 迁移尚未合入 main（非冻结），就地改 + 本地删表删 history 行重跑；已在迁移注释里留了警告。

**6. 🔴 枚举加值不够 —— DB 那条 CHECK 白名单也得放开**

`config_change_logs.config_type` 在 V78 里有 `CHECK (... IN ('PRICING','PAWCOIN','TOPUP_TIER'))`。
只在 Java 枚举加 `FEED_RANK`，写日志时会撞约束 —— 表现是**「保存推荐算法参数报 500」**，
而错误栈指向 `config_change_logs`，很容易被误判成审计模块坏了。
⚠️ V78 已合入 main 属**冻结**迁移，另起一条替换约束（决策 E6），没有改 V78。

**7. AC2 的两条都守住了**

- 🛡 **没有新建「算法参数管理」后台模块** —— 挂在既有 `/admin/config` 页，
  复用它的 diff 审计（`ConfigChangeLog`）与哈希链审计（`AdminAuditService`）
- 🛡 **没有新增权限码** —— 复用本页既有 `config.view` / `config.edit`。

**8. ⚠️ 界面上有意省掉的一个输入框：P95**

它是定期重算的动态值。做成输入框只会让人以为「填个大点的数就能压住爆款」，
而下一次重算就把它冲掉了。页面上只**展示**当前值与上次重算时间，并写明重算失败会沿用旧值。

**9. 引擎接口变了一处：窗口大小不再是常量**

`FeedRankEngine.Input` 新增 `AttributeSchedule`（两个模板 + 窗口大小），

`RankParams.speciesQuotasConsistent()` 也从读常量改成接受 `window` 入参。
⚠️ 16-2 的 `FeedRankEngineTest` 用 `AttributeTemplate.defaultSchedule()`（字面量）——
所以它对生成器的改动**不敏感**，反证 I 时它保持绿；模板正确性由
`AttributeTemplateTest` + `AttributeScheduleGenerationTest` 两层守。这个分工是有意的。

**10. ⚠️ L1 用例改了共享库那一行单行配置，必须改回去**

`FeedRankConfigLiveIntegrationTest` 有 `@AfterEach` 还原种子值。

## 🔄 2026-08-26 变更：从「运营配置」搬到独立页「算法参数」，不对运营开放

> **产品决定。** 起因是 L2 视觉验收时发现这一块**从交付起就没渲染出来过**
> （写在了 `th:fragment="content"` 的闭合标签之外），修好之后顺势重新审视了它该放哪。

### 调研结论（这是决定的依据）

行业把「推荐相关的后台能力」分**两层**，边界很清楚：

| 层 | 内容 | 运营后台里 |
|---|---|---|
| **业务规则层** | 加权 / 降权 / 置顶 / 过滤 —— 作用在模型出结果**之后** | ✅ 标配 |
| **模型参数层** | 打分公式的权重与分位数 | ❌ 通常不开放 |

最有力的样本是 **Google Cloud Retail 的 serving controls**（这件事被产品化了，所以边界写进了文档）：
运营能用的是 boost / bury / filter / pin / redirect / synonym，而文档明确写着这些控制
「modify search behavior through filtering, ranking adjustments, and query transformation —
**not by adjusting the underlying machine learning model's parameters or weights**」。

对照本项目：顶置（置顶）、装饰标签 ×1.3（加权）、限流处置（降权）**都属于业务规则层**，
运营该有；而本 story 的权重与分位数属于模型参数层。

### 🔴 为什么本项目更不该开放：判不了对错

大厂敢开放模型参数，是因为背后有 **A/B 实验平台**兜底 —— 改了能立刻看到两组数据的差异。
学术侧也记着：权重调优「尚无最佳实践共识，靠实验估计需要大量、长周期的实验」。

而本平台**没有灰度分流基建**（已记为 B4：全量上线不加开关）。
也就是说这一页改完**没有任何机制能判定对错**，只能看整体指标漂移 ——
把它和运营日常配置摆在同一页，视觉上就是在暗示一种它并不具备的可控性。

### 实际改动

1. **独立成页** `/admin/algo-params`，标题「算法参数」，侧栏「运营」组内紧跟「运营配置」。
2. **独立权限码** `config.algo_param_view` / `config.algo_param_edit`，
   🛡 **与 `config.view` / `config.edit` 完全解耦** —— 运营拿不到就看不见这一页。
   ⚠️ 这**推翻了**本 story 原先的「复用既有码、不新增码」那条注释：
   当时的理由是「它本来就属于运营配置这件事」，而现在的结论恰恰是它**不属于**。
3. **限流系数一并搬过去**：它是同一个打分公式里的乘法因子、存同一张表。
   运营需要的是「对某条内容执行限流」那个动作（17-2 已独立成型、有自己的权限），
   而这个系数是**强度标定**，属算法参数。
4. **所有操作留日志，并摆在同一屏**：逐字段变更本就写进 `config_change_logs`（9.2 的 diff 审计），
   但埋在审计后台没人翻。本页直接展示最近 20 条（时间 WIB / 参数 / 改前 / 改后 / 操作人）。
   🔴 没有 A/B 时，这个时间戳是**唯一**能与埋点指标漂移对上的锚点。
5. **顺带修了一个既有缺陷**：这一块原先 29 行**一处翻译键都没有**，全硬编码中文
   —— 英文模式下也是中文，印尼语下更是整块突兀。重写时已全部提取，四语齐备。
