# Story 11.3: 用户标签配置与分配

Status: review

## Story

As a 运营，
I want 在后台建用户标签并分配给用户、设生效时间，
so that FR-74 的用户标签不再是个没有开关的空壳。

---

> App 侧 FR-74 已交付（Epic 5，story 5-1），表 `user_tags` / `user_tag_assignments` 已建（V109）。
> **后台没有任何页面能建标签、能分配** —— 现在线上用户标签恒为空。

---

## Acceptance Criteria

### AC1 — 标签增 / 改 / 下线（L1）

**Then** 标签字段：名称 + 图标 + **一句说明文案**（用户端点标签图标时展示）`[L1]`
**And** 支持**下线**：下线后不可再分配，**已分配的照旧生效到各自 `ends_at`** `[L1]`

> 🔴 与 11-2 同：`user_tags` 表**没有下线列**，需加列（本 Epic 两处迁移之一）。
> 下线不能用删除代替 —— `user_tag_assignments` 有 FK 指向标签。

### AC2 — 分配 / 取消（支持批量）/ 生效时间窗（L1）

**Then** 为任意用户分配或取消标签，**支持批量操作** `[L1]`
**And** 支持设生效开始/结束时间；**不设结束时间 = 永久分配** `[L1]`
**And** 🛡 生效判定**查询时**按 `[starts_at, ends_at)` 算 `[L0]`；🛡 **不建状态列、不建扫描器** `[L0]`
**And** 时间输入按 **WIB** 解释、入库转 UTC，**控件旁明示「WIB」** `[L1]`

### AC3 — 🔴 分配第 4 个及以上必须提示（L1）

**Given** 用户端**同时只展示 3 个**标签
**When** 为同一用户分配第 4 个及以上生效中的标签
**Then** 🛡 界面**必须明示**：「该用户当前生效标签已达 3 个展示上限，新分配的标签会顶掉最早分配的那个（记录保留但不展示）」`[L1]`

> 不提示的后果很具体：运营分配了标签、以为用户身上就能看见，实际被顶掉了 ——
> 他会以为是 bug，然后重复分配。
>
> **分配数量本身不设上限**，只是展示封顶 3 个。

### AC4 — 🛡 展示上限与排序由 App 侧权威，后台不另立一套（L0）

**Then** 🛡 后台**不得**自行实现"取哪 3 个"的排序 `[L0]`
**And** 口径以 App 侧既有实现为准：**最多 3 个、按分配时间倒序**（最近分配的优先展示）`[L0]`

> 服务端投影 `AuthorView.tags` 的注释已写明「最多 3 个，按分配时间倒序；注销作者恒为空表」。
> 后台再写一套排序，两处迟早分叉 —— 而分叉的表现是"后台显示会展示这三个，App 上却是另三个"。
> 后台需要预览"当前会展示哪 3 个"时，**调同一个查询**，不要复制逻辑。

### AC5 — 分配记录列表（L1）

**Then** 按用户 / 按标签**两种维度**查看当前生效的分配情况，支持按标签筛选 `[L1]`

### AC6 — 权限与导航（L0 / L1）

**Then** 🛡 **双权限码**：查看一个、编辑（建标签/分配/取消）一个 `[L0]`
**And** 🛡 **入口门与侧栏 `sec:authorize` 条件逐字一致** `[L0]`
**And** 🛡 改导航名**四处同源** `[L0]`

> ⚠️ 批量分配是"一次影响很多用户"的动作，**编辑权限不要下放得比其它模块更宽**。

### Completion Notes List

**与 11-1 / 11-2 同一形状的"接上来"**：用户标签的取数与展示上限早在 Story 5.1 就随
`UserTagQueryService` 落地了（四处展示位全经作者投影拿标签），本 story 接上后台入口，
并补上标签的增改下线、分配/取消、以及批量分配。

**迁移：`user_tags.retired_at`**（时间戳号）。与 11-2 同形状同理由：分配表有 FK 指向标签，
删不掉；用可空时间戳而非布尔，「什么时候下线的」也留档。
下线只挡新分配，**已分配的照旧生效到各自 `ends_at`**。

**🔴 展示上限与排序：后台一行排序代码都没写。**
「同时只展示 3 个、按分配时间倒序」的实现在 `UserTagQueryService.findVisibleTags`。
后台那一列「当前展示中 / 超出上限未展示」**直接调它、用它的答案**。
后台另外只问了一个不同的问题：「这个用户现在有几个标签在生效」（`countActive`）——
那是"第 4 个"提示的依据，与"会展示哪几个"不是同一件事。

**🔴 我给这条并存关系写的第一版测试是假绿的，第一轮证伪当场暴露。**
我造了 5 个生效标签，本意是让「插入顺序」与「分配时间顺序」相反，好让
「按时间倒序取 3」与「按 id 取前 3」给出不同答案。但我把时间写成了**递减**
（`wibInstant(10, 11 - i)`）—— 于是两种算法答案**恰好相同**，
把错的实现（后台自己按 id 排序取前 3）塞进去，测试照样通过。

改成时间**递增**插入后重新证伪：**当场报红**，报的正是那句
「后台说展示这三个、App 上却是另三个」。**这条测试现在真的有区分能力了。**
⚠️ 这也说明"造了 5 条数据"本身不等于"数据能区分对错" —— 得让正确与错误实现在这组数据上**必然分叉**。

**🔴 展示上限的后果写成了两处提示 + 测试。**
① 页头常驻说明：只展示 3 个、按分配时间倒序、**分配数量本身不设上限**、
   第 4 个及以上会顶掉最早的那个（**记录保留但不展示**）；
② 按用户筛选且该用户已达上限时，就地再提示一次。
测试断言页面同时出现「3」「顶掉」「记录保留」三处要点 ——
不提示的后果很具体：运营分配了标签、以为用户身上就能看见，实际被顶掉了，
他会以为是 bug，然后重复分配。

**批量分配的两个取舍**（AC2）：
- **逐个用户独立处理，单个失败不拖垮整批**，失败的 id 回显出来。
  批量最怕的是"一条不合法导致整批白做"，运营无从知道是哪条。
- **去重但保持顺序**：同一用户在表单里被贴两次不该分配两条记录。
- 用户 id 支持逗号/空格分隔，便于从名单直接粘贴；非数字整批拒绝并说明格式。
- 审计记录里带本批用户数 + id 列表 —— 批量是"一次影响很多人"的动作，事后要能追。

**导航另起「用户运营」分组**，没并进 11-1/11-2 的「内容运营」——
用户标签挂在人身上、不是内容，并进去会让分组名与内容不符；
而改「内容运营」这个名字要连带改四处（侧栏名/页内标题/页面说明/权限显示名），代价更大。

**权限**：`user.tag_view` / `user.tag_manage`。⚠️ 编辑权限在 story 里特别注明
**不要下放得比其它模块更宽** —— 本页的分配是批量的。

**留 L2 的**：浏览器上看两处提示条的观感、批量粘贴大名单的手感、`data-confirm` 弹窗。
