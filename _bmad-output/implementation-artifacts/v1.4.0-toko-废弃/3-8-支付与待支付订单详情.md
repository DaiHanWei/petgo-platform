## Dev Notes

### 三条支付路径，语义各不相同
| 拆分 | 做法 |
|---|---|
| 纯 PawCoin（现金段 0） | **不建支付意图**，站内即时扣 + 当场结清（与咨询/身份证同范式：没有真钱环节就没有网关意图） |
| 纯 QRIS | 建 QRIS 意图 → 网关下单 → 到账事件推进 |
| 混合 | 建 **MIXED** 意图（三列写入），网关只收**现金段**，Coin 段在到账时扣 |

🔴 **意图的 `amount` 是订单总额，网关收的是现金段** —— 两者不同不是笔误：
库级不变式要求 `coin + cash = amount`（3.3 建立），而混同会让用户被真收走本该用币抵掉的那部分。

### 🔴 「重复回调不重复扣库存」的守卫在 `fulfillPaid`，不在意图层
`fulfillPaid` 见到非 `PENDING_PAYMENT` 就返回。回调与轮询同时到达时，两者在同一行上争
`@Version` 乐观锁，后到者看到的已是 `PENDING_SHIPMENT` —— 一件库存也不会被扣第二次。

### 🔴 超时释放库存比意图过期重要得多
支付意图滞留 PENDING 只是脏数据；订单滞留 `PENDING_PAYMENT` 会**一直占着别人想买的货**。
用户可见的正确性靠**懒过期**（读详情/点支付时就地判定），扫描（1min）只是兜底 ——
用户会在窗口刚过的那一秒点「去支付」，等扫描就晚了。
🔴 释放库存与状态迁移**同一事务**：分开做的话中间崩一次就留下「已取消但库存还锁着」的幽灵占用，
而没有任何后续流程会来清理它。

### 🔴 客户端倒计时只是显示
归零时页面做的唯一动作是**重新拉详情**，而不是自己把状态改成已取消 ——
后者意味着改一下手机时间就能看到另一套现实，而库存是真的被锁着的。
时间戳解析统一 `toLocal()`：后端一律 UTC，直接与本地 `now` 相减会整整差一个时区。

### 未知订单状态降级到「不可操作」
既不给支付也不给取消。对一个不认识的状态做资金动作是最糟的选择。

### 取消要二次确认
库存会被释放且订单不可恢复，而「去支付」与「取消」两个按钮就挨着。

## 变异验证（硬纪律 1）
9 个变异，8 个按预期变红，**1 个暴露了假绿并已修**：

| # | 变异 | 结果 |
|---|---|---|
| B1 | `fulfillPaid` 去掉「已处理过」守卫 | ⚠️ **全绿 = 假绿**（见下），补测后变红 |
| B2 | 取消时不释放库存 | 🔴 3 条 |
| B4 | 支付时不记录 intent token | 🔴 5 条 |
| B5 | 去掉懒过期判定 | 🔴 2 条 |
| F1 | 归零时客户端自己改状态 | 🔴 归零重拉 |
| F2 | 未知状态也给支付按钮 | 🔴 2 条 |
| F3 | 取消不二次确认 | 🔴 确认弹窗 |
| F4 | 混合支付只显示总额 | 🔴 两段金额 |
| F5 | 时间戳不转本地时区 | 🔴 UTC 用例 |

### 🔴 B1 是本工作线第四次假绿（同一病根：纵深防御）
「重复回调不重复扣库存」那条用例即使**删掉 `fulfillPaid` 的状态守卫也照样全绿** ——
因为 `PaymentIntentService.applyCallback` 的「已终态即返回」把第二次拦在了更外层。
测试声称守的是 A，实际被 B 兜住了。
**补法**：新增 `fulfillPaidIsIdempotentOnItsOwn`，**绕过意图层直接连调两次** `fulfillPaid`，
断言库存只扣一次。补测后 B1 立刻变红（`库存锁定量或实际库存不足，无法出库`）。
