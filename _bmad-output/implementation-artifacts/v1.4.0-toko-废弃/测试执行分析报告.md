## 3 · 缺陷

### 3.1 🔴 新发现：DEFECT-2026-08-20-01

**退货窗口文案与实际规则相差 5 天。**

| 出处 | 说法 |
|---|---|
| 后端 `ShopOrder.RETURN_WINDOW` | `Duration.ofDays(7)` |
| 确认收货弹窗 `shopOrderConfirmReceiptBody` | `bisa ajukan retur sampai 7 hari` ✅ |
| **订单详情 `shopOrderHelpBody`**（`app_id.arb:1671`） | **`Pengembalian bisa diajukan 2×24 jam`** ❌ |
| 英文同一 key（`app_en.arb:2164`） | `within 2x24 hours` ❌ |

- **影响**：用户第 3 天想退货，看到「2×24 小时」会以为过期而放弃 —— 实际还有 4 天。
  同一 App 内两处自相矛盾，且错的方向对用户不利。
- **定级**：中高。不崩溃，但造成用户放弃合法权利，属"说了假话"。
- **修法**：两个 arb 的 `shopOrderHelpBody` 改为 7 天口径。
- **看守**：`EC-SMK-014` / `EC-SMK-013` 已**故意断言当前的错误文案**，修好后会变红提醒回来改用例。

### 3.2 回归确认：5 个旧缺陷修复有效

均来自 HANDOFF §10.3/§10.7，本轮在真机复验：

| 编号 | 原症状 | 实测 |
|---|---|---|
| REG-001 | 订单列表状态显示裸枚举 `SHIPPED` | ✅ 显示 `Dikirim` |
| REG-002 | 电商待支付卡一个按钮都没有 | ✅ `Bayar sekarang` 在场 |
| REG-003 | 支付按钮写订单总额而非现金段 | ✅ `Bayar Sekarang Rp 150.000` |
| REG-004 | 已发货详情把币算两遍 | ✅ `Dibayar 150.000` + `+50.000 PawCoin`，与 QRIS 块一致 |
| REG-007 | 次操作文案折行撑高底部条 | ✅ 单词 `Batalkan` |

### 3.3 一次误报（已纠正）

一度判定「列表显示 `Menunggu dikirim`、详情显示 `Sedang dikirim`，同一单两个状态」为缺陷。
重抓后列表是 `Dikirim`，映射与 l10n 均正确 —— **是抓取时机早于 provider 刷新**。
教训已写入 `EC-SMK-012`：列表断言前必须 `extendedWaitUntil` 等数据真刷新，不能 sleep 后直接 assert。

### 3.4 据实修正的用例预期

`EC-SMK-013`：确认收货后订单转 **`COMPLETED`** 而非原写的 `DELIVERED`。
`confirmReceipt` 的设计是「用户在已发货态就能确认，不必等系统标记送达」，
`delivered_at` 同时落库，退货窗口照常有起点。**是用例写错，不是实现错。**

## 5 · 过程中暴露的方法论问题：4 个「假绿」

**全部是自己写的用例在骗自己**，且都通过变异验证才暴露：

| # | 现象 | 根因 |
|---|---|---|
| 1 | flow 全绿，深链其实没生效 | `launchApp`+`openLink` 走热启动分支，深链被吞；而上一条 flow 恰好把 App 留在了 Toko 页 ⇒ **断言测的是残留状态**。改 `stopApp`+`openLink` |
| 2 | 加购全绿，购物车却是空的 | 断言写 `visible: "1"` —— 「1」在价格 `185.000` 里就能匹配到，**恒真** |
| 3 | 加购点了没反应却不报错 | 选完规格后按钮从 DISABLED 转可用有延迟，抢跑点在禁用按钮上。**Maestro 不报错**，因为点击动作本身成功了 |
| 4 | 三条 flow 报 ✅，实际根本没跑起来 | 批量脚本用 `grep -q "FAILED"` 判定，而 YAML 语法错输出的是 `Parsing Failed`（大小写不同）。**改用退出码判定** |

**共同教训：断言必须落在「被测行为的唯一可靠信号」上。**
加购的信号不是页面上出现某个数字，而是购物车里真的多了那一行；
flow 是否通过的信号不是输出里有没有某个词，而是退出码。

> 这与本工作线此前记录的 3 次假绿同源（护栏的判定方式与它声称看守的对象对不上）。
> 判断一条护栏是否真的有效，方法只有一个：**删掉被守护的那行，看它变不变红。**

## 6 · 环境稳定性：本轮的最大时间成本

| 问题 | 表现 | 处置 |
|---|---|---|
| **网段漂移** | 本机与手机从 `192.168.1.x` 漂到 `192.168.100.x`，包里写死的 baseUrl 指向黑洞。症状是 **GET 全正常、POST 加购 `receiveTimeout` 30 秒** | 改用 **`adb reverse` 走 USB**，与 WiFi/DHCP 无关，且更快（28ms） |
| **后端反复被杀** | 三次 `Graceful shutdown`。前台后台任务、`nohup+disown`、`start_new_session`（PPID=1）均挡不住 | 最终由**人在独立终端启动** |
| **集成测试破坏演示数据** | 跑一次 `mvn test`：`Produk` 测试商品 934→1614、**demo 商品全部 `is_active=false`**、`max_coin_per_order` 从 5 万重置回 100 万 | `run_chain.sh` 前置**自愈**：强制上架 demo + 复位 PawCoin |
| **App 包被覆盖** | 手机上被装了 `1.1.4-stag`（无电商），顶掉了 v2 debug 包 | 备份 stag 包后换回；打包后必须验 `kernel_blob` |
| **USB 掉线两次** | `adb devices` 空 | 人工插线 |

🔴 **一个连锁故障值得记录**：集成测试把 `max_coin_per_order` 重置为 100 万后，
整单被币付掉（`coin=200000/cash=0`）→ 没有现金段 → 下单即 `PENDING_SHIPMENT` →
`Bayar Sekarang Rp 150.000` 不存在 → 下单 flow 失败 → 支付脚本报「创建支付意图失败」。
**三个互不相干的症状同一个根因**，排查方向极易被带偏。

## 7 · 结论与建议

### 7.1 结论

1. **主链路功能正确**：金额、状态机、币段时序、归因、运费归属，实测全部符合设计口径。
2. **五个已知缺陷确认已修**，修复有效。
3. **新发现一个中高缺陷**（退货窗口文案），影响用户行使退货权利，建议发布前修掉——改两个 arb 值即可。
4. 🔴 **不构成放行结论**：真机执行率 3.5%，P0 95 条中只覆盖了约 11 条。

### 7.2 建议的下一步优先级

### 7.3 给管理者的一句话

**这两天真正的产出不是"跑绿了 14 步"，而是建立了一条可重复、抗环境漂移、且经过变异验证的自动化链路，

### 13.2 🔴 新缺陷 DEFECT-2026-08-21-03（低）：退货超窗的拒绝文案**归因错误**

送达 8 天后申请退货，接口拒绝**行为正确**，但文案是：

> 409「当前订单状态不可申请该类型的退货：**COMPLETED**」

**而 `COMPLETED` 恰恰是允许退货的状态之一。** 根因在 `ReturnRequestService.requireReturnable()`：

```java
case QUALITY_ISSUE, NON_QUALITY_ISSUE ->
        (s == DELIVERED || s == COMPLETED) && order.isWithinReturnWindow(Instant.now());
...
throw AppException.conflict("当前订单状态不可申请该类型的退货：" + s);
```

**两个条件合成一个布尔，抛错却只报其中一个。** 修法很轻：拆开两个判断，各给各的文案。

- **影响**：主路径上 App 读 `return-eligibility`（实测 `eligible=false` 且窗口值正确），按钮多半不出现，
  用户不常撞上。但**窗口在用户停留退货页时到期**、或直连接口时会看到这句错话。
- **更大的代价在排障**：工单/日志上写着「状态不可申请：COMPLETED」，
  会把查的人直接引向状态机 —— 而真正的原因是时间窗。
  这与 §6「三个互不相干的症状同一个根因」、§8.3「症状指向 UI，根因在数据」是同一类损耗：
  **错误信息把人送错方向的成本，远高于它自身的修复成本。**
- **看守**：`EC-RET-011` 本轮判**失败**（拒绝对、提示不明确，用例判据两条只满足一条）。

### 14.1 🔴🔴 新缺陷 DEFECT-2026-08-21-04（**高**）：评价原文明文进应用日志

提交一条含 PII 的评价（`"Hubungi saya 081234567890, Jl. Melati No.7 Jakarta"`），
在 `petgo-backend/logs/petgo.log` 里原样搜到 **2 处**（`req=` 与 `resp=` 各一）：

```
api method=POST path=/api/v1/me/shop-reviews status=201 durMs=3 sub=1 role=USER
  req={"orderToken":"…","orderLineId":2490,"rating":5,
       "content":"Hubungi saya 081234567890, Jl. Melati No.7 Jakarta"}
  resp={"id":252,…,"content":"Hubungi saya 081234567890, Jl. Melati No.7 Jakarta",…}
```

**违反两条硬性要求：**
- CLAUDE.md 护栏：「日志 SLF4J + logback JSON，**严禁记录 PII / 健康数据 / 令牌 / 签名 URL**」
- `EC-REV-011` 判据：🔴「**日志与埋点里绝不出现评价原文**」

**根因**：`ApiAccessLoggingFilter` 记录全部 `/api/**` 的 req/resp body，
由 `LogSanitizer` **按字段名**打码。清单里有 `password/token/email/phone/googlesub/
symptomtext/symptom/diagnosis/receivername/receiverphone/addressline/kodepos` ——
**唯独没有自由文本字段**。而 PII 恰恰最常出现在自由文本里。

**对照证明脱敏器本身是好的**（同一份日志，地址接口）：

```
req={"receiverName":"***","receiverPhone":"***", … ,"addressLine":"***","kodePos":"***"}
```

⇒ 不是脱敏器坏了，是**按字段名的白名单机制天然覆盖不到自由文本**。

**为什么定高：**
1. `ApiAccessLoggingFilter` 是裸 `@Component`，**无 `@Profile` / 无开关 —— 生产同样生效**。
2. 日志保留 14 天 / 2GB，生产还会挂盘持久化。
3. 印尼电商场景里，用户在评价里留 WhatsApp 号是**常态**而非例外。
4. `resp=` 也回写了一份 —— 只修请求侧仍会泄露。
5. **同类风险未实测但机制相同**：退货 `reasonNote`、其它用户自填长文本字段同样不在清单里。

**建议修法**（择一或并用）：把 `content` / `reasonnote` 等自由文本字段加入 `SENSITIVE_KEYS`；
或对 body 记录改为**白名单字段**而非黑名单打码；或对评价类端点整体不记 body。
🔴 **修完必须做变异验证**：再提交一条带手机号的评价，`grep` 日志必须 0 命中。

**看守**：`EC-REV-011` 本轮判**失败**。

### 15.3 🔴 新缺陷 DEFECT-2026-08-21-05（中）：客户端错误被归类为 500

| 触发 | 实际 | 应为 |
|---|---|---|
| `GET /api/v1/me/shop-orders`（该路径只有 POST 映射） | **500** | 405 |
| `GET /api/v1/orders?cursor=%%zzz!!`（百分号编码非法） | **500** | 400 |

- **响应体本身是合规的**（只有 detail + traceId，不外泄堆栈 —— `EC-API-002` 因此顺带通过），

- **代价在监控**：405/400 是客户端错误，500 是服务端故障。任何扫描器、旧客户端或手误
  都会把这些计入 5xx —— **误触发告警、污染错误率 SLO**。
- **看守**：`EC-ORD-015` 判失败（「不泄漏内部结构」满足，「不 500」不满足）。
- 其余乱码游标处理得当：订单中心 422「游标非法」，通知 / PawCoin 按首页 200 —— 两种都在用例允许范围内。

### 20.2 连锁故障的四层症状 → 一个根因

| 观察顺序 | 症状 | 当时的判断 |
|---|---|---|
| ① | 结算页深链**永久转圈** 30 秒 | 以为是 auth 冷启动竞态（购物车页那个已知坑） |
| ② | 改走「购物车 → 点 Checkout」后，`tapOn: "Checkout"` 找不到按钮 | 以为是等标题不等行内容（§10.4 记过的坑） |
| ③ | 改等行内容后，**购物车行也渲染不出来** | 才去查登录态，发现 App 变成**游客** |
| ④ | 用登录 flow 恢复，**登录 flow 自己也失败**（连商品详情都空） | 查 `adb reverse --list` —— **空的** |

**根因：`adb reverse` 在模拟器重连时掉了**，App 完全打不通后端。
四层症状没有一层指向它：转圈、按钮找不到、行渲染不出、登录失败 —— 全是下游表现。

> 与 §6 的连锁故障、§8.3「症状指向 UI、根因在数据」同型。
> **通则：App 侧出现「页面空/卡住/元素找不到」时，第一件事查 `adb reverse --list`，
> 而不是改断言。** curl 从主机能通**不代表** App 能通 —— 这两条路径根本不共用转发。

### 20.3 另外两条环境教训

**① 模拟器从快照恢复会丢登录态。** 本轮模拟器被停了三次，每次 `default_boot` 快照恢复后 App 都回到游客态。
而「未登录」不会明说，只表现为**页面空**。换设备/重启模拟器后，**第一件事是验登录态**，
`EC-TOKO-004`（游客加购引导）退出码为 **1** 恰好可以当"已登录"的探针 —— 它断言的是游客弹窗。

**② 分支在测试中途被切走。** 从 `shawn/oneline-ecommerce` → `stag` → 切回 → 又被切到 `stag`。
带来三重连锁：`stag-guard.py` 按**库名**拦截（本地开发库恰好也叫 `petgo`，与远端生产同名）→ 所有 DB 核对被拦；
stag 的迁移改成时间戳制 → 与本地库已应用的旧号段 checksum 不符 → Flyway 校验失败；
切回后 `target/classes` 残留两个分支的迁移并集（160 个文件 vs 源码 124，**两个 V101**）→ 报「撞号」。
**`mvn clean` 是切分支后跑服务的必要步骤**，否则 Flyway 看到的是两个分支的并集。
