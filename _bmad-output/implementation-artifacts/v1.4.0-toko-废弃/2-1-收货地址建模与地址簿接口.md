## Dev Notes

### 🔴 三处刻意的设计选择

**① 越权返 404 靠「查询形状」而非「查完再判断」。**
仓储方法是 `findByPublicTokenAndUserId`（双条件），让「不是你的」和「不存在」在代码路径上**就是同一件事**。
写成「先按 token 查、查到再比 userId」很自然，但那样几乎必然写出 403 —— 而 403 等于告诉攻击者**这个 token 存在**。
已变异验证：改成后者 → 越权测试正确变红。

**② 一个用户至多一个默认，靠 DB 部分唯一索引而非应用层「先清后设」。**
`CREATE UNIQUE INDEX ... ON (user_id) WHERE is_default`。应用层清+设在并发下会出现两个默认，
而**默认地址错了 = 货寄错地方**。代价是切换默认时要显式 `saveAndFlush` 分两步，已在代码注释说明。

**③ FK 保持 `NO ACTION`，不写 CASCADE。**
OQ-41 待 Legal 拍板。现在写 CASCADE 等于替 Legal 做决定，**且删了就找不回来**；
保持默认将来无论拍成哪种都只是一条 ALTER。

### 🔴 手机号下限 9 位（不是 PRD 原文的 8 位）
8 位会放进大量无效号码，而**无效号 = 快递员联系不上 = 真实履约失败** ——
这个错的代价由平台承担（自营），且发生在最贵的环节（货已发出）。放宽这一位省下的注册摩擦远抵不上一单履约失败。
应用层 + DB CHECK 双层看住。

### ⏳ 新增依赖：Kecamatan → 邮编 对照表
AC 要求「邮编与所选 Kecamatan 做一致性校验，警告不阻断」，但**仓库里没有任何印尼行政区划参照数据**。
🔴 **没有数据就实现不了这条校验** —— 硬编几个样例等于假装做了。
**本 Story 未实现该校验**，机制位置已留（响应可加 `warnings` 数组）。
👉 **需运营提供 Jabodetabek 范围的 Kecamatan → 邮编 对照表**（与 Story 2.2 的服务范围配置是同一份基础数据，建议一并要）。
