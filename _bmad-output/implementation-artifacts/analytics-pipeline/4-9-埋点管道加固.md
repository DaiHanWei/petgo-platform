## Story

As a 后端负责人,
I want 埋点管道在写库线程意外终止、埋点库卡住、配置写错时都能被发现，且不拖垮主业务,
so that 埋点出问题不会静默丢数据，也不会让后端起不来或让 App 请求挂住。

## 背景（2026-11-13 代码核实，行号以当时为准）

1. **写库线程会静默死掉**：`analytics/ingest/IngestFlusher.java` 用 `SmartLifecycle` 起一个原生线程 `analytics-ingest-flusher`。
   - `loop()`（约 :190-206）和 `write()`（约 :225）都只 `catch (RuntimeException)`，遇到 `Error`（OOM 等）线程就直接终止。
   - `start()` 有 `worker != null` 守卫，不会重启；没有任何地方检查线程是否还活着。
   - 线程死后，`AnalyticsBatchController` 照常入队、返回 202，直到 64 MB 满了才返回 429，期间无告警；停机时队列也排不空。
2. **请求线程上的埋点库查询没有超时**：
   - `AnalyticsBatchController.batch()` 约 :184 调 `identity.resolve(...)`，会进到 `IdentityLinkRepository.findUserId`（约 :36），在 HTTP 请求线程上同步 `jdbc.query`。
   - `analyticsJdbcTemplate`（`AnalyticsDataSourceConfig.java` 约 :137-141）没设 queryTimeout，URL 也没有 `socketTimeout`；唯一的兜底是角色级 `statement_timeout=120s`。
   - 后果：埋点库卡住或网络假死时，请求线程可能挂 120 秒乃至一直挂住。
3. **4.1 的汇总配置写错会让整个后端起不来**：
   - `analytics/rollup/AnalyticsRollupProperties.java` 约 :31-40 的紧凑构造器抛 `IllegalArgumentException`；`boolean` / `int` 字段写错时，类型绑定也会失败。
   - `RollupJob` 的 `@Scheduled(cron = "${analytics.rollup.cron:...}")` 遇到非法 cron 也会让启动失败（推断，未实测）。
   - 1.10 的 `analytics/config/AnalyticsStorageProperties.java` 约 :30-38 是同类问题。
   - 4-2 复审 R1 已指出这个问题，但没有修。这违背 architecture D-12「埋点库 / 配置出问题时后端照常启动，只停用埋点」。

## Acceptance Criteria

> L0 = 编译 / 单测（可用 `ApplicationContextRunner`）；L1 = 本地 postgres + redis 真跑。

**A. 写库线程存活**

1. **Given** flusher 循环内抛出任意 `Throwable`（含 `Error`）**Then** 线程不退出：打 ERROR 日志（只记异常类名和消息，不含事件内容）；经 `OpsAlertService.send(OpsChannel.TECH, …)` 告警，按 UTC 日去重，键 `analytics-ingest-flusher-error:<yyyy-MM-dd>`；退避 1 秒后继续下一轮〔L0〕
   - 告警调用在事务外，外层 `catch RuntimeException`，照抄 `IngestFlusher` 现有 `ALERT_WRITE_FAILED` 的写法。
   - 当前这批的处理同 `RuntimeException` 分支（计入 `droppedCount`），不重试，避免同一批反复触发 OOM。
2. **And** flusher 暴露 `lastProgressAt`：每次 drain 返回（不管有没有数据）都更新。新增看门狗 `IngestFlusherWatchdog`，用 `@Scheduled(fixedDelayString = "${analytics.ingest.watchdog-interval:60s}")`，写法参照 `IngestCircuitBreaker`〔L0〕
   - 线程不在了（`!isRunning()`，且不是停机过程中）→ 重启线程（`IngestFlusher` 提供 `restartIfDead()`，内部同步），并发 TECH 告警，键 `analytics-ingest-flusher-restarted:<日>`。
   - 线程还在但 `lastProgressAt` 超过 `analytics.ingest.stall-threshold`（默认 `5m`）未更新 → TECH 告警，键 `analytics-ingest-flusher-stalled:<日>`，不重启。
   - 管道停用（`AnalyticsPipelineState` 未启用）时看门狗跳过。
3. **And** `/actuator/health` 行为不变：埋点问题不影响业务健康判定（`dbHealthContributor` 只看业务库，这是有意的设计）〔L0〕

**B. 请求线程查询超时**

4. **Given** 请求线程上的埋点库查询（目前只有 `IdentityLinkRepository.findUserId`，实现时 grep 确认没有其他）**Then** 使用一个单独的 `JdbcTemplate`〔L0〕
   - 新 bean `analyticsRequestJdbcTemplate`，`@Qualifier("analyticsRequest")`，同一个 `analyticsDataSource`。
   - `setQueryTimeout` 取 `analytics.datasource.request-query-timeout`，默认 `2s`，env 占位 `ANALYTICS_REQUEST_QUERY_TIMEOUT`。
   - 超时异常走现有的「查不到」分支：剥离身份并标记，不返回 500。
5. **And** 后台 job 和 flusher 继续用原来的 `analyticsJdbcTemplate`，不加 queryTimeout。汇总和擦除会 `SET LOCAL statement_timeout` 放宽到 10 分钟和 30 分钟，加客户端超时会把它们误杀〔L0〕
6. **And** 拿连接的等待时间不变（`connection-timeout: 5000`）；在 Dev Notes 里写明请求线程最坏要等「5s 拿连接 + 2s 查询」〔L0〕
7. **And** 有一条 L1 测试：用 `pg_sleep` 模拟慢查询（或用测试专用 SQL 钩子），请求在大约 2 秒内返回 202，事件被标记为身份未验证〔L1〕

**C. 配置非法不阻断启动**

8. **Given** `AnalyticsRollupProperties` 改成 4-2 的 `Ga4SnapshotProperties` 写法〔L0〕
   - final 类加 `@ConstructorBinding`，字段全部按 String 接收、自己解析。
   - 非法时 `enabled=false`，`invalidReason` 只含键名、不含值；打 WARN `analytics rollup disabled: invalid config ({})`。
   - `ApplicationReadyEvent` 时补发 TECH 告警「【埋点配置非法】…」，外层 `catch RuntimeException`。
   - `RollupJob` / `RollupRerunJob` 遇到非法配置直接跳过。
9. **And** 汇总 cron 改成 `SchedulingConfigurer` 编程式注册：先用 `CronExpression.isValidExpression` 校验，非法时不注册任务，并按第 8 条停用汇总、告警。不能再用 `@Scheduled(cron = "${…}")` 直接绑定可配置的 cron〔L0〕
10. **And** `AnalyticsStorageProperties`（1.10）按同一写法改。非法时存储水位告警和熔断只停用「按水位停收」，接收照常；打 WARN 并告警〔L0〕
11. **And** 盘点 `com.tailtopia.analytics` 下所有 `@ConfigurationProperties` 和带占位的 `@Scheduled(cron/fixedDelayString)`，结果列在 Completion Notes 的表里（类 / 键 / 非法时的行为）。凡是会让启动失败的，都按第 8 条改〔L0〕
12. **And** 每个被改的类加一条 `ApplicationContextRunner` 测试：给非法值（非法格式、负数、`flase`、非法 cron）→ 上下文能正常启动，对应功能为停用，其余埋点 bean 正常〔L0〕

**通用**

13. 不新增迁移、MQ 或缓存；日志不记 PII 和事件内容；新配置键都加 env 占位，并同步到 `.env.example` 和 runbook 的配置表〔L0〕
14. `mvn -B clean package` 全绿；现有 analytics 测试不回归〔L0〕

## Dev Notes

- 告警可以参照的先例：`IngestFlusher` 的 `ALERT_WRITE_FAILED`、`AnalyticsBootstrap.fail()`、`Ga4DailySnapshotJob` 约 :130-145 的就绪告警、`PushFamily` 约 :98-112。
- `OpsAlertService.send` 在有活动事务时只挂 afterCommit。看门狗和 flusher 的告警必须在事务外调用（见 4-1 story「告警与事务的坑」）。
- 全局调度池有 4 个线程（application.yml `spring.task.scheduling`）。看门狗只做内存检查，不碰库，不占连接。
- 埋点连接池 `maximum-pool-size` 默认 3，本 story 不改。
- 不改 `AnalyticsPipelineState` 的 Reason 枚举：写库线程问题靠重启和告警处理，不把整条管道停用。
- 遵守本线 `cloud-rules.md`：提交前缀 `feat(analytics-pipeline)`，不整文件 `dart format`（本 story 不涉及 App）。
