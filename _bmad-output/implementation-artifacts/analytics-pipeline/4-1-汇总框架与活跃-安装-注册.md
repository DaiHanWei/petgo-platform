# Story 4.1: 汇总框架与活跃、安装、注册

Status: ready-for-dev

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。批次 ②。 -->

## Story

作为运营和市场，
我想要每天早上查到前一天的日活、安装数和注册数，
以便不用等人手工拉数。

## Acceptance Criteria

本 story 只改后端，没有前端段。L0 = 编译 / 单测；L1 = 本地 postgres + redis 真跑（埋点测试库 `petgo_analytics_test`）；L2 = stag / 生产实测。云端只跑 L0。

**Epic 4 通用规则（本 story 及后续 4.x 全部适用，验收时逐条核对）**

- 只算生产数据且 `is_suspicious=false`；用户维度只算 `role = 'USER'` 且 `account_type = 'REAL'`。
- 按「人」去重：带用户标识的事件归该用户；匿名事件按关联表归属（事件前有关联 → 最近一次；之前没有、之后有 → 第一个；从未关联 → 匿名 id）。
- WIB 自然日；周 = 周一至周日；月 = WIB 自然月。
- 每日去重人数不跨天相加：凡「统计周期内去重人数」的指标，同时写日表、周表、月表（周期结束次日计算并回补）；比率类月指标（取每日比率平均）由日表现算。
- Toko 已付款 = `shop_orders.paid_at IS NOT NULL`，按 `paid_at` 的 WIB 日期；退款 / 取消仍算。业务库关联一律用 public token，读业务库只做窄查询，不做跨库 SQL。
- 汇总表不含 `user_id`、匿名 id 等可识别个人的字段；每张新表在迁移里授权给 `analytics_reader`。

**验收标准（原样取自 epics.md Story 4.1）**

1. **Given** 迁移建 `agg_progress`、`agg_daily_activity`、`agg_daily_install` **When** `RollupJob` 在 WIB 03:00 运行（advisory lock，晚于 `ErasureJob`，任务内放宽 `statement_timeout`）**Then** 按各指标族的 `agg_progress` 续算，每次重算最近 3 个 WIB 日（upsert，幂等）〔L1〕
2. 汇总 SQL 放在 `resources/analytics/rollup/<指标族>.sql`，日期作为参数传入〔L0〕
3. 写数据和推进 `agg_progress` 在同一事务；失败经 TECH 渠道告警，下次运行自动补上缺的日期〔L1〕
4. 提供按日期区间手动重跑的入口（只限明细层保留期内）〔L1〕
5. 身份归属规则抽成一个共用的 SQL 视图或函数，供所有指标族复用〔L1〕
6. `agg_daily_activity`：自建日活（含游客，按人）、登录用户日活，分平台〔L1〕
7. `agg_daily_install`：首次 `Application Installed` 的新装数（不含升级，分平台）、首次 `signup_succeeded` 的注册数（S2、S3）〔L1〕
8. 构造数据集测试：跨午夜事件归 WIB 日；「安装（未登录）→ 注册 → 次日打开」算同一个人；登出后的事件归上一个账号；非生产、可疑、兽医账号被排除〔L1〕

### 归属视图 `v_events_person`（架构 D-10，所有指标族共用）

```sql
CREATE VIEW v_events_person AS
SELECT d.*,
       COALESCE(d.user_id, prev.user_id, nxt.user_id) AS person_user_id,
       CASE WHEN COALESCE(d.user_id, prev.user_id, nxt.user_id) IS NOT NULL
            THEN 'u:' || COALESCE(d.user_id, prev.user_id, nxt.user_id)
            ELSE 'a:' || d.anonymous_id::text
       END AS person_key
FROM events_detail d
LEFT JOIN LATERAL (            -- ① 事件之前有关联 → 最近一次（含登出之后的事件）
    SELECT l.user_id FROM identity_links l
    WHERE d.user_id IS NULL AND l.anonymous_id = d.anonymous_id AND l.linked_at <= d.event_time
    ORDER BY l.linked_at DESC LIMIT 1) prev ON true
LEFT JOIN LATERAL (            -- ② 之前没有、之后有 → 第一个
    SELECT l.user_id FROM identity_links l
    WHERE d.user_id IS NULL AND l.anonymous_id = d.anonymous_id AND l.linked_at > d.event_time
    ORDER BY l.linked_at ASC LIMIT 1) nxt ON true;
-- ③ 从未关联 → person_key = 'a:' || anonymous_id
```

- `d.user_id` 非空（已通过 1.5 校验）直接归该用户；`identity_unverified` 的事件 1.5 已去掉用户标识，自然走匿名分支。
- 比较用 `event_time`（校正后）。`linked_at` 的含义（服务端收到时刻还是 `user_identified` 事件时刻）由 1.5 定，核对后在视图注释写明。
- 注销擦除后关联行被删、`user_id` 置空，事件自动变成匿名 id 这个「人」，与架构 A10 一致。
- 汇总 SQL 一律 `WHERE event_date = :stat_date`（或区间）过滤，PG 会把条件下推进视图、只扫对应分区；**绝不**用 `date(event_time)` 或 `received_at` 定日（架构「反例」）。
- `person_key` 只在 SQL 中间结果里用，**不写进任何 `agg_*` 表**（通用规则）。

### 排除用户（通用规则「只算 USER + REAL」）

- 1.6 已把「非 USER / 非 REAL 用户自己的事件」标为非生产，但**匿名事件按关联表归到兽医 / 官方号时**，明细层的生产标记管不到，必须在汇总时再排除一次。
- 做法：每次运行开始，用业务库 `JdbcTemplate`（`@Primary`）执行窄查询 `SELECT id FROM users WHERE role <> 'USER' OR account_type <> 'REAL'`（`ck_users_role`：USER / VET / ADMIN，见 `db/migration/V2__init_auth.sql`；`ck_users_account_type`：REAL / VIRTUAL，见 `V82__alter_users_account_type.sql`），缓存在本次运行的 `RollupContext`。
- 每个单元事务里 `CREATE TEMP TABLE tmp_excluded_users (user_id bigint PRIMARY KEY) ON COMMIT DROP` 并批量插入，SQL 里 `LEFT JOIN tmp_excluded_users x ON x.user_id = p.person_user_id … WHERE x.user_id IS NULL`。这不是跨库 SQL：数据经 Java 中转。
- 核实 1.1 的 `create-analytics-db.sql` 没有 `REVOKE TEMP … FROM PUBLIC`；若有，给写入账号补 `GRANT TEMP`，在 Completion Notes 记录。

### 指标族 SQL 口径

公共过滤（下称「标准过滤」）：`event_date = :stat_date AND is_production AND NOT is_suspicious AND source = 'APP' AND 排除用户`。H5 访客（`source = 'H5'`）不是 App 设备，不算日活（架构「技术约束」）。

- `activity.sql`
  - `dau_person`：标准过滤 + `event = 'Application Opened'`，`count(DISTINCT person_key)`。
  - `dau_logged_in`：同上，但只数事件发生时就已登录的，即 `d.user_id IS NOT NULL`，`count(DISTINCT user_id)`（不走关联表推断）。
  - 分平台：按明细层 `platform` 分组各一行，另写一行 `platform = 'all'`（总数单独去重，**不是**各平台相加——同一人两端都用会各算一次）。
- `install.sql`
  - `new_installs`：在 `[:lookback_start, :stat_date]` 区间内取 `Application Installed` 事件，按 `person_key` 求最早 `event_date`，最早日 = `:stat_date` 的人计入；平台取该人当天最早一条安装事件的 `platform`。`lookback_start = stat_date − install-lookback-days`。`Application Updated` 不计（升级不算新装，FR-3）。
  - `signups`：同样方法，事件换成 `signup_succeeded`（唯一上报入口见 `petgo_app/lib/core/analytics/analytics.dart` 约 255 行）。
  - 分平台同上，含 `all` 行。
- 写入方式：同一事务内 `DELETE FROM agg_daily_x WHERE stat_date = :stat_date` 后 `INSERT`（某平台某天可能从有到无，单纯 `ON CONFLICT DO UPDATE` 删不掉旧行）；或用 `INSERT … ON CONFLICT DO UPDATE` 并清零缺失平台。两种都满足「upsert、幂等」，选前者更简单。

**已知偏差（写进口径条目）**：卸载重装生成新匿名 id，算新装；「首次」只能在明细层保留期（约 3 个月）内判断，更早装过、换了设备的同一用户会再算一次新装；员工与测试账号按正常用户算；晚到超过 3 天的事件进明细但不回算（架构 D-6）；V1.5.0 之前无数据。

### 告警与事务的坑

`OpsAlertService.send` 在「有活动事务同步」时只挂 `afterCommit`。埋点库事务回滚时这个回调**不会触发**，告警就丢了。**一定在单元事务结束（回滚）之后**、在事务外调用告警。去重键用 `analytics-rollup:<family>:<date>`，同一天同一失败只发一次（`ops_alert_log` 在业务库，见 `admin/alert/OpsAlertService`）。告警文案只写指标族、日期、异常类名，不写事件内容或用户标识。

### 资源与护栏

- 埋点连接池只有 3 条（架构 A8：接收 1 + `DetailBuilder` 1 + 定时任务 1）。汇总按「指标族 × 日」一个短事务串行执行，不开并发，不在事务里做业务库查询或网络调用。
- 写入账号默认 `statement_timeout=120s`，单元事务首句 `SET LOCAL statement_timeout = '600s'`（取配置）。
- 不用 JPA 映射埋点表；不引入任何新依赖、中间件或扩展；异步只用 `@Async`。
- 日志只打指标族、日期、行数、耗时，不打任何事件内容和用户标识。
- SQL 文件里禁止 `now()` / `CURRENT_DATE`，日期全部由 Java 传参（架构「处理规则」）。

  - 匿名 id A：D 日未登录 `Application Installed` → D 日晚 `user_identified`（关联 A→U1）+ `signup_succeeded`（user U1）→ D+1 日 `Application Opened`（user U1）。断言 D 日新装 1、注册 1、D 与 D+1 的 `dau_person` 都是 1 且是同一人（D+1 再查新装为 0）。
  - 登出后：关联 A→U1 之后，A 的匿名 `Application Opened` 归 U1（与 U1 自己的事件合并去重）。
  - 排除：`is_production=false`、`is_suspicious=true`、user 为 VET、user 为 VIRTUAL、匿名事件经关联归到 VET——都不计入。
  - 幂等：同一日期跑两次，表内容不变；中途抛异常（如 SQL 故意失败）后 `agg_progress` 不推进，下一次补上。
