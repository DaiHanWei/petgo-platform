# Story 2.5: 环境与生产标记

Status: ready-for-dev

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为数据使用者，
我想要每条事件带足以判定「是否生产数据」的上下文，
以便模拟器、TestFlight、侧载的数据不混进统计。

## Acceptance Criteria

本 story **只改 App，没有后端段**。L1 依赖 Epic 1（含 Story 1.6 明细层解析生产标记）已部署到 stag。L0 = `flutter analyze` / `flutter test`；L1 = Android 模拟器装 profile 或 release 包连 stag（debug 包不上报），查 stag 埋点库；L2 = TestFlight 真包。

1. **〔L0〕环境字段**：新增 `production_flags.dart`。每条事件的上下文带 App 版本、构建号、平台、系统版本、机型。
2. **〔L0〕判定规则**：`isPhysicalDevice=false` 标模拟器；iOS `installerStore` 为 `com.apple.testflight` 标 TestFlight、`com.apple.simulator` 标模拟器、null 算生产；Android 只有 `com.android.vending` 算商店，其余（含 null）标侧载。
3. **〔L0〕缓存与单测**：标记在启动时算一次并缓存，单测覆盖每种组合。
4. **〔L1〕stag 隔离**：stag 包（`PETGO_API_BASE_URL` 指向 stag）的事件只发往 stag 后端，生产埋点库查不到（FR-6）。
5. **〔L1〕模拟器标非生产**：模拟器事件在 stag 明细层被标为非生产。
6. **〔L2〕TestFlight 实测**：TestFlight 包的 `installerStore` 实测为 `com.apple.testflight`，结果记进 Completion Notes；不符合时记为已知偏差。

> **AC2 补充（已核实插件源码）**：`package_info_plus 8.3.1` 在 iOS 上**不会返回 null**：模拟器返回 `com.apple.simulator`、TestFlight（沙盒收据）返回 `com.apple.testflight`、其余（App Store 安装）返回 **`com.apple`**。所以 iOS 的「算生产」实际对应 `com.apple`；null 仍按生产处理以兼容插件行为变化。见 Dev Notes。

## Tasks / Subtasks

    1. `isPhysicalDevice == false` → `simulator`（两端都先判这一条）；

## Dev Notes

### 前置

Story 2.1（sink、信封、`context` 占位）已完成。2.4 的 `_currentScreen` 若已存在就一并放进 context。

### 已核实的插件行为（2026-11-12，本机 pub cache）

- `package_info_plus 8.3.1` iOS（`FPPPackageInfoPlusPlugin.m`）：收据路径含 `CoreSimulator` → `com.apple.simulator`；含 `sandboxReceipt` → `com.apple.testflight`；否则 → `com.apple`。**不返回 null**。架构 A5 与 epics 写的「iOS null 算生产」与插件实际不符，实际 App Store 安装值是 `com.apple`；按本 story T1 规则两者都算生产，结论不变。
- 同插件 Android（`PackageInfoPlugin.kt`）：API 30+ 用 `getInstallSourceInfo().initiatingPackageName`，更低用 `getInstallerPackageName()`；`adb install` 通常为 null；Play 为 `com.android.vending`。
- `device_info_plus 11.5.0`：`AndroidDeviceInfo.isPhysicalDevice` / `model` / `manufacturer` / `version.release`；`IosDeviceInfo.isPhysicalDevice` / `systemVersion` / `utsname.machine`。

### stag 隔离为什么天然成立

2.1 的 sink 用 `dio_client.dart` 的 `kApiBaseUrl`（`PETGO_API_BASE_URL`）。stag 包注入 stag 地址 → 事件只到 stag 后端 → 只进 stag 埋点库（D-1：进哪个库取决于哪个后端收到，不加 env 列）。所以本 story 不需要「stag 标记」字段，只需 L1 验证。**不要改 `kApiBaseUrl` 的默认值**。

### 已知偏差（交口径文档）

- iOS 上从 Xcode 直接装到真机的开发包、企业分发包，`installerStore` 也是 `com.apple`，会被算作生产。发布流程里这类包只在开发者手里，量很小。
- Android 从华为 / 小米等应用商店安装的正式包会被判为侧载、不计入生产统计（A5「只认 Google Play」的既定取舍）。小米渠道 APK 用户会被排除，若后续该渠道量变大需重新评估。
- 员工和测试账号在真机商店包上算正常用户（Q5 已知偏差）。

### 必须遵守

- context 里不放任何可识别个人或设备的字段（设备名、Android ID、IDFV、IP）。NFR-3。
- 环境信息只采一次并缓存，不在每条事件时调插件。
- 不加新依赖；不整文件 `dart format`。
