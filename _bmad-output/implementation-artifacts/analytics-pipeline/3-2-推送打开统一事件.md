# Story 3.2: 推送打开统一事件

Status: review

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为内容运营，
我想要任何推送被点开都记成同一个事件并带类型，
以便按单条运营推送算打开率、按类型统计系统推送。

## Acceptance Criteria

> 以 `_bmad-output/planning-artifacts/analytics-pipeline/epics.md` Story 3.2 为准，原样带入。

1. **〔L0〕** `core/push/push_service.dart` 的推送点击处理：任一推送被点开时，上报 `push_opened`，`push_type` = 载荷里的 `type`。
2. **〔L0〕** 运营通知另带 `campaign_token` = 载荷 `targetRef`（活动 public_token）。
3. **〔L0〕** 现有 `ops_notification_opened`、`toko_coupon_expiry_push_opened` 保留；通知中心列表点击不报 `push_opened`。
4. **〔L0〕** 载荷缺 `type` 时 `push_type` 记为 `unknown`，不丢事件。
5. **〔L0〕** App 被杀后点推送冷启动时，`push_opened` 在匿名 id 就绪后入队，不丢、不抛异常。
6. **〔L2〕** 真机上分别点开一条运营推送和一条点赞推送（含一次冷启动），stag 明细层各有一条 `push_opened`，类型正确。

## Dev Notes

### 现状（读过的代码）

- `push_service.dart`：`PushPayload{type, token, targetRef}` + `parsePushExt`（非 JSON / 非对象 → 空载荷；`type` 非字符串会被 catch 吞成空载荷）。`_onNotificationClicked` 是前台 / 后台 / 冷启动三态唯一入口，先同步报两个专项事件，再异步「标记已读 + 算落点 + 导航」。
- 推送载荷来源：
  - 后端通知类推送：`LiveTencentImClient.buildBatchPushBody` 生成 `{"type":<NotificationType 名>, "token":?, "targetRef":?}`。
  - 问诊会话消息：App 端 `ChatPushSpec.toOfflinePushInfo()` 生成 `{"type":"VET_REPLY","targetRef":<sessionId>}`；后端系统消息 `{"type":"VET_REPLY"}`。
  - 因此目前所有推送都带 `type`；`unknown` 只是兜底。
- 后端 `NotificationType` 当前取值（供口径参考，`push_type` 原样取这些大写枚举名，不做小写转换）：`VET_REPLY CONSULT_CLOSED CONTENT_LIKED CONTENT_COMMENTED NEW_CONSULT_REQUEST PET_BIRTHDAY COMPANION_ANNIVERSARY MILESTONE_NODE CONTENT_REMOVED REPORT_REVIEWED CONTENT_REVIEW_APPROVED CONTENT_REVIEW_REJECTED NAME_RESET AVATAR_RESET CONTENT_REVIEW_TIMED_OUT REFUND_REJECTED TICKET_RESOLVED CSAT_SURVEY IDENTITY_REQUIRE_MODIFY ACCOUNT_WARNED ACCOUNT_SUSPENDED SHOP_ORDER_SHIPPED SHOP_ORDER_EXCEPTION SHOP_RETURN_UPDATED REPURCHASE_FOOD_LOW MILESTONE_SM_NODE LIFECYCLE_D1/D3/D7 LIFECYCLE_WINBACK CONTENT_MENTIONED OPS_ANNOUNCEMENT USER_FOLLOWED PLACE_COMMENTED GROWTH_LEVEL_UP PET_SLOT_EXPIRING PET_SLOT_EXPIRED PET_GIFT_RECEIVED GIFT_UNDELIVERED_REFUND PET_FOLLOWED PET_DIARY_POSTED COUPON_EXPIRING SHOP_ORDER_REORDERED`。

### 必须保留的现有行为

- 落点分流（`pushClickLocation`、直达例外 `kPushDirectTypes`）、标记已读、强更期间不导航、`pendingDeepLinkProvider` 冷启动暂存，全部不动。
- 两个旧事件属性不改名：`ops_notification_opened` 仍用 `campaign_id`（V1.3.4 定），新事件用 `campaign_token`（架构 §实现规范 1 定名）。两个名字指同一个值，S5 / 4.4 口径以 `push_opened` 为准（PRD FR-18）。

### 口径要点（给 4.4 用，本 story 不写汇总）

- 打开数 = `push_opened` 计数 / 去重人数；运营推送按 `campaign_token` 分，系统推送按 `push_type` 分。
- 兽医也会收到推送（如 `NEW_CONSULT_REQUEST`）并上报 `push_opened`，由汇总的 `role='USER'` 排除，不在 App 端过滤。
- 同一条推送在 TIMPush 上是否可能回调两次未实测；若 L2 发现重复，记进 Completion Notes，不在本 story 去重。

### 护栏

- 属性只放受控枚举与活动 public token；不放 `token`（通知中心行 token）、不放非运营类型的 `targetRef`。
- 不 `await` 埋点；上报失败由门面吞掉。
- 不新增依赖、不改推送注册流程。

核实项（均通过）：
- **点击入口覆盖**：`lib/` 内推送点击只有一条路径——`TencentCloudChatPush().registerPush(onNotificationClicked: _onNotificationClicked)`；项目不用 firebase_messaging / flutter_local_notifications（无 `getInitialMessage` / `onMessageOpenedApp`），不调 `addPushListener`。Android 冷启动（插件 `scheduleCheckPluginInstanceAndNotifyForOnClick` 500ms 轮询至注册后投递）、iOS（`AppDelegate.onRemoteNotificationReceived` → `tryNotifyDartOnNotificationClickEvent`，未注册时 0.5s 重试）都汇入 `on_notification_clicked` → 同一回调。插件 Dart 侧回调是单字段赋值，重复 `registerPush`（登出再登录）不会叠加回调。
- **push_type 口径**：后端全部推送出口（`NotificationService` 各 `pushToUser`、`OpsNotificationDispatcher.push`、`LiveTencentImClient` 系统消息 `{"type":"VET_REPLY"}`）的 `type` 均为 `NotificationType` 枚举名（含 `MILESTONE_SM_NODE`、`SHOP_ORDER_REORDERED`）或 `VET_REPLY`；App `ChatPushSpec` 为 `VET_REPLY`。与 yaml 描述一致。

- **不 await 埋点**：`reportPushOpened` 同步、`Analytics.capture` 为 void，置于异步导航段之前。
