# Story 4.2: GA4 快照与日活对账

Status: ready-for-dev

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。批次 ②。 -->

## Story

作为 Dai，
我想要每天看到同口径的自建日活与 GA4 日活差值和新版覆盖率，
以便有依据决定什么时候改用自建日活。

## Acceptance Criteria

本 story 只改后端，没有前端段。L0 = 编译 / 单测；L1 = 本地 postgres + redis 真跑；L2 = stag / 生产实测。云端只跑 L0。

**Epic 4 通用规则（全部适用）**

- 只算生产数据且 `is_suspicious=false`；用户维度只算 `role = 'USER'` 且 `account_type = 'REAL'`。
- 按「人」去重：带用户标识的事件归该用户；匿名事件按关联表归属（事件前有关联 → 最近一次；之前没有、之后有 → 第一个；从未关联 → 匿名 id）。
- WIB 自然日；周 = 周一至周日；月 = WIB 自然月。
- 每日去重人数不跨天相加：凡「统计周期内去重人数」的指标，同时写日表、周表、月表（周期结束次日计算并回补）；比率类月指标（取每日比率平均）由日表现算。
- Toko 已付款 = `shop_orders.paid_at IS NOT NULL`，按 `paid_at` 的 WIB 日期；退款 / 取消仍算。业务库关联一律用 public token，读业务库只做窄查询，不做跨库 SQL。
- 汇总表不含 `user_id`、匿名 id 等可识别个人的字段；每张新表在迁移里授权给 `analytics_reader`。

> 本 story 的「自建对账日活」是通用规则的**有意例外**：按设备（匿名 id）去重、不做生产排除，以便与 GA4 同口径（架构 D-11，Dai 2026-11-12 拍板）。

**验收标准（原样取自 epics.md Story 4.2）**

1. **Given** `Ga4ActiveUsersClient` 新增按 `appVersion` 维度拉取的方法 **Then** `Ga4DailySnapshotJob` 每天把 GA4 全版本日活和 V1.5.0+ 日活写入 `ga4_daily_snapshot`，**每次回拉最近 3 天覆盖旧值**〔L1〕
2. GA4 拉取失败告警，下次运行补拉；stag 无 GA4 凭证时跳过并记日志〔L1〕
3. `agg_daily_dau_reconcile` 每天一行：自建对账日活（按设备 / 匿名 id 去重、不做生产排除、只含 App 来源）、GA4 V1.5.0+ 日活、差值百分比 =（自建对账 − GA4 V1.5.0+）÷ GA4 V1.5.0+、新版覆盖率（V1.5.0+ ÷ 全版本，注明近似）、自建日活（含游客，按人）、登录用户日活、状态〔L1〕
4. 覆盖率首次 ≥90% 的那天为观察期起点，之后 4 周内 |差值| ≤10% 标「正常」，否则「异常」；观察期外为「未开始」或「已结束」（FR-25）〔L0〕
5. 对账结果只存库，不推飞书〔L0〕
6. 日活来源开关 `analytics.dau-source`（默认 `GA4`），供 4.7 使用〔L0〕

### GA4 拉取（D-11）

两种做法，用第二种：

1. 只按 `appVersion` 维度拉一次，把 ≥1.5.0 的行相加：同一设备当天用过两个版本会被算两次（D-11 说的「近似」）。
2. **推荐**：每天三次 `runReport`：
   - 全版本：沿用现有请求体（无维度，`metrics=activeUsers`）→ `all`。
   - 版本清单：`dimensions=[{name:"appVersion"}]`、`metrics=[activeUsers]` → 拿到当天出现过的版本号。
   - 新版本：把清单里 ≥ `min-app-version` 的版本放进 `dimensionFilter`，无维度再拉一次 → `newVersion`，GA4 侧已去重。
     ```json
     {"dateRanges":[{"startDate":"2026-11-20","endDate":"2026-11-20"}],
      "metrics":[{"name":"activeUsers"}],
      "dimensionFilter":{"filter":{"fieldName":"appVersion",
        "inListFilter":{"values":["1.5.0","1.5.1"]}}}}
     ```
     清单里没有新版本时 `newVersion = 0`，不发第三次请求。
- 版本号比较按数字逐段（`1.10.0 > 1.9.9`），非数字段或解析失败的版本视为不满足，单测覆盖。
- 覆盖率 = `newVersion ÷ all`，口径条目仍注明「近似」：GA4 的 `appVersion` 取的是当天上报时的版本，升级当天的设备两边都算一次。
- 日期按 GA4 属性时区解释，属性时区必须是雅加达（现有类注释已写明）。
- GA4 数据有处理延迟，日报因此放在 13:00 推（`application.yml` `petgo.daily-report` 注释）。02:30 拉到的 D−1 是初值，靠「每次回拉 3 天覆盖」在之后两天修正；对账状态随之重算。
- 请求失败只记 `HTTP 状态码` / 异常类名，**绝不**打印 token、密钥或响应体（沿用现有类的约束）。

### stag 的处理

GA4 属性只有生产包的数据（stag 包不上报 GA4）。stag 即使配了 GA4 凭证，对出来的数也没有意义，部署时在 stag env 设 `ANALYTICS_GA4_SNAPSHOT_ENABLED=false`（runbook 补一句）。stag 上 `agg_daily_dau_reconcile` 只有自建列，状态为 `NO_GA4`。

### 对账口径

- `self_reconcile_dau`：`events_detail` 中 `event_date = :stat_date AND event = 'Application Opened' AND source = 'APP' AND NOT is_suspicious` 的 `count(DISTINCT anonymous_id)`。**不**走归属视图、**不**做生产排除、**不**排除兽医等账号（与 GA4 按设备计数同口径）。可疑事件仍排除（时间不可信，日期本身就不可靠）。
- 新版 App 才会发自建事件，所以自建对账日活天然只含 V1.5.0+，与 GA4 V1.5.0+ 对齐。
- `diff_pct = (self_reconcile_dau − ga4_new_version_dau) ÷ ga4_new_version_dau`；GA4 为空或 0 → `diff_pct` 为空。
- `dau_person` / `dau_logged_in` 只作参照，直接取 4.1 `agg_daily_activity` 的 `all` 行。
- 状态（`DauReconcileCalculator`，输入整张表按日期排序）：
  - `observation_start` = 最早一个 `coverage ≥ 0.90` 的日期；没有 → 全部 `NOT_STARTED`。
  - 观察期 = `[start, start + 27]`（4 周，含两端）。
  - 观察期之前 → `NOT_STARTED`；之后 → `ENDED`；期内：GA4 缺数 → `NO_GA4`，|diff| ≤ 0.10 → `NORMAL`，否则 `ABNORMAL`。
  - `NO_GA4` 是 epics 四种状态之外新增的一种，用来区分「GA4 没拉到」与「对不上」，口径条目写明。
- 结果**只存库**，不碰 `DailyReportService` / `LarkWebhookClient`（FR-25「不推送飞书日报」）。

### 资源与护栏

- HTTP 调用不得包在任何数据库事务里；埋点库写入用短事务。
- 不加任何 Google SDK 依赖（现有实现刻意用 JDK 自带 HTTP + RS256，见类注释）。
- 告警在事务外调用（原因见 4.1 Dev Notes「告警与事务的坑」）。
