## Story

作为注销的用户，
我想要我的埋点数据在 24 小时内与我脱钩，
以便注销承诺在埋点库里也成立。

## Acceptance Criteria

本 story 只改后端，没有前端段。**云端只跑 L0，L1 / L2 留本地**，在 Completion Notes 标注「L1/L2 待本地验收」。

1. **[L1] 登记擦除请求**：迁移建 `erasure_requests`（`user_id`、`user_key`、`requested_at`、`done_at`；**不授权**给 `analytics_reader`）。`AccountDeletionService` 状态机执行注销时，新增的 `AnalyticsErasureParticipant` 写入一行；写失败抛异常，由状态机现有重试兜住。
2. **[L1] 每晚擦除**：`ErasureJob` 每晚固定时刻运行（早于汇总，advisory lock，任务内 `SET LOCAL statement_timeout` 放宽）：删除这些用户的 `identity_links`；把 `events_detail`、`events_raw` 中的 `user_id` / `user_key` 置空，并删掉清单里标为用户标识的属性键；原始层按分区逐个处理；完成后写 `done_at`。
3. **[L1] 幂等**：重复运行安全；已处理的请求不再扫描。
4. **[L1] 只脱钩不删事件**：擦除后匿名 id 上的事件仍保留（变成匿名事件）；汇总层不动。
5. **[L1] 端到端**：集成测试：注销 → 跑擦除任务 → 埋点库里查不到该 `user_id` / `user_key`，属性里也没有该用户的标识。

## Dev Notes

### 前置依赖

1.1（埋点数据源、`AnalyticsPipelineState`、`AnalyticsLockKeys`、`analyticsTransactionTemplate`）、1.2（`EventCatalog` 用户标识键）、1.3（`events_raw` 与分区）、1.5（`identity_links`）、1.6（`events_detail`、`DetailBuilder`）。以已落地代码的实际名称为准。

### 现有注销状态机（必读，`AccountDeletionService`）

- 状态：`PENDING → PROCESSING → DONE / FAILED` + `retry_count`（`account_deletions` 表，`AccountDeletion` 实体）。
- 触发：`requestDeletion` 提交后 `@Async @TransactionalEventListener onRequested` 调 `execute`；异常 → `markFailed`。
- **「现有重试」只有一种**：`@EventListener(ApplicationReadyEvent) rescanOnStartup()` 在**应用启动时**续跑 `PENDING / PROCESSING / FAILED`。没有周期性重试。含义：埋点库故障期间发起的注销会停在 `FAILED`，直到下一次后端重启才会再跑；FR-15「24 小时内」在这种情况下可能超时。这是架构 A10 接受的取舍，本 story **不新增**周期重试（不扩大改动面），在 Completion Notes 记为已知风险。
- 每个步骤各自事务、幂等可重跑；`execute` 本身无事务。新步骤遵守同样约定。
- 日志只记代理 id 与计数，**绝不落 PII**。

### 必须遵守

- 🔴 安全攸关节点：不得留下任何「注销后埋点库仍能按用户找到他」的路径；不得删除匿名事件行；不得改汇总层。
- 原始层没有 `user_id` 索引（1.3 只建 BRIN），按分区逐个全表 UPDATE 是预期做法；只在有待处理请求时才跑。
- 埋点库事务用Story 1.1 暴露的 `analyticsTransactionTemplate`（其事务管理器不注册成 bean）；**不要声明埋点事务管理器 bean**（会让业务 JPA 事务管理器自动配置失效，见 Story 1.6 Dev Notes）。`SET LOCAL` 必须在事务内执行才生效。
- 两个库之间不做跨库 SQL：participant 只写埋点库；`AccountDeletionService` 其余步骤不变。
- 迁移版本 `V20261113_1120`，只放 `db/analytics-migration/`。
- 告警文案、日志不含 `user_id` / `user_key`。

## Dai 拍板修订（2026-11-12，优先于上文）

- **待擦除记录改写进业务库**：不再往埋点库写 `erasure_requests`。新增**业务库**迁移 `petgo-backend/src/main/resources/db/migration/V20261113_1125__init_analytics_erasure_outbox.sql`，建表 `analytics_erasure_outbox`（`id`、`user_id`、`user_key`、`requested_at`、`done_at`）。`AnalyticsErasureParticipant` 用业务数据源在注销同一事务内写一行，不访问埋点库，因此埋点库故障或管道停用都不会让注销失败。
- `ErasureJob` 每晚从业务库读 `done_at IS NULL` 的行，在埋点库执行擦除，成功后回写业务库 `done_at`；埋点库不可用时跳过并 TECH 告警，下次再处理。
- 埋点库迁移 `V20261113_1120__init_erasure_requests` 作废（埋点库不再需要这张表）；若需在埋点库记录「已擦除用户」用于拦截注销后补发的旧事件，改为由 `ErasureJob` 从业务库 outbox 读取，不另建表。
- 原文「埋点库停用就抛异常」「注销重试只在启动时发生」「本地无埋点测试库会让注销集成测试失败」等风险随之消除，相关段落以本节为准。
