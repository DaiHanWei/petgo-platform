# Story 1.1: 埋点库骨架

Status: ready-for-dev

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为开发者，
我想要埋点库有独立的数据源、迁移历史和建库脚本，并且埋点库出问题时不影响业务，
以便后续 story 只管写管道逻辑，不会碰到业务库。

## Acceptance Criteria

本 story 只改后端（含 CI、运维 SQL、runbook），**没有前端段，也没有联调段**。云端只能跑 L0；L1（本地 postgres + redis 真跑）和 L2 留本地验收。

1. **〔L1〕** 新增 `analytics.datasource.*` 与 `AnalyticsDataSourceConfig`：业务数据源和 `JdbcTemplate` 显式 `@Primary`，埋点的 `DataSource` / `JdbcTemplate` 用 `@Qualifier`；现有全部测试保持绿。
2. **〔L1〕** 埋点连接池最多 3 个（stag 由 env 配为 2）。
3. **〔L1〕** 第二套 Flyway 只读 `classpath:db/analytics-migration`，历史表在埋点库内；首条迁移只建 `event_catalog`、`metric_definitions`。
4. **〔L1〕** 埋点库连不上或埋点 Flyway 失败时，后端照常启动、业务接口可用，埋点管道标记为停用并经 TECH 渠道告警。
5. **〔L0〕** `scripts/ci/check-flyway-versions.sh` 分别检查两个迁移目录（同号、非时间戳、改动 main 已有文件），跨目录撞号不算冲突；`.github/workflows/flyway-guard.yml` 的 paths 加入 `db/analytics-migration/**`。
6. **〔L0〕** 后端 CI 的测试环境建出埋点测试库，L1 测试能连上。
7. **〔L1〕** `scripts/ops/create-analytics-db.sql` 按参数分别建生产（`petgo_analytics` / `analytics_writer` / `analytics_reader`）和 stag（`petgo_analytics_stag` / `analytics_writer_stag` / `analytics_reader_stag`）；写入账号 `CONNECTION LIMIT 5`、`statement_timeout=120s`；只读账号 `CONNECTION LIMIT 3`、只有 CONNECT 权限，**不设全局默认授权**（表权限由各 story 的迁移逐表 `GRANT`）；可重复执行。
8. **〔L0〕** `.env.example` 加 `ANALYTICS_DB_NAME / ANALYTICS_DB_USER / ANALYTICS_DB_PASSWORD` 占位；docs/runbooks 补「部署前先建库」。
9. **〔L0〕** `AnalyticsLockKeys` 常量类建好，后续任务的 advisory lock 锁键只从这里取。

### 自动配置退让清单（本 story 最容易出事的地方）

定义第二个 `DataSource` / `JdbcTemplate` 后，Spring Boot 4.0.6 以下自动配置会退让，必须按上面的任务显式补齐：

| 自动配置 | 退让条件 | 后果 | 处理 |
|---|---|---|---|
| `DataSourceAutoConfiguration` 的连接池 | 存在任意 `DataSource` bean | 业务库没了 | 显式 `@Primary HikariDataSource`，仍绑定 `spring.datasource.hikari` |
| `JdbcTemplateConfiguration` | 存在任意 `JdbcOperations` bean（已用 javap 核实 4.0.6） | 85 个文件注入 `JdbcTemplate` 拿到埋点库或报歧义 | 显式 `@Primary JdbcTemplate` |
| `NamedParameterJdbcTemplateConfiguration` | 依赖单一 `JdbcTemplate` 候选 | 63 个文件注入失败 | 显式 `@Primary NamedParameterJdbcTemplate` |
| JPA `transactionManager` | 存在任意 `TransactionManager` bean | 业务 `@Transactional` 失效 | 埋点事务管理器**不注册成 bean**，只暴露 `TransactionTemplate` |
| `FlywayAutoConfiguration` | 存在任意 `Flyway` bean | 业务迁移不跑 | 埋点 Flyway 不注册成 bean |
| `DataSourceHealthContributorAutoConfiguration` | 会把所有 `DataSource` bean 并进 `db` 健康项 | 埋点库挂 → health DOWN → 部署脚本判失败 | 自定义 `dbHealthContributor` 只含业务库 |

AC1 的「现有全部测试保持绿」就是在验证这张表。

### 表结构（V20261113_1000）

```sql
CREATE TABLE event_catalog (
    event        varchar(128) PRIMARY KEY,       -- 事件名，原样（含 'Application Opened' 这类带空格的）
    source       varchar(8)   NOT NULL,          -- APP / SERVER / H5
    status       varchar(16)  NOT NULL,          -- ACTIVE / PLANNED / RETIRED
    domain       varchar(32),
    description  text         NOT NULL,
    code_ref     varchar(255),                   -- 上报点位置，供人和 AI 追溯
    properties   jsonb        NOT NULL DEFAULT '[]'::jsonb, -- [{name,type,description,user_identifier}]
    updated_at   timestamptz  NOT NULL DEFAULT now()
);
CREATE TABLE metric_definitions (
    code         varchar(32)  PRIMARY KEY,       -- 团队编号，如 S1、电商#6
    name         varchar(128) NOT NULL,
    definition   text         NOT NULL,
    sources      jsonb        NOT NULL DEFAULT '[]'::jsonb, -- 来源表 / 事件
    exclusions   text,
    known_bias   text,
    sql_path     varchar(255),                   -- resources/analytics/rollup/<指标族>.sql
    changelog    jsonb        NOT NULL DEFAULT '[]'::jsonb, -- [{date,change}]
    updated_at   timestamptz  NOT NULL DEFAULT now()
);
```

- 枚举落 `varchar` + UPPER_SNAKE（基线命名约定），加 `CHECK` 约束限定取值。时间列 `timestamptz`、UTC。
- 若 Story 1.2 实现时发现缺列，**另起新迁移 ALTER**，不要回头改本文件（一旦被任何环境应用就冻结）。
- 埋点表一律用 `JdbcTemplate`，**禁止 JPA 实体**（架构 §实现规范 5 反例）；因此业务库的 `ddl-auto=validate` 不会扫到它们。

### 迁移里的授权写法（本 story 定规矩，1.2 / 1.3 / 1.5 照用）

只读角色在生产叫 `analytics_reader`、在 stag 叫 `analytics_reader_stag`，CI 与本地测试库里根本没有这个角色。所以迁移里**不能写死角色名**，统一用 Flyway 占位符 + 条件授权：

```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = '${readerRole}') THEN
    EXECUTE format('GRANT SELECT ON %I TO %I', 'event_catalog', '${readerRole}');
  ELSE
    RAISE NOTICE 'role ${readerRole} 不存在，跳过授权（本地 / CI 预期如此）';
  END IF;
END $$;
```

占位符名固定为 `readerRole`，由 `AnalyticsBootstrap` 从 `analytics.datasource.reader-role` 传入。生产 / stag 在部署前已由 `create-analytics-db.sql` 建好角色，不会走到跳过分支。

### 建库脚本要点（`scripts/ops/create-analytics-db.sql`）

- 用 psql 变量传参，**密码不写进文件**：
  `psql -v ON_ERROR_STOP=1 -v env=prod -v writer_pw="$W" -v reader_pw="$R" -U <超级用户> -d postgres -f scripts/ops/create-analytics-db.sql`；`env=stag` 时库名、角色名都带 `_stag` 后缀。
- 可重复执行：`CREATE ROLE` / `CREATE DATABASE` 都不支持 `IF NOT EXISTS`，且 psql 变量**不会**在 `DO $$ ... $$` 里展开。用 `SELECT format(...) WHERE NOT EXISTS (...) \gexec` 生成语句；已存在的角色用 `ALTER ROLE ... PASSWORD / CONNECTION LIMIT` 重设，保证重复执行后状态一致。
- 写入账号：`LOGIN CONNECTION LIMIT 5`，`ALTER ROLE ... SET statement_timeout = '120s'`；作为埋点库的 **OWNER**（`CREATE DATABASE ... OWNER analytics_writer`），这样它能跑迁移、建分区（PG15+ public schema 归库属主）。
- 只读账号：`LOGIN CONNECTION LIMIT 3`，只 `GRANT CONNECT ON DATABASE`；**不写 `ALTER DEFAULT PRIVILEGES`**，表权限由迁移逐表授予。
- `REVOKE ALL ON DATABASE <埋点库> FROM PUBLIC`：同实例上还有业务账号、`ops_readonly`、`claude_bot` 等角色，不收回 PUBLIC 的 CONNECT 它们都能连进埋点库；也防止 stag 角色连生产库。
- 脚本开头注释写明：在 `petgo-postgres` 实例上手动执行，生产 / stag 各一次，**在首次部署含本 story 的后端之前**。

### 必须遵守

- 不引入新依赖、中间件、PG 扩展（NFR-2）。Flyway、Hikari 都是现有依赖。
- 日志不打连接串、用户名、密码。
- 新迁移只放 `db/analytics-migration/`，**绝不混进 `db/migration/`**，反之亦然。
- 埋点库故障只停埋点、不伤业务：启动路径上任何埋点异常都不能向上抛。
- 打包一律 `mvn -B clean package`（`target/classes` 残留旧迁移会导致同号崩溃）。
- 部署前建库属运维动作：**不要在任何环境执行**建库脚本或部署，留给用户。

- 现有 advisory lock 写法：`LogisticsStallJob` 用 `pg_try_advisory_xact_lock(hashtext('logistics_stall'))`，`AiQueryService` 用两段式 `pg_advisory_xact_lock(:ns, :id)`。埋点统一用两段式 + `AnalyticsLockKeys`。
- 测试：`ApiIntegrationTest`（`com.tailtopia.support`）是 L1 基类，真 PG + Redis、无 Testcontainers，385 个测试类继承它；CI `backend-ci.yml` 起 `postgres:16-alpine`（库 `petgo`）+ `redis:7-alpine`。
- Spring Boot 4.0.6 / Java 21；Jackson 3（`tools.jackson.databind`）。

### 本地 L1 跑法

本地 postgres 先 `createdb petgo_analytics_test`（以及开发用的 `petgo_analytics`），再 `./mvnw -B clean package`。不建库也能跑：管道会停用，非埋点测试不受影响——这本身就是 AC4 的验证。
