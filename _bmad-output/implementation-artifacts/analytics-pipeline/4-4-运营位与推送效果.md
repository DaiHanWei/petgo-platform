# Story 4.4: 运营位与推送效果

Status: review

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。批次 ②。 -->

## Story

作为电商和内容运营，
我想要每个弹窗、横幅、推送的展示、点击、打开和带单都能查，
以便知道哪个运营位有效。

## Acceptance Criteria

本 story 只改后端，没有前端段。L0 = 编译 / 单测；L1 = 本地 postgres + redis 真跑；L2 = stag / 生产实测。云端只跑 L0。

**Epic 4 通用规则（全部适用）**

- 只算生产数据且 `is_suspicious=false`；用户维度只算 `role = 'USER'` 且 `account_type = 'REAL'`。
- 按「人」去重：带用户标识的事件归该用户；匿名事件按关联表归属（事件前有关联 → 最近一次；之前没有、之后有 → 第一个；从未关联 → 匿名 id）。
- WIB 自然日；周 = 周一至周日；月 = WIB 自然月。
- 每日去重人数不跨天相加：凡「统计周期内去重人数」的指标，同时写日表、周表、月表（周期结束次日计算并回补）；比率类月指标（取每日比率平均）由日表现算。
- Toko 已付款 = `shop_orders.paid_at IS NOT NULL`，按 `paid_at` 的 WIB 日期；退款 / 取消仍算。业务库关联一律用 public token，读业务库只做窄查询，不做跨库 SQL。
- 汇总表不含 `user_id`、匿名 id 等可识别个人的字段；每张新表在迁移里授权给 `analytics_reader`。

**验收标准（原样取自 epics.md Story 4.4）**

1. **Given** 迁移建 `agg_daily_placement`、`agg_weekly_placement`、`agg_monthly_placement`、`agg_daily_push` **Then** 按 `placement_type` + `placement_token` 记曝光次数、点击次数、点击人数（周表、月表的点击人数为周期内去重）〔L1〕
2. 每个运营位记「点击后 7 天内产生的已付款 Toko 订单数」：读业务库已付款订单（用户 + `paid_at`），与点击按用户和时间匹配，结果写回埋点库（S5 带单，FR-22）〔L1〕
3. 运营位是否推广 Toko：读业务库运营位配置的跳转目标，作为维度写进汇总表（FR-17 第 3 条）〔L1〕
4. 运营推送按 `campaign_token` 记 `ops_notification_campaigns` 的 `planned_count` / `recipient_count`（口径注明「接收 = 写入通知中心人数，近似」）和 `push_opened` 打开人数；券过期推送的发送数取服务端事件 `toko_coupon_expiry_push_sent`；其他系统推送按 `push_type` 只记打开人数，并在口径中注明（FR-23）〔L1〕
5. 本 story 内勘察各系统推送是否有发送记录（A13 / Q4），结论写进口径条目〔L0〕
6. 带单数与直接查业务库的已付款订单抽样一致〔L1〕

**按通用规则补充（epics 表清单未列，但「周期内去重人数」规则要求）**

7. 推送打开人数同样是周期去重指标：另建 `agg_weekly_push`、`agg_monthly_push`，打开人数在周期内去重〔L1〕

### 跨库匹配的做法

两个库之间不做跨库 SQL（架构「边界」）。每个单元：

1. 埋点库短查询：当天点击事件的去重 `person_user_id`（非空）。
2. 业务库窄查询：这些用户在 `[点击日 0 点 WIB, 点击日 + 8 天 0 点 WIB)` 内付款的订单（`user_id`、`public_token`、`paid_at`）。
3. 埋点库单元事务：建临时表、批量插入，然后执行 `placement.sql` 关联计算，写日表与 `agg_progress`。

业务库查询放在埋点库事务**之外**，避免占着埋点连接（池只有 3 条）。WIB 日界换算在 Java 里做（`ZoneId.of("Asia/Jakarta")`），SQL 拿到的是 `timestamptz` 参数。

### 运营推送的打开率

- 团队要的是「每一条」的打开率（department-data-summary S5）。一条推送的打开会分散在之后几天，日去重人数不能相加，所以每行另存 `campaign_opened_persons_cum`（从发送日到当天的去重打开人数）。查打开率：取该活动最新一行的 `campaign_opened_persons_cum ÷ recipient_count`。
- 重算范围：除了重算窗口内的日期，还要刷新「发送日在最近 14 天内」的活动（取配置 `analytics.rollup.push-campaign-days`，默认 14）在 `as_of` 当天的累计值。超过这个期限的晚打开不再计入累计数，写进已知偏差。
- 接收数 = `recipient_count` = 写入通知中心人数，**不是**推送送达数：屏蔽推送（`user_push_mutes`）或推送失败的人也计入。`failed_count` 含「推送重试 3 次仍失败」的人。口径写「近似」。

### 系统推送发送记录勘察（A13 / Q4，AC5）

逐个 `notifications.type` 核对有没有「推送已发出」的记录。类型全集取**当前树里最后一条重建 `ck_notifications_type` 的迁移**（按时间戳最新，目前看是 `V20261105_1620__rebuild_ck_notifications_type_shop_coupon_reorder.sql`，开工时再确认一次）。可查的线索：

| 线索 | 能说明什么 |
|---|---|
| `notifications`（`V19__init_notify.sql` 起） | 写入通知中心的行；不等于推送发出（静音、无推送权限、推送失败都会有行） |
| `user_push_mutes`（`V20261018_1800`、`V20261104_2010`） | 哪些类型可被用户屏蔽推送 |
| `lifecycle_push_marks`（`V20260821_1646`） | `LIFECYCLE_D1/D3/D7/WINBACK` 的发送去重记录 |
| `scheduled_push_marks`（`V22`） | 定时推送去重记录 |
| `pet_diary_notify_log`（`V20261104_2020`） | `PET_DIARY_POSTED` 的通知记录 |
| `coupon_expiry_notify_log`（`V20261105_1615`） | 券过期每人每天一行，可与服务端事件互相核对 |
| 推送发送代码（`notify` 包、腾讯推送调用处） | 是否有发送结果落库 |

结论按类型列成表：「有发送记录（来源表）/ 只有通知中心记录 / 无记录 → 只统计打开数」。本 story **只勘察和写口径，不新增发送记录**；需要补记录的类型列进 Completion Notes 交 Dai 决定。

### 已知偏差（写进口径条目）

- 带单是「点击后 7 天内的已付款订单」，不代表订单一定由该运营位带来；同一订单可同时计入多个运营位。
- 匿名点击且之后从未登录的人无法匹配订单。
- `promotes_toko` 按计算时的配置判定，回补窗口内运营改了跳转会改变历史行；配置已删的为空。
- 运营推送接收数是写入通知中心人数，近似；活动发送 14 天后的打开不计入累计打开人数。
- 没有发送记录的系统推送只有打开数（以 AC5 勘察结论为准）。
- 曝光只在新版 App（Story 3.1 之后）统一为「露出超过 50% 计一次」。

### 资源与护栏

- 临时表都用 `ON COMMIT DROP`，只在单元事务内存在。
- 日志只打条数、日期、耗时；不打 token 以外的任何业务字段，不打用户标识。
- 汇总表只存 token 和计数，不存 `user_id` / 订单号以外的个人信息（订单 token 也不落汇总表，只用来计数）。
