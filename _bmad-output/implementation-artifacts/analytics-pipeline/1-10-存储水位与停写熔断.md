# Story 1.10: 存储水位与停写熔断

Status: ready-for-dev

## Story

作为 Dai，
我想要埋点库占用每天可见、超线告警、再超线自动停写，
以便埋点永远不会把共用的数据库磁盘写满。

## Acceptance Criteria

本 story 只改后端（加一段 runbook），没有前端段。**云端只跑 L0，L1 / L2 留本地**，在 Completion Notes 标注「L1/L2 待本地验收」。

1. **[L1] 每日水位**：迁移建 `storage_watermarks`，`StorageWatermarkJob` 每天运行，记录本环境埋点库占用、月事件量和月增长。
2. **[L1] 告警与切回提示**：超过 40 GB 经 TECH 渠道告警；月事件量 ≥ 6,000 万条（研究估算 10 倍区间 3,000–7,500 万条的中位）或占用增速按月外推将在 3 个月内触及 40 GB 时，告警文案提示「评估切回第三方」（FR-16）。
3. **[L1] 停写熔断**：`IngestCircuitBreaker` 每 5 分钟检查一次，超过 50 GB 后接收端返回 429，降回阈值以下自动恢复；熔断和恢复都告警。
4. **[L0] 状态切换单测**：阈值取配置，单测覆盖告警 / 熔断 / 恢复三种状态切换。
5. **[L0] 运维说明**：docs/runbooks 补一段主机整盘余量 cron 检查的说明（运维项，不在后端实现）。

### 后端（本 story 无前端、无联调段）

- [ ] **T1 迁移**（AC: 1）
  - [ ] 新建 `petgo-backend/src/main/resources/db/analytics-migration/V20261113_1140__init_storage_watermarks.sql`
  - [ ] `storage_watermarks(snapshot_date date PRIMARY KEY, db_bytes bigint NOT NULL, raw_bytes bigint NOT NULL, detail_bytes bigint NOT NULL, events_on_day bigint NOT NULL, month_events bigint NOT NULL, month_growth_bytes bigint, created_at timestamptz NOT NULL DEFAULT now())`
  - [ ] 列注释：`snapshot_date` = **WIB 日期**（任务运行当天）；`events_on_day` = 前一个 UTC 日原始层分区的行数；`month_events` = 本 WIB 自然月截至当天的 `events_on_day` 累计；`month_growth_bytes` = `db_bytes` 与 30 天前快照之差（不足 30 天时取最早快照按天数折算为 30 天，仅一条时为 NULL）
  - [ ] 是否授权给 `analytics_reader`：架构 A8 白名单未列此表 → **不授权**（如需让 AI 看水位，另行拍板）
- [ ] **T2 阈值配置**（AC: 4）
  - [ ] `application.yml` 的 `analytics:` 下新增 `storage.alert-bytes`（默认 40 GB）、`storage.stop-bytes`（默认 50 GB）、`storage.month-events-hint`（默认 60,000,000）、`storage.hint-months`（默认 3）、`storage.breaker-check-ms`（默认 300000），用 `@ConfigurationProperties`（如 `AnalyticsStorageProperties`）绑定；`.env.example` 不需要新变量（如加 env 覆盖，只放占位）
- [ ] **T3 纯函数：水位评估与熔断状态机**（AC: 2, 3, 4）
  - [ ] 新建 `com.tailtopia.analytics.store.StorageWatermarkPolicy`（无 Spring 依赖）：输入当天快照与历史快照、阈值，输出 `{overAlert, switchBackHint, monthsTo40G}`；`switchBackHint = monthEvents >= monthEventsHint || (monthGrowthBytes > 0 && (alertBytes − dbBytes) / monthGrowthBytes < hintMonths)`；已超 40 GB 时 `switchBackHint` 同样为真
  - [ ] 新建 `com.tailtopia.analytics.ingest.IngestCircuitBreaker` 的状态迁移逻辑（可抽成纯方法 `next(state, dbBytes, stopBytes)`）：`CLOSED` 且 `dbBytes > stopBytes` → `OPEN`；`OPEN` 且 `dbBytes <= stopBytes` → `CLOSED`；其他保持；返回是否发生切换
- [ ] **T4 `StorageWatermarkJob`**（AC: 1, 2）
  - [ ] 新建 `com.tailtopia.analytics.store.StorageWatermarkJob`，`@Scheduled(cron = "${analytics.storage.watermark-cron:0 30 4 * * *}", zone = "Asia/Jakarta")`（WIB 04:30，避开 02:00 擦除与 03:00 汇总）；`pg_try_advisory_xact_lock(AnalyticsLockKeys.STORAGE_WATERMARK)`（新增该键）
  - [ ] 采集：`pg_database_size(current_database())`；`raw_bytes` / `detail_bytes` = 对应父表全部分区 `pg_total_relation_size` 之和（分区从 `pg_inherits` 取，含 `events_raw_pdefault`）；`events_on_day` = `SELECT count(*) FROM events_raw_p<前一个 UTC 日>`（分区不存在记 0）
  - [ ] `INSERT … ON CONFLICT (snapshot_date) DO UPDATE`，同一天重跑覆盖（可重复跑）；日期由任务传入，SQL 里不用 `CURRENT_DATE`
  - [ ] 评估后：`overAlert` → `OpsAlertService.send(OpsChannel.TECH, "analytics:storage-over:<WIB日期>", …)`；`switchBackHint` → 文案包含「评估切回第三方」以及当前占用、月事件量、外推月数；两类告警按天去重，**不含任何用户数据**
  - [ ] 每个环境只统计**自己连接的那个埋点库**（生产后端记生产库，stag 后端记 stag 库，D-1），不要跨库查询另一环境
  - [ ] 失败只告警不抛
- [ ] **T5 `IngestCircuitBreaker`**（AC: 3）
  - [ ] 新建 `com.tailtopia.analytics.ingest.IngestCircuitBreaker`（`@Component`），持有 `volatile` 状态，`isOpen()` 供接收侧读取；`@Scheduled(fixedDelayString = "${analytics.storage.breaker-check-ms:300000}", initialDelay = 0)`（启动即检查一次）
  - [ ] 检查只做一次 `SELECT pg_database_size(current_database())`；查询失败（埋点库不可用）时**保持原状态**并记 WARN（埋点库不可用由 1.1 的管道停用逻辑处理，这里不重复告警）
  - [ ] 状态切换时告警：打开 → `analytics:breaker-open:<时间到分钟>`，恢复 → `analytics:breaker-closed:<时间到分钟>`，文案写当前占用与阈值
  - [ ] **接入接收端**（改 Story 1.4 代码）：`isOpen()` 为真时，`POST /api/v1/analytics/batch` 返回 **429 + `Retry-After`**（秒数取配置，默认 300，与检查周期一致），沿用 1.4 队列满时的同一套 429 响应构造；判定点放在 1.4 的入队判定处（`IngestQueue` 的接收入口或其前置的同一个门），这样 Story 1.9 的 `SelfHostedAnalyticsClient` 走同一入口时**自动被拒并计入丢弃**，无需再改 1.9
  - [ ] 熔断只拦新写入：已在内存队列中的事件照常由 `IngestFlusher` 写完；`DetailBuilder`、分区维护、擦除不受影响（删分区正是降水位的手段）
- [ ] **T6 runbook**（AC: 5）
  - [ ] 在 Story 1.1 建的 `docs/runbooks/runbook-analytics-pipeline.md` 补「主机整盘余量检查（运维项）」一节：后端容器看不到主机整盘余量，需在主机（`petgo-postgres` 所在机）加 cron，例如每 30 分钟 `df -P <PG 数据目录所在挂载点>`，可用空间低于阈值（建议 15 GB，与 50 GB 停写线配合留足同机其他服务余量）时发飞书技术群告警；写清安装位置、阈值、告警渠道、验证方法；说明这与后端 40 / 50 GB 水位是两道独立防线
  - [ ] 同节写熔断后的处置：查 `storage_watermarks` 看增长来源 → 手工删过期分区或缩短保留期 → 占用降回 50 GB 以下 5 分钟内自动恢复

## Dev Notes

### 前置依赖

1.1（埋点数据源、`AnalyticsLockKeys`、runbook）、1.3（原始层分区）、1.4（接收端点、`IngestQueue`、429 + `Retry-After` 构造）、1.6（明细层分区）、1.9（`SelfHostedAnalyticsClient` 的入队与丢弃计数）。以已落地代码为准。

### 必须遵守

- 熔断返回 **429**（不是 503）：App 端对 429 按 `Retry-After` 保留重发、对 400 / 413 整批丢弃（架构「接口格式」表）。PRD FR-10 写的「队列满返回 503」已被架构改为 429，以架构为准；503 只用于「管道停用」（1.4）。
- 不引入任何新组件、扩展或外部监控；主机整盘余量是**运维项**，后端只写 runbook，不实现。[Source: architecture.md 磁盘熔断、NFR-2]
- 定时任务可重复跑、日期由任务传入；埋点库事务用Story 1.1 暴露的 `analyticsTransactionTemplate`（其事务管理器不注册成 bean），**不声明埋点事务管理器 bean**（见 Story 1.6 Dev Notes）。
- 调度线程池现状为 4（`spring.task.scheduling.pool.size`，`TASK_SCHEDULING_POOL_SIZE`），不是单线程；熔断检查与其他埋点任务可能并发占用埋点连接，所有任务都要吞异常、只告警。
- `pg_database_size` 在 `DELETE` 后不下降，只有 `DROP` 分区（或 VACUUM FULL）才会释放空间 —— 恢复路径依赖 Story 1.7 的分区删除，runbook 里写明。
- 迁移版本 `V20261113_1140`，只放 `db/analytics-migration/`。
- 告警文案与日志不含用户数据。
