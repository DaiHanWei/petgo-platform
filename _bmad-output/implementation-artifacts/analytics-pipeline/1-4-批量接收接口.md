# Story 1.4: 批量接收接口

Status: review

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为 App 和服务端，
我想要把事件批量交给后端并立即拿到结果，
以便上报不阻塞主流程，后端被刷也不拖垮业务。

## Acceptance Criteria

本 story 只改后端，**没有前端段**；App 接入属 Epic 2（Story 2.1）。云端只能跑 L0；L1（本地 postgres + redis 真跑）、L2（本地按生产参数压测）留本地。

1. **〔L1〕** `POST /api/v1/analytics/batch`，可不带 JWT；批次合法时返回 `202 {accepted, rejected}`，事件进入有界内存队列。
2. **〔L0〕** 必填字段 `messageId`、`event`、`timestamp`、`sentAt`、`anonymousId`（UUID）；缺任一或格式非法只拒该条并计入 `rejected`；其余字段缺失不拒收。
3. **〔L0〕** 单条 32 KB、请求 500 KB 超限返回 413，整批格式错误返回 400（ProblemDetail）。
4. **〔L1〕** 事件名不在清单里的**照样接收**，`unknown_event=true`；按事件名计数，每天经 TECH 渠道告警一次。
5. **〔L1〕** 限流以匿名 id 为主，IP 只设很宽的兜底阈值（取配置）；429 响应带 `Retry-After`；IP 不写进任何表或日志。
6. **〔L1〕** 队列按估算字节数设上限（默认 64 MB，取配置），满了返回 429 + `Retry-After`；管道停用时返回 503。
7. **〔L1〕** `IngestFlusher` 每 1 秒或攒够 500 条批量写 `events_raw`；`received_at` 取服务端时间；`source=APP`。
8. **〔L1〕** 优雅停机时先停接收、写完队列再退出；集成测试验证停机前已 202 的事件全部落库。
9. **〔L1〕** 本接口从全接口请求日志里排除；任何日志只打条数和 `messageId`。
10. **〔L1〕** 本 story 内用户标识原样入库并标 `identity_unverified=true`，身份校验由 1.5 收紧。
11. **〔L2〕** 在本地按生产参数（`shared_buffers=128MB`、`max_connections=100`）起的 postgres 上以 10 倍现量压测，业务接口 P95 增幅 ≤10%（NFR-1），同时观察队列满载时的堆内存；结果记进 Completion Notes。**不在 stag 压**（与生产共用实例）。

## Dev Notes

### 请求 / 响应契约（Story 2.1 依赖）

```
POST /api/v1/analytics/batch
Content-Type: application/json
Authorization: Bearer <JWT>        # 可选
{
  "batch": [
    {
      "messageId":   "4f0c...-uuid",            # 必填，≤64
      "event":       "toko_add_to_cart_tapped", # 必填，≤128，原样
      "timestamp":   "2026-11-13T08:15:30.123+07:00",  # 必填，事件发生时间（客户端时钟）
      "sentAt":      "2026-11-13T08:16:00.000+07:00",  # 必填，本次发送时间（客户端时钟）
      "anonymousId": "uuid-v4",                 # 必填，UUID
      "userId":      "<64 位 hex>",             # 可选，= AnalyticsDistinctId / distinctIdFor
      "properties":  { "snake_case": ... },     # 可选
      "context":     { ... }                    # 可选，App 版本 / 平台 / 生产标记等（Story 2.5 定）
    }
  ]
}

202 { "accepted": 3, "rejected": 1 }
400 ProblemDetail   整批格式错误（App 整批丢弃）
413 ProblemDetail   请求 >500 KB / 单条 >32 KB / 条数 >500（App 整批丢弃）
429 ProblemDetail + Retry-After   限流 / 队列满（App 保留，到时再发）
503 ProblemDetail + Retry-After   管道停用 / 停机中（App 按 5xx 指数退避）
```

- 外层字段 camelCase，属性 snake_case（架构 §实现规范 1，两层不同是有意的）。
- 字段语义对齐 Segment（NFR-4）：`timestamp` → `client_ts`，`sentAt` → `sent_at`，服务端补 `received_at`。
- 原始层允许重复：同一 `messageId` 重发会再写一行，去重在明细层（1.6）。接口**不**做去重。

### 已知行为：无效 JWT 返回 401

`apiFilterChain` 用 OAuth2 资源服务器：请求带了 `Authorization: Bearer` 但 token 过期 / 无效时，`BearerTokenAuthenticationFilter` 在授权判断之前就返回 401，`permitAll` 拦不住。这是全仓现有行为，本 story 不改。App 的 `AuthInterceptor` 会先刷新 token；Story 2.1 需要把 401 当作「刷新后重发」而不是「整批丢弃」——epics 2.1 的返回码表里没有 401，作为文档缺口报告。

### 兽医 / 后台 token

兽医 token 的 `sub` 是 vetId，与 `users.id` 是两个会碰撞的命名空间（`SecurityConfig` 多处注释）。本 story 只透传 JWT；**Story 1.5 必须只认 `role=USER` 的 token**（判法同 `ops/popup/web/OpsPopupController.java:70`：`"USER".equals(jwt.getClaimAsString("role"))`），其他角色按无 JWT 处理。

### 队列与停机的边界

- 内存队列是记录在案的护栏破例（架构 D2 / §三 队列）：单实例部署，`@Async` + DB 状态机之外唯一的内存缓冲。
- 只有进程被强杀或 OOM 才丢数据（可接受，FR-10）。注意：部署脚本用 `docker stop $CONTAINER`（`scripts/deploy-backend.sh:118`），默认 10 秒后 SIGKILL；Boot 优雅停机默认每阶段 30 秒。正常队列远小于 64 MB、几秒内能写完；若压测发现 10 秒不够，在 Completion Notes 记下并建议部署脚本改 `docker stop -t 30`（**部署脚本本 story 不改**，架构定了「部署脚本不改」）。
- 容器没设 `-Xmx`（`Dockerfile.deploy` 无 JVM 参数），JVM 默认取容器 / 主机内存的 25%。64 MB 队列按估算字节计，真实堆占用会更高，压测时要看。

### 压测（AC11，L2）

- 本地 docker 起 `postgres:16-alpine`，参数 `-c shared_buffers=128MB -c max_connections=100`，与生产一致；**不要在 stag 压**（stag 与生产共用 PG 实例和 Redis）。
- 10 倍现量：现量每月 300–750 万条 → 设计 3,000–7,500 万条 / 月，日均约 100–250 万条，峰值按日均 ×5 估算请求速率；每批 20 条（App 默认攒批）。
- 同时对 1–2 个代表性业务接口（如 feed 列表、商品列表）跑基线和压测下的 P95，比较增幅（≤10%）。
- 观察：队列字节水位、堆内存（`jcmd <pid> GC.heap_info` 或 actuator 指标）、429 比例、埋点库连接数。
- 结果（参数、P95 前后、堆峰值、是否触发 429）写进 Completion Notes；IP 兜底阈值据此定。

### 必须遵守

- 不引入新依赖 / 中间件；Redis 只用于限流键。
- 埋点库只经 `@Qualifier("analytics")` 的 `JdbcTemplate` 写；禁止 JPA。
