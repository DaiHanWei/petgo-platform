## Story

As a 团队成员,
I want 向 AI 问任何 B、C 类指标都能按统一口径得到答案,
so that 不同人问同一个数，得到同一个结果。

## Acceptance Criteria

> 原样取自 `_bmad-output/planning-artifacts/analytics-pipeline/epics.md` Story 4.8。L0 = 编译 / 单测；L1 = 本地 postgres 真跑；L2 = stag 实测。

**Epic 4 通用规则（本 story 全部适用，违反即返工）**

- 只算生产数据且 `is_suspicious=false`；用户维度只算 `role = 'USER'` 且 `account_type = 'REAL'`。
- 按「人」去重：带用户标识的事件归该用户；匿名事件按关联表归属（事件前有关联 → 最近一次；之前没有、之后有 → 第一个；从未关联 → 匿名 id）。
- WIB 自然日；周 = 周一至周日；月 = WIB 自然月。
- 每日去重人数不跨天相加：凡「统计周期内去重人数」的指标，同时写日表、周表、月表（周期结束次日计算并回补）；比率类月指标（取每日比率平均）由日表现算。
- Toko 已付款 = `shop_orders.paid_at IS NOT NULL`，按 `paid_at` 的 WIB 日期；退款 / 取消仍算。业务库关联一律用 public token，读业务库只做窄查询，不做跨库 SQL。
- 汇总表不含 `user_id`、匿名 id 等可识别个人的字段；每张新表在迁移里授权给 `analytics_reader`。

**本 story 验收**

1. **Given** `metric-definitions.yaml` **Then** B、C 类每个指标都有条目：团队编号、定义、来源表、排除规则、已知偏差（卸载重装算新装、iOS `installerStore` 为 null、员工与测试账号、晚到超过 3 天不回算、V1.5.0 之前无数据、接收数为近似、购物车跨设备不可观测等）、SQL 文件位置、变更记录（FR-26）〔L0〕
2. **And** CI 校验每个汇总表都至少被一个条目引用〔L0〕
3. **And** 启动时同步进 `metric_definitions`〔L1〕
4. **And** AI 查数服务新增埋点库连接，使用 `analytics_reader`（只读、3 个连接、30 秒超时）；用该账号查 `events_raw`、`events_raw_p<今天>`、`erasure_requests`、`pipeline_progress` 都返回 permission denied（FR-27）〔L1〕
5. **And** AI 查数的说明文档写明：先查 `metric_definitions`，按口径计算；周期去重用周表 / 月表，不把日表相加；跨库问题只用预拼好的汇总表〔L0〕
6. **And** 用 5 个典型问题（昨日日活、上周 D1 留存、某弹窗上周点击人数、Toko 漏斗、某推送打开率）在 stag 实测，答案与直接查表一致，记进 Completion Notes〔L2〕

**本 story 补充的可验证细则**

7. 只读账号能读白名单表（`events_detail`、`identity_links`、全部 `agg_*`、`agg_progress`、`ga4_daily_snapshot`、`event_catalog`、`metric_definitions`），对埋点库表的任何写语句（`INSERT` / `UPDATE` / `DELETE` / `TRUNCATE`）和在 `public` 建表都失败（临时表权限属 PUBLIC 默认，与业务库只读账号同样处理，见 runbook §7）；会话默认只读、`statement_timeout=30s`、`CONNECTION LIMIT 3`〔L1〕
8. `ai-query-agent` 子进程 env 白名单只多出两个非机密变量（埋点库名、埋点库账号名），密码仍只在 `.pgpass`；`cd ai-query-agent && npm test` 全绿〔L0〕
9. 查数说明书 §5.3「付费成功」改为与本管线口径一致（Toko 按 `shop_orders.paid_at`；非 Toko 按 `metric_definitions` 产品 #3 条目），不再只认 `payment_intents`〔L0〕

### 说明书 §6 必写内容（AC 5）

1. **先查口径**：任何指标问题，先 `SELECT … FROM metric_definitions WHERE …` 找到条目，按条目的定义、来源表、排除规则计算；口径里没有的指标，按最接近的条目给数并在统计口径里写明假设。
2. **周期去重**：「上周 / 上月多少人」一律查 `agg_weekly_*` / `agg_monthly_*`，**绝不把日表人数相加**；次数类（事件条数、订单数）可以相加。比率类月指标 = 当月每日比率的算术平均（S4、产品 #3）。
3. **跨库**：埋点库与业务库不能 join；商品浏览 + 销量、运营位带单、付费占日活等问题只用预拼好的汇总表（`agg_daily_product`、`agg_*_placement`、`agg_daily_ratio` 等），不要自己分两库查再拼。
4. **新鲜度**：汇总是 T+1，`agg_progress` 记各指标族算到哪天；问「今天」时说明汇总还没出，必要时查明细 `events_detail`（只读、3 个月内）。
5. **日活来源**：观察期内日活以 GA4 为准（`ga4_daily_snapshot` / `agg_daily_ratio.dau_source`）；自建日活只作对照；对账结果在 `agg_daily_dau_reconcile`。
6. **时间**：`event_date`、`stat_date`、`week_start`、`month_start` 已是 WIB 日期，不要再转时区；`*_at` 是 UTC。
7. **不在汇总里的人**：汇总表不存个人；「是哪个用户」类问题只能在 `events_detail`（3 个月内）查，且答案里不得展示 `user_id` / 匿名 id / `user_key` 原值。
8. **看不到的表**：`events_raw*`、`erasure_requests`、`pipeline_progress` 无权限是预期，不要尝试。
9. `is_final=false` 的行（7 天窗口未关闭）回答时注明「数字仍会变化」。
10. V1.5.0 之前没有自建埋点数据；问更早的行为数据时直接说明。
