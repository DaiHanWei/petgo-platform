# Story 1.3: 原始层与分区维护

Status: review

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为开发者，
我想要原始层按天分区并自动预建，
以便写入永远有分区可落。

## Acceptance Criteria

本 story 只改后端，**没有前端段，也没有联调段**。云端只能跑 L0；L1（本地 postgres 真跑）留本地。

1. **〔L1〕** 迁移建 `events_raw`（按 `received_at` UTC 日分区，字段对齐 Segment：`message_id`、`event`、`client_ts`、`sent_at`、`received_at`、`anonymous_id`、`user_key`、`user_id`、`source`、`properties`、`context`、`identity_unverified`、`unknown_event`）与 `events_raw_pdefault`；只在 `received_at` 上建 BRIN；**不授权**给 `analytics_reader`。
2. **〔L1〕** `PartitionMaintenanceJob` 每天运行（advisory lock），保证今天起未来 7 天的分区都存在；分区边界用带 `+00` 的时间字面量；重复运行不报错。
3. **〔L1〕** 建分区前若 DEFAULT 里有落在该区间的行：DETACH DEFAULT → 建分区 → 搬行 → ATTACH DEFAULT，同一事务内完成。
4. **〔L1〕** DEFAULT 分区非空时经 TECH 渠道告警；任务失败只告警，不影响接收（FR-12）。
5. **〔L0〕** 单测覆盖分区日期计算：跨月、跨年、UTC 与 WIB 跨日。

## Dev Notes

### 范围

- 只做原始层父表 + DEFAULT + 每日预建。**不做**：删除过期分区（1.7，前提是明细进度已越过该日）、明细层分区（1.6 / 1.7）、写入（1.4）。
- `PartitionMaintenanceJob` 是 1.7 要扩展的同一个类：结构上把「原始层预建」做成一个方法，1.7 再加「明细层预建」「过期删除」，不要把逻辑写死在 `@Scheduled` 方法里。

### DDL

```sql
CREATE TABLE events_raw (
    message_id          varchar(64)  NOT NULL,
    event               varchar(128) NOT NULL,
    client_ts           timestamptz  NOT NULL,   -- 客户端声明的发生时间（请求里的 timestamp），原样
    sent_at             timestamptz  NOT NULL,   -- 客户端声明的发送时间
    received_at         timestamptz  NOT NULL,   -- 服务端收到时间，UTC；分区键
    anonymous_id        varchar(64),             -- 可空：服务端 captureForUser 事件没有匿名 id（Story 1.9）；App 事件由 1.4 接口保证非空
    user_key            varchar(64),             -- 用户标识哈希（AnalyticsDistinctId，sha256 hex 64 位）
    user_id             bigint,                  -- 内部用户 id，只在埋点库内部用，不对外
    source              varchar(8)   NOT NULL,
    properties          jsonb        NOT NULL DEFAULT '{}'::jsonb,
    context             jsonb        NOT NULL DEFAULT '{}'::jsonb,
    identity_unverified boolean      NOT NULL DEFAULT false,
    unknown_event       boolean      NOT NULL DEFAULT false,
    CONSTRAINT ck_events_raw_source CHECK (source IN ('APP', 'SERVER', 'H5'))
) PARTITION BY RANGE (received_at);

CREATE TABLE events_raw_pdefault PARTITION OF events_raw DEFAULT;

CREATE INDEX ix_events_raw_received_at_brin ON events_raw USING brin (received_at);

COMMENT ON COLUMN events_raw.received_at IS '服务端收到时间（UTC），分区键：每天一个分区（UTC 日）';
```

- **`anonymous_id` 可空**：Story 1.9 的 `captureForUser` 服务端事件只有 `user_id`、没有设备匿名 id；明细层（1.6）也按可空设计。设成 NOT NULL 会逼 1.9 再起一条 ALTER 迁移。
- **`anonymous_id` 用 `varchar(64)` 而不是 `uuid` 类型**：App 的匿名 id 是 UUIDv4，但 Story 1.9 的 H5 访客事件用 `AnonymousVisitorId`（`shared/analytics/AnonymousVisitorId.java`，32 位 hex，不是 UUID 格式）作匿名 id，`uuid` 类型会让那一路写入全部失败。UUID 格式只在 1.4 的接口层校验。
- **不建主键 / 唯一约束**：原始层只追加、允许重复（D-2），去重在明细层（D-3）。分区表的唯一约束必须含分区键，在这里也没意义。
- **只建 BRIN**：原始层按 `received_at` 顺序追加，BRIN 体积极小；明细查询走明细层的 B-tree。别加其他索引。
- 枚举 `source` 用 `varchar` + `CHECK`（基线约定），不用 PG enum。
- `properties` / `context` 保存客户端原样内容（经 1.4 校验后的 JSON），原始层是唯一保存完整报文的地方（D-4）。

### 为什么按 `received_at` UTC 分区（D-2）

离线补发的旧事件永远写进**当天**分区，不会写进已删除或已汇总的分区；口径要的 WIB 日期由明细层算出 `event_date`（1.6）。所以本 story 的一切日期计算只用 UTC，**出现 `Asia/Jakarta` 就是写错了**。

### DEFAULT 分区（D-8）

- 正常情况下 DEFAULT 永远为空：7 天预建足以覆盖。只有任务连续失败超过 7 天，或服务器时钟异常，才会有行落进 DEFAULT。
- PG 规则：DEFAULT 里若已有某区间的行，再 `CREATE TABLE ... PARTITION OF` 该区间会直接报错，所以必须先 DETACH、建、搬、再 ATTACH（AC3）。`DETACH` 会对父表加 ACCESS EXCLUSIVE 锁，短暂阻塞写入；只在 DEFAULT 有对应行时才走这条路径，正常每天只走普通 CREATE。
- `CREATE TABLE ... PARTITION OF` 在 DEFAULT 存在时会扫描 DEFAULT 校验无冲突行；DEFAULT 为空时代价可忽略。

### 必须遵守

- 埋点库只经 `@Qualifier("analytics")` 的 `JdbcTemplate` 访问；**禁止 JPA**。
- 锁键只从 `AnalyticsLockKeys` 取（1.1 已定义 `PARTITION_MAINTENANCE`）。
- 定时任务失败只告警，不影响接收（FR-12），也不把管道整体停用。
- `@Scheduled` 线程池全局只有 4 个线程（`spring.task.scheduling.pool.size`），本任务一天一次、毫秒级，不需要专用池。
- 写入账号带 `statement_timeout=120s`；本任务远低于此。
- 迁移只放 `db/analytics-migration/`，版本 `V20261113_1020`；不改 1.1 / 1.2 的迁移。

### 上一 story 的约定（Story 1.1、1.2）

- `AnalyticsPipelineState.isEnabled()`：库不可用 / 迁移失败 / 清单无效时为 false。注意清单无效（`CATALOG_INVALID`）时库其实是好的；本任务只关心库，可在 `Reason` 为 `CATALOG_INVALID` 时照常建分区（建议这样做，免得清单一错连分区也断）。
- `AnalyticsLockKeys.NAMESPACE` + `PARTITION_MAINTENANCE`，两段式 `pg_try_advisory_xact_lock(int, int)`。
- 告警：`OpsAlertService.send(OpsChannel.TECH, dedupeKey, text)`，dedupeKey 带日期，同一天只发一次。
- 测试：`ApiIntegrationTest` 已把埋点池压到 1，埋点测试库 `petgo_analytics_test`。
