# Story 1.7: 明细分区、原始层清理与重算

## Story

作为 Dai，
我想要过期数据按期删除，口径修正后能从原始层重算明细，
以便磁盘可控，算错了也能补救。

## Acceptance Criteria

本 story 只改后端，没有前端段。**云端只跑 L0，L1 / L2 留本地**，在 Completion Notes 标注「L1/L2 待本地验收」。

1. **[L1] 明细层分区维护**：`PartitionMaintenanceJob` 扩展到明细层，按 WIB 日期预建未来 7 天分区，删除超过 3 个月的分区。
2. **[L1] 原始层清理**：原始层删除超过 35 天的分区，前提是 `pipeline_progress` 已越过该日；进度落后时不删并告警。
3. **[L1] 重算入口**：提供按日期区间从原始层重算明细的入口（只限原始层保留期内；对补登记的事件同样适用），重算结果与首次处理一致。
4. **[L0] 删除判定单测**：单测覆盖「哪些分区该删、哪些不该删」的判定。

## Dev Notes

### 前置依赖

本 story 依赖 1.1（埋点数据源、锁键、runbook）、1.2（`EventCatalog`）、1.3（`PartitionMaintenanceJob`、原始层分区、建 / 删分区工具）、1.6（`events_detail`、`pipeline_progress`、`DetailBuilder` 的转换代码）。先读这些代码，以实际类名、列名为准。

### 为什么重算用「请求表」而不是接口

架构规定只新增一个对外端点 `POST /api/v1/analytics/batch`，查数走 AI 只读账号直连，**不新增读写接口**；异步一律「`@Scheduled` + DB 状态机」。所以重算入口做成埋点库里的请求表 + 定时任务消费，由 Dai 用写入账号插一行触发。不要为此新增 HTTP 接口、后台页面或 CLI 参数。[Source: architecture.md 边界、核心约束]

### 重算范围推导（为什么是 −1 分钟 / +7 天）

`event_date ∈ [D1, D2]` 的明细行，其原始行收到时间满足：
- 校正后时间最多晚于收到时间 5 秒（再晚即可疑，日期回落到收到日）→ 收到时间 ≥ D1 的 WIB 零点 − 5 秒；
- 校正后时间最多早于收到时间 7 天（再早即可疑）→ 收到时间 ≤ D2 次日 WIB 零点 + 7 天。

取 −1 分钟 / +7 天 + 1 分钟留余量。范围之外读进来的行按 `event_date` 过滤掉即可。

### 「与首次处理一致」的边界

AC6（Story 1.6）里「日期超出已建分区 → 回落到收到日」取决于处理那一刻有哪些分区。重算时分区集合可能与首次不同（例如首次处理时某天分区尚未预建），极少数行的 `event_date` 会因此不同。这是规则本身的结果，不算回归；在 Completion Notes 记一笔即可。

### 必须遵守

- 删除原始层分区的前提是「那一天已转进明细层」，判据只看 `pipeline_progress` 游标。[Source: architecture.md D-8]
- 日期参数由调用方传入，判定函数内不取当前时间；WIB 换算复用 1.6 的 `EventTimeCorrector` 中的同一个方法。
- 埋点库事务用Story 1.1 暴露的 `analyticsTransactionTemplate`（其事务管理器不注册成 bean），**不要把埋点事务管理器声明成 bean**（会让业务的 JPA 事务管理器自动配置失效，详见 Story 1.6 Dev Notes）。
- 迁移版本 `V20261113_1110`，只放 `db/analytics-migration/`。
- 告警走 `OpsAlertService` TECH 渠道，按天去重键；文案和日志不含任何用户标识与事件内容。
