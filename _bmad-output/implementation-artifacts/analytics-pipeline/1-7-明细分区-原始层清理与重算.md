## Story

作为 Dai，
我想要过期数据按期删除，口径修正后能从原始层重算明细，
以便磁盘可控，算错了也能补救。

## Acceptance Criteria

本 story 只改后端，没有前端段。**云端只跑 L0，L1 / L2 留本地**，在 Completion Notes 标注「L1/L2 待本地验收」。

1. **[L1] 明细层分区维护**：`PartitionMaintenanceJob` 扩展到明细层，按 WIB 日期预建未来 7 天分区，删除超过 3 个月的分区。
2. **[L1] 原始层清理**：原始层删除超过 35 天的分区，前提是 `pipeline_progress` 已越过该日；进度落后时不删并告警。
3. **[L1] 重算入口**：提供按日期区间从原始层重算明细的入口（只限原始层保留期内；对补登记的事件同样适用），重算结果与首次处理一致。
4. **[L0] 删除判定单测**：单测覆盖「哪些分区该删、哪些不该删」的判定。

## Dev Notes

### 前置依赖

本 story 依赖 1.1（埋点数据源、锁键、runbook）、1.2（`EventCatalog`）、1.3（`PartitionMaintenanceJob`、原始层分区、建 / 删分区工具）、1.6（`events_detail`、`pipeline_progress`、`DetailBuilder` 的转换代码）。先读这些代码，以实际类名、列名为准。

### 为什么重算用「请求表」而不是接口

架构规定只新增一个对外端点 `POST /api/v1/analytics/batch`，查数走 AI 只读账号直连，**不新增读写接口**；异步一律「`@Scheduled` + DB 状态机」。所以重算入口做成埋点库里的请求表 + 定时任务消费，由 Dai 用写入账号插一行触发。不要为此新增 HTTP 接口、后台页面或 CLI 参数。[Source: architecture.md 边界、核心约束]

### 重算范围推导（为什么是 −1 分钟 / +7 天）

`event_date ∈ [D1, D2]` 的明细行，其原始行收到时间满足：
- 校正后时间最多晚于收到时间 5 秒（再晚即可疑，日期回落到收到日）→ 收到时间 ≥ D1 的 WIB 零点 − 5 秒；
- 校正后时间最多早于收到时间 7 天（再早即可疑）→ 收到时间 ≤ D2 次日 WIB 零点 + 7 天。

取 −1 分钟 / +7 天 + 1 分钟留余量。范围之外读进来的行按 `event_date` 过滤掉即可。

### 「与首次处理一致」的边界

AC6（Story 1.6）里「日期超出已建分区 → 回落到收到日」取决于处理那一刻有哪些分区。重算时分区集合可能与首次不同（例如首次处理时某天分区尚未预建），极少数行的 `event_date` 会因此不同。这是规则本身的结果，不算回归；在 Completion Notes 记一笔即可。

### 必须遵守

- 删除原始层分区的前提是「那一天已转进明细层」，判据只看 `pipeline_progress` 游标。[Source: architecture.md D-8]
- 日期参数由调用方传入，判定函数内不取当前时间；WIB 换算复用 1.6 的 `EventTimeCorrector` 中的同一个方法。
- 埋点库事务用Story 1.1 暴露的 `analyticsTransactionTemplate`（其事务管理器不注册成 bean），**不要把埋点事务管理器声明成 bean**（会让业务的 JPA 事务管理器自动配置失效，详见 Story 1.6 Dev Notes）。
- 迁移版本 `V20261113_1110`，只放 `db/analytics-migration/`。
- 告警走 `OpsAlertService` TECH 渠道，按天去重键；文案和日志不含任何用户标识与事件内容。

  - `RetentionPolicy`（纯函数，日期 / 游标由调用方传入）：原始层 `d < todayUtc − 35` 且游标 `>= (d+1) 00:00 UTC` 才删，否则列为 `blocked`；游标缺失（进度行不存在）全部挡住。明细层 `d < todayWib.minusMonths(3)`。分区名 → 日期只认 `_pYYYYMMDD`，DEFAULT 永不进候选。

  - `DetailRecomputeJob`（`@Scheduled(fixedDelayString = analytics.recompute.fixed-delay-ms, initialDelayString = analytics.recompute.initial-delay-ms)`，默认均 60 秒；`ApiIntegrationTest` 首延设 1 天，测试直接调 `runOnce()`）：一次处理一条，`RUNNING` 优先、再按 id 取最早 `PENDING`。范围 = `(from 的 WIB 零点 − 1 分钟, min(to 次日 WIB 零点 + 7 天 + 1 分钟, 明细游标)]`（7 天取自 `EventTimeCorrector.PAST_LIMIT`，WIB 用 `EventTimeCorrector.WIB`）；最早原始日分区的 UTC 零点晚于下界（或一个分区都没有）→ `REJECTED`。否则条件 UPDATE 认领为 `RUNNING` → `DetailBuilder.clearForRecompute`（阻塞拿 `DETAIL_BUILDER` 锁，`DELETE … WHERE event_date BETWEEN`，写入账号即表主，无 DDL 锁问题）→ 用与实时同一个 `DetailBuilder.sliceUpper` 按 5 分钟切片（空区间直接跳）→ 逐片 `DetailBuilder.recomputeSlice` → `DONE`。异常 → `FAILED`（`error_code` 只放异常类名，截 64）+ `analytics-detail-recompute-failed:<id>` 告警，不自动重试。

  - 单实例前提（架构：德国单机）：认领用 `WHERE status IN ('PENDING','RUNNING')` 条件 UPDATE；不防两个实例同时重跑同一条崩溃遗留的 `RUNNING`（未新增锁键）。
- **「与首次处理一致」的边界（Dev Notes 要求记录）**：① 「日期超出已建分区 → 回落到收到日」取决于处理那一刻的分区集合，重算时分区集合可能与首次不同，极少数行 `event_date` 会不同，属规则本身的结果；② 同一 `message_id` 多次收到时，批内 `DISTINCT ON` 只取最早一条、跨片靠 `event_date ± 1 天` 查重——两次收到若一个落在同片、一个落在不同片且 `event_date` 相差 > 1 天（例如一次可疑回落），实时与重算的切片边界不同可能导致一边写 1 行、另一边写 2 行。这是 1.6 的既有特性，极罕见，不在本 story 处理。
- **L1 共享库副作用提示**：`PartitionMaintenanceJobIntegrationTest` 用 2099 年固定时钟调 `run()`，现在 `run()` 带过期删除 → 会删掉共享测试库里所有真实日期的明细分区（以及游标已越过的真实原始分区）。生产无此问题；依赖明细分区的 L1 类（`DetailBuilderIntegrationTest`、`DetailRecomputeIntegrationTest`）`setUp` 都会补建所需分区，故不影响；本地验收时留意即可。
- **已知风险**：重算 `FAILED` 后若连状态都写不进（埋点库此时不可用），请求留在 `RUNNING`，实时增量继续暂停，直到下一轮从头重跑成功；`FAILED` 后该区间明细可能不完整，直到人工改回 `PENDING` 重跑完成（告警与 runbook 已写明）。
