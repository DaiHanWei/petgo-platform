# Story 1.5: 身份校验与关联表

Status: ready-for-dev

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为数据使用者，
我想要每条事件的用户归属可信，并且留下完整的登录历史，
以便按「人」统计时不被冒充，也能还原「当时是谁」。

## Acceptance Criteria

本 story 只改后端，**没有前端段**；App 上报 `user_identified` 属 Story 2.2。云端只能跑 L0；L1（本地 postgres + redis 真跑）留本地。

1. **〔L1〕** 迁移建 `identity_links`（只追加；匿名 id、`user_id`、`user_key`、`linked_at`；主键（匿名 id, `linked_at`））；带 JWT 的请求里有 `user_identified` 时追加一行，同一设备反复登录同一账号也每次记一行。
2. **〔L0〕** `IdentityResolver` 逐条判定：没有用户标识的按匿名处理；等于 token 用户的通过；不等于 token 用户的查关联表，有关联则通过，否则去掉用户标识并标 `identity_unverified`；不带 JWT 但带用户标识的同样走关联表。
3. **〔L1〕** 通过校验的 App 事件，`user_id` 取 token 用户或关联表里对应的用户。
4. **〔L0〕** 校验不通过的事件计数并打一条汇总日志（不含标识）。
5. **〔L1〕** 同一设备先登 A、再登 B、再登回 A：关联表三行都在；A 在登出前产生、换号后才补发的事件仍归 A。
6. **〔L1〕** 迁移给 `analytics_reader` 授权 `identity_links`。

- [ ] **`com.tailtopia.analytics.identity.IdentityLinkRepository`**（AC: 1, 2）
  - [ ] `Optional<Long> findUserId(String anonymousId, String userKey)`：`SELECT user_id FROM identity_links WHERE anonymous_id = ? AND user_key = ? LIMIT 1`。
  - [ ] `int[] appendAll(List<IdentityLink>)`：`INSERT ... ON CONFLICT DO NOTHING`（主键冲突 + `message_id` 唯一冲突都吞掉，保证重试幂等）。
  - [ ] 只用 `@Qualifier("analytics") JdbcTemplate`。
- [ ] **`IdentityResolver` 正式实现**（AC: 2, 3, 4）—— 替换 Story 1.4 的直通实现，接口签名沿用 1.4 定的（若 1.4 留的签名不够用，在此调整并同步改 controller）。输入：本批已校验的事件 + 可选 JWT；输出：每条事件填好的 `userKey` / `userId` / `identityUnverified`，以及本批要追加的关联行。
  - [ ] **先确定 token 用户**：JWT 非空、`role` 声明为 `USER`、`sub` 可解析为 long，才算有 token 用户；`tokenUserKey = AnalyticsDistinctId.of(tokenUserId)`。兽医 / 后台等其他角色的 token **按无 JWT 处理**（`sub` 是 vetId，与 `users.id` 撞号；判法同 `ops/popup/web/OpsPopupController.java:70`）。
  - [ ] **再收集本批的新关联**：有 token 用户时，本批里 `event == "user_identified"` 且 `userId`（事件里声明的用户标识）等于 `tokenUserKey` 的每一条，生成一行关联（`anonymousId`、`tokenUserId`、`tokenUserKey`、`linkedAt`、`messageId`），并放进「本批已知关联」集合，供同批后续事件判定。事件里 `userId` 与 token 不符的 `user_identified` **不生成关联**（防止拿别人的 token 给自己的设备挂关联），该事件本身按下面的规则判定。
  - [ ] **逐条判定**（`userKey` = 事件请求里的 `userId` 字段）：
    1. 没有 `userKey` → 匿名：`user_key = null`、`user_id = null`、`identity_unverified = false`。
    2. 有 token 用户且 `userKey == tokenUserKey` → 通过：`user_id = tokenUserId`。
    3. 其余（有 token 但不相等，或没有 token）→ 先查「本批已知关联」，再查 `IdentityLinkRepository.findUserId(anonymousId, userKey)`：查到 → 通过，`user_id` 取关联里的用户；查不到 → **去掉用户标识**（`user_key = null`、`user_id = null`）并标 `identity_unverified = true`。
  - [ ] 同一批里同一个 `(anonymousId, userKey)` 只查一次库（批内 `Map` 记忆即可，**不要做跨请求缓存**——护栏禁止通用缓存层）。
  - [ ] 埋点库查询异常 → 该批所有需要查库的事件按「查不到」处理（剥离 + 标记），不抛、不让接口 500。
  - [ ] 计数（AC: 4）：`AtomicLong` 累计校验不通过的条数；用一个轻量 `@Scheduled(fixedDelay = 5 分钟)` 在计数 > 0 时打**一条** INFO 汇总日志（如 `analytics identity unverified count=37 window=5m`）并清零。日志里**不出现**任何匿名 id、用户标识、用户 id。
- [ ] **关联行的写入**（AC: 1）
  - [ ] 关联行随事件一起进 Story 1.4 的 `IngestQueue`，由 `IngestFlusher` 在**同一个埋点事务**里先写 `events_raw` 再 `appendAll` 关联（事件和关联同生共死；请求线程不做写库）。实现上可以给 `RawEvent` 加一个可空的 `IdentityLink` 字段，或让队列元素是「事件 + 可选关联」的小包装——选一种，保持 1.9 的服务端事件构造仍然简单（服务端事件永远不带关联）。
  - [ ] 1.4 的 flusher 当前是 `batchUpdate` 单条语句；改成在 `analyticsTransactionTemplate` 里执行两条 `batchUpdate`，失败重试语义不变。
- [ ] **测试**
  - [ ] L0 `IdentityResolverTest`（AC: 2, 4），`IdentityLinkRepository` 用 mock：
    - 无 `userKey` → 匿名，不查库。
    - token 为 USER 且相等 → 通过，`user_id = token 用户`，不查库。
    - token 为 USER 但不等 → 查库命中 → 通过，`user_id` 为关联用户；未命中 → 剥离 + 标记。

    - 同批先 `user_identified`（相符）再一条别的事件 → 第二条通过且不查库。
    - `user_identified` 的 `userId` 与 token 不符 → 不生成关联。
    - 查库抛异常 → 剥离 + 标记，不抛。

## Dev Notes

### DDL

```sql
CREATE TABLE identity_links (
    anonymous_id  varchar(64)  NOT NULL,
    user_id       bigint       NOT NULL,     -- 内部用户 id，只在埋点库内部用
    user_key      varchar(64)  NOT NULL,     -- AnalyticsDistinctId.of(user_id)，sha256 hex
    linked_at     timestamptz  NOT NULL,     -- 关联发生时间（UTC），见下
    message_id    varchar(64)  NOT NULL,     -- 来源 user_identified 的 messageId，重试幂等用
    CONSTRAINT pk_identity_links PRIMARY KEY (anonymous_id, linked_at),
    CONSTRAINT uq_identity_links_message_id UNIQUE (message_id)
);
CREATE INDEX ix_identity_links_user_id ON identity_links (user_id);   -- Story 1.8 注销擦除按用户删
COMMENT ON TABLE identity_links IS '匿名 id ↔ 用户关联，只追加；每次登录一行（D-10）';
```

- **`message_id` 列是本 story 在 AC 字段之外加的**：App 重发同一条 `user_identified` 时，若 `linked_at` 取校正后的时间，每次重发的 `sentAt` 不同、算出的时间也不同，单靠主键挡不住重复。加 `message_id` 唯一约束兜住幂等。
- **`linked_at` 取值**：用与明细层一致的校正时间 `client_ts + (received_at − sent_at)`（FR-9 / D-3），这样 1.6 和 Epic 4 按「事件时间 vs 关联时间」判定归属（D-10）时两边口径相同；校正后若晚于 `received_at`，取 `received_at`。
- 只追加：本 story 和后续 story 都**不 UPDATE** 这张表；唯一的删除来自 Story 1.8 注销擦除。
- 不与业务表建外键（FR-11，跨库也建不了）。
- `user_id` 对外不暴露（A4）：只在埋点库内部、AI 只读账号可见，不违反「对外标识不可枚举」。

### 判定规则的来源（架构 A7、D-10）

- A7（本 story 实现）：接收时逐条判定「这条事件声明的用户可不可信」。
- D-10（**不是**本 story 实现，属 1.6 / Epic 4）：**匿名事件**按「人」归属——事件之前有关联归最近一次、之前没有之后有归第一个、从未关联算匿名 id 本身。本 story 只负责把关联表写全、把声明的身份校验对，**不回写匿名事件的 `user_id`**（FR-14「不回写」）。

### 已知边界

- **换号前没发出去的 `user_identified`**：A 登录后 `user_identified` 还在本地队列、没发出去就换成 B，之后它带着 B 的 token 发出 → 与 token 不符 → 不生成关联。A 在这台设备上就缺一行关联，A 之后补发的事件会被剥离。Story 2.2 要求「切换账号前先尝试发完上一账号的事件」以降低概率；剩余情况作为已知偏差，写进 Completion Notes。
- **关联写入有不到 1 秒的延迟**（随 flusher 落库）：同一批里的新关联已用「本批已知关联」覆盖；跨批的极端竞态（前一批的关联还没落库、后一批已到）概率很低，接受。
- 无效 / 过期 JWT 会被安全过滤器直接 401（见 Story 1.4 Dev Notes），不会走到这里。

### 必须遵守

- 日志、告警**一律不出现**匿名 id、用户标识、用户 id（NFR-3、架构 §实现规范 4），只打条数。
- 只认 `role=USER` 的 token（兽医 `sub` 与用户 id 撞号）。
- 不做跨请求缓存（护栏禁止通用缓存层）；批内记忆即可。
- 埋点库只经 `@Qualifier("analytics")` 的 `JdbcTemplate`；禁止 JPA。
- 迁移只放 `db/analytics-migration/`，版本 `V20261113_1040`；不改 1.1–1.3 的迁移。

### 上一 story 的约定（Story 1.1–1.4）

- 1.1：`@Qualifier("analytics")` 的 `JdbcTemplate` / `TransactionTemplate`；迁移授权占位符 `${readerRole}` + 条件 `DO` 块；`ApiIntegrationTest` 埋点池 = 1。
- 1.2：`user_identified` 已在 `event-catalog.yaml` 预登记（`PLANNED`）。它不会被标 `unknown_event`。
- 1.3：`events_raw.user_key varchar(64)`、`user_id bigint`、`identity_unverified boolean`、`anonymous_id varchar(64)`。
- 1.4：接口外层字段 `userId`（可选）= 用户标识哈希，与 `AnalyticsDistinctId.of(long)`（`shared/analytics/AnalyticsDistinctId.java`）和 App 的 `Analytics.distinctIdFor` 逐字一致：`sha256("tailtopia-user-" + id)` 小写 hex；`IdentityResolver` 接口和直通实现、`IngestQueue` / `IngestFlusher`、`RawEvent`。JWT 通过 `@AuthenticationPrincipal Jwt`（可为 null）传入。
