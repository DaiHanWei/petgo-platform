# Story 1.2: 事件清单盘点与口径骨架

Status: review

<!-- 主题 analytics-pipeline，不归属任何版本（App 侧随 V1.5.0 切换）。分支 feat/analytics-pipeline，基于 main。 -->

## Story

作为开发者和 AI 查数，
我想要现有全部事件和后续要新增的事件都登记在一份清单里，
以便明细层知道保留哪些属性，擦除知道清哪些键，AI 知道每个事件的含义。

## Acceptance Criteria

本 story 只改后端（yaml 放在后端 resources），**没有前端段，也没有联调段**。只读 App 代码做盘点，不改 App。云端只能跑 L0；L1 留本地。

1. **〔L0〕** 新增 `analytics/event-catalog.yaml`，登记 App 现有全部事件（扫描 `Analytics.capture` / `capturePurchase` / `buttonTapped` 等调用点）及其属性，以及服务端 `AnalyticsClient` 的全部事件。
2. **〔L0〕** 预先登记 Epic 2、3 将要新增的事件：`user_identified`、`screen_viewed`、`Application Installed / Updated / Opened`、`push_opened`、`toko_cart_item_removed`、`toko_cart_quantity_changed`。
3. **〔L0〕** 每个属性标出是否为用户标识（如 `internal_user_id`、对方用户 id），供擦除使用。
4. **〔L0〕** 新增 `analytics/metric-definitions.yaml`，先放结构和 S1 示例条目。
5. **〔L1〕** 启动时加载两份 yaml 并 upsert 进 `event_catalog` / `metric_definitions`；yaml 格式错误时埋点管道停用并告警、指出出错位置，不阻断后端启动。
6. **〔L1〕** 迁移给 `analytics_reader` 授权这两张表。

## Dev Notes

### 范围

- 只登记现状 + 预登记 8 个事件；**不改任何事件名、不改 App、不改服务端上报代码**。
- 口径文档只放结构与 S1；其余指标条目随 Epic 4（FR-26）补。
- 明细属性过滤（1.6）、擦除（1.8）、`unknown_event` 判定（1.4）只消费本 story 的 API，不在这里实现。

### 为什么清单是唯一来源（架构 D-7、D-9）

- `event-catalog.yaml` 决定：明细层保留哪些属性键（只留登记过的，D-4）；注销时清哪些键（A10）；AI 查数理解事件含义（同步进 `event_catalog` 表）。
- **未登记事件照样收**：进原始层、标 `unknown_event`、不进明细、按天告警，补登记后可从原始层重算（1.4 / 1.7）。所以漏登不会丢原始数据，但会让明细缺数，盘点要尽量全。
- 新增事件的固定三步：在 yaml 登记 → 加 Dart 事件常量 → 比对测试变绿（Story 2.6 起 CI 强制）。

### 命名约定（架构 §实现规范 1）

- 只有 3 个生命周期事件用 Segment 写法（`Application Installed` / `Updated` / `Opened`，带空格、首字母大写）；其余沿用现有 snake_case `<领域>_<对象>_<动作过去式>`。
- 事件**属性**一律 snake_case；请求外层字段 camelCase（1.4）。两层写法不同是有意的。
- `$screen` → `screen_viewed`，页面名放属性 `screen`（如 `toko_page`）。

### metric-definitions.yaml 的 S1 示例

取自 `department-data-summary.zh.md` S1 与 PRD §4.5.1，大意：

- `code: S1`，`name: 日活（DAU）`
- `definition`：WIB 自然日内有 `Application Opened` 的去重人数；另含周合计、周均值、周内最高 / 最低、周增长率、工作日与周末均值。
- `sources`：观察期内用 `ga4_daily_snapshot`（GA4 日活含游客）；对账通过后切 `events_detail` 的 `Application Opened`（FR-24）。
- `exclusions`：只算生产数据；按人统计时只算 `users.role = 'USER'` 且 `account_type = 'REAL'`（Q5）。
- `known_bias`：员工与测试账号算正常用户；日去重人数不能跨天相加（§4.5.1）。
- `sql_path`：`analytics/rollup/dau.sql`（批次 ② 建，现在先写目标路径）。
- `changelog`：`[{date: 2026-11-13, change: 初版骨架}]`。

### 必须遵守

- yaml 加载失败**绝不阻断启动**：业务优先，埋点停用 + 告警。
- 不新增依赖：SnakeYAML、Jackson 都已在 classpath。
- 迁移只放 `db/analytics-migration/`，时间戳 `V20261113_1010`；不改 1.1 的迁移文件。

### 实现备注（dev 2026-11-12）

- **`signup_succeeded` 的 `$set_once` 不登记**：它是 PostHog 人物属性语义（`signup_date` / `first_entry_source`），在自建库里没有意义，`entry_source` 已是普通属性。明细层按 D-4 会把它当未登记键滤掉，完整报文仍在原始层。**Epic 2 移除 PostHog 时一并处理**（届时 `captureSignupSucceeded` 可直接去掉 `$set_once`）。
- **`ktp_unlock_failed` App 与服务端同名**：两端各报一部分失败（App：余额不足 / 请求没到服务端；服务端：支付侧超时 / 拒付 / 取消），清单要求事件名全表唯一，故合并为一条：`source: APP`，`code_ref` 同时写两端文件，属性取两端并集。
- **`tailsonality_match_unlocked`**：服务端代码在发，但现行 `AnalyticsEventGuard` 白名单没收这个名字，PostHog 实际收不到。按「代码在发」登记为 `ACTIVE` 并在描述里写明；是否补进 Guard 属 Story 1.9 改服务端上报时处理。
- **服务端属性以 `AnalyticsEventGuard` 白名单过滤后的为准**：story 列的候选 `author_id` / `virtual_user_id` / `redeemed_by_user_id` 在现有服务端上报里都不存在（grep 核实），未登记；服务端事件没有用户标识属性。
- **用户标识键**：`target_user_id`（`user_followed` / `user_unfollowed` / `user_profile_viewed`，对方用户内部 id）、`owner_id`（`pet_follow` / `pet_unfollow`，宠物主人公开 token）。`internal_user_id` 只出现在 identify 的人物属性里，没有任何事件属性用到，未登记；宠物 id / 帖子 id / 场所 token 不指向用户，不标。
- **金额键照常登记**：`price` / `price_idr` / `total_amount` / `shipping_fee` / `af_revenue` / `af_price` 只在 PostHog 出口被剥（V1.4.2 拍板，`Analytics.posthogProperties`），`scrub()` 不剥，按 story「只排除被 scrub 剥掉的键」登记。
- **预登记属性**：`Application Installed` / `Updated` 的 `version` / `build` / `previous_version` / `previous_build`、`user_identified` 的 `role` 取自已写好的 Story 2.3 / 2.2 文件（Epic 2 定为只改 App、不改 yaml，先登记免得明细层滤掉）；`toko_cart_quantity_changed` 暂无属性、`toko_cart_item_removed` 只登 `reason`，其余由 Story 3.3 补登。
- **App 事件扫描口径**：story 写的「约 191 个」是 grep 逐行匹配的结果；整文件匹配（`\s*` 跨行）为 197 个，另加非字面量的 `keepsake_card_generated`（常量）、`user_followed` / `user_unfollowed`（三元）、`button_tapped`（门面派生），App 共 201 个。`EventCatalogAppCoverageTest` 按整文件匹配。
- **口径 yaml 的告警去重键**用 `analytics-metrics-invalid:<UTC 日期>`（与事件清单的 `analytics-catalog-invalid:` 分开，免得同日两份都坏时第二条被去重吞掉）；同步失败另有 `analytics-catalog-sync-failed:<UTC 日期>`（只告警，不停管道：两张表只给 AI 查数看）。
