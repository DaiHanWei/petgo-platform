# Story 1.5: 打卡后顺手发帖

Status: review

## Story

As a 刚打完卡的用户,
I want 顺手发一条带这个场所的帖子,
so that 这次出门在 Diary 里有一条真正的记录。

**AC4 — 发布请求与服务端校验** `[L1]` `[L0]`
1. `ContentPostCreateRequest` 追加可选字段 `placeCheckinToken`（`@Size(max = 32)`）；**全部兼容构造器**（L56-76 四个）补 `null` 透传，老客户端 / 后台补发 / 既有测试不受影响。
2. App：`ContentRepository.publish` 抽象与 `DioContentRepository` 加 `String? placeCheckinToken`；**非空时才写入请求体**（为空整个键不出现，与 `mentionedUserIds` 同写法，请求体对老路径逐字节不变）。`PublishController.publish` 透传。
3. `ContentService.publish`（L403）：`placeCheckinToken` 非空 → 经 place 包只读口 `PlaceCheckinQueryService.findOwnedCheckinId(authorId, token)` 解析；不存在或**不是本人的打卡** → 422，新 ProblemDetail type `post-checkin-invalid`（`ErrorTypes` 常量 + `AppException` 工厂），**不落库、不审核**（放在三方审核之前，与 @ 名单洗白同一位置）。
4. 通过后把 `placeCheckinId` 写到帖子：**挂起分支（`pendingReview`，L481-498）与正常分支（L505-523）都要写**——同 `imageSizes` / `mentionedUserIds` 两处注释记录的同一个坑，只写一处会让审核挂起的帖永远没有关联。
5. 幂等重放（同 `Idempotency-Key`）照旧直接返回已落帖，不再校验 token。
6. `publishTrusted`（后台 / 种子发布）不接收该字段。
7. 单测 / 集成：本人打卡 → 写入；他人打卡 token → 422 `post-checkin-invalid`；不存在 token → 422；无 token → `place_checkin_id` 为 NULL；UNDER_REVIEW 挂起帖也带关联；删档（1.1 的 `PlaceCheckinDeletionService` 删打卡行）后帖子保留、`place_checkin_id` 被 FK 置空。

### 关键设计点

- **为什么走请求体而不是发布后回填**：里程碑回填是 best-effort 的第二次请求，失败就静默丢关联；打卡关联决定 Diary 里「只出帖子 vs 出打卡条目」（Story 1.6），丢了会让同一件事在 Diary 出两条。AD-10 明确「发布请求可带 `placeCheckinToken`，服务端校验后写入」，一次事务写完。
- **非本人 token 必须拒**：token 不可枚举，但被转发 / 截图泄露后可被别人拿来把帖子挂到别人的打卡上，从而影响对方 Diary 的去重（虽然 1.6 的去重只看本人帖子，拒绝仍是最简单的正确做法）。
- **FK `ON DELETE SET NULL`**：删档时 1.1 的 `PlaceCheckinDeletionService` 会删打卡行，帖子（UGC）按既有口径保留（`ProfileDeletionService` L91-94 的 `detachPet` 同理），关联自动断开，不需要在删档服务里再写一步。
- **场所条是 UI 稿 C6 / C8 的「真实新增组件」**：C6 在发帖页、C8 在详情页，位置都「请核对」过——Epic 定为「文字区后」「正文后、分隔线前」，与 `代码核对报告` §2 对详情页 L283-307 的判断一致。
- **图标不用 emoji**：UI 稿全局规则「不再用 emoji 当图标，唯一保留 emoji 的是用户发布的正文」；Epic 里的「📍」「📸」按线性图标实现。
