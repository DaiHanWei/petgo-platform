# Story 4.5: 两个新渠道的分享奖励

Status: review

## Story

As a 分享了卡片的用户,
I want 第一次分享能领到 PawCoin,
so that 分享更有动力。

## Acceptance Criteria

**AC1 — 迁移：两张渠道账本 + `pawcoin_config` 四列** `[L0]` `[L1]`
1. 新迁移（时间戳号，取创建时刻，如 `V20260929_HHmm__pawcoin_config_add_tailsonality_passport_share.sql`）：
   ```sql
   ALTER TABLE pawcoin_config
       ADD COLUMN tailsonality_share_reward    BIGINT NOT NULL DEFAULT 0,
       ADD COLUMN tailsonality_share_daily_cap INT    NOT NULL DEFAULT 0,
       ADD COLUMN passport_share_reward        BIGINT NOT NULL DEFAULT 0,
       ADD COLUMN passport_share_daily_cap     INT    NOT NULL DEFAULT 0;
   ```
   + 两条 `CHECK (… >= 0)`（照 `ck_pawcoin_age_card_share` 写法）+ 列 `COMMENT`。默认 0 = 不发（RC-3 由运营配）。
2. 新迁移（紧随其后的时间戳号，如 `…__create_tailsonality_passport_share_rewards.sql`）两张表，结构同构：
   - `tailsonality_share_rewards(id BIGSERIAL PK, pet_profile_id BIGINT NULL REFERENCES pet_profiles(id) ON DELETE SET NULL, user_id BIGINT NOT NULL REFERENCES users(id), card_type VARCHAR(16) NOT NULL, coins BIGINT NOT NULL, share_date DATE NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now())`，`CHECK (card_type IN ('RESULT','MATCH'))`，**`UNIQUE (pet_profile_id, card_type)`**，索引 `(user_id, share_date)`；
   - `passport_share_rewards` 同上，`CHECK (card_type IN ('PAGE','BOARDING'))`，**`UNIQUE (pet_profile_id, card_type)`**。
   - 表 / 列 `COMMENT`：去重粒度 = 宠物 × 卡类型；登机牌整体一个卡类型；删档置空、注销物理删除（见 AC5）。
   - ⚠️ 若 Epic 1 / 2 的迁移已按架构 §3「数据种子」提前建了其中某张表，本 story **不重复建**，改为核对其约束与本 AC 一致（不一致且未应用过则改那条迁移；已应用则新迁移 ALTER）。
3. JPA 实体 `share/domain/TailsonalityShareReward.java`、`PassportShareReward.java`（`petProfileId` 为 `Long` 可空）+ 仓库（`findByPetProfileIdAndCardType`、`countByUserIdAndShareDate`、`deleteByUserId`）；`PawCoinConfig` 加四个字段与 getter / setter。`ddl-auto=validate` 启动通过。

**AC2 — 渠道服务：照 KTP 范式的三层闸门** `[L1]`（结构 `[L0]`）
1. NEW `share/service/TailsonalityShareRewardService` 与 `PassportShareRewardService`，形状逐项照 `IdCardShareRewardService`：
   - `rewardAfterShare(long userId, CardType cardType, Instant at)` → 返回真的发了多少枚，0 = 没发；**异常在类内消化、绝不外抛**，不重试、不补偿；
   - 外层 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`，**不要**在自调用方法上标 `@Transactional`——`IdCardShareRewardService` L73-83 记录过这个坑）；
   - 顺序：① 取本人唯一宠物（无档案 → 0）→ ② **资格校验**（见 AC2.3）→ ③ `findByPetProfileIdAndCardType` 已有 → 0 → ④ 读本渠道 `…_share_reward`（≤0 → 0）→ ⑤ 渠道日上限（WIB 日，**调用 `IdCardShareRewardService.shareDateOf` 唯一实现**，不另写换算；`…_daily_cap ≤ 0` 或当日已达 → 0）→ ⑥ `saveAndFlush` 留痕行（撞唯一键 → `AlreadyRewarded` 整体回滚）→ ⑦ 登记「非提交则删 Redis 幂等键」同步器 → ⑧ `ShareRewardService.tryReward(userId, coins, REF_TYPE, null, idemKey, at)`（总开关 + 月度上限），false → `NotGranted` 回滚留痕。
   - 日上限计数前按用户取 `pg_advisory_xact_lock(ns, uid)`（照 `AgeCardShareRewardService` L162-165；两个渠道各取一个不与既有 `DAILY_CAP_LOCK_NS` 相撞的命名空间常量）。
   - `REF_TYPE` = `TAILSONALITY_SHARE` / `PASSPORT_SHARE`；钱包幂等键 = `tailsonality-share:{petProfileId}:{cardType}` / `passport-share:{petProfileId}:{cardType}`（与去重键同源，重放不重复入账）。
2. **每只宠物每卡类型只发一次**：RESULT、MATCH 各一次，PAGE、BOARDING 各一次；**带水印卡同样计**（接口不收、不看水印态）；**重测后再分享不再发**（键是宠物不是结果）；**登机牌整体一个卡类型，不按张计**（接口不收场所 token）。
3. 资格校验（防止没生成过卡就刷接口）：`RESULT` / `MATCH` → 该宠物至少有一条 Tailsonality 结果；`MATCH` 另需本人已设主人类型；`PAGE` → 该宠物已签发护照且至少 1 枚章；`BOARDING` → 该宠物至少 1 条场所打卡。读口一律走各模块的 QueryService（Epic 1 / 2 提供，名称以实际代码为准），**不跨模块直接注入别人的 Repository**。
4. 集成测试（照 `IdCardShareRewardIntegrationTest`）：首次发、同卡类型二次不发、另一卡类型再发一次、重测后不发、带水印（接口无差别）照发、日上限、月度上限、总开关关、渠道额 0 不发、无资格不发、并发两次只发一次、发放失败不留痕。

### 关键设计点

- **去重粒度 = 宠物档案 × 卡类型**（AD-13；PRD §3.2 / §3.3；内容设计 §2.5）：按卡实例计会让「打卡数 = 奖励数」「重测 → 分享 → 拿币」无限循环。所以接口**不收**结果 token、场所 token，只收卡类型。
- **`UNIQUE(pet_profile_id, card_type)` 与可空 `pet_profile_id`**：PostgreSQL 唯一约束对 NULL 不判重，删档置空后的多条历史行不会互撞；同一只活着的宠物仍被约束挡住。
- **注销口径与 AD-17 的差异（已按现有代码定）**：AD-17 写「两张分享奖励表是资金流水，保留；注销时随既有口径（与 PawCoin 流水一致）」，但**既有口径**是：`ShareRewardDeletionService` 在注销时物理删除所有分享奖励留痕，PawCoin 钱包 / 流水也由 `PawCoinAccountDeletionService` 作废并物理删除（`AccountDeletionService` L173-180 注释）。本 story 采用「删档置空、注销物理删除」，与同胞两张表一致（该类注释：同一用户各渠道留痕在注销后表现必须一致）。已列入给产品 / 架构的冲突清单。
- **KTP 渠道删档时其实没有置空**：`id_card_share_rewards.pet_profile_id` 是 `NOT NULL` 且无外键（V20260825_0248），删档后留着指向已删档案的悬空 id。epics AC 写「与 KTP 渠道一致」不准确——新表按 AD-17 用 `ON DELETE SET NULL`，**不**顺手改 KTP 表（超范围）。
- **闸门串联**：全局总开关、月度上限、渠道单次额、渠道日上限，任一为 0 都不发（V20260825_0247 注释）。上线默认全 0，RC-3 由运营配置。
- **不做「可宣传枚数」接口**：KTP 渠道有 `advertisableCoins` 是因为卡面页有「分享可得 N PawCoin」文案；本批次 UI 没有这类文案，不加（加了就要守「配好了才显示」的承诺规则）。
- **App 端「取消不发币」在客户端成立**：`CardExport.shareImage` 非 success 返回 null → `onShared` 不触发（`card_export.dart` L41-44、L100-102）。
