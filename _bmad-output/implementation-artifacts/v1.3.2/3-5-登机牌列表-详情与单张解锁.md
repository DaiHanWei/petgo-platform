# Story 3.5: 登机牌列表、详情与单张解锁

Status: ready-for-dev

## Story

As a 去过好几个地方的用户,
I want 每个去过的地方都有一张登机牌,
so that 每一趟出门都像一张可以收藏的票。

**AC2 — 解锁表** `[L0]` `[L1]`

`boarding_pass_unlocks(id BIGINT IDENTITY PK, public_token VARCHAR(32) NOT NULL UNIQUE, pet_profile_id BIGINT NOT NULL REFERENCES pet_profiles(id) ON DELETE CASCADE, place_id BIGINT NOT NULL REFERENCES places(id), unlocked_at TIMESTAMPTZ NULL, superseded_at TIMESTAMPTZ NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), CONSTRAINT uq_boarding_pass_pet_place UNIQUE (pet_profile_id, place_id))`；部分索引 `(superseded_at) WHERE superseded_at IS NOT NULL`；表 / 列 COMMENT（`superseded_at` 非空 = 合并后该行不再代表任何卡；若同时 `unlocked_at` 非空 = 用户为同一场所付过两次，后台人工退款）。

**AC3 — 列表接口** `[L1]`
`GET /api/v1/pet-profiles/me/boarding-passes`（与 1-2 的 `/me/passport` 同属 `/api/v1/pet-profiles/me/` 前缀，新控制器 `BoardingPassController` 放 passport 包），需 `USER`：
1. 该宠物每个打过卡的场所一张（**= 1-2 的 `PlaceStampQueryService.stampsOf(petId)`**：按当前 `place_id`，合并后自动一张、下架仍在）；按最近到访日期倒序。
2. 响应：`{ petName, passportNo, items: [ { placeToken, placeName, placeType, placeStatus（1-2 的 `PlaceAvailability`：ACTIVE | UNAVAILABLE）, lastVisitDate, visitCount, unlocked } ] }`；`unlocked` = 该 `(pet, place_id)` 解锁行存在、`unlocked_at` 非空、`superseded_at` 为空。
3. 价格不进本接口（App 读 `keepsakePricingProvider.boardingPass`，3-2 交付）。
4. 无打卡 → `items: []`（App 空态，见 AC6.3）。

**AC4 — 详情接口** `[L1]` `[L0]`
`GET /api/v1/pet-profiles/me/boarding-passes/{placeToken}`：
1. `placeToken` 经 `resolveForView` 同款逻辑解析：MERGED → 保留方；**DELISTED 照常返回**（卡仍在）；该宠物在该场所无打卡 → 404。
2. 字段：`passenger`（宠物名）、`breed`（宠物档案 `breed` 原文，可空）、`placeName`（TO）、`passportNo`（1-2 的护照号，12 位）、`lastVisitDate`（DATE）、`firstVisitDate`、`visitCount`（VISITS）、`seat`、`placeType`、`placeStatus`、`placeImageUrl`（该场所首张可见照片，复用 `PlaceQueryService` 取照片的 `photos.findVisibleForPlaces` + `photoService.publicUrlOf`；无照片 → null）、`addressText` + `city`（**仅 ACTIVE 时下发**；DELISTED / MERGED 解析失败时为 null）、`unlocked`、`unlockToken`（解锁行 token，未建行为 null）。
3. **SEAT**：passport 包新建 `BoardingPassSeat.of(long petProfileId, long placeId) → String`：`SHA-256("seat:" + petId + ":" + placeId)` 取前 4 字节无符号整数 `n`，行号 `n % 40 + 1`（两位补零）+ 座位字母 `"ABCDEF".charAt((n / 40) % 6)`，如 `02A`；**不存储、无业务含义**。单测：同入参恒同值；不同入参分布在合法范围；格式 `^\d{2}[A-F]$`。
4. 不下发距离（UI 稿 B3b 的「· 1,2 km」为示意；本版本登机牌不取定位）。

**AC5 — 单张解锁** `[L1]`
`POST /api/v1/pet-profiles/me/boarding-passes/{placeToken}/unlock`，body `{ "channel": … }`，需 `USER`：
1. 解析场所（同 AC4.1，DELISTED 允许购买——卡仍在）；该宠物在该场所无打卡 → 404。
2. `INSERT INTO boarding_pass_unlocks(pet_profile_id, place_id, public_token) … ON CONFLICT (pet_profile_id, place_id) DO NOTHING`，再 `SELECT … FOR UPDATE` 取行；`unlocked_at` 非空（且未 superseded）→ 409 `keepsake-already-unlocked`。
3. `KeepsakeRef(BOARDING_PASS, row.id, row.publicToken, petId, row.unlockedAt != null)` → `KeepsakePurchaseService.start`；响应 `KeepsakePurchaseResponse`。
4. 已解锁后该场所再到访：只更新次数（聚合现算），**不产生任何新购买**（测试：解锁后再打卡两次，`keepsake_purchases` 行数不变、`unlocked` 仍 true）。
5. 限流 `rl:boarding:unlock:{userId}` 10 次 / 分钟；`SecurityConfig` 精确 matcher → `hasRole("USER")`（GET 列表 / 详情同样精确列出）。

**AC6 — 发放** `[L1]`
`BoardingPassGranter implements KeepsakeGranter`（`sku() = BOARDING_PASS`），不抛异常：
1. 行不存在（删档）→ `REF_MISSING`。
2. 行未 superseded：`UPDATE … SET unlocked_at = now() WHERE id = :refId AND unlocked_at IS NULL` → 1 行 `GRANTED`，0 行 `ALREADY_UNLOCKED`。
3. 行已 superseded（付款期间场所被合并）：沿 `places.merged_into_id` 找最终场所，对 `(pet, 最终 place_id)` 的行执行 2 的逻辑（无行则先 `INSERT … ON CONFLICT DO NOTHING` 再更新）→ `GRANTED` / `ALREADY_UNLOCKED`。
4. 单测覆盖以上四种路径。

**AC7 — 合并场所时改挂（同一事务）** `[L1]`
passport 包新建 `BoardingPassMergeService.reassignForMerge(long mergedPlaceId, long keepPlaceId)`，由 `PlaceMergeService.merge`（`admin/places/service/PlaceMergeService.java` L55-84）在 `checkins.reassignPlace(...)` 之后、`markMerged` 之前**同步调用**（同一 `@Transactional`，**不走** `PlaceMergedEvent` 监听器）。对被合并方每一行（逐宠物）：

| 被合并方行 | 保留方同宠物行 | 处理 |
|---|---|---|
| 任意 | 无 | 被合并方行 `place_id` 改为保留方 |
| 未解锁 | 有 | 被合并方行置 `superseded_at = now()`（在途付款到账时由 AC6.3 转到保留方行） |
| 已解锁 | 有、未解锁 | 保留方行 `unlocked_at` = 被合并方的 `unlocked_at`；被合并方行 `superseded_at = now()` 且 `unlocked_at = NULL`（**不需退款**；购买记录仍 PAID，订单中心跳转按 3-6 解析到保留方） |
| 已解锁 | 有、已解锁 | 被合并方行置 `superseded_at = now()`、**保留** `unlocked_at` → 后台可筛出「付过两次」供人工退款（3-6） |

- 返回改挂 / supersede 条数，`PlaceMergeService` 把它追加进审计详情串（照 L77-79 的 `checkins=` 写法加 `boardingPasses=`）。
- 集成测试走真实 `merge`：四种情形各一例；`reassignForMerge` 抛异常 → 整个合并回滚（照片 / 评论 / 打卡都未改挂）。
- 更新 `PlaceMergeService` 类注释 L3-7 与 `PlaceCheckinRepository` L14 注释里「护照章归并由 App 分支监听事件实现」的过期描述（章是聚合，无需监听；登机牌改挂为同事务调用）。

### 关键设计点

- **粒度 = 宠物 × 当前场所**：列表与详情都按当前 `place_id` 聚合；合并后原两张卡变一张，解锁状态按 AC7 矩阵转移。
- **为什么合并在同一事务同步调用**（AD-7）：若用 AFTER_COMMIT 监听，合并提交到监听执行之间的窗口里，用户可对保留方再买一张（UNIQUE 在两个 place_id 上各一行不冲突），造成重复付款且不可见。
- **superseded 行不删**：它可能挂着 PENDING / PAID 购买（`ref_id` 指向它）；删了到账就成 ORPHAN。`unlocked_at` 是否保留决定它是不是退款候选（AC7 第 3 / 4 行）。
- **DELISTED 场所可以买**：卡仍在、是历史事实；只是地址与跳转换成「不存在」。
- **SEAT 纯装饰**（D-5）：确定性、不存、无含义；不要为它建列。
- **护照号 12 位单独一行**（PRD §3.3 / UX-DR15）：与 DATE / VISITS 三栏平分会被截断。
