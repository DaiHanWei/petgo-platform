# Story 1.1: 场所详情页打卡与到场校验

Status: review

## Story

As a 带着宠物到了一家宠物友好场所的用户,
I want 在场所详情页点一下就能打卡,
so that 这次到访被记下来。

## Acceptance Criteria

**AC1 — 迁移与数据** `[L0]` `[L1]`
1. 新迁移（时间戳号，取创建时刻，如 `V20260929_HHmm__add_place_checkin_pets.sql`）：
   - `place_checkins` 加 `public_token VARCHAR(32)`、`origin_place_id BIGINT REFERENCES places(id)`、`visit_date DATE`；**先回填存量行**（`origin_place_id = place_id`；`visit_date = (checked_at AT TIME ZONE 'Asia/Jakarta')::date`；`public_token` 用 SQL 生成的随机 32 位 base62 串或 `md5(random()::text || id)` 截断——只要唯一且不可枚举）再 `SET NOT NULL` + `UNIQUE(public_token)`。
   - 新表 `place_checkin_pets(checkin_id BIGINT NOT NULL REFERENCES place_checkins(id) ON DELETE CASCADE, pet_profile_id BIGINT NOT NULL REFERENCES pet_profiles(id), origin_place_id BIGINT NOT NULL, visit_date DATE NOT NULL, PRIMARY KEY(checkin_id, pet_profile_id))` + **`UNIQUE(pet_profile_id, origin_place_id, visit_date)`** + 索引 `(pet_profile_id)`。
   - 两表加 `COMMENT`；`place_checkins` 的表注释更新（合并归并现由 admin 合并事务内 `reassignPlace` 完成，章为聚合，见架构 delta AD-4 / AD-5）。
2. App 侧新建 JPA 实体 `com.tailtopia.place.domain.PlaceCheckin`（`@Entity(name = "PlaceCheckin")`）与 `PlaceCheckinPet`，列定义与既有 `AdminPlaceCheckin` 一致；**不改** `AdminPlaceCheckin` 的已有字段（它不必映射新列，但 `@PrePersist` 等行为不能因新 NOT NULL 列失效——admin 侧**从不插入**打卡行，确认这一点并在注释写明）。

**AC2 — 打卡接口** `[L1]`
`POST /api/v1/places/{token}/checkins`，body `{ "latitude": double, "longitude": double, "petIds": [long] }`，需登录（`USER` 角色）。
1. 场所解析走既有 `places.resolveForView(token)`：ACTIVE 直接用；MERGED 解析到保留方（打卡记在保留方，`origin_place_id` = 保留方 id）；**DELISTED / 删除 / 不存在 → 既有 404 `not-found`「场所不存在」**（沿用 V1.3.0 1.5 的决定：下架与不存在刻意不可区分，**不新增**「场所不可用」类型）。
2. 坐标：缺任一 / `GeoBox.isValidCoordinate` 不通过 → 422 `validation`。
3. `petIds`：必须非空且**全部属于当前用户**（本版本即唯一宠物）；否则 403，新 type `checkin-pet-forbidden`。账号没有宠物档案 → 422，新 type `checkin-no-pet`。
4. 距离：`GeoBox.distanceMeters(请求坐标, 场所坐标) ≤ 500` 才通过；否则 422，新 type `checkin-too-far`，**ProblemDetail 的 detail 与扩展字段里都不得出现距离值**。
5. 每日限一次：以 **WIB 自然日**判定，该宠物在**当前 `place_id`**（含已合并进来的原场所的历史打卡）当天已有打卡 → 409，新 type `checkin-already-today`。
6. 通过后同一事务写 `place_checkins`（`place_id` = `origin_place_id` = 当前场所 id，`visit_date` = 今日 WIB，`public_token`）+ 每只宠物一行 `place_checkin_pets`。
7. 并发兜底：唯一约束冲突（`DataIntegrityViolationException`）→ 转 409 `checkin-already-today`，**不得 500**（照 `PlaceService.report` 的 catch 写法）。
8. 响应 `201`：`{ checkinToken, placeToken, placeName, placeType, visitDate, isNewStamp, visitCount }`。`isNewStamp` = 本次写入前该宠物在当前 `place_id` 无任何打卡；`visitCount` = 写入后该宠物在当前 `place_id` 的打卡总数。（`passportNo` / `stampCount` 由 Story 1.2 追加。）
9. 限流：`rl:place:checkin:{userId}`，10 次 / 分钟（与 report 同量级，常量放 `PlaceController` 顶部）。
10. **坐标不落库、不进日志、不进埋点**：服务层与控制器不得 log 请求体；有一条测试断言 `place_checkins` / `place_checkin_pets` 无经纬度列、且打卡服务源码中不出现对 latitude / longitude 的 log 调用。

**AC3 — 详情接口带「今日已打卡」** `[L1]` `[L0]`
`PlaceDetailResponse` 新增 `Boolean checkedInToday`：已登录用户 = 本人宠物今天在该场所是否已打卡；游客 = **省略该键**（与 `distanceMeters` 为 null 时省略同一机制）。
- 后端 `PlaceDetailResponseContractTest`：`FULL_FIELDS` 加入 `checkedInToday`；排除列表中移除 `checkedIn` 类的旧禁词里与新字段冲突的项，**保留** `checkinCount` / `canCheckIn` 等仍然不该有的键；新增「游客响应不含 `checkedInToday`」一例。
- DTO 与 `PlaceDetail`（Dart）javadoc / 注释里「没有打卡字段（⑧ 在批次 B2）」改为描述新字段。

**AC4 — 详情页打卡按钮** `[L2]`
1. 位置：`_body` 中**距离行之后、描述之前**，整宽按钮「Check-in」（不吸底；吸底评论输入条原样保留，**禁止**用 `bottomNavigationBar`，有源码扫描测试）。距离行因无定位被省略时，按钮照常在名称 / 标签区之后。
2. 点击流程：`requireLogin` → 读定位权限（`LocationGateway.status()`）：
   - `denied` → `request()`；仍拒绝 → 不打卡，按钮保持可点；
   - `permanentlyDenied` → 弹「Izinkan lokasi / Buat check-in, TailTopia perlu tahu kamu ada di lokasi.」+「Nanti」「Buka Pengaturan」，后者走 `openSettings()`；
   - `granted` → `currentCoordinates()`；为 null（GPS 关 / 超时）→ 轻提示「Lokasi belum ketemu, coba lagi」。
3. 取到坐标后以**原始精度**提交（**不得**复用详情查询的 `placeDetailQueryFor` 三位小数归一）。提交中按钮 loading、防重复点击。
4. 失败提示（按 `ProblemDetail.typeSlug`）：`checkin-too-far` →「Kamu harus berada di lokasi untuk check-in」；`checkin-already-today` → 按钮切禁用态；`checkin-no-pet` →「Buat profil anabulmu dulu buat check-in」；`not-found` → 既有「场所不存在」处理；其它 → 通用失败 + 可重试。
5. 当日已打卡（`checkedInToday == true` 或刚收到 409）：按钮为**禁用态**「Sudah check-in hari ini」，**不隐藏**。
6. 本页反向验收仍成立：无收藏、无评分、无营业时间 / 电话、无编辑入口（`PlaceControllerNoEditEndpointTest` 与 App 侧 AC6 源码扫描仍须通过，按新字段更新断言而非删除）。
7. `petIds` 由 App 取当前唯一宠物（`petProfileProvider` 的 `id`）组成数组；界面**不渲染**宠物选择器。

**AC5 — 打卡成功页** `[L2]`
新路由 `/places/:token/checkin-success`（顶层 `GoRoute`，与 `/places/:token` 并列，结果经 `extra` 传入，照 `/me/refunds/pawcoin-success` 写法；`extra` 缺失时返回场所详情，不崩）。成功后 `context.push` 进入；返回键回到详情页，详情页刷新为「今日已打卡」。
1. `isNewStamp == true`（C2）：顶栏「Check-in」· 小尺寸章面（新建 `PlaceStampView(placeType, imageUrl)` 组件，本 story `imageUrl` 恒 null → 按类型的**占位章**：圆形描边 + 类型图标，原色、不做圆形裁切以外的处理；Story 1.2 / 1.4 复用并接真素材）+ 落章轻反馈（缩放 + 淡入，一次，≤400ms）+「Check-in berhasil!」+「{placeName} · {日期}」+「{pet} dapat cap baru」。
2. `isNewStamp == false`（C2b）：同骨架，章角标「×{visitCount}」跳动一次 +「Cap {placeName} sekarang {visitCount}×」；**不出**「Lihat Paspor」、不播整页落章。
3. 底部按钮「Lihat Paspor」「Rekam Momen Ini」**本 story 都不显示**（分别由 Story 1.2 / 1.5 接入）；页面只留返回。
4. 动效有静态兜底（章面 + 文案即可读懂结果）。

**AC6 — 删档与后台** `[L1]` `[L0]`
1. 新建 `place` 包内 `PlaceCheckinDeletionService.deleteForPet(petId, userId)`：删该宠物的 `place_checkin_pets`，再删该用户名下**已无任何关联宠物**的 `place_checkins`。在 `ProfileDeletionService.deleteByUserId` 中、`petProfiles.delete(pet)` **之前**调用（与 `contentPosts.detachPet` 同段）。配集成测试：删档后两表无该宠物 / 该用户残留，且**同一天重建宠物可在同一场所再次打卡**。
2. 后台打卡计数开关：stag 环境变量设 `ADMIN_PLACES_CHECKIN_VISIBLE=true`（改 `~/.env.petgo-stag` 由操作者执行，本 story 在 Completion Notes 提醒）；prod 列入发版检查单 RC-2，代码默认值**不改**。
3. `AdminPlaceQuerySqlTest` 钉的统计 SQL 不受影响（仍按 `place_checkins.place_id` 计数），测试不应变红。

### 关键设计点

- **为什么唯一约束放在 `place_checkin_pets` 且键是 `origin_place_id`**：admin 合并场所用 JPQL `UPDATE place_checkins SET place_id = keep` 把打卡改挂保留方（`PlaceMergeService` L73）。唯一键若用 `place_id`，合并当天会撞约束让合并失败；用打卡当时的场所 `origin_place_id`（永不改）则合并永不冲突。**「今日已打卡」的业务判定另按当前 `place_id` 查**（合并进来的原场所历史也算），DB 约束只是并发兜底。
- **删档后同日重建能再打卡**：唯一键含 `pet_profile_id`，新宠物是新 id，天然不冲突；删档服务同时清掉旧宠物的关联行与孤儿打卡行。
- **坐标精度**：详情查询为隐私把坐标归一到约 110m（`placeDetailQueryFor`），**打卡必须用原始坐标**，否则站在门口也可能被判超 500m 附近的误差。
- **不返回距离**：防用户试探边界。ProblemDetail 的 `detail` 用固定文案。
- **`isNewStamp` 口径**与 Story 1.2 的「章 = (宠物, 当前 place_id) 聚合」一致：该宠物在当前场所此前 0 次打卡即新章。
