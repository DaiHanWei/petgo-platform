# Story 3.1: 一次性解锁的购买链路与后台定价

Status: ready-for-dev

## Story

As a 运营,
I want 在后台设置三项新付费的价格，并且用户付的每一笔都有据可查,
so that 上线即可调价，对账不出错。

**AC4 — purchase 包：发起购买** `[L1]`
新包 `com.tailtopia.purchase`（NEW），对外只暴露：
1. `KeepsakeSku`（`TAILSONALITY | PASSPORT_SNAP | BOARDING_PASS`，与 `PaymentPurpose` 同名；`toPurpose()`）。
2. `KeepsakeGranter` 接口（**定义在 purchase 包，由 SKU 模块实现**）：
   ```java
   KeepsakeSku sku();
   GrantOutcome grant(long refId, long purchaseId);   // 不得抛异常
   ```
   `GrantOutcome` = `GRANTED | ALREADY_UNLOCKED | REF_MISSING`。Spring 按 `sku()` 收集成 `Map<KeepsakeSku, KeepsakeGranter>`，启动时校验三个 SKU 各恰好一个实现（缺失 / 重复 → 启动失败，有单测；本 story 内用测试替身实现，真实实现由 3.2 / 3.4 / 3.5 交付）。
3. `KeepsakePurchaseService.start(long userId, KeepsakeRef ref, PayChannel channel) → KeepsakePurchaseResponse`，其中 `KeepsakeRef(KeepsakeSku sku, long refId, String refToken, Long petProfileId, boolean alreadyUnlocked)` 由 SKU 模块在**加锁读业务行之后**构造传入：
   - `alreadyUnlocked == true` → 抛 409 ProblemDetail，新 type `keepsake-already-unlocked`（`ErrorTypes.KEEPSAKE_ALREADY_UNLOCKED` + `AppException.keepsakeAlreadyUnlocked(detail)`）。
   - `MIXED` → `AppException.validation("该商品不支持混合支付")`（与 `IdCardHdService` L116-119 同句，显式 case，不落 default）。
   - 价格：按 sku 读 `platformConfig.pricing()` 对应列（TAILSONALITY → `tailsonalityUnlockPrice`，PASSPORT_SNAP → `passportPageUnlockPrice`，BOARDING_PASS → `passportBoardingUnlockPrice`），**每次发起实时读**。
   - **幂等键**：基键 `{sku}:{refToken}`（如 `TAILSONALITY:Ab3…`），**禁止**用 petId / userId；**按渠道加后缀**：PawCoin 用 `{基键}:PAWCOIN`，QRIS 用 `{基键}:QRIS`（原因见 Dev Notes「幂等键撞车」——`IdempotencyService` 是全局 `idem:` 命名空间，同一串给 `createIntent` 与 `debit` 会让「先开过 QRIS 再改用 PawCoin」被当成扣币重放而**免费解锁**）。
   - **PAWCOIN**：同一事务内 `wallet.debit(userId, price, PawCoinTxnType.SPEND, refType=sku.name(), refId=ref.refId(), key)` → 插购买行（`status=PAID`、`pay_channel=PAWCOIN`、`price_idr=price`（即扣币额）、`paid_at=now`、`payment_intent_id=null`）→ 同步调 `granter.grant(refId, purchaseId)` → 按结果回写 status（GRANTED 保持 PAID；ALREADY_UNLOCKED → `DUPLICATE_PAID`；REF_MISSING → `ORPHAN_PAID`）→ 返回 `unlocked=true`。余额不足 `debit` 抛 `pawcoin-insufficient`（409）整事务回滚。
   - **QRIS**：`paymentIntents.createIntent(userId, sku.toPurpose(), QRIS, price, "IDR", key, 60min)` → 取意图实体 id →
     - 该业务行已有 PENDING 购买行且 `payment_intent_id` 相同 → 复用（不新建行）；
     - 已有 PENDING 行但意图 id 不同（旧意图已过窗被 `createIntent` 懒过期，L101-103 **不发** `PaymentIntentFailedEvent`）→ 先把旧行置 `EXPIRED`，再插新 PENDING 行；
     - 意图已是 `PAID`（`createIntent` 对 PAID 直接返回既有意图）→ 不建行，重读业务行：已解锁 → 返回 `unlocked=true`，否则 409 `keepsake-already-unlocked`（交人工）；
     - 新行 `price_idr = intent.amount`（**取意图金额**，不取本地变量）、`pay_channel=QRIS`、`status=PENDING`。
     - 向网关取码：抽出 `IdCardHdService.ensureCharge`（L225-257）的同款逻辑到 purchase 包私有方法（**不改** `IdCardHdService`），失败时 `failChargeAttempt` 留档；方法加 `@Transactional(noRollbackFor = PayException.class)`（照 `purchaseCard` L84-85 的注释理由）。
     - 返回 `unlocked=false` + `payment`（`PaymentIntentResponse`，含 `displayNo`）+ `payload`。
   - `KeepsakePurchaseResponse(boolean unlocked, PaymentIntentResponse payment, String payload, String purchaseToken)`：前三项形状**与 `HdPurchaseResponse` 一致**（App 可复用解析逻辑），`purchaseToken` 为购买行 `public_token`。
4. 有测试：①同宠物两个**不同业务行**各买一次 → 两次真实扣币（钱包余额减两次价）；②同一业务行 PawCoin 重放 → 只扣一次；③同一业务行先 QRIS 发起、再改 PawCoin → **PawCoin 真实扣币**（钉住渠道后缀）；④同一业务行两次 QRIS 发起 → 同一购买行、同一意图；⑤已解锁 → 409；⑥MIXED → 422；⑦`price_idr` 分别等于 `intent.amount` / 扣币额；⑧后台改价后新发起用新价、已有 PENDING 行价不变。

**AC5 — 到账：唯一监听器** `[L1]`
1. `KeepsakePaidHandler`（purchase 包）：`@EventListener` + `@Transactional(propagation = Propagation.MANDATORY)`（照 `IdHdPaidHandler` L28-37，**绝不 AFTER_COMMIT**）；只处理 `event.purpose() ∈ {TAILSONALITY, PASSPORT_SNAP, BOARDING_PASS}`，其余 return。
2. 按 `payment_intent_id` 找购买行：找不到 → `log.warn`（只记 intentId，不记 token）并返回，**不抛**；已是 PAID / DUPLICATE_PAID / ORPHAN_PAID → 返回（重放幂等）；PENDING / EXPIRED / CANCELED → 置 PAID、`paid_at=now`、`price_idr = event.amount()` → 同步 `grant` → 回写 DUPLICATE_PAID / ORPHAN_PAID。
3. **`grant` 不抛异常**；handler 仍用 try/catch 兜底：任何 RuntimeException → 购买行置 `ORPHAN_PAID` 并 `log.error`，**不向上抛**（向上抛会回滚 `applyCallback` 的 `markPaid`，到账状态就丢了）。
4. 成功发放（GRANTED）后发布领域事件 `KeepsakeUnlockedEvent(long userId, KeepsakeSku sku, long refId, long priceIdr, PayChannel channel)`，PawCoin 路径同样发布；供 3.2 / 3.4 / 3.5 的 AFTER_COMMIT 埋点监听器使用（**埋点监听器不得订阅 `PaymentIntentPaidEvent`**，保持「三个新 purpose 只有一个消费者」）。
5. `KeepsakePaymentFailedHandler`（purchase 包）：订阅 `PaymentIntentFailedEvent`，三个 purpose 内按 `failureCategory` 把对应 PENDING 行置 `EXPIRED`（EXPIRED）或 `CANCELED`（GATEWAY_DECLINED / USER_CANCELLED）；非 PENDING 不动。
6. 测试：模拟 `applyCallback` 重复到账两次 → 购买行 PAID 一次、`grant` 调一次；业务行已解锁时到账 → `DUPLICATE_PAID` 且意图仍 `PAID`；业务行已删（删档）时到账 → `ORPHAN_PAID` 且意图仍 `PAID`；`grant` 抛异常的替身 → 意图仍 PAID、购买行 ORPHAN_PAID；源码扫描测试：`src/main` 中带 `PaymentIntentPaidEvent` 参数且引用三个新 purpose 的监听方法只在 `KeepsakePaidHandler`。

### 关键设计点

- **幂等键撞车（必须按渠道加后缀）**：`IdempotencyService` 是全局 `idem:` 前缀、24h TTL；`createIntent` 成功后把 `key → intentId` 写入它；`debit.isReplay` 只看「该 key 在 Redis 有映射 **或** 总账有同键分录」。若 QRIS 与 PawCoin 用同一串 key：用户先点 QRIS（映射写入）→ 关掉 → 改点 PawCoin → `debit` 判为重放直接 return、**不扣币**，随后业务行被解锁 = 免费拿到。AD-1 的「`debit` 与 `createIntent` 同用」指**同一粒度**（业务行 token），不是同一字符串；本 story 以 `:PAWCOIN` / `:QRIS` 后缀落实，并以 AC4.4 ③ 钉住。（⚠️ 既有 KTP `purchaseCard` 两路同用 `"id-hd-card:" + cardId`，存在同一漏洞——不在本 story 范围，已在交付报告中上报，勿顺手改。）
- **业务行先于购买存在**（AD-1）：SKU 模块负责建 / 锁业务行并判「是否已解锁」，purchase 包不认识任何业务表；`ref_id` 固定指向业务行 id。
- **到账永不回滚**：`KeepsakePaidHandler` 运行在 `applyCallback` 的事务里（MANDATORY）；任何抛出都会把 `markPaid` 一起回滚、网关下次回调再来——宁可记 `ORPHAN_PAID` 交人工，也不让到账状态丢。
- **一个 purpose 一个消费者**：埋点、订单等下游一律订阅 `KeepsakeUnlockedEvent`（AFTER_COMMIT），不再订阅 `PaymentIntentPaidEvent`。
- **`price_idr` 是唯一成交价**：展示、对账、订单中心、仪表盘都只读它；改价只影响新发起。
- **0 元**：D-3 否决，库 CHECK 与服务校验同为 ≥1，不做零价短路（后台 PRD 的「允许 0 = 限免」段落已被 D-3 作废）。
- **命名**：包名 `purchase`、前缀 `Keepsake*`；**不要**复用 `IdCardHdPurchase*`（KTP 专表）。
