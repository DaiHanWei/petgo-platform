# Story 3.6: 我的订单与后台支付查询接入

Status: ready-for-dev

## Story

As a 买过东西的用户 / 处理售后的运营,
I want 在「我的订单」和后台支付列表里查到这三类购买,
so that 用户能回到买过的东西，运营能处理重复付款。

## Acceptance Criteria

**AC1 — 订单类型与能力闸** `[L0]` `[L1]`
1. 后端 `order/dto/OrderType.java`（现 5 值，L7-19「只在末尾追加」）**末尾追加** `TAILSONALITY`、`PASSPORT_SNAP`、`BOARDING_PASS`。
2. `OrderController.orders`（L38-46）追加 `@RequestParam(required = false, defaultValue = "false") boolean includeKeepsake`，透传给 `OrderCenterService.listOrders`（签名追加同名参数；既有调用点与测试同步）。
3. 闸门规则照电商（`OrderCenterService` L124-129）：`(filter == null && includeKeepsake) || filter ∈ {TAILSONALITY, PASSPORT_SNAP, BOARDING_PASS}` 才查新源；**老 App 不传 → 聚合结果与改动前逐字一致**（集成测试：同一用户有三类购买，不带参数请求返回中无新类型）。
4. `parseType` 对三个新值正常解析（老 App 不会传）。

**AC2 — 新数据源：`keepsake_purchases`** `[L1]`
1. `KeepsakePurchaseRepository`（3-1）新增 `findOrderCenterPageBefore(userId, statuses, skus, beforeTs, beforeId, pageable)`：`WHERE user_id = :userId AND status IN :statuses AND sku IN :skus AND (created_at < :beforeTs OR (created_at = :beforeTs AND id < :beforeId)) ORDER BY created_at DESC, id DESC`（**与 `ShopOrderRepository.findOrderCenterPageBefore` 同形**，排序键与归并全序逐字一致）。
2. `statuses` = `PAID`、`DUPLICATE_PAID`、`ORPHAN_PAID`（都是「钱已到账」）；`PENDING / CANCELED / EXPIRED` **不入订单中心**（与 A-5「仅已付 / 持久订单」一致）。`skus` = 筛选值对应的单个 sku，或聚合时三个全要。
3. 新 RANK 常量 `RANK_KEEPSAKE = 4`（追加在 `RANK_SHOP = 3` 之后，L178-181「只追加、不重排」）；三类共用一个 rank（同一张表，id 唯一）。
4. `OrderCenterService` 构造器追加 `KeepsakePurchaseRepository`（追加在末尾，不动既有 8 个依赖），`listOrders` 在电商分支之后追加本分支（照 L120-129 的注释口径写明「追加在 if 链末尾」）。
5. 翻页正确性测试：新源与既有四源同刻（相同 `created_at`）混排、跨页边界不漏不重（照 `OrderCenterIntegrationTest` 的 ORDER-CENTER-CURSOR-TIE 用例补一例）。

**AC3 — 卡片与详情映射** `[L1]` `[L0]`
1. 卡片 `mapKeepsake(KeepsakePurchase p)` → `OrderSummaryView`（用既有 8 参构造，`OrderSummaryView` L40-46）：`orderType` = sku 名、`orderToken` = 购买行 `public_token`、`displayNo` = `OrderDisplayNo.of(<新前缀>, p.getId(), p.getCreatedAt())`、`amount` = **`price_idr`**、`payChannel` = `pay_channel`、`createdAt` = `created_at`。
2. `OrderDisplayNo` 追加前缀常量：`TAILSONALITY = "TSL"`、`PASSPORT_SNAP = "PASPOR"`、`BOARDING_PASS = "BPASS"`（与支付号 `PAYTS / PAYPASS / PAYBP` 刻意不同名，照 `PaymentDisplayNo` 类注释的理由）。
3. `statusCode` / `statusColor`：`PAID` → `"PAID"` / `SUCCESS`；`DUPLICATE_PAID`、`ORPHAN_PAID` → 新码 `"UNDER_REVIEW"` / `INFO`（钱已收、待客服人工处理，蓝非红，UX-DR2 口径）。
4. 详情 `getDetail`（L205-231）在电商分支后追加：`keepsake_purchases.findByPublicToken` + owner 校验（越权与不存在同为 404）。
5. `OrderDetailView` **末尾追加**两个组件 `String targetKind`（`TAILSONALITY_RESULT` / `PASSPORT_SNAPSHOT` / `BOARDING_PASS`）与 `String targetToken`，并**保留**一个与现有 20 参完全相同的构造器委托新全参（照 `OrderSummaryView` L32-46 的做法——record 加组件会让既有 5 个构造点编译失败）。
6. `targetToken` 解析（经各 SKU 模块提供的只读接口，order 包**不直接查** SKU 表）：
   - TAILSONALITY → 结果行 `public_token`（行不存在 → null）；
   - PASSPORT_SNAP → 快照行 `public_token`（仅 `paid_at` 非空时；否则 null）；
   - BOARDING_PASS → 解锁行所在场所沿 `merged_into_id` 到最终场所的 **place token**（行不存在 → null）。
   - 为此在 purchase 包定义只读接口 `KeepsakeTargetResolver { KeepsakeSku sku(); Optional<String> targetToken(long refId); }`，由 3-2 / 3-4 / 3-5 的 SKU 模块各实现一个（本 story 负责补上三个实现）。
7. 详情其余字段：`paidAt` = `paid_at`；`petName` / `petType` / `petAvatarUrl` 取 `pet_profile_id` 对应档案，为 null 或档案已删 → `petDeleted = true`（照 `vetDetail` 的 FR-54D 口径）。

**AC5 — 后台：一次性解锁异常查询** `[L1]` `[L2]`
支付记录页（`/admin/payments`，权限 `payment.view`，`AdminPaymentController.VIEW_AUTH` L26）只查 `payment_intents`，PawCoin 购买没有意图、查不到——因此新增同权限子页：
1. `GET /admin/payments/keepsake-exceptions`（`@PreAuthorize(VIEW_AUTH)`，**与支付页同一个权限码**，入口只放在支付页顶部的一个页内链接 / 标签，**不新增侧栏项**，入口门与页面门逐字同一个表达式）。
2. 两个列表（各自分页 20 条，按时间倒序）：
   - **异常购买**：`keepsake_purchases.status IN ('DUPLICATE_PAID','ORPHAN_PAID')`；列：购买号（`OrderDisplayNo` 同款）、用户 id、SKU（i18n）、渠道、`price_idr`、状态（i18n）、`paid_at`（WIB，照 `AdminPaymentQueryService` L204-206 格式）、关联支付号（有意图时 `PaymentDisplayNo`，点击打开既有支付抽屉 `/admin/payments/{intentToken}/drawer`）。
   - **登机牌重复解锁**：`boarding_pass_unlocks.superseded_at IS NOT NULL AND unlocked_at IS NOT NULL`（3-5 AC7 第 4 行「付过两次」）；列：用户 id、原场所名 → 保留场所名、`unlocked_at`、`superseded_at`、该行关联的 PAID 购买号。**不显示宠物名**以外的 PII（宠物名也不显示，用户 id 足够定位）。
3. 只读：本页不提供退款按钮；运营按「既有人工退款流程」处理（页面顶部一行说明文案）。
4. 服务：admin 包新建 `AdminKeepsakeExceptionQueryService`，经 purchase / passport 包提供的只读查询取数（admin → purchase / passport 的依赖方向允许）；**不返回** token 以外的内部 id 给模板以外的地方。
5. i18n 四个文件（`messages.properties` / `_en` / `_id` / `_zh_CN`）补齐本页所有 key（页面标题、两个分区标题、列名、状态 `DUPLICATE_PAID` / `ORPHAN_PAID`、说明文案、空态）；模板内不得硬编码中文（`AdminMessagesExternalizedTest` 与同类 i18n 齐全性检查通过）。
6. 测试：有 `payment.view` 可看、无权限 403；两分区各造一条数据可见；PAID / PENDING 购买不出现；`AdminPagesRenderSmokeTest` 加本页。

### 关键设计点

- **唯一新源是 `keepsake_purchases`**（AD-8）：不从结果 / 快照 / 登机牌三张业务表各拉一次；金额只读 `price_idr`（成交价以购买记录为准，NFR-2）。
- **「退款态」口径**：AD-8 / epics 写「PAID 及退款态」，但 AD-1 定义的购买状态集里**没有退款状态**（退款走既有人工流程、不回写本表）。本 story 以「钱已到账」三态（PAID / DUPLICATE_PAID / ORPHAN_PAID）为入列条件，后两者对用户显示「Sedang dicek」——**2026-09-29 决策 D-15：用户侧显示**，免得以为钱丢了。
- **一个 rank 三个类型**：三类同表、id 全局唯一，单 rank 足够且游标最简单；筛选按 sku 过滤。
- **跳转目标由 SKU 模块解析**：order 包不认识结果 / 快照 / 登机牌表，经 `KeepsakeTargetResolver` 只读取 token；登机牌跳场所 token 时沿合并链走到最终场所。
- **后台子页不进侧栏**：沿用支付页的权限码，入口在支付页内；避免「侧栏条件与页面门不一致」。
