# Story 1.3: 标记一个场所

Status: review

## Story

As a 发现了一家能带狗进的咖啡店的用户,
I want 把它标记下来,
so that 别人也能找到这个地方，我自己下次也不用再翻记录。

## Acceptance Criteria

**AC1 — 字段全集（FR-112.1）** `[L0]`
名称必填 ≤80 · 类型单选**7 类全给**（咖啡店/餐厅/公园/商场/酒店民宿/宠物服务/其他）· 宠物友好标签多选 ≥1 且**6 个全给**（允许入内/户外座位/宠物餐食/宠物活动区/需牵引/大型犬友好）· 文字地址必填 · 照片 1–9 张单张 ≤10MB · 描述选填 ≤200。
⚠️ UI 稿 A5 的类型与标签是**示意省略**，实现必须按全集。

**AC2 — 保存按钮态** `[L2]`
必填未填满时「保存」**灰色禁用**；全部满足才变亮可点。不允许"点了没反应又不说少了什么"。

**AC3 — 位置来源** `[L2]`
本 story 位置取**当前定位**（地图选点在 Story 1.4 加，**本条不依赖它**）。未授权定位时明确提示需要位置，不静默失败。

**AC4 — 不可修改的前置告知** `[L2]`
表单渲染时即告知「提交后不可修改，请仔细核对」（本版用户不可编辑场所，2026-09-15 拍板）。

**AC5 — 服务端硬拒编辑** `[L0]`
服务端**不提供任何场所编辑接口** —— 硬拒而不是只在前端藏入口。

**AC6 — 成功态** `[L2]`
Toast「场所标记成功」并返回列表/详情。

**AC7 — 失败态** `[L2]`
字段级校验未通过时**只出内联错误**，请求**不真的发出**，**不叠加**通用「提交失败」横幅。

**AC8 — 审核与图片** `[L1]`
照片与文字走既有三方自动审核（先发后审）；照片走既有上传链路进**公开桶**并完成 EXIF 剥离兜底。

**已交付（L0 全绿）**

   名称必填 ≤80 · 类型单选 · 标签 ≥1（≤6）· 文字地址必填 ≤255 · 照片 1–9 张（元素 `@NotBlank`）·

2. **AC5「服务端硬拒编辑」做成了可证伪的测试**：`PlaceControllerNoEditEndpointTest` 用反射断言
   `PlaceController` 没有 `@Put/@Patch/@DeleteMapping`、没有经 `@RequestMapping(method=...)` 绕过去的写方法，
   且 `PlaceService` 没有 `update*/edit*/delete*/remove*` 公开方法。
   🔴 **「没有写某个端点」这件事，没有测试的话没人会注意到它被加上了** —— 加一个 `@PatchMapping`
   是三行代码，评审时看起来像是在补功能。
3. **审核：先发后审**（AC8 / PRD ① / F10）。L1 硬拦截（TEXT/IMAGE_BLOCKED）→ 即时拒绝不落库；
   **RISKY / DEGRADED → 照常落库**，运营走后台 AB-17A 处置。
   - 🔴 **送审文本含「文字地址」**：它同样是用户自由输入的一行字，漏掉等于留了个
     「把违规内容写在地址栏里」的口子。用换行拼接而非空格 —— 空格会把「名称尾字+地址首字」
     意外连成命中词。
   - ⚠️ **DEGRADED（三方挂了）在内容帖那边是 fail-closed 挂起，这里是放行** ——
     这是「先发后审」这条产品口径的直接后果，不是漏写。要改成 fail-closed 属产品决策，
     已在代码注释与测试用例名里写明，回决策日志谈。
4. **EXIF 服务端兜底 + 列表省流量**（AC8 / CROSS-STORY E4）：新增
   `AliyunOssClient.exifStrippedThumbUrl(url, width)`，一条 `x-oss-process` 里同时写
   `resize,w_320` 与 `format,jpg`。
   🔴 **为什么不能直接用既有的 `exifStrippedDeliveryUrl`**：客户端的 `AppImage.ossResized`
   遇到已带 `x-oss-process` 的 URL 会原样放过，于是「服务端去 EXIF」与「客户端取缩略图」
   变成二选一 —— 而列表里 20 张原图会把首屏拖垮。写成一条串两件事就都成立。
   去 EXIF 靠的是 `format,jpg` 的重编码，不是 resize。
5. **App 表单页**（AC1/AC2/AC3/AC4/AC6/AC7）：

   - **AC4 前置告知**在最上面、在所有输入之前（不是提交时才弹）；

**code-review 复审后修掉的（9 findings 全修）**

1. 🔴 **内联错误是死代码**：`_showErrors` 只在 `_onSubmit` 的 `!canSubmit` 分支里设，而保存按钮
   在 `!canSubmit` 时是禁用的 —— 那个分支**永远走不到**，于是 AC7 的内联错误一条都不会显示。
   → 改为**按字段 touched 判**（`_Field` 枚举 + `_touched` 集合）：用户在名称里打了字又删空就立刻
   看到错误，而刚进页面时一片干净。提交兜底分支改为把所有字段标成 touched。
2. 🔴 **「权限给了但定点没拿到」是个死胡同**：那时既没有「开启定位」按钮（权限已有）、
   保存又一直是灰的，退出重进也一样（provider 缓存着那个 null）。而这是**常态**
   （定位总开关关着 / 室内 5 秒没定点）。
   → 没有坐标时**永远有一个可点的东西**：缺权限 → 「开启定位」，权限有了 → 「重新定位」
   （invalidate 定位 provider 整条重跑）；正在定位时显示转圈而不是按钮。
3. 🔴 **登录后回跳会把导航栈整个换掉**：`RouteIntent(location:)` 走 `context.go`，而 `/places/new`
   是 shell 之外的顶层路由 —— 没有返回按钮、没有底部导航、安卓返回键直接退出 App，
   表单里那句 `pop(true)` 弹掉的还是唯一一页（与 V1.1.6 Story 2.4 名片深链踩过的是同一个坑）。
   → 改用 `RouteIntent(onResume:)` 命令式 `push`，并加 `context.mounted` 守卫。
4. 🔴 **确定性失败报成「请重试」**：审核硬拦截（422）与限流（429）重试一万次结果都一样，
   一句「请重试」把用户按在死循环里。
   → 按 `ProblemDetail.typeSlug` 分流出三条专用文案（text-blocked / image-blocked / rate-limited）。
5. 🔴 **创建端点没有幂等键**：场所既不能编辑也不能删除，丢一个 201（弱网常见）+ 用户再点一次保存
   = 一个**永久重复**的条目，只能等运营去后台合并。
   → 后端接 `Idempotency-Key` 头（同 `POST /content-posts` 范式，重放取回原条目**且不重复过审核**）；
   前端**整页只生成一次** key（每次点保存换一个的话幂等就白做了）。
6. 🔴 **兽医 token 能创建场所**（安全）：端点原先落到 `anyRequest().authenticated()`，而本方法把
   `jwt.sub` 当 `users.id` 用 —— 兽医 token 的 sub 是 vetId，两个命名空间大量碰撞，
   `created_by` 又没有外键，会被静默写进去。而用户不可编辑场所 → 这条错归属**没有自助纠正途径**。
   → `SecurityConfig` 显式 `POST /api/v1/places → hasRole("USER")`。
7. **`photoUrls` 元素缺 `@NotBlank`**：`[""]` 能过「≥1 张」，结果是列表里 `photoCount=1`
   却只有占位图的场所。→ 元素加 `@NotBlank`。
8. **一张上传失败丢掉整批**：已传上公开桶的对象变成孤儿，还要用户从头再选一次。
   → 逐张 try/catch，成功的进草稿、最后提示一次失败。
9. **`exifStrippedThumbUrl` 会拼出两个 `x-oss-process`**：OSS 只认一个，缩放或去 EXIF 会被静默丢掉。
   → URL 已带 `x-oss-process` 时原样返回（与客户端 `ossResized` 同一条判据）。

**范围边界（有意不做）**

- **地图选点**归 Story 1.4 —— 本页位置只取当前定位，**不预留**一个点不动的「在地图上选」按钮；
- **提交成功后跳详情**归 Story 1.5（详情页还不存在），本条先 `pop` 回列表（AC6 允许「返回列表/详情」）；
- 场所**没有**用户侧删除能力（同一条不可编辑决策）—— 用户能自删的是**自己的场所评论**（Story 1.7）。
