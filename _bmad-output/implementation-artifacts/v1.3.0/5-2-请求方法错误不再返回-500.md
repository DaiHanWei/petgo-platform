# Story 5-2: 请求方法错误不再返回 500

Status: ready-for-dev

> 自包含 story，**纯后端**（`petgo-backend/`），只改 `GlobalExceptionHandler` 一个类 + 测试，无迁移、无 App 端改动、无业务逻辑变更。
> 与用户沟通用中文。执行纪律见根 `CLAUDE.md`（`mvn -B clean package`）。

## Story

As a 运维，
I want 用错请求方法（或错的 Content-Type）时返回 405 / 415 而不是 500，
so that 告警里不再混入这类根本不是服务端故障的噪声。

## Context

### 现状：`GlobalExceptionHandler` 已有的分支

`petgo-backend/src/main/java/com/tailtopia/shared/error/GlobalExceptionHandler.java`：

| 行 | 异常 | 状态码 | 备注 |
|---|---|---|---|
| :47 | `AppException` | `ex.getStatus()` | 带 `ProblemExtensions` 扩展成员 |
| :65 | `OptimisticLockingFailureException` | 409 | 转 `AppException.conflict` |
| :71 | `MethodArgumentNotValidException` | 422 | 带 `fieldErrors` |
| :83 | `NoResourceFoundException` | 404 | |
| **:97-104** | `MissingServletRequestParameterException` / `MethodArgumentTypeMismatchException` / `HttpMessageNotReadableException` / `MissingServletRequestPartException` | **400** | detail 固定「请求格式不正确」，type = `ErrorTypes.VALIDATION`，title = 字面量 `"Bad Request"` |
| :114 | `MaxUploadSizeExceededException` | 413 | |
| :169 | `AccessDeniedException` | —— | 原样重抛交回 Spring Security |
| :174 | `Exception`（catch-all） | **500** | `log.error("Unhandled exception [traceId={}]", traceId, ex)` + 通用文案，绝不外泄堆栈 |

**确认：400 类确实已处理完（:97-104 四种），缺的只剩 `HttpRequestMethodNotSupportedException`（405）与 `HttpMediaTypeNotSupportedException`（415）**。这两个目前落进 :174 的 catch-all → 500 + `log.error` 打整条堆栈 → 告警噪声。

### 信封构造

`base(status, type, title, detail, req)` :243-245 → :247-257：`ProblemDetail.forStatusAndDetail` + `setType` + `setTitle` + `setInstance(req.getRequestURI())` + `setProperty("traceId", ...)`。**遵循这个方法就自动符合统一错误格式**，不需要自拼。

`titleFor(HttpStatus)` :264-274 只被 `handleApp` 用；400 组是直接传字面量 title 的（:101 `"Bad Request"`）。本 story 照 400 组的做法传字面量。

### `ErrorTypes` 现有常量

`shared/error/ErrorTypes.java`：`VALIDATION` / `UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `CONFLICT` / `RATE_LIMITED` / `INTERNAL` + 若干业务专属 type。**没有** 405 / 415 对应项。

### 🔴 Spring 默认行为已被本类接管

`@ExceptionHandler(Exception.class)`（:174）兜住了**所有**异常，因此 Spring 的 `DefaultHandlerExceptionResolver` 根本轮不到 —— 它本来会给 405 自动补 `Allow` 响应头、给 415 补 `Accept` 头。本 story 自己接住这两个异常后，**必须自己设这两个头**，否则 405 的响应会缺 `Allow`（HTTP 语义上 405 必须带 `Allow`）。

### 测试基建

- `src/test/java/com/tailtopia/shared/error/GlobalExceptionHandlerTest.java`：standalone MockMvc（:29-32，`standaloneSetup(new PingErrorController()).setControllerAdvice(handler())`）+ 直接调 handler 方法（:55-78 的 413 用例）两种范式并存。
- `PingErrorController`（`src/main/java/com/tailtopia/shared/error/PingErrorController.java`）只有 `GET /api/v1/_ping-error`，**对它 POST 就会触发 405**。
- 测试包里已有先例的「测试专用控制器」：`src/test/java/com/tailtopia/shared/error/H5BoomTestController.java` —— 415 的用例可照此新建一个测试专用控制器，不要去改 `PingErrorController`（那是 main 里的 dev-profile 诊断端点）。

## Acceptance Criteria

**AC1 · 405**
**Given** 任意端点被用了它不支持的 HTTP 方法（如对只声明 `@GetMapping` 的路径发 POST）
**When** Spring 抛 `org.springframework.web.HttpRequestMethodNotSupportedException`
**Then** `GlobalExceptionHandler` 新增分支返回 **405 METHOD_NOT_ALLOWED** `[L0]`
**And** 响应带 `Allow` 头，值由 `ex.getSupportedHttpMethods()` 生成（为 `null` 时不设该头，不 NPE）`[L0]`
**And** 响应体走 `base(...)`：含 `type` / `title` / `status=405` / `detail` / `instance` / `traceId` 六项 `[L0]`

**AC2 · 415**
**Given** 请求体的 `Content-Type` 不被目标端点接受
**When** Spring 抛 `org.springframework.web.HttpMediaTypeNotSupportedException`
**Then** 返回 **415 UNSUPPORTED_MEDIA_TYPE**，信封同 AC1 六项齐备 `[L0]`
**And** 响应带 `Accept` 头，值由 `ex.getSupportedMediaTypes()` 生成（为空列表时不设该头）`[L0]`

**AC3 · 不外泄堆栈、不外泄内部细节**
**Then** 两种响应的 `detail` 是**固定中文文案**（405 建议「请求方法不被支持」、415 建议「不支持的请求内容类型」），**不含** `ex.getMessage()`、不含类名、不含包名、不含任何堆栈片段 `[L0]`
**And** 响应体除 `base(...)` 的六个字段外无其它属性 `[L0]`

**AC4 · 不再产生 error 级日志**
**Given** 405 / 415 发生
**Then** **不**走 :174 catch-all 的 `log.error("Unhandled exception ...", ex)` `[L0]`
**And** 新分支若要记日志，用 `log.warn` 或 `log.debug`，且**只记方法 / URI / 支持的方法集合**，不记异常堆栈 —— 「不再污染告警」正是本 story 的全部目的 `[L0]`

**AC5 · 既有分支零回归**
**Then** `GlobalExceptionHandlerTest` 既有 6 条（AccessDenied 重抛、413 × 2、ProblemDetail 信封、locale 回落等）全绿 `[L0]`
**And** `AccessDeniedException` 仍原样重抛（:169-172 不动）、catch-all 的 H5 页面分支（:184-188）不动、413 的异常链判定（`isUploadTooLarge`）不动 `[L0]`
**And** 🔴 新分支必须放在 `@ExceptionHandler(Exception.class)` **之前**（Spring 按最具体的异常类型匹配，顺序不影响正确性，但保持文件可读性照既有排布：接在 :97-104 的 400 组之后、413 之前）`[L0]`

**AC6 · 测试覆盖两种异常**
**Then** 新增至少 4 条用例：405 状态码 + `Allow` 头、405 信封六项、415 状态码 + `Accept` 头、415 信封六项 `[L0]`
**And** 405 用**真实 MockMvc 分发**（对 `PingErrorController` 的 `GET /api/v1/_ping-error` 发 POST）—— 证明 advice 真的接得住，而不是只证明方法本身能构造 ProblemDetail `[L0]`
**And** 至少一条断言「响应体不含 `HttpRequestMethodNotSupportedException` / `org.springframework` 等字样」 `[L0]`

## Dev Notes

### 为什么 405 必须带 `Allow`

HTTP 语义要求 405 响应携带 `Allow` 头。Spring 的 `DefaultHandlerExceptionResolver` 本来会自动加，但本类的 `@ExceptionHandler(Exception.class)`（:174）把所有异常都截走了，那条默认路径**永远走不到**。这与 :208-212 注释里说的「`H5ErrorController` 接不到，因为本类兜住了所有异常」是同一种坑 —— 本类每接管一个 Spring 原生异常，就同时接管了它原有的响应头职责。

### 为什么不直接把这两个异常并进 :97-104 的 400 组

那一组统一返 400。405/415 是不同的状态码，且各自要带不同的响应头。硬塞进去要么状态码错、要么方法体里塞 `instanceof` 分叉 —— 都比新开两个方法差。

### 为什么日志降级是 AC 而不是「顺手」

SHOP-FR-31 的动机原文是「用错请求方法时服务端返回 500，**污染告警**」。如果只改状态码、日志仍是 `log.error` + 堆栈，告警噪声一点没少 —— 需求等于没做完。所以 AC4 是硬 AC，实施时别把它当锦上添花。
