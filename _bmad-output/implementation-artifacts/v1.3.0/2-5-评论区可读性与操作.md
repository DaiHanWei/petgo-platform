# Story 2.5: 评论区可读性与操作

Status: review

## Story

As a 用户，
I want 认出谁是作者、给评论点赞、长按能操作、没评论时有引导，
so that 评论区不是一堆读不出层次的文字。

---

> **依赖 Story 2.3**（底栏结构）与 **Story 2.4**（点赞接口与热度序）。
>
> 现状：评论区**没有**点赞、没有作者标识、没有时间显示、没有长按菜单，空态只有一行纯文字。

---

## Acceptance Criteria

### AC1 — 评论点赞与时间（L2）

**Given** 任一条评论（一级或二级）
**When** 渲染
**Then** 显示心形点赞图标与计数，可点赞/取消 `[L2]`
**And** 显示相对时间；超 7 天显示绝对日期 `[L2]`
**And** 时间规则与详情页（Story 2.2）**使用同一套规则、同一个格式化函数**，不写第二份 `[L0]`

### AC2 — 作者标签零接口变更（L0 / L2）

**Given** 一条评论的作者就是本帖作者
**When** 渲染该评论
**Then** 昵称旁显示「作者 / Penulis」标签 `[L2]`
**And** 该判定由客户端比对**两个已有 id** 完成 `[L0]`
**And** 服务端**不下发额外字段、不加标记位** `[L0]`

### AC3 — 长按菜单（L2）

**Given** 任一条评论
**When** 长按
**Then** 弹出底部菜单，样式参照既有底部动作面板（`_showMoreSheet`）的列表行 `[L2]`
**And** 自己的评论显示：复制文字 / 回复 / 删除 `[L2]`
**And** 他人的评论显示：复制文字 / 回复 / 举报 `[L2]`

### AC4 — 权限不放宽（安全攸关，L1）

**Given** 长按菜单的删除项
**When** 判定是否可见与可用
**Then** 沿用既有 `_canDelete` 权限判定与 `_confirmDelete` 二次确认 `[L1]`
**And** **不放宽**任何权限 `[L0]`
**And** 举报沿用既有 `openReport` 流程 `[L1]`

### AC5 — 空态（L2）

**Given** 一条没有任何评论的内容
**When** 打开评论区
**Then** 显示一枚 emoji/插画 + 引导语（现状仅一行纯文字，无插画） `[L2]`
**And** 文案为 EN `No comments yet — say something!` / ID `Belum ada komentar, yuk mulai obrolan!` `[L0]`
**And** 底部固定输入框仍然存在 `[L2]`

### AC6 — 🔴 自己刚发的评论必须可见（L2）

**Given** 用户刚发出一条新的一级评论（0 赞）
**When** 列表按热度重新拉取
**Then** 该条被置于列表首位、当次会话内始终可见 `[L2]`
**And** 该条**不参与游标计算** `[L0]`
**And** 离开详情页后该置顶失效 `[L2]`

> 🔴 不做这条会出现：在一个有 10+ 条热门评论的帖子里，用户发完评论后**看不到自己刚发的东西**（0 赞排在所有有赞评论之后，落在第一页外）。

### AC7 — 不扩散（L0）

**Then** 不改动回复态（属 Story 2.6） `[L0]`
**And** 不改两级结构、不动审核链路 `[L0]`

### Completion Notes List

**已交付（L0 全绿）**

1. **AC1 时间 —— 抽成共用函数而不是写第二份**。Story 2.2 那套规则（7 天内相对、超 7 天绝对）
   原本是详情页里的一个私有方法。本 story 要求「同一套规则、同一个格式化函数」，
   所以把它提到 `shared/utils/date_format.dart` 的 `formatPublishTime`，
   详情页改为调用它。**两处显示的是同一类东西，各留一份迟早分叉** ——
   一边「173 天前」一边「15 Jun 2025」，用户会以为是两种不同的时间。
   （点赞图标与计数在 Story 2.4 已落地，本 story 只补时间行。）
2. **AC2 作者标签零接口变更**：`isPostAuthor = c.authorId == widget.postAuthorId`，
   两个 id **详情页响应里本来就都有**。服务端没加任何字段、没加标记位。
   注销作者不挂标签（与 NFR-8 一致：不给注销账号任何身份线索）。
3. **AC3/AC4 长按菜单**：样式直接照抄详情页 `_showMoreSheet` 的结构
   （把手 + 左对齐行 + 底分隔线 + Batal），不另造视觉。
   自己的：复制 / 回复 / **删除**；他人的：复制 / 回复 / **举报**。
   🔴 **权限一点没放宽**：删除项可见性沿用既有 `_canDelete`，点下去仍走既有
   `_confirmDelete` 的二次确认。这个菜单只是**多一个入口**，不是多一条权限路径。
4. **AC5 空态**：`💬` + 新文案。两语按文案清单 §4 定稿值写入：
   EN `No comments yet — say something!` / ID `Belum ada komentar, yuk mulai obrolan!`
   （英文原值 `Be the first to comment` 是「抢第一」的激励感，PRD 要的是更软的邀请感；
   印尼语原值本就接近，也一并换成定稿值）。底部固定输入框不受影响。
5. **🔴 AC6 自己刚发的评论必须可见** —— 本 story 最要紧的一条。
   Story 2.4 改热度序后，0 赞的新评论排在所有有赞评论之后，在有 10+ 条热门评论的帖子里
   **用户发完看不到自己刚发的东西**。这是改热度序必然带出来的副作用，不是偶发 bug。

   收口方式与三条约束：
   - 新增 `sessionPinnedCommentsProvider`，composer 发一级评论成功后把**整条**存进去；
   - 列表渲染时把置顶项排到最前；
   - **服务端排序一点没改**；
   - **置顶项不参与游标计算** —— 游标仍取服务端返回那一页的最后一条；
   - **离开详情页即失效**（`CommentSection.dispose` 清空）。

   ⚠️ **存的是整条评论，不只是 id**：热度序下新评论很可能**根本不在第一页**，
   只记 id 就只能「把已拿到的那条挪前面」，拿不到时依然看不见。存下整条后，
   服务端没返回它时直接用本地那份插到首位 —— 这才是「始终可见」的保证。
   服务端返回了就优先用服务端那份（赞数、审核态都更新）。

**一处自己引入又修掉的 bug**

`dispose()` 里直接 `ref.read(...)` → Riverpod 抛
「Using "ref" when a widget is about to or has been unmounted is unsafe」，
`comment_moderation_label_test` 等 25 条用例全红。改为在 `initState` 就把 notifier 存进字段。

**⚠️ 一处语义落差，需要你定夺（我按 AC 照做了，但值得你看一眼）**

AC3 要求他人的评论菜单里有「举报」，AC4 要求「举报沿用既有 `openReport` 流程」。
我照做了 —— 但 `openReport(context, ref, postId)` 举报的是**本帖**，
后端目前**没有「举报单条评论」的端点**。也就是说：用户长按某条冒犯性评论点「举报」，
实际举报的是这篇帖子。

评论区骚扰的既有处置路径是**点作者头像/昵称 → 迷你卡 → 举报/拉黑该用户**
（代码注释里写明「影子评论 / R1 / R2 / 通知抑制全是为评论区骚扰设计的」），那条路仍然在。
如果希望长按菜单的「举报」指向评论作者而不是帖子，改一行即可，但那超出了 AC4 的字面要求，
所以我没有自行改。
