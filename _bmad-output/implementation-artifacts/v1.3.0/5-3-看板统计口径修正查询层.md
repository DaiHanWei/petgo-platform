# Story 5-3: 看板统计口径修正（查询层）

Status: ready-for-dev

> 自包含 story，**纯后端查询层**（`petgo-backend/`），改一段 SQL + 两处口径注释 + 测试，**无迁移、无 App 端改动、无接口契约变更、不动任何页面模板**。
> 与用户沟通用中文。执行纪律见根 `CLAUDE.md`（`mvn -B clean package`）。

## Story

As a 运营，
I want 库存周转页的「售罄数」是真的，
so that 我不会因为它长期显示一个偏小的数字而漏掉断货。

## Context

### 现状查询（根因）

`petgo-backend/src/main/java/com/tailtopia/admin/shop/service/ShopFinanceDashboardService.java:154-163`：

```java
/** 当前售罄 SKU 数（缺货损失的服务端近似读数）。 */
@Transactional(readOnly = true)
public long outOfStockSkuCount() {
    return scalar("""
            SELECT COUNT(*) FROM sku_inventory i
            JOIN shop_skus s ON s.id = i.sku_id
            JOIN shop_products p ON p.id = s.product_id
            WHERE p.is_active = true AND (i.actual - i.locked) <= 0
            """);
}
```

两处让数字偏小：

1. **`FROM sku_inventory i JOIN shop_skus s`** 是 INNER JOIN，且驱动表是 `sku_inventory` —— **从未建过库存行的 SKU 一条都不计入**。而「从来没进过货」恰恰是最极端的售罄。
2. **`p.is_active = true`** —— 只数已上架商品的规格。`shop_products.is_active` 建列时 `DEFAULT FALSE`（`V20260817_1154__init_shop_products_and_skus.sql:37`「新建默认未上架」），所以新建但未上架的商品，其规格全部被排除。

调用点唯一：`admin/shop/web/AdminShopFinanceController.java:65`

```java
model.addAttribute("outOfStockCount", finance.outOfStockSkuCount());
```

页面 `/admin/shop/inventory-turnover`（同文件 :59）。

### 「未删除规格」在当前 schema 里是什么

`shop_skus` 表（`V20260817_1154__init_shop_products_and_skus.sql:60-74`）**没有任何软删除列**（无 `deleted_at`、无 `is_active`），且 `admin/shop/` 下**没有删除 SKU 的服务方法或端点**（grep `deleteSku` / `skus.delete` 均无命中；唯一的 `ON DELETE CASCADE` 是 `product_id` 外键 :63，随商品硬删级联）。

⇒ **「所有未删除规格」= `shop_skus` 表内全部行**。这一条必须写进代码注释：第二批若给 SKU 引入软删除（如 Story 8-x），本查询要同步加过滤条件，否则口径又会悄悄漂。

### 另两处只做「定义」不做实现的口径

**① 售后成本**（`ShopFinanceDashboardService.java:81-86`）：

```sql
SELECT COALESCE(SUM(r.compensation_premium + r.incentive_premium
                    + r.shipback_reimbursed), 0)
FROM return_requests r
WHERE r.refunded_at >= ? AND r.refunded_at < ?
```

口径 = **平台责任补偿溢价 + 转币激励溢价 + 平台承担的回程运费**，按 `return_requests.refunded_at` 落期。

🔴 **已知缺口**（必须写进注释）：后台「订单异常处置 · 整单取消」发的补偿溢价走
`AdminShopOrderExceptionService.payCompensationPremium`（`admin/shop/service/AdminShopOrderExceptionService.java:267-286`），**只落 `pawcoin_transactions` 的 BONUS，不建 `return_requests` 行** ⇒ **这条路的补偿从来不计入售后成本**。本版两项补偿比例都是 0（Story 2-2），数字上无差别；口径标注是为了下一版恢复退货时不被这个盲区骗。

**② PawCoin 可用 / 冻结中**：

- 钱包只有一个余额列：`PawCoinWallet.balance`（`pay/domain/PawCoinWallet.java:33-34`），**没有冻结列**。
- PawCoin 是在**支付时**才扣的：`CheckoutService.settlePawCoinSegment`（`shop/order/service/CheckoutService.java:247-255`，`PawCoinTxnType.SPEND`，幂等键 `shop-order:{orderToken}`），**不是下单时扣**。
- ⇒ **冻结中 = 已被待支付订单占用、尚未扣减的部分** = `SUM(shop_orders.coin_amount)` where `status = 'PENDING_PAYMENT'`（且支付窗未过期）；**可用 = `balance` − 冻结中**。
- 当前后台的 PawCoin 余额展示在 `templates/admin/user-detail.html:40-41` 与 :96-97，数据来自 `AdminUserDetailView.pawcoinBalance`（`admin/usermgmt/dto/AdminUserDetailView.java:30`）—— 就是那个**不分可用 / 冻结中**的单一数字。

### 🔴 范围边界（硬性）

**本 story 只改查询与测试 + 写口径注释。页面展示与口径标注属于后台页面改动，随 Story 9-5 在 admin 主题 Epic 10 之后落地。**

具体地，本 story **不得**：
- 改 `templates/admin/shop-turnover*.html` 或任何 `.html`
- 改 `AdminShopFinanceController`（`outOfStockCount` 的 model 名与取值调用都不动）
- 给 `MarginSnapshot` / `ReconciliationSnapshot` 加字段
- 新增「可用 / 冻结中」的查询方法（9-5 需要时再加，加在这里会变成一个没人调用的死方法）

### 验证层级的一处修正（对 epic 的偏离，已说明）

epic 把「单测断言新口径」标成 **L0**。但 `outOfStockSkuCount` 是 `JdbcTemplate` 直接执行的原生 SQL（`scalar(...)` :246-249），**要真断言计数就必须有真 PostgreSQL**（`COALESCE` / LEFT JOIN 的行为不能靠 mock 复现）。因此本 story 拆成两层：
- **L0**：SQL 文本护栏（断言查询不再含 `is_active`、含 `LEFT JOIN`），可在无 DB 环境跑，用于云端把关 + 变异验证；
- **L1**：真库计数断言（三类规格），是口径正确性的**唯一实证**。

AC 里逐条标注了归属，请勿把 L1 那条当 L0 应付过去。

## Acceptance Criteria

**AC1 · 售罄数改新口径**
**Given** `ShopFinanceDashboardService.outOfStockSkuCount()`
**When** 改为「所有未删除规格中可售库存为 0 的数量」
**Then** 查询以 `shop_skus` 为驱动表、`LEFT JOIN sku_inventory`，**去掉 `p.is_active` 限定**，判据为 `COALESCE(i.actual, 0) - COALESCE(i.locked, 0) <= 0` `[L0]`
**And** 方法返回类型、方法名、`@Transactional(readOnly = true)`、调用点 `AdminShopFinanceController.java:65` 全部不变 `[L0]`
**And** 不再需要 `JOIN shop_products`（口径里已无商品维度）`[L0]`

**AC2 · 三类规格的计数（真库）**
**Given** 同一个库里造三类规格：
- A：商品已上架（`is_active = true`）+ 有库存行 + `actual − locked = 0`
- B：商品**未上架**（`is_active = false`）+ 有库存行 + `actual − locked = 0`
- C：**完全没有 `sku_inventory` 行**的规格
- D（对照）：有库存行且 `actual − locked > 0`

**When** 调 `outOfStockSkuCount()`
**Then** A、B、C **都计入**，D **不计入**；改前只计 A `[L1]`
**And** `actual − locked` 为**负数**的行（理论上被库级约束挡着，防御性覆盖）也计入 `[L1]`

**AC3 · L0 SQL 护栏 + 变异验证**

**And** 🔴 **变异验证**：把 `is_active = true` 加回去 → 该用例必须变红；把 `LEFT JOIN` 改回 `JOIN` → 该用例必须变红。两次变异的执行记录写进 Completion Notes `[L0]`

## Dev Notes

### 新口径为什么把「未上架商品的规格」也算进来

售罄数服务的是「运营要不要补货」这个决定。一个未上架商品的规格库存为 0，运营照样需要知道（否则上架当天就是空的）。旧写法把它排除掉，正是 SHOP-FR-28 说的「与实际不符」。

至于「上架 / 未上架」的拆分展示，是页面层的事 —— 9-5 若要拆，可以在那时增加一个带维度的查询，而不是现在把过滤留在这里。

### 为什么驱动表必须换成 `shop_skus`

`LEFT JOIN` 的方向依赖驱动表。保持 `FROM sku_inventory` 再 `LEFT JOIN shop_skus` 是反的（等于说「库存行可以没有 SKU」），照样漏掉没有库存行的规格。必须 `FROM shop_skus s LEFT JOIN sku_inventory i`。

### `COALESCE` 两个都要写

`i.actual` 与 `i.locked` 在 LEFT JOIN 无匹配时**都是 NULL**，`NULL - NULL <= 0` 在 SQL 里是 `NULL`（不是 true），整行会被 `WHERE` 过滤掉 —— 那就等于什么都没修。两个字段各套一层 `COALESCE(..., 0)` 才能让「没有库存行」落进 `0 - 0 <= 0` 为真。**这是本 story 最容易写错的一行。**
