# Story 4.3: 全屏推荐集合页

Status: review

## Story

As a 在 Diary 页看了几张觉得有意思的用户,
I want 点「查看全部」看到更多,
so that 我能一次多逛几只，而不是看完那几张就没了。

## Acceptance Criteria

**AC1 — 「查看全部」入口** `[L2]`
在 Diary 页推荐集合的**页面最下面**加上「查看全部」入口（位置按 UX-DR14：看完这一屏想看更多再点）。
⚠️ 该入口**由本 story 一并交付** —— 它的落点是本 story 才建的页面，放在 Story 4.1 会成为前向依赖。

**AC2 — 集合页** `[L2]`
点「查看全部」→ 全屏推荐集合页，**2 列网格**，卡片样式与 Story 4.1 一致。

**AC3 — 分页与失败态** `[L2]`
滚动到底按既有分页口径继续加载；加载失败走统一失败口径（保留已加载内容 + 给重试入口）。

**AC4 — 空态** `[L2]`
推荐池为空（没有任何宠物满足门槛）→ 显示空态。

**AC5 — 埋点** `[L1]`
从集合页点宠物卡 → `from` 取 `explore_grid`。

### 追加了一项 Dev Notes 没点明的后端工作

Dev Notes 写「推荐接口：Story 4.1 已交付，**加分页参数即可**」。实际做下来不是「加个参数」：
AC1 的排序是 `(WIB 日期桶, 互动量, 最后发帖时刻, petId)` 四层，游标必须是**整个排序键**
（只带 petId 等于假设按 id 排序 → 第二页从一个与排序无关的位置开始：重复 + 另一批永远刷不到，
`KeysetCursor` 类注释里记的就是这类事故）。所以后端加了：
`PetRecommendCursor`（base64url 三元组，对外不可枚举、客户端原样回传）、
候选查询的行比较 `WHERE (桶, 互动量, 时刻, petId) < (…)`、`Page` 信封多两个字段（`nextCursor` / `hasMore`）。

### 路由归属

集合页是**独立路由页**。⚠️ 判断它要不要进 `_controlledLocations`（受控路由 = 游客不可进）：
本 story 的入口来自 Diary 页的**登录态**分支，所以进不进受控前缀对当前入口无影响；
但 Story 4.4 会从**首页**加入口，而首页游客也能看——**到那时若游客可点，集合页必须对游客开放**。
本 story 建路由时**不要**随手塞进受控前缀，否则 4.4 会踩坑。

- **AC2 集合页**：`/pet-recommendations`（**不是** `/pets/recommendations` —— 那会被

- **AC3 分页**：keyset 游标（见上「追加的后端工作」）。三种形态各自不同：
  | 情形 | 这一屏 |
  |---|---|

  | **翻页失败** | **已加载的一只不动** + 底部一行「点击重试」（F13 / NFR-10） |
  | 池子为空 | 空态（**不是**错误态） |
- **AC4 空态**：复用 `EmptyState`，刻意**没有 CTA** —— 用户没法让别人去发帖。
- **AC5 埋点**：`from` 取 `explore_grid`（AC5 原文），与 `diary_empty` / `diary_non_owner`
  两两不同（有用例钉着）。事件名与属性形状不变。

**code-review（`/code-review high`）CONFIRMED findings 已修**

后端那一半（行比较与 ORDER BY 四列同序同向、`:hasCursor` 门控 + 显式 CAST、游标取自最后**看过**
的候选因而不跳行、游标必然前进故不会翻页死循环、微秒精度往返）审查通过。四条问题全在前端，
且都是「客户端没按后端的契约来」：

1. `items.isEmpty` 就摆空态、没看 `hasMore` → 服务端在「一页宠物全被过滤掉」时回的正是
   **空 items + 游标 + hasMore=true**，于是用户永久停在「还没有宠物」，而空态里既没网格也没滚动、
   **没有任何东西能触发下一页**。现在：还能自动续抓时先转圈并把后面的页翻过来；
   额度用完仍是空的才按空态处理（对这位查看者而言池子实际为空），**不会出现永远转不完的圈**。
2. `loadMore` 只挂在滚动回调上 → 「1 只 + hasMore=true」这种（其余候选被过滤）
   `maxScrollExtent` 只有十几像素，用户滚不动、回调一次都不发，池子后面永远刷不出来。
   现在每帧渲染完回头看一眼，判据与触底那条**逐字相同**（`pixels >= max - 400`，
   写成 `<= 0` 判不出来 —— 实测 15.8px）。
   🛡 这条路径**有上限**（`maxAutoEmptyRounds`）：没有它就是一个用户什么都没做却不停发请求的死循环。
3. 底部重试直接调 `controller.loadMore`、没走 setState → 重试时底部不转圈；
   而且重复失败时新旧 `AsyncData` **值相等**，Riverpod 跳过通知 → 再失败一次毫无反馈。
   现在三处触发（触底 / 没填满 / 底部重试）走**同一个出口** `_startLoadMore`。
4. 新路由被插在 `VisitorArchiveView` 的注释块与它所描述的 `GoRoute` 之间，
   留下两段互相矛盾的登录门控说明 → 挪到那条 `GoRoute` **之后**。
