## Context

### (a) 库存的真相：可售量从不落库，`stocktakeTo` 自带 CAS

`petgo-backend/src/main/resources/db/migration/V20260817_1220__init_sku_inventory.sql:15` 建 `sku_inventory`：`sku_id` FK CASCADE `:17` · `actual BIGINT DEFAULT 0` `:18` · `locked BIGINT DEFAULT 0` `:19` · `version BIGINT DEFAULT 0` `:21` · CHECK `:24-27`（**含 `locked <= actual`**）· `uq_sku_inventory_sku` `:30`。
🔴 **可售量是算出来的，从不落库**（`:20` 注释）；实体 `petgo-backend/src/main/java/com/tailtopia/shop/domain/SkuInventory.java:24`，`available() = actual - locked`（`:54`）；⚠️ `version` 是**普通列、不是 JPA `@Version`**（`:41-42` 注释明写）。

`petgo-backend/src/main/java/com/tailtopia/shop/repository/SkuInventoryRepository.java:20` 六条原语全是单行原子条件写：

```java
// :117-121
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update SkuInventory i set i.actual = :counted, i.version = i.version + 1, "
        + "i.updatedAt = CURRENT_TIMESTAMP "
        + "where i.skuId = :skuId and i.actual = :expectedBefore and i.locked <= :counted")
int stocktakeTo(@Param("skuId") long skuId, @Param("counted") long counted,
        @Param("expectedBefore") long expectedBefore);
```

两个守卫，各管一件事（javadoc `:100-116`）：
- **`i.locked <= :counted`** —— 盘点值低于锁定量会使 `locked > actual`，等于把已卖出的货抹掉。这是**防超卖**那一半。
- **`i.actual = :expectedBefore`**（CAS）—— 「盘点是赋值操作，反推不出前值」；前值被并发改动则本次盘点已过期。这是**预览即契约**那一半，AD-S5 直接指名复用它。

🔴 `clearAutomatically/flushAutomatically`（`:117`）不是可选项：调用方要在**同事务内读回** `actual` 写进流水的前后值，不清持久化上下文会读到一级缓存里的旧实体，而 `ck_inventory_movements_delta_consistent` **拦不住**（错位后仍自洽）且**不报任何错**（`:62-70` 的 javadoc 详述了这个地雷）。

### (b) 既有的单条盘点入口 —— 四步骨架，本 story 全盘复用

`petgo-backend/src/main/java/com/tailtopia/shop/service/InventoryMovementService.java:40`，类 javadoc `:22-28` 写明四步「条件原子 UPDATE 判影响行数 → 同事务读回 actual → 落流水 → 写审计」，缺一不可。

`stocktake` 方法 `:123-141`：

```java
@Transactional
public InventoryMovement stocktake(long skuId, long countedActual, String reason,
        long actorAccountId) {
    if (countedActual < 0) { throw AppException.validation("盘点值不能为负"); }
    requireText(reason, "盘点差异原因必填");

    long before = readActual(skuId);                                  // ← 🔴 提交时刻重读
    if (inventory.stocktakeTo(skuId, countedActual, before) == 0) {
        throw AppException.conflict(
                "盘点未生效：盘点值低于锁定库存，或该 SKU 库存在盘点期间已被改动，请重新盘点");
    }
    InventoryMovement m = movements.save(InventoryMovement.stocktake(skuId, before,
            countedActual, reason, actorAccountId));
    audit.record(actorAccountId, AuditActions.SHOP_INVENTORY_STOCKTAKED, "SHOP_SKU",
            skuToken(skuId), "盘点调整：%d → %d，原因：%s".formatted(before, countedActual, reason));
    return m;
}
```

辅助：`readActual:194` · `skuToken:200`。既有后台入口：`AdminShopInventoryController.java:199 @PostMapping("/admin/shop/inventory/stocktake")`，`@PreAuthorize(EDIT_AUTH):200`（`EDIT_AUTH` 定义在 `:48`，= `hasRole('SUPER_ADMIN') or hasAuthority('shop.inventory_edit')`）。

### (c) 🔴 直接循环调 `stocktake(...)` **会破坏预览即契约** —— 本 story 的核心设计点

看 `:130`：`long before = readActual(skuId);` —— **它自己在提交时刻重读前值**，然后拿这个刚读到的值去做 CAS。

后果：预览时看到 50、运营去喝了杯咖啡、期间别人改成 80、他点提交 —— `readActual` 读到 80，CAS 用 80 比 80，**通过**，直接把 80 覆盖成运营基于「50」做的决策。CAS 形同虚设，「预览即契约」整条失效。

⇒ **正确做法**：给 `InventoryMovementService` 加一个**带期望前值参数的重载**，原方法委托给它：

```java
// 新：批量路径用这个，expectedBefore 来自预览
public InventoryMovement stocktake(long skuId, long countedActual, String reason,
        long actorAccountId, long expectedBefore) { … }

// 旧签名保持不变：单条页面继续用，内部 readActual 后委托给上面那个
public InventoryMovement stocktake(long skuId, long countedActual, String reason,
        long actorAccountId) {
    return stocktake(skuId, countedActual, reason, actorAccountId, readActual(skuId));
}
```

这样：**条件写仍是唯一判定点、零新扣减路径、单条页面行为一字不变**。这正是 AD-S5「复用 `stocktakeTo` 的 CAS，不新造扣减路径」的落地方式 —— 复用的是**原语**，不是那个自带重读的便利方法。

### (e) 「在手量 vs 锁定量」—— 页面必须替运营把这句话说清楚

- **设的是 `actual`（在手量）**，`locked` **一列不碰**（`stocktakeTo` 的 SET 子句 `:118` 只有 `actual` / `version` / `updatedAt`）。
- 可售量 = `actual - locked`，**从不落库**，盘点后自动重算。
- `locked` 的来源是**已提交未支付的订单**（`InventoryService.lock:47` → `SkuInventoryRepository.lock:36`），付款成功走 `commit:59`（同减 actual 与 locked），超时/取消走 `release:47`。

运营的直觉是「我数出来 50，就该填 50」——**这是对的**，但他数的是货架上的实物，而货架上有 8 件是已经被人下单锁住、等着发的。所以页面必须显示三列（在手 / 锁定 / 可售）并写明「填在手量」，否则他会填「可售 42」，把 `actual` 打成 42、`locked` 还是 8、可售变 34 —— 凭空少了 8 件。

## Acceptance Criteria

**AC1 · 语义为盘点（设为绝对值），不做增减** `[L0]`
**Given** OD-7 已按推荐值实现
**When** 运营提交批量库存
**Then** 输入的是**每行的绝对值**，系统**不提供** `+N` / `-N` 的增减输入 `[L0]`
**And** 理由写进页面说明与代码注释：增减在并发下会叠加出错，盘点是「我数出 N」`[L0]`

**AC2 · 🔴 设的是在手量，锁定量不变** `[L0/L1]`
**Given** 某 SKU `actual=50`、`locked=8`（可售 42）
**When** 批量把它盘成 60
**Then** `actual=60`、**`locked` 仍为 8**、可售自动变 52 `[L1]`
**And** 条件写的 SET 子句**只动 `actual` / `version` / `updated_at`**（即原样复用 `stocktakeTo`，不新写一条 UPDATE）`[L0]`
**And** 🔴 页面在输入区显式写明「填**在手库存**（含已被订单锁定的部分），锁定量不受影响」，并同时显示三列：在手 / 锁定 / 可售 `[L2]`

**AC3 · 🔴 不得写成负数 / 不得低于锁定量** `[L0/L1]`
**Given** 某 SKU `locked=8`
**When** 盘点值填 5
**Then** `stocktakeTo` 的 `i.locked <= :counted` 守卫使影响行数为 **0** ⇒ **整批拒绝** `[L1]`
**And** 错误提示可读且**点名是哪一行、哪种原因**：「规格 X：盘点值 5 低于已锁定 8 件（有未付款订单占用），请核对后重盘」`[L1]`
**And** 盘点值为负在**服务层**就拒（沿用 `InventoryMovementService.java:126-128` 的 `AppException.validation("盘点值不能为负")` 口径），不靠 DB 的 `ck_inventory_movements_non_negative` 兜底 `[L0]`
**And** 🔴 **不得**为了「凑出可读文案」而在条件写**之前**读 `locked` 做判定 —— 判定只在 SQL 的 WHERE 里；失败后可重读一次**仅供文案**，并在该行注释写明 `[L0]`

**AC4 · 复用 `stocktakeTo` 的 CAS，且用的是**预览时**的前值** `[L0/L1]`
**Given** 预览时某行 `actual=50`
**When** 提交前另一会话把它改成 80，运营再提交
**Then** CAS 的 `expectedBefore` 是 **50**（来自预览），比对失败 ⇒ 影响 0 行 ⇒ **整批拒绝** `[L1]`
**And** 🔴 **不得直接循环调既有的四参 `InventoryMovementService.stocktake(...)`** —— 它 `:130` 自己 `readActual` 重读前值，会让 CAS 形同虚设（详见 Context (c)）`[L0]`
**And** 落地方式：给 `InventoryMovementService` 加**带 `expectedBefore` 的重载**，四参旧方法委托给它；🔴 **旧方法的签名与行为一字不变**，单条盘点页面零改动 `[L0/L1]`
**And** 🔴 **不新增任何 `SkuInventoryRepository` 的写方法**；本 story 的 DB 写入口只有 `stocktakeTo` 一个 `[L0]`

**AC5 · 每行写一条 `inventory_movements` 流水** `[L0/L1]`
**Given** 一批成功盘了 N 行
**When** 事务提交
**Then** `inventory_movements` 新增**恰好 N 行**，`movement_type='STOCKTAKE'` `[L1]`
**And** 每行 `actual_before` = 预览前值、`actual_after` = 盘点值、`qty_delta` = **差值**（`after - before`，可正可负可为 0），满足 `ck_inventory_movements_delta_consistent`（`V20260817_1852…:45-46`）`[L1]`
**And** 🔴 `reason` **非空非空白**（`ck_inventory_movements_reason_required` `:64-66`），且**服务层先校验**、不让 DB 兜底 `[L0/L1]`
**And** `operator_account_id` 取登录态（迁移 `:37-38` 注释「服务端从登录态取，绝不接受前端传入」）`[L0]`
**And** 流水沿用工厂 `InventoryMovement.stocktake(...)`（`InventoryMovement.java:119`），**不手拼实体、不改 `updatable=false`** `[L0]`

**AC6 · 盘点原因的口径** `[L0/L2]`

## Dev Notes

### 🔴 本 story 与 7-2 的最大区别：复用 vs 新造

| | 7-2 改价 | 7-3 盘点 |
|---|---|---|
| 条件写 | **新造**（`ShopSkuRepository` 此前无 `@Modifying`） | 🔴 **复用** `SkuInventoryRepository.stocktakeTo`（`:120-121`），一行 SQL 都不新写 |
| 服务入口 | **新造**（不复用 `upsertSku`，它是读改写） | 🔴 **加重载**（`InventoryMovementService.stocktake` 五参版），旧四参版委托，行为不变 |
| 审计码 | **新增** `SHOP_SKU_PRICE_UPDATED` | 🔴 **复用** `SHOP_INVENTORY_STOCKTAKED`（`AuditActions.java:138`） |
| 流水 | 无 | 🔴 每行一条 `inventory_movements` |

为什么盘点这边处处复用：`InventoryMovementType` 的 javadoc `:6-8` 原文「🔴 **不存在第五条路径**。AB-10C 明令不提供直接编辑库存数字的入口：直接改数会使库存与采购成本脱钩，令 AB-13A 毛利核算失真。任何 `actual` 变更都必须落一条 `inventory_movements`」。批量盘点**不是第五条路径**，它是第四条路径的批量版 —— 任何「为了批量方便」而绕开 `stocktakeTo` 或绕开流水的写法，都是在造第五条路径。

### 🔴 那个重载不是设计洁癖，它是本 story 唯一真正的风险点

再说一遍 Context (c) 的推演，因为这是最容易被「复用既有方法」的直觉带偏的地方：

四参 `stocktake` 内部 `long before = readActual(skuId);`（`:130`），CAS 用的是**它自己刚读的值**。单条页面上这没问题 —— 读和写之间只隔几微秒，中间没有人类。批量场景里，读发生在**提交时刻**，而运营的决策发生在**预览时刻**，中间隔着他看完 100 行的时间。拿提交时刻的值做 CAS，等于每次都比对成功，等于没有 CAS。

写测试时的自检：`staleExpectedBeforeRejectsWholeBatch()` 如果在「循环调四参旧方法」的实现下**也能通过**，说明测试写错了（多半是并发改动发生在预览之前而非之间）。AC9 的第三次变异就是用来验这条测试有没有写对。

### 🔴 「影响 0 行」的三种原因与那次「只为文案」的重读

`stocktakeTo` 返回 0 有三种可能，SQL 分不出来（既有单条实现 `:132-134` 就是合并成一句文案的）。批量场景下运营面对的是 100 行，「请重新盘点」等于没说。所以要重读一次生成文案。

🔴 这次重读是本 story 唯一一处「条件写之外的读」，必须在代码里用注释钉死它的用途。理由很直白：**「读一下 locked 看看够不够」这个动作，挪到条件写前面就变成了应用层读改写**——`SkuInventoryRepository` 类注释 `:14` 明令禁止的那一种。它俩在 diff 里长得几乎一样，区别只是位置。注释是唯一能防住下一个人的东西。

### 盘点原因整批一个，不逐行

`_reason_required`（`V20260817_1852…:64-66`）只要求非空。逐行填原因在 100 行的场景下没人会认真填（结果是一百个「盘点」），整批一个反而更可能填出有意义的内容（「9 月 16 日月末盘点」）。审计与流水各行都带上这同一个原因，可追溯性不损失。

### 权限：`shop.bulk_edit` 与 `shop.inventory_edit` 的关系待确认

AD-S13 定了批量四类共用 `shop.bulk_edit`，但没说是否要叠加既有的资源权限。本 story 推荐取「两者都要」：能做批量操作（`bulk_edit`）与能碰库存（`inventory_edit`）是两件事，就像 `InventoryMovementType.PURCHASE_INBOUND` 的 javadoc `:18-19` 说的「采购入库另需 `shop.cost_edit`」——本仓已有这种叠加先例。
但这是**未拍板项**，AC7 要求实施时确认并写进 Completion Notes，不要默默选一个。

### 别误伤的三件事

1. **`ck_inventory_movements_type` 的值集不改** —— `STOCKTAKE` 已在里面。改 CHECK 要 `DROP+ADD` 重列全集，此处（`ck_notifications_type` 那一类）已经出过三次事故（CLAUDE.md 纪律 5）。
2. **`InventoryMovement` 全字段 `updatable=false`**（`:35-74`，append-only）—— 流水只新增不修改。
3. **`sku_inventory.version` 不是 JPA `@Version`**（`SkuInventory.java:41-42`）—— 不要试图给它加 `@Version` 注解「顺便做个乐观锁」，六条原语都在手动 `+1`，加注解会让 Hibernate 与 JPQL 打架。
