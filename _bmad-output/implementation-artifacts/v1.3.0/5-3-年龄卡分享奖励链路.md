# Story 5.3: 年龄卡分享奖励链路

Status: review

## Story

As a 用户，
I want 分享年龄卡也能拿到 PawCoin，
so that 我有动力把它发出去。

---

> **含一条资金口径的安全攸关约束**：日界必须按 WIB 当地日切，按 UTC 切会让印尼用户在早上 6–7 点领双份。
>
> **本 story 最容易漏的是「还有一整张账本表」** —— 既有 KTP 渠道除两列配置外，另有 `id_card_share_rewards` 表记去重与日限。只加两列不算接通。
>
> 依赖 Story 5.2（分享动作已存在）。5.2 不含奖励也能独立交付，故本条不是 5.2 的前置。

---

## Acceptance Criteria

### AC1 — 渠道配置两列（L1）

**Given** PawCoin 配置表
**When** 迁移执行完毕
**Then** 新增年龄卡渠道两列：单次奖励、单日上限 `[L1]`
**And** 两列默认 0（不发币），含 `>= 0` CHECK `[L1]`
**And** 与既有 `id_card_share_reward` / `id_card_share_daily_cap` 同构 `[L0]`

### AC2 — 🔴 专用账本表（L1）

**Given** 数据库
**When** 迁移执行完毕
**Then** 存在年龄卡分享奖励**账本表**，记录发放与日限 `[L1]`
**And** **不做档案级去重** —— 无 `pet_profile_id` 唯一约束（决策 A-8） `[L0]`
**And** 迁移文件名为时间戳制 `[L0]`

> KTP 的账本以「宠物档案首次」去重，年龄卡没有卡实体、也不该按档案唯一（同一只宠物隔几个月再生成是不同的分享物），**塞不进那张表**。

### AC3 — 🔴 日界按 WIB（资金口径，L1）

**Given** 单日上限的「日」
**When** 判定
**Then** 按 **WIB（`Asia/Jakarta`）当地日**切分 `[L1]`
**And** 复用既有唯一实现（`IdCardShareRewardService.shareDateOf` / `ShareRewardService.periodOf`），**不另写换算** `[L0]`
**And** **不得按 UTC 切** `[L0]`

> 🔴 按 UTC 切会让「今天」在印尼早上 7 点才换。运营配「3 次/日」，用户在 06:00–07:00 能领双份。**这是资金口径错误，不是体验问题。**

### AC4 — 判断顺序（L1）

**Given** 一次领奖请求
**When** 服务端处理
**Then** 判断顺序为：去重命中 → 渠道日上限 → 月度全局额度 `[L1]`
**And** 顺序不可调换（最便宜的判断在前，避免占掉额度又退回） `[L0]`

### AC5 — 共用全局月度上限（L1）

**Given** 月度上限
**Then** 与其他渠道**共用同一个全局月度上限** `[L1]`
**And** 年龄卡渠道**不设**独立月度上限 `[L0]`
**And** 全局总开关关闭时，本渠道一并停发 `[L1]`

### AC6 — 领奖调用不带内容（安全，L0）

**Given** 领奖调用
**Then** 只携带渠道标识与幂等键 `[L0]`
**And** **不携带卡面内容、不上传图片** `[L0]`

> 「年龄卡不落服务端」指的是**卡片图像**；领奖是一次独立的服务端调用，这是已澄清的唯一例外。

### AC7 — 后台配置（L1）

**Given** 运营后台 PawCoin 配置页
**Then** 可编辑年龄卡渠道两列 `[L1]`
**And** 变更写入既有配置变更日志 `[L1]`

### AC8 — 幂等（L1）

**Given** 同一次分享重复上报
**When** 服务端处理
**Then** 只发放一次（幂等键兜底） `[L1]`

**实现要点（复审着眼处）**：

1. **🔴 AC3 安全攸关的落实方式是「不自己写」**：直接调 `IdCardShareRewardService.shareDateOf(at)`。
   测试反向扫本 story 的服务源码，**禁止出现** `ZoneId` / `Asia/Jakarta` / `ZoneOffset` ——
   两份时区实现迟早走歧，而走歧的那一天是钱的问题。
   另有两条边界用例：`23:30Z`（= WIB 次日 06:30）必须算作**次日**；`16:59:59Z` / `17:00:00Z` 分属两天。
2. **🔴 决策 A-8：不做档案级去重**。新建表而不是复用 `id_card_share_rewards` ——
   那张表的唯一约束在 `pet_profile_id` 上（一个档案一辈子一次），塞进去要么撞唯一键、
   要么就得拆掉那条约束，而那条约束正是身份证渠道的幂等本身。
   测试三重钉住：迁移里没有该列、实体没有该字段、**仓库里没有任何按档案查的方法**
   （提供那样一个方法就是在邀请别人把档案级去重重新做出来）。
3. **三层顺序有测试按源码位置钉住**：去重 → 日上限 → 月度额度。换序会让最便宜的判断
   排在最贵的后面，还会把额度占掉又退回。
4. **幂等键带 userId 再落库**：客户端给的那串只在它自己那台设备上唯一，
   直接当全局唯一键用，等于让两个用户有概率互相顶掉对方的发放。
5. **陈旧 Redis 幂等键清理照抄身份证渠道**：`tryReward` 会在本事务提交前就把幂等键写进 Redis，
   本 REQUIRES_NEW 事务若随后提交失败，DB 回滚而 Redis 键留 24h ⇒ 重试时入账被短路成 no-op，
   却照常留痕与占额度 —— 「留了痕、币一枚没到账」。这是同胞服务踩过并修好的坑，不重蹈。
6. **显式 `TransactionTemplate` 而不是 `@Transactional(REQUIRES_NEW)`**：
   `rewardAfterShare → attempt` 是同类自调用，不走 Spring 代理，注解上的事务语义完全不生效。
   身份证渠道第一版就是这么写坏的。
7. **注销级联**：新表进了 `ShareRewardDeletionService`（CLAUDE.md 安全攸关 D1）。
   同一个用户的两种分享留痕在注销后表现必须一致 —— 一种消失、一种留着是最难发现的那类不一致。
8. **客户端领奖挂在 `onShared` 回调上**，与埋点同一位置；失败一律当作没发（分享本身已成功，
   绝不因此报错）；**发了才提示，没发静默**（告知原因会诱导「攒着别分享」或「月初集中刷满」）。

**⚠️ 顺带更新的既有测试**：Story 5.2 里那条「AC10：本 story 不接入 PawCoin 奖励（属 5.3）」
的断言已从「不许有」**翻成「有且只能长这样」**（领奖必须在 `onShared` 之后、只带幂等键）——
直接删掉等于把这块地方交还给随便谁怎么写。
