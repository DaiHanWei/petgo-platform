# Story 5.1: 场所数据模型（AD-5）

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（Flyway 时间戳版本号、`ddl-auto=validate`、`mvn -B clean package`）。
> 本 story **只有后端建表 + 实体 + 仓储 + 契约文档**，无页面、无 App 端改动。它是 Epic 5 其余三条 story 与 App 分支 FR-112 共同的底座。

## Story

As a 平台，
I want 场所及其照片、评论、打卡、举报五张表落库，状态与合并指向明确，
so that 后台与 App 分支对同一套表读写，谁先上线都不用改表。

## Acceptance Criteria

**AC1 · 五表迁移**
**Given** 库内无任何 `place*` 表（`db-schema-reference.md` 现有 56 张表无撞名）
**When** 执行 `V<yyyyMMdd_HHmm>__init_places.sql`（取创建时刻）
**Then** 建成 `places` / `place_photos` / `place_comments` / `place_checkins` / `place_reports` 五表，列、CHECK 全集、索引、FK、COMMENT 与本文 §SQL 草案一致 `[L1]`
**And** `mvn -B clean package` 后 `ddl-auto=validate` 通过（列类型与实体逐一对上）`[L1]`

**AC2 · 状态与合并语义**
**Given** `places.status` ∈ `ACTIVE | DELISTED | MERGED`
**Then** `MERGED` 行必须有 `merged_into_id`（CHECK 约束）；`ACTIVE`/`DELISTED` 行 `merged_into_id` 必须为 NULL `[L1]`
**And** `merged_into_id` 自引用 FK，指向的行不得自身为 `MERGED`（服务层保证，5.3 实现；DB 只保证 FK 存在）`[L0]`
**And** 软删用 `deleted_at`，任何列表查询默认 `deleted_at IS NULL` `[L0]`

**AC3 · 实体与仓储**
**Then** `admin/places/domain/` 下 `Place` / `PlacePhoto` / `PlaceComment` / `PlaceCheckin` / `PlaceReport` 五实体 + `PlaceStatus` / `PlaceAttitude` / `PlaceReportStatus` 三枚举（`@Enumerated(STRING)`，UPPER_SNAKE）`[L0]`
**And** `Place.publicToken` 由 Base62 22 位生成器产生（新建 `PlaceTokenGenerator`，字符表与长度与 `CardTokenGenerator` / `ShopTokenGenerator` 完全一致），`updatable=false` `[L0]`
**And** 五个 `JpaRepository`，`PlaceRepository` 至少含 `findByPublicToken`、`findByIdAndDeletedAtIsNull` `[L0]`
**And** 五个计数列（`photo_count` / `comment_count` / `checkin_count` / `recommend_count` / `not_recommend_count`）是**反规范化缓存**，实体提供 `recount(...)` 或 setter 由服务层同事务维护；本 story 不写业务逻辑 `[L0]`

**AC4 · 契约文档（X-1 / X-3）**
**Then** `docs/reference/db-schema-reference.md` 追加五表说明；`implementation-artifacts/CROSS-STORY-DECISIONS.md` 表归属总表追加「places 五表 → 本分支定 schema，App 分支读写数据」`[L0]`
**And** 文档写明给 App 分支的三条语义：① `status != 'ACTIVE'` 或 `deleted_at IS NOT NULL` 的场所对用户端「不存在」，直链落「场所不存在」统一文案；② `MERGED` 行的 `merged_into_id` 供 App 把直链跳到保留场所；③ 5.3 合并时发布 `PlaceMergedEvent(keepId, mergedId)`，护照章归并由 App 分支监听实现 `[L0]`

**AC5 · 回归**
**Then** 全量测试绿；`bash scripts/ci/check-flyway-versions.sh origin/main` 绿 `[L0/L1]`

## SQL 草案（`V<ts>__init_places.sql`）

```sql
-- V1.3.0 后台 · Story 5.1 —— 场所内容管理数据模型（AB-17A / AD-5）。
-- 只建新表，不触碰共享表。五表：places / place_photos / place_comments / place_checkins / place_reports。
-- · 对外标识 public_token（Base62 22 位），自增 id 不外露。
-- · 枚举 varchar + CHECK 全集（UPPER_SNAKE）。软删 deleted_at；下架 = status DELISTED；合并 = status MERGED + merged_into_id。
-- · 图片只存 OSS objectKey，不存 URL / 签名 URL。
-- · 五个计数列为反规范化缓存，由服务层同事务维护，合并/删除时重算。
-- · 契约 X-3：本表 schema 由后台分支定义，App 分支（FR-112）只读写数据。

CREATE TABLE places (
    id                  BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    public_token        VARCHAR(32)   NOT NULL,
    name                VARCHAR(80)   NOT NULL,
    place_type          VARCHAR(32)   NOT NULL,                 -- 与 App 端类型枚举同名（UPPER_SNAKE），值域由 FR-112 定，本表不加 CHECK 以免两分支撞值
    tags                JSONB         NOT NULL DEFAULT '[]'::jsonb,  -- 宠物友好标签码列表
    description         TEXT,
    address_text        VARCHAR(255)  NOT NULL,                 -- 文字地址（供用户复制导航）
    lat                 NUMERIC(9,6)  NOT NULL,
    lng                 NUMERIC(9,6)  NOT NULL,
    marked_by_user_id   BIGINT        NOT NULL REFERENCES users (id),   -- 标记人（App 用户或运营身份池账号），不可改
    status              VARCHAR(16)   NOT NULL DEFAULT 'ACTIVE',
    merged_into_id      BIGINT        REFERENCES places (id),
    photo_count         INT           NOT NULL DEFAULT 0,
    comment_count       INT           NOT NULL DEFAULT 0,
    checkin_count       INT           NOT NULL DEFAULT 0,
    recommend_count     INT           NOT NULL DEFAULT 0,
    not_recommend_count INT           NOT NULL DEFAULT 0,
    created_at          TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ   NOT NULL DEFAULT now(),
    deleted_at          TIMESTAMPTZ,
    CONSTRAINT ck_places_status CHECK (status IN ('ACTIVE', 'DELISTED', 'MERGED')),
    CONSTRAINT ck_places_merged_ref CHECK (
        (status = 'MERGED' AND merged_into_id IS NOT NULL) OR
        (status <> 'MERGED' AND merged_into_id IS NULL)),
    CONSTRAINT ck_places_lat CHECK (lat BETWEEN -90 AND 90),
    CONSTRAINT ck_places_lng CHECK (lng BETWEEN -180 AND 180),
    CONSTRAINT ck_places_counts CHECK (photo_count >= 0 AND comment_count >= 0 AND checkin_count >= 0
                                       AND recommend_count >= 0 AND not_recommend_count >= 0)
);
CREATE UNIQUE INDEX uq_places_token        ON places (public_token);
CREATE INDEX        idx_places_status_ct   ON places (status, created_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX        idx_places_name        ON places (lower(name));
CREATE INDEX        idx_places_marked_by   ON places (marked_by_user_id);
COMMENT ON TABLE  places IS '场所（AB-17A / FR-112）。status ACTIVE 上架 | DELISTED 下架（软删，直链落「场所不存在」）| MERGED 已并入 merged_into_id。';
COMMENT ON COLUMN places.merged_into_id IS '合并指向：仅 status=MERGED 时非空；App 直链据此跳到保留场所（契约 X-1）。';

CREATE TABLE place_photos (
    id                BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    place_id          BIGINT       NOT NULL REFERENCES places (id) ON DELETE CASCADE,
    object_key        VARCHAR(255) NOT NULL,                    -- OSS objectKey，非 URL
    uploader_user_id  BIGINT       NOT NULL REFERENCES users (id),
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted_at        TIMESTAMPTZ
);
CREATE INDEX idx_place_photos_place ON place_photos (place_id, created_at) WHERE deleted_at IS NULL;

CREATE TABLE place_comments (
    id              BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    place_id        BIGINT        NOT NULL REFERENCES places (id) ON DELETE CASCADE,
    author_user_id  BIGINT        NOT NULL REFERENCES users (id),
    body            VARCHAR(500)  NOT NULL,
    attitude        VARCHAR(16)   NOT NULL,                     -- 二元态度
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),
    deleted_at      TIMESTAMPTZ,
    CONSTRAINT ck_place_comments_attitude CHECK (attitude IN ('RECOMMEND', 'NOT_RECOMMEND'))
);
CREATE INDEX idx_place_comments_place ON place_comments (place_id, created_at DESC) WHERE deleted_at IS NULL;

CREATE TABLE place_checkins (
    id          BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    place_id    BIGINT      NOT NULL REFERENCES places (id) ON DELETE CASCADE,
    user_id     BIGINT      NOT NULL REFERENCES users (id),
    checked_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_place_checkins_place ON place_checkins (place_id, checked_at DESC);
CREATE INDEX idx_place_checkins_user  ON place_checkins (user_id, place_id);

CREATE TABLE place_reports (
    id                 BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    place_id           BIGINT       NOT NULL REFERENCES places (id) ON DELETE CASCADE,
    reporter_user_id   BIGINT       NOT NULL REFERENCES users (id),
    reason_type        VARCHAR(24)  NOT NULL,
    status             VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
    handled_by         BIGINT,                                  -- admin_accounts.id（后台账号与 App 用户隔离，不加 FK）
    handled_at         TIMESTAMPTZ,
    created_at         TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT ck_place_reports_status CHECK (status IN ('PENDING', 'DISMISSED', 'ACTIONED')),
    CONSTRAINT ck_place_reports_reason CHECK (reason_type IN
        ('ILLEGAL', 'MISINFO', 'INAPPROPRIATE', 'HARASSMENT', 'DUPLICATE', 'CLOSED', 'OTHER')),
    CONSTRAINT uq_place_reports_reporter_place UNIQUE (place_id, reporter_user_id)   -- 同人对同场所一条，重复举报幂等（照 content_reports）
);
CREATE INDEX idx_place_reports_status ON place_reports (status, created_at);
COMMENT ON COLUMN place_reports.reason_type IS '沿用 ReportReason 五值 + 场所特有 DUPLICATE（重复场所）/ CLOSED（已关店），PRD AB-17A ②「用户举报重复类目辅助合并」。';
```

## Dev Notes

### 🔴 举报模型为什么是新表（D-5）

现有 `ContentReport` 只有 `post_id`，`AccountReport` 只有 `target_user_id`，两张表都没有通用 `target_type`。PRD 原假设 B-3「举报对象类型可扩展」评审时证伪。所以 `place_reports` 独立建表，处置流在 Story 5.4 接进 A1 统一队列（`TicketType` 加 `PLACE_REPORT`，`UnifiedTicketQueryService.UNIFIED_CTE` 加第六段 UNION）。**本 story 只建表，不碰 TicketType。**

### 🔴 `marked_by_user_id` 引用 `users` 而不是 `admin_accounts`

运营预置录入时标记人「从运营发布身份池选择」（PRD AB-17A ③）。身份池里的对象是 `users` 表里的虚拟账号（`google_sub` 前缀 `virtual:`）或授权的真实账号（`seed_real_account_grants`），不是后台账号。所以 FK 指 `users(id)`，与种子帖 `content_posts.author_id` 同一语义。`place_reports.handled_by` 才是后台账号 id，照 `ContentReport.handledBy` 不加 FK。

### 🔴 `place_type` 不加 CHECK

类型枚举的值域由 App 端 FR-112 定义（咖啡店 / 宠物公园 / 宠物酒店 / 宠物友好餐饮 …，UI 稿 2-20 出现四种）。本分支不知道最终全集，加 CHECK 会让 App 分支合入时撞约束。后台侧用 Java 枚举 `PlaceType` 做**软校验**（未知值只警告不拒），待 App 分支合入后两边对齐再补 CHECK（记入 Completion Notes 待办）。`tags` 同理用 JSONB 字符串列表不做值域约束。

### 🔴 计数列是缓存，重算规则在 5.3

`recommend_count` / `not_recommend_count` 等于 `place_comments` 未删行按 `attitude` 的 COUNT；`photo_count` / `comment_count` / `checkin_count` 同理。删单条照片/评论时服务层同事务 -1，合并时对保留方全量 `recount`。本 story 只建列和实体方法，不写维护逻辑。
