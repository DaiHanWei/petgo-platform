# Story 11.4: 权限矩阵与导航一致性收口

Status: review

> 自包含 story，L0/L1 为主。与用户沟通用中文。
> 目标：`AdminPageCatalog`（1.5 引入、2.3a 迁至 `admin/shared`）成为导航、角色矩阵、账号权限面板、`@PreAuthorize` 四方的唯一页面目录，四方之间没有孤儿。

## Story

As a 超级管理员，
I want 导航上有的页面在权限矩阵里都能找到、矩阵里勾的码都真的门控着某个端点、没权限的人既看不到菜单也进不了页面，
so that 权限配置所见即所得。

## Acceptance Criteria

**AC1 · 目录完备（Catalog ↔ 路由）**
**Given** `AdminPageCatalog`（约 35 个页面维度，8 个导航组）
**Then** 每个页面级 GET 路由（Story 11.1 after 列表，排除 login / oauth / drawer / 导出 / 片段）在目录中恰有一条；目录中每条都有存活路由；测试 `AdminPageCatalogCoverageTest` 双向断言 `[L1]`

**AC2 · 权限码完备（Catalog ↔ AdminPermissions）**
**Then** `AdminPermissions` 全部常量（基线 72 + 本版新增 `place.manage`、`comment.virtual_post` = 74）每一个都出现在矩阵的「查看 / 编辑 / 其他操作」某一格；矩阵中每个码都是常量（无手写字符串）；测试断言集合相等 `[L0]`
**And** 已撤销的 `content.stats_view` / `content.stats_export` 不出现（现状注释：整页 2026-08-28 撤销，存量账号残留字符串不清）`[L0]`

**AC3 · 门控完备（Catalog ↔ @PreAuthorize）**
**Then** 写操作清单（11.1）里每条端点的 `@PreAuthorize` 表达式中出现的每个 `hasAuthority('x')` 码 ∈ `AdminPermissions`；每个页面 GET 的门控码 = 目录中该页的「查看」码（或 SUPER_ADMIN）；脚本 `scripts/ci/check-admin-permission-consistency.sh` 输出零差异 `[L0]`
**And** 代码现状不规整项**如实保留并在矩阵注脚说明**（FR-21A-7）：评论管理无独立查看码沿用 `content.view`；退款管理 / Toko 退货 / 开封判例共用 `refund.*`；复购效果走 `config.view` 或 `order.view`；**本 story 不拆码** `[L0]`

**AC4 · 导航 ↔ 权限行为**
**Given** 一个仅持单一权限码 X 的 CUSTOM 测试账号
**When** 登录
**Then** 侧导航只渲染目录中「查看码 = X」的页面所在组与项；其余页面直接 GET 返 403（`adminAccessDeniedHandler`）；组内全部无权限则整组不渲染 `[L1]`
**And** 对 74 个码逐个跑上述用例（参数化测试），无一例外 `[L1]`

**AC5 · 账号面板 ↔ 角色矩阵同构**
**Then** 后台账号页 CUSTOM「编辑权限」面板（1.6）与角色配置页矩阵（1.5）使用同一 `PermissionMatrixBuilder` 输出：分组顺序、页面维度、码归属完全一致；模板渲染单测比对两处 DOM 的分组标题序列 `[L2]`

### Completion Notes

**AC1 · 目录 ↔ 路由双向核对：42 = 42，零差异。**

两个方向漏一边的后果不一样、但**都不会让别的测试变红**，所以必须双向：

- **路由有、目录没有** → 这一页进不了侧导航，也进不了权限矩阵的行。页面本身能打开（知道 URL 的人能进），渲染冒烟全绿；但**没有任何角色能被授予它的权限**，等于交付了一个只有超管能用的页面。
- **目录有、路由没有** → 侧导航里一个点开 404 的死项，运营会当成权限问题来问。

做了两层：

1. **L0 文本层** `scripts/ci/check-admin-permission-consistency.sh` —— 路由清单**复用 Story 11.1 的生成器**（唯一事实源，不另写一套解析），云端无 Docker 也能跑，挡住绝大多数漏配。
2. **L1 权威层** `AdminPageCatalogCoverageTest` —— 用 `RequestMappingHandlerMapping` 枚举 Spring **真正注册**的路由。为什么必须有这一层：`@StagOnly`（= `@Profile("stag")`）的 Controller 在非 stag profile 下**根本不注册**，扫源码看不出这个差别，会把 stag 专用页当成漏配的生产页报出来。

🔴 **「哪些 GET 不算页面」只有一份口径**：`scripts/ci/admin-page-catalog-exceptions.txt`，脚本与 L1 测试**共用**（两套各写各的迟早分叉）。清单是**显式的**，不是脚本里一条 `grep -v` 正则 —— 正则一改，真正漏配的页面会跟着被吞掉，而且没人看得出来吞了什么。当前 12 条，四类：多路径别名（`/admin/dashboard`）、页内片段（`/admin/charts`、`/admin/comments/distribution` 等）、选择器（`*/pick`、`seed-post/pets`）、表单页（`/admin/roles/new`、`/admin/shop/products/new`，后者是 11.3 AC1 明确要保留的）。脚本另会对**清单里的死条目**发 warning —— 留着一条早已不存在的路径，等于给未来的漏配留了个后门。

**AC2 · 权限码完备：74 个码（基线 72 + `place.manage` + `comment.virtual_post`）。**

- 「每个码恰好归属一个页面、且归属码集合 == `AdminPermissions.ALL`」由既有 `AdminPageCatalogTest.ownedCodesCoverAllPermissionsExactlyOnce` 守着，本 story 复核通过，不重复造。
- 新增 `AdminPermissionMatrixStaticTest`（L0）补三条既有测试没覆盖的：矩阵模板**不许手写权限码**（手写一个，改码时 Java 全改完、模板这处还留旧的 —— 编译不报错、渲染不报错，只是那格复选框从此对不上任何权限）；**已撤销的 `content.stats_view` / `content.stats_export` 不在册也不在目录**；权限册规模 == 74。
- ⚠️ **6 个码在册但没有任何 `@PreAuthorize` 用到**：`content.throttle_view`、`content.view_reports`、`shop.cost_view`、`shop.cost_edit`、`shop.order_phone_search`、`user.phone_view`。**不判红** —— 其中几个是服务层判定（`shop.cost_*` 裁剪字段、`user.phone_view` 控制脱敏），判红会逼人写假的 `@PreAuthorize`。脚本对它们发 warning，`AdminNavPermissionMatrixTest.codesNoNavPageClaimsAreListedForReview` 再打印一份清单，双份留痕。其中 `content.view_reports` 是退役的举报队列页遗留（Story 2.4），可在后续清理。

**AC3 · 门控完备：`hasAuthority('x')` 里的 x 全部 ∈ `AdminPermissions`（68/68），零差异。**

拼错一个码 Spring **不会报错**，只会让那个端点对所有人 403（或者更糟：码名恰好没人有，等于永久锁死）—— 这是本 story 最值钱的一条断言。

**AC3 的「不规整项如实保留」照办、本 story 不拆码**（FR-21A-7）：评论管理沿用 `content.view`、退款 / Toko 退货 / 开封判例共用 `refund.*`、复购效果走 `config.view`/`order.view`、未成功请求沿用 `vet.view` —— 这些在 `AdminPageCatalog` 里以 `sharedCodes` 登记，矩阵只展示「沿用 …」文字 + 注脚，不出复选框。

**AC4 · 逐个权限码跑导航渲染**（`AdminNavPermissionMatrixTest`，L1，74 条参数化 + 2 条）。

与既有 `AdminPagesRenderSmokeTest.everySidebarLinkMatchesItsPageGate` 的分工要说清楚：那一条**按页面**遍历，守的是页面这一侧；**没有入口的页、以及从来没被任何页面引用的码，都在它的射程之外**。本条**按码**遍历，补的正是那两个盲区：

- 一个码只授出去、任何页都不认它 → 运营被授予了一个**什么也打不开**的权限，矩阵上却是个能勾的复选框。既有那条不会红（它从页面出发，压根遍历不到这个码）。
- **整组不渲染**：组内所有页都无权限时，组标题不该单独立在那儿 —— 一个展开是空的分组，比没有这个分组更让人以为是加载失败。

🔴 为此在 `fragments/nav.html` 的 `<details>` 上加了 `data-nav-group="<组 key>"`：**这是给断言用的稳定锚点，不是样式改动**。组标题是 `#{admin.group.*}` 文案，拿文案去断言会跟同名的页面项撞车（「内容」既是组名也可能是项名），一撞就成了假绿。

**AC5 · 账号面板 ↔ 角色矩阵同构：结构上就无法不一致，因此改钉引用关系。**

AC5 写的验收方式是「比对两处 DOM 的分组标题序列」。但本项目里两处**本来就 `th:replace` 同一个 fragment**（`perm-matrix :: matrix`），数据同样来自 `AdminPageCatalog.byGroup()` —— 一致不是比出来的，是结构上给定的，**比了也是恒真**。真正值得钉的是**有没有人把它 fork 掉**：某天为了给账号面板加一列，复制一份 fragment 改改 —— 从那一刻起两处开始各自演化，而任何比对 DOM 的测试**在 fork 当天仍然是绿的**（内容还一样），等分叉显现已是几个 story 之后。所以 `bothPermissionPanelsRenderTheSameMatrixFragment` 钉的是引用关系本身。**这是对 AC5 验收方式的有意替换，结论更强而不是更弱。**

**🔬 L1 待本地验收**（云端无 Docker）：

- `AdminPageCatalogCoverageTest`（2 条）：用真实注册路由做双向核对。**这是 AC1 唯一权威的证据**，L0 文本层只是近似。
- `AdminNavPermissionMatrixTest`（74 + 2 条）：逐码渲染侧导航。74 次请求，串行 L1 大约几十秒。
- 跑通后如有某个码渲染不出对应入口，说明 `AdminPageCatalog.navCodes` 与该页 Controller 的 `@PreAuthorize` 不同集，回对应页面 story 修。
