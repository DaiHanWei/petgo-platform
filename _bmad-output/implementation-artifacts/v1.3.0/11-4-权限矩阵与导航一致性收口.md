# Story 11.4: 权限矩阵与导航一致性收口

Status: review

> 自包含 story，L0/L1 为主。与用户沟通用中文。
> 目标：`AdminPageCatalog`（1.5 引入、2.3a 迁至 `admin/shared`）成为导航、角色矩阵、账号权限面板、`@PreAuthorize` 四方的唯一页面目录，四方之间没有孤儿。

## Story

As a 超级管理员，
I want 导航上有的页面在权限矩阵里都能找到、矩阵里勾的码都真的门控着某个端点、没权限的人既看不到菜单也进不了页面，
so that 权限配置所见即所得。

## Acceptance Criteria

**AC1 · 目录完备（Catalog ↔ 路由）**
**Given** `AdminPageCatalog`（约 35 个页面维度，8 个导航组）

**And** 已撤销的 `content.stats_view` / `content.stats_export` 不出现（现状注释：整页 2026-08-28 撤销，存量账号残留字符串不清）`[L0]`

**AC3 · 门控完备（Catalog ↔ @PreAuthorize）**
**Then** 写操作清单（11.1）里每条端点的 `@PreAuthorize` 表达式中出现的每个 `hasAuthority('x')` 码 ∈ `AdminPermissions`；每个页面 GET 的门控码 = 目录中该页的「查看」码（或 SUPER_ADMIN）；脚本 `scripts/ci/check-admin-permission-consistency.sh` 输出零差异 `[L0]`
**And** 代码现状不规整项**如实保留并在矩阵注脚说明**（FR-21A-7）：评论管理无独立查看码沿用 `content.view`；退款管理 / Toko 退货 / 开封判例共用 `refund.*`；复购效果走 `config.view` 或 `order.view`；**本 story 不拆码** `[L0]`

**AC4 · 导航 ↔ 权限行为**
**Given** 一个仅持单一权限码 X 的 CUSTOM 测试账号
**When** 登录
**Then** 侧导航只渲染目录中「查看码 = X」的页面所在组与项；其余页面直接 GET 返 403（`adminAccessDeniedHandler`）；组内全部无权限则整组不渲染 `[L1]`
**And** 对 74 个码逐个跑上述用例（参数化测试），无一例外 `[L1]`

**AC5 · 账号面板 ↔ 角色矩阵同构**

### Completion Notes

**AC1 · 目录 ↔ 路由双向核对：42 = 42，零差异。**

两个方向漏一边的后果不一样、但**都不会让别的测试变红**，所以必须双向：

- **路由有、目录没有** → 这一页进不了侧导航，也进不了权限矩阵的行。页面本身能打开（知道 URL 的人能进），渲染冒烟全绿；但**没有任何角色能被授予它的权限**，等于交付了一个只有超管能用的页面。
- **目录有、路由没有** → 侧导航里一个点开 404 的死项，运营会当成权限问题来问。

做了两层：

1. **L0 文本层** `scripts/ci/check-admin-permission-consistency.sh` —— 路由清单**复用 Story 11.1 的生成器**（唯一事实源，不另写一套解析），云端无 Docker 也能跑，挡住绝大多数漏配。
2. **L1 权威层** `AdminPageCatalogCoverageTest` —— 用 `RequestMappingHandlerMapping` 枚举 Spring **真正注册**的路由。为什么必须有这一层：`@StagOnly`（= `@Profile("stag")`）的 Controller 在非 stag profile 下**根本不注册**，扫源码看不出这个差别，会把 stag 专用页当成漏配的生产页报出来。

🔴 **「哪些 GET 不算页面」只有一份口径** —— 但第一版**只有例外清单是共用的**，「什么算页面」的正则是两套，
而且**已经不一致**：脚本用子串匹配（`export` / `detail` / `nav` 出现在任意位置就排除），
L1 测试用后缀锚定。于是 `/admin/export-center`、`/admin/detail-templates`、`/admin/navigation-settings`
这三个**真页面**在脚本侧被静默吞掉、在 Java 侧却是页面。当天两边结论恰好都是 42，把这个分叉盖住了。
现在两处逐字对齐（后缀锚定 + `login|…|nav` 后面带 `(/|$)` 边界），并在两边互相注明「改这里请同步改那边」。

例外清单 `scripts/ci/admin-page-catalog-exceptions.txt` 由脚本与 L1 测试共用。清单是**显式的**，不是脚本里一条 `grep -v` 正则 —— 正则一改，真正漏配的页面会跟着被吞掉，而且没人看得出来吞了什么。当前 12 条，四类：多路径别名（`/admin/dashboard`）、页内片段（`/admin/charts`、`/admin/comments/distribution` 等）、选择器（`*/pick`、`seed-post/pets`）、表单页（`/admin/roles/new`、`/admin/shop/products/new`，后者是 11.3 AC1 明确要保留的）。脚本另会对**清单里的死条目**发 warning —— 留着一条早已不存在的路径，等于给未来的漏配留了个后门。

**AC4 · 逐个权限码跑导航渲染**（`AdminNavPermissionMatrixTest`，L1，74 条参数化 + 2 条）。

🔴 **第一版是自证**：期望值 `navPagesFor(code)` 从 `AdminPageCatalog.navCodes` 推导，而侧栏渲染走的正是
`AdminNavModel.build()` → **同样按 `navCodes` 过滤** —— 两侧同一个数据源。那样这条测试只能抓
「nav.html 模板漏渲 href」，而 AC4 真正要防的**「目录 navCodes 与 Controller `@PreAuthorize` 不同集」**
（Dev Notes 点名的历史事故）**不可能让它红**。现在期望值改从 handler 上的真实 `@PreAuthorize` 推导，
两侧才是独立的。

🔴 **两处可见性判据是手抄的，而且抄漏了 `superAdminOnly`**：`AdminNavModel.visible` 是先判
`superAdminOnly` 再判 `navCodes.isEmpty()`；测试里手抄的那版只有后者。后果是
`roles`（全站唯一的 superAdminOnly 页、`navCodes` 为空）被当成「全员可见」——
于是**「配置与安全」组（账号 / 角色 / 审计日志）整组跳过检查**，8 组里最敏感的那一组恰好没验；
`leaked` 那一侧也把 roles 排除在越权渲染检查之外。现在两处都直接调 `AdminNavModel.visible`。

与既有 `AdminPagesRenderSmokeTest.everySidebarLinkMatchesItsPageGate` 的分工要说清楚：那一条**按页面**遍历，守的是页面这一侧；**没有入口的页、以及从来没被任何页面引用的码，都在它的射程之外**。本条**按码**遍历，补的正是那两个盲区：

- 一个码只授出去、任何页都不认它 → 运营被授予了一个**什么也打不开**的权限，矩阵上却是个能勾的复选框。既有那条不会红（它从页面出发，压根遍历不到这个码）。
- **整组不渲染**：组内所有页都无权限时，组标题不该单独立在那儿 —— 一个展开是空的分组，比没有这个分组更让人以为是加载失败。

🔴 为此在 `fragments/nav.html` 的 `<details>` 上加了 `data-nav-group="<组 key>"`：**这是给断言用的稳定锚点，不是样式改动**。组标题是 `#{admin.group.*}` 文案，拿文案去断言会跟同名的页面项撞车（「内容」既是组名也可能是项名），一撞就成了假绿。

**AC5 · 账号面板 ↔ 角色矩阵同构：结构上就无法不一致，因此改钉引用关系。**

🔴 **但第一版的实现把自己的立论架空了**：`bothPermissionPanelsRenderTheSameMatrixFragment` 是纯
`contains` 字符串包含 —— 把 `th:replace` 换成 fork 出来的那一份、只在上面留一行
`<!-- 旧写法：th:replace="~{admin/fragments/perm-matrix :: matrix(...)}" -->`，**照样绿**。
而这条测试的全部立论就是「防有人 fork 一份」。现在：剥注释后再比 + 断言
`perm-matrix*.html` **只能有一个文件**（fork 的第一步就是复制一份出来）。

🔴 `theMatrixTemplateNeverHardcodesAPermissionCode` 的**判据与它自述的失败模式正好相反**：
自述防的是「改码时 Java 全改完、模板这处还留旧的」，而留下的旧码**按定义已经不 `isValid`**，
于是恰恰不报；反倒是手写一个当前仍合法的码（无害重复）才会红。实测：塞 `'content.stats_view'`
（已撤销，正是本条要防的）→ 绿；塞 `'order.view'` → 红。现在反过来判「长得像权限码的字符串一律报，
除非在 `perm.`/`admin.`/`role.` 前缀白名单里」，并且**三份模板都扫**（原来只扫 `perm-matrix.html` 一个，
消费者模板里手写码一路绿灯）。

AC5 写的验收方式是「比对两处 DOM 的分组标题序列」。但本项目里两处**本来就 `th:replace` 同一个 fragment**（`perm-matrix :: matrix`），数据同样来自 `AdminPageCatalog.byGroup()` —— 一致不是比出来的，是结构上给定的，**比了也是恒真**。真正值得钉的是**有没有人把它 fork 掉**：某天为了给账号面板加一列，复制一份 fragment 改改 —— 从那一刻起两处开始各自演化，而任何比对 DOM 的测试**在 fork 当天仍然是绿的**（内容还一样），等分叉显现已是几个 story 之后。所以 `bothPermissionPanelsRenderTheSameMatrixFragment` 钉的是引用关系本身。**这是对 AC5 验收方式的有意替换，结论更强而不是更弱。**

**🔴 顺带发现一个生产权限缺口，待拍板（不在本 story 私自改）**：
`GET /admin/comments/distribution`（评论管理页签二，Story 4.1）门是
`SUPER_ADMIN | comment.virtual_post | content.view`，**比页签一 `/admin/comments` 的
`content.proactive_takedown` 松**；非 htmx 直达时 `return "admin/comments"`，是**整页不是片段**。

🔴 **闭合 Story 11.1 转过来的观察项**。11.1 的原文是：

> 新增的 `GET /admin/charts`、`GET /admin/nav/badges` 没有 `@PreAuthorize`，只靠 `/admin/**` 链级 `ROLE_ADMIN`
> （与基线里的 `/admin`、`/admin/dashboard` 同姿态，不算漂移）—— **11.4 应显式确认这是有意为之**。

上一轮**没有回应这一条**。现逐条核实，结论是**两条都是有意为之且各自带了防护**，不需要补 `@PreAuthorize`：

| 端点 | 为什么没有门 | 敏感数据怎么挡住的 |
|---|---|---|
| `GET /admin/nav/badges` | 侧栏角标，**任何后台账号**都要能拉自己那份 | `AdminNavController` 把登录者的 `authorities` 传进 `NavBadgeService.counts(...)`，**计数只含该账号可见的队列** —— 一个只有 `shop.product_view` 的运营看不到「复核队列 87」这种数字。类注释里已写明这条口径 |
| `GET /admin/charts` | 它是 `/admin` 看板的图表片段，而 **`/admin` 本身也没有 `@PreAuthorize`**（看板是全员可见的首页）—— 给片段加门而整页没门，反而是不一致 | 唯一敏感的付费卡数据由 `canViewPayment(auth)` 在**服务端**裁剪后才进 model（`charts.chartData(range, canViewPayment(auth))`），不是靠模板 `sec:authorize` 隐藏；且非 htmx 访问直接 302 回 `/admin` |

判据不是「有没有注解」，而是「**没有注解的那条路径上，敏感数据是不是在服务端就被裁掉了**」。两条都满足。
**观察项关闭**，不转下一个 story。
