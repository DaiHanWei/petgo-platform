# Story 5.3: 场所处置——编辑、下架 / 恢复、删照片 / 评论、合并

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（写操作三件套：`@PreAuthorize` + `AdminAuditService.record` 同事务 + 三语 key）。
> 本 story 把 5.2 抽屉的操作条接上六个写端点。**合并是本版本唯一不可逆的场所操作**，务必单事务。

## Story

As a 运营，
I want 修正错误信息、下架违规场所、删掉个别违规照片评论、把重复场所合并，
so that 用户端的场所数据可控。

## Acceptance Criteria

**AC1 · 编辑**
**When** 抽屉「编辑」→ 行内表单 → `POST /admin/places/{id}/edit`
**Then** 可改 名称（≤80）/ 类型 / 标签 / 描述 / 文字地址（≤255）/ 纬度 / 经度；**标记人不可改**（表单不渲染该字段，服务端忽略传入）`[L1]`
**And** 坐标校验：纬度 [-90, 90]、经度 [-180, 180]、小数位 ≤6，越界 422 行内 err（`admin.err.places.latRange` / `lngRange` / `coordPrecision`）；落在雅加达都会区包围盒外（见 Dev Notes）→ **200 但响应 fragment 带黄条警告**「坐标不在雅加达都会区，请确认」，不拦截 `[L1]`
**And** 审计 `PLACE_EDITED`，summary 记改动字段名列表（不记坐标值与地址全文）`[L1]`

**AC2 · 下架 / 恢复**
**When** 「下架」（data-confirm 复述场所名与「用户端将不可见」）→ `POST /admin/places/{id}/delist`
**Then** `status=DELISTED`；`MERGED` 行不可下架（422 `admin.err.places.alreadyMerged`）；审计 `PLACE_DELISTED` `[L1]`
**When** 「恢复」→ `POST /admin/places/{id}/restore`
**Then** `DELISTED → ACTIVE`；审计 `PLACE_RESTORED`；恢复后无需任何数据修复（护照章与打卡记录本就未删）`[L1]`
**And** 幂等：已 DELISTED 再下架 / 已 ACTIVE 再恢复 → no-op 200，不写审计 `[L1]`

**AC3 · 删单张照片 / 单条评论**
**When** `POST /admin/places/{id}/photos/{photoId}/remove` / `POST /admin/places/{id}/comments/{commentId}/remove`（无 data-confirm，行内即删）
**Then** 软删（`deleted_at`）；照片允许删至 0 张（用户端以占位图兜底，契约 X-3 注明）；删评论同事务按其 `attitude` 扣 `recommend_count` / `not_recommend_count` 各 −1，并 `comment_count −1`；删照片 `photo_count −1` `[L1]`
**And** 审计 `PLACE_PHOTO_REMOVED` / `PLACE_COMMENT_REMOVED`，summary 记 photoId / commentId，**不记评论正文**（≤50 字摘要亦不记，场所评论可能含 PII）`[L1]`
**And** 照片 / 评论不属于该场所 → 404 fragment `[L1]`

**AC4 · 合并**
**When** 「合并」→ 弹层内搜索选择**保留场所**（搜索复用 5.2 的 `search`，排除自身与非 ACTIVE）→ data-confirm 复述「保留 A、并入 B，不可撤销」→ `POST /admin/places/{mergedId}/merge`（body `keepId`）
**Then** 单事务内：① `place_photos` / `place_comments` / `place_checkins` 的 `place_id` 从 B 改指 A；② B `status=MERGED`、`merged_into_id=A`；③ A 五个计数列全量 `recount`；④ 发布 `PlaceMergedEvent(keepId, mergedId)`（`AFTER_COMMIT` 语义，由监听方 `REQUIRES_NEW`）；⑤ 审计 `PLACE_MERGED` summary「B(name) → A(name)」 `[L1]`
**And** 校验：A ≠ B；A 必须 `ACTIVE` 且未软删；B 必须 `ACTIVE` 或 `DELISTED`（已 MERGED 不可再合并）；否则 422 `[L1]`
**And** B 的 `place_reports` 中 PENDING 行不迁移，保持指向 B（举报的是 B 这个条目），5.4 队列展示时对 MERGED 场所标注「已并入」`[L1]`
**And** 合并后用户在 A、B 两边都盖过的护照章合并语义（并一枚、次数相加）**由 App 分支监听事件实现**，本 story 只保证事件字段完整 `[L0]`

**AC5 · htmx 与权限**
**Then** 六个端点全部 `@PreAuthorize("hasRole('SUPER_ADMIN') or hasAuthority('place.manage')")`；成功 200 + 抽屉 fragment + `hx-swap-oob` 列表该行与摘要条；失败 422 / 404 fragment；无整页跳转 `[L1]`
**And** 六个端点写入 Story 2.1 的写操作清单（本版新增端点，Epic 11 diff 时应出现在「PRD 定义的新增」列）`[L0]`

**AC6 · 测试**
**Then** MockMvc：六端点各成功 + 至少一个失败分支；合并的事务性（模拟计数重算失败 → 全部回滚，B 仍 ACTIVE）；事件发布断言 `[L1]`

## Dev Notes

### 🔴 合并事务步骤（伪码）

```
@Transactional
merge(mergedId, keepId, actor):
  require mergedId != keepId                       -> admin.err.places.mergeSelf
  keep   = places.findByIdAndDeletedAtIsNull(keepId)   orElse 404
  merged = places.findByIdAndDeletedAtIsNull(mergedId) orElse 404
  require keep.status == ACTIVE                    -> admin.err.places.keepNotActive
  require merged.status in (ACTIVE, DELISTED)      -> admin.err.places.mergedNotMergeable
  photos.reassign(mergedId -> keepId)              // UPDATE place_photos   SET place_id=:keep WHERE place_id=:merged
  comments.reassign(mergedId -> keepId)            // UPDATE place_comments SET place_id=:keep WHERE place_id=:merged
  checkins.reassign(mergedId -> keepId)            // UPDATE place_checkins SET place_id=:keep WHERE place_id=:merged
  merged.markMerged(keepId)                        // status=MERGED, merged_into_id=keep, 计数列清零（可选，MERGED 行不再展示计数）
  recount(keepId)                                  // 5 个 COUNT 一条 SQL 回写 keep 计数列
  audit.record(actor, PLACE_MERGED, "PLACE", mergedId, "<merged.name> → <keep.name>")
  events.publishEvent(new PlaceMergedEvent(keepId, mergedId, now, actor))
```
`place_reports` **不迁移**：举报针对的是 B 这个条目本身（如「重复」），迁到 A 会让 A 莫名多出举报。5.4 的队列 SQL 对 `status='MERGED'` 的场所在 sub_type 里标「已并入」。

### 🔴 雅加达都会区包围盒（警告不拦截）

Jabodetabek 近似矩形：**纬度 −6.9 ～ −5.9，经度 106.3 ～ 107.3**（覆盖 Jakarta / Bogor / Depok / Tangerang / Bekasi）。落在盒外只返回 200 + 黄条「坐标不在雅加达都会区，请确认」（D-33：运营从 Google Maps 复制，抄错一位很常见，但 UI 稿 2-20 已出现 Bandung 场所，说明业务确实有雅加达以外的点，所以不拦）。硬拦的只有物理越界：纬度 ∉ [−90, 90]、经度 ∉ [−180, 180]、小数位 > 6（UI 稿 2-22 示例「纬度 −96.5 → 纬度须在 −90 ~ 90」）。

### 🔴 「已产生的护照章与 Diary 打卡记录保留不删」怎么落地

下架只改 `status`，`place_checkins` 一行不动；护照章表在 App 分支。用户端直链看到「场所不存在」是 App 侧按 `status != ACTIVE` 判断（契约 X-3 已写），恢复后自动复原，**后台不需要任何数据修复动作**——不要写「恢复时重建打卡」之类的多余逻辑。

### 🔴 审计 detail 不记评论正文与坐标值

架构模式规则：应用日志与审计 detail 禁记评论正文、邮箱、坐标。`PLACE_COMMENT_REMOVED` 只记 commentId；`PLACE_EDITED` 只记「改了哪些字段」。
