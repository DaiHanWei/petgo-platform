# Story 2.5: 被拉黑者视角与已注销用户的主页

Status: review

## Story

As a 被某人拉黑了的用户,
I want 打开他主页时看到的是一个体面的空页面,
so that 我不会因为一个刺眼的提示而确认自己被拉黑、进而去闹。

## Acceptance Criteria

**AC1 — 模糊空态** `[L2]`
被拉黑者访问拉黑者主页：头像 / 昵称 / 加入时间**正常展示**（不做模糊、不隐藏），**只有内容区**替换成空态「暂无内容（对方的隐私设置）」。**不明示拉黑**。

**AC2 — 🔴 两种空态必须同一个** `[L0]`
该空态与「这个人真的没发过公开内容」的空态**必须复用同一个组件、同一句文案**。
两者只要有任何视觉或文案差异，用户一对比就能推断出自己被拉黑，设计意图作废。

**AC3 — 服务端判定** `[L1] [L0]`
拉黑判定在**服务端**完成并决定下发什么，**不是**客户端拿到内容后再藏起来。
判定走**既有的那个统一拉黑读取口**，不新写查询。

**AC4 — Feed 与评论不屏蔽** `[L2]`
被拉黑者仍**正常看到**对方的内容与互动（仅主页维度做此例外）。

**AC5 — 已注销用户** `[L1]`
打开已注销用户的主页 → 统一「用户不存在」空态，不泄漏昵称 / 头像 / 任何内容。

**AC6 — 记录例外** `[L0]`
完成说明里写明：**这是对 1.1.4 FR-94「被拉黑方完全无感」的有意例外（仅主页维度）**，1.1.4 文档不回改、以本 FR 为准。

## Dev Notes

### 🔴 AC2 是本 story 的核心，也是最容易做错的

直觉会驱使人给"被拉黑"写一句更贴切的文案 —— 那正好毁掉整个设计。
**实现上应当是同一个 widget、同一个文案 key，服务端下发的两种情况在客户端根本区分不出来。**

最稳的写法：服务端对这两种情况返回**完全相同**的响应形状（空列表 + 同一个空态标识），客户端压根没有"被拉黑"这个概念。

### 拉黑关系读取口

`com.tailtopia.social` 模块（`UserHideRelationReader` / `UserHideRelationService`）。
AD-7 要求四处（场所评论 / 公开主页 / @候选 / 宠物推荐）**共用同一个出口**，禁各写各的——写漏的那一次是**静默**的，只有被拉黑的人看见了他不该看见的东西。

### 注销用户匿名化

既有口径见 `MiniProfileResponse.deactivated()`：不暴露任何身份信息。本 story 照同一口径。

### 验证层级

L0：AC2/3（统一出口可静态证）/6 · L1：AC3/5 · L2：AC1/4

### Completion Notes List

**已交付（L0 全绿）**

1. **四条读路径全部加了反向判据**（AC1/AC3）：判据是既有的
   `UserHideRelationReader.isBlocked`，**只是把两个参数掉过来**
   （`isBlocked(ownerId, viewerId)` = 他拉黑了我；反过来是我拉黑了他，走 403）。
   **没有新写任何查询**（AD-7：四处共用同一个出口）。
   | 路径 | 被拉黑者拿到的 |
   |---|---|
   | `GET /users/{id}/profile` | 身份区照常，**两个计数归零** |
   | `GET /users/{id}/posts` | **空信封**（空 items + hasMore=false + 无 nextCursor + 无 rankMode） |
   | `GET /users/{id}/pet` | **204**（与「他没养宠物」同一个响应） |
   | `GET /pets/{petId}/visitor/*` | **404 + 同一句 GONE_DETAIL**（与「档案不存在 / 主人注销 / 被封」合流） |
2. **两种空态是同一个**（AC2）：服务端对「真的没公开内容」与「他拉黑了我」返回
   **逐字段相等**的响应（一条测试直接 `assertThat(blocked).isEqualTo(empty)`），
   客户端因此**压根没有"被拉黑"这个概念** —— 空态是同一个 widget、同一个文案 key。
   - 🔴 **计数必须归零**：写着「18 postingan」配一个空网格，用户一眼就知道自己被拉黑了。
   - 空态文案按 UI 稿 C4 统一成「Belum ada konten (pengaturan privasi orang ini)」，
     **两种情况共用这一句**。三条守门测试：l10n 里不得出现第二个"内容区空"key、
     主页源码里不得出现 `blockedByOwner` 之类的分支、文案里不得出现 block/blokir/hidden 字样。
3. **已注销**（AC5）：Story 2.1 建立的口径，此处加了回归用例
   （昵称 / 头像 / 签名 / 加入时间 / 两个计数全空）。
4. **Feed 与评论不屏蔽**（AC4）：本 story **一行都没碰** Feed 与评论区的代码路径。

**code-review 复审后修掉的（6 findings：修 4、说明 1、本次补 1）**

1. 🔴 **自己视角的空态在说胡话**：共用那句「(对方的隐私设置)」渲染在**自己的**主页上
   变成了「你的内容被这个人的隐私设置挡住了」。→ 自己视角单独一句
   `profilePostsEmptySelf`。**在这里分一次是安全的**：被拉黑的访客 `self` 永远是 false；
   也正因如此，**他人视角那一侧绝不能再分第三种文案**（源码与 arb 注释都写了）。
2. 🔴 **畸形游标是个问答口**：短路发生在解游标之前，于是 `?cursor=@@@`
   对普通访客是 422、对被拉黑者是 200 空页 —— 两个请求就能问出「我是不是被他拉黑了」。
   → 短路前先把游标解一遍（解出来的值不用，要的就是它抛不抛），并加了一条用例。
3. 🔴 **`/mini-profile` 还在报真实 postCount**：那个端点 App 侧已无调用方但仍然活着，
   「`/profile` 说 0、`/mini-profile` 说 18」当场告诉他自己被拉黑了。→ 同口径归零。
4. **`public_profile_posts_test` 里被删掉的文案守卫没补回来** → 换成更贴切的一条
   （空态文案不得出现 block / blokir / hidden 字样）。
5. **story 状态与 sprint-status 未更新（AC6）** → 本节即为 AC6 的记录，状态已置 review。

**🔸 一条固有限制（不是本 story 引入的，记录在案）**

三个主页端点都是 `permitAll`（Story 2.1/2.2/2.3 的既定口径：点头像看这人是谁不需要登录）。
于是**把 Authorization 头去掉再请求同一个 URL，就能看到真实计数与内容** ——
被拉黑者据此可以确认自己被拉黑。

⚠️ 但这不是本 story 新开的口子，也不是最容易的那条路：**AC4 明写 Feed 与评论区不屏蔽**，
所以被拉黑者本来就会在自己的 Feed 里刷到对方的帖子，而点进那个人的主页却是空的 ——
这个对比比"退出登录再看一遍"直接得多。
换句话说，FR-118.5 求的是**不主动明示**，不是密码学意义上的不可区分；
真要堵死就得把主页整体改成登录可见（与 2.1~2.3 的口径冲突）。**这是产品取舍，本 story 不自行改动。**

**范围边界（有意不做）**

- **Feed 与评论区一行不碰**（AC4）。
- **不给"被拉黑"写更贴切的文案**（AC2 的核心，源码里写了原因）。
- **「···」照常渲染**：被拉黑者仍可举报 / 反手拉黑对方；把它藏起来反而是一个可对比的信号。
- **不改主页的鉴权口径**（见上面那条固有限制）。

**L1（需 Docker postgres）—— 全部用「B 拉黑 A，然后用 A 的 token 请求」的方式验**

| # | 验什么 | 怎么验 | 对应 AC |
|---|---|---|---|
| 1 | 🔴 主页逐字段一致 | A 请求 B 的 `/profile`，与「请求一个真的没发过公开内容的人 C」的响应**逐字段比**（除昵称/头像/加入时间等各自的身份值外，形状与两个计数必须一致） | AC1/AC2 |
| 2 | 🔴 计数归零 | B 明明有 18 条公开内容 → A 拿到的 `postCount` / `likeCount` **都是 0** | AC1 |
| 3 | 身份区照常 | 同一响应里 nickname / avatarUrl / joinedAt / signature **都在**（不做模糊、不隐藏） | AC1 |
| 4 | 🔴 无标识字段 | 响应体全文**搜不到**任何 blocked / hidden / restricted 之类的键 | AC2 |
| 5 | 🔴 内容区空信封 | A 请求 B 的 `/posts` → `{"items":[],"hasMore":false}`，**没有** nextCursor、**没有** rankMode | AC1 |
| 6 | 🔴 畸形游标同错 | `?cursor=@@@`：A（被拉黑）与 C（普通访客）拿到**同一个状态码同一个错** | AC2 |
| 7 | 宠物卡 204 | B 有宠物 → A 请求 `/users/B/pet` 回 **204**，与「C 没养宠物」同一个响应 | AC1 |
| 8 | 🔴 宠物直达 404 | A 拿着 B 家宠物的 petId 直接请求 `/pets/{petId}/visitor/profile` → **404 + 「链接已失效」**，与一个不存在的 petId **逐字节同一个响应**（⚠️ 不能是 403） | AC1/AC3 |
| 9 | 🔴 mini-profile 同口径 | A 请求 `/users/B/mini-profile` → `postCount` 也是 **0**（不能与 `/profile` 打架） | AC2 |
| 10 | ⚠️ 只举报不算 | B 只**举报**过 A（没拉黑）→ A 看 B 的主页**照常有内容** | AC3 |
| 11 | 方向不能反 | A 拉黑 B（反向）→ A 请求 B 的主页是 **403 blocked-user**（不是空页） | AC3 |
| 12 | 已注销 | B 注销后 → A 与任何人请求 B 的主页都是「什么都不给」的投影 | AC5 |
