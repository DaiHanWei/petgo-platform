# Story 2.5: 被拉黑者视角与已注销用户的主页

Status: ready-for-dev

## Story

As a 被某人拉黑了的用户,
I want 打开他主页时看到的是一个体面的空页面,
so that 我不会因为一个刺眼的提示而确认自己被拉黑、进而去闹。

## Acceptance Criteria

**AC1 — 模糊空态** `[L2]`
被拉黑者访问拉黑者主页：头像 / 昵称 / 加入时间**正常展示**（不做模糊、不隐藏），**只有内容区**替换成空态「暂无内容（对方的隐私设置）」。**不明示拉黑**。

**AC2 — 🔴 两种空态必须同一个** `[L0]`
该空态与「这个人真的没发过公开内容」的空态**必须复用同一个组件、同一句文案**。
两者只要有任何视觉或文案差异，用户一对比就能推断出自己被拉黑，设计意图作废。

**AC3 — 服务端判定** `[L1] [L0]`
拉黑判定在**服务端**完成并决定下发什么，**不是**客户端拿到内容后再藏起来。
判定走**既有的那个统一拉黑读取口**，不新写查询。

**AC4 — Feed 与评论不屏蔽** `[L2]`
被拉黑者仍**正常看到**对方的内容与互动（仅主页维度做此例外）。

**AC5 — 已注销用户** `[L1]`
打开已注销用户的主页 → 统一「用户不存在」空态，不泄漏昵称 / 头像 / 任何内容。

**AC6 — 记录例外** `[L0]`
完成说明里写明：**这是对 1.1.4 FR-94「被拉黑方完全无感」的有意例外（仅主页维度）**，1.1.4 文档不回改、以本 FR 为准。

## Dev Notes

### 🔴 AC2 是本 story 的核心，也是最容易做错的

直觉会驱使人给"被拉黑"写一句更贴切的文案 —— 那正好毁掉整个设计。
**实现上应当是同一个 widget、同一个文案 key，服务端下发的两种情况在客户端根本区分不出来。**

最稳的写法：服务端对这两种情况返回**完全相同**的响应形状（空列表 + 同一个空态标识），客户端压根没有"被拉黑"这个概念。

### 拉黑关系读取口

`com.tailtopia.social` 模块（`UserHideRelationReader` / `UserHideRelationService`）。
AD-7 要求四处（场所评论 / 公开主页 / @候选 / 宠物推荐）**共用同一个出口**，禁各写各的——写漏的那一次是**静默**的，只有被拉黑的人看见了他不该看见的东西。

### 注销用户匿名化

既有口径见 `MiniProfileResponse.deactivated()`：不暴露任何身份信息。本 story 照同一口径。

### 验证层级

L0：AC2/3（统一出口可静态证）/6 · L1：AC3/5 · L2：AC1/4
