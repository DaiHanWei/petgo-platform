# Story 1.4: 庆祝状态记账与存量回填

Status: review

## Story

As a 用户，
I want 系统记得哪些成就我还没被告知过，
so that 我错过的庆祝能被补上而不是永远消失。

---

> **现状**：庆祝只有一次机会。不在场时解锁（如被点赞触发）→ 无庆祝；存健康记录后 500/800/1200ms 三次轮询没拉到 → 永远不弹。系统**根本不记录「庆祝过没有」**，所以也无从补。
>
> **本 story 只做记账，不做补弹**（补弹在 1.5）。三件事：加字段、回填存量、提供幂等回报通道。
>
> 🔴 **回填不可省**：不回填则上线首日全体老用户进列表页被补弹一堆旧成就，且不可撤回。**必须与建列同在一支迁移内。**

---

## Acceptance Criteria

### AC1 — 字段落在正确的表（L0 / L1）

**Given** 数据库
**When** 迁移执行完毕
**Then** `milestone_completions` 新增可空列 `celebrated_at`（`TIMESTAMPTZ`，UTC） `[L1]`
**And** 该列加在 `milestone_completions` 而非 `pet_milestones` `[L0]`
**And** 迁移文件名为时间戳制 `[L0]`

> ⚠️ PRD §3.2 原文写「`pet_milestones` 新增 `celebrated_at`」，**已由架构 delta AD-A1.1 订正**。`pet_milestones` 是每宠物的目录实例（建档即全量铺行），完成态在 `milestone_completions`（1:1，`uq_milestone_completions_milestone`）。

### AC2 — 🔴 存量回填（L1）

**Given** 上线前已存在的全部完成记录
**When** **同一支迁移**执行完毕
**Then** 其 `celebrated_at` 已回填为各自的 `completed_at` `[L1]`
**And** 回填与建列在同一支迁移内，不拆两次上线 `[L0]`

**Given** 通用宠物被错点亮的 3 条脏完成行（决策 A-9：不清理）
**When** 回填执行
**Then** 这 3 条一并被标记为「已庆祝」 `[L1]`
**And** 这是期望结果 —— 它们不该再被补弹 `[L1]`

### AC3 — 判据唯一（L0）

**Given** 全链路
**When** 判断某条是否「已完成且未庆祝」
**Then** 判据一律为「`milestone_completions` 存在行 且 `celebrated_at IS NULL`」 `[L0]`
**And** 前端不得另立任何本地标记 `[L0]`

### AC4 — 回报端点幂等（L1）

**Given** 一次庆祝回报请求，目标记录 `celebrated_at` 为空
**When** 服务端处理
**Then** 写入当前时刻 `[L1]`
**Given** 目标记录 `celebrated_at` 已有值
**Then** 不覆盖 `[L1]`
**And** 实现为 `UPDATE ... WHERE celebrated_at IS NULL` `[L0]`

### AC5 — 🔴 置位范围按客户端回传列表（L1）

**Given** 客户端提交的 code 列表
**When** 服务端置位
**Then** **只**置位列表中的条目 `[L1]`
**And** **不得**执行 `WHERE celebrated_at IS NULL` 的批量置位 `[L0]`

> 🔴 批量置位会吞掉「客户端读取 → 回报」之间新解锁的条目（被点赞、被评论都可能在这几百毫秒内发生），使其**永不补弹** —— 等于用 FR-111 造出 FR-111 要修的 bug。

### AC6 — 未庆祝计数随既有接口下发（L1）

**Given** 成长档案页头部所依赖的接口
**When** 返回里程碑进度数据
**Then** 一并返回「已完成且未庆祝」的条目数 `[L1]`
**And** **不**为此新开接口、**不**额外发一次请求 `[L0]`

### AC7 — 不扩散（L0）

**Then** 不实现角标 UI、不实现补弹（属 Story 1.5） `[L0]`
**And** 不改动庆祝页任何视觉（重绘属批次 C） `[L0]`

**已交付（L0 全绿）**

1. **迁移 `V20260910_1108__add_celebrated_at_to_milestone_completions.sql`**（AC1/AC2）：
   `ALTER TABLE milestone_completions ADD COLUMN celebrated_at TIMESTAMPTZ`（**可空**）
   ＋**同支内** `UPDATE ... SET celebrated_at = completed_at WHERE celebrated_at IS NULL`。
   - 列加在 `milestone_completions` 而非 `pet_milestones` —— **PRD §3.2 原文写错了表**，按 AD-A1.1 订正。
   - 不加 `NOT NULL`：`NULL` 正是「已完成但未庆祝」这个语义本身。
2. **实体 / 仓库**：`MilestoneCompletion.celebratedAt` + `isUncelebrated()`；
   `markCelebrated(ids, now)`（`@Modifying`，JPQL 带 `celebratedAt is null`）与
   `countByPetMilestoneIdInAndCelebratedAtIsNull(ids)`。
3. **回报端点** `POST /api/v1/pet-profiles/me/milestones/celebrations`，请求体 `{codes: [...]}`
   （非空、上限 64），返回 `{markedCount, uncelebratedCount}`。owner 取自 JWT。
   - `markedCount` 是**实际由 NULL 变非空**的行数，不是请求里的 code 数（幂等自然体现）。
   - `uncelebratedCount` 让客户端一次请求就能刷角标，不必再发一次。
4. **🔴 按列表置位，不 mark-all**（AC5）：service 先把 code 解析成**该宠物自己的** roster 行 id，
   再交给仓库更新。两个作用：① 天然限定在本人档案内（别人的 code 落不到行上）；
   ② 让「按列表」在类型上就成立 —— 仓库那层拿到的是一串 id，**写不出 mark-all**。
   未知 / 非本人 / 未完成的 code 静默忽略，不报错（回报与服务端状态本就有几百毫秒偏差，
   为此让回报失败只会换来一次多余的补弹）。
5. **角标计数并入既有响应**（AC6）：`ArchiveStatsResponse` 加第 6 个字段 `milestoneUncelebrated`，
   由 `TimelineService.getStats` 顺带填。**没有新开接口、没有为角标多发一次请求** ——
   那里本来就要查 roster 与 completions。
