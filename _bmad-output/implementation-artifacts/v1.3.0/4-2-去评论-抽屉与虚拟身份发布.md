# Story 4.2: 「去评论」抽屉与虚拟身份发布（走完整审核）

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`。
> 后端为主 + 后台抽屉 UI；**含一支迁移**（`comments.reply_to_comment_id` 预留，D-35 / X-2）和一处 `/api/v1` 兼容扩展（回复请求体可选字段，本版不使用）。无 App 端改动。

## Story

As a 运营，
I want 在抽屉里选一个虚拟账号给冷帖写评论，提交后进审核，通过才公开，
so that 暖评与真实用户评论走同一条规则，不会有后台特权评论。

## Acceptance Criteria

**AC1 · 抽屉结构（UI 稿 2-9 / 2-10）**
**Given** 4-1 列表某行「去评论」
**When** `GET /admin/comments/distribution/{postId}/drawer`（`HX-Request`，返 fragment）
**Then** 自上而下：帖子预览（首图缩略 + 正文摘要 + 作者昵称 + 有效物种 + 当前可见评论数）→ 已有评论列表（一级 + 二级，时间正序；**虚拟账号发的带后台可见「虚拟」标识**；审核中的显示「审核中」标识）→ 常驻评论区 `[L2]`
**And** 评论区 = 身份下拉 + 文本框（`maxlength=200`，剩余字数）+ 「发布」按钮；**身份未选或内容为空时按钮禁用**（F7 规则 11）`[L2]`

**AC2 · 身份下拉（UI 稿 2-10）**
**Then** 选项 = `users.account_type='VIRTUAL' AND enabled=true` 的虚拟账号；**默认只列与帖子有效物种匹配**（`account_species` = 帖子物种，或帖子物种为 GENERAL 时全部）的账号，其他物种收起可「展开全部」`[L1]`
**And** 每项带「今日已评 N 条」（该虚拟账号 WIB 当日发出的评论数，含审核中）`[L1]`
**And** 下拉带搜昵称过滤；**默认不预选**（沿用 `publish-identity-select` 片段的防呆）`[L2]`
**And** 真实身份池（`seed_real_account_grants`）**不出现**在此下拉——暖评只用虚拟账号（PRD ②「取运营发布身份池中启用中账号」按 UI 稿 2-10 与 §④「身份 ∈ 虚拟账号池」收窄为虚拟账号）`[L1]`

**AC3 · 发布 = 走 App 同一入口、完整审核（D-4）**
**Given** `POST /admin/comments/virtual`（form：`postId`、`virtualUserId`、`body`、`idempotencyKey`）
**When** 提交
**Then** 服务层校验：虚拟账号存在且 `account_type='VIRTUAL' AND enabled=true`；帖子 `PUBLISHED` 且未删；body 非空 ≤200 `[L1]`
**And** 调用 `CommentService.createTopLevel(postId, virtualUserId, body)`——**与 App 端 `POST /api/v1/content-posts/{postId}/comments` 同一方法**，显式传虚拟账号 id 作 authorId，**不伪造 SecurityContext / 不切换登录态** `[L1]`
**And** L1 黑名单命中 → `AppException.commentBlocked` → 422 操作区 fragment 行内 err「评论包含不当词汇」；否则评论落 `UNDER_REVIEW`，由既有 `CommentModerationListener` 异步机审：PASS → VISIBLE + `ContentCommentedEvent`（作者收「有人评论了你的内容」通知，`ContentNotifyListener` 既有链路）；HIGH_RISK / DEGRADED → 入人工队列（A1 内容送审页签可见、由运营处置）`[L1]`
**And** **只发一级评论**（D-35）：抽屉内不提供「回复某条评论」入口 `[L0]`

**AC4 · 提交反馈与连发**
**Then** 成功 → toast「已提交，审核通过后显示」（**不是**「发布成功」）；抽屉不关、文本框清空、身份保持；已有评论列表顶部插入该条并标「审核中」；列表「评论数」列**不即时 +1**（口径是可见评论）`[L2]`
**And** 抽屉底部「下一帖」按钮：按 4-1 当前筛选结果集顺序打开下一帖抽屉（服务端在 fragment 根元素带 `data-next-post-id`）`[L2]`

**AC5 · 幂等与防呆（D-20：软提示不拦截）**
**Then** `idempotencyKey` 由抽屉打开时生成（UUID，隐藏字段），成功后刷新；重复提交同 key → 短路返回同一结果，不产生第二条评论 `[L1]`
**And** 同一虚拟账号对同一帖 **10 分钟内**已评过 → 首次点击行内提示「该账号刚评过这帖，确认再发？」，二次点击即发（不弹层）`[L2]`
**And** 同帖虚拟评论（可见 + 审核中）已 ≥3 条 → 评论区上方黄条提示「本帖虚拟评论已 N 条，注意官托观感」，**不拦截**；不加每日硬上限 `[L2]`

**AC6 · 权限、审计、数据边界**
**Then** 端点 `@PreAuthorize("hasRole('SUPER_ADMIN') or hasAuthority('comment.virtual_post')")`；无权限 403 禁用态 fragment `[L1]`

**And** 「虚拟」标识只在后台 fragment 渲染；`/api/v1` 任何评论响应不新增字段 `[L1]`

## Dev Notes

### 🔴 「同链路」的准确含义：调 `CommentService.createTopLevel`，别新写一条落库路径

`CommentService`（`content/service/`）的一级评论入口做了三件事：`requireVisible(postId)`、L1 黑名单同步拒绝、落 `UNDER_REVIEW` 并发 `CommentSubmittedEvent`。随后 `CommentModerationListener`（`@Async @TransactionalEventListener(AFTER_COMMIT)`）跑机审：PASS → `approveComment` 转 VISIBLE 并发 `ContentCommentedEvent`；其余 → `queueForReview` 入 A1 队列。**暖评只要调这一个方法，审核、通知、入队全部自动继承**（D-4）。

后台不能直接 `comments.save(Comment.create(...))`——那是绕审核直接 VISIBLE，PRD 明令禁止。`CommentService` 类注释也写了「admin 不直读 comments repo」。

### 🔴 身份不是「登录态」，是显式参数

`createTopLevel(postId, authorId, body)` 的 `authorId` 本来就是普通参数（App 端由 `CommentController` 从 JWT 解出来再传）。后台传虚拟账号 id 即可，**不要**去构造一个假的 `Authentication` 或改 `SecurityContextHolder`——审计 actor 仍是运营的 `adminAccountId`（`AdminUserDetails.getAdminAccountId()`），评论 author 是虚拟账号，两者分开记。

### 🔴 为什么「评论数不即时 +1」、toast 写「已提交」

评论落库时是 `UNDER_REVIEW`，只有评论人（这里是虚拟账号）可见；4-1 列表的评论数口径是**可见评论**。机审是异步的（阿里云评分），几秒到几十秒后才 VISIBLE。所以立刻 +1 是撒谎，D-4 拍板改成「已提交，审核通过后显示」+ 列表标「审核中」。

### 幂等：复用 `shared/ratelimit/IdempotencyService`

Redis `Idempotency-Key → resourceId` 映射、TTL 24h；`store()` 内部已做「事务内调用推迟到提交后写」（防回滚后被误判重放——支付线踩过的坑）。后台表单带隐藏 `idempotencyKey`（抽屉打开时 UUID），双击 / 网络重试不会发两条。**不要**自建幂等表。

### 「今日已评 N」与两条软提示的口径

- 今日 = WIB 自然日（`(created_at AT TIME ZONE 'Asia/Jakarta')::date = 今天`），含审核中与已可见，排除软删。
- 10 分钟窗与 ≥3 条统计都按 `author_id` + `post_id`，含审核中——目的是防「连发看着像官托」，审核中的也算。
- D-20：都是提示，不拦截，不加每日上限。

### 身份池收窄说明（回报架构 / 产品）

PRD ② 写「取运营发布身份池中启用中账号」，但 §④ 与 D-29「排除虚拟账号」判定都以**虚拟账号池**为边界，UI 稿 2-10 下拉也只有「虚拟 · 猫」这类项。真实身份池（`seed_real_account_grants`，真人授权的账号）用来发种子帖可以，**替真人去评论别人的帖**风险另一个量级（那人会在自己的 App 里看到自己「说过」的话）。本 story 只列虚拟账号；若产品要放开真实身份池，需单独拍板并复用 `publish-identity-select` 片段的 `data-real-identity-confirm` 二次确认。
