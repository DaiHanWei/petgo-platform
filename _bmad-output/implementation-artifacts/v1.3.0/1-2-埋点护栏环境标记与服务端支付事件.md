# Story 1-2: 埋点护栏、环境标记与服务端支付事件

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端→前端→联调、AC 标 L0/L1/L2、Flyway 时间戳版本号、`mvn -B clean package`）。
> 本 story **只碰后端**（`shared/analytics` + `pay/` + `shop/order/`），App 一行不改（App 侧埋点是 1-4）。
> 🔴 **本 story 无 Flyway 迁移**，但**有一项部署侧动作**：`APP_ENV` 必须写进 `~/.env.petgo` / `~/.env.petgo-stag`，否则 staging 数据会混进生产漏斗。
> 前置：本 story 的 `PaymentFailureCategory` 复用 **1-1** 的产出，请先做 1-1。

## Story

As a 运营，
I want 在 PostHog 看到电商支付的完整漏斗与失败原因分布，且 staging 的数据不混进来，
so that 我能持续判断支付到底出了什么问题，而不是靠一次性查库猜（SD-1）。

### (e) 🔴 埋点监听器**刻意不加 `@Async`**

`MilestoneAnalyticsListener.java:20-22` 的注释写明：`AnalyticsClient.capture` 本身已是 `@Async("analyticsExecutor")`，监听器再叠一层 `@Async` 等于往同一个线程池投两次任务。

（对照：`shared/im/ImAccountRegistrationListener.java:28-29` 那类**要出网做别的事**的监听器才需要自己的 `@Async`。）

## Acceptance Criteria

**AC1 · `AnalyticsEventGuard` 事件名白名单**
**Given** `shared/analytics` 无任何护栏
**When** 新增 `com.tailtopia.shared.analytics.AnalyticsEventGuard`（`@Component`），持有事件名白名单
**Then** 白名单初始含**既有 5 个**（`milestone_achieved` / `pet_card_link_opened` / `pet_card_cta_tapped` / `pet_card_cta_outcome` / `post_share_link_opened`）+ **本 story 新增 5 个**（`shop_payment_intent_created` / `shop_payment_paid` / `shop_payment_declined` / `shop_payment_expired` / `shop_payment_user_cancelled`），共 10 个 `[L0]`
**And** 不在白名单的事件名 → **整条事件丢弃 + `log.warn` 一行（只记事件名，不记 properties）**，`capture` 正常返回，**不抛异常、不影响任何业务路径** `[L0]`

**AC2 · `AnalyticsEventGuard` 属性键白名单**
**Given** 属性可能被后续工作线顺手塞进 PII
**When** 调用方传入属性 map
**Then** 白名单外的**属性键被逐键丢弃**（事件本身照发，不整条丢） `[L0]`
**And** 属性键白名单初始含既有 8 个（`code` `level` `path` `page_state` `ua_platform` `referrer_host` `outcome` `open_method`）+ 本 story 新增 4 个（`order_amount` `failure_category` `pay_channel` `has_pawcoin`），共 12 个 `[L0]`
**And** 属性**值**只允许 `String` / 数值（`Number`）/ `Boolean` 三类；其它类型（`Map` / `List` / 任意对象）**一律丢弃该键** `[L0]`
**And** `String` 值长度上限 **64**（与 App 侧 `analytics.dart:58` 的 `_maxStringValueLen` 同值），超长即丢弃该键 `[L0]`

**AC3 · 护栏接进唯一上报通路**
**Given** `PostHogAnalyticsClient.capture` 是全部服务端事件的唯一出口
**When** 本 story 落地
**Then** `capture` 在 `isEnabled()` 早退之后、组装 body 之前调用 guard；被拒的事件**不发出网请求** `[L0]`
**And** `distinct_id` 与 `app_env` 两个**框架注入**的键在 guard 之后加入，不受属性白名单约束 `[L0]`
**And** `AnalyticsClient` 接口签名**不变**（不新增方法、不改参数），既有 3 个调用方一行不改 `[L0]`

**AC4 · 环境标记 `app_env`**
**Given** staging 与生产同跑 `SPRING_PROFILES_ACTIVE=prod`，profile 区分不了
**When** `capture` 组装 properties
**Then** 每条事件都带 `app_env`，取值来自配置 `analytics.app-env` ← 环境变量 `APP_ENV`，缺省 `dev` `[L0]`
**And** 取值**只允许** `prod` / `stag` / `dev` 三者之一；配置成其它值 → 回退 `dev` 且启动时 `log.warn` 一次 `[L0]`
**And** `.env.example` 与 `docker-compose.yml` 同步登记 `APP_ENV`（默认 `dev`） `[L0]`
**And** 既有 3 个上报点的事件也一并带上 `app_env`（这是有意的口径统一，不是回归） `[L0]`

**AC5 · 🔴 变异验证（护栏假绿是本工作线出过三次的事故）**
**Given** AC2 的属性键白名单校验
**When** 把 `AnalyticsEventGuard` 中**属性键白名单那一段判断**注释掉（只删这一段，其余不动）
**Then** `AnalyticsEventGuardTest` 中**至少一条**用例变红，且失败信息能指出「本该被丢的属性键漏出去了」 `[L0]`
**And** 同样对**事件名白名单**做一次：删掉事件名判断 → 至少一条用例变红 `[L0]`
**And** 变异验证的**执行结果**（删了哪一行、哪个测试方法红了）写进 Completion Notes；只写「做过了」不算 `[L0]`

**AC6 · 服务端支付事件：五个事件名**
**Given** 电商支付的五个结局
**When** 新增 `ShopPaymentAnalyticsListener`（`com.tailtopia.shop.order.service`）
**Then** 分别上报 `shop_payment_intent_created` / `shop_payment_paid` / `shop_payment_declined` / `shop_payment_expired` / `shop_payment_user_cancelled` `[L0]`
**And** 监听器用 `@TransactionalEventListener(phase = AFTER_COMMIT)`，**不加 `@Async`**（理由见 Context (e)） `[L0]`
**And** `distinctId` 走 `AnalyticsDistinctId.of(userId)`（`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/shared/analytics/AnalyticsDistinctId.java:27`），不自造 `[L0]`
**And** **只统计 `PaymentPurpose.SHOP_ORDER`**；其余四个 purpose 一条事件都不发 `[L0/L1]`

**AC7 · 事件属性只含枚举与数值，不含任何 PII 与订单号**
**Given** SHOP-NFR-01
**When** 上报任一支付事件
**Then** 属性集合**只能是** `order_amount`（long，订单总额）/ `failure_category`（`PaymentFailureCategory` 名或 null 时不带该键）/ `pay_channel`（`PayChannel` 名）/ `has_pawcoin`（boolean，`coinAmount != null && coinAmount > 0`） `[L0]`
**And** **不含** 订单号、`orderToken`、`publicToken`、`displayNo`、收件人姓名 / 电话 / 地址 / 邮箱、`gateway_meta` 任何片段 `[L0]`
**And** 有一条测试逐键断言上述禁用键**一个都不出现**（不是「写的时候注意点」） `[L0]`

**AC8 · 拒付这一支能被订阅到**
**Given** 网关拒付完全不经过 `shop/` 代码（Context (d)）
**When** 在 `pay` 侧新增 `PaymentIntentFailedEvent` 并在失败 / 过期写入点发布
**Then** `applyCallback` 的 `FAILED` 与 `EXPIRED` 两个分支、`failByToken`、`expireOverduePending` 四处**都发**该事件 `[L0]`
**And** 事件携带 `purpose` / `channel` / `amount` / `userId` / `failureCategory`（由 1-1 的 `PaymentFailureCategory.of(intent)` 算出），**不携带 `gatewayMeta`** `[L0]`
**And** `PaymentIntentPaidEvent` 的既有形状与发布点**不改**（成功那一支复用它） `[L0]`

**AC9 · 「创建意图」事件不因幂等重放而灌水**
**Given** `ShopOrderPaymentService.ensureIntent(...)` 是幂等的 —— 重复点「去支付」取回同一个意图、同一个二维码（`ShopOrderPaymentService.java:155-166`）
**When** 同一订单连点三次「去支付」
**Then** `shop_payment_intent_created` **只发一次** `[L1]`
**And** 判据是「本次返回的意图 token 与订单上已挂的 `payment_intent_token` 不同」，不是「调用了 ensureIntent」 `[L0]`

**AC10 · 集成回归**
**When** 跑集成测试
**Then** 支付成功与失败各跑一次，断言监听器被触发、事件名正确、属性集合**恰好等于**白名单允许的子集 `[L1]`
**And** 既有 3 个上报点的事件仍能发出（白名单没把它们误伤） `[L1]`
**And** `PostHogAnalyticsClientTest` 更新后全绿；`mvn -B clean package` 通过 `[L0]`

**AC11 · staging 实跑**
**When** 在 staging 用支付模拟器跑成功 / 拒付 / 超时三支
**Then** PostHog 中出现对应的 `shop_payment_*` 事件，且每条都带 `app_env=stag` `[L2]`
**And** 生产漏斗按 `app_env=prod` 过滤后**看不到**这批 staging 事件 `[L2]`

## Dev Notes

### 白名单的两级粒度，别写反

| 违规 | 处置 | 为什么 |
|---|---|---|
| 事件名不在白名单 | **整条丢** + WARN | 未登记的事件名一旦发出去就在 PostHog 里建了一个新 event 类型，清不掉 |
| 属性键不在白名单 | **只丢该键**，事件照发 | 漏斗的分母靠事件本身，为一个多余的键把整条事件丢掉是更坏的结果 |
| 属性值类型/长度不合规 | 丢该键 | 嵌套 map / 长文本是 PII 最常见的载体 |

### 为什么值类型闸也要有（不只是键白名单）

App 侧 `scrub` 已经踩过一次：`analytics.dart:248-252` 的注释写着「**List 也要递归**（Story 9.2 补）：行级归因把 `items[]` 这种『map 的数组』带进了埋点……只要有人往行里加个收件人名，它会绕过全部三道规则直接发出去」。
服务端这道闸直接**不允许**容器类型作为属性值，从形状上杜绝同类问题，比递归过滤更省事也更难写错。

### 与 epics 的两处有意偏离（必须写进 Completion Notes）

1. **监听器不加 `@Async`** —— epics 1-2 AC3 写了 `@Async`，但 `MilestoneAnalyticsListener.java:20-22` 的既有注释明确说明 `capture` 自己已是 `@Async("analyticsExecutor")`，叠两层是往同一个有界池投两次任务（core 1 / max 2 / queue 200 / `DiscardPolicy`，`AsyncConfig.java:38-48`），会更早触发丢弃。
2. **属性键新增 4 个而非「订单金额、失败类别、支付渠道、是否含 PawCoin」四个中文描述** —— 落地键名为 `order_amount` / `failure_category` / `pay_channel` / `has_pawcoin`，snake_case，与既有服务端属性键风格（`page_state` / `ua_platform` / `open_method`）一致。

### 已知盲区（SD-1 要求如实记录，不要试图在本 story 解决）

「**用户已付款但系统没收到到账通知**」在 App 与服务端事件里**都表现为超时**（`shop_payment_expired`）。本 story 的埋点发现不了它，只能靠支付网关后台 / 对账发现。
⇒ 不要为了「补上这个盲区」去加轮询网关、加对账任务或加中间件；SD-1 已拍板本版就到监控为止。
