# Story 3.2: @ 选择器与插入

Status: review

## Story

As a 正在写评论的用户,
I want 打一个 @ 就弹出人名让我选,
so that 我不用记住对方昵称怎么拼，选一下就插进去了。

## Acceptance Criteria

**AC1 — 两处触发** `[L2] [L0]`
内容正文输入框与评论/回复输入框，输入「@」**都**弹出用户选择器浮层。
选择器是**全新叠加层**（现状输入框是纯文本框、无任何触发机制）。

**AC2 — 候选内过滤** `[L2]`
继续输入昵称文字 → **仅在候选集这 30 人内过滤**。
⚠️ 界面上那个输入框**不是搜索框**，文案与视觉不得让人以为能搜到任何用户。

**AC3 — 空态** `[L2]`
当前用户没有任何互动过的人 → 显示空态；**候选为空时不显示过滤输入框**。

**AC4 — 🔴 存 userId 不存昵称** `[L0]`
选中后正文里插入 @昵称，同时**在数据层绑定该用户的 userId**。
存昵称则对方改名后历史 @ 全部失效、点不动，也无法判断拉黑关系。

**AC5 — 上限 5 人** `[L2]`
单条内容或单条评论最多 @ **5 人**，达上限后不能再插入并给出提示（防骚扰）。

### Completion Notes List

#### 存储形态（AC4）：JSONB 列，不是 mentions 关系表

`content_posts` 与 `comments` 各加一列 `mentioned_user_ids JSONB`（迁移
`V20260915_1429__add_mentioned_user_ids.sql`）。**没有**建 mentions 表，理由三条：

1. v1.1.6 AD-10 的先例是「**不用多态外键**」，而 `mentions(target_type, target_id)` 正是那个被否掉的形状；
   要守住它就得建 `post_mentions` + `comment_mentions` 两张表，每张只装 ≤5 行 bigint。
2. 这份数据**从不被独立查询**：渲染（3.3）与发通知（3.4）都是拿着帖子/评论那一行在手时才用它。
   「按被 @ 的人反查内容」是被 @ 通知列表，走 notifications 表，不走这里。
3. 上限硬定在 5，不会长成无界数组。仓内同形先例：`content_posts.image_urls` / `places.tags`。

**存量一律 NULL、零回填**（AD-10 Rule 6：存量文本不回溯解析）。读取侧一律经
`getMentionedUserIds()` 归一成空表，永不返回 null。

#### 🔴 服务端把「@ 不到陌生人」当闸门，不当前端约定（AD-10 Rule 3）

`MentionSanitizer` 在落库前做四件事，**三条批量查询、与人数无关**（AD-6）：

| 过滤 | 判据 | 拒绝方式 |
|---|---|---|
| 超过 5 人 | AC5 | **422**（产品规则，用户看得见、该给反馈）|
| 不在候选表里 | 与 `mention_candidates` 求交 | 静默剔除 |
| 自己 / 已注销 / 不存在 | `findAuthorViewsWithoutTags` | 静默剔除 |
| 任一方向有拉黑关系 | `UserHideRelationReader.hiddenEitherWay`（AD-7 统一出口）| 静默剔除 |

- 交集判据是「**在不在这张表里**」而不是「在下发的那 30 个里」：30 是展示口径、表里留 50。
  拿 30 卡会造成假拒 —— 打开选择器时某人排第 29，选中的瞬间又有两个人冒到前面，提交时他掉到第 31。
- 静默剔除而非报错：报错等于把「这个 id 存不存在 / 他有没有拉黑我 / 跟我互动过吗」
  做成一个可以逐个试探的问答口（同 Story 2.5 的口径）。用户看到的是发出去了、那个名字点不动 ——
  与「对方发完之后才把我拉黑」的结果完全一致。
- **运营内容源（`publishTrusted`，Lark 定时发帖）刻意不写 @ 名单**：@ 会给人发通知，
  由运营账号批量发出去就是骚扰，而那条路径本就免审。

#### 🔴 给 Story 3.4 的两条硬约束（已写进源码注释，别照记忆抄）

1. **非 PUBLIC 的内容不得发 @ 通知。** PRIVATE（同步开关关掉的 Diary）**照样落 @ 名单** ——
   作者自己那条时间线上的「@昵称」得能高亮能点（3.3），不落库就是一段死文字。
   但可见范围创建后不可更改（FR-83 AC7），被 @ 的人**永远打不开它**。
   判据用 `visibility == PUBLIC`，**别用「有没有 mentionedUserIds」**。
2. **挂起帖 / 挂起评论的 @ 通知应落在「转可见那一刻」**，不是提交那一刻
   （同 `approveComment` 的既有口径）。挂起分支此刻不发任何事件，所以天然不会误发。

#### 前端：@ 的数据层是一个纯 Dart 类

`features/mention/domain/mention_draft.dart` 不依赖 Flutter / Riverpod —— 触发规则、上限、
「删字之后这个 @ 还算不算数」全是纯逻辑，所以能在 L0 逐条钉住（37 例）。

- **触发规则**：`@` 必须在词首（行首或前一个字符是空白）。少了这条，`user@mail.com`
  打到一半就会弹人名出来。`@` 与光标之间出现空白 / 第二个 `@` / 超过 20 字 → 浮层收起。
- **提交口径**：只发**文本里还留着 `@昵称`** 的那些 id。插完又删掉照单全发的话，
  对方会收到一条「有人 @ 了你」、点进去正文里根本没有他。
- @ 绑定住在 `PublishController.mentions`（与正文同生同死，随 sheet dispose 清空），
  **不在页面 State 上** —— 放页面上的话重建一次就会出现「正文里还写着 @阿花、id 已经丢了」。

#### AC2/AC3：那个输入框不是搜索框（范围红线，有机械守卫）

没有全局用户搜索（留在 1.6.0，未前移 —— AD-10 Rule 3）。`mention_picker_test.dart` 直接钉住：

- 打字**不触发任何网络请求**（一旦触发，那个框就已经是搜索框了）；
- 占位文案是「找名字」（`Cari nama…`）而**不是**「搜索用户」，且**没有放大镜图标**；
- 筛不出来说的是「没有匹配的名字」，**不是**「用户不存在 / 没找到该用户」——
  后者是在承诺全局搜索过了；
- **候选为空时不渲染过滤输入框**（AC3）——一个搜不出任何东西的输入框只会让人一直敲；
- 取数失败与「一个候选都没有」走**同一个空态**：用户能做的事完全一样（去互动 / 手打名字）。

#### ⚠️ code-review 修掉 4 条

1. **插入绕过 `maxLength`**（两处都中）：插入是直接写 `TextEditingController.value`，
   不经输入格式化器。200 字的评论插一个长昵称 → 218 字 → 服务端 `@Size(max=200)` 必拒，
   而用户只看到通用的「发送失败，请重试」，**重试永远不会成功**；发布页的表现是
   「发布按钮悄悄变灰」，更查不到原因。改成插入前用 `textAfterInsert(...)` 预演一次、
   按各自上限（200 / 1000）拦住并提示字数。
2. **服务端没把 @ 名单与候选集求交**（见上）：一个 for 循环遍历 userId 就成了对任意陌生人的
   定向推送口（3.4 会把每个 @ 变成一条通知）。
3. **`userIdsIn` 用裸 `contains`**：昵称是别的昵称前缀时误判 —— @ 了「An」又删掉、
   后文写了「@Ana」，裸 contains 认为 An 还在，于是给 An 发一条他并不在其中的通知。
   改成要求昵称后面不是 Unicode 字母 / 数字 / 下划线（只认 ASCII 等于对中文 / 带重音昵称全失效）。
4. **PRIVATE 内容的 @ 会被 3.4 通知出去**：不改行为（落库是 3.3 高亮的前提），
   改成把约束写进 `ContentPost.mentionedUserIds` 的 javadoc 与 publish 调用点（见上）。

#### 🔸 一条残留的已知不精确（记录在案，未自行加复杂度）

候选集里**两个人昵称一模一样**时（真有可能），文本里一处 `@同名` 会把两个 id 都发出去，
于是两人各收到一条通知。要分清得在文本里埋不可见标记（或逐键维护区段偏移），
代价远大于这点误差。已写进 `userIdsIn` 的注释。

#### 🔴 L1/L2 待本地验收清单

**L1（需 Docker + postgres + redis）**

1. 迁移能跑：`V20260915_1429__add_mentioned_user_ids.sql` 应用后 `/actuator/health=UP`
   （`ddl-auto=validate`，两个实体各多一列，validate 过不去会启动即崩）。
2. **JSONB 往返**：带 `mentionedUserIds: [x, y]` 发一条帖 / 一条评论，直接查库确认
   `SELECT mentioned_user_ids FROM content_posts WHERE id=?` 是 `[x, y]`；再读出来确认
   Hibernate 能把它反序列化成 `List<Long>`（`@JdbcTypeCode(SqlTypes.JSON)` + 泛型擦除，
   这一步只有真库能验）。
3. **存量行**：对一条迁移前就存在的帖子读 `getMentionedUserIds()`，应为空表（列是 NULL）。
4. **候选交集真的拦得住**：手工构造一个「不在 `mention_candidates` 里的 userId」提交，
   确认落库的 `mentioned_user_ids` 里没有它（这是本 story 最重要的一条 L1）。
5. **拉黑排除**：A 拉黑 B 后，B 提交 `mentionedUserIds: [A]` → 落库为空。
6. 超过 5 人 → 422（DTO 的 `@Size` 与 service 的权威校验各走一次：
   经 Controller 的走 `@Valid`，运营/后台链路走 service）。
7. **挂起分支也要写**：把人工审核开关打开、构造一条挂起帖，确认 `mentioned_user_ids` 有值
   （只写正常分支的话，审核挂起的帖过审后那串「@昵称」是死的）。

**L2（需模拟器 / 真机视觉）**

1. AC1 两处触发：详情页底部评论条、发布页正文，打「@」都弹出浮层；浮层位置与键盘不打架
   （评论条那个浮层长在输入条上沿，发布页那个贴正文框下沿）。
2. AC2：浮层里接着打昵称能筛；视觉上**不像搜索框**（无放大镜、占位是「Cari nama…」）。
3. AC3：拿一个从没互动过的新账号打开浮层 → 空态 + **没有过滤输入框**。
4. AC5：连选 6 个人，第 6 个插不进去且弹出「Maksimal menyebut 5 orang」。
5. 插入后光标落在昵称后的空格之后，可以接着打字（不用手动移光标）。
6. 快到字数上限时选人 → 弹字数提示、文本不被改动（对应 code-review 第 1 条）。
7. 印尼语文案核对：`mentionFilterHint` / `mentionEmptyTitle` / `mentionEmptyHint` /
   `mentionNoMatch` / `mentionLimitReached` / `publishTextLimitReached` 六条。
