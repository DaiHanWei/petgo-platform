# Story 1.9: 他人为场所补充照片

Status: review

## Story

As a 也去过这家店但照片更全的用户,
I want 给这个场所补几张照片,
so that 后面的人能看到更真实的样子，而不是只有标记人拍的那几张。

## Acceptance Criteria

**AC1 — 非标记人可补充** `[L2]`
场所详情页，非标记人的用户也可以为该场所补充照片，走既有上传链路与公开桶。

**AC2 — 标注上传者** `[L2]`
补充的照片**标注上传者**（2026-08-28 确认保留）。

**AC3 — 审核与 EXIF** `[L1]`
走既有三方自动审核（先发后审）+ EXIF 剥离服务端兜底。

### Completion Notes List

**🔴 T1 的那个选择题：扩结构化列 vs 另起一张表 —— 选了另起表，理由如下**

Story 1.1 建表时照片是 `places.photo_urls`（一个 JSONB 字符串数组）。那个形态**装不下本 story
要的三样东西**：

1. **每张照片的上传者**（AC2 要标注，而数组里只有 URL）；
2. **每张照片自己的审核态**（AC3 先发后审）—— 审核回调要改的是「某一张」，
   在 JSONB 数组上做就是**读-改-写整个数组**：两张照片同时过审必丢一条
   （后写的用自己读到的旧数组覆盖）；
3. **单张删除 / 下架**（同理）。

「扩成 JSONB 数组里放对象」能装下字段，但**装不下并发正确性** —— 所以另起
`place_photos`（CROSS-STORY C3：表名带模块前缀）。

**🔴 并且是「搬」不是「并存」**：迁移 `V20260915_0927__init_place_photos.sql` 把存量
`places.photo_urls` 逐元素展开搬进新表（上传者 = 标记人、`is_original=true`、顺序 = 数组下标），
然后**删掉那一列**。留着它就是第二份真相 —— 下一个人往哪边写都「对」，而读路径只认一边。

**已交付（L0 全绿）**

**后端**

1. **`place_photos`**：place_id / uploader_id / url / moderation_status / sort_order /
   `is_original` / 软删 / 时间戳。两条 partial 索引（按场所取、按上传者取）。
2. **谁都能补**（AC1）：`POST /api/v1/places/{token}/photos`，**没有**「只有标记人能加」的判断 ——
   场所是共享的地点条目，标记人连场所本身都改不了。加那条判断就等于把场所变成他的私产。
3. **标注上传者**（AC2）：详情响应的 `photoUrls`（字符串数组）换成了 **`photos`**
   （每项带 `uploaderId` / `uploaderNickname` / `uploaderDeleted` / `moderationStatus` / `mine`）。
   ⚠️ 这是一次**契约变更**，客户端同步改了；两侧契约测试都更新。
4. **先发后审**（AC3）：补充的照片落 `UNDER_REVIEW`（上传者自己立刻看得见，他人要等过审），
   `@Async` 监听批量送审。判定**三分**：
   - PASS → VISIBLE；
   - **确定性违规**（图审命中高置信违规 / 文本 L1）→ **REJECTED**（终态）；
   - **三方降级**（「不知道」）→ **保持挂起**，绝不自动放行。
   ⚠️ 第二条是场所**评论**那边没有的：文本审核把「高危」和「降级」混在一个判定里、分不开；
   图审能分开 —— **「确定违规」可以判死，「不知道」不行**。
5. **标记时那批不重复审**：`PlaceService.mark` 已经连同名称/地址/描述一起送过图审，
   所以 `storeInitialPhotos` 直接落 VISIBLE —— 同一批图审两遍是白花配额。
6. **上限按整个场所算**（9 张，与标记表单同一个数）：按人算的话十个人各传 9 张 = 90 张图的横滑流。
7. **EXIF 服务端兜底**（E4）：每条 URL 经 `exifStrippedThumbUrl` —— 施加点从 DTO 挪到了
   `PlacePhotoView.of`（每张照片各自带 URL）。
8. **注销级联**：上传者注销 → 他**补充的**照片置 `AUTHOR_DEACTIVATED`；
   **标记时提交的那批不隐藏**（首图 / OG 预览图都取它，随人隐藏会把整个场所变成无图条目）。

**前端**

9. **照片流重做**：每张图上浮一行「由 XX 提供」（AC2；浮在图上而不是另起一行 ——
   另起一行会让每张图矮一截、还要用户把标注和图对上号），末尾一格「+ 补充照片」。
10. **走既有上传链路**（`MediaUploadUseCase` + 公开桶）—— 不新写一条：那条链路已经带着
    「仅图片、无视频」（F4）与客户端 EXIF 剥离，另起一条等于把这两样重新实现一遍。
11. **提示「审核中」而不是「已发布」**：补充的照片此刻只有他自己看得见，
    说成「已发布」他会去问别人为什么看不到。

**code-review 复审后修掉的（8 findings 全修）**

1. 🔴 **选图数写死 9 而不是剩余张数**：一个已有 7 张照片的场所里选 9 张 → 9 张全传上公开桶、
   然后整批 422，用户只看到一句「上传失败」，而那 9 个对象已经躺在桶里成了孤儿。
   → 按 `9 - 已有张数` 选（标记表单那边本来就是这么做的）。
2. 🔴 **9 张上限把「谁都看不见的行」也算进去**：`REJECTED` / `AUTHOR_DEACTIVATED` 的行没被软删，
   于是一个界面上只有 4 张照片的场所**永远加不进第 5 张**，而用户没有任何办法腾位置
   （那些行他看不见、也删不掉）。→ 只数 VISIBLE + UNDER_REVIEW（`countOccupyingSlots`）。
3. 🔴 **被判死的照片一直标着「审核中」**：那是终态，等于让上传者永远等一个不会来的结果。
   → 区分「审核中」与「未通过」两个标签。
4. **单张删除在 App 里根本点不到**：端点、`mine` 标记、文档都承诺了它，但没有入口。
   → 自己传的那张右上角给 ✕（44×44 热区）+ 二次确认。
5. **没有上传中保护**：20 秒的上传过程中再点一次就起第二次并发补充，两批各自算剩余张数 ——
   一个成功一个 422，失败的那几张已经在桶里。→ 加 `uploading` 门 + 转圈。
6. 🔴 **可以把场所的照片删到零张**：而标记时照片是**必填**的（1–9 张），场所又不可编辑 ——
   一张张删光就留下一个永远没有照片、谁也补不回原样的条目（列表首图与 OG 预览图一起没了）。
   → 服务端挡「最后一张对外可见的照片不许删」（删待审 / 被拒的不受限）。
7. 🔴 **注销级联的豁免判据错了，且是 N+1**：原先按「上传者是不是这个场所的标记人」判 ——
   标记人**事后**给自己标的场所补的图也被一起豁免（那些该隐藏），而且每张照片查一次 `places`。
   → 改成行上的 `is_original` 列（在迁移里一并加），既判对又零额外查询。
8. **`ContentModerationService` 注入了却没用**（监听器自己持有一份）→ 删掉。

**范围边界（有意不做）**

- **举报单张照片**：违规照片走**场所举报** + 运营下架（AB-17A），本 story 不加逐张举报入口；
- **重排照片顺序**：没有任何 AC 要求，而且「谁能排」在一个共享条目上是个没讨论过的问题；
- **运营端点**：后台处置属 admin 主题（同评论那条）。

**🔴 与 Story 1.7 同一条待办（admin 主题）**

三方审核**降级**（「不知道」）的照片会一直挂在 `UNDER_REVIEW`（仅上传者可见）。
运营人工队列尚未覆盖场所资源 —— 接入需要 admin 主题扩 `ReviewContentType`。
在那之前，降级期间的照片需要人工从库里捞。
