# Story 4.1: 推荐规则与宠物卡（Diary 未建档态）

Status: review

> **依赖 Epic 2**：宠物卡点击落点复用 Story 2.3 交付的「宠物档案访客视图（站内入口）」，**本 story 不新建通道**。

## Story

As a 养了宠物但还没建档的用户,
I want 在 Diary 页看到一些别人家的毛孩子,
so that 我能看看别人是怎么记录的，而不是对着一个空页面发呆。

## Acceptance Criteria

**AC1 — 候选与排序** `[L1]`
候选 = **近 14 天有新公开 Diary 帖**的宠物；门槛 = **有头像 + 公开成长记录 ≥3 条**。
排序 = **最近更新倒序**，同日按**互动量**。
🔴 **不复用 FR-95 打分** —— 那是内容级算法，本 FR 是宠物级简单规则，两套独立。
纯自动规则、**零后台依赖**（本版不加任何后台配置项）。

**AC2 — 🔴 算法成本口径** `[L1] [L0]`
推荐池**实时 SQL 查询**（不许加缓存层）。因此必须给出索引方案 —— 至少覆盖「公开 Diary 帖的宠物 + 发布时间」与「宠物公开记录条数」两个过滤维度，并**贴出执行计划确认走索引**。
若实测实时查询扛不住，**允许的降级只有 `@Scheduled` 定时算好落表**，**不得引入任何缓存或中间件**。

**AC3 — 推荐池边界** `[L1] [L0]`
只推荐**有公开内容**的宠物；**互相拉黑的双方不互推**（判定走既有统一读取口）；**已注销用户的宠物不入池**；**不做 opt-out 设置**。

**AC4 — 宠物卡** `[L2]`
含头像 + 名字 + 物种/年龄 + **最近一张公开照片** + **陪伴天数**（「一起 238 天」）。
🔴 大图是**该宠物最近一张公开照片（帖子配图）**，左下角小圆头像是**宠物档案本身的头像** —— **两个不同字段、不同来源，不是同一张图重复摆放**。

**AC5 — 点击落点** `[L2]`
点宠物卡 → 该宠物的 Diary 访客视图，**复用 Story 2.3 的站内入口**，不新建通道。

**AC6 — Diary 未建档态** `[L2]`
「养宠但尚未建档」的用户打开 Diary 页：推荐集合**追加在现有引导之下**，原有「+ 建档」与「Ubah status」两个操作**原样保留、一个不删**。
「Ubah status」会改变宠物拥有状态，故**刻意弱化、与主按钮拉开距离**，避免手滑误触。
推荐集合以 **2 列网格铺满当前页**。
⚠️ 「查看全部」入口**不在本 story** —— 它的落点是 Story 4.3 才交付的全屏集合页，由 4.3 一并加上。

**AC7 — 埋点** `[L1]`
上报 `pet_card_tapped` / `diary_visitor_viewed`，属性 `from` 取 `diary_empty`。

## Dev Notes

### 🔴 AC2 是圆桌评审补上的，别跳过

原 epics 只写了规则，没写"这个池子怎么算"。不许加缓存（NFR-8）意味着只能实时查，那就必须像 AD-2 给距离排序那样**把索引方案写出来并验证**。

两个过滤维度都不便宜：
- "近 14 天有新公开 Diary 帖" → 要按 `pet_id + 发布时间 + 可见范围` 过滤
- "公开成长记录 ≥3 条" → 要按宠物聚合计数

**先写查询、再看执行计划、再决定索引**，不要凭感觉加索引。

### AC4 的两个图片字段（最容易做错）

| 位置 | 取哪个字段 |
|---|---|
| 卡片大图 | 该宠物**最近一条公开帖的配图** |
| 左下角小圆头像 | **宠物档案自身的头像**（`PetProfile.avatarUrl`） |

UI 稿 UX-DR15 专门强调了这点。做成同一张图重复摆放是明显 bug。

### 陪伴天数

= 今天 − 宠物档案创建日（或用户填的领养/出生日，按既有 H5 名片的口径）。
⚠️ 注意：`visitor_archive_view.dart` 里有一条注释说「Diary 页不引入陪伴天数，那是 H5 名片独有的」——那说的是**Diary 档案页**，与本 story 的**推荐卡片**是两回事，不冲突。

### Completion Notes List

**实现形态（口径以「决策日志-batch-b1.md > PRD > UI 稿」为准）**

- **AC1 候选与排序**：一条实时聚合 SQL（`ContentPostRepository.findRecommendablePets`），
  CTE 形态 —— `candidates`（GROUP BY pet_id + `HAVING COUNT(*)>=3 AND MAX(created_at)>=since`）
  LEFT JOIN 预聚合的 `liked`（点赞数）。排序 `date(last_at) DESC, interactions DESC, last_at DESC, pet_id DESC`
  —— 「同日」按日期截断分桶，否则同一天里先发的永远排后面、互动量那一半永远用不上。
  **没有复用 FR-95 的内容打分**（那是内容级算法，本条是宠物级规则，两套独立），**零后台配置项**。
- **AC2 无缓存**：实时 SQL，`PetRecommendationService` 里有 L0 机械守卫钉住
  「不得出现 `@Cacheable` / `Caffeine` / `RedisTemplate` / `@Scheduled`」。
  索引 = `V20260915_1727__add_pet_recommendation_index.sql` 两条**部分索引**（谓词已下推）。
- **AC3 边界**（各一条 L0 用例）：没头像 / 已注销 / **被封号** / 任一方向拉黑 / 自己的宠物 / 档案已删 —— 全部不入池。
  拉黑走 `UserHideRelationReader.hiddenEitherWay`（AD-7 单一出口，**双向**）。
- **AC4/AC5 卡片**：大图 = 最近一张公开照片（`findLatestPublicCovers`，`DISTINCT ON`），
  小圆头像 = `PetProfile.avatarUrl` —— **两个字段两个来源**（UX-DR15）。点击落 `/pets/{petId}`
  复用 Story 2.3 的**站内**访客入口（AD-4，**不下发 cardToken**），游客走 FR-0C 强登录、不发请求。
- **AC6 Diary 未建档态**：推荐集合追加在既有引导之下，「+ 建档」「Ubah status」原样保留
  （后者按 AC6 刻意弱化、多一段间距）。**取不到 / 池子为空 → 整块不渲染且版面不变**。
- **AC7 埋点**：`pet_card_tapped` / `diary_visitor_viewed`，属性只有 `from=diary_empty`
  （没有宠物名、没有图片 URL）；`pet_card_tapped` 在 `requireLogin` **之前**上报 ——
  游客点了卡也是一次真实点击意图。

**code-review（`/code-review high`）CONFIRMED findings 已修**

1. 卡片在 360/375/390dp 上溢出（最窄处裁掉 7.8px，「一起 238 天」那一行被切）→ 大图从
   `AspectRatio(1)` 改为 `Expanded`，任何宽度都不溢出；新增 L0 用例按三个宽度跑（旧版面下必红，已反向验证）。
2. owner 过滤只判「注销」（`AuthorView.deleted`）漏了「封号」（`status=DEACTIVATED`），
   而落地页用的是 `isActive` → **推荐位里那只宠物点进去 404**。新增
   `AccountQueryService.activeIdsAmong`（批量版 `isActive`，判据与单个版逐字相同）并改用它。
3. 互动量子查询只按 `pet_id` 数点赞，没带 `type/visibility/status/deleted_at` →
   私密 / 已删 / DAILY 帖的点赞在影响**公开**推荐位的排序（把高赞帖改成私密后仍稳坐第一）。
   现在 `liked` 段与 `candidates` 用**同一套谓词**，并有 L0 用例扫源码钉死。
4. 相关子查询形态 = 每个候选独立执行一次 → 改为一次预聚合 CTE + hash join，
   并用 `pet_id IN (SELECT pet_id FROM candidates)` 把范围收在候选集内。
5. 卡片大图没有 `errorBuilder`，图挂了是一块白 + 抛 `NetworkImageLoadException` → 落回爪印占位（新增用例）。
6. `_EmptyProfileView` 无条件把 `Center` 换成滚动容器，与旁边「引导那一段一字未改」自相矛盾 →
   改成**只在真有卡时**换版面（池子空 / 取不到 / 加载中都与改动前逐像素相同），引导那一段抽成
   两分支共用的同一份 children，连 key 都不可能在某一支里漂掉。
