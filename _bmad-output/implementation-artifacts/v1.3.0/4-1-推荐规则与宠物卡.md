# Story 4.1: 推荐规则与宠物卡（Diary 未建档态）

Status: ready-for-dev

> **依赖 Epic 2**：宠物卡点击落点复用 Story 2.3 交付的「宠物档案访客视图（站内入口）」，**本 story 不新建通道**。

## Story

As a 养了宠物但还没建档的用户,
I want 在 Diary 页看到一些别人家的毛孩子,
so that 我能看看别人是怎么记录的，而不是对着一个空页面发呆。

## Acceptance Criteria

**AC1 — 候选与排序** `[L1]`
候选 = **近 14 天有新公开 Diary 帖**的宠物；门槛 = **有头像 + 公开成长记录 ≥3 条**。
排序 = **最近更新倒序**，同日按**互动量**。
🔴 **不复用 FR-95 打分** —— 那是内容级算法，本 FR 是宠物级简单规则，两套独立。
纯自动规则、**零后台依赖**（本版不加任何后台配置项）。

**AC2 — 🔴 算法成本口径** `[L1] [L0]`
推荐池**实时 SQL 查询**（不许加缓存层）。因此必须给出索引方案 —— 至少覆盖「公开 Diary 帖的宠物 + 发布时间」与「宠物公开记录条数」两个过滤维度，并**贴出执行计划确认走索引**。
若实测实时查询扛不住，**允许的降级只有 `@Scheduled` 定时算好落表**，**不得引入任何缓存或中间件**。

**AC3 — 推荐池边界** `[L1] [L0]`
只推荐**有公开内容**的宠物；**互相拉黑的双方不互推**（判定走既有统一读取口）；**已注销用户的宠物不入池**；**不做 opt-out 设置**。

**AC4 — 宠物卡** `[L2]`
含头像 + 名字 + 物种/年龄 + **最近一张公开照片** + **陪伴天数**（「一起 238 天」）。
🔴 大图是**该宠物最近一张公开照片（帖子配图）**，左下角小圆头像是**宠物档案本身的头像** —— **两个不同字段、不同来源，不是同一张图重复摆放**。

**AC5 — 点击落点** `[L2]`
点宠物卡 → 该宠物的 Diary 访客视图，**复用 Story 2.3 的站内入口**，不新建通道。

**AC6 — Diary 未建档态** `[L2]`
「养宠但尚未建档」的用户打开 Diary 页：推荐集合**追加在现有引导之下**，原有「+ 建档」与「Ubah status」两个操作**原样保留、一个不删**。
「Ubah status」会改变宠物拥有状态，故**刻意弱化、与主按钮拉开距离**，避免手滑误触。
推荐集合以 **2 列网格铺满当前页**。
⚠️ 「查看全部」入口**不在本 story** —— 它的落点是 Story 4.3 才交付的全屏集合页，由 4.3 一并加上。

**AC7 — 埋点** `[L1]`
上报 `pet_card_tapped` / `diary_visitor_viewed`，属性 `from` 取 `diary_empty`。

## Dev Notes

### 🔴 AC2 是圆桌评审补上的，别跳过

原 epics 只写了规则，没写"这个池子怎么算"。不许加缓存（NFR-8）意味着只能实时查，那就必须像 AD-2 给距离排序那样**把索引方案写出来并验证**。

两个过滤维度都不便宜：
- "近 14 天有新公开 Diary 帖" → 要按 `pet_id + 发布时间 + 可见范围` 过滤
- "公开成长记录 ≥3 条" → 要按宠物聚合计数

**先写查询、再看执行计划、再决定索引**，不要凭感觉加索引。

### AC4 的两个图片字段（最容易做错）

| 位置 | 取哪个字段 |
|---|---|
| 卡片大图 | 该宠物**最近一条公开帖的配图** |
| 左下角小圆头像 | **宠物档案自身的头像**（`PetProfile.avatarUrl`） |

UI 稿 UX-DR15 专门强调了这点。做成同一张图重复摆放是明显 bug。

### 陪伴天数

= 今天 − 宠物档案创建日（或用户填的领养/出生日，按既有 H5 名片的口径）。
⚠️ 注意：`visitor_archive_view.dart` 里有一条注释说「Diary 页不引入陪伴天数，那是 H5 名片独有的」——那说的是**Diary 档案页**，与本 story 的**推荐卡片**是两回事，不冲突。
