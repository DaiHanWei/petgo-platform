# Story 4-5: C 端商品列表分页

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端→前端→联调、AC 标 L0/L1/L2、`mvn -B clean package`）。
> 本 story **后端 + App 两侧**，**无数据库迁移**。

## Story

As a 用户，
I want 商品多起来以后首屏也能很快打开，
so that 我不用等 App 一次性把全部商品拉完才能开始逛。

## Context（现状与根因）

**现状**：`shop/web/ShopProductController.java:51-55` 的列表端点返回**全量 `List<ShopProductSummaryView>`**，参数只有 `category` 与 `q`，**没有任何分页**。服务层 `shop/service/ShopProductQueryService.java:67` 的 `list(ProductCategory, String query)` 同样一次性返回全部行。staging 现有约 93 个商品 / 264 个规格，商品继续增长后首屏会越来越慢。

**既有约束（必须原样保留）**：
- `q` 命中 **name 或 brand**，忽略大小写；**为空或全空白时行为必须与不传逐字相同**（服务层注释 `:59-61` 明写：搜索框清空要原样回到列表，不能变成"搜了个空串"的另一条分支）。
- 🔴 `q` 与 `category` 是**与关系，不是互斥**（`:63-64`）：选了某品类再搜关键词，只在该品类里搜。做成互斥会让用户以为筛选没生效。
- 非法 `category` → 422，**不静默忽略**（`ShopProductController.java:47` 的 `parseCategory`）。

**既有分页范式**（照抄，不要另造一套）：
- `content/dto/FeedPageResponse.java:7` 与 `content/dto/CommentPageResponse.java:8` —— 统一信封 `{items, nextCursor, hasMore}`，camelCase、`NON_NULL`；`hasMore=false` 时 `nextCursor` 为 null（Jackson 省略）。

## 🔴 本 story 的核心风险：这是破坏性契约变更

线上已发布的 App 版本**期望这个端点返回一个 JSON 数组**。如果直接改成分页信封，老版本会解析失败 —— 轻则只看到第一页，重则整页打不开。本仓多次因「契约变更须前后端同批部署」出过事，而**发版也救不了已经装在用户手机上的老版本**。

因此本 story 的兼容策略是硬性要求，不是可选项：**不带分页参数时，端点必须继续返回原来的全量数组**。

### 🔴 AC2：老版本兼容做了什么，以及它真的会红

- **分支**：`cursor == null && size == null` → 走原来的 `query.list(...)`，返回**全量 JSON 数组**。
  判据是「有没有传分页参数」而**不是 User-Agent** —— 后者既不可靠也没必要。
- **删除条件已写进注释**：保留到「最低支持版本」升级到含分页的版本为止；
  删之前必须确认**线上版本分布**（看实际活跃版本，不是看发版记录）。
- **专用测试** `ShopProductListLegacyShapeTest`，类注释写明「本类保护的是线上已经装在
  用户手机上的老版本 App；删掉这个类等于删掉那条兼容性保证本身」。
  三条老版本用例：不带参数 / 带 category+q / 空结果。
- 🔴 **它不只断言「调了哪个 service 方法」**，还用真实 Jackson 序列化断言
  **第一个字符是 `[` 而不是 `{`** —— 老版本 App 解析的是字节。
  只断言「调了 `list()`」的话，有人把返回值包进信封，那条断言照样绿。
- **已做变异验证**：把兼容分支整段删掉 → **3 条老版本用例变红**，其余 5 条（新形态）不变。

### 🔍 实现中的判断（各一行）

1. **首页用哨兵游标 `ShopProductCursor.START`（`Integer.MAX_VALUE, Long.MAX_VALUE`）**，
   使首页与后续页走**同一条 SQL** —— 没有「第一页特判」，也就没有
   「第一页和第二页过滤/排序口径不一致」这一整类 bug。
2. **keyset 而非 OFFSET**：运营在用户翻页期间调了权重，OFFSET 会让同一件商品在两页里
   出现两次、或一次都不出现。
3. **多取一条判 hasMore**，比再打一次 count 便宜，且不会因为两次查询之间有商品上下架
   而自相矛盾。探测行**绝不下发**（有专门断言）。
4. **页长上限 100**：客户端传个 10000 就等于退化成全量查询，那正是本 story 要消除的东西。
5. **抽出 `toViews` 给两条路径共用**：各拼一遍迟早出现「不翻页时有图、翻页后没图」。
6. **App 侧「切品类/改搜索词重置游标」是靠 family 族键天然成立的**，不是手写 reset ——
   族键就是 `(category, keyword)`，换键即换实例、`build()` 从头拉。手写才会漏。
   有专门用例断言「换品类后第二次请求的 cursor 仍是 null」。
7. **`loadMore` 双重短路**（`loadingMore` 防并发、`hasMore` 防到底后空请求）：
   滚动回调在底部会连发，不短路就会把同一页追加两遍 —— 用户看到重复商品。
8. **`loadMore` 失败不把整页打成错误态**：首屏已经在了，用户的列表还在那儿；
   只复位 `loadingMore` 让他能再滑一次。
9. **App 侧 `fetchProductPage` 永远带 `size`**：不要「第一页省掉 size」——
   那会让第一页走老兼容分支、拿到一个数组而解析失败。
10. **Riverpod 3 家族 override 用 `overrideWith2`**（带族键的重载）；
    不带参的 `overrideWith` 已 deprecated 且拿不到族键，`seen` 这类用例就没法写。
    六处测试共用一份替身 `test/shop/fake_shop_products.dart` —— 六个文件各写一个略有出入的
    假货，正是「测试里绿、真机上红」的常见来源。
