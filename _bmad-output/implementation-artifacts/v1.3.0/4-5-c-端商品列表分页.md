# Story 4-5: C 端商品列表分页

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端→前端→联调、AC 标 L0/L1/L2、`mvn -B clean package`）。
> 本 story **后端 + App 两侧**，**无数据库迁移**。

## Story

As a 用户，
I want 商品多起来以后首屏也能很快打开，
so that 我不用等 App 一次性把全部商品拉完才能开始逛。

## Context（现状与根因）

**现状**：`shop/web/ShopProductController.java:51-55` 的列表端点返回**全量 `List<ShopProductSummaryView>`**，参数只有 `category` 与 `q`，**没有任何分页**。服务层 `shop/service/ShopProductQueryService.java:67` 的 `list(ProductCategory, String query)` 同样一次性返回全部行。staging 现有约 93 个商品 / 264 个规格，商品继续增长后首屏会越来越慢。

**既有约束（必须原样保留）**：
- `q` 命中 **name 或 brand**，忽略大小写；**为空或全空白时行为必须与不传逐字相同**（服务层注释 `:59-61` 明写：搜索框清空要原样回到列表，不能变成"搜了个空串"的另一条分支）。
- 🔴 `q` 与 `category` 是**与关系，不是互斥**（`:63-64`）：选了某品类再搜关键词，只在该品类里搜。做成互斥会让用户以为筛选没生效。
- 非法 `category` → 422，**不静默忽略**（`ShopProductController.java:47` 的 `parseCategory`）。

**既有分页范式**（照抄，不要另造一套）：
- `content/dto/FeedPageResponse.java:7` 与 `content/dto/CommentPageResponse.java:8` —— 统一信封 `{items, nextCursor, hasMore}`，camelCase、`NON_NULL`；`hasMore=false` 时 `nextCursor` 为 null（Jackson 省略）。

## 🔴 本 story 的核心风险：这是破坏性契约变更

线上已发布的 App 版本**期望这个端点返回一个 JSON 数组**。如果直接改成分页信封，老版本会解析失败 —— 轻则只看到第一页，重则整页打不开。本仓多次因「契约变更须前后端同批部署」出过事，而**发版也救不了已经装在用户手机上的老版本**。

因此本 story 的兼容策略是硬性要求，不是可选项：**不带分页参数时，端点必须继续返回原来的全量数组**。

## Acceptance Criteria

**AC1 · 分页能力**
**Given** 商品列表端点
**When** 请求带分页参数（游标 + 可选页长）
**Then** 返回 `{items, nextCursor, hasMore}` 信封，字段命名与 `FeedPageResponse` / `CommentPageResponse` **逐字一致** `[L0]`
**And** 默认每页 **20 条**（SHOP-NFR-03）`[L0]`
**And** 游标编码方式与既有 Feed 游标同范式（不暴露自增 id 的可推算信息）`[L0]`

**AC2 · 🔴 老版本兼容（不可省略）**
**Given** 请求**不带任何分页参数**
**When** 调用列表端点
**Then** 返回**原来的全量 JSON 数组**，与改动前逐字节同构 `[L1]`
**And** 该兼容分支**必须有专门的测试覆盖**，测试名里写明它保护的是线上老版本 `[L0]`
**And** 代码注释写明：此分支保留到最低支持版本升级到含分页的版本为止，**删除前须确认线上版本分布** `[L0]`

**AC3 · 既有筛选与搜索行为零变化**
**Given** `category` 与 `q` 的既有语义
**When** 与分页组合使用
**Then** `q` 仍命中 name 或 brand、忽略大小写；**空白 `q` 与不传 `q` 结果逐字相同** `[L1]`
**And** `q` 与 `category` 仍是**与关系** `[L1]`
**And** 非法 `category` 仍返 422，不因分页改动而变成静默忽略或 500 `[L1]`
**And** 既有 `ShopProductQueryServiceTest` 全绿，不修改其断言 `[L0]`

**AC4 · 分页结果正确**
**Given** 多于一页的商品
**When** 按游标连续翻页
**Then** 不重复、不丢项、顺序与全量返回一致（沿用既有 `idx_shop_products_listing` 的排序口径：品类 + 排序权重 + id）`[L1]`
**And** 最后一页 `hasMore=false` 且 `nextCursor` 省略 `[L1]`
**And** 无结果时返回空 `items` 而不是 404 `[L1]`

**AC5 · App 侧接入**
**Given** App 商品列表页
**When** 用户下滑
**Then** 按游标增量加载，滚动流畅、不重复不丢项 `[L2]`
**And** 加载中、到底了、空结果三种状态各有明确呈现 `[L2]`
**And** 切换品类或改搜索词时游标重置 `[L0]`

**AC6 · 契约同改**
**Given** 对外 DTO 变更
**When** 提交
**Then** 后端 record + App DTO + 契约 test **三处同改**（C5 原文写的是四处，其中 "App mock" 一腿在本仓已随 mock 子系统删除而不存在 —— 实施时确认后按实际处数执行，并在 Completion Notes 记下）`[L0]`

**AC7 · 回归**
**Then** 既有商品列表与详情相关测试全绿；`mvn -B clean package` 与 `flutter analyze` / `flutter test` 通过 `[L0]`

**与其它 story 的关系**
- 与 Epic 4 其余 story **无依赖**，可并行。
- **Story 6-1（品类可配置）** 会把 `category` 从枚举改为 code + 外键。届时 `parseCategory` 的 422 语义要一并迁移；本 story 的分页实现**不要把品类解析逻辑抄进新代码**，仍调用现有入口，减少 6-1 的改动面。
- **Story 9-1** 是后台商品列表的分页搜索，与本 story 是两套端点，不要混。

**不做什么**
- 不改排序规则（排序调整属于 Story 9-1 的后台侧，且本版排序只做总库存 + 状态）。
- 不改商品详情端点。
- 不加任何缓存（禁通用缓存层）。
