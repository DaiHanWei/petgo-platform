# Story 5.4: 新建场所（冷启动预置，手填坐标）与 A1 场所举报页签

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`。
> 两件事：① 后台录入场所（运营预置雅加达 10～20 个核心场所的通道）；② 用户举报的场所进 A1 统一复核工作台新页签处置。两者都复用 5.3 的服务方法，故合为一条。依赖 2.4（A1 页签结构可扩展）。

## Story

As a 运营，
I want 后台直接录入雅加达核心场所，坐标从 Google Maps 复制手填；用户举报的场所进统一复核队列处置，
so that 冷启动有数据、违规场所有出口。

## Acceptance Criteria

**AC1 · 新建场所入口与表单**
**Given** 持 `place.manage`
**When** 列表右上「＋ 新建场所」→ 右侧抽屉表单
**Then** 字段：名称*（≤80）/ 类型*（`PlaceType` 下拉）/ 宠物友好标签（多选胶囊）/ 文字地址*（≤255）/ 纬度* / 经度*（两个数字输入，占位提示「从 Google Maps 复制」）/ 描述 / 照片（0～9 张，可空——冷启动允许先无图）/ 标记人*（下拉 = 运营发布身份池 `selectableIdentities()`，默认「TailTopia Official」） `[L2]`
**And** **不渲染任何地图组件、不引地图库、不请求外部瓦片**（D-32）；UI 稿 2-21 的地图区在实现中替换为两个数字输入（D-33） `[L0]`

**AC2 · 提交与校验**
**When** `POST /admin/places`
**Then** 服务端校验：必填；坐标复用 5.3 `PlaceCoordinateValidator`（越界 422，雅加达都会区外 200 + 黄条警告不拦截）；标记人必须 ∈ 身份池（`isRealPublishIdentity` 或虚拟账号启用中），否则 422 `admin.err.places.markerNotInPool` `[L1]`
**And** 照片走 12-2 既有上传链路（`images.upload(file, "places/<placeId>")` 返回 objectKey），`place_photos.uploader_user_id` = 标记人；只存 objectKey `[L1]`
**And** `public_token` 由 `PlaceTokenGenerator` 生成；`status=ACTIVE`；审计 `PLACE_CREATED`（summary 记场所名，不记坐标）`[L1]`
**And** 成功后 PRG 回列表并高亮新行（`?open=<id>` 自动开抽屉）；失败 422 行内 err（UI 稿 2-22）`[L1/L2]`
**And** 不做批量导入（PRD ③）`[L0]`

**AC3 · A1 新页签「场所举报」**
**Given** `/admin/manual-review`（Story 2.4 已套模板 A）
**When** 打开
**Then** 页签顺序：内容送审 ｜ 内容举报 ｜ **场所举报** ｜ 名称审核 ｜ 头像审核，各带计数；`TicketType` 新增 `PLACE_REPORT`，`ManualReviewAdminController.SCOPE` 收入之 `[L1]`
**And** `UnifiedTicketQueryService.UNIFIED_CTE` 追加第 ⑥ 段：**按场所聚合**（多人举报同一场所 = 一条工单），`source_id = place_id`、`sub_type = string_agg(DISTINCT reason_type)`、`target_user_id = marked_by_user_id`、状态桶 PENDING（任一 PENDING）/ RESOLVED（有 ACTIONED）/ NO_ACTION、`reporter_count` / `report_count` / `frequent_count` 照内容举报口径、`score = reporter_count + frequent_count`、`earliest_at = MIN(created_at)`、`preview = 场所名 [+「已并入」若 status=MERGED]`、`action_ref = MIN(id) FILTER PENDING`、`content_ref = place_id` `[L1]`
**And** 左栏行：第一行 = 场所名 + 状态点；第二行 = 举报原因标签 + 举报人数/次数 + 最早时间；默认分数降序同分时间升序 `[L2]`

**AC4 · 场所举报右栏与处置**
**Then** 右栏三卡：① 场所快照（名称 / 类型 / 地址 / 坐标 / 标记人 / 当前状态 / 照片缩略 / 最近 5 条评论）② 举报列表（举报人昵称 / 原因 / 时间；高频举报人打标）③ 操作区 `[L2]`
**And** 操作表（全部复用 5.3 服务方法 + 新增 dismiss）：

| 按钮 | 端点 | 权限 | 确认 | 成功后 |
|---|---|---|---|---|
| 下架场所 | `POST /admin/places/{id}/delist`（5.3） | `place.manage` | data-confirm 复述场所名 | 该场所全部 PENDING 举报置 ACTIONED；下一条 |
| 删照片 / 删评论 | 5.3 端点 | `place.manage` | 无 | 停留本条（举报仍 PENDING，运营再决定驳回或下架） |
| 驳回举报 | `POST /admin/places/{id}/reports/dismiss-all` | `place.manage` | data-confirm 复述举报条数 | 全部 PENDING 置 DISMISSED；下一条 |

**And** `place_reports.status` 流转 PENDING → ACTIONED / DISMISSED，记 `handled_by` / `handled_at`；审计 `PLACE_REPORTS_DISMISSED`（下架走 5.3 的 `PLACE_DELISTED`）`[L1]`
**And** 场所已 MERGED / DELISTED 时：快照卡标注状态，「下架」按钮禁用并注明，「驳回」仍可用 `[L2]`

**AC5 · 计数同源**
**Then** 场所举报 PENDING 数并入待办中心角标聚合查询（`GET /admin/nav/badges`）与 A1 页签计数，处置后 `HX-Trigger: admin:badge-refresh` `[L1]`
**And** 5.2 摘要条「待处理举报数」链接 `/admin/manual-review?type=PLACE_REPORT` 此时落到该页签 `[L2]`

**AC6 · 权限**
**Then** 场所举报页签的查看与处置均 `place.manage`（不用 `content.takedown`，避免两码管一事——PRD 评审 #35 精神）；无权限则页签不渲染 `[L1]`

**AC7 · 测试**
**Then** MockMvc：新建成功 / 必填缺失 422 / 坐标越界 422 / 都会区外 200+警告 / 标记人不在池 422；A1 带 `type=PLACE_REPORT` 返回聚合行（3 人举报同一场所 = 1 行，reporter_count=3）；驳回后 3 行 DISMISSED；下架后 3 行 ACTIONED；角标计数变化 `[L1]`

## Dev Notes

### 🔴 D-33 之后新建表单长什么样

UI 稿 2-21 帧仍画着 OSM 地图 + 拖大头针（文字已改「手填经纬度（D-33）」但画面未改）。**实现以决策为准**：位置区 = 「纬度」「经度」两个 `type=number step=0.000001` 输入 + 占位「从 Google Maps 右键坐标复制」。不做地图、不做地址搜索定位。设计师同步画面属架构 §反向影响待办，不阻塞本 story。

### 🔴 为什么场所举报「按场所聚合」

与内容举报同理（`UNIFIED_CTE` ① 段注释：12 个人举报同一条帖是一条工单）。运营处置的对象是场所条目，不是某一条举报；驳回是「整场所全部举报驳回」，下架顺带把全部 PENDING 置 ACTIONED。`action_ref` 取任意一条 PENDING id 只是沿用既有列语义，场所段的端点按 `place_id` 收口。

### 🔴 UNION 段对齐清单（照 ① 段 12 列顺序）

`ticket_type` text · `source_id` bigint · `sub_type` text · `target_user_id` bigint · `status_bucket` text · `reporter_count` bigint · `report_count` bigint · `frequent_count` bigint · `score` bigint · `earliest_at` timestamptz · `preview` text · `action_ref` bigint · `content_ref` bigint。读 `UnifiedTicketQueryService.java` 56～250 行确认当前确切列名与顺序后再写；高频举报人阈值复用常量 `FREQUENT_REPORTER_THRESHOLD`。

### 🔴 权限只用 `place.manage`

PRD 评审第 35 条指出「同一个下架动作在场所页用 `place.manage`、在队列用 `content.takedown`」会两码管一事。本 story 场所举报页签查看与处置统一 `place.manage`；模板 `sec:authorize` 与 `@PreAuthorize` 一致。`place.manage` 不预授予任何预置角色（Story 1.4），需要处理场所举报的运营在角色配置页勾选。

### 🔴 标记人来源与 `marked_by_user_id`

`AdminPublishIdentityService.selectableIdentities()` 返回 `PublishIdentityOption(userId, nickname, …)`，包含启用中的虚拟账号与授权的真实账号。表单下拉直接用它；服务端复核所选 userId 仍在集合内。`marked_by_user_id` 是 `users.id`（5.1 已定），与种子帖作者同语义。
