# Story 1.8: 推荐 / 不推荐计数

Status: review

## Story

As a 在列表里挑地方的用户,
I want 不点进去就能看到大家推荐不推荐,
so that 我能快速筛掉评价差的，不用一个个点进去看。

## Acceptance Criteria

**AC1 — 计数载体（AD-9）** `[L1]`
**Redis 计数器 + DB 回算自愈**，形态沿用既有未读角标那一套（读不到 / 对不上就从库重算再写回）。
🔴 **真值永远在 `place_comments` 表里**；Redis 丢失只导致一次重算，**不丢数据**。

**AC2 — 架构边界** `[L0]`
**没有**对场所列表整页结果做缓存。AD-9 明确该做法不在授权范围内，仍受基线「禁通用缓存层」约束。

**AC3 — 两处展示** `[L2]`
**列表页与详情页都展示**推荐 / 不推荐两个计数。

**AC4 — 不参与排序** `[L0]`
这两个数**只展示、不参与排序**；**不做**列表降权、**不做**警示标（先积累数据）。

**AC5 — 三个触发点** `[L1]`
计数变更覆盖：① 评论创建（带态度）② **用户自删自己的评论** ③ 运营删除 / 下架。
⚠️ 第二个触发点是 2026-09-15 圆桌新增 —— 原先只考虑了运营删。

**AC6 — 批量读取** `[L1]`
列表页一次取回本页所有场所的计数，**禁逐个场所查 Redis**（否则把 N+1 从数据库搬到了 Redis）。

## Dev Notes

### 照抄这个现成实现

`petgo-backend/src/main/java/com/tailtopia/notify/service/NotificationCenterService.java`
- key 形如 `notify:unread:{userId}`
- 读：取不到 / 值异常 → `recompute` 从库算 → 写回
- 减：`decrement` 后若为负则置 0

场所计数照这个形状：`place:rec:{placeId}` / `place:notrec:{placeId}`（或一个 hash）。

### 🔴 这不是"缓存层解禁"

三条判据，写进代码注释：
1. Redis 是**既有**组件（本就在跑），不是新中间件
2. 用法是**单个整数计数器 + 可从库完整重算**的派生数据
3. **真值永远在表里**，Redis 丢了只是慢一次

任何"给场所列表整页结果做缓存"的做法**不在本条授权范围内**。

### AC6 是个容易漏的陷阱

列表页一页十几个场所，如果每个场所单独 `GET` 一次 Redis，就是把 N+1 从数据库搬到了 Redis——延迟照样叠加。用批量命令一次取回。

### Completion Notes List

**已交付（L0 全绿）**

1. **`PlaceAttitudeCounters`**（AC1 · AD-9）：key 形如 `place:rec:{placeId}` /
   `place:notrec:{placeId}`，形态沿用既有未读角标那一套 ——
   读 Redis → 读不到 / 值异常 → 回库重算 → 写回；减到负数置 0。
   **真值永远在 `place_comments` 表里**，Redis 整个丢掉只是慢一次。
2. **🔴 批量读**（AC6）：`MGET` 一次取回整页的 2N 个 key。
   逐个场所 `GET` 就是把 N+1 从数据库搬到了 Redis —— 延迟照样叠加，只是换了个地方发生。
   缺值的那些场所**一起**回算（一条 group-by，不是每个一条）。
   两个键**任意一个**缺就整对重算：只补一个会让 👍 是新的、👎 是旧的。
3. **🔴 计数只认 VISIBLE 的评论**（对 AC5 措辞的一处必要澄清）：
   AC5 把第一个触发点写成「评论创建（带态度）」，但**先发后审之下创建那一刻评论还是
   `UNDER_REVIEW`、对他人不可见**（Story 1.7）。创建即 +1 会让一条尚未过审、甚至最终被拒的
   评论立刻出现在所有人看到的公开计数里 —— 而列表页这两个数字正是"大家觉得这地方行不行"。
   所以自增落在**评论转可见**那一刻（`approve`），与 DB 回算口径
   （`deleted_at IS NULL AND moderation_status = VISIBLE AND attitude IS NOT NULL`）逐字一致。
   ⚠️ 两者必须一致：不一致的表现是「自愈一跑数字就变」，谁也说不清哪个对。
4. **触发点接齐**（AC5）：① 评论转可见 ② 用户自删 ③ 运营下架
   （`PlaceCommentService.takedown`，**admin 端点属 AB-17A，本 story 只把收口点放在 service** ——
   没有它，admin 那侧接上时最省事的做法就是直接改仓储，把计数绕过去）。
   **另加了第四条路径**：④ 作者注销（评论对他人不可见了，计数也要跟着减）。
   删一条**还没过审**的评论**不减** —— 它从来没被加进去过。
5. **两处展示**（AC3）：列表页与详情页的 UI 在 Story 1.1/1.5 就已按 B1-D11 画好（当时恒 0），
   本 story 接上真值。**不做「为 0 就隐藏」**：全 0 是新场所的正常状态，隐藏会让它的卡片
   比别人矮一截、看起来像加载失败。
6. **🔴 两条架构边界做成了机械检查**（AC2/AC4 —— 都属"越界了功能反而更好"那一类）：
   `PlaceCountingBoundaryTest` 扫源码断言：场所模块内**没有** `@Cacheable`/`Caffeine` 等
   Spring 缓存抽象（AD-9 授权的是计数器，不是给查询结果加一层）、计数器**只存整数**
   （不序列化任何响应对象）、**排序语句里不出现计数**、没有降权/警示标之类的判断。
   前端同样有一条 `place_attitude_display_test.dart`（客户端不重排列表、不加警示标）。
7. **口径差异是有意的，写在了两处注释里**：评论数是 **viewer 维度**（拉黑过滤让它因人而异，
   且必须与评论区列出来的条数一致），👍/👎 是**平台口径**（与谁在看无关）。不要"统一"它们。

**code-review 复审后修掉的（4 findings 全修 —— 全是"丢一次增量就永久偏差"那一类）**

1. 🔴 **写 Redis 失败后永不自愈**：`countsOf` 只在键缺失 / 非数字时回算，键存在就一直信任，
   而这些键既没有 TTL、也没有像未读角标那样"打开页面时按库校准"的天然时机 ——
   Redis 抖一下丢掉一次 `+1`，那个场所的 👍 就**永久少 1**。
   → **给每次写回加 TTL（10 分钟）**：键到期即消失、下次读自动回库重算。
   它同时兜住了下面第 3 条和任何本文件没想到的第四种情况 —— **偏差从"永久"变成"有界"**。
2. 🔴 **计数在事务提交前就改了**：三个触发点都在各自的 `@Transactional` 里直接 INCR。
   删除请求在 flush 时回滚（死锁 / 约束冲突 / 任何异常）→ 库里评论还在、计数已经减了；
   用户重试成功 → 同一条评论减了两次。
   → 改走 `TransactionSynchronization.afterCommit`（无活动事务时就地执行）。
   补了两例：有事务时提交后才写、回滚则一点没动。
3. 🔴 **回算写回是无条件覆盖**：两个线程同时发现键缺失、各自回算，其中一个读到的是更新的
   库状态 —— 慢的那个会把新值盖回旧值，一次审核通过就这么被吞掉。
   → 改用 `setIfAbsent`（先写的赢，后到的增量加在它上面；万一先写的是旧值，TTL 到期纠正）。
   顺带说明为什么逐键 set 而不是 `multiSet`：**TTL 必须跟值一起写**，
   分两步会出现"值在、TTL 没设上"的窗口，那个键从此永不过期、也就永不自愈。
4. **`parse` 把负值洗成 0**：键停在 `-1`（那次"减到负就置 0"的补偿写失败了）时，
   洗成 0 会让它被当成健康值 —— 之后每次 +1 都是 -1→0→1，计数永远比库里低且永不回算。
   → 负值也当缺失处理，走回算。

**范围边界（有意不做）**

- **不给列表整页结果做缓存**（AC2 · AD-9 §3 明确排除）——「禁通用缓存层」仍然有效；
- **不参与排序、不降权、不加警示标**（AC4 / PRD ③「先积累数据」）；
- **不做定时重算任务**：TTL 已经保证偏差有界，再加一个 `@Scheduled` 全表回算属于
  "为一个已经解决的问题加一个新的运维对象"；
- **admin 侧的下架端点**属 AB-17A（本 story 只提供 service 层的收口点）。
