# Story 1.6: 灯箱抽成公共组件并接入场所照片

Status: review

## Story

As a 想看清场所照片细节的用户,
I want 点开照片能全屏看、能放大、能左右翻,
so that 我能看清门口有没有台阶、座位区够不够大。

## Acceptance Criteria

**AC1 — 抽组件不改行为** `[L0]`
把内容详情页里那个私有灯箱（可左右翻页 + 双指缩放）抽成公共组件。
🔴 **内容详情页的行为一字不变**，既有测试全绿。

**AC2 — 场所照片接入** `[L2]`
场所详情页点某张照片 → 打开同一个公共灯箱，可左右翻页与缩放。

**AC3 — 与批次 A 的关系** `[L0]`
记录「批次 A 新版灯箱（FR-115）落地后整体替换」的后续动作。**本 story 不等批次 A**。

**code-review 复审后修掉的（5 findings 全修）**

1. 🔴 **`thumbWidth` 是死参数，注释在说一件没发生的事**：后端 `PlaceDetailResponse`
   已给每条 URL 拼好 `x-oss-process=image/resize,w_1080/format,jpg`，而客户端
   `AppImage.ossResized` 对**已带 `x-oss-process`** 的 URL 原样返回 ——
   横滑流仍在下 1080 px 图，"按 560 px 取缩略"从未生效。→ 删掉参数，注释改写成事实。
2. 🔴 **"`urls` 始终是原图"这句对场所照片不成立**：拿到的是服务端 1080 px +
   `format,jpg` 重编码版。→ 注释改为「当前能拿到的**最大安全尺寸**」，并写明
   **真·原图不对外发**的原因：那条路径没有 `format,jpg`，会把 GPS 带出去（E4）。
   要更清晰得改后端出口尺寸，不是前端加个参数。
3. 🔴 **灯箱没有 `errorBuilder` → 死链是一屏全黑** + 每页一条未捕获图片异常。
   本 story 恰好把横滑流的**破图占位也变成可点的**，点破图正好落进那一屏黑。
   → 加一个白色 `broken_image` 占位。**这是「只搬不改」的唯一一处例外，且只动失败路径**
   （成功路径的渲染一字未变）。
4. **越界下标只在入口函数里夹取**：`PhotoLightbox` 已是公共类，直接构造能绕过入口 ——
   2 张图 + `initialIndex: 5` 会得到空白视口 + 标题「6/2」。→ 夹取下沉进 state，补一例。
5. **测试里 `while (takeException() != null) {}` 把所有异常一并吞掉**：这组"守搬家没弄丢
   东西"的用例会在真实布局/断言异常下照样绿。→ 加了 errorBuilder 后不再需要 drain，
   整段删除；反过来用测试环境必然的图片加载失败去验证"死链有可见占位"。

**范围边界（有意不做）**

- **不重做灯箱**：视觉 / 交互一律不改（改了会让内容详情页既有验收失效，且与批次 A 的
  FR-115 撞车）；
- **不合并两套全屏看图组件**（见上文 5）；
- **不改后端出口尺寸**：灯箱清晰度受 1080 px 限制是**服务端口径**，要改属另一条决策
  （且必须保住 `format,jpg` 的 EXIF 兜底）。
