# Story 1.2: 按距离排序与定位权限

Status: review

## Story

As a 在外面想就近找地方的用户,
I want 场所列表默认按离我的远近排,
so that 我一眼就能看到最近的那几个，而不用自己一个个看地址猜。

## Acceptance Criteria

**AC1 — 距离排序** `[L1]`
已授权定位时，请求携带当前经纬度，列表按直线距离升序，每项显示距离。

**AC2 — 服务端排序口径（AD-2）** `[L1]`
**经纬度矩形范围粗筛 + 直线距离计算**；纬度、经度**各有索引**且粗筛能吃到索引（贴执行计划确认）。

**AC3 — 禁止项** `[L0]`
代码与迁移里**没有** `CREATE EXTENSION`（禁 PostGIS / cube / earthdistance），**没有**任何三方 LBS 调用。

**AC4 — 两条独立分支** `[L0]`
「按距离」与「按最新」是**两条独立查询分支**；**不得**写成"距离为 null 排最后"混在一条 SQL 里。

**AC5 — 无权限态** `[L2]`
未授权定位 → 列表按最新排序，顶部提示条 +「开启定位」按钮（UX-DR2）。点按钮触发系统权限申请；用户拒绝后**不反复弹**，提示条保留。

**AC6 — 权限声明** `[L0]`
安卓清单与 iOS Info.plist 均已声明定位权限；iOS 用途文案为**印尼语**，说清「按距离排序附近的宠物友好场所」。

## Dev Notes

### 🔴 定位库是个决策点，不是随手选

项目现在**没有任何定位库**。两条路：

1. **地图 SDK 自带的定位能力**（Story 1.4 会引入地图 SDK）—— 少一个依赖，但会让本 story 依赖 1.4，**违反顺序**（本 story 在前）
2. **独立定位库**（如 geolocator）—— 本 story 自足，代价是多一个依赖

**建议选 2**，并在 Completion Notes 写明选型与版本。⚠️ 选 1 会造成前向依赖，等于本 story 做不完。

### 权限请求照既有范式

`petgo_app/lib/shared/utils/media_permission.dart` 是本项目请求系统权限的既有写法（按平台与 SDK 版本分流、处理"永久拒绝"）。定位权限照这个形状写，**不要另起一套**。

### 🛡 两条分支为什么不能合并

写成一条 SQL 用「距离为 null 排最后」看似省事，实际是：无坐标时那条 SQL 仍会带着距离计算列跑全表，且排序语义混在一起，后面没人敢改。AD-2 明确要求分开。

### 埋点与日志红线

🔴 **经纬度禁止进日志、禁止进埋点属性**（NFR-4 / NFR-5）。埋点层有兜底黑名单会整条丢弃，但不要依赖兜底——源头就不要传。

### Completion Notes List

**已交付（L0 全绿）**

1. **迁移 `V20260915_0458__add_places_geo_index.sql`**（AC2/AC3）：纬度、经度**各一条部分索引**
   （`WHERE status='ACTIVE'`）。
   - 🔴 **两条单列索引而不是一条复合索引**：粗筛的两个条件都是范围条件，复合索引只有第一列
     能做有效范围扫描；两条单列索引让 PostgreSQL 走 **BitmapAnd** 把两个范围都吃掉。
   - **零 `CREATE EXTENSION`**（AC3）：禁 PostGIS / cube / earthdistance，全库仍然零扩展。
2. **两条独立查询分支**（AC4）：`PlaceQueryService.listRecent()` 与 `listByDistance()`；
   仓储侧 `findByStatusOrderByCreatedAtDescIdDesc` 与 `findActiveWithinBox` 也各是一条。
   `PlaceQueryServiceTest` 用 mock 仓储把这条架构约束变成**可证伪**的：按最新那次调用
   `verify(never())` 粗筛查询，反之亦然 —— 合并成一条 SQL 的写法会直接让测试红。
3. **距离在应用层算，不在 SQL 里算**（AC2）：`GeoBox.distanceMeters`（haversine，纯计算）。
   🔴 在 SQL 里对经纬度列套三角函数会让上面那两条索引**全部失效**、退化成全表扫描 ——
   「范围条件交给索引、距离在应用层算」正是 AD-2 Rule 2/3 的分工。
4. **粗筛半径 50 km**（`SEARCH_RADIUS_METERS`）：依据是冷启动数据为雅加达核心区（PRD ⑤），
   大雅加达东西向约 40 km。半径外**不出现**而不是排在后面（AD-2 原文）；
   但**粗筛为空时整条回落按最新**并如实下发 `sortMode=recent` ——
   否则外地用户打开就是一个空列表（技术上"正确"，用户看到的是「这功能什么都没有」）。
5. **`lat`/`lng` 可选参数 + 422 校验**：只给一个 / 超出合法区间 → `AppException.validation`。
   静默忽略会让客户端拿到按最新的列表却以为按距离排过（同 `ShopProductController` 对非法品类的处理）。
6. **App 端定位**（AC1/AC5/AC6）：
   - **选 `geolocator`（独立定位库）而不是地图 SDK 自带的定位** —— 后者会让本 story 前向依赖
     Story 1.4（顺序反了）。版本钉 `>=14.0.0 <14.0.3`：14.0.3 起 `geolocator_linux` 要求
     `package_info_plus ^10`，而本项目钉 `^8.1.0`，为一个**根本不构建的 Linux 桌面**传递依赖
     去升大版本不值。
   - **权限仍走既有 `permission_handler`**（`Permission.locationWhenInUse`），不用 geolocator
     自带的权限方法 —— 全 App 只保留一条权限申请路径（同 `media_permission.dart` 的形状：
     抽象 gateway + 真实实现，L0 可注入 fake）。
   - 🔴 **「拒绝后不反复弹」靠结构保证**：控制器 `build()` 只调 `status()`（不弹窗），
     系统弹窗只可能来自用户点「开启定位」。**不需要 shared_preferences 记「问过了」**，
     也就不存在那个标记被清掉之后又开始骚扰的情况。`place_location_controller_test.dart`
     直接数 `request()` 被调了几次。
   - 永久拒绝 → 按钮改为跳系统设置；**提示条保留**（它同时是「为什么这个列表不是按距离排的」的解释）。
   - 距离文案 `place_distance_format.dart`：<1 km 用整米、≥1 km 用一位小数公里，
     🔴 **小数点分隔符按 locale**（印尼语是逗号）—— 写死 `.` 会让印尼用户把 `1.2 km` 读成 12 公里。
7. **两端权限声明**（AC6）：Android 清单加 `ACCESS_COARSE_LOCATION` + `ACCESS_FINE_LOCATION`
   （Android 12+ 的弹窗让用户选「精确/大致」，只声明 FINE 时选大致会拿不到坐标）+ 两个
   `uses-feature required=false`；**刻意不声明 `ACCESS_BACKGROUND_LOCATION`**（要单独过
   Play 敏感权限审核，而我们没有那个需求）。iOS 加 `NSLocationWhenInUseUsageDescription`，
   **文案按 AC6 用印尼语**、说清用途是按距离排序附近的宠物友好场所；**没有 Always**。

**code-review 复审后修掉的（8 findings → 7 修 1 转 L2 观察）**

1. 🔴 **最严重的一条：坐标进了落盘日志**。`ApiAccessLoggingFilter` 对所有 `/api/**` 原样打印
   query string，而 `LogSanitizer` 只脱敏 JSON body、管不到 URL —— prod 是 INFO 且留 14 天，
   等于把每个用户每次打开场所列表时的精确位置写进日志文件，**直接违反 NFR-4**
   （而我原先在 controller javadoc 里声称已保证）。
   → 新增 `ApiAccessLoggingFilter.redactQuery`：按键打码 `lat/lng/latitude/longitude`，
   其余参数原样保留（排查要看筛选参数）；`ApiAccessLogQueryRedactionTest` 8 例守着。
   App 侧 `api_log_interceptor.dart` 同样加了 `_redactQueryKeys`（debug 控制台也会被录屏/贴工单）。
2. **截断发生在按距离排序之前**：粗筛原按 `id desc` + `Limit(200)`，框内超过 200 个时留下的是
   「最新 200 个」而不是「最近 200 个」，最近那家店会整条消失而 `sortMode` 仍说自己是 distance。
   → 粗筛 SQL 改为按**曼哈顿代理距离** `abs(lat-x)+abs(lng-y)` 排序（不需三角函数、
   只用来挑候选），精确顺序仍由应用层 haversine 决定。
3. **矩形角比半径远**（50 km 的框角上 70.7 km），且 `GeoBox.around` 在贴极点 / 跨对日线时把经度
   放宽成全范围 → 公开端点传个极点坐标就能把整条纬度带当「按距离」拿走。
   → 应用层**按半径复筛一次**；全落在半径外时与「框里一个都没有」同处理（回落按最新）。
4. **下拉刷新 await 的是旧族键**：`invalidate` 定位后新定点落到另一个族键，刷新动画绑在过期请求上，
   而正在显示的族键还是 loading → 整屏列表被换成转圈。
   → `_refresh()` 改为**先拿到定位结果、算出新族键、再刷它**。
5. **族键用原始坐标 → GPS 米级抖动就换键**（换键 = 无缓存 = 打回 loading）。
   → 新增 `placeListQueryFor()`：坐标按 3 位小数（~110 m）归一后才做族键；
   `place_list_query_test.dart` 守着「米级抖动同键、百米级移动换键」。
6. **`AsyncNotifierProvider` 默认 `isAutoDispose: false`** → 定位态整个 App 生命周期只 build 一次：
   用户移动后重进仍按旧位置算距离，去设置开了权限回来提示条还挂着。
   → 显式 `isAutoDispose: true`。
7. **`getLastKnownPosition()` 无条件优先**：系统缓存定点可能是几小时/几天前（甚至另一个城市）的，
   会把雅加达的店在泗水显示成「1,2 km」。
   → 加 `_maxCacheAge = 10min` 时间戳门槛（负年龄也当不新鲜 —— 时钟基准对不上时无法判断多老）。
8. （转 L2 观察）**首帧阻塞在定位链路上**：已授权、室内且无新鲜缓存定点时要等满 `timeLimit` 才放弃。
   → 超时从 8 s 收到 **5 s**，并在代码里写明这是「用户能忍的空屏上限」而非定位成功率最优值。
   真机上是否还嫌久，列入下方 L2 清单第 6 条。

**范围边界（有意不做）**

- **类型 / 标签筛选 chips** 不在 1.1/1.2 任何 AC 里；
- 商店合规（Play 数据安全表单 / App Store 隐私标签）归**发版检查单 RC-1**，不在本 story（epics 文件已摘出）；
