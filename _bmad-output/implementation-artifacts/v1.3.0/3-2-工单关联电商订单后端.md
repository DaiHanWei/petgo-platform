# Story 3-2: 工单关联电商订单（后端）（AD-S7）

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端 → 前端 → 联调、AC 标 L0/L1/L2、Flyway 时间戳版本号、`mvn -B clean package`）。
> 本 story **纯后端**。App 侧的「选订单」入口是 Story 3-3。
> 🔴 本 story 触碰**退款审批链路的上游**（`AdminTicketRefundService`），那是 V1.1 标注的「最高危 A-1」区域。改动原则：**给电商单开一条不碰退款的旁路，不改问诊单既有任何一行语义**。

## Story

As a 客服，
I want 打开工单就知道用户说的是哪一笔电商订单，
so that 我不用在工单里来回问「你哪一单」，也不会把电商订单当成问诊单误入退款流程。

## Dev Notes

### 🔴 为什么坚决不加跨表外键

三条，缺一不可：

1. **一列指两表，FK 在关系模型里无法表达**。`related_order_id` 的含义依赖 `related_order_type`，Postgres 的 `REFERENCES` 没有「条件外键」。硬加就只能二选一，另一类订单立刻插不进去。
2. **两类订单 id 都是自增 bigint、数值空间完全重叠**。`consult_orders.id`（`V66:28`）与 `shop_orders.id`（`V20260817_2308:16`）都是 `GENERATED BY DEFAULT AS IDENTITY`，各自从 1 开始。就算只给 `consult_orders` 加 FK，一个电商单 id 也**很可能刚好通过校验**（因为那个号在问诊表里确实存在）—— FK 在这里给的是**假安全**：它挡不住串单，只会让人以为串不了。
3. **加 FK 会把注销级联与删单顺序绑死**。`feedback_tickets` 已经被 `refund_requests.related_ticket_id` 反向引用（`V71:15`）；再往前挂两条出边，注销 / 测试 `deleteAll` 的顺序约束会变复杂（memory 记过一次：新表 FK → `consult_orders` 阻断 consult 测试 `deleteAll`）。

正解就是 AD-S7 写的：**类型列 + 服务层解析**。安全性由「解析时带归属校验 + 展示与退款按类型分流」保证，不由数据库保证。代价是需要靠测试守住（AC5 的变异验证就是为此）。

### 🔴 这条 story 真正的危险不在「加一列」，在 `ensureRefundRequest`

`ensureRefundRequest` `:90-103` 的这一行是整条链路的雷管：

```java
orders.findById(t.getRelatedOrderId()).map(ConsultOrder::getOrderToken)
```

`orders` 是 `ConsultOrderRepository`。工单挂的是电商单 42，这里会捞出 `consult_orders(42)` —— 一条别人的问诊单 —— 然后 `refundService.createRefundRequest(那条问诊单的 token, ...)`。**一次点击就能给无关订单开退款**。

所以本 story 的守卫有三层，写码时一层都不能省：

1. `linkShopOrder` 函数体里不出现任何 refund 依赖（编译期就断开）；
2. `ensureRefundRequest` 入口按 `relatedOrderType` 早退（运行期兜底）；
3. 模板不渲染退款块（界面上根本点不到）。

第 2 层是唯一真正的护栏，1 和 3 是让人不容易走到那里。AC5 的变异测试盯的就是第 2 层。

### 🔴 「APPROVED 改挂守卫」也要改，别只顾着新增

`:54-61` 那段 PR#34 finding #5 的守卫，今天无条件拿 `t.getRelatedOrderId()` 去 `refunds.findByOrderId(...)`。工单当前挂的是电商单时，这个查询会命中一条**同号问诊单的退款请求**，于是出现「挂着电商单的工单，因为某个不相干问诊单有 APPROVED 退款，而被禁止改挂」。症状很怪、很难查。加类型条件是必须的，不是优化。

### 关于 `related_order_type` 的 NOT NULL DEFAULT 'CONSULT'

存量 8 成以上的行 `related_order_id` 是 NULL（用户路径恒 NULL、后台补挂是少数），它们会被回填成 `'CONSULT'`。这是**有意的**：

- 列语义是「`related_order_id` 归哪张表」，id 为 NULL 时这个问题无意义，取什么值都行；
- `NOT NULL` 让实体不用处理 `null` 类型，代码路径少一个分支；
- 真要做成「id 为空则 type 也为空」需要一条 `CHECK ((related_order_id IS NULL) = (related_order_type IS NULL))`，收益是零、风险是存量数据不满足约束导致迁移失败。

在列注释里把这句话写下来，比在 code review 里解释三次划算。

### 解析顺序为什么是「先问诊后电商」

AD-S7 明写。理由：问诊单是既有语义，先查它保证**任何现有 token 的解释结果一个字都不变**（回归风险归零）；电商单只在问诊查不到时才试。两个 token 都是 32 位随机串（`ShopTokenGenerator` SecureRandom + Base62 × 22），跨表重复的概率可以忽略，但顺序固定能让行为可预测、可测试。

### 与 Story 4-3（订单号不可推算）的接口

4-3 会给 `shop_orders` 加 `display_no` 列并回填。本 story 先用计算式 `OrderDisplayNo.of(OrderDisplayNo.ECOMMERCE, id, createdAt)`（`order/dto/OrderDisplayNo.java:34`，格式 `TOKO-yyyyMMdd-%06d`，WIB 日期）。**两处都只是展示**，切换时改一行取值 + 一条测试断言，不涉及数据迁移。sprint-status 的 Epic 顺序说明里已登记这条依赖（「3-2 的电商订单展示在 4-3 完成后切换为新订单号」）。
