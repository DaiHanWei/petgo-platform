# Story 9-3: 订单导出

Status: ready-for-dev

> 自包含 story，**纯后台**（`admin/shop/` + `templates/admin/shop-orders.html` + i18n + 一支预置角色授予迁移），无 App 端改动、无对外契约变更。
> 与用户沟通用中文。执行纪律见根 `CLAUDE.md`（`mvn -B clean package` 一律带 `clean`；Flyway 时间戳版本号）。
>
> 🔴 **前置：admin 主题 Epic 10 完成。** 导出入口挂在 Epic 10 的 **B15「Toko 订单履约」**页上（`/admin/shop/orders`）。
> 🔴 **强烈建议排在 Story 9-2 之后**：导出「按当前筛选条件」，而筛选条件正是 9-2 扩出来的。9-2 未落地时导出只能覆盖现有 4 个维度，之后要回头改一遍。
> 🔒 **本 story 是本主题里 PII 暴露面最大的一条** —— 一次点击就能把全站订单连同用户可填字段落到一个可离线传播的文件里。三道闸（权限码 / 审计 / 公式转义）与 OD-10 的字段边界缺一不可。

## Story

As a 运营，
I want 把当前筛选出来的订单导出成 Excel，
so that 我能拿去做线下核对，而不用在页面上一行行抄。

## Acceptance Criteria

**AC1 · 按当前筛选条件导出，上限 10,000 行** `[L0/L1]`
**Then** 导出使用**与列表完全相同的查询条件**（Story 9-2 扩展后的全部维度 + `status` + 日期区间），不是「导出全部」`[L0]`
**And** 上限 **10,000 行**（SHOP-NFR-03）；超出时**只导前 10,000 行并在页面显式提示已截断**，🔴 不得静默截断 `[L0]`
**And** 截断判定沿用「多取一行」范式（`AdminPaymentExportService.java:62-66`），不额外发一次 count `[L0]`
**And** 导出行数与同条件下列表的结果集一致（在列表未被 `PAGE_SIZE` 截断的条件下）`[L1]`

**AC2 · 🔒 新权限码 `shop.order_export`，不默认授予运营专员** `[L0]`
**Then** 新增 `AdminPermissions.SHOP_ORDER_EXPORT = "shop.order_export"`，javadoc 写明「含 PII，单独成码」的理由（照 `SHOP_ORDER_PHONE_SEARCH` 的 `:267-273`）`[L0]`
**And** 🔴 **加码改满 5 处**（逐项见 T3），其中 `GROUPS` 加进 **view 组**（与既有四个导出码一致），🔴 只加一组 `[L0]`
**And** 🔴 **不默认授予运营专员（`OPERATIONS`）**；按 AD-S13 建议授予**客服 + 财务**（`SUPPORT` / `FINANCE`）`[L0]`
**And** 无该权限：页面不渲染导出按钮；直接构造请求 → **403 + 可读提示**（不是白屏 / JSON / 500）`[L1]`
**And** 权限判定**同时**做渲染门控与服务端再判两层（照 `AdminShopOrderController.java:96` + `:105-107` 的电话搜索范式）`[L0]`

**AC3 · 每次导出写审计（谁 / 何时 / 什么条件 / 多少行）** `[L0/L1]`
**Then** 每次导出写一条 `AdminAuditService.record`，detail 至少含：**筛选条件的可读摘要**、**导出行数**、**是否被截断** `[L0]`
**And** 「谁」= `actorAccountId`（方法首参，照 `exportXlsx(long actorAccountId, …)` `:60`）；「何时」由审计表自身的时间列承担 `[L0]`
**And** 🔴 审计码是 `AuditActions` 里的**新常量**（如 `SHOP_ORDER_EXPORTED`），**不是**字符串字面量 —— 不复制 `AdminPaymentExportService.java:96` 的写法 `[L0]`
**And** 🔒 **审计 detail 不得含任何 PII**：条件摘要里如果带了 9-2 的邮箱 / 昵称搜索词，**邮箱一律只写指纹**（复用 `AdminShopOrderService.fingerprint(...)` `:156-168`），昵称可写但**须与 SHOP-NFR-01「审计只记指纹」的口径对齐后再定** —— 🔴 **实施时确认**，拿不准就只记「用了哪几个维度」而不记词本身 `[L0]`
**And** 导出方法**不能标 `@Transactional(readOnly = true)`**（审计是 INSERT，照 `AdminPaymentExportService.java:57-59` 的注释）`[L0]`
**And** 导出 0 行时**同样写审计** —— 「导了个空」也是一次对导出能力的使用 `[L1]`

**AC4 · 🔒 单元格公式转义** `[L0]`
**Given** 全仓目前没有任何公式转义实现
**Then** 新建一个可单测的转义工具：字符串单元格的值若以 `=` / `+` / `-` / `@` **开头**，在前面加一个 `'` `[L0]`
**And** 转义**只施加于文本单元格**，数字/时间单元格照旧写原生类型（照 `:83` 的「金额写数字，运营可直接求和」）—— 🔴 别把金额也转成带 `'` 的文本，那会毁掉整列的可求和性 `[L0]`
**And** 覆盖**所有用户可填字段**：昵称、（OD-10 允许时的）收件人姓名、任何来自用户输入的备注类字段。🔴 判据是「这个值是不是用户打进去的」，不是「它现在看起来像不像公式」`[L0]`
**And** 单测覆盖四个前导字符各一条 + 一条正常值不被改动 + 一条 `-` 开头的**负数字符串**（确认它作为文本被转义、而作为金额仍走数字单元格）`[L0]`
**And** 🔴 **变异验证**：把转义函数改成原样返回 → 相关单测必须变红。执行记录写进 Completion Notes `[L0]`

**AC5 · 🔒 导出字段范围按 OD-10；定论前不导电话与详细地址** `[L0]`
**Then** 字段清单以 `HEADERS` 式的**单一常量**定义（照 `AdminPaymentExportService.java:42`），并在常量旁的注释里写明「本清单由 OD-10 拍板，改动须回到 OD-10」`[L0]`
**And** 🔒 **OD-10 未定论时，导出列中不含收件人电话与详细地址** —— 最细地理粒度维持 `kecamatan`（与列表口径一致，见 `AdminShopOrderRow.java:19-20`）`[L0]`
**And** 🔴 「先导出来放着、等 OD-10 定了再删列」是**不可接受**的做法：文件一旦生成就落到运营电脑上，删列追不回来 `[L0]`
**And** OD-10 已定论时，按定论的清单实现，并在 Completion Notes 记录定论内容与日期 `[L0]`

**AC6 · 端点与下载形态** `[L0]`
**Then** 新增 `GET /admin/shop/orders/export.xlsx`（命名照 `/admin/payments/export.xlsx` `AdminPaymentController.java:87`），返回 `ResponseEntity<byte[]>` + `Content-Disposition: attachment; filename=…` + xlsx MIME（照 `:104-107`）`[L0]`
**And** 🔴 这是 **AB-19A 的正式新例外**（AD-S13 原文把「两个导出」登记为例外，理由是新能力、无既有端点可复用）；🔴 **须在 admin 主题的例外清单里登记**，登记动作写进 Completion Notes `[L0]`
**And** 导出用 **`XSSFWorkbook`**（与既有两处一致），不引入新的 POI 依赖或新库 `[L0]`
**And** 生成失败时返回可读错误（照 `admin.err.users.exportFailed` `AdminUserService.java:253` 的形状），**不外泄堆栈** `[L0]`

**AC7 · 集成测试** `[L1]`
**Then** 导出行数与同条件列表一致 `[L1]`
**And** 🔒 含 `=` 开头昵称的订单：导出文件中该单元格值以 `'` 开头（用 POI 读回断言，不是只断言 service 返回的中间对象）`[L1]`
**And** 无权限账号请求导出端点 → 403；有权限 → 200 + xlsx MIME `[L1]`
**And** 每次导出（含 0 行）审计表新增一行，且 detail 不含 `@` `[L1]`
**And** 超 10,000 行时只导 10,000 行且页面有截断提示 `[L1]`
**And** OD-10 未定论时：导出文件的表头中**不含**电话与详细地址列（按表头断言，最直接）`[L1]`

## Dev Notes

### 公式转义到底在防什么

Excel / WPS 打开 CSV 或 XLSX 时，以 `=` `+` `-` `@` 开头的单元格会被当成公式求值。攻击者把昵称改成 `=cmd|'/c calc'!A0` 之类的串，运营一打开导出文件就在自己机器上触发外部调用 —— 这是 CSV/Formula Injection，属于「数据从不可信来源流到可执行上下文」的经典形态。前缀一个 `'` 让 Excel 把它当纯文本。

🔴 **判据是来源不是长相**。有人会想「只转义看起来像公式的」，那就漏了 `-` 开头的普通负数文本、`@` 开头的用户名等等。规则很简单：**用户能填的文本字段，一律过转义函数**。

### 为什么不导电话与详细地址（在 OD-10 定论之前）

订单列表刻意零 PII 是有留痕的设计（`AdminShopOrderRow.java:10,:19`：「列表只给到 Kecamatan（区级），够运营判断配送范围，又不足以定位到人」/「一个区里有几万人」）。导出把这个边界一次性抹平：一个 xlsx 文件里几千条姓名+电话+详细地址，可以邮件转发、可以拷贝到私人电脑、审计追不到第二手传播。所以字段范围必须由**产品 + 法务**拍板（OD-10），技术侧在定论前取最保守解。

### 为什么审计要记「条件」和「行数」

「谁导出过」不足以还原风险面。同一个人，导出「今天 3 单」和导出「全量 9,998 单」是两件事。审计的价值在于事后能回答「那次泄漏可能涉及哪些数据」，所以**条件 + 行数 + 是否截断**三项都要有。而条件里如果含邮箱这类 PII，只写指纹 —— 否则审计表自己变成了第二份 PII 存储（`AuditActions.java:178-182` 已经为电话搜索写过同一段理由：审计表永久保留、无 TTL）。

### `XSSFWorkbook` 在 10,000 行上够不够用

`XSSFWorkbook` 是全内存模型，10,000 行 × 十几列在后台单次导出的场景下没问题（既有两处导出都用它）。🔴 **不要**为了「更稳」擅自换 `SXSSFWorkbook` —— 它需要额外的临时文件清理，且与既有两处的写法分叉，属于本 story 范围外的技术选型变更。如果实测内存有压力，先把结论记进 Completion Notes 再谈。
