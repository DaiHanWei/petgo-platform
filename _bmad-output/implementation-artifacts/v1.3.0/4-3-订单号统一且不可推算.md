# Story 4-3: 订单号统一且不可推算

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端→前端→联调、AC 标 L0/L1/L2、Flyway 时间戳版本号、`mvn -B clean package`）。
> 本 story **后端 + App 两侧都改**，含一支带存量回填的迁移。

## Story

As a 平台，
I want 对外的电商订单号猜不出来，且一张单只有一个号，
so that 外人无法推算订单量或试探他人订单，用户与客服也不再对不上号。

### ⚠️ 核实中发现的、与规划文档不符之处

```sql
FROM shop_orders o
WHERE o.created_at >= ? AND o.created_at < ?
  AND o.status NOT IN ('PENDING_PAYMENT', 'CANCELLED')
```

—— **按表圈定实物收入，不解析任何前缀**。控制器 `admin/shop/web/AdminShopFinanceController.java:70-84`，模板 `templates/admin/shop-reconciliation.html` 里 `TOKO` / `displayNo` / `orderToken` 零命中。

👉 **结论不变、理由更新**：前缀照旧保留 —— 它服务的是**财务人眼识别**与既有测试断言，而不是一条会崩的代码路径。这条事实要写进实现者的认知，免得有人以为「反正没代码依赖」就顺手改了。

## Acceptance Criteria

**AC1 · `display_no` 落库，格式与随机性合规** `[L0/L1]`
**Given** `shop_orders` 没有展示号列
**When** 执行迁移 `V<yyyyMMdd_HHmm>__add_shop_orders_display_no.sql`
**Then** 新增 `display_no VARCHAR(32)`，回填后置为 `NOT NULL` 且有唯一约束 `[L1]`

### 迁移第 ③ 步的参考实现

```sql
-- ⚠️ 本支是本仓第一个 DO $$ 块。存量电商订单量极小，逐行循环成本可忽略。
-- ⚠️ random() 不是密码学随机 —— 见文件头注释里的取舍说明。
DO $$
DECLARE
    r         RECORD;
    candidate TEXT;
    tries     INT;
BEGIN
    FOR r IN SELECT id, created_at FROM shop_orders WHERE display_no IS NULL ORDER BY id LOOP
        tries := 0;
        LOOP
            candidate := 'TOKO-'
                || to_char(r.created_at AT TIME ZONE 'Asia/Jakarta', 'YYYYMMDD') || '-'
                || (SELECT string_agg(
                        substr('0123456789ABCDEFGHJKMNPQRSTVWXYZ',
                               1 + floor(random() * 32)::int, 1), '')
                    FROM generate_series(1, 6));
            EXIT WHEN NOT EXISTS (SELECT 1 FROM shop_orders WHERE display_no = candidate);
            tries := tries + 1;
            IF tries > 5 THEN
                RAISE EXCEPTION '回填 display_no 连续 5 次冲突，order id=%', r.id;
            END IF;
        END LOOP;
        UPDATE shop_orders SET display_no = candidate WHERE id = r.id;
    END LOOP;
END $$;
```

Crockford Base32 字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` 共 32 字符，**刻意不含 `I` `L` `O` `U`**（`I`/`1`、`O`/`0` 易混，`U` 避免拼出脏词）。6 位 ≈ 10.7 亿种组合，且唯一性只需在**同一天**内成立。

### 🎯 两次变异验证 —— 第一次「没变红」，这是本次最重要的一条

**变异 ①：把生成器的 `SecureRandom` 换成递增计数器（退回旧算法）**

- **第一次跑：12 条全绿，一条都没红。** 原因是我最初那两条靶子选错了：
  - 「1 万次全不同」—— 递增计数器**同样次次不同**；
  - 「字符都在 Crockford 字母表内」—— `%06d` 出来的数字**本来就都在字母表里**（0–9 在其中）。
  - 🔴 **被旧算法破坏的性质是「不可预测」，不是「唯一」**，而我原来的断言只测了后者。
    这是一条典型的假绿护栏：测试是绿的，但它保护的不是需要被保护的东西。

  - `everyPositionSpansTheAlphabet` —— 报「🎯 第 0 位只取到 `[0]` —— 递增序号的高位恒为 '0'，这正是可枚举的样子」

### 🔍 实现中的判断（各一行）

1. **`place()` 的 `now` 只取一次**：展示号的日期段与 `created_at` 共用同一个 `Instant`。
   各取各的 `Instant.now()`，在 WIB 跨午夜的那一瞬就会产出「号上写着昨天、建单时间是今天」的单 ——
   客服对账时无解，且一天只可能出现几笔、谁也复现不了。
2. **重试走「先查后插」**：唯一约束冲突会把当前事务打成 aborted，同一事务内重试每次都撞在
   「事务已中止」而不是撞在号上。索引是兜底报错，不是重试机制。
3. **大写归一只作用于展示号**：`public_token` 是 Base62、**大小写敏感**，对它归一会把它搜坏。
4. **`displayNo` 插在 `orderToken` 之后**（story 明确要求），但这**违反了我在 1-1 写下的
   「新字段一律末尾追加」惯例**。破例的前提是全仓只有两个按位置构造的调用点且都在本次一起改了；
   🔴 但「两个相邻的 String」正是编译器抓不住的错位 —— 所以另加了
   `displayNoAndOrderTokenAreNotSwapped` 专钉这一处（串掉的后果：用户看到 22 位 token，
   而 App 拿 `TOKO-…` 当路由键请求详情直接 404）。
5. **后台搜索标签另起 key**：`admin.shop.orders.col.token` 被 5 处模板共用（含 3 个列头），
   直接改会把列头一起改掉。新增 `admin.shop.orders.search.orderNo`，四个 bundle 都补齐。
6. **App 缺省空串而不是 null**：灰度期老后端不下发 `displayNo` 时回落显示 `orderToken` ——
   显示一个旧格式的号，好过在订单号那一行显示一片空白。
7. **AC7 说「新建契约测试」，实际是扩充**：`ShopOrderDetailViewContractTest` 在 Story 1-1 就建好了
   （commit `1f31114`）。以代码为准。
