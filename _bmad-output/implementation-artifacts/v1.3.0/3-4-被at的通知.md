# Story 3.4: 被 @ 的通知

Status: review

## Story

As a 被别人在评论里 @ 了的用户,
I want 收到通知并能点进去看,
so that 我不会错过有人在叫我。

## Acceptance Criteria

**AC1 — 🔴 通知类型的 CHECK 约束（验收条件，不是提醒）** `[L0]`
新增「有人提到了你」通知类型时：
- 必须 **DROP + ADD 重列 CHECK 约束全集**
- 取值以**代码里的类型枚举为唯一权威**，**逐个照抄源码**
- 必须**复查并行分支**（电商线 / admin 线）同期是否加了新类型，一并纳入清单

⚠️ **此处已出过四次事故**，每次都是照着一份过期清单抄，结果那几类通知一写库就 23514、服务起不来。

**AC2 — 通知与推送** `[L1]`
有人 @ 了某用户且内容/评论发布成功 → 被 @ 者收到**通知中心条目 + 系统推送**。

**AC3 — 文案架构** `[L0] [L2]`
**系统推送**由后端下发**印尼语**；**通知中心条目**由 App 按设备语言渲染（en / id 双表），后端只传类型与 targetRef。
**中文一个字都不进界面**（仅内部对照）。
文案区分「帖子提及」与「评论提及」两种。

**AC4 — 深链** `[L2]`
帖子提及 → 内容详情页；评论提及 → 内容详情页**并锚定评论区**（复用既有 `?focus=comments` 机制）。

**AC5 — 拉黑不发** `[L1]`
存在任一方向拉黑关系 → **不发通知**。

**AC6 — 样式复用** `[L2]`
复用既有通知中心样式（按日分组 / 图标块 / 未读左紫条 + 浅紫底），紫色图标块与兽医回复同色系。

## Dev Notes

### 🔴 AC1 的具体做法（照这个顺序，别跳）

1. 打开 `petgo-backend/src/main/java/com/tailtopia/notify/domain/NotificationType.java`（或同名枚举），**逐个抄下当前全部取值**
2. `git log origin/main..` 与并行分支比对，看有没有别人同期加的类型
3. 写迁移：`ALTER TABLE notifications DROP CONSTRAINT IF EXISTS ck_notifications_type;` 然后 `ADD CONSTRAINT ... CHECK (type IN (全集 + 新值))`
4. **不要**在旧清单上打补丁、**不要**照抄上一份迁移里的列表

最近一次重建见 `V20260902_1620__rebuild_ck_notifications_type_full.sql`（当时 30 个值），那份文件的头注把四次事故的来龙去脉写清楚了，动手前读一遍。

### 通知架构（已核实与 PRD 一致）

客户端按 `type` 用 l10n key 渲染条目（见 `petgo_app/lib/features/notify/presentation/notification_center_page.dart` 的 `_typeLabel` switch），**不渲染后端下发的 title/body 串**。新类型在那个 switch 里加一支即可。

深链机制见 `petgo_app/lib/features/notify/domain/notification_deep_link.dart`；`?focus=comments` 是既有参数名，两侧必须同名。

### ⚠️ 顺带留意

Bug 20260911-494 修复后，未读角标会在**回到前台**与**Feed 下拉刷新**时重新拉取。新通知类型会自动受益，无需额外处理。

#### 🔴 AC1：CHECK 约束重列（这是验收条件，按 story 的三步逐步做完了）

迁移 `V20260915_1614__rebuild_ck_notifications_type_with_mention.sql`（第五次重建）。

1. **逐个照抄 `NotificationType.java`**（唯一权威）：写这份迁移时枚举 31 个值 ——

2. **复查并行分支**：`git fetch origin` 之后远端只有 `origin/main` 与本工作分支两条；
   main 的 `NotificationType.java` 与本树**逐字节相同**，main 的迁移集合是本树的真子集
   （只少本批次新增的 7 个文件）—— 没有别人同期加的类型要纳入。
3. **DROP + ADD 重列全集**，不在旧清单上打补丁、不照抄上一份迁移的列表。

🔴 **并且把这条 AC 做成了 L0 机械检查**（`MentionNotifyTest`）：
- 迁移里的清单与枚举**双向相等**（两个方向都断言 + 数量相等）；
- 判据是「**版本序最后那一条**重建该约束的迁移」而不是写死文件名 ——
  该约束的改法是「DROP 掉再按完整清单 ADD 回去」，**谁排在版本序最后谁说了算**
  （这正是四次事故的机理）。写死文件名的话，下次别人另起一条重建时用例会失效；
- 还断言那条迁移确实是 `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT ... CHECK (type IN (`
  —— 「在旧清单上打补丁」是四次事故的共同形状。

**下一个人加通知类型时，忘了重列 CHECK 会在 L0 就红**，而不是等到 staging 起不来。

#### 🔴 一个类型，帖子 / 评论两种由 targetRef variant 分流（AD-10 Rule 5）

AD-10 Rule 5 写的是「新增**一个**通知类型」。所以**没有** `POST_MENTIONED` /
`COMMENT_MENTIONED` 两个值 —— 沿用 `NAME_RESET` / `AVATAR_RESET` / `LIFECYCLE_*` 的范式：

| | 推送文案键 | targetRef | 深链落点（AC4） |
|---|---|---|---|
| 正文提及 | `notify.CONTENT_MENTIONED.POST.*` | `POST:{postId}` | 内容详情页 |
| 评论提及 | `notify.CONTENT_MENTIONED.COMMENT.*` | `COMMENT:{postId}` | 详情页 + `?focus=comments` |

- ⚠️ targetRef 里那个 id 是 **postId 而不是 commentId**：要跳的是帖子详情，评论区靠锚点定位。
  放 commentId 客户端得先反查 postId 才跳得动。有测试钉着。
- ⚠️ 深链的锚点判定**不走 `commentAnchor` 参数**（那个参数是通知中心按
  `deepLinkType == 'CONTENT_COMMENTED'` 传的，@ 提及不在其列）——
  `pushPayloadToLocation` 自己从 targetRef 前缀读出来，列表点击与系统推送两条路径因此同口径。
- 🛡 认不出前缀 / 缺 targetRef / id 不是数字 → 一律落通知中心，**绝不拼出 `/content/POST:12`**。
  条目文案侧同理（认不出按"帖子提及"说）—— 两处判据是同一个，分叉的表现是
  「正文里说在评论里提到你，点进去却没锚到评论区」。

#### AC3 文案架构

- **系统推送**：后端按收件人语言渲染 `notify.CONTENT_MENTIONED.{POST|COMMENT}.{title,body}`
  （四份 properties 都补了；印尼语那份是实际下发的）。走 `sendWithCopy` 而不是 `send` ——
  后者只认 `notify.<TYPE>.body` 这一句静态话，一个 type 就只能有一句，AC3 要求分两种。
- **通知中心条目**：App 按 type + targetRef variant 自行本地化（en / id 双表），
  **不读后端下发的 title/body**。落库的中文 title/body 只是 i18n 缺键时的兜底，
  且只会出现在推送里 —— 有测试逐个键断言印尼语串里**没有任何中文**。
- 正文两句不同、标题共用一句（AC3 只要求正文区分）。

#### 🔴 发布时机 = 那条内容/评论变成别人看得见的那一刻

新增领域事件 `ContentMentionedEvent`（content 不直调 notify）。三个落点：

1. `ContentService.publish` **正常分支**（落 PUBLISHED）；
2. `ContentService.approveReview`（挂起帖过审 → PUBLISHED）；
3. `CommentService.publishCommented`（评论 UNDER_REVIEW → VISIBLE，与「新评论」通知同一处）。

⚠️ **挂起分支刻意不发**：审核没过就通知，被 @ 的人点进去是 404
（与既有 `ContentCommentedEvent` 的口径逐字一致 —— 同一个方法里发的）。

🔴 **非 PUBLIC 一律不发**（两条路径都判）：PRIVATE Diary 照样落 @ 名单
（作者自视那条时间线要能高亮能点 —— Story 3.3），但可见范围创建后不可更改（FR-83 AC7），
被 @ 的人**永远打不开它**。判据写在**发布侧**，notify 侧因此不必再判一次可见范围。

⚠️ **运营免审发布（Lark 定时发帖）不带 @ 名单**（Story 3.2 的既定口径），故天然不发通知。

#### 🔴 AC5 拉黑不发 —— 三条判据，任一命中即不发

| # | 判据 | 漏了会怎样 |
|---|---|---|
| ① | **actor ↔ 收件人 任一方向**有隐藏关系 | AC5 原文就是「任一方向」。只判「收件人拉黑了 actor」的话，actor 在挂起帖过审前把对方拉黑仍会发出去 |
| ② | 内容作者隐藏了 actor（R2） | 那条评论对所有人隐藏，被 actor @ 的第三方收到一条点进去什么都没有的通知，一对比就能推断出屏蔽机制存在 |
| ③ | 收件人隐藏了内容作者 | 那条内容对他 404（`ContentDetailService` 按 `isHidden(viewer, post.authorId)` 拦）——「我拉黑了帖主」这件事被一条 @ 通知漏掉 |

- ① 走 `UserHideRelationReader.hiddenEitherWay` 的**批量**出口（AD-7 / AD-6）；
- ② 与收件人无关 → 提到循环外只判一次；actor 就是作者时不判；
- ③ 正文提及里 actor **就是**作者，与 ① 的 `isHidden(recipient, actor)` 同义 → 显式跳过不白查。
  所以它只在**评论提及**时真的多查（≤5 次，名单上限 5 人）。
- ⚠️ 三条都**不区分来源**（主动拉黑与举报隐藏都算）—— 与主页访问校验只认 BLOCK 正好相反。
- ⚠️ 抑制写在 `MentionNotifyListener`，**绝不写进 `NotificationService.send`** ——
  那是全站唯一的通用发送方法（12 个调用点），写进去会把封号 / 审核结果 / 内容被移除等系统通知一起掐了。
