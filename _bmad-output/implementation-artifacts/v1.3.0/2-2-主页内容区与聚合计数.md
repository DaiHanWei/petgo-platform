# Story 2.2: 主页内容区与聚合计数

Status: review

## Story

As a 想了解一个人的用户,
I want 在他主页上看到他公开发过的东西和总共发了多少、被赞了多少,
so that 我能快速判断这人活跃不活跃、内容合不合我口味。

## Acceptance Criteria

**AC1 — 内容列表** `[L1]`
返回该用户**全部 PUBLIC** 内容，**时间倒序**，Diary / Moment / Tips **混排不分流**。
非 PUBLIC 内容**服务端就不下发**（客户端过滤不算数）。

**AC2 — 聚合计数** `[L1]`
含**发帖总数**与**获赞总数**。
⚠️ 发帖总数**已有实现可直接复用**（迷你卡在用 `MiniProfileResponse.postCount`），本 story 真正新补的是**获赞总数**。

**AC3 — 批量取数** `[L1]`
两个计数与内容列表**一次批量取齐，无 N+1**。

**AC4 — 渲染** `[L2]`
复用既有「我的」页那套 2 列内容网格；点任一内容进既有内容详情页。

**AC5 — 反向验收（FR-118.7）** `[L2]`
主页上**没有**里程碑徽章墙、护照集章数、打卡足迹、主页级 H5 分享入口、关注/粉丝、访客记录、独立 bio 字段。

## Dev Notes

### 获赞总数怎么算

该用户全部内容被赞数之和。**批量聚合，不要逐条查**（AD-6 / NFR-6）。
参照既有批量模式：`AdminContentManageService.likeCounts(...)` 的 `Map<Long, Long>` 用法。

🛡 **禁止为这个数新增冗余计数列**（AD-6）。Story 1.8 的 Redis 计数器是**经明确拍板的例外**，仅限场所推荐/不推荐计数，**不构成先例**。

### 可见范围在服务端判定

`ContentVisibility.PUBLIC` 见 `petgo-backend/src/main/java/com/tailtopia/content/domain/ContentVisibility.java`。
🔴 非 PUBLIC 的内容**服务端就不查出来**，不是查出来再让客户端藏——客户端过滤只是"看不见"，抓包照样拿得到（NFR-2）。

### Completion Notes List

**已交付（L0 全绿）**

1. **内容区接口**（AC1）：`GET /api/v1/users/{userId}/posts?cursor=` →
   `FeedService.userPublicPosts`，投影与 Feed / 「我的发布」**同一个** `FeedItemResponse`，
   三类混排不分流、时间倒序、游标分页。
   - 🔴 **可见范围在 SQL 里**：`visibility = PUBLIC` + `status = PUBLISHED`（**去掉了**
     「我的发布」那条查询里的 `UNDER_REVIEW` —— 挂起帖仅作者本人可见，照抄过来就是
     把没过审的内容提前对外放出去）。客户端一行过滤都没有（NFR-2）。
2. **两个聚合计数**（AC2/AC3）：`postCount` **复用既有统计**（没有重新实现），
   `likeCount` 是本 story 新补的 —— **一条 SQL 出数**（`COUNT` + 子查询），
   既不逐帖 count 相加、也不新增冗余计数列（AD-6；Story 1.8 的 Redis 计数器是仅限那一处的例外）。
3. **无 N+1**（AC3）：作者投影 / 点赞数 / 已赞 / 评论数**四项各自整页一次批量取**，
   与 `myPosts`、`loadFeed` 同一套聚合（AD-7 Rule 4）。一条测试直接断言**查询次数**
   不随页大小增长 —— 退化成逐条方法是"跑得通、结果也对、没有测试会红"的那类改动。
4. **网格复用**（AC4）：「我的」页那一格从 `me_page.dart` 的私有 `_MyPostCard`
   **抽成公共组件** `shared/widgets/post_grid_tile.dart`，两页共用。
   复制一份的话，圆角 / badge 配色 / 首图降级这些细节会各改各的。点任一格进既有内容详情页。
5. **反向验收**（AC5）：一条**扫源码**的测试钉着主页上不出现里程碑 / 护照 / 打卡 /
   主页级分享 / 关注粉丝 / 访客记录 / 独立 bio。这些不是"还没做"，是明确不做。

**🔴 顺带改掉的一条既有口径：发帖总数原先把私密内容也数了进去**

`countPublishedByAuthor` 只过滤了「未软删 + PUBLISHED」，**没有 visibility** ——
而它的两个出口（迷你卡 / 公开主页）**都是他人视角**，`ContentVisibility` 对这一类的
判定口径写得很死：按 PUBLIC 过滤（NFR-4）。
不改的后果有两层：① 主页上写着「18 postingan」而网格里只有 12 格，一眼对不上；
② 更要紧的是**那个差值就是这个人有几篇私密内容**，访客不该能推断出来。
→ 改为 `countPublicPostsByAuthor`（带 visibility 谓词），迷你卡端点一并跟上。
⚠️ **作者自视的口径一行未动** —— 「我的发布」走 `findMyPosts`，那边刻意不过滤 visibility。

**code-review 复审后修掉的（3 findings 全修）**

1. 🔴 **网格里会摆出一排点进去全是 404 的死格子**：新查询漏了 Feed 一直带着的两条排除 ——
   访客**举报过的那一条**（`ContentReport`）与访客**隐藏过的那个人**（`UserHideRelation`，
   不分 BLOCK / REPORT）。而 `ContentDetailService` 对这两种情况**一律 404**
   （「举报一条帖它就 404、拉黑整个人他每条帖却照样打得开」的语义倒挂，PRD §7 已消灭）。
   举报过某人账号之后进他主页，整片网格每一格都是死的。
   → 两条谓词补进查询（`hasViewer` 布尔门控，游客传 NULL 会触发 42P18），`viewerId` 透传。
   - ⚠️ **这条排除只作用于网格，不作用于两个计数**，是有意的：计数说的是「这个人发了多少」，
     网格说的是「你能看到哪些」。访客**知道自己隐藏过谁**，所以这处不一致既不泄漏也不困惑 ——
     与上面 PRIVATE 那种（关于作者、访客无从得知）的差值是两回事。
     🔸 **这一条口径是本 story 自行判定的，建议本地验收时确认**（story AC 与决策日志都没写到它）。
2. `me_page.dart` 抽走 `_MyPostCard` 后**留下一段孤儿文档注释**，挂到了下一个类头上。
3. 主页类注释里引用的守门测试**文件名写错了**。

**顺带清理**：`countByAuthorIdAndDeletedAtIsNullAndStatus` 在改口之后已无调用方，删掉。

**范围边界（有意不做）**

- **宠物卡不做**（Story 2.3）；**自己视角的「编辑资料」不做**（Story 2.4）；
  **被拉黑者 / 已注销的完整空态视觉不做**（Story 2.5）。
- 网格一格上**不放点赞 / 评论按钮**：这个接口回的是完整 `FeedItemResponse`（那些字段都在），
  但主页网格只有封面 + 类型角标 —— 前端模型**刻意只取三个字段**，省得下一个人顺手在网格上加互动。
- **主页级 H5 分享入口不做**（FR-118.7 明确列在「不放」清单里）。
