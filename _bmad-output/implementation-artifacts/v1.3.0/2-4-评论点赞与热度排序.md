# Story 2.4: 评论点赞与热度排序

Status: review

## Story

As a 用户，
I want 给评论点赞、并优先看到大家认可的评论，
so that 好评论不会被时间顺序埋掉.

---

> **本 story 是 Epic 2 后端最难的一块**，也是本批次唯一的新业务表。
>
> 三条硬约束都是「不要做什么」：不加冗余计数列、不改共享的 `FeedCursor`、不做服务端排序快照。三条都有明确代价与理由，见 Dev Notes。

---

## Acceptance Criteria

### AC1 — 新表形态（L0 / L1）

**Given** 数据库
**When** 迁移执行完毕
**Then** 存在 `comment_likes` 表，**逐字对齐** `content_likes` 的形态：`id BIGSERIAL` / `comment_id` / `user_id` / `created_at TIMESTAMPTZ DEFAULT now()` + `UNIQUE(comment_id, user_id)` + 两条外键 `[L1]`
**And** 迁移文件名为时间戳制 `[L0]`
**And** 一级、二级评论**共用同一张表**，不按层级分表 `[L0]`

### AC2 — 🔴 不加冗余计数列（L0）

**Given** 本 story 的 schema 变更
**When** 检视
**Then** **未新增任何冗余计数列**（如 `like_count`） `[L0]`
**And** 点赞数一律实时聚合 `[L0]`

> 全库至今没有任何冗余计数列（`content_likes` 亦为实时 COUNT）。开这个头就要处理并发增减、对账与回填。

### AC3 — 点赞端点幂等（L1）

**Given** 同一用户对同一条评论
**When** 重复点赞
**Then** 唯一约束兜底，不产生第二行 `[L1]`
**When** 取消点赞
**Then** 删除该行 `[L1]`

### AC4 — 热度排序（L1）

**Given** 一级评论列表
**When** 按默认序返回
**Then** 排序为 点赞数 DESC → `created_at` ASC → `id` ASC `[L1]`
**Given** 二级回复
**Then** 维持时间正序不变 `[L1]`

### AC5 — 🔴 新建独立游标，不改 `FeedCursor`（L0 / L1）

**Given** 热度序的分页游标
**When** 实现
**Then** 使用**新建的独立评论热度游标类型**（三元组 `likeCount + createdAt + id`） `[L0]`
**And** **不修改**共享的 `FeedCursor` `[L0]`
**And** Feed 的分页行为零变化 `[L1]`

> 🔴 `CommentQueryService` 当前**复用** `FeedCursor`（`FeedCursor.decode` / `new FeedCursor(createdAt, id).encode()`），而 Feed 也在用同一个类。改它会溢出到 Feed —— 项目自家 `FeedRankCursor` 的注释里已写过「静默误解码」的教训。

### AC6 — 排序键无法建索引，接受每页聚合（L0 / L1）

**Given** 排序键第一元是跨表聚合值
**When** 设计索引
**Then** 索引只支撑聚合与过滤两侧（`comment_likes(comment_id)`、`comments(post_id, parent_id, deleted_at, created_at)`） `[L0]`
**And** 接受「每页对该帖一级评论做一次聚合」 `[L1]`
**And** 该方案的成立前提是**单帖一级评论量级为几十到几百**，写入 Dev Notes 备查 `[L0]`

### AC7 — 批量取数（L1）

**Given** 点赞数与「viewer 是否已赞」
**When** 取数
**Then** 一律批量聚合，**不逐条查询** `[L1]`

### AC8 — 注销级联（安全攸关，L1）

**Given** 一个用户注销
**When** 执行注销级联
**Then** 其 `comment_likes` 行按既有 D1/D2 口径处置 `[L1]`
**And** 与 `content_likes` 采用**同一种处理**，不另立口径 `[L0]`

### AC9 — 软删口径（L1）

**Given** 一条被软删的评论
**When** 统计与列表取数
**Then** 不计入、不返回 `[L1]`
**And** 其点赞行**不物理删除** `[L1]`

### Completion Notes List

**三条「不要做」—— 全部用结构性断言钉住，而不只是"这次没做"**

「没做某件事」恰恰最容易被后来人无意中做掉：加一个计数列、给 `FeedCursor` 多塞一元、
给新表补一条删除逻辑，每一件单看都像"顺手优化"。所以每条都配了会变红的断言：

| 不要做 | 断言 |
|---|---|
| 不加冗余计数列 | 扫迁移 DDL 无 `like_count`；`CommentLike` 实体字段集恰为 `{id, commentId, userId, createdAt}` |
| 不改 `FeedCursor` | 断言它**仍是二元组**；且两种 token 互不通用（各自解对方的 token 必抛 422） |
| 不另立注销口径 | 断言 `CommentLikeRepository` 与 `ContentLikeRepository` **都没有**任何 `deleteByUser*` |

> 扫迁移时**先剥掉 `--` 注释**：注释里本来就要写「为什么不加 like_count」，
> 不剥的话一句解释性文字就能把自己的断言弄红。

**已交付（L0 全绿）**

1. **AC1 新表**：`V20260911_0419__create_comment_likes.sql`，形态逐字对齐 `content_likes`
   （`BIGSERIAL` / 两个 `BIGINT NOT NULL` / `TIMESTAMPTZ DEFAULT now()` / `UNIQUE(comment_id,user_id)`
   / 两条外键）。一级二级**共用同一张表**。
2. **AC3 幂等**：`CommentLikeService.like` **直接插、撞约束就当已赞**。
   有一个 `exists` 快速短路，但**幂等的真正保证是唯一约束** ——
   「先查后插」之间有并发窗口，两个请求会都查到「没赞过」。
3. **AC4 热度序**：`findTopLevelByHot`，`ORDER BY COUNT(l) DESC, c.createdAt ASC, c.id ASC`。
   第二元用 ASC：同样赞数时先发的排前面（「同样多人认可，谁先说的谁在上」）。
   二级回复**维持时间正序、仍用 `FeedCursor`**（AD-A8.7）。
4. **AC5 独立游标**：新建 `CommentHotCursor`（三元组）。编码带 `h1:` 前缀且段数不同 ——
   传错地方是**当场 422**，不是解出一个看似合理的错位游标（这正是不去改 `FeedCursor` 的理由，
   项目自家 `FeedRankCursor` 注释里写过「静默误解码」的教训）。
5. **AC6 索引两侧**：`comment_likes(comment_id)` 聚合侧 + 
   `comments(post_id, parent_id, deleted_at, created_at)` 过滤侧。
   **排序本身没有索引可用** —— 这是「不加计数列」的直接后果，不是遗漏。
   成立前提写进了迁移与查询注释：**单帖一级评论几十到几百**；若进入万级本方案退化，
   届时是**推翻 AD-A7.3、须走正式变更**，不得就地加列了事。
6. **AC7 批量取数**：`loadLikes` 两次查询搞定一整页（赞数 + 已赞集合），一级与内嵌二级一起取。
   仓库**刻意不提供任何逐条方法** —— 拿不到逐条版本就写不出 N+1。游客不查已赞集合
   （他不可能赞过任何东西，多发一次查询只为拿个恒空集合）。
7. **客户端**：`Comment` 加 `likeCount`/`liked`（老后端不下发时兜底 0/false）；
   评论行加心形+数字（0 赞不显示数字，一排「0」会把评论区弄得很吵；数字与心同步变色，
   与帖子点赞 FR-93 同规则）。**乐观更新**，失败静默回滚 ——
   点赞不是关键路径，为它弹错误提示比点不上还烦人。
   `_replaceComment` **三处都找**（一级列表 / 内嵌回复 / 已展开回复）：同一条评论在不同位置是
   同一对象的不同副本，只改一处会让「收起再展开」时点赞态跳回去。

**AC8 注销级联 —— 结论是「什么都不做」，这不是偷懒**

查了现网口径：注销走**就地匿名化 user 行、不物理删**（决策 D1/A，`AuthAccountDeletionService`
的类注释写明「content_posts/comments/content_likes 均以 NOT NULL + RESTRICT 外键指向 users(id)，
硬删会抛 DataIntegrityViolationException」）。`content_likes` 因此**没有任何按用户删除的路径**，
点赞行原样保留、指向已匿名化的用户。

`comment_likes` 采用**完全相同**的处理：`user_id NOT NULL` + RESTRICT 外键，不写
`ON DELETE CASCADE`，仓库不提供 `deleteByUserId`。给新表单独加删除逻辑**才是**另立口径 ——
那会让同一个用户的两种点赞在注销后表现不同（一种消失、一种留着）。

**AC9 软删口径**：软删评论本就不在任何查询结果里（`deletedAt IS NULL` 条件与既有 `findTopLevel`
逐字相同），所以它的赞数不会出现在任何地方；点赞行**不物理删除**。

**不做服务端排序快照（AD-A8.3 / 决策 A-6）**

排序键每次查询实时取。代价：某条评论的赞数恰在翻页瞬间跨越游标位置时可能重复或漏一条 ——
**后果是多看/少看一条评论，不是数据错误**。「已渲染的列表不重排」由客户端承担，服务端不留状态。
