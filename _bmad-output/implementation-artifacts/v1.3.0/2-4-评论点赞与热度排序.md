# Story 2.4: 评论点赞与热度排序

Status: ready-for-dev

## Story

As a 用户，
I want 给评论点赞、并优先看到大家认可的评论，
so that 好评论不会被时间顺序埋掉.

---

> **本 story 是 Epic 2 后端最难的一块**，也是本批次唯一的新业务表。
>
> 三条硬约束都是「不要做什么」：不加冗余计数列、不改共享的 `FeedCursor`、不做服务端排序快照。三条都有明确代价与理由，见 Dev Notes。

---

## Acceptance Criteria

### AC1 — 新表形态（L0 / L1）

**Given** 数据库
**When** 迁移执行完毕
**Then** 存在 `comment_likes` 表，**逐字对齐** `content_likes` 的形态：`id BIGSERIAL` / `comment_id` / `user_id` / `created_at TIMESTAMPTZ DEFAULT now()` + `UNIQUE(comment_id, user_id)` + 两条外键 `[L1]`
**And** 迁移文件名为时间戳制 `[L0]`
**And** 一级、二级评论**共用同一张表**，不按层级分表 `[L0]`

### AC2 — 🔴 不加冗余计数列（L0）

**Given** 本 story 的 schema 变更
**When** 检视
**Then** **未新增任何冗余计数列**（如 `like_count`） `[L0]`
**And** 点赞数一律实时聚合 `[L0]`

> 全库至今没有任何冗余计数列（`content_likes` 亦为实时 COUNT）。开这个头就要处理并发增减、对账与回填。

### AC3 — 点赞端点幂等（L1）

**Given** 同一用户对同一条评论
**When** 重复点赞
**Then** 唯一约束兜底，不产生第二行 `[L1]`
**When** 取消点赞
**Then** 删除该行 `[L1]`

### AC4 — 热度排序（L1）

**Given** 一级评论列表
**When** 按默认序返回
**Then** 排序为 点赞数 DESC → `created_at` ASC → `id` ASC `[L1]`
**Given** 二级回复
**Then** 维持时间正序不变 `[L1]`

### AC5 — 🔴 新建独立游标，不改 `FeedCursor`（L0 / L1）

**Given** 热度序的分页游标
**When** 实现
**Then** 使用**新建的独立评论热度游标类型**（三元组 `likeCount + createdAt + id`） `[L0]`
**And** **不修改**共享的 `FeedCursor` `[L0]`
**And** Feed 的分页行为零变化 `[L1]`

> 🔴 `CommentQueryService` 当前**复用** `FeedCursor`（`FeedCursor.decode` / `new FeedCursor(createdAt, id).encode()`），而 Feed 也在用同一个类。改它会溢出到 Feed —— 项目自家 `FeedRankCursor` 的注释里已写过「静默误解码」的教训。

### AC6 — 排序键无法建索引，接受每页聚合（L0 / L1）

**Given** 排序键第一元是跨表聚合值
**When** 设计索引
**Then** 索引只支撑聚合与过滤两侧（`comment_likes(comment_id)`、`comments(post_id, parent_id, deleted_at, created_at)`） `[L0]`
**And** 接受「每页对该帖一级评论做一次聚合」 `[L1]`
**And** 该方案的成立前提是**单帖一级评论量级为几十到几百**，写入 Dev Notes 备查 `[L0]`

### AC7 — 批量取数（L1）

**Given** 点赞数与「viewer 是否已赞」
**When** 取数
**Then** 一律批量聚合，**不逐条查询** `[L1]`

### AC8 — 注销级联（安全攸关，L1）

**Given** 一个用户注销
**When** 执行注销级联
**Then** 其 `comment_likes` 行按既有 D1/D2 口径处置 `[L1]`
**And** 与 `content_likes` 采用**同一种处理**，不另立口径 `[L0]`

### AC9 — 软删口径（L1）

**Given** 一条被软删的评论
**When** 统计与列表取数
**Then** 不计入、不返回 `[L1]`
**And** 其点赞行**不物理删除** `[L1]`

## Dev Notes

### 三条「不要做」及其代价

| 不要做 | 为什么 | 已接受的代价 |
|---|---|---|
| 不加冗余计数列 | 全库无先例，开头就要处理并发/对账/回填 | 排序键无法建索引，每页现算 |
| 不改 `FeedCursor` | 它是 Feed 与评论共用类，改动会溢出 | 多一个游标类型 |
| 不做服务端排序快照 | 真快照要么引服务端状态（违反禁缓存）、要么按时刻重算赞数（取消点赞是物理删行，历史不可重建） | 翻页瞬间极小概率多看/少看一条（决策 A-6 已接受） |

### 要改的文件

| 文件 | 改什么 |
|---|---|
| `petgo-backend/src/main/resources/db/migration/V<ts>__*.sql` | **新增** `comment_likes` |
| `petgo-backend/.../content/repository/CommentRepository.java` | 热度序查询（现为 `(createdAt,id)` 正序 keyset，约 144–171 行） |
| `petgo-backend/.../content/service/CommentQueryService.java` | 游标改用新类型（现复用 `FeedCursor`，约 58/129/180/189 行） |

| `V10__init_content_likes.sql` | **只读参照形态** |
