# Story 1.7: 场所评论与二元态度

Status: review

## Story

As a 去过这家店的用户,
I want 留一句攻略提示并顺手表个态,
so that 后面的人能少踩坑，也知道大家整体觉得这地方行不行。

## Acceptance Criteria

**AC1 — 独立建表（AD-8）** `[L0]`
新建 `place_comments`。**不改既有 `comments` 表**、**不使用多态外键**；表名带模块前缀；迁移用时间戳版本号。
二元态度是本表的一个**可空列**（推荐 / 不推荐 / 空）。

**AC2 — 一级评论 only** `[L2]`
只能发一级评论（≤200 字），**没有任何回复 / 盖楼入口**。

**AC3 — 可选态度** `[L2]`
提交时可选「推荐 👍 / 不推荐 👎」，**可以不选**。

**AC4 — 输入条形态（UX-DR3）** `[L2]`
👍/👎 在**评论输入的展开态**里（输入框获焦后出现），**不得与发送键并列** —— 并列会被读成"给场所点赞/点踩"的独立动作。

**AC5 — 审核** `[L1]`
评论文本走与内容评论**同一套**三方自动审核（先发后审），但审核状态**各存各的**。

**AC6 — 拉黑过滤** `[L1]`
评论列表按拉黑关系过滤，且**走既有的那个统一读取口**，不新写查询。

**AC7 — 用户自删** `[L2] [L1]`
用户可删除**自己**发的场所评论（2026-09-15 拍板）。
🔒 服务端**校验操作者是评论作者本人**，不得传个评论 id 就能删。
删除后对应的推荐/不推荐计数同步变更（计数机制见 Story 1.8）。

## Dev Notes

### 🔴 为什么必须独立建表

既有 `comments.post_id` 是 **NOT NULL** 且语义绑死内容帖（见 `content/domain/Comment.java`）。共表就得把它改成可空再加场所列 —— 那正是**多态外键**，而 v1.1.6 AD-10 已为同类问题定过先例：**两套独立表，不共用、不用多态外键**。

而且形态本就不同：内容评论有楼中楼，场所评论**只有一级**（攻略提示性质，无对话需求）。共表等于把"不能回复"降格成一条只靠代码自觉维持的约定。

### 态度与计数的关系

态度存在本表；**计数的展示与 Redis 机制是 Story 1.8**。本 story 只要保证：
- 态度正确落库
- 删除评论时**触发**计数变更（具体机制 1.8 实现，本 story 留好调用点）

**code-review 复审后修掉的（4 findings 全修）**

1. 🔴 **游客可读的 GET 把兽医 token 当成了用户**（安全）：`optionalUserId` 只看 `sub`，
   而兽医 token 的 sub 是 **vetId**，与 `users.id` 是两个会大量碰撞的命名空间 ——
   兽医打开场所详情会被当成「users.id 恰好等于该 vetId 的那个用户」，
   于是**那个人未过审 / 已下架的评论原文会下发给他**，还标着 `mine=true`。
   写端点靠 SecurityConfig 的 `hasRole("USER")` 挡住了，读端点对游客放行、挡不住。
   → 两个 controller 的 helper 都加 `role=USER` 判定，并写了
   `PlaceViewerIdentityTest`（6 例，含"缺 role claim 也按游客"的 fail-closed 分支）。
2. 🔴 **注销级联漏了 `place_comments`**（安全，D1/D2）：它是独立表，content 那条级联碰不到 ——
   注销用户的场所评论会继续挂着他的身份对所有人可见。
   → 加 `PlaceCommentService.deactivateAuthorComments`（置 `AUTHOR_DEACTIVATED`，
   **不删行**：评论内容是场所攻略的一部分，消失的是身份展示），接进
   `AccountDeletionService` 的编排、放在 user 行删除**之前**，并在既有编排测试里加了 verify。
3. **实体上两个全仓零调用的状态迁移方法**（`rejectModeration` / `takedown`）→ 删掉。
   没被执行过的状态迁移只会给人"已经能处置了"的错觉；等运营队列接上场所评论时再加。
4. **发表/删除后详情计数不刷**：评论数在**详情响应**里，只刷评论区会让同一屏上
   计数行的「💬 3」和标题「评论 (4)」对不上。→ 加 `invalidatePlaceDetail(ref, token)`
   （按 token 失效那两个可能的族键 —— 调用方手里没有归一后的坐标，猜一个只会失效没人看的族）。

**🔴 需要 admin 主题配合的一条（本主题做不了，已记在这里）**

**三方审核降级 / 高危的评论，目前会一直挂在 `UNDER_REVIEW`**（仅作者可见，他人不可见）。
内容评论那条走 `ManualReviewGate.enqueueComment` 进运营人工队列，而那张队列表的
`content_type` 只有 `CONTENT_POST` / `COMMENT` 两个值，**admin 侧对 `COMMENT` 行的处置动作
是直接打 `CommentService`（也就是 `comments` 表）** —— 把 `place_comments.id` 塞进去，
运营点一次"通过"就会去放行 `comments` 表里**同号的那条别人的评论**。那是数据事故。

- 本 story 的取舍：**宁可挂着，也不自动放行**（安全侧守住），
  **更不自动判 `REJECTED`**（终态，等于让一次三方超时判死一条可能完全正常的评论）。
- 接入队列需要 admin 主题扩 `ReviewContentType`（+ 迁移 + 处置路由 + 队列 UI），
  **请在 admin 线排一条**。在那之前，降级期间的场所评论需要人工从库里捞。
