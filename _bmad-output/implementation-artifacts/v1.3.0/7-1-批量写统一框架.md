## Story

As a 运营，
I want 批量操作有预览和二次确认，且我预览之后别人改了数据不会被我覆盖，
so that 我不会误改一片商品。

## Context

### (a) 🔴 本仓既有的三个「批量」先例，语义与 SHOP-NFR-02 要求**完全相反**

| 先例 | 位置 | 它怎么做的 | 与本 story 的关系 |

| 批量打用户标签 | `petgo-backend/src/main/java/com/tailtopia/admin/usertag/service/AdminUserTagService.java:180`（`@Transactional`:179） | 外层一个事务，但**逐个 `try/catch` 吞 `AppException` 收集 `failed`**（部分成功）；**只记一条汇总审计** `:195-196`：`audit.record(adminId, "USER_TAG_ASSIGN_BULK", "user_tag", …, "users=" + unique.size() + " failed=" + … + " ids=" + unique)`；动作码是**裸字符串、不是 `AuditActions` 常量**；**无行数上限**、无预览、无条件写 | 🔴 **反例。不得照抄。**「一条汇总审计」正是 SHOP-NFR-02 明令禁止的那一条 |
| 批量下架 / 驳回举报 | `petgo-backend/src/main/java/com/tailtopia/admin/service/AdminModerationService.java:207`（javadoc `:203-206` 原文：「**不开外层事务**；逐条经自引用代理调用（各自独立事务）；部分失败不影响已成功项」），返回 `BatchResult(ok, failed)` `:240` | 逐条独立事务、部分成功 | 🔴 **反例**（对内容审核是对的，对批量改价改库存是错的） |
| 批量解除限流 | `petgo-backend/src/main/java/com/tailtopia/admin/throttle/web/AdminThrottleController.java:99`（`:121` 日志「限流批量解除：成功 N 条，已非生效态 M 条」） | 同上，部分成功 | 反例 |

**结论：本仓没有任何「整批一个事务 + 预览即契约 + 逐条审计 + 行数上限」的先例，7-1 是首个。** 因此本 story 的 AC 不能写成「照抄某某范式」，只有条件写那一层有范式可抄（见 (b)）。
⚠️ 反过来说也成立：**7-1 的框架不得被用来重构上述三处**——它们是「一批数据」（部分成功合理），批量改价改库存是「一次决策」（AD-S5 原文），语义不同。

### (b) 唯一可照抄的范式：条件原子写 + 判影响行数

`petgo-backend/src/main/java/com/tailtopia/shop/repository/SkuInventoryRepository.java:20`，六条原语全部是**单行原子条件 UPDATE、返回影响行数、0 = 条件不满足**：

| 方法 | 行 | WHERE 守卫 |
|---|---|---|
| `lock` | `:36`（query `:33-35`） | `i.skuId = :skuId and i.actual - i.locked >= :qty` |
| `release` | `:47` | `i.locked >= :qty` |
| `commit` | `:59` | `i.locked >= :qty and i.actual >= :qty` |
| `restock` | `:79` | 仅 `skuId`（`@Modifying(clearAutomatically=true, flushAutomatically=true)`:76） |
| `damage` | `:97` | `i.actual - i.locked >= :qty`（按可售量，不是 actual） |
| **`stocktakeTo`** | `:120-121`（query `:117-119`） | `i.skuId = :skuId and i.actual = :expectedBefore and i.locked <= :counted` —— **对前值做 CAS** |

`stocktakeTo` 的 javadoc（`:104-116`）已经把「预览即契约」的道理写完整了，原文值得整段读：

> 把期望前值放进 WHERE 后，并发改动使影响行数为 0，**失败是响亮的**。这不是被禁止的「先查后改」：判定仍在同一条 SQL 内，应用层的读只用来提出期望值。

🔴 **AD-S5 的「预览即契约」就是把这句话推广到另外三类。** 框架的全部技术内容 = 让每一类批量操作都有一个这样的条件写，并在影响行数 ≠ 1 时**整批抛异常回滚**。

⚠️ 反向事实：`ShopProductRepository` 与 `ShopSkuRepository` 目前**没有任何 `@Modifying` 条件写**（全是查询方法）——商品与 SKU 侧的条件写是本 epic 新造的，`SkuInventoryRepository` 是唯一的形状参照。

### (c) 审计入口与它的事务语义（正好是本 story 需要的）

`petgo-backend/src/main/java/com/tailtopia/admin/audit/service/AdminAuditService.java:24`，方法签名 `:68-70`：

```java
@Transactional
public AdminAuditLog record(Long actorAccountId, String actionType, String targetType,
        String targetId, String summary)
```

类 javadoc `:17-19` 原文：「`record` 为 `@Transactional`（默认 REQUIRED）：被业务事务调用时**加入**该事务，业务回滚则审计一并回滚（无悬挂审计）」。
⇒ **「整批一个事务」与「逐条审计」天然相容**：批量事务回滚时，那一批审计也一起回滚，不会留下「审计说改了 100 条、实际一条没改」。这条要写进测试断言（AC3）。
另：`summary` 超 500 字符会被 `clampSummary`（`:52-58`）截断而非抛错；`targetType` / `targetId` 可空但本 story 一律必填。

## Acceptance Criteria

**AC1 · 四步流程与其形状** `[L0]`
**Given** 运营在（Epic 10 重构后的）商品页或库存页
**When** 走一次批量操作
**Then** 流程恰为四步：**圈定（勾选 / 按当前筛选结果）→ 预览 → 二次确认 → 提交** `[L0]`
**And** 预览响应中每一行都带 **行 token + 显示名 + 旧值 + 新值**，且整体带 **影响行数** `[L0]`
**And** 提交请求**必须携带预览时的旧值**（逐行），否则服务层直接 422 拒绝（缺旧值 = 没走预览）`[L0]`
**And** 圈定支持**两种粒度**（商品级 `ShopProduct` / 规格级 `ShopSku`），行标识一律用 `publicToken`，**任何请求与响应都不出现自增 id** `[L0]`

**AC2 · 🔴 预览即契约：条件写守卫，任一行不匹配 ⇒ 整批拒绝** `[L0/L1]`
**Given** 预览时第 7 行的旧值是 X
**When** 提交前该行被改成 Y，运营再点提交
**Then** 该行的条件写影响 **0 行**，服务层**立即抛异常、整批回滚** `[L1]`
**And** 返回的错误里点名**是哪一行**（token + 显示名）且提示「数据已变化，请重新预览」；**不提供「跳过该行继续」的选项** `[L1]`
**And** 条件写是**唯一判定点**：服务层**不得**先 `select` 一遍比对旧值再 update（那是被禁止的读改写，`SkuInventoryRepository` 类注释 `:14` 原文「🔴 禁应用层读改写」）`[L0]`
**And** 允许为了**生成可读错误文案**在失败后重读一次当前值，但该读**只进文案、不参与判定**，代码注释须写明这一点 `[L0]`

**AC3 · 整批一个事务，全成或全不成** `[L0/L1]`
**Given** 一批 50 行，其中第 30 行条件写影响 0 行
**When** 提交
**Then** 前 29 行的改动**全部回滚**，DB 里一行未变 `[L1]`
**And** 这一批产生的**审计行也一并回滚**（`AdminAuditService.record` 是 REQUIRED，加入业务事务）—— 集成测试须断言 `admin_audit_logs` 没有新增行 `[L1]`
**And** 批量服务方法上是 `@Transactional`（默认 REQUIRED / 单一事务），**不得**出现 `REQUIRES_NEW`、不得出现自引用代理逐条独立事务的写法（那是 `AdminModerationService.batch:207` 的范式，本处是反例）`[L0]`

**AC4 · 🔴 逐条审计：100 行 = 100 条** `[L1]`
**Given** 一批成功改了 100 行
**When** 事务提交
**Then** `admin_audit_logs` **新增恰好 100 行**，一行一条 `AdminAuditService.record(...)` `[L1]`
**And** **不得**出现任何形如「批量处理 N 条」的汇总审计行（SHOP-NFR-02 明令）`[L1]`
**And** 每条审计的 `targetType` / `targetId` 指向**该行自己的**资源与 `publicToken`，`summary` 含**改前 → 改后** `[L1]`
**And** 集成测试用 `count` 差值断言，**不是**断言「至少有一条」`[L1]`

**AC5 · 单次上限 100 行，服务层强校验** `[L0/L1]`
**Given** 圈定结果为 101 行
**When** 调预览或提交
**Then** 两个端点**都**返回 422，文案说明上限 100 与需要分批 `[L1]`
**And** 校验在**服务层**，不只在页面（页面只按同一常量做提示）；上限是**一个常量、一处定义**，四类批量共用 `[L0]`
**And** 「按当前筛选结果圈定」命中 101 行时，预览阶段就拒绝，**不得**静默截断成前 100 行 `[L0/L1]`

**AC6 · 新权限码 `shop.bulk_edit`，改满 5 处** `[L0]`
**Given** `AdminPermissions` 本分支 72 个码
**When** 新增 `SHOP_BULK_EDIT = "shop.bulk_edit"`
**Then** ① 常量落 `AdminPermissions.java` 的 `shop.*` 段（`:245-283` 之后）`[L0]`
**And** ② 加入 `GROUPS` 的 **`perm.group.edit`** 组（`:305-317`，批量写是编辑不是查看）——**只属一组** `[L0]`
**And** ③ `perm.shop.bulk_edit=…` 落 **4 个** properties（`messages.properties` / `_zh_CN` / `_en` / `_id`），四包齐备 `[L0]`
**And** ④ `AdminPermissionsTest:126` 的 `hasSize(72)` 改 `hasSize(73)`，并在 `:79-125` 的记账注释**续一行**说明为什么加（不得只改数字）`[L0]`
**And** ⑤ 第 5 处（admin 预置角色默认授予 + 种子迁移）在本分支不可达（`admin_roles` 表不存在），**按 Dev Notes 的处置办法登记为待办并写进 Completion Notes**，不得假装做完 `[L0]`
**And** `AdminPermissionWiringTest`（`petgo-backend/src/test/java/.../AdminPermissionWiringTest.java:110-118`，双向：每个 `hasAuthority('x')` 字面量 ∈ ALL 且每个 ALL 码至少有 1 处闸门）**必须绿** —— 即新码必须真的被至少一个 `@PreAuthorize` 或模板 `sec:authorize` 用上 `[L0]`

**AC7 · 二次确认走后台模板确认态，不是浏览器 `confirm()`** `[L0/L2]`
**Given** UX-S4
**When** 运营点「提交」
**Then** 页面进入**确认态 fragment**（Epic 10 的模板机制），复述影响行数与改前改后，需再点一次「确认执行」`[L2]`
**And** 代码里**不出现** `confirm(` / `window.confirm` / `data-confirm` 作为本批量流程的唯一确认手段 `[L0]`
**And** 错误按 admin delta 约定返回：业务/校验失败 **422 + 操作区 fragment**（行内错），权限不足 **403 + 禁用态 fragment 并注明所缺权限名 `shop.bulk_edit`**；**禁止向 htmx 返回 JSON** `[L1]`
**And** 🔴 Epic 10 的 fragment 壳与 `admin-core.js` 必须已在分支上；不在则**停手**（见 Context (e)）`[L0]`

**AC8 · 🔴 变异验证** `[L0]`
**Given** 条件写守卫是本 story 的全部安全性来源（风险 G-3）
**When** 把守卫从条件写里删掉（例如把 `and x.someField = :expected` 那一段去掉）
**Then** 至少有一条**具名测试变红** `[L0]`

## Dev Notes

### 🔴 为什么四类共用一个权限码 `shop.bulk_edit`

AD-S13 原文：「批量改价 / 改库存 / 上下架 / 调品类（**统一一个码，不按操作细分**——四者风险同级，细分只增加配错概率）」。

展开说：细分成四个码，运营主管要在角色配置页做四次判断，而这四次判断的答案在现实里永远相同（「这个人能不能批量改东西」）。四选一配错的后果是**静默的**——被漏授的人看到的是按钮不见了，会以为是页面 bug 而不是权限问题；被误授的人则多了一项没人评估过的能力。一个码，一次判断，一个答案。

⚠️ **共用权限码不等于共用审计码**：AC4 要求每条审计指向具体动作，7-2 / 7-3 / 7-4 各自用自己的 `AuditActions` 常量（7-3 复用既有 `SHOP_INVENTORY_STOCKTAKED`，7-2 / 7-4 需新增，见各自 story）。权限是「谁能做」，审计是「做了什么」，两者粒度本来就不同。

### 🔴 为什么不加乐观锁列、不引分布式锁

AD-S5 明写「不引入乐观锁列，不引入分布式锁」。理由：
- **乐观锁列**：`shop_skus` / `shop_products` 现在**都没有 `version` 列**（`shop_skus` 建表见 `V20260817_1154__init_shop_products_and_skus.sql:60-74` + 后来只加过 `cost_price`；`ShopProduct` 实体无 `@Version` 字段）。为批量写加一列 = 改既有表 + 所有单条写路径都要带上版本 = 改动面远大于本 story，且条件写已经把同一件事做完了。
  ⚠️ 别被 `sku_inventory.version` 误导：那是**普通列不是 JPA `@Version`**（`V20260817_1220__init_sku_inventory.sql:21`，实体注释 `SkuInventory.java:41-42` 明写这一点），六条原语手动 `i.version = i.version + 1` 只是留痕。
- **分布式锁**：F-3 / SHOP-NFR-06 禁引任何新中间件；`SkuInventoryRepository` 类注释 `:17` 原文「🔴 禁 SELECT … FOR UPDATE / Redis 扣减 / 分布式锁 / 任何新中间件」。

条件写之所以够用：它把「期望值」放进 WHERE，并发改动使影响行数为 0，**失败是响亮的**。这不是乐观锁的替代品，它就是乐观锁，只不过版本号换成了业务值本身 —— 而业务值恰好就是运营在预览页上看到的那个数。

### 🔴 「预览即契约」为什么必须整批拒绝，而不是跳过不匹配的行

跳过 = 运营看到的预览和实际发生的事不一致，而他**没有任何办法知道差在哪**（100 行里跳了 3 行，页面回一句「成功 97 条」，他不会去查是哪 3 条）。批量改价改库存是「一次决策」不是「一批数据」（AD-S5 原文），决策的输入变了就应该重做决策。

这也是它与导入（7-5）的**唯一区别**，两者不要互相照抄：导入是「一批数据」，逐行 `REQUIRES_NEW`、一行失败不拖垮整份是对的。

### 审计事务语义已经替我们做了一件事

`AdminAuditService.record` 是 REQUIRED（类 javadoc `:17-19`），加入业务事务。因此「整批回滚 ⇒ 审计一并回滚」是**免费的**，不需要额外处理。但它同时意味着：**不能**为了「即使失败也留痕」而把审计改成 `REQUIRES_NEW` —— 那会留下「审计说改了 100 条，实际一条没改」的假记录，比没有记录更糟。若确实需要记录失败尝试，那是另一件事（本 story 不做，AC 也没要求）。

### AD-S13「加码必改 5 处」在本分支只能改到 4 处

第 5 处是「admin 预置角色的默认授予 + 种子迁移」，依赖 admin 主题的 `admin_roles` / `admin_role_permissions`（B.4），**本分支两张表都不存在**。
处置：**不要为了凑满 5 处而在本分支造一张角色表或一支种子迁移** —— 那会和 admin 主题的迁移撞车。正确做法是把它登记成显式待办（T4 最后一条），在 Completion Notes 里写清楚，合流时由 admin 侧或集成分支补上。AD-S13 的建议授予是「`bulk_edit` → 运营专员（`OPERATIONS`）」。
