# Story 3.1: @ 候选集

Status: review

## Story

As a 想在评论里叫上某个人的用户,
I want 输入 @ 之后看到的是我打过交道的人,
so that 我能一眼找到那个人，而不用在一堆陌生人里翻。

## Acceptance Criteria

**AC1 — 独立建表（AD-10）** `[L0]`
**独立建表**维护"最近互动过的人"，**不每次打开输入框现扫**评论与点赞记录。
迁移用时间戳版本号，表名带模块前缀。

**AC2 — 🔴 维护逻辑（本 story 的主体，不是附属）** `[L1]`
必须在实现中定死并写进完成说明：
- **写入时机**：随互动同步写，或经 `@Async` 异步写（二选一，定死）
- **裁剪策略**：每人保留最近 N 条（N ≥ 30，留冗余以应对拉黑排除后不足 30），超出即淘汰最旧的
- **表不得无界增长**
- 🔴 禁止引入定时清理中间件；裁剪走写入时顺手淘汰，或 `@Scheduled` 日扫

**AC3 — 候选口径** `[L1]`
取**评论过我 / 我评论过 / 赞过我的 / 与我互相回复对话过**的用户，**最近 30 人**。
**任一方向存在拉黑关系的双方互不出现**；判定走**既有统一读取口**。
已注销用户不进候选集。

**AC4 — 接口性能** `[L1]`
一次批量返回，**无 N+1**；响应足够快以支撑打字时的即时交互。

**AC5 — 🔴 范围边界** `[L0]`
**没有任何全局用户搜索能力**（搜索留在 1.6.0 未前移）。
候选集接口**不接受任意关键词查全库**。

## Dev Notes

### 🔴 为什么 AC2 是主体

story 标题写的是"候选集"，容易被理解成"写个查询就行"。实际上：
- 查询部分（AC3）很简单
- **难的是这张表怎么被喂饱、怎么不撑爆**

上一轮圆桌评审专门标出这条：AC 只写"不现扫"，反过来就是"要维护"，而维护逻辑当时一个字都没有。**别跳过 AC2 去做 AC3。**

### 异步写的既有范式

若选异步：用 Spring 原生 `@Async`（CLAUDE.md 护栏：异步只用 `@Async` + DB 状态机，**禁 MQ / 禁调度中间件**）。
若选定时裁剪：用 `@Scheduled`（既有先例见 CROSS-STORY F5 的定时推送）。

### 拉黑读取口

`com.tailtopia.social` 的 `UserHideRelationReader`。AD-7：四处共用同一出口，禁各写各的。

### 为什么保留 N ≥ 30 而不是正好 30

拉黑排除是在**查询时**做的。若表里正好只存 30 人，其中 3 个被拉黑，用户就只剩 27 个候选。留冗余（比如存 50）能保证排除后仍有 30 个可选。

### 🔴 AC2 —— 维护逻辑（本 story 的主体）

两条口径**定死如下**：

| | 定下来的做法 | 为什么 |
|---|---|---|
| **写入时机** | **随互动异步写**：`@Async` + `@TransactionalEventListener` 消费**既有**的 `ContentLikedEvent` / `ContentCommentedEvent` | 评论 / 点赞是热路径，而候选集晚半秒没人看得出来。AFTER_COMMIT 保证互动事务回滚时不留痕迹。**没有在 content 侧新增任何发布点，也不直读 content 的仓储** |
| **裁剪策略** | **写入时顺手淘汰**：每次 upsert 之后删掉该 owner 最新 **50** 条之外的 | 表的上界因此是**硬的**（行数 ≤ 用户数 × 50，与互动量无关）。定时任务意味着「两次扫描之间可以涨到任意大」，还多一个会挂掉的东西 |

🔴 **没有引入任何调度中间件**，连 `@Scheduled` 都没用（CLAUDE.md 护栏：异步只用 `@Async`）。

🔴 **为什么留 50 而不是正好 30**：拉黑排除是在**查询时**做的。表里正好只存 30 人时，
其中 3 个被拉黑就只剩 27 个候选。50 是留给拉黑 / 注销排除的冗余。一条测试断言
`KEEP_PER_OWNER > MAX_CANDIDATES`。

**⚠️ 互动的方向不是一律双向**（PRD §2.3 的口径原文）：
- **评论 → 双向**：我评论了他（我评论过）+ 我进他的候选（评论过我）；
- **二级回复 → 再多一对**：评论者 ↔ 被回复的一级评论作者，这就是「与我互相回复对话过」。
  少了它，在别人帖子下聊了半天的两个人互相 @ 不到 —— 而那恰恰是最需要 @ 的场景；
- **点赞 → 单向**：只有「赞过我的」，**没有「我赞过的」**。顺手写成双向的话，
  一个只会点赞、从不说话的人的候选集里会塞满他赞过的所有作者，而他跟那些人并没有"打过交道"。

### Completion Notes List

**已交付（L0 全绿）**

1. **独立建表**（AC1）：`mention_candidates`（模块前缀 `mention`），
   唯一键 `(owner_id, candidate_id)` + `CHECK owner_id <> candidate_id` +
   `(owner_id, last_interacted_at DESC, id DESC)` 复合索引（取数与裁剪共用同一把尺子）。
   ⚠️ 排序键是 `last_interacted_at` 而**不是** `created_at`：一个人反复与你互动应当一直排在前面。
2. **维护逻辑**（AC2）：见上一节。
3. **候选口径**（AC3）：最近 30 人；**任一方向存在隐藏关系的双方互不出现**（不分来源，
   拉黑与举报隐藏都算）；已注销不进候选。
   🔴 判定走**既有统一出口** `UserHideRelationReader` —— 为此在那个端口上**加了一个批量方法**
   `hiddenEitherWay(userId, others)`，而不是在 mention 模块自己写查询（AD-7 原话：
   四处共用同一个出口，禁各写各的）。
4. **无 N+1**（AC4）：一次取数只发**三条**查询，与候选人数无关 ——
   取候选 / 批量判拉黑 / 批量取昵称头像。一条测试直接断言这三个各调一次、
   且逐条的 `isHidden`/`isBlocked` 一次都不出现。
   新用户（没互动过）直接返回空表，**一次多余的查询都不发**。
5. **范围边界**（AC5）：`GET /api/v1/me/mention-candidates` **没有任何查询参数** ——
   不接受关键词、也不分页。一条反射测试钉住「服务方法只有 ownerId 一个形参」
   「端点上没有任何 `@RequestParam`」。**没有全局用户搜索**，搜索留在 1.6.0、未前移。
6. **注销级联**（D1/D2）：接进 `AccountDeletionService`，**两个方向都物理删** ——
   只删他自己那份的话，他还会继续出现在**别人**的 @ 候选里（点进去是「用户不存在」）。
   ⚠️ 这张表是派生物不是 UGC，所以是删行，不像场所评论那样只做匿名化。

**code-review 复审后修掉的（4 findings 全修）**

1. 🔴 **乱序到达会让排序键倒退**：写入走 `@Async` 线程池（默认 core=8），同一对
   (owner, candidate) 的两个事件完全可能乱序提交 —— 先到 10:00:05 的评论、后到 10:00:01 的点赞。
   无条件覆盖会把排序键推回过去，表现是一个刚跟你聊过的人在 @ 列表里莫名靠后，
   越过 50 条边界时甚至被当成"最旧的"淘汰。→ `DO UPDATE SET last_interacted_at = GREATEST(...)`。
2. 🔴 **二级回复的两对关系包在同一个容错块里**：第一对（评论者↔帖主）写失败时 lambda 直接中断，
   第二对**整个被跳过** —— 而那恰是「与我互相回复对话过」这条口径**唯一**的落点。→ 各包一层，并加用例。
3. **为一个不展示的字段多查一次库**：`findAuthorViews` 内部会为最多 50 个人查一次运营标签，
   而 @ 列表一行只有头像 + 昵称，**查完即丢**。→ 在 `AccountQueryService` 上加
   `findAuthorViewsWithoutTags`（javadoc 里写明「要展示标签就必须用另一个」），候选服务改用它。
4. **SecurityConfig 漏了角色限定**：落到 `anyRequest().authenticated()` 时，兽医 token 会进到
   controller 再被打成 **401** —— 而同类 `/me` 端点给的是 403，客户端把 401 当「token 过期」会直接
   强制登出。→ 加进 `.hasRole("USER")` 名单（与安全评审三轮 #1 留下的那条约定一致）。

**范围边界（有意不做）**

- **没有全局用户搜索**（AC5）—— 接口不接受关键词、不分页。
- **前端一行没写**：选择器与插入是 Story 3.2、展示与跳转是 3.3、通知是 3.4。
- **没有 `@Scheduled`、没有 MQ**（护栏）。
- **存量互动不回溯建表**：新表从上线那一刻开始积累。回溯扫历史 comments / content_likes
  是一次全表级的批处理，而候选集是"最近互动过的人" —— 等用户再互动一次就有了。
