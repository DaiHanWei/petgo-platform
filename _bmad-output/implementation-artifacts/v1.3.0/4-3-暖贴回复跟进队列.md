# Story 4.3: 暖贴回复跟进队列（入队 / 出队）

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`。
> **纯后端**：一支迁移 + 两个事件监听 + 一个 content 侧新事件。无页面（页面在 4-4）。

## Story

As a 平台，
I want 真实用户回复了虚拟账号的一级评论就自动生成一条待跟进项，回复被删则自动撤掉，
so that 运营不会漏掉「已读不回」。

## Acceptance Criteria

**AC1 · 表**
**Given** 迁移 `V<yyyyMMdd_HHmm>__init_warm_reply_followups.sql`
**Then** 建表见 Dev Notes 完整 SQL；部分唯一索引 `UNIQUE (virtual_comment_id) WHERE status='PENDING'` 保证同一虚拟评论只有一条待跟进项 `[L1]`
**And** 实体 `WarmReplyFollowup`、枚举 `FollowupStatus{PENDING,HANDLED}`、`HandledAction{REPLIED,READ}`；`ddl-auto=validate` 通过 `[L1]`

**AC2 · 入队**
**Given** `ContentCommentedEvent`（评论**转可见**时发布：机审 PASS 的 `approveComment`，或人工审核 approve）
**When** `parentAuthorId` 非空且该用户 `account_type='VIRTUAL'`，且 `commenterId` 对应用户 `account_type='REAL'`
**Then** 若无 PENDING 项 → 新建（`pending_reply_count=1`，`last_reply_id/at` = 该回复）；已有 → `pending_reply_count+1`、更新 `last_reply_*` `[L1]`
**And** 监听器 `@TransactionalEventListener(AFTER_COMMIT)` + 自身方法 `@Transactional(REQUIRES_NEW)`（既有通知事故的修法）`[L1]`
**And** 以下**不**入队：一级评论（`parentAuthorId` null）；回复者是虚拟账号；被回复者是真实用户；审核中 / 被拒的回复（事件本就不发）`[L1]`

**AC3 · 出队（D-19）**
**Given** 触发入队的真实回复被作者自删（`CommentService.delete`）或被运营下架（`takedownComment`）
**Then** 对应 PENDING 项 `pending_reply_count-1`；归零 → 删除该项（不留 HANDLED 记录）`[L1]`
**And** content 侧新增领域事件 `CommentRemovedEvent(commentId, postId, authorId, parentId, reason AUTHOR_DELETE|ADMIN_TAKEDOWN, at)`，在 `delete`（含级联软删的每条二级）与 `takedownComment` 成功路径发布；`rejectComment` / `restoreComment` 不发 `[L1]`
**And** 已 HANDLED 的项不受出队影响（历史保留）`[L1]`

**AC4 · 结构限制（D-35）**
**Then** 二级虚拟评论被回复不入队（两级结构下该回复的 `parentAuthorId` 是一级作者，不是虚拟账号）——单测钉住此行为，并在监听器注释说明 X-2 启用后再扩展 `[L0]`

**AC5 · 计数供给**
**Then** `WarmReplyQueueService.pendingCount()` 供待办中心角标聚合查询（Story 2.9 的 `GET /admin/nav/badges`）调用；4-4 页面用 `listPending / listHandled(30d)` `[L1]`

**AC6 · 日志与测试**
**Then** 监听器日志只记 id，不记评论正文 `[L0]`
**And** L1：入队 / 合并累加 / 不入队四种 / 出队减一与归零删除 / 二级虚拟不入队 `[L1]`

## Dev Notes

### 🔴 `ContentCommentedEvent.parentAuthorId` 的语义已核实——正是我们要的

`CommentService.publishCommented`：`parentAuthorId = c.isTopLevel() ? null : comments.findById(c.getParentId()).authorId`。二级回复挂在一级下，`parentId` 就是那条一级，所以 **parentAuthorId = 被回复的一级评论作者**。虚拟账号发的一级评论被真实用户回复 → `parentAuthorId` = 虚拟账号 id → 入队条件成立。

同时这也证实 D-35 的限制：虚拟账号发的**二级**被回复时，回复的 `parentId` 仍是那条一级（`createReply` 的「归并到一级父」逻辑），`parentAuthorId` 是一级作者，识别不出。别试图在监听器里「猜」。

### 🔴 事件只在评论**转可见**时发

`ContentCommentedEvent` 由 `approveComment`（机审 PASS 路径的 `CommentModerationListener`、或 A1 人工通过）发布；创建时只发 `CommentSubmittedEvent`。所以审核中的回复不会入队；机审拒绝的永远不入队——与 D-4 一致，不需要额外过滤审核态。

### 🔴 现状**没有**评论删除 / 下架事件——本 story 要在 content 模块新增一个

`CommentService.delete` 与 `takedownComment` 都不发事件（`ContentRemovedEvent` / `ContentUnavailableEvent` 是**帖子**级的）。出队必须有钩子，最小改动是加 `CommentRemovedEvent` 并在两处发布。这是本 story 唯一碰 content 模块的地方，不改任何既有行为，只多两行 `publishEvent`。范式参考 `ContentUnavailableEvent` 的注释（为什么不复用别的事件）。

`restoreComment`（下架后恢复）不重新入队：恢复的是「已存在的回复」，运营早看过；如产品认为要回来，另开需求。

### 表结构（完整 SQL）

```sql
-- V<ts>__init_warm_reply_followups.sql —— V1.3.0 AB-20A 暖贴回复跟进（AD-6）
CREATE TABLE warm_reply_followups (
    id                  BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    virtual_comment_id  BIGINT       NOT NULL REFERENCES comments (id) ON DELETE CASCADE,
    post_id             BIGINT       NOT NULL,
    virtual_user_id     BIGINT       NOT NULL,          -- 被回复的虚拟账号（users.id，account_type=VIRTUAL）
    pending_reply_count INT          NOT NULL DEFAULT 1 CHECK (pending_reply_count >= 0),
    last_reply_id       BIGINT,                          -- 最近一条触发入队的真实回复
    last_reply_at       TIMESTAMPTZ,
    status              VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
    handled_by          BIGINT,                          -- admin_accounts.id
    handled_at          TIMESTAMPTZ,
    handled_action      VARCHAR(16),                     -- REPLIED | READ
    handled_comment_id  BIGINT,                          -- REPLIED 时运营以虚拟身份发出的回复 id
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT ck_warm_reply_status CHECK (status IN ('PENDING', 'HANDLED')),
    CONSTRAINT ck_warm_reply_action CHECK (handled_action IS NULL OR handled_action IN ('REPLIED', 'READ'))
);
-- 同一虚拟评论只允许一条待跟进项（多条真实回复合并累加）
CREATE UNIQUE INDEX uq_warm_reply_pending ON warm_reply_followups (virtual_comment_id) WHERE status = 'PENDING';
CREATE INDEX ix_warm_reply_status_time ON warm_reply_followups (status, last_reply_at DESC);
COMMENT ON TABLE warm_reply_followups IS '暖贴回复跟进队列：虚拟一级评论收到真实回复即入队；回复被删/下架减计数归零即删；处理后 HANDLED 保留 30 天可回看';
```

`ON DELETE CASCADE` 挂在 `comments(id)`：评论表是软删，物理删几乎不发生，留着只为一致性。

### 监听器伪码

```java
@Component
public class WarmReplyEnqueueListener {
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void onCommented(ContentCommentedEvent e) {
        if (e.parentAuthorId() == null) return;                 // 一级评论
        queue.enqueueIfWarmReply(e);                             // REQUIRES_NEW 内判 VIRTUAL/REAL 并 upsert
    }
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void onRemoved(CommentRemovedEvent e) {
        if (e.parentId() == null) return;
        queue.onReplyRemoved(e.commentId(), e.parentId());       // REQUIRES_NEW：-1，归零删行
    }
}
// WarmReplyQueueService.enqueueIfWarmReply（@Transactional(REQUIRES_NEW)）
//   User parent = users.findById(e.parentAuthorId()); User commenter = users.findById(e.commenterId());
//   if (parent.accountType != VIRTUAL || commenter.accountType != REAL) return;
//   jdbc: INSERT INTO warm_reply_followups (virtual_comment_id, post_id, virtual_user_id, last_reply_id, last_reply_at)
//         VALUES (:parentCommentId, :postId, :virtualUserId, :commentId, :at)
//         ON CONFLICT (virtual_comment_id) WHERE status='PENDING'
//         DO UPDATE SET pending_reply_count = warm_reply_followups.pending_reply_count + 1,
//                       last_reply_id = EXCLUDED.last_reply_id, last_reply_at = EXCLUDED.last_reply_at, updated_at = now();
```
⚠️ 事件里没有 `parentCommentId`（只有 `parentAuthorId`）——需要 `comments.findById(e.commentId()).getParentId()` 取一次，或给 `ContentCommentedEvent` 加一个可空字段 `parentCommentId`（推荐后者，record 加字段需同步改 `publishCommented` 与 notify 侧的构造调用点；测试里 `new ContentCommentedEvent(` 调用点也要补）。两种都可，Completion Notes 写明选了哪种。

### 为什么 AFTER_COMMIT + REQUIRES_NEW

`ContentNotifyListener` 是同步 `@TransactionalEventListener`，`NotificationService.send` 必须 `REQUIRES_NEW` 才能落库——项目 07 月「通知只涨角标不进通知中心」事故的修法（memory：notify-after-commit-tx-swallow-bug）。本监听器同款：AFTER_COMMIT 阶段外层事务已提交、无环境事务，不开新事务写入会静默丢。
