# Story 3.2: 预聚合长表与 18 项指标查询（AD-2）

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（Flyway 时间戳版本号、`ddl-auto=validate`、`mvn -B clean package`）。
> 纯后端：1 支迁移 + 实体/仓储 + 18 个指标查询类 + parity 测试。**不含跑批（3-3）与页面（3-4）**。

## Story

As a 运营，
I want 18 项指标每天各算一次存下来，帖子类 9 项同时存「真实用户」和「含种子」两个口径，
so that 看板取数快、历史数字不变、任一天都能和口径表对上。

**AC2 · 18 个 key 枚举**

**AC3 · 每指标一个查询类**

**Then** 18 个实现类各一，全部原生 SQL，切日一律 `(<ts> AT TIME ZONE 'Asia/Jakarta')::date`，日期参数为 WIB 自然日；对 `dualScope=false` 的指标传 `REAL` 与 `ALL` 结果相同或抛 `IllegalArgumentException`（统一：非双口径指标只接受 ALL）`[L0]`
**And** 「真实用户」口径统一引用 `SyntheticAccountSql.EXCLUDE_WHERE`（3-1），帖子类 REAL 口径 = **帖子作者为真实用户 且 点赞/评论发起者为真实用户** `[L0]`
**And** 「累计注册用户数」key 为 `cumulative_users`（D-16 改名），「新增建档用户数」按人去重（D-28）`[L0]`

**AC4 · 口径与参考 SQL 相等（Parity）**

**And** 9 项 REAL 口径在「样本中无合成账号」时与 ALL 相等、在「有合成账号」时严格小于等于 ALL `[L1]`

**AC5 · 不物化、不写库**

## Dev Notes

### 口径表与 SQL 草案（权威：PRD §1 ①-a，原样带入；SQL 由参考 SQL 改写）

通用：`D` = 目标 WIB 自然日；`day(ts) := (ts AT TIME ZONE 'Asia/Jakarta')::date`；`REAL_U` := `SyntheticAccountSql.EXCLUDE_WHERE`（别名 `u`）；可见帖 `p.status='PUBLISHED' AND p.deleted_at IS NULL`；有效评论 `c.deleted_at IS NULL`；得分 = 赞×1 + 评×5。

| # | key | 口径（PRD） | SQL 草案（ALL；REAL 见备注） |
|---|---|---|---|
| 1 | `new_users` | 当日注册的真实用户数 | `SELECT count(*) FROM users u WHERE day(u.created_at)=:d AND REAL_U` |
| 2 | `cumulative_users` | 截至当日 24:00 累计真实用户数（原「总安装用户数」，D-16） | `… WHERE day(u.created_at)<=:d AND REAL_U` |
| 3 | `posting_users` | 当日发布可见帖子的去重作者数（双口径） | ALL：`SELECT count(DISTINCT p.author_id) FROM content_posts p WHERE day(p.created_at)=:d AND 可见`；REAL：`JOIN users u ON u.id=p.author_id AND REAL_U` |
| 4 | `new_posts` | 当日发布的可见帖子数（双口径） | 同上 `count(*)` |
| 5 | `new_pet_owners` | 当日**首次**建档的去重用户数（D-28） | `SELECT count(*) FROM (SELECT owner_id, min(created_at) f FROM pet_profiles GROUP BY owner_id) x WHERE day(x.f)=:d`（参考 SQL 的按档案计作废） |
| 6 | `cumulative_pet_owners` | 截至当日至少有一个档案的去重用户数 | `SELECT count(DISTINCT owner_id) FROM pet_profiles WHERE day(created_at)<=:d` |
| 7 | `diary_pet_owners` | 当日发布 `GROWTH_MOMENT` 可见帖且本人有档案的去重用户数 | `count(DISTINCT p.author_id) … p.type='GROWTH_MOMENT' AND EXISTS(pet_profiles pp WHERE pp.owner_id=p.author_id)` |
| 8 | `interacted_posts` | 当日收到 ≥1 赞或有效评论的去重帖子数（双口径） | `count(DISTINCT post_id)` over `interactions_raw`（likes ∪ comments deleted_at IS NULL）`WHERE day(created_at)=:d`；REAL：帖子作者 REAL 且互动者 REAL |
| 9 | `silent_posts` | 当日发布的可见帖中当日 0 赞 0 评的帖子数（双口径） | `count(*) FROM content_posts p WHERE day(created_at)=:d AND 可见 AND NOT EXISTS(interactions ir WHERE ir.post_id=p.id AND day(ir.created_at)=:d)`；REAL 同上加作者/互动者过滤 |
| 10 | `engagement_score` | 当日新产生 赞×1 + 有效评论×5（双口径） | `SUM(CASE source WHEN 'like' THEN 1 ELSE 5 END)` over interactions `WHERE day=:d` |
| 11 | `new_posts_score` | 当日发布可见帖各自截至当日 24:00 累计得分之和（双口径） | 参考 SQL `post_score_by_day` LATERAL，把 `::date` 换 `day()` |
| 12 | `all_posts_avg_score` | 截至当日已发布全部可见帖各自累计得分平均（双口径） | 参考 SQL `all_posts_avg_score_by_day`；`AVG … FILTER (WHERE p.id IS NOT NULL)`；空集返回 NULL → 存 0 并在 3-3 记「无样本」 |
| 13 | `interacted_posts_avg_score` | 当日有互动的帖子按各自当日新增得分取平均（双口径） | 参考 SQL `daily_interaction_avg_by_day` |
| 14 | `engagement_score_all_time` | 截至当日 24:00 全部历史 赞×1 + 有效评论×5（双口径） | `(count likes ≤d)*1 + (count comments deleted_at IS NULL ≤d)*5` |
| 15 | `paying_users_cash` | 当日 `payment_intents.status='PAID'`（到账时刻 = `updated_at`）的去重真实用户数 | `count(DISTINCT pi.user_id) FROM payment_intents pi JOIN users u … WHERE pi.status='PAID' AND day(pi.updated_at)=:d AND REAL_U` |
| 16 | `payments_cash` | 同 15 笔数 | `count(*)` |
| 17 | `paying_users_incl_pawcoin` | 当日 consult_orders.paid_at ∪ ai_consult_orders(COMPLETED).paid_at ∪ id_card_hd_purchases.purchased_at ∪ PawCoin 充值到账 的去重真实用户数 | 参考 SQL `spend_events` UNION ALL 四段，每段 JOIN users 加 REAL_U，`count(DISTINCT user_id)` |
| 18 | `payments_incl_pawcoin` | 同 17 笔数；已退款订单当日仍计 | `count(*)`；不加 `NOT IN ('REFUNDING','REFUNDED')` |

REAL 口径定义（D-29）：**帖子作者 ∈ 真实用户 且 互动发起者 ∈ 真实用户**；对 #11/#12 的 LATERAL 累计得分，REAL 口径下点赞/评论子查询各自再 `JOIN users u2 ON u2.id = cl.user_id / cm.author_id AND REAL_U(u2)`。

### 🔴 切日必须显式 WIB（OQ-B3）

参考 SQL 全部 `x::date`，含义随连接时区漂移。全部查询类统一写 `(ts AT TIME ZONE 'Asia/Jakarta')::date`，常量抽到 `MetricSql.DAY(expr)` 小工具；`LocalDate` 参数就是 WIB 日。`ScheduleWindow.WIB` 已有 `ZoneId.of("Asia/Jakarta")`，Java 侧复用。

### 🔴 两处参考 SQL 与现网 schema 的差异（拆 story 时核实）

1. **`comments.moderation_status` 列已存在**（参考 SQL 写作时 stag 无此列，故只过滤 `deleted_at`）。本 story 为保 parity **仍只按 `deleted_at IS NULL`**；「审核中 / 被拒评论是否应计入互动」列为待拍板（见文末问题 1），拍板后改一处常量 `VALID_COMMENT_WHERE`。
2. **`users.account_type` 已存在**，真实用户判定改走它（3-1），前缀判定退为兜底；参考 SQL 的前缀判定与之在现网等价（3-1 parity 保证）。

### 🔴 #5 有意偏离参考 SQL

参考 SQL `profiles_by_day` 数的是 `pet_profiles` 行数（一人多档多计）；D-28 拍板按人去重。Parity 测试对 #5 单独断言，不与参考 SQL 比。`pet_profiles.owner_id` 注释「一个用户至多一条档案」——若真如此两者相等，但仍按 D-28 写法实现，防将来放开多档。
