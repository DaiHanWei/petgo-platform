# Story 1.1: 账号变更版本号与自动踢重登（AD-1）

Status: review

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（后端→前端→联调、AC 标 L0/L1/L2、Flyway 时间戳版本号、`mvn -B clean package`）。
> 本 story **只有后端 + 一处登录页文案**，无 App 端改动。

## Story

As a 超级管理员，
I want 我改了某个账号的邮箱、角色、权限或把它停用后，对方正在用的后台立刻失效，
so that 账号移交或收权不会留下几个小时的空窗。

## Acceptance Criteria

**AC1 · 版本号列**
**Given** `admin_accounts` 无版本号列
**When** 执行迁移 `V<yyyyMMdd_HHmm>__add_admin_accounts_security_version.sql`（取创建时刻）
**Then** 新增 `security_version INT NOT NULL DEFAULT 0`，存量全为 0；实体 `AdminAccount` 映射该列 `[L1]`

**AC2 · 变更即 +1**
**Given** 账号 A
**When** 对 A 执行 停用 / 改岗位角色 / 改账号级权限（`deactivate` / `changeRole` / `updatePermissions`）且**确实发生了变更**（幂等 no-op 不加）
**Then** 同一事务内 A 的 `security_version` +1 `[L1]`
**And** 服务层暴露 `bumpSecurityVersion(accountId)` 供后续 story 调用（1.3 换绑、1.5 角色模板改权限）`[L0]`
**And** 重新激活（`reactivate`）**不**加版本号（对方本来就登不进）`[L1]`

**AC3 · 登录时快照进会话**
**Given** 两条登录路径（紧急账密 formLogin、Lark OAuth 回调）都经 `AdminUserDetailsService.loadByEmail`
**When** 构造 `AdminUserDetails`
**Then** principal 携带登录时刻的 `securityVersion`，随 `HttpSessionSecurityContextRepository` 存入会话 `[L1]`

**AC4 · 每请求比对，不等即踢**
**Given** A 已登录，随后被 AC2 任一操作 +1
**When** A 发起任何 `/admin/**` 请求（`/admin/login`、`/admin/oauth/**` 除外）
**Then** `AdminSessionGuardFilter` 在现有「重查账号是否 ACTIVE」的同一次查库里比对版本号：不等 → `session.invalidate()` + 清 SecurityContext + 302 `/admin/login?relogin` `[L1]`
**And** 不新增第二次查库 `[L0]`
**And** 版本号相等的账号不受影响，无额外跳转 `[L1]`
**And** 停用仍走原 `?expired` 分支（先判 ACTIVE 再判版本，不改既有语义）`[L1]`

**AC5 · 登录页提示三语**
**Given** 跳转带 `?relogin`
**When** 渲染 `login.html`
**Then** 显示 `admin.login.relogin`（zh：账号信息已变更，请重新登录；en / id 同步），样式同 `?expired` 行 `[L2]`
**And** 三包 key 集合仍相等 `[L0]`

**AC6 · 不重算权限（D-2）**
**Given** 只有角色模板权限变化而账号自身未变（Story 1.5 的场景）
**Then** 本 story 的过滤器不重算权限、不主动踢人；由 1.5 调 `bumpSecurityVersion` 触发 `[L0]`

**AC7 · 回归**
**Then** 既有 `AdminSessionGuardFilterTest`、`AdminAccountManagementIntegrationTest`、`AdminAccountServiceTest` 全绿；`mvn -B clean package` 通过 `[L0/L1]`

## Dev Notes

### 🎯 这条 story 是全版本的第一块横切件，后面三处会直接调它

- **1.3 换绑邮箱**：换绑成功后调 `bumpSecurityVersion(accountId)`，旧持有人下次请求被踢。
- **1.5 角色配置页**：角色模板改权限后，对该角色下全部账号批量 bump。
- **1.6 账号页改角色**：走 `changeRole`，本 story 已覆盖。
所以 `bumpSecurityVersion` 必须是**公开、独立事务可复用**的方法，不要写成只在 `deactivate` 里的内联代码。

### 🔴 为什么把版本号放进 principal 而不是 session attribute

现状两条登录路径都最终经 `AdminUserDetailsService.loadByEmail` 构造 `AdminUserDetails`（`SecurityConfig.adminFilterChain` 的 formLogin 用 `loadUserByUsername`；`AdminLarkLoginController` 回调用 `larkAuth.authenticate` → 同一 service），然后由 `HttpSessionSecurityContextRepository` 存进 HttpSession。**principal 是两条路径唯一的汇合点**，在这里加字段一次改对两边；若用 session attribute 要在 formLogin successHandler 和 Lark callback 各写一次，容易漏。

### 🔴 过滤器现状与本 story 的改动边界

`AdminSessionGuardFilter`（`admin/account/web/`）**已经**每请求 `adminAccounts.findById(admin.getAdminAccountId())` 查一次库，只判 `status==ACTIVE`。本 story 在同一个 `Optional<AdminAccount> current` 上多比一个 int，**零新增查询**（AC4 明写）。它不是 `@Component`，由 `SecurityConfig` 用 `new AdminSessionGuardFilter(adminAccounts)` 手工装进 admin 链（`addFilterBefore(..., AuthorizationFilter.class)`）——构造器签名不要改，否则 `SecurityConfig` 也要改。

判序：**先 ACTIVE 再版本**。停用本身也会 bump（AC2），但停用应继续走 `?expired`（既有语义与既有测试 `invalidatesSessionWhenAccountDisabled`），所以 ACTIVE 判断放前面。

### 🔴 D-2：本 story 不重算权限

产品拍板「权限重新登录后生效」。过滤器**只比对版本号**，不去重新 `resolvePermissions`。被踢后重登，权限自然是新的。不要在过滤器里做任何权限刷新。
