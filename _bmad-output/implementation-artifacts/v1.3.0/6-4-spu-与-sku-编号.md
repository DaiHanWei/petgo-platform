# Story 6-4: SPU / SKU 编号

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（Flyway 时间戳版本号、`mvn -B clean package`）。
> 🔴 **前置：admin 主题 Epic 10 完成**（SD-16，第二批整组前置）。本 story 只在后台页面上**加两个只读列**，页面结构照 Epic 10 重构后的模板。
> 本 story **纯后端 + 一支带存量回填的迁移**，无 App 改动 —— 🔒 **编号不对外，App 永远看不到它**。
> 与 **Story 6-1 可并行**：两支迁移都动 `shop_products`，各取自己的创建时刻做版本号即可（`out-of-order` 全环境常开）。

## Story

As a 运营，
I want 商品和规格有我能读、能填进 Excel、能拿去搜的编号，
so that 我批量更新时能指名道姓，也能在几百个 SKU 里按编号找到货。

## Acceptance Criteria

**AC1 · 两列落库，格式与长度合规** `[L0/L1]`
**Given** `shop_products` 与 `shop_skus` 今天没有任何编号列
**When** 执行迁移 `V<yyyyMMdd_HHmm>__add_shop_spu_sku_no.sql`（取创建时刻，E7）
**Then** `shop_products.spu_no VARCHAR(16)`，回填后置 `NOT NULL` + `uq_shop_products_spu_no UNIQUE (spu_no)` `[L1]`
**And** `shop_skus.sku_no VARCHAR(24)`，回填后置 `NOT NULL` + `uq_shop_skus_sku_no UNIQUE (sku_no)` `[L1]`
**And** 两列都有 `COMMENT ON COLUMN`，写明「🔒 **仅后台与 Excel 可见，不进任何面向用户的接口**」与「运营不可改」`[L0]`
**And** 实体字段标 `updatable=false`：`ShopProduct` 加 `@Column(name="spu_no", nullable=false, length=16, updatable=false)`；`ShopSku` 加 `@Column(name="sku_no", nullable=false, length=24, updatable=false)` —— 🔴 与 `publicToken` 的既有写法（`ShopProduct.java:37` / `ShopSku.java:34`）逐字对齐 `[L0]`
**And** `ddl-auto=validate`：`VARCHAR(16)` ↔ `length=16`、`VARCHAR(24)` ↔ `length=24`，**不得错位** `[L1]`

**AC2 · 生成规则：专用序列 + 格式化，🔴 不用主键 id** `[L0]`
**Given** AD-S2 与 AD-S3 同一条理由：**不给外部推算余地，即便当前不外露**
**Then** 新建序列 `CREATE SEQUENCE seq_shop_spu_no START 1 INCREMENT 1;`（范式 `V74__alter_pet_profiles_serial.sql:14`）`[L0]`
**And** SPU 号 = `"SPU-" + String.format("%06d", nextval)`，例 `SPU-000123`（长度 10 ≤ 16）`[L0]`
**And** 🔴 **绝不用 `shop_products.id` 拼号**（`"SPU-" + String.format("%06d", p.getId())` 是本 AC 要禁的写法）。理由与 4-3 的订单号一致：id 拼出来的号**可枚举**，今天不外露不等于明天不外露，而一旦发出去就收不回来 `[L0]`
**And** 序列超过 999999 时 `%06d` 会自然变成 7 位（`String.format` 不截断），长度仍 ≤ 16 —— **这是可接受的**，写进注释 `[L0]`
**And** 单测断言：连续取 100 个号全不相同、全匹配 `^SPU-\d{6,}$`、**不包含任何等于某商品 id 的可推算关系**（构造两个 id 相差 1 的商品，断言它们的 `spu_no` 数值差**不**恒为 1 —— 🔴 这条要在「序列与 id 已经错开」的前提下测，构造方式见 Dev Notes）`[L0]`

**AC3 · SKU 号 = `<spu_no>-%02d`，同商品内序号** `[L0/L1]`
**Given** AD-S2：SKU 为 `<spu_no>-%02d`（同商品内序号）
**Then** SKU 号形如 `SPU-000123-01`（长度 13 ≤ 24）`[L0]`
**And** 🔴 **序号取「该商品现有 SKU 的最大后缀 + 1」，不是 `countByProductId + 1`** —— 后者在「删过 SKU 再新增」时必然撞号。`ShopSkuRepository:15` 确实有 `countByProductId(long)`，**别用它做这件事**。今天生产代码没有删 SKU 的路径（零命中），但规则不该依赖这个事实 `[L0]`
**And** 序号从 **01** 起（不是 00）`[L0]`
**And** 🔴 序号超过 **99** 时抛明确异常（带商品的 `spu_no`，不打印候选号），**不静默溢出成 `100`** —— `%02d` 对 100 会输出 `100`，长度仍合法但破坏了「两位」的口径。`VARCHAR(24)` 容得下三位，**是否放宽格式由产品决定，本 story 先抛异常**（在 Completion Notes 登记为开放项）`[L0]`
**And** 唯一索引 `uq_shop_skus_sku_no` 是**兜底报错**，不是重试机制 —— 🔴 Postgres 里唯一约束冲突会让当前事务进入 aborted 状态，同一事务内重试必然再失败（4-3 的成文教训）`[L0]`
**And** 集成测试：同一商品连续建 3 个 SKU → `-01` / `-02` / `-03`；两个不同商品的 SKU 后缀互不干扰 `[L1]`

**AC4 · 运营不可改** `[L0/L1]`
**Given** SHOP-FR-06「系统自动生成、**运营不可修改**」
**Then** 实体字段 `updatable=false`（AC1 已覆盖）—— 🔴 即便有人把值塞进实体，Hibernate 的 UPDATE 语句里也**不会带这一列** `[L1]`
**And** `ShopProductForm` / `ShopSkuForm` **不新增编号字段**（后台表单根本收不到这个值）`[L0]`
**And** 后台商品表单页把编号渲染成**只读文本**（不是 `<input readonly>`，是纯文本 + 复制按钮），并注明「系统生成，不可修改」`[L0]`
**And** 集成测试：构造一个带 `spuNo` 的表单提交 → 库里的值**不变**（证明不是靠前端挡的）`[L1]`

**AC5 · 存量回填 + 序列起点，同一支迁移内** `[L0/L1]`
**Given** 线上已有商品与 SKU
**When** 迁移执行完
**Then** 按 `id` **升序**回填 `spu_no`：第 1 个商品 `SPU-000001`、第 2 个 `SPU-000002`…（🔴 **按 id 升序是为了让编号与上架时间同序**，运营看编号就知道哪个先上的）`[L1]`
**And** 按 `(product_id, id)` 升序回填 `sku_no` = `<该商品的 spu_no>-01/02/…` `[L1]`
**And** 🔴 **序列起点设为回填后的最大值 + 1**：`SELECT setval('seq_shop_spu_no', <回填的最大序号>, true);` —— 漏了这一步，迁移后建的第一个商品会拿到 `SPU-000001` 并**撞唯一索引**，表现为「上线后第一次新建商品报 500」`[L1]`

## Dev Notes

### 迁移回填的参考实现

```sql
-- ③ 回填 spu_no：按 id 升序，编号与上架时间同序
WITH numbered AS (
    SELECT id, row_number() OVER (ORDER BY id) AS rn FROM shop_products
)
UPDATE shop_products p
SET spu_no = 'SPU-' || lpad(n.rn::text, 6, '0')
FROM numbered n
WHERE p.id = n.id;

-- ④ 回填 sku_no：按 (product_id, id) 升序，分组编号
WITH numbered AS (
    SELECT s.id,
           p.spu_no,
           row_number() OVER (PARTITION BY s.product_id ORDER BY s.id) AS rn
    FROM shop_skus s
    JOIN shop_products p ON p.id = s.product_id
)
UPDATE shop_skus s
SET sku_no = n.spu_no || '-' || lpad(n.rn::text, 2, '0')
FROM numbered n
WHERE s.id = n.id;

-- ⑤ 🔴 序列起点 = 回填后的最大序号。漏了这一步：迁移后新建的第一个商品拿到 SPU-000001，
--    撞 uq_shop_products_spu_no，表现为「上线后第一次新建商品报 500」。
--    ⚠️ 空表时 COUNT(*)=0，而序列最小值是 1 ⇒ 用 is_called=false 的写法避开。
SELECT setval('seq_shop_spu_no', (SELECT COUNT(*) + 1 FROM shop_products), false);
```

`V92__alter_id_card_hd_purchases_per_card.sql:14` 已经在迁移里用过 `nextval('pet_serial_seq')`，**序列在迁移里可用不是新事**。这里用窗口函数而不是 `nextval` 回填，是因为窗口函数能保证「按 id 升序连续编号」，而 `nextval` 的取号顺序依赖行扫描顺序（不保证）。

### AC2 最后一条断言怎么构造

「不包含任何等于某商品 id 的可推算关系」这条听起来玄，实测方式很朴素：

1. 迁移后序列已 `setval` 到「存量商品数 + 1」；
2. 测试里先建 1 个商品（拿到号 N），再**直接删一行**或**建一个不走 service 的行**，让 id 与序列错开；
3. 再建 1 个商品，断言 `spu_no` 的数值 - 上一个的数值 == 1，而 `id` 的差 != 1。

如果实现里偷偷用了 `id`，这条会红。**实施时确认**能否在当前测试基建里构造 id 跳号（`shop_products.id` 是 IDENTITY，删一行即可跳）。构造不出来就退而求其次：**用变异验证代替** —— 把生成器改成 `"SPU-" + format(id)`，`ShopProductNoIntegrationTest` 的「新建商品号不撞存量」必须变红（因为存量已占 1..N，而新商品 id 也从 N+1 起，实际上不会撞）。⚠️ **退而求其次的这条较弱**，在 Completion Notes 里如实写明用了哪种。

### 为什么不用主键 id（与 AD-S3 同一条理由）

4-3 把订单号从 `TOKO-yyyyMMdd-%06d`（id 零填充）改成随机段，理由是**可枚举**。SPU 号今天不外露，但：

- 「不外露」是一个**当前的实现选择**，不是一个数据库层的约束；7-x 的 Excel 导出、9-1 的搜索、将来某个「商品分享」都可能把它带出去；
- 一旦带出去，`SPU-000123` 就直接告诉外人**平台一共上过多少商品** —— 这是经营数据；
- 用序列的成本是**一行 `CREATE SEQUENCE` + 一次 `nextval`**，几乎为零。

所以这里不做「等需要了再改」的权衡：改号的成本（存量全部换号、运营记的号全废）远大于现在多写一行。

### SKU 后缀为什么不用 `countByProductId + 1`

`ShopSkuRepository:15` 有现成的 `countByProductId(long)`，看起来正好。但：

| 场景 | count+1 | max+1 |
|---|---|---|
| 建 3 个 SKU | 01/02/03 ✅ | 01/02/03 ✅ |
| 删掉 `-02` 再建一个 | count=2 ⇒ 生成 `-03`，**撞已有的 `-03`** ❌ | max=03 ⇒ `-04` ✅ |

今天生产代码**没有删 SKU 的路径**（`skus.delete*` 全仓零命中），所以 count+1 今天不会出事。**但这个事实随时可能变**（7-x 的批量操作、将来的规格下线），而出事的形态是「新建 SKU 报 500」，排查成本远高于当初多写一个 `max` 查询。
