# Story 1.4: 角色-权限表与预置角色迁移（AD-4 方案 A）

Status: ready-for-dev

> 自包含 story，可本地或云端 L0 执行。与用户沟通用中文。执行纪律见根 `CLAUDE.md`（Flyway 时间戳版本号、DDL 与数据迁移分文件、`mvn -B clean package`）。
> 本 story **纯后端，无页面**：两支迁移 + 实体/Repository + 权限解析改造。用户可见行为**零变化**——这是本 story 的核心验收。角色配置页在 1-5，账号页接入在 1-6。
> **依赖 1-1**：不直接用版本号，但后续 1-5 会在改角色权限时批量 bump；本 story 要把「按角色查账号」的 Repository 方法准备好。

## Story

As a 平台，
I want 运营专员、发货专员、客服、财务四个岗位的权限从代码搬进数据库，账号登录时按表解析，
so that 后续角色配置页能让运营自助改权限，而现有账号行为一丝不变。

## Acceptance Criteria

**AC1 · DDL 迁移**
**When** 执行 `V<yyyyMMdd_HHmm>__init_admin_roles.sql`
**Then** 建 `admin_roles`、`admin_role_permissions`，`admin_accounts` 加 `role_id BIGINT NULL REFERENCES admin_roles(id) ON DELETE RESTRICT` + 索引；CHECK 全集 `role_type IN ('SYSTEM','CUSTOM')` `[L1]`
**And** 实体 `AdminRoleEntity`（🔴 不能叫 `AdminRole`，与枚举撞名）、`AdminRolePermission`、`RoleType` 枚举；`AdminAccount` 加 `roleId` 字段（`Long`，可空）；`ddl-auto=validate` 通过 `[L1]`

**AC2 · 数据迁移（独立文件）**
**When** 执行 `V<yyyyMMdd_HHmm>__seed_admin_roles.sql`（时间戳晚于 AC1）
**Then** 插入四行 SYSTEM 角色：`OPERATIONS` / `FULFILLMENT` / `SUPPORT` / `FINANCE`，`name_key` = `role.<CODE>`（复用既有三语 key），`name` 填中文兜底 `[L1]`
**And** 权限码按**本 story Dev Notes 抄自 `AdminRole.java` 的清单**逐条灌入 `admin_role_permissions`（OPERATIONS 19 条 / FULFILLMENT 5 条 / SUPPORT 15 条 / FINANCE 15 条，共 54 行）`[L1]`
**And** 存量账号回填：`UPDATE admin_accounts a SET role_id = r.id FROM admin_roles r WHERE a.role = r.code`；`SUPER_ADMIN` / `OPS_MANAGER` / `CUSTOM` 账号 `role_id` 保持 NULL `[L1]`
**And** 🛡 测试断言：迁移后表中四个角色的码集合 == 迁移前 `AdminRole.<X>.permissionCodes()` 集合，逐位相等（`AdminRoleSeedParityTest`）`[L1]`

**AC3 · 解析顺序**
**Given** `AdminUserDetailsService.resolvePermissions(AdminAccount a)`
**Then** 顺序：`accountType == SUPER_ADMIN` 或 `role == null` → 空集（隐式全权）；`role == OPS_MANAGER` → 读枚举 `permissionCodes()`（**保留不迁移**，D-13）；`role == CUSTOM` → 读 `admin_account_permissions`（现状不动）；其余（`role_id != null`）→ 读 `admin_role_permissions WHERE role_id = a.roleId` `[L1]`
**And** 🛡 `role_id` 为 NULL 且 `role` 是四个已迁移值之一（异常数据）→ 空集 + `warn` 日志（不记邮箱），不抛异常、不静默给权限 `[L1]`
**And** 四类账号（OPERATIONS / FULFILLMENT / SUPPORT / FINANCE）迁移前后 `loadByEmail` 得到的 `getAuthorities()` 集合逐位相等（回归测试）`[L1]`

**AC4 · 枚举收敛**
**Then** `AdminRole` 枚举保留全部七个值（`role` 列 CHECK 与存量数据依赖它们），但 OPERATIONS / FULFILLMENT / SUPPORT / FINANCE 四个值的 `permissionCodes` 列表**清空**并加注释「权限以 `admin_roles` 表为准（Story 1.4）」；`isTemplated()` 语义不变（仍 `!= CUSTOM`）`[L0]`
**And** `AdminAccountService.effectivePermissions`（列表回显）与 `createAccount` / `changeRole` 中所有读 `role.permissionCodes()` 的地方改为经同一个 `RolePermissionResolver`（新类，`admin/roles/service/`）取码，避免两套真相 `[L1]`
**And** `AdminRole.allReferencedCodes()` 的 L0 自检测试同步改为「表 seed 的码 ⊆ `AdminPermissions.ALL`」 `[L0]`

**AC5 · 新权限码与不预授予**
**Then** `AdminPermissions` 新增 `PLACE_MANAGE = "place.manage"`、`COMMENT_VIRTUAL_POST = "comment.virtual_post"`，加入 `GROUPS.edit`（进 `ALL` 与勾选区）`[L0]`
**And** 🛡 seed 迁移**不**把这两个码授予任何预置角色（超管隐式拥有；运营需要时在 1-5 角色页勾选）`[L1]`

**AC6 · Repository 为 1-5 备好**
**Then** `AdminAccountRepository.findByRoleId(Long roleId)` / `countByRoleId(Long roleId)`；`AdminRoleRepository.findByCode`、`findAllByOrderByRoleTypeAscIdAsc`；`AdminRolePermissionRepository.findByRoleId`、`deleteByRoleId` `[L0]`

**AC7 · 回归**
**Then** `AdminUserDetailsRoleTest`（5 条）、`AdminAccountRoleServiceTest`（15 条）、`AdminAccountManagementIntegrationTest`、`AdminAccountServiceTest` 全绿（部分测试需从「读枚举」改为「mock/真库读表」，见 T6）；`mvn -B clean package` 通过 `[L0/L1]`

## Dev Notes

### 🎯 本 story 的唯一目标：把权限的真相从代码搬到表，**用户什么都感觉不到**

验收就一句话：四类岗位账号登录后拿到的权限集合与迁移前逐位相等。所有设计都围绕这个。Parity 测试里**硬编码迁移前清单**（不要从枚举读——枚举已被清空），这份清单就是 T2 数组。

### 🔴 为什么 OPS_MANAGER 不迁移

D-13 产品拍板「运营主管代码原样保留不动」。所以解析顺序里 OPS_MANAGER 是独立一路读枚举，`AdminRole.OPS_MANAGER` 的 41 条码**不要动**。它的 `role_id` 永远 NULL。

### 🔴 「模板角色」的判定不能再靠 `isTemplated()` 一个布尔

现状 `isTemplated()` = `!= CUSTOM`，同时承担「不落账号级权限表」和「权限来自枚举」两个含义。1.4 之后「权限来自哪」有三个答案（枚举 / 角色表 / 账号级表），所以：
- `isTemplated()` 保留原义（是否不落 `admin_account_permissions`），`createAccount` / `updatePermissions` 的既有分支不用改；
- 「权限从哪来」统一进 `RolePermissionResolver`，别在各处 if/else。

### 🔴 `AdminRoleEntity` 命名

包内已有枚举 `com.tailtopia.admin.account.domain.AdminRole`，且 `admin_accounts.role` 列继续用它。表实体放新包 `admin.roles.domain`，类名 `AdminRoleEntity`，避免 import 混淆。1-5 的 `AdminRoleService` / Controller 也放 `admin/roles/**`（架构 §结构树）。

### 🔴 `role` 列与 `role_id` 列并存的语义

| `role`（varchar 枚举） | `role_id` | 权限来源 |
|---|---|---|
| SUPER_ADMIN | NULL | 隐式全权 |
| OPS_MANAGER | NULL | 枚举 |
| CUSTOM | NULL | `admin_account_permissions` |
| OPERATIONS / FULFILLMENT / SUPPORT / FINANCE | → `admin_roles` 对应行 | `admin_role_permissions` |
| （1-5 新建的自定义角色）| → `admin_roles` CUSTOM 行 | `admin_role_permissions`；此时 `role` 列填什么？—— **见开放问题 ①** |

### ⚠️ 开放问题（写进 Completion Notes 请产品/架构拍板，不阻塞本 story）

① **1-5 新建的「自定义角色」账号，`admin_accounts.role` 列填什么？** CHECK 约束只允许七个枚举值。可选：a) 新增枚举值 `ROLE_TEMPLATE`（需再一支迁移改 CHECK 全集，按 CLAUDE.md 规则 DROP+ADD 重列）；b) 复用 `CUSTOM` 但靠 `role_id != null` 区分「账号级勾选」与「引用自定义角色」。本 story 建议 **a)**，因为 b) 让 `CUSTOM` 一词有两义、`isTemplated()` 失效。本 story 不实现，留给 1-5 决定并加迁移。
② `AdminRole.selectable()` 现在返回七个枚举值供下拉；1-6 要改为从表读，本 story 不动。
