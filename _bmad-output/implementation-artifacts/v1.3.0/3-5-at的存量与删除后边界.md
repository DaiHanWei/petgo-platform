# Story 3.5: @ 的存量与删除后边界

Status: review

## Story

As a 点开一条提及通知却发现内容已经没了的用户,
I want 看到一句清楚的说明,
so that 我不会以为是 App 坏了。

## Acceptance Criteria

**AC1 — 存量不回溯** `[L0]`
本功能上线前已存在的内容与评论**不回溯解析**其中的 @ 文本，存量文本保持原样。

**AC2 — 删除后不撤回** `[L2]`
含 @ 的内容或评论被删除 / 被下架后，已发出的通知**不撤回**（不做撤回链路）。
被 @ 者点进去显示「内容已删除」**统一空态**。

**AC3 — 审核链路不变** `[L0]`
@ **不改变**既有内容审核链路 —— 审核逻辑一行不动。

**AC4 — 埋点** `[L1] [L0]`
上报 `mention_inserted` / `mention_tapped`，属性 `context` 取 `post` / `comment`。
事件命名**动作落词尾**；属性里**不含**任何昵称、正文等自由文本。

## Dev Notes

### 为什么不做撤回

撤回链路要处理"通知已读/未读""用户已点开/未点开"等一堆状态，收益却只是省掉一次「内容已删除」提示。2026-08-28 拍板不做。

### 埋点红线

埋点层有兜底黑名单，`name` / `nickname` / `text` / `content` 这类键会被**整条丢弃**。别传昵称、别传正文片段——源头就不要传，不要依赖兜底。

#### AC1 存量不回溯：三道机械守卫

1. **客户端绝不自己扫文本找 @**：`MentionText` 只渲染后端下发的 `mentions`，
   空表就退化成纯 `Text` —— 用例用一段「正文里写着 @阿花 和 @Budi 但后端没给 mentions」
   的存量文本钉住：整段纯文字、一个 recognizer 都不挂、点哪儿都不报 `mention_tapped`。
2. **没有任何迁移回填 `mentioned_user_ids`**：扫所有提到该列的迁移，
   剥掉 `--` 注释后不许出现 `UPDATE`（存量一律 NULL）。
3. 后端侧「存量行读出来是空表不是 null」由 Story 3.2 的 `MentionSanitizerTest` 钉着。

#### AC3 审核链路一行未动

机械判据：`ContentModerationService` / `ManualReviewGate` 两个类的源码里
**不许出现任何 `mention` 字样** —— 一旦有人把 @ 名单塞进审核入参，这条就红。
（@ 名单的洗与落库都在 `MentionSanitizer` / 发布服务里，从未进入审核判定。）

#### AC2 删除后的边界：**复用既有统一空态，不为 @ 另开一个**

通知**不撤回**（AD-10 Rule 6；2026-08-28 拍板不做撤回链路 —— 撤回要处理
「已读/未读」「已点开/未点开」一堆状态，收益只是省掉一次提示）。
被 @ 者点进去走的是**既有那条路**：
深链 → `/content/{postId}` → 详情 404 → `ContentLoadErrorKind.gone` → `detailGoneTitle` 空态
（既有用例 `test/content/content_detail_test.dart` 的「AC4: 404 → 失效页」一直钉着它）。

本 story 加的是**反向守卫**：详情页失效态仍然只有三种、`_errorBody` 里不出现 `mention`、
`ContentLoadErrorKind` 没有因为 @ 多出取值。多一种说法就等于把「这条内容删了」和
「那个 @ 没了」变成两句话，而用户看到的是同一件事。

#### 🔸 一条对 AC2 的字面读法说明（建议本地/产品确认）

AC2 原文是「含 @ 的内容**或评论**被删除 / 被下架后…点进去显示「内容已删除」统一空态」。
两种情况的落点**刻意不同**：

| 被删的是 | 落点 | 理由 |
|---|---|---|
| **内容（帖子）** | 「内容已删除」统一空态 ✅ | 目标不可达，空态是唯一能说的话 |
| **只有评论**（帖子还在） | 落在该帖详情页的评论区，**没有**额外空态 | 那条帖子**是可达的**；说「内容已删除」是错的 —— 内容并没有删 |

- 后者若要给一句「那条评论没了」，客户端得知道 commentId 并能查它存不存在；
  而 targetRef 刻意只带 postId（Story 3.4：要跳的是帖子详情，评论区靠锚点）。
- 落在帖子上比一个空态更有用（用户还能看到上下文）。
- **未自行扩大改动**：如果产品要的是「连评论被删也给空态」，那是 targetRef 契约 +
  一个新端点的改动，应作为独立决策记入决策日志。
