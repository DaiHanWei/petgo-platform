## 2 · 为什么是零：Epic 10 六条 story 的「零新端点」是怎么做到的

这不是巧合，是六条 story 各自受同一条约束（AB-19A / 各 story 首段「**零后端功能改动、零新端点**」）的结果。
它们都需要「抽屉 / 卡区取数」这类新的服务端入口，而模板 B / C 的惯例做法（`GET …/{id}/drawer`）**就是新端点**。
六条一律改成**复用既有 mapping 的 `HX-Request` 分支**：

| story | 需要的新入口 | 实际怎么解决 |
|---|---|---|
| 10.1 A7/A8 | 工作台队列 + 右栏 | 复用 `GET /admin/shop/returns`、`/admin/shop/order-exceptions` 的 htmx 分支 |
| 10.2 B15/C1 | 订单抽屉、对账卡区 | 复用 `GET /admin/shop/orders`（`?open=`）、`/admin/shop/reconciliation` |
| 10.3 B16/B17 | Banner 新建 / 编辑抽屉 | 复用 `GET /admin/shop/banners`（`?create=1` / `?open=<id>`） |
| 10.4 B18/B19 | 库存抽屉、判例抽屉 | 复用 `GET /admin/shop/inventory/{skuId}/movements`（D-43）、`GET /admin/shop/return-precedents`（`?create=1`） |
| 10.5 C2/C3/C4 | 三张报表的卡区片段 | 复用三条报表 GET 自身的 htmx 分支 |
| 10.6 D1 | 三张配置卡的保存回卡 | 复用四个既有 POST 的 htmx 分支（`HX-Retarget` + `HX-Reswap`） |

**同一条 mapping 两种响应形态**，所以路由表纹丝不动。
这也是本报告能给出「逐字节一致」这种强结论的原因 —— 换成任何一条新开的 `/drawer` 端点，
这里就会多出一行需要解释的新增。

## 3 · 一条必须记账的口径差：「退役」≠「删路由」

Story 11.3 AC1 的退役表把 `GET /admin/shop/orders/{token}`、`GET /admin/shop/returns/{token}`
列为**本版退役的独立详情页**。上一轮核对时它们「因 Epic 10 未执行而仍在服役」，
作为**预授权**写进了白名单（当时不命中）。

Epic 10 执行后，它们**依然在清单里** —— 但性质变了：

> 10.1 / 10.2 的实际处置是**保留 mapping**：`HX-Request` 下返回抽屉 / 右栏片段，
> 非 htmx 直接抛 404（message code `admin.err.common.pageRetired`）。

也就是说「整页退役了，路由没退役」。理由是那条路径同时是**抽屉的取数入口**（`?open=<token>` 深链与
`hx-get` 都打它）—— 删掉路由，抽屉就是空的。

**对 11.3 的直接影响：这两条不要去删。** 白名单里的预授权项保留（它们是「将来若真删也不算事故」的授权），
但当前状态是「路径保留、整页退役」。同一形态的还有 9.1b 的
`GET /admin/vets/{id}/qualification` 与 `GET /admin/vets/{id}/ratings`（改成抽屉页签片段）。

四条合并成一句：**退役表里有 4 条是「整页退役、路径保留」，不是「路由删除」。**
