# Story 5-1: 评价原文不进日志

Status: ready-for-dev

> 自包含 story，**纯后端**（`petgo-backend/`），一个类 + 一组单测，无迁移、无 App 端改动、无接口契约变更。
> 与用户沟通用中文。执行纪律见根 `CLAUDE.md`（`mvn -B clean package`）。

## Story

As a 平台，
I want 用户写的评价正文不出现在请求日志里，
so that 不因为一个本版根本不做的功能，在落盘日志上留下一个用户自由文本的泄露面。

## Context

### 现状

`petgo-backend/src/main/java/com/tailtopia/shared/logging/LogSanitizer.java` 有**两套**敏感键集合：

| 集合 | 行 | 当前内容 | 作用域 |
|---|---|---|---|
| `SENSITIVE_KEYS` | :27-36 | `password, rawpassword, idtoken, accesstoken, refreshtoken, refresh, token, usersig, secret, secretkey, signature, authorization, email, phone, googlesub, symptomtext, symptom, symptoms, aiobservation, diagnosis, receivername, receiverphone, addressline, kodepos` | **请求体与响应体都打码** |
| `REQUEST_ONLY_SENSITIVE_KEYS` | :44 | `Set.of("detail")` | **只对请求体打码** |

分流点在 `redact(...)` :91-93：

```java
if (SENSITIVE_KEYS.contains(lower)
        || (isRequest && REQUEST_ONLY_SENSITIVE_KEYS.contains(lower))) {
    obj.put(name, MASK);
}
```

入口两个：`sanitize(byte[], String)` :54（响应体口径，`isRequest = false`）与 `sanitizeRequest(byte[], String)` :59（请求体口径，`isRequest = true`）。唯一调用方是 `shared/logging/ApiAccessLoggingFilter.java:81`。

`REQUEST_ONLY_SENSITIVE_KEYS` 的类注释（:38-43）已经把理由写死了：**`detail` 不能进全局集合，因为 RFC 9457 错误响应体的 `detail` 是排障主字段，全局打码会把所有错误响应弄瞎。** `content` 同理 —— 见下。

### 评价提交端点与字段名

| 项 | 事实 |
|---|---|
| 提交 | `POST /api/v1/me/shop-reviews`（`shop/review/web/MeShopReviewController.java:39-49`） |
| 改后重提 | `POST /api/v1/me/shop-reviews/{id}`（:52-61） |
| 请求体 | `record SubmitReviewRequest(String orderToken, Long orderLineId, Integer rating, String content, List<String> imageKeys)`（:77-79）—— **正文字段名就是 `content`** |
| 响应体 | `ShopReviewView`（`shop/review/dto/ShopReviewView.java:19`）**也有 `content` 字段** |

### 🔴 为什么必须进「只对请求体生效」的集合

`ShopReviewView.content` 是**响应**字段。若把 `content` 放进 `SENSITIVE_KEYS`：

- `GET /api/v1/shop/products/{token}/reviews`（`ShopReviewController.java:40`）与 `GET /api/v1/me/shop-reviews`（`MeShopReviewController.java:63`）的响应日志里，**每一条评价正文都会变成 `***`** —— 而这些正文是已经公开展示给所有人的，打码它对隐私零收益，对排障是纯损失；
- 全仓其它任何响应 DTO 里叫 `content` 的字段会一起遭殃。

放进 `REQUEST_ONLY_SENSITIVE_KEYS` 则只影响请求体。

### 请求侧的爆炸半径（已核实，很小）

全仓请求 DTO 中叫 `content` 的**只有** `SubmitReviewRequest`：
- 评论用 `body`（`content/dto/CommentCreateRequest.java:11`）
- 发帖正文用 `text`（`content/dto/ContentPostCreateRequest.java:23`）
- `UploadUrlRequest` 里是 `contentType`（`shared/media/dto/UploadUrlRequest.java:13`），**不同的键名**，`redact` 做的是整键 equals 比较（:91 `SENSITIVE_KEYS.contains(lower)`），不会误伤

### 现有测试

`src/test/java/com/tailtopia/shared/logging/LogSanitizerTest.java` 已有 7 条（:18 tokens/PII、:32 健康字段、:40 签名 URL、:48 嵌套与数组、:57 非 JSON、:64 空体、:70 非法 JSON）。**没有任何一条覆盖 `REQUEST_ONLY_SENSITIVE_KEYS` 的请求/响应分流**（grep `detail` 在该测试文件无命中）—— 本 story 要补的正是这一层。

### 范围边界

- OD-12「评价提交端点去留（推荐关闭）」**本 story 不处理**。5-1 只做日志脱敏；端点是否下线是独立决策，落点在 sprint-status 的开放项里。
- 不改 `ApiAccessLoggingFilter`、不改 `MeShopReviewController`、不改 `ShopReviewView`。

## Acceptance Criteria

**AC1 · `content` 进只对请求体生效的集合**
**Given** `LogSanitizer.java:44` 的 `REQUEST_ONLY_SENSITIVE_KEYS`
**When** 加入 `"content"`
**Then** 集合变为 `Set.of("detail", "content")` `[L0]`
**And** 🔴 `SENSITIVE_KEYS`（:27-36）**一个元素都不动**，`content` 绝不进该集合 `[L0]`
**And** 类注释（:38-43）补一句说明 `content` 为何在此：「评价正文（`SubmitReviewRequest.content`）是用户自由文本；而 `ShopReviewView.content` 是公开响应字段，全局打码只会弄瞎排障」`[L0]`

**AC2 · 评价提交请求的正文被打码**
**Given** 一段评价提交的请求体 JSON `{"orderToken":"tok","orderLineId":7,"rating":5,"content":"狗粮很好，我家狗吃了三天"}`
**When** 调 `sanitizeRequest(body, "application/json")`
**Then** 输出中 `content` 的值为 `MASK`，**且不含原文任何片段** `[L0]`
**And** 同一体中的 `orderToken` / `orderLineId` / `rating` **不受影响**（`orderToken` 不是 `token`，整键比较不命中）`[L0]`

**AC3 · 响应侧同名字段不受影响**
**Given** 一段评价列表的响应体 JSON `{"items":[{"id":1,"rating":5,"content":"公开可见的评价正文"}]}`
**When** 调 `sanitize(body, "application/json")`（响应口径，`isRequest = false`）
**Then** `content` 的值**原样保留**（走 :96-97 的 `maskString` 通用截断/签名 URL 规则，不被整值置 `MASK`）`[L0]`
**And** 嵌套在数组对象里的 `content` 同样不受影响（`redact` :99 递归路径）`[L0]`

**AC4 · `detail` 既有行为不回归**
**Given** 请求体 `{"detail":"举报补充说明"}` 与响应体 `{"detail":"请求格式不正确","status":400}`
**Then** 请求侧 `detail` → `MASK`；响应侧 `detail` **原样保留** `[L0]`

**AC5 · 🔴 变异验证**
**Given** 从 `REQUEST_ONLY_SENSITIVE_KEYS` 里**删掉** `"content"`
**When** 跑 `LogSanitizerTest`
**Then** AC2 对应的用例**必须变红** `[L0]`
**And** 再从该集合删掉 `"detail"`，AC4 的请求侧用例**必须变红** `[L0]`
**And** 变异验证的执行记录（删了哪一行、哪条用例变红、报错摘要）写进 Completion Notes `[L0]`

**AC6 · 不破坏既有**
**Then** `LogSanitizerTest` 原有 7 条全绿；`mvn -B clean package` 全绿 `[L0]`
**And** File List 不含 `MeShopReviewController.java` / `ShopReviewView.java` / `ApiAccessLoggingFilter.java` / 任何 `.sql` / 任何 `.dart` `[L0]`

## Dev Notes

### 为什么不顺手把端点关掉

sprint-status 的开放项 OD-12 写的是「评价提交端点去留 → 5-1（推荐关闭）」。**推荐 ≠ 已拍板**。关端点是对外契约变更（老版本 App 若有提交路径会直接 4xx），属产品决策；本 story 的 AC 里一条都没有它，实施时**不要**顺手加 `@Deprecated` / 加开关 / 删端点。若产品在实施期间拍板关闭，那是一个新 story。

### 为什么不放进全局集合（再说一遍，这是本 story 唯一会出错的地方）

`ShopReviewView.content`（`shop/review/dto/ShopReviewView.java:19`）是响应字段，出现在：
- `GET /api/v1/shop/products/{token}/reviews` → `ProductReviewsView.items[].content`
- `GET /api/v1/me/shop-reviews` → `List<ShopReviewView>`

这些正文**本来就是公开展示的**。打码它们：隐私收益为零，排障成本为正。这正是 `REQUEST_ONLY_SENSITIVE_KEYS` 这个集合存在的全部理由（它的类注释 :38-43 就是为 `detail` 写的同一个论证）。

### `redact` 是整键 equals，不是前缀匹配

`SENSITIVE_KEYS.contains(lower)`（:91）—— 所以：
- `contentType`（`UploadUrlRequest`）**不会**被 `content` 命中
- `orderToken` **不会**被 `token` 命中（既有行为，本 story 不改变）

不要为了「保险」改成 `startsWith` / `contains` —— 那会把 `contentType`、`contentLength` 一起打掉，也会把大量正常字段误伤。
