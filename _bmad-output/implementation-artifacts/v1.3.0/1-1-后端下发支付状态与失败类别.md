# Story 1-1: 后端下发支付状态与失败类别

Status: review

> 本 story **只碰后端**（`pay/` + `shop/order/`）+ **App 侧一个 DTO 字段与一个契约测试**。App 的界面处置在 1-3，本 story 一行 UI 都不改。

## Story

As a 用户，
I want App 能知道我的付款是被拒了还是超时了、还是我自己取消的，
so that 我不用对着一个永远不会成功的二维码干等，也不会以为是自己手机坏了。

## Context（本 story 必须知道的现状）

### 根因：App 轮询的是订单，网关拒付只改支付单

- App 侧轮询实现在 `/Users/dai/work/petgo-platform/petgo_app/lib/features/shop/presentation/shop_order_detail_page_v2.dart:748-757`：
  ```dart
  // 轮询问的是订单本身的状态 —— 到账由服务端在回调里推进，客户端不自行判定。
  pollPaid: () async {
    final fresh = await ref.refresh(shopOrderDetailProvider(widget.orderToken).future);
    if (fresh.status == ShopOrderStatus.cancelled) {
      throw const QrPaymentAborted();
    }
    return fresh.status.isPaidOrLater;
  },
  ```
  轮询打的端点是 `GET /api/v1/me/shop-orders/{token}`（`MeCheckoutController.java:103-108`），返回 `ShopOrderDetailView`。
- **网关拒付路径**：`PayCallbackController.callback(...)`（`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/pay/web/PayCallbackController.java:43`）→ `PaymentIntentService.applyCallback(cb)` → `PaymentIntentService.java:251-254`：
  ```java
  case FAILED -> {
      intent.markFailed(cb.rawMeta());
      intents.saveAndFlush(intent);
  }
  ```
  **只改 `payment_intents`，一个字都不碰 `shop_orders`**。订单仍是 `PENDING_PAYMENT`，倒计时继续走。
  ⇒ App 轮订单，永远看不到「被拒」，只能干等到 60 分钟窗口耗尽。
- **超时 / 用户取消路径**：反过来，走 `ShopOrderPaymentService.releaseAndCancel(order, reason)`（`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/shop/order/service/ShopOrderPaymentService.java:287-299`），先释放库存、订单转 `CANCELLED`，再 `paymentIntents.failByToken(intentToken, reason)`（`:296`）。App 看到的都是 `status == cancelled`，**区分不出是超时还是自己点的取消**。

### 失败原因的真实值域（已核实，不是推测）

| 写入点 | file:line | 落进 `gateway_meta` 的内容 |
|---|---|---|
| `ShopOrderPaymentService.cancel(...)` 用户主动取消 | `ShopOrderPaymentService.java:223-231` → `releaseAndCancel(order, "USER_CANCEL")` | `{"reason":"USER_CANCEL"}` |
| `ShopOrderPaymentService.expireIfOverdue(...)` 懒过期 | `ShopOrderPaymentService.java:239-245` → `releaseAndCancel(order, "TIMEOUT")` | `{"reason":"TIMEOUT"}` |
| `ShopOrderPaymentService.cancelOneOverdue(...)` 定时扫描 | `ShopOrderPaymentService.java:272-280` → `releaseAndCancel(order, "TIMEOUT")` | `{"reason":"TIMEOUT"}` |
| `PaymentIntentService.failByToken(token, reason)` 的 null 兜底 | `PaymentIntentService.java:157-166`：`reason == null ? "CANCELLED" : reason` | `{"reason":"CANCELLED"}`（当前**无调用方**会触发，但值域必须覆盖） |
| `PaymentIntentService.failPending(userId, purpose)` | `PaymentIntentService.java:307-314` | `{"reason":"USER_CANCEL"}` —— 唯一调用方是 `ConsultRequestService.java:375`（问诊线，**非电商**） |
| 网关回调 FAILED | `PaymentIntentService.java:251-254` | **网关 rawMeta 原文**，一般**没有 `reason` 键** |

`PaymentIntent.gatewayMeta` 的 Java 类型是 `java.util.Map<String, Object>`（`@JdbcTypeCode(SqlTypes.JSON)`，列 `gateway_meta JSONB`，`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/pay/domain/PaymentIntent.java:70`）。
⇒ **Java 侧是 `map.get("reason")`，不是 SQL 的 `gateway_meta->>'reason'`**。epics 里写的是 SQL 语法，实现按 Map 读。

### 🔴 epics AC1 的映射规则有一个会误判的洞（本 story 必须修正）

`PaymentStatus` 是 **四值**：`PENDING / PAID / FAILED / EXPIRED`（`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/pay/domain/PaymentStatus.java:10-18`）—— `EXPIRED` 是**独立终态**，不是 `FAILED` 的一个 reason。

电商支付单**确实会进 `EXPIRED`**：
- `ShopOrderPaymentService.ensureIntent(...)`（`:151-174`）建意图时传了 `Duration ttl = remainingWindow(order)`（`:160`），所以 `payment_intents.expires_at` **非空**。
- `PaymentIntentExpiryScanner`（`/Users/dai/work/petgo-platform/petgo-backend/src/main/java/com/tailtopia/pay/service/PaymentIntentExpiryScanner.java`）**每 60 秒**扫一次，调 `PaymentIntentService.expireOverduePending(200)`（`PaymentIntentService.java:194-207`），仓库方法 `findByStatusAndExpiresAtBefore(PENDING, now, page)` **不按 purpose 过滤**，SHOP_ORDER 照扫。
- 置 EXPIRED 走 `intent.markExpired(null)` —— **meta 传 null，`gateway_meta` 保持原样（一般为下单时的 charge 快照，无 `reason`）**。
- 随后订单侧的 `releaseAndCancel` 调 `failByToken`，但 `failByToken` 开头 `if (intent.getStatus().isTerminal()) { return; }`（`PaymentIntentService.java:159-161`）⇒ **静默 no-op，`reason` 永远写不进去**。

所以 `status = EXPIRED && gateway_meta 无 reason` 是**常态**，不是边角。若照 epics 原文「其余 → `GATEWAY_DECLINED`」，超时会被稳定误标成「网关拒付」，App 就会给一个不该给的重试入口 —— 正是 SHOP-FR-01 要防的事。

**本 story 的修正**：先判 `status`，再判 `reason`。规则见 AC1。

### 其它必须知道的

## Acceptance Criteria

**AC1 · `PaymentFailureCategory` 枚举与工厂**
**Given** `pay/domain` 下只有 `PaymentStatus`，没有失败类别的概念
**When** 新增 `com.tailtopia.pay.domain.PaymentFailureCategory`，三值 `GATEWAY_DECLINED` / `EXPIRED` / `USER_CANCELLED`，并提供 `public static PaymentFailureCategory of(PaymentIntent intent)`
**Then** 映射规则**严格按下表**，判序为「先 status 后 reason」`[L0]`

| 输入 | 结果 |
|---|---|
| `intent == null` | `null` |
| `status == PENDING` 或 `PAID` | `null` |
| `status == EXPIRED` | `EXPIRED`（**不看 meta** —— 四个置 EXPIRED 的点 meta 全传 null） |
| `status == FAILED` 且 `gatewayMeta == null` | `GATEWAY_DECLINED` |
| `status == FAILED` 且 `gatewayMeta.get("reason")` == `"TIMEOUT"` | `EXPIRED` |
| `status == FAILED` 且 `reason` ∈ {`"USER_CANCEL"`, `"CANCELLED"`} | `USER_CANCELLED` |
| `status == FAILED` 且 `reason` 为 null / 其它任意值 | `GATEWAY_DECLINED` |

**And** `reason` 读取用 `String.valueOf(...)` 前先判 null，取值比较**区分大小写、逐字面量匹配**，不做 `contains` / 忽略大小写的模糊匹配 `[L0]`
**And** 该枚举**不暴露** `gateway_meta` 原文的任何片段（meta 可能含网关返回的 PII） `[L0]`

**AC2 · 订单详情新增两个字段**
**Given** `ShopOrderDetailView` 当前 20 个组件，App 轮询只能看到 `status`
**When** 在 record **末尾追加** `String paymentStatus` 与 `String paymentFailureCategory` 两个组件（与既有 `status` / `payChannel` 一致用 `String` 承载枚举线）

**And** 三个出口（`detail` / `cancel` / `confirm-receipt`）都带上这两个字段（即改在 `detailOf` 一处） `[L1]`

## Dev Notes

### 为什么类别算在后端而不是让 App 读 meta

AD-S9(a) 原话：「**分类逻辑落在后端一处** `PaymentFailureCategory.of(intent)`，不让 App 解析 meta（meta 可能含 PII）」。
`gateway_meta` 在网关回调分支里存的是 **GemPay 返回的 rawMeta 原文**（`PaymentIntentService.java:252` 的 `cb.rawMeta()`），字段构成由第三方决定，随时可能多出持卡人姓名、手机号一类内容。所以：**它一个字节都不能进对外 DTO，也不能进日志**（`PostHogAnalyticsClient` 连 properties 都不记，就是同一条防线）。

| ③ | App mock | 🔴 **已不存在**（commit `8e85b40d` 删除全部 mock 子系统，L2 恒连真后端）⇒ N/A，Completion Notes 写明 |

### 代码复审（bmad-code-review）结论

**已修 1 条 CONFIRMED：**

- **契约测试钉错了 wire 形状（假绿）**。初版用裸 `ObjectMapper` 断言「22 个顶层键、纯 PawCoin 单两键为 null」，但 `application.yml:235` 配的是
  `spring.jackson.default-property-inclusion: non_null` —— 线上响应把 null 字段**整键省略**，那份 22 键 JSON 永远不会出现。
  已改为复用本仓既有契约测试范式（`ConsultSessionContractTest` / `MilestoneListResponseContractTest`）的 `JsonMapper.builder().changeDefaultPropertyInclusion(NON_NULL)`，
  并把「纯 PawCoin 单」一例改成断言两键**在线上被省略**、其余 20 键一个不少。App 侧 `j['paymentStatus']?.toString()` 对缺键与 null 同样得到 null，两端在此对齐。

**未改，按 story 原文施工 + 留痕：**

- **`gateway_meta.reason` 有两个写入方**：我方 `failByToken` 的哨兵值，与网关回调的 `rawMeta` 原文。若某网关的 `rawMeta` 恰好带 `reason: "CANCELLED"`（发卡行拒付），会按 AC1 映射表判成 `USER_CANCELLED`，用户被告知「你取消了」且不给重试入口。
  **AC1 的映射表明确要求 `CANCELLED` → `USER_CANCELLED`，未自行改动**（架构疑问不自行拍板）。真要收口，建议后续 story 把我方哨兵换成独立键（如 `petgoReason`）与网关原文隔离。**提请 1-3 施工前确认。**
- **`intentOf` 返回 JPA 实体**跨到 shop 的 DTO 层，与 `PaymentIntentService.findByToken:263` 注释「跨模块请走 DTO」的措辞有张力。但 T2/T3 明确规定了这个签名，且 PII 防线的实际承载是契约测试的 `doesNotContain("gatewayMeta")` 断言，故按 story 施工。
- 旧两个 `of(...)` 重载以 `intent = null` 委托，未来生产调用方会静默拿到空支付字段 —— 这正是 AC3 要求的形状（换签名要拖动 5 处无关测试），保留。

### 云端环境说明（与代码无关，勿当缺陷）

1. **`mvn -B clean package` 在本容器不可能绿**：190 个 L1 类（`*IntegrationTest` / `*EndpointTest` + 8 个具名类）无 DB 必然 `ApplicationContext` 失败（1440 errors）。故 L0 闸门取「`clean package -DskipTests` 全量编译出 jar + 排除 L1 后跑单测」，**1657 例全绿**。

3. **本容器无 git remote**：`check-flyway-versions.sh origin/main` 的冻结/撞号检查靠本地 `refs/remotes/origin/main → master`（＝本分支基线）代跑；**远端推送未执行**。
