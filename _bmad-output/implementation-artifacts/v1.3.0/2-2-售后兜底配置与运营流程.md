# Story 2-2: 售后兜底配置与运营流程

Status: ready-for-dev

> 自包含 story。与用户沟通用中文。执行纪律见根 `CLAUDE.md`。
> **本 story 不写业务代码**：交付物只有两件 —— ① 运营后台的配置动作（+ 只读核实）；② 一份 `docs/runbooks/` 下的运营流程文档。
> 🔴 **范围红线**：若实施中发现「必须改代码才能做到不发补偿」，**立刻停下，回 `_bmad-output/planning-artifacts/v1.3.0/决策日志-shop-v2.md` 记开放项并找产品确认**，不得自行扩大到改代码。本 story 的整个立论（SD-13）就是「零开发」。

## Story

As a 运营，
I want 用户要求取消或退款时，知道在后台点哪里、且系统不会多发钱给用户，
so that 我不用每次都找技术确认，也不会在 2-1 把 App 退货入口隐藏之后没有兜底路径。

## Context

SD-5 把退货退款整体移出本版，App 侧入口在 Story 2-1 隐藏；但**后端接口与运营后台退货页仍开着**（SD-13 明确「不在后端关闭用户提交退货」），老版本 App 仍可提交退货单。SD-2 定的规则是「拒收、发货前取消**一律没有额外补偿**，只退应退金额」，而系统现状会发补偿溢价 —— SD-13 的解法是靠配置置 0 让现状符合规则，再给运营一份流程。

### 🔴 核实结论一：两个「比例」的可配置性**不对等**

| 配置项 | 列 | 后台有没有入口 | 说明 |
|---|---|---|---|
| **转 PawCoin 激励比例** | `pawcoin_config.premium_rate` | ✅ 有。`/admin/config` 页 PawCoin 表单（`templates/admin/config.html:49-56`）→ POST `/admin/config/pawcoin`（`AdminConfigController.java:146`）→ `AdminConfigService.updatePawCoin`（`AdminConfigService.java:86-105`）。写 `config_change_logs` + `commit(...)` 审计哈希链 | 校验 0–50 |
| **激励的固定溢价** | `pawcoin_config.premium_fixed` | ✅ 同一表单同一提交（`config.html:53-54`） | 校验 ≥ 0 |
| **平台责任补偿比例** | `pawcoin_config.compensation_premium_rate` | ❌ **没有任何后台入口**。服务方法 `AdminShopPawcoinRulesService.updateCompensationPremium`（`shop/order/service/AdminShopPawcoinRulesService.java:78-92`）存在，但全仓 grep 后**只有测试类引用它**，没有任何 Controller / 模板调用 | 迁移 `V20260817_2330__add_compensation_premium_config.sql:12` 建列时 `DEFAULT 0` |
| **补偿溢价上限** | `pawcoin_config.compensation_premium_cap` | ❌ 同上 | 同迁移 :13，`DEFAULT 0` |

**推论**：补偿比例**从来没有人能改过**，因此现网值**应当仍是建列时的 0**。本 story 的动作因此是「**核实**它是 0」而不是「把它改成 0」；真改不了，也不需要改。

> ⚠️ 顺带记在这里（不在本 story 处置）：`updateCompensationPremium` 只调 `AdminAuditService.record`，**不写 `config_change_logs`**，与 `AdminConfigService.updatePawCoin` 的双写口径不一致。Epic AC1 写的「配置变更进 `config_change_logs` 与审计哈希链」只对 `premium_rate` / `premium_fixed` 成立。

### 🔴 核实结论二：只把 `premium_rate` 设 0 **不足以**让激励归零

`PawCoinConfig.refundPawcoinPremium`（`config/domain/PawCoinConfig.java:181-183`）：

```java
return baseAmount * premiumRate / 100 + premiumFixed;
```

`premium_fixed` 是**加法项**，不受比例影响。电商退货的激励溢价正是走这个领域方法（`RefundExecutionService.java:264`）。所以 **`premium_rate` 与 `premium_fixed` 必须一起置 0**，缺一个就仍会发钱。

（好消息：`RefundExecutionService.incentiveApplies`（:297-299）要求「未交付 + 现金段 > 0 + 配置存在」三条同时成立才给激励，所以已交付的退货本就拿不到；但「发货前取消 / 拒收」恰恰是未交付，正是 SD-2 点名的两类。）

### 🔴 核实结论三：整单取消**会不会**发补偿

`AdminShopOrderExceptionService.cancelWholeOrder`（`admin/shop/service/AdminShopOrderExceptionService.java:86-120`）在同一事务里做五件事：

1. **库存回补**（:93 → `restock` :233-241 → `movements.receiveReturn(...)` :237）
2. 订单行 `refundedQty` 补齐（:94-100）
3. **PawCoin 段全额退回**（:103 `refundCoinSegment`，:252-259，`PawCoinTxnType.REFUND`）
4. **补偿溢价**（:104 `payCompensationPremium`，:267-286）—— 读的是 `compensationPremiumRate`，`<= 0` 时 :272-274 直接 `return 0L`，**不发币**；base 是刚退的 PawCoin 数，**纯现金单本来就发不出**
5. `order.recordRefund(...)` + 转 `CANCELLED` + 审计 + 站内信（:107-116）

**现金段只算出 `cashDue` 返回，不打款**（:111、record 注释 :303「由 Epic 5 Story 5.5 的资金链路打款」）—— 也就是说**现金退款必须线下人工转账**。

> ⚠️ 结论：`compensation_premium_rate = 0` 时，「整单取消」这条路**不会**发补偿。SD-13 步骤①的目标在代码层是成立的，只要核实值确实是 0。

### 🔴 核实结论四：无采购入库记录的商品做整单取消会报错

`restock` → `InventoryMovementService.receiveReturn`（`shop/service/InventoryMovementService.java:82-89`）→ `lastPurchaseCostPrice`（:156-164）：

```java
.orElseThrow(() -> AppException.validation(
        "该 SKU 尚无采购入库记录，取不到进货单价，无法登记退货入库。"
                + "请先登记一次采购入库（0 成本入库会让毛利核算失真）"));
```

`AppException.validation` → **400**，且因为整单取消是**单一事务**（:85 `@Transactional`），整笔回滚：订单没取消、币没退、库存没回补。**规避办法**：先在 `/admin/shop/inventory` 页给该 SKU 登记一次采购入库（POST `/admin/shop/inventory/purchase`，`AdminShopInventoryController.java:138`），再回来点整单取消。

另有一个相邻失败点：`doInbound`（:168-172）在 `inventory.restock(skuId, qty) == 0` 时抛 `AppException.notFound("库存记录不存在，无法入库")` —— 即该 SKU 连 `sku_inventory` 行都没有。规避同样是先走一次采购入库（它会建行）。

### 🔴 核实结论五：后台确实没有「代用户发起退货」的入口

`AdminReturnController`（`admin/shop/web/AdminReturnController.java`）全部端点：

| 行 | 端点 | 动作 |
|---|---|---|
| :91 | `GET /admin/shop/returns` | 退货队列 |
| :113 | `GET /admin/shop/returns/{token}` | 退货详情 |
| :150 | `POST .../approve` | 批准 |
| :163 | `POST .../reject` | 驳回 |
| :178 | `POST .../shipback` | 代填寄回单号 |
| :211 | `POST /admin/shop/returns/images` | 上传验收照片 |
| :229 / :243 | `POST .../inspect-pass` / `inspect-fail` | 验收通过 / 不通过 |
| :262 | `POST .../refund` | 执行退款（`PAYOUT_AUTH`） |
| :279 / :288 | `GET`/`POST /admin/shop/return-precedents` | 开封判例 |

**没有 create / submit 类端点** —— 与 PRD §8 已知问题 10 一致。运营只能处理**用户自己提交**的退货单。

### 🔴 核实结论六：执行退款前必须确认用户已选退款去向

`RefundExecutionService.execute`（`shop/returns/service/RefundExecutionService.java:110-112`）：

```java
if (q.cashRefund() > 0 && r.getCashDestination() == null) {
    throw AppException.conflict("用户尚未选择现金段退回方式，暂不能执行退款");
}
```

→ **409**。而退款方式选择页在 App 里**只能从提交退货后的流程进入**（PRD §8 已知问题 6），2-1 隐藏入口后新版本 App 用户根本到不了那一屏。所以老版本用户提交的退货单，若他没在旧流程里选过去向，后台按「执行退款」会 409 —— **只能转线下**。

## Dev Notes

### 🔴 为什么这个 story 敢说「零开发」

SD-13 的假设是「后台 PawCoin 配置里把两个比例设为 0」。核实后这个假设**一半成立、一半是因为运气**：

- 「转 PawCoin 激励比例」确实可配（还必须连 `premium_fixed` 一起置 0，SD-13 原文没提到这一项 —— 这是本 story 发现的补充）；
- 「平台责任补偿比例」**根本没有配置入口**，但它建列即 `DEFAULT 0` 且从未有人能改，所以现网天然是 0。

于是「零开发」的实际含义是：**核实 + 改一个表单 + 写一份文档**。一旦 AC2 查出来不是 0，零开发就破了 —— 那时唯一正确的动作是停手回决策日志，而不是就地补一个配置页（补配置页是 admin 主题 Epic 10 / 本主题第二批的量级，不该塞进一个「非代码 story」）。

### 售后成本口径的连带影响（记一笔，不在本 story 处置）

`ShopFinanceDashboardService.margin` 的售后成本（`admin/shop/service/ShopFinanceDashboardService.java:81-86`）= `return_requests` 表的 `compensation_premium + incentive_premium + shipback_reimbursed`。而「整单取消」发的补偿溢价走的是 `AdminShopOrderExceptionService.payCompensationPremium`，**只落 `pawcoin_transactions` 的 BONUS，不建 `return_requests` 行** —— 也就是说这条路的补偿**从来不计入售后成本报表**。本版两项都是 0，数字上无差别；口径标注是 Story 5-3 / 9-5 的事。
