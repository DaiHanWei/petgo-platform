# Story 3.3: @ 的展示与跳转

Status: review

> **依赖 Epic 2**：跳转落点是 Story 2.1 交付的公开主页。Epic 2 未完成前本 story 无法验收。

## Story

As a 看到别人在评论里 @ 了某个人的用户,
I want 那个名字是可以点的,
so that 我能直接去看被 @ 的人是谁。

## Acceptance Criteria

**AC1 — 高亮与实时昵称** `[L2]`
含 @ 的正文或评论渲染时，@昵称**高亮**显示；昵称取**当前**昵称（按存下来的 userId 实时查，对方改名后自动跟着变）。

**AC2 — 点击跳主页** `[L2]`
点击高亮的 @昵称 → 跳转到该用户的公开主页。

**AC3 — 拉黑不高亮** `[L2]`
查看者与被 @ 者之间存在任一方向的拉黑关系 → **不高亮**该 @。

**AC4 — 注销用户** `[L2]`
被 @ 的用户已注销 → 按既有匿名化口径展示，不泄漏身份、不可点。

## Dev Notes

### 🔴 可点与否在服务端判定

拉黑关系与注销状态都不该让客户端自己算。服务端在返回内容时就把"这个 @ 能不能点、显示什么昵称"算好下发。
理由同 NFR-2：客户端判定只是"看不见"，而且两处判定迟早分叉。

### 富文本渲染

Flutter 侧用 `TextSpan` + `recognizer` 实现可点片段。⚠️ 注意 `TapGestureRecognizer` 需要在 `dispose` 时释放，否则泄漏。

#### 🔴 可点与否在服务端判定（story Dev Notes 那条）

新增 `mention.dto.MentionView(userId, nickname, tappable)` + `mention.service.MentionViewService`。
客户端**没有任何** `if 被拉黑` 的分支 —— 只有 `tappable` 这一个开关。

| 情况 | 下发形态 | 客户端表现 |
|---|---|---|
| 正常 | `{userId, nickname: 当前昵称, tappable: true}` | 高亮 + 可点 |
| 任一方向拉黑（AC3） | `{userId, tappable: false}`，**不带昵称** | 普通文字 |
| 已注销 / 库里没这人（AC4） | 同上 | 普通文字 |

- **不可点时刻意不下发昵称**：给一个已拉黑他的人下发当前昵称，等于把「对方改名了」告诉他；
  注销后按匿名化口径也不该再给身份。
- **仍然下发那一条（只留 id）而不是整条省略**：客户端据此知道「这里有一处 @，但点不动」，
  L0 契约测试也能直接断言 `tappable=false` —— 省略的话只能断言"不存在"，
  而"不存在"与"后端忘了算"长得一模一样。
- **AC1 的「对方改名后自动跟着变」靠每次实时查投影层实现**，没有任何缓存
  （护栏禁通用缓存层，这里也没有可缓存的地方）。

#### 取数形态：整页一次，与被 @ 人数无关（AD-6）

固定两步：`resolveAll(viewerId, 整页并集)` → 每条 `pick(该条的 ids, 结果)`。
- 两条批量查询（昵称投影 + 双向拉黑），**游客只发一条**（与谁都没有拉黑关系）；
- 空入参一条都不发；重复 id 去重后只判一次（一页里好几条 @ 同一个人是常态）；
- ⚠️ 评论区一页是 10 条一级 + 30 条二级 —— 逐条判就是 80 次查询，所以
  `CommentQueryService` 把**内嵌的二级回复一并并进那一次**。

#### 三个出口都接上了（不是两个）

`FeedItemResponse` / `ContentDetailResponse` / `CommentResponse` 各加 `mentions`（空表不下发）。
Feed 那个 DTO 有四个组装点（首页两条排序路径共用的 `assemble`、顶置坑位、公开主页内容区、「我的发布」），
四处都走同一个工厂。漏掉任何一处的表现是「同一条内容在这儿能点、在那儿点不动」。

⚠️ **刻意没有「不带 mentions」的窄重载**：留一个短签名，下一个出口按自动补全挑了它
就会让那一屏的 @ 全变纯文字 —— 没有编译错误、没有测试兜底（见 code-review 第 4 条）。

⚠️ **H5 分享页（`SharedPostResponse`）不接**：那是给站外访客的服务端直出页，没有 viewer
也就无从判拉黑，且站外没有主页可跳。@ 在那里保持纯文字。

#### 前端：`MentionText`（富文本 + 手势）

- **`TapGestureRecognizer` 只在 `initState` / `didUpdateWidget` 建与放，绝不在 `build` 里**
  —— 见下方 code-review 第 2 条，这是本 story 最隐蔽的一个坑。
- 没有一处可点时**退化成纯 `Text`**（不白建 span 树、不挂 recognizer）。
  顺带保住了既有那些 `find.text(comment.body)` 的回归用例。
- 点 @ 与「整块进详情 / 点整条评论=回复」是**两个手势**，靠手势竞技场分开：
  span 上的 recognizer 命中更深、同一次点击只有一个赢家。
  这是唯一一句"靠框架行为"的断言，所以单独有一个文件钉着
  （`mention_tap_priority_test.dart`：点 @ 不进详情、点非 @ 区域照旧进详情）。
- 接入三处：Feed 卡片正文（`MasonryCard`，新增 `onTapMention`；**为空则只渲染纯文字**——
  共享件不该给没有跳转语义的调用方凭空多一个可点片段）、详情页正文、评论正文。
- `AccountActionEntry` 新增 `mention('mention')`：**只新增、不改任何既有值**
  （改字面量会把既有那几条时间序列断成两截）。
  ⚠️ `mention_tapped` 事件本身属 **Story 3.5 T2**，本条没有上报任何埋点。

#### 拉黑之后的收尾：三处入口口径一致

被 @ 的人**通常不是**卡片作者 / 评论作者 / 帖主，所以收尾回调一律按**被 @ 的那个 userId** 走，
不能与 `onAuthorTap` 共用（共用会把错的人从列表里清掉）。
详情页那处还额外 bump 一次评论刷新信号（会连带 invalidate `detailProvider`）——
不刷的话回到详情页那处 @ 仍是 `tappable=true`，可以立刻再点进刚拉黑那个人的主页（违反 AC3）。
⚠️ 详情页 @ 那处**刻意不传 `popContext`**（与作者入口不同）：拉黑被 @ 的人之后这条帖依然可见，
把用户踢回列表反而莫名其妙。

#### ⚠️ code-review 修掉 7 条

1. **渲染侧的 `@昵称` 定位没有词尾边界判定**（写入侧有、渲染侧漏了）：
   @ 过「An」的正文里写了「@Ana」时被切成 `@An` + 一个孤零零的 `a`，点进去是**错的人**。
   而且"长昵称先匹配"挡不住它 —— 长的那个一旦被拉黑 / 注销就压根不在候选里。
   **两处判定抽成同一份** `MentionToken`（前后都要求不是 Unicode 字母/数字/下划线），
   顺带修掉 `mail@Aurel` 这类误判、放行手写的 `(@Aurel)`。
2. **recognizer 在 `build` 里建又在 `build` 里 dispose**：`OneSequenceGestureRecognizer.dispose()`
   会 `resolve(rejected)`，所以手指按下到抬起之间发生任何无关重建（provider 刷新、键盘 inset、
   祖先 setState），正在竞技的 recognizer 被判负、**外层手势反而赢** ——
   点 @ 变成进详情页 / 弹回复框，且是间歇性的。改到 `initState` / `didUpdateWidget`，
   并给 `MentionView` 加值相等（否则每次父级重建都被当成"内容变了"）。
3. **两个被 @ 的人昵称一模一样时会把读者送进确定错误的主页**：改成那一处**一律不高亮**。
   写入侧同名的代价只是多发一条通知（已作为已知不精确接受），这里代价大得多。
4. **四个「不带 mentions」的窄重载一个调用点都没有**，却会静默把 `mentions` 写成 null →
   全部删除（见上）。
5. **详情页 @ 拉黑后不刷新本页** → 那处 @ 仍可点、他的评论还挂着（见上）。
6. `ContentDetailResponse` 的 `{@link MentionView}` 在该文件不可解析（字段用全限定名、无 import）
   → 改成全限定 `{@link}`。
7. 新加的 javadoc 插在既有 doc 块与方法之间，把「⚠️ 要加字段就加在这里」那段顶成了悬空注释
   → 随第 4 条删掉窄重载后自动复位。

#### 🔸 一条已知取舍（记录在案，未自行加复杂度）

**对方改名之后，历史 @ 会退化成普通文字**（不高亮、点不动，但内容照常显示）。
原因：正文里存的是写入那一刻的「@旧昵称」（Story 3.2 AC4 的形态），后端下发的是**当前**昵称，
两者不一致时渲染侧定位不到那一段。

- 数据层没有问题 —— `mentioned_user_ids` 里那个 id 仍然指着对的人（AD-10 Rule 4 的初衷正是这个），
  Story 3.4 的通知也不受影响；受影响的只有**这一次渲染能不能定位到那串字**。
- 要彻底解决得在正文里埋可解析标记（AD-10 Rule 4 允许的另一种形态，如 `@{42}`），
  那意味着改掉 Story 3.2 已落库的正文格式，并连带审核 / 搜索 / H5 分享 / 通知预览等
  **所有拿 body 当纯文本的地方**。不在本 story 范围内自行改动。
- 退化后的样子与 Story 3.5「存量 @ 不回溯解析」渲染出来的完全一样，
  即这个状态本身是本功能已设计过的合法状态。
- **建议本地/产品确认**：改名频率是否低到可以接受；若不能，应作为一条独立决策记入决策日志。

#### 🔴 L1/L2 待本地验收清单

**L1（需 Docker + postgres + redis）**

1. **AC1 实时昵称**：A 发一条 @ 了 B 的帖 → 改掉 B 的昵称 → 重新 GET 详情，
   `mentions[0].nickname` 应为**新昵称**（这条只有真库能验）。
2. **AC3 拉黑双向**：B 拉黑 A（以及反过来 A 拉黑 B）各验一次 → A 看那条帖，
   `mentions[0].tappable=false` 且**没有 nickname 字段**。
3. **AC4 注销**：B 注销 → `tappable=false`、无 nickname。
4. **游客**：不带 Authorization 头取详情 → `tappable=true` 且**不发**拉黑那条查询
   （看 SQL 日志确认只有一条昵称投影查询）。
5. **整页一次**（AD-6）：造一页 20 条、每条各 @ 2 人（含重复的人），
   开 `show-sql` 确认 @ 相关查询**恰好两条**；评论区一页 10 条一级 + 30 条二级同样两条。
6. **四个 Feed 出口都带上了**：首页（两条排序路径）/ 顶置坑位 / 公开主页内容区 / 「我的发布」
   各取一次，`mentions` 都在。
7. **存量内容**：迁移前的帖子 / 评论读出来**没有 `mentions` 字段**（空表不下发）。

**L2（需模拟器 / 真机视觉）**

1. AC1：Feed 卡片正文、详情页正文、评论正文**三处**的 @ 都高亮（品牌色 + 加粗、无下划线）。
2. AC2：三处点 @ 都进那个人的公开主页；**点非 @ 区域行为一字不变**
   （Feed 卡片进详情、评论行弹回复框）。
3. 🔴 **手势不打架的实机复核**：点 @ 时不得出现「主页压在详情页上面」或「先弹回复框再跳主页」。
   L0 已钉住逻辑，但实机上还要看动画有没有重叠。
4. AC3/AC4：拉黑一个被 @ 的人 / 找一个已注销账号被 @ 的历史内容 → 那处 @ 是普通文字、点不动。
5. **拉黑后就地生效**：在详情页点 @ 进主页 → 拉黑 → 返回详情页，那处 @ 应**立刻**变成不可点
   （对应 code-review 第 5 条）。
6. Feed 卡片正文是 2 行截断的 —— @ 高亮跨行 / 被省略号截断时视觉不要出问题。
7. 长按选中文字与 @ 的点击不冲突（富文本区的既有交互）。
