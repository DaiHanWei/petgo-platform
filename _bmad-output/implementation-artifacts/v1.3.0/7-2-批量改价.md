### (b) 现在的改价路径是**读改写**，且审计不写数值

`petgo-backend/src/main/java/com/tailtopia/admin/shop/service/AdminShopProductService.java:91 upsertSku(long productId, ShopSkuForm form, long actorAccountId)`（`@Transactional:90`）：

- 编辑既有规格走 `:101-109`：`skus.findById` → 归属校验（越权按 404，不泄露存在性 `:105-107`）→ `sku.apply(specName, price, netWeightG, returnPolicy):108-109` → `skus.save(sku):111`。**JPA 脏检查的读改写，无条件写。**
- 审计 `:115-117`：`audit.record(actorAccountId, AuditActions.SHOP_SKU_UPSERTED, "SHOP_SKU", sku.getPublicToken(), (created ? "新建规格：" : "更新规格：") + sku.getSpecName())` —— 🔴 **摘要里没有价格数值**。
- 校验 `validateSku:208`：`:210-212` `if (f.getPrice() == null || f.getPrice() < 0) throw AppException.validation("价格必须为非负整数").code("admin.err.product.priceNonNegative")` —— 🔴 **单条编辑允许改到 0**。

⇒ 两条结论直接决定本 story 的 AC：

1. **批量改价不能复用 `upsertSku`**：它是读改写（破坏预览契约）、它顺带改规格名净含量退货政策（批量改价不该碰这些）、它的审计不写价格（批量场景下等于没审计）。批量改价必须走**新的条件写 + 新的审计动作码**。
2. **「不允许改到 0」是批量路径独有的收紧**，不是全局规则 —— 单条编辑仍允许 0（epics 原文「0 元商品须走单条编辑」正是指这条现存通路）。**不要顺手把 `validateSku` 也改成拒 0**，那会改掉一条与本 story 无关的既有能力。

### (c) 🔴 既有订单的价格是**快照且不可更新**，改价影响不到它

`petgo-backend/src/main/java/com/tailtopia/shop/order/domain/ShopOrderLine.java:23`（`@Table("shop_order_lines"):22`）：`unit_price`（`:41`）与 `line_total`（`:47`）**都是 `updatable = false`**，连同 `product_name:35` / `spec_name:38` / `qty:44` / `return_policy:51` 一起构成下单时刻的快照。

⇒ 「既有订单快照价格不受影响」是**结构性保证**，不是需要小心维护的约定。AC6 要求为它写一条断言，目的**不是**怕它坏，而是把这个保证钉在测试里：将来若有人为了「订单也要跟着改价」去掉 `updatable=false`，那条测试会先红。

### (d) 264 个规格与 100 行上限

SHOP-FR-15 `[ASSUMPTION]`（OD-7 已按推荐值实现）：单次 ≤100 行 ⇒ **264 个 SKU 的全场改价需分 3 批**（100 + 100 + 64）。
⚠️ 264 是 PRD 写作时的规格总数，**不是常量**。页面提示必须按**当前命中行数**算批次（`ceil(n / 100)`），不得把 3 写死。

### (e) 审计动作码现状：`AuditActions` 里没有任何批量类码

`petgo-backend/src/main/java/com/tailtopia/admin/audit/service/AuditActions.java` 的 `SHOP_*` 全集（`:124`~`:195`）：`SHOP_PRODUCT_CREATED:124` · `SHOP_PRODUCT_UPDATED:126` · `SHOP_SKU_UPSERTED:128` · `SHOP_PRODUCT_COST_UPDATED:130` · `SHOP_INVENTORY_RECEIPT_CREATED:134` · `SHOP_INVENTORY_DAMAGED:136` · `SHOP_INVENTORY_STOCKTAKED:138` · `SHOP_PRODUCT_LISTED:142` · `SHOP_BANNER_*:150-158` · `SHOP_PRODUCT_DELISTED:160` · `SHOP_SHIPPING_*:164-166` · `SHOP_PAWCOIN_RULES_UPDATED:170` · `SHOP_ORDER_*:174-185` · `SHOP_RETURN_*:189-195`。

## Acceptance Criteria

**AC1 · 两种输入模型** `[L0]`
**Given** 运营圈定了一批 SKU
**When** 选择改价方式
**Then** 支持且只支持两种：**设为固定价**（一个绝对值，全批相同）与**按百分比增减**（如 `+10%` / `-5%`）`[L0]`
**And** 两种方式都在**预览阶段**算出每行的新价，提交时带的是**算好的新价 + 预览时的旧价**（不是把百分比传到服务端再算一遍）`[L0]`
**And** 百分比的基数是**每行各自的现价**，不是全批统一基数 `[L0]`

**AC2 · 🔴 百分比结果向上取整到 100 印尼盾** `[L0]`
**Given** 某行现价 12 345，运营选 `+10%`
**When** 计算新价
**Then** 原始结果 13 579.5 → **向上取整到 100 的整数倍 = 13 600** `[L0]`
**And** **减价方向同样向上取整**（取更大的那个 100 倍数）—— 例如 12 345 的 `-5%` = 11 727.75 → **11 800**；取整方向由「向上」唯一决定，**不随增减方向翻转** `[L0]`
**And** 结果已经是 100 的整数倍时**不再上抬**（12 000 的 `+0%` 仍是 12 000）`[L0]`
**And** 用 `long` 运算，🔴 **不得出现 `double` / `float` / `BigDecimal` 的中间态**（`shop_skus.price` 的列注释 `V20260817_1154…:79` 原文「禁 DECIMAL/double —— 资金精度护栏」）；百分比本身用整数百分点或整数基点表达 `[L0]`
**And** 「固定价」方式**不做取整**（运营填多少就是多少，只受 AC3 约束）`[L0]`
**And** 单元测试覆盖边界：恰好整百、整百 +1、`+0%`、最大值不溢出 `long` `[L0]`

**AC3 · 🔴 不允许改到 0** `[L0/L1]`
**Given** 任一行的**结果价**为 0（固定价填 0，或百分比算出 0）
**When** 预览或提交
**Then** **整批拒绝**（不是跳过该行），错误文案说明「0 元商品请走单条编辑」`[L1]`
**And** 负数结果同样整批拒绝 `[L0]`
**And** 🔴 **单条编辑路径 `AdminShopProductService.validateSku:208-212` 一个字不改** —— 它允许 0 是既有能力，本 story 只收紧批量路径 `[L0]`
**And** 校验在**服务层**（页面同步提示，但不是唯一防线）`[L0]`

**AC4 · 条件写守卫 `WHERE price = :expectedPrice`** `[L0/L1]`
**Given** 7-1 的预览契约
**When** 执行某行的改价
**Then** 走新增的 `@Modifying` 条件写，WHERE 含 **`s.id = :skuId and s.price = :expectedPrice`**，返回影响行数 `[L0]`
**And** 影响行数 ≠ 1 ⇒ **整批回滚**并点名该行（走 7-1 框架的统一处置）`[L1]`
**And** 🔴 服务层**不得**先 `select` 比对旧价再 update（`SkuInventoryRepository` 类注释 `:14` 原文「禁应用层读改写」）`[L0]`
**And** 条件写同时更新 `updated_at`（形状照 `SkuInventoryRepository.java:117-119`）`[L0]`
**And** 条件写**只改 `price` 一列**，不碰 `spec_name` / `net_weight_g` / `return_policy` / `cost_price` `[L0]`

**AC5 · 预览展示每行改前改后 + 影响行数 + 分批提示** `[L0/L2]`
**Given** 圈定命中 N 行
**When** 打开预览
**Then** 逐行显示：商品名 / 规格名 / **改前价 → 改后价**；顶部显示**影响行数 N** `[L2]`
**And** 🔴 N > 100 时预览就拒绝，并提示「单次最多 100 行，本次命中 N 行，需分 `ceil(N/100)` 批」—— **批次数按 N 算，不写死 3** `[L0/L2]`
**And** 页面的上限数字取 7-1 的同一常量，不硬编码 `[L0]`
**And** 金额按既有后台口径显示（IDR 整数千分位，B.6）`[L0]`

**AC6 · 逐条审计，且摘要**含**价格数值** `[L0/L1]`
**Given** 一批成功改了 N 行
**When** 事务提交
**Then** 新增**恰好 N 条**审计，动作码为新增的 `SHOP_SKU_PRICE_UPDATED`，`targetType="SHOP_SKU"`，`targetId=sku.publicToken` `[L1]`
**And** `summary` 形如「批量改价：<商品名> <规格名> 12 345 → 13 600」，🔴 **必须含改前与改后数值** `[L1]`
**And** 🔴 **不得照抄 `SHOP_PRODUCT_COST_UPDATED` 的「审计不写数值」处置** —— 那条是因为**进货价**受 `shop.cost_view` 门控、写进审计等于绕过权限位（`AdminShopProductService.java:122-125` 与 `InventoryMovementService.java:30-32` 的注释）。**售价对所有用户公开，不是敏感数据**，不写数值等于审计没用 `[L0]`
**And** 计数用差值断言（== N），不是「至少一条」`[L1]`

**AC7 · 🔴 既有订单快照价格不受影响** `[L1]`
**Given** 某 SKU 已有一笔历史订单，订单行 `unit_price` = 12 345
**When** 批量把该 SKU 改成 13 600
**Then** 该订单行的 `unit_price` 与 `line_total` **一个字节未变**，订单 `goodsSubtotal` / `totalAmount` 未变 `[L1]`
**And** 测试注释写明：这条钉的是 `ShopOrderLine.java:41/:47` 的 `updatable=false`，**删掉它等于允许改价回溯改历史订单** `[L1]`

**Then** 端点 `@PreAuthorize` 用 `shop.bulk_edit`（7-1 新增），**不另加权限码** `[L0]`
**And** 二次确认走后台模板确认态，**不是浏览器 `confirm()`**（UX-S4）`[L0/L2]`
**And** 整批一个事务、全成或全不成（7-1 AC3）`[L1]`
**And** 新增文案进 4 个 properties（`messages{,_zh_CN,_en,_id}.properties`），key 前缀 `admin.v130.shopBulk.price.*` / `admin.err.shopBulk.price.*`；🔴 模板不写死中文 `[L0]`

**AC9 · 🔴 变异验证** `[L0]`
**When** 把 AC4 的 `and s.price = :expectedPrice` 从条件写里删掉
**Then** 必须有**具名测试变红** `[L0]`
**And** 把 AC2 的向上取整改成四舍五入或截断，取整边界测试必须变红 `[L0]`

## Dev Notes

### 🔴 为什么百分比要「向上取整」而不是「四舍五入」，以及减价方向为什么也向上

SHOP-FR-15 原文只有一句「百分比结果向上取整到 100 印尼盾」，没写方向例外。实现时最容易自作主张的地方是：「减价的时候向上取整不就等于少减了吗？应该向下吧。」——**不要这么想**：

1. 「向上」是对**结果值**说的，不是对**变化方向**说的。一个函数只有一种取整规则，才可能被测试钉住；随方向翻转的规则在代码里会长成两个分支，而那两个分支里必然有一个没人验过。
2. 印尼盾的最小实用面额决定了尾数必须归整，归整往哪边是**商业口径**，产品给的是「向上」。向上意味着永远不会因为取整而少收钱 —— 这是安全方向。
3. 运营在预览页上看到的是**算好的最终价**，不是百分比。他要是觉得 11 800 不对，改成固定价即可。

⚠️ 所以 AC2 明确要求「取整方向由『向上』唯一决定，不随增减方向翻转」，并要求减价方向单独有一条测试。

### 🔴 「不允许改到 0」只收紧批量路径

`AdminShopProductService.validateSku:210-212` 现在的规则是「非负」，即单条编辑可以设 0。epics 写「0 元商品须走单条编辑」正是承认这条通路存在。
所以本 story：**只在批量路径上加非 0 校验，不动 `validateSku`**。把 `validateSku` 也改成拒 0，等于在一个「批量改价」的 story 里顺手删掉了一项与它无关的既有能力 —— 这种改动在 review 里最难被发现，因为 diff 看起来「更严格了所以更好」。

另：DB 层 `ck_shop_skus_price CHECK (price >= 0)`（`V20260817_1154…:70`）**允许 0**，也不改 —— 改既有 CHECK 要 `DROP+ADD`，且会挡住单条编辑的合法用法（CLAUDE.md 纪律 5 与 F-2）。

### 🔴 为什么审计摘要必须写价格，而进货价的审计不写

两条规则看起来矛盾，根子是**权限门控范围不同**：

| | 进货价 `cost_price` | 售价 `price` |
|---|---|---|
| 谁能看 | 受 `shop.cost_view` 门控；无权限时服务端**根本不放进 model**（`AdminShopProductController.java:44-47` 类注释：「模板里用 `th:if` 隐藏可通过看源码绕过」） | **所有 App 用户**都看得到 |
| 审计能不能写数值 | 🔴 **不能** —— 审计日志页的可见范围与 `shop.cost_view` 不同，写进去等于绕过权限位（`AdminShopProductService.java:122-125`、`InventoryMovementService.java:30-32` 两处注释同一口径） | ✅ **必须写** —— 不写就无法回答「这批改价把价格从多少改到了多少」 |

实施时最可能出的错：看到 `SHOP_PRODUCT_COST_UPDATED` 的注释写着「绝不写数值」，就把批量改价也写成不带数值。**新动作码的 javadoc 必须显式写出这个区别**（T4），否则下一个人还会犯同一个错。

### 为什么不复用 `upsertSku`

三个理由，缺一不可：
1. **读改写**：`sku.apply(...)` + JPA 脏检查（`AdminShopProductService.java:108-111`），没有条件写 ⇒ 预览契约无从谈起。
2. **改动面过宽**：`apply(specName, price, netWeightG, returnPolicy)`（`ShopSku.java:83`）一次改四个字段。批量改价只该改价；复用它就得给另外三个字段回填「当前值」，而那个回填**又是一次读改写**。
3. **审计不对**：`SHOP_SKU_UPSERTED` 的摘要是「更新规格：<规格名>」，批量 100 行会产出 100 条完全一样、不含价格的审计。

### 264 与 3 都不是常量

PRD 里的「264 个规格分 3 批」是当时的规格总数推出来的例子。页面提示必须按**本次命中行数**算（`ceil(N/100)`）。把 3 写进文案，等于第 265 个规格上线那天页面开始说谎。
