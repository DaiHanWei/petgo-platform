## Context

### (a) 上下架的现状：**布尔列、无状态枚举**，且现有服务是读改写 + 幂等吞掉

| 层 | 事实（file:line） |
|---|---|
| 表 | `petgo-backend/src/main/resources/db/migration/V20260817_1154__init_shop_products_and_skus.sql:19` 建 `shop_products`；`is_active BOOLEAN NOT NULL DEFAULT FALSE`（`:37`，行内注释「上下架（维护逻辑属 1.5）；新建默认未上架」）。🔴 **没有状态枚举列、没有 `status VARCHAR + CHECK`** |
| 实体 | `petgo-backend/src/main/java/com/tailtopia/shop/domain/ShopProduct.java:31`（`@Table("shop_products"):30`）：`@Column(name="is_active", nullable=false):110` → `private boolean active;:111`；`publicToken:37`（len 32、`updatable=false`）；`category:47-48`（当前是 `ProductCategory` 枚举，列 `category VARCHAR(24)`）；新建时 `p.active = false;:140`；`list():178`（`this.active = true;:179`）· `delist():196`（`this.active = false;:197`）· `isActive():302` · `getCategory():229` |

| 仓储 | `petgo-backend/src/main/java/com/tailtopia/shop/repository/ShopProductRepository.java` —— 🔴 **无任何 `@Modifying` 条件写**，全是查询方法 |

`AdminShopListingService` 的两个方法都有**两处会破坏预览契约**的行为：

```java
// list :94-120
public ShopProduct list(long productId, long actorAccountId) {
    ShopProduct p = require(productId);
    if (p.isActive()) { return p; }          // ← 🔴 幂等：已上架再点一次不报错、不重复写审计
    …上限校验（见下）…
    p.list();                                 // ← 🔴 读改写（JPA 脏检查），不是条件写
    audit.record(…SHOP_PRODUCT_LISTED…);
}
// delist :123-133 同形：if (!p.isActive()) { return p; } → p.delist() → audit(SHOP_PRODUCT_DELISTED)
```

⇒ **批量上下架不能循环调它们**：
1. **读改写** ⇒ 没有条件写守卫 ⇒ 「预览即契约」无从谈起。
2. **幂等静默返回** ⇒ 预览时是「下架」、提交时已被别人改成「上架」，`list()` 会**直接 return、当成功**。这正是 AD-S5 要拦的那种情况，却被幂等吞掉了。

⚠️ 但 **`list()` 的幂等对它自己的场景是对的**（运营连点两下按钮不该报错），本 story **不改它**。

### (b) 上架的 SKU 上限 —— 批量场景下不能逐行判

`AdminShopListingService` 有一套上限机制（类 javadoc `:22-31` 详述）：
- `activeSkuCount():59` = 在售商品（`is_active=true`）的 **SKU 总数**（`skus.countActiveSkus()`），🔴 **不是商品数**。类注释 `:53-57` 原文：「不要在别处再写一遍这个查询：两处一旦漂移……表现就是『明明报警了却还能上架』，而两边各自的测试都会是绿的」。
- `skuCap():64` 取 `@Value("${petgo.shop.sku-cap:0}")`（`:41-46`），🔴 **默认 0 = 不限**（2026-08-19 产品决策，机制整套保留）。
- `capEnabled():75` = `skuCap > 0`；`atOrOverCap():81`。
- `list()` 的判定 `:103-106`：**看的是「上架之后」的总数**（`activeSkuCount() + 本商品自己的 SKU 数`），javadoc `:89-91` 解释「只看『当前是否已达 30』会让一个 3 SKU 的商品在 28 时被放行到 31」。
- 超限文案 `:107-110` + i18n `admin.err.product.skuCapExceeded`（`messages_zh_CN.properties:1901`）。

🔴 **批量上架必须一次性判定整批之后的总数**：`activeSkuCount() + Σ(本批各商品的 SKU 数)`。逐行调 `capEnabled() && after > skuCap` 会得到一个随循环变化的 `activeSkuCount`（前面的行已经改了库），在「上限开启」时放行出超限结果。
⚠️ 上限**当前默认关闭**，所以这条在默认配置下测不出来 —— AC 要求测试**显式把 `petgo.shop.sku-cap` 设成正数**再跑。

### (c) 🔴 下架只改可见性，不动库存 —— 这是电商一期已定的口径

`AdminShopListingService` 类 javadoc `:19-21` 原文：

> **SPEC-7 口径（2026-08-17 产品拍板）：下架 = 只改可见性。** 已下单未支付的用户照常付款履约；召回场景走决策 S-3 的「AB-11D 手工选单取消」。

`delist()` 的方法 javadoc `:121-122` 再说一遍：「🔴 **不做上限校验、不碰库存、不取消订单、不发通知**」。
另：`list()` 的上限只约束上架方向，类注释 `:16-18` 解释「若给下架也加上限校验，会出现『超限了反而下架不掉』的死锁」。

⇒ 本 story 不改这个口径，但 SHOP-FR-16 要求**把它写到页面上给运营看**。原因：批量下架 50 个商品时，运营脑子里的问题是「那库存怎么办」，没人会去翻 SPEC-7。

### (d) 品类现状与 6-1 之后的形态

**当前（6-1 之前）**：`ProductCategory` 是枚举（`petgo-backend/src/main/java/com/tailtopia/shop/domain/ProductCategory.java`，四值 `MAKANAN:11` / `OBAT_VITAMIN:13` / `CAMILAN:15` / `PERAWATAN`），落库 `shop_products.category VARCHAR(24)` + CHECK `ck_shop_products_category`（`V20260817_1154…:40`）。**没有「停用」这个概念** —— 枚举值全都是启用的。

**6-1 之后（AD-S1）**：
- 新表 `shop_categories`（`code` UNIQUE / `name_id` / `name_en` / `sort_weight` / **`is_active`**）。
- `ck_shop_products_category` **被删**，改为 `fk_shop_products_category FOREIGN KEY (category) REFERENCES shop_categories(code)`。
- `ShopProduct.category` **由枚举改为 `String categoryCode`**；`ProductCategory` 枚举退出持久层与 DTO、保留为 `@Deprecated` 常量持有者。
- 品类中文名以代码为准（SD-15）：`OBAT_VITAMIN` = 驱虫保健，`PERAWATAN` = 洗护。

🔴 **本 story 的条件写要写在 6-1 之后的形态上**。`WHERE category = :expectedCategory` 的参数类型是 `String`（code），不是枚举。字段名（`category` 还是 `categoryCode`）**以 6-1 的实际产出为准，实施时确认**。

⚠️ 外键 `fk_shop_products_category` 保证了「不存在的 code 写不进去」，但**不保证 code 对应的品类是启用的**（FK 不看 `is_active`）。「目标品类必须启用」是**服务层规则**，DB 兜不住。

## Acceptance Criteria

**AC1 · 批量上架 / 下架：条件写 `WHERE is_active = :expectedActive`** `[L0/L1]`
**Given** 预览时某商品 `is_active=false`
**When** 提交「批量上架」
**Then** 走新增的 `@Modifying` 条件写，WHERE 含 **`p.id = :productId and p.active = :expectedActive`**，返回影响行数 `[L0]`
**And** 影响行数 ≠ 1 ⇒ **整批回滚**并点名该行（走 7-1 框架的统一处置）`[L1]`
**And** 🔴 **不得循环调 `AdminShopListingService.list()` / `delist()`** —— 它们是读改写，且对「已是目标状态」**静默幂等返回**（`:99` / `:126`），会把「预览后被别人改掉」当成功（详见 Context (a)）`[L0]`
**And** 🔴 `AdminShopListingService` 的 `list()` / `delist()` 在本次 diff 中**零改动** —— 它们的幂等对单条按钮场景是对的 `[L0]`
**And** 条件写同时更新 `updated_at`，且**只改 `is_active` 一列** `[L0]`

**AC2 · 🔴 下架只改可见性、不动库存，且页面显式写给运营看** `[L0/L1/L2]`
**Given** 某商品的 SKU `actual=50`、`locked=8`
**When** 批量下架该商品
**Then** `sku_inventory` 的 `actual` 与 `locked` **一个字节未变**；不取消任何订单、不发任何通知 `[L1]`
**And** 🔴 批量下架的**输入区与确认态都显式写明**：「下架只让商品在 App 中不可见，**不影响库存数量**；已下单未支付的订单照常付款履约；需要召回请走异常订单处理」（沿用 `AdminShopListingService` 类 javadoc `:19-21` 的 SPEC-7 口径原意）`[L2]`
**And** 该文案进 4 个 properties，key 如 `admin.v130.shopBulk.delist.noticeStock`；🔴 **模板不写死中文** `[L0]`
**And** 集成测试逐字段断言库存未变，注释写明它钉的是 SPEC-7 口径 `[L1]`

**AC3 · 批量上架的 SKU 上限一次性判定** `[L0/L1]`
**Given** `petgo.shop.sku-cap` 被设为正数 C（**默认 0 = 不限**，`AdminShopListingService.java:41-46`）
**When** 批量上架一批商品
**Then** 判定用 **`activeSkuCount() + Σ(本批各商品的 SKU 数)`** 与 C 比，**一次算完、一次判定** `[L0]`
**And** 🔴 **不得逐行判**（逐行时 `activeSkuCount()` 会随循环变化，在开启上限时放行超限结果）`[L0]`
**And** 超限 ⇒ 整批拒绝（预览阶段就拒），复用既有文案 key `admin.err.product.skuCapExceeded`（`messages_zh_CN.properties:1901`）或新增批量版 `[L0/L1]`
**And** 🔴 在售 SKU 数**只调 `AdminShopListingService.activeSkuCount():59`**，**不另写一遍那个查询**（类注释 `:53-57` 明令）`[L0]`
**And** 集成测试**显式把 `petgo.shop.sku-cap` 设成正数**再跑（默认 0 时这条测不出来）`[L1]`
**And** 🔴 **批量下架不做上限校验**（上限只约束上架方向，否则「超限了反而下架不掉」，类注释 `:16-18`）`[L0/L1]`

**AC4 · 批量调品类：条件写 `WHERE category = :expectedCategory`** `[L0/L1]`
**Given** 预览时某商品品类为 `MAKANAN`
**When** 提交「调为 `CAMILAN`」
**Then** 条件写 WHERE 含 **`p.id = :productId and <品类字段> = :expectedCategory`**（字段名与类型以 6-1 产出为准，参数是 **code 字符串**）`[L0]`
**And** 影响行数 ≠ 1 ⇒ 整批回滚并点名该行 `[L1]`
**And** 条件写**只改品类一列** + `updated_at` `[L0]`
**And** 整批只有**一个目标品类**（不逐行指定），预览逐行显示「原品类 → 目标品类」`[L0/L2]`

**AC5 · 🔴 目标品类必须是启用状态** `[L0/L1]`
**Given** `shop_categories` 中某品类 `is_active=false`（6-1 产出）
**When** 运营把它选为批量调品类的目标
**Then** **预览阶段就拒绝**，文案「目标品类已停用，不能作为调整目标」`[L1]`
**And** 页面的目标品类下拉**只列启用品类**（双保险，但服务层是唯一防线）`[L0/L2]`
**And** 🔴 外键 `fk_shop_products_category`（6-1 建）只保证 code 存在、**不看 `is_active`** ⇒ 这条规则 DB 兜不住，服务层必须校验 `[L0]`
**And** 目标 code 不存在时同样整批拒绝（不要让 FK 抛 `DataIntegrityViolation`，运营看到的会是堆栈）`[L0/L1]`
**And** ⚠️ **源品类是否停用不设限**：从停用品类里把商品搬走恰恰是运营停用品类后要做的事 `[L0/L1]`

**AC6 · 逐条审计** `[L0/L1]`
**Given** 一批成功改了 N 行
**When** 事务提交
**Then** 新增**恰好 N 条**审计，`targetType="SHOP_PRODUCT"`、`targetId=product.publicToken` `[L1]`

**AC7 · 两者共用 7-1 的预览、确认、审计、上限与权限码** `[L0/L1]`

## Dev Notes

### 🔴 为什么不能循环调 `AdminShopListingService.list()` —— 与 7-3 的结论相反，理由也相反

7-3 的结论是「复用既有服务方法（加个重载）」，本 story 的结论是「不复用，新造条件写」。看起来矛盾，其实是同一个判据的两种答案：

| | 7-3 盘点 | 7-4 上下架 |
|---|---|---|
| 既有方法的判定层 | 判定在 **SQL 的 WHERE 里**（`stocktakeTo` 的双守卫），方法只是把前值读来传进去 | 判定在 **Java 里**（`if (p.isActive()) return p;`），写入是 JPA 脏检查 |
| 能不能改造成用预览值 | 能 —— 加个参数把 `readActual` 换掉，**SQL 一行不动** | 不能 —— 要把读改写整个换成条件写，等于重写该方法，而重写会破坏它的单条语义 |
| 结论 | **复用原语 + 加重载** | **新造条件写，既有方法零改动** |

判据是一句话：**判定在不在 SQL 里**。在，就有得复用；不在，复用只会把「看起来成功」的幂等带进批量场景。

而幂等在批量里为什么致命：运营预览时看到 50 个「未上架」，提交前有人上架了其中 3 个。`list()` 对这 3 个静默 return，整批报「成功 50 条」。运营以为自己上架了 50 个，实际上有 3 个是别人上架的——他不知道，也没有任何地方告诉他。这跟 7-1 Dev Notes 里说的「跳过 3 行」是同一个病。

### 🔴 上限判定为什么必须一次算完

`AdminShopListingService.list()` 的 javadoc `:89-91` 已经踩过一次这个坑：「只看『当前是否已达 30』会让一个 3 SKU 的商品在 28 时被放行到 31」。批量版是它的加强版 —— 逐行判时，`activeSkuCount()` 在第二行就已经包含了第一行刚上架的 SKU，看起来「每一步都没超」，但整批的目标集合从来没被整体评估过。

⚠️ 这条在**默认配置下测不出来**（`petgo.shop.sku-cap` 默认 0 = 不限，`:41-46`）。所以 AC3 要求测试显式设正数。不设就等于这条 AC 没验。

### 🔴 「下架不动库存」为什么要写到页面上

SPEC-7 的口径存在于三个地方：类 javadoc（`AdminShopListingService.java:19-21`）、方法 javadoc（`:121-122`）、和产品的记忆里。运营的界面上一个字都没有。

单条下架时这不要紧（一次一个，出了问题看得见）。批量下架 50 个商品时，运营下一句话必然是「那这 50 个商品的库存怎么算」——如果页面不答，他会去问技术，或者更糟：他会自己先把库存清零再下架。SHOP-FR-16 写「页面上显式写给运营看」，要还的就是这笔债。

文案要同时回答三件事：① 库存不动；② 已下单未支付的照常履约；③ 要召回走异常订单。少一件都会引出下一个问题。

### 🔴 目标品类的启用校验，外键兜不住

6-1 会用 `fk_shop_products_category`（FK to `shop_categories.code`）取代 `ck_shop_products_category`（AD-S1，理由是「根除重建 CHECK 时照着过期列表抄的事故模式」）。FK 保证 code 存在，**不看 `is_active`**。

所以「不可调入已停用品类」（SHOP-FR-18）**只能在服务层**。而且要在**预览阶段**就拒 —— 让运营在选完 80 个商品之后才在提交时被打回，是最差的时机。

同时：**源品类停用不设限**。SD-15 的停用语义是「App 不展示、购物车不可结算、历史订单照常、数据保留」，运营停用一个品类之后要做的第一件事往往就是把里面的商品搬到别的品类去。禁止从停用品类搬出，等于把商品锁死在停用品类里。

### 审计：为什么复用两个、新增一个

- 上下架：`SHOP_PRODUCT_LISTED` / `SHOP_PRODUCT_DELISTED` 已存在（`AuditActions.java:142` / `:160`），批量与单条**做的是同一件事**，区分靠 summary 前缀（「批量上架：」）。新增 `SHOP_PRODUCT_BULK_LISTED` 只会让审计查询变成「要记得查两个码」。
- 调品类：**没有任何既有码**（shop 段 `:124-195` 全集里没有 category 相关的）。单条改品类现在走 `SHOP_PRODUCT_UPDATED`（`:126`，`AdminShopProductService.update:67` 的整体表单更新），但那是「改了商品的某些字段」，不是「换了品类」。批量调品类值得一个自己的码，因为它是运营会专门去查的动作。

摘要记 **code 不记显示名**：显示名是运营可改的（SD-15），审计要在改名三个月后仍然读得懂「MAKANAN → CAMILAN」。

### 与 7-3 相同的未拍板项：`shop.bulk_edit` 是否叠加资源权限

7-3 AC7 与本 story AC7 提的是同一个问题。**两处结论必须一致**，在实施时一起确认并写进两个 story 的 Completion Notes。推荐「两者都要」（`bulk_edit` + `product_edit`），理由与本仓已有的叠加先例一致（`InventoryMovementType.PURCHASE_INBOUND` 的 javadoc `:18-19`：采购入库另需 `shop.cost_edit`）。
