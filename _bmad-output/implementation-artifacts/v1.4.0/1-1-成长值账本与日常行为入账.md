## Story

As a 活跃用户,
I want 登录、发帖、评论、点赞、打卡、完成里程碑、被收藏、送收礼都按规则自动得到 EXP，取消或违规时按规则扣回,
so that 我在平台上的投入被持续记下来。

**AC3 — 入账引擎 `GrowthLedgerService.accrue / reverse`** `[L0]` `[L1]`（AD-5、§5.3、§5.4）
1. `accrue(AccrualCommand cmd)`，`AccrualCommand(userId, RuleCode rule, Integer pointsOverride, String idemKey, String refType, String refId, List<Long> petIds, Instant occurredAt)`；`wibDate = occurredAt` 在 `ScheduleWindow.WIB` 下的日期。同一 `@Transactional` 内按序：
   ① 参与判定（与 `AccountQueryService.isActiveRegularUser`（:74-81）**同一口径**）：`users.role = 'USER'`（官方号 `role = ADMIN` 不参与）、`account_type = 'REAL'`、`deleted_at IS NULL`、`status = 'ACTIVE'`，否则直接返回（不建账户行、不写任何东西）。⚠️ 官方号是否参与 PRD 未定，本 story 暂按不参与实现，见 Dev Notes「待确认」；
   ② 规则 `enabled = false` → 返回；
   ③ `insertIfAbsent` + `lockById` 锁账户行（同一用户的入账从此串行）；
   ④ 幂等：`idem_key` 已存在 → 返回（**不消耗额度**）；
   ⑤ 领额：有 `daily_cap` 的主动规则按「次」领 1，剩余 0 次 → 返回；`cap_group = 'PASSIVE'` 的规则按「分值」领，`grant = min(points, 50 − 已用)`（50 读 `PASSIVE_GROUP.daily_cap`），`grant = 0` → 返回；无上限规则不领额；
   ⑥ 插流水（`delta = grant` 或规则分值 / `pointsOverride`），万一撞 `idem_key` 唯一约束（理论上已被 ③④ 挡住）→ 让整笔事务回滚，额度一起回滚；
   ⑦ `lifetime_total += delta`。
   幂等键冲突与额度不足都以「不入账」结束，**不抛给监听方**。
2. `reverse(ReverseCommand cmd)`，`ReverseCommand(String originalIdemKey, ReverseReason reason, String sourceKey, Integer amountOverride)`：按原幂等键找原流水 → 不存在（当初因额度 / 不参与没入账）→ 返回（AC14）→ 锁原流水所属账户 → 已扣总和（`SUM(-delta) WHERE reverses_id = 原id`）≥ 原入账 → 返回 → 本次扣减 = `min(amountOverride ?: 原 delta, 原 delta − 已扣, lifetime_total)`（累计不为负，截断后流水记**实际**扣减值；为 0 则不插行）→ 插反向流水（`rule_code` 同原流水、`delta` 为负、`reverses_id = 原id`、`reason`、`idem_key = GrowthIdemKeys.reverse(原id, sourceKey)`）→ `lifetime_total -= 扣减`。**不改、不删原流水；不返还当日额度**（AD-3）。
3. **本 story 不重算等级**：`lifetime_total` 变化后预留一个私有收口方法（如 `applyDelta(account, delta, source)`），Story 1.2 在此接 `GrowthLevelChangeHandler`。本 story 内 `growth_accounts.level` 保持 1。
4. 写成长值的只有本服务（§5.4）；其他模块只发事件。

**AC6 — 每日登录 `DAILY_LOGIN`** `[L0]` `[L1]`（PRD AC1）
- Given 真实用户当天（WIB）首次发起已认证请求，When `user_active_days` 首次写入成功，Then 入账一条 `DAILY_LOGIN` +3；同日后续请求不再入账；跨 WIB 零点（UTC 17:00）后可再得。
- 监听：`@Async @EventListener`（filter 无事务上下文，不能用 `@TransactionalEventListener`）。幂等键含 `wibDate`。

**AC7 — 发帖 `POST_PUBLISHED`** `[L0]` `[L1]`（PRD AC15）
- Given 用户当天已发 3 帖，When 发第 4 帖，Then 第 4 帖不入账；私密 Diary（`visibility = PRIVATE`）与公开帖同样 +5 并计入 3 次；同一帖因举报预处置（`applyReportHoldIfPublished`）后再审核通过而二次发布事件时，只入账一次（键 `POST:{postId}`）。
- `ref_type = 'CONTENT_POST'`、`ref_id = postId`、`pet_ids = [event.petId]`（非空时）。

**AC8 — 被动合计 50** `[L0]` `[L1]`（PRD AC2）
- Given 作者当天被点赞 / 被评论 / 被收藏已累计 48，When 再被评论一次（+3），Then 只入账 2，被动合计恰好 50；之后当天被动类不再入账。

**AC9 — 点赞与取消点赞** `[L0]` `[L1]`（PRD AC3 / AC14、AD-6）
- Given A 对作者 B 的帖子点赞，When A 点赞 → 取消 → 再点赞，Then A 的 `LIKE_GIVEN` 与 B 的 `LIKE_RECEIVED` 最终都为 +1 −1 +0；取消点赞时若 B 当初因满 50 未入账，则 B 不被扣（AC14）。
- 取消点赞扣回 `reason = UNLIKE`；**不返还** A 当天的 5 次点赞额度。

**AC10 — 评论** `[L0]` `[L1]`（PRD AC15、P-2）
- Given 用户在自己的帖子下评论或回复别人，When 评论变为可见（`ContentCommentedEvent`），Then `COMMENT_POSTED` 与 `COMMENT_RECEIVED` 都不入账，也不占当天 5 次额度。
- 他人评论或回复时：评论人 `COMMENT_POSTED` +2；`COMMENT_RECEIVED` +3 **只给帖子作者**（`contentAuthorId`），不给被回复者（`parentAuthorId`）。
- `contentAuthorId == -1`（帖已消失的兜底值，见 `CommentService.publishCommented` 调用处）→ 不发 `COMMENT_RECEIVED`。

**AC11 — 收藏（④ 的事件，① 只监听）** `[L0]` `[L1]`（PRD AC14a）
- Given `ContentCollectedEvent` / `ContentUncollectedEvent`，When 收藏 → 取消 → 再收藏，或收藏人就是作者，Then 作者最终 +2 −2 +0；作者自收藏不入账。④ 合并前无事件，规则自然不触发；本 story 用测试直接 `publishEvent` 验证。

**AC12 — 里程碑同 code 最多 5 次** `[L0]` `[L1]`（PRD AC15a）
- Given 同账号同一里程碑代码已入账 5 次，When 第 6 次完成该里程碑，Then 里程碑与徽章照常完成，无成长值流水。
- `MILESTONE_S/M/L` 按 `event.level` 选；`ref_type = 'MILESTONE'`、`ref_id = code`、`pet_ids = [petId]`；5 次判定 = 账户行锁内 `COUNT(*) WHERE user_id AND rule_code IN (MILESTONE_*) AND ref_id = code AND delta > 0`。

**AC13 — 打卡 `PLACE_CHECKIN`** `[L0]` `[L1]`
- 每次打卡（一个 `checkinId`，可含多只宠物）入账一次 +5，每日 3 次；`ref_type = 'PLACE_CHECKIN'`、`ref_id = checkinId`、`pet_ids = event.petIds`。

**AC14 — 违规下架只扣发帖分** `[L0]` `[L1]`（PRD AC7、P-1）
- Given 运营违规下架一条帖子，When `ContentRemovedEvent` 发出，Then 只扣回该帖的 `POST_PUBLISHED`（`reason = TAKEDOWN`），被赞 / 被评 / 被收藏所得不扣；作者自删帖、评论被删不扣（这些路径不发 `ContentRemovedEvent`，本 story 不新增监听）；下架后 `restore()` 不补回。

**AC15 — 送礼（③ 的事件，① 只监听）** `[L0]` `[L1]`
- Given ③ 发出 `GiftSentEvent`（`totalAmount` = Rp12,500），When 监听处理，Then 送礼人 `GIFT_SENT` 入账 63（12.5 × 5 = 62.5 → HALF_UP 63）、宠物主人 `GIFT_RECEIVED` 入账 50，不设上限；③ 合并前无事件，规则自然不触发。
- 换算 `BigDecimal(totalAmount) × points / unit_amount`，`RoundingMode.HALF_UP`，结果 0 不入账；`ref_type = 'GIFT_ORDER'`、`ref_id = giftOrderId`、`pet_ids = [petId]`。**不走消费返**（Story 1.3 排除 `GIFT`）。

**AC16 — 不参与者没有任何流水** `[L0]` `[L1]`（PRD AC12）
- Given 虚拟号作者、官方号（`role = ADMIN`，暂定，见待确认）、已注销或已停用用户，When 其行为或他人对其互动触发任何规则，Then 该用户没有任何流水；真实点赞人的 `LIKE_GIVEN` 照常。

**AC17 — 测试与回归** `[L0]` `[L1]`（§5.7）
1. 每条规则至少「正常 / 当日满额 / 幂等重放 / 扣回（有扣回的规则）」四类用例；被动合计与日额度有**两线程并发**测试不超上限；流水只追加，扣回为指向原流水的反向记录。
2. `mvn -B clean package` 绿；`ck_*` 共享约束未改（`MentionNotifyTest` 绿）。

### 幂等键说明（与架构文字的统一）

- AD-5 写「反向流水幂等键 `REV:{原id}:{来源键}`」，AD-9 写「退款 `REV:REFUND:{refundKey}`」。统一为 `GrowthIdemKeys.reverse(原id, sourceKey)`，退款时 `sourceKey = "REFUND:" + refundKey`（Story 1.3），最终形如 `REV:123:REFUND:rf_xxx`。同一笔退款可能对应多条原流水时各自唯一；同一原流水被多笔部分退款时各笔 sourceKey 不同。Completion Notes 记一句即可。
- 取消点赞 / 取消收藏 / 下架的 sourceKey 固定（`UNLIKE` / `UNCOLLECT` / `TAKEDOWN`），因为原入账终身一次，扣回也只能一次。

### 监听写法

- `GrowthActivityListener`、`GrowthGiftListener`：每个方法 `@Async` + `@TransactionalEventListener`（默认 AFTER_COMMIT）+ 方法上 `@Transactional`（照 `MilestoneAutoCompleteListener`）；**例外** `UserDailyActiveEvent` 用 `@Async @EventListener`（发布方 filter 不在事务里）。
- 失败记 `log.error`（只记 userId / 规则代码 / 异常类名），**不重试**（V1 姿态，运营可手动补）。**禁止**记评论原文、昵称。
- 监听只拼 `AccrualCommand` / `ReverseCommand`，**不判规则、不写表**；参与判定、额度、幂等全在 `GrowthLedgerService`。
- 自评过滤（评论人 = 帖子作者）、自收藏过滤（收藏人 = 作者）放在监听里——这是「事件语义」过滤，不是规则判定。

### 架构约束

- AD-1：无账户行 = Lv1、累计 0；行懒建；`lifetime_total` 不得为负（扣回截断到 0 并记实际值）。
- AD-2：流水只追加；不接入 `ledger_entries` 总账。
- AD-3：额度只增不减；WIB 只用 `ScheduleWindow.WIB`；被动合计截断到恰好 50。
- AD-5：所有监听 `@Async` + AFTER_COMMIT；失败不重试。
- AD-6：防刷全靠幂等键；点赞 / 收藏终身一次；自赞本就无事件。
- §5.2：幂等键只经 `GrowthIdemKeys`。§5.3：EXP 换算 `BigDecimal` + `HALF_UP`。§5.4：只有 `GrowthLedgerService` 写成长值。
- 护栏：不引 MQ / 缓存（规则配置每次读库即可，量很小）；`ddl-auto=validate`；Flyway 时间戳号已预分配。
- 规则配置修改「从下一次入账起生效」——因为每次入账读库，天然满足（Epic 4 用）。
