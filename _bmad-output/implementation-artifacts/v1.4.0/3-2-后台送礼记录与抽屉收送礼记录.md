## Story

As a 运营,
I want 查询全站送礼记录与「已付款未送达」异常单、导出 Excel，并在用户抽屉看某人送出与收到的礼物,
so that 能处理送礼客诉与退回异常。

**AC2 — 全站列表与筛选（M1 / M3）** `[L0]` `[L1]`（PRD §3.4 字段与筛选 / UI M1）
1. 筛选栏（`<form method="get" th:action="@{/admin/gift-orders}">`，写法照 `payments.html:45-87`）：送礼人 ID（`senderId`，number）、宠物主人 ID（`ownerId`，number）、渠道（`channel`：全部 / PawCoin / QRIS）、状态（`status`：全部 / 已送达 `DELIVERED` / 待支付 `PENDING` / 已过期 `EXPIRED` / 支付失败 `FAILED` / 已付款未送达 `UNDELIVERED`）、时间段（`from` / `to` 两个 `type=date`，旁标「WIB」，**含止当天**：服务层取 `[from 00:00 WIB, to + 1 天 00:00 WIB)`，口径同 `payments.html:77-83` 注释）、「查询」「清空筛选」。全部参数**宽松解析**（不认识 = 不限，照 `AdminPaymentController.parseEnum` :186-195）。`status=UNDELIVERED` = `{UNDELIVERED_REFUND_PENDING, UNDELIVERED_REFUNDED, REFUND_MANUAL}` 三个状态的合集（异常单，AC3）。
2. 表头（全站视图，UI M1 / PRD 全部字段）：时间（WIB）/ 送礼人 / 收礼宠物 / 宠物主人 / 礼物 / 数量 / 总价 / 渠道 / 状态 / payment_intent。
   - 时间：`created_at`，`${@adminTime.fmt(…)}`（`AdminTime.java:18-22`，`yyyy-MM-dd HH:mm`）。
   - 送礼人 / 宠物主人：`{昵称} #{id}`，昵称 = `COALESCE(nickname, display_name)`（与 `AdminUserService.currentName` 同一兜底，`AdminUserService.java:424-433`）；已注销（`users.deleted_at IS NOT NULL`）→ 「（已注销）#{id}」（UI M2；AD-12「已注销用户」）。
   - 收礼宠物：订单快照 `gift_orders.pet_name`（1.1 AC1.3 新增的下单时宠物名快照列）；`pet_id IS NULL`（宠物已删 / 主人已注销，AD-2 `ON DELETE SET NULL`）→ 「（已删除）{pet_name}」（UI M1「（已删除）Boba」）。**不读 `pet_profiles` 当前名**（与礼物名同一快照口径）。
   - 礼物：订单快照名（中文 / 英文界面取 `gift_name_en`，印尼文界面取 `gift_name_id`；**不读 `gift_catalog` 当前名**，NFR2）。
   - 数量 / 总价：右对齐等宽数字，总价 `Rp{千分位}`。
   - 渠道：PawCoin / QRIS。
   - 状态徽章：已送达（`badge-ok`）/ 待支付（`badge-neutral`）/ 已过期、支付失败（`badge-muted`）/ 已付款未送达（`badge-warn`，三个异常状态都显示这一个字样）。
   - payment_intent（列头文案「支付意图 / Payment intent / Intent pembayaran」，同支付记录抽屉标题；`AdminMessagesParityTest` 禁止文案值含 snake_case 标识串，T0 修订）：QRIS 单显示 `payment_intents.public_token` 缩写（前 6 + `…` + 后 3，`title` 放全值）；PawCoin 单「—」。**不渲染 `payment_intent_id` 数字**（不外露自增 id）。
3. 排序 `created_at DESC, id DESC`；每页 **20** 条（与 `AdminPaymentController.PAGE_SIZE` :33 一致）；分页「← 上一页 · 第 {n} / {m} 页（共 {total} 条）· 下一页 →」复用 `admin.audit.prev` / `.page` / `.next`（`messages_zh_CN.properties:304-306`），翻页链接**带全部筛选参数**（`payments-list.html:88-96` 的教训）。
4. 摘要条四格（**覆盖整个筛选结果**，一次 SQL 聚合，与表格同一组条件）：送礼笔数（`count(*)`）/ 送礼人数（`count(DISTINCT sender_id)`，副标「去重」）/ 成功金额（`DELIVERED` 的 `Σ total`，副标「其中 PawCoin Rp{DELIVERED 且 PAWCOIN 的 Σ total}」）/ 已付款未送达（三个异常状态的笔数）。
5. 无结果（M3）：居中 `🎁` + 灰字「暂无符合筛选条件的送礼记录」（`.empty` + `.empty-emoji`，同 `payments-list.html:83-86`）。
6. **禁 N+1**：一页的用户名、`payment_intents.public_token` 用一条带 `JOIN users` / `LEFT JOIN payment_intents` 的原生 SQL 取齐（`NamedParameterJdbcTemplate` 绑参数，禁字符串拼值）；宠物名取订单快照列，**不 JOIN `pet_profiles`、不经 `GiftPetDirectory`**（多宠物合入后零改动）；L0 测试断言查询次数为常数。
7. 行不可点（无抽屉）；页面无任何 POST 表单。

**AC3 — 异常单视图（M2）** `[L0]` `[L1]`（PRD §3.4 异常单 / AD-9 / decision-log ③「异常单『退回失败 · 待重试』」/ UI M2）
1. `status=UNDELIVERED` 时表格换成异常单视图：**去掉** payment_intent 列，**加**「原因」「PawCoin 退回」两列：
   - 原因：`undelivered_reason` → 宠物已删除（`PET_DELETED`）/ 主人已注销（`OWNER_DELETED`）/ 送礼人已拉黑主人（`SENDER_BLOCKED`）；未知值原样显示代码。
   - PawCoin 退回：`UNDELIVERED_REFUNDED` →「已退回 {total 千分位} · {refunded_at，`AdminTime.fmt`}」；`UNDELIVERED_REFUND_PENDING` → 黄色徽章「退回失败 · 待重试」（`badge-warn`）；`REFUND_MANUAL` → 红色徽章「退回失败 · 需人工」（`badge-danger`）。悬停 `title` 显示「已重试 {refund_attempts} 次」。**`refund_error` 不渲染**（可能含内部异常信息）。
2. 摘要条换成四格：已付款未送达（笔数）/ 涉及金额（`Σ total`）/ 已退回（`UNDELIVERED_REFUNDED` 笔数）/ 退回失败（`UNDELIVERED_REFUND_PENDING` + `REFUND_MANUAL` 笔数）。
3. 后台**不提供手动补退或重试**（PRD「只读，不提供后台改单」）；待重试由 1.2 的 `GiftRefundRetryJob` 自动处理（AD-9），页面说明一行灰字「退回失败的订单由系统每 10 分钟自动重试，最多 5 次；仍失败标「需人工」，请联系技术处理。」。

**AC5 — 用户抽屉「收送礼记录」页签（M4 / M5 / M6）** `[L0]` `[L1]`（PRD §3.4 抽屉 / CROSS-STORY 地基 / UI M4 ~ M6）

### SQL 要点（列名以 T0 核实为准）

```sql
-- 列表（全站）：一条取齐，禁 N+1
SELECT o.id, o.created_at, o.sender_id, o.owner_id, o.pet_id, o.gift_name_en, o.gift_name_id,
       o.unit_price, o.quantity, o.total, o.channel, o.status, o.undelivered_reason,
       o.refund_attempts, o.refunded_at,
       s.deleted_at AS s_deleted, COALESCE(s.nickname, s.display_name) AS s_name,
       w.deleted_at AS w_deleted, COALESCE(w.nickname, w.display_name) AS w_name,
       o.pet_name, pi.public_token AS intent_token
FROM gift_orders o
JOIN users s ON s.id = o.sender_id
JOIN users w ON w.id = o.owner_id
LEFT JOIN payment_intents pi ON pi.id = o.payment_intent_id
WHERE (:senderId IS NULL OR o.sender_id = :senderId) AND (:ownerId IS NULL OR o.owner_id = :ownerId)
  AND (:channel IS NULL OR o.channel = :channel) AND (o.status IN (:statuses))   -- 不限时传全集
  AND (:fromTs IS NULL OR o.created_at >= :fromTs) AND (:toTs IS NULL OR o.created_at < :toTs)
ORDER BY o.created_at DESC, o.id DESC
LIMIT :size OFFSET :offset;
```
- 宠物名用快照 `o.pet_name`（1.1 定 `VARCHAR(20) NOT NULL`，与 `PetProfile.name` :41 同宽）。
- 摘要：同 `WHERE`，`count(*)`、`count(DISTINCT sender_id)`、`sum(total) FILTER (WHERE status='DELIVERED')`、`sum(total) FILTER (WHERE status='DELIVERED' AND channel='PAWCOIN')`、`count(*) FILTER (WHERE status IN (异常三态))`；异常视图另一组 FILTER。
- `NULL` 参数在 PostgreSQL 预编译里要显式类型（`CAST(:senderId AS BIGINT)`），否则 `could not determine data type of parameter`。（T0 修订：实现改为按「有无该筛选」拼接**固定 SQL 片段**、值一律命名参数绑定，不用 `(:x IS NULL OR …)`，从根上避开该问题；JOIN users 改 `LEFT JOIN`，用户行缺失按已注销处理。）
- 抽屉「送出」：`WHERE o.sender_id = :userId`；「收到」：`WHERE o.owner_id = :userId AND o.status = 'DELIVERED'`。

### 架构约束

- **AD-2**：`sender_id` 注销后保留；`pet_id` 删宠物置空；快照列是展示唯一来源（NFR2）。
- **AD-9**：退回状态机只经送礼服务；后台只读。`REFUND_MANUAL` 只显示、不处理。
- **AD-11**：页在 `G_ORDERS`；新码不预授；抽屉页签只填地基容器。
- **AD-12**：送礼人注销显示「已注销用户」；主人注销 / 删宠物 → 订单保留、宠物显示「该宠物已不存在」（后台简写「（已删除）」）。
- **§5**：后台不改订单状态；对外标识用 token（payment_intent 显示 `public_token`）。
- **护栏**：只读查询，`@Transactional(readOnly = true)`（导出除外，见 AC4.4）；不引缓存 / 新依赖；无新迁移；日志只记 id 与计数。
- **共享约束不碰**：地基页签头与 `data-utab` 名不改；`ck_*` 两条约束不改。
