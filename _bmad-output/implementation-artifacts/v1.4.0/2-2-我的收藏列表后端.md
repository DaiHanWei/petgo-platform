## Story

As a 用户,
I want 按收藏时间倒序分页看我收藏的帖子和场所，看不到的内容也保留一条,
so that 我知道它还在、可以自己移除。

## Acceptance Criteria

### 后端

**AC1 — 两个端点与权限** `[L0]` `[L1]`（AD-11、NFR2、NFR4、PRD §3.2「仅自己可见」）
1. 新建 `collect.web.MyCollectionController`，`@RequestMapping("/api/v1/me/collections")`：`GET /posts?cursor=` 与 `GET /places?cursor=`。只作用于 JWT `sub` 本人，`currentUserId(jwt)` 照抄 `MeContentController.java`:34-43（无 sub → 401 ProblemDetail）。**不接受任何 userId / token 查询参数**；带 `?userId=` 也只返回本人。
2. `SecurityConfig`：在 `.anyRequest().authenticated()`（当前 :349）**之前**、紧随 Tailsonality 规则（:343 / :346-347）之后加
   `.requestMatchers(HttpMethod.GET, "/api/v1/me/collections/posts", "/api/v1/me/collections/places").hasRole("USER")`，带一行注释说明理由（同 :305-308：controller 把 `jwt.sub` 当 `users.id`，兽医 token 落到 `anyRequest().authenticated()` 会以同号用户名义读别人的收藏）。若 1.1 / 2.1 已在此处插入了自己的 `/me` 规则，挨着它们放，规则顺序其余不动。
3. Given 兽医 token，When 访问任一端点，Then 403 ProblemDetail；Given 无 token，Then 401 ProblemDetail；Given A、B 各有收藏，When A 请求，Then 只出现 A 的行。
4. 日志只记 userId 与条数，不记帖子正文、场所名、地址（项目约定：日志不记 PII）。

**AC2 — 帖子列表分页与排序** `[L0]` `[L1]`（AD-11、epics 2.2 AC1、PRD AC7「最上方出现这条」）
1. 按**收藏行** `content_collections.created_at DESC, id DESC` 排序（不是帖子发布时间），每页 20；SQL 取 `PAGE_SIZE + 1` 判 `hasMore`。走 2.1 建的索引 `(user_id, created_at DESC, id DESC)`。
2. 游标用 `shared.paging.KeysetCursor`（`KeysetCursor.java`:37；`encode()` :40 / `decodeOrNull()` :53 / `firstPage()` :79），由**最后一条收藏行**的 `(created_at, id)` 编码。**非法游标按首页处理、不报 400**——项目先例 `PostLikersService.java`:44-47、`FollowListQueryService.java`:144-145，且 `decodeOrNull` 的注释（:48-52）明确「坏游标不把用户锁在门外」。
3. 响应 `{ items: [...], nextCursor: string | null, hasMore: boolean }`（与 `FeedPageResponse` / `FollowListPage` 同形）。全局 `default-property-inclusion: non_null`（`application.yml`:294）→ 末页 `nextCursor` 在 JSON 中省略，App 按 null 处理。
4. **不可见行照样占位、照样计入页大小**（UI E3「位置保留在原收藏时间处」）：可见性只影响行内容，不在 SQL 里过滤，因此不存在「满页被滤空」。
5. Given 收藏 25 条帖子，When 首页 + 次页，Then 20 / 5、按收藏时间倒序、无重复无遗漏、次页 `hasMore = false` 且无 `nextCursor`（epics AC1）。Given 有 3 条收藏行 `created_at` 完全相同且恰好跨页边界，When 翻页，Then 三条都出现且只出现一次（`KeysetCursor` 注释 :7-18 的同刻坑）。

**AC3 — 帖子行结构与取数口径** `[L0]`（AD-11、PRD §3.2「帖子显示首图、标题 / 正文摘要、作者」、UI E2）
1. 行 `CollectedPostRow`：
   ```
   { postId, collectedAt, available,
     post: { type, excerpt, coverUrl, author: { nickname, avatarUrl } } | null }
   ```
   - `postId` = `content_posts.id`（沿用存量 `/api/v1/content-posts/{id}` 与 App `/content/{id}` 寻址，架构 §4「存量约定，非本线新增」）；**不下发**收藏行自增 `id`、`user_id`、`authorId`。
   - `type` 原样下发 `ContentType` 代码（`DAILY` / `GROWTH_MOMENT` / `KNOWLEDGE`），App 用 `PostGridTile._badgeStyle`（`post_grid_tile.dart`:44-53）本地化，不下发显示串。
   - `excerpt` = `content_posts.text` 去首尾空白后截前 **120 个 Unicode code point**（按 code point 截，不切断代理对；`text` 为空 → null）。App 再按 2 行省略。**帖子没有标题列**（见「不符点」①），不下发 `title`。
   - `coverUrl` = `imageUrls[0]`，**与 Feed / 我的发布同口径**：`FeedItemResponse.of` 取首图原样下发（`FeedItemResponse.java`:110-111），不加 `x-oss-process`（App `AppImage.widget(thumbWidth:)` 自行取缩略图；服务端若先加了 process 串，客户端会原样放过、取不到缩略图，见 `AliyunOssClient.java`:141-155 注释）。无图 → null。
   - `author.nickname` / `author.avatarUrl` 取 `AccountQueryService.findAuthorViewsWithoutTags`（:208）的 `AuthorView`，与 Feed 同源同值（`toAuthorView` :382-389：昵称缺则用 displayName、头像原样）。列表不展示运营标签 → 用 WithoutTags 版（该方法注释 :196-206 要求「不展示标签的调用方才用」）。
2. **`available = false` 时 `post` 整个为 null**（JSON 省略）：不下发原标题 / 正文、作者、封面、类型（NFR2、UI E3「不显示原标题、作者」）。
3. Given 一条可见的 Diary 帖（有图、作者昵称「Rina」），When 拉列表，Then 该行 `available = true`、`post.type = DAILY`、`post.coverUrl` 等于 Feed 同帖的 `firstImageUrl`、`post.author.nickname = "Rina"`。

**AC4 — 帖子不可见判定（读时、批量）与恢复** `[L0]` `[L1]`（AD-11、P-5、PRD AC9、epics AC2）
1. 对一页内每条收藏行，`available = false` 当且仅当命中任一条：
   | # | 条件 | 数据来源 |
   |---|---|---|
   | a | 帖子行不存在（防御；正常有 FK CASCADE）或 `deleted_at IS NOT NULL`（作者删除 / 运营下架都是软删） | `ContentPostRepository.findAllById` |
   | b | `status ≠ PUBLISHED`——但 **作者本人 + `UNDER_REVIEW` 算可见**（与 `ContentDetailService.requireVisiblePost` :79-84 同口径）；`AUTHOR_DEACTIVATED`（作者注销）与举报预处置（翻成 `UNDER_REVIEW`，`ContentDisplayability.java`:25-26）均落在这里 | 同上 |
   | c | 我举报过该帖 | **新增批量**（见第 3 点） |
   | d | 我与作者**任一方向**存在隐藏关系（我拉黑 / 我举报作者 / 作者拉黑我；不分来源） | `UserHideRelationReader.hiddenEitherWay(me, authorIds)`（:75，实现 `UserHideRelationReaderImpl`:48，一次查询） |
   作者 = 我时，c / d 跳过（不把自己放进 `hiddenEitherWay` 的入参）。上表即 2.1 AC4.2 的规则，**不看 `visibility`**（2.1 定：PRIVATE 由收藏入口 422 挡住）。
2. **只调 2.1 的批量版 `CollectVisibility.visiblePostIds(me, posts)`**（2.1 AC4.1：固定 2 次查询，与条数无关），不在列表服务里另写一份条件——收藏列表「显示不可见」与取消收藏「不发 `ContentUncollectedEvent`」（P-7）必须是同一个判断，否则会出现「列表显示不可见、移除时却扣回成长值」。若 T0 发现 2.1 实际实现与上表有出入（例如只做了单向 `isHidden`），以 P-5 双向为准改 2.1 的类并在 Completion Notes 记一句。
3. 「我举报过哪些帖」的批量查询（仓库原本没有，`ContentReportRepository` 只有单条 `existsByPostIdAndReporterId` :15、`ReportService` 只有 `hasReported` :90）由 **2.1 新增** `ReportService.reportedPostIds` + `ContentReportRepository.findReportedPostIds`（2.1 AC4.3），本 story 经 `CollectVisibility` 间接使用；T0 若发现 2.1 未做，在本 story 按 2.1 AC4.3 原文补上。
4. Given 收藏的帖子分别被：作者删除 / 运营下架 / 作者注销 / 举报预处置 / 我拉黑作者 / 作者拉黑我 / 我举报过该帖 / 我举报过作者，When 拉列表，Then 这些行均 `available = false`、无 `post` 字段，且仍按原收藏时间占位（epics AC2）。
5. Given 上述任一帖恢复可见（运营恢复 `deleted_at = NULL`、预处置通过翻回 `PUBLISHED`、解除拉黑），When 再拉，Then 该行 `available = true` 且 `post` 完整（AC9「恢复后自动正常」——全部读时判断，不存状态）。
6. Given 我收藏了自己的帖子且它被举报预处置（`UNDER_REVIEW`），When 拉列表，Then `available = true`（作者本人可见，同详情口径）。

**AC5 — 场所列表分页与行结构** `[L0]` `[L1]`（AD-11、PRD AC8、PRD §3.2「场所显示首图、名称、类型、地址」、UI E6）
1. 排序 / 分页 / 游标 / 响应外形同 AC2，排序键为**去重后每组保留行**的 `place_collections.(created_at, id)`（见 AC7）。
2. 行 `CollectedPlaceRow`：
   ```
   { placeToken, collectedAt, available, name,
     place: { type, coverUrl, addressText } | null }
   ```
   - `placeToken` / `name` 取**解析后的场所**（MERGED → 保留场所，AC7）；`name` **不可见时也下发**（UI E7「保留名称置灰」、AD-11）。
   - `place.type` = `PlaceType` 代码（App 本地化）；`place.addressText` = `places.address_text`（`Place.java`:83-84；`PlaceListItemResponse` 无地址，地址只在 `PlaceDetailResponse.addressText` :48，此处直接取实体列）；`place.coverUrl` = 首张对外可见照片，**与场所列表同口径**：`PlacePhotoRepository.findVisibleForPlaces`（:43-49，已按 `sortOrder` 排）取第一张 → `PlacePhotoService.publicUrlOf`（:79-81）→ `AliyunOssClient.exifStrippedThumbUrl(url, PlaceListItemResponse.LIST_THUMB_WIDTH_PX)`（`PlaceListItemResponse.java`:55 / :84）。无照片 → null。
   - **不下发** `places.id`、`merged_into_id`、`place_collections.id`、坐标、标签、计数。
3. Given 收藏了 3 个在架场所，When 拉列表，Then 按收藏时间倒序，每行含 token、名称、类型、地址、首图缩略 URL（带 `x-oss-process=image/resize,w_320/format,jpg`）。

**AC6 — 场所不可见与恢复** `[L0]` `[L1]`（AD-11、PRD AC9a、epics AC3、UI E7）
1. `available = false` 当且仅当**与 `PlaceRepository.resolveForView`（:140-146）结果为空等价**：解析后的场所 `status ≠ ACTIVE` 或 `deleted_at IS NOT NULL`（覆盖 DELISTED、软删、MERGED 但保留场所已下架 / 已删 / 又被合并）。
2. 不可见时：`name`、`placeToken`、`collectedAt` 照常下发；`place` 为 null（不下发类型、地址、封面——见「拍板点」②）。
3. Given 收藏的场所被下架，When 拉列表，Then `available = false`、`name` 仍为原名称（AC9a）；Given 运营恢复上架，When 再拉，Then `available = true`、`place` 完整。Given 场所被软删，Then 同下架。

**AC7 — MERGED 解析与去重（P-6）** `[L1]`
1. 解析只跳一层，与 `resolveForView` 一致：收藏行指向的场所 `status = MERGED` **且未软删**且 `merged_into_id` 非空 → 有效场所 = `merged_into_id`；否则有效场所 = 收藏行自身的 `place_id`。（`resolveForView` 先过 `findUndeletedByPublicToken` :126 的软删过滤，所以「已软删的 MERGED 行」不跳转、按不可见处理。）
2. **去重在 SQL 层、分页之前做**：同一用户多条收藏行解析到同一有效场所时，只保留 `created_at DESC, id DESC` 最新的一条（P-6「保留最近收藏的一条」），`collectedAt` 取该条；游标条件**套在去重之后的外层**（见「实现提示」SQL），保证翻页稳定、同一场所不会在后续页以较旧的那条重新出现。
3. Given 用户先收藏 B、后收藏 A，运营把 B 合并进 A，When 拉列表，Then 只出现一行，`placeToken` = A 的 token、`name` = A 的名称、`collectedAt` = 收藏 A 的时间。Given 用户只收藏过 B，B 合并进 A，Then 一行、显示 A、`available = true`。
4. Given 21 条场所收藏，其中 2 条合并后指向同一保留场所，When 翻页，Then 共 20 行、首页 20 行且 `hasMore = false`；Given 41 条（含 1 组重复）跨三页，Then 无重复无遗漏。

**AC8 — 移除路径与 2.1 DELETE 的衔接（不新增接口）** `[L1]`（AD-9、P-6 / P-7、PRD AC9 / AC9a / AC11c）
1. 本 story 不新增删除接口：App 移除不可见条目调 2.1 的 `DELETE /api/v1/content-posts/{postId}/collect` 与 `DELETE /api/v1/places/{placeToken}/collect`，传的就是本列表下发的 `postId` / `placeToken`。
2. 场所 DELETE 必须能删掉本列表展示的那一组：传入的是**解析后保留场所**的 token，而用户的收藏行可能挂在被合并的旧场所上。2.1 AC5.3 已按此设计——`findAnyByPublicToken`（含下架与软删）+ `deleteForDisplayItem`（删 `rawId`、`targetId` 及所有 `merged_into_id = targetId` 的场所上本人的行）。本列表下发的 token 恒为有效场所（`rawId = targetId`），正好覆盖整组。T0 核对 2.1 实现；不满足则在本 story 按 2.1 AC5.3 补改其服务方法（同一端点、不改路径与响应），并补 L1。
3. Given 列表里一条不可见帖子 / 场所、一条 MERGED 去重后的场所，When 依次调 DELETE 后再拉列表，Then 三条都消失、重复组不会「冒出旧的那条」；帖子那条不发 `ContentUncollectedEvent`（P-7 由 2.1 判断，本 story 只做 L1 断言）。

**AC9 — 批量组装、无 N+1** `[L0]` `[L1]`（AD-11、epics「查询次数与页大小无关」）
1. 帖子页固定查询：收藏行分页 1 + `ContentPostRepository.findAllById` 1 + `CollectVisibility.visiblePostIds`（内部 `reportedPostIds` 1 + `hiddenEitherWay` 1）+ `findAuthorViewsWithoutTags` 1（只取可见行的作者）= **至多 5 条**（作者全是自己 / 全部不可见时相应短路）。空页只发 1 条（分页本身），后续批量全部短路。
2. 场所页固定查询：去重分页 1 + 有效场所 `findAllById` 1 + 可见场所照片 `findVisibleForPlaces` 1 = **至多 3 条**（无可见场所时照片查询短路）。
3. 禁止在逐行循环里调用：`ContentDetailService.requireVisiblePost`、`ReportService.hasReported`、`UserHideRelationReader.isHidden`、`PlaceRepository.resolveForView` / `findVisibleById`、`AccountQueryService.findAuthorViews(List.of(x))`。
4. 所有查询都经 JPA 仓库（JPQL 或 `nativeQuery = true`），**不用 `JdbcTemplate`**——否则 Hibernate `Statistics` 数不到，L1 守卫形同虚设。

**AC10 — 回归** `[L0]`：`./mvnw -B clean package` 绿（云端只验 L0）；`PlaceListResponseContractTest`、`ContentDetailService` 相关既有测试不变绿；不改 `FeedItemResponse` / `PlaceListItemResponse` / `PlaceDetailResponse` 的字段。

### 不符点（架构 / epics 与代码对照，以代码为准）

- ① AD-11 帖子行写了 `title` 与 `excerpt`：`content_posts` **没有标题列**（只有 `text`），故只下发 `excerpt`，App 行组件「标题 / 正文摘要」就是这一段。
- ② AD-11 写「图片 URL 与 Feed、场所列表同口径」：两者口径**本就不同**——Feed 首图原样下发、由 App 缩放；场所列表服务端已拼 `resize,w_320/format,jpg`。本 story 帖子封面跟 Feed、场所封面跟场所列表，各自不分叉。
- ③ gift 2.3 等 story 写「非法游标 → 400」：`KeysetCursor` 的设计与三处先例都是**坏游标当首页**，本 story 跟代码先例。

### 拍板点（按建议实现，Completion Notes 复述）

- **① 可见性完全复用 2.1，不另加条件**：本可在列表层再加「作者已注销」「PRIVATE 且非本人」两条防御，但那会让列表与 P-7 的事件判断分叉（列表显示不可见、取消时却发 `Uncollected`）。前者已被 `AUTHOR_DEACTIVATED` 覆盖，后者在 P-2 下不可能出现（收藏入口 422、无转私密功能），故不加。
- **② 不可见场所不下发封面**：PRD 写「图片置灰」、UI E7 灰度缩略图，但 AD-11 与本次任务口径是 `place` 仅可见时下发；下架可能正因图片违规，下发后只靠客户端置灰不稳妥。App（2.4）对不可见场所用灰色占位块表达「置灰」。若操作者坚持显示原图灰度，只需把 `coverUrl` 提到行级、不改其他。
- **③ 摘要长度 120 code point**：UI 行最多 2 行 14 号字，120 足够；比 Feed 下发全文（≤1000）省一页约 15KB。
- **④ MERGED 列表下发保留场所的 token / 名称**（P-6 按保留场所显示），由此要求 2.1 DELETE 按「组」删除（AC8.2）。

### 实现提示

- **帖子分页（JPQL，挂在 2.1 的收藏仓库上）**：
  `SELECT c FROM ContentCollection c WHERE c.userId = :me AND (c.createdAt < :ts OR (c.createdAt = :ts AND c.id < :lastId)) ORDER BY c.createdAt DESC, c.id DESC`，`PageRequest.of(0, 21)`。
- **场所去重分页（原生，`List<Object[]>`）**——游标条件必须在外层：
  ```sql
  SELECT d.id, d.created_at, d.eff_place_id FROM (
      SELECT DISTINCT ON (e.eff_place_id) pc.id, pc.created_at, e.eff_place_id
        FROM place_collections pc
        JOIN places p ON p.id = pc.place_id
        CROSS JOIN LATERAL (SELECT CASE
             WHEN p.status = 'MERGED' AND p.deleted_at IS NULL AND p.merged_into_id IS NOT NULL
             THEN p.merged_into_id ELSE pc.place_id END AS eff_place_id) e
       WHERE pc.user_id = :me
       ORDER BY e.eff_place_id, pc.created_at DESC, pc.id DESC
  ) d
  WHERE d.created_at < :ts OR (d.created_at = :ts AND d.id < :lastId)
  ORDER BY d.created_at DESC, d.id DESC
  LIMIT :limit
  ```
  代价：每页扫该用户全部场所收藏（个人收藏量级为几十～几百，走 `(user_id, …)` 索引），可接受，**不为此加缓存或冗余列**（NFR4）。游标稳定性：每组恒取组内最新一条，外层再比游标，已出现过的组在后续页只会以同一条（已被游标排除）出现，不会以较旧行重现；两页之间恰好发生合并时，最多让某条「提前消失」，不会重复——可接受。`created_at` 用 `ContentService.toInstant` 同款转换（保留微秒，配合 `KeysetCursor`）。
- **场所卡片批量**：有效场所 id 集合 → `places.findAllById`（一次）→ 可见 = `status == ACTIVE && deletedAt == null` → 只对可见 id 调 `photosOf`（一次）→ 组装。注意 `findAllById` 不过滤软删，正好拿到不可见场所的名称与 token。
- **帖子批量**：收藏行 postId 集合 → `findAllById`（一次）→ `CollectVisibility.visiblePostIds(me, posts)`（两次）→ 可见行作者 id 去重 → `findAuthorViewsWithoutTags`（一次）→ 组装。按收藏行顺序输出，不按帖子顺序；`findAllById` 缺失的 postId（防御）直接判不可见。
- excerpt 截断：`text.strip()`，`codePointCount > 120` 时 `text.substring(0, text.offsetByCodePoints(0, 120))`，不加省略号（App 负责）。
- 所有查询方法 `@Transactional(readOnly = true)`。
