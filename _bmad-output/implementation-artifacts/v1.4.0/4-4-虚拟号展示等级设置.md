# Story 4.4: 虚拟号展示等级设置

Status: ready-for-dev

> 版本 v1.4.0 · 主题 tailrent-level · 分支 `feat/1.4.0-tailrent-level`
> 口径优先级：`decision-log.md` ① 节 > `Tailrent等级/1-4-0Tailrent等级prd.md`（§3.1「参与范围」虚拟号、§3.4「虚拟号展示等级」、AC12）> `architecture-v1.4.0-tailrent-level-delta.md`（AD-1 `display_level`、AD-13、AD-14、AD-17、§5.5）> `Tailrent等级/ui-admin-1-4-0-tailrent-level-integrated-v1.html`（J1 / J2）（均在 `_bmad-output/planning-artifacts/v1.4.0/`）。
> 前置：**Story 1.1**（`growth_accounts.display_level` 列、`growth_levels`）、**Story 2.2**（存量虚拟号账户行 + 随机 6–8；**新建虚拟号随机 6–8 已在 `AdminVirtualAccountService.create` 路径实现**）、**Story 3.1**（`GrowthQueryService.getBadges` 对虚拟号读 `display_level` → App 角标 / 头像框）、**Story 4.1**（段位色点 CSS、`admin.v140.growth.tier.*` 文案）。
> 范围：**后端 + 后台模板**。无迁移。App 零改动（App 显示由 Story 3.1 / 3.2 已接通，本 story 只改数据）。

## Story

As a 运营,
I want 在「运营发布身份」页看到并修改每个虚拟号的展示等级,
so that 虚拟号在社区里的等级看起来合理。

## Acceptance Criteria

**AC1 — 列表新增「展示等级」列（J1）** `[L0]` `[L1]`（PRD §3.4 / AD-17 / UI J1）
1. `/admin/virtual-accounts` 虚拟账号表在「账号物种定位」列之后、「建号人」之前插一列「展示等级」：段位色点 + `Lv{n}`（色点类沿用 Story 4.1 的 `.tier-dot .tier-<TIER>`）。现有 7 列全部保留、顺序不变。
2. 数据**一次批量查询**取当页全部虚拟号的 `display_level` 与段位（禁止逐行查）；以 model 属性 `displayLevels`（`Map<Long, DisplayLevel(level, tier)>`）传给模板，**不改** `VirtualAccountRow` 记录。
3. 无账户行或 `display_level` 为空（边角：Story 2.2 之后仍未初始化）→ 显示「—」。停用的虚拟号照常显示其展示等级（UI J1 的 20005 行）。
4. 列表随抽屉保存后的 `admin:virtual-account-list-refresh` 整表重拉自动刷新（既有机制，`AdminVirtualAccountController.afterAction` :165-170）。

**AC2 — 详情抽屉新增「展示等级」卡（J2）** `[L0]` `[L1]`（PRD §3.4「同『账号物种定位』卡形态：下拉 + 保存 + 原生确认」/ UI J2）
1. `drawer-virtual-account.html` 的「账号物种定位」卡（`data-section="virtual-species"`，:38-55）**之后**新增同形态卡 `data-section="virtual-display-level"`：标题「展示等级」；说明「只用于头像角标与对应段位的头像框；不参与成长值，不享受露出加权等任何权益。」；下拉 `name="displayLevel"`，选项 `Lv1 ~ 当前最高级`（读 `growth_levels` 的最大 level，**随等级表追加自动变长**），每项文案「Lv{n} · {段位名}」，当前值预选；「保存」。
2. 原生确认：表单 `data-confirm="#{admin.v140.growth.display.confirm}"`（「确认把「{0}」的展示等级改为 Lv{1}？」）+ `data-confirm-args=${a.nickname}` + `data-confirm-input="displayLevel"`——`{1}` 由 `admin-core.js` 取下拉当前值（`tailtopiaConfirmArgs` :49-65：args 不足 2 个时取 `[name=data-confirm-input]` 的值）。
3. 无 `virtual_account.manage`：不渲染表单，只显示当前展示等级 + 提示「需要「管理虚拟账号」权限」（与物种卡 :53-54 同写法，`#{admin.v130.err.forbidden(#{perm.virtual_account.manage})}`）。
4. 「停用」区块、头部卡、物种卡一字不动。

**AC3 — 保存端点与校验** `[L0]` `[L1]`（PRD §3.4 / FR-143.8 / AC12 / AD-1）
1. `POST /admin/virtual-accounts/{id}/display-level`（`@PreAuthorize(AdminVirtualAccountController.MANAGE_AUTH)`，即 `virtual_account.manage`，与物种定位同门），参数 `displayLevel`。htmx 与非 htmx 两支，写法照 `setSpecies`（:234-253）：htmx 成功 → `afterAction`（抽屉 oob 重渲染 + toast「展示等级已保存」+ 列表整表重拉）；非 htmx → PRG 回列表 + flash。
2. 校验（服务端为准）：目标必须是 `account_type = VIRTUAL`（真实用户 → 422 `admin.err.growth.display.virtualOnly`，照 `setAccountSpecies` :164-168 的守卫口径）；`1 ≤ displayLevel ≤ max(growth_levels.level)`，越界 → 422 `admin.err.growth.display.outOfRange`；账号不存在 → 404。
3. 写入走 growth 模块的**单一方法** `growth.service.GrowthDisplayLevelService.set(userId, level)`（类由 Story 2.2 建，本 story 追加方法）：`INSERT INTO growth_accounts (user_id, display_level, …) VALUES (…) ON CONFLICT (user_id) DO UPDATE SET display_level = EXCLUDED.display_level, updated_at = now()`（无行时补建，与 AD-1「行懒建」一致）。**只写 `display_level`**：不碰 `lifetime_total` / `level`，不写任何 `growth_ledger` 行，不调用 `GrowthLevelChangeHandler`、不发 `GrowthLevelChangedEvent`、不发通知、不写待弹庆祝（AC12「不产生任何成长值流水」；虚拟号无庆祝）。
4. 值未变化 → 不写库、不写审计，toast 照常。

**AC4 — 生效与权益隔离** `[L1]` `[L2]`（PRD AC12 / AD-14 / §5.5）
1. 保存后 App 各处（Feed、详情、评论、他人主页、关注条）该虚拟号的角标与头像框按新等级与其段位显示（例：Lv12 → GUARDIAN，自动最高可用档 UPGRADED 框）——经 Story 3.1 的 `GrowthQueryService.getBadges` 实时读 `display_level`，**无缓存、无需额外失效**。
2. 权益判定不变：`GrowthQueryService.getLevel(s)` 对虚拟号仍返回 `GrowthLevel.NOT_PARTICIPATING`（地基契约），不吃 Feed 加权（Story 3.4）、不享 ② 名额 / ③ 专属礼物——本 story **不得**为展示等级改动 `getLevel(s)`。
3. 真实用户给该虚拟号点赞 / 评论后，该虚拟号仍没有任何成长值流水（Story 1.1 已保证，本 story 回归断言即可）。

**AC5 — 新建表单不加字段** `[L0]`（PRD §3.4「新建表单不加此字段（系统随机分配）」/ AD-13）
1. `drawer-virtual-account.html :: createForm`（:81-115）与 `POST /admin/virtual-accounts`（:181-206）**不加** `displayLevel` 参数。
2. 新建后系统随机分配 Lv6 ~ 8 由 **Story 2.2** 实现；本 story 只加一条回归断言：新建一个虚拟号 → `growth_accounts.display_level ∈ [6, 8]`。若 T0 发现 2.2 未覆盖新建路径，**不在本 story 补实现**，回报操作者（避免两处写随机逻辑）。

**AC6 — 审计** `[L0]`（PRD §3.4 / AD-17 / NFR6）
1. `AuditActions.GROWTH_DISPLAY_LEVEL_CHANGED`；`AdminAuditService.record(adminId, GROWTH_DISPLAY_LEVEL_CHANGED, "user", String.valueOf(userId), "displayLevel " + old + "→" + new)`（`old` 为空写 `—`），与写库同一事务。
2. 既有虚拟号审计用的是字符串字面量（`"VIRTUAL_ACCOUNT_SET_SPECIES"` 等，`AdminVirtualAccountService` :127 / :145 / :171）；本 story 新动作按 AD-17 用 `AuditActions` 常量，**不回改**既有字面量。

**AC7 — 文案四份** `[L0]`
新键四份同加（`messages.properties` = en），见 Dev Notes「文案键」；`check-i18n-keys.sh`、`check-admin-hardcoded-text.sh` 本地绿。

**AC8 — 回归** `[L0]` `[L1]`
`mvn -B clean package` 全绿（含 `AdminVirtualAccountServiceTest`、`AdminActiveKeyCatalogTest`、`AdminPermissionWiringTest`）；L1 `AdminVirtualAccountIntegrationTest` / `AdminPublishIdentityDrawerIntegrationTest` 既有用例不变绿，新增用例写好能编译，云端标「L1 待本地验收」。

### 架构约束

- **AD-1**：`display_level INT NULL` 仅虚拟号；行懒建（`ON CONFLICT DO NOTHING / DO UPDATE`）。
- **AD-13**：上线随机 6–8 与新建随机 6–8 属 Story 2.2；本 story 只做「运营逐个修改」。
- **AD-14 / §5.5**：展示只走 `getBadges`（虚拟号用 `display_level` 与其段位、自动最高框）；权益只走 `getLevel(s)`（虚拟号恒不参与），两者不混用。
- **§5.4**：成长值写入纪律管的是 EXP / 等级 / 流水；`display_level` 不在其列，但仍集中在 growth 模块一个方法里写，后台不直接拼 SQL 改 `growth_accounts`。
- **FR-143.8 / AC12**：虚拟号不入任何流水、无等级页与庆祝；展示等级只用于角标与头像框。
- 不加迁移、不改共享 CHECK、不改地基签名；不引缓存。
