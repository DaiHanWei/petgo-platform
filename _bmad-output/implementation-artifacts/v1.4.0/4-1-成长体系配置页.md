## Story

As a 运营,
I want 在后台调整成长值规则、消费换算比例和等级表，改等级表后系统自动重算全部用户的等级,
so that 不发版也能调控用户成长节奏。

**AC4 — 规则编辑抽屉（480）与校验** `[L0]` `[L1]`（PRD §3.3 ① / UI G2 / G3）
1. 「编辑」= `data-drawer-open` 打开 `GET /admin/growth/rules/{code}/drawer`（`VIEW_AUTH`；只读用户不渲染该按钮，见 AC8）。抽屉标题「编辑规则 · {CODE}」；只读展示「名称」「触发来源」（`admin.v140.growth.rule.<CODE>.source`）。
2. 可编辑字段按规则分型（**只渲染该型有的字段**）：
   | 型 | 规则 | 可改字段 |
   |---|---|---|
   | 主动计次 | `DAILY_LOGIN / POST_PUBLISHED / COMMENT_POSTED / LIKE_GIVEN / PLACE_CHECKIN` | 每次分值 *、每日上限（次，留空 = 不限）、启用 |
   | 被动 | `LIKE_RECEIVED / COMMENT_RECEIVED / COLLECT_RECEIVED` | 每次分值 *、**合计上限组（每天）** *（写 `PASSIVE_GROUP.daily_cap`，三条共用，任一条改了三条一起生效）、启用 |
   | 里程碑 | `MILESTONE_S / M / L` | 每次分值 *、启用（「每个里程碑 1 次 / 同 code 最多 5 次」是代码常量，不在此改） |
   | 按金额 | `GIFT_SENT / GIFT_RECEIVED` | 每 Rp（`unit_amount`）*、= 分值（`points`）*、启用 |
   | 运营活动 | `OPS_CAMPAIGN` | 只有启用 |
   | 消费 | `SPEND_DIGITAL / SPEND_SHOP` | 不开抽屉（端点对这两个 code 返回 422 `admin.err.growth.ruleNotEditable`） |
   启停用**勾选框**（后台无开关组件）。
3. 保存 = `POST /admin/growth/rules/{code}`（`EDIT_AUTH`，htmx）。前端走**原生 diff 确认**：表单套模板 D 配置卡壳（`tpl-d-config-card :: configCard`，`confirmDiff=true`），确认框标题用新键 `admin.v140.growth.confirm.title`「确认修改以下配置？」、末尾追加 `confirmDiffNote`=「修改从下一次入账起生效，不追溯已入账的成长值。」（见 Dev Notes「tpl-d 的标题」）。成功：关抽屉 + 刷新规则表 + toast「已保存」。
4. 服务端校验（**一次收集全部字段错误**，照 `OpsPopupValidationException` 写法）：分值、每日上限、合计上限、`unit_amount` 均须为 **≥ 1 的整数**（每日上限允许留空 = 不限）；不合法 → 422，抽屉不关，各字段下方红字 + 底部汇总「{n} 处填写有误」（G3）。前端 `min="1" step="1"` 只是体验，服务端为准。
5. 生效口径：从下一次入账起使用新值、不追溯（`accrue` 每次读 `growth_rules`；见 T0 核对）；停用后不再入账，已入账不变。
6. 每次保存写审计（AC9），只对真变化的字段记；全无变化 → 不写库、不写审计，toast 仍显示「已保存」。

**AC7 — 改等级表后的批量重算（AD-12）** `[L0]` `[L1]`（PRD AC9 / FR-143.5 / AD-10 / AD-12）
1. 迁移 **`V20261018_1505__growth_recalc_jobs.sql`**：建 `growth_recalc_jobs`（列见 Dev Notes「表结构」），状态 CHECK `('PENDING','RUNNING','DONE','FAILED')`，**部分唯一索引保证同时最多一个进行中的任务**。文件头注释写明「V1.4.0 Story 4.1，AD-12；号预分配」。提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`。
2. `growth.service.GrowthRecalcService`：`@Async` 执行，状态机 `PENDING → RUNNING → DONE / FAILED`（每次改状态自己一个短事务，照 AD-5「只用 @Async + DB 状态机」）。执行体在**一个事务**内：
   - 先用一条 SQL 选出「按新表算出的等级 ≠ 当前 `level`」的真实用户 id（见 Dev Notes「预览 / 执行 SQL」）；
   - 对每个 id：`SELECT … FOR UPDATE` 锁账户行（Story 1.1 的锁行仓储方法），调用 **Story 1.2 的 `GrowthLevelChangeHandler.onLifetimeChanged(GrowthAccount lockedAccount, RuleCode source)`**——handler 自己按 `growth_levels`（此时已是新表）重算 `level`、更新、发 `GrowthLevelChangedEvent(userId, old, new)`（升降都发，② 据此重算名额），并按 Story 2.1 的连锁在升级时写待弹庆祝（保留已有 from、只更新 to）、AFTER_COMMIT 发 `GROWTH_LEVEL_UP` 通知；降级不通知不弹窗。**本 story 不再自写 `UPDATE … SET level`**（AD-12 原文的 `UPDATE … RETURNING` 由「选 id + 逐个经 handler」替代，否则 handler 看到的 level 已是新值、不会发事件与通知）；
   - `source`：不能是 `LAUNCH_BACKFILL`（2.1 会把它当补算跳过通知）。`RuleCode` 里没有「等级表重算」这个值；T0 核对后二选一并记 Completion Notes：(a) 在 handler 上**追加**重载 `onLevelTableChanged(GrowthAccount lockedAccount)`，内部复用同一逻辑、视作非补算来源（推荐，不污染 `RuleCode` / `rule_code` 取值）；(b) 若 handler 的 `source` 只用于「是否补算」判断，传 `RuleCode.ADMIN_ADJUST`。不改 handler 既有签名。
   - 计数：handler 返回或 job 自己比较前后 `level` 得出 `upgraded / downgraded`；提交后 job 置 `DONE`，写 `upgraded / downgraded / finished_at`。
   - 任何异常 → job 置 `FAILED`（`failure_reason` 只记异常类名，不记 PII），整个事务回滚、等级全部保持旧值。
3. **本 story 不自写**待弹庆祝字段、通知发送或 `GrowthLevelChangedEvent` 发布——这些只在 `GrowthLevelChangeHandler` 一处（§5.4）。
4. 页面「等级表」页签顶部显示**最近一次重算**：状态（排队中 / 进行中 / 已完成 / 失败）、升级 N / 降级 N、完成时间（WIB，`@adminTime.wib`）；从未重算显示「尚未重算过」。
5. 最近一次为 `FAILED`，或 `RUNNING` 已超过 30 分钟（进程中途重启导致的僵死任务）→ 有编辑权限者看到「重新执行重算」按钮：`POST /admin/growth/levels/recalc`（`EDIT_AUTH`）把僵死 / 失败任务置 `FAILED` 后插一条新 `PENDING` 并触发；写审计。
6. 追加 Lv21（AC9）走同一流程：已达新门槛的用户自动升级、收到升级通知。
7. 只读视图与重算无关：`accrue` 期间若与重算并发，二者都对 `growth_accounts` 行加锁（`accrue` 的 `SELECT … FOR UPDATE` / 重算的 `UPDATE`），按新表定级，不会写回旧等级；本 story 不另加锁。

```sql
CREATE TABLE growth_recalc_jobs (
    id             BIGSERIAL    PRIMARY KEY,
    status         VARCHAR(16)  NOT NULL,                -- PENDING | RUNNING | DONE | FAILED
    requested_by   BIGINT       NOT NULL,                -- admin_accounts.id（不建 FK，后台账号不物理删）

    downgraded     INT          NULL,

CREATE INDEX idx_growth_recalc_jobs_created ON growth_recalc_jobs (created_at DESC);
```

### 预览人数 / 执行 SQL（思路，列名以 T0 核实为准）

```sql
-- 新等级 = 满足 threshold <= lifetime_total 的最大 level（新表）
WITH lv AS (SELECT level, threshold FROM growth_levels),            -- 预览时用「候选新表」：VALUES 列表或临时 CTE，不写库
     calc AS (
       SELECT a.user_id, a.level AS old_level,
              (SELECT max(l.level) FROM lv l WHERE l.threshold <= a.lifetime_total) AS new_level
       FROM growth_accounts a JOIN users u ON u.id = a.user_id
       WHERE u.account_type = 'REAL' AND u.deleted_at IS NULL)
SELECT count(*) FILTER (WHERE new_level > old_level) AS up,
       count(*) FILTER (WHERE new_level < old_level) AS down
FROM calc;
```
- 预览**不写库**：候选新表用 `VALUES (level, threshold), …` 拼进 CTE（`NamedParameterJdbcTemplate` 绑参数，禁止字符串拼值）。
- 执行：新表已写入后，用同一个 `calc`（此时 `lv` 读真表）选出 `new_level <> old_level` 的 `user_id`，再逐个锁行 + `GrowthLevelChangeHandler`（AC7.2）；预览人数与执行结果可能因中间入账有微小差异，以执行结果写 job。
- 虚拟号账户行（`display_level` 非空，Story 2.2 建）`lifetime_total = 0` 且 Lv1 门槛恒 0，不会变；`account_type = 'REAL'` 过滤是双保险。
- 停用（`status = DEACTIVATED`）用户：等级照常重算（数据正确性）；是否给其发升级通知沿用 2.1 handler / `NotificationService` 的既有口径，本 story 不另判。
- 规模：≤ 500 DAU、账户行数千级，一次改门槛受影响的通常是几十到几百人，单事务逐个经 handler 足够；不做分批。
