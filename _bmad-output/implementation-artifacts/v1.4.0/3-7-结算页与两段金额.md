## Dev Notes

### 后端新增的两个端点
- `GET /api/v1/me/checkout?addressToken=` → 试算
- `POST /api/v1/me/shop-orders` → 下单（201 + 不可枚举 `orderToken`）

🔴 **两者共用 Story 3.4 的 `CheckoutService`，控制器里零金额计算。**
「结算页显示 285.000、提交后变成 305.000」的唯一防法就是自始至终只有一处在算。

### 🔴 超服务范围不是错误，是一个可渲染的状态
`preview` 遇到不可送达的 Kecamatan **不抛异常**，回 `serviceable=false` + 金额位全 null。
抛异常会让整页变错误态 —— 用户看不到自己选的是哪个地址，也就不知道该改哪里。
**`placeOrder` 仍照抛不误**，阻断能力一点没少。
金额位保持 null 而不是 0：0 会被读成「免运费」。

### 🔴 「被上限截断」的判定是「若没有上限本可以用更多」
不是 `coinAmount == 上限` —— 余额恰好等于上限时也相等，但那不是被截断，
多提示一行只会让用户困惑。反过来，真被截断却不提示，用户会以为系统算错了。

### 🔴 归因暂时一律不发（entrySource / triggerType 传 null）
购物车行上**没有**「这件商品当初从哪个入口加进来的」（V108 无该列），
前端此刻能填的只有「从购物车结算」——那不是归因，是废话。
**编一个值比留空更糟**：AB-13B 看板会把它当真，而错误的归因数据没人能事后识别。
👉 归因链闭合归 **Story 9.2 / Epic 6**，届时从加购处一路带下来。已在测试里钉死「不发」。

### UX-DR13 二选一：取「保留但固定」而非整区隐藏
整区隐藏会让用户不知道货怎么送、几天到；保留一档正好回答这两个问题，成本只是一行文字。
🔴 但**不给选择控件**（无 Radio）—— 留一个恒选中的单选框只会让用户去找并不存在的第二档。

### 🔴 RFC 9457 扩展成员：新增 `ProblemExtensions` 接口（shared，只增不改）
逐行明细要随 409 下发，而控制器自拼 ProblemDetail 会漏掉 `traceId` / `instance`
（它们由 `GlobalExceptionHandler` 统一注入），错误信封就此分叉 —— 排障时最先看的就是 traceId。
做法：`CheckoutUnavailableException` 改为 **继承 `AppException` + 实现 `ProblemExtensions`**，
handler 里只加一处「有扩展就合并」。⚠️ 触碰共享文件 `GlobalExceptionHandler`，**只追加不改既有分支**。

## 变异验证（硬纪律 1）
9 个变异全部按预期变红：

| # | 变异 | 变红的用例 |
|---|---|---|
| M1 | 支付区不显示 PawCoin 段 | 混合支付两段金额 · 纯 Coin |
| M2 | 去掉单笔上限截断提示 | 被截断→多一行 |
| M3 | 免运抵扣并进运费（不单列） | 免运是负数行 |
| M4 | 超范围也允许提交 | 超范围提交禁用 |
| M5 | 退货规则取第一行而非服务端最严 | S-6 逐行展开 |
| M6 | 409 整单打回（不列逐行） | FR-95 逐行 + 可移除 |
| B1 | 后端 `strictest` 改成取最宽松 | 混装取最严 · 含不可退 |
| B2 | 截断判定改成 `coin == 上限` | 余额恰等于上限不算截断 |
| B3 | 超范围仍抛异常 | 超范围仍渲染地址与清单 |

### 🔴 Java 侧做变异验证的一个坑（这次真踩到了）
用脚本改源码 → 跑测试 → **`shutil.move` 还原**，会把文件 mtime 一并还原成变异前的时间，
于是 Maven 增量编译认为「源码没变」，**后续构建跑的仍是变异后的 class**。
表现：还原后跑全量出现一条与本次改动毫无关系的红（`outOfRangeStillRenders…`），
查数据库、查缓存、查事务全是死路 —— 因为源码和行为对不上。
👉 **还原后必须 `touch` 源文件**（或直接重写文件内容而非 move）。Dart 侧无此问题。
