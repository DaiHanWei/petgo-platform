## Dev Notes

### 🔴 归因链此前是断的 —— 本 story 才真正闭合
Story 3.4 在 `shop_order_lines` 上留好了 `entry_source` / `trigger_type`，
但**下单时没有任何地方能提供它们的值**：商品「什么时候、从哪个入口加进购物车」只有加购那一刻知道，
而那一刻的信息此前没有被保存。Story 3.7 因此一律传 null（宁可空着也不编）。

**V114 补上这一环**：`shop_cart_items` 加两列 → 加购时记 → 下单时抄到订单行。
链路：`Toko 卡片(?from=) → 详情页 → POST /me/cart/items?entrySource= → shop_cart_items → shop_order_lines`。

**为什么选服务端而不是客户端埋点**（AC 明说二选一）：AB-13B 要用它判定 A-16（复购引擎值不值得做），
而客户端事件会被广告拦截、丢包、杀进程吃掉。**决定下个版本做什么的数字，不能建在会丢的通道上。**

🔴 **同一 SKU 二次加购不覆盖首次来源**：第二次加购通常发生在用户已决定要买之后
（比如在购物车里 +1），那不是转化发生的地方。让后来的动作覆盖首次来源会把转化归给错的入口。

🔴 **区域④「全部精选」与品类页是两个入口**，不能混为一谈 —— 混了就算不出「品类页值不值得做」。

### 埋点：AC 的七个名字全部改名（护栏要求，不是妥协）
| AC 原名 | 实际事件名 |
|---|---|
| `add_to_cart` | `toko_add_to_cart_tapped` |
| `cart_viewed` | `toko_cart_page_viewed` |
| `checkout_started` | `toko_checkout_page_viewed` |
| `checkout_blocked_out_of_range` | `toko_checkout_out_of_range_shown` |
| `order_submitted` | `toko_order_submitted` |
| `payment_succeeded` | `toko_order_payment_succeeded` |
| `payment_failed` | `toko_order_payment_failed_shown` |

命名护栏要求「模块前缀 + 动作词尾」（2026-08-04 用户明确要求：产品要能一眼看出是哪个页面的哪个动作）。
🔴 `payment_failed` 的 `_failed` 不在允许词尾里 —— **不放宽规则、不塞 legacyEvents**，
改成 `_shown`（报的本就是「向用户展示了失败」这件事，而漏斗上要看的正是有多少人在这一步被挡住）。

`items[]{sku_id, qty, entry_source, trigger_type}` **不进客户端事件**：行级归因走服务端（见上），
客户端只报一个 `item_count`。多送一份易丢的副本没有价值，还多一处 PII 风险面。

### 🔴 H3 是本工作线第五次假绿（这次的病根：整文件 `contains`）
原断言是「`cart_repository.dart` 的源码里含 `entrySource`」——
删掉真正发请求的那一行后，**方法签名里还有这个词**，于是照样绿。
与 HANDOFF 记的 `damageSqlGuardsAvailableNotActual` 是同一个病根：
**用整文件 contains 断言行为，等于让任何同形状的文本替它满足**。

**补法**：新增 `cart_attribution_test.dart`，用真 `CartRepository` + 捕获型 `HttpClientAdapter`，
断言**真实请求的 queryParameters**：
- 带来源 → 参数里确实有它（H3 红）
- 无来源 → **不发这个参数**（防「编一个 TOKO_CART 默认值」，H3b 红）
- 详情页把路由 `?from=` 一路带进加购（H3c 红）
