# Story 7.1: 评价建模与提交接口

Status: **review**（后端）

## 交付物
`V123__init_shop_reviews.sql` · `review/domain/{ReviewStatus,ShopReview}` · 仓储 ·
`ShopReviewService` · `MeShopReviewController` + `ShopReviewController` ·
审核重试接入既有 `ShopOrderExpiryScanner`（不新建定时器）。

## AC 与验证
| AC | 层级 | 验证 |
|---|---|---|
| 表结构（评分 1–5 / 文字 ≤500 / 图 ≤6 / 审核状态） | L0 | `ddl-auto=validate` + `inputValidation` |
| 🔴 唯一约束保证「每个订单每个 SKU 各评一次」 | **L1** | `oneReviewPerOrderLine` |
| 仅 `COMPLETED` 可评，否则明确 ProblemDetail | L1 | `nonCompletedOrderCannotBeReviewed` |
| 1–5 星必填；文字与图选填 | L1 | `inputValidation`（只给星级也能提交） |
| 🔴 **复用既有内容审核，同步过滤，命中即拦截不发布** | **L1** | `blockedContentIsNotPublished` |
| 🔴 **不走「先发布后审核」** | L1 | 同上（先出结论再落库） |
| 被拦截时停留编辑态、可改后重提，**不进人工队列** | L1 | `resubmitAfterBlockOverwrites` |

## 三处刻意的设计选择
1. **唯一约束打在【订单行】上，不是打在 SKU 上。**
   同一 SKU 在一张订单里可能有两行（不同价快照），各自可评；换一张订单也能再评。
   打在 SKU 上会变成「上次买的评过了这次就不能评」—— 那不是我们要的语义。
   用例 `sameSkuInAnotherOrderCanBeReviewedAgain` 正面守住它。
2. **`RISKY` 也拦。** 内容审核在别处会把 RISKY 送人工队列，但评价**不进人工队列**：
   让用户自己改两个字，比让运营每天筛一遍评价快得多，也准得多。
3. **三方不可用时落 `PENDING` 而不是 `BLOCKED`。**
   fail-closed（都不发布）是一致的，但**不该让用户去改一段本来没问题的文案** ——
   那是把系统故障说成用户违规。由既有扫描组件的重试自己收敛。
