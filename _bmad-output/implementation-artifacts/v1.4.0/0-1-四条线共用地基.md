# Story 0.1: 四条线共用地基（共享约束、跨分支接口与事件、后台抽屉页签头）

Status: ready-for-dev

> 版本 v1.4.0 · 地基 · 分支 `feat/1.4.0-foundation`（从 `dev_1.4.0` 切，完成后合回 `dev_1.4.0`）
> 口径优先级：`CROSS-STORY-DECISIONS.md`「2026-10-18 V1.4.0 四条线共用地基」> 本 story > 各线 PRD §6（`_bmad-output/planning-artifacts/v1.4.0/`）
> 范围：**只做后端 + 后台模板**。不做任何业务逻辑（不入账成长值、不算名额、不送礼、不收藏），App 端零改动。

## 为什么有这条 story

V1.4.0 四条线（① Tailrent Level / ② 多宠物 / ③ 送礼 / ④ 推送开关与收藏）要用四个云端会话并行开发。① PRD §6.2 规定共享约束、后台抽屉页签头由 ① 一次做完，②③ 调 ① 的 `GrowthQueryService`、① 监听 ③④ 的事件。若四个分支同时从 `dev_1.4.0` 切出，②③ 编译期找不到 ① 的接口、L1 撞上缺值的 CHECK 约束，agent 会自造替身或私改约束，合并时出现重复定义与约束丢值（`ck_notifications_type` 已出过三次事故）。

本 story 把**所有跨分支的东西**提前落进 `dev_1.4.0`：四个功能分支都从本 story 合入之后的 `dev_1.4.0` 切出，从第一天起就有真接口、真事件类、真约束。

## Story

As a V1.4.0 四条线的开发者,
I want 共享约束、跨分支接口与事件类、后台抽屉页签头在开工前就已存在于集成分支,
so that 四个分支各自开发时不需要替身、不需要改共享约束，合并时不冲突。

### 开工第一步：两条约束的并集核查

```bash
git fetch --all --prune
for b in $(git for-each-ref --format='%(refname:short)' refs/remotes/origin | grep -v HEAD); do
  git diff --name-only main...$b -- petgo-backend/src/main/resources/db/migration | while read f; do
    git show $b:$f 2>/dev/null | grep -qiE "ck_notifications_type|ck_payment_intents_purpose" && echo "$b $f"

done | sort -u
```
