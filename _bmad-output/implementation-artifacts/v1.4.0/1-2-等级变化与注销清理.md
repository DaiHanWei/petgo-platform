## Story

As a 用户,
I want 累计 EXP 达到门槛时等级自动变化、注销后成长值数据被清理,
so that 我的等级总是准确的，个人数据不残留。

## Acceptance Criteria

**AC1 — 单一连锁出口 `GrowthLevelChangeHandler`** `[L0]`（AD-10、§5.4）
1. 新建 `growth.service.GrowthLevelChangeHandler`，方法 `onLifetimeChanged(GrowthAccount lockedAccount, RuleCode source)`：在**调用方的同一事务**内（账户行已被锁）按 `growth_levels` 计算 `newLevel = max(level) where threshold ≤ lifetime_total`；与 `account.level` 不同则更新 `level` 并 `publishEvent(new GrowthLevelChangedEvent(userId, oldLevel, newLevel))`（升降都发）。
2. Story 1.1 的 `GrowthLedgerService` 在 `accrue` 与 `reverse` 改完 `lifetime_total` 后都经 1.1 预留的收口方法调用本 handler，`source` 传本次流水的规则代码（`reverse` 传原流水规则代码）。
3. 等级变化的一切连锁**只在这一处**（§5.4）：本 story 只做「更新 level + 发事件」；Story 2.1 在同一方法里加「升级且非 `LAUNCH_BACKFILL` → 写待弹庆祝 + AFTER_COMMIT 发通知」，本 story 为此**保留 `source` 参数**并写 TODO 注释指向 Story 2.1。
4. 等级表查询：一条 SQL（`SELECT MAX(level) FROM growth_levels WHERE threshold <= :total`），不缓存（护栏：不加缓存层）。

**AC2 — 升级** `[L0]` `[L1]`
- Given 用户累计 495、等级 Lv4，When 入账 +5 达到 500，Then 等级变为 Lv5（BUDDY），发布一次 `GrowthLevelChangedEvent(u, 4, 5)`。

**AC3 — 一次跨多级只发一条** `[L0]` `[L1]`
- Given 用户一次入账跨越多级（Lv4 → Lv7），When 入账完成，Then 只发布一次 `GrowthLevelChangedEvent(u, 4, 7)`。

**AC4 — 降级** `[L0]` `[L1]`（PRD AC6 前半、FR-143.5）
- Given Lv10 用户（累计 ≥ 3,300）因扣回累计跌破 3,300，When `reverse` 完成，Then 等级降为 Lv9 并发布 `GrowthLevelChangedEvent(u, 10, 9)`；`GrowthQueryService.getLevel` 立即（事务提交后）返回 Lv9。
- 本 story 用 Story 1.1 已有的扣回路径（如 `reverse` 一条大额流水，测试里直接造数据）验证；「因退款」的真实链路在 Story 1.3。

**AC5 — 满级照常累积** `[L0]` `[L1]`
- Given 达到当前最高级（Lv20，门槛 41,300）的用户，When 继续入账，Then `lifetime_total` 照常增加，等级不变，不发事件。

**AC6 — 头像框读时推导** `[L0]`（AD-10 第三点、PRD AC19）
1. 新建 `growth.service.GrowthFrameResolver`（纯函数，无 IO）：
   - `Set<FrameChoice> availableFrames(GrowthTier tier)`：NEWBIE → 空（只有「不戴」）；BUDDY → {BASIC}；GUARDIAN → {BASIC, UPGRADED}；STAR → {BASIC, UPGRADED, ANIMATED}。`NONE` 恒可选，不计入「可用框」集合。
   - `FrameChoice effectiveFrame(GrowthTier tier, FrameChoice frameChoice)`：`frameChoice == null`（自动）→ 最高可用档（NEWBIE → `NONE`）；`NONE` → `NONE`；已选且仍可用 → 它；已选但不可用（降级）→ 最高可用档。
   - `boolean isManual(FrameChoice frameChoice)`：非 null 即手动。
2. Given 用户手动选了 UPGRADED 后从 Lv10 降到 Lv9，When 查询生效头像框，Then 返回 BASIC（AC19）；未手动选过的用户返回当前段位最高可用档，NEWBIE 无框（`NONE`）。
3. **不存「当前框」**；`frame_choice` 只在用户主动切框时写（Story 3.3），降级时**不改写** `frame_choice`（重新升回 GUARDIAN 时恢复用户原来的手动选择）。
4. 供 Story 1.4（`/me/growth` 头像框四档）、Story 2.1（`frameAction`）、Epic 3（作者等级下发、切框接口）使用；本 story 不暴露任何接口。

**AC7 — 注销清理** `[L0]` `[L1]`（AD-18、PRD AC10）
1. 新建 `growth.service.GrowthAccountDeletionService.deleteByUserId(long userId)`（`@Transactional`，幂等可重跑）：物理删除 `growth_ledger`、`growth_daily_counters`、`growth_accounts` 中该用户的行。`growth_ledger.reverses_id` 自引用 FK：先删本用户的反向流水再删原流水，或一条 `DELETE … WHERE user_id = ?`（同一用户的原流水与反向流水同属一人，一条 DELETE 内 FK 检查在语句结束时满足——以 L1 实测为准，若报 FK 错误改为两步）。
2. `AccountDeletionService.execute` 中，在 `tailsonalityDeletion.deleteOwnerTypeByUserId(userId)` **之后**、`pawCoinDeletion.voidBalanceAndPurge(userId)` **之前**调用（AC10 / AD-18），并写一行注释说明位置原因（users 行只匿名化不删，FK CASCADE 永不触发，必须显式删）。
3. Given 用户注销，When `AccountDeletionService.execute` 执行，Then 该用户的三张表行全部删除，后台查不到其明细（AC10）。
4. 停用账号（`status = DEACTIVATED`）**保留**数据（AD-18）；不显示等级由 Epic 3 的展示层处理，`getLevel` 已在 Story 1.1 对停用返回不参与。

**AC8 — 契约与回归** `[L0]`
1. ② 依赖的 `GrowthLevelChangedEvent` 字段与地基一致（不改 record）；事件在入账事务内发布，② 的监听可用 AFTER_COMMIT。
2. `mvn -B clean package` 绿。

### 实现提示

- handler 的事件在**入账事务内**发布，② 用 `@TransactionalEventListener` 接，事务回滚不会让 ② 误算名额。
- 连跳只发一条是自然结果：一次 `accrue` 只调一次 handler，比较的是本次入账前后的落库等级。
- 降级与「运营调高门槛」的批量重算（Story 4.1，`GrowthRecalcService`）不走本 handler 的单用户路径，但会复用 `GrowthLevelChangedEvent` 与 Story 2.1 的连锁逻辑——本 story 把「算新等级」写成 handler 内可复用的包级方法即可，不要提前做批量。
- 头像框推导只依赖段位（`GrowthTier`），段位来自 `growth_levels.tier`；Epic 4 允许改等级表但段位单调，推导不受影响。

### 架构约束

- AD-10：`level` 落库，入账 / 调整 / 改等级表时同事务重算；升降都发 `GrowthLevelChangedEvent`；头像框读时推导；权益判定一律 `getLevel(s)`。
- AD-18：注销删三张表；在 tailsonality 之后、PawCoin 作废之前；停用保留数据。
- §5.4：等级变化连锁只在 `GrowthLevelChangeHandler` 一处。
- 跨线（§6.5）：② 依赖 `GrowthLevelChangedEvent` 升降都发、`getLevel` 返回落库真实等级。

### 与前后 story 的边界（本 story 不做）

- **不做**升级待弹庆祝（`celebrate_from_level / celebrate_to_level`）、`GROWTH_LEVEL_UP` 通知与推送、`/popups` 接口 → **Story 2.1**（在本 story 的 handler 里追加）。
- 不做 `LAUNCH_BACKFILL` 存量补算（Story 2.2，迁移内纯 SQL，**不经** handler、不发事件）。
- 不做消费返 / 退款（Story 1.3；1.3 的退款扣回经 1.1 `reverse` → 本 story handler 自动降级，AC6 的真实链路在 1.3 验收）。
- 不做接口与 App（1.4 / 1.5 使用 `GrowthFrameResolver`）；不做切框接口 `PUT /frame`（Story 3.3）；不做等级表修改与批量重算（Story 4.1）。
