## A · 阻塞发布（没有这些不能上线）

### A1 🔴 V121 共享表加列的认领签字
- **做什么：** `V121__add_pet_profile_weight.sql` 给**共享表 `pet_profiles`** 加了
  `weight_kg` / `neuter_status` 两列（只加列、全可空、不回填）。
- **为什么阻塞：** 并行契约要求触碰共享表**先认领**；这次是**在产品的临时授权范围之外**的，
  当时为了不停工先做了、并明确记为待补。三线并行时这类漏认领正是 2026-07-30 事故的成因。
- **谁来做：** 认领人 + 另两条工作线确认。
- **机器为什么做不了：** 这是跨团队的约定，不是代码。

### A2 🔴 HEX-SIGNOFF 未发出
- **做什么：** 发出 `HEX-SIGNOFF.md`，收齐签字。
- **机器为什么做不了：** 需要人对内容负责并签字。

### A3 ⚠️ S-12「赠币核销额（近似）」须财务确认精度够不够
- **做什么：** 财务看 `/admin/shop/reconciliation` 的「其中：赠币核销额（近似）」一行，
  确认这个近似值**够不够做账**。
- **为什么阻塞：** 本版本**没做**钱包侧余额批次分层（S-12 折中，钱包只留了不启用的
  `batch_type` 扩展位）。**够用 → 就这样发；不够用 → 得回头改钱包，那是全套里代价最高的返工。**
  🔴 越晚确认越贵 —— 上线后数据一多，改钱包要带数据迁移。
- **机器为什么做不了：** 「够不够用」是财务口径判断。

### A4 🔴 三处游标 wire 格式变更 —— 确认发布顺序
- **做什么：** 确认后端与 App **同版本发布**，或确认过渡兼容够用。
- **背景：** 本轮修了同一族的三处分页丢数据缺陷，`nextCursor` 都从「纯 epochMillis」
  改成了 base64url 复合键：

  | 端点 | action_item |
  |---|---|
  | `GET /api/v1/notifications` | `NOTIFY-CURSOR-TIE` |
  | `GET /api/v1/orders` | `ORDER-CENTER-CURSOR-TIE` |
  | `GET /api/v1/me/pawcoin` | `PAWCOIN-LEDGER-CURSOR-TIE` |

  已核对 Flutter 侧三处都把游标当**不透明串**原样回传、不解析，
  服务端也各留了一轮过渡兼容（纯数字按旧语义处理）。
- **要人确认的是：** 有没有**第三方/后台/脚本**在解析这个游标。
- **机器为什么做不了：** 仓库外的消费者，扫不到。

### B4 ✅ 已决策（2026-08-18）：健康记录页的品类跳转入口 **保留**

- **决策：留着。** 无需改代码。
- **它是什么：** 驱虫 / 疫苗记录下方一行**系统生成**的文字入口 → `/shop?category=OBAT_VITAMIN`。
  🔴 品类级、**整条路径上不存在能携带 SKU 的位置**，有 CI 守卫看着（`ConsultShopBoundaryTest`）。
- **背景（为什么当初是个问题）：** FR-110 允许「按结论中的结构化健康记录类型跳转对应品类」，

  所以入口做在了那里。
- **⚠️ 转成 staging 的观察项（不是决策项）：** **无视觉稿**，现在是用既有 token 拼的一行
  TextButton。在 staging 上看一眼观感 —— 位置、字重、与卡片的间距是否像「系统提示」而不是广告。
- **如果日后要撤：** 删 `health_list_page.dart` 的 `_categoryJumpRow` 一个 widget 即可，
  边界守卫与埋点都不受影响。

### C1 🔴 两个必须立刻挂的告警

### C2 归因链偏差率：上线第一周就对一次，别攒
- **怎么对：** `/admin/shop/repurchase-dashboard` 的「归因链核对底账」是**服务端权威口径**；
  把 PostHog 里 `toko_order_submitted.items[]` 按 `entry_source` 的同口径聚合放旁边，
  差值就是客户端埋点的丢失量。
- 🔴 **偏差过大一律以服务端为准**，不要反过来改服务端迁就端上。

### C3 ⚠️ 基线埋点缺口 —— 不可弥补，只能知情
- 电商 Tab 替换既有 Tab 时，被替换 Tab 的曝光基线**必须在前一个版本先发**才有对比。
  本版本发布时**那个基线不存在**（归 DEP-1）。
- 后果：能看到 Toko 的绝对数，**看不到「用一个 Tab 位换来的东西值不值」**。
  🔴 **不要**拿上线后的 Toko 数据去和「凭印象记得的」旧 Tab 数据比 —— 那个对比不成立。
- 详见 `EPIC-9-DELIVERY-NOTE.md` §4（附 L-6 前车之鉴）。

### C4 A-19：按月核对实际承运成本与收取运费的差额
- 读数在 `/admin/shop/margin` 的 `shippingNet`（运费收入 − 承运成本），**为负说明运费在补贴配送**。
- A-19 承接的正是 FR-99「省掉整条承运商 API 对接工期」的全部风险 —— 这个假设**必须真的去验**。

### C5 DEP-6 到位前，复购引擎的读数会长期接近 0
- FR-109 的触发覆盖率分母是「有粮购买历史的用户」，分子是「有触发的用户」。
  **喂量数据没填 → 恒不触发**，这是**一等路径**，不是故障。
- 看板已经会显式提示「这是 DEP-6 数据没到位，不是机制无效」——
  ⚠️ 不看提示就下结论会得出完全相反的判断。
