## Dev Notes

### 🔴 不变式放在 DB 而不是只放应用层
`coin + cash = amount` 由 CHECK 强制。理由：**拆分金额对不上就是账对不平，
而账不平只在退款时才暴露 —— 那时已经动过真钱了**。测试里连「差 1 分钱」都断言必须被拒。

### 🔴 放宽 CHECK 时最容易顺手丢掉的是既有值
2026-07-30 事故正是「两边各自 `DROP + ADD` 同一个 CHECK，合并后一方取值整类失效」——
**两边测试全绿、git 无冲突、编译不报错**，只在真跑那条路径时才炸。
故本迁移 `DROP + ADD` 时显式列全三值并注明本次新增的只有 `MIXED`，且有断言验既有两值仍被接受。

### ✅ 编译器帮了大忙：三处虚拟商品支付被强制面对 MIXED
加 `MIXED` 后，`ConsultPayService` 与 `IdCardHdService`（两处 switch）的**穷尽 switch 直接编译失败**。
这不是"补编译错误"，而是**把 AD-3 的纵深防御落到代码里**：三处均显式
`case MIXED -> throw validation("该商品不支持混合支付")`。
🔴 **显式拒绝而不是落到 default** —— 前者在编译期就逼着每个新渠道的引入者来面对这个分支，
后者会静默把新渠道当成某个旧分支处理。

> ⚠️ 顺带修正一处自己的误判：`AiUnlockService` 的 switch 是 `UnlockMethod` 不是 `PayChannel`，
> 我一开始误加了 `case MIXED` 导致编译失败，已撤回。

### 🔴 coin_ratio 不参与计算
只作展示与审计冗余（AD-2）。退款拆分一律用 `coin_amount/amount` 的**整数累计法** ——
浮点比例参与计算必然凑不平，而 Epic 5 要求多次部分退款后全额退款**精确归零**。
