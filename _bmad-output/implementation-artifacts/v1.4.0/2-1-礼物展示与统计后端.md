Status: ready-for-dev

> 前置：**Story 1.1**（`gift_catalog` / `gift_orders` / `gift_pet_wall` / `gift_pet_supporters` 四表、`GiftPetDirectory` + `SinglePetGiftPetDirectory`、`GiftDeliveryService` 在交付同事务维护两张汇总表）、**Story 1.2**（退回只改订单状态、不碰汇总表）、**Story 1.3**（App 送礼按钮；本 story 不依赖其代码）。

## Story

As a 浏览宠物的用户,
I want 看到这只宠物收到的礼物总价值、礼物墙和粉丝榜,
so that 礼物成为宠物的荣誉展示。

## Acceptance Criteria

**AC1 — 礼物页汇总 + 礼物墙 `GET /api/v1/pets/{petId}/gifts`** `[L0]` `[L1]`（AD-3、AD-10、PRD AC11 / AC17）
1. 需登录 USER（`SecurityConfig` 显式规则，见 Dev Notes「安全规则」）。响应 `PetGiftShowcaseResponse`（camelCase，只下发代码与数字、礼物名 EN / ID 两份快照原样下发，不下发任何拼好的显示串）：
   ```
   {
     pet: { petId, name, avatarUrl, petType },
     viewerIsOwner: false,
     totalValue: 53000,          // Σ unit_price × count，只含已送达（汇总表本身只在交付时写）
     giftCount: 4,               // Σ count
     supporterCount: 2,          // 见 AC2.5 的主人视角口径
     wall: [ { nameEn, nameId, iconUrl, unitPrice, count }, … ]   // 全部种类
   }
   ```
2. 礼物墙排序：`unit_price DESC, count DESC`，再按 `gift_id ASC` 兜底保证稳定；每行来自 `gift_pet_wall` 的快照列（`gift_name_en` / `gift_name_id` / `gift_icon_url` / `unit_price`），**不 join `gift_catalog` 取现值**。同一礼物改价后按价位分成两行（AD-3 主键含 `unit_price`）。
3. Given 宠物收到 3 个 🦴（Rp1.000）与 1 个 🎂（Rp50.000），When 主人或访客请求，Then `totalValue = 53000`、`giftCount = 4`、`wall = [🎂×1, 🦴×3]`（单价降序）；主人与访客拿到的 `totalValue` / `giftCount` / `wall` 完全一致（AC11）。
4. Given 运营把 🎂 下线（`gift_catalog.status = OFFLINE`）且改名改价，When 请求，Then 墙上 🎂 仍按收到时的快照名称、图标、单价显示，总数不变（AC17）。
5. 无礼物时 `totalValue = 0`、`giftCount = 0`、`supporterCount = 0`、`wall = []`（App 据此出 E3 / E4 空态），仍 200。
6. 宠物信息取自 `GiftPetDirectory.pet(petId)`（1.1 定义的 `GiftPet(petId, ownerId, name, avatarUrl, petType, breed, ownerActive, ownerDeleted)` 的 name / avatarUrl / petType）；`avatarUrl` 经 `AliyunOssClient.exifStrippedDeliveryUrl` 处理（与 `VisitorProfileResponse.of` 同口径，`VisitorProfileResponse.java`:44）。

**AC2 — 粉丝榜 `GET /api/v1/pets/{petId}/gifts/supporters?cursor=`** `[L0]` `[L1]`（AD-3、AD-10、PRD AC12 / AC12a、decision-log ③ Q1「粉丝榜显示累计金额」）
1. 一人一行，数据源 `gift_pet_supporters`；排序 `total_amount DESC, last_sent_at DESC, sender_id DESC`；每页 20；响应 `{ items: [...], nextCursor: string | null }`。
2. 行结构 `GiftSupporterRow`：`{ rank, nickname, avatarUrl, deleted, totalAmount, giftCount, gifts: [{ iconUrl, nameEn, nameId, count }], moreKinds }`
   - `rank` 从 1 连续递增（同额也不并列——同额已按最近送礼时间定序）；跨页连续（游标里带下一页起始名次）。
   - `gifts`：该送礼人送给这只宠物的礼物按种类聚合（数据源 `gift_orders WHERE pet_id = ? AND status = 'DELIVERED' AND sender_id IN (本页)`，按 `(gift_id, unit_price)` 分组，取快照列），按 `unit_price DESC, count DESC` 取前 3 种；`moreKinds` = 其余种类数（0 时省略或为 0，二选一写死并在 DTO 注释说明）。**一页一次查询**，不按行查。
   - `nickname` / `avatarUrl` / `deleted` 来自 `AccountQueryService.findAuthorViewsWithoutTags`（一页一次，`AccountQueryService.java`:208；本列表不展示运营标签）；注销者 `deleted = true`、`nickname` / `avatarUrl` 为 null，由 App 本地化为「已注销用户」（AuthorView 既有口径，`AuthorView.java`:8-10、:21-23）。
   - **不下发** `sender_id`、`users.public_token`、任何自增 id（UI 稿 E1 粉丝行不可点）。
3. Given 粉丝榜，When 请求，Then 一人一行、按累计金额降序（同额按最近送礼时间倒序）、每行含累计金额 `totalAmount`；注销者 `deleted = true`（AC12）。
4. **主人视角隐藏**（AC12a）：`viewerIsOwner` 为 true 时，排除主人隐藏的送礼人——SQL 内 `NOT EXISTS (SELECT 1 FROM user_hide_relations h WHERE h.holder_id = :ownerId AND h.target_id = s.sender_id)`（**不分来源**，BLOCK 与 REPORT 都排除，与 `UserHideRelationReader.isHidden` / `hiddenByHolder` 同口径，见 Dev Notes「拍板点」）；排除在 SQL 里做，名次因此顺延、分页不出空洞。访客视角不排除。
5. `supporterCount`（AC1 汇总里那个数）与本列表同口径：主人视角排除其隐藏的人（「Pendukung · N orang」与列表行数一致）；`totalValue` / `giftCount` / `wall` **不排除**（墙数量照算）。
6. Given B 拉黑了 A 之后 A 给 B 的宠物送礼，When B 看自己宠物的粉丝榜，Then 没有 A、后面的人名次前移；When 其他访客 C 看，Then 有 A；墙数量与 `giftCount` 两边都包含 A 的礼物（AC12a）。
7. 游标：新建 `gift.web.dto.SupporterCursor(long totalAmount, Instant lastSentAt, long senderId, int nextRank)`，base64url 编码 / 解码照 `shared.paging.KeysetCursor`（`KeysetCursor.java`:37-60 的 `encode()` / `decodeOrNull()` 写法）；非法游标 → 400 ProblemDetail。⚠️ 游标内含 `senderId` 与既有 PawCoin 流水游标内含流水 id 是同一档取舍（不透明串、不作为标识使用），在类注释写明。

**AC3 — 礼物页可见性（两个端点共用）** `[L0]` `[L1]`（AD-10「可见性沿用访客视图的拉黑规则」、FR-148.1）
1. 新建 `gift.service.GiftShowcaseAccess.requireVisible(viewerId, petId)`，规则逐条对齐 `InAppVisitorPetController.requireVisible`（`InAppVisitorPetController.java`:107-121）：
   - `GiftPetDirectory.pet(petId)` 为空或 `ownerDeleted = true` → 404，detail 用与访客视图同一句 `"链接已失效"`（`InAppVisitorPetController.java`:62）；
   - 查看者主动拉黑了主人（`hideRelations.isBlocked(viewer, owner)`）→ 403 `AppException.blockedUser("你已拉黑该用户")`；
   - 主人主动拉黑了查看者（`isBlocked(owner, viewer)`）→ **同一个 404**（不可与「宠物不存在」区分）；
   - 主人本人查看 → 放行，`viewerIsOwner = true`。
2. **主人被封号**（`ownerActive = false` 且 `ownerDeleted = false`）：访客 Diary Tab 对封号主人返回 404（`VisitorProjectionService.findVisibleProfileById` 过滤 `isActive`，`VisitorProjectionService.java`:106-109），但 FR-148.1 规定「主人封号仍可收礼」、1.1 发起送礼也放行封号主人 → 礼物页**放行封号主人的宠物**（按建议实现，见 Dev Notes「拍板点 ①」）。
3. 两个端点**不接受** userId / token 参数，查看者只取 JWT `sub`；非 `role=USER` 的 token 不可达（见安全规则）。

**AC4 — 统计字段 `giftTotalValue`（主人 / 访客 / H5 一致）** `[L0]` `[L1]`（AD-10、PRD §3.2 影响面、decision-log ③「统计卡中间格改礼物总价值」）
1. `ArchiveStatsResponse`（`ArchiveStatsResponse.java`:23-29）末尾追加 `long giftTotalValue`；**保留** `consultCount`（旧版 App 仍在读）。
2. `VisitorStats`（`VisitorStats.java`:28-32）末尾追加 `long giftTotalValue`；**保留** `consultCount`。
3. 计算只有一处：`TimelineService.getStats`（`TimelineService.java`:616-628）里，用它已解析出的那只宠物 `profile.getId()` 调新的 `GiftShowcaseQuery.totalValueOfPet(petId)`（`SELECT COALESCE(SUM(unit_price * count), 0) FROM gift_pet_wall WHERE pet_id = ?`）。**按宠物算，不按主人汇总**——② 合入后同一主人多只宠物，按主人汇总会把几只宠物的礼物混在一起。
4. `VisitorProjectionService.stats`（`VisitorProjectionService.java`:261-268）把 `authorStats.giftTotalValue()` 透传进 `VisitorStats`——**复用作者态的计算，不另写一份**（与该类注释「两个页面的数字出自同一个实现」一致）。站内访客 `/api/v1/pets/{petId}/visitor/stats`（`InAppVisitorPetController.java`:85-88）、分享 token `/api/v1/public/shared-pets/{cardToken}/stats`（`VisitorPetController.java`:73-76）、主人 `/api/v1/pet-profiles/me/archive-stats`（`ProfileApiController.java`:178-181）三处因此自动带上该字段。
5. Given 宠物收到 3 个 🦴（Rp1.000）与 1 个 🎂（Rp50.000），When 分别请求上述三个统计端点，Then `giftTotalValue` 都是 `53000`；无礼物为 `0`（AC11）。
6. 已退回（`UNDELIVERED_REFUNDED`）、待退回、需人工、过期、失败、待付款的订单**都不计入**——汇总表只在 `DELIVERED` 时由 1.1 写入，本 story 不得从 `gift_orders` 现算总价值。

**AC5 — Diary 详情礼物区 `giftPets`** `[L0]` `[L1]`（AD-5、AD-10、UI 稿 A3 / A5 / A6、PRD AC14 单宠部分）
1. `ContentDetailResponse`（`ContentDetailResponse.java`:20-85）末尾追加 `List<GiftPetSummaryView> giftPets`（NON_NULL：为 null 时省略）。
2. 只有 `post.getType() == ContentType.GROWTH_MOMENT`（Diary）才调：经 `GiftPetDirectory.petsOfPost(post.getId())` 取宠物（单宠过渡实现返回 0 或 1 只；**不得**直接读 `post.getPetId()` 绕过端口）。端口返回空表 → `giftPets = null`（App 不渲染礼物区）。⚠️ 1.1 的过渡实现对**私密 / 审核中 / 举报隐藏**的 Diary 也返回空表（1.1 AC3.2）——作者本人看自己的私密 Diary 因此没有礼物区，与「私密 Diary 他人看不到、自然不展示礼物」一致，按此实现，不在本 story 另开口子。`DAILY`（Moment）/ `KNOWLEDGE`（Tips）不调端口、直接 null。
3. 元素 `GiftPetSummaryView`：`{ petId, name, avatarUrl, totalValue, giftCount, kindCount, wallPreview: [{ iconUrl, nameEn, nameId, unitPrice, count }] }`
   - `wallPreview` = 该宠物礼物墙前 3 行（与 AC1.2 同序，UI 稿 A3「单价最高的 3 种礼物图标」）；`kindCount` = 墙总行数（App 算「+N」= `kindCount − wallPreview.length`）。
   - 宠物有关联但 0 礼物 → 照常给一项：`totalValue = 0`、`giftCount = 0`、`wallPreview = []`（A5「Belum ada hadiah」）。
4. 查询批量：一次取全部关联宠物的汇总（`WHERE pet_id IN (:ids)`）+ 一次取墙前 3 行（窗口函数 `ROW_NUMBER() OVER (PARTITION BY pet_id ORDER BY unit_price DESC, count DESC, gift_id)`），不按宠物逐个查——为 4.1 多宠留好形状。
5. 本人看自己的 Diary（A6）照常下发；送礼按钮显隐由 App 按 `isAuthor` 判断（Story 1.3），后端不另给字段。
6. 可见性不另做：详情本身已过 `requireVisiblePost`（`ContentDetailService.java`:76-101）。
7. Given 关联 1 只宠物的他人 Diary 详情，When 请求，Then 响应含 `giftPets` 一项、数值与 AC1 同一宠物的 `totalValue` / `giftCount` / 墙前 3 行一致；Moment / Tips 详情不含 `giftPets`。

**AC7 — Java 金额缩写工具（与 App 同规则、同用例）** `[L0]`（PRD §3.2 影响面、AD-10）
1. 新建 `com.tailtopia.shared.format.IdrCompact`（纯函数、无 Spring 依赖）：`static String format(long amount)` 返回整串（如 `"Rp1,5rb"`）；`static Parts parts(long amount)` 返回 `record Parts(String number, String unit)`（供模板分字号）。

3. **共用测试用例表**（单一事实源是本表；Java `IdrCompactTest` 与 Dart `test/shared/format/idr_compact_test.dart`（Story 2.2）**逐行照抄同一张表**，两边测试文件头注释互相指向对方路径，改一边必须改另一边）：

   | 0 | Rp0 | 1000000 | Rp1jt |
   | 999 | Rp999 | 1050000 | Rp1jt |
   | 1000 | Rp1rb | 1200000 | Rp1,2jt |
   | 1500 | Rp1,5rb | 1290000 | Rp1,2jt |
   | 1999 | Rp1,9rb | 1999999 | Rp1,9jt |
   | 53000 | Rp53rb | 25000000 | Rp25jt |
   | 188000 | Rp188rb | 1234567890 | Rp1234,5jt |
   | 188500 | Rp188,5rb | | |

   `parts` 另测：188000 → (`"188"`, `"rb"`)、1500 → (`"1,5"`, `"rb"`)、0 → (`"0"`, `""`)、1200000 → (`"1,2"`, `"jt"`)。

### 安全规则

- `GET /api/v1/pets/*/gifts` 与 `GET /api/v1/pets/*/gifts/supporters` → `hasRole("USER")`。理由：主人视角判定靠 `viewerId == ownerId`，兽医 token 的 `sub` 与 `users.id` 撞号会被误判成主人（`InAppVisitorPetController` 类注释 :43-46 同一风险）。
- 1.1 只加了 `POST /api/v1/pets/*/gifts`（限定方法，见 1.1 story AC9.3）→ 本 story 补 `HttpMethod.GET` 的 `/api/v1/pets/*/gifts` 与 `/api/v1/pets/*/gifts/supporters` 两条精确 matcher（不写通配，不影响 `/api/v1/pets/*/visitor/**`），放在 `anyRequest()` 之前。T0 以 1.1 实际提交为准。
- 游客 → 401 ProblemDetail。

### 实现提示

- 总价值、墙、粉丝榜一律读汇总表；`gift_orders` 只在粉丝行的「礼物 × 数量」聚合里读（限定 `status = 'DELIVERED'` 与本页送礼人），不用于总价值。
- `GiftShowcaseQuery` 用 `NamedParameterJdbcTemplate`；整页查询次数为常数：汇总 1 + 墙 1（礼物页）；粉丝页 1 + 礼物聚合 1 + 作者投影 1；详情 2（汇总 + 墙前 3）。
- `TimelineService` 注入的是 `gift.service.GiftShowcaseQuery`（读汇总表的只读查询），**不是**送礼交付服务；`GiftShowcaseQuery` 不得反向依赖 `profile` / `content` 的 service（避免环）。
- 「Rp」「rb / jt」的分字号只在 H5 模板与 App 里做；DTO 里只有数字。
- `wall` 不分页（种类数受目录规模限制，首批 40 种 × 价位变化）。

### 拍板点（按建议实现，Completion Notes 复述）
