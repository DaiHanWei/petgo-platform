## Story

As a 用户,
I want 升级时看到庆祝页、老用户首次打开看到汇总弹窗、通知中心里有升级条目,
so that 我能感知到自己的成长。

## Acceptance Criteria

**AC1 — 数据层** `[L0]`
1. 在 Story 1.5 的 `GrowthRepository` 里加三个方法：`Future<GrowthPopups?> fetchPopups()`、`Future<void> ackCelebration(int toLevel)`、`Future<void> ackBackfill()`；路径加进 `core/network/api_paths.dart`（`growthPopups`、`growthPopupAck(String kind)`）。
2. 照 `features/ops/data/ops_popup_repository.dart` 的姿态：**失败即空、绝不抛**——超时 5s / 非 2xx / 解析失败一律当「没有弹窗」，ack 失败静默不重试，不出任何错误提示。
3. 模型放 `features/growth/domain/growth_popups.dart`：`GrowthPopups { GrowthCelebration? celebration; GrowthBackfill? backfill; }`、`GrowthCelebration { fromLevel, toLevel, tierUp, toTier, lifetimeTotal, unlockedBenefits (List<String>), frameAction (enum: auto / offerNewFrame / none，未知值按 none) }`、`GrowthBackfill { level, tier, activeDays, milestoneCount, milestoneExp, total }`。`fromJson` 对缺字段 / 类型不对的单项返回 null，不抛。段位代码与权益代码的解析**复用 Story 1.5 已有的枚举**，不另造。

**AC2 — 弹窗协调器 `GrowthPopupCoordinator`** `[L0]`（AD-11 · PRD「升级反馈」）
1. 新文件 `features/growth/presentation/growth_popup_coordinator.dart`，`Provider` 单例（写法照 `ops_popup_coordinator.dart:292-303`），依赖全部可注入（拉取、ack、当前登录态、根 context、是否前台、计时器）以便 L0 测试。
2. **拉取时机**（四个触发点，全部经同一个 `requestPull(GrowthPullReason reason)` 入口）：
   - `coldStart`：`AppShell` 首帧后 `attach`（照 `shared/widgets/app_shell.dart:71-78` 挂运营弹窗协调器的写法，紧挨着它），等 `StartupPopupLedger.instance.startupChainDone` 与登录态恢复（`authControllerProvider.notifier.ensureRestored()`，超时 5s）后、停在落地页（`/home` 或 `/profile`）时拉一次；
   - `resumed`：`app.dart:187` `didChangeAppLifecycleState` 的 `resumed` 分支里加一行调用（与 `unreadCountProvider` 刷新并列）；
   - `afterAction`：用户自己完成可能得 EXP 的动作成功后 **延迟 1.5s** 拉一次（入账是后端异步的）。实现为一个 Dio 拦截器 `features/growth/data/growth_action_interceptor.dart`，在 `core/network/dio_client.dart:50-74` 的拦截器链里加上：响应 2xx 且「方法 + 路径」命中以下之一即触发——`POST /content-posts`（发帖，`content_repository.dart:92`）、`POST /content-posts/{id}/comments` 与 `POST /comments/{id}/replies`（评论 / 回复，`detail_repository.dart:100 / :110`）、`POST /content-posts/{id}/like`（点赞，`like_repository.dart:34`；取消点赞的 `DELETE` 不触发）、`POST /places/{token}/checkins`（打卡，`place_repository.dart:148`）。路径用 `ApiPaths` 常量拼出的正则匹配，**不在各页面里分散加调用**。支付成功另在 6 个 `Analytics.capturePurchase(` 调用点之后各加一行 `growthPopupTrigger.afterAction()`（`shop_order_detail_page_v2.dart:833`、`unlock_method_sheet.dart:194`、`id_card_hd_flow.dart:137`、`keepsake_pay_flow.dart:89`、`vet_timed_pay_page.dart:118`；`recharge_page.dart:154` 是 PawCoin 充值、**不计成长值，不加**），以及同文件里纯 PawCoin 支付成功的分支（T0 逐个确认位置）；
   - `pushClicked`：点击 `GROWTH_LEVEL_UP` 系统推送（见 AC7.4）后。
   - ⚠️ 架构 AD-11 还列了「前台收到 `GROWTH_LEVEL_UP` 推送时拉取」：现状 App 只注册了 `onNotificationClicked`（`core/push/push_service.dart:176-179`），前台时 `doForeground()`（:297-298）离线推送不下发，没有前台收推送的入口；vendored 插件有 `addPushListener(onRecvPushMessage)`（`third_party/tencent_cloud_chat_push/lib/common/tim_push_listener.dart:16`）但从未接入、前台是否回调需真机验证。**本 story 不接这个触发点**，被动升级（如在 App 内收到礼物）在下一个触发点补弹（架构「已知限制」已接受「偶发未赶上时在下次触发点补弹」），Completion Notes 记为与架构的偏差。
3. **防抖与单飞**：1.5s 内多次 `afterAction` 只拉一次；拉取进行中再来的请求合并进当前这次；游客、兽医（`authState.isVet`）不拉。
4. **一次只弹一个**：同一次拉取结果里 `celebration` 与 `backfill` 都有时只弹 `celebration`，`backfill` 顺延到下一个触发点（下次回前台 / 下次冷启动 / 下次动作）——Epic AC「升级庆祝优先、汇总顺延」。
5. **何时不弹（不 ack、等下一个触发点）**：App 不在前台；当前在 `/splash`；根 Navigator 顶层是 `PopupRoute`（已有对话框 / 底抽屉 / 另一个庆祝在显示）；强制更新弹窗在显示（`appUpdateControllerProvider` 判定 forced）。普通页面（含 push 进来的详情页、发布成功后的页面）**照弹**——PRD「立即在当前页面上方弹出」。
6. **本进程去重**：弹过的 `(fromLevel, toLevel)` 与 backfill 记在内存，ack 失败时同一进程内不再弹第二次；下次冷启动若服务端仍有待弹，照常再弹（以服务端为准）。
7. **登记 `StartupPopupLedger`**：`core/startup/startup_popup_ledger.dart:6` 枚举**末尾**追加 `growthCelebration`、`growthBackfill`；在弹窗**真正出现之前**调 `StartupPopupLedger.instance.record(StartupPopupKind.growthCelebration)` / `(…growthBackfill)`（写法与 `milestone_celebration.dart:48` 相同，必须是这个字面量形式，`startup_popup_ledger_wiring_test.dart` 一类的源码扫描测试会按字面量找）。
8. **与运营开屏弹窗的先后（竞态必须处理）**：运营弹窗协调器只在 `ops_popup_coordinator.dart:187`（延迟 500ms 后）与 `:216`（图片预加载后）两处读 `_ledger.hasAny`，而 `/popups` 是异步拉取，可能晚于这两次检查返回 → 两个弹窗叠在一起。做法：`OpsPopupCoordinator` 构造器加一个可选注入 `Future<void> Function()? beforeLedgerCheck`（默认 null = 不等，**既有测试零改动**），在 `:187` 那一步之前 `await beforeLedgerCheck().timeout(3s)`（超时 / 异常都放行）；`opsPopupCoordinatorProvider`（:292-303）传入 `() => ref.read(growthPopupCoordinatorProvider).coldStartSettled`——`coldStartSettled` 在冷启动那次拉取「无弹窗」或「已登记 ledger 并弹出」后完成。结果：有升级庆祝或汇总时本次冷启动运营弹窗让路（PRD「升级庆祝优先，运营弹窗顺延到下一次冷启动」）。

### 关键设计说明

- **为什么用 Dio 拦截器触发「动作后拉取」**：发帖 / 评论 / 回复 / 点赞 / 打卡的调用点分散在 5 个仓储、十几个页面里，逐页加调用易漏且难测；拦截器一处挂上、按 `ApiPaths` 正则匹配，L0 可以直接对「方法 + 路径 + 状态码」做表驱动测试。支付成功没有统一的 HTTP 特征（QRIS 是轮询状态），所以在已有的统一成功点（`capturePurchase` 调用处）旁边显式调用。
- **为什么运营弹窗协调器要等成长弹窗**：`StartupPopupLedger` 的设计是「只登记、不排队」，它假设功能弹窗在运营弹窗判定之前就已出现；成长弹窗依赖一次网络请求，必须给运营弹窗一个「等成长弹窗冷启动拉取结束」的钩子，否则两窗叠加。钩子做成可选注入、默认不等，保证运营弹窗既有测试零改动。
- **为什么一次只弹一个**：PRD「每次冷启动最多一个」的精神；庆祝与汇总都是「重要但不紧急」，连弹两个会稀释第二个。
