## Story

As a 嫌推送太吵的用户,
I want 我的推送分类设置存在服务端、跟着账号走,
so that 换手机也不用重新设置。

## Acceptance Criteria

### 后端

**AC1 — 迁移 `V20261018_1800__create_user_push_mutes.sql`** `[L0]` `[L1]`（AD-2、PRD §3.1 影响面「只存关闭的分类」）
1. 建表（只存「关闭」的分类，无行 = 开启）：
   ```sql
   CREATE TABLE user_push_mutes (
       user_id     BIGINT       NOT NULL,
       category    VARCHAR(24)  NOT NULL,
       created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
       CONSTRAINT pk_user_push_mutes PRIMARY KEY (user_id, category),
       CONSTRAINT fk_user_push_mutes_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
       CONSTRAINT ck_user_push_mutes_category CHECK (category IN
           ('LIKE', 'COMMENT', 'MENTION', 'FOLLOWER', 'GIFT', 'PET_REMINDER', 'ACHIEVEMENT', 'PROMO'))
   );
   CREATE INDEX idx_user_push_mutes_category_user ON user_push_mutes (category, user_id);
   ```
   - CHECK **只列 8 个可关分类**，`ORDER_ACCOUNT` 被排除——库里不可能出现「订单与账号已关闭」。
   - `(category, user_id)` 索引供 Story 1.2 运营公告按批 `mutedAmong` 预取。
   - `ON DELETE CASCADE` 只是兜底（让测试库 `deleteAll` 不被阻断）：注销是就地匿名化、users 行不删，CASCADE 在注销路径上**永不触发**，必须走 AC7 显式删除。
2. 文件头注释写明：本表的 CHECK 是本线自有约束（不是地基两条共享约束之一）；以后新增可关分类 = 新起一条时间戳迁移 **DROP + ADD 重列全集**（CLAUDE.md 第 5 条「改 CHECK 约束必须重列全集」）。
3. 无实体类（`JdbcTemplate` 读写，见 AC3），因此与 `ddl-auto=validate` 无关；不建 JPA 实体。
4. 提交前本地自查 `bash scripts/ci/check-flyway-versions.sh origin/main`（云端跑不通可跳过，Completion Notes 记一句）。

**AC2 — 分类枚举与穷尽映射 `notify.preference.PushCategory`** `[L0]`（AD-1、PRD §3.1 分类对照表、PRD AC6）

**AC3 — `PushPreferenceService`** `[L0]` `[L1]`（AD-3）
1. 新建 `com.tailtopia.notify.preference.PushPreferenceService`（`@Service`），读写经同包 `UserPushMuteDao`（`@Repository`，`JdbcTemplate` + `NamedParameterJdbcTemplate`，先例 `notify/repository/NotificationAggregateDao.java`:17-28、`auth/service/OpsAudienceQuery.java`:35-37）。方法签名**固定**（Story 1.2 直接调用，PRD §6.4 对外接口）：
   - `boolean isEnabled(long userId, NotificationType type)`：`PushCategory.of(type)` 为 `ORDER_ACCOUNT`（`!lockable`）→ 直接 `true`、**不查库**；否则查 `SELECT EXISTS (SELECT 1 FROM user_push_mutes WHERE user_id = ? AND category = ?)`，有行 → `false`。**查询抛任何 `RuntimeException` → 返回 `true` 并 `log.warn`**（宁多勿漏，与去抖 Redis 异常同口径 `NotificationService.java`:271-281；日志只记分类与异常类名 `e.getClass().getSimpleName()`，不记 userId 以外的个人信息）。

   - `PushSettingsView get(long userId)`：一次查出该用户全部关闭行，按 `PushCategory.values()` 顺序组装 9 项 `(code, enabled, lockable)`。

**AC5 — `PATCH /api/v1/me/push-settings`** `[L0]` `[L1]`（AD-4、PRD AC3 / AC4、§3.1「切换即保存」）
1. 请求体 `UpdatePushSettingsRequest(@NotNull Map<PushCategory, Boolean> categories)`，例 `{ "categories": { "LIKE": false, "FOLLOWER": false } }`；**部分更新**（照 `PATCH /api/v1/me` 语义，`MeController.java`:45-49 + `UpdateMeRequest` 字段 null 即不动）：没出现的分类不动。响应 = 更新后的完整设置（同 AC4 结构）。
2. 校验（整单原子：任一条不过 → 整单拒绝、**一行都不写**）：
   - 未知 code（如 `"FOO"`、小写 `"like"`）→ **400**：map key 用 `PushCategory` 枚举，Jackson 反序列化失败 → `HttpMessageNotReadableException` → `GlobalExceptionHandler.handleBadRequest`（`GlobalExceptionHandler.java`:101-108，400 + ProblemDetail）。**不新增 400 工厂方法**（现有 `AppException.validation` 是 422）。
   - `"ORDER_ACCOUNT": false` → **422** `type = https://petgo/errors/push-category-locked`（新增 `ErrorTypes.PUSH_CATEGORY_LOCKED` + `AppException.pushCategoryLocked(String)`，照 `tailsonalityBadgeLocked` 写法 `AppException.java`:168-171 / `ErrorTypes.java`:62-63）。
   - `"ORDER_ACCOUNT": true` → 接受、无操作（本就恒开，见拍板点 ①）。
   - 某个值为 `null` → 422 `AppException.validation`；`categories` 缺失 → 422（Bean Validation，`GlobalExceptionHandler.java`:76-86）；`categories` 为空对象 `{}` → 不写库，返回当前设置。
3. Given 用户在手机 A `PATCH {LIKE:false, FOLLOWER:false}`，When 用同一账号的另一个 token（模拟手机 B）`GET`，Then `LIKE` / `FOLLOWER` 为关闭、其余 7 项开启（PRD AC4）；库里该用户**恰好两行**。再 `PATCH {LIKE:true}` → 只剩 `FOLLOWER` 一行；重复 `PATCH {FOLLOWER:false}` 幂等不报错、仍一行。
4. Given `PATCH {ORDER_ACCOUNT:false, LIKE:false}`，When 请求，Then 422 `push-category-locked`，`LIKE` **未被写入**（PRD AC3「订单与账号开关无法关闭」）。

### 拍板点（按建议实现，Completion Notes 复述）

- **① `ORDER_ACCOUNT: true` 接受为无操作**：AD-4 只规定 `false → 422`。传 `true` 与现状一致、不改变任何东西，报错反而让 App 必须特殊处理「全量回写」；故接受、不写库。
- **② 未知 code 走 Jackson 反序列化失败得 400**：不新增 `AppException` 的 400 工厂（全仓无先例、加了要改共享类）；`GlobalExceptionHandler` 已把 `HttpMessageNotReadableException` 映射为 400 ProblemDetail。代价是 detail 为通用「请求格式不正确」，不点名哪个 code——App 只会发 9 个已知 code，可接受。
- **③ 值为 null / 缺 `categories` 是 422 而非 400**：与全仓 Bean Validation 口径（:76-86 → 422）一致；AD-4 只对「未知 code」规定了 400。
- **④ 注销调用位置**：放 `opsPopupImpressionDeletion`（:199）之后、`tailsonalityDeletion`（:202）之前——同类「账号级纯个人数据物理删」聚在一起，且避开 ① 等级线（其 1-2 story 插在 :202 与 :205 之间），减少合并时同一位置的冲突。
- **⑤ `isEnabled` 的 warn 日志**：只记分类名与异常类名（`userId` 可记，与 `NotificationService` 现有日志口径一致），不记通知标题 / 正文。

### 实现提示

- `PushCategory.of` 写法示意（不写 `default`；地基 5 值也要显式列出）：
  ```java
  return switch (type) {
      case CONTENT_LIKED -> LIKE;
      case CONTENT_COMMENTED, PLACE_COMMENTED -> COMMENT;
      // …
      case SHOP_ORDER_SHIPPED, SHOP_ORDER_EXCEPTION, /* … */ IDENTITY_REQUIRE_MODIFY -> ORDER_ACCOUNT;
  };
  ```
- `update` 先**完整校验**（遍历 map：null 值 → 422、`ORDER_ACCOUNT=false` → 422），全部通过后再逐条写；校验与写在同一 `@Transactional` 方法内。
- 关 = `INSERT … ON CONFLICT DO NOTHING`（主键冲突幂等，不用「先查后插」，并发下不会撞唯一键中止事务）；开 = `DELETE`（0 行也不报错）。
- `get` 一次 `SELECT category FROM user_push_mutes WHERE user_id = ?`，库里出现不认识的字符串（理论上 CHECK 已挡）→ 忽略该行并 warn，不 500。
- 请求 DTO：`record UpdatePushSettingsRequest(@NotNull Map<PushCategory, Boolean> categories)`；Controller 参数 `@Valid @RequestBody`。
- Controller 不做业务判断，全部校验在 service（便于 1.3 以外的调用方复用、L0 好测）。
- 不在本 story 写任何调用 `isEnabled` / `mutedAmong` 的生产代码（1.2）；这两个方法本 story 只有单测与 L1 覆盖。

### 架构约束

- AD-1：映射只在 `PushCategory.of`；穷尽 switch + 单测双保险。
- AD-2：只存关闭项；CHECK 排除 `ORDER_ACCOUNT`；新增可关分类 = 重建 CHECK 全集。
- AD-3：`isEnabled` 异常返回 `true`（宁多勿漏）；签名固定，供 1.2 / 3.1 调用。
- AD-4：GET / PATCH 结构、422 `push-category-locked`、400 未知 code、显式 `hasRole("USER")`、30 次 / 分钟 / 人；分组与文案归 App。
- AD-6：注销显式删除、在 `authDeletion` 之前。
- 护栏：不引 MQ / 缓存 / 新依赖；不建 JPA 实体（无 `ddl-auto` 影响）；日志不记 PII / 令牌。
- 地基契约：`NotificationType`、`ck_notifications_type` 只引用不改。
