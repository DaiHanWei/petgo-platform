## Story

As a **后端系统**,
I want **具备库存的持久化模型、可售库存计算口径与原子变更原语**,
so that **售罄判定有唯一权威来源，且后续下单锁定不会超卖（FR-95）**。

### AC1 — `sku_inventory` 表 + 可售库存不落库

**Given** 迁移 **`V102__init_sku_inventory.sql`**（独占号段内；🔴 **号必须 > V101**，Flyway `outOfOrder=false`）
**When** 上下文启动
**Then** `ddl-auto=validate` 与实体一致
**And** 含 `sku_id`（**FK → `shop_skus(id)`，`ON DELETE CASCADE`；UNIQUE，一 SKU 一行**）· `actual` · `locked`，两个数量列均 `BIGINT NOT NULL DEFAULT 0`
**And** 🔴 CHECK 保证 **`actual >= 0 AND locked >= 0 AND locked <= actual`**
**And** 🔴 **可售库存 = `actual − locked` 为查询期计算，绝不落第三列** —— 三列并存必然出现三值不一致，而库存不一致等于钱不一致
`[L0]` `mvn -B package` + 实体编译 · `[L1]` 启动 validate 过；直接 `UPDATE` 造出 `locked > actual` 被 DB 拒绝

### AC2 — 🔒 锁定原语：单条 DB 条件原子写（安全攸关）

**Given** 并发请求同时对同一 SKU 扣减
**When** 调用 `InventoryService.lock(skuId, qty)`
**Then** 🔴 实现为**单条 SQL 条件原子写**，依**影响行数**判定成败：
```sql
UPDATE sku_inventory SET locked = locked + :qty, updated_at = now()
 WHERE sku_id = :skuId AND (actual - locked) >= :qty
```
**And** 🔴 **禁止「先 SELECT 查可售、再 UPDATE」** —— 两步之间的窗口就是超卖发生的地方
**And** 影响 0 行 → 抛明确的「已售罄」领域错误（`AppException`），🔴 **不静默失败、不重试、不排队**（FR-95）
**And** 🔴 **禁引入分布式锁、禁用 Redis 扣减、禁任何新中间件**（NFR-1 / AD-6）—— 范式照 V1.0 决策 **F11**（兽医抢单：`UPDATE ... WHERE status='WAITING'` 判影响行数）
**And** 不变式「**可售库存不得为负，超卖目标为 0**」有对应断言（NFR-8）
`[L0]` 单测：影响行数 1 → 成功；影响行数 0 → 抛「已售罄」；且断言**实现中不存在预查询**
`[L1]` **并发集成测试：N=50 线程抢 M=10 件，成功数恰为 10，`locked` 恰为 10，无负库存**

### AC3 — 其余三条流转原语

**Given** FR-95 定义了库存四段流转
**When** 实现其余三条
**Then** 提供并各自为**单条条件原子写**：
| 原语 | SQL 条件 | 调用方（本 Story 不实现调用） |
|---|---|---|
| `release(skuId, qty)` 锁定 → 可售 | `WHERE sku_id=? AND locked >= ?` | 3.4 支付超时/取消 |
| `commit(skuId, qty)` 锁定 → 扣减出库 | `WHERE sku_id=? AND locked >= ? AND actual >= ?`（同时减 `actual` 与 `locked`） | 3.8 支付成功 |
| `restock(skuId, qty)` 增加可售 | `WHERE sku_id=?`（只增 `actual`） | 1.4 采购入库 / 5.4 退货质检通过 |
**And** 每条影响 0 行时均抛明确领域错误，**不静默**
`[L0]` 单测四条原语的成功/失败分支

### AC4 — 三态下发 + 售罄不下架

**Given** 商品查询接口返回 SKU（1.1 已建 `ShopSkuView`）
**When** 计算展示状态
**Then** 按可售库存下发三态：`OUT_OF_STOCK`（=0）/ `LOW_STOCK`（≤ 运营阈值，**含剩余数**）/ `IN_STOCK`
**And** 🔴 **`LOW_STOCK` 的剩余数取真实值，不虚构数字**（FR-95：制造合理紧迫感但不造假）
**And** 🔴 **售罄商品不自动下架**，仍出现在列表与详情中（保留复购提醒与外部落点）
**And** 低库存阈值从**配置**读取（`petgo.shop.low-stock-threshold`，默认 5），**不硬编码在业务代码里**
**And** ⚠️ **扩展 1.1 的 `ShopSkuView` 增加库存字段** —— 这是本 Story 唯一需要改既有代码的地方，且是**纯追加字段**，不改既有字段
`[L0]` 单测三态边界（0 / 1 / 阈值 / 阈值+1）· `[L1]` 详情接口返回三态正确

#### 🔴 但绿灯当时并不成立 —— 变异验证发现该测试原本没有判别力

**做法：** 把 `SkuInventoryRepository.lock` 的 `and i.actual - i.locked >= :qty` **整条删除**后重跑。
**结果：4 个用例照样全绿。**

**根因：** `sku_inventory` 上有 `ck_sku_inventory_locked_le_actual`。应用层原子条件被删后，超卖请求落到 **DB CHECK** 上被拒；而测试写的是 `catch (Exception e) { soldOut++ }`，把「干净的售罄 `AppException` → 409」与「DB CHECK 拒绝 `DataIntegrityViolationException` → 500」**记成了同一件事**。

即：它证明的是「**系统**不超卖」（纵深防御整体成立），**不是**本 Story 顶部声称的「应用层原子条件成立」。用户侧的可观测差异（409 vs 500）也被吞掉了。

**已修：** 分别 catch `AppException` 与其他异常，新增判别性断言 `dbRejected == 0`（不得有请求越过应用层条件、靠 DB CHECK 兜底），两个并发用例都加。

**修后复验：** 同样删掉守卫再跑 → **红了**，`soldOut expected 40 but was 0`、`dbRejected expected 0 but was 31`。守卫已还原。

> ✅ 至此本 Story 顶部「未跑 L1 前不得认为防超卖已验证」的前置条件**已解除**：50 线程真实并发、真 PostgreSQL、且测试确有判别力。

## Dev Notes

### 🔒 本 Story 最容易写错的一处

**「先查可售、再扣减」是超卖的唯一成因。** 它在单线程测试里 100% 正确，在并发下静默失败：

```java
// ❌ 绝对不要这样写 —— 两步之间就是超卖窗口
long available = repo.findAvailable(skuId);
if (available >= qty) { repo.addLocked(skuId, qty); }

// ✅ 单条 SQL，条件与写入原子，靠影响行数判定
int affected = repo.lock(skuId, qty);   // UPDATE ... WHERE (actual - locked) >= :qty
if (affected == 0) { throw AppException.conflict("已售罄"); }
```

**范式照 V1.0 决策 F11**（兽医抢单）：`UPDATE consult_sessions SET vet_id=?, status='IN_PROGRESS' WHERE id=? AND status='WAITING'`，影响 0 行 = 已被抢。同一套思路。

🔴 **禁止的替代方案**：`SELECT ... FOR UPDATE`（行锁会在高并发下排队，且本仓无此先例）· Redis 扣减（NFR-1 禁缓存层）· `synchronized`/`ReentrantLock`（单机有效、多实例无效，且德国单机现状不是可依赖的前提）· 任何分布式锁中间件。

### 复用而非重造

| 要做的事 | 照抄谁 |
|---|---|
| 条件原子写 + 判影响行数 | V1.0 决策 **F11** 兽医抢单（`consult` 模块） |
| `@Modifying @Query` 原生 SQL 返回影响行数 | 仓库既有 repository 中的 `applyDelta` 类方法（如 `PawCoinWalletRepository`） |
| 领域异常 | `AppException.conflict(...)`（已售罄属状态冲突，非校验失败） |
| 配置项读取 | 既有 `petgo.*` 前缀配置范式（如 `petgo.id-hd.download-price`） |
| 模块与分层 | Story 1.1 已建的 `com.tailtopia.shop.{domain,dto,repository,service,web}` |

### Completion Notes List

**L0 全绿：31 个单测**（1.1 的 18 个 + 本 Story 新增 13 个）

`InventoryServiceTest` 的重点不是「数字算对了」，而是**防超卖的实现方式没被写坏**：
- 🔒 `lockNeverPreReads` —— 用 Mockito 断言 `lock()` 全程**不调用任何查询方法**。「先查可售、再扣减」在单线程下 100% 正确、在并发下静默超卖，这条测试是唯一能在 L0 层拦住它的手段
- 🔒 两条**源码级护栏**：扫 `InventoryService` 不得出现 `synchronized`/`RedisTemplate`/`Redisson`/`ReentrantLock`/`FOR UPDATE`；扫 `SkuInventoryRepository` 必须包含 `i.actual - i.locked >= :qty`（lock 的可售条件）与 `i.locked >= :qty`（release/commit 的锁定条件）—— **条件一旦被删掉就是无条件加锁量 = 超卖**，而这种改动不会引起任何编译或行为报错
- 四条原语均拒绝非正数量，且拒绝时 `verifyNoInteractions(repo)`

**⏳ L1 待本地验收（关键）：** 🔒 **`InventoryConcurrencyIntegrationTest` 的「50 线程抢 10 件」是本 Story 唯一能真正证明防超卖成立的测试**，本次未执行。L0 证明不了并发正确性。另含「并发按不同数量抢，总锁定量不超实际库存」「四原语完整流转」「DB CHECK 兜底：绕过应用层也造不出 locked > actual 或负库存」三条。

**架构落实：**
- 可售库存 = `actual - locked` **查询期计算，未落第三列** —— 三列并存必然三值不一致，而库存不一致等于钱不一致
- 四条原语全部是**单条条件原子 UPDATE + 判影响行数**，范式照 `PawCoinWalletRepository.applyDelta` 与 V1.0 决策 F11（兽医抢单）
- DB CHECK 作最后兜底：`actual >= 0` · `locked >= 0` · **`locked <= actual`** —— 即便应用层写错，DB 也不允许超卖落库
- 低库存阈值走配置 `petgo.shop.low-stock-threshold`（默认 5），**未硬编码**
- `LOW_STOCK` 才给 `remaining` 真实剩余数；售罄与充足均为 `null` —— 售罄不必给数字，充足时给数字会泄露经营数据
