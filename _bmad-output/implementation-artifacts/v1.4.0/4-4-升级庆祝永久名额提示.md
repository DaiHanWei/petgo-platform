## Story

As a 有月租名额的用户,
I want 升级获得永久名额时看到正向提示,
so that 我知道以后可以少租一个名额。

## Acceptance Criteria

**AC1 — `/popups` 的 `celebration` 增加 `petSlotHint`** `[L0]` `[L1]`（AD-16 · FR-146.6 · AC13a）
1. `GrowthPopupsResponse.CelebrationView` **末尾追加** `boolean petSlotHint`（JSON `petSlotHint`；其他字段名、顺序、取值一律不变）。
2. 判定（读时计算，**不落库**）：`petSlotHint = levelSlots(effectiveTo) > levelSlots(fromLevel) && 当前生效中月租数 > 0`。
   - `fromLevel` / `effectiveTo` 用 `GrowthPopupService` **读时校正之后**的值（与 `celebration` 里返回的 `fromLevel` / `toLevel` 同一对数）；校正后无待弹（`celebration = null`）则不计算。
   - `levelSlots(level)` = 等级带来的名额数（AD-5 的 `[Lv≥5] + [Lv≥10]`），**只经 ② 的 `PetSlotService` 提供**（新增或复用其公开方法，如 `levelSlotsOf(int level)`），① 不自写 5 / 10 门槛。
   - 「有生效中月租」取 `PetSlotService.quotaOf(userId).hasActiveRental`（2.2 计划专为本 story 预留的字段；含运营补发名额，二者同表同状态）；拉取那一刻已过期的不算。
   - 虚拟号 / 官方号：① 本就返回 `celebration = null`（① 2.1 AC3.4），不涉及。
3. 模块方向：`growth` 不直接依赖 `profile.slot`。在 `growth` 侧定义一个小接口（建议 `growth.service.CelebrationPetSlotHint`，单方法 `boolean petSlotHint(long userId, int fromLevel, int toLevel)`），由 ② 在 `profile.slot` 里实现（建议 `PetSlotCelebrationHint`，`@Component`）；`GrowthPopupService` 以 `ObjectProvider` / 可选注入使用，**缺实现时恒 false**（① 的既有单测不需要造 ② 的 bean）。
4. 例（AC13a / Epic AC）：Lv4 默认 1 + 月租 1，升到 Lv5 → `petSlotHint = true`；没有生效月租的用户升到 Lv5 → false；Lv5 → Lv7（不跨门槛）有月租 → false；Lv9 → Lv10 有月租 → true；Lv4 → Lv11（跨两道门槛）有月租 → true。

**AC2 — App：升级庆祝页「+1 slot hewan」行内说明（K2 / K3）** `[L0]` `[L2]`（decision-log 2026-10-14 · UI 稿 K2 / K3）
1. `GrowthCelebration`（`growth_popups.dart`）加 `final bool petSlotHint`；`fromJson` 缺字段 / 类型不对 → `false`（旧后端兼容），不抛。
2. `level_up_celebration.dart` 跨段位全屏页（D2–D4）的「Terbuka di {段位}」权益白卡里，`PET_SLOT_PLUS_ONE` 那一行（「+1 slot hewan」）下方，当 `petSlotHint == true` 时多一行 12 号灰字说明（K-5）：「Slot ini permanen. Mulai perpanjangan berikutnya, kamu bisa sewa 1 slot lebih sedikit.」——**放在该权益行下面、不另起一张卡**（UI 稿 K2 批注：避免被吸底按钮挡住）。
3. `petSlotHint == false` → 页面与 ① 定稿 D2 / D3 **完全一致**（K3）。
4. 权益列表里没有 `PET_SLOT_PLUS_ONE` 行（如连跳到 STAR，① 只给最终段位权益）或走段位内卡片形态（无权益列表）→ **不显示**说明（无处挂靠），不另加块。
5. 文案方向：只说正向（永久、可少租），**不出现**「闲置 / 浪费 / 不退款」（AC13a）；不渲染后端显示串（`petSlotHint` 只是布尔）。

**AC3 — App：名额管理页「下次续租默认少勾一个」** `[L0]` `[L2]`（Epic 4.4 范围）
1. 2.4 的续租抽屉（D11）默认勾选规则改为：默认勾选数 = `min(生效中月租数, renewableMax, max(0, 正常宠物数 − (defaultSlots + levelSlots)))`（`renewableMax` / `defaultSlots` / `levelSlots` 取 2.2 的 `GET /pet-slots/me` 下发值），从**最早到期**的月租名额开始勾；其余不勾（用户可手动再勾）。效果：升级拿到永久名额后，下次续租默认少勾一个；没升级时与 2.4 现行默认一致（T0 核对 2.4 的现行默认规则，若 2.4 已是同一规则则本条只补测试）。
2. 默认勾选数为 0 时，抽屉主按钮按 2.4 现有「未勾选」态处理（禁用），不自动关闭抽屉。
3. 页面不新增文案（对照表无此条，见「需拍板」）。

**AC4 — ① 成长值流水的关联宠物改取多宠** `[L0]` `[L1]`（AD-16 · CROSS-STORY-DECISIONS「② 合并后改为写入全部关联宠物」· Epic AC3）

4. 已写入的历史流水不回填（append-only，AD-2 of ①）。
5. 例：发布关联 A、B 的 Diary → ① 入账 `POST_PUBLISHED` 流水 `pet_ids = {A, B}`；他人点赞这条 → `LIKE_RECEIVED` 流水 `pet_ids = {A, B}`。

### 为什么 `petSlotHint` 由后端算

- 「本次升级是否跨过 Lv5 / Lv10」需要 `fromLevel` / `toLevel`（只有 `/popups` 有），「是否有生效月租」需要名额数据（只有 ② 有）；App 两头都拿得到，但名额门槛是后端口径（AD-5），放 App 会多一份 5 / 10 的硬编码。AD-16 也明确「由本线填充」。
- 读时计算而非升级时落库：升级到弹出可能隔很久（离线 / 后台），期间月租可能到期，读时算更贴近「此刻有生效中月租」。

- **AD-5 / §5**：名额（含等级名额）只经 `PetSlotService`；① 不自写门槛。
- CROSS-STORY-DECISIONS：不反向合并 dev 进功能分支；对齐在从 dev 切的分支上做；不改两条共享 CHECK、不改地基事件字段；`GrowthQueryService` 签名不动。
- 无迁移；不引 MQ / 缓存；App 不渲染后端显示串。
