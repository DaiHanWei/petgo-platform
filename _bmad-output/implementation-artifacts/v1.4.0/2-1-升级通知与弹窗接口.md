## Story

As a 用户,
I want 升级时收到一条通知和推送，并且不论在不在 App 里都能看到一次升级庆祝,
so that 升级这件事被郑重地告诉我。

## Acceptance Criteria

**AC1 — 升级时写入待弹庆祝（改 Story 1.2 的 `GrowthLevelChangeHandler`）** `[L0]`（AD-10 · FR-143.6 · PRD AC8）
1. 只在 **`newLevel > oldLevel` 且本次入账的规则代码 ≠ `LAUNCH_BACKFILL`** 时写待弹；写法：`celebrate_from_level = COALESCE(celebrate_from_level, oldLevel)`（已有待弹就保留原 from）、`celebrate_to_level = newLevel`。与等级更新在**同一事务**（账户行已被 `accrue` 的 `SELECT … FOR UPDATE` 锁住）。
2. 例：Lv4 → Lv5 后未确认、又升到 Lv7 → 待弹为 from 4 → to 7（只弹一次、显示最终等级）。
3. 降级（`newLevel < oldLevel`）**不写、不清**待弹；等级不变不动。
4. 虚拟号 / 注销 / 停用用户不会走到这里（Story 1.1 参与判定已挡住），本 story 不另加判断，但单测要覆盖「handler 不因此抛错」。
5. 运营调整（Story 4.2 的 `adjust`）与等级表重算（Story 4.1）只要经过本 handler，就自动获得同样行为——本 story 不改它们。

**AC2 — `GROWTH_LEVEL_UP` 通知 + 推送** `[L0]` `[L1]`（AD-10 · UI 稿 F1 / F2）
1. 新监听器 `com.tailtopia.growth.listener.GrowthNotifyListener`：`@Async` + `@TransactionalEventListener`（默认 `AFTER_COMMIT`），消费 `GrowthLevelChangedEvent`，写法照 `notify/service/MilestoneNotifyListener`。入账事务回滚则不发。
2. 只在 `newLevel > oldLevel` 时发；降级、相等直接 return。存量补算迁移不发事件（Story 2.2），因此天然不发通知。
3. 发送调用（参数逐字照此）：
   ```java
   notificationService.sendWithCopy(userId, NotificationType.GROWTH_LEVEL_UP,
           "GROWTH_LEVEL_UP." + tier.name(),          // copyKey，完整键 notify.GROWTH_LEVEL_UP.<TIER>.title/body
           new Object[] {String.valueOf(newLevel)},    // 传字符串：避免 MessageFormat 把 1000 渲染成「1,000」
           "Naik ke Lv" + newLevel + "!",              // fallbackTitle（只落库留痕，App 不读）
           "Kamu sekarang " + tierNameId + ". Lihat keuntungan barumu.", // fallbackBody
           newLevel + ":" + tier.name());              // targetRef，见 AC2.4
   ```
   - `tier` = `growth_levels` 中 `newLevel` 那一行的段位（读 Story 1.1 的等级表仓储，**不要**按 5 / 10 / 15 写死）。
   - `sendWithCopy` 的 `deepLinkType` 固定为 `type.name()` = `"GROWTH_LEVEL_UP"`（`NotificationService.java:385`），App 据此路由到等级页（Story 2.3）。
   - 推送前跳过虚拟号是 `sendWithCopy` 既有行为（`:387`），本 story 不重复判断。
4. **`targetRef` 格式 = `{toLevel}:{TIER}`**（如 `7:BUDDY`）：App 通知中心标题「Naik ke Lv{n}!」与正文「Kamu sekarang {段位}…」要按代码本地化（App 不渲染后端显示串），只能从 `targetRef` 取等级与段位。用发通知那一刻的段位（之后改等级表不回改历史通知）。这是 AD-10 未写明的契约，写进类 Javadoc，并在 Completion Notes 记为对架构的补充。
5. 一次入账跨多级只发**一条**（`GrowthLevelChangedEvent` 本就每次变化只发一个，Story 1.2 AC）；两次独立升级（4→5、5→7）各发一条——与 Epic AC「通知只新增一条」一致。
6. 推送文案新增 i18n 键（**四个文件都加**：`i18n/messages.properties`、`messages_en.properties`、`messages_id.properties`、`messages_zh_CN.properties`；`bash scripts/ci/check-i18n-keys.sh` 必须过），共 8 个键：
   | 键 | id | en | zh_CN |
   |---|---|---|---|
   | `notify.GROWTH_LEVEL_UP.NEWBIE.title` / `BUDDY` / `GUARDIAN` / `STAR`（4 个） | `Naik ke Lv{0}!` | `Reached Lv{0}!` | `升到 Lv{0}！` |
   | `notify.GROWTH_LEVEL_UP.NEWBIE.body` | `Kamu sekarang Pemula. Lihat keuntungan barumu.` | `You''re now a Newbie. See your new perks.` | `你现在是 Pemula 段位，看看新权益。` |
   | `notify.GROWTH_LEVEL_UP.BUDDY.body` | `Kamu sekarang Sahabat. Lihat keuntungan barumu.` | `You''re now a Buddy. See your new perks.` | `你现在是 Sahabat 段位，看看新权益。` |
   | `notify.GROWTH_LEVEL_UP.GUARDIAN.body` | `Kamu sekarang Penjaga. Lihat keuntungan barumu.` | `You''re now a Guardian. See your new perks.` | `你现在是 Penjaga 段位，看看新权益。` |
   | `notify.GROWTH_LEVEL_UP.STAR.body` | `Kamu sekarang Bintang. Lihat keuntungan barumu.` | `You''re now a Star. See your new perks.` | `你现在是 Bintang 段位，看看新权益。` |
   - 文案来源：UI 稿顶部文案表「通知」行 + F1 / F2。`messages.properties`（默认包）与 en 同值（照 `notify.CONTENT_MENTIONED.*` 的现状，`messages.properties:3483`）。
   - ⚠️ `args != null` 时 Spring 走 `MessageFormat`，**单引号必须写成 `''`**（`NotificationService.java:373` 的告诫），所以 en 写 `You''re`；id / zh 无单引号。
   - 推送分类「成就与等级」由 ④ 映射，本 story **不碰**任何推送偏好 / 分类代码。
7. 不发的情况（任一命中 return，不写行不推送）：`newLevel <= oldLevel`；`accountQuery.isActive(userId) == false`（注销 / 停用，双保险）；`accountQuery.isVirtual(userId)`（双保险）。
8. 日志只记 userId 与等级、异常类名，不记昵称等 PII。

**AC3 — `GET /api/v1/me/growth/popups`** `[L0]` `[L1]`（AD-11）
1. 加在 Story 1.4 的 `MeGrowthController` 里（需登录 USER，游客 401，错误走 RFC 9457）。聚合逻辑放新服务 `com.tailtopia.growth.service.GrowthPopupService`，controller 只转发。
2. 响应（JSON camelCase）：
   ```json
   {
     "celebration": {
       "fromLevel": 4, "toLevel": 5,
       "tierUp": true,
       "toTier": "BUDDY",
       "lifetimeTotal": 512,
       "unlockedBenefits": ["PET_SLOT_PLUS_1", "FRAME_BASIC", "EXCLUSIVE_GIFTS_1"],
       "frameAction": "AUTO"
     },
     "backfill": null
   }
   ```
   - `celebration`：无待弹 → `null`。
   - `tierUp` = `fromLevel` 与 `toLevel` 的段位不同（都读 `growth_levels`）。
   - `toTier`：`toLevel` 的段位代码。`lifetimeTotal`：当前累计 EXP（UI 稿 D1 / D7 卡片的「1.250 EXP」胶囊要用）。**这两个字段 AD-11 未列，属于本 story 新增**（只加不改，App 按代码本地化段位名），Completion Notes 记为对架构的补充。
   - `unlockedBenefits`：`tierUp = false` → 空数组；`tierUp = true` → **最终段位**（`toTier`）的权益代码，顺序与等级页一致，不含优惠券（AC20）。权益代码**复用 Story 1.4 已定义的那套**（上面示例里的代码名只是示意，以 1.4 实际为准，不另造一套）。连跳跨两个段位（如 Lv4 → Lv11）也只给最终段位的权益，与 UI 稿「Terbuka di {段位}」只写一个段位名一致。
   - `frameAction`（读时计算，用当前 `frame_choice`）：`tierUp = false` → `NONE`；`tierUp = true` 且 `frame_choice IS NULL` → `AUTO`（已自动戴上，UI 稿 D2 / D4）；`tierUp = true` 且 `frame_choice IS NOT NULL`（含用户主动选的 `NONE`）且新段位有框（`toTier ≠ NEWBIE`）→ `OFFER_NEW_FRAME`（UI 稿 D3）；其余 → `NONE`。
   - `backfill`：本 story 恒返回 `null`，字段先占位（Story 2.2 填充）；DTO 用可空 record 字段，Jackson 输出 `null`。
3. **读时校正**（降级后才拉到的情况）：`effectiveTo = min(celebrate_to_level, 当前 level)`；若 `effectiveTo <= celebrate_from_level` → 视为无待弹，返回 `celebration = null` **并顺手清掉两列**（同一 `@Transactional` 写）；否则按 `effectiveTo` 计算上述字段。PRD「降级不弹窗」。
4. 虚拟号（无等级页与庆祝）→ 两个字段都 `null`。无账户行 → 两个字段都 `null`。

**AC4 — `POST /api/v1/me/growth/popups/{kind}/ack`** `[L0]` `[L1]`（AD-11）
1. `kind ∈ {celebration, backfill}`（小写），其它值 → 400 ProblemDetail（`type` 用项目既有校验错误类型）。
2. `celebration`：可选查询参数 `toLevel`（App 传本次弹出时看到的 `toLevel`）：
   - 带 `toLevel` 且 `celebrate_to_level > toLevel`（弹出期间又升了级）→ 只把 `celebrate_from_level` 改为 `toLevel`、保留 `celebrate_to_level`（下次拉取弹「toLevel → 新等级」，不吞掉新的升级）；
   - 其余（含不带参数）→ 两列置 `NULL`。
   - 这个参数是 AD-11 之外的补充（解决「看着 4→5 的弹窗时又升到 7，ack 把 7 也清掉」的竞态），Completion Notes 记一句。
3. `backfill`：本 story 先实现为「把 `backfill_popup_pending` 置 false」（Story 2.2 的迁移才会让它为 true）；无账户行时空操作。
4. 两种 ack **重复调用幂等**：无待弹时返回 204、不报错；响应体为空，状态码 **204**。

### 为什么通知走监听器而不是写在 handler 里

- handler 在入账事务内；通知要等事务提交（`AFTER_COMMIT`），否则入账回滚了通知照发。监听 `GrowthLevelChangedEvent` 正好拿到「已提交的等级变化」。
- 5.4「连锁只在 handler 一处」仍成立：事件只由 handler 发布，监听器只是事件的一个订阅方（② 是另一个）。
- 4.1 等级表重算、4.2 运营调整只要经过 handler 发事件，升级通知自动生效，不用各写一遍。

### 架构约束

- AD-10：只有升级且非 `LAUNCH_BACKFILL` 写待弹 + 发通知；降级不通知不弹窗；连跳只弹一次、显示最终等级。
- AD-11：两个接口路径与 `kind` 取值照抄；`backfill` 字段 Story 2.2 填。
- AD-16：规则名 / 段位名 / 权益只下发代码；本 story 新增的 `toTier`、`targetRef` 也只放代码。
- 5.4 写入纪律：除 handler 与 `GrowthPopupService.ack*`（清待弹两列 / 清 `backfill_popup_pending`）外，不在别处写 `growth_accounts`；ack 只动这三列，**不碰** `lifetime_total` / `level`。
- 护栏：只用 `@Async` + 事件，不引 MQ / 缓存；`ddl-auto=validate`；本 story 不加迁移。
- 已知取舍（Completion Notes 如实记）：降级后再升回同一级会再发一条通知（不为此加「最高已通知等级」列，代价与收益不对等）；`@Async` 监听失败只记 ERROR、不重试（AD-5 V1 姿态）。

### 本 story 不做

- App 的庆祝页、存量弹窗、通知中心条目、深链（Story 2.3）。
- 存量补算、`backfill` 字段取值、虚拟号展示等级（Story 2.2）。
- 「戴上新框」切框接口 `PUT /api/v1/me/growth/frame`（Story 3.3）；本 story 只算 `frameAction`。
- `GROWTH_LEVEL_UP` 推送分类映射（④）；等级表重算任务（Story 4.1）；运营调整（Story 4.2）。
