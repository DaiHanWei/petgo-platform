# Story 2.3: 名额到期扫描与通知

Status: ready-for-dev

> 版本 v1.4.0 · 主题 multi-pet · 分支 `feat/1.4.0-multi-pet`
> 口径优先级：`decision-log.md` ② 节 > `多宠物/1-4-0多宠物prd.md` > `architecture-v1.4.0-multi-pet-delta.md` > UI 稿（均在 `_bmad-output/planning-artifacts/v1.4.0/`）；跨分支契约以 `CROSS-STORY-DECISIONS.md`「2026-10-18 V1.4.0 四条线共用地基」节为准。
> 前置：**Story 2.1**（`PetSlotStateService.reconcile(RENTAL_EXPIRED)` 返回被转只读的宠物、`PetSlotLock`）、**Story 2.2**（`pet_slot_rentals` 表、`(status, expires_at)` 索引、续租清空 `reminded_at`）、地基 0.1（`NotificationType.PET_SLOT_EXPIRING` / `PET_SLOT_EXPIRED` 与 `ck_notifications_type` 39 值——**本 story 不改该约束与枚举**）。
> 范围层：**只后端**。**无迁移**（状态列 `reminded_at` / `status` / `expired_at` 已在 2.2 的 1601 里）。
> 🔴 K1 拍板（decision-log ② 第一轮）：两类到期通知**照 `OPS_ANNOUNCEMENT` 读后端 title / body**——后端按收件人账号语言生成，可带到期日、宠物名；推送与通知中心同一句；用户之后切换 App 语言旧通知不变。推送分类「订单与账号」由 ④ 映射，本线不处理。

## Story

As a 月租用户,
I want 名额到期前收到提醒、到期时知道哪只宠物进入只读,
so that 我能及时续租不丢记录。

## Acceptance Criteria

**AC1 — `PetSlotExpiryScanner`（每小时）** `[L0]` `[L1]`（AD-7，照 `SipdhExpiryScanner`）
1. 包 `com.tailtopia.profile.slot`。`@Scheduled(cron = "${petgo.pet-slot.expiry-scan-cron:0 5 * * * *}", zone = "UTC")`（每小时第 5 分，避开整点其它任务）；方法体 `try { … } catch (RuntimeException e) { log.warn("宠物名额到期扫描失败 cause={}", e.getClass().getSimpleName()); }`，单次失败不 crash 调度；有处理量时 `log.info` 汇总计数（不记宠物名 / 用户名）。
2. 扫描器只做调度，业务在 `PetSlotExpiryService.scan(Instant now)`（便于测试注入时间）；`application.yml` 加配置项默认值，测试 profile 可关（照现有 `petgo.*` 扫描器写法，确认测试环境是否统一关调度，照做）。
3. 先跑「到期」再跑「提醒」：同一次扫描里已到期的名额不再收到「即将到期」。

**AC2 — 到期处理** `[L0]` `[L1]`（AD-7、FR-146.4）
1. 取 `status = 'ACTIVE' AND expires_at <= now` 的名额（按 `user_id` 分组，单批上限如 500 个用户，剩余下一轮）。
2. **逐用户独立事务**（`PetSlotExpiryService.expireForUser(userId, now)`，`@Transactional(propagation = REQUIRES_NEW)` 或经代理的独立 bean 调用，确保一个用户失败不回滚他人）：
   - `PetSlotLock.lockUser(userId)`（与 2.1 / 2.2 同一把锁，避免与续租到账并发时把刚续上的名额误判过期）；
   - 加锁后**重读**该用户 `ACTIVE AND expires_at <= now` 的名额（续租可能已把 `expires_at` 推后）→ 置 `EXPIRED`、`expired_at = now`；
   - `reconcile(userId, RENTAL_EXPIRED)` → 得到 `demoted`（被转只读的宠物）。
3. 单个用户处理抛异常 → 记 WARN（只记 `userId` 与异常类名）、继续下一个用户；该用户的名额仍是 `ACTIVE`，下一轮自动重试。
4. 用户无宠物 / 宠物数 ≤ 新名额 → `demoted` 为空 → **不发通知**（PRD：没有宠物因此变成只读时不发）。

**AC3 — `PET_SLOT_EXPIRED` 通知** `[L0]` `[L1]`（K-3 / K-4）
1. 仅 `demoted` 非空时，**在该用户事务提交之后**发一条（每次到期处理每用户最多一条，不按名额拆）。
2. 文案（后端 i18n，按 `AccountQueryService.localeOf(userId)`：`en` → EN，其余 → ID）：
   - `notify.PET_SLOT_EXPIRED.title` = id「Slot hewan sudah berakhir」/ en「Pet slot has expired」
   - `notify.PET_SLOT_EXPIRED.body` = id「{0} sekarang hanya-baca. Perpanjang slot untuk mengaktifkannya lagi.」/ en「{0} is now read-only. Renew the slot to reactivate it.」
   - `{0}` = 被转只读的宠物名：1 只直接用名；多只用「A, B & C」（id / en 同一连接写法，`&` 前不加逗号）。宠物名来自用户输入，放进 `MessageFormat` 参数而非拼进模板（不会被当成占位符解析）。
3. 发送：`NotificationService.sendWithCopy(userId, PET_SLOT_EXPIRED, "PET_SLOT_EXPIRED", args, renderedTitle, renderedBody, targetRef = null)`——`renderedTitle / renderedBody` 先用同一 `messageSource` + 收件人 locale + args 渲染好作为落库值（通知中心读它），推送由 `sendWithCopy` 按同一键同一 args 渲染（两边同一句）。`deepLinkType` = 类型名（`sendWithCopy` 固定写 `type.name()`），App 2.4 据类型直达名额管理页。
4. 🔴 不要用 `send(...)`：它的推送文案取 `notify.<TYPE>.title` 且 `args = null`（`NotificationService.pushText`:90-92），带 `{0}` 的串会原样推出去（`sendWithCopy` 注释 :365-374 讲的就是生日推送踩过的这个坑）。
5. 文案键加在 `messages.properties`、`messages_en.properties`、`messages_id.properties`、`messages_zh_CN.properties` 四份（zh 只给运营排障看，值用中文对照表原句）；串里若出现单引号须写 `''`（`MessageFormat`）。

**AC4 — 即将到期提醒 `PET_SLOT_EXPIRING`** `[L0]` `[L1]`（AD-7、AC11、K-1 / K-2）
1. 取 `status = 'ACTIVE' AND reminded_at IS NULL AND expires_at > now AND expires_at <= now + 3 天` 的名额。
2. 逐用户：条件更新 `UPDATE pet_slot_rentals SET reminded_at = :now WHERE id IN (:ids) AND status = 'ACTIVE' AND reminded_at IS NULL`（返回实际更新的行）→ 提交后对**实际更新到的**名额发提醒。
3. **合并口径**：同一用户本次扫描命中的名额中，**到期日（WIB 自然日）相同的合并为一条**通知；不同到期日各一条。（AD-7 原文「每个名额一条」；同一次租的多个名额到期日相同，按名额发会出现几条一模一样的提醒。见 Dev Notes「待确认」。）
4. 文案：
   - `notify.PET_SLOT_EXPIRING.title` = id「Slot hewan berakhir {0}」/ en「Pet slot ends {0}」
   - `notify.PET_SLOT_EXPIRING.body` = id「Perpanjang sebelum {0} agar semua hewanmu tetap aktif.」/ en「Renew before {0} to keep all your pets active.」
   - `{0}` = 到期日，**按 WIB（`ScheduleWindow.WIB`）换算**，格式 `d MMM`、收件人 locale（id「16 Okt」/ en「16 Oct」）；预格式化为字符串再传参（避免 `MessageFormat` 按 JVM 时区格式化日期）。
5. 发送同 AC3.3（`sendWithCopy`，`targetRef = null`）。
6. 续租后 2.2 已把 `reminded_at` 清空 → 新到期日前 3 天会再提醒一次；PRD「每个名额每月最多 2 条」= 1 条即将到期 + 1 条已到期。
7. 2.2 / 4.3 的补发名额（`ADMIN_GRANT`）同样适用（AC13b「到期照常提醒」）；期限不足 3 天的补发在首轮扫描即提醒，属预期。

**AC5 — 幂等与可重放** `[L0]` `[L1]`（NFR3）
1. 重复执行扫描：已 `EXPIRED` 的名额不再处理、`reminded_at` 非空的不再提醒 → **不重复通知、不重复处理**。
2. 中途失败：失败用户的事务回滚、名额保持原状态，下一轮重做；已成功用户不受影响。
3. 通知在状态提交之后发送（at-most-once）：若提交后发送失败，只记 WARN，不回滚状态、不重发（宁漏一条也不重复，且失败概率极低——落库是本地 DB 写）。L1 测试「扫描执行两次只有一条通知」。
4. 不加分布式锁（单实例部署 + 状态列幂等，同全库 `@Scheduled` 范式，AD-7）。

**AC6 — 验收（Epic AC 逐条）** `[L0]` `[L1]`
- Given 某名额 3 天后到期，When 扫描，Then 发一条 `PET_SLOT_EXPIRING`（含到期日），同一名额不重复发（AC11）。
- Given 名额到期且导致宠物只读，When 扫描，Then 名额置 `EXPIRED`，`reconcile(RENTAL_EXPIRED)`，发一条 `PET_SLOT_EXPIRED`（含转只读的宠物名）；无宠物因此只读时不发。
- Given 扫描中途失败或重复执行，When 再次扫描，Then 不重复通知、不重复处理。
- Given 续租在扫描前把 `expires_at` 推后，When 扫描与续租到账并发，Then 不把该名额置 EXPIRED（加锁后重读）。

**AC7 — 回归** `[L0]` `[L1]`
1. `MentionNotifyTest`（39 值约束与枚举双向比对）、`NotificationService` 相关既有测试全绿；不改 `NotificationType`、不改 `ck_notifications_type`。
2. `mvn -B clean package` 绿。

### 为什么不直接 `writeOpsAnnouncements`

它绑定运营活动实体（`OpsNotificationCampaign`）、不推送、无 args；本线需要推送 + 参数化 + 按账号语言，`sendWithCopy` 正好覆盖（落库值 = 已按收件人语言渲染好的句子，即「OPS_ANNOUNCEMENT 同款读后端 title / body」的效果）。
