## Story

As a 关掉了某类推送的用户,
I want 这类通知照样进通知中心但手机不再弹推送,
so that 不错过信息，也不被打扰。

## Acceptance Criteria

### 后端

**AC1 — `NotificationService` 三处闸门：「落库与加角标之后、调 pusher 之前」** `[L0]` `[L1]`（AD-5、PRD §3.1 影响面「推送闸门」、FR-150.2）
1. `NotificationService` 构造器新增依赖 `PushPreferenceService prefs`（1.1 提供，包 `com.tailtopia.notify.preference`）。新增私有方法 `pushAllowed(long recipientUserId, NotificationType type)`：调 `prefs.isEnabled(recipientUserId, type)`；**再包一层 `try/catch RuntimeException` → 返回 `true` 并 `log.warn("推送偏好查询失败（照常推送）cause={}", e.getClass().getSimpleName())`**（AD-3 已规定 `isEnabled` 自身异常返回 true，这里是双保险，与 `bumpUnreadBadge` :346-361、`acquirePushSlot` :271-281 同口径；日志不记 userId 以外的 PII，且不记 userId 也可）。
2. **`write(…, push = true)`**（`send` :104-108 走这里）：在 `skipPushForVirtual` 判断（:139-141）**之后**、`accountQuery.localeOf`（:142）与 `pusher.pushToUser`（:143-145）**之前**插入 `if (!pushAllowed(recipientUserId, type)) return saved;`。`repo.save`（:129）与 `bumpUnreadBadge`（:133）的位置与行为**不变**。
3. **`sendWithCopy`**（:379-396）：在 `skipPushForVirtual`（:387-389）之后、`localeOf`（:390）与 `pusher.pushToUser`（:391-394）之前插入同一判断，返回 `saved`。`CONTENT_MENTIONED`（`MentionNotifyListener`:128）、生日 / 纪念日 / 一周岁里程碑（`ScheduledPushDispatcher`:53）、`LIFECYCLE_*`（`LifecyclePushDispatcher`:64）都走这条。
4. **`pushInteraction`**（:244-265，由 `sendInteraction` 在事务提交后执行 :217-233）：在虚拟号 / 官方号跳过判断（:247-249）**之后**、`debounceKey` + `acquirePushSlot`（:250-253）**之前**插入 `if (!pushAllowed(recipientUserId, type)) return;`。**关了推送的人不占去抖键、不查触发人、不渲染文案**（AD-5「先于 `acquirePushSlot`」）。`sendInteraction` 的落库 / 合并 / 角标 / T-29 分支（:187-213）**不动**。
5. **不加闸门**（P-3、PRD「只有 `MILESTONE_SM_NODE` 不推送」）：`sendWithoutPush`（:120-124，本来就不推）、`sendToVet`（:334-339，发兽医账号）、`writeOpsAnnouncements`（:429-456，本来就不推；运营公告的闸门在 AC2）、问诊 IM 系统消息 `LiveTencentImClient.sendSystemMessage`（:156-182，调用方 `ConsultCloseService`:80 / `ConsultInterruptService`:67、:76、:96 / `ConsultAcceptService`:84）。这几条路径**不得调用** `PushPreferenceService`。
6. 闸门只认 `NotificationType`，分类判断只经 `PushPreferenceService`（内部 `PushCategory.of`）；`NotificationService` 里**不得**出现按类型 / 分类写死的 if 分支。

**AC2 — `OpsNotificationDispatcher` 按批预取「活动与优惠」关闭名单** `[L0]` `[L1]`（AD-5、P-4、PRD AC2）
1. 两个构造器（Spring 用的 :60-65、测试用的 :68-79）都新增参数 `PushPreferenceService prefs`（测试构造器放在 `pusher` 之后、`pacer` 之前；Spring 构造器委托时传入）。
2. `sendBatch`（:176-242）：在 `repo.addRecipients(id, written.size(), …)`（:192）**成功之后**、逐条推送循环（:196-211）**之前**，对本批 `written` 的收件人 id 调**一次** `prefs.mutedAmong(ids, PushCategory.PROMO)`（包 `try/catch RuntimeException` → 视为空集合、照常全推、`log.warn` 只记 campaignId 与异常类名），得到 `toPush = written` 中 `recipientUserId` 不在关闭名单里的行（保持原顺序）。
3. 首轮推送循环、`failed` 重推轮次（:213-233）一律只遍历 `toPush`。**命中者既不调 `push(n, campaign)`（:288-291）、也不调 `tick(id, pushed)`（:294-297）**，不进 `failed` 列表。
4. 中断 / 停止时未完成人数改为按 `toPush` 计：五处 `abort(id, written.size() - succeeded)`（:201、:209、:216、:221、:229）一律改为 `abort(id, toPush.size() - succeeded)`——被关闭名单拦下的人**不计失败**。
5. 计数口径（P-4）：
   - `recipient_count`（`addRecipients` :192，仓储 `OpsNotificationCampaignRepository`:67-76）= 本批**写入通知中心**的人数，**仍含**被拦下的人（他们确实收到了通知中心这条）；不改。
   - `failed_count`（`addFailed`，仓储 :89-98）**不含**被拦下的人。
   - `BatchOutcome(written.size(), failed.size())`（:241）不变；`finish` 判 `DONE` / `PARTIAL_FAILED`（:305-309）不变 → 一批里只有被拦下的人、没有真失败时，活动终态是 `DONE`。
   - 批次日志（:154-155）可追加 `muted={}`（**只记人数**，不记 id），同步改类注释「日志只记……」那句（:42）。
6. Given B 关掉「活动与优惠」、C 未关，When 运营公告（IDS 模式）发给 B、C，Then 两人都有一行 `OPS_ANNOUNCEMENT` 通知、角标各 +1；`pushToUserNow` 只对 C 调用一次、对 B 从未调用；活动 `recipient_count = 2`、`failed_count = 0`、状态 `DONE`。
7. 后台活动列表「触达」列（`AdminOpsNotifyController.reach` :185-196 读 `recipient_count`）与「失败 N」（:155-156 读 `failed_count`）**代码不改**；显示效果：触达数仍等于写入通知中心人数，被拦下的人不出现在失败数里（见 Dev Notes「拍板点 ③」）。

**AC3 — 分类与路径的验收组合（PRD AC1 / AC2a / AC2b / AC3）** `[L0]` `[L1]`
1. **AC1（点赞）**：B 关掉「点赞」后 A 赞 B 的帖子 → 通知中心有这条（`CONTENT_LIKED` 行 + actor）、`notify:unread:{B}` +1；`pusher.pushToUser` 未对 B 调用；`notify:likepush:{postId}` **不存在**（去抖键未被占）。B 打开「点赞」后 C 再赞同一帖（10 分钟内、通知仍未读、合并进同一行）→ 抢到去抖键、推送一次。
2. **AC2a（工单结案）**：`SupportTicketService.resolveTicket`（:198-217）在同一事务里先 `send(TICKET_RESOLVED)`（:209-211）、再 `send(CSAT_SURVEY)`（:212-214），两次各自 `REQUIRES_NEW`。B 关掉「活动与优惠」后结案 → 两条都进通知中心、角标 +2；推送只发 `TICKET_RESOLVED` 一条（属「订单与账号」，不可关），`CSAT_SURVEY` 不推。**`SupportTicketService` 不改**——闸门按每次 `send` 的 type 分别判断即满足。
3. **AC2b（@ 提及 vs 评论）**：B 关掉「@ 提及」、开着「评论与回复」→ 被 @（`sendWithCopy(CONTENT_MENTIONED)`）不推送、被评论（`sendInteraction(CONTENT_COMMENTED)`）照常推送。
4. **AC3（订单与账号）**：B 关掉其余 8 类后，`SHOP_ORDER_SHIPPED`（`AdminShopOrderService`:260）、`PET_SLOT_EXPIRING`（地基已有枚举值；本分支无发送方，测试直接调 `send`）、`ACCOUNT_SUSPENDED`（`AccountDisposalService`:231）照常推送。
5. 虚拟号 / 官方号：仍按原逻辑跳过推送，且**不触发**偏好查询（闸门在跳过判断之后，见拍板点 ①）。

**AC4 — 闸门失败兜底** `[L0]`（epics 1.2「闸门查询异常时照常推送并记 warn」、AD-3）
- `prefs.isEnabled` 抛 `RuntimeException` → `send` / `sendWithCopy` / `pushInteraction` 照常推送、通知照常落库，记 warn；`mutedAmong` 抛异常 → 本批照常全推，记 warn，活动不因此进 `PARTIAL_FAILED`。

**AC5 — 推送出口结构守卫** `[L0]`（NFR1「所有可关类型的推送出口都经 `PushPreferenceService`」、AD-5 末条）

- **① 闸门放在虚拟号 / 官方号跳过判断之后**：AD-5 写「`pushInteraction` 开头」，代码里开头已是虚拟号 / 官方号跳过（:247-249）。两者都是「不推」，先后不影响结果；放在其后能让这两类账号不多查一次库，并保持既有「虚拟号用例不碰偏好」的测试旁证。**硬约束只有一条：必须在 `acquirePushSlot` 之前**。`write` / `sendWithCopy` 同理放在 `skipPushForVirtual` 之后、`localeOf` 之前。
- **② `NotificationService` 与 dispatcher 各自再兜一层异常**：AD-3 只规定 `isEnabled` 自己兜底；`mutedAmong` 未规定。两处调用方都加 `try/catch` → 照常推送 + warn（宁多勿漏，与去抖 Redis 异常同口径）。
- **③ P-4「不计入推送数」的落地**：代码里**没有「已推送数」这一列**——后台「触达」显示的是 `recipient_count`（写入通知中心人数），`tick` 只是内存计数。因此：被拦下的人**照算进触达数**（他们确实进了通知中心），**不算进失败数**；后台显示与列定义**都不改**。P-4 里「推送数会小于收件人数」在后台看不到差异，运营若问「为什么某人没收到推送」，以批次日志的 `muted` 计数与该用户推送设置为准。
- **④ 一批全被拦下**：循环不执行，走 :238 `touchProgress` 收尾，`BatchOutcome(written, 0)`，活动 `DONE`。

### 实现提示

1. 闸门写法统一为早返回，不要把 pusher 调用包进 `if` 嵌套，便于阅读与 diff 审查：
   ```java
   if (skipPushForVirtual(recipientUserId)) { return saved; }
   if (!pushAllowed(recipientUserId, type)) { return saved; }   // V1.4.0 ④ AD-5：关了这类推送 → 只留通知中心
   java.util.Locale locale = accountQuery.localeOf(recipientUserId);
   ```
2. **事务回滚风险**：`write` / `sendWithCopy` 在 `REQUIRES_NEW` 事务里执行闸门查询。若 1.1 的 `isEnabled` 标了默认传播的 `@Transactional` 且在方法内部抛异常，Spring 会把**外层事务标成 rollback-only**——即使 `pushAllowed` 接住了异常，通知行也会在提交时回滚（角标却已 +1）。T0 必须确认 `isEnabled` 不带 `@Transactional`（或在其内部 try/catch 后正常返回）。查询走 `user_push_mutes` 主键，一次往返；与已在同一事务里执行的 `isVirtual` / `localeOf` 读库同一风险级别，不额外处理。
3. `pushInteraction` 在 `afterCommit` 里执行（无环境事务），偏好查询是一次自动提交的只读查询，没有回滚问题；它外层已有 `try/catch`（:217-223），但那条兜底会**吞掉整次推送**，所以仍要靠 `pushAllowed` 自己返回 true 来实现「异常照常推」。
4. dispatcher 预取：
   ```java
   Set<Long> muted = mutedAmong(id, written);          // 一次查询；异常 → Set.of() + warn
   List<Notification> toPush = muted.isEmpty() ? written
           : written.stream().filter(n -> !muted.contains(n.getRecipientUserId())).toList();
   ```
   之后把 :199 的 `for (Notification n : written)` 改为 `toPush`，所有 `abort(id, written.size() - succeeded)` 改为 `toPush.size() - succeeded`；`addRecipients` 与 `BatchOutcome` 仍用 `written.size()`。
5. 不在闸门处记 userId + 类型的 info 日志（每条推送都会打，且属于用户偏好数据）；被拦下的个案只在 debug 级、不带 PII。
6. 推送文案、深链、`targetRef` 一律不动；闸门只决定「推 / 不推」。

### 架构约束

- AD-5：三处 + dispatcher；`sendToVet` 与 IM 系统消息不加（P-3）；闸门不放 `NotificationPusher` / IM 客户端层。
- AD-3：`isEnabled` 对 `ORDER_ACCOUNT` 直接 true、不查库（1.1 实现）；本 story 不重复判断分类。
- P-4：被拦下的人不推送、不计失败；后台不加列、不改。
- 护栏：不加缓存层（闸门每次推送查一次库；运营公告按批一次）、不引新依赖 / MQ；通知中心落库与角标行为不得改变（cloud-rules「推送闸门纪律」）。
- 地基契约：`NotificationType` / `ck_notifications_type` 只读。

### 与前后 story 的边界（本 story 不做）

- **1.1**：`PushCategory` 映射、`user_push_mutes` 迁移 `V20261018_1800`、`PushPreferenceService` 本体、`GET / PATCH /api/v1/me/push-settings`、注销清理——本 story 只调用。若 1.1 尚未合入，**不要**在本 story 里自造替身类。
- **1.3**：App 通知设置页与设置页入口。
- **2.1 / 2.2 / 2.3 / 2.4**：收藏后端、详情字段、收藏列表、App 收藏按钮与 Disimpan Tab——收藏**不发任何通知**，与闸门无关。
- **3.1（对齐分支，云端跳过）**：①③ 合入后新增的推送出口（如 ③ 的送礼通知、② 的名额到期扫描、① 的升级通知）若不经本 story 已加闸门的路径，在对齐分支补 `isEnabled`；并在那时用真实发送方验收「关掉礼物 / 成就与等级后不推、名额到期照推」。`PushExitStructureTest` 会在合入时帮忙发现绕过的出口。
- 不改后台运营通知页面与统计口径；不改问诊 IM 推送；不做免打扰时段。
