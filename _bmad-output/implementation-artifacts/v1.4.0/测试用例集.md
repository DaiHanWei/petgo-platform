### 0.2b 🔴 HTTP 状态码口径校正（2026-08-21 实测）

**本文档里所有写「400」的期望都与实现不符**（共 25 处）。后端的约定是：

| 场景 | 实现返回 | 依据 |
|---|---|---|
| 领域校验失败（字段格式、必填、越界、业务前置不满足） | **422 Unprocessable Entity** | `AppException.validation()` → `HttpStatus.UNPROCESSABLE_ENTITY`，全项目统一 |
| 资源**状态冲突**（库存不足、已售罄、订单状态不允许该操作） | **409 Conflict** | 请求本身合法，是资源状态不允许；端上 `CartMutationError.from()` 亦**显式判 409** |
| 请求体畸形 / 缺参数解析失败 | 400 | Spring 默认 |

422 与 409 都比 400 更准：请求是良构的，问题在语义或状态。**不是缺陷，是用例写错。**

已逐条实测确认的：

| 用例 | 用例原写 | 实测 |
|---|---|---|
| EC-ADDR-007 邮编位数 | 400 | **422**「邮编应为 5 位数字」 |
| EC-ADDR-008 手机号留空 | 400 | **422**「请填写收件人手机号」 |
| EC-CKT-012 空车提交 | 400 | **422**「购物车为空」 |
| EC-CKT-013 无地址提交 | 400 | **422**「请选择收货地址」 |
| EC-CART-006 超库存加购 | 400 | **409**「库存不足，该规格最多可购买 N 件」 |
| EC-CART-007 售罄加购 | 400 | **409**「该规格已售罄」 |
| EC-CART-013 qty≤0 | 400「数量必须为正」 | **200，删除该行** —— `CartService.setQty` 注释明写「qty ≤ 0 视为删除」，`remove()` 即 `setQty(...,0)`。**是设计** |

⚠️ 其余 18 处**未逐条实测**，按上表约定判断即可（校验类走 422）。执行到时按实测结果就地更正本表。

### 1.2 灌演示数据（不灌则 10 个页面一个都点不动）

```bash
{ echo "SET petgo.allow_demo_seed='yes';"; cat scripts/seed-shop-demo.sql; } \
  | docker exec -i petgo-pg psql -U petgo -d petgo -v ON_ERROR_STOP=1
```

5 个 Kecamatan 的配送范围与运费 + 满额包邮门槛 300,000。

| ⚠️ 陷阱 | 处理 |
|---|---|
| 演示商品可能 `is_active=false`（集成测试残留），Toko 空 | `UPDATE shop_products SET is_active=true WHERE public_token LIKE 'demo-%';` |
| `main_image_key` 是占位 key，**图位是空的** | **这是预期不是 bug**。要看真图从后台上传 |
| 采购入库段需要**真实存在的 ACTIVE 超管** | 缺则该段跳过并告警，商品/SKU/库存照常灌。**但缺它整条退货链走不完**（质检入库要回查采购价） |
| 跑一次后端全量测试会**清空本地 `petgo` 库** | 重启后端 Flyway 会迁回来，**演示数据要重灌** |
| DB 重置后 Redis 里全是孤儿键（新用户继承旧账号角标） | `docker exec petgo-redis redis-cli -n 0 FLUSHDB` |

### 1.3 造用户侧数据（dev 用户 id=1 默认零订单、无档案，7 屏点不动）

用 `_bmad-output/implementation-artifacts/v1.4.0/seed-user1-l2.sh`。下单/支付/收货走**真实 API**，
只有「发货」与「日期回溯」用 SQL。四个要点：

1. **混合支付**靠 `shop_pawcoin_rules.max_coin_per_order` 封顶（设 50000）——
   光给余额会让整单被币付掉，拿不到两段拆分。
2. **有现金段的订单 `pay` 之后不会自动结清**，要补一发 stub 网关回调：
   `POST /pay/callback`，form `order_id=<intentToken>&transaction_id=stub-<intentToken>&transaction_status=settlement`。
3. **复购触发卡要 4 个条件同时成立**：档案有体重 · 商品有 `feeding_guide` · SKU 有 `net_weight_g` ·
   源订单 `delivered_at` 回溯到「耗尽日 −7 天」窗口内。
   演示数据里 Whiskas 1.2kg + 3.4kg 猫 = 55g/天 → 21 天 → 送达日回溯 16 天正好落窗口。
4. 后台权限用例需要**多个角色账号**（见 §ADM-F），提前建好。

### 1.4 起 App（🔴 本文档的 App 用例默认跑 **v2** 版式）

```bash
cd petgo_app && flutter build apk --debug \
  --dart-define=SHOP_UI=v2 \
  --dart-define=PETGO_API_BASE_URL=http://10.0.2.2:8081 \
  --dart-define=DEV_GOOGLE_STUB=true \
```

- **不传 `SHOP_UI=v2` 拿到的是 v1**，这是**发布安全的默认值**（新版式尚未通过人工验收）。

- **v1 与 v2 走同一路由、同一批 provider**，差异只在渲染层。因此
  **数据类缺陷两套都会有，版式类缺陷只在一侧**（这条判断能省一半排查时间）。

## 3 · 速查：状态机与枚举

### 3.1 订单状态 `ShopOrderStatus`（8 值）

```
PENDING_PAYMENT ──付款──> PENDING_SHIPMENT ──后台发货──> SHIPPED ──送达──> DELIVERED ──> COMPLETED
      │                          │                                          │
      ├─取消/超时─> CANCELLED     └─异常处置─> CANCELLED                      └─退货─> REFUNDING ─> REFUNDED
```

- **支付窗口 60 分钟**（`ShopOrder.PAYMENT_WINDOW`，AD-8）
- **发货后 7 天自动标记送达**（`AUTO_DELIVER_AFTER`）
- **送达后 7 天自动完成**（`AUTO_COMPLETE_AFTER`）
- **退货窗口 7 天**（`RETURN_WINDOW`，自送达起算）

### 3.2 退货状态 `ReturnStatus`（9 值）

```
PENDING_REVIEW ─驳回─> REJECTED
      │
      └─通过─> AWAIT_SHIPBACK ─用户寄回─> INSPECTING ─质检通过─> REFUNDING ─> REFUNDED
                    │  (寄回窗口 7 天)          │                    │
                    └─用户撤销─> WITHDRAWN      └─质检不通过─> CLOSED  └─失败─> REFUND_FAILED (最多重试 3 次)
```

| ID | P | 层 | 用例 / 步骤 | 预期结果 | 溯源 |
