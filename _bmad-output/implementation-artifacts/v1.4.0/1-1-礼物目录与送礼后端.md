## Story

As a 想给别人宠物送礼的用户,
I want 选礼物和数量后用 PawCoin 或 QRIS 付款、礼物送达,
so that 我能表达对这只宠物的喜爱。

**AC4 — 目录接口 `GET /api/v1/gifts/catalog`** `[L0]` `[L1]`（AD-10、PRD AC3 / AC3a）
1. 参数二选一：`petId`（Diary Tab / 礼物页入口）或 `postId`（Diary 详情页入口，经 `petsOfPost` 取**第一只**；单宠过渡，多宠在 4.1）。都不给或都给 → 422 validation。**`postId` 入参是对 AD-10 的补充**（见 Dev Notes「偏离架构 ②」）。
2. 校验同发起（AC5.1 的 1 ~ 4 条：宠物可送达、非自己的宠物、送礼人未拉黑主人），失败码与发起一致，让 App 打开面板时就能显示 C9。
3. 响应 `GiftCatalogResponse`：
   ```
   { recipient: { petId, name, avatarUrl, petType, breed },
     qrisMinAmount: 10000,
     tiers: [ { price, gifts: [GiftItem…] } … ],          // 普通礼物，按 price 升序分组
     exclusiveGroups: [ { minLevel, gifts: [GiftItem…] } … ], // 已解锁的专属礼物，按 minLevel 升序分组（第一批在前）
     lockBlock: { requiredLevel } | null }
   GiftItem = { giftToken, nameEn, nameId, iconUrl, price, kind, minLevel }
   ```
   - 只含 `status = ONLINE`。不下发 `id`、`sort_order`、物种布尔值。
   - **组内排序**（AD-10，PRD AC3a）：先「适用收礼宠物物种」（CAT → `for_cat`、DOG → `for_dog`、OTHER → `for_other` 为 true），再「通用」（三者皆 false），再「其他」；同组 `sort_order ASC, id ASC`。专属组内同此规则。
   - **专属过滤**：`GrowthQueryService.getLevel(sender)`；`participating = false` 视为 level 0。只放 `min_level <= level` 的专属礼物。
   - **`lockBlock.requiredLevel`** = `min(min_level)` over ONLINE 且 `min_level > level` 的专属礼物；不存在 → `lockBlock = null`。
4. Given Lv1（地基占位）用户，When 拉取目录，Then 不含任何专属礼物、`lockBlock.requiredLevel = 5`（库里有 min_level 5 与 15 两批时）（AC3 后端）。
5. Given 给猫送礼，When 拉取 Rp1,000 档，Then 标「猫」的排最前、通用其次、只标「狗」的最后；给狗时相应调整（AC3a）。
6. 需登录且 `role = USER`（SecurityConfig 加精确 matcher，见 AC9）。

**AC5 — 发起 `POST /api/v1/pets/{petId}/gifts`** `[L0]` `[L1]`（AD-6、PRD AC1 / AC4 / AC5 / AC9 / AC10）
请求 `GiftSendRequest { @NotBlank giftToken, @NotNull Integer quantity, @NotNull PayChannel channel, @NotBlank @Size(max=64) requestId, @NotBlank source, Long postId }`（`postId` 只作来源记录，可空；AD-6 写的 `postToken` 改为 `postId`，内容帖子在 App 内按数字 id 寻址、无 public token）。
1. **校验顺序**（全部在任何写库之前；失败即抛，不留任何行）：
   1. `GiftPetDirectory.pet(petId)` 为空，或 `ownerDeleted = true` → 404 `gift-pet-gone`。**`ownerActive = false` 但未注销（封号）→ 允许**（PRD：封号主人可收礼）。**只读宠物不校验**（PRD AC10：只读可收）。
   2. `sender == ownerId` → 422 `gift-own-pet`（AC1 后端）。
   3. `UserHideRelationReader.isBlocked(sender, ownerId)` → 403 `gift-blocked`。**只拦单向**：`isBlocked(ownerId, sender)`（主人拉黑送礼人）**不拦**（AC9 后端）。
   4. 礼物按 `giftToken` 查得到且 `ONLINE`，否则 409 `gift-unavailable`。
   5. `EXCLUSIVE` 时 `getLevel(sender)` 必须 `participating` 且 `level >= min_level`，否则 403 `gift-locked`（AC3 后端）。
   6. `quantity ∈ [1, 99]`，否则 422 validation（0 / 100 被拒）。
   7. `channel = MIXED` → 422 validation（显式 `case MIXED -> throw`，不落 default，照 `KeepsakePurchaseService.start`）。
   8. `total = price × quantity`；`channel = QRIS` 且 `total < pricing.giftQrisMinAmount` → 422 `gift-qris-below-min`（AC4 后端）；Rp10,000 可用 QRIS。
   9. `source` 不在三值内 → 422 validation。
2. **幂等**：`idem_key = GiftIdemKeys.send(senderId, requestId)` = `GIFT:{senderId}:{requestId}`。先按 `idem_key` 查已有订单：
   - 有 → **不再校验、不再扣款**，按当前订单状态返回同一订单（PawCoin → `delivered = true`；QRIS PENDING → 重走 AC7.3 取回同一意图与二维码；其它状态 → 返回 status）；
   - 并发同键插入撞 `uq` → 捕获 `DataIntegrityViolationException`，新事务重读后按上一条返回。
   - Given 同一 `requestId` 重复提交，When 第二次请求，Then 返回同一 `orderToken`，余额只扣一次。
3. 下单快照：`pet_name`、`gift_name_en / gift_name_id / gift_icon_url / unit_price`（取下单时目录行）、`owner_id`、`source`；`public_token` 32 位 base62（新建 `gift.service.GiftTokenGenerator`，照 `KeepsakeTokenGenerator`）。
4. 限流：controller 内 `rateLimiter.check("rl:gift:send:" + userId, 20, Duration.ofMinutes(1))`（与 `createIntent` 的 20 次 / 分钟同档；PawCoin 渠道不经 `createIntent`，必须自己限）。
5. 响应 `GiftSendResponse(boolean delivered, PaymentIntentResponse payment, String payload, String orderToken, String status)`：前三项与 `KeepsakePurchaseResponse` 同形（App 复用解析）；PawCoin 成功 `delivered = true, payment = null`；QRIS `delivered = false` + 意图 + 二维码载荷。

**AC6 — PawCoin 渠道（同步成交）** `[L0]` `[L1]`（AD-6、PRD AC5）
1. 同一事务：插入订单（`status = PENDING`, `channel = PAWCOIN`）→ `wallet.debit(senderId, total, PawCoinTxnType.SPEND, "GIFT", orderId, GiftIdemKeys.coin(orderToken))`（`GIFT_COIN:{orderToken}`）→ `GiftDeliveryService.deliver(order)`。
2. `refType` 必须是字面量 **`"GIFT"`**（= `PaymentPurpose.GIFT.name()`）：① 的消费返成长值监听按 `refType ∉ {…, GIFT, …}` 过滤，写错会被重复计成长值。
3. 余额不足 → `debit` 抛 409 `pawcoin-insufficient` → 整事务回滚（订单行不留）。
4. Given PawCoin 送 Rp10,000，When 发起成功，Then 余额 −10,000（`debit SPEND`，总账 FLOAT_LIABILITY → PLATFORM_REVENUE），订单 DELIVERED，墙与粉丝榜更新，发布**一次** `GiftSentEvent(orderId, senderId, ownerId, petId, totalAmount = 10000)`（AC5 后端）。成长值数值由 ① 入账，本分支不验。
5. 只读宠物可收（AC10）。

**AC7 — QRIS 渠道** `[L0]` `[L1]`（AD-6、AD-7、PRD AC6 / AC7）
1. 插入订单（`PENDING`, `QRIS`）→ `paymentIntents.createIntent(senderId, PaymentPurpose.GIFT, PayChannel.QRIS, total, "IDR", GiftIdemKeys.qris(orderToken), GiftSendService.PAY_WINDOW)`（`GIFT_QRIS:{orderToken}`，`PAY_WINDOW = Duration.ofMinutes(60)` 常量，照 Keepsake）→ 回填 `payment_intent_id` → 私有 `ensureCharge`（照抄 `KeepsakePurchaseService.ensureCharge` 的逻辑，gift 包私有副本，Keepsake 不改）。
2. `@Transactional(noRollbackFor = PayException.class)`（同 Keepsake：网关下单失败时 `failChargeAttempt` 已把意图置 FAILED，这一行须随事务提交留档；订单随之在 AC8.4 的失败处理里置 FAILED）。
3. **幂等重放取回**：对已有 QRIS PENDING 订单，再次 `createIntent(…同键…)`：返回的意图 id == 订单 `payment_intent_id` → 返回它与 `ensureCharge` 的已存载荷；**不等**（旧意图已过窗被懒过期、不发失败事件）→ 订单置 `EXPIRED`（不发事件）并返回 `status = EXPIRED`，**不**把新意图挂到旧订单上（App 换新 `requestId` 重发）。
4. 改价只影响新订单：PENDING 订单的 `unit_price / total` 不随目录改价变化（AC17 的下单侧）。

**AC8 — 交付 `GiftDeliveryService.deliver` 与两个支付监听** `[L0]` `[L1]`（AD-7、PRD AC6 / AC7 / AC8）
1. `deliver(GiftOrder order)` 只接受 `PENDING`；**交付前再校验可送达**（顺序）：主人已注销 → `OWNER_DELETED`；`order.pet_id` 为空或 `GiftPetDirectory.pet` 为空 → `PET_DELETED`；`isBlocked(sender, owner)` → `SENDER_BLOCKED`。
2. 可送达 → 条件更新 `UPDATE gift_orders SET status = 'DELIVERED', delivered_at = now() WHERE id = :id AND status = 'PENDING'`（返回 0 行 = 已被并发交付，直接返回，不再写汇总、不发事件）→ 同事务 upsert 汇总：
   - `gift_pet_wall`：`INSERT … ON CONFLICT (pet_id, gift_id, unit_price) DO UPDATE SET count = gift_pet_wall.count + EXCLUDED.count`（**名称 / 图标保留首次快照，不覆盖**）；
   - `gift_pet_supporters`：`ON CONFLICT (pet_id, sender_id) DO UPDATE SET total_amount = total_amount + :total, gift_count = gift_count + :qty, last_sent_at = now()`；
   - 然后 `events.publishEvent(new GiftSentEvent(order.id, sender, owner, petId, order.total))`（同步发布，① 与 1.2 的监听都是 AFTER_COMMIT）。
3. 不可送达（只可能出现在 QRIS 到账时；PawCoin 同步成交、校验刚做过）→ 条件更新为 `UNDELIVERED_REFUND_PENDING` + `undelivered_reason`，**不写汇总、不发 `GiftSentEvent`**，发布本模块内部事件 `gift.event.GiftUndeliveredEvent(long giftOrderId)`（退回与通知由 Story 1.2 监听实现；本 story 只发布）。
4. `gift.listener.GiftPaidHandler`：`@EventListener` + `@Transactional(propagation = MANDATORY)` 加入 `applyCallback` 事务（照 `KeepsakePaidHandler`，**绝不 AFTER_COMMIT**）；只认 `event.purpose() == PaymentPurpose.GIFT`；按 `payment_intent_id` 找订单，非 PENDING → 返回（重放幂等）；调 `deliver`。**任何路径都不向上抛**（向上抛会回滚 `markPaid`）：外层 `try/catch RuntimeException` 记 `log.error`（只记 `intentId` / 订单 id，不记金额以外信息）。
5. `gift.listener.GiftPaymentFailedHandler`：`@EventListener` + `@Transactional`（照 `KeepsakePaymentFailedHandler`）；`purpose == GIFT` 且 `failureCategory != null`；对应 PENDING 订单：`EXPIRED` 类别 → `EXPIRED`，其余（`GATEWAY_DECLINED` / `USER_CANCELLED`）→ `FAILED`；**不发事件、不通知**（AC7）。
6. Given QRIS 送礼，When 回调与轮询同时到达（两线程并发 `applyCallback`），Then 只交付一次、墙计数只 +N 一次、`GiftSentEvent` 只一次（AC8）；离开 App 后付款照常交付（AC6，交付不依赖 App 在线）；未付过期（`PaymentIntentExpiryScanner` 60 秒扫描发 `PaymentIntentFailedEvent`）→ `EXPIRED`、无事件（AC7）。

### 偏离 / 补充架构（实现照本 story，Completion Notes「待确认」各记一句）

1. **`gift_orders.pet_name` 快照列（AD-2 未列）**：退回通知要说「你送给 Mochi 的礼物未能送达」，而宠物被删后 `pet_id` 已置空、名字无处可取；2.3 送礼记录同理。按「订单快照」口径补此列。
2. **目录接口接受 `postId`（AD-10 只写 `petId`）**：现 `ContentDetailResponse` 不含宠物（`giftPets` 在 2.1），App 详情页（1.3）拿不到 petId；经 `GiftPetDirectory.petsOfPost` 取，响应 `recipient.petId` 交给发起接口。对齐 story 4.1 多宠时改为 A7 先选宠物再按 `petId` 取。
3. **单笔状态查询 `GET /api/v1/me/gift-orders/{orderToken}`（AD-10 未列）**：`showQrPaymentSheet` 需要 `pollPaid`；现有无通用意图状态端点（`PaymentIntentService.statusOf` 只经充值端点，且其懒过期不发事件）。本端点**只读订单**，不懒过期意图。
4. **不可送达时不在 `GiftPaidHandler` 同事务里调 `wallet.credit`（AD-7「同事务尝试退回」）**：`credit` 是 `@Transactional` 参与方法，抛异常会把**外层 `applyCallback` 事务**标成 rollback-only，`markPaid` 跟着回滚（到账丢失）。本 story 只置 `UNDELIVERED_REFUND_PENDING` 并发 `GiftUndeliveredEvent`；1.2 在提交后用 `REQUIRES_NEW` 退回。

### 架构约束

- AD-5 / P-3：取宠物只经 `GiftPetDirectory`；不引 ① 的等级页、② 的任何接口。
- AD-6：校验全集与幂等；MIXED 显式拒绝；QRIS 最低额只在送礼服务内校验。
- AD-7：交付前二次校验；状态守卫 + `payment_intent_id` 唯一保证只交付一次；`GiftSentEvent` 只在 DELIVERED 时发。
- §5：钱包服务不改、gift 包避开 `transfer`；幂等键集中 `GiftIdemKeys`；对外标识 `public_token`（礼物、订单），宠物沿用 `petId` 路由。
- 护栏：不引 MQ / 缓存 / 新依赖；`ddl-auto=validate`；日志 SLF4J，**不记**昵称、宠物名、二维码载荷、网关 meta；金额与内部 id 可记。

### 本 story 不做

- 退回 PawCoin、退回重试、收礼 / 退回通知（Story 1.2）；App（1.3）。
- 礼物墙 / 粉丝榜 / 统计 `giftTotalValue` / 详情 `giftPets` / H5 名片（2.1）；送礼记录列表（2.3）；订单中心不接入送礼。
- 后台礼物目录与 QRIS 最低额改值（3.1）、送礼记录页（3.2）。
- 成长值（① 监听 `GiftSentEvent`，本分支不触发也不验数值）；多宠选宠物（4.1）。
