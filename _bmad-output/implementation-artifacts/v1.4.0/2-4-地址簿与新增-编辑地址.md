## Dev Notes

### 🔴 手机号校验必须两端逐条一致
App 端 `normalizeIdPhone` 与服务端 `IndonesiaPhone` **逐条对齐**，测试也刻意写成镜像。
两边不一致时用户在 App 里通过了、提交却被服务端拒 —— 表面是「保存失败」，实际是两套规则打架，
**是最难排查的一类问题**。

### 🔴 级联换上级必须清空下级
选了省再改省，若不清 Kota/Kecamatan 会拼出**自相矛盾的地址**；
而运费按 Kecamatan 算、承运商按省市派送，矛盾组合直接导致派送失败。

### ⚠️ 级联数据源的已知局限
三级树来自 `shipping_zones`（仓库里唯一的行政区划数据），**含 `active=false` 的区域** ——
这样用户能存下「已录入但暂不送达」的地址（FR-99 允许），下单时才被挡。
🔴 **但平台从未录入过的区域用户选不到**，也就存不了那里的地址。
👉 在拿到完整印尼行政区划基础数据前，**运营录服务范围时应把计划开通的区域也录进来并置 inactive**。

### 🔒 PII
`ShippingAddress.toString()` 已覆盖，只输出 token + kecamatan（非 PII，排障需要）。
保存失败的错误提示**不回显用户输入**。
