## Story

As a 运营,
I want 在后台查看与调整库存、登记采购入库,
so that 系统里的库存数与仓库实物对得上。

## Acceptance Criteria

> 每条 AC 标注验证层级：`[L0]` 静态（无需 DB）· `[L1]` 集成（需 Docker postgres+redis，**本机现已可跑**）· `[L2]` 端到端（需真机/真实凭证/人工视觉）

### AC1 — 库存管理页：三个数不合并显示

**Given** 运营具备 `shop.inventory_view` 权限
**When** 打开 `/admin/shop/inventory`
**Then** 按 SKU 展示 **实际库存 `actual` / 锁定库存 `locked` / 可售库存（计算值 `actual - locked`）** 三列
**And** 🔴 **三列必须并排展示，不得合并、不得只显示可售** —— AB-10C 原文：客服排查「用户说买不了但后台显示有货」时，**差异一定在锁定库存上**，合并显示等于把排查依据删掉
**And** 可售库存**不落库、查询期计算**（继承 V102 表设计与 Story 1.2 口径），页面不得新增第三列存储
**And** 无 `shop.inventory_view` 权限 → 页面不可达（302 登录 / 403）

`[L1]` 集成：三列数值正确且 `available == actual - locked`
`[L0]` 单测：可售库存计算与三态映射复用 `InventoryService.statusOf`

### AC2 — 库存增减只有四条合法路径，且全部留痕

**Given** 库存变更来自多个途径
**When** 检视库存状态机实现
**Then** 覆盖四条 `actual` 增减路径（补齐 SPEC-7）：

| # | 路径 | 方向 | 触发者 | 本 Story 是否实现 |
|---|---|---|---|---|
| 1 | **采购入库** | `actual +` | 后台运营（本页） | ✅ 实现 |
| 2 | **报损** | `actual −` | 后台运营（本页） | ✅ 实现 |
| 3 | **盘点调整** | `actual` 设为盘点值（可增可减） | 后台运营（本页） | ✅ 实现 |
| 4 | **退货质检通过入库** | `actual +` | 后台质检（AB-12B，Story 5.4） | 🔶 **本 Story 只提供入库原语与批次类型，不实现质检流程** |

**And** 🔴 **不提供直接编辑库存数字的入口**（AB-10C 原文）—— 直接改数会使库存与采购成本脱钩，令 AB-13A 毛利核算失真。**所有 `actual` 变更必须经由一条流水记录产生。**
**And** 每次变更**必须留存：操作人 · 原因 · 变更前值 · 变更后值**（可审计）
**And** 退货入库须标记为**退货入库批次**，与采购入库区分（二次销售风险不同）

`[L0]` 状态机单测：四条路径 × 成功/失败分支
`[L1]` 集成：入库 / 报损 / 盘点各自正确改变 `actual` 且留痕

### AC3 — 采购入库单（含 S-9 的拒收货口径）

**Given** 运营具备 `shop.inventory_edit` **且** `shop.cost_edit` 权限
**When** 登记采购入库
**Then** 表单字段：**采购单号 · 供应商 · SKU · 数量 · 进货单价 · 入库日期**，操作人由服务端从登录态取（**不接受前端传入**）
**And** 入库成功后该 SKU 的 `actual` 增加对应数量
**And** 🔒 **进货单价受 `shop.cost_edit` 门控** —— 无该权限**不能登记采购入库**（因 S-9 规定进货单价不允许留空，缺权限即无法完成必填项）。页面对无权限者**不渲染入库入口**，服务端**独立再判一次**

> 📌 **2026-08-17 产品确认**：采购入库**强制要求 `shop.inventory_edit` + `shop.cost_edit` 双权限**，不拆成「仓管先录量、财务后补价」两步。
> 拆两步会产生「已入库但无成本」的中间态，与 S-9「不允许留空」字面冲突，且 AB-13A 毛利在补价前不准。
> **已知代价并接受**：普通仓管无法独立完成采购入库，须由财务或管理层操作。
> ⚠️ 退货入库不受此限（单价由系统带出，非人工填写），只需 `shop.inventory_edit`。

**Given** 拒收商品退回仓库（S-9 / SPEC-11）
**When** 登记该批货入库
**Then** 批次类型为 **`RETURN_INBOUND`（退货入库批次）**，非采购批次
**And** **采购单号填原订单号**、**进货单价取该 SKU 最近一次采购入库单价**（系统自动带出）
**And** 🔴 **两者均不允许留空** —— 留空会让「钱已退、货已回、系统里不存在」，并污染 AB-13C 的资金占用读数
**And** 因单价由系统带出而非人工填写，退货入库**只需 `shop.inventory_edit`，不需 `shop.cost_edit`**
**And** 若该 SKU **从无采购入库记录**（无历史单价可取）→ 明确报错拒绝，**不得静默以 0 入库**（0 成本会让毛利虚高）

`[L1]` 集成：采购入库改变 `actual` 且流水含全部字段；退货入库自动带出单价；无历史单价时被拒
`[L0]` 单测：单价带出逻辑、必填校验、权限组合

### AC4 — 报损与盘点调整的不变式（安全攸关）

**Given** 某 SKU `actual=10`、`locked=7`（7 件已被下单锁定）
**When** 运营报损 5 件
**Then** 🔴 **必须被拒绝** —— 可售仅 3 件，报损 5 件会使 `locked > actual`，等于把已卖给用户的货报损掉
**And** 报损的合法上限是**可售库存**（`actual - locked`），**不是** `actual`

**Given** 同一 SKU
**When** 盘点调整把 `actual` 设为 5
**Then** 🔴 **必须被拒绝** —— 盘点值 `5 < locked 7`，同样破坏不变式
**And** 盘点调整的合法下限是 `locked`

**And** 🔴 两条判定**必须是单条条件原子 UPDATE 判影响行数**（AD-6），**不得**「先查可售、再改」
**And** DB CHECK `ck_sku_inventory_locked_le_actual` 是最后一道兜底，**不是**本 AC 的证明对象

`[L0]` 单测：边界值 —— 报损 3（成功）/ 4（拒绝）；盘点 7（成功）/ 6（拒绝）
`[L1]` 集成：并发报损不产生 `locked > actual`

**Given** 模块 10 已由 Story 1.3 接入后台

**Then** 新增两个权限码 **`shop.inventory_view`** / **`shop.inventory_edit`**，🔴 **不默认授予任何既有运营角色**（NFR-11）
**And** 导航「电商」分组**末尾追加**「库存管理」，既有「商品管理」项与分组顺序**一行不动**
**And** 三类操作各写一条审计：`SHOP_INVENTORY_RECEIPT_CREATED` / `SHOP_INVENTORY_DAMAGED` / `SHOP_INVENTORY_STOCKTAKED`
**And** 🔒 **审计详情不写进货单价数值** —— 审计日志页的可见范围与进货价权限不同，写进去等于绕过 `shop.cost_view`（沿用 Story 1.3 对 `SHOP_PRODUCT_COST_UPDATED` 的同一处置）

`[L0]` 护栏单测：权限码已注册 · `perm.*` 三份 i18n 齐全 · 导航既有项未丢 · 审计详情不含单价

### 表设计：单张追加式流水表

**`inventory_movements`（V104）** —— 一张 append-only 流水表同时承担「入库单」「报损单」「盘点单」与「审计前后值」四个职责。

理由：AB-10C 要求的「操作人 · 原因 · 前后值」对三类操作是同一组字段；拆成多表会让 AB-13D 对账（进货成本 → 销售收入 → 毛利的可追溯链路）需要 union 多张表。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `sku_id` | bigint NOT NULL FK → `shop_skus(id)` | |
| `movement_type` | varchar NOT NULL | `PURCHASE_INBOUND` / `RETURN_INBOUND` / `DAMAGE` / `STOCKTAKE` |
| `qty_delta` | bigint NOT NULL | 🔴 **带符号**：入库为正、报损为负、盘点为差值（可正可负） |
| `actual_before` | bigint NOT NULL | 变更前 `actual` |
| `actual_after` | bigint NOT NULL | 变更后 `actual` |
| `reason` | varchar | 报损/盘点**必填**；入库可空 |
| `purchase_no` | varchar | 采购单号；退货入库时**填原订单号**（S-9） |
| `supplier` | varchar | 供应商；退货入库可空 |
| `unit_cost` | bigint | 🔒 **商业敏感**，进货单价（最小币种单位）。需 `shop.cost_view` 才下发 |
| `inbound_date` | date | 入库日期 |
| `operator_account_id` | bigint NOT NULL | 🔴 服务端从登录态取，**不接受前端传入** |
| `created_at` | timestamptz NOT NULL | UTC |

**约束：**
- `CHECK (actual_before >= 0 AND actual_after >= 0)`
- `CHECK (actual_after = actual_before + qty_delta)` —— 🔴 让「流水与实际不符」在 DB 层就写不进去
- 入库类必填单价：`CHECK (movement_type NOT IN ('PURCHASE_INBOUND','RETURN_INBOUND') OR (unit_cost IS NOT NULL AND purchase_no IS NOT NULL))` —— 落实 S-9 的「不允许留空」
- 索引 `(sku_id, created_at DESC)`（取最近一次采购单价 + 页面流水）

> 🔴 **本表不落 `locked`** —— `locked` 只由订单流程改动，与本 Story 的四条路径无关，冗余存储会产生第二个真相。

### ⚠️ 三个必踩的陷阱

**陷阱 1 —— `@Modifying` 后读回是脏的。**
现有 `SkuInventoryRepository` 的四条原语**都没有**加 `clearAutomatically` / `flushAutomatically`（Story 1.2 不需要读回）。本 Story 要记录 `actual_after`，**照抄现有注解会读到持久化上下文里的旧实体**，写进流水的前后值就是错的——而且**不会报任何错**。

新原语必须写成：
```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
```
读回是安全的：条件 UPDATE 成功后该行持有写锁直到提交，同事务内再读拿到的是稳定值，其他事务改不动它。

**陷阱 2 —— 报损的上限是可售，不是 `actual`。**
`WHERE i.actual >= :qty` 是错的：它允许把已被 `locked` 的货报损掉，直接破坏 `locked <= actual`，等于把已卖出的货销账。正确条件是 `i.actual - i.locked >= :qty`。
> 这与 Story 1.2 的 `lock()` 是同一个条件形状——**照抄 `lock()` 的 WHERE，不要照抄 `commit()` 的**。

**陷阱 3 —— 窄过滤器跑测试会漏掉跨模块护栏。**

#### 🔴 变异验证：本 Story 的源码护栏最初是假绿的

按 Story 1.2 沉淀的方法论，对最关键的守卫做了变异验证 —— 把 `SkuInventoryRepository.damage` 的 WHERE 从 `i.actual - i.locked >= :qty` 改成 `i.actual >= :qty`（即「报损上限误写成 actual」这个最可能犯的错）：

| 测试 | 变异下的表现 | 判定 |
|---|---|---|
| `AdminShopInventoryEndpointIntegrationTest`（L1）2 条 | ✅ **变红** | 有牙 |
| `InventoryMovementServiceTest`（L0）18 条 | 绿 | 预期——L0 mock 掉了仓储，扫不到 SQL |
| `damageSqlGuardsAvailableNotActual`（源码护栏） | 🔴 **仍然绿 = 假阳性** | **无牙，已修** |

**假绿根因：** 护栏原本断言的是「**文件里含** `where i.skuId = :skuId and i.actual - i.locked >= :qty`」，而 **`lock()` 的 WHERE 与之逐字相同** —— 整文件 `contains` 被 `lock()` 满足了，报损条件改坏它照样绿。

**已修：** 新增 `queryOf(code, methodSignature)`，按方法定位到它自己的 `@Query` 块再断言。修后在变异未还原的状态下复跑 → **正确变红**；还原守卫后 → 绿。

> 📌 这与 2026-08-17 在 `AdminPermissionWiringTest` 上遇到的是**同一类错误**：护栏的判定方式与它声称要看守的东西对不上。
> **沉淀：源码级护栏若断言的是「文件含某字符串」，必须先确认该字符串在文件里唯一。**否则同形状的邻居代码会替它满足断言。

#### 与原任务描述的三处偏离（实现时按更正确的方案走）

| # | 任务原文 | 实际实现 | 理由 |
|---|---|---|---|
| 1 | `stocktakeTo(skuId, counted)` | `stocktakeTo(skuId, counted, expectedBefore)` —— 带期望前值的 **CAS** | 入库/报损是**增量**操作，前值可由 `after ∓ qty` 精确反推；**盘点是赋值操作，反推不出前值**。若「先读前值、再赋值」，两步之间的并发改动会把**错误的前值**写进审计流水，而 DB 的 `ck_inventory_movements_delta_consistent` **查不出来**（流水行自身仍自洽）。把期望前值放进 WHERE 后失败是响亮的；语义上也更对——盘点是「我数出 N、系统当时是 M」，M 变了说明本次盘点已过期，应当重盘 |
| 2 | 单一入口 `receive()` | 拆为 `receivePurchase()` / `receiveReturn()` | 两者**权限要求不同**（前者需 cost_edit 双权限、后者不需）、**单价来源不同**（人工填 vs 系统带出）。合成一个入口会让权限判定依赖参数取值，是容易写错的形状 |
| 3 | 独立的 `ShopInventoryGuardTest` | 护栏并入 `InventoryMovementServiceTest` 末尾 5 条 | 与被守护的逻辑同文件，改坏时更难忽略；Story 1.3 的 `ShopSharedFileGuardTest` 独立成类反而产生了「以为查了其实没查」的盲区 |

#### 🔒 安全攸关点的落地方式

- **`locked <= actual` 不变式**：报损条件 `actual - locked >= qty`、盘点条件 `locked <= counted`，两者都在**单条 UPDATE 的 WHERE 里**判定行数，服务层不做任何预读判断
- **决策 S-3 的另一半**：并发报损 L1 用例（20 线程抢 5 件可售）加了**判别性断言** `unexpected == 0`，要求失败必须全部来自应用层条件，不得有请求越过它靠 DB CHECK 兜底 —— 沿用 Story 1.2 的教训，避免纵深防御制造假阳性绿灯
- **S-9 不允许留空**：应用层 `requireCost` + DB `ck_inventory_movements_inbound_required` 双层；无采购历史时**明确抛错**而非以 0 入库
- **进货单价不外泄**：审计详情只写数量与前后值（L0 有断言）；流水页无 `shop.cost_view` 时 `costByMovementId` **根本不进 model**
- **流水不可篡改**：仓储无任何 `@Modifying`/delete（L0 护栏断言）；实体全部字段 `updatable = false` 且无 setter（L0 反射断言）
