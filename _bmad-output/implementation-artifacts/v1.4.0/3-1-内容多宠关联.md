## Story

As a 多宠物用户,
I want 一条 Diary 关联多只宠物,
so that 同时记录几只宠物的时刻只需发一次。

## Acceptance Criteria

**AC1 — 迁移 `V20261018_1600__create_content_pets.sql`** `[L0]` `[L1]`（AD-10、§6.4）
1. 号已预分配，**不得另取**；提交前跑 `bash scripts/ci/check-flyway-versions.sh origin/main`。**不碰** `ck_notifications_type` / `ck_payment_intents_purpose`。
2. 建表（照 AD-10 原样，不加列）：
   ```sql
   CREATE TABLE content_pets (
       post_id        BIGINT NOT NULL REFERENCES content_posts (id) ON DELETE CASCADE,
       pet_profile_id BIGINT NOT NULL REFERENCES pet_profiles (id)  ON DELETE CASCADE,
       CONSTRAINT pk_content_pets PRIMARY KEY (post_id, pet_profile_id)
   );
   CREATE INDEX idx_content_pets_pet_post ON content_pets (pet_profile_id, post_id);
   ```
   两条外键**都要** `ON DELETE CASCADE`（AD-10）：删宠物 / 测试 `deleteAll` 不被它挡住（项目踩过的坑：新表 FK 无级联会阻断别处的删除）。
3. 回填存量：`INSERT INTO content_pets (post_id, pet_profile_id) SELECT id, pet_id FROM content_posts WHERE pet_id IS NOT NULL ON CONFLICT DO NOTHING;`——不过滤 `deleted_at` / `status`（软删帖的关联无害，读口自己会过滤），现状只有 `GROWTH_MOMENT` 有 `pet_id`（V86 列注释）。
4. 照 V86 惯例加 `COMMENT ON TABLE` / `COMMENT ON COLUMN`；文件头注释写清：表归属 ② 线、`content_posts.pet_id` 保留为「第一只关联宠物」兼容字段、新代码一律读本表。
5. **不删、不改** `idx_content_posts_pet_id`、`idx_content_posts_pet_recommend`、`idx_content_posts_pet_cover`（`V20260915_1727` 注释写明别处按 `pet_id` 精确查还在用）。

**AC2 — 领域与只读口** `[L0]`（AD-10 末段、PRD §6.3、CROSS-STORY ③ 依赖）

### 关键设计说明

- **为什么旧字段 `petId` 要兼容为 `[petId]`**：旧版 App（不强更，FR-145.7）与后台种子发帖（`AdminWebController`:575 → `publish`）都只传 `petId`。Epic AC「不带 petIds → 拒」按「`petIds` 与 `petId` 都没有」实现，否则旧版 App 发 Diary 全挂。
- **为什么非本人改 404**：NFR5 / §5「不属于本人的 petId 一律 404」。App 只会传自己的宠物，影响只在恶意 / 错误调用；后台种子靠 `.code(...)` 回显文案不变。
- **为什么不加 `position` 列**：AD-10 定了三列结构。「第一只」用宠物创建顺序确定性得出，F3 / F6 / `pet_id` / 事件同一口径，删宠后的「顺延」也天然一致。
- **为什么推荐池按关联表聚合**：PRD 影响面点名「宠物推荐等按 pet_id 的查询改走关联表」；不改的话 B 在多宠帖里永远不计数。
- 架构边界：content 只经 `PetQueryService` 读宠物名字头像（详情），物种解析器沿用既有的直读 `PetProfileRepository`（3.2 再动）。
