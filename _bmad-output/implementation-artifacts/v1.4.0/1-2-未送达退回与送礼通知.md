## Story

As a 送礼人 / 收礼宠物的主人,
I want 付款后无法送达时自动退回并告诉我原因；收到礼物时收到通知,
so that 钱不会白花，收礼也有提醒。

## Acceptance Criteria

**AC1 — 退回服务 `gift.service.GiftRefundService`** `[L0]` `[L1]`（AD-9、P-1）
1. `attempt(long giftOrderId)`：`@Transactional(propagation = REQUIRES_NEW)`。行锁读订单（`SELECT … FOR UPDATE`，仓储 `@Lock(PESSIMISTIC_WRITE)`）；`status != UNDELIVERED_REFUND_PENDING` → 直接返回（幂等）。
2. `wallet.credit(order.senderId, order.total, PawCoinTxnType.TOPUP, "GIFT_REFUND", order.id, GiftIdemKeys.refund(order.publicToken))`（`GIFT_REFUND:{orderToken}`）—— 总账走 `CASH_IN → FLOAT_LIABILITY`（P-1：这笔钱以 QRIS 现金进来，参照充值）。
3. 成功 → 同事务置 `UNDELIVERED_REFUNDED`、`refunded_at = now()`、`refund_error = null`，并 `publishEvent(new GiftRefundedEvent(giftOrderId))`（`gift.event`，过去式 record，本模块内部事件）。
4. 失败（`credit` 抛任何 `RuntimeException`）→ 本 REQUIRES_NEW 事务回滚；由调用方在**另一个** `REQUIRES_NEW` 方法 `recordFailure(giftOrderId, String errorClass)` 里：`refund_attempts += 1`、`refund_error = 异常简单类名`（≤ 64 字符，不存 message）；`refund_attempts >= 5` → 置 `REFUND_MANUAL`（后台 3.2 异常单显示「需人工」）。`recordFailure` 自身也只认 `UNDELIVERED_REFUND_PENDING`。
5. 退回幂等：同一订单无论被首次触发、重试任务、并发触发多少次，`pawcoin_transactions` 里 `ref_type = GIFT_REFUND, ref_id = 订单 id` 只有一条、余额只加一次（`credit` 的 `isReplay` + 行锁 + 状态守卫三重）。
6. 送礼人**无**送礼成长值：全程不发 `GiftSentEvent`（1.1 已保证），退回也不发任何成长值事件。

**AC2 — 首次退回触发 `gift.listener.GiftUndeliveredListener`** `[L0]` `[L1]`（AD-9）
1. `@TransactionalEventListener(phase = AFTER_COMMIT)` 监听 `GiftUndeliveredEvent` → `GiftRefundService.attempt(id)`；`catch (RuntimeException e)` → `recordFailure(id, e.getClass().getSimpleName())`，**再外层 catch 只记 `log.warn`（订单 id + 异常类名）不向上抛**（AFTER_COMMIT 里抛出会冒到网关回调的 HTTP 响应，触发无意义的回调重试）。
2. 为什么不在交付同事务里退：见 1.1 Dev Notes「偏离 / 补充架构 4」（`credit` 抛错会把 `applyCallback` 事务标成 rollback-only，到账回滚）。Completion Notes「待确认」记一句。

**AC3 — 重试任务 `gift.service.GiftRefundRetryJob`** `[L0]` `[L1]`（P-2）
1. `@Scheduled(fixedDelayString = "${petgo.gift.refund-retry-ms:600000}")`（每 10 分钟；写法照 `PaymentIntentExpiryScanner` / `ShopOrderExpiryScanner`，DB 状态机驱动，**禁 MQ / 延迟队列**）。
2. 每批最多 100 条：`status = UNDELIVERED_REFUND_PENDING AND refund_attempts < 5`，按 `id` 升序；逐笔 `attempt` / 失败 `recordFailure`，单笔失败不阻断批次；整批 `try/catch` 只记日志（笔数），不记 PII。
3. 第 5 次失败后置 `REFUND_MANUAL`，之后不再被扫到。
4. Given 退回时钱包写入失败，When 重试任务运行，Then 最多 5 次（含首次触发那一次），成功后补发退回通知；仍失败置 `REFUND_MANUAL`；退回幂等不重复入账。

**AC4 — 退回通知 `GIFT_UNDELIVERED_REFUND`** `[L0]` `[L1]`（AD-8、UI 稿 G3、PRD 异常情况）
1. `GiftNotifyListener.onRefunded(GiftRefundedEvent)`（`@TransactionalEventListener` AFTER_COMMIT，同步，写法照 `ContentNotifyListener`）读订单 → `notificationService.sendWithCopy(senderId, NotificationType.GIFT_UNDELIVERED_REFUND, "GIFT_UNDELIVERED_REFUND", args, title, body, orderToken)`：
   - `args = { petName（订单快照）, 金额（按收件人语言千分位：id「25.000」/ en「25,000」）, 原因文案 }`；
   - `title` / `body`：在本监听器里按 `accountQuery.localeOf(senderId)` 用同一组键渲染好再传入（`sendWithCopy` 把这两个参数落库为 title / body，推送也用同一键渲染 → 通知中心与推送同一句；App 2.2 对本类型读后端 title / body，见 Dev Notes「待确认 ②」）；
   - `targetRef` = 订单 `public_token`（深链送礼记录，2.2 / 2.3 用）；`deepLinkType` 由 `sendWithCopy` 置为 `GIFT_UNDELIVERED_REFUND`。
2. 原因文案（三种原因**同一句**，与 UI 稿 C9「拉黑场景同一句、不暴露拉黑关系」一致）：键 `notify.giftRefund.reason`。
3. 通知 / 推送失败不影响退回结果（退回已在前一事务提交）；监听器 catch 后只记 `log.warn`。
4. Given QRIS 发起后、付款前主人删除了宠物，When 付款成功，Then 不送达，送礼人钱包 +等额 PawCoin（流水 `type = TOPUP, ref_type = GIFT_REFUND`），收到说明原因的通知，无 `GiftSentEvent`、无送礼成长值，订单 `UNDELIVERED_REFUNDED`（AC10a）；付款期间送礼人拉黑主人（`SENDER_BLOCKED`）、主人注销（`OWNER_DELETED`）同理。

**AC5 — 收礼互动通知 `PET_GIFT_RECEIVED`：通知服务扩展** `[L0]` `[L1]`（AD-8、PRD FR-149.5 / AC16）
1. `NotificationService.INTERACTION_TYPES`（:46-47）**加入** `PET_GIFT_RECEIVED`（同一事实源会自动带到 `InteractionActorResolver.INTERACTION_TYPE_NAMES`、未读角标校准查询）；`fallbackTitle` 加 `case PET_GIFT_RECEIVED -> "有人给你的宠物送了礼物"`。
2. 新增公开方法 `sendGiftReceived(long recipientUserId, long actorUserId, long petId, String pushTitle)`（`@Transactional(propagation = REQUIRES_NEW)`，理由同 `send`）：
   - `aggregateKey = "GIFT:PET:" + petId`（≤ 64，列宽 `VARCHAR(64)`）、`targetRef = String.valueOf(petId)`（与访客路由 `/pets/:petId` 同口径，NotificationItem 类注释「id 寻址类」）、`commentId = null`、`variant = null`；
   - 走与 `sendInteraction` 相同的 upsert / `addActor` / 角标逻辑（**抽私有方法复用，`sendInteraction` 的签名与行为一字不变**）；
   - **与点赞的两处不同**：① 同一送礼人在未读期间再送（`addActor` 返回 false，即 T-29 分支）→ **照样 `touch` 刷新时间并推送**（每份礼物都有人花钱，PRD「推送每次都发」）；② 推送**不去抖**（`debounceKey("GIFT:PET:…")` 返回 null，现状 :294-305 只认两个前缀，**不改该方法**）。
   - 推送：提交后（`afterCommit`，与 `sendInteraction` 同写法）调 `pusher.pushToUser(recipient, pushTitle, "", "PET_GIFT_RECEIVED", token, targetRef)`；虚拟号 / 官方号不推（复用 `skipPushForVirtual` 与 `isOfficialAccount`）。`pushTitle` 由调用方按收件人语言渲染（单笔文案）；**不落库、不进日志**。
3. `InteractionCopyRenderer.title`（:109-126）加 `PET_GIFT_RECEIVED` 分支 —— 需要宠物名：新增重载 `title(NotificationType type, String variant, ActorSummary s, Locale locale, String petName)`，原 4 参方法委托它传 `null`（**既有四类行为不变**）；
   - `others == 0` → `notify.tpl.giftReceived.one`（`{0}` 昵称、`{1}` 宠物名）；`others > 0` → `notify.tpl.giftReceived.many`（`{0}` 昵称、`{1}` 其余人数、`{2}` 宠物名、`{3}` 总人数仍传入备用；zh 改用 `{1}`，见 T0）；
   - `petName == null`（宠物已删 / 查不到）→ `notify.tpl.giftReceived.one.noPet` / `.many.noPet`。
   - 新增 `giftPushTitle(String actorName, String giftLabel, String petName, Locale locale)` → `notify.tpl.giftReceived.push`（`giftLabel` = 数量 1 时礼物名、≥ 2 时「礼物名 ×N」，UI 稿 G4「N=1 时省略 ×1」）。
4. **通知列表取宠物名**：`NotificationCenterService.renderPage`（:203）对本页 `PET_GIFT_RECEIVED` 行的 `targetRef` 收集 petId，**一次**调新端口 `notify.port.NotificationPetNames.namesOf(Collection<Long> petIds) → Map<Long, String>`；`render`（:253-270）对该类型调 5 参 `title(…, petName)`。
   - 端口接口放 `notify.port`（提供方无关），实现 `gift.port.GiftNotificationPetNames`（`@Component`，逐个调 `GiftPetDirectory.pet`，一页 ≤ 20 行可接受；类注释写明对齐 4.1 时随端口换实现）；`NotificationCenterService` 以 `ObjectProvider<NotificationPetNames>` 注入，缺 bean（切片测试）时按 `noPet` 文案渲染，不报错。
   - **notify 模块不 import 任何 `gift.*` / `profile.*` 新类**。
5. 既有通知中心 `bodyDeleted` / 关注回关等逻辑不受影响；`PET_GIFT_RECEIVED` 条目 `body = null`。

**AC6 — 收礼监听 `gift.listener.GiftNotifyListener.onGiftSent`** `[L0]` `[L1]`（AD-8、PRD AC9 / AC16）
1. `@TransactionalEventListener`（AFTER_COMMIT，同步）监听地基 `GiftSentEvent`；按 `giftOrderId` 读订单（取礼物快照、数量、宠物名）。
2. **抑制**（照 `ContentNotifyListener.suppressed`（:69）的「压根不调 send」写法，**只在本监听器**）：`hideRelations.isHidden(receiverOwnerId, senderId)` 为 true → 不通知（不分来源：拉黑与举报隐藏都算）。`senderId == receiverOwnerId` 理论不会出现（1.1 已拒），防御性 return。
3. 渲染 `pushTitle`：`locale = accountQuery.localeOf(ownerId)`；礼物名按 locale 取订单快照 `gift_name_id`（`id`，含 null / 其它语言兜底）或 `gift_name_en`（`en`）；昵称取 `accountQuery.findActorViews(List.of(senderId))`，取不到（已注销 / 封号）→ 不推但仍落库（交给列表过滤）；调 `notificationService.sendGiftReceived(ownerId, senderId, petId, pushTitle)`。
4. 主人封号仍落库（恢复后可见）；推送是否送达交给推送通道现状。
5. 整个方法 `try/catch RuntimeException` → `log.warn`（订单 id + 异常类名），不向上抛。
6. Given 主人未读期间 3 人各送一次，When 查看通知中心，Then 只有一条合并通知（id：「Andi dan 2 lainnya mengirim hadiah untuk Mochi」），推送收到 3 次（单笔文案）（AC16）；已读后再收到新起一条；同一主人两只宠物按 `GIFT:PET:{petId}` 分开两条（多宠真实场景在 ② 合入后，本分支用两只 `pet_profiles` 行的测试夹具验）。
7. Given 主人拉黑了送礼人，When 送礼送达，Then 主人不收到通知（AC9），礼物照常送达（1.1）。
8. Given 同一人未读期间连送两次，When 第二次送达，Then 通知仍一条、`actorCount` 不变、时间刷新到最上、推送 2 次。
