## Story

As a 付费用户,
I want 每笔消费按实付金额返 EXP、退款时按比例扣回,
so that 付费也算在我的成长里，而且规则公平不重复。

**AC4 — 消费返验收** `[L0]` `[L1]`（PRD AC4 / AC5 / AC13）
- Given 用户用 PawCoin 充值，When 充值到账，Then 不产生任何成长值（AC4；`TOPUP` 是 `credit`，且 `PAWCOIN_TOPUP` 的 `PaymentIntentPaidEvent` 被过滤）。
- Given 用户用纯 PawCoin 买 KTP 高清（Rp20,000），When 扣币成功，Then `SPEND_DIGITAL` 入账 100；同一笔不会因 `IdHdPawcoinUnlockedEvent` 再算一次。
- Given 用户用 QRIS 买 Tailsonality 解锁，When 回调与轮询同时到达，Then 只入账一次（AC5；`applyCallback` 已有三道幂等闸，再加 `SPEND:PI:{intentId}` 兜底）；`KeepsakeUnlockedEvent` 不被计入。
- Given 用户用 MIXED（PawCoin + QRIS）支付 Toko 订单 Rp200,000，When 支付成功，Then 按订单只入账一次 `SPEND_SHOP` 100（AC4 / AC13）；币段 `debit` 与现金段都不再单独计。
- Given 支付用途为 `GIFT`，When 付款成功，Then 不走消费返（只走 Story 1.1 的送礼规则）。

**AC5 — 退款扣回监听 `GrowthRefundListener`** `[L0]` `[L1]`（AD-9）
1. 定位原消费流水：`paymentIntentId != null` 且 `purpose != SHOP_ORDER` → 原幂等键 `SPEND:PI:{paymentIntentId}`；否则按 `(ref_type = purpose.name(), ref_id = bizRefId)` 找 `rule_code IN (SPEND_DIGITAL, SPEND_SHOP)` 且 `delta > 0` 的那一条。找不到（当初未入账 / 档位 NONE）→ 不扣。
2. 扣回额 = `round(原入账 × refundAmount / originalAmount)`（`HALF_UP`）；调 `GrowthLedgerService.reverse(原幂等键, REFUND, sourceKey = "REFUND:" + refundKey, amountOverride = 扣回额)`——1.1 的 `reverse` 已保证**同一原流水累计扣回 ≤ 原入账**（截断）与幂等（`REV:{原id}:REFUND:{refundKey}`）。
3. `originalAmount ≤ 0` 或 `refundAmount ≤ 0` → 不扣，记 WARN（只记 refundKey / userId）。
4. 送礼不退款，无扣回。

**AC6 — 退款扣回验收** `[L0]` `[L1]`（PRD AC6 / AC13）
- Given Toko 订单 Rp200,000 已得 100，When 先退 Rp60,000、再退 Rp140,000，Then 依次扣回 30、70，共 100，不超扣（AC13）。
- Given 某笔消费全额退款，When 退款成功，Then 该笔消费的成长值全部扣回；累计跌破当前等级门槛时等级下降（AC6，降级由 Story 1.2 的 `GrowthLevelChangeHandler` 生效）。
- Given 同一笔退款事件重放，When 再次处理，Then 不重复扣（幂等键）。
- Given 原消费当初未入账，When 退款，Then 不扣。

### 问诊纯币的 ref 缺口（偏离架构 AD-8，需确认）

- AD-8 设想纯币消费一律经 `PawCoinSpentEvent`，`ref_id` 取「退款也拿得到的业务单号」。但问诊纯币 `debit` 的 `refId` 是 `consult_requests.id`（`ConsultPayService:130`），而该请求行在同一事务的 `buildOrderAndConvert` 里**被删除**（:224），`consult_orders` 也不存请求 id —— 退款侧（只拿得到 `ConsultOrder`）**无法反查**原消费流水。
- 本 story 默认做法：`GrowthSpendListener` 对 `PawCoinSpentEvent` **额外排除 `refType = VET_CONSULT`**；改由 `ConsultPayService.payByPawCoin` 在订单建好后发 `ConsultPaidByPawCoinEvent(userId, consultOrderId, amount)`，消费流水 ref = (`VET_CONSULT`, consultOrderId)。不改 `debit` 参数、不改支付顺序与 PawCoin 流水。
- 若产品 / 架构不接受新增该事件，替代方案是把问诊纯币的 `debit` 挪到建单之后、`refId` 改为订单 id —— 会改变 `pawcoin_transactions.ref_id` 的含义与扣币时机，**风险更高，未采用**。

### 咨询退款按全额

- 咨询退款（`refundToPawCoin` / `payoutRefund` / 问诊中断）在现有代码里都是整单退（`order.getAmount()` 或其净额），没有部分退款。`payoutRefund` 打出的是 `r.getNetAmount()`（扣手续费后的净额），但对用户而言是「这单退了」，按 `refundAmount = originalAmount = order.getAmount()` 全额扣回，避免因手续费残留零头 EXP。Completion Notes 记一句。

### 电商实付总额

- `paidTotal` = `coinAmount`（null 记 0）+ `cashAmount`（null 记 0）；纯现金单 `coinAmount` 为 0 / null。写 L0 断言它与 `order.getTotalAmount()` 相等（`totalAmount = goodsSubtotal + shippingFee + shippingDiscount`，`ShopOrder.java:195`）；若有不等的单据形态（如运费减免另记），以 `coin + cash` 为准并在 Completion Notes 说明。
- 退款的 `originalAmount` 取同一口径（订单实付总额）。
- 电商异常单整单取消的**现金段**「走 Epic 5 打款」，当前代码没有现金段退款成功的落点 → 本 story 只能扣回币段对应的 EXP。现金段的打款落点出现时须补发 `RefundSucceededEvent`（Completion Notes 记为已知缺口）。

### 架构约束

- AD-8：一笔消费只算一次；MIXED 只经 `ShopOrderPaidEvent`；Keepsake / KTP 业务事件不监听；未登记用途按 DIGITAL。
- AD-9：扣回 = 按比例 HALF_UP；同一原流水累计 ≤ 原入账；幂等；五处发布（P-3 / P-4）。
- §5.2：新幂等键只加在 `GrowthIdemKeys`。§5.3：`BigDecimal` + `HALF_UP`；1 PawCoin = Rp1。§5.4：只有 `GrowthLedgerService` 写成长值。
- 支付护栏：新发布点只在原 `@Transactional` 方法内 `publishEvent`，**不新开事务、不吞支付异常、不改返回值**；日志不记金额以外的 PII（收款账号、姓名绝不入日志）。
- `ck_payment_intents_purpose` 不改（地基已含 `GIFT` / `PET_SLOT_RENT`）。

### 与前后 story 的边界（本 story 不做）

- 依赖 1.1 的 `accrue / reverse` 与 1.2 的降级，**不重写**入账 / 定级逻辑。
- 不做后台「消费换算」页签与锁定行只读（Story 4.1，`growth_spend_tiers.locked` 本 story 只 seed）。
- 不做接口（Story 1.4 的明细里 `SPEND_*` 行的 `detail` 读本 story 写的 `ref_type`）、App（1.5）。
- 不实现 ② 的月租、③ 的送礼支付；只在口径表写明它们须遵守的 refType 约定。
