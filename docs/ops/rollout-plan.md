> 把已经写完的四块东西真正跑进日常运营。逐条可勾选。
> 配套：`retention-push-copy-matrix.md`（文案与召回可达性）、`seed-content-30d-plan.md`（内容）、

## 0. 决定顺序的三个约束（先读，否则会按错顺序做）

**① App 必须先发版，再开推送开关。**
深链映射写在客户端（`deep_link_routes.dart`），后端推送只带 `type + variant`，
而后端**不知道收件人的 App 版本**（`users` 表没有版本字段，无法按版本定向投递）。
老版本收到 `LIFECYCLE_*` 推送 → 推送照常显示，但**点击落通知中心，不是建档页**。
「深链直达建档」是这套东西的全部转化点，落错页等于白推。
→ 顺序只能是：**发版 → 等升级占比 → 才开开关**。

**② 后端开关默认关，且要按天放量。**
迁移把存量用户的 `last_active_at` 回填成 `updated_at`，开关一开会有一大批人
同时命中「7 天未回」。`LIFECYCLE_PUSH_DAILY_CAP` 是这里唯一的安全阀。
一次放开的代价不是「效果差」，是**用户关掉推送权限**——那不可逆。

**③ 手册要求先人工跑 2 周把阈值跑准，再自动化。**
`scripts/ops/thresholds.json` 里标 `guess` 的都是拍脑袋的。
跳过这两周直接交给 agent，agent 只会自动化地犯错。

## 阶段 0 · 本周就能做（**不依赖任何代码上线**）

这四件事今天就能启动，和发版完全并行。手册第三章「本周三件事」有两件在这里。

### 0.1 让体检脚本先跑起来，建立基线 🔴 最先做

没有基线，两周后你无法判断阈值该往哪边挪。

- [ ] 去 PostHog → Settings → **Personal API keys** → 建一个只读 key（Query Read 权限即可）
- [ ] `export POSTHOG_PERSONAL_API_KEY=phx_...`（**绝不写进任何文件、不进仓库**）
- [ ] 先看它要查什么，不需要 key：`python3 scripts/ops/daily-health-check.py --dry-run`
- [ ] 正式跑：`python3 scripts/ops/daily-health-check.py --out ~/tailtopia-health/$(date +%F).md`
- [ ] **补跑过去 14 天**，一次性建立基线：
      `for d in $(seq 1 14); do python3 scripts/ops/daily-health-check.py --date $(date -v-${d}d +%F) --out ~/tailtopia-health/$(date -v-${d}d +%F).md; done`
- [ ] 把这 14 天的 D1 / DAU / 无人接单 / Feed 新内容抄进 `daily-weekly-sop.md` 的《阈值校准记录》

> 脚本**只读、只诊断、不执行任何动作**——不发推送、不改投放、不写库。可以放心跑。

### 0.2 强制升级（一条 env，同时解决两个问题）

这一步既是手册第三章第 1 件事（召回 1.1.0）的**可行手段**，
又是阶段 1「等升级占比」的**加速器**——一箭双雕，所以排在这么前面。

- [ ] 生产 env 设 `APP_MIN_SUPPORTED_VERSION=1.1.6`（现为默认 `1.0.0`）
- [ ] 同步更新 `APP_LATEST_VERSION` 到当前发布版本
- [ ] 确认 `APP_ANDROID_STORE_URL` 已配（留空的话用户点了没反应）
- [ ] 验证：用旧版本 App 打开，应命中强制更新提示

> ⚠️ 这条**不要**在新 APK 上架之前做，否则用户被要求升级却没有可升的版本。
> 正确时点：新版本在商店上架**之后**立刻做。

### 0.3 1.1.0 残留的再营销受众（push 到不了他们）

推送绑 IM 账号 `u_{userId}`，未注册就没有通道，而 v1.1.0 的 473 人里**只有 1 人注册过**。
详见 `retention-push-copy-matrix.md` §0 / §4。

- [ ] AppsFlyer / TikTok Ads 里建自定义受众：**已安装 & 未完成注册**
- [ ] 素材单一诉求：`Profil anabulmu belum jadi — 30 detik`，落地页直达建档深链
- [ ] 前置：TikTok 优化目标从「安装」切到「注册」（AEO）——手册第三章第 2 件事
- [ ] 同步把投放压到 30%（8/14 起的付费 cohort D1 反而更低，买到的是低意向装机）

### 0.4 种子内容开跑（后台工具已就绪，不用等任何东西）

- [ ] 确认有可用的**虚拟账号**（需 `VIRTUAL` 且 enabled）
- [ ] 按 `seed-content-30d-plan.md` 的配比开始每天 5 条（日常 3 + 科普 1 + 钩子 1）
- [ ] 🔴 **科普必须走 `/admin/seed-post` 单条发布并选 `KNOWLEDGE`**——
      批量工具硬编码 `DAILY`，科普走批量会被记成日常，「科普内容数」永远是 0
- [ ] 发布时段集中 **18:00–20:00 WIB**，与后续的推送时段（19:00 WIB）对齐

**阶段 0 的验收门**：体检脚本能跑出报告 + 连续 3 天 Feed 新内容 ≥ 5 条。

## 阶段 2 · 放量（新版本占比够了才开）

### 2.1 先看升级占比，别急着开

老版本收到推送 = 深链落错页。等占比上来再开，是这套东西唯一的正确用法。

- [ ] 在 PostHog 按 `$app_version` 拆 DAU，看新版本占比
- [ ] **占比 ≥ 70% 之前不开开关**（阈值可议，但别低于 50%）
- [ ] 强制升级（0.2）会大幅加速这个过程

### 2.2 三档放量，每档 3 天

| 档 | env | 观察 |
|---|---|---|
| 第 1 档 | `ENABLED=true` + `DAILY_CAP=50` | 召回漏斗（送达/点击/建档）、有没有推送权限关闭的迹象 |
| 第 2 档 | `DAILY_CAP=100` | 同上，且 D1 有没有动 |
| 第 3 档 | `DAILY_CAP=200` | 同上 |

- [ ] 每档跑满 3 天、漏斗不劣化，才抬下一档
- [ ] 每天看日志那一行：`planned` 与 `dispatched` 的差 = 被上限压住、明天补的量
- [ ] 召回漏斗取数用体检报告末尾给的 SQL（`lifecycle_push_marks` + `notifications`）

**回滚**：任何一档出问题，`LIFECYCLE_PUSH_ENABLED=false` 重启即停。
去重表 `lifecycle_push_marks` 保证已推过的人不会因为重开而被重复打扰。

## 阶段 3 · 跑阈值的那两周（手册第五章第 1 步）

- [ ] 每天跑体检脚本 + 在《阈值校准记录》补一行
- [ ] **「判定对不对」这一列必须填**——`准` / `虚警` / `漏报`。这是整张表的全部价值
- [ ] 两周后：`虚警` 多的阈值放宽，`漏报` 多的收紧，改 `scripts/ops/thresholds.json` 的 `value`，
      并把 `confidence` 从 `guess` 升上去
- [ ] 同期跑第一轮文案 A/B（备选臂见 `retention-push-copy-matrix.md` §2）
  - [ ] 一次只换一层、只换一个变量
  - [ ] 看的是**点击→建档/发布**，不是点击率（点击率高但不建档的文案是骗点击，比不发更糟）

**阶段 3 的验收门**：每个阈值都有两周实测支撑，`guess` 清零。

## 阶段 4 · 交给 agent（手册第五章第 3 步）

| 交不交 | 动作 | 理由 |
|---|---|---|
| ✅ 先交 | 种子内容**生产**（选题/写稿/出 Excel） | 可逆、低风险，发错能下架 |
| ✅ 先交 | push 文案 A/B 的**方案生成** | 只出方案，按不按下由人决定 |
| ✅ 先交 | 每日体检**跑数 + 出诊断** | 脚本已经只读，天然安全 |
| ⏸️ 后交 | 召回 push 的**发送节奏调整** | 有引擎 + 上限兜底，但放量判断仍归人 |
| ⏸️ 后交 | 投放调整 | 涉及预算 |
| ❌ 不交 | 兽医供给调度 | 涉及人 |
| ❌ 不交 | 内容举报处置 | 涉及社区规则与用户申诉 |
