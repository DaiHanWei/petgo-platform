# Runbook — 售后处理流程（V1.3.0）

> **写给运营看的，不假设你懂代码。**
> 适用版本：**V1.3.0**。依据：决策 **SD-2**（拒收 / 发货前取消一律无额外补偿）、**SD-5**（退货退款整体留到下一版）、
> **SD-13**（本版靠后台配置置 0 兜底，不改代码）。
> 上一次核对代码：2026-09-16。

---

## 0. 一句话背景

V1.3.0 把 **App 里的退货入口整个隐藏了**（Story 2-1）。但：

- **后端退货接口没关**，运营后台的退货队列 `/admin/shop/returns` **照常能用**；
- **老版本 App 的用户仍然能提交退货单**，它们会照常出现在你的队列里；
- 所以本版不是「没有售后」，而是「**售后从 App 自助改成走你和客服**」。

这份文档就是告诉你：用户来找你的时候，**点哪里、系统会自动做什么、哪一部分必须你线下做、留痕留在哪**。

### 🔴 本版最重要的一条规矩

> **拒收、发货前取消，一律只退应退金额，没有任何额外补偿。**（SD-2）

审批和沟通时**不要口头承诺补偿**，也不要承诺「转成 PawCoin 会多给一点」——
那个激励在本版已经被配置置 0，答应了也发不出来，最后是你去圆场。

## 1. 场景一：**待发货**，用户要取消

### 在哪里

后台 → **`/admin/shop/order-exceptions`**（异常订单处理）→ 找到该订单 → 点 **「整单取消」**。
需要**填写原因**，不填提交不了。原因会进审计日志，也会出现在发给用户的站内信里，**请写人话**。

### ⚠️ 动手之前，先做这一步

**先确认这张订单里的每一个商品都登记过采购入库。**

没登记过会直接报错、**整笔回滚**（订单没取消、币没退、库存没回补，什么都没发生），报错原文逐字是：

```
该 SKU 尚无采购入库记录，取不到进货单价，无法登记退货入库。请先登记一次采购入库（0 成本入库会让毛利核算失真）
```

还有一种相邻的报错，原因相同（这个 SKU 连库存行都还没建）：

```
库存记录不存在，无法入库
```

**规避办法（两步）**：

1. 去 **`/admin/shop/inventory`** 给该商品**登记一次采购入库**（它会同时把库存行建出来）；
2. 回到 `/admin/shop/order-exceptions` 重新点「整单取消」，这次就会成功。

> 为什么会这样：取消订单时系统要把货**退回库存**，而入库必须有单价，单价取的是「该商品最近一次采购价」。
> 从来没采购入库过 ⇒ 取不到价 ⇒ 系统宁可报错也不肯按 0 成本入库（那会让毛利报表失真）。

### 点下去之后，系统**自动**做这些

1. **库存回补** —— 货退回可售库存（走退货入库批次，采购单号填原订单号）
2. **PawCoin 段全额退回用户钱包** —— 用户下单时抵扣的币，原路退回
3. **订单转为「已取消」**
4. **发一条站内信给用户**，内容是「订单无法履约，已取消并安排退款」+ 你填的原因
5. 写审计日志

### 🔴 系统**不会**自动做的：现金段打款

**现金部分不会自动退给用户。** 系统只算出一个「待退现金」的数字给你看，**钱要你线下转**。

所以完整流程是：

1. 后台点「整单取消」→ 记下它显示的**待退现金金额**
2. **线下转账**给用户（走公司既定的转账流程）
3. 回到该用户的**工单内部备注**里写清楚：**退了多少、转到哪个账号、经办人是谁、什么时候转的**

> ⚠️ 第 3 步不是形式主义。系统里没有这笔转账的记录，**工单备注是唯一的凭证**，
> 用户事后说没收到钱时，只有它能说明情况。

### 🔴 关于补偿

「整单取消」这条路**本版不会发补偿**（平台责任补偿比例已确认为 0）。
你在页面上看到的补偿金额应该恒为 0；**如果不是 0，先停下来找技术**，不要继续操作。

## 2. 场景二：**已发货 / 已送达 / 已完成**，用户要退款

### 🔴 先说结论：**后台没有「代用户发起退货」的入口**

退货队列 `/admin/shop/returns` 只能处理**用户自己提交的**退货单。
后台这一整套端点里**没有 create / submit 这一类**，你找不到「帮他建一个退货单」的按钮 —— 不是你没找到，是确实没有。

**也不要试图用场景一的「整单取消」来处理已发货订单** —— 系统会拦下来，因为货已经出去了。

### 所以这类只能走线下

| 要退的东西 | 怎么办 |
|---|---|
| **现金部分** | 线下转账 |
| **PawCoin 部分** | 后台 **`/admin/users/{用户 id}`** → **「赠送 PawCoin」**，人工调账（需要 `user.grant_pawcoin` 权限，没有的话找管理员开） |

### 留痕（必做）

在**工单内部备注**里写清四件事：

1. **金额**（现金多少、PawCoin 多少，分开写）
2. **去向**（转到哪个账号 / 调账给哪个用户 id）
3. **经办人**
4. **原因**（对应哪张订单、什么问题）

> 同样，系统里没有这笔账的自动记录，备注就是凭证。

## 3. 场景三：**老版本 App 提交上来的退货单**

它们会照常出现在 **`/admin/shop/returns`** 队列里。按电商一期的既有流程走：

```
批准(approve) → 代填寄回单号(shipback) → 收到货后验收(inspect-pass / inspect-fail) → 执行退款(refund)
```

### 🔴 执行退款前，先确认「用户已选好现金退回方式」

否则点「执行退款」会被系统挡下来，报错原文是：

```
用户尚未选择现金段退回方式，暂不能执行退款
```

**为什么会没选**：选退款方式那一屏，在 App 里**只能从「提交退货」之后的流程进去**。
V1.3.0 把退货入口隐藏后，**新版本 App 的用户根本走不到那一屏**。
老版本用户如果当初没选过，你在后台也没法替他选。

**遇到就转线下**：线下问清楚用户要退到哪里 → 线下转账 → **工单备注留痕**（金额 / 去向 / 经办人）。

### 🔴 审批时不要承诺补偿

本版**没有额外补偿**（SD-2）。
「转成 PawCoin 可以多给一点」这种话**不要说** —— 那个激励已经配置为 0，说了也发不出来。

### 另外两个会卡住你的点

- **用户无处登记寄回单号**：退款会停在「等待寄回」。运营后台有**代填入口**（`shipback`），你替他填。
- **退货收件地址没配置时，批准退货不会有任何提示**：批了之后用户不知道往哪寄。**批准前先确认收件地址配好了。**

## 4. 本版已知问题速查

以下是 V1.3.0 **已知**、且**与你日常直接相关**的问题。碰到了不用慌，也不用每次找技术确认 —— 这里有就是已知的。

| # | 现象 | 怎么办 |
|---|---|---|
| 2 | **从未登记过采购入库的商品**，发货前取消 / 退款会执行失败并整笔回滚 | 先在 `/admin/shop/inventory` 登记一次采购入库，再重试（详见 §1） |
| 3 | **「不可退」商品**的待发货取消与拒收**会被系统拒绝** | 货还没到用户手里是否适用退货规则，尚未拍板 → 转线下处理并留痕 |
| 4 | **「已送达、未确认收货」**的订单：后端允许申请退货，但 App 只给「确认收货」按钮 | 口径不一致，以后端为准；用户来问就走线下 |
| 5 | **「自助取消」实际仍需你手动批准、再手动执行退款**，没有自动路径 | 当成普通工单处理，别等系统自己走完 |
| 6 | **执行退款要求用户已选退款去向**，而退款方式页只能从 App 提交退货后进入 | 未选的一律转线下（详见 §3） |
| 7 | **退货批准后用户无处登记寄回单号**，退款会停在「等待寄回」 | 用后台的代填入口替他填 |
| 8 | **退货收件地址未配置时，批准退货没有任何提示** | 批准前先确认地址已配置 |
| 10 | **后台没有代用户发起退货的入口** | 不是你没找到，确实没有 → 走线下（详见 §2） |

## 5. 🔴 下一版恢复退货之前，必须做的事

本版为了让「不发补偿」成立，把补偿相关配置**置 0 / 核实为 0**了。
**下一版恢复退货时，这几项必须按规则重新配置，否则该发的补偿也发不出来。**

| 配置项 | 本版状态 | 恢复时 |
|---|---|---|
| 转 PawCoin 激励比例（`premiumRate`） | 置 0 | 按规则重配 |
| 转 PawCoin 激励固定额（`premiumFixed`） | 置 0 —— **这一项是加法，只把比例置 0 不够** | 按规则重配 |
| 平台责任补偿比例 | 核实为 0 | 按规则重配 |
| 平台责任补偿上限 | 核实为 0 | 按规则重配 |

⚠️ **平台责任补偿的两项目前后台没有配置页面**，恢复时需要技术一并补上。

⚠️ **「平台责任补偿」与「转 PawCoin 激励」是两个独立配置项，不得合并成一个数值** ——
合并会静默破坏售后成本口径与资金归因。

---

## 6. 不确定就找谁

- **后台点不动 / 报错看不懂** → 技术对接人（Dai）
- **该不该给补偿、给多少** → 产品（本版规则是「不给」，要破例必须产品拍板并留痕）
- **权限不够（比如没有「赠送 PawCoin」）** → 后台管理员开权限

> 🔴 **任何时候都不要自己在数据库里改数字。** 后台页面那条路会自动留审计；直接改库不会，
> 出了问题谁都查不出来发生过什么。
